# Consumer tests — proving the checker is *consumable*, not only correct

Everything under [`../src`](../src) tests the checker from inside Kotlin, where the code under test is on the compile classpath by construction. That says nothing about whether a developer can install the package and call it — and **the two have failed independently here**: the JS target compiled green for the module's whole life while emitting nothing importable, because `binaries.library()` was missing. A test that imported a relative path into `build/` would not have caught that either.

So every project here **packs a real npm tarball, installs it into a throwaway project, and imports it by package name**. That is the only arrangement that exercises the resolution a consumer actually performs.

| project | host | what only this arm can establish |
|---|---|---|
| [`node/`](node) | plain Node, no bundler | that `npm install` + `import` works at all; the CI-gate example; the cold, prepared, after-edit and retained-memory boundaries on a host with a real heap API |
| [`browser/`](browser) | real system Chrome, Vite-bundled | that the package survives bundling and runs in a browser — where `jsdom` and Karma would test the compiler's output instead of the packed artifact |
| [`shared/`](shared) | neither — it is the corpus both hosts replay | that "the same cases" is *structural* rather than a promise, and that the JVM, Node and browser arms agree on the **full** report contract |

**The shared tree is why a divergence between hosts is a test failure rather than a surprise.** Each host used to carry its own hand-written case floor (`outcomes.length >= 18`), which had to be bumped in two files whenever a case was added — a maintenance defect paid for three times. The suites are now data, so a host runs them without knowing how many cases any of them has.

## Running them

From the repository root, through [`../../build.sh`](../../build.sh):

```sh
./build.sh :consistency:nodeConsumerTest      # needs node + npm
./build.sh :consistency:browserConsumerTest   # needs pnpm + a system Chrome
```

**Both are deliberately off `check`.** They need tooling a JVM lane should not require, and a lane that silently demanded node would fail on machines where the rest of the build is fine. `:consistency:nodeConsumerTest` runs in push CI by name; the browser arm is local and release-gated. Neither reaches the network: the packed package declares no runtime dependency and the Node consumer project declares none either, so `npm install <tarball>` resolves entirely from disk.

The parity corpus is regenerated by a task, never by hand — `./build.sh :consistency:syncCheckerParityCorpus` packs and installs first, so the corpus is written by the artifact a consumer receives. See [`shared/parity/README.md`](shared/parity/README.md).
