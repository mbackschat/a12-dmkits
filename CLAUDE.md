# a12-dmkits — project instructions

Design and rationale live under [`docs/`](docs/) — **[`docs/README.md`](docs/README.md) indexes every document** (the proposal, the kernel findings/notes, the CI-locked MVK ledger, the API/DSL/grammar surveys, the corpus analysis, and the API experience study). Read it to find the right doc; the conventions below stay here.

## Language

English is the project default: code, identifiers, comments, docs, and the **default render target** (`DslRenderer` defaults to `ConditionLanguage.EN`) are English. **German is a supported render target, not the default** — the operator catalog carries verified `de` keywords and `new DslRenderer(ConditionLanguage.DE)` renders to it. Translations are welcome; English stays canonical.

## Self-explaining surface (standing requirement, 2026-06-05)

**Favor a self-explaining, explorable CLI over relying on the N1 skill.** A cold LLM agent — given only the binary — must be able to discover the verbs, their parameters, and what they mean, and to learn each output's shape, *without* the skill. The skill (`skill/SKILL.md`) is the material-under-test for the N6 eval and **must stay as simple as possible**; it teaches judgment (polarity, the traps), not the verb/parameter catalog the tool should describe about itself. So when adding or changing a verb: make it discoverable (help/usage + a machine-readable manifest) and schema-describe its I/O. Discoverability lives in the *tool*, not the skill. Detail + rationale: [`docs/CLI-SPEC.md`](docs/CLI-SPEC.md).

## Test & sample document models

- **Research freely; commit only own-domain re-expressions.** All three sources — **`a12-kernel-demo`**, the **A12 Tools workspaces** (`/Volumes/Buffer/Apps/A12 Tools/A12 Tools - 2025.06-ext5/workspaces`, the 2025.06-ext5 distribution = kernel `30.8.1`, our pin), and **`a12-kernel-mm`** — may be read and studied without limit. What gets **committed** must be our own original fixtures.
- **The license-safe rule: copy the *mechanism*, never the *expression*.** You may reproduce an abstract pattern (the includes/`modelAlias` scheme, an operator-usage shape, a rule skeleton) and re-express it in a **wholly different, coherent domain** with **our own field names, business content, and rule text**. You may **not** commit a source model's domain/fields/rules/text verbatim or lightly renamed. Mechanisms/ideas aren't protected; their concrete expression is — so a genuine domain change keeps committed fixtures clear of `a12-kernel-mm`'s **EUPL-1.2** copyleft and the **proprietary** A12 Tools licensing. When unsure, transform more, not less. Everything committed **must make sense**: realistic domain, field names, types, plausible rules; no nonsense placeholders.
- **`a12-kernel-demo` is the easy case** — it's the demo; copying/adapting its example models directly is fine.
- The earlier `a12-kernel-mm` **reference-only, opt-in integration test** path (sibling clone `../a12-kernel-mm`, env-overridable, skipped if absent) remains available for tests that *read* the real models without committing them. (§19 license decision before first publish should still confirm fixture provenance.)

## Coding style — make full use of Java 21

Write idiomatic modern Java 21, not Java 8 with newer syntax:
- **Records** for immutable data (AST nodes, value objects, results). **Sealed interfaces + exhaustive pattern-matching `switch`** for closed hierarchies — model the AST this way and let the renderer/visitors dispatch with a switch that the compiler proves exhaustive (no `default`). See proposal §18.5.
- Record/`instanceof` **deconstruction patterns**, `var` for obvious locals, **text blocks** for multi-line strings (DM-JSON fixtures, expected output), enhanced `switch` expressions, `Optional` over nulls in APIs, `List.of`/`List.copyOf` for immutability.
- Prefer making illegal states unrepresentable in the type system over runtime checks — that is the whole point of the typed builder.
- **Javadoc `*/` trap:** never write a literal `*/` inside a Javadoc block comment — most often a wildcard path in `{@code …}` like `Group*/field` — it ends the comment early and breaks compilation. Reword (e.g. "the flatten of `Group*` then `field`", or a space: `Group* / field`). This recurs whenever documenting repetition-list syntax.

## Documentation discipline

- **Every non-obvious finding gets written down under `docs/`** — kernel/build/environment facts default to [`docs/KERNEL-INTEGRATION-NOTES.md`](docs/KERNEL-INTEGRATION-NOTES.md); design decisions to [`docs/PROJECT-PROPOSAL.md`](docs/PROJECT-PROPOSAL.md). If a finding doesn't fit an existing doc's scope, **propose a new doc** rather than overloading one.
- **`../a12-kernel-demo/KERNEL-SEMANTICS.md` is the canonical kernel-truth reference — consult-only** (owner policy, 2026-06-04). Before each increment, read the relevant section (truth values, null semantics, formal errors, decimals, dates, enums, iteration, paths, computations, messages). **Do not write to it.** Kernel-behavior findings it *lacks* go to our own [`docs/KERNEL-FINDINGS.md`](docs/KERNEL-FINDINGS.md) (section-numbered to mirror KERNEL-SEMANTICS for easy upstreaming; every entry experiment-verified and test-locked); rulekit's *treatment* of each fact stays in `KERNEL-INTEGRATION-NOTES.md`.
- **Anti-whack-a-mole: mine constraints proactively, don't trip over them** (owner direction, 2026-06-04). Structural laws live in enumerable sources — sweep them instead of discovering by accident: **(1)** slot parity vs the public `IRule`/`IComputation` accessors (every accessor = supported or explicitly deferred); **(2)** the **MVK ledger** — every `MVK_*` code classified (erased-by-types / pre-checked / kernel-delegated / pending / unknown→experiment queue), CI-checked; **(3)** the `../a12-kernel-mm` metamodels as the **source of truth for valid DM structure** (schema oracle: `MM_*`/`CT_MODEL_HEADER` define the slots; constraint oracle: their rules encode validity laws — read-only, own-words analysis only, EUPL); **(4)** deserializer/serializer-tier checks (constraints that fire before `checkConsistency`): the write gate is `BasicConsistencyCheck` (run by `serialize()`, aborts on ERROR), its `BasicDocumentModelConsistencyCategory` enum (16 categories) the F6 output contract — every category classified (pre-checked by an authoring builder / n/a-structural), reflectively CI-locked; the deserialize tier (Jackson: locale format, type discriminators) documented in `KERNEL-FINDINGS.md`. **(5)** the parsetree-api construct-name enums as the **operator inventory** (reverse parity: every member cataloged or explicitly excluded — `adapter.KernelConstructParityTest`), catching operators the kernel *adds*. **When the kernel (or `a12-kernel-mm`) changes, follow [`docs/KERNEL-UPGRADE.md`](docs/KERNEL-UPGRADE.md)** — the coupling map (each guardian ↔ what its failure means ↔ the realignment), the bump procedure, and the dry-run negative-controls. Guiding split (F11): quiet tolerance at runtime, loud detection at build.
- A finding is only "done" when it's documented. When a new fact **contradicts** an existing note, update that note — don't leave stale claims.
- **After any substantive change, state which docs need updating** (proposal / notes / README status / this file) and update them in the same change.
- **Write docs like a human, not a changelog.** This holds for *all* docs — README, the proposal, the specs, the findings/notes. Favor a clear, scannable voice: avoid long paragraphs that string facts together with semicolons or em-dash chains — break them into **lists or tables**. `README.md` is the strictest case (it's the first doc a newcomer reads, so keep it a snapshot that points at the canonical docs rather than restating them), but the same readability bar applies everywhere prose is meant to be *read*. The one exception is the **special sections an agent maintains for status or plan tracking** — the canonical §9 status board, the MVK ledger, and similar structured trackers — where a terse, regular, machine-checkable shape is the point; leave those dense.
- **Reach for visuals when they out-scan prose — tables and diagrams, not walls of text.** If you'd sketch a box-and-arrow or jot a table while *explaining* something live, put that in the doc — don't transcribe it back into paragraphs. Use a **table** for comparisons, matrices, or parallel-structured facts (options × criteria, param × meaning, boundary × payload, who-builds-what × when); use an **ASCII diagram** (or mermaid where the surface renders it) for layering, data flow, topology, or state — the things a reader pictures spatially. Keep prose for the **rationale/argument** (the *why*), which doesn't tabulate. The bar: a visual must out-scan the paragraph it replaces and stay maintainable (ASCII travels everywhere and doesn't rot; don't hand-draw something fragile). Applies to all user-facing docs (README strictest). Reference example: [`docs/EVAL-SPEC.md`](docs/EVAL-SPEC.md) §8c — a layer diagram + boundary/parameter tables instead of three prose paragraphs.
- **Formalization discipline: match the representation to the knowledge kind, and formalize only when a consumer exists** (decided 2026-06-05). The document-model knowhow isn't homogeneous — don't ask "prose vs formal," ask *what representation per kind*: operator/structural **vocabulary** → a self-verifying machine-readable catalog (the `operators.json`/`OperatorCatalog` model, served via the CLI); **structural validity** → derive from the kernel's own oracles (MM_ metamodels / `BasicConsistencyCheck`) and make illegal states unrepresentable in the typed builder; **behavioral semantics** (empty-as-0, polarity, path walk-up) → *executable runtime laws* (`adapter/.../laws/…LawsTest` via the `RuntimeLaws` oracle — fires/does-not-fire on real data; distinct from the accept/reject `validate/laws/`) that the build can't let go stale; **rationale/the *why*** → stays prose (it doesn't tabulate). The governing test before formalizing any fact: **a consumer must exist** (the tool, the LLM, or a CI gate) — formalization that only feeds other formalization is cost without payoff and rots worse than prose. Full reasoning, the five options with trade-offs, and the per-kind gradient: [`docs/MODELKIT-PROPOSAL.md`](docs/MODELKIT-PROPOSAL.md) §B/§D.
- **Specs hold the stable method; measured results live in a dated log.** Keep time-stamped, churny *results* out of spec docs — a spec is the fixed contract (method, scoring, task definitions), not a changelog of runs. Eval/benchmark results go in **[`eval/RESULTS.md`](eval/RESULTS.md)** (dated + time-of-day, newest first — we run several a day); `docs/EVAL-SPEC.md` just points to it. `eval/RESULTS.md` lives outside `docs/`, so it's indexed from both `docs/README.md` and here rather than only the docs index.
- **Docs travel inside the feature commit, never after it.** Before committing a feature: update the affected docs — flip the row in the **canonical §9 status board** (`docs/API-POC-STUDY.md`) and make its snippet real, add any kernel-fact note, mark the corpus backlog — and **sweep the touched docs for stale claims**, then commit code + docs together. Status lives on the board, not scattered across README/proposal/this file (README is the outside snapshot, the proposal is intent). No separate "docs: refresh" commits trailing a feature.
- **[`docs/API-POC-STUDY.md`](docs/API-POC-STUDY.md) is a living study & review surface and holds the canonical §9 implementation-status board — keep it current.** When a feature lands, flip its §9 row and study snippet from 🔮 to ✅ and make the snippet real (test-backed where possible); when an interesting usage, idiom, or combinator pattern emerges (in tests, fixtures, or discussion), **showcase it there**. New ergonomic observations go into its numbered findings list — that list feeds the next increments. It is also the seed material for the LLM skill (N1) and the self-sufficiency eval (N6).
- **Doc evolution: the proposal stays whole; specs split out on implementation boundaries** (decided 2026-06-03). Don't split `PROJECT-PROPOSAL.md` into per-section files — it's one argument, densely cross-referenced by stable anchors (`§N`, `Fn`/`Nn`/`Dn`, forks Q1–Q12). Instead, when a component's design detail outgrows its proposal section during implementation, extract a **component spec** (e.g. `docs/CATALOG-SPEC.md`, `docs/ADAPTER-SPEC.md`, `docs/AST-SPEC.md`): the spec supersedes the section's *detail*, and the proposal section shrinks to intent + a pointer. Revisit a wholesale split only if the proposal exceeds ~800 lines despite spec extraction.

## Testing strategy

- **Example-based TDD is the primary spec** (red/green) — readable, intent-revealing tests drive each feature.
- **The real kernel is the oracle.** `RuleValidator` + `checkConsistency` confirm that rendered output is actually accepted (F4); N7 runs every catalog example through it.
- **Test layout: one file per operator family; hotspot files never grow** (decided 2026-06-04). A new increment adds a *new* small test file, it does not pile onto a monolith. The split:
  - `dsl/` keeps only the renderer/handle **core** (`RenderConditionTest`: composition, parenthesization, literal quoting, kind checks). Each operator family gets its own file under **`dsl/operators/`** (`PatternConditionTest`, `ValueListConditionTest`, `AggregateConditionTest`, `IterationConditionTest`, `EnumConditionTest`, …) holding that family's render (EN/DE) + handle pre-checks.
  - `validate/` keeps only F4 **mechanics** (`RuleValidatorTest`: injection, round-trip, problem mapping). The kernel-law locks are *executable `KERNEL-FINDINGS.md` entries* in **two tiers**: **accept/reject** (structural validity) under **`validate/laws/`** (core; `…LawsTest`, one per findings section, sharing the `KernelLaws` harness), and **fires/does-not-fire** (runtime *behavior* — polarity, empty-as-0, …) under **`adapter/src/test/.../adapter/laws/`** (the `RuntimeLaws` oracle over `IDocumentRtService.validateFull`; F-LAW). Each `KERNEL-FINDINGS` §/ledger row points at its `…LawsTest` class. Detail: KERNEL-INTEGRATION-NOTES "Runtime behavioral-law oracle".
  - Fixtures load once via the shared **`Fixtures`** util (`subscription()`/`order()`/`…Json()`) — no copied `@BeforeAll`, so a new file costs a few lines. `BoundModel` is an immutable snapshot (F0), safe to share.

- **Running the self-sufficiency eval / benchmark (N6): use the `run-rulekit-eval` skill** (`.claude/skills/`). It loads the protocol guardrails (clean subagent, material boundary, neutral prompts, pinned model, cost model, targeted re-runs) at the moment of running — **don't run the benchmark from memory**, the guardrails are easy to violate silently. Method/rationale: [`docs/EVAL-SPEC.md`](docs/EVAL-SPEC.md); measured results: [`eval/RESULTS.md`](eval/RESULTS.md). (That operator skill is distinct from `skill/SKILL.md`, which is the *material under test* — never give the operator skill to the eval's subagents.)
