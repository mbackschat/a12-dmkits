## Eat your own dogfood (the #1 standing requirement, 2026-06-26)

**Be your own consumer of the dmkits, feel the friction, and improve the library on the fly.** Every piece of *internal* code that touches a document model — tests, fixtures, benchmarks, demos, the CLI, the eval harness, the interpreter's differential — is a **first-class consumer of rulekit/modelkit/`dm.edit`** and MUST author through the typed surface a real user would reach for, never reach *around* it for low-level strings. This is the project's central discipline: the kits earn their design by being *used* by their own author.

Concretely, in order of preference, always:

1. **Refs over path strings.** Acquire a typed handle and reuse it — by-path (`m.num("/A/B")`) for an existing element, or **relative navigation off an editor/info** (`s.group("/A").num("B")`, `info.flatten("Lines*/Amount")`) so a path is written **once**, validated at the call site, and type-safe. A repeated string path, a hand-built `"../X/Y"` error path, or a hand-written condition/operation string in *new* internal code is a smell — the ref/editor form exists.
2. **The dmkit's own objects over ad-hoc records.** A rule is a `Rule` (error field + condition are refs; `errorEntityRelPath()`/`render()` are *derived*). A computation is a `Computation` (`computedFieldRelPath()` derived). A model is a `DocumentModelDraft`/`EditSession`. Don't reinvent a local `(group, code, errorRel, cond)` tuple when the typed object carries it and the kernel-canonical rendering for free.
3. **Friction is the most valuable signal — fix it, don't work around it.** When the typed surface is missing something a consumer needs (the editor lacked `flatten`; you couldn't build a `Rule` off an editor without adding it), that gap *is the bug*. Record it dated+timed in [`docs/DEV-API-GAPS.md`](docs/DEV-API-GAPS.md), **extend the library (TDD, clean code), and showcase it in [`docs/API-GUIDE.md`](docs/API-GUIDE.md)** — then use the new capability. Working around a gap with strings hides the very feedback the kit needs. *It is the same project — extending the kit to serve its own consumer is the intended workflow, not scope creep.*

**Fix gaps in ANY component you use — escalate only on a blocker (standing directive, 2026-06-29).** This generalizes rule 3 beyond the dmkits' typed surface to *every* component you reach for — rulekit, modelkit, `dm.core`/`ModelIndex`, the CLI, the interpreter, any internal library: if it has a gap or deficiency that your task exposes, **fix it** (TDD, clean code, lock it, document it in the same commit) rather than working around it. The *only* exception is a genuine **blocker** — something you cannot resolve or decide on your own (a cross-cutting design call, an external/licensing constraint, a change that would break a contract you can't unilaterally change) — and then you **report it first** and wait. A workaround that hides a fixable gap is itself a defect; surface it. (Example, 2026-06-29: `FieldInfo` didn't expose declared field config (min/max/length/pattern), so `model describe` couldn't show bounds — the fix was to extend `ModelIndex`/`FieldInfo`, not to read raw DM-JSON in the CLI.)

Existing internal code is **not** the spec for how to consume the kit — the API + its guide are (the trap that bit once: pattern-matching to older by-path test code instead of the preferred `EditSession` relative-nav idiom). Treat a new internal consumer as a usability test of the library, and report what you learn.

## Self-explaining surface (standing requirement, 2026-06-05)

**Favor a self-explaining, explorable CLI over relying on the N1 skill.** A cold LLM agent — given only the binary — must be able to discover the verbs, their parameters, and what they mean, and to learn each output's shape, *without* the skill. The skill (`skill/SKILL.md`) is the material-under-test for the N6 eval and **must stay as simple as possible**; it teaches judgment (polarity, the traps), not the verb/parameter catalog the tool should describe about itself. So when adding or changing a verb: make it discoverable (help/usage + a machine-readable manifest) and schema-describe its I/O. Discoverability lives in the *tool*, not the skill. Detail + rationale: [`docs/CLI-SPEC.md`](docs/CLI-SPEC.md).

**Which surface does a learned fact go in? (the placement rule.)** A document-model fact lands in exactly **one** home, chosen by *what kind of fact it is* — always the most self-describing surface that can carry it; the skill is the **last** resort. Four lanes:

| The fact is about… | It goes in | Carried as |
|---|---|---|
| **one operator** (a semantic surprise, a constraint, a relation, an example) | the operator catalog `rulekit/src/main/resources/catalog/operators.json` (served by `dmtool operators <id>`, N7-validated) | a `gotcha` with its `kind` (`SURPRISE`/`AUTHORING`/`RENDERING` — `GotchaKind`), `seeAlso`, `validExample`/`invalidExample{fix}` |
| **one spec/field shape** (a key, its requiredness, allowed values, a co-requirement) | the published JSON schema (`schema <target> <op>`), CI-executed examples | a property `description` / `enum` / required-together prose |
| **one kernel rejection's** meaning + corrective | the diagnostic enricher (`StructuralKernelFix.forCode`/`forMessage`, `RkCode`, the catalog-join) | a `fix`+`explain` that rides the `MVK_*`/`RK_*` itself |
| **cross-cutting judgment**, or a **trap that spans constructs / is no single operator** | the skill `skill/SKILL.md` (the #1-rule discipline applies) | a concise judgment note (polarity, iteration scope, the bilingual `--add-locale` cascade, "is this even a rule?") |

Decision test: *one operator → catalog; one spec field → schema; one error code → enricher; none of those (judgment / a multi-construct trap) → skill.* The skill is the **N6 material-under-test and is measured**, so a fact any of the first three surfaces can carry must **not** go in the skill (it would be cost without reach — and stale-prone). A trap can legitimately appear in **two** lanes when it is hit *before* the diagnostic fires (e.g. the enum locale cascade gets both an enricher hint *and* a skill note — the diagnostic corrects after the failure, the skill prevents it).

### Editing `skill/SKILL.md` — the #1 rule: re-read the whole file, and verify every claim against the live tool (standing requirement, 2026-06-22)

The skill is the **material under test for the N6 eval** — a wrong or stale claim in it is the *worst* class of defect, because it actively misleads every agent that reads it and **only an expensive probe run catches it** (a JUnit guard does not). So **before any edit to `skill/SKILL.md`, two things are mandatory, in order, no exceptions:**

1. **Re-read the WHOLE skill file first** — not just the section you're touching. The skill's sections interlock (e.g. `GroupFilled` is the *per-row* guard in one section but is *rejected* from a model-level scope in another); editing one paragraph in isolation silently contradicts another. You cannot keep it coherent without holding all of it in view.
2. **Check every factual claim against the CURRENT tool/schema/catalogs — run it through the binary.** Every DSL snippet, operator name, error code, path form, and "X is rejected / Y is valid" assertion must be **executed** (`rule check` against a fixture, `dmtool operators <id>`, `dmtool schema …`, `dmtool manifest`) and seen to behave as written. **Nothing in the skill may be stale or unverified.** If you cannot run it, you cannot write it.

This is not optional polish — it is **priority #1** for any skill change; it exists because an unverified edit once shipped three wrong claims, caught only by an expensive probe run. Treat a skill edit like a code change with a failing-build guard you satisfy by hand: re-read, verify against the tool, *then* write. (Mechanical guards still apply: `CommandReferencesResolveTest` resolves command refs; `scripts/sync-plugin-assets.sh` re-syncs the plugin copies.)

### Schema discipline — no drift, no rot (what triggers a schema check/update)

The published schemas (`cli/.../resources/schema/*.json`) are part of the self-describing surface, so they must never lag the code. Two kinds, two guards — and the rule is: **a change to the thing a schema describes must update that schema in the same commit, and a guard must fail the build if it doesn't.**

| change you make | schema to touch | the guard that catches a lag |
|---|---|---|
| **add/rename a result-envelope key** (`ResultEnvelope`) | `result.schema.json` | `SchemaVerbTest` — every target-first verb's real output keys must be declared in `result.schema` |
| **change a `Diagnostic`/`Where` field** | `diagnostic.schema.json` | `SchemaVerbTest`/`SchemaExamplesGuardTest` (diagnostics in real envelopes conform) |
| **change the rule/computation spec shape** | `add.schema.json` (+ its `examples`) | `SchemaExamplesGuardTest` — the input examples are **executed through the tool** |
| **change the `apply`/`batch` op-record frame or add an op/key** | `apply.schema.json` / `batch.schema.json` (+ `examples`) + the `ApplyCommand.Op` enum's `keys` (field ops single-source `FieldSpec.{ADD,MODIFY}_KEYS`) | `SchemaExamplesGuardTest` — both frame example blocks are CI-executed |
| **add/rename/remove a verb** | nothing by hand for the *contract* — `manifest` + `schema <target> <op>` are **derived from the live picocli tree** (can't drift); but flip `ManifestVerbTest.EXPECTED_VERBS`, add a read-only `verb-examples.json` demonstration (or a reasoned `DEMONSTRATION_PENDING` row), and if the verb takes a rich JSON input, add its input schema + `SchemaCommand.INPUT_OPS` mapping. A new **cross-cutting** verb that returns the result envelope gets a `schema` pointer automatically; one that doesn't (renders an artifact / custom payload) is classified in `SchemaCommand.CONTRACT_EXEMPT` with a reason | `ManifestVerbTest`/`ManifestTreeTest` + **`CliConformanceMatrixTest`** (described · params-described · schema-resolves · demonstrated) + `VerbDemonstrationTest` (executes the example) + **`CommandReferencesResolveTest`** (a **rename** that leaves stale `dmtool …` examples fails here — every command ref must resolve against the live tree, across **both** the in-binary text (help/diagnostics/schema) **and** the command-bearing markdown an agent/installer reads: the source + public READMEs, the canonical `skill/SKILL.md`, the Codex `AGENTS.md` — markdown scanned by code-context, not prose; the tool name is single-sourced as `Cli.TOOL_NAME`); see [`docs/CLI-CONFORMANCE-SPEC.md`](docs/CLI-CONFORMANCE-SPEC.md) "the conformance matrix" + "the two-guard defense" |
| **structure change** (new `FieldKind`, new structure op) | only if it changes a verb's I/O shape (above) | the relevant guard above |

The **no-rot** lever is that **every schema `examples` block is CI-executed through the tool** (`SchemaExamplesGuardTest`) — a stale example actively misleads an agent, so an unverified one cannot ship. The **no-drift** lever is that the *contracts* an agent reads (`manifest`, `schema <target> <op>`) are **derived, not authored** — they recompute from the command tree. When in doubt: add the worked `examples` so the guard executes it; never hand-author a schema fact a guard can't check.

**Native-image side effect (only if shipping native):** the bundled reflection metadata is TEST-SUITE-captured, so ANY `:cli`/`src` source-or-test change since the last capture stales it. Practical rule — about to (re)build native? **RE-CAPTURE FIRST** ([`scripts/capture-native-config.sh`](scripts/capture-native-config.sh)), then rebuild, then [`scripts/native-gate.sh`](scripts/native-gate.sh); **NEVER run a probe or ship on a binary older than your changes** ([`probe/prep-probe.sh`](probe/prep-probe.sh) enforces it). Full trigger table + cadence: [`docs/NATIVE-IMAGE-GRAALVM.md`](docs/NATIVE-IMAGE-GRAALVM.md) §5.1. (No action on a JVM-only/dev build.)

## Refactoring safety gate (standing requirement, 2026-06-12)

**Before proposing a *new* refactor verb, apply the earns-a-verb bar (CLI-SPEC §6).** A refactoring deserves a first-class verb only when hand-composing it from primitives (`read` + `add`/`remove`/`modify`) is unreliable — it trips **reference fan-out**, **non-trivial mechanical correctness** (path rebasing), or **atomicity/loss**. If none trips, prefer teaching the primitives (schema + diagnostics) to compose correctly — *self-explaining primitives > more verbs*. (This is the standing trigger for "should we add refactor X?" discussions; e.g. `rule/computation move` is deferred under it.) For any refactor we *do* add, the gate below applies.

**Any refactor — now or in the future — checks safety *before* it changes anything; if the specific refactor isn't safe on this model it refuses with rich, corrective diagnostics and mutates nothing; only when safe does it proceed.** We gate the refactor and stay in control — never a best-effort rewrite, never a silent degrade. This generalizes the safe-delete `where-used` gate to the whole Refactor class (rename, move, extract/inline). Two non-negotiables for every refactor:

- **Document the gate well in the md docs** — each refactor's safety preconditions, what it refuses on, and the diagnostics it emits. Its home is [`docs/CLI-SPEC.md`](docs/CLI-SPEC.md) §6; never leave the safety contract implicit in code.
- **Test the refusal** — when a refactor op lands, its refusal path gets a law test proving the gate *fires* on unsafe input (the `adapter/laws` does-fire tier), not just that the happy path works.

An ungated, undocumented, or untested-on-refusal refactor is not shippable. Full principle + per-refactor preconditions: [`docs/CLI-SPEC.md`](docs/CLI-SPEC.md) §6.

## Root-cause generalization (standing requirement, 2026-06-19)

**When you find a defect — from a bug report or a probe — fix the *class*, not the symptom.** Once you know the root cause, **always sweep for every sibling site where the same class can occur** *before* declaring it fixed, and fix them together at the shared root. A symptom-only patch (the one verb/path that was reported) leaves the rest of the class live — that is how whack-a-mole starts.

The drill: **reproduce → root-cause → generalize (enumerate every site of the class) → fix at the shared root → lock with a guard that covers the siblings, not just the reported case.** Worked example: P1 — a raw stack trace from a duplicate `rule add` — root-caused to `RuleValidator.check` letting a kernel conversion exception escape, a path shared by six callers; the fix went in the validator and the guard covers `computation add` too, not only the reported `rule add`. This complements the anti-whack-a-mole mining below (mine constraints proactively) and the probe's proactive loop ([`docs/PROBE-SPEC.md`](docs/PROBE-SPEC.md)).

## Multi-session work programs

Running a work program that spans multiple sessions (a master session minting worker prompts, per-item hybrid model choice, review gates on every landing)? **Load the `run-work-program` skill** (`.claude/skills/`) — don't run the protocol from memory; its gate checklist and drill criteria are easy to violate silently. ## Interpreter — the two #1 rules (never scoped down)

The **`:interpreter`** module is the kernel-free Kotlin Multiplatform evaluator (native image + standalone JVM/JS library). **Its full module instructions live in [`interpreter/CLAUDE.md`](interpreter/CLAUDE.md)** (auto-loaded for work in that subtree) — **read that file before ANY interpreter-related work, including its differential/perf work in `:adapter`** (which lives outside the subtree, so it does not auto-load). It carries the goals/priorities, customization-surface parity, the performance method, the generator layering, and the hygiene rules (the `verifyInterpreterPurity` lint enforces the import boundary). Two rules are repeated here because a miss is catastrophic and they must hold before any file is even opened:

1. **(A) MATCH kernel semantics EXACTLY — BOTH evaluation strategies** (the md-runtime dynamic service AND the Groovy code generator). Bit-for-bit on every legal input; no "close enough"; a differential-observable special case is a must-match, never "obsolete". Where the two strategies diverge, match production codegen; a behavior is droppable only when proven DEAD in both strategies from source.
2. **(B) Clean-room reimplementation, NEVER kernel delegation — the EUPL license boundary.** The A12 kernel is EUPL-1.2/commercial; a runtime that links/ships/calls it is a combined work the copyleft reaches. So: never delegate evaluation to the kernel (no `com.mgmtp.*` call, no JS-kernel binding), and **never copy/transliterate the kernel's source expression** — a line-by-line port is a copyright derivative that re-attracts the EUPL. Read the source to learn the exact behavior → write original Kotlin → lock it with the differential. Copy the *mechanism*, never the *expression*. The `--kernel` flag (JVM-only) is the only place dmtool touches the kernel.

## Coding style — make full use of Java 21

Write idiomatic modern Java 21, not Java 8 with newer syntax:
- **Records** for immutable data (AST nodes, value objects, results). **Sealed interfaces + exhaustive pattern-matching `switch`** for closed hierarchies — model the AST this way and let the renderer/visitors dispatch with a switch that the compiler proves exhaustive (no `default`). See PROJECT-DESIGN §18.5.
- Record/`instanceof` **deconstruction patterns**, `var` for obvious locals, **text blocks** for multi-line strings (DM-JSON fixtures, expected output), enhanced `switch` expressions, `Optional` over nulls in APIs, `List.of`/`List.copyOf` for immutability.
- Prefer making illegal states unrepresentable in the type system over runtime checks — that is the whole point of the typed builder.
- **Long parameter list → builder, never a positional N-arg constructor (standing rule).** When a value object (record included) would take many arguments — the smell bites hardest with **several same-typed** params (multiple `String`/`boolean`/`List`), which are silently swap-prone — give it a fluent `Builder` and make the builder the *public* construction path; the record's canonical constructor stays but is called only by `build()`. A `null`/empty/`false` setter argument means "leave this aspect unset". Exemplars: `FieldModification`, `ConfigModification`, `GroupModification`. (Rule of thumb: ≳5 params, or ≥2 adjacent same-typed params, ⇒ builder.)
- **Clean code is non-negotiable — never knowingly write a code smell, and if you spot one (even pre-existing), stop, report it immediately, and provide the fix.** Reach for the idiomatic Java-21 construct over the expedient shortcut (the items above), make illegal states unrepresentable, and when a structure *scales across increments* do an explicit refactor pass rather than letting duplication accrete behind green tests. (Smells bite worst when they creep in incrementally — e.g. the string-keyed dispatch for a closed set that crept into `ApplyCommand`, since fixed with an enum + exhaustive `switch`.)
- **Javadoc `*/` trap:** never write a literal `*/` inside a Javadoc block comment — most often a wildcard path in `{@code …}` like `Group*/field` — it ends the comment early and breaks compilation. Reword (e.g. "the flatten of `Group*` then `field`", or a space: `Group* / field`). This recurs whenever documenting repetition-list syntax.

## Testing strategy

The conventions below are enforced; the **map of the whole testing approach** (the kinds of test, the two law tiers, the guardians, the corpus harnesses, how to run) lives in [`docs/TESTING-SPEC.md`](docs/TESTING-SPEC.md) — read it to place a new test.

- **Example-based TDD is the primary spec** (red/green) — readable, intent-revealing tests drive each feature.
- **The real kernel is the oracle.** `RuleValidator` + `checkConsistency` confirm that rendered output is actually accepted (F4); N7 runs every catalog example through it.
- **Test layout: one file per operator family; hotspot files never grow** (decided 2026-06-04). A new increment adds a *new* small test file (the shared `Fixtures` util keeps that cheap), never piles onto a monolith. The kernel-law locks are executable `KERNEL-FINDINGS.md` entries in **two tiers**: **accept/reject** (structural validity) under `validate/laws/` and **fires/does-not-fire** (runtime behavior) under `adapter/.../laws/` (the `RuntimeLaws` oracle); each findings §/ledger row points at its `…LawsTest` class. Where a new test goes: [`docs/TESTING-SPEC.md`](docs/TESTING-SPEC.md).

- **Keep test-task dependencies slim and specific — a test that reads a repo file at runtime declares that file as an input on a task scoped to *just* that test, never on the broad suite** (standing requirement, 2026-06-30). Gradle inputs are per-task: declaring a doc/demo on the whole `:cli:test` re-runs all ~620 tests on any `.md` edit; *omitting* it lets the task go up-to-date / restore from the build cache into a **false green** locally while CI (fresh) fails. The pattern — the doc-reading guards (`CliTourFreshnessTest`, `CommandReferencesResolveTest`) run in a dedicated `docGuardTest` task with exactly those files as its inputs, and `test dependsOn docGuardTest` (so CI + the `-PrkNativeAgent` capture still drive them). Detail: [`docs/TESTING-SPEC.md`](docs/TESTING-SPEC.md) "Tests that read repo files at runtime".

- **Running the self-sufficiency eval / benchmark (N6): use the `run-dmtool-eval` skill** (`.claude/skills/`). It loads the protocol guardrails (clean subagent, material boundary, neutral prompts, pinned model, cost model, targeted re-runs) at the moment of running — **don't run the benchmark from memory**, the guardrails are easy to violate silently. Method/rationale: [`docs/EVAL-SPEC.md`](docs/EVAL-SPEC.md); measured results: [`eval/RESULTS.md`](eval/RESULTS.md). (That operator skill is distinct from `skill/SKILL.md`, which is the *material under test* — never give the operator skill to the eval's subagents.)

- **Authoring skills/workflows: put deterministic or permission-gated setup in a committed script the main loop runs — never prompt an agent to do it.** A workflow subagent runs under a restricted permission mode and **cannot self-approve a mutating command** (`rm`/`cp`/`mkdir`), so an agent *prompted* to do setup is non-deterministically denied — and a denied setup the run doesn't hard-check silently corrupts the results (the eval's produce agents mutated committed fixtures this way three times, once even into a commit). The fix pattern: setup lives in a checked-in script (e.g. [`eval/prep-sandbox.sh`](eval/prep-sandbox.sh)) the main loop invokes alongside the build; the workflow only **verifies** (read-only) the precondition and **halts loudly** if it's missing. General rule: **agents for judgment/exploration, scripts for deterministic side-effecting setup.**

## Build

Build with an isolated, public-repos-only Gradle home so the machine's global config (private registry) is bypassed, on JDK 21 — see the README's "Build & test" section. **Simplest: `./build.sh <gradle args>`** — the committed wrapper pins the isolated `GRADLE_USER_HOME` + JDK 21 then runs Gradle, so a bare `./gradlew` can't be silently contaminated by the machine's global `init.d` (root cause: [`docs/KERNEL-INTEGRATION-NOTES.md`](docs/KERNEL-INTEGRATION-NOTES.md) "Build / environment gotchas"). The kernel must first be published to `mavenLocal` via the sibling `a12-kernel-bootstrap` kit.

**Inner loop: run TARGETED tests, not the full suite, for each minor change (standing requirement, 2026-06-24).** The full `./build.sh :interpreter:check :adapter:test :cli:test` (+ `scripts/verify-demos.sh`, which rebuilds `installDist`) takes **>1 min** and slows development when run after every small edit. While iterating, run a **single test class** — `./build.sh :adapter:test --tests "<FqcnOrPattern>"` (one `*DiffTest`/fuzz class is ~3–7 s), or `:interpreter:check` alone when only `:interpreter` changed. Reserve the **full suite + `verify-demos.sh`** for **strategic checkpoints**: right before a commit, after a structural/parser change, or when a verb's output shape changed (only then do the demos matter — otherwise skip them).

**Capturing a long build/test run: redirect the FULL output to a file, then grep the file — NEVER pipe the build through `tail`/`head`/`grep`.** Use `./build.sh --console=plain <args> > build/run.log 2>&1` then `grep -E 'BUILD (SUCCESSFUL|FAILED)|FAILED' build/run.log`. Two traps a pipe hits (the reason [`scripts/perf.sh`](scripts/perf.sh) exists, and the rule generalizes to any long run): a pipe **buffers**, so a backgrounded build's log stays empty until it finishes (polling looks frozen and you can't read it incrementally); and `head`/early-closing readers can **SIGPIPE the build and lose its output** entirely. Writing the raw log to a file fixes both — and a backgrounded run can then be `Read` as it grows. (Lesson codified here, not in agent memory, so it travels across machines.)

**A run that can exceed ~10 minutes must NOT be a plain backgrounded shell command — agent harnesses cap those** (Claude Code kills a background Bash task at 10 min; the kill mid-run looks like a mystery failure — it bit twice on 2026-07-10). Run it through a mechanism without that cap (in Claude Code: the Monitor tool with a generous `timeout_ms`, emitting only the result line), or split the run into sub-10-minute tiers — one reason the perf suite is two-tiered: `scripts/perf.sh gate` (the fast routine gate, every landing) vs `perf.sh bench` (the slow kernel-ratio benchmarks, perf-relevant checkpoints only); both take an optional method pattern (`perf.sh gate 'semanticIndex*'`) for a ~1-minute single-scenario re-check.

**Launch every long run through a HARNESS-MANAGED background mechanism — NEVER a hand-rolled `setsid`/`nohup`/`&` detach inside a tool call (standing rule, 2026-07-12).** The harness runs each tool invocation in its own process group and reaps that group when the call returns, so a child you background yourself dies (or is silently orphaned) the instant the tool call returns — the build never actually runs. Use the Bash tool's own `run_in_background` (harness-tracked; notifies on completion; readable incrementally — but still ~10-min-capped) or the **Monitor tool to *run* the command itself** (not to watch a separately-detached process), with a generous `timeout_ms`; run shorter (<10 min) commands in the **foreground** so their output returns and is visible. The tell that a "backgrounded" run is actually **dead on arrival**: a 0-byte log + idle CPU + a Gradle daemon parked in `awaitExpiration` (`jstack` shows `Daemon.stopOnExpiration`, near-zero cpu) = it never received a build request — **investigate immediately, never keep waiting on a corpse.** (Cost this once: a `setsid …&` corpus sweep was reaped at launch and "watched" for 14 min against an empty log; the fix is `run_in_background`/Monitor, which is exactly why the tiered `:adapter:test` runs worked.) Corollary on visibility: Gradle **block-buffers** to a non-TTY, so `--console=plain > file` shows *nothing* until the buffer flushes — treat an empty log after minutes as a launch failure to diagnose, not "still buffering," and prefer foreground (output returns) or a Monitor that streams filtered progress lines.

**Release/public-mirror boundary (standing guardrail): the public `a12-dmtool-releases` repo is generated output, not a hand-edited working tree.** Never push directly to the mirror or mutate release assets by hand unless the maintainer explicitly asks for emergency mirror surgery after the scripted process failed. Use [`scripts/publish-release.sh`](scripts/publish-release.sh), which assembles the mirror tree, pushes it, creates/uses a draft release, uploads macOS, dispatches the public native build, and flips the draft live. After `--go-live`, treat the GitHub release as immutable by project policy: adding a platform, replacing a binary, changing `SHA256SUMS`, or changing the public workflow for that release means cut a patch release.

**Release artifacts (native image, developer jars) and the release procedure are NOT here — they live in [`docs/RELEASE-SPEC.md`](docs/RELEASE-SPEC.md)** (the durable release spec: verification gate + versioning + distribution). **The GraalVM native-image build is its own topic in [`docs/NATIVE-IMAGE-GRAALVM.md`](docs/NATIVE-IMAGE-GRAALVM.md)** (recipe, findings, the reflection/Groovy walls, sizing, status) — consult it before touching the native build; its **current shippability + residual caveats are tracked there** (§1), not asserted here (so this line can't rot). Everyday dev build (JVM/tests) stays in the README + above; native-image is release-only and never in the dev inner loop.
