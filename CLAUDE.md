## Self-explaining surface (standing requirement, 2026-06-05)

**Favor a self-explaining, explorable CLI over relying on the N1 skill.** A cold LLM agent — given only the binary — must be able to discover the verbs, their parameters, and what they mean, and to learn each output's shape, *without* the skill. The skill (`skill/SKILL.md`) is the material-under-test for the N6 eval and **must stay as simple as possible**; it teaches judgment (polarity, the traps), not the verb/parameter catalog the tool should describe about itself. So when adding or changing a verb: make it discoverable (help/usage + a machine-readable manifest) and schema-describe its I/O. Discoverability lives in the *tool*, not the skill. Detail + rationale: [`docs/CLI-SPEC.md`](docs/CLI-SPEC.md).

**Which surface does a learned fact go in? (the placement rule.)** A document-model fact lands in exactly **one** home, chosen by *what kind of fact it is* — always the most self-describing surface that can carry it; the skill is the **last** resort. Four lanes:

| The fact is about… | It goes in | Carried as |
|---|---|---|
| **one operator** (a semantic surprise, a constraint, a relation, an example) | the operator catalog `src/main/resources/catalog/operators.json` (served by `dmtool operators <id>`, N7-validated) | a `gotcha` with its `kind` (`SURPRISE`/`AUTHORING`/`RENDERING` — `GotchaKind`), `seeAlso`, `validExample`/`invalidExample{fix}` |
| **one spec/field shape** (a key, its requiredness, allowed values, a co-requirement) | the published JSON schema (`schema <target> <op>`), CI-executed examples | a property `description` / `enum` / required-together prose |
| **one kernel rejection's** meaning + corrective | the diagnostic enricher (`StructuralKernelFix.forCode`/`forMessage`, `RkCode`, the catalog-join) | a `fix`+`explain` that rides the `MVK_*`/`RK_*` itself |
| **cross-cutting judgment**, or a **trap that spans constructs / is no single operator** | the skill `skill/SKILL.md` (the #1-rule discipline applies) | a concise judgment note (polarity, iteration scope, the bilingual `--add-locale` cascade, "is this even a rule?") |

Decision test: *one operator → catalog; one spec field → schema; one error code → enricher; none of those (judgment / a multi-construct trap) → skill.* The skill is the **N6 material-under-test and is measured**, so a fact any of the first three surfaces can carry must **not** go in the skill (it would be cost without reach — and stale-prone). A trap can legitimately appear in **two** lanes when it is hit *before* the diagnostic fires (e.g. the enum locale cascade gets both an enricher hint *and* a skill note — the diagnostic corrects after the failure, the skill prevents it).

### Editing `skill/SKILL.md` — the #1 rule: re-read the whole file, and verify every claim against the live tool (standing requirement, 2026-06-22)

The skill is the **material under test for the N6 eval** — a wrong or stale claim in it is the *worst* class of defect, because it actively misleads every agent that reads it and **only an expensive probe run catches it** (a JUnit guard does not). So **before any edit to `skill/SKILL.md`, two things are mandatory, in order, no exceptions:**

1. **Re-read the WHOLE skill file first** — not just the section you're touching. The skill's sections interlock (e.g. `GroupFilled` is the *per-row* guard in one section but is *rejected* from a model-level scope in another); editing one paragraph in isolation silently contradicts another. You cannot keep it coherent without holding all of it in view.
2. **Check every factual claim against the CURRENT tool/schema/catalogs — run it through the binary.** Every DSL snippet, operator name, error code, path form, and "X is rejected / Y is valid" assertion must be **executed** (`rule check` against a fixture, `dmtool operators <id>`, `dmtool schema …`, `dmtool manifest`) and seen to behave as written. **Nothing in the skill may be stale or unverified.** If you cannot run it, you cannot write it.

This is not optional polish — it is **priority #1** for any skill change. It exists because it was violated: a "wildcard/aggregate paths" edit shipped three wrong claims (`GroupFilled(/Group)` as the valid model-level form; row-count via `NumberOfFilledGroups(/Group)` without the required `*`; "`*` never on a group ref"), none of which had been run through the binary — caught only after the fact. Treat a skill edit like a code change with a failing-build guard you have to satisfy by hand: re-read, verify against the tool, *then* write. (Mechanical guards still apply too: `CommandReferencesResolveTest` resolves command refs, and `scripts/sync-plugin-assets.sh` must re-sync the plugin copies.)

### Schema discipline — no drift, no rot (what triggers a schema check/update)

The published schemas (`cli/.../resources/schema/*.json`) are part of the self-describing surface, so they must never lag the code. Two kinds, two guards — and the rule is: **a change to the thing a schema describes must update that schema in the same commit, and a guard must fail the build if it doesn't.**

| change you make | schema to touch | the guard that catches a lag |
|---|---|---|
| **add/rename a result-envelope key** (`ResultEnvelope`) | `result.schema.json` | `SchemaVerbTest` — every target-first verb's real output keys must be declared in `result.schema` |
| **change a `Diagnostic`/`Where` field** | `diagnostic.schema.json` | `SchemaVerbTest`/`SchemaExamplesGuardTest` (diagnostics in real envelopes conform) |
| **change the rule/computation spec shape** | `add.schema.json` (+ its `examples`) | `SchemaExamplesGuardTest` — the input examples are **executed through the tool** |
| **change the `apply`/`batch` op-record frame or add an op/key** | `apply.schema.json` / `batch.schema.json` (+ `examples`) + the `ApplyCommand.Op` enum's `keys` (field ops single-source `FieldSpec.{ADD,MODIFY}_KEYS`) | `SchemaExamplesGuardTest` — both frame example blocks are CI-executed |
| **add/rename/remove a verb** | nothing by hand for the *contract* — `manifest` + `schema <target> <op>` are **derived from the live picocli tree** (can't drift); but flip `ManifestVerbTest.EXPECTED_VERBS`, add a read-only `verb-examples.json` demonstration (or a reasoned `DEMONSTRATION_PENDING` row), and if the verb takes a rich JSON input, add its input schema + `SchemaCommand.INPUT_OPS` mapping. A new **cross-cutting** verb that returns the result envelope gets a `schema` pointer automatically; one that doesn't (renders an artifact / custom payload) is classified in `SchemaCommand.CONTRACT_EXEMPT` with a reason | `ManifestVerbTest`/`ManifestTreeTest` + **`CliConformanceMatrixTest`** (described · params-described · schema-resolves · demonstrated) + `VerbDemonstrationTest` (executes the example) + **`CommandReferencesResolveTest`** (a **rename** that leaves stale `dmtool …` examples fails here — every command ref must resolve against the live tree, across **both** the in-binary text (help/diagnostics/schema) **and** the command-bearing markdown an agent/installer reads: the source + public READMEs, the canonical `skill/SKILL.md`, the Codex `AGENTS.md` — markdown scanned by code-context, not prose; the tool name is single-sourced as `Cli.TOOL_NAME`); see [`docs/CLI-CONFORMANCE-SPEC.md`](docs/CLI-CONFORMANCE-SPEC.md) "the conformance matrix" + "the two-guard defense" |
| **structure change** (new `FieldKind`, new structure op) | only if it changes a verb's I/O shape (above) | the relevant guard above |

The **no-rot** lever is that **every schema `examples` block is CI-executed through the tool** (`SchemaExamplesGuardTest`) — a stale example actively misleads an agent, so an unverified one cannot ship. The **no-drift** lever is that the *contracts* an agent reads (`manifest`, `schema <target> <op>`) are **derived, not authored** — they recompute from the command tree. When in doubt: add the worked `examples` so the guard executes it; never hand-author a schema fact a guard can't check.

**Native-image side effect of a verb/catalog change (only if shipping native):** the GraalVM native build bundles **captured reflection metadata** that goes stale when the reflective surface changes. A **verb add/rename**, a **new Jackson-deserialized POJO**, or an **`operators.json` change** is one of the re-capture triggers (alongside a kernel bump and a Jackson dep bump). **But the capture is TEST-SUITE-DRIVEN ([`scripts/capture-native-config.sh`](scripts/capture-native-config.sh) runs the `:cli` suite under the agent), so the *operational* trigger is broader than that list: any new/changed test that exercises a new shape stales the metadata too. Practical rule — touched `:cli`/`src` source or tests since the last capture and about to (re)build native? RE-CAPTURE FIRST, then rebuild, then [`scripts/native-gate.sh`](scripts/native-gate.sh).** **#1 hard rule: NEVER run a probe (or ship) on a native image built from metadata older than your changes** — the probe then measures a fiction; [`probe/prep-probe.sh`](probe/prep-probe.sh) enforces it (refuses if the binary is older than any `:cli`/`src` source/test or the bundled metadata). Full trigger table + cadence: [`docs/NATIVE-IMAGE-GRAALVM.md`](docs/NATIVE-IMAGE-GRAALVM.md) §5.1. The native gate is the trip-wire if you forget. (No action on a JVM-only/dev build.)

## Refactoring safety gate (standing requirement, 2026-06-12)

**Before proposing a *new* refactor verb, apply the earns-a-verb bar (CLI-SPEC §6).** A refactoring deserves a first-class verb only when hand-composing it from primitives (`read` + `add`/`remove`/`modify`) is unreliable — it trips **reference fan-out**, **non-trivial mechanical correctness** (path rebasing), or **atomicity/loss**. If none trips, prefer teaching the primitives (schema + diagnostics) to compose correctly — *self-explaining primitives > more verbs*. (This is the standing trigger for "should we add refactor X?" discussions; e.g. `rule/computation move` is deferred under it.) For any refactor we *do* add, the gate below applies.

**Any refactor — now or in the future — checks safety *before* it changes anything; if the specific refactor isn't safe on this model it refuses with rich, corrective diagnostics and mutates nothing; only when safe does it proceed.** We gate the refactor and stay in control — never a best-effort rewrite, never a silent degrade. This generalizes the safe-delete `where-used` gate to the whole Refactor class (rename, move, extract/inline). Two non-negotiables for every refactor:

- **Document the gate well in the md docs** — each refactor's safety preconditions, what it refuses on, and the diagnostics it emits. Its home is [`docs/CLI-SPEC.md`](docs/CLI-SPEC.md) §6; never leave the safety contract implicit in code.
- **Test the refusal** — when a refactor op lands, its refusal path gets a law test proving the gate *fires* on unsafe input (the `adapter/laws` does-fire tier), not just that the happy path works.

An ungated, undocumented, or untested-on-refusal refactor is not shippable. Full principle + per-refactor preconditions: [`docs/CLI-SPEC.md`](docs/CLI-SPEC.md) §6.

## Root-cause generalization (standing requirement, 2026-06-19)

**When you find a defect — from a bug report or a probe — fix the *class*, not the symptom.** Once you know the root cause, **always sweep for every sibling site where the same class can occur** *before* declaring it fixed, and fix them together at the shared root. A symptom-only patch (the one verb/path that was reported) leaves the rest of the class live — that is how whack-a-mole starts.

The drill: **reproduce → root-cause → generalize (enumerate every site of the class) → fix at the shared root → lock with a guard that covers the siblings, not just the reported case.** Worked example: P1 — a raw stack trace from a duplicate `rule add` — root-caused to `RuleValidator.check` letting a kernel conversion exception escape, a path shared by six callers; the fix went in the validator and the guard covers `computation add` too, not only the reported `rule add`. This complements the anti-whack-a-mole mining below (mine constraints proactively) and the probe's proactive loop ([`docs/PROBE-SPEC.md`](docs/PROBE-SPEC.md)).

- **Research freely; commit only own-domain re-expressions.** All three sources — **`a12-kernel-demo`**, the **A12 Tools workspaces** (`/Volumes/Buffer/Apps/A12 Tools/A12 Tools - 2025.06-ext5/workspaces`, the 2025.06-ext5 distribution = kernel `30.8.1`, our pin), and **`a12-kernel-mm`** — may be read and studied without limit. What gets **committed** must be our own original fixtures.
- **The license-safe rule: copy the *mechanism*, never the *expression*.** You may reproduce an abstract pattern (the includes/`modelAlias` scheme, an operator-usage shape, a rule skeleton) and re-express it in a **wholly different, coherent domain** with **our own field names, business content, and rule text**. You may **not** commit a source model's domain/fields/rules/text verbatim or lightly renamed. Mechanisms/ideas aren't protected; their concrete expression is — so a genuine domain change keeps committed fixtures clear of `a12-kernel-mm`'s **EUPL-1.2** copyleft and the **proprietary** A12 Tools licensing. When unsure, transform more, not less. Everything committed **must make sense**: realistic domain, field names, types, plausible rules; no nonsense placeholders.
- **`a12-kernel-demo` is the easy case** — it's the demo; copying/adapting its example models directly is fine.
- **`a12-kernel/documentation/_merged/kernel-ba.md` (the merged BA doc) is pure gold for examples** — kernel-team-written/reviewed prose with worked examples covering nearly the whole DSL (the filter `$`-operator, `CurrentRepetition` predecessors, comparisons, value lists, dates, …). Mine it for fixtures and laws — but the **license-safe rule above applies: transfer to our own domain, never copy** the example's fields/text.
- The earlier `a12-kernel-mm` **reference-only, opt-in integration test** path (sibling clone `../a12-kernel-mm`, env-overridable, skipped if absent) remains available for tests that *read* the real models without committing them. (§19 license decision before first publish should still confirm fixture provenance.)
- **The showboat demos own their fixtures, separate from the JUnit/eval fixtures (decided 2026-06-15).** The `examples/` walkthroughs read their sample models from **`examples/models/`** — the demos' *own* fixtures, **published with the demos to the release mirror** so the walkthroughs run there. The license-safe own-domain rule applies to both. When a demo needs a model, add/adjust it under `examples/models/`; never repoint a demo into `cli/src/test/resources/`.

## Coding style — make full use of Java 21

Write idiomatic modern Java 21, not Java 8 with newer syntax:
- **Records** for immutable data (AST nodes, value objects, results). **Sealed interfaces + exhaustive pattern-matching `switch`** for closed hierarchies — model the AST this way and let the renderer/visitors dispatch with a switch that the compiler proves exhaustive (no `default`). See PROJECT-DESIGN §18.5.
- Record/`instanceof` **deconstruction patterns**, `var` for obvious locals, **text blocks** for multi-line strings (DM-JSON fixtures, expected output), enhanced `switch` expressions, `Optional` over nulls in APIs, `List.of`/`List.copyOf` for immutability.
- Prefer making illegal states unrepresentable in the type system over runtime checks — that is the whole point of the typed builder.
- **Clean code is non-negotiable — never knowingly write a code smell, and if you spot one (even pre-existing), stop, report it immediately, and provide the fix.** Reach for the idiomatic Java-21 construct over the expedient shortcut (the items above), make illegal states unrepresentable, and when a structure *scales across increments* do an explicit refactor pass rather than letting duplication accrete behind green tests. (Smells bite worst when they creep in incrementally — e.g. the string-keyed dispatch for a closed set that crept into `ApplyCommand`, since fixed with an enum + exhaustive `switch`.)
- **Javadoc `*/` trap:** never write a literal `*/` inside a Javadoc block comment — most often a wildcard path in `{@code …}` like `Group*/field` — it ends the comment early and breaks compilation. Reword (e.g. "the flatten of `Group*` then `field`", or a space: `Group* / field`). This recurs whenever documenting repetition-list syntax.

## Documentation discipline

- **Every non-obvious finding gets written down under `docs/`** — kernel/build/environment facts default to [`docs/KERNEL-INTEGRATION-NOTES.md`](docs/KERNEL-INTEGRATION-NOTES.md); design decisions to [`docs/PROJECT-DESIGN.md`](docs/PROJECT-DESIGN.md). If a finding doesn't fit an existing doc's scope, **propose a new doc** rather than overloading one.
- **`../a12-kernel-demo/KERNEL-SEMANTICS.md` is the canonical kernel-truth reference — consult-only** (owner policy, 2026-06-04). Before each increment, read the relevant section (truth values, null semantics, formal errors, decimals, dates, enums, iteration, paths, computations, messages). **Do not write to it.** Kernel-behavior findings it *lacks* go to our own [`docs/KERNEL-FINDINGS.md`](docs/KERNEL-FINDINGS.md) (section-numbered to mirror KERNEL-SEMANTICS for easy upstreaming; every entry experiment-verified and test-locked); rulekit's *treatment* of each fact stays in `KERNEL-INTEGRATION-NOTES.md`.
- **Cross-check findings against the kernel-team BA doc — `a12-kernel/documentation/_merged/kernel-ba.md` (consult-only, standing policy 2026-06-07).** It is carefully written and reviewed by the a12 kernel team and covers nearly every DSL aspect in prose, with worked examples and per-`MVK_*`-error rationale (the filter operator + `$`, `CurrentRepetition`, comparisons, value lists, dates, iteration). **It is original material — read/study freely, but never copy; transfer examples to our own domain** (the license-safe rule). Use it as a second oracle: when recording or trusting a kernel-behavior finding, confirm it there (it already caught one missing finding, `MVK_INVALID_ITERATION_IN_FILTER_CONDITION`, and validated the `$`/`CurrentRepetition` predecessor pattern). Companion: `kernel-dev.md` (developer-facing). **Do not write to either.**
- **The kernel SOURCE is the primary oracle — read it before decompiling jars or guessing** (2026-06-07). The full kernel is checked out at **`../a12-kernel/kernel-tool/`** (consult-only). For DSL **syntax** read the ANTLR grammar (`kernel-core-parser/.../grammar/gen/*.g4`); for **rendering** read the `FormatterVisitor`/`FormatterUtil`; for **validation semantics** read the `check/.../Check*Impl` classes (their javadoc states the rules); for **keywords** grep `LexerTerminals_en/_de.java`. The map + rationale: [`docs/KERNEL-INTEGRATION-NOTES.md`](docs/KERNEL-INTEGRATION-NOTES.md) "The kernel SOURCE is the primary oracle". Probing the live kernel stays the way to confirm *behavior*; the source is the way to learn *syntax/rendering/rules*.
- **Anti-whack-a-mole: mine constraints proactively, don't trip over them** (owner direction, 2026-06-04). Structural laws live in enumerable sources — sweep them instead of discovering by accident: **(1)** slot parity vs the public `IRule`/`IComputation` accessors (every accessor = supported or explicitly deferred); **(2)** the **MVK ledger** — every `MVK_*` code classified (erased-by-types / pre-checked / kernel-delegated / pending / unknown→experiment queue), CI-checked; **(3)** the `../a12-kernel-mm` metamodels as the **source of truth for valid DM structure** (schema oracle: `MM_*`/`CT_MODEL_HEADER` define the slots; constraint oracle: their rules encode validity laws — read-only, own-words analysis only, EUPL); **(4)** deserializer/serializer-tier checks (constraints that fire before `checkConsistency`): the write gate is `BasicConsistencyCheck` (run by `serialize()`, aborts on ERROR), its `BasicDocumentModelConsistencyCategory` enum (16 categories) the F6 output contract — every category classified (pre-checked by an authoring builder / n/a-structural), reflectively CI-locked; the deserialize tier (Jackson: locale format, type discriminators) documented in `KERNEL-FINDINGS.md`. **(5)** the parsetree-api construct-name enums as the **operator inventory** (reverse parity: every member cataloged or explicitly excluded — `adapter.KernelConstructParityTest`), catching operators the kernel *adds*; **(6)** the **RT-semantics ledger** ([`docs/RT-SEMANTICS-LEDGER.md`](docs/RT-SEMANTICS-LEDGER.md)) — every class of the kernel's runtime evaluation core (`kernel-core-runtime` `…internal.core`) classified (mined / already-locked / canonical / infrastructure / out-of-scope / queued), CI-locked by `adapter.RtSemanticsLedgerTest`, so *behavioral* semantics are drained from the source proactively, each fact law-locked (source-read proposes, law test confirms); **(7)** the **grammar-production ledger** ([`docs/GRAMMAR-LEDGER.md`](docs/GRAMMAR-LEDGER.md)) — every parser production of the condition grammar classified (`GrammarProductionLedgerTest`, opt-in vs the sibling `../a12-kernel` checkout), catching syntax *shapes* no keyword or construct enum reveals. **When the kernel (or `a12-kernel-mm`) changes, follow [`docs/KERNEL-UPGRADE.md`](docs/KERNEL-UPGRADE.md)** — the coupling map (each guardian ↔ what its failure means ↔ the realignment), the bump procedure, and the dry-run negative-controls. Guiding split (F11): quiet tolerance at runtime, loud detection at build.
- A finding is only "done" when it's documented. When a new fact **contradicts** an existing note, update that note — don't leave stale claims.
- **A full doc sweep includes a laws-and-findings pass, not just prose.** Besides the regular stale-claim check, sweep specifically for: **(1)** stale `KERNEL-FINDINGS.md` claims — every "deferred / not yet / no … yet / rides feature X" must be re-verified against the actual code + tests (these accumulate: a feature lands but the finding that called it "deferred" doesn't get flipped — e.g. enum-vs-enum, `FirstFilledValue`, `$` correlation all drifted); **(2)** the same for the `MVK-LEDGER` classifications and `KERNEL-INTEGRATION-NOTES`; **(3)** the **two law tiers** for *gaps* — a behavior implemented without a `validate/laws` (accept/reject) or `adapter/laws` (fires/does-not-fire) lock is an unguarded fact; **(4)** **cross-check kernel-behavior findings against the kernel-team oracles** — `KERNEL-SEMANTICS.md` and the merged BA doc `kernel-ba.md` (which covers nearly the whole DSL and reliably surfaces both missing findings and missing examples). Verify each candidate before "fixing" it — don't swap one false claim for another.
- **After any substantive change, state which docs need updating** (the design / notes / README status / this file) and update them in the same change.
- **[`docs/ARCHITECTURE.md`](docs/ARCHITECTURE.md) is the *living structural view* — update it in the same commit as a *structural* change, and never let roadmap/status creep back in.** It describes the system **as it is today**: the component map, the Gradle units + dependency edges, the package layering (`dm.core` + the sibling kits `dm.rulekit ⊥ dm.modelkit` + `dm.edit`), the N8/D15 kernel boundary, and the CLI (picocli, the self-describing surface, native-image, the eval/probe harnesses). **Triggers:** a new module / package group, a moved boundary, a renamed kit, a changed dependency edge, a new CLI verb family, a native-build change → update ARCHITECTURE.md in that commit. **Why it rotted before (don't repeat it):** it carried a "Proposed components (TBD)" section + per-phase `✅` status columns — *dispositions*, which go false the moment work ships and which no one flips because the doc wasn't in the commit reflex (the "rationale is timeless; a disposition is status" trap). So: **no roadmap, no "proposed/TBD/Phase," no status columns here** — planned structure lives in `PROJECT-DESIGN §16` or the ledgers; don't enumerate what a derived surface already lists (`manifest` for verbs, git for status) — point at it. Full discipline: ARCHITECTURE.md §7.
- **Write docs like a human, not a changelog.** This holds for *all* docs — README, the design, the specs, the findings/notes. Favor a clear, scannable voice: avoid long paragraphs that string facts together with semicolons or em-dash chains — break them into **lists or tables**. `README.md` is the strictest case (it's the first doc a newcomer reads, so keep it a snapshot that points at the canonical docs rather than restating them), but the same readability bar applies everywhere prose is meant to be *read*. The one exception is the **structured, machine-checkable trackers an agent maintains** — the MVK / RT-semantics / grammar ledgers and similar — where a terse, regular shape is the point; leave those dense.
- **Reach for visuals when they out-scan prose — tables and diagrams, not walls of text.** If you'd sketch a box-and-arrow or jot a table while *explaining* something live, put that in the doc — don't transcribe it back into paragraphs. Use a **table** for comparisons, matrices, or parallel-structured facts (options × criteria, param × meaning, boundary × payload, who-builds-what × when); use an **ASCII diagram** (or mermaid where the surface renders it) for layering, data flow, topology, or state — the things a reader pictures spatially. Keep prose for the **rationale/argument** (the *why*), which doesn't tabulate. The bar: a visual must out-scan the paragraph it replaces and stay maintainable (ASCII travels everywhere and doesn't rot; don't hand-draw something fragile). Applies to all user-facing docs (README strictest). Reference example: [`docs/EVAL-SPEC.md`](docs/EVAL-SPEC.md) §8c — a layer diagram + boundary/parameter tables instead of three prose paragraphs.
- **Formalization discipline: match the representation to the knowledge kind, and formalize only when a consumer exists** (decided 2026-06-05). The document-model knowhow isn't homogeneous — don't ask "prose vs formal," ask *what representation per kind*: operator/structural **vocabulary** → a self-verifying machine-readable catalog (the `operators.json`/`OperatorCatalog` model, served via the CLI); **structural validity** → derive from the kernel's own oracles (MM_ metamodels / `BasicConsistencyCheck`) and make illegal states unrepresentable in the typed builder; **behavioral semantics** (empty-as-0, polarity, path walk-up) → *executable runtime laws* (`adapter/.../laws/…LawsTest` via the `RuntimeLaws` oracle — fires/does-not-fire on real data; distinct from the accept/reject `validate/laws/`) that the build can't let go stale; **rationale/the *why*** → stays prose (it doesn't tabulate). The governing test before formalizing any fact: **a consumer must exist** (the tool, the LLM, or a CI gate) — formalization that only feeds other formalization is cost without payoff and rots worse than prose. Full reasoning, the five options with trade-offs, and the per-kind gradient: [`docs/PROJECT-DESIGN.md`](docs/PROJECT-DESIGN.md) §21B/§21D.
- **Specs hold the stable method; measured results live in a dated log.** Keep time-stamped, churny *results* out of spec docs — a spec is the fixed contract (method, scoring, task definitions), not a changelog of runs. Eval/benchmark results go in **[`eval/RESULTS.md`](eval/RESULTS.md)** (dated + time-of-day, newest first — we run several a day); `docs/EVAL-SPEC.md` just points to it. `eval/RESULTS.md` lives outside `docs/`, so it's indexed from both `docs/README.md` and here rather than only the docs index.
- **Docs travel inside the feature commit, never after it.** Before committing a feature: update the affected docs — for a **DSL/API** capability make its [`API-GUIDE`](docs/API-GUIDE.md) snippet real (test-backed) and, if it's a design observation worth keeping, record a finding in [`API-FINDINGS`](docs/API-FINDINGS.md), for a **CLI-tool** feature update [`CLI-SPEC`](docs/CLI-SPEC.md)/[`CLI-CONFORMANCE-SPEC`](docs/CLI-CONFORMANCE-SPEC.md) + the CLI tour instead (the API scope rule below) — add any kernel-fact note, mark the corpus backlog — and **sweep the touched docs for stale claims**, then commit code + docs together. A shipped feature is recorded by being **documented + demonstrated + committed**, not by a separate status entry (the per-feature status board was retired 2026-06-19 — see the status-surface bullet below). No separate "docs: refresh" commits trailing a feature.
- **A user-facing capability lands in its living surface(s) — keep them current in the same commit.** (1) If it's a **DSL/API** capability, showcase it in [`docs/API-GUIDE.md`](docs/API-GUIDE.md) (a real, test-backed TYPED-builder snippet) **and**, if it's a design observation worth keeping, record a finding in [`docs/API-FINDINGS.md`](docs/API-FINDINGS.md) — a CLI-*only* feature is *not* showcased in the guide (it's documented in the CLI specs; see the API scope rule below). **A *canonical* guide snippet should be CI-locked verbatim to its run test** — wrap the showable lines of a passing test in `// tag::<id>[]` … `// end::<id>[]`, mark the doc fence with `<!-- snippet: <id> -->`, and register a `Lock` row in `DocSnippetFreshnessTest` (the test region is canonical, the doc mirrors it; mechanism + lifecycle in [`docs/TESTING-SPEC.md`](docs/TESTING-SPEC.md) "Locked doc snippets"). Teasers with `…` elisions stay hand-maintained. (2) **Whenever a CLI verb is added or its surface changes**, update **and re-verify** the showboat demos in [`../examples/`](examples/) (per [`docs/CLI-TOUR-SPEC.md`](docs/CLI-TOUR-SPEC.md)) — they are **CI-gated and drift** (e.g. a new verb shifts the `manifest` list, which breaks `cli-tour`'s captured block); extend the right demo, run **`./scripts/verify-demos.sh`** (builds installDist + runs `showboat verify` on every *discovered* demo — the local equivalent of the CI gate, in one command) until green, add it to the CI gate (`.github/workflows/ci.yml`), and flip the CLI-TOUR backlog row. **What the demos are for — and what they are NOT:** they do **not** serve cold-agent discoverability — the **N6 cold agent never sees `examples/`** (its material boundary is the binary alone, or binary + skill; never the repo/docs/examples). Making the CLI self-explaining *to that agent* is the self-describing surface's job (`manifest`/`--help`/`schema`/diagnostics — the **Self-explaining surface** standing requirement above; the cold agent's only "demonstration" is the binary describing itself, e.g. a read verb echoing its own output shape). The `examples/` demos exist for two *different* audiences: a **CI drift-guard** (the captured output must keep matching the live CLI, so a behavior regression fails the gate) and a **repo-equipped reader** — a human, or an agent handed the repo — learning the verb worked end-to-end. Update them for *those* reasons; don't justify them by cold-agent self-sufficiency (that's the binary's job, verified separately). **The showboat gate is CI-only, so a high-churn value a demo *pins* (the `manifest` verb list, the `diagnostics` count) can drift in a *local* commit and sit there with CI red, unnoticed — it did: adding two `RkCode` codes shifted the tour's `diagnostics` count 31→33 without a regenerate, undetected until a later session.** So every value a demo pins from live code needs a **local** lock in `:cli:test`, not just the CI demo: the verb list is locked by `ManifestVerbTest.EXPECTED_VERBS`, the diagnostics count by `CliTourFreshnessTest` (runs the real verb in-process, compares to the tour's capture, fails the inner loop naming the regen command). Add such an inner-loop guard whenever a demo starts pinning a new live-derived value. **A broader, second drift class is an output-SHAPE change — a verb now echoes a new field or changes a payload, so the whole captured block moves, not one pinned scalar (it bit us twice silently: `field read` gaining the per-kind config block, and the missing-target read becoming a structured `refused` envelope — both shipped with CI red until a later session).** No single `:cli:test` lock catches a whole-block change, so the guard is *running the demos*: **after ANY change to a verb's output shape / behavior / diagnostics, run `./scripts/verify-demos.sh` before committing** (it discovers every demo, so it can't itself go stale). Treat it like the build — green demos are part of "done," not a post-commit chore.
- **Index/README surfaces drift silently — update the index in the same commit that changes what it indexes (learned: `examples/README.md` + `eval/README.md` + `scripts/README.md` all went stale).** A README that *lists or schema-describes* a directory is a derived surface with no compiler/test to catch drift, so name it in the trigger or it rots: **(a)** add/rename/remove a **demo** → update the demo table in [`examples/README.md`](examples/README.md) **and** the CI-gate list (`.github/workflows/ci.yml`) **and** the CLI-TOUR backlog (above); **(b)** change the **eval corpus** — **(b1)** add/rename/remove/change a **task** → update its row in the per-task catalog [`eval/TASKS.md`](eval/TASKS.md) **in the same commit** (hand-maintained, no drift guard — this is the surface that rots; a new *family* also needs `benchmark.workflow.js` + `EvalGoldOracleTest` wiring); **(b2)** change the **layout / filenames / task-schema fields** → update [`eval/README.md`](eval/README.md) (Layout + Task-schema — the *shapes*, not the inventory) **and** the recursive `eval/tasks/*/*.json` globs in the runner/skill. **Doc-responsibility split (don't duplicate):** [`docs/EVAL-SPEC.md`](docs/EVAL-SPEC.md) = the *method* (no per-task table); `eval/README.md` = schema + gold-shapes + how-to; `eval/TASKS.md` = the per-task inventory; `eval/RESULTS.md` = measured results; **(c)** add/rename/remove a **`scripts/` file** → update the script table in [`scripts/README.md`](scripts/README.md) (this one recurs — don't skip it). Rule of thumb: if you changed *what a directory contains or how it's named/shaped*, grep for the directory path across `*.md`/`*.yml` and fix every index that mentions it.
- **The top-level [`README.md`](README.md) is the project's feature/usage showcase — keep its samples + verb list current, but it is NOT a status board.** It now leads with *what's possible*: the DSL approach, library code samples (rulekit/modelkit/`EditSession` builders), and a grouped `dmtool` verb tour with sample commands. These are **hand-maintained and NOT CI-verified** (unlike the `examples/` demos), so they drift silently — update them in the **same commit** as the change. Triggers:
  - **a CLI verb is added / renamed / removed** → fix the `dmtool` section's sample commands + the demo table (and the `examples/` index per the bullet above);
  - **a library API shown in a sample changes** (a `BoundModel`/`EditSession`/builder signature, a `Dsl.*` entry, `ModelContext`/`KernelAdapter`, a `FieldKind`/enum name) → fix the affected snippet so it would still compile;
  - **a new user-facing capability worth teasing** lands → add a short teaser (a line or a small sample) + a link to its demo/spec;
  - **a rename** (the tool name `dmtool`, a kit name, a verb) → propagate it across the README.
  Rules for the README specifically: **link docs/specs/`examples/`, never impl sources** (`src/…` is too much detail for the front door); keep samples **minimal teasers** and let the CI-gated `examples/` carry the authoritative runnable forms; **no phase/status tables in the README** (the project doesn't track per-feature status; what's built is shown by the docs + the CI-gated `examples/`). **A library code sample must use the TYPED builder, never a raw condition string** — `addRule(m -> m.rule(…).when(m.num(path).lt(0))…)`, not `addRule(…, "FieldFilled(x) And […] < 0", …)`. The string overload is the CLI/`apply` *spec* path (conditions arrive as text); a Java sample that hand-writes the DSL string **undercuts the very thesis the README sells** (typed builder > fragile strings). Mirror the canonical typed example in [`docs/API-GUIDE.md`](docs/API-GUIDE.md) §5b. When unsure a shown sample is still accurate, verify the API/verb against the code (or `dmtool manifest`) before committing.
- **Wrap long `dmtool` CLI calls, and write the bare `dmtool` (never `bin/dmtool`)** — in the README, `examples/`, and docs. (1) **Bare `dmtool`:** displayed commands are what an installed/plugin user types; the repo artifact `bin/dmtool` is not. The `examples/` demos call `dmtool`; their `showboat verify` runs with the repo `bin/` on PATH (`export PATH="$PWD/bin:$PATH"`), where the shim resolves it — so displayed = executed. (2) **Wrap (Cause 1 — long *commands*):** break an invocation whose command portion would scroll (~>90 cols) with trailing `\`, one logical piece per line (`-m <model>`, the `<target> <op>`, each `--flag`, a trailing `| jq …`), continuations indented 2 spaces — it reveals the call structure and reads better. (3) **Leave (Cause 2):** a *short* command followed by a long aligned `# comment` (the width is the comment, not the call) — `\` wouldn't help; comment-only scrolling is fine. Likewise leave long **Java** sample lines and compact shell `>file 2>&1; echo "(exit $?)"; jq …` capture-chains (the call within is already short). (4) **`examples/` are exact-matched:** wrapping a command doesn't change its output, so `verify` stays green; keep *output* narrow with `jq -c '{…}'` projection (output blocks can't be reflowed). Re-verify a touched demo: `export JAVA_HOME="$(/usr/libexec/java_home -v 21)"; export PATH="$PWD/bin:$PATH"; uvx showboat@0.6.1 verify examples/<demo>.md`.
- **User-facing docs (the top-level [`README.md`](README.md) and the [`examples/`](examples/) demos) describe *capability*, never project status or plan.** Keep out roadmap/status phrasing — no "completes the FEATURE-GAPS §3.1 refactor set", no tier labels ("Tier-1/2/3"), no "deferred/parked/remaining/flagship", no "shipped 2026-..", no roadmap/milestone identifiers (a gap-proposal section like `§3.1`, milestones like `M9`/`F8`). Write what the feature *does* and how to use it. A pointer to a **contract/reference spec** is fine — link it by name (`CLI-SPEC §6` for the gate contract, `KERNEL-FINDINGS §10` for a kernel fact, the API study) — because that documents *what/why*, not *when it's scheduled*; the line not to cross is transcribing a roadmap/status. The internal design docs *may* note where a feature sits; user-facing docs never do. (The project no longer keeps a per-feature status board — what's built is shown by the docs + demos + git.) The trap is subtle in a worked demo: end a section with what the verb *did*, not with where it sits on the roadmap.
- **[`docs/API-GUIDE.md`](docs/API-GUIDE.md) is the DSL/API capability guide — it covers the rulekit/modelkit *library* (the typed builder, `DocumentModelDraft`/`EditSession`, the DSL), NOT the `dmtool` CLI tool.** Its narrative + snippets show **API/DSL capabilities**; the numbered **design findings** (the *why*) live in [`docs/API-FINDINGS.md`](docs/API-FINDINGS.md). The CLI tool's own concerns — verbs, the self-describing/conformance/diagnostics harness — are documented in [`docs/CLI-SPEC.md`](docs/CLI-SPEC.md) / [`docs/CLI-CONFORMANCE-SPEC.md`](docs/CLI-CONFORMANCE-SPEC.md) and the CLI tour, **not in the guide** (no `dmtool ...` invocations or CLI-tool meta). **Keep it current:** when a *DSL/API* feature lands, make its guide snippet real (a TYPED-builder snippet, test-backed where possible); when an interesting library usage/idiom emerges, showcase it in the guide; new API ergonomic observations go into the numbered findings list in `API-FINDINGS.md` (it seeds the N1 skill / N6 eval).
- **Doc evolution: the project design stays whole; component *detail* splits out into specs, never the argument** (decided 2026-06-03; reshaped 2026-06-19). [`docs/PROJECT-DESIGN.md`](docs/PROJECT-DESIGN.md) (formerly `PROJECT-PROPOSAL.md`) is **one argument**, densely cross-referenced by stable anchors (`§N`, `Fn`/`Nn`/`Dn`, forks Q1–Q12) — don't split it into per-section files. modelkit's rationale was **folded *in*** as §21 (fork #8), not fragmented out, for the same reason. When a component's design *detail* outgrows its section during implementation, extract a **component spec** (`docs/CATALOG-SPEC.md`, `docs/ADAPTER-SPEC.md`, `docs/CLI-SPEC.md`, …): the spec supersedes the section's *detail*, the section shrinks to intent + a pointer. Revisit a wholesale split only if the design exceeds ~800 lines despite spec extraction.
- **Spec-vs-proposal lifecycle, and the status-surface split** (decided 2026-06-19). The doc-name *suffix* is a contract: a **spec** is a **stable, *implemented*** contract (method / verb surface / I-O — `CLI-SPEC`, `EVAL-SPEC`, `RELEASE-SPEC`); a **proposal** is **intent + rationale *not yet built*** (it graduates to a ledger — or is archived — once its items ship; `docs/archived/` holds the parked/resolved ones); a **ledger** records gaps/facts → where each graduated (`FEATURE-GAPS-LEDGER`, `DEV-API-GAPS-LEDGER`, `MVK-LEDGER`, the RT/grammar ledgers); a **design** is built vision + decision log (`PROJECT-DESIGN`). **The lifecycle:** when a proposal's item *ships*, **graduate its contract into the owning spec in the same commit**, then **retire the proposal** — keep it a proposal if it still holds unbuilt items; once everything graduated, **rename it** (→ `-LEDGER` if it's now a graduation record; fold into the design / `-DESIGN` if it's settled design) or **archive under `docs/archived/`** (resolved/parked — kept as the measurement/decision record). **Never leave a `*-PROPOSAL.md` describing shipped work.** **No per-feature status tracking (decided 2026-06-19):** a shipped feature is recorded by being **documented** (the guide/spec), **demonstrated** (the CI-gated `examples/` demos + the eval), and **committed** (git) — *not* by a hand-maintained status entry, which only duplicates the gated/derived surfaces and drifts. So: no status board, no `🔮→✅` flip-tracking, no graduation tables. What survives is **rationale** — [`docs/API-FINDINGS.md`](docs/API-FINDINGS.md) (the *why* behind the API, cited as `finding N`) and the design's decision log + non-goals — plus the **kernel-coverage ledgers** (MVK / RT / grammar, CI-locked — a different job). Eval results stay in [`eval/RESULTS.md`](eval/RESULTS.md). The design + specs state *intent + contract*; `PROJECT-DESIGN §16` is phasing *intent*, not a ✅ log.
- **Rationale is timeless; a disposition is status (decided 2026-06-19).** A *rationale* note — a finding, a decision, a "why it's built this way" — records a **decision, a tradeoff, a rejected alternative, or a principle** (things that stay true, or become a *superseded* note: "superseded YYYY-MM-DD by … because …", which is itself rationale). It must **not** state a live **disposition** — "X is parked / deferred / not yet / won't be built / low-value / still open / rides feature Y" — because that silently goes **false** the moment the plan changes. It already bit us: findings called *enum-vs-enum* / `FirstFilledValue` / `$` correlation "deferred" after they shipped; D10's module-wall *why* outlived the wall; `DEV-API-GAPS`'s "every item proposed, not built" outlived the shipping of DG1–DG6. **Dispositions belong where stating a plan is the section's job** — a roadmap / backlog / non-goals / open-questions list (dated, expected to change) — or in git; never dressed as a durable *why*. For a decision resting on a *current fact*, **embed its re-open trigger** ("revisit only if X") so the rationale carries its own expiry (the `dmtool serve` non-goal is the model). **Scope: this targets the *evolving-project* docs** (the design, the specs, `API-FINDINGS`, the treatment notes). Docs grounded in the **stable kernel + original material** — `KERNEL-FINDINGS`, the `MVK`/`RT-SEMANTICS`/`GRAMMAR` ledgers, the kernel API survey — describe an external constant, so their rationale doesn't rot from *our* changes; leave them.

## Testing strategy

The conventions below are enforced; the **map of the whole testing approach** (the kinds of test, the two law tiers, the guardians, the corpus harnesses, how to run) lives in [`docs/TESTING-SPEC.md`](docs/TESTING-SPEC.md) — read it to place a new test.

- **Example-based TDD is the primary spec** (red/green) — readable, intent-revealing tests drive each feature.
- **The real kernel is the oracle.** `RuleValidator` + `checkConsistency` confirm that rendered output is actually accepted (F4); N7 runs every catalog example through it.
- **Test layout: one file per operator family; hotspot files never grow** (decided 2026-06-04). A new increment adds a *new* small test file, it does not pile onto a monolith. The split:
  - `dsl/` keeps only the renderer/handle **core** (`RenderConditionTest`: composition, parenthesization, literal quoting, kind checks). Each operator family gets its own file under **`dsl/operators/`** (`PatternConditionTest`, `ValueListConditionTest`, `AggregateConditionTest`, `IterationConditionTest`, `EnumConditionTest`, …) holding that family's render (EN/DE) + handle pre-checks.
  - `validate/` keeps only F4 **mechanics** (`RuleValidatorTest`: injection, round-trip, problem mapping). The kernel-law locks are *executable `KERNEL-FINDINGS.md` entries* in **two tiers**: **accept/reject** (structural validity) under **`validate/laws/`** (core; `…LawsTest`, one per findings section, sharing the `KernelLaws` harness), and **fires/does-not-fire** (runtime *behavior* — polarity, empty-as-0, …) under **`adapter/src/test/.../adapter/laws/`** (the `RuntimeLaws` oracle over `IDocumentRtService.validateFull`; F-LAW). Each `KERNEL-FINDINGS` §/ledger row points at its `…LawsTest` class. Detail: KERNEL-INTEGRATION-NOTES "Runtime behavioral-law oracle".
  - Fixtures load once via the shared **`Fixtures`** util (`subscription()`/`order()`/`…Json()`) — no copied `@BeforeAll`, so a new file costs a few lines. `BoundModel` is an immutable snapshot (F0), safe to share.

- **Running the self-sufficiency eval / benchmark (N6): use the `run-dmtool-eval` skill** (`.claude/skills/`). It loads the protocol guardrails (clean subagent, material boundary, neutral prompts, pinned model, cost model, targeted re-runs) at the moment of running — **don't run the benchmark from memory**, the guardrails are easy to violate silently. Method/rationale: [`docs/EVAL-SPEC.md`](docs/EVAL-SPEC.md); measured results: [`eval/RESULTS.md`](eval/RESULTS.md). (That operator skill is distinct from `skill/SKILL.md`, which is the *material under test* — never give the operator skill to the eval's subagents.)

- **Authoring skills/workflows: put deterministic or permission-gated setup in a committed script the main loop runs — never prompt an agent to do it.** A workflow subagent runs under a restricted permission mode and **cannot self-approve a mutating command** (`rm`/`cp`/`mkdir`), so an agent *prompted* to do setup is non-deterministically denied — and a denied setup the run doesn't hard-check silently corrupts the results (the eval's produce agents mutated committed fixtures this way three times, once even into a commit). The fix pattern: setup lives in a checked-in script (e.g. [`eval/prep-sandbox.sh`](eval/prep-sandbox.sh)) the main loop invokes alongside the build; the workflow only **verifies** (read-only) the precondition and **halts loudly** if it's missing. General rule: **agents for judgment/exploration, scripts for deterministic side-effecting setup.**

## Build

Build with an isolated, public-repos-only Gradle home so the machine's global config (private registry) is bypassed, on JDK 21 — see the README's "Build & test" section. **Simplest: `./build.sh <gradle args>`** — the committed wrapper pins the isolated `GRADLE_USER_HOME` + JDK 21 then runs Gradle, so a bare `./gradlew` can't be silently contaminated by the machine's global `init.d` (root cause: [`docs/KERNEL-INTEGRATION-NOTES.md`](docs/KERNEL-INTEGRATION-NOTES.md) "Build / environment gotchas"). The kernel must first be published to `mavenLocal` via the sibling `a12-kernel-bootstrap` kit.

**Release artifacts (native image, developer jars) and the release procedure are NOT here — they live in [`docs/RELEASE-SPEC.md`](docs/RELEASE-SPEC.md)** (the durable release spec: verification gate + versioning + distribution). **The GraalVM native-image build is its own topic in [`docs/NATIVE-IMAGE-GRAALVM.md`](docs/NATIVE-IMAGE-GRAALVM.md)** (recipe, findings, the reflection/Groovy walls, sizing, status) — consult it before touching the native build; it is currently NOT shippable. Everyday dev build (JVM/tests) stays in the README + above; native-image is release-only and never in the dev inner loop.
