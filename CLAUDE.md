## Eat your own dogfood (the #1 standing requirement, 2026-06-26)

**Be your own consumer of the dmkits, feel the friction, and improve the library on the fly.** Every piece of *internal* code that touches a document model — tests, fixtures, benchmarks, demos, the CLI, the eval harness, the interpreter's differential — is a **first-class consumer of rulekit/modelkit/`dm.edit`** and MUST author through the typed surface a real user would reach for, never reach *around* it for low-level strings. This is the project's central discipline: the kits earn their design by being *used* by their own author.

Concretely, in order of preference, always:

1. **Refs over path strings.** Acquire a typed handle and reuse it — by-path (`m.num("/A/B")`) for an existing element, or **relative navigation off an editor/info** (`s.group("/A").num("B")`, `info.flatten("Lines*/Amount")`) so a path is written **once**, validated at the call site, and type-safe. A repeated string path, a hand-built `"../X/Y"` error path, or a hand-written condition/operation string in *new* internal code is a smell — the ref/editor form exists.
2. **The dmkit's own objects over ad-hoc records.** A rule is a `Rule` (error field + condition are refs; `errorEntityRelPath()`/`render()` are *derived*). A computation is a `Computation` (`computedFieldRelPath()` derived). A model is a `DocumentModelDraft`/`EditSession`. Don't reinvent a local `(group, code, errorRel, cond)` tuple when the typed object carries it and the kernel-canonical rendering for free.
3. **Friction is the most valuable signal — fix it, don't work around it.** When the typed surface is missing something a consumer needs (the editor lacked `flatten`; you couldn't build a `Rule` off an editor without adding it), that gap *is the bug*. Record it dated+timed in [`docs/DEV-API-GAPS.md`](docs/DEV-API-GAPS.md), **extend the library (TDD, clean code), and showcase it in [`docs/API-GUIDE.md`](docs/API-GUIDE.md)** — then use the new capability. Working around a gap with strings hides the very feedback the kit needs. *It is the same project — extending the kit to serve its own consumer is the intended workflow, not scope creep.*

**Fix gaps in ANY component you use — escalate only on a blocker (standing directive, 2026-06-29).** This generalizes rule 3 beyond the dmkits' typed surface to *every* component you reach for — rulekit, modelkit, `dm.core`/`ModelIndex`, the CLI, the interpreter, any internal library: if it has a gap or deficiency that your task exposes, **fix it** (TDD, clean code, lock it, document it in the same commit) rather than working around it. The *only* exception is a genuine **blocker** — something you cannot resolve or decide on your own (a cross-cutting design call, an external/licensing constraint, a change that would break a contract you can't unilaterally change) — and then you **report it first** and wait. A workaround that hides a fixable gap is itself a defect; surface it. (Example, 2026-06-29: `FieldInfo` didn't expose declared field config (min/max/length/pattern), so `model describe` couldn't show bounds — the fix was to extend `ModelIndex`/`FieldInfo`, not to read raw DM-JSON in the CLI.)

The trap this exists to prevent (it bit on 2026-06-26): pattern-matching to *existing* internal code (the by-path `BoundModel.ofJson(...).num(path)` the older `*DiffTest`s use) instead of reading the API for the better idiom (the `EditSession`/`GroupEditor` relative-nav the README/API-GUIDE call the *preferred* idiom). Existing internal code is **not** the spec for how to consume the kit — the API + its guide are. Treat a new internal consumer as a usability test of the library, and report what you learn.

## Self-explaining surface (standing requirement, 2026-06-05)

**Favor a self-explaining, explorable CLI over relying on the N1 skill.** A cold LLM agent — given only the binary — must be able to discover the verbs, their parameters, and what they mean, and to learn each output's shape, *without* the skill. The skill (`skill/SKILL.md`) is the material-under-test for the N6 eval and **must stay as simple as possible**; it teaches judgment (polarity, the traps), not the verb/parameter catalog the tool should describe about itself. So when adding or changing a verb: make it discoverable (help/usage + a machine-readable manifest) and schema-describe its I/O. Discoverability lives in the *tool*, not the skill. Detail + rationale: [`docs/CLI-SPEC.md`](docs/CLI-SPEC.md).

**Which surface does a learned fact go in? (the placement rule.)** A document-model fact lands in exactly **one** home, chosen by *what kind of fact it is* — always the most self-describing surface that can carry it; the skill is the **last** resort. Four lanes:

| The fact is about… | It goes in | Carried as |
|---|---|---|
| **one operator** (a semantic surprise, a constraint, a relation, an example) | the operator catalog `src/main/resources/catalog/operators.json` (served by `dmtool operators <id>`, N7-validated) | a `gotcha` with its `kind` (`SURPRISE`/`AUTHORING`/`RENDERING` — `GotchaKind`), `seeAlso`, `validExample`/`invalidExample{fix}` |
| **one spec/field shape** (a key, its requiredness, allowed values, a co-requirement) | the published JSON schema (`schema <target> <op>`), CI-executed examples | a property `description` / `enum` / required-together prose |
| **one kernel rejection's** meaning + corrective | the diagnostic enricher (`StructuralKernelFix.forCode`/`forMessage`, `RkCode`, the catalog-join) | a `fix`+`explain` that rides the `MVK_*`/`RK_*` itself |
| **cross-cutting judgment**, or a **trap that spans constructs / is no single operator** | the skill `skill/SKILL.md` (the #1-rule discipline applies) | a concise judgment note (polarity, iteration scope, the bilingual `--add-locale` cascade, "is this even a rule?") |

Decision test: *one operator → catalog; one spec field → schema; one error code → enricher; none of those (judgment / a multi-construct trap) → skill.* The skill is the **N6 material-under-test and is measured**, so a fact any of the first three surfaces can carry must **not** go in the skill (it would be cost without reach — and stale-prone). A trap can legitimately appear in **two** lanes when it is hit *before* the diagnostic fires (e.g. the enum locale cascade gets both an enricher hint *and* a skill note — the diagnostic corrects after the failure, the skill prevents it).

### Editing `skill/SKILL.md` — the #1 rule: re-read the whole file, and verify every claim against the live tool (standing requirement, 2026-06-22)

The skill is the **material under test for the N6 eval** — a wrong or stale claim in it is the *worst* class of defect, because it actively misleads every agent that reads it and **only an expensive probe run catches it** (a JUnit guard does not). So **before any edit to `skill/SKILL.md`, two things are mandatory, in order, no exceptions:**

1. **Re-read the WHOLE skill file first** — not just the section you're touching. The skill's sections interlock (e.g. `GroupFilled` is the *per-row* guard in one section but is *rejected* from a model-level scope in another); editing one paragraph in isolation silently contradicts another. You cannot keep it coherent without holding all of it in view.
2. **Check every factual claim against the CURRENT tool/schema/catalogs — run it through the binary.** Every DSL snippet, operator name, error code, path form, and "X is rejected / Y is valid" assertion must be **executed** (`rule check` against a fixture, `dmtool operators <id>`, `dmtool schema …`, `dmtool manifest`) and seen to behave as written. **Nothing in the skill may be stale or unverified.** If you cannot run it, you cannot write it.

This is not optional polish — it is **priority #1** for any skill change. It exists because it was violated: a "wildcard/aggregate paths" edit shipped three wrong claims (`GroupFilled(/Group)` as the valid model-level form; row-count via `NumberOfFilledGroups(/Group)` without the required `*`; "`*` never on a group ref"), none of which had been run through the binary — caught only after the fact. Treat a skill edit like a code change with a failing-build guard you have to satisfy by hand: re-read, verify against the tool, *then* write. (Mechanical guards still apply too: `CommandReferencesResolveTest` resolves command refs, and `scripts/sync-plugin-assets.sh` must re-sync the plugin copies.)

### Schema discipline — no drift, no rot (what triggers a schema check/update)

The published schemas (`cli/.../resources/schema/*.json`) are part of the self-describing surface, so they must never lag the code. Two kinds, two guards — and the rule is: **a change to the thing a schema describes must update that schema in the same commit, and a guard must fail the build if it doesn't.**

| change you make | schema to touch | the guard that catches a lag |
|---|---|---|
| **add/rename a result-envelope key** (`ResultEnvelope`) | `result.schema.json` | `SchemaVerbTest` — every target-first verb's real output keys must be declared in `result.schema` |
| **change a `Diagnostic`/`Where` field** | `diagnostic.schema.json` | `SchemaVerbTest`/`SchemaExamplesGuardTest` (diagnostics in real envelopes conform) |
| **change the rule/computation spec shape** | `add.schema.json` (+ its `examples`) | `SchemaExamplesGuardTest` — the input examples are **executed through the tool** |
| **change the `apply`/`batch` op-record frame or add an op/key** | `apply.schema.json` / `batch.schema.json` (+ `examples`) + the `ApplyCommand.Op` enum's `keys` (field ops single-source `FieldSpec.{ADD,MODIFY}_KEYS`) | `SchemaExamplesGuardTest` — both frame example blocks are CI-executed |
| **add/rename/remove a verb** | nothing by hand for the *contract* — `manifest` + `schema <target> <op>` are **derived from the live picocli tree** (can't drift); but flip `ManifestVerbTest.EXPECTED_VERBS`, add a read-only `verb-examples.json` demonstration (or a reasoned `DEMONSTRATION_PENDING` row), and if the verb takes a rich JSON input, add its input schema + `SchemaCommand.INPUT_OPS` mapping. A new **cross-cutting** verb that returns the result envelope gets a `schema` pointer automatically; one that doesn't (renders an artifact / custom payload) is classified in `SchemaCommand.CONTRACT_EXEMPT` with a reason | `ManifestVerbTest`/`ManifestTreeTest` + **`CliConformanceMatrixTest`** (described · params-described · schema-resolves · demonstrated) + `VerbDemonstrationTest` (executes the example) + **`CommandReferencesResolveTest`** (a **rename** that leaves stale `dmtool …` examples fails here — every command ref must resolve against the live tree, across **both** the in-binary text (help/diagnostics/schema) **and** the command-bearing markdown an agent/installer reads: the source + public READMEs, the canonical `skill/SKILL.md`, the Codex `AGENTS.md` — markdown scanned by code-context, not prose; the tool name is single-sourced as `Cli.TOOL_NAME`); see [`docs/CLI-CONFORMANCE-SPEC.md`](docs/CLI-CONFORMANCE-SPEC.md) "the conformance matrix" + "the two-guard defense" |
| **structure change** (new `FieldKind`, new structure op) | only if it changes a verb's I/O shape (above) | the relevant guard above |

The **no-rot** lever is that **every schema `examples` block is CI-executed through the tool** (`SchemaExamplesGuardTest`) — a stale example actively misleads an agent, so an unverified one cannot ship. The **no-drift** lever is that the *contracts* an agent reads (`manifest`, `schema <target> <op>`) are **derived, not authored** — they recompute from the command tree. When in doubt: add the worked `examples` so the guard executes it; never hand-author a schema fact a guard can't check.

**Native-image side effect of a verb/catalog change (only if shipping native):** the GraalVM native build bundles **captured reflection metadata** that goes stale when the reflective surface changes. A **verb add/rename**, a **new Jackson-deserialized POJO**, or an **`operators.json` change** is one of the re-capture triggers (alongside a kernel bump and a Jackson dep bump). **But the capture is TEST-SUITE-DRIVEN ([`scripts/capture-native-config.sh`](scripts/capture-native-config.sh) runs the `:cli` suite under the agent), so the *operational* trigger is broader than that list: any new/changed test that exercises a new shape stales the metadata too. Practical rule — touched `:cli`/`src` source or tests since the last capture and about to (re)build native? RE-CAPTURE FIRST, then rebuild, then [`scripts/native-gate.sh`](scripts/native-gate.sh).** **#1 hard rule: NEVER run a probe (or ship) on a native image built from metadata older than your changes** — the probe then measures a fiction; [`probe/prep-probe.sh`](probe/prep-probe.sh) enforces it (refuses if the binary is older than any `:cli`/`src` source/test or the bundled metadata). Full trigger table + cadence: [`docs/NATIVE-IMAGE-GRAALVM.md`](docs/NATIVE-IMAGE-GRAALVM.md) §5.1. The native gate is the trip-wire if you forget. (No action on a JVM-only/dev build.)

## Refactoring safety gate (standing requirement, 2026-06-12)

**Before proposing a *new* refactor verb, apply the earns-a-verb bar (CLI-SPEC §6).** A refactoring deserves a first-class verb only when hand-composing it from primitives (`read` + `add`/`remove`/`modify`) is unreliable — it trips **reference fan-out**, **non-trivial mechanical correctness** (path rebasing), or **atomicity/loss**. If none trips, prefer teaching the primitives (schema + diagnostics) to compose correctly — *self-explaining primitives > more verbs*. (This is the standing trigger for "should we add refactor X?" discussions; e.g. `rule/computation move` is deferred under it.) For any refactor we *do* add, the gate below applies.

**Any refactor — now or in the future — checks safety *before* it changes anything; if the specific refactor isn't safe on this model it refuses with rich, corrective diagnostics and mutates nothing; only when safe does it proceed.** We gate the refactor and stay in control — never a best-effort rewrite, never a silent degrade. This generalizes the safe-delete `where-used` gate to the whole Refactor class (rename, move, extract/inline). Two non-negotiables for every refactor:

- **Document the gate well in the md docs** — each refactor's safety preconditions, what it refuses on, and the diagnostics it emits. Its home is [`docs/CLI-SPEC.md`](docs/CLI-SPEC.md) §6; never leave the safety contract implicit in code.
- **Test the refusal** — when a refactor op lands, its refusal path gets a law test proving the gate *fires* on unsafe input (the `adapter/laws` does-fire tier), not just that the happy path works.

An ungated, undocumented, or untested-on-refusal refactor is not shippable. Full principle + per-refactor preconditions: [`docs/CLI-SPEC.md`](docs/CLI-SPEC.md) §6.

## Root-cause generalization (standing requirement, 2026-06-19)

**When you find a defect — from a bug report or a probe — fix the *class*, not the symptom.** Once you know the root cause, **always sweep for every sibling site where the same class can occur** *before* declaring it fixed, and fix them together at the shared root. A symptom-only patch (the one verb/path that was reported) leaves the rest of the class live — that is how whack-a-mole starts.

The drill: **reproduce → root-cause → generalize (enumerate every site of the class) → fix at the shared root → lock with a guard that covers the siblings, not just the reported case.** Worked example: P1 — a raw stack trace from a duplicate `rule add` — root-caused to `RuleValidator.check` letting a kernel conversion exception escape, a path shared by six callers; the fix went in the validator and the guard covers `computation add` too, not only the reported `rule add`. This complements the anti-whack-a-mole mining below (mine constraints proactively) and the probe's proactive loop ([`docs/PROBE-SPEC.md`](docs/PROBE-SPEC.md)).

## Interpreter: built out in-repo; separation by convention + linting (standing requirement, 2026-06-23)

The **`:interpreter`** module is a Kotlin Multiplatform, native-safe rule evaluator (package `…dm.interpreter`) being **grown into the full evaluator in this repo** (decision 2026-06-23, [`docs/INTERPRETER-SPEC.md`](docs/INTERPRETER-SPEC.md) §8; impl in [`docs/INTERPRETER-ARCHITECTURE.md`](docs/INTERPRETER-ARCHITECTURE.md)) — *not* extracted to a sibling repo. The committed goal is a full-blown interpreter serving two consumers: (1) dmtool's **native image** (the `model eval`/`model compute`/`rule eval` verbs the Groovy ceiling bars — acceptance: `examples/cli-runtime.md` runs end-to-end on the native image), and (2) a **standalone Kotlin/JVM + Kotlin/JS library** for any consumer running full **and partial** validation + computations, incl. **single-rule / single-computation** eval. Correctness = agrees with the real kernel — **both its runtime AND codegen strategies** (the differential oracle verifies the runtime half; see the #1 rules §A).

**The goals, with the owner's priorities (decided 2026-06-23):** the interpreter is **(a) feature-complete** (the full operator catalog — scope), **(b) matches kernel semantics/behaviour EXACTLY** (**priority #1**), and **(c) performant** — *good* performance is **priority #1**, *equal-to-or-better-than the kernel* is **priority #2** (a stretch, plausible since we carry no Groovy/codegen). (b) and the "good performance" half of (c) are co-equal #1s and never traded against each other: never sacrifice exactness for speed, nor ship a known-slow (O(N²)) path. The #1-rules section (exact match + clean-room) governs (b); [`docs/INTERPRETER-PERFORMANCE.md`](docs/INTERPRETER-PERFORMANCE.md) governs (c).

**Customization-surface parity is part of (a)+(b) — a #1-priority goal (added 2026-06-27).** *The interpreter must expose, on its API, EVERY customization point the kernel offers* — a customization the kernel honors but the interpreter can't accept is a compatibility gap, NOT a "nice to have." These are the consumer SPIs the kernel takes at runtime/codegen: **custom conditions** (`ICustomCondition` → `CustomCondition`), **custom field types** (`ICustomFieldType` → the predefined-type registry), and the **legal/restricted charset** (the kernel's project-level `legalCodepoints`, e.g. **DIN 91379** for EU public administration → `LegalCharset`, default `BMP`, IF43). Each must (1) have a default that matches the kernel's DM-JSON default (so the differential — which has no project config — stays exact), and (2) accept a consumer-supplied value so the interpreter enforces the SAME restriction the configured kernel would. When you discover a kernel customization the interpreter doesn't surface, that *is* a gap: add the SPI (default-matching), thread it, and lock it. The standing memory note for `CustomCondition` is the first instance of this rule; it generalizes to all customization points. **The surface as of kernel 30.8.1** (re-audit on a [`KERNEL-UPGRADE`](docs/KERNEL-UPGRADE.md)): `DocumentProcessingConfig` = `{languageOfErrorMessages (locale), customConditionFactory, customFieldTypeFactory}` (its `additionalInformation` is deprecated), plus the meta-model `legalCodepoints` (charset) and the `Now`/`Today` clock/timezone — each mapped to a `DmInterpreter` input (`locale` / `customConditions` / `predefinedTypes` / `legalCharset` / `EvalClock`), so the surface is currently complete.

### #1 rules — MATCH kernel semantics EXACTLY, via a clean-room reimplementation (decided 2026-06-23)

The interpreter has **two non-negotiables**, a WHAT and a HOW:

**(A) MATCH kernel semantics EXACTLY — BOTH evaluation strategies (runtime AND codegen).** Every behavior the interpreter produces must equal the real kernel's, bit-for-bit on every legal input. There is no "close enough." A kernel special case that is **observable through the differential** (e.g. the Feb-28 leap-year time-clearing in `AddYears`/`AddMonths`, the scale-19 compare-rescaling, the `MathContext(50)` arithmetic cap) is a **must-match**, never droppable as "obsolete." The "kernel is old — report German-only/obsolete/feature-flagged special cases for review" guidance is **narrow**: only things that are *not observable runtime behavior* are reportable-and-droppable — German message *text* (we use our own, IF3), a dead/feature-flagged code path that never executes, pure editor/rendering cruft. If a behavior changes any differential outcome, match it exactly; only genuinely unreachable/irrelevant cruft is reported for a drop decision.

**"The real kernel" means BOTH of its evaluation strategies — the md-RUNTIME dynamic service (`IDocumentRtService`) AND the Groovy CODE GENERATOR — and the interpreter must match BOTH (clarified 2026-06-27).** Compatibility is NOT "match the differential oracle"; the differential oracle (`RuntimeLaws`/`KernelAdapter`, both the runtime dynamic service) is the *primary verification surface*, but it only proves **runtime**-parity. **Codegen-parity is a co-equal target** that the runtime oracle CANNOT verify — so where a behavior lives in codegen, confirm it from the **codegen source** (`kernel-core-codegen-*`) and lock it against codegen-derived expectations. The two strategies can DIVERGE (a kernel fact to characterize, not ignore): if they differ on a legal input, the interpreter matches the **production codegen** behavior, and the runtime-only differential must explicitly carve out the divergent code (it cannot gate it). The **one place a behavior is legitimately droppable is when it is DEAD in *both* strategies** — generated by neither the runtime autogen service nor the codegen (proven from source, not assumed). Worked precedent (2026-06-27): the multi-select value-uniqueness `FEHLER_MULTI_SELECT`/`uniqueValue` is dead in 30.8.1 — `AutogeneratedRulesService` has no multi-select method (runtime) AND no `IAutogeneratedRule.getGenerationType()` returns `UNIQUE_VALUE`, so `CodeGenRuleDefinition`'s `case UNIQUE_VALUE` is unreachable (codegen) — so the interpreter does NOT fire it, matching both (KERNEL-FINDINGS "multi-select value uniqueness is DEAD code"; the sibling of the dead `mandatoryGroup`).

**(B) Clean-room reimplementation, NEVER kernel delegation (the license boundary).** Reimplement the kernel's semantics; do not delegate to the kernel, and do not transliterate its source. The reason is **licensing, not preference**: the A12 kernel is **EUPL-1.2** (copyleft) / commercial. A runtime that *uses* the kernel (links/ships/calls it) is a combined work the EUPL copyleft reaches — so it would have to be EUPL (or commercial). The whole point of `:interpreter` is to give dmtool's **native runtime a kernel-FREE engine**, so that runtime carries **no kernel code and is free of the EUPL** (and the kernel's Groovy codegen can't go native anyway — delegation fails the native goal too).

A and B together: *read the kernel source to learn the exact behavior → write original Kotlin that reproduces it exactly → lock it with the differential.* Therefore:

- **Never delegate** operator evaluation to the kernel from the interpreter (no `com.mgmtp.*` call, no JS-kernel binding) — the purity lint enforces the no-link half.
- **Derive each operator from BEHAVIOR, clean-room** — the **differential oracle** (the real kernel as a *black box*: feed inputs, observe outputs) + the public BA/KERNEL-SEMANTICS spec. **Do NOT copy/transliterate the kernel's source expression** (e.g. don't port `BedingungsOperatorHelper`), because a line-by-line port can be a copyright **derivative** that re-attracts the EUPL. Copy the *mechanism/behavior* (not protected), never the *expression* — the standing license-safe rule. **Reading the kernel source is encouraged for *understanding*, not only to audit a divergence** — proactively scan the **operator sources *and* the code-generator sources** to learn an operator's real semantics and surface *surprising special cases* you'd never think to probe blind (e.g. `Now` truncation-to-day, datetime day-rollover, the `Date(...)`/`Time(...)` digit-pattern operand rules). Then the loop is *read source → write original Kotlin → verify against the differential*; the *fix* is never a transliteration.
- The `--kernel` flag (JVM-only, refused in native) is the *only* place dmtool touches the kernel; that JVM distribution is where EUPL/commercial applies. The native/JS runtime stays clean.

**Separation is kept by convention + linting, not a repo wall** — the §7 hygiene rules are mechanically enforced, so don't hand-wave them:
- `:interpreter` carries **no kernel/dmtool dependency** (it is the publishable standalone artifact). The kernel **differential tests stay in `:adapter`** (never in `:interpreter`'s test source), so the module is kernel-free even in test scope.
- The **purity lint** (`:interpreter`'s `verifyInterpreterPurity`, wired into `check`) fails the build on a forbidden import: `commonMain` may not import `java.*`/`com.mgmtp.*`/`groovy.*`; `jvmMain`/`jsMain` may not import `com.mgmtp.*`/`groovy.*`. Run it as part of any `:interpreter` change.
- `:interpreter` never depends on `:`/`:adapter`/`:cli` — they consume it, never the reverse.

Extraction to a sibling repo is now a **future option, not a prerequisite** — do it only if the interpreter earns an independent OSS life/release cadence (§8); the lint keeps that a lift, not a rewrite. Implementation structure: [`docs/INTERPRETER-ARCHITECTURE.md`](docs/INTERPRETER-ARCHITECTURE.md).

### Performance — benchmark on REAL documents, measure against the kernel, invest heavily in groups (standing requirement, decided 2026-06-23)

The interpreter must be **performant on the hard cases**, and performance is **gated, not hoped for**. Three non-negotiables:

- **REAL documents only — benchmarking a shortcut data structure is cheating.** Measure over the production evaluation path: the general `Document` (and the kernel's `IDocument`) built from real DM-JSON models. The spike's `Map`-backed `RepDoc` (O(1) lookups) must **never** be the thing benchmarked — its numbers are a fiction that hides the real complexity. A benchmark that doesn't exercise the real group resolution (parallel index, common-prefix, star) is not a benchmark.
- **Measure AGAINST the kernel, as a regression gate.** The perf benchmark is the twin of the correctness differential and lives in `:adapter` (which has the kernel): for each scenario run BOTH `kernel.validateFull` and `DmInterpreter.validateFull` over the same real instance, record both wall-clocks + the ratio, assert correctness (interp == kernel) AND a time/ratio bound that trips on an O(N²)-class regression.
- **Target the non-obvious group machinery, at scale.** Deeply **nested repeatable groups** (3–4 levels), **parallel iteration** / cross-level (common-prefix) references, **starred aggregates** over large repetition lists, and **many rows (up to 100 000)** — not the flat/obvious cases. "Invest heavily in all things groups": this is where a naive impl is O(N²) and where it matters. Prerequisite: the general `Document`'s O(P) linear-scan lookups must be indexed to O(1)/O(log) first, or 100k rows can't even run.
- **Run on the PURE engine, decoupled from the CLI — cheap to run, very often.** Both the correctness differentials and the perf harness hit the **`DmInterpreter` + `Document` API directly** (kernel via `RuntimeLaws`), never through `dmtool`/`InterpreterEngine`/the loader — no process spawn, no `installDist`, no JSON envelope. A "real document" is the real `Document` *structure* built programmatically in-test, not loaded through the CLI. **Invest heavily in a proper, reusable harness** (scenario abstraction, warmup+repeats+median, ratio-vs-kernel, profile mode) — it gates regressions *and* finds the hotspots.

Method, harness design, benchmark catalog, and the regression-gate mechanics live in [`docs/INTERPRETER-PERFORMANCE.md`](docs/INTERPRETER-PERFORMANCE.md).

### Structure for a future GENERATOR — separate runtime semantics from evaluation strategy (standing requirement, decided 2026-06-23)

We build the **interpreter** now, but must stay flexible to later add a **generator** (the kernel's approach: emit code per model instead of tree-walking). **Both an interpreter and a generator are evaluation *strategies* that delegate to the SAME runtime** — the operator implementations. So **don't implement the generator, but keep the layering ready for it**:

- **Layer the engine as: data-access → runtime operator semantics → strategy.** (1) **Data access** = `EvalContext`/`Document` (`field`/`filled`/`signed`/`star`/`reps`). (2) **Runtime operator semantics** = pure, AST-walk-agnostic functions over *resolved* values (`Val`/`Tri`/`Fill`): 3VL `and`/`or`, directional number compare, `quantifierFires`, the date/time math (`DateMath`), aggregates, value-list, pattern. (3) **Strategy** = the interpreter's tree-walk *today*; a generator that emits code *later* — both consume (1)+(2). This mirrors the kernel exactly: its codegen emits Groovy that calls `BedingungsOperatorHelper`/`ValidierungsErgebnis`/`Combiner` (the runtime).
- **The rule that keeps it ready:** operator semantics must **not** be inlined into the tree-walk or depend on "I am walking an AST" — they live in the shared runtime layer as pure functions a generated program could call just as the interpreter does. `DateMath` and the `PredicateOp`/`FunctionOp` registries already are; the comparison/3VL/aggregate logic in `Interpreter` should migrate there as it's touched. When adding an operator, put its *semantics* in the runtime layer, and let the strategy only **dispatch + resolve operands**.
- Detail + the target layer diagram: [`docs/INTERPRETER-FINDINGS.md`](docs/INTERPRETER-FINDINGS.md) IF10. The extraction of today's inlined semantics is a tracked refactor, not a prerequisite for more operators.

## Coding style — make full use of Java 21

Write idiomatic modern Java 21, not Java 8 with newer syntax:
- **Records** for immutable data (AST nodes, value objects, results). **Sealed interfaces + exhaustive pattern-matching `switch`** for closed hierarchies — model the AST this way and let the renderer/visitors dispatch with a switch that the compiler proves exhaustive (no `default`). See PROJECT-DESIGN §18.5.
- Record/`instanceof` **deconstruction patterns**, `var` for obvious locals, **text blocks** for multi-line strings (DM-JSON fixtures, expected output), enhanced `switch` expressions, `Optional` over nulls in APIs, `List.of`/`List.copyOf` for immutability.
- Prefer making illegal states unrepresentable in the type system over runtime checks — that is the whole point of the typed builder.
- **Clean code is non-negotiable — never knowingly write a code smell, and if you spot one (even pre-existing), stop, report it immediately, and provide the fix.** Reach for the idiomatic Java-21 construct over the expedient shortcut (the items above), make illegal states unrepresentable, and when a structure *scales across increments* do an explicit refactor pass rather than letting duplication accrete behind green tests. (Smells bite worst when they creep in incrementally — e.g. the string-keyed dispatch for a closed set that crept into `ApplyCommand`, since fixed with an enum + exhaustive `switch`.)
- **Javadoc `*/` trap:** never write a literal `*/` inside a Javadoc block comment — most often a wildcard path in `{@code …}` like `Group*/field` — it ends the comment early and breaks compilation. Reword (e.g. "the flatten of `Group*` then `field`", or a space: `Group* / field`). This recurs whenever documenting repetition-list syntax.

- **User-facing docs (the top-level [`README.md`](README.md) and the [`examples/`](examples/) demos) describe *capability*, never project status or plan.** Keep out roadmap/status phrasing — no "completes the FEATURE-GAPS refactor set", no tier labels ("Tier-1/2/3"), no "deferred/parked/remaining/flagship", no "shipped 2026-..", no roadmap/milestone identifiers (a gap-proposal section like `§3.1`, milestones like `M9`/`F8`). Write what the feature *does* and how to use it. A pointer to a **contract/reference spec** is fine — link it by name (`CLI-SPEC §6` for the gate contract, `KERNEL-FINDINGS §10` for a kernel fact, the API study) — because that documents *what/why*, not *when it's scheduled*; the line not to cross is transcribing a roadmap/status. The internal design docs *may* note where a feature sits; user-facing docs never do. (The project no longer keeps a per-feature status board — what's built is shown by the docs + demos + git.) The trap is subtle in a worked demo: end a section with what the verb *did*, not with where it sits on the roadmap.
- **[`docs/API-GUIDE.md`](docs/API-GUIDE.md) is the DSL/API capability guide — it covers the rulekit/modelkit *library* (the typed builder, `DocumentModelDraft`/`EditSession`, the DSL), NOT the `dmtool` CLI tool.** Its narrative + snippets show **API/DSL capabilities**; the numbered **design findings** (the *why*) live in [`docs/API-FINDINGS.md`](docs/API-FINDINGS.md). The CLI tool's own concerns — verbs, the self-describing/conformance/diagnostics harness — are documented in [`docs/CLI-SPEC.md`](docs/CLI-SPEC.md) / [`docs/CLI-CONFORMANCE-SPEC.md`](docs/CLI-CONFORMANCE-SPEC.md) and the CLI tour, **not in the guide** (no `dmtool ...` invocations or CLI-tool meta). **Keep it current:** when a *DSL/API* feature lands, make its guide snippet real (a TYPED-builder snippet, test-backed where possible); when an interesting library usage/idiom emerges, showcase it in the guide; new API ergonomic observations go into the numbered findings list in `API-FINDINGS.md` (it seeds the N1 skill / N6 eval).
- **Doc evolution: the project design stays whole; component *detail* splits out into specs, never the argument** (decided 2026-06-03; reshaped 2026-06-19). [`docs/PROJECT-DESIGN.md`](docs/PROJECT-DESIGN.md) (formerly `PROJECT-PROPOSAL.md`) is **one argument**, densely cross-referenced by stable anchors (`§N`, `Fn`/`Nn`/`Dn`, forks Q1–Q12) — don't split it into per-section files. modelkit's rationale was **folded *in*** as §21 (fork #8), not fragmented out, for the same reason. When a component's design *detail* outgrows its section during implementation, extract a **component spec** (`docs/CATALOG-SPEC.md`, `docs/ADAPTER-SPEC.md`, `docs/CLI-SPEC.md`, …): the spec supersedes the section's *detail*, the section shrinks to intent + a pointer. Revisit a wholesale split only if the design exceeds ~800 lines despite spec extraction.
- **Spec-vs-proposal lifecycle, and the status-surface split** (decided 2026-06-19). The doc-name *suffix* is a contract: a **spec** is a **stable, *implemented*** contract (method / verb surface / I-O — `CLI-SPEC`, `EVAL-SPEC`, `RELEASE-SPEC`); a **proposal** is **intent + rationale *not yet built*** (it graduates to a ledger — or is archived — once its items ship; `docs/archived/` holds the parked/resolved ones); the suffix is self-describing (the 2026-07-06 `-GAPS` rename): a **`-GAPS` doc** (`FEATURE-GAPS`, `DEV-API-GAPS`, `INTERPRETER-GAPS`, `SCHEMAKIT-GAPS`, `MODEL-REVIEW-GAPS`) tracks only OPEN/deferred/out-of-scope items — a **fixed gap is DELETED, never kept as a "shipped"/"graduated" list** (git is the *what/when*; the gap's API-FINDINGS finding or CLI-SPEC section is the *why* — and findings back-reference the `Gn`/`DGn` so refs still resolve); a **`-LEDGER`** is the opposite instrument — a complete, CI-locked classification of an external constant (`MVK-LEDGER`, the RT/grammar ledgers: every kernel code/class/production), so it **keeps every row forever** by design (not gap history). A **design** is built vision + decision log (`PROJECT-DESIGN`). **The lifecycle:** when a proposal's item *ships*, **graduate its contract into the owning spec in the same commit**, then **retire the proposal** — keep it a proposal if it still holds unbuilt items; once everything graduated, **rename it** (→ `-GAPS` if it still tracks open gaps; fold into the design / `-DESIGN` if it's settled design) or **archive under `docs/archived/`** (resolved/parked — kept as the measurement/decision record). **Never leave a `*-PROPOSAL.md` describing shipped work.** **No per-feature status tracking (decided 2026-06-19):** a shipped feature is recorded by being **documented** (the guide/spec), **demonstrated** (the CI-gated `examples/` demos + the eval), and **committed** (git) — *not* by a hand-maintained status entry, which only duplicates the gated/derived surfaces and drifts. So: no status board, no `🔮→✅` flip-tracking, no graduation tables. What survives is **rationale** — [`docs/API-FINDINGS.md`](docs/API-FINDINGS.md) (the *why* behind the API, cited as `finding N`) and the design's decision log + non-goals — plus the **kernel-coverage ledgers** (MVK / RT / grammar, CI-locked — a different job). Eval results stay in [`eval/RESULTS.md`](eval/RESULTS.md). The design + specs state *intent + contract*; `PROJECT-DESIGN §16` is phasing *intent*, not a ✅ log.
- **Rationale is timeless; a disposition is status (decided 2026-06-19).** A *rationale* note — a finding, a decision, a "why it's built this way" — records a **decision, a tradeoff, a rejected alternative, or a principle** (things that stay true, or become a *superseded* note: "superseded YYYY-MM-DD by … because …", which is itself rationale). It must **not** state a live **disposition** — "X is parked / deferred / not yet / won't be built / low-value / still open / rides feature Y" — because that silently goes **false** the moment the plan changes. It already bit us: findings called *enum-vs-enum* / `FirstFilledValue` / `$` correlation "deferred" after they shipped; D10's module-wall *why* outlived the wall; `DEV-API-GAPS`'s "every item proposed, not built" outlived the shipping of DG1–DG6. **Dispositions belong where stating a plan is the section's job** — a roadmap / backlog / non-goals / open-questions list (dated, expected to change) — or in git; never dressed as a durable *why*. For a decision resting on a *current fact*, **embed its re-open trigger** ("revisit only if X") so the rationale carries its own expiry (the `dmtool serve` non-goal is the model). **Scope: this targets the *evolving-project* docs** (the design, the specs, `API-FINDINGS`, the treatment notes). Docs grounded in the **stable kernel + original material** — `KERNEL-FINDINGS`, the `MVK`/`RT-SEMANTICS`/`GRAMMAR` ledgers, the kernel API survey — describe an external constant, so their rationale doesn't rot from *our* changes; leave them.

## Testing strategy

The conventions below are enforced; the **map of the whole testing approach** (the kinds of test, the two law tiers, the guardians, the corpus harnesses, how to run) lives in [`docs/TESTING-SPEC.md`](docs/TESTING-SPEC.md) — read it to place a new test.

- **Example-based TDD is the primary spec** (red/green) — readable, intent-revealing tests drive each feature.
- **The real kernel is the oracle.** `RuleValidator` + `checkConsistency` confirm that rendered output is actually accepted (F4); N7 runs every catalog example through it.
- **Test layout: one file per operator family; hotspot files never grow** (decided 2026-06-04). A new increment adds a *new* small test file, it does not pile onto a monolith. The split:
  - `dsl/` keeps only the renderer/handle **core** (`RenderConditionTest`: composition, parenthesization, literal quoting, kind checks). Each operator family gets its own file under **`dsl/operators/`** (`PatternConditionTest`, `ValueListConditionTest`, `AggregateConditionTest`, `IterationConditionTest`, `EnumConditionTest`, …) holding that family's render (EN/DE) + handle pre-checks.
  - `validate/` keeps only F4 **mechanics** (`RuleValidatorTest`: injection, round-trip, problem mapping). The kernel-law locks are *executable `KERNEL-FINDINGS.md` entries* in **two tiers**: **accept/reject** (structural validity) under **`validate/laws/`** (core; `…LawsTest`, one per findings section, sharing the `KernelLaws` harness), and **fires/does-not-fire** (runtime *behavior* — polarity, empty-as-0, …) under **`adapter/src/test/.../adapter/laws/`** (the `RuntimeLaws` oracle over `IDocumentRtService.validateFull`; F-LAW). Each `KERNEL-FINDINGS` §/ledger row points at its `…LawsTest` class. Detail: KERNEL-INTEGRATION-NOTES "Runtime behavioral-law oracle".
  - Fixtures load once via the shared **`Fixtures`** util (`subscription()`/`order()`/`…Json()`) — no copied `@BeforeAll`, so a new file costs a few lines. `BoundModel` is an immutable snapshot (F0), safe to share.

- **Keep test-task dependencies slim and specific — a test that reads a repo file at runtime declares that file as an input on a task scoped to *just* that test, never on the broad suite** (standing requirement, 2026-06-30). Gradle inputs are per-task: declaring a doc/demo on the whole `:cli:test` re-runs all ~620 tests on any `.md` edit; *omitting* it lets the task go up-to-date / restore from the build cache into a **false green** locally while CI (fresh) fails. The pattern — the doc-reading guards (`CliTourFreshnessTest`, `CommandReferencesResolveTest`) run in a dedicated `docGuardTest` task with exactly those files as its inputs, and `test dependsOn docGuardTest` (so CI + the `-PrkNativeAgent` capture still drive them). Detail: [`docs/TESTING-SPEC.md`](docs/TESTING-SPEC.md) "Tests that read repo files at runtime".

- **Running the self-sufficiency eval / benchmark (N6): use the `run-dmtool-eval` skill** (`.claude/skills/`). It loads the protocol guardrails (clean subagent, material boundary, neutral prompts, pinned model, cost model, targeted re-runs) at the moment of running — **don't run the benchmark from memory**, the guardrails are easy to violate silently. Method/rationale: [`docs/EVAL-SPEC.md`](docs/EVAL-SPEC.md); measured results: [`eval/RESULTS.md`](eval/RESULTS.md). (That operator skill is distinct from `skill/SKILL.md`, which is the *material under test* — never give the operator skill to the eval's subagents.)

- **Authoring skills/workflows: put deterministic or permission-gated setup in a committed script the main loop runs — never prompt an agent to do it.** A workflow subagent runs under a restricted permission mode and **cannot self-approve a mutating command** (`rm`/`cp`/`mkdir`), so an agent *prompted* to do setup is non-deterministically denied — and a denied setup the run doesn't hard-check silently corrupts the results (the eval's produce agents mutated committed fixtures this way three times, once even into a commit). The fix pattern: setup lives in a checked-in script (e.g. [`eval/prep-sandbox.sh`](eval/prep-sandbox.sh)) the main loop invokes alongside the build; the workflow only **verifies** (read-only) the precondition and **halts loudly** if it's missing. General rule: **agents for judgment/exploration, scripts for deterministic side-effecting setup.**

## Build

Build with an isolated, public-repos-only Gradle home so the machine's global config (private registry) is bypassed, on JDK 21 — see the README's "Build & test" section. **Simplest: `./build.sh <gradle args>`** — the committed wrapper pins the isolated `GRADLE_USER_HOME` + JDK 21 then runs Gradle, so a bare `./gradlew` can't be silently contaminated by the machine's global `init.d` (root cause: [`docs/KERNEL-INTEGRATION-NOTES.md`](docs/KERNEL-INTEGRATION-NOTES.md) "Build / environment gotchas"). The kernel must first be published to `mavenLocal` via the sibling `a12-kernel-bootstrap` kit.

**Inner loop: run TARGETED tests, not the full suite, for each minor change (standing requirement, 2026-06-24).** The full `./build.sh :interpreter:check :adapter:test :cli:test` (+ `scripts/verify-demos.sh`, which rebuilds `installDist`) takes **>1 min** and slows development when run after every small edit. While iterating, run a **single test class** — `./build.sh :adapter:test --tests "<FqcnOrPattern>"` (one `*DiffTest`/fuzz class is ~3–7 s), or `:interpreter:check` alone when only `:interpreter` changed. Reserve the **full suite + `verify-demos.sh`** for **strategic checkpoints**: right before a commit, after a structural/parser change, or when a verb's output shape changed (only then do the demos matter — otherwise skip them).

**Capturing a long build/test run: redirect the FULL output to a file, then grep the file — NEVER pipe the build through `tail`/`head`/`grep`.** Use `./build.sh --console=plain <args> > build/run.log 2>&1` then `grep -E 'BUILD (SUCCESSFUL|FAILED)|FAILED' build/run.log`. Two traps a pipe hits (the reason [`scripts/perf.sh`](scripts/perf.sh) exists, and the rule generalizes to any long run): a pipe **buffers**, so a backgrounded build's log stays empty until it finishes (polling looks frozen and you can't read it incrementally); and `head`/early-closing readers can **SIGPIPE the build and lose its output** entirely. Writing the raw log to a file fixes both — and a backgrounded run can then be `Read` as it grows. (Lesson codified here, not in agent memory, so it travels across machines.)

**Release/public-mirror boundary (standing guardrail): the public `a12-dmtool-releases` repo is generated output, not a hand-edited working tree.** Never push directly to the mirror or mutate release assets by hand unless the maintainer explicitly asks for emergency mirror surgery after the scripted process failed. Use [`scripts/publish-release.sh`](scripts/publish-release.sh), which assembles the mirror tree, pushes it, creates/uses a draft release, uploads macOS, dispatches the public native build, and flips the draft live. After `--go-live`, treat the GitHub release as immutable by project policy: adding a platform, replacing a binary, changing `SHA256SUMS`, or changing the public workflow for that release means cut a patch release.

**Release artifacts (native image, developer jars) and the release procedure are NOT here — they live in [`docs/RELEASE-SPEC.md`](docs/RELEASE-SPEC.md)** (the durable release spec: verification gate + versioning + distribution). **The GraalVM native-image build is its own topic in [`docs/NATIVE-IMAGE-GRAALVM.md`](docs/NATIVE-IMAGE-GRAALVM.md)** (recipe, findings, the reflection/Groovy walls, sizing, status) — consult it before touching the native build; its **current shippability + residual caveats are tracked there** (§1), not asserted here (so this line can't rot). Everyday dev build (JVM/tests) stays in the README + above; native-image is release-only and never in the dev inner loop.
