## NEVER invent a shape A12 already defines (the #1 interop rule, 2026-07-28)

**Where A12 has an established shape — a wire format, a serialization, a pointer syntax, a domain type — we USE IT. We do not design a parallel one, not "simpler", not "cleaner", not "typed better".** This is a MUST for **`:interpreter` and `dmtool`** (both touch Documents) and applies to any other component that meets an A12 concept. A shape we invent where A12 already has one is a defect on sight, regardless of how well it is implemented or tested.

The rule exists because it was broken badly: the interpreter shipped a `DocumentInputV1` "placement" transport (`{groups:[{path,coordinates}], fields:[{path,coordinates,raw}]}`) alongside A12's real, kernel-serialized Document JSON — a nested object tree, repeating groups as **arrays** with `{}` for empty/sparse rows, native JSON for number/boolean, model-format strings for the date family and enum S-values, key-absent for omitted. Every justification written into that transport turned out to be something A12 already does, and the kernel's own deserializer (`DocumentJsonAndXmlDeserializationInfoImpl`) even runs *our* pipeline — `asText()` → model-driven parse → keep the raw string on conversion failure (`[A12K-3638]`). The root cause was one layer down: we invented a **pointer** representation (`path` + `coordinates[]`) where A12 has `DocumentPointer` with the canonical `Group[1]/Sub[3]/Field` string, and the document transport was built on that invention.

**Before designing any type that crosses our boundary, find the A12 counterpart first** — by SOURCE (`../a12-kernel`), the kernel serializers, the demo, and real documents in the sibling repos. Cite the counterpart you matched, or state explicitly that none exists. "I didn't find one" is only valid after looking; the shapes above were all discoverable. Inventing is legitimate **only** where A12 genuinely has no concept (the `dmtool` CLI result envelope, our conformance-corpus case files) — and that exemption is about *our own tooling surfaces*, never about a domain object A12 owns.

### …and adopt A12's JSON I/O BEHAVIOUR exactly, not just its shape (owner directive, 2026-07-28)

The shape rule above says *what the tree looks like*; this one says *what reading and writing it must do*. Matching the shape while normalizing values differently still produces a document A12 would not have written. The worked case is numbers, where the contract has **three separately load-bearing stages** — parse configuration, read stringification, and write emission — set out with their measurements in [`docs/KERNEL-FINDINGS.md`](docs/KERNEL-FINDINGS.md) "The canonical Document JSON …". Getting one stage right is not enough: a mapper configured for `BigDecimal` still loses the scale if the write stage re-normalizes, and a correct write stage cannot recover a scale the parse already destroyed.

Three rules follow, and they generalize past numbers:

- **Never route a transport value through an evaluation type.** `Dec` carries the kernel's rounding/precision model; a transport must preserve text, so the plain-form conversion is deliberately **lexical**. Reach for a string transformation, not a numeric one.
- **Do not "play safe" by changing the encoding.** Quoting a number to protect its zeros looks safe and *is* a deviation: A12 emits `250.00` unquoted, so quoting breaks read→write identity on genuine A12 documents while fixing nothing (the loss it fears happens at parse time, upstream). Preserve fidelity by configuring the parser, never by re-encoding the value. A string is correct in exactly one place — a value the converter could not parse, which is A12's own pass-through.
- **Oracle a format claim against the format's own implementation.** `A12NumberPlainFormTest` compares our lexical plain form against `java.math.BigDecimal.toPlainString` itself; it immediately caught a hand-derived edge case (`-0e5` is `0`, not `000000`). Specification prose is not the oracle when the real implementation is runnable.

## Language

English is the project default: code, identifiers, comments, docs, and the **default render target** (`DslRenderer` defaults to `ConditionLanguage.EN`) are English. **German is a supported render target, not the default** — the operator catalog carries verified `de` keywords and `new DslRenderer(ConditionLanguage.DE)` renders to it. Translations are welcome; English stays canonical.

### Document terminology

In prose, user interfaces, and document-level APIs, a **DocumentModel** validates a **Document**. Do not call the domain object a “Data Document” or “placement document”; “placement” belongs only to individual location records such as a field value at a model path and repetition coordinate.

## Commits

Automatically commit each finished, verified feature set unless the user explicitly asks not to commit. Never commit partial, failing, or unrelated work. A prompt shortcut that explicitly forbids committing, such as the global `F:` shortcut, remains an exception.

## Eat your own dogfood (the #1 standing requirement, 2026-06-26)

**Be your own consumer of the dmkits, feel the friction, and improve the library on the fly.** Every piece of *internal* code that touches a document model — tests, fixtures, benchmarks, demos, the CLI, the eval harness, the interpreter's differential — is a **first-class consumer of rulekit/modelkit/`dm.edit`** and MUST author through the typed surface a real user would reach for, never reach *around* it for low-level strings. This is the project's central discipline: the kits earn their design by being *used* by their own author.

Concretely, in order of preference, always:

1. **Refs over path strings.** Acquire a typed handle and reuse it — by-path (`m.num("/A/B")`) for an existing element, or **relative navigation off an editor/info** (`s.group("/A").num("B")`, `info.flatten("Lines*/Amount")`) so a path is written **once**, validated at the call site, and type-safe. A repeated string path, a hand-built `"../X/Y"` error path, or a hand-written condition/operation string in *new* internal code is a smell — the ref/editor form exists.
2. **The dmkit's own objects over ad-hoc records.** A rule is a `Rule` (error field + condition are refs; `errorEntityRelPath()`/`render()` are *derived*). A computation is a `Computation` (`computedFieldRelPath()` derived). A model is a `DocumentModelDraft`/`EditSession`. Don't reinvent a local `(group, code, errorRel, cond)` tuple when the typed object carries it and the kernel-canonical rendering for free.
3. **Friction is the most valuable signal — fix it, don't work around it.** When the typed surface is missing something a consumer needs (the editor lacked `flatten`; you couldn't build a `Rule` off an editor without adding it), that gap *is the bug*. Record it dated+timed in [`docs/DEV-API-GAPS.md`](docs/DEV-API-GAPS.md), **extend the library (TDD, clean code), and showcase it in [`docs/API-GUIDE.md`](docs/API-GUIDE.md)** — then use the new capability. Working around a gap with strings hides the very feedback the kit needs. *It is the same project — extending the kit to serve its own consumer is the intended workflow, not scope creep.*

**Fix gaps in ANY component you use — escalate only on a blocker (standing directive, 2026-06-29).** This generalizes rule 3 beyond the dmkits' typed surface to *every* component you reach for — rulekit, modelkit, `dm.core`/`ModelIndex`, the CLI, the interpreter, any internal library: if it has a gap or deficiency that your task exposes, **fix it** (TDD, clean code, lock it, document it in the same commit) rather than working around it. The *only* exception is a genuine **blocker** — something you cannot resolve or decide on your own (a cross-cutting design call, an external/licensing constraint, a change that would break a contract you can't unilaterally change) — and then you **report it first** and wait. A workaround that hides a fixable gap is itself a defect; surface it. (Example, 2026-06-29: `FieldInfo` didn't expose declared field config (min/max/length/pattern), so `model describe` couldn't show bounds — the fix was to extend `ModelIndex`/`FieldInfo`, not to read raw DM-JSON in the CLI.)

Existing internal code is **not** the spec for how to consume the kit — the API + its guide are (the trap that bit once: pattern-matching to older by-path test code instead of the preferred `EditSession` relative-nav idiom). Treat a new internal consumer as a usability test of the library, and report what you learn.

## Self-explaining surface (standing requirement, 2026-06-05)

**Favor a self-explaining, explorable CLI over relying on the N1 skill.** A cold LLM agent — given only the binary — must be able to discover the verbs, their parameters, and what they mean, and to learn each output's shape, *without* the skill. The skill (`skill/SKILL.md`) is the material-under-test for the N6 eval and **must stay as simple as possible**; it teaches judgment (polarity, the traps), not the verb/parameter catalog the tool should describe about itself. So when adding or changing a verb: make it discoverable (help/usage + a machine-readable manifest) and schema-describe its I/O. Discoverability lives in the *tool*, not the skill. Detail + rationale: [`docs/CLI-SPEC.md`](docs/CLI-SPEC.md).

**Which surface does a learned fact go in? (the placement rule.)** A document-model fact lands in exactly **one** home, chosen by *what kind of fact it is* — always the most self-describing surface that can carry it; the skill is the **last** resort. Four lanes:

| The fact is about… | It goes in | Carried as |
|---|---|---|
| **one operator** (a semantic surprise, a constraint, a relation, an example) | the operator catalog `rulekit/src/main/resources/catalog/operators.json` (served by `dmtool operators <id>`, N7-validated) | a `gotcha` with its `kind` (`SURPRISE`/`AUTHORING`/`RENDERING` — `GotchaKind`) and local `seeAlso`; primary `validExample`/`invalidExample{fix}`; plural code-specific `correctives[]` for additional rejection triggers |
| **one spec/field shape** (a key, its requiredness, allowed values, a co-requirement) | the published JSON schema (`schema <target> <op>`), CI-executed examples | a property `description` / `enum` / required-together prose |
| **one kernel rejection's** meaning + corrective | the diagnostic enricher (`StructuralKernelFix.forCode`/`forMessage`, `RkCode`, the catalog-join) | a `fix`+`explain` that rides the `MVK_*`/`RK_*` itself |
| **cross-cutting judgment**, or a **trap that spans constructs / is no single operator** | the skill `skill/SKILL.md` (the #1-rule discipline applies) | a concise judgment note (polarity, iteration scope, the bilingual `--add-locale` cascade, "is this even a rule?") |

Decision test: *one operator → catalog; one spec field → schema; one error code → enricher; none of those (judgment / a multi-construct trap) → skill.* The skill is the **N6 material-under-test and is measured**, so a fact any of the first three surfaces can carry must **not** go in the skill (it would be cost without reach — and stale-prone). A trap can legitimately appear in **two** lanes when it is hit *before* the diagnostic fires (e.g. the enum locale cascade gets both an enricher hint *and* a skill note — the diagnostic corrects after the failure, the skill prevents it).

### Editing `skill/SKILL.md` — the #1 rule: re-read the whole file, and verify every claim against the live tool (standing requirement, 2026-06-22)

The skill is the **material under test for the N6 eval** — a wrong or stale claim in it is the *worst* class of defect, because it actively misleads every agent that reads it and **only an expensive probe run catches it** (a JUnit guard does not). So **before any edit to `skill/SKILL.md`, two things are mandatory, in order, no exceptions:**

1. **Re-read the WHOLE skill file first** — not just the section you're touching. The skill's sections interlock (e.g. `GroupFilled` is the *per-row* guard in one section but is *rejected* from a model-level scope in another); editing one paragraph in isolation silently contradicts another. You cannot keep it coherent without holding all of it in view.
2. **Check every factual claim against the CURRENT tool/schema/catalogs — run it through the binary.** Every DSL snippet, operator name, error code, path form, and "X is rejected / Y is valid" assertion must be **executed** (`rule check` against a fixture, `dmtool operators <id>`, `dmtool schema …`, `dmtool manifest`) and seen to behave as written. **Nothing in the skill may be stale or unverified.** If you cannot run it, you cannot write it. **One class needs a stronger oracle: a RUNTIME-semantics claim** (what fires, how often, where the error attaches) **must be verified against the real KERNEL** (an adapter differential, `CliTestSupport.runKernel`, a laws lock) — `model eval`/`rule eval` run the interpreter, which can carry a known-or-unknown `IG` divergence, so binary-verified ≠ kernel-verified exactly there (the 2026-07-18 IG73 incident: a skill bullet's "fires per row" was binary-true and kernel-false). Accept/reject claims may rest on `rule check` — that *is* the kernel.

This is not optional polish — it is **priority #1** for any skill change; it exists because an unverified edit once shipped three wrong claims, caught only by an expensive probe run. Treat a skill edit like a code change with a failing-build guard you satisfy by hand: re-read, verify against the tool, *then* write. (Mechanical guards still apply: `CommandReferencesResolveTest` resolves command refs; `scripts/sync-plugin-assets.sh` re-syncs the plugin copies.)

### Schema discipline — no drift, no rot (what triggers a schema check/update)

The published schemas (`cli/.../resources/schema/*.json`) are part of the self-describing surface, so they must never lag the code. Two kinds, two guards — and the rule is: **a change to the thing a schema describes must update that schema in the same commit, and a guard must fail the build if it doesn't.**

| change you make | schema to touch | the guard that catches a lag |
|---|---|---|
| **add/rename a result-envelope key** (`ResultEnvelope`) | `result.schema.json` | `ResultEnvelopeFrameTripwireTest` pins the complete frame; `SchemaVerbTest` samples real effective envelope outputs against `result.schema` |
| **change a `Diagnostic`/`Where` field** | `diagnostic.schema.json` | `SchemaVerbTest`/`SchemaExamplesGuardTest` (diagnostics in real envelopes conform) |
| **change the rule/computation spec shape** | `rule-add.schema.json` / `computation-add.schema.json` (+ their `examples`) | `SchemaExamplesGuardTest` — the target-specific input examples are **executed through the tool** |
| **change the `apply`/`batch` op-record frame or add an op/key** | `apply.schema.json` / `batch.schema.json` (+ `examples`) + the `ApplyCommand.Op` enum's `keys` (field ops single-source `FieldSpec.{ADD,MODIFY}_KEYS`) | `SchemaExamplesGuardTest` — both frame example blocks are CI-executed |
| **add/rename/remove a verb** | nothing by hand for the *contract* — `manifest` + `schema <target> <op>` are **derived from the live picocli tree** (can't drift); but flip **`ManifestVerbTest.EXPECTED_VERBS`** — the **single source of the live-leaf denominator**, which `DmtoolPublicContractTest` now derives from rather than pinning its own copy (it carried a second literal, and `mcp` updated one of the two) — add a read-only `verb-examples.json` demonstration (or a reasoned `DEMONSTRATION_PENDING` row), and if the verb takes a rich JSON input, add its input schema + `SchemaCommand.INPUT_OPS` mapping. A new **cross-cutting** verb that returns the result envelope gets a `schema` pointer automatically; one that doesn't (renders an artifact / custom payload) is classified in `SchemaCommand.CONTRACT_EXEMPT` with a reason | `ManifestVerbTest`/`ManifestTreeTest` + **`CliConformanceMatrixTest`** (described · params-described · schema-resolves · demonstrated) + `VerbDemonstrationTest` (executes the example) + **`CommandReferencesResolveTest`** (a **rename** that leaves stale `dmtool …` examples fails here — every command ref must resolve against the live tree, across **both** the in-binary text (help/diagnostics/schema) **and** the command-bearing markdown an agent/installer reads: the source + public READMEs, the canonical `skill/SKILL.md`, the Codex `AGENTS.md` — markdown scanned by code-context, not prose; the tool name is single-sourced as `Cli.TOOL_NAME`) + **`:cli:publicContractTest`**, which `:cli:test` CANNOT run (see the checkpoint note under "Build") and which additionally pins the **return-kind vocabulary** in both `result.schema.json` and `skill/SKILL.md` — a verb introducing a new `returns.kind` must add it to both; see [`docs/CLI-CONFORMANCE-SPEC.md`](docs/CLI-CONFORMANCE-SPEC.md) "the conformance matrix" + "the two-guard defense" |
| **structure change** (new `FieldKind`, new structure op) | only if it changes a verb's I/O shape (above) | the relevant guard above |

The **no-rot** lever is that **every schema `examples` block is CI-executed through the tool** (`SchemaExamplesGuardTest`) — a stale example actively misleads an agent, so an unverified one cannot ship. The **no-drift** lever is that the *contracts* an agent reads (`manifest`, `schema <target> <op>`) are **derived, not authored** — they recompute from the command tree. When in doubt: add the worked `examples` so the guard executes it; never hand-author a schema fact a guard can't check.

**Operational-contract trigger.** Adding or changing a verb's effect, dry-run behavior, failure persistence, aggregate success, output kind, or provenance expectation must update `CommandContracts` in the same commit. Ordinary single-mode leaves derive their profile; every argument-dependent mode needs an explicit selector. `CommandContractsTest` locks the live denominator and the manifest/schema/help projections, while `:cli:publicContractTest` must falsify the claim through the packaged launcher (and the native gate reuses that exact suite against the native artifact).

**Native-image side effect (only if shipping native): STALENESS MUST NEVER HAPPEN, and neither kind is left to judgement.** Two things can lag your source, with different remedies — see [`docs/NATIVE-IMAGE-GRAALVM.md`](docs/NATIVE-IMAGE-GRAALVM.md) §5.1 for the reasoned account of *what* to redo. (a) The **binary** lags on any source change; that is gated by an mtime sweep on **both** consuming paths — [`probe/prep-probe.sh`](probe/prep-probe.sh) before a probe and [`scripts/native-gate.sh`](scripts/native-gate.sh) before a ship (the ship path was ungated until 2026-08-05). (b) The **reflection metadata** is TEST-SUITE-captured and has **no cheap detector** — a reflective site no test reaches is invisible to the capture *and* to the gate's runtime trip-wire, which is exactly the class that shipped five native-only defects (§3.5). Because (b) cannot be checked cheaply, the rule for it is **unconditional, not conditional on your change looking harmless**: about to (re)build native? **RE-CAPTURE FIRST** ([`scripts/capture-native-config.sh`](scripts/capture-native-config.sh)), then rebuild, then the gate. §5.1's trigger table explains which capture script a given change affects; it is never a licence to skip one. Full trigger table + cadence: [`docs/NATIVE-IMAGE-GRAALVM.md`](docs/NATIVE-IMAGE-GRAALVM.md) §5.1. (No action on a JVM-only/dev build.)

## Refactoring safety gate (standing requirement, 2026-06-12)

**Before proposing a *new* refactor verb, apply the earns-a-verb bar (CLI-SPEC §6).** A refactoring deserves a first-class verb only when hand-composing it from primitives (`read` + `add`/`remove`/`modify`) is unreliable — it trips **reference fan-out**, **non-trivial mechanical correctness** (path rebasing), or **atomicity/loss**. If none trips, prefer teaching the primitives (schema + diagnostics) to compose correctly — *self-explaining primitives > more verbs*. (This is the standing trigger for "should we add refactor X?" discussions; e.g. `rule/computation move` is deferred under it.) For any refactor we *do* add, the gate below applies.

**Any refactor — now or in the future — checks safety *before* it changes anything; if the specific refactor isn't safe on this model it refuses with rich, corrective diagnostics and mutates nothing; only when safe does it proceed.** We gate the refactor and stay in control — never a best-effort rewrite, never a silent degrade. This generalizes the safe-delete `where-used` gate to the whole Refactor class (rename, move, extract/inline). Two non-negotiables for every refactor:

- **Document the gate well in the md docs** — each refactor's safety preconditions, what it refuses on, and the diagnostics it emits. Its home is [`docs/CLI-SPEC.md`](docs/CLI-SPEC.md) §6; never leave the safety contract implicit in code.
- **Test the refusal** — when a refactor op lands, its refusal path gets a law test proving the gate *fires* on unsafe input (the `adapter/laws` does-fire tier), not just that the happy path works.

An ungated, undocumented, or untested-on-refusal refactor is not shippable. Full principle + per-refactor preconditions: [`docs/CLI-SPEC.md`](docs/CLI-SPEC.md) §6.

## A client-side refusal needs a measured kernel basis (standing requirement, 2026-07-25)

**Before adding or widening any check that REFUSES input — a builder `throw`, a type-level erasure, a CLI pre-flight — measure that the real kernel refuses the same input, and lock that measurement.** Delegation can only under-report and is safe; a refusal we invent can be *wrong*, and it is invisible precisely because the kernel never gets asked. Three rules:

- **Never broader than its measured basis.** A refusal justified by analogy ("dates ride the date family"), by an error message's wording, or by a comment that says *unverified* is a defect waiting to be found. Both over-rejections the 2026-07-25 audit turned up were exactly this, and in both cases our own source carried the give-away.
- **Check the READ path too.** A refusal in a record's constructor also fires when the adapter converts a kernel model *inbound*, so an over-strict check makes a legal model **unreadable**, not merely unauthorable. That is the sharper half and the reason a read test belongs beside the authoring test.
- **Deliberate over-strictness is allowed — but only with its reason written down.** Being stricter than the kernel is sometimes right (the enum S-value domain check, API-FINDINGS 96). Undocumented, it is indistinguishable from a bug.

A type-level erasure is the same defect one layer earlier and harder to see: no runtime error, just a missing factory, so the shape reads as "not a thing" rather than "refused". The conformance model + the audit's disposition: [`docs/MVK-LEDGER.md`](docs/MVK-LEDGER.md) "What the buckets mean for CONFORMANCE".

## Root-cause generalization (standing requirement, 2026-06-19)

**When you find a defect — from a bug report or a probe — fix the *class*, not the symptom.** Once you know the root cause, **always sweep for every sibling site where the same class can occur** *before* declaring it fixed, and fix them together at the shared root. A symptom-only patch (the one verb/path that was reported) leaves the rest of the class live — that is how whack-a-mole starts.

The drill: **reproduce → root-cause → generalize (enumerate every site of the class) → fix at the shared root → lock with a guard that covers the siblings, not just the reported case.** Worked example: P1 — a raw stack trace from a duplicate `rule add` — root-caused to `RuleValidator.check` letting a kernel conversion exception escape, a path shared by six callers; the fix went in the validator and the guard covers `computation add` too, not only the reported `rule add`. This complements the anti-whack-a-mole mining below (mine constraints proactively) and the probe's proactive loop ([`docs/PROBE-SPEC.md`](docs/PROBE-SPEC.md)).

## Advertise nothing you cannot point at (standing requirement, 2026-07-16)

**For every invariant a change *advertises* (a schema field, a declared policy, a guarantee in docs or help text), name the enforcement locus and the test that fails when it is violated.** "Parsed but never consumed" is a shipped class here: a boundary once parsed a request's declared policy and observation fields and enforced neither, and only an external consumer's independent audit caught it. A does-fire test proves that a *built* thing fires; this rule proves that a *claimed* thing was built at all.

## A client's stop rule is never overridden from inside (standing requirement, 2026-07-17)

**In cross-project work, an external client's explicit stop/verify rule is never reinterpreted away by our own documentation, however well reasoned.** A conflict between our state and a client's pin goes BACK TO THE CLIENT as a question before any run proceeds. The shipped class: a published identity's freeze status was pre-ruled "the documented pre-freeze upgrade, not drift" using *our* freeze definition, but the client's smoke run had already exercised that identity externally, so one published id briefly meant two byte contracts and an otherwise flawless run was rejected on version identity. A published identity's freeze status is the CONSUMER'S exercised reality, not the producer's ledger, and the one-message round trip is always cheaper than a rejected handback.

## Convergence gate — stop when a slice keeps expanding (standing requirement, 2026-08-02)

**Two consecutive implementation/review rounds that add net-new blockers to the same slice, or any round that changes its acceptance denominator, are evidence that the work is not converging. Stop patching at that point.** A perpetually growing slice usually couples distinct mechanisms (for example a generic evidence guard, several owner-semantic fixes, and public documentation) and makes each review invalidate the framing of the previous one. More review inside that frame burns tokens without creating a stable landing.

The recovery is mandatory: freeze the observations already established; name the coupled mechanisms; partition them into the smallest independently meaningful feature commits; write a finite acceptance matrix for each partition with its oracle and explicit non-goals; then finish one partition before reopening another. A finding enters the current partition only when its discriminator violates that partition's named invariant. An adjacent improvement or newly exposed independent defect goes to the owning gap/task for a later slice—it does not silently enlarge the current denominator.

Review obeys the same discipline; how it does is "Cold adversarial review gates" below.

## Before you STATE a finding: match the oracle to the CLAIM KIND, or surface the doubt (standing requirement, 2026-07-25)

**A finding is done when the right oracle has been run — not when it is plausible.** The retro that produced this rule is unambiguous: across a long kernel exchange the *measurements* were right nearly every time and the *mechanisms* were wrong four times, because a mechanism was shipped carrying the confidence of the observation it explained. So pick the oracle by the **kind** of claim, and never let one kind borrow another's authority.

| claim kind | the oracle that settles it | stays a HYPOTHESIS until |
|---|---|---|
| accept / reject | `rule check` / `checkConsistency` — the kernel itself | — (terminal) |
| runtime behavior (what fires, how often, where it attaches) | an adapter differential / `RuntimeLaws` — never `model eval` alone, it can carry a known-or-unknown `IG` divergence | a differential has run |
| value conversion / arithmetic | execute the real chain on the pinned JDK | executed, output read |
| **mechanism / causation ("because X")** | a **discriminating case that the rival mechanism gets wrong** | you can name that case and it behaves as predicted. **The observation it explains is not evidence for it** |
| **completeness / absence ("no other caller", "sole implementor", "dead code")** | an enumeration you can show, with **anchored** exclusions (`grep -v '/build/'`) | the search is stated *and* its recall limits are |
| **reachability ("unauthorable", "cannot happen", "unrepresentable")** | an attempt to author it, **plus an attempt to DEFEAT every link** of the argument | each link has been *attacked*, not merely measured — measuring each link does not establish the chain |

**A control that moves more than one variable is not a control — and the tell is that it looks like one.** Two published clauses went wrong this way in two days (the index-keying conjunct; the `FirstFilledValue` date row), both with controls attached, both reading as clean measurements, one of them written *inside the batch correcting the other*. So before stating a row, name the variables it moves and check that its control holds all but one fixed. Prefer a **within-model** control — the same model built twice, differing in exactly one builder call — over comparing two models, because two models differ in every way you did not think about. **And when an inbound row disagrees with a clause you already hold, the disagreement is the HYPOTHESIS TO TEST, not the finding: your clause names the variable the inbound row may not have controlled, which is precisely why you are the one who can see the confound.** Recording it instead as "both measured, neither generalizes" reads as careful and is how a confounded row reached a peer's spec (a12-kernel-lean `LF89`, 2026-08-15). A confound removes support symmetrically — the incumbent claim does not get to stand because it was there first, and the incumbent may be *your own claim wearing a different hat*: a green `FieldValuesNotUnique` lock contradicted a published `FirstFilledValue` catalog line in this repository, both live, until an outside reader put them side by side.

**An absence claim almost never arrives in the phrasing the table forbids — that is why the table does not catch it.** The completeness and reachability rows above name the formal register ("no other caller", "unauthorable", "cannot happen"), and a session that is about to get one wrong does not write those sentences. It writes **"I probed the candidates and only one worked"** and **"the sweep covered the class"** — the identical negative existential in the register of a working note, where it reads as diligence rather than as a claim needing an enumeration. Both shipped here in one week: a six-candidate probe became "this kind admits exactly one format" and reached a peer's spec, and a sibling sweep excluded an entire kind for three months on a cardinality nobody had measured, hiding a live defect behind a finding that had *closed the class*. So treat those two sentence shapes as the trigger, not the formal ones: **before "only X worked" or "that is the whole class", name where the denominator was measured — and look first in your own findings, which is where both answers already were.** *(Sharpened by a12-kernel-lean, `LF89`, 2026-08-15, from the mirror of our own rule.)*

**Then dispose of what is left, explicitly. Three outcomes, no fourth:**

1. **Verified** → state it plainly, with the basis named inline (which oracle, which layer).
2. **Doubt that one targeted run would settle** → run it; see "Never park what one targeted run answers" below.
3. **Doubt a run cannot settle** → **SURFACE IT**, and classify it:
   - **gap** → a row in the owning `-GAPS`/ledger doc naming what would settle it and what it blocks. Never a silent hedge buried in prose, and never a confident sentence with the doubt omitted.
   - **blocker** → **ASK, and wait.** A blocker is anything you cannot resolve or decide alone: a cross-cutting design call, an external/licensing constraint, a contract you can't change unilaterally, or a choice whose wrong answer is expensive or hard to reverse. Do not pick a branch and proceed.

**Never dress a mechanism as an observation — in docs or in a handback.** Measurements travel; mechanisms carry their basis with them. When handing findings to another party the payload is the table of *(input → observed output → oracle used)*; the explanation belongs in a separate section marked as hypothesis and explicitly not actionable. Two full round-trips of the 2026-07-25 kernel exchange existed *only* because that separation was missing — and one of them was a correction of my own previous handback.

**Name the quantity before you compare numbers.** That same exchange burned rounds because one word ("digits") stood for seven different measurements on four axes; each side then "corrected" the other about a different number. When a topic has several same-typed quantities, fix a glossary first and cite it — see KERNEL-FINDINGS "the seven digit gates".

**AMEND IN PLACE; never mint a new round to correct yourself.** A correction to something you already handed over belongs in that document, marked, not in a fresh one that supersedes it — a supersession chain is pure cost to the reader and multiplies the churn it was meant to fix. The 2026-07-25 exchange produced five handover docs where two would have done, one of which existed *solely* to retract the previous one. Same for a ledger row or a finding: edit the row, mark the correction inline (the "Corrected <date>:" form already used throughout `MVK-LEDGER`), and keep exactly one live statement of the fact.

**Batch by topic, not by finding.** Closing one fact at a time reopens the next adjacent one and guarantees another round; sweep the *class* ("enumerate every gate that counts digits, measure each") so a topic closes once. This is the root-cause-generalization rule applied to the reporting channel rather than to code, and not applying it there is what turned a two-round exchange into six.

## Never park what one targeted run answers (standing requirement, 2026-07-25)

**An item may be handed back as "open" only when resolving it is genuinely blocked** — it needs a decision that isn't yours, an oracle you don't have, or a run whose cost you'd have to justify. **If a single targeted test or probe would settle it, run it instead of reporting it**: measuring is usually cheaper than the paragraph explaining why you didn't. Two traps, both of which make the wrong choice feel responsible:

- **"Deliberately left open" is a disposition, not a rationale.** The doc rule (a disposition is status, never dressed as a durable *why*) applies to handbacks too — labelling an unfinished item as a considered choice launders incompleteness into judgment.
- **Disclosure is not discharge.** Naming a weakness reads as rigor and is never criticized, so it is exactly the move to distrust when the fix costs seconds. Note this is the mirror of the full-run budget smell: there the uncriticizable option spends the maintainer's CPU, here it spends the maintainer's *correctness* — both times the tell is that the safe-looking choice costs you nothing.

Applies hardest to a claim reached by **reasoning rather than execution**: if a chain has an unmeasured link, measure the link — a client-side bound justified "by transitivity" was once flagged as open rather than settled by a 15-second kernel probe, which then confirmed it outright (`MVK_FRACT_DIGITS_INVALID`, 2026-07-25).

## This session does the work; sub-agents only review (standing requirement, 2026-08-06)

**The session you are in plans, implements, and verifies.** Use plan mode or a task list for anything multi-step. **Sub-agents are read-only**: they review, search, and report findings. Never delegate implementation to one, and never use one to double-check work you can check yourself. Never let two sessions write the same tree: **one active session per worktree, always** (a read-only reviewer is compatible with that rule; concurrent editing is not).

Pick the review checkpoints **while writing the plan**, not while working, and record them as real tasks so they cannot be skipped silently. Planning them is this rule's job; which ones are warranted is "Cold adversarial review gates" below.

Work that outgrows one session carries its state in a proposal/design doc whose work-item table is the state carrier, updated in the same commit as each landing. No separate tracker, and no relay protocol: the next session reads that table and continues.

## Cold adversarial review gates

**One test decides it: review where a mistake would be expensive to discover later and the guards cannot see it.** Not where the work was large, not where it felt hard. This is the archived model policy's criterion ("the price premium is paid exactly where CI can't help") applied to review instead of to model choice.

**Does this work need a review at all?** Yes when it touches a published API or wire/output contract, a new or materially changed guard, kernel-oracle or clean-room work, or release/publishing machinery, and yes when a mistake would be **self-confirming** (you would believe it worked). **No** when a deterministic guard covered the change red-to-green and it is off that list. State the skip in that direction: "simple work" is not checkable, "the guard went red then green and this is off the high-risk list" is.

**Where in the plan does it go?** Default to **one terminal review before landing**. Add **at most one earlier review**, after a **foundational** task: one whose output changes the *shape* of later tasks, not merely whether they run. A new record or type, a schema key, an error-code taxonomy, a pointer representation, a guard's invariant are foundational; the twelfth operator on an established pattern, tests for a settled shape, and docs are elaboration. A plan that seems to need three foundational reviews is three plans, so partition it (convergence gate above).

**How to call one.** The reviewer gets the task, the governing rules, the frozen diff, the acceptance matrix, and the verification claims, but **not your rationale or conclusions**: the point is an independent reading, not another vote inside your framing. Same model, fresh context, review-only prompt, never a cheap default worker as a substitute; **effort is a dial**, not a mirror of the implementing session: default `high`, `low`/`medium` for a cheap first pass (review accuracy holds down there), `xhigh` or `max` for the hardest landing; set it per call where the tooling exposes it, otherwise on the session. Ask it to attack vacuity and positive controls, denominator completeness, owner-shape fidelity, source-vs-artifact oracle choice, whether every advertised invariant has its enforcement locus and failing test ("Advertise nothing you cannot point at" above), and whether the stated measurement actually supports the mechanism. Tell it to report **everything** it finds on those axes in the form *discriminator input → observed/expected output → exact source locus → oracle → execution status*, each tagged in-scope or adjacent: a reviewer told to be selective complies literally and reports less, so **you** filter, it does not. Batch compatible axes into that one call with explicit sections; split across reviewers only when the mechanisms need genuinely different source estates. It stays read-only (and build-free while an isolated timing-sensitive gate runs); you stay the sole writer and settle each finding against the correct oracle.

**Assemble the packet; never delegate discovery.** The dominant cost of a review is the reviewer rebuilding context, not its reasoning. Every deterministic fact you list first (the frozen range, authoritative test output, denominator enumerations, the API diff, stale-surface searches, mechanical mutants, findings already closed) costs you one cheap command and saves expensive exploration. A tight packet on a frozen slice is a fraction of what the implementation cost; an open-ended "review this area" can exceed it.

**Does a fix earn another review? No: one review per slice.** A second call must name something the first could not possibly have seen, and only two things qualify: the fix **changed the shape** the reviewer read (that is new work, so re-enter at the first gate), or it landed in a **different high-risk category** than the one reviewed. Everything else stops. A **contested** finding is settled by its oracle, never by a second opinion; a reviewer is not an oracle, and asking another is how two rounds become six. Warm review keeps its narrow job (bounded closure: compilation fallout, regression inventory, API/doc/golden synchronization) and never substitutes for a cold read of completeness, owner semantics, clean-room boundaries, a new guard, or a new public contract. Do not build it into the cycle: confirming that accepted findings were applied is a checklist you run yourself against the finding list and the diff.

**Three mechanical stops, so "is this converging?" is never a judgement call in the moment.** (1) **Write the acceptance matrix before you call the reviewer**, so a finding either violates a named item (fix it) or does not (log it to the owning gap ledger); without a pre-committed matrix every finding reads as a blocker and there is no principled stop. (2) **Two rounds maximum** on one slice. (3) If a round **changes what "done" means**, stop and re-partition rather than continuing. Once the matrix is green, land it; never redesign a slice to improve an already-satisfied mechanism.

## Interpreter — the two #1 rules (never scoped down)

The **`:interpreter`** module is the kernel-free Kotlin Multiplatform evaluator (native image + standalone JVM/JS library). **Its full module instructions live in [`interpreter/CLAUDE.md`](interpreter/CLAUDE.md)** (auto-loaded for work in that subtree) — **read that file before ANY interpreter-related work, including its differential/perf work in `:adapter`** (which lives outside the subtree, so it does not auto-load). It carries the goals/priorities, customization-surface parity, the performance method, the generator layering, and the hygiene rules (the `verifyInterpreterPurity` lint enforces the import boundary). Two rules are repeated here because a miss is catastrophic and they must hold before any file is even opened:

1. **(A) MATCH kernel semantics EXACTLY — BOTH evidence strategies where they agree.** The evidence axis is **dynamic-Groovy** (the generated/cached Groovy md-runtime service) vs. **static-Java** codegen. Match the dynamic-Groovy result bit-for-bit on every legal input and match static-Java wherever it agrees; no "close enough", and a differential-observable special case is a must-match, never "obsolete". On a legal split, dynamic-Groovy is normative; record the static-Java result as a characterized divergence and never adopt it (IF136). A behavior is droppable only when proven DEAD in both strategies from source.
2. **(B) Clean-room reimplementation, NEVER kernel delegation — the EUPL license boundary.** The A12 kernel is EUPL-1.2/commercial; a runtime that links/ships/calls it is a combined work the copyleft reaches. So: never delegate evaluation to the kernel (no `com.mgmtp.*` call, no JS-kernel binding), and **never copy/transliterate the kernel's source expression** — a line-by-line port is a copyright derivative that re-attracts the EUPL. Read the source to learn the exact behavior → write original Kotlin → lock it with the differential. Copy the *mechanism*, never the *expression*. Since the `--kernel` eval flag was retired (Set V), dmtool never delegates document evaluation to the kernel: the evaluation path uses the interpreter. The JVM dmtool distribution still bundles the kernel-backed adapter for consistency checks and non-evaluation authoring and inspection capabilities; that distribution remains subject to the EUPL/commercial license.

## Coding style — make full use of Java 21

Write idiomatic modern Java 21, not Java 8 with newer syntax:
- **Records** for immutable data (AST nodes, value objects, results). **Sealed interfaces + exhaustive pattern-matching `switch`** for closed hierarchies — model the AST this way and let the renderer/visitors dispatch with a switch that the compiler proves exhaustive (no `default`). See PROJECT-DESIGN §18.5.
- Record/`instanceof` **deconstruction patterns**, `var` for obvious locals, **text blocks** for multi-line strings (DM-JSON fixtures, expected output), enhanced `switch` expressions, `Optional` over nulls in APIs, `List.of`/`List.copyOf` for immutability.
- Prefer making illegal states unrepresentable in the type system over runtime checks — that is the whole point of the typed builder.
- **Long parameter list → builder, never a positional N-arg constructor (standing rule).** When a value object (record included) would take many arguments — the smell bites hardest with **several same-typed** params (multiple `String`/`boolean`/`List`), which are silently swap-prone — give it a fluent `Builder` and make the builder the *public* construction path; the record's canonical constructor stays but is called only by `build()`. A `null`/empty/`false` setter argument means "leave this aspect unset". Exemplars: `FieldModification`, `ConfigModification`, `GroupModification`. (Rule of thumb: ≳5 params, or ≥2 adjacent same-typed params, ⇒ builder.)
- **Clean code is non-negotiable — never knowingly write a code smell, and if you spot one (even pre-existing), stop, report it immediately, and provide the fix.** Reach for the idiomatic Java-21 construct over the expedient shortcut (the items above), make illegal states unrepresentable, and when a structure *scales across increments* do an explicit refactor pass rather than letting duplication accrete behind green tests. (Smells bite worst when they creep in incrementally — e.g. the string-keyed dispatch for a closed set that crept into `ApplyCommand`, since fixed with an enum + exhaustive `switch`.)
- **Javadoc `*/` trap:** never write a literal `*/` inside a Javadoc block comment — most often a wildcard path in `{@code …}` like `Group*/field` — it ends the comment early and breaks compilation. Reword (e.g. "the flatten of `Group*` then `field`", or a space: `Group* / field`). This recurs whenever documenting repetition-list syntax.

## Documentation — the iron rules + the trigger table

Full procedures + rationale: [`docs/DOC-DISCIPLINE.md`](docs/DOC-DISCIPLINE.md). Five iron rules, always:

1. **Every non-obvious finding gets written down** in its home doc, in the same change — kernel behavior → [`docs/KERNEL-FINDINGS.md`](docs/KERNEL-FINDINGS.md) (§-numbered to mirror the canonical [`docs/KERNEL-SEMANTICS.md`](docs/KERNEL-SEMANTICS.md); a new fact lands in KERNEL-FINDINGS FIRST, experiment-verified + test-locked — folding it into the canonical prose is a separate, deliberate upstream edit); kernel-integration facts → [`docs/KERNEL-INTEGRATION-NOTES.md`](docs/KERNEL-INTEGRATION-NOTES.md); build/environment facts (Gradle home, JDK pin, build cache, offline limits) → [`docs/BUILD-ENVIRONMENT.md`](docs/BUILD-ENVIRONMENT.md); design decisions → [`docs/PROJECT-DESIGN.md`](docs/PROJECT-DESIGN.md). A finding is only "done" when documented; a contradicted note is updated, never left stale.
2. **Docs travel inside the feature commit, never after it** — update the affected docs and sweep them for stale claims in the same pass; commit code + docs together. No trailing "docs: refresh" commits.
3. **Rationale is timeless; a disposition is status.** A durable note records decisions/tradeoffs/principles; "parked / deferred / not yet / rides X" belongs in a `-GAPS` ledger, a backlog, or git — never dressed as a durable *why*. When a decision rests on a current fact, embed its re-open trigger.
4. **Codify only what recurs, and PRUNE what a guard now enforces.** A rule earns its place by naming the cost it prevents, and every session pays to read it. So ask the inverse question as often as the additive one: once a guard, script, or lint enforces a rule mechanically, retire the prose. Codification must not only accrete.
5. **Match a doc's length to its substance.** Cover what the reader needs and stop: no filler sections, no redundant summaries, no boilerplate restating the section above. Length is not thoroughness, and an over-long doc taxes every future reader of it. (A finding carries its own tighter weight rule, in [`docs/CLAUDE.md`](docs/CLAUDE.md).)

Research kernel facts by **SOURCE, never by jar** (the golden rule): the consult-only `../a12-kernel/` checkout is the primary oracle for syntax/rendering/rules/signatures (match the fully-qualified class, not the file name; ignore generated `delombok` trees); probing the live kernel confirms *behavior*; the kernel-team BA doc (consult-only, never copied) is the second oracle. **Route the question to the artifact that answers it** — complete denominator → the class inventory + the RT-semantics/MVK ledgers; the **general lowering of a rule shape** → the **codegen template** (`kernel-tool/kernel-core-codegen-*/src/main/resources/internal/templates/validation/{groovy,java,java_script_vk}/**/*.st`, a standing instrument; skip the `build/resources/` duplicates) **and then the codegen BACKING BEAN it interpolates** — most operand templates are 2–3-line **pass-throughs** (`CompositeOperation.st` is just `<t.feldOperationCodeJava>`), so the emission shape lives in the bean property, reached by following the interpolated attribute (`…/backingbeans/**`); a silent-looking template means *pass-through*, never "no lowering"; the actual order for one concrete shape → the generated program; an operation's local meaning → the runtime class; whether a locally correct reading *manifests* → a probe. **Cite which layer you consulted** — names collide across layers (`CompositeOperation` is both a template and a bean; `java_script_vk` names a codegen dialect *and* pairs with a separate TS runtime), so a basis that just says "CompositeOperation" is ambiguous. **A claim about read order, precedence, reachability, or interaction between runtime classes, established by source reading alone, stays a HYPOTHESIS until a template, a generated program, or a probe confirms it** — locally correct reads compose wrongly, repeatedly. Detail + the proactive kernel-coverage ledgers (MVK / RT-semantics / grammar, and [`docs/KERNEL-UPGRADE.md`](docs/KERNEL-UPGRADE.md) on a bump): [`docs/DOC-DISCIPLINE.md`](docs/DOC-DISCIPLINE.md) §1–§2.

## Testing strategy

The conventions below are enforced; the **map of the whole testing approach** (the kinds of test, the two law tiers, the guardians, the corpus harnesses, how to run) lives in [`docs/TESTING-SPEC.md`](docs/TESTING-SPEC.md) — read it to place a new test.

- **Example-based TDD is the primary spec** (red/green) — readable, intent-revealing tests drive each feature.
- **The real kernel is the oracle.** `RuleValidator` + `checkConsistency` confirm that rendered output is actually accepted (F4); N7 runs every catalog example through it.
- **Test layout: one file per operator family; hotspot files never grow** (decided 2026-06-04). A new increment adds a *new* small test file (the shared `Fixtures` util keeps that cheap), never piles onto a monolith. The kernel-law locks are executable `KERNEL-FINDINGS.md` entries in **two tiers**: **accept/reject** (structural validity) under `validate/laws/` and **fires/does-not-fire** (runtime behavior) under `adapter/.../laws/` (the `RuntimeLaws` oracle); each findings §/ledger row points at its `…LawsTest` class. Where a new test goes: [`docs/TESTING-SPEC.md`](docs/TESTING-SPEC.md).

- **Keep test-task dependencies slim and specific — a test that reads a repo file at runtime declares that file as an input on a task scoped to *just* that test, never on the broad suite** (standing requirement, 2026-06-30). Gradle inputs are per-task: declaring a doc/demo on the whole `:cli:test` re-runs all ~620 tests on any `.md` edit; *omitting* it lets the task go up-to-date / restore from the build cache into a **false green** locally while CI (fresh) fails. The pattern — the doc-reading guards (`CliTourFreshnessTest`, `CommandReferencesResolveTest`) run in a dedicated `docGuardTest` task with exactly those files as its inputs, and `test dependsOn docGuardTest` (so CI + the `-PrkNativeAgent` capture still drive them). Detail: [`docs/TESTING-SPEC.md`](docs/TESTING-SPEC.md) "Tests that read repo files at runtime".

- **Running the self-sufficiency eval / benchmark (N6): use the `run-dmtool-eval` skill** (`.claude/skills/`). It loads the protocol guardrails (clean subagent, material boundary, neutral prompts, pinned model, cost model, targeted re-runs) at the moment of running — **don't run the benchmark from memory**, the guardrails are easy to violate silently. Method/rationale: [`docs/EVAL-SPEC.md`](docs/EVAL-SPEC.md); measured results: [`eval/RESULTS.md`](eval/RESULTS.md). (That operator skill is distinct from `skill/SKILL.md`, which is the *material under test* — never give the operator skill to the eval's subagents.)

- **Authoring skills/workflows: put deterministic or permission-gated setup in a committed script the main loop runs — never prompt an agent to do it.** A workflow subagent runs under a restricted permission mode and **cannot self-approve a mutating command** (`rm`/`cp`/`mkdir`), so an agent *prompted* to do setup is non-deterministically denied — and a denied setup the run doesn't hard-check silently corrupts the results (the eval's produce agents mutated committed fixtures this way three times, once even into a commit). The fix pattern: setup lives in a checked-in script (e.g. [`eval/prep-sandbox.sh`](eval/prep-sandbox.sh)) the main loop invokes alongside the build; the workflow only **verifies** (read-only) the precondition and **halts loudly** if it's missing. General rule: **agents for judgment/exploration, scripts for deterministic side-effecting setup.**

## Build

Build with an isolated, public-repos-only Gradle home so the machine's global config (private registry) is bypassed, on JDK 21 — see the README's "Build & test" section. **Simplest: `./build.sh <gradle args>`** — the committed wrapper pins the isolated `GRADLE_USER_HOME` + JDK 21 then runs Gradle, so it also shares the warm cache. The repo additionally defends itself, so a bare `./gradlew` is no longer contaminated by the machine's global `init.d`: `settings.gradle` declares the public plugin repositories **first**, and the committed `.no-global-gradle-repos` marker makes an init script that honours it skip this build (root cause + measurements: [`docs/BUILD-ENVIRONMENT.md`](docs/BUILD-ENVIRONMENT.md)). The kernel must first be published to `mavenLocal` via the sibling `a12-kernel-bootstrap` kit.

**`:cli:test` IS NOT the cli estate — the checkpoint verb is `:cli:check` (standing correction, 2026-08-07).** `publicContractTest` (the black-box lane that spawns the packaged launcher: `DmtoolPublicContractTest`, `DmtoolMutationSafetyTest`, `PackagedDmtoolJourneyTest`, `CommandRouteEquivalenceTest`) hangs off **`check`**, and `routeExclusivelyHostedTests` excludes its classes from `test` — so a local `:cli:test`, however green, cannot fail on them. Its four reviewed `@TempDir` classes overlap their independent packaged-process waits in a task-local pool capped at four; this reduced the measured end-to-end lane from 409.8 s serial to 281 s with the launcher build included (2026-08-09), without deleting, batching, or moving a check in-process. New classes stay serial until they explicitly opt in. This sentence used to read `:interpreter:check :adapter:test :cli:test` and was itself the trap: `mcp` (2026-08-06) left two stale verb-count denominators in that lane and one skill term unadded, and the red went unseen for a day.

> **Why it went unseen is NOT "CI does not run that lane" — CI names it explicitly** (`ci.yml`: `… :cli:test :cli:publicContractTest …`). The actual mechanism is that **nothing had been pushed**: 129 commits sat unpushed, so CI never ran on any of them. Local green was the *only* signal, and the local command omitted the lane. *(Recorded because the first version of this note asserted the CI mechanism from the same observation that fits both — the failure mode the "match the oracle to the CLAIM KIND" rule exists to prevent. The discriminating check was one `grep` of `ci.yml` plus one `git log origin/main..HEAD`.)*

**Root `:test` and `:schemakit:test` are lanes too — a `:interpreter:check :adapter:test :cli:check` checkpoint is still not the whole estate.** Root `:test` carries the `validate/laws` accept/reject tier plus the guard tasks it pulls in by `dependsOn`, so the kits' own coverage (`rulekit`/`modelkit`/`core`/`edit` — none of which has its own test source) lives there and nowhere else. `:adapter:test` needs its own invocation (perf lanes); the rest may share one. **Prefer making a lane cheap over deciding whether to run it:** the reason omitting one ever looked attractive is that up-to-date tracking was broken in specific places, and a lane whose inputs are declared costs nothing when nothing it depends on changed.

**Inner loop: run TARGETED tests, not the full suite, for each minor change (standing requirement, 2026-06-24).** The full estate (+ `scripts/verify-demos.sh`, which rebuilds `installDist`) takes **>1 min** and slows development when run after every small edit. While iterating, run a **single test class** — `./build.sh :adapter:test --tests "<FqcnOrPattern>"` (one `*DiffTest`/fuzz class is ~3–7 s), or `:interpreter:check` alone when only `:interpreter` changed. Reserve the **full suite + `verify-demos.sh`** for the **session-end checkpoint — ONE run, scoped to what changed**; the budget and its scoping rule are item (5) of the differential-loop list below, and **they govern ALL work, not only differential work**. **A session with N commits does NOT earn N full runs** — commits land on targeted green, and the single end-of-session run is what catches cross-cutting regressions. (`verify-demos.sh` is additionally gated on a verb's output shape/behavior/diagnostics changing — otherwise skip it. **Decide it by grep, and grep for the right thing:** `grep -rln '<verb-or-operator-id>' examples/*.md`. For a **catalog** edit the target is the **operator id, not the verb** — `examples/cli-tour.md` pins `meaning` *and* `gotchas` verbatim for `And`, `AllFieldsFilled`, `LessThan`, `DifferenceInDays` through `rule explain`, so the word `operators` appears nowhere in the demo that would drift; `examples/cli-discover.md` separately pins the operator **count**, so adding or removing an operator drifts it while editing one operator's prose does not.) *This sentence used to read "right before a commit", which licensed one full run per commit and contradicted item (5); an eight-commit session duly burned ~40 minutes of CPU on 2026-07-25 while staying literally compliant with it.*

**Three habits that quietly manufacture full runs — all three cost the MAINTAINER's CPU, not yours (standing rules, 2026-07-25, from the eight-full-runs retro).**

- **Don't let the report format create demand for runs.** Full-estate totals ("435 classes, 2214 tests, 0 failures") are **not** the proof-of-done and must not be a standing line in a handback — making them one forces a fresh full run after every commit. The honest evidence for a change is **the targeted test result plus the guard task that covers what changed**; the session-end full run is a regression backstop, not the deliverable. Report what you changed and what covers it.
- **Diagnose — and CONFIRM THE FIX — with the narrowest command that can discriminate.** When a full run fails, re-run **the single failing class** to classify it (real regression vs load-sensitive floor) — *never* the whole suite again. A second full run to test a flakiness hypothesis spends minutes to learn what one class answers in seconds. **The confirmation half is the one that gets missed, because it arrives disguised as diligence: a red full run does NOT create a debt for a green one.** That run already reported every other class as passing, and only your fix's BLAST RADIUS can invalidate it — so ask what the change can actually reach. A test-lane exclusion, a one-class fix, a doc or comment edit reaches nothing the prior run covered, and re-running 2700 tests to re-confirm 2695 of them is the budget smell below wearing a safety label. *(2026-08-15: a new script guard was routed into two lanes and failed 5 of 2712 in the lane that supplies no system property. Fixed in one line and verified twice — green in its owning lane, absent from the broad lane's filter — then a second full six-minute suite was launched anyway, purely on the feeling that a red run owed a green one.)*
- **Treat "more testing" as a budget smell, not a safe default.** The broader run is never criticized on thoroughness, and its cost lands on the maintainer while the reassurance accrues to you. Whenever the cautious-looking option spends someone else's budget and cannot be faulted, that asymmetry is the signal to stop and pick the cheap one.

**A new test must not perturb timing-sensitive floors that share its task (2026-07-25).** Hoist codegen, in-memory compilation, and model loading to **lazy class fields** instead of repeating them per case. A per-case regeneration in one new differential class inflated `CharsetPerfTest`'s median N/4N growth ratio to **10.24× against its 9.0× catastrophe floor** — failing a class it never touched, and reading exactly like an unrelated perf regression (it passed in isolation, which is the tell). The existing "codegen is primed out of every timed region" rule covers *perf* tests; this extends it to **any** expensive test sharing a task with a timing assertion.

**NEVER run anything in parallel with a perf test — a task carrying a timing assertion gets the machine to itself (owner rule, 2026-07-28).** This governs how you *launch* runs, not just how you write tests. `:adapter:test` carries performance/profile lanes, so it must be its **own** Gradle invocation: never `./build.sh :interpreter:check :adapter:test` in one command, and never a second build, demo script, native build, or eval alongside it. Concurrency does not have to be extreme to corrupt a wall-clock observation — pairing the browser gate (Chrome + Vite) with `:adapter:test` once pushed `CharsetPerfTest`'s then-wall-clock grapheme growth ratio to **9.37× against its 9.0× floor**, a 4 % overshoot that passed instantly on re-run in isolation. Sequence the lanes instead: `:adapter:test` alone, then everything else.

> **The rule covers REMOTE dispatch too — `gh workflow run` ×N is not isolation just because each job gets its own VM (2026-08-11).** Hosted runners are VMs on shared physical hosts, so concurrent jobs of your own evict each other's cache lines and consume each other's memory bandwidth. That is spent in **user-mode** cycles, so the CPU clock does not filter it and neither would `getCurrentThreadUserTime` — a finer clock is never a substitute for isolation. Three concurrently dispatched nightly-gate runs of one commit differed by **1.94×** at the whole-run level, ordered monotonically by their gate wall times (`6m37s / 9m27s / 11m57s`), which made the hosted runner class look far noisier than any evidence supports and stalled an anchor decision on a number that measured only the dispatch pattern (IF280, INTERPRETER-PERFORMANCE "Checkpoint 2026-08-11"). Dispatch one run, wait for it, dispatch the next. Saving wall time by fanning out is exactly the trade this rule exists to refuse.

> **Extended to the sub-quadratic growth gates 2026-08-10.** The nightly gate failed on `MSC-multi-star-correlation` at a median **9.11×** against the 9.0 floor, and the same commit had **passed one night and failed the next two** — the signature of contention, not drift. `PerfHarness.measureCurrentThreadCpu` already existed and its own doc already said "use it for CPU-work ratios and **growth floors**"; the 17 `PerfGateTest` call sites had simply never been migrated. They now route through `timeInterpreterCpu`; `timeInterpreter` is unchanged for its other 11 call sites, including `KernelEdgeTest`'s cross-engine comparisons, which stay wall-clock by the rule below. Measured after, **on the local 8-processor machine**: all **18** growth observations land in **4.00×–5.99×** (`MSC` 4.74×, `B1-per-row` 5.54× and 4.21×), against linear ≈4 and n·log n ≈4.65. *(Both halves qualified 2026-08-11 by three same-commit runs of the real 2-processor hosted runner: that envelope is a property of the MACHINE, not of the migration — on CI the same 18 lanes spanned **2.48×–7.98×**, so the closest lane sat at 89 % of its 9.0 floor and the re-measure-on-breach median is what stands between that and a false red. `FVNU-uniqueness` therefore cannot serve as the stability control the original claim rested on: it spanned **3.94×, 5.85×, 6.10×** there, a 1.55× spread, so "it barely moved" was one pair of samples from a quantity that is noisy on CI. **Caveat on these three numbers:** those runs were dispatched concurrently, which contends them against each other (see IF280) — the interleaved N/4N paired estimator protects a within-pair ratio from slow drift, so a growth figure survives that better than an absolute one does, but the clean values are the sequential re-measurement's.)*
>
> **Algorithmic-only exception adopted 2026-08-03:** `CharsetPerfTest` and `CustomTypePerfTest` now measure current-thread CPU time (`ThreadMXBean.getCurrentThreadCpuTime()`), because their factor/growth floors assert single-threaded CPU work rather than user latency. A full isolated `:adapter:test` had still scheduled these classes beside other test forks and produced a **10.22×** BMP elapsed-time growth result; the focused class passed, and the unchanged full estate passed once the observation excluded time outside the measuring thread. Multi-fork scheduler contention is the basis for the correction; the measurements establish that the excess was elapsed time, not interpreter-thread CPU work. This exception does **not** convert cross-engine throughput or user-facing latency bars: the ratified 250 ms browser first-answer median (IF225) remains wall-clock because that is what a user experiences, and Node/Chrome expose no per-thread CPU time. It also does not relax the launch-isolation rule above for the rest of the adapter performance estate.

**Differential-work loop discipline (2026-07-24, from the G1 retro — the tax is the guard `dependsOn`, not compile OR execution).** A `:adapter` differential class compiles+executes in **~5–8 s** in isolation, yet `./build.sh :adapter:test --tests "<Class>"` takes **~1m40s** — because `:adapter:test` declares `dependsOn` on `corpusReplayTest` + the footprint/performance/profile fixture guards, and `--tests` filters only the test task, NOT its dependencies. An `:interpreter` edit re-runs those guards (corpusReplayTest replays the whole committed corpus THROUGH the interpreter; the fixture guards fork kernel JVMs) — ~1m33s of them. **`./build.sh -Pfast :adapter:test --tests "<Class>"` drops those guard prerequisites → ~8 s** (measured), reserving them for the checkpoint full run (no `-Pfast`; CI unchanged). Kotlin incremental compile + the build cache both work (a 1-file test edit recompiles in ~1 s; an `:interpreter` ABI change recompiles the adapter test set in ~2 s), so compilation is NOT the bottleneck. So: (1) **design the full probe matrix before the first run**; (2) **characterize divergences from the tri-check's own failure message** (`kernel=… interp=…`), never a println-then-rerun pass; (3) **batch edits and desk-check compilability**; (4) **iterate the FIX against `:interpreter:jvmTest` (~5 s, no kernel/guards); use the differential to characterize + confirm**; (5) **one full `:adapter:test` per session, at the end — scoped to what changed** (this is the project-wide full-run budget, not a differential-work-only rule — the "Inner loop" paragraph above defers to it): an interpreter/main-source change gets the full estate (guards + corpus replay); a session that changed only tests/docs/skill gets `-Pfast` + the affected guard tasks instead — with no main-source change the corpus replay and fixture guards cannot produce new information (~9 min saved, measured 2026-07-24). Independent items may land mid-session on `-Pfast` green, but if the final full run fails, fix forward before handing back; (6) the big estate's evidence standard is **verified-fresh** (result XMLs fresh, `skipped="0"`, task executed not UP-TO-DATE), not `--rerun-tasks`-forced — a source change already invalidates the task; keep `--rerun-tasks` for the doc-reading guards and review-gate re-runs, where the false-green risk is real.

**NEVER store data that must survive under `build/` — it is gitignored and `clean` deletes it (owner rule, 2026-08-11).** A `build/` tree is for *derived output*: something a later run regenerates. A **record** is the opposite — it is read back *across* runs, so putting it there destroys the only thing that makes it valuable. This is not hypothetical: the performance gate wrote every measured median to `adapter/build/perf-observations.jsonl`, so the estate could compare a run against one committed anchor but **never against its own history**, because the history was on a deletion schedule. Records now live in the committed, text-only [`perf-results/`](perf-results/README.md) tree, one JSON-Lines file per run, each carrying the conditions it ran under (environment, JDK, processor count, load average per observation, CI run id) because the same commit measured on a busy laptop and on a 2-vCPU hosted runner are not comparable numbers. **The rule is enforced, not advised:** `SurvivingDataNotInBuildGuardTest` fails on any source-level path under `build/` that is not declared transient *with its reason*, and it also asserts the allowlist stays fully used so it cannot decay into a blanket exemption. Two ways to satisfy it — write to a committed directory, or declare why losing the file is harmless.

**Capturing a long build/test run: redirect the FULL output to a file, then grep the file — NEVER pipe the build through `tail`/`head`/`grep`.** Use `./build.sh --console=plain <args> > build/run.log 2>&1` then `grep -E 'BUILD (SUCCESSFUL|FAILED)|FAILED' build/run.log`. Two traps a pipe hits (the reason [`scripts/perf.sh`](scripts/perf.sh) exists, and the rule generalizes to any long run): a pipe **buffers**, so a backgrounded build's log stays empty until it finishes (polling looks frozen and you can't read it incrementally); and `head`/early-closing readers can **SIGPIPE the build and lose its output** entirely. Writing the raw log to a file fixes both — and a backgrounded run can then be `Read` as it grows. (Lesson codified here, not in agent memory, so it travels across machines.)

**A run that can exceed ~10 minutes must NOT be a plain backgrounded shell command — agent harnesses cap those** (Claude Code kills a background Bash task at 10 min; the kill mid-run looks like a mystery failure — it bit twice on 2026-07-10). Run it through a mechanism without that cap (in Claude Code: the Monitor tool with a generous `timeout_ms`, emitting only the result line), or split the run into sub-10-minute tiers — one reason the perf suite is two-tiered: `scripts/perf.sh gate` (the fast routine gate, every landing) vs `perf.sh bench` (the slow kernel-ratio benchmarks, perf-relevant checkpoints only); both take an optional method pattern (`perf.sh gate 'semanticIndex*'`) for a ~1-minute single-scenario re-check.

**Launch every long run through a HARNESS-MANAGED background mechanism — NEVER a hand-rolled `setsid`/`nohup`/`&` detach inside a tool call (standing rule, 2026-07-12).** The harness runs each tool invocation in its own process group and reaps that group when the call returns, so a child you background yourself dies (or is silently orphaned) the instant the tool call returns — the build never actually runs. Use the Bash tool's own `run_in_background` (harness-tracked; notifies on completion; readable incrementally — but still ~10-min-capped) or the **Monitor tool to *run* the command itself** (not to watch a separately-detached process), with a generous `timeout_ms`; run shorter (<10 min) commands in the **foreground** so their output returns and is visible. The tell that a "backgrounded" run is actually **dead on arrival**: a 0-byte log + idle CPU + a Gradle daemon parked in `awaitExpiration` (`jstack` shows `Daemon.stopOnExpiration`, near-zero cpu) = it never received a build request — **investigate immediately, never keep waiting on a corpse.** (Cost this once: a `setsid …&` corpus sweep was reaped at launch and "watched" for 14 min against an empty log; the fix is `run_in_background`/Monitor, which is exactly why the tiered `:adapter:test` runs worked.) Corollary on visibility: Gradle **block-buffers** to a non-TTY, so `--console=plain > file` shows *nothing* until the buffer flushes — treat an empty log after minutes as a launch failure to diagnose, not "still buffering," and prefer foreground (output returns) or a Monitor that streams filtered progress lines.

**Waiting on a long run: key the poll on the command's TERMINAL marker, not an intermediate `BUILD SUCCESSFUL` (standing rule, 2026-07-12).** A bare `./build.sh` ends at `BUILD SUCCESSFUL`, but a **wrapper script** (`scripts/verify-demos.sh`, `scripts/perf.sh`) runs a Gradle sub-build that prints its OWN `BUILD SUCCESSFUL` *before* the real work — so `until grep -q 'BUILD SUCCESSFUL'` reports "done" mid-run. Grep the script's **final line** (verify-demos: `all N … demos match the live CLI`), never a `BUILD` line. (The two mechanical traps — a hand-detached `&` and a self-matching `pgrep -f` liveness gate — are hard-blocked under Claude Code by a `PreToolUse` hook, [`.claude/hooks/guard-long-run-antipatterns.sh`](.claude/hooks/guard-long-run-antipatterns.sh); Codex, lacking the hook, self-enforces from this rule.)

**Release/public-mirror boundary (standing guardrail): the public `a12-dmtool-releases` repo is generated output, not a hand-edited working tree.** Never push directly to the mirror or mutate release assets by hand unless the maintainer explicitly asks for emergency mirror surgery after the scripted process failed. Use [`scripts/publish-release.sh`](scripts/publish-release.sh), which assembles the mirror tree, pushes it, creates/uses a draft release, uploads macOS, dispatches the public native build, and flips the draft live. After `--go-live`, treat the GitHub release as immutable by project policy: adding a platform, replacing a binary, changing `SHA256SUMS`, or changing the public workflow for that release means cut a patch release.
