# dmtool result contract — proposal

> **What this is.** The design for **what a `dmtool` result asserts, who vouches for it, and what it is about** — the four coupled contract changes that close the 2026-07-31 field feedback: the result taxonomy (`valid`), the evidence vocabulary (`engine` / `verification`), canonical A12 pointer identity in runtime output, and one uniform aggregate envelope. All four are **breaking** and ship together as one downstream migration.
>
> **Why a proposal and not a spec edit.** The contract lands in [`CLI-SPEC.md`](CLI-SPEC.md) and [`CLI-CONFORMANCE-SPEC.md`](CLI-CONFORMANCE-SPEC.md); this doc carries the *design plus its measured provenance* until then, and is **archived** under `docs/archived/` once the contract graduates. Durable facts do **not** live here — the kernel matrix behind §4 is [KERNEL-FINDINGS kf167](KERNEL-FINDINGS.md#kf167), and the open work it does not itself close is tracked as rows in [`CLI-CONFORMANCE-GAPS.md`](CLI-CONFORMANCE-GAPS.md).
>
> **Status.** Owner-approved 2026-07-31 as the direction for the next release, with the rulings recorded inline. Measured against revision `a955143d`, dmtool `0.10.1`, kernel build/runtime `30.8.1`.

## 1. Provenance — what was measured, and what the external analysis got wrong <a id="provenance"></a>

External field feedback (2026-07-31) reported seven user-visible defects; an accompanying third-party analysis proposed root causes. **All seven reproduce.** The analysis's central mechanisms are sound, and four of its claims are not. Both halves are recorded because the corrections changed the plan.

### 1a. Confirmed by measurement

| Claim | Oracle | Result |
|---|---|---|
| Repeatable `model compute` loses row identity | live CLI on a purpose-built 4-row repeatable computed field | 4 items, identical `field`, distinct `value`/`cleared`/`error`; row association only by list position |
| The loss is a CLI **projection**, not an evaluator gap | source + existing differential | `ComputationEngine` populates `Computed.indices`; `InterpreterEngine.computeData` emits `c.getPath()` only; `ComputePerRowIdentityDiffTest` locks the interpreter against the kernel |
| Summary counts instances but says "field(s)" | live CLI | `computed 5 field(s)` for **2 declarations × 5 instances** — wrong on both axes, and the list *mixes* declarations, so position is ambiguous, not merely fragile |
| Runtime envelopes claim `valid: true` | live CLI | `true` even on a model the kernel **rejects** |
| Runtime schemas carry a `"fields"` wrapper and false kernel provenance | `schema model compute` / `schema model eval` | both, in the same document that names the interpreter |
| `Abs`/Round refuse an immediate literal | real kernel via `rule check` **and** `computation add --dry-run` | `MVK_NO_CONST`; see [kf167](KERNEL-FINDINGS.md#kf167) |
| `apply --text` / `batch --text` emit JSON | live CLI, both placements, success and failure | `TextRenderer` requires `isObject() && outcome.isTextual()`; `apply` emits a custom object without `outcome`, `batch` an array |
| Unknown subcommand + `--help` exits 0 with parent help | live CLI | generalizes to `rule`/`model`/`field`/`workspace`; without `--help` it correctly exits 2 |
| Stale `JAVA_HOME` fails before dmtool; JDK 26 warns | generated launcher under three JDKs | confirmed — **but the warning is on stderr and stdout stays clean JSON**, which neither source distinguished |

### 1b. Corrections — analysis claims that are wrong <a id="corrections"></a>

1. **`model read` does run the kernel consistency oracle.** `KernelAdapter.ofJson` → `checkAndOpen` → `ConsistencyGate.REQUIRED` → `requireConsistent()`. On an inconsistent model `model read` returns `outcome: rejected`, exit 1. Its `valid:true` is a hard-coded literal that is *coincidentally* correct because the command already bailed — fragile, not false.
2. **The fabricating verbs are different ones.** Measured on a kernel-invalid model: **`model info`, `field read`, `group read`, `config read`, `meta`, `model compute`, `model eval`** report `valid:true`; **`model read`, `model describe`, `computation read`, `model usage`, `computation explain`, `model report`, `where-used`** are gated (honest, but never report `verification`) — and that list was **incomplete**: review added `rule read`, `rule explain`, `rule deps`, `rule format`, and `computation format`, of which `rule read`, `rule deps`, and `computation format` are measured gated (2026-07-31) and `rule explain` and `rule format` are measured gated too — `cli … InvalidModelLoadDiagnosticTest` drives both against the invalid-model path (review, 2026-07-31). The inventory is therefore **not** the contract; the executed path is, and Phase 1 derives it rather than transcribing any list — including this one. Sharper still: **`model report` is gated and `model report --tree` is not** — one verb, two evidence classes, because it has two `ResultEnvelope.read` sites. This is why evidence must be derived from the executed path and never from a per-verb list.
3. **The `Abs`/Round fact was not already recorded.** The only `MVK_NO_CONST` entry in KERNEL-FINDINGS was the **temporal** extractor case (§6, locked by `TemporalExtractorComponentLawsTest`). The numeric-wrapper instance was undocumented and unlocked; only `MVK-LEDGER`'s row gestured at "rounding", in wording that was itself wrong. Now [kf167](KERNEL-FINDINGS.md#kf167) + `NumericWrapperConstantLawsTest`.
4. **The pointer correction is right, but it is a breaking change the analysis did not flag.** Canonical A12 is `Order/Items[2]/Count` — no leading slash, `[1]` omitted (source-verified against `DocumentPointerImpl`, this section's grammar). The current `/Order[1]/Items[1]/…` is **our** `interpreter/eval/Pointer.kt` rendering; `adapter … RuntimeLaws.fmtPointer` re-renders the kernel pointer's *components* through it, so the `[1]`-explicit string in that differential is ours, not the kernel's. Converging is correct **and** breaks published output.

### 1c. Why every harness missed this <a id="why-missed"></a>

Three harnesses **encode** the defective output, so they do not merely miss it — they defend it. `examples/cli-runtime.md` captures `"valid" : true` ×5 and `computed 1 field(s)` ×2, so `verify-demos.sh` fails the *fix*. `probe/` gold answers encode `/Policy[1]/Claims[1]/Amount`, so a probe would mark the canonical form wrong. `cli … KernelEval.java` applies the *same* lossy projection to the kernel side, so a CLI-level differential compares two equally-lossy projections and agrees.

The guards that should have caught the rest are **presence-shaped, not property-shaped**: `CliConformanceMatrixTest` is entirely non-blankness (`assertFalse(...isBlank())`, `hasNonNull`, exit-code-0), so a false description passes; `TextRendererDispatchTest` has **3** cases and never touches the aggregates; `CatalogExamplesAreKernelValidTest` filters `e.invalidExample() != null`, so a *missing* example is invisible (43 of 110 entries have one). And the eval cannot see any of it — **zero** tasks invoke `model compute`, `model eval`, `rule eval`, or `--text`, and it scores task success against a gold, not envelope conformance.

Timeline, against the last full eval run (**2026-07-09**): the catalog gap postdates it (`42c9d18b`, 2026-07-23); the schema prose (2026-06-09), the `boolean valid` parameter (2026-06-11), the aggregate shape (2026-06-12), and `Computed.indices` (2026-07-06) all **predate** it. Four defects were live during that run.

**One sentence:** every harness is anchored either to previously-observed output or to the presence of text; none is anchored to an independently-stated invariant — which is why adding harnesses did not help.

### 1d. What review found wrong in THIS work <a id="self-corrections"></a>

Recorded because the same class of defect this proposal exists to fix recurred while fixing it.

1. **A message-pattern owner extraction was English-only** — replaced by evidence-based resolution. *Its stated justification was itself false, and is corrected here (review, 2026-07-31): the claim "the default bundle renders `MVK_NO_CONST` as `Kein Fehler definiert!`, naming no operator at all" holds only for the base stub `error_messages.properties`. The populated `error_messages_de.properties` shipped in `kernel-core-parser` reads `Bei '%s' darf keine Konstante verwendet werden.` and **does** name it — verified live on a `de_DE` model, where ownership resolved correctly. The file is ISO-8859-1, so a plain `grep` treats it as binary and finds nothing, which is the likely origin. The conclusion (never parse a localized sentence) stands on other grounds; the evidence offered for it did not, and a mechanism must not travel with the confidence of the observation it explains.*
2. **The ambiguous fallback still asserted an owner.** The union fixed `fix` but kept a `firstMeaning()` `explain`, so a `LessThan` rejection was explained as "less than or equal". A passing test (then named `DiagnosticTest.catalogJoinSuppliesFixAndExplain`, now `catalogJoinSuppliesTheSharedFixButNoUnearnedExplain`) was *asserting* that defect — and kept its old name for a further day, so it then asserted the opposite of what it was called.
3. **Ownership was recomputed on only one of two paths.** `lint.SpanResolver` recomputed both fields; `interp.TextConditionCorrective` pinned the operator and left `explain` untouched.
4. **A catalog gotcha claimed `Today` is admitted by the time extractors.** The kernel refuses it (`MVK_WRONG_DATE_FORMAT_FOR_OP`). N7 executes *examples*, not gotcha prose, so nothing caught it — the same presence-shaped-guard gap as §1c.
5. **A law did not lock what its finding claimed.** The sibling-literal case contained no literal.
6. **A status word did work no action backed.** This document was reported as having the Phase-3 stop line removed while the sentence was still live in §6.
7. **A sole documenter was treated as proven ownership.** `documenters.size() == 1` — but the catalog is a *partial* map, so "exactly one entry documents this code" is equally consistent with an undocumented sibling having raised it. Reproduced by review: a `MinValue` rejection was corrected with `MaxValue`'s advice, while the kernel message in hand said `At 'MinValue'`.
8. **The kernel's own boilerplate could elect an operator.** The repair that replaced (7) searched the *whole* message for a documenter's identifier. `MVK_INVALID_COMPARE_TO_YESNO`'s text ends "…or with the constants **True** or False", and `True` documents that code — so every occurrence was explained as "the boolean constant 'true'", including a boolean-versus-string comparison. That message carries no `%s` at all. Closed by reading only the operand the kernel **delimited** (`KernelMessageOperands`) — but see §1d item 12: that mechanism was then over-trusted in two further ways, and the measurement quoted for it did not reproduce.
9. **Two counts in this document were wrong.** §2 said "36 call sites pass a literal"; measured, there were 35 `ResultEnvelope.read(` sites of which 4 passed a *computed* verdict, so **31** literal — and those 4 are exactly the verdict routes the taxonomy is built around. §1c and the `-GAPS` row said "36 of 110" catalog entries carry an `invalidExample`; the same commit series raised it to **43**.
10. **A gate cited a metric that cannot fail.** §6 Phase 4's gate read "160, 0 skipped", but `CatalogExamplesAreKernelValidTest`'s `@TestFactory` filters *before* generating, so a missing example yields no test to skip and "0 skipped" is structurally always 0 — the very blind spot §1c names. The count is real; the "0 skipped" was evidence of nothing.
11. **A canonical findings entry declared a correct refusal a defect.** [kf1](KERNEL-FINDINGS.md#kf1) called `A12PointerFormat.parse`'s refusal of an earlier-part `[0]` "an over-rejection with no kernel basis", though `DocumentPointerImpl`'s constructor throws for exactly that input and a committed test locks the refusal. The mirror of the client-side-refusal rule: a claim that a refusal is *unsound* needs measuring too.
12. **The delimiter mechanism was over-trusted, twice, and its measurement was wrong.** Reading only the *delimited* span of a kernel message is better than parsing the sentence, but two claims made for it were false. (a) It was called **localization-independent** "because every bundle inherits the same `'%s'`" — delimiters are hand-typed per language and three keys already disagree (`MVK_MAX_GROUP_RESTRICTION_TO_ONE` and `MVK_INTERNAL_ERROR` drop them in DE; `MVK_SEMANTIC_INDEX_AND_WILDCARD` DE writes `' %s'`). (b) The count **"146 of 148 templates"** does not reproduce: the EN bundle has **144** with a `%s`, **140** delimited, **4** exceptions — and one exception, `MVK_GROUP_NOT_REPEATABLE`'s `Corrupt: %s.`, belongs to a catalog-documented operator, contradicting the claim that the exceptions substitute nothing confusable with one. This is the project's own oracle rule broken *in the commit whose subject was not doing that* — the measurement was cited from a shell count over one file, then generalized to a mechanism.
13. **The repair for (8) then made things STRICTLY WORSE, which is the fifth instance of that class.** It widened ownership from the code's ≤7 documenters to all 110 catalog entries, reasoning that whoever the kernel names is who rejected. But the kernel delimits **values** as well as operators: `MVK_INVALID_STRING_CONSTANT_FOR_ENUM_COMPARISON` is `'%s' is not valid in the used enumeration.` with the author's enum S-value substituted, so a comparison against an ordinary value like `"Max"` elected the `Max` *operator*, explained an enum-value error with `Max`'s meaning, and **suppressed** the correct `EnumCategory` corrective. Worse on both fields than the honest ambiguity it replaced. Restricting the electable set had been a real safety property and its removal was presented as a pure gain. Election is documenter-restricted again; the message can now only *narrow* a candidate set, and `SpanResolver`'s veto is corroborated against the operators the AST actually contains.
14. **A receipt built over an ambient value is still ambient.** `ValidationResult` stamped `Backends.verification()` — "a backend is on the classpath", unconditionally true in the CLI — onto results from paths that never consulted the oracle, and `ConsistencyEvidence.of(ValidationResult)` read it as a gate receipt. So the type introduced *to make a forged verification unrepresentable* published one: `valid:false` + `KERNEL_CONFIRMED` next to a `PRECHECK`-sourced diagnostic. The hole was one layer below the new type, which is where it will be next time too.
15. **A structurally-0 exit made a gate pass silently.** `workspace check` routed "no model reached the oracle" through the query family, whose exit code cannot be nonzero by construction — so a CI gate reported success for a workspace it never checked. The structural guarantee that a query cannot exit 1 is *correct*; using the query family for a gate that failed to run was not.
16. **"Holding the artefact proves the gate ran" was true of neither artefact that claimed it.** `ConsistencyEvidence.of(ModelReport)` and `of(ModelDiff)` documented the object's *existence* as the witness, so "only the mode has to be read from the environment" — and then read `Backends.verification()`, which is the claim being published, not a detail. Both halves failed independently: an assembly over the deliberately unchecked `KernelAdapter.of` would have reported `KERNEL_CONFIRMED` anyway, and both types were `public record`s, whose canonical constructor cannot be narrowed below the record's own access — so `new ModelReport(…)` minted a receipt with no kernel involved. The same public-canonical-constructor hole that item 14 closed one layer up, restated one layer down. Both now store the receipt of the adapter that assembled them and are closed types; the pairing is the point, since a receipt inside a forgeable type only moves the hole and a closed type that still reads the ambient mode fixes nothing.
17. **One catch-all conflated three origins, and made the envelope contradict itself three ways at once.** The edit gates' `catch (RuntimeException)` funnelled the kernel's deserialize/expand refusal (what it is for), our own `toJson()`, and our own resolver's `UnresolvedReferenceException` into a single `ModelConsistencyException`. Measured on a model whose `include` names an absent id: `verification: KERNEL_CONFIRMED` + `summary: "rejected by the kernel"` + a `PRECHECK`-sourced, code-less diagnostic — for a refusal `ReferenceResolvers` made, on a model the *read* path publishes as `RK_UNRESOLVED_REFERENCE` per a contract CLI-SPEC already documented. Fixing the wrap then exposed the class it had been hiding: **all 23 edit gates** answered a domain rejection with `fail(e.getMessage())` — a bare stderr line at exit 2, no envelope — so the two fixes only make sense together (`failEditGate`). The remaining notification-free tier now derives its diagnostic's origin from the gate that ran (`Diagnostic.gateRefusal`) instead of defaulting to `PRECHECK` beside a kernel receipt.
18. **The guard that would have caught the last two was green because it stopped at a `$ref`.** `workspace list --validate` emitted `checked`/`verification`/`problem` against its own schema's `additionalProperties:false`, and `WorkspaceListCommand` wrote `Backends.verification().name()` raw into every entry — the ambient bypass, again, in the one place the taxonomy explicitly blessed a *nested* verdict. Neither was caught, and the reason was not leniency: `SpecKeys` had no `$ref` handling, so a node consisting of one yielded "nothing to enforce", and enforcement silently stopped at the reference in **9 of 28** bundled schemas. `DataSchemaConformanceTest` additionally ran the verb *without* `--validate`, so even a working walk had nothing to walk. Resolving refs surfaced drift in `model-diff` too, on the first run. A guard that quietly enforces nothing is worse than no guard, because the green is read as coverage — and this is the second time in this effort that a *presence-shaped* check turned out to be structurally unable to fail (§1d item 10). Fixed at the root (refs resolve; an unresolvable one throws) with the ambient read replaced by a receipt the gate now returns — see [API-FINDINGS](API-FINDINGS.md) 111–112.
19. **The same fragment lived in three places and each copy lost something different.** Mapping a `ModelConsistencyException` to diagnostics was written out at `BaseCommand.kernelRejectionEnvelope`, `ApplyCommand.gateRejection` (a verbatim copy, so item 17's fix to the notification-free tier landed in one and not the other), and `PatternsCommand`, which mapped only `notifications()` — so a gate that refused *before* `checkConsistency` produced `diagnostics: []` beside the summary "0 finding(s)": a rejection that discarded its own cause. **The tier they all got wrong is the one that carries no code**, which is the pattern: a branch with nothing in it is the branch nobody notices is missing. One shared `gateRejectionDiagnostics`, three consumers.

20. **The witness types were only witnesses for the writes we had already made.** Threading the receipt into the mutation routes needed one from `ModelDocument`/`EditSession`, and those are the first **mutable** things ever asked to attest. A stored `Verification` would have compiled, passed a gate-ran-after-`validate` test, and then vouched for a tree the kernel never saw the moment any verb edited after gating — real receipt, wrong subject, and invisible. Hence a state-checked receipt (kept against the exact gated DM-JSON) and a guard written around *invalidation* rather than presence. The general rule the earlier witnesses had satisfied by accident: **a witness must be immutable, or it must re-derive.** ([API-FINDINGS](API-FINDINGS.md) 113.)

21. **The obvious witness was the wrong one in four places.** The reference-rewriting refactors (`rule`/`include`/`typedef rename`, the shared `ReferenceRewritingRefactorCommand`) hold a `ModelDocument doc` in scope at the envelope — read before any mutation, used only by the safety gate, never gated. It is the variable a sweep reaches for, and `ConsistencyEvidence.of(doc)` would have compiled, run, and quietly published `none()` for a route that *does* gate. The receipt type made the failure benign (under-report, never over-claim) instead of a wrong claim, which is exactly what it was designed to do — but "which object gated" still has to be answered per site, and a mechanical sweep cannot answer it.

22. **A guard whose oracle is its own implementation cannot fail for the reason it exists.** The canonical-pointer column first asserted `value.equals(A12Pointers.canonical(value))` — the published output compared against the very function that produced it. Neutering `canonical` to return its input makes every such assertion *trivially true* while the interpreter's house form flows straight to the user, so the guard would have been green in exactly the scenario it was written to catch. The fix is to restate the published contract in the contract's own terms (no leading slash, no explicit `[1]`) and consult the type only for representability, which is a different question. This is the fourth shape in this list that reads as coverage while enforcing nothing (10, 18, the receipt column's silence, now this) — and the first where the vacuity came from *reusing the production code as the expectation*, which is normally good practice.

23. **Two demonstrations an agent reads were demonstrating nothing, and only a totality guard noticed.** `model eval`'s worked example produced `fired: []` — its intent line says "which rules fire" — and `model compute`'s ran against a model that declares no computations, so it published `computed: []`. Both had been CI-executed all along, because the demonstration gate asserts the *outcome* (`read`, exit 0) and an empty payload satisfies that perfectly. What surfaced them was the pointer column's insistence that every schema-marked key be *reached* by some scenario: the walk found no pointers at all. A worked example is the surface a cold agent trusts most, and "it runs" is a much weaker property than "it shows the thing".

24. **The schema that told an agent how to shape its input was teaching a form the tool refuses.** `eval-doc.schema.json` described the `--instance` payload as "a nested tree under `\"fields\"`" — the wrapper removed long ago — while `document-instance.schema.json`, served by the *same* `dmtool schema model eval` call, said "there is NO wrapper key". The tool itself rejects the wrapper, and its rejection diagnostic helpfully points at `dmtool schema model eval`, i.e. straight back at the wrong instruction. Three surfaces, two of them right, and nothing compared them, because a *restatement* is invisible to every guard: it is well-formed JSON, it conforms to its meta-schema, and no example executes prose. Found while de-duplicating the description per Phase 3's "$ref the shared document description" item, which was scoped as tidying. The durable fix is the de-duplication itself — the shape is described in exactly one schema and the others point at it — plus a guard that fails on any restatement *and* on a description that disagrees with the tool's actual behaviour, since agreeing descriptions can still be collectively wrong.

25. **Three routes I classified "ungated" ran real gates one frame away — and the guard that should have caught the class could not reach them.** `profile synthesize` assembles through `BoundModel.addAll`, `model export-jsonschema` reads every condition back through the kernel `ConditionReadBack` backend, and `model import-jsonschema` binds through `BoundModel` whenever Tier-A+ rule synthesis has work. All three gate; all three published `none()`. The classification was made by reading each command's own body, where the gate is invisible because it happens inside a helper that returns a `String` — API-FINDINGS 111's shape ("a gate that hands back nothing forces its consumer to re-derive"), one layer further out than the layer that finding fixed. That the guess degraded to *silence* rather than a false claim is the receipt type working; that it went unnoticed for a full phase is the guard's fault, not the type's. **The receipt-totality column ran only over demonstrated branches, and these verbs are demonstrated without `-o`** — printing an artifact to stdout with no envelope at all, so the one branch that publishes provenance was the one branch no demonstration exercised. A totality guard scoped to the demonstrations proves totality over the demonstrations. Fixed by threading the real receipt out of each producer (`ModelSynthesizer.Synthesized`, `RuleSynthesis.Applied`, and a CLI-side bind for export, whose gate lives behind a published SPI not worth widening for this), and by covering the `-o` branches directly. The import case is the one worth keeping: a schema with `exclusiveMinimum` synthesizes a rule and publishes the receipt, a purely structural schema binds nothing and correctly stays silent — same verb, two invocations, two honest answers.

26. **The `--text` totality guard accepted the exact regressions its own doc comment cites.** It asked "is this the JSON *envelope*" — an object with a textual `outcome` — so a bespoke object without `outcome`, and a bare array, both answered *no* and satisfied the assertion. Those are precisely the two shapes `apply` and `batch` used to emit. The guard was written to catch a pass-through and was phrased in terms of a well-formed envelope, which is the one thing a pass-through is not: the same blind spot as the renderer test it was added to compensate for, reproduced one level up while explicitly describing it. The fix is to ask "is this JSON at all", which is the only phrasing that covers shapes nobody anticipated. Verified by simulating the bespoke shape: green before, red after.

27. **Item 16 was fixed on its two instances and not on its class, so the hole was reopened three more times — twice within hours, by me.** Closing `ModelReport`/`ModelDiff` established the rule that a gate witness must not be publicly constructible; the very next phase then threaded receipts out of three more producers as `public record`s (`ModelSynthesizer.Synthesized`, `JsonSchemaImporter.ImportResult`), each one a fresh `new …(json, KERNEL_CONFIRMED)` away from minting a kernel receipt over JSON no oracle saw. A **derived** guard (the witness set read from `ConsistencyEvidence`'s own `of(…)` signatures at runtime, `WitnessTypesAreUnforgeableTest`) found a third the review had not named and that predates this effort entirely: **`ValidationResult`** — a public record carrying `Verification`, on the busiest route there is, `rule check`/`model check`. The lesson is not "remember the rule": it was written down, in a test class whose javadoc explains it, and that changed nothing. What a witness type *is* was never machine-checkable, because the set lived in a reviewer's head; enumerating it by hand is what failed each time. Once the set is read from the signatures, a new witness is in scope the moment it is declared, and nobody has to remember. Closing the three narrowed the published API (the record constructors and their generated `equals`/`hashCode`/`toString` leave `dmkits-rulekit`/`dmkits-schemakit`); the golden dump is the reviewable record of that.

## 2. The result taxonomy <a id="taxonomy"></a>

`ResultEnvelope.read(String, String, String, boolean valid, …)` places a `boolean` in a long same-typed parameter list, and **31 of its 35 call sites pass a literal** (the other 4 — `model check`, `rule check`, `workspace check`, `profile compare` — pass a computed verdict, and are exactly the routes this taxonomy is built around). **Required:** replace it with factories that make the wrong claim unrepresentable.

| factory | emits | may NOT emit |
|---|---|---|
| `queryResult(target, op, summary, data, ConsistencyEvidence)` | `ok`, `data`, and `verification` **iff** the read's own path gated | `valid` |
| `consistencyVerdict(target, op, summary, valid, diagnostics, data, ConsistencyEvidence)` | `valid` **and** its kernel evidence, structurally inseparable — **plus verdict-associated `data`** | — |
| `runtimeObservation(target, op, summary, data, RuntimeEvidence)` | `data` + execution evidence | `valid` |
| `dispatchCompleted` (aggregate `batch`) · `transaction` (aggregate `apply`) | the aggregate's own disposition + `data.results[]` of per-item envelopes | a verdict of its own, except where the transaction's terminal gate produced one |
| existing `applied`/`preview`/`staged`/`refused`/`rejected`/`internalError` | unchanged | — |

*Signatures corrected 2026-08-01 — implementing this changed three of them, and the table still specified the intentions the code had rejected.* `queryResult` **must** take evidence: a read may legitimately have gated (`model read` binds strictly), and the original signature made the gated reads unable to say so — the same silence the contract exists to remove, in the other direction. `consistencyVerdict` takes `ConsistencyEvidence`, never a bare `Verification`: a nameable mode is the forgery this design removes, so the parameter type *is* the enforcement. `runtimeObservation` takes one `RuntimeEvidence` rather than three adjacent strings, per the builder rule — three same-typed parameters are the swap-prone shape the whole refactor is about, and reproducing it in the replacement would have been the joke telling itself.

**Required semantics.**

- Envelope-level `valid` survives only on genuine consistency verdicts (`model check`, `rule check`, `workspace check`).
- **Nested** verdicts are preserved verbatim — `workspace list --validate` keeps its per-model `valid`, and a nested verdict never feeds `exitCode()`.
- `profile compare` is **reclassified, not re-behaved**: it keeps exit 1 for "differs" and stops calling profile equality `valid`.
- `PatternsCommand` performs real kernel validation and emits **no** `ResultEnvelope` at all (it prints a raw node). It either joins the envelope or is classified in `SchemaCommand.CONTRACT_EXEMPT` with a reason. **Resolved 2026-08-01: it joined the envelope, and the exemption was then a lie that had to go too.** The verb stayed in `CONTRACT_EXEMPT` reading "emits the validation-idiom catalog … itself — run it" after it began emitting the standard envelope, so `schema patterns` dead-ended for a verb with four documented routes — and the conformance matrix only checks that an exemption's *reason is non-blank*, so a false reason is invisible to it. The lesson generalizes past this verb: **an either/or acceptance item needs a guard on the branch that was NOT taken**, or the abandoned branch's leftovers keep asserting themselves.
- `exitCode()` keeps `Boolean.FALSE.equals(valid)` → 1 for verdict routes only.
- **A verdict may carry data.** `workspace check` returns per-model entries and `rule check --suggest-error-field` returns a suggestion alongside its verdict, so the verdict factory takes `data`; a signature without it would force those two back onto the query factory and re-create the very conflation being removed.
- **Mutation and preview routes that execute a kernel gate must state their evidence too.** `rule add`, `computation add`, their `--modify` siblings and every `--dry-run` preview run the real consistency oracle before writing, so `applied`/`preview`/`rejected` carry `verification` on the same per-invocation basis as a read. The taxonomy previously ruled only on query/verdict/runtime, which left the largest kernel-touching family unclassified.
- **`profile compare` gets a typed comparison result, not a verdict.** Profile equality is not model validity, so it emits a comparison outcome (`equivalent` | `differs`) in `data` and **keeps exit 1 for `differs`** — a reclassification, never a change of exit semantics, because CI almost certainly depends on that code.

**Excluded:** no deprecation alias for the removed key. The break is declared, not shimmed.

**What implementing this added to the design** (2026-07-31, recorded because each was discovered by a call site the taxonomy could not classify as written):

- **A gate attests through its EXCEPTION, not only through a bound object.** The check verbs learn a model is invalid by catching `ModelConsistencyException`, so on that branch they hold no binding at all — yet the gate unambiguously ran and its notifications *are* the verdict. Without a witness for that branch the negative half of every verdict would have had to fabricate its evidence, which is the same defect one layer along. Hence `ConsistencyEvidence.of(ModelConsistencyException)`.
- **Two routes choose their FAMILY at runtime, and both are honest.** `workspace check` runs N gates, so "did any gate run" decides whether there is an aggregate verdict at all — an empty directory has nothing to be valid *about*, and claiming `valid:true` there is the very fabrication being removed. `rule check` is a verdict when the validator returned and a pre-flight rejection when it threw. A family is a property of what happened, not of the verb.
- **A rejection may need `data`.** `rule check --suggest-error-field`'s candidate list is most useful precisely when the candidate was rejected — it answers "then what should I have written?". So `rejected` gained a `data`-bearing overload, mirroring `refused`.
- **`data.comparison.matches` was wrong in this document.** `profile compare` publishes `matches` at the *top* of `data`, not nested under a `comparison` object. The published shape is unchanged; the doc's description of it was not accurate.

## 3. The evidence vocabulary <a id="evidence"></a>

**Required:** orthogonal keys, never merged, emitted **flat on the envelope** — not nested under an `evidence` object *(owner ruling 2026-07-31, given as the shape below)*:

```json
{
  "engine": "DM_INTERPRETER",
  "engineVersion": "0.10.1",
  "toolVersion": "0.10.1"
}
```

They are equal today, which is precisely why both must be emitted rather than one inferred from the other.

- `verification: KERNEL_CONFIRMED | STRUCTURAL_ONLY` — *how a consistency verdict was arbitrated*. Attached to **every invocation that actually ran the gate**, derived from the executed path (`BoundModel.ofJson` / `checkAndOpen` = gated; `ofJsonLenient` / `ModelIndex`-only = not), **never** from a per-verb table. This adds evidence to seven currently-silent read verbs.
- `engine: A12_KERNEL | DM_INTERPRETER` + **`engineVersion`** — *which implementation produced the semantic observation*: the `:interpreter` module version for `DM_INTERPRETER`, the **actual runtime kernel** version for `A12_KERNEL` (dmtool already separates built-vs-runtime kernel in `--version`, so reuse that distinction).
- **`toolVersion`** — dmtool, which *projected and serialized* that observation. **Both are required**, not one: semantics can change in the engine while pointers, summaries, or result shape change independently in dmtool, so a single version cannot identify what produced a retained result. *(Owner ruling 2026-07-31.)*

**`Verification` must not gain `INTERPRETER_OBSERVED`.** An interpreter run produces no verdict, so the value would read as "the interpreter verified something" — a category error.

**Required boundaries.**

- Evidence is **per-invocation, not per-verb**; the schema says so, and the conformance matrix must not assert a static verb→evidence map (`model report` vs `--tree` is the live counter-example).
- `model seed` emits canonical A12 Document JSON and therefore carries **no** provenance keys inside the document — inventing one would break the shape rule it exists to honour. Its engine is exposed through `schema`/`manifest`/help.
- A mixed-engine `batch` has no single aggregate engine; evidence stays on its children.

**`KERNEL_CONFIRMED` means "the kernel arbitrated THIS invocation" — never "the model was valid"** *(owner ruling 2026-07-31)*. The two are independent, so the marker must remain meaningful on a **rejected** envelope: today `model read` on an inconsistent model returns `outcome: rejected` with **no** `verification`, even though the kernel is precisely what rejected it. Verdict and evidence are orthogonal — `valid:false` + `KERNEL_CONFIRMED` is the correct shape, as `model check` already emits.

**The `model report` / `--tree` split is the worked case, and is LOCKED rather than normalized away** *(owner ruling 2026-07-31)*. `verification` records evidence actually obtained, not a capability of the verb, so `model report` carries `KERNEL_CONFIRMED` and `model report --tree` carries no `verification` key. Do **not** run the kernel merely to make the shapes uniform: that converts `--tree` from an ungated inspection path into one that *rejects* inconsistent models. Splitting it into a separate verb adds migration cost without improving correctness. Instead the **conditional presence** is documented in the schema and locked against one invalid model: `model report` must take the kernel-rejection path while `--tree` retains its projection behaviour and makes no verification claim.

## 4. Pointer identity <a id="pointers"></a>

**Required:** one canonical A12 pointer, typed at the boundary and serialized once; the house `formatPointer` unreachable from CLI projection.

- `computed[]` carries **`field`** — the canonical field-instance pointer — and **`declaration`** — the model declaration path. Two different facts, unambiguously named. No coordinate array, no second pretty spelling.
- Summaries count declarations from the declaration identity and instances from result items — never by stripping indices from a display string.
- **Input stays permissive**: one shared parser accepts A12's legal non-canonical spellings (leading `/`, explicit `[1]`) and normalizes, matching A12's own reader. This covers `--relevant` and every pointer-taking input.
- The test-side `KernelEval.java` projection is fixed in the same change; leaving it lossy would let a differential hide the defect by agreeing.

**Required migration order** (identity is spelling-only, so it must be provable):
corpus expectations migrate by **mechanical re-render**, with the per-case `(outcome, value)` multiset proven unchanged in the same commit — so the spelling moves and nothing else can. Then examples, then probe gold.

**Landed 2026-08-01 — and the scoping finding that made it small.** `formatPointer` turned out to have **two roles**, of which only one is a contract: it is the *internal comparison key* for the conformance corpus (CONFORMANCE-CORPUS-SPEC §7), the differential (`RuntimeLaws` renders the **kernel's** pointer through it so both sides compare), and the published interpreter library's `Message.errorPath`, which its JVM/JS/TS consumers already read. Migrating *that* would have churned the whole differential estate for no user-visible gain. So the house form stays where it is, and the canonical form is produced at the single CLI projection seam (`cli.interp.A12Pointers`, used by `InterpreterEngine`) — which is exactly what "unreachable from CLI projection" asks for. The conversion goes **through the type** (`parse` → `A12Pointer` → `format`), not by string surgery: `A12PointerFormat.parse` already accepts the house form, since a leading `/` is stripped as redundant and an explicit `[1]` is legal.

Two things the implementation forced, both recorded rather than worked around:

- **A12's `UNKNOWN_REPETITION` had to be named.** A parallel iteration leaves `-5` — `IIdentifier.UNKNOWN`, source-verified in kernel 30.8.1 — on a level with no matching row, and the kernel renders such pointers itself. The exact-pointer format now accepts it *at any part*, which is not a loosening of the `[0]` rule: the two brackets share a syntax and mean unrelated things, and `[0]` on an earlier part is still refused (locked in `A12PointerFormatTest`).
- **The kernel-side projection was lossy one layer deeper than the CLI's.** `ComputedField` (`:adapter`) dropped `IComputedFieldInstance.getRepetitions()` entirely, so fixing `KernelEval` meant carrying repetitions through the adapter first. That is the §1c mechanism made concrete: the test-side kernel projection and the CLI's published shape have to be the *same* contract, or a CLI-level differential compares two lossy projections and agrees.

**A consequence worth stating, because it reads as a gap and is not one:** canonical A12 omits `[1]`, so the **first row's** instance pointer and the declaration coincide as strings (`Order/Lines/LineTotal`). An absent bracket *means* repetition 1 — which is also precisely why an omitted index can never be read as "all rows" (§4a).

### 4a. `--relevant`: an omitted index on a repeatable segment is REFUSED <a id="relevant-break"></a>

**Owner ruling, 2026-08-01.** `RelevantSelection` read an omitted index as **all repetitions**; A12 reads it as **repetition 1**, on both pointer types. Same spelling, opposite scope — and this one decides *which rows get validated*, so it is not a formatting difference. Three options were on the table and two are disallowed on their own terms: silently adopting A12's reading narrows every existing caller from all-rows to row-1 with a **clean pass** as the only symptom, and keeping ours means knowingly publishing a competing meaning for A12's own spelling, which the interop rule forbids outright. That leaves the third.

So an omitted index on a repeatable segment is a **corrective refusal** naming the segment and *both* explicit forms — `[0]`/`[*]` for all repetitions, `[1]` for the first. Callers that relied on omission fail loudly and migrate deliberately, which is the only outcome where nobody's validation scope changes without them deciding it. `[0]` is additionally now **accepted** as A12's all-repetitions spelling, where it previously joined the negatives as an error.

**Bounded on purpose:** a *non-repeatable* segment has exactly one instance, so an omitted index there is unambiguous under both readings and stays legal. Without that bound the rule would read as "always write an index" — noise on every ordinary selection, and not the rule. (`PartialValidationCliTest`, both directions.)

## 5. Aggregate uniformity <a id="aggregates"></a>

**Required:** `apply` and `batch` return the standard outer envelope, so `--text` dispatches on one public shape.

- `apply.data.results[]` holds **per-operation envelopes**, plus aggregate metadata (`ops`, `committed`, `failedAt`, `written`).
- `batch.data.results[]` holds **typed batch items**, because a batch child may be an artifact (`model seed`) or a catalog/schema payload rather than an envelope. Existing child-exit semantics are preserved and documented.

**Excluded:** the transitional renderer registry. A bridge preserves two parallel top-level contracts for a release — the defect being fixed — and hides the break instead of surfacing it.
