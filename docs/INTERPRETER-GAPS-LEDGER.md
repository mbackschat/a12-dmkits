# interpreter — gaps & open-issues ledger

> **What this is** — the interpreter's peer of [`DEV-API-GAPS-LEDGER.md`](DEV-API-GAPS-LEDGER.md) and [`FEATURE-GAPS-LEDGER.md`](FEATURE-GAPS-LEDGER.md): the single tracking surface for **open `:interpreter` gaps, deferred items, and to-fix issues**. It exists so open work is easy to **track, report, and pick up** — and so [`INTERPRETER-FINDINGS.md`](INTERPRETER-FINDINGS.md) can be what a findings doc should be: **settled, verified knowhow** you read to warm up and not re-investigate (like `KERNEL-FINDINGS.md`), never a backlog of dispositions ("open / to fix / deferred"). Per the CLAUDE.md *"rationale is timeless; a disposition is status"* rule — the findings hold the timeless fact, this ledger holds the live status.
>
> **The lifecycle.** A gap is born here with an `IG<n>` code under the section matching its status (§1 open / §2 deferred / §3 out-of-scope). When it ships, three things happen **in the fix's own commit**: (1) its **rationale graduates to a numbered `IF<n>` finding** in [`INTERPRETER-FINDINGS.md`](INTERPRETER-FINDINGS.md) — that finding notes it "graduated from IGn"; (2) any code/test comment citing `IGn` is **repointed to `IFn`**; (3) the gap's row is **deleted from this ledger**. **There is no "fixed/shipped" section — we don't record fixed gaps.** A fixed gap is no longer a gap; **git is the history of *when/what* was fixed, and the `IFn` finding is the *why*** — a hand-kept "shipped" list would only duplicate both and rot. So this ledger only ever lists **live, unfinished work** (the already-shipped IF20-per-cell / IF21 / IF23 / IF24 / IF25 live as findings, not here). A **deferred** gap stays in §2 with its re-open trigger; the technical detail of each gap lives in its cited `IF<n>` finding (the knowhow), this ledger holds only *what's left to do and why*.
>
> **Section invariant (the placement rule):** every section holds exactly one **live** status — **§1 = open, §2 = deferred, §3 = out-of-scope**. A FIXED/graduated entry belongs in **none** of them: shipping a fix *deletes* its row (see the lifecycle). So §1 reads "(none)" whenever nothing is open, and a FIXED entry **anywhere** in this ledger is a bug in *this doc* — git already records the fix.
>
> **Scope.** `:interpreter` only — the kernel-free Kotlin evaluator (parser, evaluation semantics, model loader, the differential/perf harnesses' interpreter side). dmkit (rulekit/modelkit/edit) authoring gaps go to [`DEV-API-GAPS-LEDGER.md`](DEV-API-GAPS-LEDGER.md); kernel-coverage classification stays in the MVK / RT-semantics / grammar ledgers.

## 1. Open (to fix)

A systematic **7-surface gap audit (2026-06-26, kernel-source-verified)** found the interpreter **materially short of full kernel parity beyond `validateFull`** — across the parser, `compute()`, the model loader, date construction, and partial validation (method: enumerate every surface where a divergence can hide — disposition prose, `unsupported`/throw census, entry-point × parameter dimensions, construct × entry-point matrix, loader-property diff, kernel ledgers cross-checked, differential-coverage holes — then verify each candidate against the kernel source). The bulk of the audit's confirmed divergences have since **shipped** (each graduated to a numbered `IF` finding + a differential lock and was **deleted** from here — git is the record). What remains below is the **residual/narrowed** set: one partial-validation aggregate gap (IG20) the new partial fuzz surfaced. The rest of the **partial-validation** dimension is modeled and locked against the kernel (rule-gating + 3VL, subset aggregates IF35, global fields IF37, custom-condition relevant-set IF38, subset uniqueness IF39), and `compute()` is at parity (cascade, ERRORED bucket, errored-dependency skip). Each row is a kernel-source-verified divergence. (Closed 2026-06-26: IG11 global-field auto-relevance → IF37; IG10 CustomCondition relevant-set propagation → IF38; the `uniqueIndex`/`RepetitionNotUnique` subset case → IF39; IG13 errored-dependency cascade-skip → IF40; IG19's DATE_TIME residual as **parity by construction** → IF33.)

### Partial validation
| code | item | status / action | detail |
|---|---|---|---|
| **IG20** | starred aggregates over a repeatable group under **mixed** partial relevance *(surfaced by the partial fuzz, 2026-06-26)* | open — IF35 gates a starred aggregate to UNKNOWN when *any* cell is non-relevant, which is right for the simple "one-row-relevant" case but NOT the general one. The partial fuzz (`PartialValidationFuzzDiffTest`, which excludes these codes pending this) found two kernel-exact rules the blanket gate misses: **`FirstFilled`** fires on the first FILLED *relevant* cell even when a later cell is non-relevant (the interpreter over-gates → UNKNOWN, kernel fires); **`Sum`** treats a cell whose **GROUP row** is non-relevant as UNKNOWN *even when the field pointer is directly in the relevant set* (the interpreter under-gates on the field pointer → fires, kernel UNKNOWN). The fix needs the kernel's per-operator partial-aggregate rule + group-row (not just field-pointer) cell relevance. Probe each operator (`Sum`/`MaxValue`/`MinValue`/`FirstFilled`/`SumOfProducts`/`NumberOfDifferentValues`) before fixing. | `Interpreter.evalFunc` cell-relevance gate; `DmInterpreter.cellRelevant` |

**The partial-validation FUZZ differential is built** (`adapter/…/perf/PartialValidationFuzzDiffTest`, 2026-06-26): it sweeps random (document, relevant-subset) combinations and asserts the interpreter's `validatePart` matches the kernel's fired-message signatures. It is the standing guard for the relevant-set dimension — and it earned its keep immediately by surfacing **IG20** (above). It currently excludes the IG20 aggregate codes; **un-exclude them once IG20 ships** (that is IG20's done-criterion).

Deferred items are in §2; a fixed gap is deleted from here (git + its `IFn` finding are the record).
