# interpreter — gaps & open-issues ledger

> **What this is** — the interpreter's peer of [`DEV-API-GAPS-LEDGER.md`](DEV-API-GAPS-LEDGER.md) and [`FEATURE-GAPS-LEDGER.md`](FEATURE-GAPS-LEDGER.md): the single tracking surface for **open `:interpreter` gaps, deferred items, and to-fix issues**. It exists so open work is easy to **track, report, and pick up** — and so [`INTERPRETER-FINDINGS.md`](INTERPRETER-FINDINGS.md) can be what a findings doc should be: **settled, verified knowhow** you read to warm up and not re-investigate (like `KERNEL-FINDINGS.md`), never a backlog of dispositions ("open / to fix / deferred"). Per the CLAUDE.md *"rationale is timeless; a disposition is status"* rule — the findings hold the timeless fact, this ledger holds the live status.
>
> **The lifecycle.** A gap is born here with an `IG<n>` code under the section matching its status (§1 open / §2 deferred / §3 out-of-scope). When it ships, three things happen **in the fix's own commit**: (1) its **rationale graduates to a numbered `IF<n>` finding** in [`INTERPRETER-FINDINGS.md`](INTERPRETER-FINDINGS.md) — that finding notes it "graduated from IGn"; (2) any code/test comment citing `IGn` is **repointed to `IFn`**; (3) the gap's row is **deleted from this ledger**. **There is no "fixed/shipped" section — we don't record fixed gaps.** A fixed gap is no longer a gap; **git is the history of *when/what* was fixed, and the `IFn` finding is the *why*** — a hand-kept "shipped" list would only duplicate both and rot. So this ledger only ever lists **live, unfinished work** (the already-shipped IF20-per-cell / IF21 / IF23 / IF24 / IF25 live as findings, not here). A **deferred** gap stays in §2 with its re-open trigger, and an **ongoing as-touched** refactor stays in §2 with its remaining-work note (it is progressing in increments, not parked — its shipped parts graduate to its `IF<n>` finding while the row stays until *all* of it lands); the technical detail of each gap lives in its cited `IF<n>` finding (the knowhow), this ledger holds only *what's left to do and why*.
>
> **Section invariant (the placement rule):** every section holds exactly one **live** status — **§1 = open, §2 = deferred / ongoing-incremental, §3 = out-of-scope**. A FULLY-shipped/graduated entry belongs in **none** of them: completing it *deletes* its row (see the lifecycle). So §1 reads "(none)" whenever nothing is open, and a fully-FIXED entry **anywhere** in this ledger is a bug in *this doc* — git already records the fix. (A partially-shipped *ongoing* refactor in §2 is not "fixed" — it stays until all of it lands.)
>
> **Scope.** `:interpreter` only — the kernel-free Kotlin evaluator (parser, evaluation semantics, model loader, the differential/perf harnesses' interpreter side). dmkit (rulekit/modelkit/edit) authoring gaps go to [`DEV-API-GAPS-LEDGER.md`](DEV-API-GAPS-LEDGER.md); kernel-coverage classification stays in the MVK / RT-semantics / grammar ledgers.

## 1. Open (to fix)

A systematic **7-surface gap audit (2026-06-26, kernel-source-verified)** found the interpreter **materially short of full kernel parity beyond `validateFull`** — across the parser, `compute()`, the model loader, date construction, and partial validation (method: enumerate every surface where a divergence can hide — disposition prose, `unsupported`/throw census, entry-point × parameter dimensions, construct × entry-point matrix, loader-property diff, kernel ledgers cross-checked, differential-coverage holes — then verify each candidate against the kernel source). The bulk of the audit's confirmed divergences have since **shipped** (each graduated to a numbered `IF` finding + a differential lock and was **deleted** from here — git is the record). **Every audit-confirmed divergence across `validateFull` / `validatePart` / `compute` is closed** — the one open item below sits in a blind spot the audit's *method* could not reach: **IG22** (a date-literal parse gap). The whole renderer-vocabulary class it also missed — the `$` outer-correlation (was IG23) and IG24–IG27 — has since shipped (IF46–IF50). The `$` gap exposed a limit of the audit itself — it enumerated constructs by the *operator inventory*, so a non-operator syntactic modifier like `$` was never in scope (IF47 records the full "why/how it hid"). partial validation matches the kernel (rule-gating + 3VL, subset aggregates IF35, per-operator starred-aggregate relevance IF42, global fields IF37, custom-condition relevant-set IF38, subset uniqueness IF39), and `compute()` is at parity (cascade, ERRORED bucket, errored-dependency skip). (Closed 2026-06-26: IG10→IF38, IG11→IF37, IG13→IF40, IG19→IF33 (parity-by-construction), the uniqueIndex/RepetitionNotUnique subset case→IF39, IG20→IF42.)

- **IG22 — the omitted-year date literal `"13.07."` (a day-month partial-date constant) is not modeled.** rulekit authors it (`DateLiteral`, `Dsl.dateValue("13.07.")` — KERNEL-FINDINGS §6 "with or without the year"), the kernel stores it as a DATE constant, but the interpreter's `coerceDate` only canonicalizes the FULL `dd.MM.yyyy` form, so a `[SomeDate] > "13.07."` comparison isn't evaluated as a date → the interpreter diverges from the kernel.
  **Probed + source-characterized (2026-07-06) — it IS validation-legal (not parity-by-construction):** `[/Order/DeliveryDate] > "13.07."` is accepted and evaluated. The omitted-year form is a **REFERENCE-YEAR feature** — the kernel injects the model's reference year into the literal (parser `DateFormat`: *"in Modellen mit Referenzjahr kann die Jahresangabe hinzugefügt werden"*), so `"13.07."` becomes `13.07.<baseYear>`. With **no** reference year (the order model) the injected year defaults to a **floor (~year 0)**, so `[Date] > "13.07."` fires **true for every real date** (probe: 2024-07-20 / 2024-06-01 / 2024-07-13 / 2023-08-01 all fire — year dominates, so it is NOT a month/day-only recurring compare). **Fix (well-scoped):** teach the date-literal coercion to accept `dd.MM.` and inject the model's base year (the interpreter already carries `baseYear: Int?` + the `BaseYear` constant), defaulting to the kernel's floor year when unset — confirm the exact default (0 vs 1) with a boundary probe before locking. Lock with a comparison differential (with AND without a configured base year). Degenerate without a base year (always-true), but real; the LAST open renderer-vocabulary-adjacent gap. Surfaced by the 2026-07-06 findings sweep.

**A full renderer-vocabulary audit (2026-07-06) found five MORE gaps of the same class as the `$` gap** (IG24–IG28) — constructs `DslRenderer` emits that no interpreter differential ever fed to `DmInterpreter` (only `*ReadTest` render-checks or kernel-only `*LawsTest` covered them). **The crash-class ones are WORSE than IG22:** they threw an *uncaught* `ClassCastException`/`IllegalStateException`, not the caught `UnsupportedConstructException`, so they **abort the entire `validate()`/`compute()` run**, not degrade one rule. Two shared root mechanisms: **(R1)** `pathOf` (`e as Expr.Field`) assumes every predicate/count operand is a plain field — any starred/group operand crashes (this bit IG24…IG27); **(R2)** `+` was numeric-only (`evalArith`→`num`) — string operands crashed. Of the five: **IG24** (concat, R2) shipped as **IF48**, **IG25** (group-scoped fill, R1) as **IF49**, **IG26** (`NumberOfFilledGroups(/Group*)`, R1) as **IF46**, **IG27** (entity value list, R1) as **IF50**; only **IG28** (the EN-only render-target decision) remains of the five.

- **IG28 — German render target unparseable (low, likely by-design).** `DslRenderer(ConditionLanguage.DE)` emits `Und`/`FeldAngegeben`/`Heute`/`@Von`; the interpreter parser hard-codes English keywords. The interpreter is EN-only today; decide whether to keep it EN-only (declare out-of-scope, since the differential authors EN and the kernel accepts EN) or make the parser language-parametric. Not a crash on any EN-rendered model.

**A second interpreter-vocabulary sweep (2026-07-06) found FIVE MORE gaps of the IG24–IG27 class — the `feldListenOp` value/count family (`Sum`/`MaxValue`/`MinValue`/`NumberOfDifferentValues`/`NumberOfFilledFields`/`SumOfProducts`) is modeled as SINGLE-STARRED-OPERAND only, but rulekit + the kernel also accept the explicit MULTI-FIELD-LIST form, GROUP operands, and non-numeric (STRING/ENUM) element types.** Each is reachable (a `*ReadTest`/kernel-`*LawsTest` proves kernel legality — e.g. `MultiFieldSumReadTest` asserts the kernel accepts `Sum(A, B)`) but has NO `*DiffTest` feeding it to `DmInterpreter` (the exact blind spot). Four crash uncaught (aborting the whole run), one silently miscounts. The unifying root: the aggregate branches assume `f.args.single() as Expr.Star` / `pathOf(field)`.

- **IG29 — multi-field `Sum` / `MaxValue` / `MinValue` crashes.** `Sum(/Order/Quantity, /Order/BackorderQuantity)` etc. (≥2 plain number fields; `Dsl.sum/maxValue/minValue(FieldOperand, FieldOperand...)`). Locus: `Interpreter.kt` `starVals` does `f.args.single() as Expr.Star` → `IllegalArgumentException` on a 2-arg list. Fix: collect values across ALL args (star-expand each `Expr.Star` via `ctx.star`, take each filled plain field); the `Aggregates` folds already take a `List<Val>`. Small. Kernel-legal (`MultiFieldSumReadTest`).
- **IG30 — `NumberOfDifferentValues`: the multi-field form AND string/enum operands crash.** `NumberOfDifferentValues(a, b)` (≥2 fields) → the same `single()` crash; a STRING/ENUM operand (`NumberOfDifferentValues(Items*/Sku)`) → `Aggregates.numberOfDifferentValues` → `numOf(Val.Txt)` `error("expected a number")`. Kernel explicitly permits both (`CountAggregate.checkValueComparable`). Fix: collect across args + count distinct by TYPED key (reuse the `"N"+scale19`/`"S"+str` canonicalization in `fieldValuesNotUnique`), not numeric. Small-medium.
- **IG31 — `NumberOfFilledFields` over a starred repetition list crashes.** `NumberOfFilledFields(Items*/Count)` → `pathOf(Expr.Star)` `ClassCastException` (root mechanism R1, the IG26/IG27 sibling on an operand the fix missed). Kernel-legal (`Dsl.numberOfFilledFields(FieldListRef)`). Fix: count filled cells across the star's rows (mirror `filledGroupsCount`/`starQuantTally`). Small.
- **IG32 — `NumberOfFilledFields` over a GROUP operand silently miscounts.** `NumberOfFilledFields(SomeGroup)` → `ctx.filled(groupPath)` is false for a group path → the group is counted as one unfilled *field* → diverges (the kernel counts the filled fields INSIDE the group). Silent-wrong (no abort). Fix: expand a group operand to its descendant fields (reuse `fillScope`'s group expansion) and count filled. Medium.
- **IG33 — `SumOfProducts` over plain (non-star) fields crashes — VERIFY kernel legality first.** `SumOfProducts(Qty, Price)` (plain `FieldRef`s; `Dsl.sumOfProducts` only `requireNumber`, doesn't require a `FieldListRef`) → `ctx.starAll((args[0] as Expr.Star).path)` `ClassCastException`. **STEP 1 is a probe:** does the kernel accept a non-repetition-list `SumOfProducts`? If it rejects at codegen (`MVK_*`), this closes as parity-by-construction (add a DSL guard); if it accepts, fix like IG29. Low confidence.

**The durable guard for THIS class (the multi-operand-aggregate net):** a single `MultiFieldAggregateDiffTest` sweeping `Sum`/`MaxValue`/`MinValue`/`NumberOfDifferentValues`/`NumberOfFilledFields` across {plain-field-list, group-list, single-star} × {number, string/enum} locks IG29–IG32 together — and, like the renderer-modifier net, it is keyed on the DSL's *emit* shapes (multi-field / group / typed) the operator-keyed guards can't see. Add it with the fixes.

**The originally-reported condition needed BOTH the `$` correlation (IF47) and the starred-quantifier-with-`Having` path** (`AtLeastOneFieldFilled(Star Having …)`), which IF47's `starQuantTally` handles. **The durable guard that closes the whole class (so "the `$`-class can't happen again") is BUILT (2026-07-06):** (1) the differential fuzz net (`InterpreterKernelFuzzTest`, 100 random docs × both engines, CI-gated on every push) now includes a `$` equality self-correlation rule (`PerfCatalog` DQ), so a `$`-eval regression fails the fuzz; (2) **`CatalogParityTest.fuzzNetCoversRendererModifiers`** asserts the fuzz corpus exercises the non-operator **MODIFIERS** `$`/`*`/`Having` — keyed on the RENDERER's emit vocabulary, the net the operator-keyed guards structurally cannot provide (a modifier is not a catalog operator — exactly how `$` hid). This is the standing prevention for IF46/IF47/IF48/IF49/IF50 (the whole renderer-vocabulary class). *Optional future extension:* a full reflective round-trip over every `Condition`/`Calculation` `permits` subtype (author + render + eval each) would additionally force a brand-new renderable NODE type into the net; the per-family `*DiffTest`s + the modifier net cover the current vocabulary.

**The partial-validation FUZZ differential is built** (`adapter/…/perf/PartialValidationFuzzDiffTest`, 2026-06-26): it sweeps random (document, relevant-subset) combinations and asserts the interpreter's `validatePart` matches the kernel's fired-message signatures across the WHOLE partial surface (including the starred aggregates — it surfaced IG20, now fixed as IF42 and un-excluded). It is the standing guard for the relevant-set dimension.

Deferred items are in §2; a fixed gap is deleted from here (git + its `IFn` finding are the record).
