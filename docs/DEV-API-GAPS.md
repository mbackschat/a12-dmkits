# dmkits DSL-API (developer perspective) — gaps

> **What this is** — the developer-perspective peer of [`FEATURE-GAPS.md`](FEATURE-GAPS.md), one persona over. dmkits (rulekit + modelkit) is also driven directly as a **typed Java library** by a **developer working inside their own JVM project** — binding a model, authoring rules/computations as typed code the compiler steers, editing structure, reading foreign rules back, and testing against sample documents, all kernel-confirmed. A 2026-06-14 review against the kernel team's developer reference (`a12-kernel/documentation/_merged/kernel-dev.md`, consult-only) surfaced the first batch. The doc keeps the review's framing (§1), the open backlog (§2), and the out-of-scope decisions (§3).
>
> **Lifecycle.** §2 holds the live, unfinished work. **This ledger records only OPEN work** — a shipped gap is **deleted**, never kept as a "shipped" list, because such a list duplicates git (the *what/when*) and the finding (the *why*) and rots against both. A gap's durable *why* is its numbered finding in [`API-FINDINGS.md`](API-FINDINGS.md), which names the `DGn` it closed, so a code comment citing `DEV-API-GAPS DGn` — or a legacy `DEV-API-GAPS §N` — resolves **by topic**: grep `API-FINDINGS.md` for the id. Two deliberate exceptions: the editor-ergonomics pair **DG11/DG12** is shown in API-GUIDE [§5c](API-GUIDE.md#refs-and-editors) instead, and **DG16** was declined rather than built, so its decision lives in §3 here.
>
> **Current state.** §2 lists what is open; read it rather than this paragraph. A row lands there only when a new developer-facing authoring friction is both surfaced and queued, and it is deleted when it ships — so a closed gap's *why* is its [API-FINDINGS](API-FINDINGS.md) finding, not a line here.
>
> **Id allocation — one CHUNK per author, declared here and nowhere else.** Two branches appending from one base allocate the same next id, so a merge has to renumber whichever side is smaller and move every citation with it — and a citation rewritten to the *wrong* entry still resolves, so no guard can see that mistake. Not hypothetical: `DG47` was allocated on both sides of the 2026-09-20 harvest and named two different gaps, one of which this repository had already closed. The same collision hit that harvest's kernel findings and API findings, each of which had appended from a shared base into ids this repository had since issued to other entries, so every one had to be renumbered by hand against its heading and every citation moved with it. Allocating from a per-author range removes the collision, and ids are dense within a range rather than globally. The boundaries live on the line below and nowhere else; an open upper bound means the range has no declared end.
>
> `dg-id-chunks: 1-999 = Martin Backschat; 1001- = Alexander Ried`
>
> **Scope — the filter that matters.** dmkits has **model-authoring scope**: it defines, edits, validates, reads, and tests a document **model** — its fields/groups/type-defs/includes/config and its **rules + computations** (the condition-language DSL). It is **not** a runtime form engine, a document-instance data-binding layer, a rendering/UI toolkit, or a persistence/service layer. The kernel dev doc is ~80% about the *runtime consumer* (manipulating document *instances*); those concerns are deliberately **out of scope** (§3).

## 1. The loop we're improving

A developer using rulekit/modelkit writes Java, so the **project's own compiler is the first safety net** — a wrong path, or a number operator on a date, fails before the kernel ever runs. The loop:

```
bind (BoundModel.ofJson) → author rules/computations via typed handles → validate (RuleDiagnostics.diagnose)
   → read foreign rules back (KernelAdapter.read, tolerant) → edit structure + rules in one session (EditSession)
   → test behaviour on sample documents (KernelAdapter.evaluate / testRule / compute)
```

dmkits already serves this well, and these strengths are the baseline the gaps built on:

- **Handles come off the model** — `m.num(path)`/`m.enumOf(path)`/`m.group(path)` fail at lookup on a wrong path or kind; the AST never holds a string a typo could corrupt.
- **Illegal states are unrepresentable** — Field ≠ Group types, no `ConfirmRef.isFalse`, enum/category values domain-checked at build, number `==`/`!=` scale-gated, wildcards erased from scalar slots.
- **Immutable records + a sealed AST** with `transform`, and **snapshot write semantics** (every write returns a *new* re-validated `BoundModel`).
- **Tolerant read** — `KernelAdapter.read` returns a sealed `ReadResult` (`Converted`/`Opaque`); an unmodeled construct is preserved verbatim, never lost.
- **One author-time front door for rules** — `RuleDiagnostics.diagnose` folds kernel + lint + gotcha + version-skew into a single `ValidationResult`.
- **Self-describing catalogs** — `OperatorCatalog`/`PatternCatalog` carry meaning, gotchas, and CI-executed examples.
- **The L2c editor/ref layer** and **runtime eval as an oracle** (`evaluate`/`compute`/`testRule`) close the read→edit→reference and prove-it-fires loops.

The gaps below were the **ergonomic and consistency remainder** — what added friction, forced a drop out of the typed surface, or surprised a developer expecting symmetry between siblings.

## 2. Open

- **DG62 — a bare-`IllegalArgumentException` refusal can contradict its own `kernel-delegated` ledger row, and nothing can see it.** `ClientRefusalKernelBasisCensusTest` checks refusals that CITE a code, which is the right scope for what it guards — a citation makes a refusal read as measured whether or not it is. But the kits also refuse with plain `IllegalArgumentException`, and those are outside the census by construction, so a code the [MVK-LEDGER](MVK-LEDGER.md) buckets `kernel-delegated` ('left to the kernel entirely') can be pre-checked by rulekit all along with no surface disagreeing. Measured 2026-09-22: `MVK_NO_STRING_OR_ENUM_OR_EXT_ENUM` was bucketed `KERNEL_DELEGATED` while `Dsl.customTypeValidity` had always refused every non-STRING/ENUMERATION operand; giving that refusal its (already-locked) code is what made the contradiction visible, and the bucket, the ledger cell and the pinned gate count all had to move with it. **Open remainder, and the triage criterion rather than a list:** a bare refusal is fine when it reports an API-usage error the kernel never sees — a wrong-kind typed handle, an arity violation, a non-absolute path — and is a gap when it encodes a rule the KERNEL also applies, because then the kit is pre-checking and owes a measured code. **Enumerated 2026-09-22:** `rulekit/dsl` carries 63 bare `IllegalArgumentException` refusals; 43 are API-usage (typed-handle kind, arity, name well-formedness, wrapper invariants, factory routing) and 20 encode a kernel rule. *Corrected the same day:* three of those 20 are `Dsl`'s `firstFilled*` factory-routing checks, which are API usage because the kernel never sees a factory; the fourth, a trailing-operand check, was removed as a second copy of the record's own list gate. **Closed:** the rounding places slot (`Rounding`, `FieldRounding`, including `AbsValue`'s refused places), which turned out to be two classes rather than one ([KF393](KERNEL-FINDINGS.md#kf393)); and the `DateRange` endpoint slot (`DateRangeConstruction` ×2), whose parse class depends on the operand's spelling, so a non-date non-entity and an `UNKNOWN` kind stay deliberately uncoded; and `SumOfProducts`' number check, which stays uncoded because an outranking gate needs the model's repeatability, but now runs last, as the kernel's does ([KF370](KERNEL-FINDINGS.md#kf370)); and `FirstFilledValue`'s list gate (×2), which cites `MVK_VARYING_TYPES_NOT_ALLOWED` now that it asks A12's gates in A12's order over the expanded fields, and stops refusing two date-bearing kinds ([KF71](KERNEL-FINDINGS.md#kf71)). `FirstFilledOperand`'s four shapes: the empty group, a category on a group and a `Having` on a group cite `MVK_GROUP_IS_EMPTY` or `MVK_NO_GROUPS_ALLOWED` exactly where neither the rule nor a semantic index can move the class, which `BoundModel` tells the operand. A `Having` on an unstarred field stays uncoded, because its class depends on whether the field crosses a repeatable level, which a `FieldRef` does not carry, and then on whether the rule iterates it ([KF71](KERNEL-FINDINGS.md#kf71), [KF424](KERNEL-FINDINGS.md#kf424)). And `DateListAggregate`'s kind check, which cites `MVK_NOT_SORTABLE` behind a leading field that is not date-like and withholds the class behind a date-like or group leader, where A12's date walk reads precision and component sets first ([KF389](KERNEL-FINDINGS.md#kf389)). Closing it exposed the same leader-routing defect in two siblings, fixed with it: `ListAggregate`'s Max/Min cited `MVK_NOT_SORTABLE` behind a date-like leader, and `NumberOfDifferentValues` refused a non-leading Boolean with the leader-only class. The model-bound factories also asked precision and component sets as two passes ahead of duplicates, and now run A12's one walk (`validate.laws.EntityListLeaderRouteLawsTest`). And `NumberOfFilledGroups`' single-group refusal (`Dsl`, `RootGroupCount`), which stays uncoded because an empty group or root answers ahead of its class and a `GroupRef` does not show it ([KF458](KERNEL-FINDINGS.md#kf458)). **Open, 1 site:** `Computation.errorCodesToSuppress`. Whether each mechanism already has a measured basis is checked as it is closed, not assumed. **Not worth a guard:** deciding 'encodes a kernel rule' from source text is the same low-precision classification [AF158](API-FINDINGS.md#af158) records being built, measured and reverted, and a guard that fails honest content gets disabled. The lever is the promotion itself — coding a refusal forces the ledger, the bucket and the gate count to agree, so the way to close a site is to measure it and cite it.
- **DG67 — `GroupFilled(Group For key)` has no typed form.** A12 admits `GroupFilled(Packages For "P1")` and `GroupNotFilled(Packages For "P1")` ([KF351](KERNEL-FINDINGS.md#kf351)), but `GroupPresenceCondition` holds a `GroupRef`, so the first cannot be authored. Its read stays `Opaque` on purpose, because the kernel node is a one-operand `AllGroupsFilled`, which A12 refuses when spelled that way (`MVK_PARAMSIZE_INVALID2`). `adapter.SemanticIndexGroupOperandReadTest.aSingleIndexedGroupPresenceReadsAsItsNodeOrStaysVerbatim` locks that. `GroupNotFilled(G For k)` reads as `NoGroupFilled(G For k)`, the same node. Settled by a typed indexed presence, either a widened operand or a sibling record, swept through every exhaustive `Condition` switch (Linter, `ExplanationTreeBuilder`, `ConditionComplexity`, `DslRenderer`, bridge `Predicates`), then flipping that lock and choosing the canonical single-presence spelling for an indexed group.
- **DG68 — an index-selected group is authored by constructor, not by a ref.** Fields have `ref.forIndex(key)` / `ref.semanticIndex(key)`. A group needs `new GroupSemanticIndexValue(m.flattenGroup(path), key)`, and the group-scoped field-fill factories (`Dsl.allFieldsFilled(GroupListRef…)` and its peers) do not take one, so only `Dsl.entityListPredicate` can. Settled by a `forIndex` on the group handle and an `IndexedGroupValue` path through the field-fill family, shown in [API-GUIDE](API-GUIDE.md), with `SemanticIndexGroupOperandCarrierLawsTest`, `SemanticIndexWildcardPlacementLawsTest` and `EntityListDuplicateGateTest` moved to the new idiom.
- **DG69 — an index-selected field below a star has no typed aggregate operand.** `NumberOfFilledFields(/Order/Packages/Parcels*/Label For "P1") > 0` is kernel-admitted (measured 2026-09-23) and reads `Opaque`. `IndexedFieldValue` holds one `FieldRef`, so it cannot carry the starred list, and the converter refuses the shape rather than losing the star. `FirstFilledOperand` already carries a list with a key. Settled by an indexed field-list operand for the aggregates and quantifiers, with its kernel admission grid measured first, since A12's star-placement law was measured on group operands ([KF351](KERNEL-FINDINGS.md#kf351)).
- **DG70 — a group-list quantifier cannot hold an index-selected FIELD.** `AtLeastOneGroupFilled(/Order/Packages/Carrier For "P1", /Order/Title)` is kernel-admitted (measured 2026-09-23) and reads `Opaque`, because `GroupListOperand` permits `FieldRef`, `GroupListRef` and `IndexedGroupValue` but not `IndexedFieldValue`. Settled by admitting it there once the five quantifiers' verdicts on it are measured, and by reading it back.
- **DG71 — an index-selected field cannot reach the operations that exist only on a field handle.** Each row is kernel-admitted and reads `Opaque` (measured 2026-09-23 on `adapter.SemanticIndexFieldOperandPositionReadTest`'s fixture): `[/Order/Packages/Carrier For "P1"] PatternMatched "[A-Z]{2}"`, `Length(/Order/Packages/Carrier For "P1") > 10`, the keyed value-list subject `FieldValueIncludedInValueList(/Order/Packages/Carrier For "P1", "DHL", "UPS")`, and the keyed member of a literal value-list quantifier, `AtLeastOneFieldValueIncludedInValueList(/Order/Packages/Carrier For "P1", /Order/Title In "n/a")`. The keyed cell is an `IndexedFieldValue` read as a `StringExpr`, while `matches`/`violates`, `length()` and `in(…)` live on `StringRef`, and the literal value-list factories take `StringRef`/`EnumListRef`/`FieldListRef` members. A12 fixes where the operations belong. The pattern operators and `Length` take a field or its keyed cell and refuse every expression ([KF387](KERNEL-FINDINGS.md#kf387)), so they cannot move to `StringExpr` without making refused shapes authorable. Settled by a sealed cell type that `FieldRef` and `IndexedFieldValue` both satisfy, held by `PatternCondition`, `LengthOf` and `ValueListCondition` in place of `FieldRef`, and swept through their exhaustive consumers, including the interpreter-bridge. Read-back and a row per operation lock it.
- **DG72 — the list-QUANTIFIER and value-list carriers still cite a list gate that an operand's read can pre-empt.** A12 checks a semantic index and a group's emptiness as it reads each operand, ahead of every list gate, and the first unreadable operand answers ([KF458](KERNEL-FINDINGS.md#kf458)). The entity-list aggregates and `FirstFilledValue` withhold their list gates' classes on a list holding an index or a group ([AF160](API-FINDINGS.md#af160)). The other carriers that call `DuplicateGate` still cite on such lists: the field-fill quantifiers (`EntityListPredicate`, `FieldListEntityListCondition`), the group-list quantifiers (`GroupListPredicate`), `NumberOfValueInFields`, the value-list quantifiers (`FieldListValueListCondition`, `ValueListCondition`) and `RepetitionNotUnique`. **What would settle it:** per carrier, the kernel grid `validate.laws.EntityListOperandReadLawsTest` holds for the aggregates, since the aggregates' order is a claim about these carriers, not a measurement of them. Then withhold where the class moves. **Blocks nothing:** the refusals stand either way, only the cited class can be wrong.
- **DG74 — the model-bound path withholds a numeric or count aggregate's class on a group list it could read.** `BoundModel` sees a group's expansion, so it can tell an empty group from one holding fields, and its temporal-extremum and `NumberOfDifferentValues` walk already cites on that basis. `Sum`, the numeric `MaxValue`/`MinValue`, `NumberOfFilledFields` and `NumberOfFilledGroups` have no model-bound factory, so every consumer that holds a model, the interpreter bridge first, gets their duplicate, root, param and kind classes withheld on a group list (`bridge.ConditionBridgeTest`). **What would settle it:** model-bound factories that read the operands first and then ask the records' own gates coded, as the walk does. **Blocks nothing:** an under-report, never a wrong class.
- **DG73 — the model-bound temporal walk stops at a group operand instead of walking its expansion.** A12 walks a group's expanded fields in place ([KF389](KERNEL-FINDINGS.md#kf389)), so `MaxValue(DatedBatches*, ApproxDay)`, a group of full dates leading a partial one, is `MVK_PARTIAL_DATE_NOT_ALLOWED` in A12 and is admitted by `BoundModel.latestOf`, which leaves the list to the kernel (row locked in `validate.laws.EntityListLeaderRouteLawsTest`). Until 2026-09-23 the precision pass skipped the group and refused that list with the right code, but only because the group happened to hold full dates. `BoundModel.descendantFields` is already A12's expansion for typing ([AF162](API-FINDINGS.md#af162)). **What would settle it:** walk rows with a group leading and a group in the middle, holding a partial date, a non-date and a second component set. An empty group is settled: the walk reads every group first and cites it ([KF458](KERNEL-FINDINGS.md#kf458)). **Blocks nothing:** an under-report, never a wrong class.

## 3. Adjacent but out of scope

The durable decisions about what dmkits deliberately does *not* do (its model-authoring scope — not a runtime form engine, instance-data layer, or UI):

- **Document-instance manipulation** (`DocumentV2` read/update/merge/traverse) — the runtime-consumer surface and ~80% of the dev doc. dmkits authors the *model*, not its instances; it runs instances only as a *test oracle* (`evaluate`/`compute`).
- **Typed-accessor / overlay code generation** over document instances — consumer-app codegen, not model authoring.
- **Mapping runtime** (model→model data-transfer execution) — the dev doc covers running generated mapping code; mapping *modeling* is a separate modeler concern.
- **Rendering / UI / data-binding / ResourceBundle locale plumbing** — presentation and runtime, never model content.
- **Custom-condition / custom-field-type *implementations*.** The model only *references* them (`CustomCondition <Name>` in a condition; a `Custom` field type), and dmkits already represents those references (`CustomConditionRef`; the `custom` field builder). The Java/TS validator impls are runtime — out. The `CustomCondition` operator catalog entry carries the author-facing callback-owned dependency, formal/relevance-pointer, empty-eligibility, and error-condition polarity gotchas; there is no remaining authoring-surface gap.
- **Model-version migration** — a distinct concern with the kernel's own `MigratorCli` / `IDocumentModelMigrator`; dmkits authors/edits and deliberately never bumps a model's version on write (same call as [`FEATURE-GAPS.md`](FEATURE-GAPS.md) §4). dmkits' job is to **detect** skew (`RK_MODEL_VERSION_SKEW` / `RK_MODEL_VERSION_INCOMPATIBLE`) and stay tolerant — not to migrate.
- **`variantFilter` authoring** (was DG16) — a field/rule/computation may carry a `variantFilter` (`{filterType: ONLY|ALL_EXCEPT, variants}`) that gates its per-variant membership (KERNEL-FINDINGS "variant filtering"). dmkits deliberately does **not author or interpret** it: it is a **pass-through** — an existing model that carries one has it **preserved verbatim** on a modelkit load→edit→save (the raw-JSON tree surgery never strips an unmodeled slot; the interpreter still *honors* it on load, IF36). *Decision 2026-07-06 (was briefly built as DG16, then rolled back): variant modeling is a modeler concern; the authoring surface would need to span field/rule/computation × draft/edit/serializer for no current consumer. Re-open only if a consumer must AUTHOR variant-scoped elements. Preservation is locked by `modelkit.VariantFilterPreservationTest`.*
- **Warm-kernel daemon / caching generated validation code** — a performance concern, the library peer of the BA doc's `dmtool serve`; out of scope for the same reasons (see that non-goal in [`FEATURE-GAPS.md`](FEATURE-GAPS.md) §4).
- **Grouping the `Dsl` factory into sub-facades** *(an API-shape non-goal, not a scope exclusion)* — `Dsl` stays a **flat** factory by design. A coding agent — a first-class consumer of this API — discovers operators by querying the **catalog** and grepping examples, not by browsing IDE autocomplete the way a human does; so sub-facades (`Dsl.dates().…`) would aid a human's autocomplete but be a *net* debt for the agent (an indirection + a "which facade?" wrong-guess surface + a dual API). The discovery investment goes into the catalog + consistent verb-prefix naming instead. Full human-vs-agent reasoning: **API-FINDINGS finding 52** / API-GUIDE [§6](API-GUIDE.md#semantics-as-data). Re-open only if `Dsl` becomes *incohesive* (mixes concerns beyond constructing a DSL node).
