# Interpreter findings — design & treatment record

The numbered **design-findings** for the `:interpreter` module (the kernel-free, native-safe + Kotlin/JS rule evaluator) — the *why* behind how it reproduces kernel behavior. This is the interpreter's peer of [API-FINDINGS.md](API-FINDINGS.md) (the rulekit/modelkit library's findings): a **rationale record, not a status surface**. What's *built* is shown by the differential tests (`adapter/…/laws/*DiffTest.kt`) and the catalog-parity meter; the implementation structure is [INTERPRETER-ARCHITECTURE.md](INTERPRETER-ARCHITECTURE.md), the design contract [INTERPRETER-SPEC.md](INTERPRETER-SPEC.md).

> **Open issues, deferred items, and to-fix gaps are NOT here — they live in [INTERPRETER-GAPS.md](INTERPRETER-GAPS.md)** (the live `IG<n>` items + §3 out-of-scope; a shipped gap is deleted from the ledger and lives as a finding here — e.g. IG1→IF25, IG7→IF26). This doc is **settled, verified knowhow** you read to warm up and not re-investigate (like `KERNEL-FINDINGS.md`): the timeless fact, the decision, the *why*. Where a finding below mentions a deferred/residual item, the live *status* is tracked in the ledger by `IG<n>`; the finding keeps only the knowhow.
>
> **Anti-smell rule (the one that bit IF20 — added 2026-06-26):** a finding states what the interpreter **DOES** and **why** — it must **never** carry a "**not modeled** / not yet / deferred / out of scope" *status about the interpreter*, and must never preserve an audit's "not modeled" table. That is a **disposition → the ledger**. State the **kernel FACT** (e.g. "X has no DM-JSON key, so it can't appear in a loadable model") as timeless knowhow and **point to the ledger** (`IG<n>` / §3) for the live status. "The interpreter doesn't do X yet" is exactly the claim that goes stale the moment X ships (it did, repeatedly) — so it lives in the ledger, never here.

**Where a fact lives — the routing rule + its decision test (owner-set 2026-06-23; sharpened 2026-06-26 after a mis-file).** Three homes, chosen by *what the fact is about*:

| the fact is about… | home | recorded as |
|---|---|---|
| **what the KERNEL does** — a behavior, capability, error code, limit, or extensibility surface (true regardless of our code; a kernel-team member would recognize it, and it would matter even if neither the interpreter nor dmkit existed) | [KERNEL-FINDINGS.md](KERNEL-FINDINGS.md) (write), cross-checked vs the consult-only `../a12-kernel-demo/KERNEL-SEMANTICS.md` | section-numbered to mirror KERNEL-SEMANTICS; experiment/source-verified |
| **how the INTERPRETER reproduces / diverges from / locks it** — an engine design choice, a mechanism, a deliberate divergence, the differential that proves parity | **here** (an `IF<n>`) | cite the kernel fact in KERNEL-FINDINGS; keep only the interpreter treatment + the lock |
| **how rulekit/modelkit (the JVM library) treats a kernel fact** | [KERNEL-INTEGRATION-NOTES.md](KERNEL-INTEGRATION-NOTES.md) | the treatment note |

**The decision test — apply it before writing a finding:** *"Would this fact be true, and worth recording, even if our interpreter and dmkit did not exist?"* → **yes ⇒ KERNEL-FINDINGS** (a kernel truth); **no, it's about how OUR code mirrors/diverges/locks it ⇒ here.** A finding that is *purely* a kernel statement whose interpreter "treatment" is generic (e.g. "an unknown X fails loud") belongs in KERNEL-FINDINGS with a one-line pointer from here — **not** dressed as an `IF<n>`. (Worked example of the trap: *"custom computations are not a kernel concept"* moved to KERNEL-FINDINGS "Custom-extensibility surface" on 2026-06-26 — it was a kernel-capability truth, not an interpreter design. A full sweep that day confirmed it was the **only** such mis-file; every other `IF<n>` is genuine interpreter treatment that correctly cites its kernel fact in KERNEL-FINDINGS §2/§3/§6/§9.)

Correctness throughout = **agrees with the real kernel** (the `RuntimeLaws` differential oracle). Each finding cites the lock.

### IF0 — Clean-room reimplementation is a LICENSE boundary, not a style choice (decided 2026-06-23)

Why the interpreter reimplements rather than delegates, and why it derives from behavior rather than source: the A12 kernel is **EUPL-1.2 (copyleft) / commercial**. A dmtool runtime that *used* the kernel (linked, shipped, or called it) would be a combined work the EUPL copyleft reaches → it would have to ship as EUPL (or under the commercial license). The interpreter exists to give the **native runtime a kernel-free engine**, so that runtime carries **no kernel code and is free of the EUPL** — and, independently, the kernel's Groovy codegen can't compile into a native image, so delegation fails the native goal regardless. Two consequences that govern every operator:

- **No delegation** — the interpreter never calls the kernel (purity-lint-enforced: no `com.mgmtp.*` in any source set). The `--kernel` flag is the only kernel-touching path, JVM-only, refused in native; that JVM distribution is where EUPL/commercial applies.
- **Clean-room from behavior, not a source port** — each operator is derived from the **differential oracle** (the kernel as a *black box*) + the public spec, and written as original Kotlin. The kernel source may be **read freely for *understanding*** — scan the **operator *and* generator sources** proactively to learn the real semantics and surface *surprising special cases* you'd never think to probe blind (not only to audit a known divergence). But a fix is **never a transliteration** of kernel source (a line-by-line port can be a copyright derivative that re-attracts the EUPL): the loop is *read source → write original Kotlin → lock with the differential*. Copy the mechanism/behavior/special-case (not protected); never the expression. This is the [[license-safe rule]] applied to the runtime engine. Detail: `CLAUDE.md` "Interpreter … #1 rule".

**The behavioral bar is EXACT match (the co-equal #1 rule).** Clean-room is the *how*; the *what* is that the interpreter equals the kernel bit-for-bit on every legal input. A kernel special case that is **observable through the differential** is a **must-match**, never droppable as "old/obsolete" — the Feb-28 leap-year time-clearing, the scale-19 compare-rescaling, the `MathContext(50)` arithmetic cap all qualify. The "report German-only/obsolete/feature-flagged cases for review" guidance is **narrow**: only things that change *no* differential outcome — German message *text* (IF3 — we use our own), a dead/feature-flagged path that never runs, editor/rendering cruft — are reportable-and-droppable. If it moves a differential result, match it exactly.

### IF1 — Operator dispatch is enum-keyed by the kernel construct name; the AST stays string-typed

The evaluator dispatches presence predicates and value functions on the `PredicateOp` / `FunctionOp` enums (each carrying its kernel construct name, e.g. `FieldFilled`, `Sum`), not on raw strings. But the AST node (`Cond.Pred.name` / `Expr.Func.name`) keeps the name as a **string** on purpose: the kernel vocabulary is open and growing (109+ constructs), and an *unmodeled* operator must round-trip far enough to be **reported** (`validate` returns it as `unsupported`), not fail at parse. So the parser emits the string; the evaluator decodes the handled subset via `byName`, and an unknown name → `null` → `UnsupportedConstructException` (caught and reported). The enums double as the handled-operator registry that operator-coverage growth extends. *(Locked: every `*DiffTest`; the registry is `Operators.kt`.)*

### IF2 — Value-list membership reuses the typed `==` path, so empty→UNKNOWN falls out for free

`FieldValueIncludedInValueList` is evaluated by `evalExpr(field)` then the same typed `eq` used by `==`, against each member expression. This means the kernel's two value-list facts (KERNEL-FINDINGS §8) are reproduced *without special-casing*: an empty string/enum operand evaluates to `Val.Unknown` → the predicate is `Tri.UNKNOWN` → neither the included nor the `Not` form fires; and members compare with the field's type (numbers numerically, strings by text). Reusing the existing 3VL machinery — rather than a bespoke string-contains — is why the differential passed on the empty and number cases. *(Locked: `adapter.laws.ValueListDiffTest`.)*

### IF3 — `$field$` and formal-error text: faithful structure, own prose

Both message tiers reproduce the kernel's **structural** channels exactly but diverge deliberately on free text, to keep the publishable `:interpreter` artifact clear of kernel-copyrighted strings:
- **`$field$`** resolves to the field's label-for-locale else the field NAME (`ModelDef.labelOf`), mirroring the kernel under a label provider — see KERNEL-FINDINGS §3 and the cross-engine treatment in [KERNEL-INTEGRATION-NOTES.md](KERNEL-INTEGRATION-NOTES.md).
- **Formal errors** emit the kernel's verbatim `FormalErrorCode.id` + `formalePruefung` + pointer + ERROR/VALUE, but the human text is the interpreter's **own wording (Option A)** — the kernel's German bundle is its copyrighted text (IF0 license boundary), so byte-identical kernel text is a deliberate non-goal; its live status is `IG6` (KERNEL-INTEGRATION-NOTES "Formal-error message text"). *(Locked: `adapter.laws.DisplayNameDiffTest`, `FormalErrorMessageDiffTest`.)*

### IF5 — Field-list quantifier polarity is computed, not tabled

The field-list quantifiers (`NoFieldFilled`/`AtLeastOneFieldFilled`/`NotAllFieldsFilled`/`MoreThanOneFieldFilled`/`NotExactlyOneFieldFilled`/`FieldsNotCollectivelyFilled`) share one firing law — a function of the filled-count `k` over `N` operands (`quantifierFires(op, k, n)`), reused by both `evalPred` and the polarity computation. Their **message polarity is data-dependent** (KERNEL-FINDINGS §1): rather than guess a static `MsgType` per operator (which is *wrong* for `NotExactlyOneFieldFilled`), `PredicateOp.polarity` is `null` for the quantifiers and `predType` computes it the way the kernel does — **OMISSION iff filling some empty operand (raising `k` toward `N`) could clear the firing, else VALUE**. One rule covers all six and the data-dependent case falls out for free. *(Locked: `adapter.laws.FieldListQuantifierDiffTest`.)*

### IF6 — The empty-row gate is condition-structural (`canFireEmpty`), not a data check

A source audit (clean-room: behavior confirmed via the differential) found my row gate was a **data** check — "the row carries any value" (`EvalContext.evaluated`) — which wrongly skipped a *truly-empty* row, so a mandatory-presence rule like `NoFieldFilled(A, B)` never fired on a blank instance (and my own quantifier test masked it by padding a sibling). The kernel's gate is **structural**: evaluate iff the row is non-empty **or** the condition `canFireEmpty`. `Interpreter.canFireEmpty` recurses the AST — a comparison/pattern can't (keeps empty-as-0 suppressed on a blank row), a presence predicate fires-on-empty iff its count-law holds at k=0 (`quantifierFires(op, 0, n)` / FieldNotFilled, GroupNotFilled), `And`=both, `Or`=either. The 3VL "leaf UNKNOWN leaks under `Not`/`Or`" the audit also noted is **not reachable** — the DSL/parser has no standalone `Not`, so an UNKNOWN never reaches a position where it differs observably from FALSE; left as-is (no speculative change). *(Locked: `adapter.laws.EmptyRowGateDiffTest`.)*

### IF7 — The clock constants read an INJECTED current date, not the platform clock

`Today` (the date-valued, no-operand current-date constant) resolves to `EvalClock.today`, **injected** on the `DmInterpreter` constructor — *not* read from a platform clock. Two reasons force injection: `commonMain` may not call `java.time` / `Date.now()` (the purity lint), and a deterministic value is what makes evaluation testable. The kernel reads "today" from its own runtime clock; the interpreter's contract is **"given this current date, `Today` = that date"** — the consumer supplies it (dmtool from the JVM clock; a JS consumer from `Date`). With **no clock** a `Today` rule cannot be evaluated → it is reported `unsupported` (tolerated, the [[IF1]] round-trip), never crashed.

This shapes the differential: the kernel side uses its **wall clock** and the interpreter side the **injected** date, so they could only be pinned to the same instant via a midnight-racy `LocalDate.now()` read. Instead the differential is made **wall-clock-independent** — it compares `OrderDate` against dates FAR from any plausible "today" (year 2000 / 2999), where both sides agree regardless of the exact current date; it locks that `Today` behaves as a *date* in a chronological comparison. The exact-value boundary (`== Today`) is locked **deterministically in `commonTest`** with a fixed injected clock (no kernel). AST-wise a no-operand constant is `Expr.Const`, dispatched via the `ConstantOp` enum (the [[IF1]] enum-keyed pattern); `Now` (date-time) and `BaseYear` (model base-year metadata, polymorphic) extend it as those types land. *(Locked: `adapter.laws.ClockDiffTest`, `InterpreterMultiplatformTest.todayConstantResolvesToInjectedClock`.)*

### IF8 — TIME is an ISO-text value (`Kind.TIME` → `Val.Txt`); malformed TIME/DATE_TIME now format-checked (2026-06-25)

A `Kind.TIME` field is modeled as a `Val.Txt` holding the ISO `HH:mm:ss` string — **no new `Val` variant**, exactly as `Kind.DATE` is. The reason is the same one that makes date comparison free: a zero-padded ISO time string's **lexicographic order is its chronological order**, so the existing text `ORDER` comparator already compares times correctly, and the time-of-day extractors (`HoursFromTime`/`MinutesFromTime`/`SecondsFromTime`) just parse the `HH:mm:ss` parts (the `timeComponent` sibling of `dateComponent`). `DATE_TIME` follows the same pattern (`yyyy-MM-ddTHH:mm:ss`, still ISO-ordered). An empty TIME → `Unknown` (not evaluated), like DATE.

**The formal check:** a malformed `TIME` or `DATE_TIME` value emits the kernel's **`datumFormatFalsch`** (VALUE — probe-verified, the same code as a bad DATE) and resolves to `Val.Unknown`, suppressing a referencing rule (without it a malformed time would resolve to a plain `Val.Txt` and even *escape* suppression — a correctness concern, not just a missing message). `parseTimeToIso` (DateMath) validates the field's time format + ranges; the field's date-ish format reaches the check via `ModelDef.dateLikeFormatOf` / the `Document` `timeFormats` map. *(Locked: `adapter.laws.TimeDateTimeFormalDiffTest` (formal-message + suppression vs the kernel), `adapter.laws.TimeExtractDiffTest`.)* The `DATE_RANGE` formal messages (`datumBereich*`) and **calendar validity** (Feb-31 etc.) are now implemented too — IF12.

### IF9 — Value-vs-omission leaf typing is DIRECTIONAL and sign-aware (matches the kernel's `kannGroesser/kannKleiner`)

The kernel types a fired comparison OMISSION (`TRUE_AF`) only when filling an operand *in the breaking direction* could clear it (`BedingungsOperatorHelper.vergleiche`): GT/GE break when the left shrinks or the right grows; LT/LE the mirror; EQ when either can move; NE depends on which side is larger. The per-operand fillability of an **empty number** is asymmetric — `kannGroesserWerden = true` (always fillable bigger) but `kannKleinerWerden = hatVorzeichen` (fillable smaller only if SIGNED) — and the sign comes from **`NumberType.positivesOnly`**, *not* `minValue` (verified: `BirthDay` with `minValue:1` is still signed; only `positivesOnly:true` is unsigned). Source: `RuntimeController.feldWertAlsZahl`, TS twin `BigDecimalUtils.ts`.

My earlier `leafOmission` was non-directional + sign-unaware (OMISSION if *any* operand empty/growable), which diverged for unsigned fields: `[UnsignedEmpty] >= 0` is **VALUE** in the kernel (an unsigned 0 can't shrink, so filling can't break it) but I typed it OMISSION. Now `Interpreter.leafType(op, …)` computes a directional `Fill(canGrow, canShrink)` per operand and applies the kernel's per-operator rule; the sign is read via `EvalContext.signed(path)` (the general `Document` answers it from an `unsignedFields` set — sign rides with the instance context, like `kinds`, because the evaluator resolves operands through `ctx`). **Key design choice for zero regression:** only a **field** operand gets the directional+signed `Fill`; every non-field operand (star aggregate, function, arithmetic) keeps the prior *symmetric* `leafOmission` value, and with `canGrow == canShrink` every operator's rule reduces algebraically to the old `leafOmission(left) || leafOmission(right)` — so aggregates/arith are provably unchanged, and only unsigned-empty *number fields* move. The same directional model extends to the **starred aggregates** (`Interpreter.funcFill`): a `Sum`'s omitted-tail fill is `(canGrow=true, canShrink=signed)`, `MaxValue` `(true,false)`, `MinValue` `(false,true)` — the kernel's `NumberCombiner` directions — so an unsigned `Sum(*) >= 0` types VALUE while a signed one types OMISSION (a signed `Sum` is `(true,true)` ≡ the old symmetric notion, hence unchanged). The **count** aggregates stay symmetric (kernel: a fillable count operand is unconditionally OMISSION). The CLI loader reads `positivesOnly` → `FieldDef.signed` → `ModelDef.unsignedFields` → `Document`, so dmtool's runtime matches too. *(Locked: `adapter.laws.DirectionalPolarityDiffTest` + `AggDirectionalPolarityDiffTest`; the signed cases stay green in `PolarityDiffTest`/`AggPolarityDiffTest`.)*

### IF10 — Layer the engine for a future generator: data-access → runtime semantics → strategy (decided 2026-06-23)

We implement the **interpreter** (tree-walk) now, but the owner wants the door open to a **generator** later — the kernel's approach, which emits per-model code instead of walking an AST. The key realization: **an interpreter and a generator are two evaluation *strategies* over one shared runtime.** The kernel proves it — its codegen (`kernel-core-codegen-rules`) emits Groovy that *calls* `BedingungsOperatorHelper` / `ValidierungsErgebnis` / `Combiner` (the runtime operator helpers); the generated code is just a different *driver* of the same semantics. So the engine is layered, and the operator semantics never know which strategy is on top:

```
   AST  (model / ast / parse)
    │  fed to
    ▼
 ┌──────────────────────────────────────────────────────────┐
 │ Strategy            interpreter (tree-walk)  ← TODAY        │
 │                     generator (emit code)    ← FUTURE      │
 └───────────────────────────┬──────────────────────────────┘
            delegates to      │      (both strategies, same calls)
 ┌───────────────────────────▼──────────────────────────────┐
 │ Runtime operator semantics  — PURE, AST-walk-agnostic      │
 │   3VL and/or · directional number compare · quantifier     │
 │   count-laws + polarity · DateMath · aggregates · value-   │
 │   list · pattern   (over resolved Val / Tri / Fill)        │
 └───────────────────────────┬──────────────────────────────┘
            over resolved     │      values
 ┌───────────────────────────▼──────────────────────────────┐
 │ Data access   EvalContext / Document                       │
 │   field · filled · signed · star · reps                    │
 └──────────────────────────────────────────────────────────┘
```

**The discipline that keeps it generator-ready:** operator semantics must be **pure functions over resolved values**, not inlined into the tree-walk — so a generated program could call them exactly as the interpreter does. The **value-only** semantics now obey this as pure, strategy-agnostic functions: `DateMath`, the `PredicateOp`/`FunctionOp` registries, the **three-valued Kleene logic** (`Kleene.and`/`or`/`not`, `eval/ThreeValued.kt` — the kernel's `combineUND`/`combineODER`), **`quantifierFires`** (a top-level fun beside `PredicateOp` in `Operators.kt`), the value comparison **`ValCompare`** (`language` + `ORDER`), the **aggregate folds `Aggregates`** (`sum`/`min`/`max`/`numberOfDifferentValues` + `SumOfProducts` — pure `List<Val> -> Val`; the same fold serves the operand-list `Min`/`Max` and the starred `MinValue`/`MaxValue`), and the **comparison-polarity rules `Polarity`** (the `Fill` value object + `fillable`/`neFillable`/`anyMove` — the kernel's `vergleiche` "is this firing fillable?" decision over two operand `Fill`s). **The extraction completed 2026-06-27 (the IG5 refactor fully landed):** every substantial operator semantic is now a pure runtime function. What remains *inside* `Interpreter` is **operand RESOLUTION** — the data-access half that *belongs* in the strategy: resolving a field/aggregate operand to its `Fill` (`fill`/`funcFill`/`starFill`, reading `EvalContext` fill/sign), the star walks (`starVals`/`starAll`), `evalExpr`, and a couple of trivial resolution-coupled inline classifications (the value-list IN/OUT count, the pattern regex match). The strategy **resolves + dispatches**; the runtime layer **applies the operator** — so a generator emits the same runtime calls over its own resolution. When adding an operator: put its **semantics** in the runtime layer; let the strategy only **dispatch + resolve operands**. **We do NOT build the generator now** — this is purely preparing the structure so adding one later is a new top layer, not a rewrite. (Rhymes with the IF0 clean-room separation: the runtime stays kernel-free and strategy-agnostic.)

### IF4 — `GroupFilled` is an `EvalContext` seam resolved only by the general `Document`

"Is this group filled?" needs the document's instance structure, which only the general `Document` models; the single-row / repetition spike contexts (`SingleRowDoc`/`RepDoc`, slated for consolidation) don't, and throw the same way `star` does on a flat doc. So `groupFilled` is an `EvalContext` method the general `Document` overrides, **splitting on repeatability to match the kernel's `GroupFillCache` exactly** (KERNEL-FINDINGS §9 "`GroupFilled` splits on repeatability"): a **non-repeatable** group is filled iff a valued descendant is in the row's scope; a **repeatable** group is filled iff *its row is instantiated* (a created-but-empty repeat row counts — `repsFor(g) in rowsOf(g)`). This resolved the earlier "created-empty repeat row" divergence and is what requiredness's `GroupFilled(relativeTo)` gate rides on ([IF11]). Distinct from the `*`-aggregate form (`GroupFilled(Items*)` referenced from a *non-iterating* outer scope, which the kernel rejects without the asterisk, `MVK_NO_WILDCARD`) — that parses to a `Star` operand and belongs to the `*`/aggregate family. *(Locked: `adapter.laws.GroupFilledDiffTest` (non-repeatable) + `adapter.laws.RequirednessDiffTest` (the repeatable row-exists gate).)*

### IF11 — Requiredness is operand-unknown (not a whole-rule skip), unified with format errors

`mandatoryField` (a required-but-empty field, KERNEL-FINDINGS §4) is modeled exactly as the kernel's autogenerated mandatory rule, but the interpreter realizes both of its effects through **one** predicate, `DmInterpreter.requiredEmpty(path, ctx)` = empty **and** the mode's `GroupFilled` gate holds (`ABSOLUTE` is unconditional with no repeatable ancestor, else gated by the lowest repeatable ancestor; `RELATIVE_TO_PARENT` by the immediate parent — both via the repeatability-aware [IF4] `groupFilled`). Index fields are folded in by `ModelDef.requirednessOf` (auto `RELATIVE_TO_PARENT`). The two effects:

- **Emit** `mandatoryField` (OMISSION, pointer = the field) per required-empty instance — unconditional-`ABSOLUTE` fields are checked at the canonical all-1s pointer via `Document.filledAt` (they fire even on an un-instantiated document); the rest iterate `contextsFor(emissionScope)`.
- **Suppress** referencing rules by resolving the field to `Val.Unknown` — **NOT a whole-rule skip**. This was the key correction: the old `firstFormalError` gate dropped the *whole* row, which diverges from the kernel's **branch-scoped** unknown (KERNEL-FINDINGS §3 refinement — `[ReqNum] < 100 Or <true>` still fires). The fix unifies format errors and requiredness behind one `formalErrorAt(path, ctx)` oracle, fed to `Interpreter`'s `invalid` lambda; the 3VL then does the rest. So a single root change fixed a latent `Or`-compound bug for format errors too (the class, not just the reported requiredness case). *(Locked: `adapter.laws.RequirednessDiffTest` + the `Or`-fires case in `adapter.laws.SuppressionDiffTest`.)*

### IF12 — Format-aware dates: canonicalize to ISO; `DateRangeType` → `Val.Range` (locale-variant by reading the format)

The interpreter shortcuts a DATE as ISO `yyyy-MM-dd` text (so comparison is lexicographic-chronological and the extractors parse directly). The rest of the date family breaks that shortcut — `DateRangeType` renders `dd.MM.yyyy`, `DateTimeType` is `yyyy-MM-dd'T'HH:mm:ss` — so the foundation is **carry each date field's `format` and canonicalize to ISO**. First slice (this increment): `Kind.DATE_RANGE` + `Val.Range(startIso, endIso)`; the general `Document` parses a rendered range value via its `(format, separator)` ([ModelDef.rangeConfig]) into two ISO endpoints with a **structural, format-driven parser** (`DateMath.parseRangeToIso` — runs of `y`/`M`/`d` as digit groups, an anchored regex that splits the two halves even when the separator also appears inside the format). Because it READS the declared format, the **en/US `MM/dd/yyyy` and de `dd.MM.yyyy` variants are handled by the same code** (no locale table) — locked on the pure engine (JVM+JS) by `DateFormatTest`. `StartOfDateRange`/`EndOfDateRange` then return the start/end as an ISO date the `*FromDate` extractors read (`adapter.laws.DateRangeDiffTest`).

**The malformed-range formal check:** probe-verified, the kernel emits **`datumBereichTrennerFehlt`** when the value does not split into two on the separator, **`datumBereichFormatFalsch`** when a side is not a valid date for the format (incl. a calendar-invalid date), and **`datumBereichNichtGueltig`** when the start is *after* the end (`start == end` is allowed). `formalError(Kind.DATE_RANGE, …, rangeSep)` reproduces that decision and the value resolves to `Val.Unknown` (suppression). A directly-compared range (`==`/`<` on a `Val.Range`) is a kernel type error; the interpreter's comparators reject it too. **`DateRangesOverlap`** lives on this foundation — a predicate over a scalar range + a starred range list, firing when the scalar overlaps **any** row; ranges are **closed intervals** (overlap ⇔ `end1 ≥ start2 ∧ end2 ≥ start1`, KERNEL-FINDINGS §6, lexicographic on ISO), so touching ranges overlap (`adapter.laws.DateRangeDiffTest`, `DateRangeFormalDiffTest`).

**Calendar validity (a fuzz-blind gap, fixed 2026-06-25):** a parsed date's day must be `≤ daysInMonth(year, month)` (Gregorian leap Februarys) — the kernel rejects `2021-02-31` / non-leap `2023-02-29` / `2024-04-31` as **`datumFormatFalsch`**, but the interpreter's `buildIso`/`buildIsoDateTime` had only checked `d ≤ 31`, so it **accepted** these (and a malformed-but-in-range date even escaped suppression). The differential fuzz never surfaced it because `ValidValues` caps the generated day at 28; the fuzz's malformed-date injection now also emits a Feb-31. Applies to DATE, DATE_TIME, and each date inside a DATE_RANGE. *(Locked: `adapter.laws.DateRangeFormalDiffTest.calendarInvalidPlainDateMatchesKernel`.)*

**Plain-date locale canonicalization — DONE (the fuzz net found it).** The kernel stores a DATE field's value in its **declared format**, not always ISO (`OrderDate` is `yyyy-MM-dd`, but `ApproxDate` is de `dd.MM.yyyy` — its value is literally `15.06.2024`). The interpreter assumed ISO, so it flagged every valid de date `datumFormatFalsch` and couldn't extract its year — a divergence `InterpreterKernelFuzzTest` hit on 75/100 seeds. Fixed at the root with `DateMath.parseDateToIso(raw, format)` (the single-date twin of `parseRangeToIso`, same `dateFragment`/`buildIso`): `Document.resolveValue(DATE)` canonicalizes a non-ISO value to ISO via the field's [ModelDef.dateFormats] (ISO default), and `FormalError.formalError(DATE, …)` is now **format-aware** (valid-for-its-format ⇒ well-formed; wrong-format ⇒ `datumFormatFalsch`). So `dd.MM.yyyy` / `MM/dd/yyyy` / ISO all canonicalize through one path (the format is read, not a locale table). The format flows model → `Document` (the perf harness + the CLI loader pass `model.dateFormats`). Locked: `adapter.laws.PlainDateDiffTest` (ISO and non-ISO fields, both directions + garbage) + the now-green fuzz. The rest of the family is built on this foundation: `AtLeastOneDateRangeOverlaps` (the `X IN list` syntax), the `DateRange` constructor, and `DateTime` canonicalization (`Document.resolveValue(DATE_TIME)` via `parseDateTimeToIso`).

### IF13 — A model-driven seed generator (kernel-free, in `:interpreter`) feeds the perf harness, the differential fuzz net, and a future `dmtool seed` verb

The instances for the against-kernel work are no longer hand-written per scenario — a **`SeedGenerator`** (package `…interpreter.gen`) builds a **valid-by-construction** instance from a `ModelDef`: it walks the model's group tree (derived from field paths + the declared repeatable groups), instantiates rows per repeatable group (a `rowsOf` hook, so counts vary per parent / per run), and emits a value per field via a `ValueStrategy` (the default `ValidValues` respects NUMBER scale/sign and date/time/range formats; `null` leaves a field empty). The seam is **`gen.PlacementSink`** — the interpreter `Document` satisfies it via `asSink()`, the kernel `Doc` via a `:adapter` adapter, and (later) a JSON serializer. It is placed in `:interpreter` deliberately (kernel-free, multiplatform, passes `verifyInterpreterPurity`) so **three consumers share one generator**: the perf harness, the fuzz net, and a future **`dmtool seed`** verb on the native image (the verb just wires loader → generate → serialize). `populate` is deterministic for a fixed `seed` (one `Random(seed)`, fixed walk order) — which is how the fuzz net materializes one generated instance into BOTH engines identically.

**Why it matters (the payoff was immediate):** the **differential fuzz net** (`adapter.perf.InterpreterKernelFuzzTest`) sweeps random documents and asserts interp == kernel — the strongest gate for the #1 match-exactly rule, covering random *combinations* (varying nested-row counts, fill/empty patterns, aggregates over varying lists, a cross-level ref, and — when malformed-value injection is on — formal-error/suppression paths) no hand-picked `*DiffTest` reaches. Its three finds so far: (1) two missing NUMBER **sign formal errors** — signed-zero (`zahlNullEnthaeltVorzeichen`) + leading-plus (`zahlMitPlus`), with the kernel's check-*ordering*, fixed as a class in `FormalError.kt`, locked by `NumberSignFormalDiffTest`; (2) the **plain-date locale** divergence (IF12, `PlainDateDiffTest`); (3) the **malformed-operand combiner** crash/divergence (IF14, `AggMalformedDiffTest`). `ValidValues` was also corrected to never emit a signed zero — a generator that claims "valid by construction" must not produce a value the kernel rejects.

### IF14 — Number parsing is TOTAL (malformed → Unknown), and a numeric combiner with an Unknown element is non-evaluable

Two coupled fixes, both surfaced by the fuzz net's malformed-value injection. **(a) Total parsing:** `typedValue(NUMBER)` was `Val.Num(dec(raw))`, and `dec("abc")`/`dec(" 5 ")` *throws*. The direct-operand path guards malformed fields up front (the `invalid` predicate → `Val.Unknown` → rule suppressed), but a malformed value reached through a **starred aggregate** (`Sum(x*)`) or a **computation** is resolved without that guard, so the parse itself crashed. Now `decOrNull` (expect/actual, JVM `try BigDecimal` / JS `try Big`) makes parsing total: a malformed number → `Val.Unknown`, never an exception. **(b) Combiner propagation:** `Sum`/`Min`/`Max`/`MaxValue`/`MinValue`/`NumberOfDifferentValues` now route through one `combine(vals)` helper that yields `Val.Unknown` if **any** element is `Unknown` — so the whole combiner is non-evaluable and the rule is **suppressed**, matching the kernel exactly (probed: a `Sum` with one `"abc"` fires only the formal error, not the rule; KERNEL-FINDINGS "numeric combiner" generalization). Empties never reach a starred aggregate (the star drops absent/empty cells), so only a FILLED-but-malformed value suppresses. *(Locked: `adapter.laws.AggMalformedDiffTest` — every combiner, malformed + all-valid.)*

**(c) Refinement — "malformed" = FORMALLY invalid, decided by the formal check, not parseability (a later fuzz seed).** `decOrNull` only rejects *unparseable* values; but `-0` *parses* (`BigDecimal("-0") = 0`) and `+5` parses (`= 5`), yet both are formal errors the kernel treats as unknown. So `combine`'s `any { Unknown }` over those would have folded `-0` as `0` and fired where the kernel suppresses. The root fix moved the decision into **`Document.resolveValue`**, which now gates on `formalError(kind, raw, scale, dateFormat)` — a formally-invalid value resolves to `Val.Unknown` for EVERY consumer (direct ref, aggregate element, computation operand), uniformly. `Document` gained `scales` (the formal check needs it; alongside `dateFormats`/`rangeConfig`) and the format flows model → `Document` (perf harness + CLI loader pass `model.scales`). This subsumes (a)+(b) at the value-resolution boundary.

### IF15 — Index-field uniqueness (`uniqueIndex`), per-parent scoped

The kernel auto-checks a repeatable group's `indexFieldName` for uniqueness; the interpreter now models it (`DmInterpreter.uniquenessErrors`, alongside `formalErrors`/`mandatoryErrors`). For each `indexFields` member, group the instantiated rows by **parent scope** (the index reps minus its own + the group-row index — `dropLast(2)`), find index values appearing in >1 row of a scope, and emit `uniqueIndex` on **every** such row (the kernel flags every participant, not all-but-first). Empty/absent index values are excluded — those are requiredness (`mandatoryField`). Per-parent scoping means the same `PartId` under two different Lines does not clash. A VALUE error on an autogenerated rule path (`<parent>/vk_vk<field>_unique`). This **narrows the perf "not apples-to-apples" caveat** — uniqueness was one of the dimensions the kernel validated that the interpreter didn't. *(Locked: `adapter.laws.UniquenessDiffTest` — all-unique, two/three duplicates, absent-vs-duplicate, nested within-line + across-lines; plus the fuzz net with a small index-key pool so collisions arise.)*

**Suppression effect (2026-06-24, fuzz-found): a duplicate index also makes the field "unknown" for rules referencing it.** The fuzz's `Length(ItemId)` rule on a duplicate-`ItemId` row diverged — the interpreter fired it, the kernel suppressed it. ### IF16 — Arithmetic division `/` and power `^`: `MathContext(50)`, quiet edge cases

`evalArith` now handles `/` and `^` (parser precedence `^` > `*`/`/` > `+`/`-`; `^` not nestable without braces, matching the kernel's `MVK_TOO_MANY_POW_FOR_CALC`). The exact-match subtleties (operators.json `Arithmetic`; KERNEL-SEMANTICS "evaluate quietly"): **division by zero is quiet** — the expression is non-evaluable → `Val.Unknown` → a referencing rule simply does not fire (never an error); a **power's** exponent is whole, and `0` to a negative power or an exponent outside `[-1000, 1000]` is likewise quiet → `Unknown`. `evalArith` already returned `Val` and propagated `Unknown` from a malformed operand, so `[bad] / 2` doesn't crash — it's `Unknown`. *(Locked: `adapter.laws.DivPowDiffTest` — div fire/no-fire, div-by-zero quiet, high-precision boundary, power, zero/negative exponent, `^`-binds-tighter-than-`*`; plus the fuzz net's `DV`/`PW` rules.)*

The JVM is kernel-exact (the differential); JS matches to `Big.DP`. (Joins the JS-regex-dialect edge — relevant only to the standalone JS runtime, not the kernel-checked JVM path.)

### IF17 — The truth model is Kleene 3-valued logic, and it is the engine's *single* suppression mechanism (extracted to `Kleene`, 2026-06-24)

The most quietly important design fact about the engine: **its boolean core is [Kleene's strong three-valued logic (K₃)](https://en.wikipedia.org/wiki/Three-valued_logic#Kleene_and_Priest_logics), and almost everything the kernel calls "suppression" is just that one logic doing its job.** Worth a full section because it unifies four features that *look* independent — formal-error suppression, empty-row gating, partial validation, and directional polarity all reduce to "send an operand to UNKNOWN, then evaluate the same tiny truth table." The pure functions live in `eval/ThreeValued.kt` (`Kleene.and`/`or`/`not`) + `quantifierFires` (in `Operators.kt`), extracted from `Interpreter` so they are strategy-agnostic (a future generator emits calls to them; IF10).

**The three values.** A condition evaluates to `Tri.TRUE` (the rule **fires** — an error), `Tri.FALSE` (no error), or **`Tri.UNKNOWN`** — "not enough information to decide." A rule **fires only on `TRUE`**; `UNKNOWN` reads as "cannot convict," so an `UNKNOWN` rule produces no message (and, in `rule eval`, a *suppressed* verdict). The kernel's name for this third state is the *nicht prüfungsrelevant* / formally-incorrect operand; we model it as one value and let the algebra carry it.

**The defining law (why K₃ is exactly right here).** A combination is definite (`TRUE`/`FALSE`) **iff it would be that value for every way the `UNKNOWN`s could resolve to T/F**; if the unknowns could swing the outcome, the result is `UNKNOWN`. So `UNKNOWN` means precisely *"the answer depends on a value we don't have."* That is the correct reading of a malformed/absent/irrelevant field: we genuinely don't know what it would be.

**The truth tables** (∧ = `and`, ∨ = `or`, ¬ = `not`):

```
  A ∧ B │ T   U   F          A ∨ B │ T   U   F            ¬A
  ──────┼───────────         ──────┼───────────         ──────
    T   │ T   U   F            T   │ T   T   T           ¬T = F
    U   │ U   U   F            U   │ T   U   U           ¬U = U
    F   │ F   F   F            F   │ T   U   F           ¬F = T
```

The two corners that carry all the weight:

| combination | result | why |
|---|---|---|
| `T ∧ U` | **U** (suppressed) | the unknown could be `F`, which would make the AND false — we can't be sure it fires |
| `F ∧ U` | **F** | `F` is absorbing for ∧ — *no* value of the unknown could rescue it |
| `T ∨ U` | **T** (fires) | `T` is absorbing for ∨ — *no* value of the unknown could prevent it |
| `F ∨ U` | **U** | the unknown could be `T`, which would fire it — we can't be sure it doesn't |

Each connective has an **absorbing** value (`F` for ∧, `T` for ∨) that wins even against `UNKNOWN`; otherwise `UNKNOWN` propagates. This is monotonicity: known information that already settles the outcome is never un-settled by an unknown.

**One table, three sources of UNKNOWN.** We never write code that says "suppress this rule." Instead, every suppression path funnels an *operand* to `UNKNOWN` and this table does the rest:

| source of `UNKNOWN` | where | finding |
|---|---|---|
| **Formal error** — a referenced field is malformed, required-but-empty, or a duplicate index → un-evaluable | `Interpreter`'s `invalid` predicate → `Val.Unknown` | KERNEL-FINDINGS §1 (branch-scoped), IF11 |
| **Empty-row gating** — a comparison's empty-as-0 must not fire a fresh blank row | the structural `canFireEmpty` gate | KERNEL-FINDINGS §1 |
| **Partial validation** — a field outside the *relevant* set is treated as unknown | `DmInterpreter.validatePart` → `Val.Unknown` | KERNEL-FINDINGS "Partial validation" |

**The punchline (partial validation).** The kernel documents partial validation as: *"an error is suppressed if the rule references a non-relevant field — **except where the kernel is sure no possible value of that field could have prevented the error**."* That exception sounds like a hairy special case. It is **not a special case at all** — it is literally `T ∨ U = T` versus `T ∧ U = U`. Resolve non-relevant fields to `UNKNOWN`, run this table, and the "except where sure" behaviour falls out for free. The same identity explains branch-scoped formal-error suppression: `healthyTrue ∨ [broken] > 0` still **fires** (the broken operand is `UNKNOWN`, but `T ∨ U = T`), while `healthyTrue ∧ [broken] > 0` is **suppressed** (`T ∧ U = U`). KERNEL-SEMANTICS §1's prose ("removes the rules over it from evaluation") reads stricter than the engine behaves; the truth is this algebra. *(This is why the partial-validation increment needed almost no new code — the 3VL engine already produced the kernel's exact suppression, including the hard clause; KERNEL-FINDINGS "Partial validation".)*

**Quantifiers share the spirit.** `quantifierFires(op, t, f, n)` decides a list quantifier from a tally of `t` TRUE + `f` FALSE among `n` operands (the rest `UNKNOWN`) — the same "definite only when the unknowns can't change it" idea at the list level (`AllFieldsFilled` is `t == n`, `NoFieldFilled` is `f == n`, etc.), which is why a malformed operand in a quantifier list also yields `UNKNOWN` rather than a wrong count.

**Correspondence + provenance.** This mirrors the kernel's `ValidierungsErgebnis.combineUND`/`combineODER`; we reimplement the *behaviour* clean-room (IF0), not the source. Locked broadly by the full-message fuzz (`FullMessageFuzzDiffTest`) and specifically by `adapter.laws.KleeneDiffTest` (every AND/OR truth-table cell — kernel-fires == `Kleene` prediction == interp-fires), `FormalErrorScopeLawsTest` (branch-scoped) + `PartialValidationDiffTest` (the `∨`-fires / `∧`-suppresses cases) + the quantifier diff tests.

**Verified 100% kernel-compatible (source-read 2026-06-24).** The kernel's `ValidierungsErgebnis` (kernel-core-runtime) is **three states** that DIFFER from a textbook K₃ in two ways — yet are observably equivalent to our split model:
- It **collapses FALSE and UNKNOWN into one state** (`FALSE_OR_UNKNOWN`), and folds **polarity** into the two TRUE states (`TRUE_WF` = VALUE, `TRUE_AF` = OMISSION). We instead keep `Tri` (TRUE/FALSE/**UNKNOWN** distinct) and carry polarity separately as `MsgType`. The collapse is harmless because **a rule fires only on TRUE** — both our FALSE and our UNKNOWN map to the kernel's single non-firing state, and our `Kleene.and`/`or` never turn a non-TRUE into TRUE (∧ only needs both TRUE; ∨ needs one TRUE), so firing is identical cell-for-cell (proved by `KleeneDiffTest`).
- The **one** place FALSE≠UNKNOWN in Kleene is `not` (`¬F=T` but `¬U=U`) — and that distinction is **never exposed**: the kernel has **no `negate` method on `ValidierungsErgebnis`** (only `combineUND`/`combineODER`), the DSL has **no general boolean `Not`** (the interpreter parser never emits `Cond.Not` — negation is always a complementary *leaf* operator: `FieldNotFilled`, `NotEqual`, `FieldValueNotIncludedInValueList`, computed directly), so `Kleene.not` is only ever applied to a leaf result, never to a combined sub-expression that could be UNKNOWN. Hence the kernel can safely collapse FALSE+UNKNOWN, and our finer split agrees everywhere observable.
- The **polarity** combination matches the kernel's tables exactly: `combineUND` → omission (`AF`) wins among TRUE operands (our `evalTyped` And: `OMISSION` if either branch is OMISSION); `combineODER` → value (`WF`) wins (our `orType`: VALUE if any TRUE branch is VALUE). The full `code|type|pointer` agreement is what `FullMessageFuzzDiffTest` + `ModelFuzzDiffTest` already prove across thousands of generated And/Or combinations.

### IF18 — The semantic index supports BOTH a literal and a field key: `[F For "lit"]` and `[F For keyField]` (2026-06-24)

The semantic index `[targetField For <key>]` resolves the value of `targetField` in the repetition whose INDEX field equals `<key>`. The kernel (BA doc: *"the value of the semantic index can be specified as either a constant or a Field"*) allows the key to be **either a string literal or another field** whose current value is the key. The interpreter now supports both: the parser, after `For`, takes a string literal (`indexValue`) **or** a field path (`indexFieldPath`); `Interpreter.resolveIndexKey` returns the literal, or the key field's current value (empty/absent key field → no match → the kind's empty value, exactly like a non-matching literal). The key field is a **per-row reference** (`exprRefs` includes `indexFieldPath`), so it drives iteration scope and appears in the rule's referenced fields; the *target* `F` stays an absolute semantic lookup (not a per-row ref). Lookups remain O(1) via the row-prefix index (INTERPRETER-PERFORMANCE #4). Locked by `adapter.laws.SemanticIndexFieldKeyedDiffTest` (matched / other-key / no-match→omission, firing + polarity, vs the kernel) alongside the literal-form `SemanticIndexDiffTest`. *(Single repetition layer only — KERNEL-SEMANTICS §9.10 lists the unsupported combinations; matches the kernel.)*

### IF19 — Parallel iteration: the index-keyed outer join (every kernel-valid shape, exact + O(rows)) (2026-06-25)

A rule referencing two NON-nested repeatable groups (siblings) per-row is a **parallel iteration**: the kernel joins them by a shared **index field**, iterating the **union of index values** as an outer join (KERNEL-FINDINGS §9). The interpreter implements this directly. `DmInterpreter.iterationContexts` detects the parallel groups (a repeatable ancestor of a ref that is not the scope's chain), and `Document.parallelContexts` builds one `ParallelRowContext` per (common-parent row × index value): each value resolves each group to its row carrying that value, or **"not specified"** (empty fields, and the pointer level set to `UNKNOWN_REP = -5` — the kernel's `IIdentifier.UNKNOWN`, so `…/Demand[-5]/Headcount` renders bit-for-bit). Polarity, empty-as-0, and the `-5` pointer all fall out of the existing operator/`formatPointer` logic — the join only changes *how operands resolve*, mirroring the §10 *strategy vs runtime-semantics* layering (IF10).

**Scope — every kernel-VALID shape is modeled exactly** (verified by probing which shapes the kernel even accepts):
- **Group topology:** sibling groups (direct children of the common ancestor); **wrapped / asymmetric-depth** groups (non-repeatable intermediates are transparent — the kernel renders them `[1]`, only the repeatable level goes `-5`); and a **frame** — a repeatable, non-indexed group above ONE joined group (`/Plan/X/A ⋈ B`): the frame iterates normally and the join runs inside each frame row, the other joined group shared across frame rows (`Document.parallelContexts`'s `frameGroup`/per-group `parentReps`). Locked by `ParallelIterationDiffTest`, `WrappedParallelIterationDiffTest`, `FramedParallelIterationDiffTest`, `SiblingGroupFuzzDiffTest`.
- **The invalid-index 3VL corner:** matched rows, the synthetic `-5` side, polarity, empty-as-0, AND a *duplicate/empty* index value — a group whose index is invalid here reads its **unmatched** references as 3VL **UNKNOWN** (routed through `EvalContext.presenceUnknown` → the Kleene logic in `filledTri`/`quantTally`), suppressing a negative operator like `FieldsNotCollectivelyFilled` on the compromised side exactly as the kernel does; `uniqueIndex`/`mandatoryField` still fire from the auto checks. Fuzzed with injected dup/empty indices (`SiblingGroupFuzzDiffTest`, `FramedParallelIterationDiffTest`).
- **Loud-declined shapes are all KERNEL-INVALID models** (they fail `generateCode`, so a real model never reaches the decline) — *probed*: a repeatable frame above the non-error joined group is `MVK_NO_WILDCARD` (demands an aggregate `*`); an indexed repeatable intermediate is `MVK_MULTIPLE_INDEX_FIELDS`; a negative operator over a frame is `MVK_NEG_CONDITION_IN_ITERATION`; a joined group without an index field is rejected (parallel iteration requires one). `parallelIterationContexts` declines these loudly anyway (never silently wrong if a hand-built `ModelDef` reaches it).
- **Performance:** O(rows) — a value→row map per group built once per (frame row), O(1) row lookups via the row-prefix index (INTERPRETER-PERFORMANCE #4), so the join matches the kernel's `IndexFieldCache` complexity class (linear, not nested-loop O(rows²)). Gated by `PerfGateTest.parallelIterationStaysSubQuadratic` (4× rows → ~4×, not ~16×) + `parallelIterationScalesLikeKernel`.

### IF20 — Declared field-type constraints: the per-cell auto-validation family (emission + suppression)

The interpreter's automatic, **rule-free** validation (what `validateFull` emits with no author rule) spans **format well-formedness** (`FormalError.kt` — date/number/time/range formats, blanks, signed-zero/plus; KERNEL-FINDINGS §3), **requiredness** (`mandatoryField`, IF11), **index-field uniqueness** (`uniqueIndex`, IF15), AND the kernel's **declared field-type constraint** family — the per-cell checks `validateFull` auto-emits as formal errors (KERNEL-FINDINGS §3 "declared field-type constraints"). Each is a VALUE error on the `formalePruefung` path that both **emits** a message and makes the cell **"unknown"** so a referencing rule is **suppressed** — the two share one `formalError(...)` decision, used by `formalErrors` (emission) and `computeFormalErrorAt` (suppression). The point of modeling them: a constraint-violating value is "unknown" to the kernel (referencing rules suppressed), so without these the interpreter would read it as a *valid* value and produce **extra firings** the kernel suppresses. The differential corpus is constraint-**valid** by construction (the seed generator picks in-domain values), so this class only surfaces on an out-of-constraint value — locked by `adapter.laws.FieldConstraintFormalDiffTest`. Precedence is the kernel's (probe-verified):

| constraint | kernel code | precedence (probe-verified) |
|---|---|---|
| string `minLength` / `maxLength` | `stringZuKurz` / `stringZuLang` | after pattern |
| string `pattern` / **enum value-domain** | `stringFalschesMuster` | **before length** |
| string **newline** (default-forbidden; `lineBreaksPermitted` toggles off) | `stringMitNewline` | format layer, **before length** |
| number `minValue` / `maxValue` | `zahlZuKlein` / `zahlZuGross` | after format |
| number `minFractionalDigits` (too few / none) | `zahlFalscheAnzahlNachkommastellen` / `zahlOhneDezimalTrenner` | format layer |
| number **leading-zeros** (default-forbidden; `leadingZerosAllowed` toggles off) | `zahlHatFuehrendeNullen` | format layer, after sign |
| number `zeroNotAllowed` (declared; the inverted DM-JSON key) | `zahlIstNull` | constraint layer |

**Two of these are kernel DEFAULTS, not declared constraints:** newlines and leading zeros are forbidden on **every** string/number field unless it opts in (`lineBreaksPermitted` / `leadingZerosAllowed`) — wider than the declared-constraint cases. They live in the format layer (`numberFormalError` / `stringConstraintError`), and `FieldConstraints.NONE`'s `false` flags reproduce the default-forbidden behavior for a plain field, so no per-field declaration is needed to get them.

Mechanism: `FieldDef`/`FieldConstraints` gained `minLength`/`maxLength`/`pattern`/`minValue`/`maxValue`/`minFractionalDigits` + the three booleans `lineBreaksPermitted`/`leadingZerosAllowed`/`zeroNotAllowed` (default false = the kernel default); `InterpreterModelLoader` extracts them; `ModelDef.constraintsOf` feeds a `FieldConstraints` to the single `formalError(...)` used by **both** the emission pass (`formalErrors`) and the suppression path (`computeFormalErrorAt`). **Performance — MEASURED:** all are per-cell, O(1)–O(value-length), folded into the existing single-pass formal loop (no new loop, no cross-row); gated by `PerfGateTest.constrainedFieldsStaySubQuadratic` (linear in rows). The two new defaults run on every string/number cell but are cheap scans — the full-suite + perf gate confirm no regression.

**Facts about the model-format edges (knowhow; live status of the residuals is in INTERPRETER-GAPS).** A few kernel constraint codes have **no DM-JSON serialization**, so they cannot appear in a loadable model and there is nothing to validate against: `maxNumberOfDigitsBeforeDecimalPlace` (`zahlZuVieleVorkommastellen`) and a string **charset** (`zeichenNichtImZeichensatz`, which also doesn't fire by default — tab / non-ASCII / control chars on a plain string are all clean, probed). The field-level **`uniqueValue`** flag is likewise not deserializable (`Field.unique`/`StringType.unique` don't load; `IField` has no `unique` accessor — it rides the USB/declared-unique machinery, kin to the handled `uniqueIndex`/IF15). A **`mandatoryGroup`** cannot fire on any loadable model — its `FEHLER_PFLICHTKONTEXT` code is **unemitted** in kernel 30.8.1 and **no DM-JSON property declares a group mandatory** (source-verified; KERNEL-FINDINGS "mandatoryGroup is a DEAD code in 30.8.1"). The one remaining residual — `uniqueValue` — is tracked in [INTERPRETER-GAPS.md](INTERPRETER-GAPS.md) (IG2); `mandatoryGroup` is §3-confirmed-unreachable, and the structural **over-repetition** bound (`zuGrosseZeile`/`zuGrosseKontextnummer`) is now **modeled** (IF27). `uniqueValue` is no O(N²) risk (it is unauthorable). (`zeroNotAllowed` IS authorable — an earlier note used the wrong key `zeroAllowed` — and is modeled above.)

`dmtool model eval` (the default interpreter) matches `--kernel` on a constraint-violating document for this whole per-cell family: the modelkit/CLI-authored `minLength`/`maxLength`/`pattern`/`minValue`/`maxValue` constraints are validated at runtime, not silently ignored.

### IF21 — TIERED computations: preconditions / multiple alternatives / commonPrecondition (audit 2026-06-25; FIXED 2026-06-26)

**A genuine missing feature, not a defensible boundary (unlike IF20) — now fixed.** A kernel computation is a list of `computationAlternatives` (each an optional `precondition` + an `operation`) under an optional `commonPrecondition`; the runtime selects the **first alternative whose precondition holds**, else clears the field (KERNEL-FINDINGS §2 "tiered computations"). The interpreter models a computation as a **single unconditional operation**: `ComputationDef` is `(targetPath, group, expressionText)` — no precondition, no alternative list, no `commonPrecondition` — and `DmInterpreter.compute` evaluates that one expression. The lossy join is `InterpreterModelLoader`, which reads **`computationAlternatives[0].operation`** and discards the precondition, the other alternatives, and `commonPrecondition`.

**Consequence — silent wrong value (violates the "fail loud, never silently wrong" #1 rule).** Probe-verified: a `UnitPrice` computation tiered `9.99` (when `[Quantity] < 100`) / `0` (else) computes — in the kernel — `9.99` at Quantity=50 and `0` at Quantity=150; the interpreter computes **`9.99` always** (it takes `alternatives[0].operation`, ignoring the precondition). Three sub-divergences from the one root: a **discriminating precondition** picks the wrong tier; a **false-on-every-alternative** computation should clear but doesn't; a **false `commonPrecondition`** should clear but doesn't. (The §66 redundant-`commonPrecondition AllFieldsFilled` equivalence masks *only* the degenerate fill-guard case — a real tiered computation is not masked.)

**Cross-stack — the worst kind: dmtool authors it, dmtool mis-runs it.** rulekit's `DraftComputation` carries `commonPrecondition()` + `alternatives()` (each `Alternative(precondition, operation)`), `RuleValidator.computationNode` emits the full `computationAlternatives` array (kernel-validated, `ComputationAuthoringTest`/`ComputationVerbTest`), and the CLI `computation add` accepts `{commonPrecondition?, alternatives:[{precondition?, operation}]}` — and a committed fixture (`cli/src/test/resources/models/order-tiered.dm.json`) uses it. So `dmtool computation add` writes a tiered computation that `dmtool model compute` (interpreter = default) then evaluates **wrong**, diverging from `--kernel`. No "form UI" excuse — this is a core authoring feature the default runtime silently mis-evaluates.

**Why uncaught:** the differential `RuntimeLaws.withComputation` builds only a **single unconditional** alternative, and `order-tiered.dm.json` has **no test that computes it** — no differential ever exercised a precondition.

**FIXED (2026-06-26).** `ComputationDef` now carries `alternatives: List<ComputationAlternative(precondition, operation)>` + `commonPrecondition: String?` (with an `expressionText` secondary constructor as single-unconditional sugar — back-compat for every hand-built model); `InterpreterModelLoader` loads all alternatives + the common precondition; `DmInterpreter.compute` parses each precondition to a `Cond` and selects the first alternative whose precondition is `Kleene`-TRUE (null = unconditional), clearing the field when the common precondition fails or no alternative holds. Dependency-ordering + iteration-scope ref-gathering now span every alternative's operation + precondition + the common precondition. Locked by `adapter.laws.ComputationPreconditionDiffTest` (tiered low/high select, no-match→cleared, common-precondition true/false — all interp == kernel), via the new `RuntimeLaws.withTieredComputation`.

**Kernel law surfaced while fixing — `MVK_ERROR_EMPTY_PRECONDITION`.** A trailing **unconditional** alternative mixed with guarded ones is a *kernel-invalid* model ("Empty prerequisite is not allowed here") — an empty/absent precondition is valid only as the **sole** alternative (the ordinary non-tiered computation). So the interpreter never has to match a "default after guards" shape (it can't be authored); a null precondition is still treated as always-true for the sole-alternative case. Recorded in KERNEL-FINDINGS §2.

**Performance — MEASURED, not asserted (the standing perf discipline).** A precondition is a `Cond` evaluated once per computed-field instance, O(condition size) per row, folded into the existing `computationsInDependencyOrder` graph — **no new N² term, confirmed**: `PerfGateTest.tieredComputationStaysSubQuadratic` measured **1.53× growth for 4× rows** (linear≈4, a per-row-rescan quadratic≈16), and `tieredComputeScalesLikeKernel` measured **interp 0.90ms vs kernel-Groovy 150.88ms at 3000 rows** with interp == kernel correctness asserted. The benchmark uses scale-exempt literal operations (Amount is scale-2, Qty scale-0 — a field operand would trip the kernel's `MVK_INVALID_COMPARE_DEC_PLACES` scale gate; the per-row *precondition* selection is what it stresses).

### IF24 — condition parser rejected ABSOLUTE paths as predicate/aggregate args (FIXED 2026-06-26)

The interpreter's condition parser (`parse/Parser.kt`) accepted an absolute path inside a `[...]` value reference (so cross-level walk-ups like `[/Pol/Claim/CL0]` parsed) but had **no atom case for a bare absolute path as a predicate / aggregate argument** — `FieldFilled(/Pol/Cap0)`, `AllFieldsFilled(/A/x, /B/y)`, a starred `Sum` over an absolute path — so it threw `parser: unexpected '/'`. That is the **canonical form the kernel accepts and the rulekit DSL renderer emits** (`DslRenderer` writes absolute paths — see `MirroringRuleStudyTest`'s expected output and `ReadRoundTripTest`'s `FieldFilled(/Order/CustomerName)`). The free-text benchmark/diff tests never hit it because they hand-wrote *relative* names; it surfaced the moment the perf benchmark moved to **DSL-authored** (absolute) conditions. **Root cause + fix:** `parseAtom` dispatched `{`, `[`, `"`, digit/`-`, and a bare identifier (→ relative `pathFrom`), but not a leading `/`; added `'/' -> { next(); pathFrom(readIdent(), absolute = true) }`, mirroring the existing `[...]` absolute handling. Pure parser addition — no eval change, no perf impact — and it makes the interpreter consume the kernel/DSL canonical path form, a prerequisite for the **dmkit migration** of the tests. Locked by `interpreter.AbsolutePathParseTest` (absolute ≡ relative AST for predicate args, field-list predicates, and single/nested starred aggregates; JVM+JS). The AST's `NumLit` carries a `Dec` (the `expect`/`actual` BigDecimal wrapper) that compares by **identity** (no value `equals`/`hashCode`), so whole-AST equality is unreliable wherever a number literal appears — a cross-platform + BigDecimal scale-sensitivity decision tracked as `IG4` in [INTERPRETER-GAPS.md](INTERPRETER-GAPS.md).

### IF25 — condition parser resolves `../` PARENT-RELATIVE cross-level paths (FIXED 2026-06-26, graduated from IG1)

The twin of IF24, on the *relative* axis. The kernel's canonical condition render — its `FormatterVisitor`, which the rulekit `DslRenderer` reproduces (fork #9) — writes a rule's field paths **relative to the rule's group**, so a cross-level UP reference (a `/Perf/Lines/Subs`-scoped rule reading the parent Line's `Qty`) renders **`../Qty`** — each `..` is one group level up, exactly as `relativize()` emits one `../` per base segment beyond the common prefix. The parser's `parseAtom` handled the leading-`/` absolute form (IF24) and the bare same-group relative ident, but had **no `..` case** in either the `[...]` value-ref branch or the bare predicate/aggregate-arg branch: `readIdent()` on `../Qty` reads nothing and `expect(']')` threw `parser: expected ']' … [../Qty]`. **Why it hid:** every pre-migration fixture hand-wrote cross-level refs *absolute* (`[/Perf/Lines/Qty]`, parseable via IF24); nothing fed the parser the kernel's *relative* form until the dmkit migration authored rules as typed `Rule`s and rendered them with `Rule.render()` (group-relative) — `PerfGateTest`, `InterpreterKernelFuzzTest`, and `deepNestedHavingStaysSubQuadratic` all choked at once.

**Root cause + fix:** path resolution had only two modes (absolute `/joined`, or `base/joined`); a `../` ref needs a *walked-up* base. Added `readParentUps()` (consume the `../` runs, count the levels — it MUST run before `readIdent`, the prefix precedes the first segment) + `walkUp(base, ups)` (drop that many trailing segments, refusing to walk above root), threaded as a `ups` param through `pathFrom`, and a unifying `readRef()` that dispatches absolute / parent-relative / plain at every reference site (`[…]` value ref, the `For` index field, the bare arg via a new `.` atom case alongside `/`). **A `../` ref resolves to the same absolute path string the absolute render produces, so the AST is byte-identical** — locked directly by `interpreter.ParentRelativePathParseTest` (`../` ≡ the equivalent absolute AST, in value refs + bare predicates, multi-level, into-sibling-subtree, and starred aggregates; JVM+JS), and *differentially* by switching `adapter.laws.TypedRules` back to the canonical group-relative `Rule.render()` — so the **entire catalog + fuzz gate now drives `../` resolution against the real kernel** (the strongest lock; it replaced IF24's absolute-render workaround).

**No eval change, no perf impact** (the same class as IF24): the `..` is resolved to an absolute path **at parse time** — once, when condition text becomes the AST — so `Expr.Field` carries the fully-resolved absolute path and evaluation walks it identically regardless of render style. The post-fix gate confirmed it empirically: the cross-level scenarios (B3/B4/B5, the `complexRealWorld` walk-up, the once-choking deep-nested `Having`) stayed in their normal single-digit-ms / near-linear-growth range. The `..` mechanism here is distinct from `DmInterpreter.resolveGroupRef` (the `@From`/`Von` reference-group selector for `RepetitionNotUnique`, which already resolved raw `..` segments at setup) — that the kernel emits `..` *there* in real stored models corroborates that `../` field paths occur in real models too, so this was a genuine load-a-real-model gap, not only a test artifact.

### IF26 — CUSTOM-typed fields are auto-validated via the predefined-type registry (the implicit per-cell `Valid`); unregistered → unsupported + lenient (FIXED 2026-06-26, graduated from IG7)

A field declared with a **`CustomFieldType{name}`** is the *implicit, per-cell* form of the `Valid(field, name)` operator: every filled cell is auto-validated against the registered type of that name. The kernel runs this by **full delegation** to a registered validator (KERNEL-FINDINGS §8 supplement "custom-typed field … full delegation"); the interpreter mirrors it on the SAME machinery the `Valid`/`Invalid` operator already uses — the consumer-supplied **`PredefinedTypeRegistry`** (`PredefinedType.accepts(value)`). So a Kotlin/JVM **and** Kotlin/JS library consumer that registers a type reaches **100%** parity; the kernel-free native CLI cannot host the validator, so there it degrades (below).

**Three behaviours** (all in `commonMain` → JVM + JS):
- **registered + rejected** → a `customFieldTypeInvalid` formal error on the cell, and the cell resolves to `Val.Unknown` so a value-reading rule referencing it is **suppressed**, branch-scoped exactly like any formal error (the single `computeFormalErrorAt` oracle gained a custom-type branch, so the message *and* the suppression share one decision).
- **registered + accepted** → clean; a referencing rule evaluates normally.
- **unregistered** → the cell is reported `ValidationOutcome.unsupported` ("custom field type 'N' has no registered validator") and validation **continues leniently** — the value is used as a plain string. This is a **deliberate, documented divergence**: the kernel *throws* `FaultException("Unable to invoke validation")` here, but a hard crash is the wrong runtime behaviour for the native tool, so the interpreter degrades gracefully so a model that uses custom types can still be **test-run** (the CLI's intended `--lenient`/skip surface — FEATURE-GAPS).

**Loader + the bounds question.** `InterpreterModelLoader` captures the `CustomFieldType.name` onto `FieldDef.customTypeName` (kind stays `Kind.STRING` — the value is string-shaped); it does **not** load the field's declared `minLength`/`maxLength` into a `StringType`-style length check, and that is **correct, not a regression** — the kernel does not generically enforce a custom type's bounds either (they are hints to the validator). The *registered* type's own `accepts` is the single source of truth on both engines; the field's declared bounds are metadata. (This retires the original IG7 worry — "the loader drops min/maxLength" — which would have been a *divergence* had we "fixed" it by enforcing the bounds directly.)

**Message-code caveat.** The kernel emits the validator's **project-specific** error key; the interpreter emits its own `customFieldTypeInvalid` (Option-A, like IF3 — there is no fixed kernel code to match). So the differential compares the **observable**: a rejected cell suppresses the referencing rule, an accepted cell lets it evaluate — bit-for-bit with the kernel. *Locked:* `interpreter.CustomFieldTypeMultiplatformTest` (the three behaviours, JVM+JS) + `adapter.laws.CustomFieldTypeBoundsDiffTest` (registers the same length validator on both engines; suppression parity vs the real kernel).

### IF27 — Over-repetition structural check: `zuGrosseZeile` (group) / `zuGrosseKontextnummer` (field), with suppression (2026-06-26)

`validateFull` also runs a STRUCTURAL **over-repetition** check (KERNEL-FINDINGS "over-repetition errors", the kernel's `FormalChecker`): an entity instance whose repetition index exceeds the declared `repeatability` is flagged — a repeatable **group row** whose OWN index is over the cap → **`zuGrosseZeile`** (the group entity); a **field** sitting inside an over-limit repeatable *ancestor* (the over-limit level is intermediate) → **`zuGrosseKontextnummer`** (full field pointer). Both VALUE, on the `formalePruefung` path. An over-limit instance is **"unknown"**: its ordinary checks (format, mandatory, uniqueIndex, and any referencing rule) are suppressed.

The interpreter models it. `overLimitLevel(path, reps)` is the single predicate — the outermost repeatable ancestor whose row index exceeds [ModelDef.declaredReps] — and it threads through every pass: `overRepetitionMessages` emits one message per over-limit field (`zuGrosseKontextnummer`) and per over-limit group row (`zuGrosseZeile`); `computeFormalErrorAt` returns the over-repetition code for an over-limit cell (so a referencing rule goes UNKNOWN → suppressed, the single "is this operand unknown?" oracle, alongside format / required / dup-index); `formalErrors` skips an over-limit field (it carries the over-repetition code, not a format error); and `mandatoryErrors` + `duplicateIndexCells` skip over-limit rows. The group pointer falls out for free — [formatPointer] omits the trailing (group) segment's index, so an over-limit `/Order/Lines` row renders `/Order[1]/Lines`. The USB/multi-form `FEHLER_LAUFENDE_NR_ZU_GROSS` sibling is out of the single-document scope.

This is a deliberate **scope expansion**: the interpreter, a rule + computation evaluator, now also performs the kernel's structural document-shape validation, so `validateFull` output matches even on malformed-structure input (more rows than declared) — not just the structurally-valid documents a form UI produces. All in `commonMain` (JVM + JS). *Locked:* `adapter.laws.OverRepetitionDiffTest` — emission (flat + nested), rule suppression (a typed rulekit `Rule` via `TypedRules`), and mandatory + unique-index suppression on over-limit rows, all vs the real kernel.

### IF28 — condition/operation parser tolerates leading `;;` comments + all whitespace (FIXED 2026-06-26, graduated from IG18)

`;;` comments are kernel concrete syntax (KERNEL-FINDINGS "Condition comments"): the `Comment` token is grammatically valid as `before`/`after` of a `teilBedingung`/`operation`, and `WS` is `channel(HIDDEN)`, so the kernel parses past a leading comment (and any newline/tab) and evaluates the body at `validateFull`/`compute`. The interpreter's recursive-descent parser did **not** — `skipWs()` skipped only `' '`, so `readIdent` hit the `;` and threw `IllegalArgumentException`; worse, `validateWith`'s catch is `UnsupportedConstructException`-only, so the exception **escaped and crashed the whole run** (all four entry points — validateFull/validatePart/compute/evalCandidate — share this parser). This was a **crash**, not a wrong result.

The fix is the single shared locus: `skipWs()` now skips all whitespace (space/tab/newline/CR/`\u000C`, mirroring the kernel lexer's `WS`) and `;;` line comments (`;; …` to end of line, the `Comment` token). Because every meaningful parse position calls `skipWs()` first (`parsePrimary`, `parseAtom`), a commented condition/operation now parses straight to its body on every entry point. Deliberately **not** widened the `validateWith` catch — a genuine parse failure should still surface loudly (fail-fast), not be swallowed. *Locked:* `adapter.laws.CommentConditionDiffTest` — a DSL-authored body carrying a `;;` comment (attached via `Comments.before`, the model built through the real `EditSession` write path) fires identically on both engines.

### IF29 — STRING `noValueValidation` skips the whole per-cell format check (FIXED 2026-06-26, graduated from IG17)

`noValueValidation` is a StringType key the kernel honors at runtime (KERNEL-FINDINGS "StringType `noValueValidation`"): `FormatDefinitionString.validiereFormat` returns `Valid` immediately, so pattern / length / the default newline check are all bypassed. The interpreter ignored the key and enforced the constraints anyway — a **false positive** (`stringFalschesMuster`/`stringZuKurz`/`stringZuLang`/`stringMitNewline`) on a value the kernel accepts, reachable on shipped A12 Tools StringType fields (Country/City/Person).

The kernel only allows a *valid* `noValueValidation` field to carry `maxLength` (no pattern/minLength — `MVK_STRING_TYPE_PARAMS_INCONSISTENT`) and requires line breaks permitted (`MVK_STRING_TYPE_NO_VAL_AND_NO_LINE_BREAK`), so the single observable runtime effect is **a declared `maxLength` is NOT enforced**. The fix: `FieldDef`/`FieldConstraints` carry `noValueValidation`, `stringConstraintError` returns `null` immediately when set, and `InterpreterModelLoader` reads the StringType key. *Locked:* `adapter.laws.FieldConstraintFormalDiffTest` — a kernel-valid `noValueValidation` field (maxLength 6, line breaks allowed) leaves a length-7 value clean on both engines. (modelkit's `StringFieldBuilder.noValueValidation()` authors the key — DEV-API-GAPS DG14 — and fails fast on the line-break co-requirement.)

### IF30 — NUMBER integer-digit cap + value-string length formal checks (FIXED 2026-06-26, graduated from IG15)

Three NumberType keys the kernel formal-checks but the interpreter dropped (KERNEL-FINDINGS §3 supplement, kernel-probe-verified): **`maxIntegerDigits`** (integer-part digit count above it → `zahlZuvieleVorkommastellen`); **`trait:"amount"`** (an implicit integer-digit cap of `15 − scale`, but a *distinct* code `stelligkeitZuLang`, and only when no explicit `maxIntegerDigits`); and NumberType **`minLength`/`maxLength`** on the value-string length → `zahlZuKurz`/`zahlZuLang`. ### IF31 — 4-arg century `Date(day, month, century, year)` construction (FIXED 2026-06-26, graduated from IG12)

The kernel's `Date` construction has a 4-arg century form whose year is split into a 2-digit century + 2-digit year — full year = `century*100 + year` (KERNEL-FINDINGS "Date construction — 4-arg century form", kernel-probe-verified: `Date(15,6,20,24)` → year 2024). The interpreter's `analyzeDate` declined any non-3-arg form as `MALFORMED`, so `YearFromDate`/`Valid`/`Invalid` over a 4-arg date went `Unknown`/quiet — a **silent** divergence (the kernel evaluates a real date). ### IF32 — every computation is also a validation rule: the implicit `[F] != <term>` check (FIXED 2026-06-26, graduated from IG14)

### IF33 — a computed DATE is stored in the TARGET field's format, not ISO (FIXED 2026-06-26, graduated from IG19)

### IF34 — an out-of-range computed value is bucketed ERRORED (FIXED 2026-06-26, graduated from IG13)

### IF40 — compute(): a computation that reads an ERRORED dependency is SKIPPED (FIXED 2026-06-26, graduated from IG13)

In the computation **cascade**, when a dependency computes an **errored** value (out of range — IF34), the kernel does NOT compute any dependent that reads it: the dependent appears in **no** bucket of `compute()` — not changed, not cleared, not errored (probe-confirmed: `T := A` errors at `A=5000 > maxValue 999`, and `U := T + 1` is simply absent from the result, transitively `V := U + 1` too). The fix tracks **poisoned** `(target, reps)` instances in `compute()`: an ERRORED result poisons its target and is NOT overlaid (it is still reported as ERRORED); a computation whose computed dependencies include a poisoned instance is **skipped** (no outcome) and transitively poisons its own target. The empty-operand→0 and resolved-VALUE cascade paths are unchanged. *Locked:* `adapter.laws.ComputeCascadeErroredDiffTest` — the in-range control (full T/U/V cascade) and the errored case (kernel + interpreter both emit only the errored `T`, skipping `U`/`V`). ### IF41 — `Dec` is a value type: scale-insensitive equality (FIXED 2026-06-26, graduated from IG4)

The interpreter's cross-platform decimal `Dec` (JVM `BigDecimal`, JS `big.js`) compared by **reference identity** — it declared `compareTo` but no `equals`/`hashCode`. Since `Val.Num(val v: Dec)` and `Expr.NumLit(val v: Dec)` are **data classes**, their auto-generated equality inherited that identity break: `Val.Num(dec("2.0")) != Val.Num(dec("2.0"))`, and a `Set<Val.Num>` never deduped. No *behavioral* path tripped it (every number comparison goes through `compareScaled19`/`compareTo`, never `equals` — which is why it stayed latent and was deferred), but it was a real landmine for any future AST dedup / caching / `Set` use.

The decision (the deferral's open question) is **scale-insensitive value equality**, consistent with how `Dec` is *compared* everywhere (`compareTo`, the kernel's `BigDecimal.compareTo`): `2.0 == 2.00`. Both actuals now implement `equals` via `compareTo(other) == 0` and `hashCode` off the canonical trailing-zero-stripped form (JVM `stripTrailingZeros().toPlainString()`, JS big.js `toString()`), each self-consistent. *Locked:* `interpreter/commonTest/DecEqualityTest` — equal-across-scales, distinct values, hashCode/`Set` dedup, and `Val.Num` equality, on JVM **and** JS.

### IF42 — partial validation: starred-aggregate relevance is PER-OPERATOR (FIXED 2026-06-26, graduated from IG20)

The partial-validation fuzz (`PartialValidationFuzzDiffTest`) surfaced that the blanket IF35 gate ("a starred aggregate with ANY non-relevant cell is UNKNOWN") was an oversimplification — the kernel's rule is per-operator, confirmed by a controlled probe (separate always-relevant error field, 2 rows, no fillable tail):

- **All-rows aggregates** (`Sum`, `MaxValue`, `MinValue`, `NumberOfDifferentValues`, `SumOfProducts`): the kernel evaluates them **only when the relevant set WILDCARDS the starred level** (`ALL_SEMANTIC` at the repeatable group, or a relevant ANCESTOR group whose descent makes all rows relevant). Enumerating concrete rows — **even ALL of them** — leaves the aggregate UNKNOWN: the `*` reference is "fully known" only via a wildcard (the BA's "encourages wildcarding every path level"; runtime: a `*`-read over a non-wildcarded set has unknown extent). The interpreter keyed on per-cell relevance, so concrete-both-rows wrongly evaluated → fired where the kernel suppressed.
- **`FirstFilled`**: **order-aware** — it returns the first FILLED cell's value; it is UNKNOWN only when a NON-relevant cell precedes that first filled cell (its filledness is unknown, so it can't be skipped). So it fires when the first filled row is relevant (wildcard / both-rows / that-row-only) and is UNKNOWN when that row is non-relevant. The interpreter's blanket gate over-suppressed it (any non-relevant cell → UNKNOWN), so the kernel fired where the interpreter didn't.

The fix splits the `evalFunc` partial gate: a `starRelevant: (starPath) -> Boolean` (threaded from `DmInterpreter.starRelevantOf` — does the relevant set wildcard every repeatable level of the path) gates the all-rows aggregates; `FirstFilled` is exempt and evaluated order-aware over `starCells` via `cellRelevant`. **Full validation is byte-identical** (`starRelevant`/`cellRelevant` null → the gate is skipped, `FirstFilled` falls to the plain first-filled path), so the `validateFull` perf path is untouched; the partial check is O(relevant-set), cheaper than the old per-cell scan. This subsumes IF35 (its row-1-only concrete cases → not wildcarded → still UNKNOWN). *Locked:* `adapter.laws.PartialValidationAggregateDiffTest` (curated per-operator cases) + the now-unrestricted `perf.PartialValidationFuzzDiffTest` (random document × relevant-subset). KERNEL-FINDINGS "Partial validation — starred-aggregate relevance".

### IF43 — baseline value checks: legal charset + leading/trailing blank (FIXED 2026-06-26, was the §3 "charset" out-of-scope item)

The §3 "string charset" item was recorded out-of-scope on a "not DM-JSON-declarable (no serialized key)" basis — flagged SUSPECT after the audit found the sibling `maxIntegerDigits` claim wrong (IF30), and indeed it WAS wrong. A probe proved the kernel runs three BASELINE value checks for **every** field kind (`FormalChecker.checkFieldValueFormat`), BEFORE the type-specific format check: **legal charset → leading blank → trailing blank**. They apply with no model configuration at all:
- **charset** → `ZeichenNichtImZeichensatz`: with no programming-language charset configured (a plain DM-JSON model), the default legal charset is the **BMP** (`0x0000-0xFFFF`, `CharsetUtil`: "empty list ≡ 0x0000-0xFFFF"), so any SUPPLEMENTARY-plane character — a UTF-16 surrogate, e.g. an emoji `😀` (U+1F600) — is illegal. BMP chars (`é`, `ü`, `€`, `™`, CJK) are legal.
- **leading blank** → `fuehrendesBlank`; **trailing blank** → `nachfolgendesBlank`. The baseline pre-empts the type check (a ` 2024-01-01` DATE is `fuehrendesBlank`, not a date-format error).

The interpreter missed all three for STRING, missed charset entirely, and mis-coded a NUMBER **trailing** blank as `fuehrendesBlank` (it had only a single `raw != raw.trim()` → `LEADING_BLANK` check). The fix is a single cross-kind `baselineValueError(raw, legalCharset)` (charset → leading → trailing) applied FIRST in `formalError` for every kind, replacing the number-only blank check. *Locked:* `adapter.laws.BaselineValueFormalDiffTest` — astral/leading/trailing across STRING/NUMBER/DATE + BMP-clean + internal-blank-clean controls, vs the kernel. KERNEL-FINDINGS §3 "baseline value checks".

**The charset is also CUSTOMIZABLE — the `LegalCharset` SPI (the customization-surface #1 goal).** The kernel's legal charset is a project/codegen config (not a DM-JSON property): the default is the BMP, but a project can configure a narrower restricted set — the real case is **DIN 91379** (EU public-administration). To be 100% compatible the interpreter exposes it: `DmInterpreter(legalCharset = …)`, default `LegalCharset.BMP` (so the differential, which has no project charset, stays exact), `ofRanges(…)` for a custom allow-list. A code point the configured set rejects fires `ZeichenNichtImZeichensatz`; the check is a cross-platform code-point walk (combines UTF-16 surrogate pairs, since `String.codePoints()` is JVM-only). *Locked:* `interpreter/commonTest/LegalCharsetTest` (BMP default + ASCII/range customizations, JVM+JS). This is the first general instance of the CLAUDE.md "customization-surface parity" #1 goal (every kernel customization exposed on the API).

### IF44 — code-based `CustomFieldType` SPI: the imperative twin of `PredefinedType`, dispatched additively (FIXED 2026-06-27, graduated from IG21)

Custom field types were **declarative-only** — the registry value was `PredefinedType(minLength, maxLength, pattern)`, a *data* record interpreted by `accepts(value)` — so a consumer could declare a *format* constraint but not an *imperative* one (a checksum: IBAN mod-97, ISIN/Luhn). Custom *conditions* already had a code seam (`CustomCondition` is a `fun interface`); field types did not. Part of the CLAUDE.md "customization-surface parity" #1 goal.

### IF45 — `applyComputations`: the apply-computed-back primitive + the compute-then-validate flow (2026-06-28)

The kernel keeps validation and computation **separate** — `validateFull` does NOT compute first (KERNEL-FINDINGS "validateFull does NOT run computations") — and the consumer applies computed values back with `IDocumentComputationResult.applyTo(doc)` before re-validating (the **form-engine flow** `compute → apply → validate`). The interpreter exposed the two halves (`validate`, `compute`) but **not** the apply-back step, so a consumer couldn't reproduce the realistic "is this document valid in the app?" answer — a required-or-referenced **computed** field validated raw false-fires `mandatoryField` / reads empty.

IF45 adds the clean-room twin of `applyTo`: **`DmInterpreter.applyComputations(doc): Document`** returns the updated document — a VALUE outcome **sets** the computed cell, an ERRORED or CLEARED outcome **empties** it (matching `applyTo`, which applies `WithChanges` and clears both `WithErrors` and `Cleared`; KERNEL-FINDINGS). It rides the existing reps-aware compute core (`computeInstances`, the cascade/poison machinery) and materializes the result through a new `Document.withComputed(overrides)` clone (placements re-added through the public builders so the index/auto-grouping/document-order invariants hold). The form-engine flow is then just `validate(applyComputations(doc))`.

**Faithfulness** is locked by the differential `adapter.laws.ComputeApplyDiffTest` — for a required-computed field and a rule over a computed field, the interpreter's `applyComputations` + `validate` equals the kernel's `compute().applyTo().validateFull()` in BOTH modes (raw false-fires / applied clears), and the two modes genuinely differ. The **engine-level** `validate == validateFull` parity stays foundational (every other differential rests on it); the composed path is verified on top, never replacing it. Consumers: the CLI `model eval` / `rule eval` **default to** the composed flow (`--no-computations` opts to raw); the `--kernel` engine path is `KernelAdapter.evaluateApplied`. Part of the CLAUDE.md "customization-surface parity / match-the-kernel" goal — the apply-back primitive was a missing surface, not just a CLI convenience.

### IF46 — `NumberOfFilledGroups(/Group*)` counts a repeatable group's INSTANTIATED repetitions (FIXED 2026-07-06, graduated from IG26)

`NumberOfFilledGroups` has two rendered shapes. The **plain multi-group** form (`NumberOfFilledGroups(g1, g2)`, ≥2 distinct groups) counts each listed group that is filled — it worked, its operands are plain `Expr.Field`. The **starred single-repeatable-group** form — `NumberOfFilledGroups(/Group*)`, which the `RootGroupCount` DSL node (a repeatable *root* group) and `Dsl.numberOfFilledGroups(repeatableGroup)` (a repeatable non-root group) both render — carries a bare `Expr.Star` operand, and the count branch did `pathOf(it)` (`it as Expr.Field`) → an **uncaught `ClassCastException` that aborted the whole `validate()` run** (root mechanism R1, the `pathOf`-assumes-a-plain-field class; sibling of the `$`/star gaps). ### IF47 — `$` outer-iteration correlation: the enclosing-row seam + the O(N) equality hash-join (FIXED 2026-07-06, graduated from IG23)

A `$`-marked reference inside a `Having` filter correlates the inner filtered row to the **enclosing (outer) iteration row** — the kernel BA's "predecessors" pattern `AtLeastOneFieldFilled(../G* / F Having CurrentRepetition(/G) != CurrentRepetition($/G) And [F] == [$F])` (KERNEL-FINDINGS §"$ correlation is implemented, both directions"). dmkits reads/authors/renders it in full, but the interpreter **hard-failed at parse** (`parser: unexpected '$'`), making `model eval` / `rule eval` / `model compute` unusable on any model that uses it (reported on a real corpus model). It hid because the interpreter's parity is only as complete as the differential + fuzz *feed* it, and `$` was never fed to `DmInterpreter` — the process root cause the durable guard (below) closes.

The three-layer fix: **(1) parser** accepts `$` in all four atom positions (`[$path]`, `CurrentRepetition($path)`, bare `$path`, value-list `$Group*/field`) → an `outer` flag on `Expr.Field`/`Expr.Star`/`Expr.EnumCategory`; **(2)** the evaluator threads the enclosing iteration as `outer: EvalContext`, set only while a `Having` sub-interpreter (`havingInterp`) evaluates, so `ctxOf` routes a `$`-ref to `outer` and a bare `$` at top level is a fail-fast error; **(3)** a filtered quantifier over a star (`starQuantTally`) iterates the group's rows and keeps those the `Having` accepts. Bit-exact via `adapter.laws.OuterCorrelationDiffTest` (self-excluded / no-self-exclusion / non-equality-fallback / empty-and-zero-join-keys) — the very differential whose absence hid the gap. Clean-room from the BA example, no kernel delegation.

**Performance — an O(N) hash-join, faster than the kernel (INTERPRETER-PERFORMANCE.md).** A naive filtered self-correlation is O(N²) (each of N outer rows scans N inner rows). The equality self-correlation shape `[X] == [$X]` (± a `CurrentRepetition` self-exclusion) is recognized (`parseCorrelationJoin`) and resolved by a value-keyed **bucket map** the `Document` builds + caches once per (group, scope) — O(N) — then an O(1) lookup per outer row (`hashJoinTally`, self-subtracting the outer row's own contribution when self-excluded). This is the kernel's own linear strategy; a non-equality `Having` keeps the O(N²) scan fallback (still `$`-correct). Gated by `adapter.perf.OuterCorrelationPerfTest` (sub-cubic per-row + an against-kernel ratio via `RuntimeLaws.kernelEngine`) — measured **8–11× faster than the kernel** on the self-correlation curve. **Known edge (shared with the plain star path):** a malformed inner field inside a `$`-`Having` uses the path-only `invalid` check (both fast-path and fallback), so per-cell malformed-in-`Having` is not yet differential-covered — closes when the fuzz generates `$` + malformed cells (the durable guard).

### IF48 — string concatenation: `+` is kind-dispatched, not numeric-only (FIXED 2026-07-06, graduated from IG24)

`+` was numeric-only (`evalArith` → `num`), so a `Concatenation` computation with two present STRING operands hit `num(Val.Txt)` → an **uncaught `IllegalStateException` that aborted the whole `compute()` run** (root mechanism R2) — highest real-world impact, since `FullName = FirstName + " " + LastName` is one of the commonest computations and it broke the moment the fields were filled. It was authored/rendered/kernel-accepted but only render-checked (`ConcatenationReadTest`), never fed to `DmInterpreter`.

The fix kind-dispatches `+`: when either operand is textual (a `Val.Txt`, a STRING-field ref, or a nested `+`-concatenation) the result is **string concatenation**, else numeric addition — matching the kernel's overloaded `+`. An **empty** string operand contributes `""` (kernel-probed: `FirstName + " " + LastName` with `LastName` empty → `"Jane "`, not Unknown), so `concatText` maps a `Val.Txt` to its text, a `Val.Num` to its display form, and empty/other to `""`. *Locked:* `adapter.laws.ConcatComputeDiffTest` (both filled / first-empty / last-empty against the kernel's `compute()`).

### IF49 — group-scoped field-fill quantifiers: expand to descendant fields, over the kernel's TWO iteration ranges (FIXED 2026-07-06, graduated from IG25)

A field-fill quantifier can take a **group scope** rather than a field list — `AllFieldsFilled(/Order/ShippingAddress)`, `AtLeastOneFieldFilled(/Order/Items*)`. Two failures: a **bare group** operand was treated as ONE field (`ctx.filled("/Order/ShippingAddress")` on a group path → **quiet wrong verdict**, the worst kind), and a **starred group** operand crashed (`pathOf(Star)` → `ClassCastException`, aborting the run — root mechanism R1). It was authored/rendered/kernel-accepted (`GroupScopedFieldFillReadTest`) but never fed to `DmInterpreter`. The **same class latently mis-evaluated `AllFieldsFilled` over a single *starred field*** (`AllFieldsFilled(/Items*/Sku)`) — the old `starQuantTally` flattened instantiated cells, which is the wrong range (see below).

**The kernel semantics (source `RuntimeController` + `ExpandService`, probe-confirmed — KERNEL-FINDINGS §1).** A group scope means "the fields inside the group", **recursively** (the kernel `ExpandService` → `getAllContainedFields`, so a nested subgroup's fields count). The runtime then uses **two iteration ranges** for a starred entity: `AllFieldsFilled`/`NotAllFieldsFilled` iterate the **full DECLARED** repetition range (an un-instantiated rep reads empty → `AllFieldsFilled(/Lines*)` is TRUE only when *every declared rep* is filled), while `AtLeastOne`/`NoField`/`MoreThanOne`/`NotExactlyOne` clamp to the **instantiated** rows; `FieldsNotCollectivelyFilled` mixes (instantiated-≥1-filled AND declared-≥1-empty). A bare non-repeatable group is one declared rep, so the ranges coincide.

The fix: `EvalContext.fillScope(scopePath, isGroup)` (the general `Document` resolves it) enumerates the descendant fields from the model (`kinds` under the scope) and returns a `FillScope` carrying **both** ranges — the instantiated 3-state tally (`tInst`/`fInst`/`nInst`, malformed cell → `hasUnknownInst`, exact per-cell via `resolveValue`) **and** the declared flags (`allFilledDeclared`/`anyEmptyDeclared`, a short-circuiting scan over `1..declaredMax` at each repeatable level — **O(instantiated + 1)** in the common under-filled case, O(data) when fully filled, never worse). `Interpreter` routes a fill quantifier with a scope operand (a bare-group `Field`, or a `Star` **without** a `Having` — a `Star` *with* a `Having` stays the IF47 filtered-correlation path) through `fillScopeFires`/`fillScopeType`; a plain field list keeps the existing `quantCounts` path (byte-identical), and the instantiated-range ops reduce to the same `quantifierFires`. *Locked:* `adapter.laws.GroupScopedFieldFillDiffTest` (bare / starred / nested-recursion × both ranges × firing **and** polarity, against the kernel). Surfaced by the 2026-07-06 renderer-vocabulary audit (IG25).

### IF50 — entity-valued value list: a starred value ref is the flattened FILLED cell set (FIXED 2026-07-06, graduated from IG27)

A value-list quantifier can take an **entity** value list — `AtLeastOneFieldValueIncludedInValueList(f In /Order/Items*/Sku)` — where the value side is a **starred repetition list** (a field's cells across all rows), not literal constants. `evalValueListQuant` mapped `evalExpr` over the value refs, so an `Expr.Star` value hit "a starred path must sit inside an aggregate" (root mechanism R1's value-list sibling). Authored/rendered/kernel-accepted but only the LITERAL form was fed to `DmInterpreter` (`ValueListQuantifierDiffTest`).

**The kernel semantics (probed 2026-07-06):** the value SET is the starred field's **filled** cell values across all rows — empties dropped (`PC=A In Sku=[A,B]` → in; `In []` → not in; an empty field on the left is skipped). The fix expands a `Star` value ref via `ctxOf(v).star(v.path)` (the filled values; a malformed cell stays `Unknown` → the whole quantifier is `Unknown`), leaving a literal or plain-field value ref on the existing `evalExpr` path. *Locked:* `adapter.laws.EntityValueListDiffTest` (`AtLeastOne`/`No`/`NotAll` membership, empty value set, empty field). Surfaced by the 2026-07-06 renderer-vocabulary audit (IG27).

### IF51 — the multi-operand aggregate forms: multi-field / group / typed, not single-star-only (FIXED 2026-07-06, graduated from IG29–IG32)

The value/count aggregate family (`Sum`/`MaxValue`/`MinValue`/`NumberOfDifferentValues`/`NumberOfFilledFields`) was modeled **single-starred-operand only** — `starVals` did `f.args.single() as Expr.Star`, `NumberOfFilledFields` did `pathOf(field)`, and `Aggregates.numberOfDifferentValues` folded via `numOf` (numeric). But rulekit + the kernel also accept the explicit **multi-field list** (`Sum(A, B)`), a **GROUP** operand (`NumberOfFilledFields(/Addr)`), and **non-numeric** (STRING/ENUM) element types. Each form is authored/rendered/kernel-accepted (`MultiFieldSumReadTest`) but had **no** `*DiffTest` feeding it to `DmInterpreter` — the exact renderer-vocabulary blind spot, the second sweep's `feldListenOp` sibling of IF46–IF50. Four forms crashed **uncaught** (`IllegalArgumentException`/`ClassCastException`, aborting the whole `validate()`/`compute()` run — root mechanism R1: an operand that is not a single plain field/star); one silently miscounted.

The fixes, all clean-room + differential-locked:
- **multi-field value aggregates** (`Sum`/`MaxValue`/`MinValue`) — `starVals` now flattens across **all** operands (`aggOperandVals`): a `Star` expands over its rows (a `Having` filters them), a plain field contributes its value when filled. An empty operand is **dropped** (not folded as 0), so `MinValue(20, empty) == 20`; an all-empty set folds to the kernel's `0` identity (KERNEL-FINDINGS §1 supplement).
- **`NumberOfDifferentValues` typed** — `Aggregates.numberOfDifferentValues` counts distinct by a canonical **TYPED** key (`"N"+scale19` / `"S"+str` / `"B"+bool`, mirroring `fieldValuesNotUnique`), so a STRING/ENUM operand no longer hits `numOf`'s numeric `error`.
- **`NumberOfFilledFields` scope** — `filledFieldsValue` counts across operands: a plain field 1-when-filled, a **starred** repetition list its filled cells across rows (IG31, the `pathOf(Star)` crash), a **group** operand its filled descendant fields recursively (`fillScope(path, isGroup=true)` — IG32, the "group counted as one unfilled field" silent-wrong). A present-but-**malformed** cell is a formal error that makes the whole count **non-evaluable → `Val.Unknown`** (the rule is suppressed, exactly as `combine` does for the value aggregates) — **not** "count the valid ones and skip it." The **fuzz caught this**: my first cut counted present cells, so a doc with 4 valid + 1 malformed `Qty` fired `NumberOfFilledFields(Lines* Qty) >= 2` in the interpreter while the kernel suppressed it (the malformed field is a formal error the referencing rule inherits). Locked deterministically by the malformed case in `MultiFieldAggregateDiffTest.numberOfFilledFieldsStar` + the differential fuzz's `NF` rule.
- **count polarity** — the count family now types directionally (grow-only, KERNEL-FINDINGS §1 supplement): `funcFill` returns `Fill.of(canGrow = leafOmission, canShrink = false)`, so a fired `count >= n` is VALUE (was wrongly OMISSION under the old symmetric fill).

**IG33 — `SumOfProducts` over plain fields — is parity-by-construction, NOT a gap:** the kernel rejects it at codegen with `MVK_REPEATABLE_LEVEL_REQUIRED` ("All fields must be repeatable at least at one layer"), so a plain-field `SumOfProducts` never appears in a valid/loadable model and the interpreter's `sumOfProducts` (which resolves both operands as stars) is unreachable on any valid input (INTERPRETER-GAPS §3). *Locked:* `adapter.laws.MultiFieldAggregateDiffTest` — every form × {number, string} × firing **and** polarity, against the kernel; it is the durable net for this sub-class, keyed on the DSL's *emit* shapes (multi-field / group / typed) the operator-keyed guards can't see. Surfaced by the 2026-07-06 second interpreter-vocabulary sweep (IG29–IG32).

### IF52 — the omitted-year date literal `"13.07."` injects the model's base year (FIXED 2026-07-06, graduated from IG22)

A date literal can omit the year — `"13.07."` (day.month., trailing dot) — a **reference-year** feature: the kernel injects the model's `baseYear`, so `[OrderDate] > "13.07."` is a full-date comparison against `13.07.<baseYear>`. The interpreter's `coerceDate` canonicalized only the full `dd.MM.yyyy` form, so the omitted-year literal stayed an un-coerced string and the comparison diverged.

**The kernel semantics (probed 2026-07-06 — this CORRECTS the IG22 hypothesis).** The injected year is exactly `baseYear`, **not a floor**: on the order fixture (`baseYear = 2020`), `[OrderDate] > "13.07."` fires for `2024-07-20` and `2020-07-20` but **not** for `2019-07-20` (a floor would fire) nor `2020-07-10` (day/month within the base year). And a model with **no** base year **rejects** the literal at validation (`MVK_INVALID_COMPARE_TO_DATE`, "only allowed to compare dates with other fitting dates") — so the interpreter only ever sees `"13.07."` when a base year is present; there is no floor case to handle. The fix teaches `coerceDate` to match the `dd.MM.` shape and append `baseYear` (zero-padded to 4 digits) before the ISO parse; the full `dd.MM.yyyy` path is unchanged, and a non-date string still passes through untouched. *Locked:* `adapter.laws.OmittedYearDateDiffTest` (`>` and `<` × the base-year boundary dates, against the kernel). KERNEL-FINDINGS §6 supplement.

### IF53 — full validation: an INSTANTIATED repeatable-group row is *content* (evaluated), not just a valued field (FIXED 2026-07-06, graduated from IG34)

The interpreter's row-content gate — `EvalContext.evaluated` (built by `Document.attachByDepth`), which feeds the `Interpreter.gated` rule-eval check — counted only **valued fields**. So a rule whose iteration scope contained an all-field-empty but **instantiated** repeatable-group row was skipped, where the kernel **evaluates** it: the kernel treats *creating a repeatable row as content in itself* (KERNEL-FINDINGS §4/§9's `GroupFillCache` split — a repeatable group is "filled" once its row exists). Two shapes diverged, both firing OMISSION in the kernel and nothing in the interpreter:

- a **per-row comparison** `[Qty] < 5` over instantiated-empty `Lines` rows (empty `Qty` = 0 < 5) — fired on **every** instantiated row;
- an **ancestor-scoped empty-identity aggregate** `MinValue` over `Lines* then Qty`, `< 5` (empty identity 0 < 5) — the instantiated `Lines` rows make the non-repeatable `/Cart` scope content-bearing, so it fires @ the first row.

**Fix (single-sourced — the "content" notion is one thing, two consumers).** The `Document.Index` gains a `content` list = **a valued field OR an instantiated REPEATABLE-group row** (a non-repeatable group's mere structural presence is excluded — its group placement has `value == null` and is not in `declaredReps`). Both consumers route through it: **`attachByDepth`** (the rule-eval `evaluated` gate) and **`nonRepGroupFilledDepths`** (the `GroupFilled` OPERATOR for a non-repeatable group). The second is the **sibling the root-cause sweep found** (both once scanned valued fields only): `GroupNotFilled(Box)` over a non-repeatable `Box` with 3 instantiated-empty repeatable `Items` rows — the kernel reports `Box` **filled** (the instantiated rows are content), the interpreter wrongly reported it unfilled → `GroupNotFilled` mis-fired. So the "non-repeatable group is filled iff a descendant FIELD is filled" reading of KERNEL-FINDINGS §4/§9 was incomplete: an instantiated repeatable descendant row also fills it. The truly-empty non-repeatable `/Order` of [[IF6]]/`EmptyRowGateDiffTest` is unchanged (no instantiated repeatable descendant, no valued field). The `evaluated` flag stays O(1) per row (precomputed, memoized per group); `content` is O(document), same order as the valued-field scan it replaces — no new N² term (perf-gate confirmed). **Zero rows → still no fire** (no content). Surfaced by the aggregate-fuzz's re-added `MinValue < 5` rule (the only unguarded empty-firing aggregate in the net). *Locked:* `adapter.laws.RepeatableRowContentDiffTest` (rule-eval gate) + `adapter.laws.NonRepGroupFilledContentDiffTest` (the `GroupFilled` sibling) + the full differential fuzz. KERNEL-FINDINGS §2 + §4/§9 supplements.

### IF54 — partial validation: a RELEVANT instance is evaluated regardless of content — empty-as-0 / empty-identity FIRE (FIXED 2026-07-06, graduated from IG34)

The other half of [[IF53]], in **partial** validation: the content gate does **not** apply at all — the kernel checks **every RELEVANT error-field instance**, firing a comparison's empty-as-0 or an empty-identity aggregate even on a **non-content-bearing (empty / phantom)** relevant row. This is a genuine **full-vs-partial asymmetry** — relevance is the kernel's explicit "check this," which `validateFull` has no analogue of. Probed 2026-07-06:

- `MinValue` over `Lines* then Qty`, `< 5` on a `/Cart`-relevant **empty document** (zero `Lines` rows) → the kernel FIRES `OMISSION @ /Cart[1]/Lines[1]/Qty` — a **phantom** row that does not exist — though `validateFull` over 0 rows does **not** fire ([[IF53]]);
- `[Note] < 5` on a **relevant empty** `Note` → FIRES (empty-as-0), though full validation of a blank field does not ([[IF6]]);
- the **IF42 star-relevance gate still bounds an aggregate under a *concrete* relevant row**: `MinValue` with only a concrete `Lines[1]` relevant → the star is not wildcard-relevant → UNKNOWN → no fire (matching the kernel).

**Fix:** `Interpreter.gated` is bypassed when `partial` (the caller supplied a relevant set → `cellRelevant` is non-null) — the upstream `DmInterpreter.rowOutcomes` relevance gate has already decided (it only reaches an eval for a relevant error-field instance), so re-applying the content gate would wrongly suppress. Full validation (`cellRelevant == null`) keeps the gate ([[IF53]]). *Locked:* `adapter.laws.RepeatableRowContentDiffTest.partialRelevantEmptyInstanceIsEvaluated` + `perf.PartialValidationFuzzDiffTest` (the `MinValue < 5` rule re-added). KERNEL-FINDINGS §2 supplement. IG34 is now closed — the interpreter gap ledger's §1 is empty.

### IF55 — the hand-written parser accepts the legal stored DSL: case variants, `;;` comments, `..Name`, `For` on bare args (FIXED 2026-07-06, graduated from IG35)

The interpreter's parser (`parse/Parser.kt`) is the **default `model eval`/`rule eval` path** and must accept whatever the real kernel STORES — but a Phase-0 sweep (SEMANTICS-FORMALIZATION-PROPOSAL S1) found it rejected several legal shapes real conditions use. WI-P completed it, TDD-driven by a recreated sweep (`adapter.laws.ParserCorpusSweepTest`) — which is now a **permanent guard** with two postures: the catalog + fuzz DSL parse **100%** (always-on, in-repo, must stay green) and the `a12-kernel-mm` metamodels + A12 Tools workspace corpora parse **100%** (opt-in, external-sibling, `assumeTrue`-skip). Before/after: mm conditions 647→657/657; workspace conditions 177→368/368, operations 206→234/234. The shapes:

- **Keyword case variants** — `And`/`and`/`AND`, `Or`/`or`/`OR`, `In`/`in`/`IN`, EXACTLY as `LexerTerminals_en` enumerates them (the UND/ODER/IN token families) — a fixed `KEYWORD_VARIANTS` table in `matchKeyword`, NOT blanket case-folding, so `aNd`/`oR` stay rejected. The `to`/`To`/`TO` (ZU) family is intentionally absent: its only user is the `ValueNotConsistent` separator, which the interpreter does not parse (not in the catalog, not in the corpora) — no match site, so adding it would be dead.
- **`;;` comments** — already skipped in `skipWs` (kernel `Comment` token), incl. the **multi-line continuation** form; `;;` inside a string literal stays data (`readString` doesn't skip). The kernel channels `Comment` as `before`/`after` a (sub)condition/operation; skipping it wherever whitespace is skipped is a safe superset for *reading* stored conditions.
- **`..Name` turning-point paths** — the grammar's `relativeUp` (`relUp? '..' idName?`). Clean-room from `CheckRelativeUpImpl`: the up-count is set purely by the number of `..` tokens; `Name` merely NAMES the ancestor landed on (the kernel raises `MVK_INVALID_ENTITY` on mismatch) and NEVER changes the target, so `..Name/rest` ≡ `../rest` and `..Name` ≡ the ancestor group. **Behavior-bearing → locked against the real kernel** (`adapter.laws.NamedAncestorPathDiffTest`: kernel accepts `..Name`, interpreter agrees, and it fires bit-identically to its plain-`..` twin), plus the syntactic `interpreter.NamedAncestorPathParseTest`.
- **`For` semantic-index suffix on BARE args** — `Fuer` rides the kernel's `entitySpec`, so it can follow any entity reference, not only inside `[...]`: `FieldValueAsString(field For Index)` and semantic-index refs inside a `+` string concatenation now parse to the same `Expr.SemanticIndex` the bracketed form does (a shared `entitySuffix` helper) — eval already locked by `SemanticIndexDiffTest`.
- **Value-list literal form** — `FieldValueIncludedInValueList(field, "a", "b", …)` (the kernel's comma-separated `wertListenSpezifier2`) already mapped onto the generic `Cond.Pred` the evaluator's `valueInList` interprets (`ValueListDiffTest`); WI-P pins the parse (`interpreter.ValueListLiteralParseTest`).

Parser-source decision (INTERPRETER-SPEC §11, fork F4): the gap was small and enumerable, so **complete the hand-written recursive-descent parser** rather than adopt the kernel parse-tree-api or generate ANTLR from the EUPL `.g4` — keeping the component kernel-free (native-safe / JS-compilable) and the `.g4`-derivative licensing question moot (reading the grammar for syntax *shapes* is mechanism, not expression). No GRAMMAR-LEDGER row classification flips (that ledger tracks the rulekit renderer/adapter, not the interpreter parser).
