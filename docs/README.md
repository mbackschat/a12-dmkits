# a12-dmkits docs — index

What each document under `docs/` holds, so you can jump to the right one. This is an *index*, not policy: the project's working conventions (language, fixture sourcing, coding style, documentation discipline, testing strategy, build) live in [`../CLAUDE.md`](../CLAUDE.md).

## Design & vision

- **[PROJECT-DESIGN.md](PROJECT-DESIGN.md)** — the one argument: vision (the bidirectional *read → explain → modify → diff → validate* loop), requirements (`Fn`/`Nn`/`Dn`), architecture, the operator-catalog spine, the decision log (§17), the phased roadmap (§16 — phasing *intent*; what's built is shown by the docs + demos), and the **modelkit addendum (§21)** — the structure-authoring peer of rulekit (fork #8): why it's worth it, why not `betterbuilders`, the formalize-the-knowhow gradient + five options, a material-source evaluation, and the read→edit→write-back plan. Densely cross-referenced by stable anchors; component *detail* splits out into specs rather than fragmenting the argument.
- **[ARCHITECTURE.md](ARCHITECTURE.md)** — the *physical* view: the Gradle subprojects (core / opt-in `adapter` / `cli`) and the skill, their artifacts, the core's acyclic package layering, the N8/D15 kernel-coupling boundary, what crosses each boundary as plain data, and the **proposed parts laid out as TBD** with each one's intended home. Complements the design's conceptual component view (§15).
- **[CLI-SPEC.md](CLI-SPEC.md)** — the standalone CLI (the modeller/BA front-end, N10): the verb surface, the JSON I/O contract, the **dev/test workflow that keeps the inner loop fast** (JUnit verb tests; packaging out of the loop), the `export` verb detail, sizing, and the dev-vs-distribution packaging phases.
- **[CLI-CONFORMANCE-SPEC.md](CLI-CONFORMANCE-SPEC.md)** — the **self-explain + diagnosis harness**: the diagnostic contract (every domain error is a structured, coded, fixable envelope), the self-explain criteria, the anti-pattern catalog, the **gates** that enforce each (the conformance fuzzer, registry parity, single-source derivation), the never-stale guarantee, and the verb-authoring checklist.
- **[FEATURE-GAPS-LEDGER.md](FEATURE-GAPS-LEDGER.md)** — the **BA-workflow gaps ledger** (the `-LEDGER` family): the ergonomic gaps in the BA+agent loop that a 2026-06-14 review (+ the OQ1 probe) surfaced — **G1–G11 + R1–R4, all shipped**. §2 keeps each gap's identity + a pointer to where its durable *why* now lives (API-FINDINGS / CLI-SPEC), so `Gn` code refs stay meaningful; the per-gap status table is gone (that was status). The durable part is **§4 — the out-of-scope decisions** (the cross-model refactor, the native interpolated-message preview, `dmtool serve`, each with its reasoning + re-open trigger). Code comments citing `FEATURE-GAPS §N`/`Gn` resolve here by name.
- **[DEV-API-GAPS-LEDGER.md](DEV-API-GAPS-LEDGER.md)** — the **developer-perspective peer of FEATURE-GAPS-LEDGER**, one persona over: the DSL-API gaps for rulekit/modelkit as a typed Java library, surfaced by a 2026-06-14 review against the kernel *dev* doc. **DG1–DG6 all shipped**; §2 maps each `DGn` → its API-FINDINGS finding (so the code refs resolve), with two cosmetic edges still open. **§3 records what's adjacent-but-out-of-scope** (document-instance manipulation, codegen, mapping runtime, …).

## Kernel truth (verified facts & their treatment)

- **[KERNEL-FINDINGS.md](KERNEL-FINDINGS.md)** — experiment-verified kernel behaviors that **complement** `a12-kernel-demo`'s canonical, consult-only `KERNEL-SEMANTICS.md` (checked out as `../../a12-kernel-demo/KERNEL-SEMANTICS.md`). Section-numbered to mirror it; every entry is test-locked in this repo.
- **[KERNEL-INTEGRATION-NOTES.md](KERNEL-INTEGRATION-NOTES.md)** — rulekit's *treatment* of each verified kernel/build/environment fact: how the kit validates (F4), writes (F6), and diagnoses (F4a) against the real engine.
- **[MVK-LEDGER.md](MVK-LEDGER.md)** — the classified inventory of every kernel `MVK_*` rule-diagnostic (erased-by-types / pre-checked / kernel-delegated / n/a-structural). **Fully classified — 300/300 as of 2026-06-10**; the kernel-delegated rows double as an own-words law inventory. CI-locked, so a code a kernel bump adds can't slip through unclassified; its "How the queue resolves" section maps the per-source resolution path for newcomers.
- **[RT-SEMANTICS-LEDGER.md](RT-SEMANTICS-LEDGER.md)** — the MVK ledger's *runtime* sibling (instrument 6): every class of the kernel's runtime evaluation core classified (mined / already-locked / canonical / infrastructure / out-of-scope / queued), so behavioral semantics get drained from the source proactively — each drained fact law-locked in `adapter/…/laws/` and recorded in KERNEL-FINDINGS. CI-locked by `adapter.RtSemanticsLedgerTest`.
- **[GRAMMAR-LEDGER.md](GRAMMAR-LEDGER.md)** — the *syntax* sibling (instrument 7): all 119 parser productions of the kernel's condition grammar classified (rendered / plumbing / entry / legacy / queued), closing the blind spot keywords and construct enums can't see — a new syntax *shape*. Guardian: `GrammarProductionLedgerTest` (opt-in, reads the sibling `../a12-kernel` checkout, skips when absent).
- **[KERNEL-UPGRADE.md](KERNEL-UPGRADE.md)** — the runbook for *when a12-kernel(-mm) changes*: the coupling map (each guardian test ↔ what its failure means ↔ the realignment), the bump procedure, and the dry-run negative-controls that rehearse a change. Embodies F11's "quiet runtime tolerance, loud build-time detection".

## Experience study

- **[API-GUIDE.md](API-GUIDE.md)** — the user-facing **capability guide**: what the rulekit/modelkit library *feels like* to use — a motivating case study (Part I) then the parts in detail (Part II). The numbered design-findings (the *why*) live in `API-FINDINGS.md`.
- **[API-FINDINGS.md](API-FINDINGS.md)** — the numbered **design-findings** record for the rulekit/modelkit API/DSL: the *why* behind the library's shape (split out of API-GUIDE so the guide stays user-facing). A **rationale record, not a status surface** — *what's built* is shown by the docs + the gated/derived surfaces (the API-GUIDE snippets, the `examples/` demos, `manifest`/the conformance matrix). Findings (referenced as "finding N") seed the LLM skill + self-sufficiency eval; the numbering is stable so those anchors resolve.
- **[EVAL-PRIMER.md](EVAL-PRIMER.md)** — **start here if LLM evals are new to you**: a plain-language intro to what an eval is (oracle, gold, judge, pass@k) plus the **glossary** of all the vocabulary. The onboarding/reference companion to the spec.
- **[EVAL-SPEC.md](EVAL-SPEC.md)** — the self-sufficiency eval & benchmark (N6/N1): the method (a **clean subagent** as the LLM-under-test, since self-eval is invalid), the material boundary, objective+soft-regression scoring, the build-measure-learn loop, the probe protocol, and the runner cost model + execution architecture (§8). The *method* — not the task inventory (`eval/TASKS.md`) or the numbers (`eval/RESULTS.md`).
- **[../eval/TASKS.md](../eval/TASKS.md)** — the per-task **catalog** (sibling of the runner, outside `docs/`): every eval task's intent + what it exercises (the rulekit operator-coverage map + the modelkit/mixed families). The *inventory*; the schema/gold-shapes live in `eval/README.md`.
- **[../eval/RESULTS.md](../eval/RESULTS.md)** — the dated **results log** (sibling of the runner, outside `docs/`): baselines, per-change lifts, model comparisons, and pass@k runs, newest first. EVAL-SPEC is the fixed method; this is the moving record.
- **[PROBE-SPEC.md](PROBE-SPEC.md)** — the **probe** harness: the *other* experience instrument, focused not on CLI self-sufficiency but on **shipped-product DX** (the **native** binary + the skill, over a realistic **multi-prompt** session). The method — why the eval can't see native/delivery/multi-step defects, the objective logging-shim capture, gold-from-existing-models as the correctness anchor, the six analysis dimensions, and the discover→fix→graduate-into-a-guard loop. **No k, no score** — one deep session per task, a diagnostic report. How-to + layout: [`../probe/README.md`](../probe/README.md); scenarios: `../probe/tasks/`; findings: `../probe/reports/`.
