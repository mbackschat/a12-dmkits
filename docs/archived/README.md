# Archived docs — resolved, parked, or superseded

Documents kept for the record but **no longer live**. Each was a `*-PROPOSAL.md` whose question is now **settled** — its durable conclusions have graduated into the live specs/design (linked per entry), and what stays here is the **measurement / decision record**. Nothing in this folder is a current contract; the live docs are indexed in [`../README.md`](../README.md).

- **[CLI-ORIENTATION-PROPOSAL.md](CLI-ORIENTATION-PROPOSAL.md)** — *(resolved 2026-06-19)* how a cold consumer **orients** to `dmtool`. A cheap-first measurement deflated the premise (the help/guide system isn't the bottleneck): two items shipped — a top-level `--help` **orientation footer** and **`--text` dual-format** — and the rest was shelved. The durable design (the **read-when layer map**, the **indirect-primary/direct-secondary audience model**) and the **`manifest`-positioning finding** (the bulk/machine + conformance surface, not the agent's front door) graduated into [`../CLI-SPEC.md`](../CLI-SPEC.md) §2; this file is the measurement record.
- **[DMCODE-PROPOSAL.md](DMCODE-PROPOSAL.md)** — *(not feasible, on hold)* the **code-mode delivery (`dmcode`)** experiment: a tier where a coding agent *writes and executes typed Java* against the kits instead of calling fixed CLI verbs. **OQ1 measured 2026-06-17 → parked** — code-mode tied the bare CLI at ~2.3× cost (a coding agent clears the "verb ceiling" by shell-scripting around it); no advantage for BA authoring. Retained for the record + the re-open conditions (the runtime-eval need; a task the CLI+shell genuinely can't express). The design detail (JDK-25 source-launcher, runtime sizing, the managed Runner, the separate-mirror release approach) lives in the doc.
- **[OQ1-INVESTIGATION.md](OQ1-INVESTIGATION.md)** — the full **OQ1 probe analysis** behind the DMCODE parking decision: the experiment design, the cost comparison (code-mode vs the bare CLI), and the verdict. Companion to `DMCODE-PROPOSAL.md`; its sample inputs are in `oq1-fixtures.zip`.
- **[INTERPRETER-PERFORMANCE-DESIGN.md](INTERPRETER-PERFORMANCE-DESIGN.md)** — *(superseded 2026-06-25)* the proposed **eval-strategy ladder** for interpreter perf (Layer 0 CSE/DAG → Layer 1 sealed compiled-node tree → Layer 2 vectorized batch). Measurement overtook the thesis: Layer 1 measured ~7% end-to-end (the eval isn't the bottleneck) and was reverted; the real levers were per-row **resolution caching** + reduced allocation (the kernel's `ValidationCache`/`IndexFieldCache` analogs), which now beat kernel-Java at 192 rules. Kept for the **cited SOTA research** (§3) and the **rejected approaches + why** (§6); the live story is in [`../INTERPRETER-PERFORMANCE.md`](../INTERPRETER-PERFORMANCE.md).
- **[JSON-SCHEMA-PROPOSAL.md](JSON-SCHEMA-PROPOSAL.md)** — *(built 2026-06-28)* the **JSON Schema ⇄ Document Model** feasibility argument behind `:schemakit`. Its conclusions shipped — the transcoder library + the `dmtool model import-jsonschema`/`export-jsonschema` verbs — so the **contract** graduated into [`../SCHEMAKIT-SPEC.md`](../SCHEMAKIT-SPEC.md) (incl. the §4d at-a-glance coverage tables). Kept for the durable **rationale**: the asymmetric-boundary finding (import maps richly; export is best-effort), the interop-vs-fidelity fork, the three-tier rule story (native keyword / `x-a12-*` carriage / opaque computation), and the missed-potential list.
