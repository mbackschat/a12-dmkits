# dmkits — BA-workflow gaps

> **What this is.** dmkits (rulekit + modelkit + `dmtool`) is driven by a **business analyst working through an LLM agent**: the BA holds a requirement in business terms ("delivery can't precede the order date"), and the agent realizes it through `dmtool` — authoring the **rule or computation** (rulekit), shaping the **model structure** it references (fields, groups, annotations — modelkit), and **reading/auditing** the result. This doc tracks **ergonomic gaps in that BA+agent loop, across all three kits** — so a gap may be a rulekit, a modelkit, or a `dmtool`-verb concern (each gap notes which).
>
> **Status (re-verified 2026-06-17): the 2026-06-14 review's gaps G1–G7 have all shipped** — like the *structural* authoring-coverage inventory that preceded them (also long closed). Each is now contracted + test-locked where it lives: the [status board](API-STATUS.md) (the single source of truth for what's built), [`CLI-SPEC.md`](CLI-SPEC.md) (verb/gate contracts), [`KERNEL-FINDINGS.md`](KERNEL-FINDINGS.md) (kernel facts), or the operator catalog. **Code comments citing `FEATURE-GAPS §N` / `Gn` resolve via the graduation table (§2).** **All four OQ1-probe gaps shipped 2026-06-17:** **G8** (the rich per-kind field spec in `apply`'s `field add`), **G9** (the model-wide usage/audit read — the new **`model usage`** verb), **G10** (`rule read` surfaces a rule's stored message text), and **G11** (`where-used` takes the entity positionally, model via `-m`). The **open backlog (§3)** is now just one **new modelkit gap** (**R3** — resolve the `roles` annotation against `roles.yaml`, surfaced 2026-06-17); **R1** (pattern idioms beyond `kind:rule` — the computation + field-constraint idioms) and **R2** (the `seeAlso` constraint↔operator bridge) both **shipped 2026-06-17 → §2**. **§4** records what's out of scope or parked.

## 1. The loop we're improving

A BA does not write DSL. The kernel BA doc frames the job as mapping a business requirement onto a rule that **describes the violation** (not the requirement), carrying a **rule group**, an **error field**, an **error text**, and a **severity** — plus **computation tables** (mutually-exclusive preconditions → calculations). Its recurring pitfalls — *polarity* (the rule is the error scenario), *"no generic negation"* (use the paired predicate), *error-field placement*, *computation-table exclusivity* — are where an agent stumbles.

dmkits serves the **correctness** axis well, and these strengths are the baseline:
- `schema rule add` **teaches polarity inline** ("TRUE on a VIOLATION … to enforce a requirement write its violation").
- `rule test --doc` / `model eval --doc` **confirm polarity by execution** (fired / passed / suppressed) and now also return the **interpolated end-user message** (G1).
- `RK_INVERTED_REQUIREDNESS` backstops the #1 trap; diagnostics are coded, located, fix-carrying (`diagnostics <CODE>`).

## 3. Open backlog

**All four OQ1-probe gaps (G8–G11) shipped → §2; R1 and R2 shipped 2026-06-17 → §2.** What remains is one **new cross-file modelkit gap** (R3 — `roles.yaml` resolution, surfaced 2026-06-17; modelkit, not rulekit; **designed + sized 2026-06-18**, ready to build).

- **R3 (new, 2026-06-17; designed + sized 2026-06-18 — a MODELKIT gap): resolve the model's `roles` annotation against the workspace `roles.yaml`.** A **modelkit** concern, **not rulekit** (the condition DSL): the `roles` annotation is model metadata modelkit owns, and cross-file config resolution is already modelkit's job (it resolves sibling models via include/`modelAlias`, and scans a directory via [`Workspace`](../src/main/java/io/github/mbackschat/a12/dm/modelkit/Workspace.java)). Today **modelkit treats `roles` as opaque header text** with **no linkage to `roles.yaml`**.

  **Verified against the original SME workspaces** (the A12 Tools `2025.06-ext5` set: `advanced`/`basic`/`e-commerce`/`with-workflows`/`tutorial`/`kernelLanguage`) and the project template — facts that correct the original framing:
  - **Placement is workspace-root-anchored: `<workspace-root>/auth/roles.yaml`, a sibling of `models/`** (the workspace root carries a `workspace.json` marker). The project template's `import/auth/roles.yaml` is the *same* convention — its SME workspace just lives under `import/`. A Preview-App-created workspace instead names it `user/access-rights.yaml` (same schema; not in the SME set) — so **discovery must tolerate all three** and accept an explicit override.
  - **The annotation is on the model *header*** (model-level — it gates the whole model), not on fields/elements. Its **value is a comma-separated list of role names** (e.g. `"tester,reviewer"`, `"systemAdmin,modeler,tester,reviewer"`) — **multi-role is the norm** (208/208 role-bearing SME models use one `roles` annotation with a CSV value), so the read splits on commas exactly like `Workspace.splitCsv` does for `superTypes`/`subTypes`.
  - **`roles.yaml` schema:** `roles: [{ name, description?, accessRights[] }]`; `name` is the identifier the annotation binds to. (`users.yaml` sits beside it, mapping `username → authorities[]` of role names — out of scope for R3.)
  - **The SME validates role *presence* but not role *names*:** with a roles file present, a model lacking a `roles` annotation is an **error**; a model with roles but no roles file is a **warning**; multiple roles files **block** the workspace (`sme-sme-ba-docs.md:462–476`). It explicitly **does not** check that an annotated role is *defined* — "additional roles can be specified and added as well" (`:456`). The SME set even contains a live candidate (`with-workflows` models gate to `…,workflows`).

  **The gap, all modelkit-side:** **(a)** parse `roles.yaml` into a typed `RolesFile`/`Role` model + discover it from a workspace root; **(b)** a **modelkit structure-consistency check** (sibling to the structural checks, *not* a rule `MVK_*`) flagging an **undefined role** — the flagship, since *even the SME doesn't do it* — alongside the three SME-parity states (missing-assignment-when-file-present, declares-roles-but-no-file, multiple-files); **(c)** surface which roles gate each model and which access rights a role carries.

  **Decided design (2026-06-18):** a workspace-level capability surfaced as **`dmtool workspace roles <dir>`** (roles are workspace-scoped; it joins the existing `workspace list/graph/validate` family, reusing `Workspace.scan` + the `ResultEnvelope`/exit-1 gate pattern). Auto-discovers the roles file under the root (`auth/roles.yaml` → `import/auth/roles.yaml` → `user/access-rights.yaml`), `--roles <path>` overriding; scans models recursively; **exits 1 on any ERROR** so CI can gate on it. The `roles` annotation stays authorable via the generic annotation surface (no new typed write builder this increment).

**Sequencing.** **R3** is the only open item — designed + sized above; once it ships it graduates to §2 the same way G1–G11 / R1 / R2 did (a status-board row + the CLI-SPEC contract + its test lock).

## 4. Out of scope / won't build

- **Workspace-wide cross-model refactor (OQ1 candidate, dropped).** Composable today by looping a per-model verb — OQ1 E ran `for m in orderA orderB orderC; do field rename …; done` cleanly. A cross-model refactor verb adds real complexity (reference resolution across includes, the per-model safety gate, partial-failure semantics over N files) for a loop that already works. Not worth a verb.
- **Native interpolated-message preview (parked; this is the G1 caveat above).** `model eval` (JVM) interpolates the message; on the shipped **native** binary it's absent because runtime-eval is Groovy-only / hidden ([`NATIVE-IMAGE-GRAALVM.md`](NATIVE-IMAGE-GRAALVM.md) §4). A native structural-interpolation render isn't worth building unless a real need appears — the **raw-text read (G10)** covers the common "what does it say" case.
- **`dmtool serve` (warm-kernel daemon / stdin REPL) — won't build (decided 2026-06-15).** Examined and **rejected**; the premise collapsed once checked. Don't re-litigate without new evidence against these assumptions:
  - **The premise is dead.** "Seconds, not ms" was the *JVM* path (~600 ms+). The shipped CLI is the **native binary at ~37 ms** ([`NATIVE-IMAGE-GRAALVM.md`](NATIVE-IMAGE-GRAALVM.md) §6) — a warm process exists only to amortize JVM startup + JIT + kernel static init, none of which native pays.
  - **The cheap tier doesn't fix the real cost.** A stateless serve (re-passes `-m` per op, like `batch`) re-pays the per-model bootstrap every op. Only a **stateful warm-model** serve removes it — and that drags in the whole cache-coherence problem (staleness over the resolved file set, a `reload` that refuses on conflict, compare-and-swap on commit), the bulk of a ~1–2 week build and the part most able to corrupt work silently.
  - **`batch`/`apply` already occupy the space** ([`CLI-SPEC.md`](CLI-SPEC.md) §7): `batch` amortizes warm-up over a known op-list; `apply` keeps a warm in-memory model across an ordered transaction with one terminal gate + atomic rollback.
  - **It fights the agent-facing thesis** — the CLI is deliberately a self-explaining, **stateless** surface; serve adds session/lifecycle/reload/stale-write semantics, a second mental model that makes agent reasoning harder.
  - **The one narrow, future exception:** the JVM-only runtime-eval verbs (`model eval`/`rule test`/`model compute`) *do* pay Groovy-codegen warm-up every call. *If* they ever ship as a JVM artifact *and* an agent runs them in a tight interactive loop, a warm process becomes the only way to make them fast. Re-open only then.
- **Whole-model NL summary** ("explain every rule in business terms") — composable today by looping `rule explain`; a `model explain` convenience is minor.
- **Model-version migration** — a distinct concern with its own tool (`kernel-md-cli` → `MigratorCli`). dmkits authors/edits; it deliberately never bumps a model's version on write.
