## 1. Purpose & persona <a id="purpose"></a>

`dmtool` is the **modeller/BA's** interaction surface (N10): one engine (core + adapter + the modelkit/rulekit kits), driven by an **agent** through JSON/flags with operationally profiled JSON/text output, the JVM bundled and invisible. It is *not* the developer's surface — a developer uses the kits as libraries (no CLI). It edits the **whole document model** — structure (fields, groups, type definitions, includes, doc config) *and* rules/computations — validates, reads/explains, and batches. The CLI never shells out to `javac`; the agent authors via **JSON / flags**, which `dmtool` deserializes *through the typed builders*, so the BA gets the builder pre-checks **plus** the kernel `Diagnostic`s (F4a) at runtime — the runtime analogue of the developer's compile-time steering.

## 2. Design principle — self-explaining **and** corrective diagnostics (the #1 priority) <a id="self-explaining"></a>

The tool exists to be driven by a cold LLM agent. Two properties, above all else, make that work — and they are the tie-breaker for every CLI decision:

1. **Self-explaining & explorable.** A cold agent, given only the binary, must discover the verbs, their parameters and meaning, and each verb's I/O shape — *without* the N1 skill. Discoverability is a property of the **tool**, not the skill (which stays minimal: it teaches judgment — polarity, the traps — not the verb catalog).
2. **Corrective diagnostics.** Good diagnostics let the agent **fix its own mistakes**. Every error reaches *detect → locate → repair*: a stable `code`, a `where`, and a `fix`. Self-correction is a measured eval dimension (N-correct, [`EVAL-SPEC.md`](EVAL-SPEC.md) §3), not an aspiration.

**Who reads the surface (the audience model).** Consumption is asymmetric: a BA mostly talks to an **agent** that runs `dmtool` and renders results back in natural language (the #1 path); the BA is a *direct* consumer only occasionally (the N10 front-end). So **the CLI orients the agent; the agent orients the BA** — orientation work targets the agent first, and the human-readable surface (`--text`, below) is sized for the secondary direct-BA/dev path, not the primary one.

```
BA → (talks to) Agent → (runs) dmtool      #1 path; the agent renders results in NL
BA → (runs) dmtool                         #2 path, direct; --text serves it
```

**The read-when map — three layers, cheapest first.** A cold consumer orients in layers ordered by precision and audience; the standing rule is that **discoverability lives in the tool** (the precision layer, derived + gated) while the **skill stays minimal** (judgment, not catalog):

| Layer | Surface(s) | Answers | Audience | Format |
|---|---|---|---|---|
| **Orientation** (cheap, first contact) | `--help` (tool + per-verb) + its *Getting started* footer | "what is this, what can it do, roughly how do I call it" | agent **+** direct BA/dev | text |
| **Precision contract** | `manifest` · `schema <t> <op>` · `operators` · `patterns` · `diagnostics` | "exact verb tree, params, I/O shape, DSL vocabulary + gotchas, error codes" | agent (+ conformance machinery) | JSON |
| **Judgment** | `skill/SKILL.md` | "the traps — polarity, the iteration guard — and *when* to reach for what" | agent | markdown |

The mechanism table below expands the **Precision contract** layer — each concern and the verb that answers it:

| Concern | Question | Mechanism |
|---|---|---|
| **Targets & ops** | "what can this tool do?" | `dmtool --help` (target list) · `dmtool <target> --help` (its ops) · `manifest` (the whole tree, machine-readable, one call) |
| **Parameters** | "how do I call `<target> <op>`?" | per-op `--help` + the `manifest` `params[]` |
| **A worked call** | "show me this verb in action" | the `manifest` `example {intent, command}` — a read-only invocation per verb (CI-executed; see [`CLI-CONFORMANCE-SPEC`](CLI-CONFORMANCE-SPEC.md)) |
| **I/O shape** | "what does it emit / expect?" | `schema` — the standard result envelope (§3) + each op's directional and operational output/input contract |
| **Operational behavior** | "does this invocation read or write, what survives failure, does dry-run write, and what makes outer `ok` true?" | each leaf's generated `--help` footer + `manifest.verbs[].operationalProfiles` + the same `operationalProfiles` annotation on `schema <target> <op>` |
| **Failure space** | "what can go wrong, and how do I fix it?" | every code the tool can emit resolves in the `diagnostics` catalog (`diagnostics` list + `diagnostics <CODE>`), each carrying a `fix` (§4) |
| **DSL vocabulary** | "what operators exist, what do they mean — and how do I express the inverse?" | `operators` (list + per-operator semantics + gotchas), narrowed by a positional **substring** (`operators date` — matched over id/keyword/meaning, the agent's natural reach; composes with `--kind`/`--keyword`), or an **exact id** for full semantics; `operators <id>` carries `opposite` — the negation partner(s) (`FieldFilled`→`FieldNotFilled`, `<`→`>=`), serving the kernel's "no generic negation" model (G3) — plus the **machine tier** ([CATALOG-SPEC §7](CATALOG-SPEC.md)): `semantics.emptyOperand` (the kernel-probe-verified empty-operand facet claims), `correctives` (operand-conditional fixes), gotchas **with their `kind`**, and the bare list's `emptyOperandDefaults` (kind → default empty behavior) |
| **Validation idioms** | "what's the standard way to express *this kind* of rule / computation / field constraint?" | `patterns` (the catalogue — rule idioms (date-order, …), the `tiered-amount` **computation** idiom, and the **field-constraint** idioms `bounded-number`/`formatted-string`/`value-set-enum`; each lists its `kind` and lean `paramNames`); `patterns <id>` (its full `params` + note + skeleton); `patterns <id> --arg k=v` scaffolds a kernel-valid **rule-spec** (right polarity + a referenced error field), **computation-spec** (a mutually-exclusive precondition table), or **field-spec** (a constrained field) and auto-checks it, `--apply` persists it via `rule add`/`computation add`/`field add` (G2/R1) |
| **Diagnostic codes** | "what does this `code` mean, how do I fix it?" | `diagnostics` (list all `RK_*` codes, filterable) · `diagnostics <CODE>` (one code's meaning + canonical fix) — the `operators` twin; see [`CLI-CONFORMANCE-SPEC`](CLI-CONFORMANCE-SPEC.md) |
| **Versions** | "which commit is this build based on, did it diverge, and what does it target?" | `--version` (human) · `manifest.version` (machine-readable) — §2a |

**Implementation: picocli** (§8). One `@Command`/`@Option(description=…)` declaration per op drives parsing, `--help`, *and* the `manifest` — help cannot drift from behavior. The manifest emits the **entire** target×op tree in one response, so an agent discovers everything without walking the subcommand tree interactively. Drift is caught at build: `ManifestVerbTest` (the verb tree), `SchemaVerbTest` (schema ↔ envelope coverage) — the F11 discipline.

**Operational profiles are invocation contracts, not command labels.** `CommandContracts` is the typed owner rendered by help, manifest, and schema. Every live leaf has at least one profile; argument-dependent leaves have explicit selectors under `when`: command-line occurrence (`supplied`/`omitted`), non-default semantic presence (`anySet`/`noneSet`), and parsed `values`. Matching uses parsed values, not token spelling, so `--dry-run=false` is a commit and `--format TREE` selects the canonical `tree` profile. Each profile declares `execution` (`STATIC` or `DM_INTERPRETER_RUNTIME`), `effect` (`READ_ONLY`, one model/artifact write, multi-file write, transaction, or dispatch), `failurePersistence` (`NO_WRITE`, `ROLLBACK`, `PARTIAL`, or `CONTINUE_AFTER_CHILD_FAILURE` after a command, domain, or child failure; never a claim about an I/O failure mid-write or abnormal process termination, since no destination is atomically replaced), `dryRun`, `aggregateSuccess`, the meaning of top-level `ok`, output kind/schema, and expected consistency/runtime provenance. The tool publishes that scope in `manifest.contractVocabulary` and in `schema <verb>` for every verb that can write. Matching `operationalProfiles[].returns.views[]` overrides `operationalProfiles[].returns.kind`; without a matching view, the primary kind is effective. A result-envelope return declares the global `--text=true → RAW_TEXT` view, while raw artifacts do not. Consistency provenance is `NOT_EMITTED` when a gate ran but the selected raw/empty output form has no envelope field, rather than falsely promising `verification`; `NONE` means no receipt exists. The envelope still derives an actual `verification`/`engine` receipt only from what that invocation ran. `apply` is one rollback transaction. Ordinary `batch` is continuing, independent dispatch whose outer `ok` and exit follow all child exits; observation mode instead follows full dispatch plus artifact write, as its explicit selector states.

**Measured positioning — `manifest` is the bulk/machine door, not the agent's front door (2026-06-19).** The table lists `manifest` beside `--help` as a "what can this tool do?" mechanism, but the eval measured what cold agents *actually* do: they reach `--help` (top-level, once) → per-verb `--help` → the catalog verbs (`operators`/`patterns`/`diagnostics`), and **never call `manifest`** — in read, authoring, *and* `apply`/batch composition (where per-verb `--help` flag names supply the op-record keys `manifest` would). That is rational: `manifest` emits the whole command tree, so for a focused task targeted `--help` is cheaper. `manifest` earns its keep as the **conformance backbone** (`ManifestVerbTest`, the matrix, the schema pointers all derive from it) and the **one-call machine/bulk** option — not as the agent's primary orientation path, which is `--help` + the catalog verbs. (Evidence: [`../eval/RESULTS.md`](../eval/RESULTS.md) 2026-06-19; reasoning: the archived [`CLI-ORIENTATION-PROPOSAL.md`](archived/CLI-ORIENTATION-PROPOSAL.md) §3.)

**Orientation footer (shipped 2026-06-19).** The root `--help` ends with a short *Getting started* footer — the read-when map in miniature — that routes first contact to the catalog verbs (`manifest` for the one-call bulk tree, `operators`/`patterns` for the DSL, `diagnostics <CODE>` for errors, `<target> <op> --help` for per-verb detail). It lives only on the root command (per-verb `--help` is unchanged), is single-sourced on `Cli.TOOL_NAME`, and adds no new gate (`CommandReferencesResolveTest` already covers its verb refs; `CliHelpTest` locks its presence). Rationale + the measurement that scoped it: the archived [`CLI-ORIENTATION-PROPOSAL.md`](archived/CLI-ORIENTATION-PROPOSAL.md) §3 (R1).

**Dual-format output (`--text`, shipped 2026-06-19).** A global `--text` flag renders the result envelope as human-readable text for the secondary direct-BA/dev path; **JSON stays the default and the machine contract** (not TTY-detected — explicit, so an agent in a PTY never silently gets text). The self-describing **catalogs** (`operators`/`manifest`/`schema`/`diagnostics`) and `export` **artifacts** stay JSON — `--text` is gated to the result envelope (`TextRenderer` re-renders only an envelope, else passes through). Locked by `CliTextFormatTest`. With R1 (the orientation footer) this resolves the actionable items in the archived [`CLI-ORIENTATION-PROPOSAL.md`](archived/CLI-ORIENTATION-PROPOSAL.md); the remaining candidates there were measured and shelved.

**A route that only an undocumented spelling reaches is worse than a missing feature — it manufactures an unreachability conclusion (2026-09-04).** The four add-verbs that can create something at the top of a model (`group add`, `include add`, `group multiselect`, `group attachment`) keyed the root LEVEL on an **empty** `--parent`, which no help text mentioned, while `/` — the spelling an author reaches for first — refused with `no group at '/'`. Read together those two facts say "this model has no root", and a12-kernel-lean's agent duly concluded that multi-root models are unauthorable through this CLI. Nothing was missing: a two-root model is the only shape that separates model-wide from root-wide addressing, so a whole class of measurement was gated behind a string nobody had written down. `/` is now a synonym for the root level in all four verbs, both spellings are in each `--parent` description, and the missing-parent refusal names the root spelling in its `fix` rather than sending the author to `model describe`:

```
dmtool -m order.dm.json group add --parent / --name SecondRoot
```

Two things generalize. **State the spelling in the option's own description, not only in a spec** — the flag is the surface an agent reads. And **make the refusal name the value the author probably meant**: the likeliest wrong `--parent` is not a typo but a value that meant the root level, which is why that slot gets its own corrective (`ModelPaths.missingParentHint`) instead of the generic "go and read the model". The normalization is single-sourced (`ModelPaths.rootLevelParent`) and `RootLevelParentSpellingTest` asserts the class of four rather than the one verb that was reported — accepting a synonym in one verb would have left the same dead end in three.

**And the class is verbs *plus routes*, which the first pass got wrong.** A cold review found `apply` still reading `parent` raw from its op-records, so `/` stayed a dead end on the surface this spec documents as being at parity with those verbs — the enumeration had been over the standalone verbs, not over the ways to reach them. `apply`'s `group add` and `include add` records now normalize through the same helper; `batch` needs nothing, because it re-enters picocli with argv and inherits the verbs' own handling. **`field add` is the one slot where `/` is genuinely refused** — a field cannot be a root element — and it gets its own corrective saying so (`ModelPaths.fieldParentHint`) rather than the generic missing-group message, because its `--parent` help calls itself the alias matching every sibling add-verb and those now accept the spelling. A denominator over verbs is not a denominator over surfaces.

### 2a. Version & compatibility surface

The tool reports **which commit it is based on, whether the build diverged from it, and what it targets** on two peer surfaces fed from one `VersionInfo`: `--version` (human) and `manifest.version` (machine-readable, so a cold agent reads it like any other manifest fact). Seven axes, each from its single source of truth: the **rulekit** release; the full Git **source revision** plus its build-time **clean/dirty state**; the kernel **built-against** (the `build.gradle` pin) and **runtime** (the kernel jar on the classpath — may be newer); the **A12 Tools distribution** label the built-against kernel ships in (`build.gradle` `a12Distribution`; the human-facing tag for the kernel semver); the **catalog verified-against** floor (`operators.json`); and the **model-format reference** (`core.ModelFormat.VERSION`). `CLEAN` makes the artifact commit-identifiable; `DIRTY` is an explicit warning that different working-tree contents at the same revision are not distinguished. With no Git metadata both fields are `UNKNOWN`, never inherited from an enclosing repository. The generated resource treats both Git values as build inputs, so changing HEAD or dirtying/cleaning the working tree invalidates an older `installDist` provenance stamp.

```
$ dmtool --version
a12-dmkits 0.1.1
  source: <git-revision> (<clean-or-dirty>)
  kernel: 31.1.1 (built) / 31.1.1 (runtime)
  A12 Tools distribution: 2026.06-ext1
  catalog verified against: 31.1.1
  model version (reference): 29.4.0
```

**Compatibility — tolerant, but explicit, with the kernel as the authority.** Two version axes, each handled the same way (inform, don't second-guess the kernel):

- **Kernel skew** (F11): a runtime kernel newer than the catalog floor is safe (rulekit binds only the public surface), so it yields a single advisory INFO `RK_KERNEL_VERSION_SKEW` — never an error. `manifest.version.kernel.skewed` exposes it too.
- **Document `modelVersion`** (the load-time policy): the kernel itself accepts an older same-major model and rejects a newer/different-major one with a clear `"Version mismatch …"` ERROR (KERNEL-FINDINGS, *Header `modelVersion` compatibility*). rulekit **classifies** that verdict so it's machine-actionable: the un-coded kernel ERROR is enriched to **`RK_MODEL_VERSION_INCOMPATIBLE`** (+ a fix — the **fail-fast** case, `valid:false`, exit 1), and an accepted-but-off-reference model gets a tolerant INFO **`RK_MODEL_VERSION_SKEW`** (the **tolerant** case, still `valid:true`). rulekit never re-derives the rule or flips `valid` — the kernel decides; rulekit annotates.
- **A DATE_RANGE's `interpretationOfYear` is authorable and round-trips** (the wrapping-range policy): `field add`/`field modify`/`typedef add` accept it in the `dateRange` block, `field read`/`typedef read` echo it, `model diff` reports a change to it, and the read block is itself a legal write input. It decides which endpoint of a *wrapping yearless* range keeps the base year — without it, `01.11-31.01` on a `dd.MM` range reads as start-after-end and is reported invalid. **The direction is the reverse of what the names suggest**: the value names the endpoint the base year LABELS and the opposite one moves, so `FROM` keeps the start and rolls the END forward a year, `TO` keeps the end and rolls the START back. **`STANDARD` has no spelling** — omit the key; the tool API's `STANDARD`/`PREVIOUS`/`SUBSEQUENT` tokens are refused by the kernel, and the published `enum` refuses them at the boundary with a coded `RK_INVALID_VALUE` naming the admitted set rather than passing them through. *(Locked: `cli.field.DateRangeInterpretationVerbTest` for the CLI channels, `modelkit.DateRangeYearInterpretationTest` for the kernel admission, `adapter.laws.WrappingYearlessRangeDiffTest` for the runtime direction on both kernel strategies.)*
- **A JSON input may be `-` for stdin** (the input policy, G56): the seven **authoring specs** (`field add`/`modify`, `typedef add`/`modify`, `rule add`, `computation add`/`modify`) and the two **op lists** (`apply`, `batch`) accept `-` in place of the path and read the JSON from stdin. **That is nine of the CLI's eighteen declared JSON-file inputs, and the boundary is deliberate — not a claim about the class.** Still file-only: the document `--instance` on `model eval`/`model compute`/`rule eval`, both `profile compare` operands, `profile synthesize --input`, `model diff`'s two model files, and the global `-m`. Those are *document and model* inputs rather than authored specs, and widening to them is a separate decision with its own double-claim consequences (`profile compare` and `model diff` each take two). It exists because `--kind` covers only the *config-less* field kinds: TIME, DATETIME, DATERANGE, DATEFRAGMENT, ENUM and CUSTOM carry config, so authoring one used to require a temp file per field, and a script became a loop with cleanup. The **rich-spec schema stays the single source** for the config shape — `-` changes where the bytes come from and nothing else, and the file form is byte-for-byte unchanged.
  - **`--config <json>` was the alternative and is deliberately not built.** It would duplicate the rich-spec schema as a second, parallel input surface on every one of those verbs, which is the drift the schema-discipline rule exists to prevent.
  - **`--observations` refuses `-` on both halves, because the artifact commits to authored BYTES (G60).** Capture re-reads each candidate's spec from disk and hashes it, which a consumed, unnamed stream cannot serve — so ops-on-stdin and a `-` computation-spec child are each refused with that reason. Verified by execution, not reasoning: before this, both coerced `-` into `<cwd>/-`, which produced a corrective pointing at a nonexistent file *and* put that path into the overwrite-protection set, so a real file named `-` was falsely protected while the actual ops source was not protected at all. *(Locked: `cli.BatchObservationStdinTest`, both refusals plus a from-files control.)*
  - **A transport with no caller stdin refuses `-` outright.** An MCP request has none — over stdio, stdin IS the protocol channel a verb would eat; over `--http` there is no caller stdin at all and a worker would block on the process's until EOF. So the invoker installs that posture around each dispatch, nested children included, and the refusal names MCP content as the alternative — the same answer the server already gives for a caller-supplied path, which is what `-` is one step further out. **Stated precisely because it is easy to overclaim: this is defense in depth, not the closing of a reachable hole.** A stdin read is not reachable over MCP today, and the two links were attacked rather than assumed — of the nine wired inputs, eight require `-m`, which an MCP caller cannot supply, and the ninth is `batch`, whose nesting is refused before the child runs. Both links are asserted by `cli.McpStdinRefusalTest`, so if either changes, that test says so rather than leaving the posture silently load-bearing.
  - **stdin belongs to the PROCESS and is claimed once, with a second `-` REFUSED rather than starved.** The reachable double-claim is `batch -` (or the MCP invoker) whose child argv also carries `-`: those re-enter the dispatch per child, so a claim that did not survive nesting would hand the child a drained stream and let it 'succeed' on nothing. The claim therefore lives for the process — cleared in the process shell, never per dispatch — and the refusal names which parameter already holds it. Two consequences worth stating because both were defects first: the read **never closes** the stream (closing a reader over `System.in` closes fd 0 for the whole process, which would end an `mcp` stdio session mid-conversation), and the claim is taken **before** consumption, so a read that fails part-way still blocks a retry. An **empty** stdin is refused with the pipe spelled out, since a blank read is otherwise a confusing JSON parse error. **Both refusals are coded result envelopes on stdout**, not stderr prose: `RK_INPUT_UNREADABLE` with the parameter in `where` and a corrective in `fix`, so an agent can branch on them — an advertised corrective that only a human can read is not one. The same code covers a missing or unreadable spec FILE, so the shape does not depend on whether the source was a path or a stream; that also removed two prefixes that had started lying (`cannot read ops file` when there is no file). *(Locked: `cli.StdinJsonInputTest` — the file form, the stdin form, their byte equality, the double-claim and empty refusals, the exact-marker discrimination, and two successive claims through `Cli.run`.)*
- **Every unreadable caller-named input refuses in coded form, `-m` included** (the input-failure policy, G58 and G61): a missing `-m` is `RK_MODEL_NOT_NAMED`, an unreadable one `RK_INPUT_UNREADABLE`, and the same code covers the model files of `model diff`, the two `profile compare` operands, `profile synthesize --input` and `model import-jsonschema`'s schema. Two facts here are not obvious and were both defects first. **(1) A `refused` envelope needs a `ResultIdentity`, and an ordinary verb derives one from its depth-2 picocli leaf — so a ONE-TOKEN verb crashes on that derivation.** `apply` and `batch` shipped exactly that: an unreadable `<ops.json>` answered with `RK_INTERNAL_ERROR`, exit **70** and a raw stack trace, telling an agent the tool was broken when the file simply was not there. `batch` even had the named identity two lines further down, which is why reading the code did not show it. Every such verb now takes the identity explicitly, and `export` — which had no identity at all — gained one, so a refusal is an envelope even where the success output is a rendered artifact. **(2) A refusal must name WHICH argument failed.** `rule add`, `computation add` and `apply` read the model inside the catch of a *different* input, so an unreadable model was reported as an unreadable `<rule-spec.json>`, naming an argument that was fine and a path the caller never gave for it; the reads are now separate. *(Locked: `cli.UnreadableModelRefusalTest` — a sweep over the live leaf set, keyed on the argument the diagnostic names, which is what makes the mis-attribution visible.)*
- **An unwritable OUTPUT refuses the same way, and says what it left behind** (G62, the mirror of the bullet above): `RK_OUTPUT_UNWRITABLE`, exit 2, on stdout. Three decisions in it are not the read side's. **Its `source` is `ENVIRONMENT`, not `PRECHECK`** — every check passed and the work was done; the destination refused it, so blaming the input would send an author to the wrong place, and blaming the tool (`INTERNAL`) would send them to file a defect. It is the first ENVIRONMENT code that is an ERROR rather than an advisory: the origin marks *where* the problem is, not how severe. **`written` stays `false` even when bytes reached the disk**, because the published contract defines it as whether the invocation wrote its *selected* destination and a half-written bundle is not that — so **the files that did land are named in `data.written`**, which is the only way a caller can clean up after `export --out-dir` or `model import-jsonschema --out-dir` (both already `FailurePersistence.PARTIAL`). `group extract`, which writes two files, was split for the same reason: one catch over two destinations could name neither. **`batch --observations` keeps its family and exit code and changes only its code** — the children really did run and write, so it is a partial success rather than a refusal; what was wrong was `RK_INTERNAL_ERROR` ("a dmtool defect, report it") sitting beside its own `fix` telling the caller to choose a writable path. *(Locked: `cli.UnwritableOutputRefusalTest` — the shared mutation tail, a single-file writer, a directory-creating writer, an arranged part-way failure that checks the debris list, and the remaining sites by absence of the old literal.)*
- **Model id vs file basename** (the packaging policy): A12 Tools requires a model's file basename to equal its `header.id` and does not strip the `_DM`/`_TDM` suffix from the id, so `Order_DM` belongs in `Order_DM.json`. `model new --id` has always said so in its help, and nothing made the pair *readable* — a plain `cp` broke the invariant with no way to notice short of opening the raw JSON. So **`model info` emits `fileName` beside `id`, plus the computed `fileNameMatchesId`** — the invariant answered rather than left for the caller to re-derive, and that is the whole feature: facts on an opt-in read.
  - **Deliberately NOT a diagnostic**, and the measurement is worth keeping because it is counter-intuitive. An INFO on `model check` was built first, on the `RK_MODEL_VERSION_SKEW` template, and removed when the demo gate showed six demos drifting — with the triggering names `subject.dm.json`, `struct.dm.json`, `edit-add.json`, every one a `cp`-made working copy. **Copy to a scratch name, edit, check is the normal workflow**, so the warning fired on the common case rather than the exceptional mistake, and a diagnostic that always fires teaches its reader to skip diagnostics. The kernel does not enforce this convention; we make it visible and leave the call to the caller.
  - **The comparison TOLERATES a double extension**, deliberately: an id equal to either the last-extension stem or the all-extensions stem agrees, so `cover.dm.json` matches id `cover`. A12 Tools' treatment of `.dm.json` is **not measured by this project**, and the strict reading would report the convention our own docs and fixtures use throughout as broken — under-reporting is the right bias for an unmeasured claim about another product. `fileNameMatchesId:false` therefore means the two disagree under **every** stripping rule (`cover-ruled.dm.json` against id `cover`). *(Locked: `cli.ModelIdBasenamePolicyTest` — both polarities, the double-extension tolerance, and the no-diagnostic non-goal.)*

**Write-back never bumps the version.** Edits are surgical (the `header` is untouched), so a loaded model writes back with its `modelVersion` verbatim — no implicit bump to the reference. (Locked: `cli.ModelVersionPolicyTest`.)

## 3. The op model — one record, two surfaces <a id="op-model"></a>

Every action is one **operation record** — `{ target, op, args }`. A single CLI invocation is *one* record; a batch is an ordered *list* of them ([§7](#7-batching--dispatcher-batch-vs-session-apply)). Its matching operational profile declares the primary output, and a matching view can override it; the resulting effective stdout is the standard result envelope, a raw JSON/text artifact or rendering, or empty after an artifact write. Define the vocabulary once; render it onto both surfaces. Consistency on the two axes — **element family** (modelkit structure ⟂ rulekit rules) × **operation** — then holds by construction, in both the CLI and the batch.

### 3a. Model-bound invocation shape — `dmtool -m <model> <target> <op> [args]`

The model file is **context**, named once with `-m/--model`, like `git -C <dir>` / `kubectl -n <ns>` / `docker --context`. The per-op object (a field path, a rule name) is a positional on the op, like `docker image rm <image>`. So the op's own flags are never interrupted by the model path, and the op record carries **no model** — making single-verb and batch perfectly symmetric:

```
single:  dmtool -m order.dm.json field add --group /Order --name PromoCode --kind STRING
batch:   dmtool -m order.dm.json apply edits.json             # edits.json = [ {target,op,args}, … ]
```

`-m` is an **inherited, position-tolerant** option (accepted before or after the verb). If it is **missing**, the refusal is the coded `RK_MODEL_NOT_NAMED` envelope on stdout; if it names a file that cannot be **read**, it is `RK_INPUT_UNREADABLE`, the same code the JSON inputs beside it use. Two codes rather than one because there is no path to check when nothing was named, and a corrective that says "check the path" would send an agent to a file it never supplied. Both are stdout envelopes, not stderr lines — a refusal an agent cannot parse leaves it with an empty stream and no reason (G61; `UnreadableModelRefusalTest` sweeps every verb that reads a model). We deliberately keep the model **explicit per call** rather than an ambient "use this model" state — a fully-specified, stateless invocation is easier for an agent to generate and to reproduce/debug.

**The workspace root — `-w/--workspace`, one option for the whole CLI.** A multi-file model `include`s / type-def-imports other models *by id*, so every reference-resolving verb needs to know where those models live. There is **one** way to say it: an inherited, repeatable **`-w/--workspace <dir>`** option (sibling to `-m`), set once for every verb, with the **`DMTOOL_WORKSPACE` env var** as the set-once-per-shell-session fallback (ideal for an agent harness). The resolution precedence, one rule for the whole CLI (`WorkspaceOption`):

```
-w/--workspace  >  $DMTOOL_WORKSPACE  >  the model's own directory
```

So a workspace resolves with no per-verb flag once the root is set, and a self-contained model needs none of it. **There is deliberately no separate `--include-dir`** — "include" is a document-model concept (a *mounted* sub-model), but the resolver serves *every* reference (includes **and** type-def imports), so naming it after one kind would mislead and split the vocabulary. (The earlier `--include-dir` option was renamed to `-w/--workspace` and **removed outright** — it predates the first release, so no alias and no tombstone are needed; a stale caller gets the standard unknown-option error.) `-w/--workspace` stays **observable, not ambient**: it is in the manifest/`--help`, and an unresolved reference fails loudly naming the directories it searched (never a silent wrong-model). (Locked: `cli.WorkspaceOptionTest` for the precedence, `cli.WorkspaceRootTest` end to end.)

**Resolution is by the model's `header.id`, not its filename.** `ReferenceResolvers` walks the workspace, parses every `*.json` header, and indexes the `modelType=="document"` models by `id` — so a model file's **name is recognizability, not correctness**: `Person_DM.json`, `person.dm.json`, and `Person.json` all resolve identically if their header `id` matches the reference. The A12 Tools workspace **naming convention** is `<Name>_<TYPE>.json` — `_DM` for a document model, `_TDM` for a type-definition model (`_FM`/`_OM`/… are other model kinds dmtool doesn't author); a12-kernel-demo uses the lowercase `.dm.json`. Because the right suffix is "whatever the workspace already uses" (a context judgment, with `_DM` the fallback), the tool does **not** impose one — it's taught in the agent skill (`skill/SKILL.md`, "Naming model files"), and `group extract`'s auto-derived sub-model name is cosmetic (it resolves by id regardless).

### 3b. The result envelope <a id="result-envelope"></a>

Every invocation whose effective output kind is `RESULT_ENVELOPE`, and every `apply` op, emits the same shape. Resolve the effective kind from a matching `returns.views[]` selector first and the profile's primary `returns.kind` second. `RAW_JSON`, `RAW_TEXT`, and `EMPTY_STDOUT` bypass the envelope for an artifact/catalog value, a rendered view, or a file-only result; `manifest.operationalProfiles` and `schema <target> <op>` expose the discriminator before invocation. The envelope **embeds the existing diagnostics array verbatim** (§4); the new part is only the wrapper around it.

| field | meaning |
|---|---|
| `target`, `op` | echo the request — self-identifying, never mis-attributed |
| `outcome` | `applied · preview · refused · rejected · read · staged · completed · error` (the execution result class; `completed` = every `batch` child was dispatched; `error` = the **tool itself** failed) |
| `ok` | the operation succeeded (`outcome ∈ {applied, preview, read, staged}`; ordinary completed `batch` follows `data.allExitedZero`; completed observation mode means every child was dispatched and the artifact was written) |
| `valid` | *(consistency verdicts + a kernel rejection)* the **subject model** is kernel-valid — **distinct from `ok`**. Present only where a gate produced a verdict: `model/rule/workspace check`, and a `rejected` the kernel itself made. **Not** on a read, a runtime observation, or a mutation — a successful write asserts that the edit passed the gate, which is `ok`, not a standing claim about the model *(corrected 2026-08-01: this row read "and after a mutating op", which the typed algebra had already stopped doing)* |
| `verification` | *(every invocation that ran a gate — reads, verdicts, rejections **and writes**, plus a nested per-model verdict)* **which gate arbitrated this invocation** — `KERNEL_CONFIRMED` or `STRUCTURAL_ONLY`. Orthogonal to the verdict: it says who decided, never what they decided, so it stays present on a rejection and appears on a mutation *without* `valid`. Emitted only from a gate's own receipt, never from "a backend is installed" |
| `engine`, `engineVersion`, `toolVersion` | *(runtime observations — `model eval`, `model compute`, `rule eval`)* who executed the document: the evaluator, its version, and the dmtool version. A runtime observation carries **no** `valid`, because evaluating an instance produces fired rules and computed values, not a verdict about the model |
| `summary` | one human-readable line (the agent's quick read / log line) |
| `changed` | *(mutations)* the delta on success — e.g. `{added, kind}`, a refactor's rewritten refs |
| `data` | *(reads/queries)* the op's payload — explanation tree · model card · fired-list · … ; shape is op-specific (`schema <target> <op>`) |
| `diagnostics` | exactly `ValidationResult.toJson()` — an array of `Diagnostic` (§4) |
| `written`, `output` | whether the selected model or artifact destination was written, and where (`output` is absent when `written:false`) |

**The envelope identity is one value, not three adjacent strings (2026-08-02).** Every `ResultEnvelope` factory takes an opaque `ResultIdentity` followed by the summary; no raw `(target, op)` constructor or factory exists. An ordinary two-token verb derives the value from its injected live picocli leaf, so it never repeats its own command name. The command forms where picocli is not a total oracle use named sources: `meta` read/modify, `patterns` read/scaffold, `where-used read`, `batch run`, `apply run`, the terminal `model validate` step, and the no-parse exception fallback. An apply op gets its identity from the same closed `ApplyCommand.Op` that validates and dispatches it; an unknown selector is parsed once from the named JSON fields into the only other permitted source. `ResultIdentityContractTest` derives every ordinary route from the live command tree, reflection-enumerates the complete compiled public factory surface, locks the closed construction surface, executes every user-selectable exceptional route including known and unknown nested apply results, and unit-locks the defensive parsed/no-parse exception fallbacks. `ApplyVerbTest` executes the terminal `model validate` identity. `VerbDemonstrationTest` remains the independent wire-level backstop across the demonstration corpus.

**The `ok` / `valid` split fixes a real overload:** `ok` means "the tool did the job"; `valid` means "the model is kernel-valid." A `model check` that finds the model invalid is `ok:true, valid:false`: the tool worked, the model did not. **`apply` and `batch` return that same envelope and derive status by operation (2026-07-31; batch aggregate corrected 2026-08-03 and 2026-08-10).** Both used to print a bespoke shape with no `outcome` key, which made them the two verbs an agent had to learn a second output contract for and silently disabled `--text` for both. **`apply`** is `apply run`; its aggregate facts ride `data` (`ops`, `committed`, `failedAt`, `results[]` of per-op envelopes), and it derives its outcome from the all-or-nothing transaction. **`batch`** is `batch run`: `outcome:completed` and `data.dispatched:true` mean every child was attempted, while `data.allExitedZero` reports the independent child-exit aggregate. Ordinary batch derives outer `ok` and exit 0/1 from that value. Observation batch derives them from full dispatch plus artifact write. Each child's exact exit remains in its item. Batch is non-transactional, so an earlier successful write remains after a later failure.

**Exit codes** key off this: **0** = the selected operation succeeded, including an observation batch that fully dispatched and wrote its artifact even when `data.allExitedZero:false`; **1** = `rejected`, a validate/check with `valid:false`, or an ordinary completed batch with any nonzero child; **2** = `refused` (safe-gate) or a usage error; **3** = a consistency gate RAN and established no verdict; **70** = `error` (the tool itself failed). **3 exists because the other three cannot carry an inconclusive check** (added 2026-09-16 with `model check --engine=portable`, whose ordinary answer this is): 0 reads as a pass on a check that concluded nothing, 1 would claim the subject invalid when no engine said so — an over-report, the one direction a checker must never take — and 2 claims nothing ran, where in fact a full report was produced. Such an envelope is `ok:true` with **no `valid` key at all** and its `verification` naming what arbitrated. Everything else lives in the envelope. **An unknown subcommand is a usage error even with `--help` (2026-07-31):** picocli honours a help option during parsing and skips its unmatched-argument check when one fires, so a group plus a nonexistent verb plus `--help` used to print the group's help and exit 0 while the same line without `--help` correctly exited 2. An execution strategy now rethrows the suppressed `UnmatchedArgumentException`, so the rejection takes the same message, suggestions, and exit code as the no-`--help` case. `UnknownSubcommandHelpTest` locks this across every command group.

**No raw stack trace escapes a verb — one `Cli` seam classifies every throwable into a structured envelope.** picocli routes a thrown `Exception` to the execution-exception handler; an `Error` (e.g. GraalVM's `MissingReflectionRegistrationError` — a native reflection-metadata gap) propagates uncaught, so the seam *also* wraps `execute()` in a `catch (Throwable)`. Both funnels classify into three shapes, never a bare trace:

| Thrown | Meaning | Envelope | Exit |
|---|---|---|---|
| `ModelConsistencyException` | the model is invalid *as stored* (a strict `ofJson` at load) | `rejected` — the same `MVK_*` `diagnostics[]` a write-path rejection produces | 1 |
| `UnresolvedReferenceException` | an `include` / type-def import the workspace can't provide | `rejected` — corrective **`RK_UNRESOLVED_REFERENCE`** (`where.arg` = the reference; `fix` points at `-w`) | 1 |
| *any other throwable* | the **tool itself** failed (a bug, a native gap) — **not** an input rejection | `error` — **`RK_INTERNAL_ERROR`** (the real cause in `summary`); the full trace goes to **stderr**, stdout stays the machine-readable envelope | 70 |

The first two are **input** problems (exit 1, a clean corrective). The third is a tool failure (`outcome:error`, exit 70). A reader must preserve typed input and model rejections for the central mapper; `BaseCommand.withFailureContext` adds operation context to unexpected failures while retaining their cause. `InvalidModelLoadDiagnosticTest` locks strict readers and unresolved references; `LocalFailureBoundaryTest` locks unexpected NPE/IAE failures through the reader helper and the real CLI mapper. (`model check` remains tolerant by design.)

**The same contract binds the WRITE path (2026-08-01).** An edit verb must reach the same envelope for the same model — `field add` on a host whose `include` is unresolvable is the identical input problem as `model read` on it. Two things stood in the way, and neither was visible from the other:

- **Validation must preserve the failure's origin.** `ModelDocument.validate` and `EditSession.validate` no longer classify arbitrary runtime exceptions. The adapter translates A12's diagnosed `DocumentModelExpansionException`; malformed input and unresolved references retain their own types, and unrelated callback or serialization defects propagate. `ValidationFailureBoundaryTest` injects NPE/IAE resolver failures through both entry points, with valid includes and a genuine kernel expansion refusal as controls.
- **Edit commands handle the candidate's verdict and let other failures reach the central mapper.** Their local `ModelConsistencyException` catch emits the kernel rejection; the former generic `failEditGate` catches are removed. `EditGateRejectionTierTest` locks unresolved references without a verification claim and genuine kernel rejections with their evidence.
- **Corrected 2026-08-24: "they now call `failEditGate`" was true of the gates that had one, and four verbs did not.** Reported by an external consumer measuring the kernel's error-text grammar, who could reach a kernel verdict only by scraping stderr. The kernel runs a **second** checker over a persisted rule or computation — `RuleErrortextChecker`, over each localized message — and its rejection surfaces from the *re-bind*, which those four verbs had caught locally: `rule add` and `computation add` answered it with `fail("persisted … is invalid …")`, so a rule refused for its **error text** produced empty stdout at exit 2 while the same verb refused for its **condition** produced the envelope. `rule modify` and `computation modify` did publish an envelope, which is why they read as correct and were the harder half: they built a single hand-rolled `PRECHECK`-origin diagnostic wrapping the joined exception message and published it beside `verification: KERNEL_CONFIRMED` — a rulekit-origin finding attributed to a kernel arbitration, the kernel's per-problem detail collapsed to prose, and a corrective pointing at `rule check`, which cannot reach an error text at all. All four now take the same `emitKernelRejection` path as the other gates; publishing *an* envelope was never the contract, publishing **the gate's own verdict** is. `ErrorTextRejectionEnvelopeTest` locks the channel, the class, and the locus across all six sites — `rule add` (± `--dry-run`), `computation add`, `rule modify`, `computation modify`, `model check`, and the nested terminal-gate envelope in `apply` — and the two modify rows additionally assert `source: KERNEL`, which is the half that was wrong there rather than missing.

- **`source: KERNEL` IS attributable, and a `pre-checked` ledger row does not contradict it (2026-08-30).** An external consumer read a `MVK_ERROR_REFERENCE_TO_CALCULATED_FIELD` from `computation add --dry-run` carrying `source: KERNEL` + `verification: KERNEL_CONFIRMED`, and could not reconcile it with our own statement that the code is pre-checked in the library — if a client-side throw could publish a kernel basis, no diagnostic's attribution would be trustworthy. It cannot, and the enforcement is two links rather than the one first written here. **`diagnostics[].source`** — the field actually read — is `KERNEL` only via `Diagnostic.fromKernel`, reachable only from a kernel `Notification`. **The envelope's `verification`** comes from `RejectionBasis`, and the route in question uses `RejectionBasis.from(ConsistencyEvidence.of(check))`, which maps an EMPTY `ValidationResult.consistencyGate()` — deliberately empty when no gate ran — to `PreflightRejection`, i.e. no verification claim at all. (`RejectionBasis.kernel(...)` additionally refuses to construct without a gate receipt, locked by `ResultAlgebraTest`, but it is not on this route; citing it alone was a pointer that did not reach the invariant, corrected 2026-08-30.) The reconciliation is that the two refusals live on **different routes**: the pre-check is `Computation.Builder.build()`'s, and `computation add` never builds a typed `Computation` — it parses a `DraftComputation` of raw DSL text that `RuleValidator` serializes into DM-JSON for `checkConsistency`. That split is a property of the whole DSL-bearing verb family, and it is now stated where it can be found from either side: the [MVK-LEDGER](MVK-LEDGER.md)'s bucket note scopes `pre-checked` to the typed surface, and `ComputationSelfReadBasisTest` asserts both routes on one shape so a refactor that moved the builder onto the CLI path would fail rather than silently re-attribute.

**A write states its provenance too (2026-08-01).** The mutation families published no `verification` at all, so a write was the one route that ran the real oracle and then said nothing about it — and `--dry-run` was worse, because `written:false` reads as "nothing happened" when in fact everything was checked. `applied`/`preview`/`transaction` now take a `ConsistencyEvidence` like every read does, derived at each site from **the object that actually gated**: the `ModelDocument` or `EditSession` the verb edited, the re-bound `BoundModel` for the rule/computation verbs, `apply`'s session for its one terminal gate. The three genuinely ungated writes — `model expand` (an artifact render), `model normalize` (a pure reformat), `profile extract` (an extraction) — pass `none()` explicitly, so an absent key is a decision on the record. *Corrected 2026-08-01: this listed six, having classified `profile synthesize` and the JSON-Schema import/export pair by reading each command's own body, where the gate is invisible because it happens inside a helper that returns only a `String`. All three do gate and now carry real receipts.*

Two things had to be built for this to be honest rather than decorative. **The edit gates had to become witnesses**: `ModelDocument.consistencyGate()` / `EditSession.consistencyGate()` return the receipt of the gate that ran, and because both types are *mutable* — unlike every earlier witness — the receipt is kept against the exact DM-JSON that was gated and any later edit revokes it (API-FINDINGS 113, `EditGateReceiptTest`). And **the witness has to be the right document**: the four reference-rewriting refactors hold a pre-mutation `ModelDocument` for their safety gate *and* produce a rewritten one, so they name the rewritten one. A staged `apply` step deliberately carries nothing — its ops run through the session's no-per-op-gate text overloads, and the transaction owns the receipt for the state that is actually committed (`MutationEvidenceTest`).

**And it ends in one place (2026-08-01).** Thirty-three source sites, serving thirty-six editing routes, hand-wrote the same ending — preview under `--dry-run`, else resolve `--output`-or-in-place, `Files.writeString`, emit `applied` — differing only in the payload. Four reference-rewriting routes inherit one of those sites, which is why “source sites” and “routes” are different quantities. That fragment is now `BaseCommand.emitMutation` over a `ModelWrite` value object, which names the pieces at the call site instead of passing ten positional arguments (four `String`, two `boolean` — the swap-prone shape the style rules forbid, and the one whose `boolean valid` neighbour produced the fabricated verdicts in the first place). `--dry-run`/`--output` stay per-command options: hoisting them would reorder every verb's `--help`, which is a published-surface change with its own decision, not a side effect. The live command tree currently exposes thirty-nine `--dry-run` routes: those thirty-six shared-tail routes plus three reasoned custom tails (`group extract` writes two artifacts, `apply` is a transaction, and `patterns` has four routes of which two are a verdict rather than a write). `MutationTailSingleSourceTest` reconciles that live denominator with independently authored preview demonstrations, rich-input editors derived from the schema registry, and reasoned multi-mode/custom-tail dispositions. It then parses each reachable Java implementation and accepts only a command `call()` whose direct terminal statement returns `emitMutation(ModelWrite.of(...))`, or a custom-tail row. A comment, string, unused helper/construction, unreachable return, omitted `--dry-run`, or unclassified live route therefore fails; artifact writers without an authored preview remain outside this editing invariant rather than exemptions. ## 4. Diagnostics — reuse, extend, correct

The diagnostic is **already defined** — reuse it, don't reinvent it.

- **`Diagnostic`** (LSP-modelled): `severity` (ERROR/WARNING/INFO) · `source` (PRECHECK/KERNEL/LINT/ENVIRONMENT/INTERNAL — the five `diagnostic.schema.json` admits; rulekit carries a sixth, `PORTABLE_CHECKER`, which only the library gate emits and no CLI verb can produce) · `code` (optional; `MVK_*` kernel / `RK_*` rulekit-or-structure) · `summary` · `where` · `fix` (optional) · `explain` (optional).
- **`ValidationResult{ok, diagnostics[]}`** with `toJson()` — the agent-parseable array (empty optionals omitted) that the envelope's `diagnostics` *is*.
- **`DiagnosticEnricher`** — the **catalog-join**: an `MVK_*` code is matched against the catalog entries that *document* it, and a curated `fix`/`explain` is attached **only once one owning operator is established** (the ownership invariant below — a code is not owned by one operator, so matching the code is the lookup, never the attribution). The fix database is the N7-locked catalog — one source, so kernel diagnostics and authoring examples never drift. A **structural-code fallback** (`StructuralKernelFix`) covers placement/iteration-scope codes that no *operator* documents — `MVK_ERROR_FIELD_NOT_IN_RULEGROUP` (the error-field-placement law, KERNEL-FINDINGS §9) and `MVK_NEG_CONDITION_IN_ITERATION` (the negative-in-iteration guard): each gets a corrective `fix` instead of a bare kernel message, locked by tests that trigger the real codes. The same `StructuralKernelFix` is the single source for the **`diagnostics <code>` lookup** of these codes — a probe (P-mini-1) found an agent that hit one naturally tries `diagnostics <code>`, which used to dead-end ("see `operators`/`explain`") since they have no operator home; now it resolves (meaning + fix). The bare `diagnostics` list stays `RK_*`-only; operator-owned `MVK_*` codes still route to `operators`/`explain`. Where a **typed AST** exists (the built-rule path, converted reads), `lint.SpanResolver` refines the join further: it classifies the pinned comparison's actual operands and selects the operand-matched **corrective** from the catalog (`MVK_INVALID_TYPE_FOR_COMPARISON`'s date-vs-ISO-literal trigger gets the date fix, string-vs-string the `==`/`!=` fix — the D1 class), falling back to the code-level fix when no corrective matches or no AST exists ([CATALOG-SPEC §6](CATALOG-SPEC.md); the text-path boundary is FEATURE-GAPS G30). **Ownership invariant (2026-07-31):** an operator-specific `fix` *or* `explain` is emitted only once exactly ONE owning operator is established — structured `where.operator` first, then **the operand the kernel delimited in its message** (`KernelMessageOperands`; never a localized sentence pattern, and never the message's fixed prose — the kernel's own boilerplate names operators that had nothing to do with the rejection). Resolution runs against the whole catalog, so where the message names an operator that documents no example for this code, that operator is still identified (its meaning rides; no curated fix does) and the documenters are positively *excluded* rather than hedged. Unresolved ownership yields a code-level corrective enumerating the candidates and **no `explain` at all**; whichever later stage does establish the owner (`lint.SpanResolver` on the typed AST, `interp.TextConditionCorrective` on the text path) recomputes **both** fields.

The shared unexpected-token corrective distinguishes fixed operator spellings from enumerated connective variants such as `And`/`and`/`AND`; it does not prescribe PascalCase for every keyword ([KF76](KERNEL-FINDINGS.md#kf76)). `DiagnosticEnricherTest` locks the hint and `CheckVerbTest` verifies its kernel-backed CLI projection. `CheckerCorrectiveProjectionGuardTest` keeps the portable checker's generated corrective synchronized with that same owner.

Two extensions this redesign adds (minimal, deliberate):

1. **`Where` gains `path` and `arg`.** Today `Where` only points at a `rule` (+`operator`/`span`). Structure ops and arg-level errors have no locus — so `Where` grows a **model-element `path`** (any field/group/typedef/include) and an optional input **`arg`/token**, keeping `rule`/`operator`/`span`.
2. **An `RK_*` curated-fix source.** `DiagnosticEnricher` only fixes catalog `MVK_*` codes; the new structure/refusal codes (`RK_NO_SUCH_GROUP`, the safe-delete `RK_REFERENCED`, …) get a curated-fix table so **every error-severity code carries a `fix`** — CI-guarded.

**The corrective bar — detect → locate → repair.** A diagnostic that only says *what's wrong* lets the agent report failure; one that says *how to fix it* lets the agent close the loop. The `fix` is the highest-value field (an applicable DSL/path replacement or a discovery command, e.g. *"list paths with `field read`"*). Discipline: a "did-you-mean" only appears above an edit-distance threshold — a wrong suggestion is worse than none. A structured machine-applicable `suggest` field is **withheld until a consumer needs it** (an apply-the-fix harness) — the consumer-exists discipline; until then a correction rides the human-readable `fix`.

Worked shapes (the real `Diagnostic` fields, inside the envelope):

```jsonc
// kernel rejection — MVK_* verbatim, located, with a catalog-joined fix:
{ "severity":"ERROR", "source":"KERNEL", "code":"MVK_UNKNOWN_FIELD",
  "summary":"/Order/Quanity is not a field in the model",
  "where": { "rule":"/Order/MinQuantity", "operator":"…", "span":[12,26] },
  "fix":"replace /Order/Quanity with /Order/Quantity",
  "explain":"…" }

// structure precheck — the Where extension (path/arg) + an RK_* curated fix:
{ "severity":"ERROR", "source":"PRECHECK", "code":"RK_NO_SUCH_GROUP",
  "summary":"no group /Order/Lines in the model",
  "where": { "path":"/Order/Lines", "arg":"--group" },
  "fix":"list groups with `dmtool -m order.dm.json group read`" }
```

## 5. Verb surface — target × op <a id="verb-surface"></a>

Model-bound operations use `dmtool -m <model> <target> <op> [args]`. Family (modelkit ⟂ rulekit) is a **grouping in `--help`/manifest**, not a command level — the real two axes (kind × op) *are* the two command levels. Artifact and cross-model operations can replace the `-m` input with their own source: **`model new`** creates a model from scratch; **`profile synthesize --input <profile.json>`** creates a model from a profile; and the `workspace` verbs scan a directory of models. Their exact inputs remain derived in help/manifest and the rows below.

`model diff` binds both states independently. In two-file mode, repeatable `--base-workspace` and `--head-workspace` roots distinguish snapshots that contain different versions of the same referenced model id; without them, shared `-w` applies, then each model's folder. In `--since` mode, the base model and its dependencies come from the Git ref while the head resolves from the working tree.

**`model check --engine` selects the checking engine, and nothing else ever does (2026-09-16, F1-a).** `kernel` is the default and is the consistency authority; `portable` runs the bundled Kernel-free checker ([`:consistency`](CONSISTENCY-API.md)) instead. The two answer **different contracts**, which is why this is a selector and not an optimization: the portable checker cannot report a model VALID at all, so on a model A12 accepts it answers INCONCLUSIVE at exit 3, and its findings ride `data` in [the checker's own published report shape](CONSISTENCY-API.md) — `status`, `complete`, `findings`, `diagnostics`, `checksCompleted`, `gaps` — rather than being folded into the envelope's `diagnostics`, which would re-create the finding/diagnostic conflation that shape exists to prevent. The receipt names both `engineRequested` and `engineExecuted` on all three request shapes, the default included, because an absent `--engine` is itself a request for the kernel. **There is no fallback in either direction and no `auto`:** availability, discovery order, coverage, completeness and exceptions must never choose an engine, an INCONCLUSIVE portable answer is not an invitation to consult the Kernel, and a Kernel failure never becomes a portable answer. The enforcement is structural rather than documentary — `ConsistencyEvidence.requestedBy` refuses to build an envelope whose executed engine is not the requested one, so a substitution cannot be published even when both engines would return the same verdict (locked by `PortableEngineSelectionTest`, whose controls rest on the engines visibly disagreeing; `PortableEngineVersionIsDerivedGuardTest` keeps the reported engine version derived from the engine rather than written down here).

**`rule check --engine portable` answers about the CANDIDATE, which needs one thing `model check` does not (2026-09-16, F1-b).** A candidate is spliced into the model before a whole-model checker can see it — the same `RuleValidator.inject` step the Kernel arm already runs, so both engines judge identical bytes — and the checker's report is therefore about the whole spliced model. Publishing that as the candidate's verdict would reject a sound candidate whenever the model already carried an ERROR of its own, which is a verdict about another declaration delivered as a verdict about this one: an **over-rejection**, the one direction a checker must never take. So the portable arm publishes an ATTRIBUTION instead, `data` carrying the checker's own edit shape — `status` (the EDIT's, not the model's), `introduced`, `resolved`, `gaps`, and both nested `baseline` and `edited` reports. `introduced` decides the verdict; the baseline's findings are a **disclosure**, because an author checking a candidate against an already-broken model needs to know that, and they never decide the candidate's status. Attribution is by set difference rather than by each finding's `at` path because it assumes strictly less — the path form additionally needs every candidate-caused finding to land under the candidate, which nothing has measured ([the record](archived/PORTABLE-CONSISTENCY-IMPLEMENTATION-PLAN.md#f1b-attribution) carries the 2×2 and the Kernel control). **It refuses rather than guesses when the baseline could not be analysed at all**, since with no baseline every finding would read as introduced and a pre-existing defect would be blamed on the candidate; the refusal is stated as a gap. Locked by `PortableCandidateCheckTest`, whose load-bearing control is a sound candidate against a broken model.

Portable checks preserve the measured rule-message group diagnostics, including read siblings, intermediate enclosing groups, field short-name ambiguity, parent-walk outcomes, keyword/name decisions, signed retired offsets and reached-fault ordering documented in [KF214](KERNEL-FINDINGS.md#kf214). The enforcing checker and its kernel/JVM/Node locks are named in [CONSISTENCY-API](CONSISTENCY-API.md); the existing candidate attribution and engine receipt apply to these findings too.

`model check` refuses malformed DM-JSON before consistency checking: `outcome: refused`, exit 2, and a `PRECHECK` diagnostic coded `RK_MODEL_INPUT_INVALID`, without `valid` or `verification`. Truncated JSON and wrong value types belong here. A member kernel 31.1.1 does not know is read past, and a rule, computation or sort entry missing the element it names is read and then cannot be built, so `model check` reports it `valid: false` at exit 1 with the kernel's "could not build this model" diagnostic ([KF654](KERNEL-FINDINGS.md#kf654)). Unexpected failures reaching the CLI exception boundary retain exit 70. The shared model-load boundary also serves model readers and edit gates; `ModelInputFailureTest` and `MalformedModelPublicContractTest` exercise these distinctions.

`group modify --index-field <fieldName>` preserves a relative field reference whose final short name names a direct child, on both repeatable and non-repeatable groups; the consistency gate validates resolution. `GroupModifyVerbTest.preservesAnAdmittedRelativeIndexField` locks the `../Code` spelling when both parent and child declare `Code`. Row sort declarations still require repeatability. Enforcement: `ModelDocument.setIndexField` and `GroupBuilder.toDraft`; locks: `NonRepeatingIndexFieldCliTest`, `IndexFieldTest`, and `GroupSortFieldTest`.

**`model expand`, `model seed`, and every interpreter runtime verb share one portable workspace boundary.** The Java CLI supplies exact ids through the public `CompletionStage` provider projection; commonMain discovers only the entry closure, mounts includes, imports effective typedefs, normalizes element ids to name paths, and MOVE-remaps included references. `model expand` returns those self-contained bytes before `ModelLoader`, so conversion accepts Kernel-legal evaluator-unsupported configuration. Runtime verbs pass the same bytes through the strict public expanded-input preparation gate before evaluation. A genuinely unmappable reference, ambiguity, cycle, limit failure, or surviving residue becomes a structured corrective refusal; no caller silently under-reads a raw model (IF145/IF146). The published JVM/Jackson `ModelReader` remains the model-index/metadata implementation and parity comparator, not a second dmtool runtime assembler.

**`--lang` (format) vs `--condition-language` (config) are two knobs, not one (2026-07-10 — Set-G T6 design call).** They look like the same vocabulary but are deliberately distinct concepts, so they keep distinct names *and* distinct value domains — a shared name would falsely imply one knob and collide their value spaces. `rule/computation format --lang <EN\|DE>` is an **ephemeral render toggle**: re-emit *this* call's canonical text in EN or DE kernel keywords (the two languages the operator catalog carries), changing nothing in the model. `config modify --condition-language <locale>` sets a **persistent model setting** (`modelInfo.conditionLanguage`, a locale code like `en_US`/`de_DE`). Reconciliation was to sharpen both descriptions to state the distinction (and each self-corrects a wrong-flag guess), **not** to merge them: `format --lang de_DE` (a locale where a keyword-language belongs) and `config modify --lang EN` (a render enum where a persistent locale belongs) would both be category errors.

**Read is uniform — no specifier lists, a specifier reads one (2026-06-19).** Every `read` obeys one rule: **`<target> read` with no argument reads everything in scope; with a path/id it reads that one.** For the element kinds (`rule`/`computation`/`field`/`group`) "everything" is a lean **name-index** (`data.<plural>` = the full-name list + `count`) — the navigation handle to then `<target> read <name>`; for `include`/`typedef` it is the declared list, and one is read by `<alias>`/`<id>`; for the singular `config`/`model`, "everything" is the one thing (`model read` is the whole-model rules+computations read). The index is deliberately lean — distinct from `model read` (full DSL of everything) and `export` (a takeaway artifact), so the three stay non-overlapping. This closed the gap that made an agent reach for `rule read` to enumerate and hit a dead-end (probe finding P2); the **served schemas are now guarded** so a flag named in `schema <target> <op>` must be a real option of the verb (`SchemaFlagParityTest`), and the verb-ref guard validates flags too (`CommandReferencesResolveTest`). **A read of a *missing* target is a structured `refused` envelope** — the matching `RK_NO_SUCH_*` code, a `where.path`, and a corrective `fix` (e.g. *list them with `<target> read` — no arg*) — across every read verb (field/group/rule/computation/typedef), never a plain-text stderr line, so a bad path is as machine-readable and recoverable as any other refusal (was a probe DX gap — `field read` of a bad path printed prose + exit 2; locked by `ReadMissingTargetEnvelopeTest`). **And a read/locator verb handed the WRONG locator FLAG self-corrects:** these verbs locate by a *positional* `<…PathInModel>`/`<…Id>`, but an agent carrying `rule check`'s `--field` over (or guessing `--path`) used to get a bare picocli "Unknown option". The parse-error handler now names the positional form (*"… locates its target by a POSITIONAL `<fieldPathInModel>`, not a flag — pass it directly"*) for any locator-positional verb; a **spec-input verb** (`<spec.json>`/`<ops.json>` — `rule add`, `field add`, `apply`, …) handed an unknown `--flag` is instead **redirected to its schema** (*"… takes a JSON spec `<rule-spec.json>` as its input — see `schema rule add` for the fields it expects"*), since its fields live INSIDE the spec, not as flags (the eval finding: an agent reused `rule check`'s `--field`/`--condition` on `rule add`). Both close the cross-verb inconsistency (probe 06-rr; locked by `CliHelpTest`).

**The locator contract — the canonical positional, plus the target-noun flag as an alias (2026-06-28).** Self-correction *mopped up* each wrong-flag instance; the contract makes the agent's habit actually *work*, fixing the class. The rule an agent learns once and applies everywhere: **the canonical locator is the positional `<path>`/`<id>`; every entity read verb also accepts the flag named after its own target noun** — `field read --field`, `rule read --rule`, `computation read --computation`, `group read --group`, `typedef read --typedef` (also `--id`), `include read --include` (also `--reference`), `criterion read --criterion`. `field read` keeps its `--group`+`--name` decomposition; the positional wins if both are given. **The whole family is covered — no half-fix:** omitting one (e.g. `computation read` while `rule read` has it) would just move the inconsistency down a level, so every read verb with a locator carries its noun flag. `where-used`'s target is polymorphic, so its canonical `--entity` *plus* the noun flags (`--field`/`--group`/`--rule`/…) all bind the entity path — an agent looking up "what uses this field" can type `--field`. This is why an agent's `--field` (learned on the most-used verb, `rule check`) no longer mis-fires on `field read`/`where-used`: it's a real alias now, not just a corrected error. The self-correction stays for a *genuinely* unknown flag (`--path`, `--xyz`). Locked family-wide by `LocatorContractTest` (each `--<noun>` alias resolves identically to the positional) + the updated `CliHelpTest`. **One `--field` is NOT a locator and stays that way:** `group multiselect --field` *names the new selection field* (a create-verb parameter, like `field add --name`), not "locate an existing field" — contextually unambiguous from its own `--help`, so it's left as-is; the contract is about the read/locate verbs, not create verbs.
**Every model-mutating library operation has a `dmtool` path, and the parity is guarded rather than reviewed.** `CliCoverageParityTest` fails the build when an `EditSession`/`ModelDocument` mutator has no verb reaching it, so the verb surface cannot regrow a coverage hole as the library gains capability.


**A read never publishes a condition the kernel would refuse (the grouping backstop, 2026-09-22).** `rule read` and `computation read` report `converted:false` with a `reason` whenever the typed readback would lose a `{ … }` group the kernel decided on, and `rule read` adds the authored `canonicalText` (a computation's stored text is A12's joined form, which truncates at a `$` correlation, so publishing it as canonical would hand back something no one wrote). The loss is A12's, not the converter's — a group is recorded only on a composite operand, so `{Today} == Today` and `Today == Today` reach us as one parse tree while the checker admits the first and refuses the second ([KF445](KERNEL-FINDINGS.md#kf445)) — and the visible symptom was a successful read handing back an illegal replacement for a legal rule, reported by an external consumer against 0.13.0. A dropped group is a suspicion rather than a verdict, since the renderer drops one its own precedence rules make redundant: on the rule path the kernel arbitrates and only a rendering it refuses degrades the read, so a redundant group still reads typed. The computation path degrades on the suspicion alone, because the joined text A12 returns for a computation is itself lossy and cannot serve as the same candidate.

### The check / eval / compute verb scheme — verb = operation, target = scope (2026-06-28)

The validation/execution verbs follow one coherent rule an agent can learn once: **the verb names the operation, the target names the scope.** Three operations, each mapping one-to-one onto a kernel runtime primitive — so the surface mirrors the kernel exactly (KERNEL-FINDINGS "validateFull does NOT run computations"):

| operation (verb) | kernel primitive | what it does | rule scope | model scope | workspace scope |
|---|---|---|---|---|---|
| **`check`** | `checkConsistency` | **static** validation of *definitions* (no instance) — rule conditions AND computation expressions | `rule check` (a candidate) | `model check` | `workspace check` |
| **`eval`** | `validateFull` | **runtime** evaluation of *conditions* on a `--instance` — which rules fire | `rule eval` (stored path or non-stored `--condition` + `--field`) | `model eval` | — |
| **`compute`** | `compute` | **runtime** execution of *computations* on a `--instance` — each computed value, in the form `compute-doc.schema.json` states (CG7) | — | `model compute` | — |

**`check` judges under a UTC JVM default, whatever the machine's zone.** A12's `checkConsistency` judges a DateTime constant against the JVM default zone rather than the model's declared one ([KF231](KERNEL-FINDINGS.md#kf231)), so a spring-forward gap label under a Europe/Berlin model was refused on a Berlin machine and admitted on a UTC one. The kernel oracle swaps the default to UTC for the check and restores it, which matches the portable checker and the kernel probe. *(Enforced by `KernelModelPreparation.underJudgingZone`; locked by `adapter … KernelOracleJudgingZoneTest`.)*

**Why `check`, not `validate`, for the static op:** it maps to the kernel's own `checkConsistency`, and it keeps "validate" from colliding with the kernel's *runtime* `validateFull` — which this CLI exposes as **`eval`**. So the words stay unambiguous: `check` = static (definitions), `eval` = runtime (conditions), `compute` = runtime (computations). (The pre-v0.1.0 spellings `model validate`/`rule test`/`workspace validate` were renamed to this scheme; clean break, no caller to migrate.)

**Two integration facts the scheme makes precise** (both in the runtime-flow note above): (1) `eval`/`compute` are *separate* kernel primitives — `model eval` runs the **form-engine flow** (compute → apply → validate) by **default** so a computed field is filled before validation, with `--no-computations` for the bare `validateFull`; (2) *every computation is also an implicit validation rule*, so a computed field's stored value is checked by `eval` even though its *value* is `compute`'s job.

**A SUPPRESSED verdict recognizes a formal error anywhere inside a referenced GROUP (2026-08-14).** The three-way verdict exists so a rule the kernel never evaluated is not reported as a pass. For a group operand the kernel's reference set holds the **group** path while a formal-check message names the **field** whose stored value would not parse, so an exact comparison could never match and the verdict fell through to `PASSED` — a wrong answer in the one path whose purpose is not to mislead (`CG14`). The scan now tests containment at a path-segment boundary and reports the offending field. Locked by `adapter.laws.RuleTestGroupOperandSuppressionTest`, whose three controls keep it from degenerating into "suppressed whenever any formal error exists": a genuine below-the-bar pass stays `PASSED`, the rule still `FIRED`s over the group operand, and a malformed field in the string-prefix sibling `/Claim/AssessmentNotes` does not suppress a rule reading `/Claim/Assessment`.

**`rule eval` accepts one stored rule or one non-stored candidate.** The stored form locates a `<rulePathInModel>`. The candidate form omits that positional and supplies `--condition <DSL>` plus an absolute `--field <fieldPathInModel>`; `--code` is optional. The candidate is constructed in memory, evaluated through the same focused fired/passed/suppressed/unsupported path, and never written to the model. The two forms are mutually exclusive, and an unpaired candidate flag is refused before evaluation.

**A fired `rule eval` publishes the firing message's own channels (2026-08-04).** Beyond `rule`/`fired`/`verdict`, a `fired` verdict carries `code`, `field`, `severity`, `type`, `message`, `referenced` and — for an omission — `fillToFix`: the **same keys with the same meanings** as one `model eval` `messages[]` entry, so a single message parser reads both, and the same per-address form contract applies (canonical A12 when the address names one cell, the house form otherwise). The reason is that `type` is a **semantic observable, not presentation**: for `FieldValuesNotUnique` it is the only thing separating a filtered from an unfiltered firing on identical data (a reached `Having` on the starred operand escalates the firing to `OMISSION_ERROR` where the unfiltered form is `VALUE_ERROR`), so a candidate that reported only the verdict forced the measurement through *persisting* the rule and running `model eval` — the model-dirtying cycle candidate mode exists to remove. Both locators return the identical shape, published as `schema rule eval`'s `dataSchema` (`rule-eval.schema.json`) and locked against real output by `DataSchemaConformanceTest`, against the kernel's own message by `RuleEvalMessageProjectionTest`, and address-form-wise by `PublishedPointerCanonicalTest`. Scope difference from `model eval`, stated because it is easy to misread as a loss: this verb reports the **first** firing, so a rule violating several rows of its iteration scope yields one message here where `model eval` yields one per row.

**The grid's empty cells are already covered — no real capability gap** (an earlier draft mis-called these "gaps"): a candidate computation's static pre-flight is **`computation add --dry-run`** (verified: it previews a valid candidate `outcome:preview, written:false` and rejects an invalid one with diagnostics, never persisting — the spec-based twin of `rule check`; a *flag*-based `computation check` wouldn't fit since a computation is a spec-structured table, not one condition+field+code). A single computation's runtime value is in **`model compute`**'s output (it reports every computed field; the one you want is in the list). So there's no missing verb to add — the asymmetry vs `rule` is ergonomic (computations pre-flight via `add --dry-run`, not a dedicated flag verb), not a capability hole.

**Every runtime verb refuses a condition or operation that names an undeclared entity (2026-08-04).** `rule eval`, `model eval`, and `model compute` check, before evaluating, that each entity a rule condition or computation operation names is declared by the model, and refuse with exit 2 and one **`RK_UNDECLARED_ENTITY_REFERENCE`** diagnostic *per* offending reference (so all of them are repairable in one pass). A model carrying such a reference is invalid — the kernel's gate rejects it as `MVK_INVALID_ENTITY` — so this is not a stricter client-side bar but the same verdict reached without a kernel, which is what lets it hold on the native binary.

The refusal exists because there is no honest answer to give, and the old answers were confident and mutually contradictory: a **presence** predicate read the absent cell as empty and the rule **FIRED** (`type:"OMISSION_ERROR"` with `referenced:[]` — a message naming operands it never found), a **starred aggregate** collapsed to an empty row domain and the rule **PASSED**, and a **value** position, having no empty reading, died as an untyped `computation failed:` line with no envelope. Two of those exit 0 with opposite polarity, so no consumer-side heuristic can recover the truth. This is the sibling of `--field`'s existing `RK_NO_SUCH_FIELD` refusal — the same class of mistake arriving through a different flag — and it is deliberately **not** the lenient `data.unsupported` channel (G29), which means "the engine cannot evaluate this legal construct" and would blame the engine for the model's defect while still exiting 0.

**Stored rules and computations are checked, not just `--condition` candidates.** The report scoped this to candidate mode on the reasoning that every dmtool write path gates references before storing — true, and irrelevant to a model that arrived from anywhere else; an injected stored rule reproduced the identical false FIRED. The check is therefore at the evaluation entry.

**The gate speaks for exactly what the verb evaluates — no more, no less.** Both bounds are load-bearing: reporting less would let a reached reference through and put the verb back to answering about nothing, while reporting more would refuse a call that is sound as issued *and*, on a focused route, force every rule's AST, defeating the interpreter's parse-only-what-you-touch preparation that keeps a single-rule call cheap. Per route:

| route | in scope | why |
|---|---|---|
| `model eval` (± `--no-computations`) | every stored rule **and** every computation | validation evaluates the implicit computation-validation rules (`[F] != <operation>`, one per computation) whichever way the flag is set, so the operation is reached either way — the flag governs compute-and-apply, not validation's rule set |
| `model eval --condition` | the candidate **plus** the whole model | the candidate is appended to the model and evaluated alongside every stored rule |
| `rule eval <rulePathInModel>` / `--condition` | that one rule, **plus** the computations | focused does not mean "the condition only": the default form-engine flow applies the computations before validating |
| …the same **with `--no-computations`** | that one rule, alone | the compute step is skipped and `testRule`/`evalCandidate` never touch the implicit rules, so no computation is reached |
| `model compute` | the computations alone | this verb validates nothing, so a stored rule's bad reference cannot reach its answer |

The mechanism is the interpreter's own (`DmInterpreter.undeclaredReferences`, kernel-free) and the reference is bound by the **model's** rules before it is tested — declaring-group precedence, then the `fieldRefByShortNameAllowed` model-wide short name — so no legal reference form becomes unauthorable; a starred operand is tested with its wildcard markers already resolved away. Detail, the over-rejection controls, and the measurement that corrected the whole-model row: [INTERPRETER-FINDINGS IF248](INTERPRETER-FINDINGS.md#if248).

**Computation alternative tolerance is first-class metadata.** Each computation-spec alternative may carry `toleranceRangeOp`, restricted by the published schema to `DiffersWithToleranceRange1|2|5|10`. It stays attached to that tier through add/apply, read, modify, diff, explain, and model report; omission means strict inequality. A present malformed value is rejected rather than silently treated as omission.

**A computation's rounding mode is A12's `roundingMode`, spelled as A12 stores it.** A computation-spec may carry `roundingMode`, restricted by the published schema to `Exact|RoundUp|RoundDown` — A12's internal values, so a constant name such as `ROUND_UP` is refused. `Exact` is the default and is never stored, because A12's serializer omits it; `computation read`, `computation explain` and `model report` likewise show the key only for `RoundUp`/`RoundDown`, and the model diff reports it as the computation's `roundingMode` aspect. All four read it as the element's own member, as A12 stores it beside the formula, so an Opaque formula shows it too. A non-`Exact` mode needs a `toleranceRangeOp` on every alternative, and the kernel refuses the pair with `MVK_ERROR_WRONG_ROUNDING_MODE` ([KF297](KERNEL-FINDINGS.md#kf297)). `model compute` writes the value rounded to a whole number in the mode's direction, and floors an `Exact` banded alternative to the target's digits; `model eval` compares the entered value with the operation unrounded ([KF474](KERNEL-FINDINGS.md#kf474)). `computation modify` is a whole re-expression, so a spec that omits the mode makes the computation exact again.

**Computation warning suppression uses A12's exact owner shape.** A computation-spec may carry `errorCodesToSuppress:["MVK_INVALID_COMPARE_DEC_PLACES"]`, matching `IComputation.errorCodesToSuppress` without a parallel flag or encoding. The list is preserved through standalone and `apply` add/modify, persisted as the same DM-JSON array, and exposed by read, explain, re-expression diff, and model report. `computation modify` is a whole re-expression: omitting the property removes the list. The published `computation-add` schema restricts the domain to the kernel-measured supported code; an unsupported value is a write-safe `RK_INVALID_VALUE` rejection. It also bounds the list to one entry, because A12 renders it into a one-code pragma: a second entry, even the supported code again, is A12's own `MVK_UNEXPECTED_TOKEN`, also write-safe ([KF298](KERNEL-FINDINGS.md#kf298)). Rule and computation specs have separate `rule-add`/`computation-add` schemas, so a key owned by the other target is `RK_UNKNOWN_ARG`, never valid-but-ignored.

**A field's value type is one vocabulary — `kind` with `ValueKind` names, the kernel discriminator never leaks (2026-06-22).** Wherever a field (or type-def) value type is reported — `field read`/`typedef read`, the `apply` `field read` op, **and** the write echoes (`field`/`typedef` `add`/`modify`'s `changed.kind`, the `apply` ops) — it is the key **`kind`** carrying a clean `ValueKind` name (`NUMBER`, `STRING`, `DATE`, `DATE_TIME`, `TIME`, `DATE_FRAGMENT`, `DATE_RANGE`, `ENUMERATION`, `BOOLEAN`, `CONFIRM`, `CUSTOM`, `UNKNOWN`) — **the same vocabulary `model describe` reports and `field add`'s `kind` key accepts**, so a read round-trips back into a write. The kernel's internal storage discriminator (`NumberType`, `TypeDefType`, …) is an implementation detail that **never reaches a user surface**. A **typedef-typed** field reports its **resolved underlying** kind (matching `model describe`, which classifies the `getEffectiveType()`) plus the `typedef` id as the reference signal and `resolvedType` for the referenced config — so you see both what it effectively holds and that it's typed by reference. This closed `07-vocab` (`field read` said `type: "NumberType"` while `describe` said `kind: "NUMBER"` for the same field — a broken round-trip: a token you couldn't feed back to `--kind`). One resolver single-sources it: `ValueKind.fromKernelType(String)` (the read-side inverse of the kernel discriminator) behind `ModelDocument.fieldKind`/`typeDefinitionKind`, used by every report site (read-back semantics on the write echoes, so a non-canonical input spelling like `ENUM` comes back canonical as `ENUMERATION`). The read output shape is published: `schema field read` / `schema typedef read` serve `field-read.schema.json` / `typedef-read.schema.json` (the `kind` vocabulary stated there), CI-locked against real output by `DataSchemaConformanceTest`; the unified value is locked by `FieldVerbTest`/`TypedefVerbTest` (read ↔ describe agreement) and `ValueKindTest`.

**Target-first only — the migration is complete (2026-06-19).** The CLI surface is exclusively target-first (`<target> <op>`, the table above). The earlier flat verbs — `check`, `validate`, `read`, `explain`, `add`, `modify`, `remove`, `describe`, `eval-doc`, `compute-doc`, `add-field`/`-group`/`-typedef`/`-include` — were **hidden** aliases kept through the migration; they predate v0.1.0 (never shipped non-hidden), and have now been **removed** (their canonical spellings are the target-first verbs above). Their test coverage migrated onto the canonical surface in the same change.

**`doc` → `model` is a clean rename.** The whole-model target was once `doc`, but in A12 "document" is the runtime **instance** (the data), so naming the *schema* target `doc` was ambiguous. The target was renamed to **`model`** (the schema); the runtime instance is supplied to `model eval`/`model compute`/`rule eval` via the **`--instance`** flag (itself renamed from `--doc` for the same reason — "document" reads as the instance, so an agent kept reaching for `--instance`; the old `--doc`/`--document`/`--data` guesses now self-correct to `--instance`). The old `doc` target was **removed outright** (the rename predates v0.1.0, so it never shipped — no caller to migrate); `dmtool doc <op>` simply errors with picocli's unknown-subcommand message. Rationale: "document"/instance and "model"/schema must not share a word.

**Parallel validation message multiplicity.** `model eval` retains every emitted message occurrence. Numeric index declarations with different minimum fractional digits may generate two tokens (`5`, `5.00`) that resolve to the same matched rows; both occurrences remain in `data.messages`, while `data.fired` contains distinct codes. [KF114](KERNEL-FINDINGS.md#kf114) records the kernel rule; `DmtoolPublicContractTest.packagedNumericParallelValidationRetainsRenderedTokenMultiplicity` locks the packaged projection.

**Nested first-filled polarity.** Full `model eval` preserves the empty-prefix provenance of a nested `FirstFilledValue` scan, including an omitted inner group below an earlier parent. Moving the empty branch after the selected value changes OMISSION to VALUE without changing the selected value. [KF126](KERNEL-FINDINGS.md#kf126) owns the measured scope; `DmtoolPublicContractTest.packagedFirstFilledRetainsNestedPrefixPolarity` locks the packaged result.

**`--instance` is A12's canonical Document JSON — one codec, both directions (2026-07-28, breaking in 0.9.2).** The document instance the runtime verbs read, and the one `model seed` writes, is **the A12 kernel's own document shape** (the format spec: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) "The canonical Document JSON and `DocumentPointer` string"): a root group name is a **top-level key** — there is no wrapper — the tree mirrors the model, a repeating group is an **array** whose index is the repetition (`{}` for an unfilled row), an omitted entity is a **missing key**, `null` is a field that is *present with no value*, and a field's value is **native JSON for NUMBER and BOOLEAN/CONFIRM**, a model-format string for the date family, the S-value for an enumeration. `schema model eval` serves it as `docInput`; `schema model seed` serves the same `document-instance.schema.json` as its artifact output schema.

**`model seed` is the model-discovery authoring surface.** Its default seed `0` materializes every declared group and field, including non-repeatable fieldless containers, with one row per repeatable group; editable source fields receive constraint-aware values while computation-owned targets remain present-empty for the engine to fill. `--seed`, `--rows`, and `--rows-default` vary source values or row counts. It is a best-effort model-shaped candidate, not a proof that arbitrary cross-field rules pass. This is the same `SeedGenerator` preset the public interpreter exposes as `PreparedModel.documents.seedDocument()`. The top-level `profile` target does not overlap: it extracts or synthesizes an identifier-free **model performance workload**, never a Document instance.

Both directions run through the **single** implementation of that shape, the interpreter's `ModelDef.readDocumentJson` / `Document.toDocumentJson` codec, so `seed` cannot drift from what `eval` reads. That is not tidiness: dmtool previously walked the tree itself, which matched the shape but **not** A12's value-normalizing ingress *behaviour* (CLAUDE.md "…and adopt A12's JSON I/O BEHAVIOUR exactly, not just its shape") and so reported formal errors on documents A12 accepts silently — `1e5` drew `zahlHatUngueltigeZeichen`, `"+5"` `zahlMitPlus`, `"007"` `zahlHatFuehrendeNullen`, against a kernel that stores `100000`/`5`/`7` and reports nothing (`DocumentInstanceIngressTest` locks each row end-to-end).

The codec also matches A12's **parse configuration**, so a hand-maintained instance file **may carry `//` and `/* */` comments** — A12 builds both of its mappers with `ALLOW_COMMENTS` — while a **trailing comma stays a parse error**, which A12 also refuses (IF228; `DocumentInstanceIngressTest` locks the commented document end-to-end). **The same holds for a `-m` DM-JSON model**, on every model verb: A12's model mapper accepts comments too, so a commented model reads, describes, and passes `model check` exactly as its uncommented twin (`CommentedModelSourceTest`).

The canonical reader discards unknown keys and wrong-shaped entities, preserving valid siblings; `{}` occupies a row and field `null` remains present-empty. The retired `{"fields": {…}}` wrapper is an unknown key and is discarded, never unwrapped. Syntax/root faults, Boolean/null scalar IDs, an array holding anything but objects at a member of the root or of a group row ([KF664](KERNEL-FINDINGS.md#kf664)), and decode resource ceilings are fatal on the plain-text `fail` channel (exit 2). `A12JsonIngressDiffTest` measures the conversion against the owner serializer; `DmtoolPublicContractTest.packagedRuntimeVerbsShareCanonicalJsonRowsAndRefusals` locks model eval/compute and stored/candidate rule eval through the packaged launcher. See [IF389](INTERPRETER-FINDINGS.md#if389).

**Runtime validation runs computations first — the form-engine flow (the `model eval` / `rule eval` default).** The kernel keeps validation and computation as *separate* primitives: `validateFull` does **not** compute computed fields first (KERNEL-FINDINGS "validateFull does NOT run computations"); the running application orchestrates **compute → apply computed values → validate**. So a *bare* `validateFull` over an instance whose computed fields are empty **false-fires** `mandatoryField` on a required-but-computed field, and a rule over a computed field reads it empty. To match the app, the runtime-validate verbs **compose by default**:

- **`model eval` / `rule eval`** run **compute → apply → validate** — the computation fills a computed field before the required/condition checks run. This is the realistic "would this document be valid in the running app?" answer.
- **`--no-computations`** drops to the bare `validateFull` (the kernel primitive): validate the document's **stored** values as-is. Use it to validate a computed field's *stored* value against its computation (the kernel's "every computation is also a validation rule"), or to validate externally-produced data without recomputing.
- **`model compute`** is unchanged — the pure `compute` (what each field computes to), reported read-only.

The apply-computed-back step is a first-class library primitive too — `DmInterpreter.applyComputations(doc)` (the interpreter, native-safe) / `KernelAdapter.evaluateApplied` (the JVM-only kernel-adapter API path) — mirroring the kernel's `IDocumentComputationResult.applyTo` (apply the changed values, clear the errored/cleared ones). No verb ever mutates the `--instance` file; the flow is in-memory. (Detail: KERNEL-FINDINGS "validateFull does NOT run computations"; INTERPRETER-FINDINGS IF45.)

**Runtime output addresses cells by canonical A12 pointer, and names the two identities separately (2026-08-01).** Every pointer dmtool publishes at runtime — `model compute`'s `computed[]`, `model eval`'s `messages[].field`/`referenced`/`fillToFix` — is A12's canonical spelling: **no leading slash, and `[1]` omitted**, so a first-row cell reads `Order/Lines/LineTotal` and row 2 reads `Order/Lines[2]/LineTotal`. A computed result carries **`field`** (the canonical *instance* pointer — which cell) and **`declaration`** (the model declaration path — which computation), because those are two different facts and collapsing them is what lost row identity: a repeatable computed field used to emit N items with an identical path, distinguishable only by list position. Summaries count declarations from the declaration identity and instances from the result items, never by stripping indices off a display string.

A consequence that reads as a gap and is not one: since canonical A12 omits `[1]`, the **first row's** instance pointer and its declaration coincide as strings. An absent bracket *means* repetition 1 — which is exactly why an omitted index can never be read as "all rows", the rule the `--relevant` refusal below enforces.

**`schema result` states the convention, because that is where a message parser meets it (2026-08-04).** The per-key contracts live in the payload schemas, but a consumer parsing one envelope saw a coordinate-free `field` beside a fully-coordinated `referenced` with no signal in front of it — and read the pair as *two conventions on two channels*, which makes a coordinate-free address look like a declaration address. It is one contract decided **per address**: that message's error field hit a single cell (canonical) while its operand was a whole column (no A12 string, so the house form). So the envelope schema now carries the cross-cutting statement — the two address kinds, that a leading slash marks a declaration path while a canonical cell address has none and omits `[1]`, the two `format` marks and what each promises, and that the decision is per address so one message may legitimately show both spellings. `MessageAddressSpellingTest` locks both halves: the live mixed-spelling message *and* its exact-operand control (the case that falsifies the per-channel reading), plus that `schema result` still names the discriminator.

**Input stays permissive.** One shared parser accepts A12's legal non-canonical spellings (a leading `/`, an explicit `[1]`) and normalizes them, matching A12's own reader — so every pointer-taking input keeps working and only *output* is canonicalized. The conversion goes through the type at a single CLI projection seam (`cli.interp.A12Pointers`), never by string surgery. **What A12 canonicalizes depends on the channel.** A *computed cell* address is an exact `DocumentPointer` — every level resolved to one row — and always renders canonically. A *message* address is A12's `PartiallyKnownDocumentMultiPointer`, which may carry a wildcard above the last part, the `-5` of a level that matched no row, or the `-6` A12 leaves on a joined level ([KF607](KERNEL-FINDINGS.md#kf607)), and **A12 defines no pointer string for that type at all**. So `field`, `referenced` and `fillToFix` are canonical A12 exactly when the address names one cell, and otherwise pass through as the interpreter's house form — the tool does not invent a canonical spelling for a value A12 has none for. Their schema mark is therefore `a12-message-address`, not `a12-pointer`: a weaker keyword for a weaker promise, so a consumer is not told the value is always paste-compatible. **That decision reads the typed pointer, never the text.** The interpreter hands the CLI A12's `PartiallyKnownDocumentMultiPointer`, and the classification is taken from it — because the house form `/Plan[1]/Demand` parses perfectly well as the *exact* pointer `Plan[1]/Demand`, so a try-parse fallback would silently publish an unresolved address as a resolved one. See [KERNEL-FINDINGS kf171](KERNEL-FINDINGS.md#kf171).

**The interpreter library publishes the pointer VALUE; the house form is a tool projection of it.** `ValidationFinding.errorPath`, `referenced` and `fillToFix` are `A12PartiallyKnownMultiPointer`s on JVM/JS/TS, and the conformance corpus and `:adapter` differential render `/Order[1]/Items[2]/Count` from them as their *shared comparison key* — the differential renders the kernel's pointer through the same spelling, so both sides compare. That key is not an A12 serialization and is deliberately absent from the interpreter's public ABI. dmtool owns its fallback rendering for unresolved message addresses; the corpus and browser qualification own their comparison projection. `PublishedPointerCanonicalTest` walks every schema-marked address key across the demonstrated surface and asserts the published form, in the contract's own terms rather than by re-running the converter — holding an `a12-pointer` key to the full canonical contract and an `a12-message-address` key to the two forms its schema actually admits.

**Partial validation is a projection of `model eval` (G43).** `model eval --relevant <json>` routes the prepared document through `DmInterpreter.validatePart` instead of full validation, exposing the kernel-matched wizard-page mechanism without adding a verb or a second evaluator. The value is a JSON array of field/group instance paths. **`[0]` or `[*]` means `ALL_SEMANTIC`**; `[n]` selects one 1-based row: `["/Order/Name","/Order/Lines[2]/Quantity"]`. **An omitted index on a REPEATABLE segment is refused (breaking, 2026-08-01)** — it used to mean ALL here and means repetition 1 in A12, the same spelling with opposite scope, so it is no longer guessed: the refusal names the segment and both explicit forms, and an existing selection that relied on omission migrates deliberately rather than having its validation quietly narrowed to row 1 with a clean pass as the symptom. On a **non-repeatable** segment there is one instance, so an omitted index is unambiguous and stays legal. Ordinary rules run only when their error field is relevant — compared at the repetition levels the rule's *iteration* bound, so a rule reporting into a repeatable group it does not iterate runs when any row of that group is relevant and reports at row 1 (IF268); non-relevant operands stay UNKNOWN under the ordinary three-valued logic; a relevant group covers its descendants; global fields are auto-relevant. A clean, empty parent group is provably empty when descendant selections jointly cover every declared finite repetition combination and every descendant field, independently of held rows (`PartialParentGroupCoverageDiffTest`). Starred group absence also needs every missing declared position covered; a positive relevant row remains decisive. A keyed lower star binds the matched parent, or needs parent wildcard coverage on a no-match (`PartialStarredGroupCoverageDiffTest`). Extent knowledge depends on the operator family. Starred value lists and `NumberOfValueInFields` accept concrete selectors covering every declared slot: rows 1 and 2 suffice at capacity 2, but not capacity 3, regardless of held rows (`PartialDeclaredListExtentDiffTest`). The families also differ when a `[*]` mixes with concrete selections: an **all-rows aggregate** (`Sum`/`MaxValue`/…) needs every retained identifier to use `[*]` after group expansion and wildcard-redundancy removal, so a `[*]` establishes its extent only when it encompasses the concrete siblings rather than surviving beside them; a **`No`/values-side-`NotAll` value-list quantifier** also accepts one covering `[*]`, and concrete siblings beside it do not suppress it (KERNEL-SEMANTICS §12; SPEC-2026-07-22-09/IF42/IF262/IF264). Unknown paths, malformed brackets, negative indices, an omitted index on a repeatable segment, and an index attached to a non-repeatable segment all fail before evaluation, with a nearest-path hint where available. Structural over-repetition findings do not by themselves make ancestors erroneous for partial group counts; ordinary in-capacity invalid values still can (`OverRepetitionAncestorCacheDiffTest` and `DmtoolPublicContractTest.packagedPartialCountsIgnoreExcessDescendantCacheErrors`). A nonempty selection also reports structural over-repetition outside the selected fields, including present null/empty occurrences; an empty selection emits no structural findings (`DmtoolPublicContractTest.packagedPartialValidationReportsEmptyExcessOccurrences`). The result carries `data.validationMode:"partial"`; its `fired`/`messages` shape otherwise stays identical to full `model eval`. `schema model eval` and the option help are the self-describing contract.

For parallel rules, partial validation compresses error selectors: differing coordinates become wildcards. A concrete joined error coordinate suppresses a rule with ordinary outer/frame iteration; conflicting joined selections can restore dispatch without widening operand relevance. A fixed-root join with no ordinary frame visits all keys once admitted. Both validation modes share the ordinary frame domain. See [KF544](KERNEL-FINDINGS.md#kf544); `PartialValidationCliTest.parallelDispatchCompressesSelectorsWithoutChangingTheirInputSyntax` locks the CLI boundary. Selector syntax and output shape are unchanged.

Message addresses retain association identity separately from value availability: a duplicate key or full-call invalid singleton index default may yield a concrete address while its value remains unreadable. Duplicate selected/parallel addresses use the interpreter's [first-admitted policy](INTERPRETER-FINDINGS.md#if376); generated uniqueness findings still retain their physical cells. [KF545](KERNEL-FINDINGS.md#kf545) and the linked CLI control lock this distinction.


**The evaluation instant: `--clock <instant>` (2026-10-14).** `model eval`, `rule eval` and `model compute` read `Today` and `Now` from one instant: the current one by default, as A12 samples a calendar in the model's zone when `DocumentProcessingConfig.currentDateForTest` is unset (`RuntimeController`), or the instant `--clock` pins, which is that slot. The value is an ISO-8601 instant with a zone offset (`2026-10-14T10:00:00Z`, `2026-10-14T12:00:00+02:00`); the model's `timeZone` decides its day and wall time, and a non-zero millisecond remainder survives as `Now`'s identity ([KF82](KERNEL-FINDINGS.md#kf82)); a finer fraction is dropped, since `currentDateForTest` holds milliseconds. An offset-less date-time, and an instant beyond the millisecond range, are refused as `RK_INVALID_VALUE` rather than read in a guessed zone or failing the run. `EvalClockTest` locks the zone reading across Berlin midnight on all three verbs, the default against the run's own date, the millisecond identity, and both refusals.

**Custom field types & custom conditions — the runtime verbs' support knobs.** Project code (`ICustomFieldType.validate` / `ICustomCondition.check`) lives in the deploying app, not the model JSON. A library consumer registers an in-process implementation; native `dmtool` can host project JavaScript through the Node bridge below. An absent or unusable implementation stays visible through the unsupported/strict-custom contract rather than being mistaken for a clean result.

- **Visible-ignore: `data.unsupported` (G29).** A construct the engine can't evaluate — a `CustomCondition` with no registered impl, or a custom-typed cell with no `--predefined-types` entry — is reported in **`data.unsupported`** (`[{name, reason}]`; `name` is the rule's slash-path or the cell's instance pointer), present only when non-empty. It is **never silently absent from `fired`**, which would read as a clean pass — the dangerous case for a skipped *condition* rule (a whole rule that never fired). `rule eval` reports the same as a fourth verdict, **`unsupported`** (not a crash, not a false `passed`).
- **`--strict-custom` (G29).** Flips the lenient default: when `data.unsupported` is non-empty, the verb **refuses** (`outcome:refused`, exit 2), retaining the observed data and runtime provenance so missing or unusable handlers can be inspected. Interpreter-only.
- **`--predefined-types <file>` (G30).** A custom-typed field (`CustomFieldType{name}`) is reported `unsupported` and silently NOT validated unless its type is supplied. This flag supplies a declarative registry — `{ "<TypeName>": { "minLength"?, "maxLength"?, "pattern"? } }`, **merged over the built-ins** (e.g. `EMail`; a consumer entry overrides a same-named built-in) — so a *format-constraint* custom type is enforced: a value that fails the length/pattern fires `customFieldTypeInvalid`. Same vocabulary as a `field add` `string` config. Genuinely *imperative* custom types (checksums — IBAN mod-97, ISIN/Luhn) are out of this declarative model — for those, see `--custom-conditions-js` below / the JS escape.
- **`--custom-conditions-js <dir>` / `--custom-field-types-js <dir>` (G31).** The escape to JS for imperative custom logic the declarative forms cannot express. A condition `<Name>.js` exports `check(data, relevantEntities, formallyIncorrectFields, errorField)`. A field type exports `validate(value, context)`, where `context` is `{ locale, minLength, maxLength, isDisplayValue }`; omitted declaration bounds arrive as the kernel-effective `1` and `999`, and normal document validation passes stored mode `false`. The result is either a Boolean or the single object vocabulary `{ valid, errorKey?, errorMessage? }`; an object must contain Boolean `valid`, optional members must be strings, and aliases such as `{ ok, code, message }` are rejected. `false` without a project key uses `customFieldTypeInvalid`; `errorKey` is preserved; the exact reserved `testIDNummer` key reports without suppressing reads ([KF541](KERNEL-FINDINGS.md#kf541)), while ordinary rejecting keys suppress, and every `$<fieldName>$` in `errorMessage` is replaced with the localized field identifier. Malformed results, a missing `node`, worker failure, and project exceptions fail inside the custom-support boundary and enter the existing visible unsupported/`--strict-custom` path. Both families share one lazily spawned persistent Node worker with one NDJSON request/response per check; the worker exits on stdin EOF or idle timeout and is backstopped by a JVM shutdown hook. IF152 locks the signature, context, strict result vocabulary, and callback cardinality.
- **Custom-condition input contract (IF187).** `data` is the document-wide exact-pointer view. `relevantEntities` is `null` for full validation and the exact external relevant set for partial validation. `formallyIncorrectFields` is the separate exact address set produced by that call's formal pass; partial validation excludes cells it did not formally check rather than reclassifying non-relevance as invalidity. `errorField` is the current repeated rule error pointer. The callback owns every hidden dependency: it must return `false` when a field it needs is absent from the relevant set or present in the formal-invalid set. The evaluator does not infer those dependencies or suppress the callback before it can decide. A custom leaf can be reached on a blank row through an eligible `Or`; the common `FieldFilled(error) And CustomCondition X` form remains the authoring guard when blank-row invocation is unwanted.
- **Computation uses the same registries.** `model compute` checks stored source values and each reached CUSTOM target in one execution. It retains support observations from that pass; strict mode includes missing target handlers and callback failures. An unsupported construct reached during computation stops the execution and preserves earlier completed results and support observations. It does not run stored validation rules or custom conditions. A collision in the final computation diagnostic addresses fails with exit 2 and no stdout payload; `model eval` uses the same boundary before validation. `--no-computations` retains the ordinary validation findings (`ComputationDiagnosticAssemblyCliTest`).
- **These options refine the interpreter — the sole runtime eval engine.** `--predefined-types` / `--strict-custom` / `--custom-conditions-js` / `--custom-field-types-js` tune how the interpreter handles custom constructs; there is no separate eval engine to conflict with.

**The spec-vs-flags asymmetry is inherent and stated, not hidden.** A rule/computation is a rich JSON envelope (condition, code, messages, severity), so `rule add` takes a `--spec <file>`; a field/group is a few scalars, so `field add` takes `--group/--name/--kind` flags. Consistency lives at the **selector** (`<target> <op>`), uniform across the lifecycle (`field add` ↔ `field remove`, `rule add` ↔ `rule modify`); the *payload* differs by necessity.

**The canonical metadata writer (G45).** `meta <ref>` is the single post-creation route for labels, annotations, and internal/external descriptions across fields, groups, rules, computations, and type definitions. Its transactional peer is `{target:"meta",op:"modify",ref,…}` in `apply`; `ref` is intentionally polymorphic because it accepts either a name-path or a type-definition id. Target-specific `field`/`group`/`rule modify` keep only their semantic properties, and removed standalone flags/spec keys and apply keys return a corrective that points to `dmtool meta <ref> …`. The choice is semantic, not cosmetic: `meta --label` merges locales (where the old target-specific route replaced the entire map) and `meta` has complete removal peers. Target-specific reads keep their common-metadata projections because they are complete element summaries, while `schema meta` publishes the complete common-metadata payload. A label write to a rule, computation, or type definition is a structured `RK_LABEL_NOT_SUPPORTED` refusal; an empty transactional metadata op is refused before the atomic terminal gate. Creation-time metadata stays on add specs because there is no element to address until creation, and the model header remains a `config modify` carve-out. This is a deliberate breaking CLI consolidation: no retired write alias survives.

**Write convention.** Every mutating op writes the model **in place** by default, `-o <file>` redirects, `--dry-run` previews (read-only).

**The workspace roles lint (`workspace roles <dir>` — R3/R4).** An A12 model carries a `roles` **header** annotation (a comma-separated list — multi-role is the norm) naming who may access it; a workspace declares those roles in a roles file and its users (+ the roles each holds) in a users file. This verb is the **cross-file linkage** the kernel never makes: it resolves the whole **RBAC triangle** — every model's gating roles *and* every user's authorities against the roles file — and reports the inconsistencies. It is a **read** that is **purely advisory and never blocking** — access-control config is often a dev seed or owned by an external IdP, so a finding must *inform* a BA / agent, never *stop* their model work. Every finding is a WARNING (or a softer INFO), **never an error, and the verb always exits 0** (`outcome:read`, `valid:true`). The `data` payload (`workspace-roles.schema`) surfaces the resolved `rolesFile`/`usersFile`, the `definedRoles` (+ access rights), the `users` (+ authorities), each model's gating `roles`, the `findings`, and `warnings`/`infos` counts.

- **Discovery** locates the roles file under the workspace root in convention order — `auth/roles.yaml` (the SME convention, a sibling of `models/`), then the project-template `import/auth/roles.yaml`, then the Preview-App `user/access-rights.yaml`; the users file likewise — `auth/users.yaml` (a list) or an `auth/users/` directory of per-user files, plus the `import/auth/…` nesting. **`--roles <file>`** / **`--users <file>`** override discovery. Models are scanned **recursively** (a workspace is a tree; roles gate it workspace-wide — unlike `list`/`graph`, which mimic `ls`).
- **Findings (all WARNING except `ORPHAN_ROLE` which is INFO — the SME *enforces* the roles ones as errors; this tool deliberately only *advises*).** Roles edge: the flagship **`UNDEFINED_ROLE`** — a model gates to a role the file doesn't declare, which **even the A12 SME doesn't catch** (it permits "additional roles … beyond" the file); **`MISSING_ROLE_ASSIGNMENT`** (a roles file is present but a model carries no `roles` annotation); **`NO_ROLES_FILE`** (a model declares roles but no roles file was found); **`MULTIPLE_ROLES_FILES`** (more than one roles file; which governs is ambiguous, so name-checking is skipped). Users edge (R4): **`UNDEFINED_AUTHORITY`** — a user holds an authority the roles file doesn't declare (the `UNDEFINED_ROLE` twin on the membership side); **`UNREACHABLE_MODEL`** — a model gates to roles no user holds (nobody can open it); and the lone INFO **`ORPHAN_ROLE`** — a declared role held by no user and gating no model (a dead definition). Each finding carries both a `message` (the problem) **and a `fix`** (the concrete remedy) — parity with the `{meaning, fix}` shape of the `RK_*` diagnostic catalog, so a finding is actionable. There is deliberately **no ERROR severity**. The lint is a **modelkit structure-consistency check** (`modelkit.WorkspaceRoles` over `RolesFile`/`UsersFile`), a sibling of the kernel structural checks — *not* a rule `MVK_*`. (Locked: `modelkit.WorkspaceRolesTest` + `modelkit.UsersFileTest` + `cli.workspace.WorkspaceRolesCommandTest`.)
- **Code discoverability (the three classes).** A `data.findings[]` code (e.g. `UNDEFINED_ROLE`) is documented in this verb's output schema (`schema workspace roles`) — *not* in `dmtool diagnostics`, which is the `RK_*`-envelope catalog. The `diagnostics <code>` dead-end routes all three classes: `RK_*` here, `MVK_*` kernel codes → `operators`/`explain`, and a verb's `data.findings[]` code → `schema <target> <op>`.

### 5a. Schema discovery & the op-record

`schema <X>` accepts both forms of the address published by the tool:

- `schema result` / `schema diagnostic`: the cross-cutting structures (raw JSON Schema).
- bare `schema`: the orientation, including the structures, batch frames, `schema <target> <op>` form, and self-contained guarantee below.
- `schema <target> <op>` or `schema "<target> <op>"`: that op's **directional contract**, `{input?, docInput?, returns:"result"|"artifact", data?, dataSchema?, artifact?}` (CG6). The scalar form is the direct consumption path for each manifest `schema` / `operationalSchema` value; the tokenized form is convenient at a shell. Both resolve every live pointer and return byte-identical content. Unknown-address diagnostics retain the original argv boundaries. The contract states what the verb *consumes*, including a rich JSON spec file (`input`) and/or a `--instance` document instance (`docInput`), and the shape it *returns*. A read's `data` payload is described by `dataSchema` where one is published; an explicitly registered artifact operation describes its artifact kind, default destination, an output `schema` where one exists, and an `-o` receipt branch only where the verb actually has that option. Flag-only ops carry no input schema because their params are in the manifest.

**Every served document is self-contained — the sources single-source, the emission bundles (2026-08-05).** A schema addresses a sibling by its `$id` instead of restating its shape: `result`'s `diagnostics` item points at `diagnostic`, and `patterns`' scaffold branch at the three `add` verbs' input schemas. That single-sourcing stays, because a restatement conforms to its meta-schema, executes nothing, and drifts invisibly — exactly how the `eval-doc` reference shipped. But it must cost the *consumer* nothing, so **emission embeds each referent under `$defs` as a JSON Schema 2020-12 compound schema document**: the embedded resource keeps its `$id`, so the existing absolute `$ref` resolves against it with no rewriting and no second call. The distinction that makes this safe is **authored vs. derived duplication** — a copy in the source files drifts; a copy recomputed at serve time from the one source cannot. `patterns`' own authored `$defs` is merged, never clobbered, and the inner `$schema` is dropped (all 32 documents share one dialect, and a differing `$schema` on an embedded resource is the corner of the spec implementations support least).

*Measured, not assumed:* handed only `schema result`, a 2020-12 validator with an **empty** registry (no network, no pre-registration) accepts the document, validates real envelopes, and **rejects a malformed `diagnostics` entry with 11 errors** — so the embedded definition is enforced, not inert. Strip the bundle and the same validator raises `Unresolvable` rather than warning. This retires the earlier open question of whether a consumer would hard-fail or degrade: it hard-fails. Relatedly, a published `$id` is an *identifier*, not a locator — fetching one returns **HTTP 404** — so do not "fix" that by publishing these documents at that URL; it would add a second, drift-prone channel for a shape the tool already serves. Bare `schema` states the guarantee rather than listing fetches to make (an earlier revision listed them, which bundling made actively wrong).

Three guards, three claims: `SchemaResourceSurfaceTest.everyEmittedDocumentResolvesItsOwnRefs` asserts no emitted `$ref` points outside the output it arrived in (checking the referent is present *anywhere* in that output, since a document served under a contract key carries its `$defs` with it); `…everyCrossDocumentRefTargetsASchemaTheToolServes` forbids referencing a document no invocation serves, with positive controls per nesting shape since the join passes vacuously on a scan that finds nothing; and `SchemaVerbTest.theOrientationPublishesTheSelfContainedGuarantee` pins the promise into the output and forbids the stale fetch instruction.

The `manifest` is the index that makes assembly *copy, not infer*: every verb entry carries `target`, `op`, its params (each with the CLI `flag` **and** the op-record `key` = the `--`-stripped name an `apply` op uses), a scalar `schema` pointer for every directional contract (result-envelope operations and explicitly registered artifact operations such as `profile synthesize` and `model seed`), and a worked **`example` `{intent, command}`** — a read-only invocation the agent can run to see the verb *in action* (CI-executed by `VerbDemonstrationTest`). Pass the scalar pointer directly as one argument to `schema`; splitting it into target/op tokens is equivalent but not required. Verbs in the reasoned `SchemaCommand.CONTRACT_EXEMPT` ledger carry no pointer. The root carries `resultSchema:"result"` and the global `-m`. So an agent builds any call, single or batched, straight from the manifest. (`schema add` is gone: it splits into `schema rule add` / `schema computation add`.)

## 6. Op taxonomy — Local / Cascading / Refactor <a id="op-taxonomy"></a>

Classify every op by **blast radius** — this is the standing rule for adding ops, CRUD or not:

| class | ops | semantics | mechanism |
|---|---|---|---|
| **Local** | add · read · modify · remove-leaf | one element only | plain surgery, gate at end |
| **Cascading** | remove-referenced | element + *deletes* dependents | the `where-used` refuse-or-`--cascade` gate |
| **Refactor** | **rename** (field/group/rule/typedef — **reference-rewriting** ✅; **model** id — single-model, G27; **include** alias — structural repoint, no AST rewrite, G37) · **move** (field/group — **reference-rewriting** ✅) · **extract/inline typedef** ✅ · **extract group→include** + **inline include** ✅ | rename/move rewrite the element **and every reference** atomically → valid→valid (move also relocates the node to a new parent); extract/inline lift or fold a subtree at a same-name mount (paths preserved); typedef ops repoint structural pointers; **model rename** changes the header id and refuses (via the `-w` workspace scan) when a sibling includes the old id — the cross-model cascade is out of scope | the **safety gate** (✅, this §) for collisions/preconditions + the kernel's `MoveSupportDM` reference-rewriter (`adapter.ReferenceRewriter`) |

### When a refactoring earns a verb — the bar (standing principle, consult before proposing one)

A refactoring deserves a first-class `dmtool` verb **only when an agent composing it from existing primitives** (`read` + `add`/`remove`/`modify`) would unreliably get it right or safe. It earns a verb if it trips **any** of these, strongest first:

1. **Reference fan-out / integrity** — it touches things *beyond* the element itself (every referrer). `field`/`group` rename·move rewrite N references; a hand-rolling agent *will* miss some. ← the strongest justifier, and why those are verbs.
2. **Non-trivial mechanical correctness** — relative-path rebasing, id re-prefixing: error-prone reasoning agents botch.
3. **Atomicity / the gate** — naive composition can leave a broken or *lossy* intermediate (`rule remove` then a failing `rule add` = the rule is gone); a gated verb is atomic, valid→valid.

It is **overkill** — leave it to the agent composing primitives — when none trips: a pure single-element edit `modify` already covers, a cosmetic reordering (DM child-order is largely non-semantic), or a rare/judgment-heavy transform ("extract a shared sub-condition", "merge/split rules"). The bias is the project thesis — **self-explaining primitives that compose correctly > more verbs**: invest in the schema + diagnostics so the agent composes the edit right, and reserve verbs for the fan-out cases where hand-composition reliably fails.

Worked application — **`rule`/`computation move`:** *no* fan-out (nothing references a rule), but **yes** on #2 (rebasing the `../` operands + `errorEntityRelPath`) and #3 (remove+add is non-atomic/lossy) → a *medium* case: legitimate but optional, **deferred** — the mini-probe (P-mini-1) found a cold agent places the error field correctly *at add-time*, so there is no pull yet; re-open if a probe shows agents botch repositioning (FEATURE-GAPS §4).

**Candidate verdicts (the bar applied — a decision record, not a roadmap):**

| candidate | trips the bar? | verdict |
|---|---|---|
| `field`/`group`/`rule`/`typedef rename`, `field`/`group move`, `group extract` / `include inline`, `model rename` | ✓ (#1 fan-out + #2 rebasing + #3 atomic) | **shipped** — the bar's positive cases |
| `rule`/`computation move` (reposition to another valid group) | partial (#2 + #3; **no** #1) | **deferred** — medium; no probe pull (above) |
| reorder fields/groups within a parent | ✗ — DM child-order is largely non-semantic; no fan-out/rebasing/loss | **non-goal** (cosmetic) |
| merge / split a rule | ✗ — rare + judgment-heavy; the agent composes `read`+`add`+`remove` | **non-goal** |
| extract a shared sub-condition into a reusable rule | ✗ — no real fan-out; rare | **non-goal** |
| copy / duplicate a field/group/rule | ✗ — a *new* element has no referrers to rewrite; `read`+`add` suffices | **non-goal** |

### The refactor safety gate — *check before you change* (standing principle, every refactor, now and future)

Every refactor — and every cascading op — is **precondition-checked and refusable**. The author stays in control; the tool never best-effort-rewrites and never silently degrades. The shape is always the same:

1. **Check** the *specific* refactor's safety preconditions against *this* model, **before** touching anything.
2. **Refuse if unsafe** — `outcome:refused`, exit 2, **no mutation** — with rich, corrective diagnostics (detect → locate → repair, §4): *what* is unsafe, *where*, and *how* to resolve it.
3. **Only when every precondition holds, mutate** (then the usual single end-gate).

This generalizes the safe-delete gate below to the whole Refactor class. Each refactor declares its own preconditions and the diagnostic it refuses with:

| refactor | unsafe precondition → refuse with a named diagnostic |
|---|---|
| **move** (group-operand membership) | a move has no reference TEXT to rewrite when the reader reaches the element through an ancestor GROUP — the kernel expands such an operand to every field below it, so moving a field out silently removes it from that operand while every condition string stays valid and the model stays kernel-valid. Measured before the fix: `applied`, `verification: KERNEL_CONFIRMED`, `rewroteReferences: []`, no diagnostics, while a rule's `AllFieldsFilled(<group>)` lost a member (`CG18`). Now an **advisory** (`RK_MOVE_CHANGES_GROUP_EXPANSION`, WARNING) naming the rules and computations whose expansion changed — deliberately **not** a refusal, since the move is legal and usually intended; blocking it would stop ordinary work, and what the author needs is to be told which rules changed meaning. Computed by differencing reachability at the old and new paths, so a move WITHIN one group operand's scope emits nothing. *(A separate claim, `ReferenceRewriter`'s "a `*`-reference a rename would dangle must be refused", was measured FALSE and deleted: the starred reference is carried across.)* |
| **remove** (referenced) | anything still **reads** the target → refuse, list referrers (`RK_REFERENCED`), or proceed only on explicit `--cascade`. **Reading includes reach through a group operand**, in both directions: a rule naming a field's ancestor GROUP reads that field, and a rule naming a group's ancestor reaches into that group. That case is the one the terminal kernel check cannot catch — the rule still names a group that still exists, so the model stays valid and the delete succeeds silently (`CG13`; measured returning `outcome: applied`, `verification: KERNEL_CONFIRMED`, no diagnostics). The refusal names the group responsible, since otherwise the author hunts for a rule mentioning a field no rule mentions. Shared by the standalone verbs and the `apply` ops through `FieldRemoval.plan`/`GroupRemoval.plan`, because `apply`'s field-remove op previously ran **no gate at all** while its group-remove sibling enforced one |
| **rename** | the target element does not exist → refuse (`RK_NO_SUCH_FIELD` / `RK_NO_SUCH_GROUP` / `RK_NO_SUCH_RULE`, located at the path); a name **collision** with an existing sibling → refuse (`RK_NAME_EXISTS`). References — including starred and `Opaque`-to-rulekit conditions — are **rewritten**, not refused (the kernel's lenient `MoveSupportDM`) |
| **move** | the source element does not exist → refuse (`RK_NO_SUCH_FIELD` / `RK_NO_SUCH_GROUP`); the destination parent group does not exist → refuse (`RK_NO_SUCH_GROUP`); a group moved **into itself or its own subtree** → refuse (`RK_MOVE_INTO_SELF` — it would orphan the subtree); the destination is **already** the element's current parent → refuse with a **no-op-aware** `RK_NAME_EXISTS` ("'X' is already directly under 'G' — nothing to move", so the request-already-satisfied case isn't mis-read as a sibling-name clash — probe 09); the destination already has a *different* child of that name → refuse (`RK_NAME_EXISTS`). When safe: relocate the node (re-prefixing its + descendants' ids) and **rewrite every reference** to the new path (same `MoveSupportDM` engine as rename), then re-validate. **Cross-boundary moves (KERNEL-FINDINGS §9):** a field move into/out of a repeatable group is fine as long as it doesn't *split* a bound rule/computation across two cardinalities — the kernel scopes a rule by the repeatable fields it *references*, not by node placement, so the rewritten relative path reaches up/down correctly. The one case that's refused is a genuine **cross-cardinality split** (the moved field's bound rule/computation also references another field still inside the repeatable): the kernel rejects it (`MVK_ERROR_FIELD_NOT_IN_RULEGROUP`, enriched with a corrective `fix` — see the `StructuralKernelFix` note above) and the move mutates nothing. A mechanical "co-move the bound rule/computation" is a **non-goal** — it can't fix the split (that needs a logic rewrite, e.g. an aggregate), and every valid move already succeeds without it (the §6 candidate-verdicts table; FEATURE-GAPS §4). |
| **extract group → include** | a rule **or computation** inside the subtree references **outside** it (`RK_OUTWARD_REFERENCE`, names the offending elements); the group is **repeatable** (`RK_REPEATABLE_INCLUDE_ROOT` — an include's root must be a single, non-repeatable group) → refuse. A carried rule/computation's **absolute** operands are **re-based** to the sub-model root (`/Parent/Group/X` → `/Group/X`, at path-segment boundaries; relative `../X` rides along), and the sub-model is **kernel-validated standalone** before writing — refusing if a residual break remains, never emitting a broken artifact (probe 01-de Finding 6). (A rule *outside* referencing *into* the subtree is fine — the mount preserves that path; verified.) **Both element kinds are checked, and the subtree ROOT counts as inside** — `CG17`, where the gate was wrong in opposite directions at once: it looped rule names only, which deliberately exclude computations, so a computation reading an outside field moved into a sub-model that could not see its own operand; and its membership test was `startsWith(groupPath + "/")`, under which `/Order/Shipping` is not inside `/Order/Shipping`, so a rule referencing the extracted group *itself* was refused as escaping the subtree it is the root of. That reference travels fine, so the refusal was an over-refusal naming a problem the author cannot fix. Membership is now compared at a path-segment boundary, which also keeps `/Order/ShippingNotes` out. (Locked by `GroupExtractComputationGateTest`: the computation escape mutation-confirmed, the root self-reference admitted, and a genuine outward reference still refused as the control that the gate was not simply loosened.) The sub-model's **root group** keeps the extracted group's name by default; **`--root-name <n>`** names it independently — for a sub-model meant for **reuse** under a different mount (extract `HomeAddress` as a shared `Address`, mounted under both Home and Work). The base **mount** always keeps the original name, so composed paths are preserved either way; mount-name ≠ root-name composes cleanly (probe F05-3, verified + locked by `GroupExtractVerbTest.rootNameNamesTheSubModelRootIndependentlyOfTheMount`). |
| **model rename** (`model rename --to <newId>`, G27) | a **single-model** id edit, so the cross-model cascade (repointing every includer) is out of scope (§4 OQ1). The gate is checkable only with a workspace (`-w`): a sibling that **includes/imports** the old id → refuse (`RK_REFERENCED`, `data.referencedBy.models`, fix = "repoint those includers first"); the new id **collides** with a sibling → refuse (`RK_NAME_EXISTS`). Without `-w` there are no siblings to scan, so it is a pure single-model header edit. A no-op (`--to` equal to the current id) is a usage error. When safe: rewrite `header.id`, re-validate, write. |
| **include set-reference** (`include set-reference <reference> --to <newReference>`, G36) | a **Local** edit rather than a refactor: the model named is not included → refuse (`RK_NO_SUCH_INCLUDE`); the kernel re-validate is the backstop when the new reference does not resolve. When safe: every mount's `includeConfig.reference` and the header entry name the new model, each mount keeping its position and options. Rules over mounted content are keyed by **path**, so nothing dangles. *(The DM 28 `include rename`, G37, renamed an alias; DM 29.4 has none (KF651), so the verb is retired and answers with this one as its corrective.)* |

**Two obligations on every refactor — non-negotiable:**

1. **Document the gate well in these md docs.** Its preconditions, its refusal conditions, and the diagnostics it emits belong here in §6 (or the refactor's own spec section) — never left implicit in code. The safety contract is part of the published, self-describing surface.
2. **Lock the refusal with a law test.** The refusal path gets a test proving the gate **fires** on unsafe input, just as the accept path proves it proceeds when safe. An ungated *or* undocumented refactor does not ship.

**Implemented** (2026-06-12) as `SafetyGate` (runs the registered checks in order, returns the first `Refusal`) + `SafetyChecks` (the reusable preconditions — the first is the `RK_REFERENCED` reference gate shared by safe-delete and safe-rename) + `Refusal`/`BaseCommand.refuse` (the `refused`-envelope emit). **Safe-delete (`field`/`group remove`) is the first adopter** — its hand-rolled refusal was replaced by the shared check. Locked by `SafetyGateTest` + the remove verb tests; each new refactor registers its own `SafetyChecks` precondition and adds the matching refusal test.

**Reference-rewriting rename + move shipped (2026-06-12) — §3.1 complete.** `field` / `group` / `rule` / `typedef rename` rename the declaration **and rewrite every reference** to it — rule conditions, error-entity paths, computations — then re-validate. **`field` / `group move`** add the node relocation on top of the same rewrite: detach the element, re-home it under a new parent (re-prefixing its + descendants' ids), rewrite every reference to the new path, re-validate. The rewriter is the kernel's own **`MoveSupportDM`** (lenient, token-precise, preserves absolute-vs-relative style, *follows* starred-group references, and also rewrites a group's index/sort-field refs — KERNEL-FINDINGS §10), wrapped at the N8 boundary as `adapter.ReferenceRewriter`; rulekit builds no parser of its own. For a `group` rename/move the whole subtree re-homes and references **into** it from outside are rewritten too. The gates refuse only on a precondition (rename: `RK_NAME_EXISTS`; move: `RK_NO_SUCH_GROUP` / `RK_MOVE_INTO_SELF` / `RK_NAME_EXISTS`); a narrow case the rewriter can't fix is caught loudly by the kernel re-validate (`rejected`), never a silent dangle. The eval task `03-rename-field` (refactor family) is now **active** — its Layer-1 oracle (`EvalGoldOracleTest`) applies the gold rename via the rewriter and asserts it re-binds valid→valid. (**Typedef rename/extract/inline** need no rewriter — a typedef never appears in a condition.) These reference-rewriting refactors (field/group **rename·move**, **rule rename**, **typedef rename**) run **both as standalone verbs and as `apply` op-records** (§7): a single `StructureRefactor` definition single-sources each op's gate + entity-moves + node change, so the standalone verb and the in-session apply op share one gate and can't drift. (**`extract`/`inline` stay standalone** — they produce/consume a second artifact, which apply's one-model-one-write shape doesn't represent.)

`field move` performs reference propagation through `ReferenceRewriter`/`MoveSupportDM`, followed by the shared refactor's kernel validation before persistence. The successful move and refusal controls are locked by `MoveVerbTest`; this is the path described by `field move --help`.

### Re-type reader advisory — `field modify` across a KIND change

`field modify` re-types a field in place (§3.1 G6). A **within-kind** config tweak (give a STRING a `pattern`, tighten a NUMBER's scale, extend an ENUM's values) is the common, safe case. But a **kind change** (STRING→ENUM, …) is the riskiest re-type: unlike rename/move it does **no reference rewriting**, so every condition that reads the field stays textually identical while its *type validity* can flip — a `PatternViolated` on what is now an enum, an enum-category navigation on what is now a string.

So `field modify` runs a **proactive advisory** (not a refusal): when the re-type changes the field's KIND (the DM-JSON `fieldType.type` discriminator) **and** a rule/computation reads the field (the adapter's exact `where-used`, the same primitive safe-delete uses), it attaches a **WARNING** `RK_RETYPE_AFFECTS_READERS` diagnostic to the result envelope listing the referrers, so the author sees the audit set up front instead of decoding a raw kernel `MVK_*` after the fact.

It is **advisory, not a gate**, on purpose — a kind change with only kind-agnostic readers (e.g. `FieldFilled`) is genuinely safe, so a hard refusal would over-block. The **kernel re-validate stays the authoritative hard gate**: a reader the kind change actually invalidates makes the whole `field modify` a `rejected` envelope (nothing written). The advisory's value is the accepted-but-audit-worthy case. (Like safe-delete, the proactive reader check lives at the CLI, which has the adapter; this is the standalone `field modify` verb — the `apply` op (§7) defers to the one terminal gate.) Locked by `cli.FieldModifyCommandTest` (fires on a kind change with readers; silent on a within-kind change and on a kind change with no readers).

### Safe-delete — the Cascading gate (recorded so it isn't re-litigated)

Removing a field/group a rule/computation still references would dangle a reference. So `field remove`/`group remove` run the adapter's exact **`where-used`** first. If anything references the target it **refuses** (`outcome:refused`, exit 2) and surfaces the references as a structured diagnostic (`RK_REFERENCED`, `data.referencedBy:{rules,computations,documentUniquenessCriteria}`, a `fix`), so an agent can act — remove them first, or pass **`--cascade`** (which removes the referrers, then the element). **Never a silent cascade.** **A document uniqueness criterion naming the field, or a field inside the group, refuses even with `--cascade`:** A12 refuses a criterion over a missing field ([KF671](KERNEL-FINDINGS.md#kf671)), and `--cascade` removes only rules and computations, so the fix names the criteria to `criterion remove` first, each re-declarable over other fields with `criterion add` (`cli.UniquenessCriterionVerbsTest`). **Inside `apply` this is deliberately stricter than A12:** each op is gated on the model as it stands, so removing a criterion's field and adding it back in a later op is refused at the removal, though A12 would admit the final model. A field changes in place through `field modify` or `field rename`, which keep the criterion valid (`applyRefusesRemovingACriterionFieldEvenIfALaterOpAddsItBack`). **One refinement for composite groups (§3.8):** the gate counts only referrers **outside** the removed subtree — a rule/computation that *lives inside* the group being removed (an attachment template's own internal rules, which the author never wrote) goes away with the subtree and must not trigger a spurious `--cascade`. So `group remove` drops in-subtree referrers (those whose full name is under `<group>/`) before applying the gate (`cli.GroupAttachmentVerbTest`). This whole cascade computation is single-sourced in **`GroupRemoval`** and shared by the **standalone `group remove` verb and the `apply` `group remove` op** (G12), so the two can't drift — the op takes a `cascade` key with the same meaning, and a refused gate rolls the whole apply sequence back. The *proactive* "what references this?" check lives at the CLI (which has the adapter — `where-used` is an adapter capability above `EditSession`, and `dm.modelkit ⟂ dm.rulekit` means modelkit can't see rule knowledge); the *authoritative* dangling-reference check stays the kernel gate (`EditSession.validate()`). Layering rationale: [`KERNEL-INTEGRATION-NOTES.md`](KERNEL-INTEGRATION-NOTES.md) "Structure edits + the delete-safety rule".

### What counts as a "reference" — the symmetry, and querying both directions

The whole Cascading/Refactor story hinges on one definition, so make it explicit. A **reference** is whatever the kernel's `getDirectlyReferencedEntities` returns for a rule — and it is **not** just the field a rule's error is *attached to*. It is **every field/group the condition reads** (the operands), and for a **computation** it additionally spans all four sites: the computed (calculated) field, the common precondition, each alternative's precondition, **and each operation expression**. A field read *only* inside a computation's operation — invisible to a rule scan — still counts. (KERNEL-FINDINGS §9 — the `getDirectlyReferencedEntities` primitive; locked by `adapter.WhereUsedInComputationsTest`.)

That definition makes the dependency direction — and the whole gate behaviour — fall out of a simple **referrer vs referent** asymmetry:

```
   rule / computation  ──references──▶  field / group
   (referrer — a leaf)                  (referent — depended-upon)
```

- A **rule or computation is a leaf**: nothing references *it*. So `rule remove` / `computation remove` need **no cascade gate** — removing one can't dangle anything (a computation's computed field simply survives, now unfilled). It only re-binds, so a removal that somehow broke the model still fails loudly.
- A **field/group is a referent**: removing it could dangle every referrer. So `field remove` / `group remove` are gated.

The three things you can do to a field a rule/computation *reads* — operand, precondition, computed-target, or error-entity alike — each resolve **valid→valid, or refuse/reject; never a silent break**:

| operation on a referenced field | what happens | safe? |
|---|---|---|
| **delete** (`field remove`) | every referring rule **and** computation surfaces via `where-used` → **refused** (`RK_REFERENCED`) unless `--cascade`, which removes the *whole* referrers first (it cannot excise a single operand from a condition); a document uniqueness criterion naming the field refuses even with `--cascade`, and the refusal's fix names `criterion remove`, which frees it | gated |
| **rename** (`field rename --to`) | every referring site is **rewritten** to the new name — condition operands, preconditions, operations, error-entity + computed-field refs — atomically (`MoveSupportDM`), then re-validated | ✅ automatic |
| **move** (`field move --to <group>`) | same rewrite **plus** node relocation; refuses first on a missing/again-taken destination (`RK_NO_SUCH_GROUP` / `RK_NAME_EXISTS`) | ✅ automatic |

**Both directions are queryable today** — you don't reason about references by hand:

| direction | verb | output |
|---|---|---|
| **usages of an element** (inverse) | `dmtool -m <model.json> where-used <path>` | `data: {entity, rules:[…], computations:[…], documentUniquenessCriteria:[…], count}` — every rule/computation that directly references the field/group, the two kinds kept separate, and by name the document uniqueness criteria that name the field (A12 gives a criterion no path) (rides the result envelope; shape = `where-used.schema`) |
| **usages across the whole model** (inverse, aggregate — G9) | `dmtool -m <model.json> model usage` | `data: {usage: {field → [referrers]}, documentUniquenessCriteria: {field → [names]}, unreferenced: […]}` — every field's reading rules/computations, the criteria naming each field, and the fields neither reads nor names, in one call. **Reachability, not exactness**: a field reached only through an ancestor GROUP operand is reported read, since the kernel expands a group operand to every field below it |
| **dependencies of a rule** (forward) | `dmtool -m <model> rule deps <rulePath>` | `data: {references:[{path, kind}], iterates, iterationGroup?, count}` — the fields/groups the condition touches + the repeatable group it ranges over. The focused verb; `rule explain` carries the same `references`/`iterates` inside its fuller projection (tree + operators + gloss + **`polarity`** + the stored **`messages`**) |
| **every rule's dependencies at once** | `dmtool -m <model> export …` | a `referencedFields` array per rule across the whole model |
| **a candidate's error TEXT** | `dmtool -m <model> rule check --field … --condition … --code … --message en_US='…$Field.value$…'` | the kernel's error-text findings in the ordinary `diagnostics`, carrying the checker's own class (`INVALID_ENTITY`, `NO_BASE_YEAR`, `FIELD_NO_ENUM`, …) and the rule locus. The read-only peer of `rule add --dry-run`, which was previously the only route to that checker |
| **valid error fields for a candidate** (G4) | `dmtool -m <model> rule check --field … --condition … --code … --suggest-error-field` | `data: {field, candidates:[…], fieldIsCandidate}` — the referenced fields inside the condition's iteration scope, the legal error-field picks (the `MVK_ERROR_FIELD_NOT_REFERENCED` law, up front). Same `getDirectlyReferencedEntities` source as `rule deps`, filtered to the iteration scope; the candidate is bound *leniently* so a bad error field still yields the corrective list |

One primitive (`getDirectlyReferencedEntities`) seeds all of these, but they answer **two different questions** and the difference is deliberate, not incidental:

- **Exactness — "which rules NAME this entity?"** `where-used` is literally the primitive's inverse. A rule that names an enclosing *group* is not listed for a field inside it; it is listed for the group.
- **Reachability — "does anything READ this field?"** **`model usage`** and the report's dead-field set aggregate the inverse over every field **and walk ancestor groups**, because the kernel expands a group operand recursively to every field below it. `AllFieldsFilled(/Order/Address)` reads `/Order/Address/Region/Code` while naming neither, so an exact answer here reported a live field as `unreferenced` — which an agent acts on as safe-to-delete (`CG16`). The ancestor walk is segment-wise, so `/Order/Billing` does not reach into `/Order/BillingContact`.

So `where-used` and `model usage` **differ on exactly the group-reached fields, by design** (pinned by `cli.model.ModelUsageGroupOperandTest.whereUsedStaysExactWhereModelUsageIsReachable`, which runs both verbs on one model). The adapter seam is `KernelAdapter.referrersReaching(byEntity, path)` — or `isReadByAnything` for the boolean question — beside the exact `whereUsed` / `whereUsedInComputations` / `referencedFields` / `referencedFieldsOfComputation`.

**Reachability is deliberately CONSERVATIVE, and that is a stated over-report rather than an exact claim.** It answers *"a rule reaches into this group"*, not *"this particular field enters that operator's expansion"*. The two come apart on a repeatable terminal group: `NoGroupFilled(/Order/Items*)` counts instantiated **rows** — an empty created row is still a row (API-GUIDE [§3.5b](API-GUIDE.md#group-quantifiers)) — so `Items/Qty` is reported read though that operator never inspects its value. Erring toward "read" is the correct direction here, because the surface's `unreferenced` half is what an agent acts on as safe-to-delete; the opposite error deletes a live field. **Not measured:** whether every group-consuming operator's expansion really covers every contained field on a *repeatable* terminal group (KF183 measures the non-repeatable case and shows recursive expansion). The conservative direction makes that gap safe rather than closed.

*(This paragraph used to claim all of these "can never disagree about what 'references' means", which was the thing to fix rather than a fact to preserve. `explain`'s `references` and `rule deps` take theirs from the **converted** AST rather than from the kernel primitive. **Measured 2026-08-15** (`cli.rule.RuleDepsVerbTest`): over a rule whose operand is a group, `rule deps` names the **GROUP** — that is what the condition references — while `where-used` on a field inside it names **nothing**, because it answers the exact question and no rule names that field. The two disagree, and both are right: they are inverses of different questions. Only the reachability reader closes the loop, which is why `model usage` walks ancestors and `where-used` does not.)*

Locks: `cli.WhereUsedVerbTest`, `cli.ModelUsageVerbTest`, `cli.model.ModelUsageGroupOperandTest` (the group-reached rows and both vacuity controls), `adapter.WhereUsedInComputationsTest`, `cli.RemoveVerbTest`, `adapter.ReferenceRewriteTest`.

## 7. Batching — dispatcher `batch` vs session `apply` <a id="batching"></a>

Two batch verbs, because they solve different problems — conflating them would break the eval runner:

| verb | op shape | model | semantics | for |
|---|---|---|---|---|
| **`batch`** | `{verb, args:[…], id?}` — the verb + its CLI argv | many ops, **any verb** (incl. refactors), possibly **different models** | stateless dispatch — each op is a full `Cli.run`; continues after failure; never rolls back | independent calls where partial writes are acceptable; **the N6 eval runner** ([`eval/benchmark.workflow.js`](../eval/benchmark.workflow.js)) |
| **`apply`** | `{target, op, …args}` — the op-record | one model, ordered edits | one read → ordered surgery on one `EditSession` → **one terminal gate** → one write; **atomic rollback** | the north-star: read → add fields/groups → add/modify rules → **rename/move** → delete → write back |

A **batch-level `-m`** is the default model for ops that omit their own `-m` (G18, the universal-`-m` convention); an op carrying its own `-m` keeps it. `dmtool -m m.json batch ops.json` therefore runs every op against `m.json` without repeating it per op, while a heterogeneous batch can still point individual ops at different models. Full dispatch produces `data.dispatched:true`; `data.allExitedZero` aggregates child exits without replacing them, and the summary separates genuine child failures from negative verdicts or comparisons. In ordinary mode, outer `ok` and exit 0/1 follow `allExitedZero`. Because `batch` is not a transaction, a successful write remains if a later child fails. Use it for independent calls, read-only checks, or cases where partial writes are explicitly acceptable. Use `apply` for an atomic set of edits to one model.

**Every verb's schema has ONE shape, frames included (2026-09-22).** `schema batch` and `schema apply` used to serve their op-record document raw at the top level, because the name resolved as a "frame" before it resolved as a verb — so a consumer projecting `.input`, which is where every other verb publishes its input schema, got `null` on exactly the two responses whose shape is least guessable. They are now ordinary verb contracts: `{op, input, returns, resultSchema, operationalProfiles}`, with the frame document and its worked examples under `input` and `batch`'s `observationArtifact` annotation beside them inside it. A consumer reads `.input` everywhere or nowhere; the structure schemas (`schema result`, `schema diagnostic`) are unchanged, since those name no verb.

**A `verb` is spelled either way, and a verb that names no command refuses the whole batch (2026-09-22).** `manifest` names a two-word verb as one string, so `{"verb": "model check"}` is what a batch written from the manifest looks like — and the dispatcher used to pass that string through as a single argv token, failing every child with `Unmatched argument at index 0`. It now splits `verb` on whitespace, which cannot collide with the split form because no single-token verb contains a space; the result still echoes the caller's own spelling. The failure was worth fixing rather than documenting because it is invisible in the shape `batch` exists for: a separating matrix fails *uniformly*, controls included, which reads as a route problem rather than a spelling one, and the envelope it produces is the one a genuine mixed-verdict run also reports. Reported twice by an external consumer, a round each time. A verb naming no command at all is now answered once, before child zero, since it is wrong for every child and dispatch never rolls back — `RK_UNKNOWN_ARG` located at the item's index, quoting the verb as written. Locked by `BatchVerbSpellingTest`.

**Compact static-kernel observations.** `batch --observations <file>` overwrites one deterministic replay artifact after dispatch. Full dispatch plus artifact write is the operation, so it returns `ok:true` and exit 0 even if a captured child exits nonzero; `data.allExitedZero` retains that independent aggregate. A completed artifact write is explicit as `written:true` plus `output`; ordinary batch remains `written:false`. Every item must carry a non-blank caller `id`, and the only supported children are `rule check --condition ...`, `computation add <spec> --dry-run`, and `computation modify ... --spec <spec> --dry-run`; capture never persists a computation candidate. The artifact header carries contract version 2, dmtool/kernel/source identity from `manifest.version`, and the SHA-256 of the single effective model's persisted bytes only when every child resolves to that same model identity; a heterogeneous/no-model/mixed-model-and-no-model batch omits `model`. Each observation, in dispatch order, carries the caller `id`, SHA-256 of the framed authored candidate, the child's independent `ok` and optional `valid` axes, and diagnostic codes in emitted kernel order. Preflight rejection occurs before child zero, writes nothing, and exits 1. A child failure still produces the post-dispatch artifact. An artifact-write failure retains all completed child results, returns `outcome:error`, and exits 70. `schema batch` serves both the batch frame and the exact `observationArtifact` schema, the artifact annotation riding inside `input` beside the frame it annotates.

Version 2 hashes distinguish the canonical verb and all authored candidate arguments: `rule check` includes condition, error field, optional group, code, severity, name, and effective message locale/text pairs sorted by locale; computation add includes exact spec bytes, and computation modify additionally includes its target path. The [observation schema](../cli/src/main/resources/schema/batch-observations.schema.json) specifies the byte framing, defaults, and absent values. Text and spec bytes are not normalized. Hashes exclude caller IDs, filesystem paths, output options, and model/workspace contents; the optional model hash is separate and does not identify workspace dependencies. An artifact identifies retained candidates but does not contain the authored inputs needed for replay. Version 1 hashes are not comparable with version 2. `BatchObservationCapture.candidateInput` enforces this contract; `BatchObservationInputIdentityTest` locks message-only opposite verdicts, metadata/target distinctions, locale ordering and rerun stability, and `BatchObservationsTest` pins independently calculated byte-frame SHA-256 vectors. No authored prose is retained.

**A nonzero child exit is not a failed child (2026-08-04; observation contract realigned 2026-08-10; classification corrected 2026-08-10).** Two result families exit nonzero while reporting `ok:true`: a verdict whose `valid` is false (`rule check`, `model check`, `workspace check`) and a comparison that differs. Both ran. The child-exit aggregate is therefore named `allExitedZero`, not `allSucceeded` (CG9), and the summary states the split rather than calling every nonzero child a failure.

**`ok` is not the discriminator — the established verdict is.** The first version of this fold read `result.ok` alone, which silently assumed every negative verdict rides an `ok:true` family. A kernel `REJECTION` breaks that assumption by design: `computation add <spec> --dry-run` on a candidate the kernel refuses reports `outcome:rejected`, `ok:false` (the operation did not succeed), **and** `valid:false` + `verification:KERNEL_CONFIRMED` (the gate ran and arbitrated it). Reading `ok` alone called that deliberate negative control a failure, contradicting the very axis-separation contract the summary exists to state — reported by a consumer on 2026-08-10 whose computation capture matrix reported `1 failed, 0 reported a negative verdict`. The discriminator is now **"did this child's own envelope establish a negative subject verdict or finding"**: `ok:true` with a nonzero exit (structurally only a negative verdict or a differing comparison), **or** `valid:false` wherever it appears. `ResultEnvelope.ChildDisposition` owns it, and `BatchComputationRejectionClassificationTest` locks the `REJECTION` family the earlier rule-verdict test could not reach.

Three parts form the contract:

- **The summary states the split**, derived from each child's own envelope: `<n> of <m> exited nonzero (<f> failed, <v> reported a negative verdict or comparison)`. Only a child that established nothing counts as a failure: a preflight rejection publishes neither `valid` nor `verification` (nothing arbitrated it), and a child whose stdout is not a result envelope has no axes to read at all, because those verbs hold no verdict.
- **`data.allExitedZero` states only the child-exit aggregate** in both modes. Ordinary batch derives outer `ok` and exit 0/1 from it. Observation batch derives outer `ok` and exit 0/1 from full dispatch plus artifact write. The `dispatch-with-observations` profile publishes that selector as `DISPATCHED_AND_ARTIFACT_WRITTEN` for both `aggregateSuccess` and `topLevelOk`.
- **The self-describing surfaces state both mode rules.** `batch --help`, `schema batch`, `schema result`, and the manifest operational profiles agree, and none of them says that every `ok:false` child failed to run. `BatchObservationNegativeControlTest` locks ordinary negative-child behavior, successful negative-control capture, preflight rejection, and the help/schema claims; `BatchComputationRejectionClassificationTest` adds the kernel-rejection family plus its preflight positive control. `BatchObservationsTest` locks artifact-write failure and successful all-zero capture.

The sibling sweep is complete and bounded. `ResultEnvelope.dispatchData` owns the single `allExitedZero` fold. `dispatchCompleted` applies the ordinary child-exit rule, while `dispatchCompletedWithArtifact` applies the observation operation rule. The other multi-subject aggregates do not compress these axes: `workspace check` exits 1 with aggregate `valid:false` beside `ok:true`; `workspace list --validate` keeps per-entry `valid` informational; and `apply` is one transaction with a terminal gate, so a rejection is a genuine operation failure.

**`apply` semantics.** It tolerates **transient-invalid states between ops** (defers the kernel gate to the end) and emits a **per-op result envelope** plus a batch summary (`{ops, committed, failedAt, written, results[]}`); a read op's payload rides its envelope's `data` (§3b). On a mid-sequence failure it **rolls back** (nothing written), the failing op's diagnostic cross-op aware (*"op f1 added /Order/Discount — fix the spelling"*). Rule ops carry **raw DSL/spec text** (the surgery path), so a transient-invalid model doesn't block authoring the fix; clean per-op attribution comes from validating per-op while the model is currently valid.

**The transient-invalid tolerance is bounded by the ops that need a bound model, and the boundary is measured.** An op whose own work requires a `KernelAdapter` builds one **from the session as it stands at its turn**, so it surfaces a mid-sequence inconsistency *there* rather than at the terminal gate: `field`/`group remove` (their §6 safe-delete gate), every Refactor op (its §6 gate), and `rule`/`computation read` (the condition/formula echo is an AST conversion). Measured 2026-08-28 on one sequence — a computation added with a message for only one of two model locales, then an unrelated `field remove` — which fails at **op 1** with `RK_APPLY_OP_FAILED` carrying the kernel's `MVK_ERROR_MESSAGE_FOR_LANGUAGE_MISSING`, and rolls back. The pure-JSON reads (`field`/`group`/`config`/`typedef`/`include`/`criterion read`) read `ModelDocument` and do **not** bind, so they stay tolerant. So: an intentionally transient-invalid stretch must not span an op from the first list.

**Refactors in `apply` — rename/move are op-records too.** `apply`'s op-set is the **Local** class (add · read · modify · remove + config, incl. `include set-reference`) — **enforced, not merely stated**: `ApplyOpSetParityTest` takes the live command tree's Local-class leaves from `manifest` and requires each to have an `ApplyCommand.Op` or a recorded reason why it cannot be an op-record, with the reason list guarded against staleness too. That guard exists because the claim was false in three places at once until 2026-08-28 — `computation remove`, `computation read`, and `rule read` had no op, so a sequence that replaced a computation atomically was unrepresentable and hit `RK_UNKNOWN_OP` mid-flight (found by an external probe, not by us: `CliCoverageParityTest` cannot see this class, since its denominator is `EditSession`'s mutators and the *standalone* verb already satisfied each one). **Plus the Refactor ops** `field`/`group rename·move`, `rule rename` and `typedef rename` (§6; the reference-rewriting ones use `MoveSupportDM`, while `typedef rename` repoints structural pointers with no AST rewrite). Each refactor op runs its own §6 safety gate **at its turn, against the live (transiently-edited) session** — so it sees prior ops' effects (e.g. moving a field into a group an earlier op just added) — then rewrites references via the kernel's `MoveSupportDM` and re-homes the result into the session; the change rides the one terminal gate + atomic rollback like every other op. A **refused** refactor (a name collision, a missing destination, move-into-self) becomes a mid-sequence failure → the whole sequence rolls back with the gate's corrective diagnostic in the failing op's `refused` envelope. The same `StructureRefactor` definition backs both the standalone verb and the apply op, so the gate can't drift. **Still standalone-only:** `extract`/`inline` — they produce/consume a *second* artifact (an include file), which apply's one-model-one-write shape doesn't represent; an `apply` op-record naming one is rejected with `RK_UNKNOWN_OP`, which lists the **`(target op)` pairs** `apply` *does* support — named as pairs because an op-record spells its op as two keys while the list is space-joined, so a bare "supported ops" list read as a value for `op` and handed an agent back the very spelling it had just been refused for (measured 2026-09-04). When only `op` is passed and its value IS a label, the corrective now splits it into the two keys. Decision rule: **rename/move + edits on one model, transactionally → `apply`**; **a cheap fan-out of independent verbs, or `extract`/`inline` → `batch`/standalone**.

**Writing a batch without prior knowledge — by composition.** A batch op *is* a CLI call as JSON, so discovering a verb (manifest + `schema <target> <op>`, §5a) *is* discovering how to batch it. `schema apply`/`schema batch` add only the list *frame* + a worked `examples` block, served under `input` like every other verb's input schema (they are verbs, and were the one exception until 2026-09-22); the per-op fields are the verb's params, copied from the manifest — **including the op-record locator key for an existing element, which equals the standalone verb's `--`-stripped positional** (the manifest's `key`). A path-located element uses `<element>PathInModel` (`fieldPathInModel` / `groupPathInModel` / `rulePathInModel` / `computationPathInModel`), a typedef `typeDefId`, an include `alias`; an *add* op instead carries the new element inline (`field`/`code`/`condition`/`messages` for `rule add`), with no path. Because the manifest derives that `key` and apply reads the same convention, the two can't advertise different names — locked by `ApplyVerbTest.everyPathLocatedApplyOpAcceptsTheLocatorKeyTheManifestAdvertises`. **The same parity holds for a flag-driven verb's *settable* flags:** every `--flag` the manifest advertises (minus the CLI I/O mechanics — `-o/--output`, `--dry-run`, `-w/--workspace`) is a valid op-record key, so an `include add` op honors the standalone verb's `repeatability`/`exclude-rules`/`exclude-computations` and a `config modify` op its `supported-character` — was a drift hazard (the op silently couldn't do what the verb could), now locked by `ApplyVerbTest.everyFlagDrivenApplyOpAcceptsTheSettableFlagsItsStandaloneVerbAdvertises` (the rich-spec verbs — field/rule/computation/typedef add·modify — are excluded: they carry a JSON spec body whose keys diverge from the flags, guarded by `SpecKeys` + the executable schema examples instead). The op schema is intentionally loose (`additionalProperties:true` — inlining every op's args would need an unreadable `oneOf`), so **validation moves to the runtime, and stays corrective:**

- **Op-arg validation.** `apply`/`batch` validate each op's keys against that verb's param model and emit a corrective diagnostic in that op's envelope — `RK_UNKNOWN_ARG`, `where.arg`, a did-you-mean `fix`. The most common batch mistake (a typo'd/wrong key, or an `op` not valid for `target`) self-corrects instead of failing opaquely. This is the point: corrective diagnostics must reach *inside* batches, not just standalone calls.
- **Value-shape validation — key *values*, not just names.** The same `SpecKeys` gate validates each declared key's **value** against the schema, the sibling of the key-name check: a recognized key carrying a wrong-shaped value is a structured **`RK_INVALID_VALUE`** (with `where.arg` + an expected-type `fix`), not a silent coercion. It checks the schema's `type`/`enum` at every level, for **every served spec** (field add/modify, rule add, computation add, and `apply`/`batch` — top-level scalars and nested) — so `required:"MANDATORY"` (outside the `[true,false,"ifParentPresent"]` enum the `required` schema now declares), `annotations:[…]` (array vs the declared object), and a localized-text field as a bare string (vs the locale→text object) are all refused, never swallowed to a default/empty and falsely reported `applied`. An **open** object (a locale map) still requires an *object* value while leaving its keys unrestricted — the name and value checks compose. The `FieldSpec` parsers keep a fail-fast invariant *behind* the gate (defense-in-depth; it also backstops the `apply` op-record's top-level scalars, which the nested-only check can't see). Locked by `SpecKeysTest` (the gate, per-spec) + `FieldMetadataRoundTripTest`'s "applied ⇒ effected" round-trip (end-to-end through the CLI). **The BUILDER half answers in the same shape (2026-08-29).** A value the schema admits as well-typed but the kits will not build from — a fractional-digit scale above the kernel's cap of 14, an enum category that does not classify every value — used to be prose on stderr with an empty stdout and exit 2, so one input gate had two contracts and the local refusal was indistinguishable from a kernel verdict to a consumer reading only the exit code. It is now the same `rejected` envelope with `RK_INVALID_VALUE` and `source: PRECHECK`, on all four spec verbs (`field add`/`modify`, `typedef add`/`modify`), and such a message no longer attributes its rule to the kernel that never saw it. The kernel's own gate stays observable where it always was: `model check` over a hand-written model runs `checkConsistency` with no spec preflight in the way ([KF216](KERNEL-FINDINGS.md#kf216)), which is why no skip-validation flag was added. **Re-open trigger:** a declaration gate that `model check` cannot reach — one where the refused shape is not expressible in DM-JSON at all, so no hand-written model can put it in front of the kernel. Then an opt-out flag (`--no-spec-preflight`) becomes the only observation route and this decision expires. Locked by `SpecValueRefusalEnvelopeTest`.
- **Cross-type corrective.** Feeding `batch` an `apply`-shaped op (or vice versa) is detected and named (*"this op has `target`/`op` — did you mean `apply`?"*).
- **Examples can't rot.** Every schema `examples` block is CI-executed through the tool (a drift guard alongside the manifest/schema guardians) — a stale example actively misleads an agent, so an unverified one cannot ship.

**Implementation status.** `batch` is the long-standing dispatcher. `apply` is **built and feature-complete**: ordered surgery on one `EditSession` → one terminal gate → one write, atomic rollback, per-op envelopes (edits `staged`, reads `read`+`data`) + the `{ops, committed, failedAt, written, results[]}` summary. Its edit matrix covers field/group/typedef/include add·remove, the semantic target-specific modifiers, config and include changes, rule/computation add·modify, the reference-rewriting refactors, and generic `{target:"meta",op:"modify",ref,…}` metadata edits across every describable element and type definition. Rich creation specs remain available inside the corresponding add op; field modify deliberately uses the narrower `field-modify` schema, while common metadata uses the generic op (G45). Structure reads (field/group/typedef/include/config) observe the live in-session state; the field read uses the same complete projection as the standalone verb. Every edit is deferred to the one terminal kernel gate, so a refusal or invalid final model writes nothing. Op-arg validation (`RK_UNKNOWN_ARG`/`RK_UNKNOWN_OP` + did-you-mean) is schema-sourced and nested: standalone and transactional spec verbs reject typo'd, retired, or wrong-shaped values instead of silently dropping them; retired metadata keys receive a direct relocation to `dmtool meta <ref> …`. Dispatch is an exhaustive `switch` over the `Op` enum. **The one niche extension left:** rule/computation/model reads inside `apply` (they would bind the live model through the adapter for each read; low value because reads are normally standalone). `extract`/`inline` remain standalone because they are multi-artifact operations.

## 8. Module shape

- **`:cli` Gradle subproject**, `application` plugin, **builds the `dmtool` binary** (`applicationName = "dmtool"`; the gradle module stays `:cli`). Depends on **core + adapter + the kits**; the adapter pulls the internal kernel read tier — fine for an *app* (N8 confines the internal tier to adapter/cli, never core).
- **picocli** drives the command tree (§2): `RootCommand` (`name = "dmtool"`) + a target group per kind + one `@Command` op per cell, each a `Callable<Integer>` extending `BaseCommand` (the `out`/`err` seam). `picocli-codegen` auto-emits the GraalVM native-image reflection config.
- **Testability split — the fast loop:** `Cli.run(String[] args, Appendable out, Appendable err) -> int` is **pure and testable** (no `System.exit`, returns an exit code, writes to passed sinks); `CliMain.main` is the thin `System.exit(Cli.run(…))` shell. Every op is unit-testable in-process — no packaging, no spawned process.

## 9. Dev/test workflow — keep packaging out of the inner loop

The self-contained binary (jlink/jpackage) only *provisions a JVM* — zero behavior, ~a minute to build — so it is **never** in the code-build-test cycle. Three speeds:

| Changing | Command | Speed |
|---|---|---|
| **CLI/verb code** | `./gradlew :cli:test` — JUnit over `Cli.run(...)` | sub-second (warm daemon); the primary loop |
| code, want a real process | `./gradlew -q :cli:run --args="-m model.json model check"` | seconds (incremental; skips packaging) |
| **only inputs** (model/spec JSON) | `./gradlew :cli:installDist` once, then `cli/build/install/dmtool/bin/dmtool …` (or the `bin/dmtool` shim) | ~1s JVM startup, no rebuild |
| sibling project needs current-source evidence | `DMTOOL="$(./scripts/prepare-dmtool-source.sh)"`, then `"$DMTOOL" …` or one `batch` | one provenance startup; Gradle only when the clean revision changed |

Rules of the loop: never `clean`; never `installDist`/jlink/jpackage to test *behavior* (only to produce a distributable). Point an agent dry-run at the one-time `installDist` launcher. *Future option (if multi-call latency bites):* a resident/stdin mode (JVM startup paid once across many calls).

`prepare-dmtool-source.sh` is the strict cross-project evidence route. It refuses a dirty source tree, accepts an existing JVM launcher only when `--version` reports the exact current clean commit, otherwise builds `:cli:installDist` once, and rechecks both source and artifact before printing one absolute path. It never consults `RK_NATIVE`, `DMTOOL_CLI`, or native build output, so it needs no native-image metadata capture. A retained capsule records the clean revision before and after its calls; use `batch` when several operations can share one process. It is **working-directory independent**: it anchors its own cwd, because `build.sh` ends in `exec "$ROOT/gradlew"` with no `cd` and no `-p`, so Gradle would otherwise take the caller's directory as the project directory and every rebuild from a sibling repository would fail. That failure hid behind the cache — a caller got a working launcher whenever one already matched HEAD, and only a *required* rebuild surfaced it. It classifies on the launcher's ANSWER before its exit status — the provenance line counts from either stream — while keeping a launcher that names the right revision and still exits non-zero out of the `current` state, since the caller runs the returned path next. `DmtoolLauncherTest` runs its disposable-repository self-test in `deliveryGuardTest`, covering cache reuse, stale rebuild, dirty refusal, a mismatched post-build artifact, a rebuild forced from a foreign working directory, the four launcher answer shapes, both post-build rechecks, an unavailable JDK pin in its two forms, and a caller JDK that runs but is too old. The foreign-working-directory case only discriminates because the fake build models the real one's caller-directory dependence, and the too-old case only discriminates because the fake launcher models the real one's death on an unsupported class version; a fixture better behaved than the thing under test cannot fail.

## 10. Sizing <a id="sizing"></a>

- **Application jars: ~18.5 MB** (51 jars — kernel subset + Jackson + commons + antlr4-runtime + Groovy; Groovy ~7–8 MB).
- **jlink-trimmed JRE: ~45–70 MB**; jpackage launcher +1–3 MB. **Self-contained app-image: ~65–90 MB/OS; compressed download ~30–50 MB.**
- **Shrink levers:** drop kernel jars the verbs never exercise (verify with `jdeps`/coverage — Groovy + `kernel-core-runtime`/codegen may be unused; biggest win); `jlink --compress=zip-9 --strip-debug …`; ship per-OS only → could approach ~25–35 MB.

## 11. Packaging phases & licensing <a id="packaging"></a>

- **Phase A — dev/test:** `application` plugin → `run`/`installDist`/`distZip`. Dev JDK + kernel from `mavenLocal`. CI-testable; redistributes nothing.
- **Phase B1 — distribution, default: jlink + jpackage app-image.** Self-contained, signed; real JVM (no closed-world issues). `jdeps`-measured JDK modules → ~50–65 MB runtime + the classpath jars. Adds no behavior.
- **Phase B2 — GraalVM native-image: the chosen v1 packaging (native-only).** Full recipe, findings, sizing, and status: **[`NATIVE-IMAGE-GRAALVM.md`](NATIVE-IMAGE-GRAALVM.md)**. On GraalVM 25 native is ~31 MB / ~37 ms start; it needs Groovy excluded (native-classpath-only), resources bundled, and reflection metadata captured (`scripts/capture-native-config.sh`) — all done and gated. The Groovy ceiling has been **lifted for the verbs** (2026-06-24): the runtime verbs (`model eval`/`rule eval`/`model compute`) **run on the kernel-free `dm.interpreter` — the sole runtime eval engine on every target** (no `GroovyClassLoader.parseClass`), so they **run on the native binary** and stay on every self-describing surface — `Cli.JVM_ONLY_VERBS` is empty, and the native gate discovers and verifies every Showboat demo plus the packaged public-contract matrix. The opt-in **`--kernel` eval engine** that hit this ceiling (kernel runtime validation via Groovy — root cause: [`KERNEL-FINDINGS.md`](KERNEL-FINDINGS.md) "`checkConsistency` runs runtime code generation") **was retired** (Set V, 2026-07-12; `NativeImageRuntimeVerbsTest` now asserts the flag is rejected on every profile); the kernel stays bundled only for the consistency gate (`rule check`/`model check`), never the eval path. **Decision: v1 ships native-only**; the JVM `installDist` stays the dev/eval vehicle but is not a shipped artifact. B1 (jpackage) is the documented fallback only. See [`NATIVE-IMAGE-GRAALVM.md`](NATIVE-IMAGE-GRAALVM.md) §7.

**JPMS verdict:** use **jlink** (runtime trimming) — yes; full app modularization — no (53 non-modular jars with near-certain split packages, ~zero payoff). **Licensing** (settled — [`LICENSING.md`](LICENSING.md)): source is **MIT**; the bundled distributable embeds the kernel and ships under **EUPL-1.2** (carrying the kernel LICENSE/NOTICE/THIRD_PARTY + source pointer, **no "mgm A12" branding** — which the `dmtool` name respects).
