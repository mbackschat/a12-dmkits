# interpreter — gaps & open issues

> **What this is** — the interpreter's peer of [`DEV-API-GAPS.md`](DEV-API-GAPS.md) and [`FEATURE-GAPS.md`](FEATURE-GAPS.md): the single tracking surface for **open `:interpreter` gaps, deferred items, and to-fix issues**. It exists so open work is easy to **track, report, and pick up** — and so [`INTERPRETER-FINDINGS.md`](INTERPRETER-FINDINGS.md) can be what a findings doc should be: **settled, verified knowhow** you read to warm up and not re-investigate (like `KERNEL-FINDINGS.md`), never a backlog of dispositions ("open / to fix / deferred"). Per the CLAUDE.md *"rationale is timeless; a disposition is status"* rule — the findings hold the timeless fact, this ledger holds the live status.
>
> **The lifecycle.** A gap is born here with an `IG<n>` code under the section matching its status (§1 open / §2 deferred / §3 out-of-scope). When it ships, three things happen **in the fix's own commit**: (1) its **rationale graduates to a numbered `IF<n>` finding** in [`INTERPRETER-FINDINGS.md`](INTERPRETER-FINDINGS.md) — that finding notes it "graduated from IGn"; (2) any code/test comment citing `IGn` is **repointed to `IFn`**; (3) the gap's row is **deleted from this ledger**. **There is no "fixed/shipped" section — we don't record fixed gaps.** A fixed gap is no longer a gap; **git is the history of *when/what* was fixed, and the `IFn` finding is the *why*** — a hand-kept "shipped" list would only duplicate both and rot. So this ledger only ever lists **live, unfinished work** (the already-shipped IF20-per-cell / IF21 / IF23 / IF24 / IF25 live as findings, not here). A **deferred** gap stays in §2 with its re-open trigger, and an **ongoing as-touched** refactor stays in §2 with its remaining-work note (it is progressing in increments, not parked — its shipped parts graduate to its `IF<n>` finding while the row stays until *all* of it lands); the technical detail of each gap lives in its cited `IF<n>` finding (the knowhow), this ledger holds only *what's left to do and why*.
>
> **Section invariant (the placement rule):** every section holds exactly one **live** status — **§1 = open, §2 = deferred / ongoing-incremental, §3 = out-of-scope**. A FULLY-shipped/graduated entry belongs in **none** of them: completing it *deletes* its row (see the lifecycle). So §1 reads "(none)" whenever nothing is open, and a fully-FIXED entry **anywhere** in this ledger is a bug in *this doc* — git already records the fix. (A partially-shipped *ongoing* refactor in §2 is not "fixed" — it stays until all of it lands.)
>
> **Scope.** `:interpreter` only — the kernel-free Kotlin evaluator (parser, evaluation semantics, model loader, the differential/perf harnesses' interpreter side). dmkit (rulekit/modelkit/edit) authoring gaps go to [`DEV-API-GAPS.md`](DEV-API-GAPS.md); kernel-coverage classification stays in the MVK / RT-semantics / grammar ledgers.

## 1. Open (to fix)

- **IG88 — the BOOLEAN/CONFIRM formal check hard-codes `true`/`false`, but the kernel compares against the field's CONFIGURED tokens** (source-verified 2026-07-28, raised by the `a12-kernel-lean` maintainers reviewing our handover). `FormatDefinitionJaNein` compares `param.getWert()` with `.equals()` against `jaWert`/`neinWert` — the editor-stored values — each overridable at runtime by `DarstellungsInformationIntern.getWahrWert()`/`getFalschWert()`. IF229 measured the comparison correctly as **case-sensitive** (`.equals`, not `equalsIgnoreCase`) but generalized the *tokens* from one fixture to "lowercase is literal". Lowercase `true`/`false` is the **default profile**, not the contract. So our `FormalErrorCode.BOOLEAN_INVALID` check is a refusal **broader than its measured basis** — the defect CLAUDE.md "A client-side refusal needs a measured kernel basis" exists to prevent, and it is **two-sided**: on a model configuring `Y`/`N` we would fire `feldJaNeinFalsch` on the legal `Y` *and* accept the illegal `true`. **Why nothing caught it:** neither `ModelDef`/`ModelLoader` nor any committed fixture carries the tokens, so the probe's model used the defaults and no test can currently express the case. **Completion gate:** the `BooleanType` token configuration is loaded into `FieldDef`, the formal check compares against it (defaulting to `true`/`false` when absent), a fixture declares non-default tokens, and a kernel differential covers both the legal-configured-token and the now-illegal-`true` directions. Until then the check is correct only for the default profile — a scope limit that must be stated wherever IF229's "lowercase" claim appears.

- **IG87 — a `minFractionalDigits` field draws THREE false formal errors, because the kernel's runtime PADS a stored decimal and we do not** (found by independent review 2026-07-28, measured against the real kernel). IG85 recorded that A12 renders one stored decimal twice and claimed they "differ exactly on fractional trailing zeros beyond `minFractionalDigits`". That is only half the split: the runtime's `setScale(max(bd.stripTrailingZeros().scale(), minFractionalDigits))` also **pads** when the stored value has *fewer* fractional digits than `minFractionalDigits`, and `FormalError.kt` checks our stored text directly. On a `minFractionalDigits: 2` field:

  | authored Document JSON | kernel | interpreter |
  |---|---|---|
  | `250` | — | `zahlOhneDezimalTrenner` |
  | `250.0` | — | `zahlFalscheAnzahlNachkommastellen` |
  | `250.5` | — | `zahlFalscheAnzahlNachkommastellen` |
  | `250.00` | — | — |

  **Why no guard caught it:** `A12JsonIngressDiffTest.KNOWN_DIVERGENCES` calls itself "the exhaustive, characterized residual", but it is exhaustive only over `A12JsonIngressKernelTest.rows()`, and **that model declares no `minFractionalDigits`** — so the whole padding direction is outside the matrix. An "exhaustive" set is only exhaustive over its generator. **Completion gate:** the ingress matrix gains a `minFractionalDigits` field so the class is *reachable*; the three rows above either pass or are named residuals; IG85's "differ exactly on trailing zeros" wording is corrected (its own quoted formula pads, which the prose called stripping). Related to IG85 but **not** the same residual — this one fires errors the kernel does not, on values a user would plainly write.

*No other* open semantic or performance defect currently carries actionable work — every live item is dispositioned in §2 or §3 with its re-open trigger. An empty §1 is a real state, not an oversight: it means the next defect found gets a row here rather than joining a queue.

New semantic or performance defects belong here only while they have actionable work and a defined completion gate.

## 2. Deferred / ongoing-incremental (recorded with status; detail in [`INTERPRETER-FINDINGS.md`](INTERPRETER-FINDINGS.md))

Two kinds live here when present: a **deferred** item (parked or owner-accepted until its re-open trigger flips) and an **ongoing as-touched** refactor. A deferred item may be a safely guarded capability residual; it is not a silent semantic mismatch. A fully shipped item is deleted (its `IF<n>` finding + git are the record).

- **IG83 — Route A: general portable timezone-id support (owner-accepted deferred capability; Route B completed as IF155/IF165/IF166).** The enforced evaluator contract supports exact `{UTC, GMT, Europe/Berlin}`; Berlin uses the independently locked legacy-`java.util.TimeZone` history, explicit invalid ids fail as configuration errors, and known kernel-legal zones outside the set fail with the precise supported-scope diagnostic. The kernel accepts a wider Java `TimeZone` id domain, so this remains an honest product limit, not full timezone parity. **Re-open trigger:** a real consumer needs a non-Berlin zone or a publication wave promises full timezone parity. Then build one portable, deterministically versioned tzdb for JVM + JS and pin its version relationship to the kernel's JDK tzdb.

- **IG85 — A12 renders one stored decimal TWICE, and our single stored text can only match one of them (owner-deferred 2026-07-28).** Measured 2026-07-28 (KERNEL-FINDINGS "The canonical Document JSON …"): the serializer writes `bd.toPlainString()` while the runtime validates `bd.setScale(max(bd.stripTrailingZeros().scale(), minFractionalDigits)).toPlainString()`. They differ exactly on **fractional trailing zeros beyond `minFractionalDigits`** — `250.00` is written `250.00` and validated `250`. Our Document cell holds one text, so IF227's read normalization stores the write-faithful form: read→write identity on a document A12 itself wrote is preserved, and the eval side is left exactly where it stood before normalization existed (so this is a pre-existing residual, not one the change introduced). Observable only where the stripped zeros would change a text-reading check — locked as the single `Quantity="250.00"` row of `A12JsonIngressDiffTest.KNOWN_DIVERGENCES`. **Closing it requires a cell-model change** (carrying the converted value, or its two renderings, beside the text) in the interpreter's hottest data structure, which trades against the module's stated performance priority — an owner design call, not a local fix, which is why it sits here rather than in §1. **Re-open trigger:** a consumer hits it on real data, or the cell model is being reworked for another reason.
