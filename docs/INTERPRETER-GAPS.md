# interpreter — gaps

> **What this is** — the interpreter's peer of [`DEV-API-GAPS.md`](DEV-API-GAPS.md) and [`FEATURE-GAPS.md`](FEATURE-GAPS.md): the single tracking surface for **open `:interpreter` gaps, deferred items, and to-fix issues**. It exists so open work is easy to **track, report, and pick up** — and so [`INTERPRETER-FINDINGS.md`](INTERPRETER-FINDINGS.md) can be what a findings doc should be: **settled, verified knowhow** you read to warm up and not re-investigate (like `KERNEL-FINDINGS.md`), never a backlog of dispositions ("open / to fix / deferred"). Per the CLAUDE.md *"rationale is timeless; a disposition is status"* rule — the findings hold the timeless fact, this ledger holds the live status.
>
> **Lifecycle.** A gap is born here with an `IG<n>` code under the section matching its status (§1 open / §2 deferred / §3 out-of-scope). When it ships, three things happen **in the fix's own commit**: (1) its **rationale graduates to a numbered `IF<n>` finding** in [`INTERPRETER-FINDINGS.md`](INTERPRETER-FINDINGS.md) — that finding notes it "graduated from IGn"; (2) any code/test comment citing `IGn` is **repointed to `IFn`**; (3) the gap's row is **deleted from this ledger**. **There is no "fixed/shipped" section — we don't record fixed gaps.** A fixed gap is no longer a gap; **git is the history of *when/what* was fixed, and the `IFn` finding is the *why*** — a hand-kept "shipped" list would only duplicate both and rot. So this ledger only ever lists **live, unfinished work** (the already-shipped IF20-per-cell / IF21 / IF23 / IF24 / IF25 live as findings, not here). A **deferred** gap stays in §2 with its re-open trigger, and an **ongoing as-touched** refactor stays in §2 with its remaining-work note (it is progressing in increments, not parked — its shipped parts graduate to its `IF<n>` finding while the row stays until *all* of it lands); the technical detail of each gap lives in its cited `IF<n>` finding (the knowhow), this ledger holds only *what's left to do and why*.
>
> **Section invariant (the placement rule):** every section holds exactly one **live** status — **§1 = open, §2 = deferred / ongoing-incremental, §3 = out-of-scope**. A FULLY-shipped/graduated entry belongs in **none** of them: completing it *deletes* its row (see the lifecycle). So §1 reads `_None open._` whenever nothing is open — the marker every `-GAPS` ledger uses, so one grep rolls up the whole family (`GapLedgerTemplateGuardTest`) — and a fully-FIXED entry **anywhere** in this ledger is a bug in *this doc* — git already records the fix. (A partially-shipped *ongoing* refactor in §2 is not "fixed" — it stays until all of it lands.)

## 1. Open

- **IG136 — group expansion is opt-in at every operand site, and a 2026-08-14 audit names six more places the omission is reachable.** EIGHT instances of the class are measured and fixed, and a ninth prediction turned out to be a kernel REFUSAL ([IF287](INTERPRETER-FINDINGS.md#if287)); the root cause is that each operator resolves its own operands, so expanding a group is a step to remember rather than a chokepoint. The tell is that sites disagree with a sibling that got it right. **Audited candidates, none yet measured, ranked by the auditor:** `minMaxOperandVals` (the operand-list `Min`/`Max`) maps `evalExpr` over its args with no group branch, the shape whose `aggOperandVals` twin was measured wrong and fixed; `PolarityWalk.legacyStarFill` reads a group path as a field, mistyping VALUE/OMISSION; the value-list quantifier operands have no group check. `filteredStarCells` (`DateRangesOverlap`) is deliberately unexpanded and documented as such — listed only so a later reader does not re-derive it. **Actionable work:** for each, build the discriminator FIRST (a nested repeatable with **two** rows, the interesting value in row 2, and a bar only the correct reading clears), measure against both kernel strategies, and fix only what a measurement confirms — three of the five fixed instances were predicted correctly and one prediction about the authored-star arm was wrong, so the source read is a lead and never the basis. Kernel admission is unmeasured for several of these operand slots and must be established before a runtime row means anything. **Completion gate:** every candidate above is either locked by a tri-checked differential row or carries a recorded measurement showing the shape is inadmissible; and the shared expansion has one owner, so a new operand site cannot silently skip it. **The sentinel half, and a CORRECTION to what this row first claimed (2026-08-14).** An audit characterized `bindDepth = -1` precisely: five resolvers, three different formulas, and it is *path-relative* where any `bindDepth >= 0` is an absolute level count, so copying it onto a field BELOW the operand changes what it denotes — which produced IF287's fourth defect. `ast.expansionBindDepth` now resolves it to the operand's own absolute depth. **This row previously said "all five expansion sites call it" and "only one of the five has a measured discriminator"; a cold review falsified both.** There are **four** callers (`ExprEval.kt:129`, `:1522`, `:1797`, `PolarityWalk.kt:400`); the two sites that compute the same formula inline are `Interpreter.kt:1205` and `ExprEval.kt:1776`, and `comparedCells`' starred arm passes `bindDepth` raw through neither. So the one MEASURED fix is an inline literal and **zero of the normalizer's callers have a discriminator**. **A second correction, and it reframes the change:** `-1` is **unreachable from parsed input** — `Parser.pathFrom` only builds a `Star` when a star is present and its arithmetic is `>= 0` for absolute, `..`-relative and walk-up forms alike, and the only `.copy()` sites change `having` only. So the normalizer is a **no-op for every authored condition**, and is defensive hardening for hand-built AST (our own tests, and the public `Expr` API) rather than a behavioural fix. It is kept on that basis, not as a root-cause fix. **Actionable work:** give the normalizer a discriminator on a hand-built `Expr.Star` group operand with two repeatable levels below it; unify the two inline duplicates onto the helper so the "one owner" claim becomes true; and measure the two `Document` sites the audit ranked highest, which are NOT normalized — `containedFieldCells` → `starRows` at the default (`Document.kt:1245`) and `fillScope`/`instCells` (`:1271`), whose `-1` resolves against the FIELD's parent rather than the operand's and which feed the bare-group fill quantifiers, `FirstFilledValue`'s group operand, the semantic-index-selected group and `OverlayContext`. **The discriminator recipe:** a repeatable level *between* operand and field, plus a non-starred reference to a field ON that level to anchor iteration there — every current group-scope fixture is flat or guards on a non-repeatable field, so the plan binds `Once` and nothing is pinned.

**The remaining measured-nothing candidates, consolidated 2026-08-14 so none lives only in a session task list.** (a) `fillScopeInfo` (`Interpreter.kt:478-496`) is entered when ANY operand qualifies and then calls `fillScope` for EVERY operand without inspecting `having`, so `AtLeastOneFieldFilled(/Inv/Charges*, /Inv/Lines*/Amount Having …)` tallies the filtered operand UNFILTERED in validation while compute honours the filter — both operand shapes are ordinary and the estate contains nothing of that shape. (b) **Mode-BLIND operators that can never poison on the compute path**: `ValueListQuantEval.kt` has zero `computeMode` reads (a malformed cell is classified `Val.Unknown` at `:126` instead of throwing), as does `filteredStarCells` (`Interpreter.kt:1022-1028`, feeding both date-range predicates and `FieldValuesNotUnique`), and `config.groupPresence` is null on the compute path (`ComputationEngine.kt:167-190`), which silently also changes `GroupFilled`/`GroupNotFilled` and `NumberOfFilledGroups`. **Zero** compute-touching test files contain a value-list quantifier or either date-range predicate. (c) The compute-only poison prescans for `SumOfProducts` (`ExprEval.kt:758-765`), `NumberOfValueInFields` (`:734`) and `NumberOfFilledFields` (`:158`, `:172`) are unexercised. (d) `minMaxOperandVals` (`ExprEval.kt:1752`) still has the shape whose `aggOperandVals` twin was measured wrong and fixed — settle admission first with one `rule check` on `Min(/Order/Billing, 5)`. (e) `dateAggregate`/`minMaxEmpty` (`ExprEval.kt:1739-1749`) are group-BLIND: both test `declaredKind(a.path)`, null for a group, so `MinValue(/X/Dates*)` over a group of DATE fields takes the NUMERIC branch and the `0` empty identity — while `firstFilledEntityKind` (`:1725-1726`) already implements the correct group fallback. (f) `starVals` feeds four aggregates but only `Sum` is measured, and the empty-cell question is invariant for `Sum` (drop ≡ add 0) and **not** for the others: `MinValue(/Order/Billing)` with one operand empty yields the filled value here and `0` if the kernel substitutes the numeric empty — one row settles all four. (g) `expandMessageReference` dispatches on reference KIND, so an `outer`/`$` group reference inside a `Having` — deliberately `Ordinary` so it resolves in the enclosing row (`AstRefs.kt:146-148`) — is now converted to a wildcard; the measured basis was a top-level unstarred operand, not that shape. (h) Performance, against the module's co-#1 goal: `expandGroupStars` runs **per row** on hot paths and allocates a fresh `Expr.Star` per expanded field per row although every input is model-static, which is exactly what `ModelStaticPlans` exists to hoist.

**Also open from the same audit: the assertions and fixtures that hid the class** — nine differential classes compare only a boolean/count/value where the full `errorPath|type|referenced` signature was available (the fourth and fifth defects were invisible for 19 and 4 cases respectively for exactly this reason), and six fixtures place a nested repeatable with exactly ONE row, where "every row" and "row 1 only" predict the same output. Widening an assertion found a defect with no new fixture; that is the cheapest lever here.

- **IG135 — `FirstFilledValue` and the other field-list quantifiers have no group-operand runtime row, and the item was tracked only outside this repo.** [KF173](KERNEL-FINDINGS.md#kf173) records that `FirstFilledValue` routes through the same shared entity-list checker as `FieldValuesNotUnique`, whose group-operand runtime contract is now fully measured ([IF287](INTERPRETER-FINDINGS.md#if287): recursive expansion over every `(row × field)` cell below the operand, one message anchored at the error field's concrete first row). Routing through one checker is a **source-level reading, not a measured mechanism**, so nothing here establishes that the sibling carriers behave the same way — and the `FieldValuesNotUnique` history is the reason to distrust the inference: the same shape produced **two** silent wrong answers in our evaluator, each found only by a differential, each reporting a missed duplicate as "no error". **Why this row exists at all:** the residual was carried only in the a12-kernel-lean handover document, which lives outside version control on one machine, so an open item had no in-repo home and would have been lost with that file. **Actionable work:** extend `adapter.laws.FieldValuesNotUniqueGroupOperandDiffTest`'s pattern to `FirstFilledValue` and the six other field-list quantifiers — a group operand over the nesting fixture, the duplicate-in-nested-row-2 discriminator, a per-row error field for multiplicity, and the equivalent explicit field list as the control on each. **Completion gate:** every field-list quantifier that admits a group operand has a tri-checked runtime row (both kernel strategies + interpreter), or a measured static rejection recorded for the ones that do not admit the shape.

## 2. Deferred / ongoing-incremental (recorded with status; detail in [`INTERPRETER-FINDINGS.md`](INTERPRETER-FINDINGS.md))

Two kinds live here when present: a **deferred** item (parked or owner-accepted until its re-open trigger flips) and an **ongoing as-touched** refactor. A deferred item may be a safely guarded capability residual; it is not a silent semantic mismatch. A fully shipped item is deleted (its `IF<n>` finding + git are the record).

- **IG83 — Route A: general portable timezone-id support (owner-accepted deferred capability; Route B completed as IF155/IF165/IF166).** The enforced evaluator contract supports exact `{UTC, GMT, Europe/Berlin}`; Berlin uses the independently locked legacy-`java.util.TimeZone` history, explicit invalid ids fail as configuration errors, and known kernel-legal zones outside the set fail with the precise supported-scope diagnostic. The kernel accepts a wider Java `TimeZone` id domain, so this remains an honest product limit, not full timezone parity. **Re-open trigger:** a real consumer needs a non-Berlin zone or a publication wave promises full timezone parity. Then build one portable, deterministically versioned tzdb for JVM + JS and pin its version relationship to the kernel's JDK tzdb.
