# interpreter — gaps & open issues

> **What this is** — the interpreter's peer of [`DEV-API-GAPS.md`](DEV-API-GAPS.md) and [`FEATURE-GAPS.md`](FEATURE-GAPS.md): the single tracking surface for **open `:interpreter` gaps, deferred items, and to-fix issues**. It exists so open work is easy to **track, report, and pick up** — and so [`INTERPRETER-FINDINGS.md`](INTERPRETER-FINDINGS.md) can be what a findings doc should be: **settled, verified knowhow** you read to warm up and not re-investigate (like `KERNEL-FINDINGS.md`), never a backlog of dispositions ("open / to fix / deferred"). Per the CLAUDE.md *"rationale is timeless; a disposition is status"* rule — the findings hold the timeless fact, this ledger holds the live status.
>
> **The lifecycle.** A gap is born here with an `IG<n>` code under the section matching its status (§1 open / §2 deferred / §3 out-of-scope). When it ships, three things happen **in the fix's own commit**: (1) its **rationale graduates to a numbered `IF<n>` finding** in [`INTERPRETER-FINDINGS.md`](INTERPRETER-FINDINGS.md) — that finding notes it "graduated from IGn"; (2) any code/test comment citing `IGn` is **repointed to `IFn`**; (3) the gap's row is **deleted from this ledger**. **There is no "fixed/shipped" section — we don't record fixed gaps.** A fixed gap is no longer a gap; **git is the history of *when/what* was fixed, and the `IFn` finding is the *why*** — a hand-kept "shipped" list would only duplicate both and rot. So this ledger only ever lists **live, unfinished work** (the already-shipped IF20-per-cell / IF21 / IF23 / IF24 / IF25 live as findings, not here). A **deferred** gap stays in §2 with its re-open trigger, and an **ongoing as-touched** refactor stays in §2 with its remaining-work note (it is progressing in increments, not parked — its shipped parts graduate to its `IF<n>` finding while the row stays until *all* of it lands); the technical detail of each gap lives in its cited `IF<n>` finding (the knowhow), this ledger holds only *what's left to do and why*.
>
> **Section invariant (the placement rule):** every section holds exactly one **live** status — **§1 = open, §2 = deferred / ongoing-incremental, §3 = out-of-scope**. A FULLY-shipped/graduated entry belongs in **none** of them: completing it *deletes* its row (see the lifecycle). So §1 reads "(none)" whenever nothing is open, and a fully-FIXED entry **anywhere** in this ledger is a bug in *this doc* — git already records the fix. (A partially-shipped *ongoing* refactor in §2 is not "fixed" — it stays until all of it lands.)
>
> **Scope.** `:interpreter` only — the kernel-free Kotlin evaluator (parser, evaluation semantics, model loader, the differential/perf harnesses' interpreter side). dmkit (rulekit/modelkit/edit) authoring gaps go to [`DEV-API-GAPS.md`](DEV-API-GAPS.md); kernel-coverage classification stays in the MVK / RT-semantics / grammar ledgers.

  **Stability analysis (done 2026-07-11, broadened 2026-07-19 — LEFT OPEN, not implemented).** An overlay-derived index column or correlation-bucket map is stable across one computation's row loop *under a condition*: in `ComputationEngine.computeInstances` the mutable `overlay`/`cleared`/`poisoned` maps are written only for the CURRENT computation's TARGET cells (`computeAt` writes them *after* `evalComputation` returns), and prior computations' writes have all landed before this computation's loop begins (dependency order). Therefore every different field used as a semantic-index column, correlation join key, or filtered target is fixed for the duration of the loop, and within a single row's evaluation nothing is written at all. Those derived views are cacheable once per computation. The **unstable cases** are self-referential computations whose target writes can change the same index column, join key, or correlation target being read; their own writes shift the view mid-loop. A correct cache must live at the `computeInstances` level, be invalidated when the loop advances to the next computation, and guard every self-referential dependency shape rather than only the semantic-index case. It must land with the perf cases and compute differentials, never as an unmeasured memoization.

The harness times `validateFull` (which now fails loud on unsupported, IF139, rather than silently dropping); the explicit `unsupported.isEmpty()` + tri-engine preflight before timing is still owed here. IG60 and IG98 are the distinct algorithmic risks this governance must expose, and IG94 must derive the scenario-to-capability/strategy coverage.

- **IG79 — NFR-F1/F2 relative-footprint certification is not implemented (footprint-governance gap, found and contract-anchored 2026-07-18).** Low footprint is explicitly **relative** and subordinate to the performance benefit of bounded caches: indices/hash maps/memos are allowed and advised. The candidate contract compares equivalent interpreter and kernel-backed capability, ratchets previous-release artifacts/closures, and requires cache-lifetime + warm-plateau checks plus multi-scale `N, 2N, 4N, 8N` runtime-footprint fitting. Today only import purity is guarded; there is no resolved-dependency size task, production npm package measurement, retained-heap/allocation probe, or plateau/growth gate. Existing artifacts provide plausibility only: the JVM closure estimate (~23%) uses a conservative named-jar comparator rather than equivalent fresh-consumer graphs; the JS development modules are not a production package; and the repeatedly cited 33 MB native / 119 MB JVM pair was measured on 2026-06-15, before the interpreter runtime existed, so it is neither a same-revision nor an equal-capability comparison. **Remaining work now the numerical bars' contract is ratified (IF137):** define exact byte bases for thin artifacts, packed artifacts, resolved non-JDK closures, and native/JVM images; construct equivalent fresh-consumer dependency graphs and rebuild both delivery artifacts from one clean commit; add reproducible JVM/npm measurements; and run forked JVM+Node retained-heap/allocation scenarios with an explicit post-GC method, warmup/plateau criterion, owner-release check, Node `--expose-gc`, and logical cache-entry counts so GC noise cannot accidentally satisfy or fail the fitted exponent. Record dated baselines and require every owner-scoped cache to release or plateau as its contract says. A cache that raises memory but measurably improves NFR-S/P is an acceptable reviewed trade, not a failure.

- **IG83 — the interpreter implements only UTC/GMT and modern Berlin while the kernel accepts the Java timezone-id domain and full history (correctness/capability gap, broadened from IF128's certificate residual 2026-07-19).** `ModelTimeZone.of` accepts only UTC/GMT/Europe/Berlin, and its Berlin implementation encodes only the EU regime in force since 1996. Kernel 30.8.1 does not whitelist those two documented zones: its structural check accepts Java `TimeZone` IDs except unknown IDs that silently collapse to GMT (literal GMT remains valid), and runtime parsing/arithmetic uses the selected zone's database history. Therefore a valid model using another zone is loud-rejected by the interpreter, and legal pre-1996 Berlin values can evaluate differently. The certificate's “small Berlin-history caveat” understates both the accepted zone domain and the historical transition/gap/overlap surface. **Required work:** first enumerate the kernel-accepted zone-id contract and characterize representative non-Berlin zones plus historical Berlin transitions against both kernel strategies. Then provide a portable tzdb-backed abstraction in common code (with deterministic versioning) and lock it on JVM + JS, including instant arithmetic, wall-day arithmetic, gaps, overlaps, and clock constants. If the product instead chooses a narrower supported-zone/date contract, that is an owner decision and must be enforced before evaluation with a precise diagnostic; “documented values” or “realistic dates” cannot silently narrow the kernel's legal domain.

- **IG87 — legal included-model rule/computation reference shapes refuse instead of evaluating (open capability gap, promoted from the retirement-accepted G1′ residual 2026-07-19).** The kernel-free relativizer handles relative conditions and single-root-group absolute `/RG/rest` references, but not MODEL_ROOT-absolute references, a bare `/RG` group reference, or outer-correlated absolute `[$/…]` references after the included root is mounted away. `expandForEval` detects those shapes and emits `RK_INTERPRETER_INCLUDE_RULES_UNSUPPORTED`, so the failure is loud and safe rather than a silent wrong result; it is nevertheless a legal model class the kernel evaluates, and the module's standing exactness goal makes owner acceptance for the 2026-07-12 flag retirement historical context, not a reason to keep the gap deferred indefinitely. **Required work:** characterize all three reference families at mount depth 0/1/n against kernel expansion and both evaluation strategies, extend the shared relativizer without losing the refusal for any still-unhandled shape, and differentially lock rules and computations over each form. If the product deliberately excludes a form, enforce and document that supported-input boundary as an explicit contract decision.

- **IG88 — `supportedCharacters` loses combined-grapheme atomicity by flattening legal sequence entries (source-demonstrated correctness gap, 2026-07-19; differential pending).** Kernel charset parsing distinguishes singleton/range entries from legal multi-code-point graphemes and stores the latter in a trie; runtime matching consumes a complete configured sequence atomically. `LegalCharset.ofSupportedCharacters` instead flattens every non-range entry into independent UTF-16 units, and formal validation tests each input code point independently. For a legal entry such as decomposed `e` + combining acute, the interpreter therefore admits the full sequence but also incorrectly admits the bare base, the bare combining mark, reversed order, and repeated components. Current locks cover BMP singletons/ranges only; the original certificate nevertheless marked the model slot GREEN before this source audit. Supplementary-plane charset definitions are not the discriminator—the kernel rejects surrogate-bearing definitions. **Required work:** characterize valid combined and overlapping sequence matching against both kernel strategies; implement an original portable atomic-sequence/trie matcher while retaining the fast BMP/range path; prove the full sequence is accepted without admitting its components; and lock model-slot + consumer-SPI behavior on JVM + JS with a scale guard for the hot membership path.

- **IG89 — Kotlin/JS decimal arithmetic and rendering violate the common MathContext(50)/plain-decimal contract (confirmed cross-platform correctness gap, 2026-07-19).** The common `Dec` contract and JVM actual apply 50-significant-digit HALF_UP semantics to multiplication, division, and powers. The JS actual delegates multiplication exactly and division/negative powers to big.js's host-global/default `Big.DP`/`Big.RM` (normally 20 decimal places), so large products and non-terminating quotients differ. It also parses `Big.toString()` as if it were plain notation, although big.js emits exponent form at ordinary extremes; precision/scale accounting and computed storage/display can then be corrupted. Existing JS tests exercise only small exact arithmetic and low-range rounding. **Required work:** isolate the JS decimal context from mutable host globals—prefer a cloned/configured constructor—then implement the 50-significant-digit HALF_UP contract and plain-decimal rendering for every operation. Add JVM/Node parity vectors for >50-digit products, non-terminating division, positive/negative powers, rounding boundaries, exponent-form extremes, and computed-field storage/display; differentially pin the same legal cases to both kernel strategies where available.

- **IG90 — Kotlin/JS rejects or misinterprets kernel-valid Java regular expressions (confirmed legal-input correctness gap plus condition hot-path cost, 2026-07-19).** Conditions (`PatternMatched`/`PatternViolated`), declared field patterns, and predefined-type patterns all use common Kotlin `Regex`: Java `Pattern` on JVM and JS `RegExp` on Node/browser. Kernel validation/runtime uses Java `Pattern` and its model check rejects only a limited subset; live checks accept constructs such as inline flags `(?i)` and `\R`/`\h`, which JS `RegExp` rejects under the generated flags. A legal model can therefore fail during JS model construction/evaluation or acquire different matching semantics. Declared field and predefined-type patterns are already constructed once with their model objects; the hot construction defect is the literal condition-pattern path, which recompiles the same regex per evaluated row. **Required work:** derive and version the full kernel-legal pattern contract, then use either a portable regex engine or a proven compatibility translation for every legal construct; a loud, structurally enforced subset is only an interim safety boundary, not exact parity. Cover whole-match behavior, flags, Unicode classes, escaping, field constraints, predefined types, and both condition operators on JVM + JS against both kernel strategies, with no host `SyntaxError`. Compile lazily on first relevant use, require compile count no greater than the distinct model-static patterns per engine, and add a pattern-heavy N/4N gate so the fix removes per-row compilation without regressing first-answer latency.

- **IG91 — there is no single enforced prepared-model boundary, and `model seed` bypasses the CLI's expander (source-demonstrated preparation defect, 2026-07-19).** `ModelLoader` explicitly accepts only expanded, self-contained, name-path-keyed models; unresolved `TypeDefType` silently becomes STRING and the flat scan trusts raw IDs as paths. The eval/compute/rule commands prepare input through `ModelReader.expand`, but `ModelSeedCommand` reads raw DM-JSON and calls `InterpreterModelLoader.load` directly. Includes, imported typedefs, or opaque ids can therefore produce a structurally plausible but incomplete/wrong seed rather than the semantics the model declares. The corpus differential hides this class because `CorpusModelPreparer` performs its own expansion/type/ID normalization before loading. **Required root work:** introduce one preparation boundary shared by every CLI consumer, including seed, and make the common loader either consume an explicit prepared-model type/marker or loudly reject raw includes, unresolved typedefs, and non-name-path ids. Lock the class with own-domain include + typedef + opaque-id fixtures that compare seed structure/value constraints with the prepared model. Coordinate with IG68: that item owns a complete commonMain assembler for standalone JS; this item owns preventing any consumer from bypassing preparation today.

- **IG92 — custom field-type rejection loses the validator's observable error code (confirmed exactness gap, reclassified from certificate DOC-EQUIV 2026-07-19).** The kernel's `ICustomFieldType` validator returns the project-specific rejection key that becomes the cell's formal error code. The interpreter SPI returns only `Boolean`, and `AutoChecks` emits the constant `customFieldTypeInvalid`; the existing differential compares downstream suppression, not the per-cell code. Unlike intentionally original human wording, the code is a machine-observable contract used by consumers and the module's “bit-for-bit on every legal input” rule does not authorize replacing it. **Required work:** evolve the SPI to return a typed accepted/rejected result carrying the rejection code and any kernel-observable metadata, thread it through formal messages and suppression, and tri-lock both an accepted value and multiple project-specific rejection keys against dynamic + generated-Java kernels. If code identity is deliberately excluded, that needs an explicit owner-level exactness-contract exception rather than a certificate footnote.

- **IG93 — bare-group computation fill quantifiers may violate the kernel's ordered early-stop/poison semantics (source-predicted correctness gap, 2026-07-19; discriminator probe required).** Field/star computation quantifiers use ordered scans so a decisive early operand can prevent a later invalid read, matching the kernel. The bare-group branch instead derives an aggregate `fillScope`, checks for any unknown before synthesizing the TRUE/FALSE counts, and its own source comment calls this an approximation. Kernel source evaluates the entity list in declaration order with quantifier-specific early return. No current differential distinguishes “early decisive field, later formally invalid field” for a bare group in compute mode. **Required work:** first tri-probe each legal group-fill quantifier with both operand orders and both kernel strategies. If the predicted split is confirmed, preserve declared contained-field traversal order and stop at the same decisive point without losing nested-group scope; lock VALUE/CLEARED/ERRORED outcomes and the absence/presence of the poisoning read. If the kernel result refutes the prediction, record the finding and delete this row.

- **IG95 — legal `RepetitionNotUnique` boolean compositions degrade to unsupported (confirmed capability divergence, 2026-07-19).** `RepetitionNotUniqueEvaluator` recognizes only a standalone predicate or exactly one top-level conjunct in an `And` tree. An RNU below `Or` or nested inside another boolean operand falls through to the generic interpreter, where it is not a `PredicateOp`, and validation records it as unsupported. Live kernel checks accept both `RepetitionNotUnique(key) Or otherCondition` and `guard And (RepetitionNotUnique(key) Or otherCondition)`; multiple RNU predicates in one rule remain kernel-invalid and are not part of this gap. The existing unit test deliberately locks the unsupported result, and no dynamic/static differential covers the legal compositions. **Required root work:** model RNU as a normal per-row 3VL/polarity leaf backed by one call-scoped duplicate cache, so arbitrary legal `And`/`Or` composition does not rebuild the cache. Tri-lock the two accepted discriminator shapes plus FALSE/UNKNOWN/OMISSION siblings, partial validation, dynamic + generated-Java behavior, and JVM + JS.

- **IG96 — computation `toleranceRangeOp` is dropped, so implicit validation over-fires (source-confirmed legal-feature divergence, 2026-07-19; end-to-end differential pending).** DM-JSON serializes a computation alternative's `toleranceRangeOp`, and kernel code generation replaces strict `target != operation` with the matching `DiffersWithToleranceRange{1,2,5,10}` condition. `ModelLoader` and `ComputationAlternative` retain only precondition + operation, while `ParsedModel` always synthesizes strict inequality and explicitly admits the narrower behavior. A stored target value inside the declared tolerance can therefore fire an implicit computation-validation error only in the interpreter. **Required work:** carry the field as a closed tolerance enum through the model/loader, validate unknown values loudly, synthesize the corresponding `Cond.Tolerance`, and tri-lock equal/inside-boundary/at-boundary/just-outside cases for every band, including guarded/tiered alternatives and JVM + JS. Keep `errorCodesToSuppress` separate: it is a structural/codegen preamble, not this runtime comparison semantic.

## 3. Out of scope (won't build unless the trigger flips; recorded so it's not re-investigated)

- **German render target unparseable by the interpreter** (was IG28) — **out-of-scope, verified 2026-07-06.** `DslRenderer(ConditionLanguage.DE)` emits `Und`/`FeldAngegeben`/`Heute`/`@Von`; the interpreter's parser is EN-only. This is **correct by construction, not a gap**, because the interpreter only ever parses **stored** conditions, and the kernel stores every `errorCondition` in **English keywords regardless of authoring language** — confirmed against the real German A12 Tools workspace (2025.06-ext5): its stored conditions read `GroupFilled(...)`/`FieldNotFilled(...)`/`And`/`MinValue(...)`, not `Und`/`FeldAngegeben`. The German render is a **display-only** transform, never round-tripped back through the interpreter (dmtool's `model eval`/`rule eval` read the stored English form; authoring accepts DE via the kernel's language-parametric parser on the JVM, not the interpreter). Re-open trigger: the kernel starts persisting conditions in the authoring language, or a consumer needs the interpreter to parse a DE-rendered string. Detail: KERNEL-FINDINGS "stored conditions are canonical English".
- **`SumOfProducts` over plain (non-repetition-list) fields** — **parity-by-construction, probe-confirmed 2026-07-06** (was IG33). `SumOfProducts(Qty, Price)` over two plain `FieldRef`s is **rejected by the kernel at codegen** with `MVK_REPEATABLE_LEVEL_REQUIRED` ("All fields must be repeatable at least at one layer"), so it never appears in a valid/loadable model — the interpreter's `sumOfProducts` (which resolves both operands as stars) is unreachable on any valid input. No interpreter change; the RuleValidator/kernel is the gate. Re-open trigger: a kernel upgrade that starts accepting a non-repeatable `SumOfProducts`. Detail: IF51.
- **`mandatoryGroup`** (`FEHLER_PFLICHTKONTEXT`) — **source-confirmed unreachable in 30.8.1**: the code is defined but **never emitted**, and **no DM-JSON property declares a group mandatory**, so it can't fire on any loadable model (parity by construction). Was the deferred IG3; re-check on a kernel upgrade. Detail: KERNEL-FINDINGS "mandatoryGroup is a DEAD code in 30.8.1".
- **custom-ref error-entity attribution** (`IRule.getCustomRefErrorEntitiesIfFilled/IfNotFilled`) — **source-confirmed unwired in 30.8.1**: the md-model rule mapping returns empty pending A12K-2281/2361, so the kernel always uses its default error-entity attribution (which the interpreter matches; `CustomConditionDiffTest` locks the CustomCondition error field). Was the deferred IG8; re-check on a kernel upgrade. Detail: KERNEL-FINDINGS "getCustomRefErrorEntities… is UNWIRED in 30.8.1".
- **`getRoundingMode`** on a computation — inert in the runtime (rounding is explicit via the round operators). Detail: IF22.
- **`uniqueValue` (`FEHLER_MULTI_SELECT`)** — was the deferred IG2; **out-of-scope, rationale CORRECTED 2026-06-27** (the earlier "the construct is unmodeled, interpreter reports it unsupported" reasoning was WRONG — a `usageType: "multi-select"` group IS a serialized, loadable construct that **modelkit already authors** (`multiSelectGroup`), and 6 real ones ship in the 2025.06-ext5 workspaces). The real reason it's parity-by-construction: the multi-select value-uniqueness check **is generated by NO kernel evaluation path in 30.8.1** — `AutogeneratedRulesService` (md-runtime) has no multi-select method, AND no `IAutogeneratedRule.getGenerationType()` returns `UNIQUE_VALUE`, so the `CodeGenRuleDefinition.case UNIQUE_VALUE` is unreachable dead code (the runtime-and-codegen sibling of the dead `mandatoryGroup`). **Both** kernel strategies produce nothing, so the interpreter loads the group as a plain repeatable group and (correctly) fires no `uniqueValue` — matching both, NOT a silent-wrong gap and NOT a runtime-vs-codegen divergence. Re-open trigger: a kernel upgrade that wires `UNIQUE_VALUE` into `AutogeneratedRulesService` or an `IAutogeneratedRule`. Detail: KERNEL-FINDINGS "multiSelect value uniqueness is DEAD code"; locked by `adapter.laws.MultiSelectUniquenessDiffTest`.
- **formal-error message TEXT** (byte-identical to the kernel's) — was the deferred IG6; **out-of-scope by the license boundary**: the kernel's formal-error text is German-only and **EUPL/commercial-licensed** (IF3) — it cannot be copied into the kernel-free interpreter. The interpreter emits its own English wording; the *code* / pointer / severity already match the kernel (the parts a consumer acts on). Re-open trigger: a consumer needs verbatim kernel text AND a license-clean source for it exists. Detail: IF (formal errors) / KERNEL-INTEGRATION-NOTES.
