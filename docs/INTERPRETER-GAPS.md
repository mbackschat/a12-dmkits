# interpreter — gaps

> **What this is** — the interpreter's peer of [`DEV-API-GAPS.md`](DEV-API-GAPS.md) and [`FEATURE-GAPS.md`](FEATURE-GAPS.md): the single tracking surface for **open `:interpreter` gaps, deferred items, and to-fix issues**. It exists so open work is easy to **track, report, and pick up** — and so [`INTERPRETER-FINDINGS.md`](INTERPRETER-FINDINGS.md) can be what a findings doc should be: **settled, verified knowhow** you read to warm up and not re-investigate (like `KERNEL-FINDINGS.md`), never a backlog of dispositions ("open / to fix / deferred"). Per the CLAUDE.md *"rationale is timeless; a disposition is status"* rule — the findings hold the timeless fact, this ledger holds the live status.
>
> **Lifecycle.** A gap is born here with an `IG<n>` code under the section matching its status (§1 open / §2 deferred / §3 out-of-scope). When it ships, three things happen **in the fix's own commit**: (1) its **rationale graduates to a numbered `IF<n>` finding** in [`INTERPRETER-FINDINGS.md`](INTERPRETER-FINDINGS.md) — that finding notes it "graduated from IGn"; (2) any code/test comment citing `IGn` is **repointed to `IFn`**; (3) the gap's row is **deleted from this ledger**. **There is no "fixed/shipped" section — we don't record fixed gaps.** A fixed gap is no longer a gap; **git is the history of *when/what* was fixed, and the `IFn` finding is the *why*** — a hand-kept "shipped" list would only duplicate both and rot. So this ledger only ever lists **live, unfinished work** (the already-shipped IF20-per-cell / IF21 / IF23 / IF24 / IF25 live as findings, not here). A **deferred** gap stays in §2 with its re-open trigger, and an **ongoing as-touched** refactor stays in §2 with its remaining-work note (it is progressing in increments, not parked — its shipped parts graduate to its `IF<n>` finding while the row stays until *all* of it lands); the technical detail of each gap lives in its cited `IF<n>` finding (the knowhow), this ledger holds only *what's left to do and why*.
>
> **Section invariant (the placement rule):** every section holds exactly one **live** status — **§1 = open, §2 = deferred / ongoing-incremental, §3 = out-of-scope**. A FULLY-shipped/graduated entry belongs in **none** of them: completing it *deletes* its row (see the lifecycle). So §1 reads `_None open._` whenever nothing is open — the marker every `-GAPS` ledger uses, so one grep rolls up the whole family (`GapLedgerTemplateGuardTest`) — and a fully-FIXED entry **anywhere** in this ledger is a bug in *this doc* — git already records the fix. (A partially-shipped *ongoing* refactor in §2 is not "fixed" — it stays until all of it lands.)
>
> **Current state.** IG111 shipped as [IF263](INTERPRETER-FINDINGS.md#if263), IG112 as [IF262](INTERPRETER-FINDINGS.md#if262), and IG113 as [IF266](INTERPRETER-FINDINGS.md#if266) + [IF267](INTERPRETER-FINDINGS.md#if267) + [IF268](INTERPRETER-FINDINGS.md#if268) — it was scoped as one `AtLeastOne` divergence and decomposed under measurement into three independent partial-relevance defects (a relevance-blind index-duplicate relation, a value-list scan reading non-relevant cells, and a rule-run gate comparing repetition levels the rule never bound). New semantic or performance defects belong in §1 only while they have actionable work and a defined completion gate.
>
> **Scope.** `:interpreter` only — the kernel-free Kotlin evaluator (parser, evaluation semantics, model loader, the differential/perf harnesses' interpreter side). dmkit (rulekit/modelkit/edit) authoring gaps go to [`DEV-API-GAPS.md`](DEV-API-GAPS.md); kernel-coverage classification stays in the MVK / RT-semantics / grammar ledgers.

## 1. Open

- **IG114 — a SPARSE repeatable row: the kernel's document builder materializes the gap, the interpreter's does not.** Observed 2026-08-08 while delta-debugging an unrelated seed. Feeding **identical placements** to both engines — `/Plan[1]`, `/Plan/A[1,5]`, `/Plan/A/Dept[1,5,1]="D5"`, `/Plan/A/Va[1,5,1]` empty, i.e. only repetition **5** addressed — dynamic Groovy fires `mandatoryField|OMISSION_ERROR` at `/Plan[1]/A[1]/Dept` through `A[4]/Dept`, treating rows 1–4 as present-and-empty; the interpreter fires nothing and sees one row. Rows placed at repetition 2 and 4 behave the same way (1 and 3 firings respectively), so the kernel materializes `1..n-1` for a row addressed at `n`.

  **Reachability is settled — corrected 2026-08-09 after a cold review challenged it, and the answer narrows the gap rather than closing it.** The question the row previously called open ("does canonical Document JSON reach this shape?") has been measured on both sides and the answer is **no**: `{"Staffing":{"PlanName":"Q3","Demand":[{},{},{},{},{"Department":"D5","Headcount":null}]}}` through the kernel's own JSON ingress is rewritten **byte-identically** and yields four `mandatoryField` codes, i.e. `{}` is an *instantiated empty row*, not an absent coordinate; the interpreter's reader agrees, instantiating five rows for five array elements (`DocumentTransportTest.anOverRepeatedRowStaysRepresentableAndANonRepeatableExcessRowRefusesToEncode`). So there is **no divergence on the JSON path** — and that is the path every dmtool evaluation verb takes (`InterpreterEngine` goes through `InterpreterModelLoader.document(documentJson, def)`).

  **What is left is the PLACEMENT seam** — `Document.group`/`field` against the kernel's `IDocumentFactory`. The kernel materializes predecessor rows there and the interpreter does not, so the two document *builders* disagree even though the two *readers* do not. *Corrected within the same day, 2026-08-09: this row first called that seam "internal" on the strength of `eval.Document`'s absence from `interpreter/api/interpreter.api`. That is the wrong inference.* The `eval` package is excluded from the **frozen ABI contract** by `interpreterEngineSubpackages`, whose own build comment says these declarations "stay public only where another module still consumes them during the pre-1.0 migration; publishing must not freeze them" — they are ordinary public Kotlin, so a consumer compiling against the artifact can call `document.group(path, 1, 5)` today and get an answer the kernel would not give. In-repo the seam additionally carries a shipped verb: `model seed` (`ModelSeedCommand`) builds its document by placement, as do the fuzz generators and the shrinker.

  **Blocks:** the public placement builder is observably divergent, although no known shipped in-repo producer currently emits a gap. `SeedGenerator`, `model seed`, and `PreparedModel.documents.seedDocument()` build contiguous rows; canonical Document JSON materializes every array element; the shrinker is the one known in-repo source of sparse coordinates. `ApplyCommand` edits models rather than Documents, so the previous claim that CLI apply/edit lay in the blast radius was false. **Disposition:** matching the kernel means auto-materializing rows `1..n-1` whenever a row is addressed at `n`. That changes `instantiatedRows` for the public `Document`/`asSink` seam and every placement-backed seed, conformance, fuzz, perf, reader-copy, and test consumer. Measure those consumers before choosing the shared root. Teaching only the shrinker to refuse the shape would close a false-divergence risk while leaving the public builder mismatch live. Deliberately not folded into the parallel-join slice that found it under the convergence gate: different mechanism, different denominator.

- **IG116 — no performance scenario has a NUMBER index field, so the index-key projection's cost is unmeasurable.** [IF272](INTERPRETER-FINDINGS.md#if272) put `indexKeyOf` on three per-cell paths: the parallel join's `Document.indexMap` (once per index cell per parent row), `AutoChecks.duplicateIndexCells`, and `ComputationEngine.invalidIndexParentCoords`. On a **String** index field the function returns its argument after one enum comparison, so the added cost is noise — and **every index field in the performance estate is a String**: `PerfCatalog`'s `LineKey` is declared `StringType` in the hand-written model JSON, and the builder-side `VKey`/`PKey`/`SubKey` are all `FieldKind.STRING`. On a **Number** index field the same call parses a decimal (`decOrNull`) and re-renders it (`Dec.display`) per cell. So `scripts/perf.sh gate` passing after IF272 is honest evidence that nothing regressed *on the measured scenarios* and **no evidence at all** about the case the change actually touches.

  This is a pre-existing hole that IF272 made newly relevant rather than one IF272 introduced; before it, a Number index field had no special cost and no scenario either. **Blocks:** a performance claim for the Number path. A sub-quadratic growth gate alone is the wrong oracle for constant per-cell parse/render cost, and validation does not execute `ComputationEngine.invalidIndexParentCoords`. **What would settle it:** paired Number-index validation and computation scenarios measured against both kernel strategies at fixed sizes, with an absolute or kernel-relative regression bound; add a growth row only as an additional catastrophe check. The validation row must reach parallel join plus auto-uniqueness, and the computation row must reach invalid-index detection. Raised 2026-08-09 while assembling the review packet for the IF272 slice; measurement prescription corrected after the testing-architecture review.

## 2. Deferred / ongoing-incremental (recorded with status; detail in [`INTERPRETER-FINDINGS.md`](INTERPRETER-FINDINGS.md))

Two kinds live here when present: a **deferred** item (parked or owner-accepted until its re-open trigger flips) and an **ongoing as-touched** refactor. A deferred item may be a safely guarded capability residual; it is not a silent semantic mismatch. A fully shipped item is deleted (its `IF<n>` finding + git are the record).

- **IG83 — Route A: general portable timezone-id support (owner-accepted deferred capability; Route B completed as IF155/IF165/IF166).** The enforced evaluator contract supports exact `{UTC, GMT, Europe/Berlin}`; Berlin uses the independently locked legacy-`java.util.TimeZone` history, explicit invalid ids fail as configuration errors, and known kernel-legal zones outside the set fail with the precise supported-scope diagnostic. The kernel accepts a wider Java `TimeZone` id domain, so this remains an honest product limit, not full timezone parity. **Re-open trigger:** a real consumer needs a non-Berlin zone or a publication wave promises full timezone parity. Then build one portable, deterministically versioned tzdb for JVM + JS and pin its version relationship to the kernel's JDK tzdb.
