# interpreter — gaps

> **What this is** — the interpreter's peer of [`DEV-API-GAPS.md`](DEV-API-GAPS.md) and [`FEATURE-GAPS.md`](FEATURE-GAPS.md): the single tracking surface for **open `:interpreter` gaps, deferred items, and to-fix issues**. It exists so open work is easy to **track, report, and pick up** — and so [`INTERPRETER-FINDINGS.md`](INTERPRETER-FINDINGS.md) can be what a findings doc should be: **settled, verified knowhow** you read to warm up and not re-investigate (like `KERNEL-FINDINGS.md`), never a backlog of dispositions ("open / to fix / deferred"). Per the CLAUDE.md *"rationale is timeless; a disposition is status"* rule — the findings hold the timeless fact, this ledger holds the live status.
>
> **Lifecycle.** A gap is born here with an `IG<n>` code under the section matching its status (§1 open / §2 deferred / §3 out-of-scope). When it ships, three things happen **in the fix's own commit**: (1) its **rationale graduates to a numbered `IF<n>` finding** in [`INTERPRETER-FINDINGS.md`](INTERPRETER-FINDINGS.md) — that finding notes it "graduated from IGn"; (2) any code/test comment citing `IGn` is **repointed to `IFn`**; (3) the gap's row is **deleted from this ledger**. **There is no "fixed/shipped" section — we don't record fixed gaps.** A fixed gap is no longer a gap; **git is the history of *when/what* was fixed, and the `IFn` finding is the *why*** — a hand-kept "shipped" list would only duplicate both and rot. So this ledger only ever lists **live, unfinished work** (the already-shipped IF20-per-cell / IF21 / IF23 / IF24 / IF25 live as findings, not here). A **deferred** gap stays in §2 with its re-open trigger, and an **ongoing as-touched** refactor stays in §2 with its remaining-work note (it is progressing in increments, not parked — its shipped parts graduate to its `IF<n>` finding while the row stays until *all* of it lands); the technical detail of each gap lives in its cited `IF<n>` finding (the knowhow), this ledger holds only *what's left to do and why*.
>
> **Section invariant (the placement rule):** every section holds exactly one **live** status — **§1 = open, §2 = deferred / ongoing-incremental, §3 = out-of-scope**. A FULLY-shipped/graduated entry belongs in **none** of them: completing it *deletes* its row (see the lifecycle). So §1 reads `_None open._` whenever nothing is open — the marker every `-GAPS` ledger uses, so one grep rolls up the whole family (`GapLedgerTemplateGuardTest`) — and a fully-FIXED entry **anywhere** in this ledger is a bug in *this doc* — git already records the fix. (A partially-shipped *ongoing* refactor in §2 is not "fixed" — it stays until all of it lands.)
>
> **Current state.** §1 lists what is open; read it rather than this paragraph — it held drained from 2026-09-05, IG149 having closed as measured parity across all three routes a widened fragment vocabulary opened up ([IF327](INTERPRETER-FINDINGS.md#if327)), until IG152 opened on 2026-09-18 carrying NFR #1's un-instantiated standing anchor — narrowed twice on 2026-09-19, first to the timed and native rows once the deterministic byte rows landed and then to cost per unit once the work gate did. §2 carries the deferred rows with their re-open trigger or remaining work: **IG151** (a `MODEL_ROOT` mount's `usageType` survives in both clean-room readers), **IG143** (a hand-built interpreter document is a route hybrid), **IG141** (DateRange shared-format declaration order), **IG139** (the `group-star expansion @8000` anchor sits just under its own ceiling), **IG137** (performance tooling and reporting residuals), and **IG83** (portable timezone-id support, Route A); §3 carries the out-of-scope decisions. A **shipped** gap appears nowhere here: its rationale graduated to a numbered `IF<n>` finding that names the `IGn` it came from, so a code comment citing `IGn` resolves by grepping [`INTERPRETER-FINDINGS.md`](INTERPRETER-FINDINGS.md), with one measured exception: **`IG30`** (cited in `adapter/.../laws/MultiFieldAggregateDiffTest.kt`) predates that convention and names no finding, so its citation site carries the contract and git holds the row. A cold review's enumeration on 2026-08-24 found it; do not assume the sweep that found it covered other families.
>
> **Scope.** `:interpreter` only — the kernel-free Kotlin evaluator (parser, evaluation semantics, model loader, the differential/perf harnesses' interpreter side). dmkit (rulekit/modelkit/edit) authoring gaps go to [`DEV-API-GAPS.md`](DEV-API-GAPS.md); kernel-coverage classification stays in the MVK / RT-semantics / grammar ledgers.

## 1. Open

- **IG152 — H4's timed rows are now gated on WORK and on BYTES but still not on cost per unit: a change that does identical work with identical allocation in more cycles remains invisible to every permanent gate (opened 2026-09-18; narrowed twice 2026-09-19).** No instrument in the estate sees that residue — a count cannot (the work is unchanged), allocation cannot (the bytes are unchanged), and a clock's own noise is larger than the bar, which is the measurement below. It is the smallest remaining form of the original exposure and needs an instrument nobody has proposed yet, so it stays open rather than being written off. The remaining exposure is the timed and native half of H4's row set — `interpreterPerformance`, `performanceJvmThroughput`, `perfGateTest`, `interpreterNativePerformance`. Those keep the `1.665×` absolute anchor in `anchors.json`, which is the very tolerance the 5 % bar exists to get underneath, so for time the blind band is still open: a uniform regression below ~1.65× passes every permanent gate, and two migration phases at +4.9 % would sit permanently invisible. **Why they cannot simply be added to the standing anchor is measured, not assumed** (2026-09-19): over the 30 committed run files, one machine, non-CI, accepted observations, **66 keys appear in ≥3 distinct runs and all 66 spread more than 5 % run-to-run** — 28.8 % at the median key, 160.5 % at the worst — so a 5 % bar there fires on noise on every row it covers. H4's own wording is what licenses leaving them out: it bars regression in a *comparable* row and refuses inconclusive evidence, and a row whose noise is 28.8 % is not comparable at 5 %. **Two candidate instruments have since been measured and BOTH are ruled out (2026-09-19), so what remains is a direction rather than a pending run.** The trend reader ([`scripts/perf-trend.sh`](../scripts/perf-trend.sh)) judges a SERIES rather than one comparison, so it could in principle resolve below single-run noise — but its `MIN_SHIFT` defaults to `1.15`, so a sustained 5 % step is below the threshold at which it speaks. The sharper candidate was the **margin**, the kernel/interpreter ratio the early-warning band already judges, whose noise genuinely does cancel because both engines run in one JVM on the same vCPUs: measured as a within-row control, the margin halves the spread — 33.0 % → 17.2 % at the median, within-15 % rows tripling from 8 to 24 — and still puts **zero of 68 rows** inside 5 % ([the measurement](INTERPRETER-PERFORMANCE-RESULTS.md)). No quantity this estate records can carry the bar. **The direction that would** was to bar a *deterministic counter of the work done* instead of the clock that measures it — the move that makes the byte anchor work, and the arrangement already accepted for the checker, where `Sweep.comparisons` decides the growth invariant deterministically on every carrier and a budget was declined as redundant to it.

  Landed 2026-09-19: the work gate. `WorkLedger` is an internal null-branch seam on the evaluation path tallying condition nodes, value-expression nodes and validation rule-row instantiations; `WorkLedgerGuardTest` holds every footprint scenario to an **exact per-row constant** at three scales, on JVM and Node alike. It needs no baseline at `c8e3b997` — a per-row constant is arithmetic rather than a remembered value — and it leaves no sub-threshold band, because the constants are low single-digit integers and the smallest possible regression is one extra node per row. Measured per-row work and the kill proof: [INTERPRETER-PERFORMANCE-RESULTS](INTERPRETER-PERFORMANCE-RESULTS.md).

  Landed 2026-09-19: the deterministic half. The baseline was measured at `c8e3b99795fe9c2ce3e9db32632a6dd8f6537043` (a detached checkout, each record verified by its own `commit` field), which is the reading the proposal treats as needing no owner decision, re-basing being the one it reserves. 66 rows — 24 JVM-heap, 24 Node-heap, 18 delivered-size — in [`adapter/src/test/resources/perf/nfr1-standing-anchor.json`](../adapter/src/test/resources/perf/nfr1-standing-anchor.json), enforced by `:adapter:verifyNfr1StandingAnchor` and invoked from the footprint lane. ## 2. Deferred / ongoing-incremental (recorded with status; detail in [`INTERPRETER-FINDINGS.md`](INTERPRETER-FINDINGS.md))

Two kinds live here when present: a **deferred** item (parked or owner-accepted until its re-open trigger flips) and an **ongoing as-touched** refactor. A deferred item may be a safely guarded capability residual; it is not a silent semantic mismatch. A fully shipped item is deleted (its `IF<n>` finding + git are the record).

- **IG151 — both clean-room readers PRESERVE a `MODEL_ROOT` mount group's own `usageType` where expansion clears it (opened and deferred 2026-09-15).** Measured through `PreparationParityHarness`: the real kernel's expanded mount carries no usage type at all, exactly as the `SINGLE_RG` replacement leaves it, while `dm.core.ModelReader` keeps the authored marker; `IncludeAssembly`'s `UsageTypeTransfer.PreserveMount` makes the same choice and is unmeasured. The fact is in [KF3](KERNEL-FINDINGS.md#kf3).

  **Why deferred rather than fixed.** The divergence has no reachable witness: an `attachment` group must declare the eight mandated attachment fields itself, a `MODEL_ROOT` mount's children are the provider's root GROUPS, and declaring those fields locally beside the alias makes the group an already-expanded mount whose reference A12 ignores — so no model `checkConsistency` accepts can carry a marked `MODEL_ROOT` mount, and `WorkspacePreparationParityTest` can hold no fixture for it (its harness runs consistency). **Re-open trigger:** A12 admits an attachment group whose mandated fields arrive through a mount, or a consumer reads the expanded `usageType` of a mount group. **What would settle it:** clear the mount's slot in both readers and lock it with the kernel row that already exists (`adapter.WorkspaceIncludeStructureKernelTest.kernelClearsAModelRootMountsOwnAttachmentMarkerBeforeApplyingItsExclusion`), whose parity assertion is deliberately omitted today.

- **IG143 — a HAND-BUILT interpreter document is a route hybrid, so two cross-route laws are ungated (opened 2026-08-28, deferred).** `Document.field(path, text)` is the test-only construction route (the public ingress is `readDocument`/`seedDocument` — enumerated from the ABI golden in [IF313](INTERPRETER-FINDINGS.md#if313)). It leaves `numberIdentity` null, so **NUMBER behaves like A12's V1 String route** (always changed), while every other kind compares stored text and so behaves like the **typed** route. That hybrid is not a defect in shipped behaviour, but it means a law comparing a kernel V1 applied state against a hand-built interpreter one is route-mismatched for Number and route-matched for the rest.

  **Two sites, both latently safe today:** `adapter.laws.ComputedTimeTargetDiffTest` and `AppliedCellStateDiffTest` (kernel apply + `newDocument()`, no `readDocument`). Neither seeds a computed cell with its own computed value, which is the only input that separates the routes, so no assertion is currently wrong. `CrossRouteGateCensusGuardTest` deliberately scopes itself to the TYPED transport and says so, rather than pretending to cover these.

  **Why deferred rather than gated now.** `CrossRouteSourceGate.requireRouteAgnostic` compares the V1 changed set against the TYPED retained set; gating the hand-built sites needs a third comparand, and the honest fix is upstream — decide whether a hand-built document should model the V1 route (populate no identity for any kind) or the typed route (populate identity for Number too) and make it coherent. Choosing while two laws depend on the current hybrid is what the convergence gate says not to do inside a slice that already grew twice. **Re-open trigger:** a hand-built cross-route law seeds a source-identical cell, or the harness's document construction is unified. **What would settle it:** measure a source-identical NUMBER and a source-identical DATE through all three routes and pick the profile `Document.field` should present.

- **IG141 — the interpreter keeps DateRange formats declaration-local while kernel codegen shares an order-dependent first format (opened and deferred 2026-08-24).** [KF210](KERNEL-FINDINGS.md#kf210) and [IF311](INTERPRETER-FINDINGS.md#if311) pin the discriminator: placing interpreted `dd.MM` declarations before interpreted `MM` declarations makes both kernel strategies admit `11/02` and store `01.11-01.02`; reversing only those declaration blocks rejects the wrap and keeps ordered `03/10`. The interpreter gives the second, declaration-local result under both orders.

  **Why it is deferred rather than copied from the reported model.** The proposed field-local correction is falsified, and the actual contract belongs to a cross-model shared-format mechanism. Implementing first-wins behavior from one equivalence class would silently widen the slice to every DateRange format, separator, interpretation direction, declaration order, formal check, computation source and target, and JSON conversion path. The convergence gate applies because the acceptance denominator changed during reconciliation. **Re-open trigger:** either the pinned kernel fixes the shared-format defect, or a bounded conformance decision explicitly chooses to mirror it. **What would settle it:** enumerate the shared-format equivalence classes from `IDateRangeType.getFormatOfDateRange` and `CodeGenDateRangeTypeImpl`, then run order-swapped dynamic/Java controls across formal validation, direct reads, and computation input/output before choosing the interpreter policy.

## 3. Out of scope (won't build unless the trigger flips; recorded so it's not re-investigated)

- **IG150 — the two form-line message parameters (`<field>.Vordruckzeile`, `<field>.Vordruckname`) render VERBATIM, because there is no kernel behaviour to match (opened 2026-09-07).** Both are statically ADMITTED on an A12 model and both **skip** the field-membership gate every other name-position form meets ([KF279](KERNEL-FINDINGS.md#kf279)), so a model carrying one passes `model check`. At runtime **both kernel strategies fault identically** — the rule's message text comes back as `An error occurred while evaluation the data check: Index 1 out of bounds for length 1` — while the interpreter leaves the `$…$` token in place, measured three-way in `adapter.laws.RuleMessageFormLineParameterDiffTest`.

  **Why this is out of scope rather than an unimplemented parameter** (the distinction from the shipped IG148, which was the same shape with a kernel target): the form line is an H-model concept with no A12 counterpart, the kernel's static checker verifies only that the argument names an existing field, and `NO_VORDRUCKZEILE` — the class its own enum reserves for "the field specifies no form line" — is raised nowhere in the 30.8.1 checkout (a12-kernel-lean's source measurement, carried here as their report). There is therefore no defined value to emit: matching the kernel would mean encoding an internal error, and emitting an empty string or a form-line number would be inventing behaviour. The verbatim token is the fail-fast reading and is deliberately visible.

  **Re-open trigger:** the kernel raises `NO_VORDRUCKZEILE` (making the shape a static refusal we should pre-check or delegate cleanly), or it renders a defined value for these parameters on an A12 model. Either gives the differential a target and turns this into an ordinary parity gap.
