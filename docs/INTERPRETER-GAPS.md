# interpreter — gaps

> **What this is** — the interpreter's peer of [`DEV-API-GAPS.md`](DEV-API-GAPS.md) and [`FEATURE-GAPS.md`](FEATURE-GAPS.md): the single tracking surface for **open `:interpreter` gaps, deferred items, and to-fix issues**. It exists so open work is easy to **track, report, and pick up** — and so [`INTERPRETER-FINDINGS.md`](INTERPRETER-FINDINGS.md) can be what a findings doc should be: **settled, verified knowhow** you read to warm up and not re-investigate (like `KERNEL-FINDINGS.md`), never a backlog of dispositions ("open / to fix / deferred"). Per the CLAUDE.md *"rationale is timeless; a disposition is status"* rule — the findings hold the timeless fact, this ledger holds the live status.
>
> **Lifecycle.** A gap is born here with an `IG<n>` code under the section matching its status (§1 open / §2 deferred / §3 out-of-scope). When it ships, three things happen **in the fix's own commit**: (1) its **rationale graduates to a numbered `IF<n>` finding** in [`INTERPRETER-FINDINGS.md`](INTERPRETER-FINDINGS.md) — that finding notes it "graduated from IGn"; (2) any code/test comment citing `IGn` is **repointed to `IFn`**; (3) the gap's row is **deleted from this ledger**. **There is no "fixed/shipped" section — we don't record fixed gaps.** A fixed gap is no longer a gap; **git is the history of *when/what* was fixed, and the `IFn` finding is the *why*** — a hand-kept "shipped" list would only duplicate both and rot. So this ledger only ever lists **live, unfinished work** (the already-shipped IF20-per-cell / IF21 / IF23 / IF24 / IF25 live as findings, not here). A **deferred** gap stays in §2 with its re-open trigger, and an **ongoing as-touched** refactor stays in §2 with its remaining-work note (it is progressing in increments, not parked — its shipped parts graduate to its `IF<n>` finding while the row stays until *all* of it lands); the technical detail of each gap lives in its cited `IF<n>` finding (the knowhow), this ledger holds only *what's left to do and why*.
>
> **Section invariant (the placement rule):** every section holds exactly one **live** status — **§1 = open, §2 = deferred / ongoing-incremental, §3 = out-of-scope**. A FULLY-shipped/graduated entry belongs in **none** of them: completing it *deletes* its row (see the lifecycle). So §1 reads `_None open._` whenever nothing is open — the marker every `-GAPS` ledger uses, so one grep rolls up the whole family (`GapLedgerTemplateGuardTest`) — and a fully-FIXED entry **anywhere** in this ledger is a bug in *this doc* — git already records the fix. (A partially-shipped *ongoing* refactor in §2 is not "fixed" — it stays until all of it lands.)
>
> **Current state.** IG114, IG118, and IG119 shipped as [IF276](INTERPRETER-FINDINGS.md#if276), [IF277](INTERPRETER-FINDINGS.md#if277), and [IF278](INTERPRETER-FINDINGS.md#if278). IG120's mechanism shipped as [IF280](INTERPRETER-FINDINGS.md#if280) and its row now carries only the one-step residual that needs a hosted run to produce. New semantic or performance defects belong in §1 only while they have actionable work and a defined completion gate.
>
> **Scope.** `:interpreter` only — the kernel-free Kotlin evaluator (parser, evaluation semantics, model loader, the differential/perf harnesses' interpreter side). dmkit (rulekit/modelkit/edit) authoring gaps go to [`DEV-API-GAPS.md`](DEV-API-GAPS.md); kernel-coverage classification stays in the MVK / RT-semantics / grammar ledgers.

## 1. Open

- **IG120 — the hosted runner class has no anchor block yet, so CI's uniform-regression bar is still in bootstrap.** The mechanism shipped as [IF280](INTERPRETER-FINDINGS.md#if280): the 18 growth lanes are held against a committed per-runner-class absolute-time anchor, which is the only bar that can see a uniform slowdown. Only the `darwin-aarch64` block exists, because **a hosted runner's numbers can only be authored from a hosted run** — so on CI every lane reports `UNANCHORED (no block for this runner class yet)` and passes, by design.

  **Status (2026-08-11): the artifacts now exist and the block is deliberately still uncommitted.** The mechanism reached the remote as `1845f8af` and three dispatched runs each produced a complete 36-observation record for `linux-amd64-ci` (`processors=2`). Committing the block is blocked on **one open question, not on a run**: whether the ratified `1.8× + 1 ms` is viable there. The three runs disagreed by up to `1.94×` at the whole-run level, but they were dispatched **concurrently** and so contended with each other — a method error, recorded with its evidence in [INTERPRETER-PERFORMANCE](INTERPRETER-PERFORMANCE.md) "Checkpoint 2026-08-11". Three **sequential** runs are the corrected measurement. Two outcomes, both decided by that data: if solo runs cluster, commit the block as authored at `1.8×`; if they spread comparably, the choice is a per-block tolerance around `2.5×–3×` versus leaving the class unanchored, and at that width the bar adds little over the `beats both` bars already at 4.0×–10.0× — an owner call, since `PerfBounds` is the ratified floor.

  The authoring sequence itself is settled and written out in [`scripts/perf-anchor.sh`](../scripts/perf-anchor.sh)'s header (the nightly is `workflow_dispatch`-able, so it is a dispatch and never a wait for `03:00`) — but dispatch the runs **one at a time**:

  ```
  gh workflow run 'Nightly performance' --ref <branch>
  gh run download <run-id> --name perf-observations --dir /tmp/anchor
  scripts/perf-anchor.sh show /tmp/anchor/perf-results/*/*.jsonl
  ```

  **Everything that can be prepared without a hosted run is done, and the one step was rehearsed end to end** against a synthesized hosted record (2026-08-11): the refresh is purely **additive** — it writes the second block and leaves `darwin-aarch64` byte-identical — `PerfAnchorResourceTest` and `PerfAnchorCoverageGuardTest` both hold with two blocks, and a deliberately partial **34-of-36** input, which is what a run with a breached growth floor uploads, is refused by the script naming the missing lanes. That refusal is new: it compared only against the keys *that block* already had, so it was blind to exactly the case the blocked step exercises — a new class with no previous block. `PerfAnchorScriptTest` now executes each refusal against a temporary anchor.

  **Two residuals, both narrowed rather than open-ended:**
  1. **The anchor is one run's sample, not a median.** `scripts/perf-anchor.sh` now accepts several observation files and anchors the per-key **median**, refusing inputs from different runner classes — so the capability is in place and the committed block is simply not yet built from it. Until it is, a lane anchored on a fast run carries a tighter-than-advertised bar and one anchored on a slow run a looser one. This is also the prerequisite for tightening `ANCHOR_TOLERANCE` below `1.8× + 1 ms`: the factor is set from a 1.36× worst observed run-to-run ratio, and a median-of-N anchor is what shrinks that number honestly.
  2. **One anchoring machine per runner class.** `PerfEnvironment.key` names an os/arch family, and absolute times are a property of the machine. A block now records the `processors` count it was captured on and `PerfAnchors` declines to assert against a block from a different one — so a second machine reads as bootstrap instead of reddening 18 lanes. That **narrows** the class without closing it: two machines with the same core count and different generations still collide, so the standing rule is one anchoring machine per class. Closing it properly needs a CPU-model signal the JVM does not expose.

  **Resolved since the row was opened** (2026-08-11, all from one cold review of the mechanism): the tolerance's basis was falsified by this repo's own gate log and corrected from `1.5×` to `1.8× + 1 ms` against a measured `0.92×–1.36×` envelope; `perf-anchor.sh` now refuses a refresh that would leave any lane the anchor file carries without a bar, which was the one path that removed the bar through the sanctioned tool, and its refusals are executed by `PerfAnchorScriptTest` rather than asserted in prose; a missing key inside an anchored class now fails the isolated gate **unconditionally** rather than only under `CI`, since a moved scenario fingerprint keeps the observation count intact and so is invisible to the coverage guard too; the record is the **accepted** median rather than a breaching first sample; a breach re-measures with the observation's own estimator; the bar asserts only in the isolated single-fork lane, so a broad `-PrunPerf` run cannot false-red it; `PerfAnchorResourceTest` guards the committed file's shape and `PerfAnchorCoverageGuardTest` binds every lane to an anchor at both scales, both on every push and both with their mutants executed. The wall-clock *fixed-size comparison* rows stay unanchored as a **reasoned exclusion, not a gap**: they move up to 1.54× run-to-run on one machine and already carry `requireInterpreterBeatsBoth` at 4.0×–10.0×, so an absolute bar there would need a ~2.5× tolerance to buy roughly nothing. The `COLD first-call` growth lane *is* anchored, on the wall clock, at a measured 1.26× worst observation. The two authoring debts moved to their owners: the group-star DSL gap is [DEV-API-GAPS](DEV-API-GAPS.md) DG32, and [KF174](KERNEL-FINDINGS.md#kf174)'s non-discriminating "second pair" is corrected in place.

## 2. Deferred / ongoing-incremental (recorded with status; detail in [`INTERPRETER-FINDINGS.md`](INTERPRETER-FINDINGS.md))

Two kinds live here when present: a **deferred** item (parked or owner-accepted until its re-open trigger flips) and an **ongoing as-touched** refactor. A deferred item may be a safely guarded capability residual; it is not a silent semantic mismatch. A fully shipped item is deleted (its `IF<n>` finding + git are the record).

- **IG83 — Route A: general portable timezone-id support (owner-accepted deferred capability; Route B completed as IF155/IF165/IF166).** The enforced evaluator contract supports exact `{UTC, GMT, Europe/Berlin}`; Berlin uses the independently locked legacy-`java.util.TimeZone` history, explicit invalid ids fail as configuration errors, and known kernel-legal zones outside the set fail with the precise supported-scope diagnostic. The kernel accepts a wider Java `TimeZone` id domain, so this remains an honest product limit, not full timezone parity. **Re-open trigger:** a real consumer needs a non-Berlin zone or a publication wave promises full timezone parity. Then build one portable, deterministically versioned tzdb for JVM + JS and pin its version relationship to the kernel's JDK tzdb.
