# interpreter — gaps & open issues

> **What this is** — the interpreter's peer of [`DEV-API-GAPS.md`](DEV-API-GAPS.md) and [`FEATURE-GAPS.md`](FEATURE-GAPS.md): the single tracking surface for **open `:interpreter` gaps, deferred items, and to-fix issues**. It exists so open work is easy to **track, report, and pick up** — and so [`INTERPRETER-FINDINGS.md`](INTERPRETER-FINDINGS.md) can be what a findings doc should be: **settled, verified knowhow** you read to warm up and not re-investigate (like `KERNEL-FINDINGS.md`), never a backlog of dispositions ("open / to fix / deferred"). Per the CLAUDE.md *"rationale is timeless; a disposition is status"* rule — the findings hold the timeless fact, this ledger holds the live status.
>
> **The lifecycle.** A gap is born here with an `IG<n>` code under the section matching its status (§1 open / §2 deferred / §3 out-of-scope). When it ships, three things happen **in the fix's own commit**: (1) its **rationale graduates to a numbered `IF<n>` finding** in [`INTERPRETER-FINDINGS.md`](INTERPRETER-FINDINGS.md) — that finding notes it "graduated from IGn"; (2) any code/test comment citing `IGn` is **repointed to `IFn`**; (3) the gap's row is **deleted from this ledger**. **There is no "fixed/shipped" section — we don't record fixed gaps.** A fixed gap is no longer a gap; **git is the history of *when/what* was fixed, and the `IFn` finding is the *why*** — a hand-kept "shipped" list would only duplicate both and rot. So this ledger only ever lists **live, unfinished work** (the already-shipped IF20-per-cell / IF21 / IF23 / IF24 / IF25 live as findings, not here). A **deferred** gap stays in §2 with its re-open trigger, and an **ongoing as-touched** refactor stays in §2 with its remaining-work note (it is progressing in increments, not parked — its shipped parts graduate to its `IF<n>` finding while the row stays until *all* of it lands); the technical detail of each gap lives in its cited `IF<n>` finding (the knowhow), this ledger holds only *what's left to do and why*.
>
> **Section invariant (the placement rule):** every section holds exactly one **live** status — **§1 = open, §2 = deferred / ongoing-incremental, §3 = out-of-scope**. A FULLY-shipped/graduated entry belongs in **none** of them: completing it *deletes* its row (see the lifecycle). So §1 reads "(none)" whenever nothing is open, and a fully-FIXED entry **anywhere** in this ledger is a bug in *this doc* — git already records the fix. (A partially-shipped *ongoing* refactor in §2 is not "fixed" — it stays until all of it lands.)
>
> **Scope.** `:interpreter` only — the kernel-free Kotlin evaluator (parser, evaluation semantics, model loader, the differential/perf harnesses' interpreter side). dmkit (rulekit/modelkit/edit) authoring gaps go to [`DEV-API-GAPS.md`](DEV-API-GAPS.md); kernel-coverage classification stays in the MVK / RT-semantics / grammar ledgers.

- **IG75 — `Document` configuration is propagated through a long positional constructor and is already lost on two production-adjacent paths (correctness defect, found 2026-07-18).** `ModelDef.newDocument()` passes all fourteen configuration inputs, including the final `timeZone`, but `Document.emptyCopy()` reconstructs only through `fieldConstraints`; the omitted argument silently takes the default `UTC`. `DmInterpreter.applyComputations()` delegates to `Document.withComputed()`, which uses that copy, so a `Europe/Berlin` document becomes UTC after compute→apply and subsequent DATE_TIME formal checks/evaluation can disagree with the kernel across DST — directly breaking the copy invariant and IF128's timezone contract. The predicted sibling exists in the perf harness: `InterpreterPerfEngine` constructs `Document` with only the first six inputs, omitting datetime/date-precision/enum/time/base-year/constraint/timezone configuration, so “real Document” scenarios can exercise a semantically incomplete instance (including the constrained-field scenario). The same mechanism previously dropped `baseYear` and `fieldConstraints` in the CLI loader, confirming this is the class, not a one-off missing argument. **Root fix required:** replace positional configuration threading with one typed immutable configuration value/factory that `newDocument`, `emptyCopy`, and every harness consumer preserve wholesale; make partial construction impossible or conspicuous. Red/green locks: a Berlin compute→apply→validate differential spanning a DST gap, a configuration-preservation invariant covering every slot, and perf-harness coverage proving configured constraints/timezone reach the interpreter path. Do not append `timeZone` at the one call site and leave the mechanism live.

- **IG76 — the normative oracle for a legal kernel runtime/codegen split is contradictory (correctness-contract gap, found 2026-07-18; owner decision required).** [interpreter/CLAUDE.md](../interpreter/CLAUDE.md) says both strategies are co-equal but, when they diverge on legal input, the interpreter follows **production codegen** and carves the runtime-only differential out. [CONFORMANCE-CORPUS-SPEC.md](CONFORMANCE-CORPUS-SPEC.md) instead declares **kernel Groovy-dynamic** the production-normative anchor and says a differing static strategy is recorded but “never adopted”; `expected` always remains the dynamic result. Both contracts cannot decide the same future split, while the current tri-engine fuzz/capture assumes equality and therefore does not resolve the precedence. Before the next genuine strategy divergence, choose the authoritative behavior, align the module instructions + corpus contract + certificate language, and add a characterized divergence case that proves capture and replay enforce that choice. This is a design decision, not an implementation assumption.

- **IG77 — the executable startup/performance gates do not certify NFR-S1/S2/P1/P2 (performance-governance gap, found and contract-anchored 2026-07-18).** The product bars now live in [INTERPRETER-SPEC.md](INTERPRETER-SPEC.md) “Non-functional contract” and the exact measurement protocol in [INTERPRETER-PERFORMANCE.md](INTERPRETER-PERFORMANCE.md): true first-answer p95, absolute large-document/Node throughput, `<6×` growth for a declared linear 4× axis, and `≤1.25×` the fair kernel-Java baseline (design target ≤1.0). The current floor remains materially weaker: twelve interpreter-only checks require only `<9×` growth, one reduced Groovy canary allows `<5 s` and `<5×`, and no gate uses the fair Java comparator. `coldRunMillis` starts after engine/document construction, takes minima, checks no rule-count axis, and has no absolute SLA; `OuterCorrelationPerfTest` permits `<36×` growth even though the equality fast path is documented O(N). Push/PR CI excludes `@Tag("perf")`; nightly/manual `-PrunPerf` runs both tiers, `DocumentScaleTest` is not in that workflow, and `scripts/perf.sh js` suppresses a failing Node exit. **Remaining work:** implement the pinned-runner NFR lane (fresh-process p95 + end-to-end native, warm Java ratios/absolute bars, declared-complexity growth, failing Node checks), keep correctness-first and benchmark-tier separation, and wire a reduced subset on push/PR while retaining the full nightly/release sweep. - **IG78 — executable comments still describe retired behavior or carry copy drift (documentation defect, partially repaired 2026-07-18).** The NFR documentation pass corrected the as-is docs: parse-once, 110 operators, current gate-tier attribution/wiring, publishable-vs-published, and the performance script's `bench` mode are now coherent. Source/test comments remain stale: `PerfHarness`, `PerfCatalog`, `KernelEdgeTest`, `PerfScalingTest`, and `EvalProfileTest` still attribute cost to per-call reparsing or compare startup with kernel codegen; `PerfBounds.CAVEAT` still says the kernel validates more field constraints although that coverage caveat is cleared; `PerfCatalog.semanticIndexPerRow` describes the raw semantic-index path as O(rows²) after IF116 fixed it; and `DmInterpreter.validatePart` repeats the same partial-star/global-fields KDoc sentence twice. - **IG79 — NFR-F1/F2 relative-footprint certification is not implemented (footprint-governance gap, found and contract-anchored 2026-07-18).** Low footprint is now explicitly **relative** and subordinate to the performance benefit of bounded caches: indices/hash maps/memos are allowed and advised. The contract requires a kernel/Groovy-free interpreter closure no more than 50% of the equivalent kernel-backed evaluator, previous-release artifact/closure ratchets, cache-lifetime + warm-plateau checks, and multi-scale `N, 2N, 4N, 8N` runtime-footprint fitting (median space exponent ≤1.25; no 4× step >8×; logical cache entries linear), with >20% runtime growth triggering review rather than an arbitrary heap rejection. - **IG80 — the Europe/Berlin datetime path has no committed perf gate; the IF128 offset optimization's speedup is probe-measured only (performance-coverage gap, found 2026-07-18).** IF128's DST offset optimization — pure-integer civil math (`epochDayOfCivil`/`yearOfEpochDay`) replacing the per-conversion string build + regex parse in `berlinOffsetSeconds` — was measured ~42% faster (Berlin/UTC 2.1× → 1.26×) on a hand-run 3-datetime-rules-per-row probe that was then discarded; nothing in the committed suite exercises it. `PerfCatalog` carries **no DATE_TIME field** (its model JSON declares `timeZone: Europe/Berlin`, but every scenario is zone-inert numbers/strings/dates), so neither the routine gate nor the bench sweep touches the datetime instant math under any zone. The *correctness* of the two helpers is locked (`interpreter … DateMathCivilArithmeticTest`, JVM+JS), but their *cost* — and the optimization's win — are ungated and free to silently regress. A fair against-kernel datetime scenario is additionally blocked by **IG75**: `InterpreterPerfEngine` builds `Document` without `timeZone`, so a Berlin datetime instance would evaluate as UTC on the interpreter side and mismatch the Berlin kernel — the scenario cannot be authored until that positional-config loss is fixed. **Remaining work (after IG75):** add a Europe/Berlin DATE_TIME scenario to `PerfCatalog` (a per-row `DifferenceIn*` / datetime-comparison / chained-`Add*` mix over a large repetition list) with a UTC control so the fast-path/DST delta is itself pinned; gate it as **declared-linear** per NFR-P1 and against the fair **kernel-Java** baseline per NFR-P2 (the Berlin-vs-kernel ratio IG77 governs). This closes the datetime hole in the NFR-P coverage and locks the IF128 optimization. Close trigger: the Berlin datetime scenario lands green in gate + bench with the Java ratio recorded.

## 2. Deferred / ongoing-incremental (recorded with status; detail in [`INTERPRETER-FINDINGS.md`](INTERPRETER-FINDINGS.md))

Two kinds live here when present: a **deferred** item (parked until its re-open trigger flips) and an **ongoing as-touched** refactor (progressing in increments, recorded so the remaining work isn't lost). Neither is a parity gap (those are §1); a fully-shipped item is deleted (its `IF<n>` finding + git are the record).

- **IG60 — compute-mode (overlay) indexed reads rebuild the index column per read.** The IF116 memo covers RAW reads (validation, and any raw-context read); an OVERLAY context must rebuild per read because its view changes as the cascade lands (IF116's delegation-trap note) — so a computation doing an indexed read per row over a large repetition list is O(rows) per read, O(rows²) for that computation in the worst case. No perf case pins it today (the gate's compute benchmarks carry no indexed read). Re-open trigger: a compute-scale indexed perf case added to the `PerfCatalog` trips, or a safe per-cascade-step cache is proven (the overlay is plausibly stable within ONE computation's row loop — needs the stability analysis, never assumed).

  **Stability analysis (done 2026-07-11, IG59 rider — LEFT OPEN, not implemented).** The overlay index-column view IS stable across one computation's row loop *under a condition*: in `DmInterpreter.computeInstances` the mutable `overlay`/`cleared`/`poisoned` maps are written only for the CURRENT computation's TARGET cells (`computeAt` writes them *after* `evalComputation` returns), and prior computations' writes have all landed before this computation's loop begins (dependency order). So every cell of a *different* field — including the index field a `[F For key]` reads — is fixed for the duration of the loop, and within a single row's evaluation nothing is written at all (the read sees consistent data). The read column would therefore be cacheable ONCE per computation. The **unstable case** is a self-referential computation that both targets and semantic-index-reads the same index-field column (its own writes shift the column mid-loop); it is rare and plausibly authoring-invalid, but is NOT ruled out here. **Why it stays open, not implemented:** (1) a correct cache must live at the `computeInstances` level (the `OverlayContext` is created fresh per row, so it cannot hold cross-row state) and be invalidated when the loop advances to the next computation AND guarded against the self-referential case — this is a perf *feature* with a real correctness surface (a stale column → wrong compute results, a #1-rule violation), not a behavior-neutral extraction; (2) no compute-scale indexed perf case exists to justify or lock it (the re-open trigger's other half). It should be picked up *with* its perf case + a compute differential, not as a drive-by. Neither the Set-I extraction nor the Set-K seam landing (which moved `computeInstances` into `ComputationEngine` VERBATIM — the overlay lifecycle is unchanged, IF117) reshaped `computeInstances` enough to make the cache land safely on its own.

- **IG68 — a pure-JS standalone consumer with includes has no `commonMain` model expander (graduated-residual of IG67 / IF122, 2026-07-12).** dmtool's JVM + native eval path pre-expands includes kernel-free via the **Java** `dm.core.ModelReader` (`InterpreterEngine.expandForEval`), so an includes-bearing model evaluates with its mounted content present on every dmtool target. A **standalone Kotlin/JS** library consumer, however, has no `commonMain` expander — the reader is JVM-only — so a JS consumer feeding an includes-bearing model to `DmInterpreter` directly would see the raw (unmounted) model. **Not a dmtool gap** (dmtool always expands first); a `:interpreter`-library gap. Re-open trigger: a JS/browser consumer needs to evaluate an includes-bearing model without a host-side expander (port the reader's mount + relativize to `commonMain`).

*(The runtime-semantics extraction discipline — a new operator's semantics land in the pure runtime layer, migrated as-touched — graduated to IF10 and `interpreter/CLAUDE.md`; it is a standing convention now, not a tracked refactor.)*

## 3. Out of scope (won't build unless the trigger flips; recorded so it's not re-investigated)

- **German render target unparseable by the interpreter** (was IG28) — **out-of-scope, verified 2026-07-06.** `DslRenderer(ConditionLanguage.DE)` emits `Und`/`FeldAngegeben`/`Heute`/`@Von`; the interpreter's parser is EN-only. This is **correct by construction, not a gap**, because the interpreter only ever parses **stored** conditions, and the kernel stores every `errorCondition` in **English keywords regardless of authoring language** — confirmed against the real German A12 Tools workspace (2025.06-ext5): its stored conditions read `GroupFilled(...)`/`FieldNotFilled(...)`/`And`/`MinValue(...)`, not `Und`/`FeldAngegeben`. The German render is a **display-only** transform, never round-tripped back through the interpreter (dmtool's `model eval`/`rule eval` read the stored English form; authoring accepts DE via the kernel's language-parametric parser on the JVM, not the interpreter). Re-open trigger: the kernel starts persisting conditions in the authoring language, or a consumer needs the interpreter to parse a DE-rendered string. Detail: KERNEL-FINDINGS "stored conditions are canonical English".
- **`SumOfProducts` over plain (non-repetition-list) fields** — **parity-by-construction, probe-confirmed 2026-07-06** (was IG33). `SumOfProducts(Qty, Price)` over two plain `FieldRef`s is **rejected by the kernel at codegen** with `MVK_REPEATABLE_LEVEL_REQUIRED` ("All fields must be repeatable at least at one layer"), so it never appears in a valid/loadable model — the interpreter's `sumOfProducts` (which resolves both operands as stars) is unreachable on any valid input. No interpreter change; the RuleValidator/kernel is the gate. Re-open trigger: a kernel upgrade that starts accepting a non-repeatable `SumOfProducts`. Detail: IF51.
- **`mandatoryGroup`** (`FEHLER_PFLICHTKONTEXT`) — **source-confirmed unreachable in 30.8.1**: the code is defined but **never emitted**, and **no DM-JSON property declares a group mandatory**, so it can't fire on any loadable model (parity by construction). - **`uniqueValue` (`FEHLER_MULTI_SELECT`)** — was the deferred IG2; **out-of-scope, rationale CORRECTED 2026-06-27** (the earlier "the construct is unmodeled, interpreter reports it unsupported" reasoning was WRONG — a `usageType: "multi-select"` group IS a serialized, loadable construct that **modelkit already authors** (`multiSelectGroup`), and 6 real ones ship in the 2025.06-ext5 workspaces). Re-open trigger: a kernel upgrade that wires `UNIQUE_VALUE` into `AutogeneratedRulesService` or an `IAutogeneratedRule`. Detail: KERNEL-FINDINGS "multiSelect value uniqueness is DEAD code"; locked by `adapter.laws.MultiSelectUniquenessDiffTest`.
