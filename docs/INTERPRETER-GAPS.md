# interpreter — gaps

> **What this is** — the interpreter's peer of [`DEV-API-GAPS.md`](DEV-API-GAPS.md) and [`FEATURE-GAPS.md`](FEATURE-GAPS.md): the single tracking surface for **open `:interpreter` gaps, deferred items, and to-fix issues**. It exists so open work is easy to **track, report, and pick up** — and so [`INTERPRETER-FINDINGS.md`](INTERPRETER-FINDINGS.md) can be what a findings doc should be: **settled, verified knowhow** you read to warm up and not re-investigate (like `KERNEL-FINDINGS.md`), never a backlog of dispositions ("open / to fix / deferred"). Per the CLAUDE.md *"rationale is timeless; a disposition is status"* rule — the findings hold the timeless fact, this ledger holds the live status.
>
> **Lifecycle.** A gap is born here with an `IG<n>` code under the section matching its status (§1 open / §2 deferred / §3 out-of-scope). When it ships, three things happen **in the fix's own commit**: (1) its **rationale graduates to a numbered `IF<n>` finding** in [`INTERPRETER-FINDINGS.md`](INTERPRETER-FINDINGS.md) — that finding notes it "graduated from IGn"; (2) any code/test comment citing `IGn` is **repointed to `IFn`**; (3) the gap's row is **deleted from this ledger**. **There is no "fixed/shipped" section — we don't record fixed gaps.** A fixed gap is no longer a gap; **git is the history of *when/what* was fixed, and the `IFn` finding is the *why*** — a hand-kept "shipped" list would only duplicate both and rot. So this ledger only ever lists **live, unfinished work** (the already-shipped IF20-per-cell / IF21 / IF23 / IF24 / IF25 live as findings, not here). A **deferred** gap stays in §2 with its re-open trigger, and an **ongoing as-touched** refactor stays in §2 with its remaining-work note (it is progressing in increments, not parked — its shipped parts graduate to its `IF<n>` finding while the row stays until *all* of it lands); the technical detail of each gap lives in its cited `IF<n>` finding (the knowhow), this ledger holds only *what's left to do and why*.
>
> **Section invariant (the placement rule):** every section holds exactly one **live** status — **§1 = open, §2 = deferred / ongoing-incremental, §3 = out-of-scope**. A FULLY-shipped/graduated entry belongs in **none** of them: completing it *deletes* its row (see the lifecycle). So §1 reads `_None open._` whenever nothing is open — the marker every `-GAPS` ledger uses, so one grep rolls up the whole family (`GapLedgerTemplateGuardTest`) — and a fully-FIXED entry **anywhere** in this ledger is a bug in *this doc* — git already records the fix. (A partially-shipped *ongoing* refactor in §2 is not "fixed" — it stays until all of it lands.)
>
> **Current state.** §1 lists what is open; read it rather than this paragraph — it held drained from 2026-09-05, IG149 having closed as measured parity across all three routes a widened fragment vocabulary opened up ([IF327](INTERPRETER-FINDINGS.md#if327)), and it was drained again from 2026-09-20 until IG155 opened on 2026-09-23. **IG154** carried it for a day: opened 2026-09-19 because the occupancy instrument reached the interpreter protocol's timed samples and neither `:adapter` collector, and closed once each of those two got the quantity its own carrier can actually form — a ratio was measured blind to moderate contention, so `perfGateTest` judges **foreign demand** and the native lane reports **unattributed demand**, the child's own CPU being unreadable on this platform. A **shipped** gap appears nowhere here: its rationale graduated to a numbered `IF<n>` finding that names the `IGn` it came from, so a code comment citing `IGn` resolves by grepping [`INTERPRETER-FINDINGS.md`](INTERPRETER-FINDINGS.md), with one measured exception: **`IG30`** (cited in `adapter/.../laws/MultiFieldAggregateDiffTest.kt`) predates that convention and names no finding, so its citation site carries the contract and git holds the row. - **IG156 — `NumberOfFilledGroups` over a group below a starred level BESIDE another group is declined as unsupported (opened 2026-09-24).** `NumberOfFilledGroups(/Item/Batches*/Seal, /Item/Grading)` is kernel-admitted ([KF462](KERNEL-FINDINGS.md#kf462)), and both kernel strategies agree that it counts the filled Seals plus `Grading`'s own filled state. That test locks the decline today, so a fix flips its interpreter assertion. **Blocks:** evaluating such a stored rule kernel-free.

## 2. Deferred / ongoing-incremental (recorded with status; detail in [`INTERPRETER-FINDINGS.md`](INTERPRETER-FINDINGS.md))

- **IG143 — a HAND-BUILT interpreter document is a route hybrid, so two cross-route laws are ungated (opened 2026-08-28, deferred).** `Document.field(path, text)` is the test-only construction route (the public ingress is `readDocument`/`seedDocument` — enumerated from the ABI golden in [IF313](INTERPRETER-FINDINGS.md#if313)). The remaining exposure is the timed and native half of H4's row set — `interpreterPerformance`, `performanceJvmThroughput`, `perfGateTest`, `interpreterNativePerformance`. Those keep the `1.665×` absolute anchor in `anchors.json`, which is the very tolerance the 5 % bar exists to get underneath, so for them the blind band is still open: a uniform regression below ~1.65× passes every permanent gate, and two migration phases at +4.9 % would sit permanently invisible. **Why they cannot simply be added to the standing anchor is measured, not assumed** (2026-09-19): over the 30 committed run files, one machine, non-CI, accepted observations, **66 keys appear in ≥3 distinct runs and all 66 spread more than 5 % run-to-run** — re-derived at `f5905bf9a` as **28.5 % at the median key and 173.2 % at the worst**, the quantity being *worst-against-median*, per key `max/median − 1` — so a 5 % bar there fires on noise on every row it covers. *(This first read 28.8 % / 160.5 % with the quantity unnamed; the corpus is mutable, so a figure derived from it is dated to a commit, and the worst key in particular moves on a single new observation.)* H4's own wording is what licenses leaving them out: it bars regression in a *comparable* row and refuses inconclusive evidence, and a row whose noise is 28.8 % is not comparable at 5 %. **The first two of the three routes are ruled out on the evidence below (2026-09-19); the third has its own paragraph, because it was refuted by the very capture meant to instantiate it.** The trend reader ([`scripts/perf-trend.sh`](../scripts/perf-trend.sh)) judges a SERIES rather than one comparison, so it could in principle resolve below single-run noise — but its `MIN_SHIFT` defaults to `1.15`, so a sustained 5 % step is below the threshold at which it speaks. The sharper candidate was the **margin**, the kernel/interpreter ratio the early-warning band already judges, whose noise genuinely does cancel because both engines run in one JVM on the same vCPUs: measured as a within-row control, the margin halves the spread — 33.0 % → 17.2 % at the median, within-15 % rows tripling from 8 to 24 — and still puts **zero of 68 rows** inside 5 % ([the measurement](INTERPRETER-PERFORMANCE-RESULTS.md)). No quantity this estate records can carry the bar. **The direction that would** was to bar a *deterministic counter of the work done* instead of the clock that measures it — the move that makes the byte anchor work, and the arrangement already accepted for the checker, where `Sweep.comparisons` decides the growth invariant deterministically on every carrier and a budget was declined as redundant to it. **A prior gap sat underneath all of this, added 2026-09-19 and CLOSED the same day: a local capture's machine conditions were not certifiable, so no timed bar could be trusted however it was computed.** `perf-anchor.sh`'s 1.0-runnable-threads-per-core refusal is the only idleness check in the estate and it is blind to the dominant mechanism — load average lags a minute and rates two saturated cores on eight at ~0.25/core, while a CPU-time clock still absorbs cache-contention stalls — so a contended capture session re-levelled two anchors on 2026-09-19 and the fold was reverted the same day. What closed it is narrower than the per-core sweep first proposed and answers the same question on the collectors it reaches — the interpreter protocol's, not `perfGateTest`'s or the native lane's, which is [IF330](INTERPRETER-FINDINGS.md#if330): every timed region of that protocol now records its own CPU milliseconds beside its wall milliseconds, so each sample carries the ratio of the two — its *occupancy* — and a process that spent its elapsed time waiting is refused at aggregation rather than reaching a report. The floors are measured per carrier, because the two carriers cannot report the same quantity; the refusal is proven to fire under real contention and proven not to fire on an idle machine, and both directions are locked ([IF329](INTERPRETER-FINDINGS.md#if329)). [INTERPRETER-PERFORMANCE](INTERPRETER-PERFORMANCE.md) carries the contract and [the checkpoint](INTERPRETER-PERFORMANCE-RESULTS.md) the numbers. **What it does not do is rescue the 5 % bar**, and the distinction is the reason this row is declined rather than reopened on the strength of it: occupancy certifies that a capture *ran*, which removes machine state as an **unmeasured** confound without shrinking the run-to-run spread that defeats the bar. So the noise figures above still bound what a bar can carry, and still do not establish that a controlled machine could not do better. **Part of that split has been made: GC state is a measured driver of the widest lane's spread.** A within-commit control on each arm of the 2026-09-19 baseline comparison put `charset grapheme@32000` at 62.52 ms with `gcCountInWindow=0` and 110.56 ms with `gc=36` at an essentially unchanged load — a **1.77× swing from a run property rather than from code** — and across the darwin archive every run at `gc` 35–76 sits at 101–138 ms against 48–92 ms at `gc` 0–6. Four captures that same afternoon recorded `gc=0` and still measured 88–119 ms, so at least one further inflation path (external CPU load) remains unseparated. **Corrected 2026-09-19: this row previously called filtering on `gcCountInWindow` "the most promising lead" and "the cheapest available path to a resolvable timed comparison". It was measured the same day and it buys nothing.** Filtering the corpus to quiet observations halves the evidence and leaves the spread where it was — at `gc == 0` the eligible key population falls 66 → 30 while the median worst-against-median spread moves only 28.5 % → 27.3 % — and **not one key becomes gateable at any threshold** (0 of 66, 0 of 48, 0 of 39, 0 of 36, 0 of 30 at no filter / ≤40 / ≤20 / ≤6 / ==0). Discriminating the two modes and narrowing the distribution are different achievements, and only the first was measured; the lead read as promising because the mechanism was correct about *what* the modes are and silent about whether removing one mode leaves a resolvable remainder. [The measurement](INTERPRETER-PERFORMANCE-RESULTS.md).

  **The obvious alternative was measured too and is refuted harder: more forks per side cannot rescue these lanes.** A 20 000-iteration bootstrap of the null ratio `(median of n)/(median of n)`, both arms drawn from one key's own runs — and every one of the 66 eligible keys carries 17–26 distinct runs, so this resamples a rich population rather than extrapolating from three points. The median upper bound falls +40.7 % → +26.3 % → +21.0 % → +14.7 % → +9.8 % → +7.1 % at n = 1 / 3 / 5 / 10 / 20 / 40, and **at 40 forks per side — 80 fresh processes for one comparison — 48 of the 66 keys still cannot carry 5 %**. So the `1.665×` anchor on these lanes is not a tolerance anyone chose; it is the resolution the instrument has, and repetition does not convert it into 5 %. That is the durable answer for the `perfGateTest` family and it needs no further probing.

  **A third route — the library throughput collector `performanceJvmThroughput` — looked like the exception and was refuted by the capture built to instantiate it (2026-09-19).** Ten consecutive invocations at one commit gave spread 1.059× and CV 1.79 %, a bootstrapped null upper bound of +2.9 % at five processes per side, and a structural story for why this lane and no other could carry the bar: each process medians its own nine repetitions, so it reports a statistic rather than a sample. The instrument was built — the protocol fanned out to n processes, the fork tasks registered, a reader and identity designed. Then the anchor capture, ten fresh processes across the two arms on an idle machine, measured **CV 5.98 %** and a null upper bound of **+12.3 % at n=5**; reaching +3.2 % would need n = 40 per side, 80 processes and ~25 minutes per comparison. **Two errors, and the second is the durable one.** The study's ten runs were consecutive invocations in one warm session in one tree, so "one tight session" was an unnamed constant across every row of the set — re-measuring gave 4.13 % in the same tree and 7.05 % in the clone, which rules out a carrier effect and implicates the session. And **a bootstrap cannot manufacture the independence its input lacks**: resampling n = 20 and n = 40 from those ten minutes-apart observations reported +0.2 % and +0.1 %, figures no shared-machine clock produces, and their absurdity sat unremarked in the same table whose route-B sibling was explicitly sound *because* its keys carried 17–26 independent runs. Sizing this lane honestly needs ≥30 processes across several sessions and at least two days, with the session treated as a factor; until then its variance is unknown rather than small. [The measurement](INTERPRETER-PERFORMANCE-RESULTS.md).

It needs no baseline at `c8e3b997` — a per-row constant is arithmetic rather than a remembered value — and it leaves no sub-threshold band, because the constants are low single-digit integers and the smallest possible regression is one extra node per row. Contract and coverage: [INTERPRETER-PERFORMANCE](INTERPRETER-PERFORMANCE.md#nfr1-standing-anchor).

  **What closes this row rather than parking it, and the trigger that would re-open it.** Two things. First, the deterministic route is exhausted rather than untried. Enumerating the interpreter's cost paths — condition dispatch, expression dispatch, rule-row instantiation, per-reference index probes, whole-map placement scans, and work *inside* a primitive — leaves only the last beyond a counter's reach in principle, and barring it would need instrumentation on every primitive, which would itself cost interpreter performance and so violate the very NFR the bar serves. A partial counter was designed and deliberately not shipped: it would have covered the probe path while leaving the placement scan, the `RepDoc` flat-spike reader and the in-primitive residue uncounted, and an exact-equality bar that looks complete and is not is worse than none. Second, the sub-gap this row explicitly carried — *a local capture's machine conditions are not certifiable, so no timed bar can be trusted however it is computed* — is now **closed**: every timed sample records its own occupancy, the floors are measured per carrier, and the refusal is proven to fire on real contention and not on an idle machine ([IF329](INTERPRETER-FINDINGS.md#if329)). So what remains is not an instrument gap but a MACHINE one — the variance that defeats a 5 % bar is session-and-machine variance, not the lane's. **Re-open trigger:** a dedicated, quiesced measurement host. Re-measure the per-process CV there over ≥30 processes spanning several sessions and at least two days, with the session treated as a factor rather than held constant; if it lands under ~1 %, a 5 % bar becomes viable and this decision should be revisited. Until such a host exists, re-deriving any of the four refuted routes on this machine class is re-investigation, which is what this section exists to prevent.

- **IG150 — the two form-line message parameters (`<field>.Vordruckzeile`, `<field>.Vordruckname`) render VERBATIM, because there is no kernel behaviour to match (opened 2026-09-07).** Both are statically ADMITTED on an A12 model and both **skip** the field-membership gate every other name-position form meets ([KF279](KERNEL-FINDINGS.md#kf279)), so a model carrying one passes `model check`. At runtime **both kernel strategies fault identically** — the rule's message text comes back as `An error occurred while evaluation the data check: Index 1 out of bounds for length 1` — while the interpreter leaves the `$…$` token in place, measured three-way in `adapter.laws.RuleMessageFormLineParameterDiffTest`.

  **Why this is out of scope rather than an unimplemented parameter** (the distinction from the shipped IG148, which was the same shape with a kernel target): the form line is an H-model concept with no A12 counterpart, the kernel's static checker verifies only that the argument names an existing field, and `NO_VORDRUCKZEILE` — the class its own enum reserves for "the field specifies no form line" — is raised nowhere in the 30.8.1 checkout (a12-kernel-lean's source measurement, carried here as their report). There is therefore no defined value to emit: matching the kernel would mean encoding an internal error, and emitting an empty string or a form-line number would be inventing behaviour. The verbatim token is the fail-fast reading and is deliberately visible.

  **Re-open trigger:** the kernel raises `NO_VORDRUCKZEILE` (making the shape a static refusal we should pre-check or delegate cleanly), or it renders a defined value for these parameters on an A12 model. Either gives the differential a target and turns this into an ordinary parity gap.
