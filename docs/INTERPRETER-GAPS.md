# interpreter — gaps & open issues

> **What this is** — the interpreter's peer of [`DEV-API-GAPS.md`](DEV-API-GAPS.md) and [`FEATURE-GAPS.md`](FEATURE-GAPS.md): the single tracking surface for **open `:interpreter` gaps, deferred items, and to-fix issues**. It exists so open work is easy to **track, report, and pick up** — and so [`INTERPRETER-FINDINGS.md`](INTERPRETER-FINDINGS.md) can be what a findings doc should be: **settled, verified knowhow** you read to warm up and not re-investigate (like `KERNEL-FINDINGS.md`), never a backlog of dispositions ("open / to fix / deferred"). Per the CLAUDE.md *"rationale is timeless; a disposition is status"* rule — the findings hold the timeless fact, this ledger holds the live status.
>
> **The lifecycle.** A gap is born here with an `IG<n>` code under the section matching its status (§1 open / §2 deferred / §3 out-of-scope). When it ships, three things happen **in the fix's own commit**: (1) its **rationale graduates to a numbered `IF<n>` finding** in [`INTERPRETER-FINDINGS.md`](INTERPRETER-FINDINGS.md) — that finding notes it "graduated from IGn"; (2) any code/test comment citing `IGn` is **repointed to `IFn`**; (3) the gap's row is **deleted from this ledger**. **There is no "fixed/shipped" section — we don't record fixed gaps.** A fixed gap is no longer a gap; **git is the history of *when/what* was fixed, and the `IFn` finding is the *why*** — a hand-kept "shipped" list would only duplicate both and rot. So this ledger only ever lists **live, unfinished work** (the already-shipped IF20-per-cell / IF21 / IF23 / IF24 / IF25 live as findings, not here). A **deferred** gap stays in §2 with its re-open trigger, and an **ongoing as-touched** refactor stays in §2 with its remaining-work note (it is progressing in increments, not parked — its shipped parts graduate to its `IF<n>` finding while the row stays until *all* of it lands); the technical detail of each gap lives in its cited `IF<n>` finding (the knowhow), this ledger holds only *what's left to do and why*.
>
> **Section invariant (the placement rule):** every section holds exactly one **live** status — **§1 = open, §2 = deferred / ongoing-incremental, §3 = out-of-scope**. A FULLY-shipped/graduated entry belongs in **none** of them: completing it *deletes* its row (see the lifecycle). So §1 reads "(none)" whenever nothing is open, and a fully-FIXED entry **anywhere** in this ledger is a bug in *this doc* — git already records the fix. (A partially-shipped *ongoing* refactor in §2 is not "fixed" — it stays until all of it lands.)
>
> **Scope.** `:interpreter` only — the kernel-free Kotlin evaluator (parser, evaluation semantics, model loader, the differential/perf harnesses' interpreter side). dmkit (rulekit/modelkit/edit) authoring gaps go to [`DEV-API-GAPS.md`](DEV-API-GAPS.md); kernel-coverage classification stays in the MVK / RT-semantics / grammar ledgers.

## 1. Open (to fix)

- **IG68 — standalone commonMain has no complete workspace/prepared-model assembler (graduated residual of IG67 / IF122, broadened 2026-07-19; activated 2026-07-26; implementation complete through R2.10, browser and dmtool gates remain).** `ModelLoader` handles only one already-expanded, self-contained, name-path-keyed model. It cannot mount `modelReferences`/includes, merge imported typedefs and inline effective types, normalize opaque ids to name paths, or remap included references; recognized raw residue does **not** load silently — an unexpanded include, unresolved `TypeDefType`, or opaque element id is rejected loudly (IF145). R2.2–R2.10 now provide one original commonMain preparation pipeline over a bounded immutable workspace, constructible from an initial source map or collected on demand through an asynchronous exact-id `ModelSourceProvider`: it implements all four transforms, the assembler-only expanded artifact, structured acquisition/preparation diagnostics, JVM/Node Java-reader/Kernel parity, immutable prepared ownership, the minimum evaluation façade, Kotlin suspension, an unexported Promise/`AbortSignal` bridge, and Java `CompletionStage` acquisition without platform types in `commonMain`. Collection requests only one snapshot-consistent discovered closure, loads each id at most once, verifies identity and SHA-256 before following edges, freezes admitted bytes, enforces acquisition and aggregate limits, propagates typed no-retry cancellation/failures, and retains only sanitized provenance. The row remains open for R2.11 dmtool dogfooding and R4.2's real-browser workspace/parity gate; only that browser evidence graduates it. The public contract is specified in [INTERPRETER-API-PROPOSAL](INTERPRETER-API-PROPOSAL.md) §4.1 and the release gate in [INTERPRETER-RELEASE-PROPOSAL](INTERPRETER-RELEASE-PROPOSAL.md).

- **IG85 — the standalone interpreter is source-consumable but has no Maven/npm publication wiring or ABI lock (delivery gap, found 2026-07-19; activated 2026-07-26; npm measurement trigger transferred from IG79 by IF173).** The module's dependency direction and purity lint make it eligible to become an independent artifact, but `interpreter/build.gradle` currently configures only the KMP JVM/Node builds: it has no Maven publication, functional exported npm API, production package/bundle, generated `.d.ts`, publication coordinates, consumer metadata verification, or Kotlin binary-compatibility guard. The Kotlin/JS production-library experiment is not a usable substitute: with no exported API its main module is effectively empty and its declared type file is absent, so IF173's delivery collector correctly records no npm byte base. The public-library wave has started; publication cannot complete without this row. Land Maven + npm consumer fixtures, GitHub-only deployment policy, and KMP/TypeScript ABI locks together. The same increment must pack the real production npm artifact, require its non-empty API and `.d.ts`, execute a non-repo consumer smoke, and add its bytes/SHA plus previous-release delta to IF173's delivery report; a KLIB, empty DCE output, or unpacked `node_modules` closure is not that measurement.

- **IG86 — no browser build or verification lane (activated 2026-07-26; prior deferral recorded in IF138).** `:interpreter` runs under `js { nodejs() }` only — no `browser()` target, browser smoke/conformance replay, bundled consumer fixture, or browser first-answer bar. Decimal and regex host semantics are complete under IF163/IF164; the regex translator and registry use the browser-safe ES2018 baseline. The requested GitHub Pages showcase is now a real browser consumer, so the re-open trigger has fired. Add a `browser()` target and packed-package bundle smoke, replay the portable conformance subset in a real browser, prove the IG68 workspace preparation path there, and give browser first-answer its own explicitly scoped owner-ratified bar. Node remains a CI proxy only after real-browser equivalence is demonstrated; retain IF164's dialect locks and avoid Node-only APIs.

New semantic or performance defects belong here only while they have actionable work and a defined completion gate.

## 2. Deferred / ongoing-incremental (recorded with status; detail in [`INTERPRETER-FINDINGS.md`](INTERPRETER-FINDINGS.md))

Two kinds live here when present: a **deferred** item (parked or owner-accepted until its re-open trigger flips) and an **ongoing as-touched** refactor. A deferred item may be a safely guarded capability residual; it is not a silent semantic mismatch. A fully shipped item is deleted (its `IF<n>` finding + git are the record).

- **IG83 — Route A: general portable timezone-id support (owner-accepted deferred capability; Route B completed as IF155/IF165/IF166).** The enforced evaluator contract supports exact `{UTC, GMT, Europe/Berlin}`; Berlin uses the independently locked legacy-`java.util.TimeZone` history, explicit invalid ids fail as configuration errors, and known kernel-legal zones outside the set fail with the precise supported-scope diagnostic. The kernel accepts a wider Java `TimeZone` id domain, so this remains an honest product limit, not full timezone parity. **Re-open trigger:** a real consumer needs a non-Berlin zone or a publication wave promises full timezone parity. Then build one portable, deterministically versioned tzdb for JVM + JS and pin its version relationship to the kernel's JDK tzdb.
