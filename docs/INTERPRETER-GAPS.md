# interpreter — gaps

> **What this is** — the interpreter's peer of [`DEV-API-GAPS.md`](DEV-API-GAPS.md) and [`FEATURE-GAPS.md`](FEATURE-GAPS.md): the single tracking surface for **open `:interpreter` gaps, deferred items, and to-fix issues**. It exists so open work is easy to **track, report, and pick up** — and so [`INTERPRETER-FINDINGS.md`](INTERPRETER-FINDINGS.md) can be what a findings doc should be: **settled, verified knowhow** you read to warm up and not re-investigate (like `KERNEL-FINDINGS.md`), never a backlog of dispositions ("open / to fix / deferred"). Per the CLAUDE.md *"rationale is timeless; a disposition is status"* rule — the findings hold the timeless fact, this ledger holds the live status.
>
> **Lifecycle.** A gap is born here with an `IG<n>` code under the section matching its status (§1 open / §2 deferred / §3 out-of-scope). When it ships, three things happen **in the fix's own commit**: (1) its **rationale graduates to a numbered `IF<n>` finding** in [`INTERPRETER-FINDINGS.md`](INTERPRETER-FINDINGS.md) — that finding notes it "graduated from IGn"; (2) any code/test comment citing `IGn` is **repointed to `IFn`**; (3) the gap's row is **deleted from this ledger**. **There is no "fixed/shipped" section — we don't record fixed gaps.** A fixed gap is no longer a gap; **git is the history of *when/what* was fixed, and the `IFn` finding is the *why*** — a hand-kept "shipped" list would only duplicate both and rot. So this ledger only ever lists **live, unfinished work** (the already-shipped IF20-per-cell / IF21 / IF23 / IF24 / IF25 live as findings, not here). A **deferred** gap stays in §2 with its re-open trigger, and an **ongoing as-touched** refactor stays in §2 with its remaining-work note (it is progressing in increments, not parked — its shipped parts graduate to its `IF<n>` finding while the row stays until *all* of it lands); the technical detail of each gap lives in its cited `IF<n>` finding (the knowhow), this ledger holds only *what's left to do and why*.
>
> **Section invariant (the placement rule):** every section holds exactly one **live** status — **§1 = open, §2 = deferred / ongoing-incremental, §3 = out-of-scope**. A FULLY-shipped/graduated entry belongs in **none** of them: completing it *deletes* its row (see the lifecycle). So §1 reads `_None open._` whenever nothing is open — the marker every `-GAPS` ledger uses, so one grep rolls up the whole family (`GapLedgerTemplateGuardTest`) — and a fully-FIXED entry **anywhere** in this ledger is a bug in *this doc* — git already records the fix. (A partially-shipped *ongoing* refactor in §2 is not "fixed" — it stays until all of it lands.)
>

## 1. Open

- **IG124 — the hosted anchor block measures a revision the code has moved well past.** It was authored from three sequential dispatched runs of `1845f8af` (2026-08-11), which predates both 2026-08-12 optimizations; the local block's refresh measured the same lanes at `0.47×`–`1.11×` of their old numbers (34 of 36 fell; two compute-overlay lanes rose slightly), so the hosted ceilings are loose by roughly that factor and the class's absolute bar cannot fire. It is not silent about it — `[perf][STALE]` now reports every lane below `0.6 × anchor − slack` ([IF280](INTERPRETER-FINDINGS.md#if280)) — but a report is not a bar.

  **Why it is not fixed here: a hosted block can only be authored from hosted runs, and those need the revision on the remote.** `origin/main` is at `1845f8af` with 40+ local commits unpushed, so nothing newer is dispatchable. **Closing step, once the commits are pushed:** three *strictly sequential* `gh workflow run 'Nightly performance'` dispatches (concurrent ones contend and inflate each other — IF280's dispatch note), then `scripts/perf-anchor.sh refresh` over the three downloaded artifacts. The refresh will also supply the block's `machine` field, which the current one predates. Two smaller caveats the block already carried and which that refresh should clear: its `jdk` reads `21.0.11,21.0.12` because the script joins differing JDKs rather than refusing them, and 2 of its 36 keys have two samples rather than three.

  **Two loose ends in the same mechanism, from the 2026-08-12 cold review.** (a) `scripts/perf-anchor.sh` refuses a header with **no** `machine` but accepts the literal `"unknown"` the probe emits when it cannot name the machine, which would author a block the gated lane then refuses forever — the never-fires block the refusal exists to prevent. Reachable on **linux-aarch64**, where `/proc/cpuinfo` carries `CPU implementer`/`CPU part` and no `model name`; `PerfMachineIdentityTest.theProbeNamesTheMachineThisRunIsMeasuringOn` reds there, so it surfaces, but the script should refuse the sentinel too. (b) `scripts/perf-history.sh` groups rows by environment alone and its header carries commit/JDK/processors but not `machine` — the one surface where a human compares absolute numbers across runs, built on the assumption this work disproved.

- **IG126 (reopened) — four of the five list-in-key memos have still never been measured on a scenario that runs them.** [IF285](INTERPRETER-FINDINGS.md#if285)'s sweep profiled a full validation and a compute cascade, and read 0 samples for four memos whose owning code those scenarios never execute — `ValidationPass.indexColumns` even documents itself as "Empty and unread in a FULL validation". A 0 from a scenario that cannot reach the code is not evidence of cheapness, and the four are fields rather than classes, so no frame carries their name even when hot. Only `AggregateMemoKey` was genuinely measured (2 of 1,615 validate samples).

  **Closing step, per memo, each needing a scenario that engages it:** a **partial-validation** profile for `ValidationPass.indexColumns:55` and `DmInterpreter.decided` (`:326`/`:354`/`:545`); a model carrying a `RepetitionNotUnique` or index group for `RepetitionNotUniqueEvaluator.rows:148`; a **relevance-scoped** call for the group-relevance cache at `DmInterpreter.kt:1111`. Then fix or record each as measured-and-cheap. A source-level unreachability argument is an acceptable substitute for a profile, but "0 samples" from these two scenarios is not. `scripts/perf-keys.sh` has no partial-validation or RNU driver today, so this needs one added.

- **IG127 — the unmemoized over-repetition prelude, 20.25 % of the validate profile.** `ValueAdmissionCache.resultAt` calls `AutoChecks.overRepetitionResultAt` before consulting its memo, so a `HashMap<String, PathInfo>` lookup plus a bounds loop runs on every consultation by every consumer — all of that 20.25 % arrives through that single caller. [IF284](INTERPRETER-FINDINGS.md#if284) moved the walk out of the key deliberately, so putting it back in would reintroduce the cell-shaped key the same finding removed: the fix has to make the *walk* cheap (or reach the `PathInfo` once per path) while the memo stays value-shaped. Attributed and reproducible with `scripts/perf-keys.sh validate`; numbers in INTERPRETER-PERFORMANCE "Checkpoint 2026-08-12 — the list-in-key sweep".

  **One attempt is already ruled out by measurement, so the next one should not repeat it.** A one-slot memo of the resolved `path → PathBounds` handle in the call-local `ValueAdmissionCache`, keyed by identity, was built and reverted: the same probe still showed in 11.36 % of samples afterwards, because the consultations that create the multiplicity happen in different *passes*, which interleave paths row-major rather than repeating one path in consecutive calls. A per-path memo of any shape is therefore the same probe. **Closing step:** resolve the bounds once per cell where the formal walk already has a per-cell record (a resolved handle on the placement/scan cell), which means deciding how far model-static data may travel into the document index — a design call, not a tuning one. With a before/after profile and the growth anchors re-measured. *(The gap's second item — `OverlayContext.stateOf`'s three hashes of one key — shipped 2026-08-12 as [IF286](INTERPRETER-FINDINGS.md#if286).)*

- **IG121 — the flag surface is a print and a recorded number, with no trend detection over the series.** [IF281](INTERPRETER-FINDINGS.md#if281) makes every self-referential bar a flag on shared hardware and the cross-engine comparison the gate. The gate half is built and enforced; the flag half is only half-built. A breach prints `[perf][FLAG]` and the run's medians land in [`perf-results/`](../perf-results/README.md) with their status, which `scripts/perf-history.sh` renders as a table with a crude newest-vs-median-of-earlier trend column — so a regression is *visible to someone who looks*, and nothing looks.

  **Three pieces are named and unbuilt, in the order they would pay off.**
  1. **An early-warning band on both cross-engine gates.** They fire only at parity (`< 1.0`), so they say nothing until a catastrophe. *(Rewritten 2026-08-12, twice over. The original text proposed a flat `0.5` and called it the cheapest of the three. Both claims are now false. The flat constant rested on margins of `5×`–`17×` measured on the **two** scenarios that carried a bar at the time; once the bar reached all seventeen the tightest row sat at `0.52`, so a flat band would fire on it every night from the first run. The obvious repair — derive the band from each row's own noise — was then **built and falsified in the same session**: the only per-row dispersion a single gate run can see is the spread between its interleaved pairs, and that is not the run-to-run spread of the reported row. A pair ratio divides two three-iteration medians while the row divides two nine-sample medians, so it is dispersed by construction — `FVNU-uniqueness @250` spread `3.21×` between its pairs against a run-to-run spread near `1.3×`, and a band built on it warned about three rows the real quantity leaves alone (the traced run is [`2026-08-12T010604Z`](../perf-results/darwin-aarch64/2026-08-12T010604Z.jsonl)). The code was removed rather than kept, and the negative result recorded here.)* **What that leaves:** the honest per-row noise lives in the committed series across runs, so piece 1 is not independent of piece 2 — it is downstream of it, and cannot be built first. It also needs the series segmented by revision, not only by platform: after the 2026-08-12 `PF-framed` optimization that row's historical spread is `2.5×` and means nothing about its noise.
  2. **Trend / change-point detection over the recorded series**, segmented on JDK, OS and hardware identity, since a platform change re-bases every number and would otherwise read as a regression. The record exists and carries the conditions; nothing reads it but the table renderer. **This is the prerequisite for piece 1**, not a parallel nicety — see above.
  3. **Environment-quality fields per observation** — steal time, cgroup throttling, GC and JIT activity in the window — **recorded, never used to reject a sample**. Rejection on a post-treatment variable launders the evidence: an allocation regression causes GC, so excluding GC windows censors exactly what proves it.

  **Carried over from the retired proposal, so they are not rediscovered.** Four things it recorded have no other home. (a) The comparative margins rest on a small basis — six rows, only two scenarios with two scales — which the 2026-08-12 checkpoint has now widened to 34 rows but which is why the first margin claim was wrong. (b) A **paired same-run comparison against the previous release and a pinned performance epoch, in alternating isolated forks** is a fourth flag, not listed above, and it is the only one that can see a uniform regression the anchor's tolerance absorbs. (c) An attempt to measure the inflation from optional stopping **failed to produce a magnitude**: at nominal `α=3.3e-6`, 200 000 simulated trials expect 0.67 events and produced 1, so the mechanism argument stands alone and no number should be quoted for it. (d) Family size is cheap — widening from 36 to 200 hypotheses moves the sample requirement about 13 % — and if a statistical treatment is ever built, warmup must be equalized **by state rather than by iteration count**, with each timed region consuming a correctness checksum outside the clock.

  **What the fourth piece left, found by the same cold review.** (a) Only `kernel parity` passes a lane to `pairedScenarioGrowth`, so the two Number-index lanes (`PerfGateTest.assertNumberIndexCurve`) and `SynthesizedModelPerfTest` still only *print* their warm outcomes — including the instance whose cap set the 8 s budget in the first place ([IF282](INTERPRETER-FINDINGS.md#if282)'s `Number index validate` Groovy arm at N=2,000). Fixing it means those lanes must also record their observations, or the warm rows would join nothing and the guard would refuse them. (b) A lane that **breaches** writes no `cost` row at all: `recordCost` sits after the throwing assertions, so the run whose cost is most interesting is the one that loses it. (c) `cost.scenario` carries a lane-local name (`"CO correlation"`) while `warm`/`observation` carry the fingerprinted identity, so a cost row cannot be joined to the medians it accounts for.

  **The fourth piece SHIPPED 2026-08-12** as the record's `warm` and `cost` kinds ([`perf-results/README.md`](../perf-results/README.md)): the steady-state warm's outcome is written beside the medians it qualifies, joined on the observation's own `(lane, scenario, n, engine)`, and each lane's measurement cost is recorded so the tier's wall time is a sum rather than a line in a deleted log. `PerformanceRecordShapeGuardTest` fails a warm row that joins no observation — the failure a renamed field or a shorthand engine name produces silently, and one it caught during the change itself — and fails when no committed run carries a warm outcome at all, which is the bound of what committed data can prove about a producer.

  **Also unbuilt, and separately triggered:** a deterministic work counter over the index build (`PreparationObserver`/`PreparationWork`, the eval-time `CacheObserver`) is what would let the `COLD first-call` lane be *gated* on shared hardware instead of flagged — the one lane where a flag is a real loss, since its coverage is the super-linear index build the warm harness structurally cannot see. **Re-open trigger:** a cold-path regression reaches a release, or the COLD lane flags twice on hosted runs without a local reproduction.

## 2. Deferred / ongoing-incremental (recorded with status; detail in [`INTERPRETER-FINDINGS.md`](INTERPRETER-FINDINGS.md))

Two kinds live here when present: a **deferred** item (parked or owner-accepted until its re-open trigger flips) and an **ongoing as-touched** refactor. A deferred item may be a safely guarded capability residual; it is not a silent semantic mismatch. A fully shipped item is deleted (its `IF<n>` finding + git are the record).

- **IG83 — Route A: general portable timezone-id support (owner-accepted deferred capability; Route B completed as IF155/IF165/IF166).** The enforced evaluator contract supports exact `{UTC, GMT, Europe/Berlin}`; Berlin uses the independently locked legacy-`java.util.TimeZone` history, explicit invalid ids fail as configuration errors, and known kernel-legal zones outside the set fail with the precise supported-scope diagnostic. The kernel accepts a wider Java `TimeZone` id domain, so this remains an honest product limit, not full timezone parity. **Re-open trigger:** a real consumer needs a non-Berlin zone or a publication wave promises full timezone parity. Then build one portable, deterministically versioned tzdb for JVM + JS and pin its version relationship to the kernel's JDK tzdb.
