# interpreter — gaps

> **What this is** — the interpreter's peer of [`DEV-API-GAPS.md`](DEV-API-GAPS.md) and [`FEATURE-GAPS.md`](FEATURE-GAPS.md): the single tracking surface for **open `:interpreter` gaps, deferred items, and to-fix issues**. It exists so open work is easy to **track, report, and pick up** — and so [`INTERPRETER-FINDINGS.md`](INTERPRETER-FINDINGS.md) can be what a findings doc should be: **settled, verified knowhow** you read to warm up and not re-investigate (like `KERNEL-FINDINGS.md`), never a backlog of dispositions ("open / to fix / deferred"). Per the CLAUDE.md *"rationale is timeless; a disposition is status"* rule — the findings hold the timeless fact, this ledger holds the live status.
>
> **Lifecycle.** A gap is born here with an `IG<n>` code under the section matching its status (§1 open / §2 deferred / §3 out-of-scope). When it ships, three things happen **in the fix's own commit**: (1) its **rationale graduates to a numbered `IF<n>` finding** in [`INTERPRETER-FINDINGS.md`](INTERPRETER-FINDINGS.md) — that finding notes it "graduated from IGn"; (2) any code/test comment citing `IGn` is **repointed to `IFn`**; (3) the gap's row is **deleted from this ledger**. **There is no "fixed/shipped" section — we don't record fixed gaps.** A fixed gap is no longer a gap; **git is the history of *when/what* was fixed, and the `IFn` finding is the *why*** — a hand-kept "shipped" list would only duplicate both and rot. So this ledger only ever lists **live, unfinished work** (the already-shipped IF20-per-cell / IF21 / IF23 / IF24 / IF25 live as findings, not here). A **deferred** gap stays in §2 with its re-open trigger, and an **ongoing as-touched** refactor stays in §2 with its remaining-work note (it is progressing in increments, not parked — its shipped parts graduate to its `IF<n>` finding while the row stays until *all* of it lands); the technical detail of each gap lives in its cited `IF<n>` finding (the knowhow), this ledger holds only *what's left to do and why*.
>
> **Section invariant (the placement rule):** every section holds exactly one **live** status — **§1 = open, §2 = deferred / ongoing-incremental, §3 = out-of-scope**. A FULLY-shipped/graduated entry belongs in **none** of them: completing it *deletes* its row (see the lifecycle). So §1 reads `_None open._` whenever nothing is open — the marker every `-GAPS` ledger uses, so one grep rolls up the whole family (`GapLedgerTemplateGuardTest`) — and a fully-FIXED entry **anywhere** in this ledger is a bug in *this doc* — git already records the fix. (A partially-shipped *ongoing* refactor in §2 is not "fixed" — it stays until all of it lands.)

## 1. Open

- **IG131 — nothing mechanically stops a new timing assertion from landing in the broad parallel-fork lane.** `PerfTestClassificationTest` is syntactic by design (name ⇒ tag, tag ⇒ name, closed vocabulary, both lane declarations), so it cannot see a clock-reading assertion written under a neutral name with no tag. A cold review found the estate already contains one: `PerfGrowthEstimatorTest.currentThreadCpuExcludesBlockedWallTime` sleeps 100 ms and asserts `cpu < wall/4` in `:adapter:test`. That one is contention-*safe* (load only adds wall time and leaves CPU near zero, so both of its assertions get easier under load) and stays untagged deliberately, documented at the test — but the reasoning is specific to its shape and the next such assertion may not share it. **Actionable work:** a detector that is not a name heuristic. The false positives to beat are recorded in [INTERPRETER-PERFORMANCE](INTERPRETER-PERFORMANCE.md) "What counts as a performance test" — a helper-name detector admits five harness unit tests that call the bar helpers on *scripted* values plus `KernelParityCoverageGuardTest`, which matches because it scans those sources as text. Candidate discriminator: the bar helpers take their estimate as a closure, so instrumenting `PerfHarness`/`PerfAnchors` to refuse at **runtime** when a real measurement is asserted outside an opted-in lane separates measured from scripted without guessing from source text. **That seam covers only what routes through the harness** — a review's constructible bypass reads `System.nanoTime()` directly and asserts a duration, never reaching it — so the other half is an exact **raw-clock API census** (`nanoTime`, `currentTimeMillis`, `kotlin.time.measureTime`/`TimeSource`, `performance.now`, `Date.now`, `ThreadMXBean`) over the test tree with a reviewed allowlist for the legitimate holders: worker/profiler infrastructure and the one contention-safe harness-contract test. **Completion gate:** a positive control proving the runtime check fires on a neutrally-named timing assertion added to the broad lane, a second proving the census fires on a direct-clock assertion that bypasses the harness, and green on all five legitimate scripted-value callers plus every allowlisted holder — each allowlist entry carrying its reason.

- **IG132 — `:interpreter`'s own tests, including four untagged timing bars, run in no CI lane.** Measured 2026-08-13: `./build.sh --dry-run` for `test`, `:adapter:test` and `:noBackendTest` selects no `:interpreter:jvmTest`/`jsTest` task, and `ci.yml`'s single job names none either, so the module is local-only. **Corrected 2026-08-13** (a cold review's anchored clock-API census against the first count of three, which had come from a `nanoTime`/`currentTimeMillis` sweep that missed `kotlin.time`): **four** classes assert on elapsed time outside the `perf`/`perf-bench` tiers, which are an `:adapter` mechanism. `DocumentScaleTest` asserts `elapsed < 20.seconds` on two 10 000-row scenarios; `InterpreterMultiplatformTest.scalesToManyRepetitionRows` asserts `elapsed < 5.seconds` **while its own comment claims "no hard bound"**; `PartialRelevanceDepthTest` asserts `elapsed < 300` ms; `StarRelevanceReductionGrowthTest` asserts a **3.0× growth floor** over re-measured attempts. Two separable questions, and they should not be answered together: (1) which CI lane runs the module — the semantics are covered by `:adapter`'s differential, but the **JS/Node** target is covered nowhere, and the task to wire is `:interpreter:allTests` (JVM + JS tests only) rather than `:interpreter:check`, which additionally pulls release packaging, API generation, Maven/npm publication verification and runtime-closure work; (2) whether each bar is a genuine performance requirement or a liveness timeout wearing a bar's clothing. **Completion gate:** the lane wired (or its omission recorded as deliberate), and each of the four either demoted to a correctness test plus a framework timeout, converted to a deterministic work counter, or moved into the isolated routine tier. Pre-existing and outside the classification slice that surfaced it.

- **IG130 — seven of the nine routine-tier classes leave no observation in the committed record.** Measured 2026-08-13 on the first tag-selected gate run: all 138 observations come from `PerfGateTest` (36 `accepted`) and `KernelParityGateTest` (102 `unasserted`, all three engines). (Five of the seven are *newly* gated; `Charset` and `CustomType` were already running, in the broad lane, and recorded nothing there either — so this gap predates the classification change for two of them.) `CharsetPerfTest`, `CustomTypePerfTest`, `GroupScopedFillPerfTest`, `OuterCorrelationPerfTest`, `PatternPerfTest`, `EntryPointPerfTest` and `PartialSumOfProductsPerfTest` contribute **zero** rows. They now execute and can fail the gate, which is what the classification change bought — but `perf-history.sh`, `perf-trend.sh`'s change-point detection, the cross-engine margin band and the absolute anchor are all built on the record, so none of them can see these seven. A slow drift in those lanes stays invisible until it crosses a catastrophe floor, which is 6×–1000× away (the blind-band table in [INTERPRETER-PERFORMANCE](INTERPRETER-PERFORMANCE.md) "The regression gate"). **Actionable work:** route their measurements through the recording seam `PerfHarness`/`PerfAnchors` already own, so each emits an `observation` with its lane, scenario fingerprint, scale, engine and clock. **Completion gate** (**corrected 2026-08-13** after a cold review showed the first version admitted an incomplete denominator — "a row per class" passes while sibling bars in the same class stay unrecorded, and `CharsetPerfTest` owns several distinct measurements): recording happens at the **assertion seams**, so every asserted measurement identity emits its own row; `perf-history.sh` renders them; and each new key is then **armed**, because a uniform slowdown leaves both a growth ratio and a same-run cross-engine ratio unchanged, so unarmed rows would let a 2× regression ship under rule 4 of the [performance policy](TESTING-SPEC.md). Arming is gated on three sequential isolated gate runs: if the global `1.65× + 1 ms` tolerance covers the observed spread, arm every key; where a measurement is too unstable for it, improve that estimator rather than widening the tolerance (`ANCHOR_TOLERANCE` was fitted to the existing 36 keys and a per-class relaxation stays refused, IF280). Adjacent to the classification slice that exposed it, not part of it.

## 2. Deferred / ongoing-incremental (recorded with status; detail in [`INTERPRETER-FINDINGS.md`](INTERPRETER-FINDINGS.md))

Two kinds live here when present: a **deferred** item (parked or owner-accepted until its re-open trigger flips) and an **ongoing as-touched** refactor. A deferred item may be a safely guarded capability residual; it is not a silent semantic mismatch. A fully shipped item is deleted (its `IF<n>` finding + git are the record).

- **IG83 — Route A: general portable timezone-id support (owner-accepted deferred capability; Route B completed as IF155/IF165/IF166).** The enforced evaluator contract supports exact `{UTC, GMT, Europe/Berlin}`; Berlin uses the independently locked legacy-`java.util.TimeZone` history, explicit invalid ids fail as configuration errors, and known kernel-legal zones outside the set fail with the precise supported-scope diagnostic. The kernel accepts a wider Java `TimeZone` id domain, so this remains an honest product limit, not full timezone parity. **Re-open trigger:** a real consumer needs a non-Berlin zone or a publication wave promises full timezone parity. Then build one portable, deterministically versioned tzdb for JVM + JS and pin its version relationship to the kernel's JDK tzdb.
