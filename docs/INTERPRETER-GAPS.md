# interpreter — gaps

> **What this is** — the interpreter's peer of [`DEV-API-GAPS.md`](DEV-API-GAPS.md) and [`FEATURE-GAPS.md`](FEATURE-GAPS.md): the single tracking surface for **open `:interpreter` gaps, deferred items, and to-fix issues**. It exists so open work is easy to **track, report, and pick up** — and so [`INTERPRETER-FINDINGS.md`](INTERPRETER-FINDINGS.md) can be what a findings doc should be: **settled, verified knowhow** you read to warm up and not re-investigate (like `KERNEL-FINDINGS.md`), never a backlog of dispositions ("open / to fix / deferred"). Per the CLAUDE.md *"rationale is timeless; a disposition is status"* rule — the findings hold the timeless fact, this ledger holds the live status.
>
> **Lifecycle.** A gap is born here with an `IG<n>` code under the section matching its status (§1 open / §2 deferred / §3 out-of-scope). When it ships, three things happen **in the fix's own commit**: (1) its **rationale graduates to a numbered `IF<n>` finding** in [`INTERPRETER-FINDINGS.md`](INTERPRETER-FINDINGS.md) — that finding notes it "graduated from IGn"; (2) any code/test comment citing `IGn` is **repointed to `IFn`**; (3) the gap's row is **deleted from this ledger**. **There is no "fixed/shipped" section — we don't record fixed gaps.** A fixed gap is no longer a gap; **git is the history of *when/what* was fixed, and the `IFn` finding is the *why*** — a hand-kept "shipped" list would only duplicate both and rot. So this ledger only ever lists **live, unfinished work** (the already-shipped IF20-per-cell / IF21 / IF23 / IF24 / IF25 live as findings, not here). A **deferred** gap stays in §2 with its re-open trigger, and an **ongoing as-touched** refactor stays in §2 with its remaining-work note (it is progressing in increments, not parked — its shipped parts graduate to its `IF<n>` finding while the row stays until *all* of it lands); the technical detail of each gap lives in its cited `IF<n>` finding (the knowhow), this ledger holds only *what's left to do and why*.
>
> **Section invariant (the placement rule):** every section holds exactly one **live** status — **§1 = open, §2 = deferred / ongoing-incremental, §3 = out-of-scope**. A FULLY-shipped/graduated entry belongs in **none** of them: completing it *deletes* its row (see the lifecycle). So §1 reads `_None open._` whenever nothing is open — the marker every `-GAPS` ledger uses, so one grep rolls up the whole family (`GapLedgerTemplateGuardTest`) — and a fully-FIXED entry **anywhere** in this ledger is a bug in *this doc* — git already records the fix. (A partially-shipped *ongoing* refactor in §2 is not "fixed" — it stays until all of it lands.)
>
> **Current state.** §1 carries four rows as of 2026-07-30. IG106–IG108 came from the lean project's `SPEC-2026-07-27-*` queue; IG109 records the separately measured field-owned message channel exposed by `EXP-2026-07-30-01`. Every row names its real-kernel basis and completion gate. Every other live item is dispositioned in §2 or §3 with its re-open trigger. New semantic or performance defects belong in §1 only while they have actionable work and a defined completion gate.
>
> **Scope.** `:interpreter` only — the kernel-free Kotlin evaluator (parser, evaluation semantics, model loader, the differential/perf harnesses' interpreter side). dmkit (rulekit/modelkit/edit) authoring gaps go to [`DEV-API-GAPS.md`](DEV-API-GAPS.md); kernel-coverage classification stays in the MVK / RT-semantics / grammar ledgers.

## 1. Open

Four rows, all **measured** against the real kernel rather than inferred. IG106–IG107 are capability gaps where the kernel accepts input we do not: IG106 declines loudly (a guarded, diagnosed refusal — an honest product limit), while IG107 is the harder kind, a **type-level erasure** with no runtime error at all, just a missing factory — the class the root CLAUDE.md client-side-refusal rule names. IG108 is different in kind: nothing refuses those shapes, they are simply not locked yet, and its row carries the measured gate matrix so the evidence is not re-gathered. IG109 is an unmodelled output channel whose two kernel producers cannot be collapsed to the existing rule-message renderer.
- **IG106 — the model loader declines `MONTH_OPTIONAL` and `YEAR_OPTIONAL` date precisions.** This one is a *guarded* decline, not a silent mismatch: `ModelLoader` names both in `UNSUPPORTED_DATE_PRECISIONS` and raises `UnsupportedDatePrecisionException`, and the interpreter's own `DatePrecision` enum is `{FULL, DAY_OPTIONAL, FRAGMENT}`. It is still a capability gap, because the kernel admits the wider precisions: `ValueAsDate(ApproxMonth, FirstDay)`, `ValueAsDate(ApproxYear, FirstDay)`, and `YearFromDate(ApproxMonth)` are all accepted (measured 2026-07-29 on a modelkit draft; modelkit already emits the two precisions). **Completion gate:** the loader admits all four precisions, `ValueAsDate` completes an unknown month before the day boundary, and an unknown YEAR returns a non-relevant date so a direct comparison is UNKNOWN rather than ordinary non-firing emptiness. Reconciles lean SPEC-2026-07-27-03 (and unblocks the two wider modes in SPEC-2026-07-27-01).
- **IG107 — `Date(...)`/`Time(...)` component-declaration gates are not modelled.** The kernel's positional gates were measured in full on 2026-07-29 (source: `CheckBaseDateConstructionImpl` + `CheckDatumKonstruktImpl`/`CheckTimeKonstruktImpl`; confirmed by `rule check`): a Number component passes on `maxLength == expected` **or** an exact/flexible `maxValue`, needs no declared fractional digits (an *unspecified* `maxFractionalDigits` passes), and needs a nonnegative domain; a String component needs `maxLength == expected` plus one of six digit-only patterns or an extensible enum; complete Year additionally accepts a Date field of format `yyyy`. The `maxValue` arm and the six-pattern String arm are **measured but not yet locked**; DG26/finding 104 now makes the stored-length arm and the `maxIntegerDigits`-is-not-a-substitute separator authorable. KF63 corrects the former DG27 premise: extensible-enum is a client-SPI runtime quality with no DM-JSON property, so that non-serializable branch is characterized from source rather than invented in the model shape. **Completion gate:** the complete serializable positional matrix is locked as static accept/reject cases and the interpreter enforces the admitted declaration gates. Reconciles the remainder of lean SPEC-2026-07-27-10 / SPEC-2026-07-27-08 / SPEC-2026-07-27-13.
- **IG108 — the `Date(...)`/`Time(...)` CONSTANT and EXTRACTOR component forms are unlocked (not blocked — just not done).** Nothing prevents these: the typed `DateConstruction`/`TimeConstruction` operands are already `Calculation`, so both forms are representable today, and no client-side check refuses them. The gate matrix was **measured** on 2026-07-29 and is recorded here so the next pass does not re-probe it:
  - **Quoted constants — CLOSED 2026-07-29, no longer part of this gap.** Admission, the positional runtime decoding, and the BMP-vs-supplementary digit boundary are all measured and locked; see KERNEL-FINDINGS §6 and `DateComponentConstantLawsTest` / `DateComponentConstantDiffTest` / `interpreter DateComponentConstantTest`. The Time-component constant gates (no width gate, real-clock bound) remain part of the Time arm below.
  - **Extractors.** Only the position-matching token is admitted, and its source is the ordinary nonliteral temporal grammar, not just a direct field: `Date(DayFromDate(OrderDate), MonthFromDate(OrderDate), YearFromDate(OrderDate))` ✓, `Date(DayFromDate(AddDays(OrderDate, 1)), …)` ✓, `Date(DayFromDate(Today), …)` ✓, `Date(DayFromDate(ScheduledAt), …)` ✓ (a DateTime source), and mixed extractor/constant/field prefixes ✓. A mismatched token is `MVK_INVALID_DATE_OR_TIME_EXTRACT_OP`; `QuarterFromDate` anywhere is `MVK_DATE_OR_TIME_EXTRACT_OP_NOT_ALLOWED`; any extractor in the **four**-part form is `MVK_EXTRACT_OP_NOT_ALLOWED_4_DATE_CONSTRUCT_WITH_4_PARAMS`; a direct temporal **literal** inside the extractor is `MVK_NO_CONST`. `Time(HoursFromTime(PickupTime|AddHours(ScheduledAt,1)|Now), …)` ✓ with the same mismatch/literal rules. *(Reconciles SPEC-2026-07-27-12 and SPEC-2026-07-27-09.)*
  - **`TimeFromDateTime`** needs a complete DateTime operand — a Date or Time source is `MVK_WRONG_DATE_FORMAT_FOR_OP` — and composes under `DateTime(ValueAsDate(…), TimeFromDateTime(…))` ✓. *(Reconciles the static half of SPEC-2026-07-27-07; its wall-clock projection is a runtime claim needing a differential.)*
  - **Bonus, unrequested:** the two-parameter `Date("01","01")` form is legal **when the model declares a base year** (`CheckDatumKonstruktImpl` refuses it with `MVK_MISSING_YEAR` otherwise), producing a year-less date. Not in the lean queue and not modelled here.

  **Static halves CLOSED 2026-07-30** — the constant, extractor and `TimeFromDateTime` matrices are now maintained cases (`DateComponentConstantLawsTest`, `TemporalExtractorComponentLawsTest`), including the three distinct extractor refusal codes and the `MVK_NO_CONST` direct-literal arm. **Completion gate for what remains:** the extractor form still needs JVM/Node + dual-kernel RUNTIME coverage for source-before-extractor order and the empty/formal source propagation, and `TimeFromDateTime` its wall-clock projection.

- **IG109 — field-owned custom error templates are not retained or rendered.** `ModelLoader` retains neither a String type's invalid-pattern `errorMessage` nor `requirednessConfig.errorMessage`, so interpreter formal messages cannot surface the model author's text. EXP-2026-07-30-01 proves this is not safely implementable by reusing `renderMessage`: an `en_US` String-pattern template accepts only lowercase `$field$`/`$field.value$`, rejects `$$` as an empty invalid parameter, and inserts values once; the measured requiredness template instead accepts and preserves `$$` on both kernel strategies. **Completion gate:** retain the two declarations as distinct model channels, reproduce the dynamic-Groovy anchor for each measured legal form on JVM and Node, keep inserted bytes opaque, refuse unsupported producer/locale forms loudly rather than applying the rule grammar, and add dual-kernel differentials without changing rule/computation message rendering.

## 2. Deferred / ongoing-incremental (recorded with status; detail in [`INTERPRETER-FINDINGS.md`](INTERPRETER-FINDINGS.md))

Two kinds live here when present: a **deferred** item (parked or owner-accepted until its re-open trigger flips) and an **ongoing as-touched** refactor. A deferred item may be a safely guarded capability residual; it is not a silent semantic mismatch. A fully shipped item is deleted (its `IF<n>` finding + git are the record).

- **IG83 — Route A: general portable timezone-id support (owner-accepted deferred capability; Route B completed as IF155/IF165/IF166).** The enforced evaluator contract supports exact `{UTC, GMT, Europe/Berlin}`; Berlin uses the independently locked legacy-`java.util.TimeZone` history, explicit invalid ids fail as configuration errors, and known kernel-legal zones outside the set fail with the precise supported-scope diagnostic. The kernel accepts a wider Java `TimeZone` id domain, so this remains an honest product limit, not full timezone parity. **Re-open trigger:** a real consumer needs a non-Berlin zone or a publication wave promises full timezone parity. Then build one portable, deterministically versioned tzdb for JVM + JS and pin its version relationship to the kernel's JDK tzdb.
