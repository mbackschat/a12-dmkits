# interpreter — gaps & open issues

> **What this is** — the interpreter's peer of [`DEV-API-GAPS.md`](DEV-API-GAPS.md) and [`FEATURE-GAPS.md`](FEATURE-GAPS.md): the single tracking surface for **open `:interpreter` gaps, deferred items, and to-fix issues**. It exists so open work is easy to **track, report, and pick up** — and so [`INTERPRETER-FINDINGS.md`](INTERPRETER-FINDINGS.md) can be what a findings doc should be: **settled, verified knowhow** you read to warm up and not re-investigate (like `KERNEL-FINDINGS.md`), never a backlog of dispositions ("open / to fix / deferred"). Per the CLAUDE.md *"rationale is timeless; a disposition is status"* rule — the findings hold the timeless fact, this ledger holds the live status.
>
> **The lifecycle.** A gap is born here with an `IG<n>` code under the section matching its status (§1 open / §2 deferred / §3 out-of-scope). When it ships, three things happen **in the fix's own commit**: (1) its **rationale graduates to a numbered `IF<n>` finding** in [`INTERPRETER-FINDINGS.md`](INTERPRETER-FINDINGS.md) — that finding notes it "graduated from IGn"; (2) any code/test comment citing `IGn` is **repointed to `IFn`**; (3) the gap's row is **deleted from this ledger**. **There is no "fixed/shipped" section — we don't record fixed gaps.** A fixed gap is no longer a gap; **git is the history of *when/what* was fixed, and the `IFn` finding is the *why*** — a hand-kept "shipped" list would only duplicate both and rot. So this ledger only ever lists **live, unfinished work** (the already-shipped IF20-per-cell / IF21 / IF23 / IF24 / IF25 live as findings, not here). A **deferred** gap stays in §2 with its re-open trigger, and an **ongoing as-touched** refactor stays in §2 with its remaining-work note (it is progressing in increments, not parked — its shipped parts graduate to its `IF<n>` finding while the row stays until *all* of it lands); the technical detail of each gap lives in its cited `IF<n>` finding (the knowhow), this ledger holds only *what's left to do and why*.
>
> **Section invariant (the placement rule):** every section holds exactly one **live** status — **§1 = open, §2 = deferred / ongoing-incremental, §3 = out-of-scope**. A FULLY-shipped/graduated entry belongs in **none** of them: completing it *deletes* its row (see the lifecycle). So §1 reads "(none)" whenever nothing is open, and a fully-FIXED entry **anywhere** in this ledger is a bug in *this doc* — git already records the fix. (A partially-shipped *ongoing* refactor in §2 is not "fixed" — it stays until all of it lands.)
>
> **Scope.** `:interpreter` only — the kernel-free Kotlin evaluator (parser, evaluation semantics, model loader, the differential/perf harnesses' interpreter side). dmkit (rulekit/modelkit/edit) authoring gaps go to [`DEV-API-GAPS.md`](DEV-API-GAPS.md); kernel-coverage classification stays in the MVK / RT-semantics / grammar ledgers.

## 3. Out of scope (won't build unless the trigger flips; recorded so it's not re-investigated)

- **German render target unparseable by the interpreter** (was IG28) — **out-of-scope, verified 2026-07-06.** `DslRenderer(ConditionLanguage.DE)` emits `Und`/`FeldAngegeben`/`Heute`/`@Von`; the interpreter's parser is EN-only. This is **correct by construction, not a gap**, because the interpreter only ever parses **stored** conditions, and the kernel stores every `errorCondition` in **English keywords regardless of authoring language** — confirmed against the real German A12 Tools workspace (2025.06-ext5): its stored conditions read `GroupFilled(...)`/`FieldNotFilled(...)`/`And`/`MinValue(...)`, not `Und`/`FeldAngegeben`. The German render is a **display-only** transform, never round-tripped back through the interpreter (dmtool's `model eval`/`rule eval` read the stored English form; authoring accepts DE via the kernel's language-parametric parser on the JVM, not the interpreter). Re-open trigger: the kernel starts persisting conditions in the authoring language, or a consumer needs the interpreter to parse a DE-rendered string. Detail: KERNEL-FINDINGS "stored conditions are canonical English".
- **`SumOfProducts` over plain (non-repetition-list) fields** — **parity-by-construction, probe-confirmed 2026-07-06** (was IG33). `SumOfProducts(Qty, Price)` over two plain `FieldRef`s is **rejected by the kernel at codegen** with `MVK_REPEATABLE_LEVEL_REQUIRED` ("All fields must be repeatable at least at one layer"), so it never appears in a valid/loadable model — the interpreter's `sumOfProducts` (which resolves both operands as stars) is unreachable on any valid input. No interpreter change; the RuleValidator/kernel is the gate. Re-open trigger: a kernel upgrade that starts accepting a non-repeatable `SumOfProducts`. Detail: IF51.
- **`mandatoryGroup`** (`FEHLER_PFLICHTKONTEXT`) — **source-confirmed unreachable in 30.8.1**: the code is defined but **never emitted**, and **no DM-JSON property declares a group mandatory**, so it can't fire on any loadable model (parity by construction). Was the deferred IG3; re-check on a kernel upgrade. Detail: KERNEL-FINDINGS "mandatoryGroup is a DEAD code in 30.8.1".
- **custom-ref error-entity attribution** (`IRule.getCustomRefErrorEntitiesIfFilled/IfNotFilled`) — **source-confirmed unwired in 30.8.1**: the md-model rule mapping returns empty pending A12K-2281/2361, so the kernel always uses its default error-entity attribution (which the interpreter matches; `CustomConditionDiffTest` locks the CustomCondition error field). Was the deferred IG8; re-check on a kernel upgrade. Detail: KERNEL-FINDINGS "getCustomRefErrorEntities… is UNWIRED in 30.8.1".
- **`getRoundingMode`** on a computation — inert in the runtime (rounding is explicit via the round operators). Detail: IF22.
- **`uniqueValue` (`FEHLER_MULTI_SELECT`)** — was the deferred IG2; **out-of-scope, rationale CORRECTED 2026-06-27** (the earlier "the construct is unmodeled, interpreter reports it unsupported" reasoning was WRONG — a `usageType: "multi-select"` group IS a serialized, loadable construct that **modelkit already authors** (`multiSelectGroup`), and 6 real ones ship in the 2025.06-ext5 workspaces). The real reason it's parity-by-construction: the multi-select value-uniqueness check **is generated by NO kernel evaluation path in 30.8.1** — `AutogeneratedRulesService` (md-runtime) has no multi-select method, AND no `IAutogeneratedRule.getGenerationType()` returns `UNIQUE_VALUE`, so the `CodeGenRuleDefinition.case UNIQUE_VALUE` is unreachable dead code (the runtime-and-codegen sibling of the dead `mandatoryGroup`). **Both** kernel strategies produce nothing, so the interpreter loads the group as a plain repeatable group and (correctly) fires no `uniqueValue` — matching both, NOT a silent-wrong gap and NOT a runtime-vs-codegen divergence. Re-open trigger: a kernel upgrade that wires `UNIQUE_VALUE` into `AutogeneratedRulesService` or an `IAutogeneratedRule`. Detail: KERNEL-FINDINGS "multiSelect value uniqueness is DEAD code"; locked by `adapter.laws.MultiSelectUniquenessDiffTest`.
- **formal-error message TEXT** (byte-identical to the kernel's) — was the deferred IG6; **out-of-scope by the license boundary**: the kernel's formal-error text is German-only and **EUPL/commercial-licensed** (IF3) — it cannot be copied into the kernel-free interpreter. The interpreter emits its own English wording; the *code* / pointer / severity already match the kernel (the parts a consumer acts on). Re-open trigger: a consumer needs verbatim kernel text AND a license-clean source for it exists. Detail: IF (formal errors) / KERNEL-INTEGRATION-NOTES.
