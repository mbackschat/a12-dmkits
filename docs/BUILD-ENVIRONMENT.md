# Build environment — the machine-level traps

> **What this is.** Everything about *getting a build to run correctly on a machine*: the isolated Gradle home, the JDK pin, the build cache, and the limits of the offline/bootstrap path. It was carved out of [KERNEL-INTEGRATION-NOTES.md](KERNEL-INTEGRATION-NOTES.md) on 2026-08-10, which keeps that doc about the kernel itself. Kernel API, version and licensing facts stay there.

## The global init script trap

- **The machine's global Gradle config injects a private registry — the root cause, precisely (confirmed 2026-06-19).** The culprit is one global init script: `~/.gradle/init.d/repositories.gradle`. Init scripts run for *every* build on the machine and force a private, credentialed registry (authenticated with the `~/.gradle/gradle.properties` credentials) into **every** project at **three** levels — `pluginManagement.repositories` (plugins), `allprojects { repositories }` (dependencies — listed first, so it's *tried* first), and `buildscript.repositories`. This repo's `build.gradle` deliberately declares only `mavenCentral()` + `mavenLocal()`, but **a project cannot remove a repository that an init script adds**, so it can't defend itself from inside. A bare `./gradlew` then routes resolution through that registry; if the token is expired or the host is unreachable, it fails *confusingly* — it reads like a network/dependency error, not "you forgot an env var". **One fix is a Gradle home carrying no foreign init script:** init scripts load from `$GRADLE_USER_HOME/init.d/`, so a home without that file loads none. Use `GRADLE_USER_HOME=../.gradle-isolated` (the sibling dir shared across the public A12 repos — the README's `$ROOT/.gradle-isolated` is the same path, since `ROOT=$(cd .. && pwd)`). Note what that directory actually contains: **`init.d/public-repos.init.gradle`**, ours, pinning the public repositories — so "isolated" means *no foreign init script*, never *no init script*, and a private one dropped in there would be honoured like any other. The JDK is the *second* half of the footgun: the shell's `JAVA_HOME` may point at a newer JDK, so pin 21 with `$(/usr/libexec/java_home -v 21)`.
  - **To make forgetting impossible, use the committed wrappers** (added 2026-06-19): [`build.sh`](../build.sh) — `./build.sh <gradle args>` sets both vars then `exec`s `gradlew` (no extra tooling; deterministic for agents/CI) — or, with direnv, [`.envrc`](../.envrc), which auto-applies both on `cd`. Both default `GRADLE_USER_HOME` to the sibling and respect an explicit one (CI sets its own).
  - **Why not let the project self-defend** via `settings.gradle` `dependencyResolutionManagement { repositoriesMode = PREFER_SETTINGS }`? It only governs *dependency* resolution (not the plugin/buildscript injection) **and** would require moving every repo declaration out of `build.gradle` into a centralized settings block — partial *and* invasive, so that particular mechanism stays rejected. What the project does defend with instead is declaration *order* plus an opt-out marker, both in the bullet below; neither centralizes anything.
  - **Changing the global init script needs the machine owner's approval AND a measured no-op for every other project on that machine.** Not a formality: sibling checkouts can declare no repositories of their own and depend entirely on the injection, so a *path-scoped* skip — the first design drafted here — would have broken them silently at their next build, and it was abandoned for exactly that reason. The change that did land (2026-08-10, owner-approved) is a marker-file early return, verified first in a sandbox Gradle home holding a *copy* of the script: against patched and unpatched scripts alike, a project **without** the marker resolved an identical repository list and identical applied plugins, while a marked project got no injection at all. Never commit a per-machine init that hardcodes a private repo. *Security:* a registry token in `~/.gradle/gradle.properties` is stored in cleartext — rotate it if any transcript that surfaced it is untrusted.
  - **A wrapper only helps if you call it — so the injection is removed at its source rather than detected (2026-08-10, after the same failure recurred and went unnoticed for days).** Three designs that *detected* the bad configuration and refused the build were built and discarded first; each needed an opt-out (a flag, an environment variable, a hidden file), and every opt-out is a switch someone can leave on. Two committed pieces replace all of it, with no flag, no environment variable and no machine-wide state: (1) [`settings.gradle`](../settings.gradle) declares its own `pluginManagement.repositories`, and since an init script appends its own in `settingsEvaluated` — *after* the settings file — ours are tried first and an injected registry degrades to a fallback instead of deciding where plugins come from; (2) the committed **`.no-global-gradle-repos`** marker, which an init script honouring it uses to skip this build entirely. **The two pieces do not cover the same half, and an early draft of this paragraph claimed they did.** Ordering covers **plugins only**: a discriminating sandbox run (injecting init script, *no* marker) shows `pluginManagement` resolving `[mavenLocal, portal, mavenCentral, INJECTED…]`, ours first — but the project's dependency repositories come out `[INJECTED…, mavenLocal, mavenCentral]`, injected first, because `Gradle.allprojects` runs before `build.gradle`'s `repositories {}`. So **dependencies are covered by the marker alone.** On a machine whose init script does not honour it, a bare `./gradlew` still resolves dependencies through the injected registry. The measured end-to-end result here — `could not resolve plugin artifact 'org.jetbrains.kotlin.jvm…'` becoming `BUILD SUCCESSFUL`, with `:core:compileJava` also succeeding — was taken *with* the marker active and therefore cannot separate the two pieces; it is evidence for the pair, not for ordering alone. To build *through* such a registry on purpose, delete the marker: it shows in `git status`, it is scoped to one checkout, and it cannot leak into another project. Deleting it fails `BuildPerformancePolicyTest.publicRepositoriesComeFirstAndTheOptOutMarkerIsCommitted` by design — that red is the signal, not a defect. That test strips `//` line comments before asserting, so a commented-out declaration cannot satisfy it; a block comment would, which is not a realistic drift for a settings file.

## Build cache and the Kotlin compiler daemon

- **Disabled Gradle build caching made clean-worktree verification repeat identical Kotlin compilation (confirmed 2026-07-20; CI persistence completed 2026-07-22).** The timed-out aggregate was not a hung test: Gradle reported caching disabled, and the default adapter test compilation alone comprised 255 Kotlin files plus analysis of 131 Java test files while the interpreter compiled for both JVM and JS. A two-clean-worktree reproduction then exposed the coupled cold-build defect: overlapping JVM-test, JS-link, and adapter-test compilation exhausted the Kotlin daemon's 512 MiB default heap. This was not caused by a blocked Gradle web request: task-output caching defaults off, the repo had no `org.gradle.caching` setting, the isolated Gradle home had no override, and no remote build cache is configured. [`gradle.properties`](../gradle.properties) now enables the local build cache and sizes that compiler daemon to 1536 MiB; no runtime or test lane was removed. A follow-up worktree run exposed one path bug in the wrapper: deriving the home from `ROOT/..` created `/private/tmp/.gradle-isolated` for a temporary linked worktree. [`build.sh`](../build.sh) now derives the primary checkout through Git's common directory, so arbitrarily located linked worktrees share the intended sibling home. Build-driving scripts must delegate to that wrapper rather than repeat its environment logic: [`verify-demos.sh`](../scripts/verify-demos.sh) once reintroduced the same `/private/tmp/.gradle-isolated` failure by deriving the home from its linked worktree parent. [`BuildPerformancePolicyTest`](../src/test/java/io/github/mbackschat/a12/dm/BuildPerformancePolicyTest.java) prevents the cache, compiler sizing, common-directory derivation, and script-delegation policies from disappearing, and [`verify-build-cache.sh`](../scripts/verify-build-cache.sh) runs Gradle offline while requiring the expensive compiler tasks to report `FROM-CACHE` in a second clean worktree at the same commit. The GitHub workflows originally set an equally isolated home inside the ephemeral workspace but saved none of it, so `org.gradle.caching=true` could not help the next hosted runner; the official Gradle setup action now persists that exact home for push and nightly jobs. Performance observations are deliberately excluded: `perfGateTest` is single-fork, never up-to-date, and never restored from the build cache, so only compilation and dependency preparation are reusable. `GateTierWiringTest` locks the workflow/home/task chain. Timings remain diagnostic because host load varies; the invariants are successful cache restoration without reducing JVM, JS, adapter, or test coverage, and a fresh execution for every timed gate.

## JDK 21 vs 25/26

- **JDK split:** JDK 21 runs the build (toolchain target). The bootstrap additionally needs JDK 25 only to compile `a12-devtools`' build-utilities — not relevant to a consumer like rulekit. Never hardcode a JDK path in committed files, and never re-encode the `java_home` lookup either — resolve it through `a12_pinned_jdk21_home` in [`scripts/gradle-environment.sh`](../scripts/gradle-environment.sh), which `JdkPinSingleSourceGuardTest` enforces by sweeping every tracked file.
- **Why JDK 21 for the build, not a newer JDK (21 vs 25/26 — decided 2026-06-15).** The build/test toolchain is **pinned** to `JavaLanguageVersion.of(21)` in every module (root, `:cli`, `:adapter`), so Gradle auto-resolves an installed JDK 21 **regardless of `JAVA_HOME`** — installing OpenJDK 25/26 alongside does *not* change what compiles or runs the tests. Moving to 25 would be an explicit toolchain bump, and it isn't worth it: (1) the source targets Java 21 features only — nothing needs 25; (2) 21 is the LTS and the validated baseline against the pinned kernel; (3) the kernel's embedded **Groovy 3.0.25**, used by kernel-backed consistency and differential paths rather than the interpreter-backed runtime-eval verbs, is not validated on JDK 25 — running its tests there risks spurious ASM/class-version failures for no gain. **GraalVM for JDK 25 is used *only* for `:cli:nativeCompile`** (a separate toolchain via `GRAALVM_HOME`, `toolchainDetection=false` — see [`NATIVE-IMAGE-GRAALVM.md`](NATIVE-IMAGE-GRAALVM.md)); plain OpenJDK 25/26 can't build native images anyway. So: JDK 21 for the JVM dev/test loop, GraalVM 25 for native — don't bump the dev toolchain.

- **The build JDK is OpenJDK 21, and a GraalVM 21 is skipped rather than accepted (owner rule 2026-08-23).** The pin used to be `java_home -v 21`, which returns the **highest-versioned** JDK 21 installed — so it names whichever JDK was most recently installed, not one anyone chose. On **2026-08-19** `brew install openjdk@21` (21.0.12.1) thereby displaced Oracle GraalVM 21.0.12 as the build JDK with no commit in this repository. The two are different JIT compilers, and the swap moved **45 of 91 perf lanes** (median **1.15×**, worst **1.60×** on `charset-grapheme`), which presented as a perf-gate breach and was first read as an interpreter regression; the same commit measured 105.88 ms under OpenJDK and 66.07 ms under GraalVM on the same machine the same day. `a12_pinned_jdk21_home` now enumerates every JDK 21 and takes the first non-GraalVM home, **refusing** rather than falling back when only a GraalVM 21 is present — a silent second-choice JDK is precisely the failure being replaced. GraalVM stays reserved for `:cli:nativeCompile` via `GRAALVM_HOME` (GraalVM 25), which is a separate toolchain and unaffected. The discriminator is a `release`-file read (`GRAALVM_VERSION=`), not a JVM launch, since this runs on every `./build.sh`. Locked by [`scripts/selftest-jdk-pin.sh`](../scripts/selftest-jdk-pin.sh), which `JdkPinScriptTest` executes — its GraalVM-refusal arm is covered there, while the *no JDK at all* arm is unexercisable on any machine that can build this repo and is covered instead by `selftest-prepare-dmtool-source.sh` case 15, which asserts `java_home`'s own wording reaches the caller. **What the pin does NOT cover, stated because the commit subject overreached:** it governs `./build.sh` and `.envrc`, not the Gradle **toolchain**. Every `toolchain { languageVersion = JavaLanguageVersion.of(21) }` block here declares no `vendor`, so a bare `./gradlew` — a path this file presents as supported — may still resolve a GraalVM 21, exactly as the bullet above warns ('Gradle auto-resolves an installed JDK 21 regardless of `JAVA_HOME`'). Constraining the vendor is not free: it would have to admit Homebrew locally and Temurin on CI, and `cli/build.gradle` uses `JvmVendorSpec.ORACLE` only for the separate GraalVM 25 native toolchain. Left open deliberately — the perf lane is protected regardless by `JdkIdentity.requireSupported()`, which judges the JVM it actually runs on.

- **Configuration cache: measured, and the marker is tracked correctly (2026-08-10).** Gradle 9 prints its "consider enabling configuration cache" hint on every build here, so the question was whether the marker check survives a cache hit, on which the settings script is not re-evaluated. It does: with the patched init script, creating the marker reports `configuration cache cannot be reused because the file system entry '.no-global-gradle-repos' has been created`, and deleting it reports the mirrored `… has been removed`, so Gradle tracks the filesystem entry as a configuration input. The unpatched control reuses the cache in both directions. The side effect is real and worth knowing: the patch adds a filesystem-entry input to **every** build on that machine, which costs one extra invalidation whenever the marker appears or disappears.

## Test selection

- **`--tests` is ANDed with a task's own `filter`, so it can only ever NARROW a lane (measured 2026-08-13).** A `Test` task that declares `filter { includeTestsMatching 'a.b.C' }` and is invoked as `--tests "*PerfTest"` runs **nothing**: Gradle keeps `includePatterns` and `commandLineIncludePatterns` as separate sets and requires a test to match both. The failure is loud but easy to misread — `No tests found for given includes: [a.b.C](filter.includeTestsMatching) [*PerfTest](--tests filter)` names both sets, and the fix people reach for (widen the command line) cannot work. The consequence to remember: **a task filter is the denominator, and no invocation can widen it.** A lane whose membership must not silently shrink therefore selects by TAG (`useJUnitPlatform { includeTags '…' }`) rather than by an enumerated class list — the routine performance gate ran 2 of 9 tagged classes for exactly this reason, and a `--tests` "fix" for it was written and probed before being discarded. Corollary for the everyday inner loop, already relied on elsewhere: `--tests` also does not filter a task's `dependsOn` prerequisites, which is why `-Pfast` exists.

## Why `:adapter:test` takes minutes — and why there is no hotspot to attack (measured 2026-08-15)

Recorded so the question is not re-investigated. On the 8-processor darwin machine: **530 classes, 2711 tests, 759 s of test time in 323 s wall — 2.35× effective parallelism.** The cost is the estate's nature, not a defect: this is the kernel differential, so essentially every test drives the **real A12 kernel**, which does Groovy codegen *and compilation* per rule. That is exactly the work the interpreter exists to avoid at runtime, and paying it here is what makes the differential an oracle.

**It is broad, not concentrated.** The ten slowest classes total 161 s — **21 %** of test time — and the largest single class is 35.5 s. So there is no hot class whose optimization would move the lane; shaving it means removing kernel work, which is the one thing this lane may not do.

**Why it looks like it saturates every core.** `maxParallelForks` is capped at `min(4, processors)`, and the cap is a **memory** guard rather than a CPU one — each fork is an isolated JVM that loads the memory-heavy kernel. Four such JVMs doing Groovy compilation, each with its own JIT and GC threads, will keep 8 logical cores busy even though only 4 test forks exist. `-PtestForks=N` is the documented override; raising it trades wall time against OOM risk and has not been measured.

**The lever that does work is scope, not concurrency:** `-Pfast` plus a single class is ~8 s (see [TESTING-SPEC](TESTING-SPEC.md) "Test tiers"), and the full lane belongs to the session-end checkpoint.

## A failing test must say WHY in the build log (2026-08-22)

Gradle's default console output for a failed test is one line — `SomeTest > case() FAILED` plus
`AssertionFailedError at SomeTest.java:41`. The assertion **message** goes only to the HTML report. This project
puts its evidence *in* that message on purpose: a spawned script's entire output, a kernel diagnostic, the
`kernel=… interp=…` of an engine disagreement. So the default hid exactly the part worth reading.

On CI it was worse than inconvenient. `ci.yml` uploads no artifact on failure, so the HTML report dies with the
runner: a red run left nothing but a file and a line number. The 2026-08-22 `deliveryGuardTest` failure was
undiagnosable for that reason, and it reproduces **only on Linux** (the launcher self-test branches on
`/usr/libexec/java_home`, so a Mac takes the other path), which put the one readable copy of the message
somewhere no local re-run could produce it.

Fixed in `build.gradle` with an `allprojects` block setting `exceptionFormat = 'full'` on every `Test` task.
Verified by planting a mutant and reading the message back out of the log rather than assuming the setting took.

**The general lesson, which outlives this setting:** when a guard's evidence lives in a channel the failure path
discards, the guard is only as good as a green run. Ask where the message goes *before* trusting a red one to
tell you anything.

## A platform-branched self-test needs its OTHER branch exercised (2026-08-22)

`scripts/selftest-prepare-dmtool-source.sh` branches on whether the platform offers the JDK 21 pin —
`/usr/libexec/java_home`, so macOS yes, Linux/CI no. Case 13 asserted "a wrong-major caller JDK is not fatal",
whose own comment names the precondition: *"the note's whole subject is 'the pin carried the check, your own JDK
will not run the result', which needs a pin to exist."* It enforced that precondition **by ordering only** —
running before a later case stubs the pin out — and never by asking whether the platform has one. On Linux there
is never a pin, so the case asserted a contradiction from the start and CI failed on it for six days.

Every local run took the other branch, so the estate looked clean. Three things follow:

- **The pin question is asked of the production helper** (`a12_pinned_jdk21_home`) once, into `PLATFORM_HAS_PIN`,
  and both gates read it. The inline `/usr/libexec/java_home` re-test is gone: a pin mechanism added for another
  platform now switches the cases instead of silently skipping them.
- **The no-pin branch asserts the opposite outcome**, because without a pin the wrong-major JDK is the only java
  there is, so refusing to vouch for the launcher is *correct* — not a regression to tolerate.
- **Exercise the branch you are not on before believing a fix.** Stubbing the pin out of the helper locally
  reproduced CI's path in seconds, and immediately caught that the repair had put two assertions in the wrong
  branch. Note the one limit of that trick: it collides with the case that stubs the pin itself (its `sed`
  becomes a no-op and its commit finds nothing to do), so it validates everything up to that case, not past it.

## Bash 3.2 is the script baseline (measured 2026-09-01)

The repository's shell scripts must run on the Bash that ships with macOS: `/bin/bash` is **3.2.57** on the maintainer's machine. That is a compatibility contract, not a requirement to use exactly 3.2: newer Bash releases remain supported. The trap is interpreter selection — `command -v bash` resolves to Homebrew's `/opt/homebrew/bin/bash` 5.3 on that same machine, so every `#!/usr/bin/env bash` script looks healthy when invoked normally even if stock macOS cannot parse or execute it. Hosted Linux CI supplies a newer Bash too, so a green Linux run cannot prove the lower boundary.

The 2026-09-01 sweep found **six active Bash-4-only constructs in four scripts**: associative-array declarations in `check-infographic-freshness.sh`, `native-gate.sh`, and `test-evidence.sh`, plus `mapfile` in `native-battery.sh` and `test-evidence.sh`. The introducing changes used them as convenient containers for duplicate detection, task-state lookup, skip reasons, or sorted file lists; none recorded a Bash-version decision. `release-perf-gate.sh` was also inspected because it explicitly documents the 3.2 baseline, but its live code already uses the compatible `while IFS= read -r` form and contained no forbidden construct.

The lower boundary now has two enforcement layers. `ShellPortabilityGuardTest`, in the always-run `leakGuardTest` lane, scans every tracked shell script and rejects `mapfile`, `readarray`, and associative-array declarations, including a declaration split across backslash-continued physical lines; its own planted controls prove each spelling fires. Behaviour that needs a real interpreter is driven explicitly through `/bin/bash`: `TestEvidenceScriptTest` runs the evidence reporter's complete self-test there, while `DoctorScriptTest` runs the environment doctor there and requires the doctor to identify its actual Bash and the `>=3.2` contract. [`scripts/doctor.sh`](../scripts/doctor.sh) reports whichever Bash its shebang selected, so an unexpected Homebrew selection is visible without treating a newer compatible interpreter as a problem; it does not claim to test every Bash installed on the machine.

The evidence-reporter boundary is load-bearing. Before `81e69c634`, Bash 3.2 silently treated its `mapfile` result as empty and printed that no result file belonged to the run; after that change, the same interpreter aborted before producing evidence. Both outcomes were wrong. The reporter now uses indexed arrays populated by `while IFS= read -r`, a file-backed task-state lookup, and a file-backed Python cutoff result, and its self-test exercises both the does-count and does-not-count arms under stock `/bin/bash`.

## `stat` has two dialects, and the wrong one does not fail cleanly (2026-08-22)

The pre-commit doc-guard staleness check read mtimes as `stat -f %m F 2>/dev/null || stat -c %Y F 2>/dev/null || echo 0` — BSD spelling first, GNU as the fallback. Measured on one file, same second:

| invocation | GNU coreutils 9.11 | macOS BSD `stat` |
|---|---|---|
| `stat -c %Y F` | `1787433603`, exit 0 | `illegal option -- c`, exit 1 |
| `stat -f %m F` | reads `%m` as a **file**: prints F's *filesystem* block on **stdout**, exit 1 | `1787433603`, exit 0 |

The fallback chain therefore never worked on Linux, and not because it errored: the "failed" first command still wrote to stdout, so `||` appended the real number to a multi-line filesystem dump. Every later `[ "$t" -gt … ]` then died with *integer expression expected* — and because such a test sits on the **left of a `&&`**, `set -e` exempts it, so the loop continued with `newest_trigger` still `0`. Both evidence readings collapsed to `0` as well, `0 -lt 0` is false, and the check **never fired on any GNU-coreutils machine**. It was dead on CI from the day it landed; only its own selftest, which runs there, ever saw it.

Three things follow, and the first two are why this is an environment trap and not a typo:

- **A dialect fallback needs a probe, not a `||` chain**, because the wrong dialect writes to stdout and exits non-zero at the same time. The hook now probes once (`stat -c %Y -- .`, then `stat -f %m .`), remembers the dialect, validates every reading as digits, and compares with `if` rather than `&&` so an unusable reading cannot be swallowed a second way.
- **A check that cannot measure must refuse.** Unreadable mtimes now abort the commit with the reason. The old shape failed *open*, which is the property that made a dead check look like a passing one.
- **Exercise the other dialect with a shim, not with the CI queue.** [`scripts/selftest-precommit-doc-guards.sh`](../scripts/selftest-precommit-doc-guards.sh) now prepends a one-dialect `stat` on `PATH` — GNU semantics, BSD semantics, and an answers-neither case — so all three paths run wherever the selftest runs, and the GNU shim reproduces the CI failure on a Mac in under a second. Same lesson as the section above, one layer down: there the platform branch was written out in the script, here it hid inside a command's argument parsing.
- **And the class is now guarded rather than remembered.** `ShellPortabilityGuardTest`, in the always-run `leakGuardTest` lane, scans every tracked shell script for a one-dialect `stat` spelling ([TESTING-SPEC](TESTING-SPEC.md)). Its sweep found one live sibling: [`scripts/test-evidence.sh`](../scripts/test-evidence.sh) took its freshness cutoff from `stat -f %B` plus `date -r <epoch>`, both BSD-only, so on Linux it silently fell back to the log's mtime and under-reported fresh results. It now reads the timestamp through `python3`'s `os.stat`, which has one spelling everywhere. Two related measurements from the same probe: `date -r FILE` works on **both** dialects (macOS accepts a path, contrary to its man page's "seconds"), while `date -r <epoch>` is BSD-only; and `xargs -r` and a `command -v timeout` probe, the other two suspicious spellings in the tree, were measured portable and left alone.

## `>` truncates, so a reused log keeps its birth time — a run-start cutoff cannot come from the filesystem (measured 2026-08-31)

Redirecting into an existing path **truncates** the file; it does not create one. macOS preserves `st_birthtime` across that, so a log written by `cmd > build/run.log` reports the first time that *name* was ever used, not when this run started. [`scripts/test-evidence.sh`](../scripts/test-evidence.sh) took its freshness cutoff from exactly that value, on the reasoning that "the shell creates the log at run start". Measured: `build/run-docguard.log` carried a birth time of **2026-08-01**, so a **6-second** run was credited with 13 result directories and **2016 tests**, every one of them written by earlier runs — the precise false green that script exists to prevent, arriving through its own cutoff and formatted as evidence.

Two rules follow, and the second is the load-bearing one:

- **Derive a run's start from the run's own output, not from file metadata.** Gradle prints `BUILD SUCCESSFUL in <time>`; `mtime − duration − margin` is immune to path reuse. Take the **later** of that and the birth time, so a freshly created log still uses its true start and a reused one cannot pin the cutoff a month early.
- **A timestamp answers "was this written recently", never "did THIS run write it".** No cutoff, however exact, can separate this run's files from a concurrent build's or an editor's. The task's own reported state is the gate — a directory whose task the log does not report as EXECUTED is withheld, not counted — and the timestamp then only separates the classes a `--tests` filter matched from its unmatched siblings.

Both directions are locked by [`scripts/selftest-test-evidence.sh`](../scripts/selftest-test-evidence.sh), executed in the build by `TestEvidenceScriptTest`; the script had no selftest until this defect, alone among its siblings.

## A shell guard's verdict must not depend on the developer's LOCALE — and pinning `LC_ALL=C` is not the fix (measured 2026-08-31)

`scripts/check-infographic-freshness.sh` **refused a clean push** on this machine. It derives the production Java size from the README's Tokei block and requires `docs/INFOGRAPHICS.md` to carry that exact string; `awk`'s `printf "%.1f"` honours `LC_NUMERIC`, so under `LANG=de_DE.UTF-8` it computed `47,7 kLOC` and compared it against the committed `47.7 kLOC`. Nothing had drifted. CI runners are C/UTF-8, so the guard was green there and wrong only where it was standing — the inverse of the usual danger, and it blocks work rather than shipping a defect.

**The obvious fix is the trap.** `export LC_ALL=C` fixes the number and breaks the same guard one line later: the performance report's evidence line is split with `IFS='·'`, and IFS members are **bytes**, so a C `LC_CTYPE` splits U+00B7's two UTF-8 bytes separately and yields phantom empty fields — the guard then reports the machine, browser and JDK as blank. One locale bug traded for its mirror, in the same commit, both looking like drift.

So the rule has two halves, and the second is the durable one:

- **Force only the category you need** — `unset LC_ALL` (it overrides everything else) then `export LC_NUMERIC=C`. Pinning `LC_ALL` reaches `LC_CTYPE` and `LC_COLLATE` as well, which is almost never what a numeric-formatting problem wants.
- **Never byte-split on a multi-byte separator.** `IFS='<multibyte>'` is fragile by construction; split on the literal string instead (an `awk` field separator, `sed`, `tr`). Once the split no longer reads the character class, no locale category can decide the verdict.

`InfographicFreshnessLocaleTest` runs the real script under `C` and under a comma-decimal locale and requires the same exit status **and** the same output. It is a property test rather than a pinned pass on purpose: asserting the guard *passes* would couple it to the docs being fresh, which is the guard's own job, and an honest drift would then fail here too. Both bugs above were demonstrated to fail it independently before the fix.

### …and the test that locks it must ESTABLISH the locale, not name one (measured 2026-08-31, one push later)

That test first hard-coded `de_DE.UTF-8` and **went red on CI**, where the locale is not generated: bash prints `setlocale: cannot change locale` to stderr and then runs in C regardless. Two distinct defects in one line, and the second is the dangerous one — the run *fails*, and filtering the warning away to make it pass would leave both arms executing the same C run and agreeing with itself, so the guard would read green while testing nothing. A missing environment premise does not announce itself as a missing premise; it announces itself as a passing test.

So an environment-dependent guard test carries two arms:

- **Establish the premise by measurement, never by name or by `locale -a`.** The candidate list is probed by asking `awk` to format `1.5` and keeping the first locale that answers `1,5` — the exact mechanism under test, rather than a directory listing that says a locale is generated. Where none answers, the behavioural arm is **skipped with the probe result in the message**, because that machine cannot express the hazard at all.
- **Keep an always-on arm that fails everywhere.** The fix is one line in a shell script, and on a runner that cannot run the behavioural arm nothing else would notice it being deleted; `theGuardPinsTheNumericLocaleItselfRatherThanInheritingIt` asserts the script still pins `LC_NUMERIC`. It is a source-text check and weak by design — it claims only that the variable is still pinned, not that the guard is locale-invariant.

The general form, for any guard that reads the machine: **a test whose premise the environment may not supply must measure the premise and skip loudly, and must leave behind an assertion that still bites where it skipped.** The failure mode is not a red build — it is a green one.

## Offline and bootstrap limits

- **Wrapper download is blocked in the offline sandbox.** The committed wrapper points at the canonical `services.gradle.org` URL (correct for outside users). Locally, the bootstrap already extracted Gradle 9.0.0 under the a12 parent's `.gradle-dist/gradle-9.0.0/` — run that binary directly when offline.
- **`:interpreter:check` carries two tasks that need the network or a working Dokka, and one of them was CACHED-GREEN (measured 2026-08-23).** `installPackedInterpreterInBrowserConsumer` runs `pnpm` and fails `ENOTFOUND registry.npmjs.org` with no network — expected offline. `dokkaGeneratePublicationHtml` is the one that misleads: its worker JVM dies with **SIGSEGV (exit 139) in under a second**, on a CLEAN tree, and the task only *looks* green because it restores `FROM-CACHE`. `--rerun-tasks` on an unmodified checkout reproduces it, which is what separates "my change broke Dokka" from "Dokka is broken here" — the first bisect went the wrong way for exactly this reason, and the rule it violated is the estate one: **read the task line, not `BUILD SUCCESSFUL`.** The worker JDK itself is healthy (the same `java -Xmx2g -version` command line exits 0). *Hypothesis, not measured: the Homebrew `openjdk@21` on this machine is build `21.0.12.1` dated 2026-08-18, days before the crash appeared, and Dokka 2.2.0's `analysis-kotlin-symbols` is the plausible victim; the discriminator nobody has run is Dokka against the previous JDK build.* Until it is settled, verify interpreter work with `:interpreter:jvmTest :interpreter:jsNodeTest` and treat a cached `:interpreter:check` as no evidence.
- **TypeScript runtime is not built/published** by the OSS bootstrap (Java artifacts only). This is the concrete blocker behind "TS *validation* is a later milestone" — TS *build+render* can come sooner, TS *validate* cannot until the kernel TS runtime is buildable here.
