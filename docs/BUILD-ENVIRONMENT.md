# Build environment — the machine-level traps

> **What this is.** Everything about *getting a build to run correctly on a machine*: the isolated Gradle home, the JDK pin, the build cache, and the limits of the offline/bootstrap path. It was carved out of [KERNEL-INTEGRATION-NOTES.md](KERNEL-INTEGRATION-NOTES.md) on 2026-08-10, which keeps that doc about the kernel itself. Kernel API, version and licensing facts stay there.

## Script runtime policy

Repository shell entrypoints use POSIX `#!/bin/sh`; Dash is the executable portability oracle because macOS `/bin/sh` accepts Bash extensions. Stateful parsing, registries, reports, and concurrency belong in TypeScript under [`scripts/typescript/`](../scripts/typescript/), reached through [`scripts/run-typescript.sh`](../scripts/run-typescript.sh). [`scripts/check-shell-portability.sh`](../scripts/check-shell-portability.sh) discovers the denominator and applies `shellcheck -x -s sh` plus `dash -n`; `ShellPortabilityGuardTest` prevents new Bash entrypoints and ratchets the explicitly enumerated legacy set downward. The public plugin installer and its sourced release-asset manifest are part of this POSIX boundary: their behavioral self-test drives the actual installer through Dash, including checksum and cache-failure paths.

## The global init script trap

- **The machine's global Gradle config injects a private registry — the root cause, precisely (confirmed 2026-06-19).** The culprit is one global init script: `~/.gradle/init.d/repositories.gradle`. Init scripts run for *every* build on the machine and force a private, credentialed registry (authenticated with the `~/.gradle/gradle.properties` credentials) into **every** project at **three** levels — `pluginManagement.repositories` (plugins), `allprojects { repositories }` (dependencies — listed first, so it's *tried* first), and `buildscript.repositories`. This repo's `build.gradle` deliberately declares only `mavenCentral()` + `mavenLocal()`, but **a project cannot remove a repository that an init script adds**, so it can't defend itself from inside. A bare `./gradlew` then routes resolution through that registry; if the token is expired or the host is unreachable, it fails *confusingly* — it reads like a network/dependency error, not "you forgot an env var". **One fix is a Gradle home carrying no foreign init script:** init scripts load from `$GRADLE_USER_HOME/init.d/`, so a home without that file loads none. Use `GRADLE_USER_HOME=../.gradle-isolated` (the sibling dir shared across the public A12 repos — the README's `$ROOT/.gradle-isolated` is the same path, since `ROOT=$(cd .. && pwd)`). Note what that directory actually contains: **`init.d/public-repos.init.gradle`**, ours, pinning the public repositories — so "isolated" means *no foreign init script*, never *no init script*, and a private one dropped in there would be honoured like any other. The JDK is the *second* half of the footgun: the shell's `JAVA_HOME` may point at a newer JDK, so pin 21 with `$(/usr/libexec/java_home -v 21)`.
  - **To make forgetting impossible, use the committed wrappers** (added 2026-06-19): [`build.sh`](../build.sh) — `./build.sh <gradle args>` sets both vars then `exec`s `gradlew` (no extra tooling; deterministic for agents/CI) — or, with direnv, [`.envrc`](../.envrc), which auto-applies both on `cd`. Both default `GRADLE_USER_HOME` to the sibling and respect an explicit one (CI sets its own).
  - **Why not let the project self-defend** via `settings.gradle` `dependencyResolutionManagement { repositoriesMode = PREFER_SETTINGS }`? It only governs *dependency* resolution (not the plugin/buildscript injection) **and** would require moving every repo declaration out of `build.gradle` into a centralized settings block — partial *and* invasive, so that particular mechanism stays rejected. What the project does defend with instead is declaration *order* plus an opt-out marker, both in the bullet below; neither centralizes anything.
  - **Changing the global init script needs the machine owner's approval AND a measured no-op for every other project on that machine.** Not a formality: sibling checkouts can declare no repositories of their own and depend entirely on the injection, so a *path-scoped* skip — the first design drafted here — would have broken them silently at their next build, and it was abandoned for exactly that reason. The change that did land (2026-08-10, owner-approved) is a marker-file early return, verified first in a sandbox Gradle home holding a *copy* of the script: against patched and unpatched scripts alike, a project **without** the marker resolved an identical repository list and identical applied plugins, while a marked project got no injection at all. Never commit a per-machine init that hardcodes a private repo. *Security:* a registry token in `~/.gradle/gradle.properties` is stored in cleartext — rotate it if any transcript that surfaced it is untrusted.
  - **A wrapper only helps if you call it — so the injection is removed at its source rather than detected (2026-08-10, after the same failure recurred and went unnoticed for days).** Three designs that *detected* the bad configuration and refused the build were built and discarded first; each needed an opt-out (a flag, an environment variable, a hidden file), and every opt-out is a switch someone can leave on. Two committed pieces replace all of it, with no flag, no environment variable and no machine-wide state: (1) [`settings.gradle`](../settings.gradle) declares its own `pluginManagement.repositories`, and since an init script appends its own in `settingsEvaluated` — *after* the settings file — ours are tried first and an injected registry degrades to a fallback instead of deciding where plugins come from; (2) the committed **`.no-global-gradle-repos`** marker, which an init script honouring it uses to skip this build entirely. **The two pieces do not cover the same half, and an early draft of this paragraph claimed they did.** Ordering covers **plugins only**: a discriminating sandbox run (injecting init script, *no* marker) shows `pluginManagement` resolving `[mavenLocal, portal, mavenCentral, INJECTED…]`, ours first — but the project's dependency repositories come out `[INJECTED…, mavenLocal, mavenCentral]`, injected first, because `Gradle.allprojects` runs before `build.gradle`'s `repositories {}`. So **dependencies are covered by the marker alone.** On a machine whose init script does not honour it, a bare `./gradlew` still resolves dependencies through the injected registry. The measured end-to-end result here — `could not resolve plugin artifact 'org.jetbrains.kotlin.jvm…'` becoming `BUILD SUCCESSFUL`, with `:core:compileJava` also succeeding — was taken *with* the marker active and therefore cannot separate the two pieces; it is evidence for the pair, not for ordering alone. To build *through* such a registry on purpose, delete the marker: it shows in `git status`, it is scoped to one checkout, and it cannot leak into another project. Deleting it fails `BuildPerformancePolicyTest.publicRepositoriesComeFirstAndTheOptOutMarkerIsCommitted` by design — that red is the signal, not a defect. That test strips `//` line comments before asserting, so a commented-out declaration cannot satisfy it; a block comment would, which is not a realistic drift for a settings file.

### Project dependency defaults — 2026-09-21

[CI run 35601541478](https://github.com/mbackschat/a12-dmkits/actions/runs/35601541478) failed before compilation because `:predicates` had no dependency repositories; a separate resolution probe reproduced the same defect in `:consistency`. Root `build.gradle` repositories are project-scoped. The local `public-repos.init.gradle` supplied the missing declarations, so a local green run did not establish that a clean CI home could resolve dependencies. Holding the artifact caches constant and removing only the init-script-bearing home reproduced both failures; the injected-home control resolved the same `:predicates` classpath.

[`settings.gradle`](../settings.gradle) now supplies Maven Central through `dependencyResolutionManagement`. Gradle's default [`PREFER_PROJECT` behavior](https://docs.gradle.org/current/userguide/centralizing_repositories.html) keeps explicit module repositories authoritative, including the existing `mavenLocal()` paths for bootstrapped Kernel artifacts; modules without declarations use the shared public default. This does not select `PREFER_SETTINGS` or remove module-specific repositories. The regression oracle is dependency resolution and JVM/JS compilation in an init-script-free Gradle home, using the same dependency cache; CI's full build exercises that boundary on every push. Cached artifacts alone do not compensate for a missing repository declaration.

## Build cache and the Kotlin compiler daemon

- **Disabled Gradle build caching made clean-worktree verification repeat identical Kotlin compilation (confirmed 2026-07-20; CI persistence completed 2026-07-22).** The timed-out aggregate was not a hung test: Gradle reported caching disabled, and the default adapter test compilation alone comprised 255 Kotlin files plus analysis of 131 Java test files while the interpreter compiled for both JVM and JS. A two-clean-worktree reproduction then exposed the coupled cold-build defect: overlapping JVM-test, JS-link, and adapter-test compilation exhausted the Kotlin daemon's 512 MiB default heap. This was not caused by a blocked Gradle web request: task-output caching defaults off, the repo had no `org.gradle.caching` setting, the isolated Gradle home had no override, and no remote build cache is configured. [`gradle.properties`](../gradle.properties) now enables the local build cache and sizes that compiler daemon to 1536 MiB; no runtime or test lane was removed. A follow-up worktree run exposed one path bug in the wrapper: deriving the home from `ROOT/..` created `/private/tmp/.gradle-isolated` for a temporary linked worktree. [`build.sh`](../build.sh) now derives the primary checkout through Git's common directory, so arbitrarily located linked worktrees share the intended sibling home. Build-driving scripts must delegate to that wrapper rather than repeat its environment logic: [`verify-demos.sh`](../scripts/verify-demos.sh) once reintroduced the same `/private/tmp/.gradle-isolated` failure by deriving the home from its linked worktree parent. [`BuildPerformancePolicyTest`](../src/test/java/io/github/mbackschat/a12/dm/BuildPerformancePolicyTest.java) prevents the cache, compiler sizing, common-directory derivation, and script-delegation policies from disappearing, and [`verify-build-cache.sh`](../scripts/verify-build-cache.sh) runs Gradle offline while requiring the expensive compiler tasks to report `FROM-CACHE` in a second clean worktree at the same commit. The GitHub workflows originally set an equally isolated home inside the ephemeral workspace but saved none of it, so `org.gradle.caching=true` could not help the next hosted runner; the official Gradle setup action now persists that exact home for push and nightly jobs. Performance observations are deliberately excluded: `perfGateTest` is single-fork, never up-to-date, and never restored from the build cache, so only compilation and dependency preparation are reusable. `GateTierWiringTest` locks the workflow/home/task chain. Timings remain diagnostic because host load varies; the invariants are successful cache restoration without reducing JVM, JS, adapter, or test coverage, and a fresh execution for every timed gate.

- **An IDE that writes into the checkout can make the SOURCE look broken, and every cheap diagnosis of it is wrong (measured 2026-08-31).** An Eclipse-derived language server (the VS Code Java extension) compiles each Gradle source set into `<module>/bin/<sourceSet>/` and copies every non-Java file in a source folder alongside it — so a Kotlin file exists twice on disk. Symptoms, in the order they mislead you: `:adapter:compileTestKotlin` reports `Conflicting overloads` for a function declared exactly once, or ~200 `Unresolved reference` errors naming symbols whose own files compile fine; the errors CHANGE between identical runs; and the tree is byte-identical to `HEAD` throughout. Three plausible causes were each investigated and each refuted by measurement — a second Gradle daemon (9.6.0 on JDK 25, from the machine-default home, alongside the pinned 9.0.0 on JDK 21), a poisoned 268 MB build cache, and a Kotlin compile daemon shared with the IDE's own — and removing all three changed nothing. What discriminates: **quarantining `<module>/bin/` removes the overload conflict**, and the directory is recreated *during* the next build, so any run in that checkout races it. **The reliable move is not to diagnose it but to step outside it:** `git worktree add` a checkout the IDE has not opened and build there. At the same commit that produced 197 compile errors in the watched directory, the untouched worktree compiled clean and ran 554 classes / 2873 tests green. Two traps that cost the most time: `grep` here honours `.gitignore`, so searching for the duplicate declaration silently skipped the ignored copy and returned exactly one hit — `find` shows both; and Gradle's own source-set probe reports the `bin/` copies as *not* being inputs (448 sources, none under `bin/`), which is true and still does not stop the compiler seeing them, so the probe reads as exoneration and is not. The repo-walking guards are separately immune since they enumerate `git ls-files` rather than the filesystem.

- **A Kotlin/JS failure that the JVM does not share, right after an enum changed, can be a build-cache entry holding a wrong incremental compile, and `clean` restores it (measured 2026-09-25).** Renaming an internal enum's file and reordering its entries left 40 `[js, node]` failures across 23 classes while all 854 JVM tests passed. The wrong answers fitted the OLD ordinals exactly: an unchanged file's `when` over the enum read a date range, now the fifth entry, as the confirm class the old declaration put fifth, and missed confirm, now seventh, where the old order put the date range. `:consistency:clean :consistency:check` failed identically because every compile task reported `FROM-CACHE`: the stale output had been stored under a key that matches the current sources, so `clean` only deleted what the cache then put back. `--no-build-cache` recompiled it and gave 853/0 on JS. **That run stores nothing, so the bad entry survives it**; overwrite it with `--rerun` on the JS compile and link tasks, then confirm that a cached `clean` build is green. The tell is a JS-only failure whose wrong answers are coherent under the previous declaration order. *Hypothesis, not measured: the incremental JS link reused a per-file artifact that inlined the old ordinals.*

- **Inserting a constant into the MIDDLE of a Kotlin Multiplatform enum can leave the JS lane running against stale ordinals, and it fails in code the change never touched (measured 2026-09-13).** Adding `UNTERMINATED_QUOTED_NAME` between two existing `TokenKind` constants left `:consistency:jvmTest` green and `:consistency:jsNodeTest` red in `ConditionCompletenessTest`, a file the change did not touch and whose rows carry no quotes at all. The tell is which rows failed: every branch keyed on a constant whose ordinal SHIFTED (`OPERATOR_SYMBOL`, `PUNCTUATION`) silently fell through to `else`, while every branch keyed on one that did not (`NAME`) and every `!=` comparison (the `COMMENT` filter, which compiles to equality rather than a switch) kept working. Kotlin/JS lowers a `when` over an enum subject to a switch on the ordinal, so a module the incremental compiler did not rebuild carries the OLD numbers. `:consistency:clean` does not clear it — the run came straight back FROM-CACHE in one second, reporting `jsTestTestDevelopmentExecutableCompileSync UP-TO-DATE` — and `--rerun` on the test task does not either, since it re-runs the test rather than the compile. **`--rerun-tasks` is what clears it**, and the same twelve seconds also re-proves the JVM lane. Append to such an enum where the ordinals are not load-bearing; when a middle insertion is the honest shape, run the module's `check` with `--rerun-tasks` before believing a failure in unrelated code.

- **A top-level `private val` read only from a PRIVATE top-level function can be `undefined` on Kotlin/JS, and the JVM lane stays perfectly green (measured 2026-09-16).** A `private val ALTERNATIVE_MEMBER = Regex(…)` in `:consistency`, read from a private top-level function that an internal function in the same file calls, left **359 of 615 `jsNodeTest` rows** failing with `TypeError: Cannot read properties of undefined (reading 'matchEntire_…')` against **0 of 615 on `jvmTest`**. Kotlin/JS does not initialise file-level properties eagerly: it emits a per-file init function and inserts a call to it at the entry of the functions that need one, and that insertion did not reach this private function when it was entered from another file's call chain. The tell is the failing SET rather than any one row — every family that reads DSL text failed, in files the change never touched, all inside one shared helper. `--rerun-tasks` does not clear it, because nothing is stale: the property genuinely has no value yet. **The fix is to hold no file-level state at all** where a cross-platform helper can avoid it — parsing a fixed-shape name by hand has no initialisation order to get wrong — and where a constant is genuinely wanted, `by lazy` initialises on first read rather than on the compiler's schedule. Sibling of the stale-ordinal bullet above, and the same discipline applies: a green `jvmTest` is not evidence about the JS target, so run the module's `check`.

## JDK 21 vs 25/26

- **JDK split:** JDK 21 runs the build (toolchain target). The bootstrap additionally needs JDK 25 only to compile `a12-devtools`' build-utilities — not relevant to a consumer like rulekit. Never hardcode a JDK path in committed files, and never re-encode the `java_home` lookup either — resolve it through `a12_pinned_jdk21_home` in [`scripts/gradle-environment.sh`](../scripts/gradle-environment.sh), which `JdkPinSingleSourceGuardTest` enforces by sweeping every tracked file.
- **Why JDK 21 for the build, not a newer JDK (21 vs 25/26 — decided 2026-06-15).** The build/test toolchain is **pinned** to `JavaLanguageVersion.of(21)` in every module (root, `:cli`, `:adapter`), so Gradle auto-resolves an installed JDK 21 **regardless of `JAVA_HOME`** — installing OpenJDK 25/26 alongside does *not* change what compiles or runs the tests. Moving to 25 would be an explicit toolchain bump, and it isn't worth it: (1) the source targets Java 21 features only — nothing needs 25; (2) 21 is the LTS and the validated baseline against the pinned kernel; (3) the kernel's embedded **Groovy 3.0.25**, used by kernel-backed consistency and differential paths rather than the interpreter-backed runtime-eval verbs, is not validated on JDK 25 — running its tests there risks spurious ASM/class-version failures for no gain. **Oracle GraalVM 25.3.4.1 / LabsJDK 25.0.4.1 is used *only* for native metadata capture and `:cli:nativeCompile`** through mandatory `GRAALVM_HOME`, `toolchainDetection=false`, and the exact identity verifier documented in [`NATIVE-IMAGE-GRAALVM.md`](NATIVE-IMAGE-GRAALVM.md); plain OpenJDK 25/26 cannot build native images. So: JDK 21 for the JVM dev/test loop, the pinned GraalVM 25.3 builder for native — don't bump the dev toolchain.

- **The build JDK is OpenJDK 21, and a GraalVM 21 is skipped rather than accepted (owner rule 2026-08-23).** The pin used to be `java_home -v 21`, which returns the **highest-versioned** JDK 21 installed — so it names whichever JDK was most recently installed, not one anyone chose. On **2026-08-19** `brew install openjdk@21` (21.0.12.1) thereby displaced Oracle GraalVM 21.0.12 as the build JDK with no commit in this repository. The two are different JIT compilers, and the swap moved **45 of 91 perf lanes** (median **1.15×**, worst **1.60×** on `charset-grapheme`), which presented as a perf-gate breach and was first read as an interpreter regression; the same commit measured 105.88 ms under OpenJDK and 66.07 ms under GraalVM on the same machine the same day. `a12_pinned_jdk21_home` now enumerates every JDK 21 and takes the first non-GraalVM home, **refusing** rather than falling back when only a GraalVM 21 is present — a silent second-choice JDK is precisely the failure being replaced. GraalVM stays reserved for native capture and `:cli:nativeCompile` through the separately verified `GRAALVM_HOME`; it cannot displace the ordinary build JDK. The discriminator is a `release`-file read (`GRAALVM_VERSION=`), not a JVM launch, since this runs on every `./build.sh`. Locked by [`scripts/selftest-jdk-pin.sh`](../scripts/selftest-jdk-pin.sh), which `JdkPinScriptTest` executes — its GraalVM-refusal arm is covered there, while the *no JDK at all* arm is unexercisable on any machine that can build this repo and is covered instead by `selftest-prepare-dmtool-source.sh` case 15, which asserts `java_home`'s own wording reaches the caller. **What the pin does NOT cover:** it governs `./build.sh` and `.envrc`, not Gradle's Java 21 toolchain resolution. Every `toolchain { languageVersion = JavaLanguageVersion.of(21) }` block declares no `vendor`, so a bare `./gradlew` may still resolve a GraalVM 21. Constraining that vendor is not free because local Homebrew and CI Temurin must both remain admissible; the perf lane is protected independently by `JdkIdentity.requireSupported()`, which judges the JVM it actually runs on. Native no longer relies on Gradle vendor auto-discovery: it requires `GRAALVM_HOME` and checks both exact 25.3 identities before capture or compilation.

- **Where Homebrew's `openjdk@21` is installed, the pin is its formula alias, never a patch version (owner directive 2026-10-26).** `a12_pinned_jdk21_home` answers `$HOMEBREW_PREFIX/opt/openjdk@21/libexec/openjdk.jdk/Contents/Home` (default prefixes `/opt/homebrew`, `/usr/local`) before asking `java_home`. The reason is that `java_home` reports the versioned Cellar directory, which `brew upgrade` deletes: `.envrc` exported it, direnv re-runs only on a watched-file change, so every shell and agent session that outlived the 2026-10-23 upgrade kept a `JAVA_HOME` with no `java` in it, and the launcher refused to start. The alias is moved by the upgrade instead, and `bin/dmtool`'s recovery hint now prints the pin rather than the `java_home` lookup that reproduced the defect. `java_home` stays the fallback for a machine without the formula. Locked by [`scripts/selftest-jdk-pin.sh`](../scripts/selftest-jdk-pin.sh); `selftest-prepare-dmtool-source.sh` hides the formula through `HOMEBREW_PREFIX` for its no-pin cases.

- **Configuration cache: measured, and the marker is tracked correctly (2026-08-10).** Gradle 9 prints its "consider enabling configuration cache" hint on every build here, so the question was whether the marker check survives a cache hit, on which the settings script is not re-evaluated. It does: with the patched init script, creating the marker reports `configuration cache cannot be reused because the file system entry '.no-global-gradle-repos' has been created`, and deleting it reports the mirrored `… has been removed`, so Gradle tracks the filesystem entry as a configuration input. The unpatched control reuses the cache in both directions. The side effect is real and worth knowing: the patch adds a filesystem-entry input to **every** build on that machine, which costs one extra invalidation whenever the marker appears or disappears.

## Kotlin 2.4 — what the 2.2 → 2.4 bump forces (measured 2026-09-20)

The Kotlin plugins and `abi-tools` move together to **2.4.0**, and no main-source file changed. Three things break at configuration or compile time, each with a fix the error does not suggest:

- **ABI validation lost its typed nested extension.** `kotlin.extensions.getByType(org.jetbrains.kotlin.gradle.dsl.abi.AbiValidationMultiplatformExtension)` now fails at configuration time with `Extension of type 'AbiValidationMultiplatformExtension' does not exist`; the `kotlin.abiValidation` accessor replaces it, and Groovy still cannot call the Kotlin-only `abiValidation { }` shortcut. Inside that block `included`/`excluded` became `include`/`exclude`, and 2.4 throws the deprecation as a hard error rather than warning. **`:consistency` fails first**, which is the part worth remembering: a migration done only where the pattern is most visible — `:interpreter`, which owns the older and more elaborate of the two blocks — leaves the build broken.
- **The kernel's Lombok annotations must reach the Kotlin test compile classpath.** The kernel is a Lombok codebase and `@NonNull` is CLASS-retention, so it is baked into the published kernel bytecode (107 `Llombok/NonNull;` descriptors in `kernel-md-a12internal-30.8.1.jar` alone) while the kernel POMs never declare it. javac ignores an unresolvable CLASS-retention annotation; Kotlin 2.4 refuses a type it infers from such a signature — `CorpusModelPreparer.kt:56:33 Type annotation class 'lombok.NonNull' of the inferred type is inaccessible.` `:adapter` therefore declares `testCompileOnly 'org.projectlombok:lombok:1.18.42'`. That scope is exact rather than cautious: `adapter/src/main` holds no Kotlin at all, and this is an annotation the compiler must resolve, never something the module ships or runs against.
- **`abi-tools`' own API flattened.** `org.jetbrains.kotlin.abi.tools.api[.v2]` collapsed into `org.jetbrains.kotlin.abi.tools`, and the version hop disappeared with it: `AbiToolsFactory.get()` returns `AbiTools` directly where it used to return an `AbiToolsInterface` carrying `.v2`. This reaches exactly one site, `InterpreterAbiGoldenDepthTest`, as four imports plus the dropped `.v2`.

**All four regenerated goldens are dump RENDERING, not a binary change — the bump is consumer-invisible.** `abi-tools` 2.4 stopped reporting synthetic constructors, which deletes 32 `public synthetic fun <init> (… DefaultConstructorMarker)V` lines from `interpreter/api/interpreter.api` and 2 from `consistency/api/consistency.api`; `javap -p` shows every one of them still emitted. `api/dmkits-interpreter-bridge.api` loses `public boolean isGroup(java.lang.String)` because 2.4 compiles it `ACC_BRIDGE` and `PublicApiDumper` filters bridge methods, while `Mapping.isGroup` remains a real JVM default method a Java caller still binds to. Only `api/dmkits-consistency-gate.api` carries a genuine bytecode rename — `of$dmkits_consistency_gate` → `of$io_github_mbackschat_a12_dm_dmkits_consistency_gate` — on an `internal` function nothing outside the module can call.

**Two downloaded toolchains move with the plugin, and this repository pins neither.** The Kotlin/JS Node default rises **22.0.0 → 24.10.0** — both trees now sit under the isolated Gradle home and no module declares `nodeVersion` — so the first build after the bump downloads a Node and is the one step that needs the network. `kotlinStoreYarnLock` then refuses the committed lock, and `kotlinUpgradeYarnLock` rewrites it by 248/191 lines: Mocha **10.7.3 → 11.7.5**, `kotlin-web-helpers` **2.0.0 → 3.0.0**, TypeScript **5.5.4 → 5.9.3**, with `glob` 8 → 10 and `chokidar` 3 → 4 dragging in the `jackspeak`/`path-scurry`/`minipass` tree. That churn is a consequence of the plugin bump rather than a project choice, which is worth knowing when reading a diff that appears to change JS test infrastructure on purpose.

A Kotlin bump also stales the native-image reflection metadata, which costs a JVM-only build nothing and blocks a native one; the trigger and the stamp that refuses it are [NATIVE-IMAGE-GRAALVM](NATIVE-IMAGE-GRAALVM.md) §5.1's.

## Test selection

- **Filtered broad tests require `-Pfast`.** [The Gradle selection guard](../gradle/focused-test-selection.gradle) inspects the resolved task graph before execution and refuses `test --tests …` (including module-qualified tasks) without `-Pfast`. A filter narrows test cases but does not narrow prerequisite suites: a combined documentation/filtered-test command pulled in the unrelated interpreter release suite on 2026-09-08. Run named guard tasks separately. Full unfiltered suites and dedicated filtered guard tasks remain valid; `-PrkNativeAgent` retains its intentional full capture surface. `FocusedTestSelectionGuardTest` executes both the live refusal and an isolated prerequisite sentinel, with fast/full/named-guard/capture controls.

- **`--tests` binds only to the task just before it, so give each task its own filter (measured 2026-10-20).** `:test :cli:test :adapter:test --tests X` filters `:adapter:test` and runs the root and CLI suites whole beside it; one session's targeted runs each paid for both full suites that way, and the targeted classes passing among the rest hid it. The selection guard now refuses a requested test task left without any filter beside a filtered one, before anything runs; a guard lane its build script bounds with its own filter is exempt. Write `:test --tests A :adapter:test --tests B`, or run the whole suite in an invocation of its own.

- **`--tests` is ANDed with a task's own `filter`, so it can only ever NARROW a lane (measured 2026-08-13).** A `Test` task that declares `filter { includeTestsMatching 'a.b.C' }` and is invoked as `--tests "*PerfTest"` runs **nothing**: Gradle keeps `includePatterns` and `commandLineIncludePatterns` as separate sets and requires a test to match both. The failure is loud but easy to misread — `No tests found for given includes: [a.b.C](filter.includeTestsMatching) [*PerfTest](--tests filter)` names both sets, and the fix people reach for (widen the command line) cannot work. The consequence to remember: **a task filter is the denominator, and no invocation can widen it.** A lane whose membership must not silently shrink therefore selects by TAG (`useJUnitPlatform { includeTags '…' }`) rather than by an enumerated class list — the routine performance gate ran 2 of 9 tagged classes for exactly this reason, and a `--tests` "fix" for it was written and probed before being discarded. Corollary for the everyday inner loop, already relied on elsewhere: `--tests` also does not filter a task's `dependsOn` prerequisites, which is why `-Pfast` exists.

- **A filter that selects no test fails, on the Kotlin/JS lanes too (measured 2026-09-24).** A JVM `Test` task already refuses an empty selection ("No tests found for given includes"), but a Kotlin/JS test task ignores `failOnNoMatchingTests`: `:consistency:jsNodeTest --tests '*StarBindingContainmentTest'` ran nothing and reported `BUILD SUCCESSFUL`, because the JS runner matches the pattern against class-and-method names. So a JS class pattern needs a trailing `*` (`--tests '*StarBindingContainmentTest*'`). The same selection guard now counts the root suite of every test task and fails a filtered run that executed none, whichever filter did the selecting; `FocusedTestSelectionGuardTest` carries the control.

## Why `:adapter:test` takes minutes — and why there is no hotspot to attack (measured 2026-08-15)

Recorded so the question is not re-investigated. On the 8-processor darwin machine: **530 classes, 2711 tests, 759 s of test time in 323 s wall — 2.35× effective parallelism.** The cost is the estate's nature, not a defect: this is the kernel differential, so essentially every test drives the **real A12 kernel**, which does Groovy codegen *and compilation* per rule. That is exactly the work the interpreter exists to avoid at runtime, and paying it here is what makes the differential an oracle.

**It is broad, not concentrated.** The ten slowest classes total 161 s — **21 %** of test time — and the largest single class is 35.5 s. So there is no hot class whose optimization would move the lane; shaving it means removing kernel work, which is the one thing this lane may not do.

**Why it looks like it saturates every core.** `maxParallelForks` is capped at `min(4, processors)`, and the cap is a **memory** guard rather than a CPU one — each fork is an isolated JVM that loads the memory-heavy kernel. Four such JVMs doing Groovy compilation, each with its own JIT and GC threads, will keep 8 logical cores busy even though only 4 test forks exist. `-PtestForks=N` is the documented override; raising it trades wall time against OOM risk and has not been measured.

**The lever that does work is scope, not concurrency:** `-Pfast` plus a single class is ~8 s (see [TESTING-SPEC](TESTING-SPEC.md) "Test tiers"), and the full lane belongs to the session-end checkpoint.

**Extended 2026-09-22 — the cost has a precise locus, and "shaving it means removing kernel work" is too strong.** Re-measured at 652 classes / 3321 tests / 1024 s of test time in 384 s wall (same machine, 2.7×), and then split cold from warm on one model, which the 2026-08-15 pass did not do:

| rules in the model | engine object | **first evaluation** | warm evaluation |
|---|---|---|---|
| 1 | 13 ms | **800 ms** | 1.37 ms |
| 5 | 1 ms | **224 ms** | 2.32 ms |
| 20 | 1 ms | **298 ms** | 1.84 ms |
| 50 | 3 ms | **437 ms** | 1.59 ms |

Codegen is **lazy** — it happens inside the first `validationMessages`, not in the engine constructor, which is why a harness that warms up before timing hides it entirely (the first attempt at this measurement did exactly that and reported 1 ms engine builds). It is ~99.5 % of the per-model cost, it barely scales with rule count, and it is therefore fixed Groovy-compiler startup **per distinct model, per strategy**. At ~650 fixture models that is ≈650 s, which is the right order for the 1024 s measured.

**The reducible part is code GENERATION, not compilation and not evaluation — and the kernel ships the seam for it.** Splitting the 1036 ms three ways on a 20-rule model: generate + compile **1036 ms**, revive the same `IModelCode` from disk and let Groovy compile it again **240 ms**, hold the live object **6 ms**. So a disk round trip removes **~77 %**. The reason is that the kernel's `ModelGroovyCode` serializes the generated *source* in a `String` and marks the compiled `GroovyObject` `transient`: generation persists, compilation repeats. And the SPI was already there — `RuntimeLaws.dynamicConfig()` was handing the kernel an `IModelCodeCache` backed by a **fresh `HashMap` per engine**, thrown away on eviction, while `IModelCode` is declared `extends Serializable` and carries a model hash "to determine if the model has changed".

**Landed 2026-09-22 as `KernelModelCodeCache`.** Entries are keyed by (kernel runtime version, JDK, model JSON), written gzipped under `adapter/build/kernel-model-code.noindex/`, and the lane opts in — every `perf`/`measurement` lane must generate what it times, so the cache defaults **off** and a new timing lane cannot inherit it by omission. Measured on the full lane, same 3326 tests and the same result either way: **cold 5m30s → warm 3m21s** (and 4m22s → 2m57s/3m08s on the pre-gzip build). Two details that are not incidental. Gzip takes the populated cache from **94 MB to 18 MB** over 1805 entries, because the payload is generated Groovy source. And the `.noindex` suffix is load-bearing on macOS: before it, `mdfind -onlyin` found **134** of the cache files indexed with `corespotlightd` and `spotlightknowledged.updater` at 85 % and 106 % CPU — on a machine that also runs the timing lanes, that is CPU a measurement competes with. After: **0**.

**Corrected 2026-09-28:** the process-resident generated-code map was unbounded even though the shared engine caches were bounded. A CI `:adapter:test` worker with a 512 MB heap ran for about 20 minutes before both in-memory javac and Groovy compilation ran out of heap. The resident hot set now has a 64-entry LRU bound; evicted generated code remains available from the unchanged disk cache. `KernelModelCodeCacheTest.residentCodeIsBoundedAndEvictedCodeStillLoadsFromDisk` locks both the bound and the reload path.

**What must NOT be cached is the kernel's ANSWERS.** Recording messages keyed by kernel version turns the oracle into a golden file, and the differential's question is whether the interpreter matches the *live* kernel. A recorded answer can go stale for reasons no practical key captures — JDK, timezone database, locale data, `Set` iteration order — and the test would then pass against something the kernel no longer says. A silent false green in the oracle is strictly worse than a slow lane.

## A failing test must say WHY in the build log (2026-08-22)

Gradle's default console output for a failed test is one line — `SomeTest > case() FAILED` plus
`AssertionFailedError at SomeTest.java:41`. The assertion **message** goes only to the HTML report. This project
puts its evidence *in* that message on purpose: a spawned script's entire output, a kernel diagnostic, the
`kernel=… interp=…` of an engine disagreement. So the default hid exactly the part worth reading.

On CI it was worse than inconvenient. `ci.yml` uploads no artifact on failure, so the HTML report dies with the
runner: a red run left nothing but a file and a line number. The 2026-08-22 `deliveryGuardTest` failure was
undiagnosable for that reason, and it reproduces **only on Linux** (the launcher self-test branches on
`/usr/libexec/java_home`, so a Mac takes the other path), which put the one readable copy of the message
somewhere no local re-run could produce it.

Fixed in `build.gradle` with an `allprojects` block setting `exceptionFormat = 'full'` on every `Test` task.
Verified by planting a mutant and reading the message back out of the log rather than assuming the setting took.

**The general lesson, which outlives this setting:** when a guard's evidence lives in a channel the failure path
discards, the guard is only as good as a green run. Ask where the message goes *before* trusting a red one to
tell you anything.

## `stat` has two dialects, and the wrong one does not fail cleanly (2026-08-22)

The pre-commit doc-guard staleness check read mtimes as `stat -f %m F 2>/dev/null || stat -c %Y F 2>/dev/null || echo 0` — BSD spelling first, GNU as the fallback. Measured on one file, same second:

| invocation | GNU coreutils 9.11 | macOS BSD `stat` |
|---|---|---|
| `stat -c %Y F` | `1787433603`, exit 0 | `illegal option -- c`, exit 1 |
| `stat -f %m F` | reads `%m` as a **file**: prints F's *filesystem* block on **stdout**, exit 1 | `1787433603`, exit 0 |

The fallback chain therefore never worked on Linux, and not because it errored: the "failed" first command still wrote to stdout, so `||` appended the real number to a multi-line filesystem dump. Every later `[ "$t" -gt … ]` then died with *integer expression expected* — and because such a test sits on the **left of a `&&`**, `set -e` exempts it, so the loop continued with `newest_trigger` still `0`. Both evidence readings collapsed to `0` as well, `0 -lt 0` is false, and the check **never fired on any GNU-coreutils machine**. It was dead on CI from the day it landed; only its own selftest, which runs there, ever saw it.

Three things follow, and the first two are why this is an environment trap and not a typo:

- **A dialect fallback needs a probe, not a `||` chain**, because the wrong dialect writes to stdout and exits non-zero at the same time. The hook now probes once (`stat -c %Y -- .`, then `stat -f %m .`), remembers the dialect, validates every reading as digits, and compares with `if` rather than `&&` so an unusable reading cannot be swallowed a second way.
- **A check that cannot measure must refuse.** Unreadable mtimes now abort the commit with the reason. The old shape failed *open*, which is the property that made a dead check look like a passing one.
- **Exercise the other dialect with a shim, not with the CI queue.** [`scripts/selftest-precommit-doc-guards.sh`](../scripts/selftest-precommit-doc-guards.sh) now prepends a one-dialect `stat` on `PATH` — GNU semantics, BSD semantics, and an answers-neither case — so all three paths run wherever the selftest runs, and the GNU shim reproduces the CI failure on a Mac in under a second. Same lesson as the section above, one layer down: there the platform branch was written out in the script, here it hid inside a command's argument parsing.
- **And the class is now guarded rather than remembered.** `ShellPortabilityGuardTest`, in the always-run `leakGuardTest` lane, scans every tracked shell script for a one-dialect `stat` spelling ([TESTING-SPEC](TESTING-SPEC.md)). Its sweep found one live sibling: [`scripts/test-evidence.sh`](../scripts/test-evidence.sh) took its freshness cutoff from `stat -f %B` plus `date -r <epoch>`, both BSD-only, so on Linux it silently fell back to the log's mtime and under-reported fresh results. Its typed implementation now reads `birthtimeMs`/`mtimeMs` through Node's cross-platform filesystem API and compares result mtimes without a shell dialect. Two related measurements from the same probe remain useful: `date -r FILE` works on **both** dialects (macOS accepts a path, contrary to its man page's "seconds"), while `date -r <epoch>` is BSD-only; and `xargs -r` and a `command -v timeout` probe, the other two suspicious spellings in the tree, were measured portable and left alone.

## `>` truncates, so a reused log keeps its birth time — a run-start cutoff cannot come from the filesystem (measured 2026-08-31)

Redirecting into an existing path **truncates** the file; it does not create one. macOS preserves `st_birthtime` across that, so a log written by `cmd > build/run.log` reports the first time that *name* was ever used, not when this run started. [`scripts/test-evidence.sh`](../scripts/test-evidence.sh) took its freshness cutoff from exactly that value, on the reasoning that "the shell creates the log at run start". Measured: `build/run-docguard.log` carried a birth time of **2026-08-01**, so a **6-second** run was credited with 13 result directories and **2016 tests**, every one of them written by earlier runs — the precise false green that script exists to prevent, arriving through its own cutoff and formatted as evidence.

Two rules follow, and the second is the load-bearing one:

- **Derive a run's start from the run's own output, not from file metadata.** Gradle prints `BUILD SUCCESSFUL in <time>`; `mtime − duration − margin` is immune to path reuse. Take the **later** of that and the birth time, so a freshly created log still uses its true start and a reused one cannot pin the cutoff a month early.
- **A timestamp answers "was this written recently", never "did THIS run write it".** No cutoff, however exact, can separate this run's files from a concurrent build's or an editor's. The task's own reported state is the gate — a directory whose task the log does not report as EXECUTED is withheld, not counted — and the timestamp then only separates the classes a `--tests` filter matched from its unmatched siblings.

Both directions are locked by [`scripts/selftest-test-evidence.sh`](../scripts/selftest-test-evidence.sh), executed in the build by `TestEvidenceScriptTest`; the script had no selftest until this defect, alone among its siblings.

## A shell guard's verdict must not depend on the developer's LOCALE — and pinning `LC_ALL=C` is not the fix (measured 2026-08-31)

`scripts/check-infographic-freshness.sh` **refused a clean push** on this machine. It derives the production Java size from the README's source-statistics block and requires `docs/INFOGRAPHICS.md` to carry that exact string; `awk`'s `printf "%.1f"` honours `LC_NUMERIC`, so under `LANG=de_DE.UTF-8` it computed `47,7 kLOC` and compared it against the committed `47.7 kLOC`. Nothing had drifted. CI runners are C/UTF-8, so the guard was green there and wrong only where it was standing — the inverse of the usual danger, and it blocks work rather than shipping a defect.

**The obvious fix is the trap.** `export LC_ALL=C` fixes the number and breaks the same guard one line later: the performance report's evidence line is split with `IFS='·'`, and IFS members are **bytes**, so a C `LC_CTYPE` splits U+00B7's two UTF-8 bytes separately and yields phantom empty fields — the guard then reports the machine, browser and JDK as blank. One locale bug traded for its mirror, in the same commit, both looking like drift.

The first repair kept the shell implementation and therefore had two halves:

- **Force only the category you need** — `unset LC_ALL` (it overrides everything else) then `export LC_NUMERIC=C`. Pinning `LC_ALL` reaches `LC_CTYPE` and `LC_COLLATE` as well, which is almost never what a numeric-formatting problem wants.
- **Never byte-split on a multi-byte separator.** `IFS='<multibyte>'` is fragile by construction; split on the literal string instead (an `awk` field separator, `sed`, `tr`). Once the split no longer reads the character class, no locale category can decide the verdict.

The TypeScript migration removes both locale-sensitive mechanisms: kLOC uses `Number.toFixed(1)`, and the evidence footer is split as a Unicode string. `InfographicFreshnessLocaleTest` runs the public Bash command under `C` and under a measured comma-decimal Node locale and requires the same successful exit and output. An always-on arm additionally requires the shared runtime-gate refusal when `A12_NODE` names a missing executable, so a launcher that merely synthesizes the success line cannot pass; the structural arm keeps fixed-decimal formatting visible in the implementation.

### …and the test that locks it must ESTABLISH the locale, not name one (measured 2026-08-31, one push later)

That test first hard-coded `de_DE.UTF-8` and **went red on CI**, where the locale is not generated: bash prints `setlocale: cannot change locale` to stderr and then runs in C regardless. Two distinct defects in one line, and the second is the dangerous one — the run *fails*, and filtering the warning away to make it pass would leave both arms executing the same C run and agreeing with itself, so the guard would read green while testing nothing. A missing environment premise does not announce itself as a missing premise; it announces itself as a passing test.

So an environment-dependent guard test carries two arms:

- **Establish the premise by measurement, never by name or by `locale -a`.** The candidate list is probed through Node's default `Intl.NumberFormat`, keeping the first locale that answers `1,5` — the ambient input a future default-locale formatter would consume. Where none answers, the behavioural arm is **skipped with the probe result in the message**, because that machine cannot express the hazard at all.
- **Keep an always-on arm that fails everywhere.** On a runner that cannot express the locale difference, the source-wiring test still requires the stable shell command to reach the TypeScript implementation through `run-typescript.sh` and requires `.toFixed(1)` to remain the numeric primitive. It is narrow by design: the behavioral property owns the full verdict.

The general form, for any guard that reads the machine: **a test whose premise the environment may not supply must measure the premise and skip loudly, and must leave behind an assertion that still bites where it skipped.** The failure mode is not a red build — it is a green one.

## An Xcode update makes `/usr/bin/git` refuse, and it reads as a guard failure (measured 2026-09-15)

On macOS `/usr/bin/git` is a shim that defers to the active developer directory, so after an Xcode update it exits **69** with *"You have not agreed to the Xcode license agreements"* until someone runs `sudo xcodebuild -license`. Everything that shells out to `git` fails at once, and the shape it arrives in is confusing: `:deliveryGuardTest` reports two failures inside `DmtoolLauncherTest`, whose scripts build a scratch clone, so the message reads as a defect in the launcher self-tests rather than as machine state. The tell is the exit code and that both failures name a `scripts/selftest-*.sh`.

**The remedy that needs no `sudo`:** the Command Line Tools carry their own git at `/Library/Developer/CommandLineTools/usr/bin/git`, which is not behind the shim. Putting that directory first on `PATH` for the build (`PATH=/Library/Developer/CommandLineTools/usr/bin:$PATH ./build.sh …`) turns the lane green again, because every guard that reaches for git finds the working one. Accepting the licence is the durable fix; the `PATH` prefix is what unblocks a run in progress.
