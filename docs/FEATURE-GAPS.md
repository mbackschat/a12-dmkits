# dmkits BA-workflow — gaps

> **What this is.** A record of the **ergonomic gaps** in the BA+agent loop that a 2026-06-14 review (and the later OQ1 probe) surfaced — and what we decided about each. dmkits (rulekit + modelkit + `dmtool`) is driven by a **business analyst working through an LLM agent**: the BA holds a requirement in business terms ("delivery can't precede the order date"), and the agent realizes it through `dmtool` — authoring the **rule or computation** (rulekit), shaping the **model structure** it references (modelkit), and **reading/auditing** the result.
>
> **Lifecycle.** §3 stays OPEN-only. A gap lives here only while open; when it ships, **delete its row in the same commit** and record its *why* in its home. There is **no "shipped" list** anywhere in this doc — git is the *what/when*, the finding/spec is the *why*. Never leave a shipped item here, and never re-add a "shipped" sub-list.
>

Before that the ledger was empty as of 2026-08-04: the review's ergonomic gaps, the custom-type/condition cluster, the 2026-07-06 CLI-coverage sweep, G45's canonical metadata-write route, and G46's undeclared-reference refusal ([INTERPRETER-FINDINGS IF248](INTERPRETER-FINDINGS.md#if248), whose scope turned out wider than reported: stored rules and computations carry the same defect, so the gate sits at the evaluation entry) — each deleted from here on ship, its *why* recorded in its home (an **API-FINDINGS** finding for a DSL/API gap, a **CLI-SPEC** section for a `dmtool` gap, named by its `Gn` so code refs resolve) and its *what/when* in git. ## 1. The loop we're improving

A BA does not write DSL. The kernel BA doc frames the job as mapping a business requirement onto a rule that **describes the violation** (not the requirement), carrying a **rule group**, an **error field**, an **error text**, and a **severity** — plus **computation tables** (mutually-exclusive preconditions → calculations). Its recurring pitfalls — *polarity* (the rule is the error scenario), *"no generic negation"* (use the paired predicate), *error-field placement*, *computation-table exclusivity* — are where an agent stumbles.

dmkits serves the **correctness** axis well, and these strengths are the baseline:
- `schema rule add` **teaches polarity inline** ("TRUE on a VIOLATION … to enforce a requirement write its violation").
- `rule eval --instance` / `model eval --instance` **confirm polarity by execution** (fired / passed / suppressed) and also return the **interpolated end-user message**.
- `RK_INVERTED_REQUIREDNESS` backstops the #1 trap; diagnostics are coded, located, fix-carrying (`diagnostics <CODE>`).

## 2. Shipped gaps are not listed here

A shipped gap is **removed** from this ledger — there is no graduation table, no "shipped" history. **Git** is the *what/when*; the gap's durable *why* lives in its home: an **API-FINDINGS finding** for a DSL/API gap, a **CLI-SPEC** section for a `dmtool` gap. G1–G27 + R1–R4 all shipped this way and are gone from here.

So a code/doc comment citing **`FEATURE-GAPS §N`** / **`Gn`** (including legacy pre-restructure **`§3.x`** numbers) resolves **by topic** to that finding or spec section — and many findings name their `Gn` (e.g. finding 29 = G3, 30 = G4, 31 = G5, 32 = G2), so the reverse lookup works — **not** to a section in this doc. (§3/§4 below keep their numbers, so refs to *those* still resolve here.) **A retired id is never reused**: before assigning a new `Gn`, collision-check docs + src + `git log --all` for the bare id (word-boundary — `IGn` substrings are a different namespace), because shipped gaps live on as code refs (e.g. `Linter`'s G41, the eval-candidate G42).

## 4. Deferred / out of scope / won't build

The durable part of this ledger — what we considered but are not building now, with explicit re-open triggers where evidence could change the decision:

- **Contradiction-analysis family (retired G40 umbrella; three distinct deferred questions, recorded 2026-07-17; SME mechanism verified and the questions disentangled 2026-07-18; retired as one open gap 2026-07-21).** The original SME-inspired idea accreted three analyses that ask different questions over different objects, with different procedures and cost profiles. They remain grouped here only by research provenance; if a trigger fires, mint a fresh independent gap ID for that one analysis rather than reviving G40 or collapsing the family again.
  - **Q1 — condition reachability / dead-rule analysis (solver-free candidate).** An A12 rule condition describes the violation, so the local query is **∃ document/context. errorCondition = TRUE**. UNSAT means the condition is unreachable and the rule never fires; it does **not** mean the model is uninhabitable. A future conservative analyzer may cover single-field interval/domain reachability over the typed `Condition` AST plus declared field bounds, report only proven-unreachable conditions, and leave unsupported shapes unknown. A SAT local condition still does not establish that the rule's iteration, content, relevance, and eligibility gates can fire. The existing `RK_CONTRADICTORY_PRESENCE` name remains valid because its message already states the local consequence. **Re-open only when** an eval, probe, or user report shows an agent actually authoring an unreachable condition. Until then, `rule eval --instance` is a witness tool: a firing proves reachability for that instance, while a non-firing sample does **not** prove unreachability.
  - **Q2 — whole-model inhabitance / accepted-sample generation (SMT/TDG territory).** This asks **∃ document. Accepted(model, document)**, where the selected acceptance profile names the structural/formal checks, computations, severity policy, and authored firings that count. SME's “Rule Contradiction Detection” delegates to TDG, translates the whole model to SMT-LIB2, and asks for a satisfying accepted sample; UNSAT means no accepted document exists. Its bundled Z3 4.13.3.0 executables are spawned as subprocesses over stdio, not JNI; Z3 is roughly 26–33 MB per OS, while Yices2/CVC5 are bring-your-own alternatives. An unsat core names contributing assertions but is neither a checked proof nor guaranteed minimal. This is poor ROI for dmtool without a second SMT-grade consumer: A12 amortizes the translator/solver across its test-data generator, while `dmtool model seed` is only a best-effort candidate generator. If ever built, the least-bad route is an MIT Z3 subprocess mirroring the existing Node bridge. **Re-open only when** a12-dmkits itself adopts SMT-grade accepted-sample generation/model inhabitance, or another concrete measured a12-dmkits consumer supplies equivalent amortization; interest from another repository alone is insufficient.
  - **Q3 — computation-table partition analysis (overlap and gap are separate queries).** Both queries apply only where `commonPrecondition` completes TRUE; an absent common precondition means TRUE, FALSE disables the table without creating a gap or overlap, and UNKNOWN/poison retains ordinary computation semantics. Under an enabled guard, an absent alternative precondition is unconditional TRUE; overlap asks whether two ordered alternatives can both be TRUE, while gap asks whether none can be TRUE. Preserve evaluator truth and authored first-match order rather than treating the table as unordered Boolean clauses. The general joint case is SMT-shaped; a conservative single-field-guard slice may be solver-free. **Re-open only when** an eval, probe, or user report shows authors producing overlapping alternatives or enabled tables with uncovered cases and demonstrates that instance evaluation is insufficient as the authoring backstop.
  - **Separating controls for any future entry.** Q1 needs an unreachable conjunction, a reachable sibling, and a declared-bound boundary sibling. Q2 needs whole-model UNSAT and SAT polarity controls plus an explicit severity/acceptance-profile control. Q3 needs a false common guard, a true guard with no matching alternative, and a true guard with two matching alternatives. An out-of-domain enum literal is not a Q1 example because the typed `EnumRef` API rejects it before a condition exists; every retained numeric/date/domain case must be realizable through the typed or converted AST and respect empty/UNKNOWN semantics, scale, signedness, and declared constraints.

- **A per-invocation `JsonInput` instance instead of the process-global static — considered under G59, not built (2026-08-22).** A cold review proposed it so that double-claim, nesting and MCP-HTTP concurrency became unrepresentable rather than guarded. It was rejected because threading an instance would *break* the property it protects: the stdin claim must span **nested** `Cli.run` calls (`batch` and the MCP invoker re-enter per child), so a tree-scoped instance would let a nested `-` through unless the instance were passed into every nested `Cli.run` — enlarging that signature to model a resource that genuinely is process-global. The concurrency half was addressed at its cause instead: an MCP dispatch declares no caller stdin, so no dispatch on the HTTP pool can take the claim and only the single-threaded CLI chain ever writes it. *Re-open if* a second concurrent dispatch route appears that legitimately needs `-`, since that is the assumption the fix rests on.
- **Workspace-wide cross-model refactor (OQ1 candidate, dropped).** Composable today by looping a per-model verb — OQ1 E ran `for m in orderA orderB orderC; do field rename …; done` cleanly. A cross-model refactor verb adds real complexity (reference resolution across includes, the per-model safety gate, partial-failure semantics over N files) for a loop that already works. Not worth a verb.
- **Native interpolated-message preview (the G1 caveat).** `model eval` (JVM) interpolates the message; on the **native** binary it's absent because runtime-eval is Groovy-only / hidden ([`NATIVE-IMAGE-GRAALVM.md`](NATIVE-IMAGE-GRAALVM.md) §4). A native structural-interpolation render isn't worth building — the **raw-text read (G10)** covers the common "what does it say" case. *Re-open only if* a native build needs the *interpolated* preview specifically.
- **`dmtool serve` (warm-kernel daemon / stdin REPL) — won't build (decided 2026-06-15).** Examined and rejected; don't re-litigate without new evidence against these assumptions:
  - **The premise is dead.** "Seconds, not ms" was the *JVM* path (~600 ms+). The shipped CLI is the **native binary at ~37 ms** ([`NATIVE-IMAGE-GRAALVM.md`](NATIVE-IMAGE-GRAALVM.md)) — a warm process exists only to amortize JVM startup + JIT + kernel static init, none of which native pays.
  - **The cheap tier doesn't fix the real cost.** A stateless serve (re-passes `-m` per op, like `batch`) re-pays the per-model bootstrap every op. Only a **stateful warm-model** serve removes it — and that drags in the whole cache-coherence problem (staleness over the resolved file set, a `reload` that refuses on conflict, compare-and-swap on commit), the bulk of a ~1–2 week build and the part most able to corrupt work silently.
  - **`batch`/`apply` already occupy the space** ([`CLI-SPEC.md`](CLI-SPEC.md) [§7](CLI-SPEC.md#batching)): `batch` amortizes warm-up over a known op-list; `apply` keeps a warm in-memory model across an ordered transaction with one terminal gate + atomic rollback.
  - **It fights the agent-facing thesis** — the CLI is deliberately a self-explaining, **stateless** surface; serve adds session/lifecycle/reload/stale-write semantics, a second mental model that makes agent reasoning harder.
  - **The one narrow exception is now closed.** It rested on the opt-in `--kernel` eval engine, which paid Groovy-codegen warm-up every call (the interpreter does not — the runtime-eval verbs run native). That eval engine **was retired** (Set V, 2026-07-12), so the warm-up cost no longer applies to any path and there is nothing left to re-open here.
  - **A resident process shipped in 2026-08-06 anyway — and this decision stands, because it is a different thing.** `dmtool mcp` ([`MCP-SPEC`](MCP-SPEC.md)) is a resident *transport*, not a warm-model daemon: it re-reads everything per call, holds no model, no resolved-reference cache and no workspace index, and exists for a caller that **cannot execute the binary** rather than for speed. It makes no performance claim, so the first three grounds above are untouched. The fourth is *reduced*, not retired — the revision it implements deleted sessions, reload, and stale writes, so what remains of "a second mental model" is process lifecycle and a second tool-name vocabulary. Introduce a warm model there and every cache-coherence ground returns in full.
- **Per-instance custom-construct mock/oracle (`--custom-conditions '{"X": true}'`) — considered with G31, not built.** A lighter alternative to the JS escape: declare a custom condition's *outcome* for the instance instead of running its logic, to test-run the *surrounding* rules without an impl. The JS escape (`--custom-conditions-js`, shipped) runs the real logic and is the honest answer; visible-ignore (G29) already lets the surrounding rules run with the construct reported `unsupported`. *Re-open if* a user wants to force a specific custom-condition outcome in a what-if test without supplying JS.
- **Whole-model NL summary** ("explain every rule in business terms") — composable today by looping `rule explain`; a `model explain` convenience is minor.
- **Model-version migration** — a distinct concern with its own tool (`kernel-md-cli` → `MigratorCli`). dmkits authors/edits and deliberately never bumps a model's version on write.
- **Refactor verbs beyond rename/move (the earns-a-verb bar, [`CLI-SPEC.md`](CLI-SPEC.md) [§6](CLI-SPEC.md#op-taxonomy)).** Standalone `computation move` (a computation is bound to its computed field's iteration scope) and `field move` co-move across an iteration boundary (the cross-boundary premise was wrong — the kernel scopes a rule by the fields it *references*, not node placement, so valid moves already succeed and the one refused case is an unfixable cardinality split; KERNEL-FINDINGS §9, locked by `IterationLawsTest`); plus reorder / merge-split rules / extract-sub-condition / copy — none clears the bar (the agent composes them). Full verdict table: CLI-SPEC [§6](CLI-SPEC.md#op-taxonomy). *Re-open* a move verb only if a probe shows agents botch repositioning.
- **"Insert From DM"** — a one-time copy of another model's *resolved* content as plain children (vs the live `include`/`inline` reuse). Deferred; *re-open if* a workflow needs a detached one-time snapshot.
- **Intentional divergences from the A12 editor (supersets, not gaps — don't mistake for bugs).** `group attachment --repeatable` (editor disallows multi-upload, SME 1431); `group multiselect --max-rows` configurable (editor fixes 999,999, SME 1441); we split "Exclude Rules" into `--exclude-rules` + `--exclude-computations`; `date` carries an extra `format` knob.
- **Editor expert-mode / compatibility-only knobs (SME §Expert-Mode 277–291) — non-goals unless a real model needs one:** Number `min/maxLength`/`maxIntegerDigits`/`positivesOnly`; Date `partiallyKnownAllowed` + must-be-after-1900; DateRange `youngerThan1900Check` (the *range's* own before-1900 gate — a separate `IDateRangeType` property from the Date one above, and its trigger has **not** fired). String `noValueValidation` **left this list — the trigger fired**: the kernel *requires* it on an attachment `content` field, so it is fully built (modelkit builder + the MVK line-breaks co-requirement law, interpreter IF29) and CLI-authorable since 2026-07-10 (`field add`/`typedef add`). *(Authorability 2026-06-26, corrected: `maxNumberOfDigitsBeforeDecimalPlace` IS unauthorable — no DM-JSON key — so `zahlZuVieleVorkommastellen` is unreachable. But `zeroNotAllowed` (the **inverted** real key — not `zeroAllowed`) and `leadingZerosAllowed` ARE authorable and the interpreter now models them (`zahlIstNull` / `zahlHatFuehrendeNullen`, IF20); leading zeros + string newlines are in fact kernel **defaults**. So number `min/maxLength` + `maxIntegerDigits` remain expert-mode non-goals, but zero/leading-zero/newline are modeled, not skipped.)* **DateRange year-interpretation left this list too — its trigger fired twice** (2026-08-22, now [§3](#3-open)'s G53): [IF305](INTERPRETER-FINDINGS.md#if305) had to model `interpretationOfYear` to stop reporting an ordinary winter season invalid, and an external consumer is blocked authoring it through the structured surface. Kernel-modelled but unauthorable is the *same* defect one layer earlier and harder to see: there is no runtime refusal, just a missing slot, so the property reads as "not a thing" rather than "refused".
- **Broaden the skill beyond rules-only (S1) — decided "not for now" (2026-06-21).** The skill is rules-only but surfaces for "create a document model," so an agent framed everything as a rule. Broadening pulls against the self-describing surface (`manifest`/`--help`/`schema` teach structure, not the skill), N6 (a bigger skill measures the skill's coverage, not the tool's self-sufficiency), and skill simplicity. Decision: rely on the shipped "is it even a rule?" gate + the self-describing surface. *Re-open if* an eval/probe shows the rules-only framing still biases structure tasks despite the gate — then a thin reframe (not a structure catalog), eval-validated.
