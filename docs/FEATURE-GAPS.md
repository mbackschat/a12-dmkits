# dmkits — BA-workflow gaps

> **What this is.** A record of the **ergonomic gaps** in the BA+agent loop that a 2026-06-14 review (and the later OQ1 probe) surfaced — and what we decided about each. dmkits (rulekit + modelkit + `dmtool`) is driven by a **business analyst working through an LLM agent**: the BA holds a requirement in business terms ("delivery can't precede the order date"), and the agent realizes it through `dmtool` — authoring the **rule or computation** (rulekit), shaping the **model structure** it references (modelkit), and **reading/auditing** the result.
>
> **This ledger records only OPEN work** — like its siblings [`DEV-API-GAPS.md`](DEV-API-GAPS.md) and [`INTERPRETER-GAPS.md`](INTERPRETER-GAPS.md), a shipped gap is **deleted**, not kept as a "shipped" list (git is the *what/when*; the gap's API-FINDINGS finding / CLI-SPEC section is the *why*). What the doc keeps is the **review's framing** (§1), the no-history policy + how legacy `Gn`/`§N` refs resolve (§2), the **open backlog** (§3), and the **out-of-scope decisions** (§4 — the durable part).

---

## 1. The loop we're improving

A BA does not write DSL. The kernel BA doc frames the job as mapping a business requirement onto a rule that **describes the violation** (not the requirement), carrying a **rule group**, an **error field**, an **error text**, and a **severity** — plus **computation tables** (mutually-exclusive preconditions → calculations). Its recurring pitfalls — *polarity* (the rule is the error scenario), *"no generic negation"* (use the paired predicate), *error-field placement*, *computation-table exclusivity* — are where an agent stumbles.

dmkits serves the **correctness** axis well, and these strengths are the baseline:
- `schema rule add` **teaches polarity inline** ("TRUE on a VIOLATION … to enforce a requirement write its violation").
- `rule eval --instance` / `model eval --instance` **confirm polarity by execution** (fired / passed / suppressed) and also return the **interpolated end-user message**.
- `RK_INVERTED_REQUIREDNESS` backstops the #1 trap; diagnostics are coded, located, fix-carrying (`diagnostics <CODE>`).

## 2. Shipped gaps are not listed here

A shipped gap is **removed** from this ledger — there is no graduation table, no "shipped" history. **Git** is the *what/when*; the gap's durable *why* lives in its home: an **API-FINDINGS finding** for a DSL/API gap, a **CLI-SPEC** section for a `dmtool` gap. G1–G27 + R1–R4 all shipped this way and are gone from here.

So a code/doc comment citing **`FEATURE-GAPS §N`** / **`Gn`** (including legacy pre-restructure **`§3.x`** numbers) resolves **by topic** to that finding or spec section — and many findings name their `Gn` (e.g. finding 29 = G3, 30 = G4, 31 = G5, 32 = G2), so the reverse lookup works — **not** to a section in this doc. (§3/§4 below keep their numbers, so refs to *those* still resolve here.) **A retired id is never reused**: before assigning a new `Gn`, collision-check docs + src + `git log --all` for the bare id (word-boundary — `IGn` substrings are a different namespace), because shipped gaps live on as code refs (e.g. `Linter`'s G41, the eval-candidate G42).

## 3. Open backlog

- **G40 — contradiction-detection lint, scoped solver-free variant (recorded 2026-07-17; SME mechanism verified 2026-07-18).** The SME ships SMT-solver-based Rule Contradiction Detection; a full SMT dependency is out for dmtool — but the reason is amortization, not only the native-image wall (below). The variant worth building on demand: an advisory `RK_*` lint over the typed `Condition` AST + `ModelIndex` field kinds that catches the common **single-field** contradiction classes **without a solver** — same-field numeric interval emptiness (`[A] > 5 And [A] < 3`), an enum equality against a value outside the field's allowed set, and empty date-bound windows. Those are pure interval/domain intersection over the sealed `ComparisonCondition`/`CompareOp` + `FieldInfo.numberMin/Max()`/`EnumRef.allowedValues()` that already exist: zero native-image delta, zero dependency, zero license concern. The slice it **concedes** to real SMT is cross-field linear (`A+B≤100 ∧ A≥60 ∧ B≥60`) and computation-table joint partition (overlap/gap) — rarer in BA rule sets, and where an advisory lint's false-negatives are tolerable. Mint when an eval/probe/user report shows an agent actually authoring contradictory conditions; until then `rule eval --instance` is the honest empirical check.
  - **How SME actually does it (verified from `sme.jar` bytecode, 12.5.2).** Not a bespoke checker — it **reuses the Test-Data Generator (TDG)**. `RuleContradictionCheckService.check(DocumentModel, Date)` → `runTDG(…)` → `ITdgCheckModelResult` / `containsContradictions()`; TDG translates the *whole* model to SMT-LIB2 and asks the solver for a satisfying assignment = a valid sample document. **UNSAT ⇒ no valid document exists ⇒ the rules contradict**, and the unsat-core/proof (`SmtProofTranslator`, `Smt2ProofLib$Z3`) names the conflicting rules. Contradiction detection is a **free rider** on a test-data-generation product A12 already shipped.
  - **The stack.** `tdg-solver-7.8.1.jar` bundles **Z3 4.13.3.0 (MIT)** as **per-platform native binaries** (`z3/osx64/z3` 26 MB x64-only, `z3/linux64/z3` 33 MB, `z3/win64/z3.exe`+`libz3.dll` 17 MB + VC-runtime DLLs), spawned as a **subprocess over SMT-LIB2/stdio** (`SmtProcessorCli` holds a `Process` + reader/writer — **no JNI**, the exact shape as dmtool's `node` bridge). `SmtSolverName{Z3_CLI, YICES2_CLI, CVC5_CLI}` — Yices2/CVC5 are bring-your-own alternatives; only Z3 is bundled. Theories span LIA/NIA/LRA + strings (QF_SLIA) + bitvectors/arrays — a full-model translation.
  - **Why poor ROI for dmtool (the deepest reason).** A12's SMT cost is **amortized across the generator product**; dmtool has **no such second consumer**, so it would pay 100% of the cost (bundle Z3 ≈ **+26–33 MB per OS**, or JNI + a new risk row, or an **LGPL pure-JVM** solver — SMTInterpol/Princess, disqualified for a shipped binary) for the contradiction feature alone. If ever built, **route B (subprocess + SMT-LIB2, mirroring the `node` bridge) with Z3/MIT is the least-bad path** — precisely what A12 does.
  - **Honest re-open trigger.** dmtool's `model seed` is today a **heuristic sampler** (`SeedGenerator.kt`), not SMT-based. The day dmtool wants **SMT-grade seed generation** (guaranteed-valid instances under tight cross-field constraints, or a proof none exists), *that* generator becomes the amortizing consumer that flips this ROI — the same TDG↔contradiction coupling. Re-open G40 then; until then the scoped solver-free lint stands.

- **G43 — no CLI partial-validation surface: `model eval`/`rule eval` are full-validation only, so the `Global` field flag's effect and multi-stage "wizard-page" logic aren't exercisable through dmtool (recorded 2026-07-18).** `DmInterpreter.validatePart(doc, relevant, locale)` **fully implements** partial validation, kernel-matched and differential-locked: rule-gating by the relevant error field + 3VL suppression of non-relevant refs, GLOBAL auto-relevance (IF37), per-operator star relevance (IF42), the `CustomCondition` relevant set (IF38), and uniqueness-partner relevance (IF39). **But no dmtool verb reaches it** — `model eval`/`rule eval` run **full** validation, where every field is relevant, so `Global` is inert on the CLI (it round-trips as a field flag via `field add`/`field modify`, but its runtime effect can't be observed) and the wizard-page mechanism (KERNEL-SEMANTICS §12: the relevant set *is* "the current wizard page") can't be demonstrated. This is **pure CLI-surface exposure of an already-built, kernel-matched library capability** — not new eval logic. **Shape (recommended):** a `--relevant <json>` option on `model eval` (and/or `rule eval`) carrying the relevant set (field paths + per-repetition `*`/index wildcards mirroring the library's `RelevantEntity`/`FieldPointer`), passed straight to `validatePart`; globals auto-added, so the caller supplies only the current page's fields. An **option, not a new verb** — under the self-describing-surface discipline (schema + `manifest` + help + a demo) but it does **not** trip the earns-a-verb bar ([`CLI-SPEC.md`](CLI-SPEC.md) §6). **Open design question:** the CLI encoding of the relevant set — how to express the `ALL`/`ALL_SEMANTIC` wildcard per repeatable level concisely — settle against the library's `RelevantEntity` vocabulary. Mint when a consumer needs per-page/partial validation on the CLI, or a demo/eval wants to show global-field or multi-stage behavior end-to-end.

- **G44 — a structure/comprehension tree for a model (`model report --tree [--root <path>] [--depth N] [--include …]`), agent-first + human-browsable (recorded 2026-07-18; refined 2026-07-18).** No verb emits a hierarchical view: `model describe` is two **flat** path-keyed arrays (fields[]+groups[]) and `model report`'s "structure outline" is the same flat `ModelCard` (`ModelContext.describe()`). A tree over the model's **schema** — containment of groups/fields; **NOT an instance** (a repeatable group is ONE node, no row explosion, unlike `model eval`) — is the one orientation view neither the flat card nor raw DM-JSON gives ergonomically. **Ride on `model report`, NOT `model describe`** (owner-decided): the chosen node scope (rules + computations + descriptions + usage) *is* report's payload (identity + structure + the field→referrers usage map + locales + a `ReportText` `--text` renderer), whereas `describe` is the deliberately lean agent card — so the tree is a **reprojection** of data report already assembles. Read-only, native-safe (pure `ModelIndex`/`FieldInfo` + the DSL renderer; no kernel, no interpreter).
  - **Flag surface — one projection, two renderings.** `--tree` selects the **per-node outline projection**; it *replaces* report's `data` with `{root, summary, nodes[]}` (not a section in the bundle). The **JSON `data` is always a FLAT node list** (each node: `path`, `parent`, `depth`, `kind`, facets) — agent-first, trivially jq-able, hierarchy recoverable from `path`/`depth`. **`--text` draws the indented `├─/└─` tree** from those same records (the drawn tree is the *only* human-specific artifact). Scope/verbosity are orthogonal **projections** that apply to BOTH renderings: **`--root <path>`** (subtree; root node at depth 0), **`--depth N`** (vertical cap), **`--include rules,computations,descriptions,annotations`** (facets; `--include all` = everything). Filtering stays in **jq over the flat records** — no `--kind`/`--annotation`/`--repeatable` filter-flags (self-explaining primitives > flags; `--include`/`--depth`/`--root` are projections, filter *predicates* are jq's job).
  - **Node model & facets — lean by default, rich opt-in.** *Always (lean — the cheap map for "get the iteration scope right before authoring"):* `path`/`parent`/`depth`/`kind`; fields → type, scale, numeric/string bounds, enum domain (**summarized when large**: count + first few, full under `--include enum` — token-thrift with **no silent cap**: emit a `truncated` marker + count), a `computed` flag; groups → `repeatable` + `maxReps`; **provenance** on every node (below). *Opt-in via `--include` (the "understand the logic" case — token-heavy, duplicates `model read`):* `rules` + `computations` as **DSL**, `descriptions` (internal/external/helper), `annotations`. **Two provenance kinds, kept distinct:** an **include** is a mounted **group subtree** → `origin: <SourceModel>` on the subtree root, **expanded inline** (not a collapsed reference node); a **typedef** is a field's named **type** → `typeRef: <TypedefName>` on the field node (no subtree). **Anchoring:** a rule attaches at its **error entity** (a field OR a group node), a computation at its **computed field**, a model-level rule at the **root** — each anchored **once**, **not duplicated** under every field it references (the read side is `model usage`'s job). **Deterministic document order.** `--root` on a nonexistent path **refuses with a corrective diagnostic** (not found + near-match hint), never a partial/empty tree.
  - **Sample — agent JSON (lean default, `--root /Order`):**
    ```json
    { "root": "/Order",
      "summary": { "fields": 8, "groups": 4, "rules": 2, "computations": 1, "maxDepth": 2, "repeatableGroups": 1 },
      "nodes": [
        { "path": "/Order",                 "parent": null,              "depth": 0, "kind": "group", "repeatable": false },
        { "path": "/Order/Channel",         "parent": "/Order",          "depth": 1, "kind": "field", "type": "ENUMERATION", "values": ["WEB","STORE","PHONE"], "categories": ["Segment"] },
        { "path": "/Order/Customer/Email",  "parent": "/Order/Customer", "depth": 2, "kind": "field", "type": "STRING", "minLength": 5, "maxLength": 80 },
        { "path": "/Order/Lines",           "parent": "/Order",          "depth": 1, "kind": "group", "repeatable": true, "maxReps": 999 },
        { "path": "/Order/Lines/LineTotal", "parent": "/Order/Lines",    "depth": 2, "kind": "field", "type": "NUMBER", "scale": 2, "computed": true },
        { "path": "/Order/Payment",         "parent": "/Order",          "depth": 1, "kind": "group", "origin": "PaymentModule" } ] }
    ```
    With `--include rules,computations`, the relevant nodes gain `"rules":[{"name":"QtyPositive","dsl":"[Qty] < 1"}]` / `"computation":{"dsl":"[Qty] * [UnitPrice]"}`.
  - **Sample — human `--text` (`--root /Order --include rules,computations`):**
    ```
    /Order  (group)
    ├─ Channel        ENUM    {WEB, STORE, PHONE}  →Segment{ONLINE,OFFLINE}
    ├─ Customer  (group)
    │  └─ Email       STRING  min5 max80   @pii   "Billing email"
    │      └─ rule EmailRequired :  FieldNotFilled(Email)
    ├─ Lines  (group · repeatable · max 999)
    │  ├─ Qty         NUMBER  scale0 min1
    │  │   └─ rule QtyPositive :  [Qty] < 1
    │  └─ LineTotal   NUMBER  scale2   <= comp  [Qty] * [UnitPrice]
    └─ Payment  (group · origin: PaymentModule)
       └─ Iban        STRING
    fields 8 · groups 4 · rules 2 · computations 1 · repeatable 1
    ```
  - **Reuse map — ~90% reprojection + ONE new read.** structure/types/bounds/enum/repeatable/locales ← `ModelCard`; annotations ← `FieldInfo.annotations()`; descriptions ← `field read`; rules/computations-as-DSL ← `model read`'s renderer + report's usage map (anchored by error/computed entity). **The one genuinely new read: provenance** (`origin`/`typeRef` — element→source-model/typedef) — surfaced nowhere today; small addition. Plus a nesting/depth pass over the flat card + a `ReportText` tree renderer.
  - **Build/contract notes (NO new verb).** `--tree` is a **mode** on `report`; keep the **default (non-tree) report unchanged** (stable contract). Same-commit: update `model-report.schema.json` + its **executed** examples covering BOTH the lean and `--include` shapes (`SchemaVerbTest`/`SchemaExamplesGuardTest`), extend `ReportText`, add/adjust an `examples/` demo + run `scripts/verify-demos.sh`; help/`schema` describe the new options + output shape. `manifest`/conformance untouched (same verb).
  - **Why agent-first (the design axis).** An agent pays token cost for the whole payload, *queries* rather than skims, and reads structure to *act* — so the agent-optimal shape is nearly the **inverse** of the human one: default lean, flat records (not nested JSON), projections not filters, counts in the headline, each node carrying the canonical reference the mutation verbs expect (an *actionable* launchpad → `rule read`/`field modify`/`rule add`); the rich DSL comprehension view is opt-in, and the drawn tree is the `--text` form for humans.
  - **Design nicety (optional generalization) + rejected alternative.** `--tree`/`--root`/`--depth`/`--include` are conceptually **shared projection options** orthogonal to a verb's richness — `describe --tree` would give the lean structure-only tree, `report --tree` the rich comprehension tree; start with `report` (matches the chosen scope), generalize to `describe` only if the lean variant is wanted. *(Rejected: a standalone `model tree` verb — overloads the read-verb family for what is a projection of report's data; the mode-on-report form reuses more and adds no verb.)*

Everything else has shipped — the review's ergonomic gaps, the custom-type/condition cluster, and the 2026-07-06 CLI-coverage sweep — each deleted from here on ship, its *why* recorded in its home (an **API-FINDINGS** finding for a DSL/API gap, a **CLI-SPEC** section for a `dmtool` gap, named by its `Gn` so code refs resolve) and its *what/when* in git. The CLI-coverage class is guarded against regrowth by `CliCoverageParityTest` (every `EditSession`/`ModelDocument` mutator has a `dmtool` path). Out-of-scope decisions are in §4.

## 4. Out of scope / won't build

The durable part of this ledger — what we considered and decided *against*, with the reasoning so it isn't re-litigated:

- **Workspace-wide cross-model refactor (OQ1 candidate, dropped).** Composable today by looping a per-model verb — OQ1 E ran `for m in orderA orderB orderC; do field rename …; done` cleanly. A cross-model refactor verb adds real complexity (reference resolution across includes, the per-model safety gate, partial-failure semantics over N files) for a loop that already works. Not worth a verb.
- **Native interpolated-message preview (the G1 caveat).** `model eval` (JVM) interpolates the message; on the **native** binary it's absent because runtime-eval is Groovy-only / hidden ([`NATIVE-IMAGE-GRAALVM.md`](NATIVE-IMAGE-GRAALVM.md) §4). A native structural-interpolation render isn't worth building — the **raw-text read (G10)** covers the common "what does it say" case. *Re-open only if* a native build needs the *interpolated* preview specifically.
- **`dmtool serve` (warm-kernel daemon / stdin REPL) — won't build (decided 2026-06-15).** Examined and rejected; don't re-litigate without new evidence against these assumptions:
  - **The premise is dead.** "Seconds, not ms" was the *JVM* path (~600 ms+). The shipped CLI is the **native binary at ~37 ms** ([`NATIVE-IMAGE-GRAALVM.md`](NATIVE-IMAGE-GRAALVM.md)) — a warm process exists only to amortize JVM startup + JIT + kernel static init, none of which native pays.
  - **The cheap tier doesn't fix the real cost.** A stateless serve (re-passes `-m` per op, like `batch`) re-pays the per-model bootstrap every op. Only a **stateful warm-model** serve removes it — and that drags in the whole cache-coherence problem (staleness over the resolved file set, a `reload` that refuses on conflict, compare-and-swap on commit), the bulk of a ~1–2 week build and the part most able to corrupt work silently.
  - **`batch`/`apply` already occupy the space** ([`CLI-SPEC.md`](CLI-SPEC.md) §7): `batch` amortizes warm-up over a known op-list; `apply` keeps a warm in-memory model across an ordered transaction with one terminal gate + atomic rollback.
  - **It fights the agent-facing thesis** — the CLI is deliberately a self-explaining, **stateless** surface; serve adds session/lifecycle/reload/stale-write semantics, a second mental model that makes agent reasoning harder.
  - **The one narrow exception is now closed.** It rested on the opt-in `--kernel` eval engine, which paid Groovy-codegen warm-up every call (the interpreter does not — the runtime-eval verbs run native). That eval engine **was retired** (Set V, 2026-07-12), so the warm-up cost no longer applies to any path and there is nothing left to re-open here.
- **Per-instance custom-construct mock/oracle (`--custom-conditions '{"X": true}'`) — considered with G31, not built.** A lighter alternative to the JS escape: declare a custom condition's *outcome* for the instance instead of running its logic, to test-run the *surrounding* rules without an impl. The JS escape (`--custom-conditions-js`, shipped) runs the real logic and is the honest answer; visible-ignore (G29) already lets the surrounding rules run with the construct reported `unsupported`. *Re-open if* a user wants to force a specific custom-condition outcome in a what-if test without supplying JS.
- **Whole-model NL summary** ("explain every rule in business terms") — composable today by looping `rule explain`; a `model explain` convenience is minor.
- **Model-version migration** — a distinct concern with its own tool (`kernel-md-cli` → `MigratorCli`). dmkits authors/edits and deliberately never bumps a model's version on write.
- **Refactor verbs beyond rename/move (the earns-a-verb bar, [`CLI-SPEC.md`](CLI-SPEC.md) §6).** Standalone `computation move` (a computation is bound to its computed field's iteration scope) and `field move` co-move across an iteration boundary (the cross-boundary premise was wrong — the kernel scopes a rule by the fields it *references*, not node placement, so valid moves already succeed and the one refused case is an unfixable cardinality split; KERNEL-FINDINGS §9, locked by `IterationLawsTest`); plus reorder / merge-split rules / extract-sub-condition / copy — none clears the bar (the agent composes them). Full verdict table: CLI-SPEC §6. *Re-open* a move verb only if a probe shows agents botch repositioning.
- **"Insert From DM"** — a one-time copy of another model's *resolved* content as plain children (vs the live `include`/`inline` reuse). Deferred; *re-open if* a workflow needs a detached one-time snapshot.
- **Intentional divergences from the A12 editor (supersets, not gaps — don't mistake for bugs).** `group attachment --repeatable` (editor disallows multi-upload, SME 1431); `group multiselect --max-rows` configurable (editor fixes 999,999, SME 1441); we split "Exclude Rules" into `--exclude-rules` + `--exclude-computations`; `date` carries an extra `format` knob.
- **Editor expert-mode / compatibility-only knobs (SME §Expert-Mode 277–291) — non-goals unless a real model needs one:** Number `min/maxLength`/`maxIntegerDigits`/`positivesOnly`; Date `partiallyKnownAllowed` + must-be-after-1900; DateRange year-interpretation. String `noValueValidation` **left this list — the trigger fired**: the kernel *requires* it on an attachment `content` field, so it is fully built (modelkit builder + the MVK line-breaks co-requirement law, interpreter IF29) and CLI-authorable since 2026-07-10 (`field add`/`typedef add`). *(Authorability 2026-06-26, corrected: `maxNumberOfDigitsBeforeDecimalPlace` IS unauthorable — no DM-JSON key — so `zahlZuVieleVorkommastellen` is unreachable. But `zeroNotAllowed` (the **inverted** real key — not `zeroAllowed`) and `leadingZerosAllowed` ARE authorable and the interpreter now models them (`zahlIstNull` / `zahlHatFuehrendeNullen`, IF20); leading zeros + string newlines are in fact kernel **defaults**. So number `min/maxLength` + `maxIntegerDigits` remain expert-mode non-goals, but zero/leading-zero/newline are modeled, not skipped.)*
- **Broaden the skill beyond rules-only (S1) — decided "not for now" (2026-06-21).** The skill is rules-only but surfaces for "create a document model," so an agent framed everything as a rule. Broadening pulls against the self-describing surface (`manifest`/`--help`/`schema` teach structure, not the skill), N6 (a bigger skill measures the skill's coverage, not the tool's self-sufficiency), and skill simplicity. Decision: rely on the shipped "is it even a rule?" gate + the self-describing surface. *Re-open if* an eval/probe shows the rules-only framing still biases structure tasks despite the gate — then a thin reframe (not a structure catalog), eval-validated.
