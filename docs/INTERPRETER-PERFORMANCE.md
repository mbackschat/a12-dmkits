# Interpreter non-functional performance — startup, throughput, relative footprint

The `:interpreter` must have **low first-answer latency**, be **fast on the hard cases**, and keep a **low relative footprint** without giving up the caches that make it fast. These are measured requirements, not hopes. [INTERPRETER-SPEC.md](INTERPRETER-SPEC.md) “Non-functional contract” owns the numerical candidates and, after per-number certification (IF137), the ratified bars; this doc owns the measurement method, benchmark catalog, verification status, and dated evidence. A number in the results log is evidence, not a product decision or a substitute for the contract.

## The decision (five non-negotiables)

1. **REAL documents only — benchmarking a shortcut is cheating.** Measure the production evaluation path: the general `Document` (interpreter) and the kernel's `IDocument`, both built from **real DM-JSON models**. The spike's `Map<String,String>`-backed `RepDoc` (O(1) lookups, one-pass `star`) must **never** be the benchmarked object — it sidesteps the exact machinery (parallel index, common-prefix resolution, star aggregation) that is hard to make fast, so its numbers are a fiction. If a benchmark doesn't exercise real group resolution, it isn't a benchmark.
2. **Measure AGAINST the kernel, as a regression gate.** The perf benchmark is the **twin of the correctness differential** and lives in `:adapter` (the only module with the kernel). Before timing a scenario, use the outcome-bearing interpreter API to prove `unsupported.isEmpty()` and assert that the interpreter, kernel dynamic runtime, and generated-Java strategy agree with the ratified Groovy-dynamic anchor (IF136). `validateFull` now fails loud on unsupported (IF139) rather than silently dropping, but the preflight still proves `unsupported.isEmpty()` explicitly on the outcome-bearing API. Then record the eligible wall-clocks + ratio and apply the time/ratio bound. The harness now enforces the `unsupported.isEmpty()` half explicitly on the outcome-bearing API before **every** timed sample (IF156 — `PerfHarness.preflight`, refusing to time a fiction and naming the construct); binding that eligibility to a versioned scenario identity remains IG77's. The interpreter should be within a sane constant factor of the kernel — ideally faster (no Groovy, no codegen).
   - **⭐ NEVER count Groovy codegen — in ANY benchmark, including startup (standing rule, re-affirmed 2026-06-24).** Kernel codegen is **always ahead of use in real-world projects**: a real deployment generates + compiles the validator at **model-load / deploy time** (cached in `IModelCodeCache`), so the kernel **never pays codegen per request** — its real cost is steady-state validation against already-generated code. Timing codegen therefore measures a cost production never incurs — a fiction that unfairly flatters any "interpreter is faster / starts faster" claim. **This is absolute and has no exception:**
     - **Comparison benchmarks** prime it out — the kernel generates on its FIRST `validateFull` (cached for the engine's life), and every timed region is preceded by a correctness `run()` + warmup, so the codegen call is always discarded. (This is also why the kernel's per-call time only JIT-warms downward over the first ~dozen calls — the Groovy validator warming, not recodegen.)
     - **Startup measurements too.** The interpreter's "fast startup" (goal #1) is measured **on its own terms** — its engine build + first-call index/parse cost in absolute terms — **NOT** as a race against the kernel's codegen. Do not put a "kernel cold start incl. codegen" number next to it; that's the forbidden comparison. The interpreter's no-codegen advantage is a **capability** point (it matters for native-image — the kernel's Groovy codegen can't go native at all — and for one-shot CLI / JS use where there's no ahead-of-time deploy step), stated as prose, never as a benchmark timing.
     - **Codegen+compile is ONCE PER DEPLOYMENT/RELEASE — it is not a per-call, setup, OR startup cost, so it belongs in NO column of ANY comparison.** It runs at model-load / deploy time (cached in `IModelCodeCache`) and is paid **zero** times per request. Consequence: in any steady-state / hot-reuse comparison BOTH engines are already *past* setup — the kernel's code generated at deploy, the interpreter's first-parse amortized — so the only thing left to compare is **per-operation evaluation cost** (tree-walk vs already-generated code). Two traps that break this even while *saying* "paid once": **(a)** listing codegen as the kernel's *per-call setup* in a comparison table — it is not a per-call cost at all; **(b)** framing a **cold / one-shot** run as "the kernel must codegen first" — in production the model is already deployed, so the kernel does **not** codegen on the call. The interpreter's *not needing* codegen is a **capability** (it runs where Groovy codegen can't — native image, JS — and where there is no deploy step), **never** a "starts faster / faster per call than the kernel" timing claim.
3. **Target the non-obvious group machinery, at scale.** Not flat single-row rules — the cases that bite: **deeply nested repeatable groups**, **parallel iteration** / cross-level references, **starred aggregates** over large lists, and **many rows (up to 100 000)**. *Invest heavily in all things groups.*
4. **Run on the PURE engine, decoupled from the CLI — it must be CHEAP to run, very often.** Both the correctness differentials and the perf harness call the **`DmInterpreter` + `Document` API directly** (kernel via `RuntimeLaws`), NOT through `dmtool`/`InterpreterEngine`/`InterpreterModelLoader`. No process spawn, no `installDist`, no JSON envelope, no native build — just in-process JUnit (and `jsTest`). "Real document" means the real `Document` *data structure* with real nested-group shape, built **programmatically in-test**, not loaded through the CLI. The CLI's loader is a separate, thinner concern with its own small test; the engine's semantics + performance are measured at the engine, so the loop stays fast enough to run on every change.
5. **The hot path stays a MONOMORPHIC CONCRETE call — extend the engine ADDITIVELY, never by interface-ifying a common path (standing design rule, 2026-06-27).** A per-cell / per-operand / per-code-point check on the formal-error or evaluation hot path must be a **monomorphic call on a concrete (`final`) type the JIT can inline** — never a `fun interface` / virtual dispatch the *common* case has to pay. The precedent is in the source: `LegalCharset` is deliberately a `final class` (NOT a SAM) "so the call is monomorphic and JIT-inlined," and `PredefinedType.accepts` is a concrete `data class` method, not an interface. So when a new consumer SPI is added (e.g. the code-based `CustomFieldType` shipped in IF44), it must be **additive + opt-in**: the declarative/common path keeps its concrete inlined call **unchanged**, and the polymorphic SPI call is reached **only** for the construct that actually uses it — exactly how `CustomCondition.check` is paid only by models that contain a `Cond.Custom` node; a consumer who registers no code-based handler pays nothing. A library consumer must run **as fast as today** even as the surface grows. This is **gated, not hoped**: a many-row, declarative-path scenario stays in the perf suite, so any deopt of an inlined hot path (e.g. unifying everything behind one interface) trips the build. Two live guards of this rule: **`CharsetPerfTest`** (the `LegalCharset` per-codepoint path — a SAM `fun interface` once blew the suite up 16 min, so it's a `final class`) and **`CustomTypePerfTest`** (the declarative custom-field-type `PredefinedType.accepts` per-cell path — locks it within a factor of plain-string-with-the-same-pattern + sub-quadratic, so a careless IF44 SPI dispatch that boxes per cell or goes megamorphic trips it). The trap to refuse is the "clean" unify-behind-one-interface refactor — it converts a free inlined check into a per-cell virtual (and, with several impls, megamorphic) call.

## The NFR certification protocol

The candidate budgets and their evidence status are single-sourced in [INTERPRETER-SPEC.md](INTERPRETER-SPEC.md) as NFR-S1/S2, NFR-P1/P2, and NFR-F1/F2. The contract posture is ratified (IF137): the numbers are **informative until per-number certified**, `PerfBounds` is the only ratified NFR/release-level floor, and the paired growth estimator is **interleaved N/4N with the median of within-pair ratios**. Other executable implementation-regression assertions remain diagnostics/catastrophe guards, not certified NFR bars. A number promotes to a release bar only per-number, once its scenario + estimator are fixed, the runner/runtime is pinned, the p95/median sampling is performed, semantic preflight passes, the measurement is reproducible, and the owner ratifies it (the six-point gate, INTERPRETER-SPEC). A later run is **certifying** only when it records the commit, scenario identity, CPU/runner, OS, JDK or Node version, heap settings, estimator, and sample count. Before timing, the outcome-bearing interpreter result must contain zero unsupported and the interpreter/dynamic/generated-Java outcomes must satisfy the ratified Groovy-dynamic anchor (IF136); message-only equality is insufficient (and `validateFull` now fails loud on unsupported, IF139). The recommended sample/fork and job/miss defaults bind a number only at its promotion, not globally. The numbers remain **UNVERIFIED CANDIDATES**, not silently “green” because an older laptop minimum was below one.

### Startup / first answer (NFR-S1 and NFR-S2)

Library startup measures the time from an already-expanded, in-memory `ModelDef` and a materialized `Document` to the first fully materialized result. The clock starts **before `DmInterpreter(model)`** and ends after `validate`/`compute`/`testRule` has produced its complete result. Model loading and document construction are separate consumer work and stay outside this library clock; engine construction, lazy parse/index initialization, evaluation, and result construction stay inside. Run at least 50 independent fresh JVM/Node processes, discard no samples, and gate the **nearest-rank p95** while reporting median too. A minimum is never a startup statistic.

Native CLI startup is a separate end-to-end measure: the parent clock starts before process launch and stops after the complete result envelope is read and the process exits. It includes process startup, option parsing, model/instance file reads, JSON/model loading, compute→apply when enabled, validation, serialization, and shutdown. Use warm OS filesystem caches for repeatability and at least 50 independent invocations. The absence of runtime codegen is a capability advantage; kernel codegen is never included in or compared with a startup timing.

Keep the absolute p95 budgets and the row/rule growth checks separate. The former catches a uniformly slow but linear implementation; the latter catches an asymptotic regression. The current `coldRunMillis` helper starts its clock **after** engine/document construction, uses minima, and the current gate checks only row growth, so it is a complexity probe—not NFR-S certification ([IG77](INTERPRETER-GAPS.md)).

### Warm throughput and scaling (NFR-P1 and NFR-P2)

Build each engine and materialize its document outside the timed region, perform the zero-unsupported/tri-engine correctness preflight, warm the engines, then record repeated evaluation medians. The absolute large-document budget uses the interpreter on the production `Document`; the relative budget uses the same logical instance against the kernel's generated-**Java** evaluator, because Groovy's dynamic-dispatch tax makes it the wrong comparator for an “on-par algorithm” claim. Groovy remains useful as the fast routine oracle and historical runtime comparison, not the fair NFR-P2 denominator.

Every scenario declares its intended complexity class. A linear or `N log N` axis is measured at `N` and `4N` and must satisfy the NFR-P1 growth bar under the ratified paired estimator (IF137): interleaved N/4N samples with the median of within-pair ratios. A genuinely pairwise semantic operation may keep an `O(outer×inner)` fallback only when the exception is explicit, correctness-locked, and no worse than the kernel's same operation. An optimized equality/hash-join path is declared `O(outer+inner)` and must be gated as linear; a permissive sub-cubic guard does not protect that optimization.

### Relative footprint (NFR-F1 and NFR-F2)

**Footprint is not “minimize memory.”** Indices, hash maps, parsed-AST caches, row-context memoization, and other bounded caches are the preferred implementation when they remove repeated work or improve the complexity class. A footprint review asks whether the state has the right owner/lifetime, reaches a plateau, grows in the declared space class, and earns its cost—not whether a smaller but slower implementation exists.

Measure four relative surfaces:

1. **Dependency closure:** sum the resolved non-JDK runtime artifacts needed by a fresh interpreter consumer and compare them with the equivalent kernel/Groovy evaluation closure. Kernel, Groovy, dmtool, `:adapter`, and other-kit dependencies remain a hard zero in the interpreter graph.
2. **Packed artifacts:** compare the thin JVM artifact and production npm package with the previous release. Do not use Kotlin/JS development/test modules as a published-package number.
3. **Runtime state:** in forked JVM and Node probes, measure retained heap and allocation volume above fixed setup at `N, 2N, 4N, 8N`; the recommended fork count (≥5) binds at promotion (IF137). Define the JVM post-GC sampling method and run Node with `--expose-gc`, report logical cache-entry counts separately, and verify owner release as well as warm-owner plateau so GC noise cannot pass or fail the exponent accidentally. Fit a log-log space exponent per fork and gate its median plus the worst 4× step under the ratified policy. This multi-scale check does not mistake a hash table's discrete backing-array resize for a super-linear design. Report cache owners and the performance delta they buy.
4. **Native delivery:** compare the native binary with the equivalent trimmed JVM app image. This is a dmtool product measure—the binary still bundles the kernel for the MVK oracle—not an isolated interpreter-jar measure.

A >10% artifact/closure increase or >20% same-scenario runtime-footprint increase is a **review trigger**, not an automatic demand to remove a cache. It may be accepted with the measured exactness/startup/throughput benefit that pays for it. An unbounded cache, a non-plateauing repeated-eval run, or a space-complexity breach is a failure.

**Provisional local baseline (2026-07-18; existing artifacts inspected, not rebuilt or certified):** the interpreter JVM jar is 556,845 bytes; its jar + Kotlin stdlib + serialization core/json closure is 2,984,760 bytes; the current install's named kernel jars + Groovy are 12,909,518 bytes, so the interpreter closure is ~23% of that conservative comparator. The available JS development modules total ~0.371 MiB gzip including stdlib, serialization, and `big.js`, but this is **not** a production npm metric. The often-cited 33 MB native / 119 MB JVM pair was measured on 2026-06-15, before interpreter-backed native evaluation existed, and is neither a same-revision nor an established equal-capability comparison. These establish plausibility only; [IG79](INTERPRETER-GAPS.md) tracks the missing reproducible footprint gate, paired delivery build, and production package measurement.

## Why this matters (the cheating we caught)

The encouraging spike timing (`InterpreterMultiplatformTest.scalesToManyRepetitionRows`, ~30 ms / 20k rows) ran on `RepDoc`, whose field lookup is a `HashMap.get` and whose `star` is one pass — **O(N) overall**. At the time, the **production** `Document` stored placements in a `List` and did a linear `placements.firstOrNull{…}` scan on **every** `field`/`filled`/`displayValue`/`groupFilled` (and `star` was O(rows×P)) → **O(N²)** per-row evaluation. So the green spike number said nothing about the real path. Task #28 closed that gap by indexing the real `Document`; the durable rule is still to benchmark that production structure against the kernel at scale.

## The kernel baseline: Groovy vs Java (the fairness question, 2026-06-24)

The kernel's dynamic `validateFull` runs **Groovy-generated, Groovy-compiled** validators (the codegen architecture is in [`KERNEL-INTEGRATION-NOTES.md`](KERNEL-INTEGRATION-NOTES.md) "Code generation targets"). Compiled Groovy executes as JVM bytecode, but carries a **per-operation dynamic-dispatch / metaclass tax** over equivalent Java. The kernel team themselves treat this as real — they disable Groovy's Parrot parser (`groovy.antlr4=false`) specifically because it *"slows down the groovy compilation"*. So a naive "interp vs kernel" ratio conflates two things: the interpreter's algorithm **and** the fact that the kernel pays a Groovy tax the interpreter doesn't.

Two consequences, and what we do about each:

- **Scaling is tax-immune — trust it.** A constant factor (Groovy-vs-Java per-op overhead) does not bend the complexity curve. So the linearity / O(N²)-detection analysis (the "large docs" story) is unaffected by which language the kernel ran; it is the robust deliverable.
- **The absolute ratio is tax-inflated — so we also measure a Java baseline.** To get a *Groovy-tax-free* absolute comparison, we run the kernel's **own generated validator compiled as Java**, via the supported **static-model runtime path** (generate Java source through `generateValidationCode(…, JAVA)`, compile in-memory with `javax.tools.JavaCompiler`, run it through `DocumentStaticRtService` — same `validateFull` scaffolding, Java underneath). Each scenario then reports **interp × kernel-Groovy × kernel-Java**, and the honest "how much faster is the interpreter's *algorithm*" question is read against **kernel-Java**, not kernel-Groovy. This is the kernel's own logic, just stripped of the Groovy execution overhead — so it isolates the algorithmic comparison from the language tax.

**Why this matters beyond fairness — the generator signal.** Our tree-walker being *competitive* with compiled Groovy is already encouraging; the kernel-Java number tells us how much of that edge is real algorithm vs Groovy tax. It also informs the **future generator** (the "generator-ready" layering): if a JVM-bytecode/Java target is what beats Groovy, that's the perf opportunity a generator would chase.

**The JS generalization (forward-looking).** TypeScript/JS is the kernel's *other* documented codegen target, so this exact harness — *generate code in language X → compile/load → run through the rt path → diff against the interpreter* — generalizes to a **kernel-JS vs interpreter-JS** comparison later (the interpreter's other reason-to-exist). The baseline engine is therefore built **language-parameterized** (Java now; JS-capable later), not hardwired.

## The interpreter's two goals: fast startup + on-par at all rule counts (the tradeoff, 2026-06-24)

The interpreter is steered by **two CO-EQUAL goals that pull against each other** (owner direction — neither is secondary):

1. **Low cold / startup cost** — the time from *(model, document)* to the **first** answer must be small: minimal upfront work, no codegen, a fast first `validateFull`. This is the realistic latency for a one-shot CLI invocation, a native-image run, a Node-hosted JS consumer, or a freshly-built engine—not a warm steady state. A browser host needs its own assurance lane, deferred (IF138).
2. **On-par with the kernel at *all* rule counts** — the warm steady state, not just the few-rule case.

These are **co-equal and must be gated separately**, because they measure opposite regimes and a win in one can hide a loss in the other — the index-build O(N²) (#7) was invisible to the warm gate for exactly this reason. The current warm suite supplies broad complexity and Groovy-ratio evidence; `PerfGateTest.coldStartStaysSubQuadratic` supplies only a first-validation row-growth probe. Neither currently certifies the full NFR-S/P contract above; [IG77](INTERPRETER-GAPS.md) is the wiring gap.

The tension: goal 2 wants the per-call rule work eliminated (cache parsed ASTs, precompute scopes), but doing that *eagerly* at construction is exactly the cold cost goal 1 forbids. The resolution is **lazy memoization** — do the work once, **on first use**, then reuse (so the *constructor* is trivial and the first call is O(N), never O(N²)):

- **Prepare-once ASTs** (`DmInterpreter`): each rule's condition / computation's expression is parsed **lazily, exactly once** (a `lazy {}` per rule — SYNCHRONIZED, so the engine is thread-safe to reuse), then reused across every call and every row. The constructor only builds the wrappers (no parsing) → startup stays cheap, and a single-rule `testRule` forces only the one rule it touches. **This is the direct analog of the kernel's compile-once-at-model-load** — but lazy. *Caveat learned by measuring:* parsing turned out **not** to be the high-rule-count bottleneck (it didn't move the crossover), so this change is for startup + hygiene (it also removed a redundant double-parse), not the headline win.
- **Per-group row-context memo** (`Document`): `contextsFor`/`attachByDepth` did an **O(valued) attach-depth scan on every rule** (and every nested row). Since many rules share a handful of iteration scopes, and the document is immutable during a validation, this is memoized **per group inside the mutation-invalidated `Index`** — computed once per distinct scope, reused across all rules. **This *was* the lever**: ~24% faster across all rule counts, crossover pushed out ~2× (see the log). This mirrors the kernel computing the row structure once and reusing it across rules.

**Historical measurement (2026-06-24, the log below; not NFR certification):** engine build was ~1.5 ms (lazy — just the AST wrappers), first `validateFull` ~57 ms on a 48-rule model (one-time lazy index build + first parse), then steady-state. A single document stayed linear to 300,000 rows (~2.5 µs/row). `PerfScalingTest` is the opt-in reporting harness for those numbers; it has no NFR assertions.

**Historical first-validation spectrum (2026-06-25, `coldStartupSpectrum`; not NFR certification):** **37 ms** (6 rules) → **62 ms** (48) → **126 ms** (192) on a ~500-row document, and **85 ms** (10,000 rows) → **495 ms** (100,000 rows) at one rule. The helper used one fresh engine/document per sample but started timing only the first `validateFull` after both had been constructed; the sweep used one sample per point. It demonstrates plausible absolute latency and near-linear first-evaluation growth, not p95 or end-to-end startup. We do not compare it with kernel codegen (non-negotiable #2); the no-codegen property is a native/JS capability, not a timing race.

## Where the kernel *used to* win (the crossover — closed 2026-06-26; was justified at the 2026-06-24 baseline)

The kernel's documented architecture is **compile-once codegen + per-run caches** (`IndexFieldCache`, `ValidationCache`, `CalculationCache`, `GroupFillCache`, `RepetitionNotUniqueErrorCache` — `kernel-core-runtime/_30_8/internal/core/`), plus short-circuit optimizations (BA doc: skip comparison rules when the root group is empty; cancel quantifiers early). So its edge is the **many-rules** regime: generated straight-line code beats a tree-walker's per-node dispatch + `Val` allocation, and that per-(rule,row) overhead accumulates with rule count.

This is **measured, not assumed** — the rule-count sweep (`KernelEdgeTest`, opt-in `-Dperf.edge=true`) finds the crossover where interp/kernel passes 1.0. The original crossover was **~96 rules vs Groovy**; the per-operation levers below (resolution caching + reduced allocation, NOT an eval-strategy change — see the next section) later produced fair generated-Java ratios of **0.40 firing / 0.52 low-firing at 192 rules** in the recorded 2026-06-27 run (the interpreter was faster in both).

**A codegen ceiling exists, but only for pathologically CONCENTRATED rules (2026-06-25, corrected).** The kernel's codegen splits its validator into methods **by error-field count** (10 fields/method Groovy, 50 Java), each holding all rules of its fields. So when **many rules pile onto few error fields**, they collapse into one method that can exceed the JVM 64 KB bytecode limit (`MethodTooLargeException`) — `manyRules` (rules on ~3 fields) trips this at ~512–768. With rules **distributed** across many fields, the recorded run compiled and measured through **1,000 rules**, so the concentrated failure is not a demonstrated general per-model ceiling. The evidence does not include the previously claimed 2,000-rule run. This is a reminder that generator method-size management is real work the interpreter avoids, not evidence beyond the measured counts.

### Eval-strategy was NOT the lever — the per-operation cost was (measured, 2026-06-25)

An early hypothesis was an **eval-strategy ladder** (compile-to-closures → partial-eval → bytecode VM → vectorize → cross-rule CSE → runtime JIT), the Futamura idea of specializing the interpreter to the model. A closure spike measured ~2.5× **on the firing-eval in isolation**, which looked decisive. **It wasn't:** productionized as a sealed compiled-node engine ("Layer 1"), it measured ~**7% end-to-end** and was reverted — `firedType` is only ~7% of `validateFull`, so an eval-strategy change can't move the dominant cost. The real per-operation levers were **resolution caching** (per-row `placeCache`/`valCache`, and the call-local complete `FormalResultCache` that evolved from the original code-only `formalErrorAt` memo) and reduced allocation, which **beat kernel-Java at 192 high-firing** — see "Kernel optimizations from SOURCE" below + the results log. The full SOTA research that informed the ladder (closures-vs-bytecode, Truffle warmup, vectorization, AOT/JS facts) and the rejected approaches are archived in [`archived/INTERPRETER-PERFORMANCE-DESIGN.md`](archived/INTERPRETER-PERFORMANCE-DESIGN.md). The two-phase short-circuit was re-measured after the resolution caches landed and rejected again; the lazy-polarity single walk captured its useful half. Reconsider it only if a future compiled/straight-line dispatch materially changes the second walk's cost.

### The kernel's per-run caches → where the interpreter is naive (the optimization map, 2026-06-24)

The crossover is the *constant-factor* gap. An **O(N²) cliff** (the kernel has a cache, the interpreter does a per-call scan) is the *steeper* danger — but **do not dismiss a constant factor as "not a cliff"**: a per-(rule,row) redundancy is a **~rules× constant** that, at 192 rules, dominates (the `ValidationCache` "repeated field reads" row below was mis-triaged exactly this way — parked as "not a cliff," it turned out the largest remaining gap). The discipline for **both**: check the interpreter's analog and **measure at real rule counts**, not assume. Read the kernel source **for the mechanism, not the expression** (clean-room): the *idea* — index by key, memoize group-fill, **resolve a field once per row** — is reproduced in original Kotlin.

Plus non-cache kernel optimizations worth noting as hints: **iterator pruning** (skip empty repetitions above a threshold) and **end-index pruning** (iterate to the max *filled* row, not the declared max) — the interpreter sidesteps both because it only materializes *instantiated* rows (no empty-row iteration), so sparsity isn't its problem.

**The honest lesson (the owner's skepticism, confirmed — and it kept paying out):** it is **not** easy to beat the kernel. A second investigation pass (the aggregation / parallel-iteration / calculation-cascade machinery, beyond the six named caches) found **two more silent bugs** the differential fuzz net hadn't generated:
- **Parallel iteration** (two non-nested repeatable groups, the kernel's index-keyed outer join — its *steepest* O(N²) avoidance): the interpreter was **silently wrong** (under-fired, no unsupported report). It went *loud* first (declined), then was **implemented exactly for every kernel-valid shape** — the clean-room index-keyed outer join (`Document.parallelContexts`): sibling / wrapped / asymmetric-depth groups, a repeatable **frame** above one joined group (`/Plan/X/A ⋈ B`, iterated per frame row), matched / synthetic `-5` / polarity / empty-as-0, AND the invalid-index 3VL corner (a duplicate/empty index makes a group's unmatched references read UNKNOWN), at O(rows). Reverse-engineered from the source (`ValidationCache.getIterationValuesForGroups`, `IndexFieldCache`, `IIdentifier.UNKNOWN = -5`) + targeted probes. The shapes still declined-loud were all confirmed by probe to be **kernel-invalid models** (`MVK_NO_WILDCARD` for a multi-frame, `MVK_MULTIPLE_INDEX_FIELDS` for an indexed frame, `MVK_NEG_CONDITION_IN_ITERATION` for a negative-over-frame) — so a valid model is never declined.
- **The computation cascade** (a computed field referencing another): the interpreter was **silently wrong** (read the stale operand → wrong value). Now **fixed** — `compute()` orders by dependency and reads prior results via a side-effect-free overlay, matching the kernel.

Across those passes we mirrored the remaining kernel-cache analogs clean-room on the measured common raw-validation paths (semantic index #4/#10, repeatable group fill #6, cold-path build #7, non-repeatable group fill #8, the cascade, and the parallel-iteration outer join), leaving no known quadratic cliff in those specific raw scenarios. That is not a whole-evaluator claim: compute overlay index columns and correlation buckets are now shared per computation step (IF143, was IG60 — the last confirmed compute-side O(rows²) cliff), and legal multi-star equality correlation now uses the bind-depth-scoped hash join (IF144). The broader source audit also found semantic gaps outside these performance cases; [INTERPRETER-GAPS.md](INTERPRETER-GAPS.md) is authoritative. The lesson: a tree-walker is not inherently fast or correct at the edges—you earn both by indexing/ordering exactly where the kernel does, probing which shapes are valid, and failing loudly on anything not yet supported.

## How the kernel's GENERATED code evaluates a rule — and what the interpreter can mimic (2026-06-25)

A deep read of the kernel's **generated Java** validator (dumped for the `manyRules` shapes + an `Or` and a 3-way `And`, via `generateValidationCode(…, JAVA)`) shows *exactly* where its per-operation edge comes from — and confirms the owner's intuition that it's **mimickable with tree-walk techniques, no codegen needed.** (Mechanism described in our own words + stylized pseudocode; the verbatim generated source is not reproduced — license-safe rule.)

**The generated shape — one rule = one method, a two-phase body.** Each rule compiles to a method that iterates its scope and, per row, does:

```
for (row in iter) {                                  // the rule's iteration scope (cached repetitions)
  if ( fieldsGiven(Qty).isKnownAndTrue()             // PHASE 1: short-circuit BOOLEAN guard —
       && compare(GT, num(Qty), num(Amount))         //   Java && / || ; reads only .isKnownAndTrue();
            .isKnownAndTrue() ) {                     //   later operands skipped once firing is decided
    var tb0 = fieldsGiven(Qty);                       // PHASE 2 (only inside the if = only when it FIRES):
    var tb1 = compare(GT, num(Qty), num(Amount));     //   RE-evaluate operands, build the typed results,
    var v   = tb0.combineUND(tb1);                    //   combine (UND for And, ODER for Or) to get polarity
    addMessage(errorField, row, code, v.fehlerType());
  }
}
```

**The two structural differences from our tree-walk** (both confirmed across `And`, `Or`, `Cmp`, `FieldFilled`, `Sum` — the pattern is uniform; only the combine differs per operator: `combineUND` ↔ our `And` type rule, `combineODER` ↔ our `orType`):

| | kernel generated code | interpreter (`Interpreter.firedType` → `evalTypedLazy`) |
|---|---|---|
| **firing decision** | **short-circuits** — `a.isKnownAndTrue() && b…` / `|| ` skips later operands (and *their* whole evaluation) once the result is forced | validation's `firedType` stays strict — `evalTypedLazy` evaluates both branches; compute preconditions use IF85's kernel-exact short-circuiting `evalCond`, and compute-mode fill quantifiers use ordered early-stopping scans |
| **polarity (VALUE/OMISSION)** | computed **only when the rule fires** (the `combineUND/ODER → fehlerType()` is inside the `if`) | computed only for **TRUE nodes** — a non-firing root skips polarity, while a firing row gets truth + polarity in one walk |
| **index/reps** | primitive `long[]` (no boxing) | boxed `List<Int>` keys, but resolved once per path in each `RowContext`; primitive reps are an unproven, trigger-gated candidate |
| **dispatch** | generated straight-line calls (no per-node `when`) | AST re-walk per node — **NOT the lever** (a JFR profile, #64, put the whole eval at ~3–4%; the compiled-node engine that targets this stays unbuilt, twice-rejected) |

**Why this matters for the profiler hotspot.** The profiler put **eval-proper at ~181 ms** (low-firing, the residual after the `formalErrorAt` memo): `ctx.field` + `Val` allocation + the walk **+ the polarity (`leafType`/`fill`)**. The kernel pays the polarity **only on the rare firing rows** and **skips whole operands** via short-circuit; the interpreter *used to* pay polarity on **every** row. In the realistic **low-firing** regime (valid documents — most rules pass) this was pure waste: e.g. `FieldFilled(Qty) And [Qty] > 50` with a small `Qty` evaluates `FieldFilled` (true) then the comparison (false → no fire), and the interpreter *also* computed the comparison's `leafType`/`fill` polarity that is then discarded. **Closed 2026-06-25 (#62)** by the **lazy-polarity single walk** (`evalTypedLazy` — polarity only on TRUE nodes). The validation-rule *short-circuit* half (skip whole operands) remains the kernel's; computation preconditions separately gained kernel-exact short-circuiting in IF85. For this benchmark's `FieldFilled(true) And …` shape there is nothing to short-circuit, so the polarity skip was the lever.

**Per-operand primitive cost is ~equal — it is NOT the lever.** `controller.vergleiche(…)` builds a `ValidierungsErgebnis` (truth **+** `fehlerTyp`, eager — set in its constructor) and `feldWertAlsZahl` returns an allocated decimal — the same order of work as our `evalCmp` + `leafType` + `Val.Num`. So polarity is eager in *both*; the kernel's win is **not** a cheaper leaf, it is **(a) not running the leaf at all when short-circuited, and (b) not combining/typing on non-firing rows.**

**The mimic that was tried — a two-phase tree-walk — REVERTED TWICE, then beaten by a lazy single walk (measured 2026-06-25).** The natural validation-rule mimic is two-phase: Phase 1 a truth-only `evalCond` (no polarity); Phase 2 the typed `evalTyped` **only when fired**. Measured both pre- and post-`placeCache`/`(C)` (bias #5): a noise-free in-run A/B re-rejected it **both** times — pre: +1.16× low-firing / −1.5× high-firing; post-(C): +4% low-firing / −6.5% high-firing. The reason is the **second walk**: the kernel affords its two-phase because Phase-2 (`combineUND`) is cheap *straight-line generated code* over cached leaves; the interpreter's Phase-2 re-**traverses** the AST and re-**evals** the leaves (and would double-invoke a `CustomCondition`), costing more on firing rows than the polarity-skip saves. **The fix is to keep ONE walk but make the polarity LAZY** — `evalTypedLazy` computes a node's type only when its truth is TRUE — which gets the non-firing skip with **no** second walk. Measured faster in **both** regimes; adopted (#62 in the results log). **Lesson:** the kernel's *two-phase structure* is not the validation win — a tree-walk cannot make the second walk cheap; the extractable win is "don't *type* what doesn't fire," and that fits in a single lazy walk. Validation still evaluates both logical operands; computation preconditions use IF85's separate short-circuiting `evalCond` because poisoning makes their read order observable.

**What this means for the real lever.** The against-kernel low-firing sweep (`KernelEdgeTest.ruleCountCrossoverLowFiring`) shows the kernel's per-operation edge is **largest in the realistic valid-document regime** (192 rules: interp/java **≈1.70** low-firing vs ≈1.16 high-firing — the kernel drops far more when rules pass, via short-circuit + no message-building + straight-line). So closing the gap requires **cheaper per-operation eval**, not an eval *restructure*. Potential directions are (a) **compiled/straight-line dispatch** (the Layer-1 sealed-node engine measured ~7% alone, but it is the prerequisite that could also make two-phase worthwhile), (b) a primitive repetition-key representation if a fresh allocation profile earns its correctness risk, and (c) **vectorized columnar eval** for the rows axis. These are profiling candidates, not current gap-ledger commitments; the structural mimic alone is not enough.

**Conclusion at the 2026-06-25 measurement point (refining the owner's assumption).** The experiment showed that mimicking the generated structure (short-circuit + two-phase) was **only potentially worthwhile on top of cheap dispatch**; bolting two phases onto the tree walk regressed the firing-heavy case. Later resolution-cache and allocation work reached and then beat the recorded fair generated-Java ratios without compiled dispatch, unboxed repetition keys, or vectorization. Those mechanisms are therefore profile-earned future options, not the current “path to parity”; a two-phase validation walk should be reconsidered only after a materially cheaper dispatch changes its measured economics.

## Kernel optimizations from SOURCE — mechanism, interpreter analog, and the biases to re-check (2026-06-25)

After the `ValidationCache` mis-triage (I had it in my own table, dismissed it on a wrong verdict, and only the profiler forced the revisit), I stopped reasoning about the kernel's optimizations from memory and **read the runtime + codegen source** (four parallel deep reads: the per-run caches, the short-circuits/pruning, the codegen rule structure + eval primitives, the index/value representation). This records *exactly why and how* each kernel technique works, the interpreter's **true** status (not the assumed one), and — the durable part — **the biases that hid the gaps**. This is iterative: re-read the source and re-run this checklist whenever a new perf problem is learned.

### The technique map (source-grounded)

| Kernel technique | Exactly how/why (mechanism) | Interpreter status |
|---|---|---|
| **`ValidationCache.datenCache`** (value store) | one O(1) `HashMap<id → value>` built once at load; every operand read is a probe, never a scan. The win is a **large constant ×(rules·rows·ops)**, plus *resolve-once-per-row* | **DONE** — `Index.valueByKey` + the per-row `placeCache` (the placeCache was the missing "resolve once per row, reused across rules" half) |
| **`IndexFieldCache`** (value→row) | nested `group → parentReps → value → row` map, so `[F For v]` / parallel-join is O(1), not an O(rows) scan per ref → O(rows²)→O(rows) | **DONE for raw reads** — parallel iteration uses `indexMap`; semantic-index `indexedCell` uses `Index.indexRowByValue`; IF116's `Index.indexColumnByScope` memoizes the associated column state. Compute overlays formerly bypassed both raw memos and rebuilt per request; now they cache the index-column and `$`-bucket views per computation step (IF143, was IG60) |
| **`GroupFillCache`** | per-instance filled-children nodes, up-propagated; `GroupFilled`/requiredness O(1), not an O(fields) scan → O(rows²)→O(1)/O(rows) | **DONE** — `groupFilled` (repeatable=row-instantiated, O(1) via prefix index) + `nonRepGroupFilledDepths` |
| **`CalculationCache`** (computed overlay) | `id → computed value` layered over the value store; a dependent reads the computed value, not recomputes the producer's tree (avoids re-expanding a DAG) | **DONE** — `compute()`'s `overlay` + `OverlayContext` (incl. through-star); *verify dependency order is topological* |
| **`RepetitionNotUniqueErrorCache`** | **lazy** all-pairs sweep on first touch → O(rows²) once, then O(1) lookups (vs O(rows³) naive) | **DONE & FASTER** — hash group-by, O(rows). **Don't "match the kernel" by reintroducing the all-pairs sweep** — match the *result*, not the algorithm |
| **`USBIndexCache`** | bidirectional USB-number maps; H-DV/legacy models only (`assert hasUniqueEntities()`) | **n/a** — legacy USB world out of scope; **zero analog is correct** |
| **Two-phase guard** (`if (a.isKnownAndTrue() && …)` then typed `combineUND/ODER` on fire) | the firing decision runs on native `&&`/`||` over primitive booleans (real short-circuit; later operands' field reads skipped); the *typed* combine (allocating, type-discriminating) runs **only on fired rows** | **REJECTED after both measurements** — the two-walk form lost before and after `placeCache`; the adopted `evalTypedLazy` single walk computes polarity only on TRUE nodes without re-walking or double-invoking custom conditions. | **Short-circuit `∧`/`∨`** | skip the right operand once the left forces the result (`F∧x=F`, `T∨x=T` — monotone, semantics-preserving) | **PARTIAL, semantics-driven** — compute preconditions use IF85's kernel-exact short-circuiting `evalCond`, preserving the kernel's poisoning-read order. Validation and polarity still tally the complete operand/star set; profile before promoting further early-cancel work |
| **Iterator pruning / end-bounding** | iterate **set** repetitions (`GesetzteWiederholungen`), bound to max-*filled* not declared-max, skip empty rows; star-opt threshold 100 | **DONE** — instantiated-row index (`rowsByGroup`/`contextsFor`) is O(filledRows), cleaner. Risk: any star/parallel path iterating **declared** reps; audit |
| **Interned result + packed polarity** | a comparison returns an **interned enum** (truth+`fehlerTyp`, 0 alloc); fillability rides as **booleans on `VkBigDecimal`** (no separate object); polarity eager (a cheap flag), operator-aware | **DONE (C+#62)** — `Res`/`Fill` are interned (0 alloc, like the kernel's enum); and where the kernel pays the eager polarity *cheaply* on every reached node, the interpreter's `leafType`/`fill` is *not* cheap, so it instead computes polarity **only on firing nodes** (the `evalTypedLazy` walk) — same observable result, the non-firing waste removed |
| **Unboxed `long[]` indices, carried in-place** | a row's index path is one primitive `long[]`, mutated while advancing, `clone()`d only on emit; `Arrays.equals/hashCode` keys; sentinels packed as negative slots | **PARTLY HARVESTED; candidate, not a live gap** — reps remain boxed `List<Int>` keys, but `RowContext.repsCache` resolves each path once and the nested-map refactor removed the hot `Pair` allocation. A long-accumulator Sum path is not live work—aggregates already beat the kernel 10–50×. IF153 is a partial JS correctness increment; IG89 also requires a bounded-working-precision power implementation and its growth guard |

**Correction to a prior mental model (a bias, below): the kernel's value store is itself a `HashMap`, not array-indexed storage.** Its per-row cheapness comes from **memoization (the caches) + iteration pruning**, NOT contiguous arrays. The interpreter's `Map`-keyed `Index` is already kernel-aligned — *don't chase a column-store rewrite*; port the cache/pruning mechanisms that measurements justify, and consider primitive repetition keys only when a fresh profile earns that representation change.

### The biases to re-check (the durable lesson)

Each one already caused, or nearly caused, a mis-triage. Run this list when a new perf problem appears:

1. **Cliff-hunting** — "an O(N²) cliff is the danger; a constant factor isn't." A per-(rule,row) redundancy is a **~rules× constant** that dominates at high rule counts. *(Mis-triaged `ValidationCache`.)* → measure constant factors at real rule counts, not just complexity class.
2. **One-cache-one-analog** — "six kernel caches ⇒ six interpreter analogs." `USBIndexCache` → zero (legacy); `RepetitionNotUnique` → a *better* algorithm. → **match the result/behavior, not the data structure.**
3. **Map-vs-array** — "the kernel is fast because it stores values in arrays." It uses a `HashMap` too; speed = memoization + pruning. → don't rewrite the store; port the caches.
4. **Elegant-single-walk** — the original eager `evalTyped` walk (truth+polarity per node) was *tidy*, which hid that it did the kernel's expensive phase-2 work on every non-firing row. The shipped `evalTypedLazy` single walk closed that waste by typing only TRUE nodes, without paying for a second walk. → tidiness is not the goal; measured laziness is.
5. **Measured-once-settled** — a rejected optimization can become viable after a *related* change. The two-phase was re-measured after `placeCache` changed the cost structure and still lost; record both results, and reopen it only after another material prerequisite such as compiled dispatch changes the calculus. → **re-measure rejected optimizations when the cost structure shifts, then close the question when it does not.**
6. **Cross-run-noise** — a 20% kernel-Java shift between runs hid/faked wins (Layer 1 looked like noise; the placeCache magnitude was confounded). → use the **within-run ratio** (interp/kernel-Java in the same run) or an **in-run A/B toggle**, never cross-build absolutes.
7. **High-firing-benchmark** — the only against-kernel sweep was high-firing (`perfValues`), which hid that the kernel's edge is *largest in the realistic valid-document (low-firing) regime*. → always measure both regimes.
8. **Resolved-on-demand-is-fine** — "lazy per-call resolution is cheap." It's cheap *once*; re-done per accessor per operand per rule per row it's the dominant cost (`placeCache`). → measure the *redundancy*, not the single call.
9. **Allocation-blindness** — counting lookups/dispatch but not the per-op object churn (`Val`+`Fill`+`Res`, boxed reps). The kernel interns results + packs polarity. → count allocations on the hot path.

## Optimization catalog (rationale · implementation · example · results)

The implementations below are shared in **`commonMain`**, so JVM and JS use the same algorithmic structures; that does not prove identical host-library semantics or constants (decimal IG89; regex IG90). Caches and prepared artifacts are lazy where stated; non-cache algorithmic rewrites are not meaningfully “lazy.” Node evidence covers the named scenarios only. The numeric IDs are historical landing IDs, so #8 appears before the later-added #7 even though the prose follows the evaluation story.

### 1. Non-quadratic `Document` (the foundation, #28)

- **Rationale.** The general `Document` stored placements in a `List`; every `field`/`filled`/`displayValue`/`star`/`groupFilled` did a linear `firstOrNull{…}` scan, so per-row evaluation was **O(N²)** — 100k rows could not even run (a quadratic JS document blew the 2 s test timeout at 20k).
- **Implementation.** A lazily-built, **mutation-invalidated `Index`** maps `(path, reps) → placement` and `groupPath → rows`; lookups become O(1)/O(rows). Each row's `evaluated` flag is computed in **one amortized pass** over the **content-bearing** placements — `Index.content` = a valued field OR an instantiated repeatable-group row (IF53), so an all-field-empty-but-instantiated repeatable row counts as content exactly as the kernel's `GroupFillCache` does. It stays **one pass, O(document), memoized per group** (the same `content` list also feeds `GroupFilled` on a non-repeatable group and requiredness — one build, three consumers); `autoGroup` dedups via a set (was O(P²)). Re-measured 2026-07-06: the content extension is **perf-neutral** — B1 per-row, wide sibling-groups, and the constrained-field formal check all stay linear (~4× growth for 4× rows), gated by `PerfGateTest`.
- **Example.** B1 — a per-row `[Qty] > 50` over N `/Perf/Lines`.
- **Results & discussion.** Linear: **300 000 rows at ~2.5 µs/row**. This is the prerequisite every later optimization builds on — without an O(1) value store, nothing else matters.

### 2. Prepare-once ASTs (lazy parse cache)

- **Rationale.** Before this optimization, every `validateFull` re-parsed each rule's condition—in fact **twice** (`repetitionNotUnique` + `rowOutcomes`). The hypothesis (#31) was that this per-call re-parse caused the many-rules slowdown.
- **Implementation.** A per-rule `lazy {}` (`SYNCHRONIZED`, so the engine is thread-safe to reuse) AST wrapper, built in the constructor **without parsing** (→ fast startup); the first use parses and caches, every later call/row reuses. A single-rule `testRule` forces only the rule it touches.
- **Example.** B6 / `manyRules(N)` in repeated-eval (engine reused over many documents).
- **Results & discussion.** **Honest negative result:** parsing was *not* the bottleneck — the crossover did not move. The value is **startup + hygiene** (it also removed the redundant double-parse). The lesson — *measure before assuming* — is why the next optimization was found by profiling, not guessing.

### 3. Per-group row-context memo

- **Rationale.** `contextsFor`/`attachByDepth` did an **O(valued) attach-depth scan on every rule** (and every nested row). Many rules share a handful of iteration scopes, so this was O(rules × valued) of pure recomputation.
- **Implementation.** Memoize `contextsFor` and `attachByDepth` **per group** inside the `Index` — computed once per distinct scope, reused across all rules. The clean-room analog of the kernel computing the document's row structure once and reusing it.
- **Example.** B6 — 12 rules over ~3 distinct scopes (`/Perf`, `/Perf/Lines`, `…/Subs`).
- **Results & discussion.** **~24 % faster across all rule counts**; crossover vs Groovy moved **~48 → ~96 rules**. This was the first real lever (vs #2's null result).

### 4. Row-prefix index (the semantic-index / star cliff — the steepest)

- **Rationale.** `starRows` did an **O(all-rows) `.filter` per call**; inside per-row iteration (a semantic index `[F For "v"]`, or a cross-level star aggregate) that is **O(rows²)**. Measured genuinely quadratic (growth ×3.5 per doubling, the interpreter's lead collapsing 0.17→0.66 over 500→4000 rows) while the kernel's `IndexFieldCache` stayed linear and **won at scale** — the proof that the kernel's optimization is well-founded.
- **Implementation.** The `Index` indexes each group's rows by **every prefix of their rep tuple** (built once, dropped on mutation); `starRows` is then an O(1) lookup. The clean-room `IndexFieldCache`/row-index analog — the *idea*, in original Kotlin.
- **Example.** A per-row rule `FieldFilled(Amount) And [/Perf/Lines/Amount For "NOMATCH"] > 0` (`PerfCatalog.semanticIndexPerRow`).
- **Results & discussion.** **98 ms → 6.8 ms at 4000 rows**; linear again (growth ~×2/doubling), pulling *ahead* of the kernel (ratioG 0.66→0.04). Guarded against regression by `PerfGateTest.semanticIndexStaysSubQuadratic`. Also fixes any cross-level star aggregate evaluated per row (e.g. a per-Line `Sum(Subs* / Cost)` at scale).

### 5. Single typed walk per row (no double AST walk)

- **Rationale.** `rowOutcomes` called `fires()` (a Tri-only walk via `eval`) **and then** `firedType()` (a typed walk via `evalTyped`) — **two full AST walks on every firing row**. But `evalTyped` already yields the truth value, so the second walk is redundant.
- **Implementation.** Call `firedType()` **once**: non-null ⟺ the rule fires (`truth == TRUE`), and the value *is* the polarity (VALUE/OMISSION). A firing row now costs one walk, not two.
- **Example.** B6 / `manyRules(96)` — 45 480 firing rows, each previously walked twice.
- **Results & discussion.** Crossover vs **kernel-Java reached parity at ~96 rules (ratioJava 0.99)**; the 192-rule gap narrowed **1.30 → 1.19**. The win scales with the firing ratio (no help for all-passing documents — those already walked once).

### 6. O(1) repeatable-group fill

- **Rationale.** `groupFilled`'s repeatable-group branch did `reps in rowsOf(group)` — an **O(rows) `List` membership** — so requiredness over a **sparse-required** document (many empty required fields, each triggering a `GroupFilled` check per row) was **O(rows²)**. The `GroupFillCache` analog (the repeatable half).
- **Implementation.** O(1) membership via the row-prefix index (`rowsWithPrefix(group, reps).isNotEmpty()`).
- **Example.** A form with many empty required fields across N rows (every empty field triggers the per-row group-fill check).
- **Results & discussion.** Removes the latent requiredness O(N²). (The *non-repeatable* `GroupFilled` branch was the sibling — now fixed too, #8.)

### 8. O(1) non-repeatable group fill

- **Rationale.** `groupFilled`'s non-repeatable-group branch scanned `index().valued` and tested each descendant's scope — **O(valued) per call** → O(rows × valued) when a model has `GroupFilled(nonRepeatableGroup)` checks per row. The other half of the `GroupFillCache` analog (#6 did the repeatable half). It looked hard because the scope depth varies with the rule's iteration group.
- **Implementation.** A per-`(groupPath, group)` **attach-depth index** over the valued *descendants* of `groupPath` — exactly the `attachByDepth`/`contextsFor` shape (group descendants by their `commonPrefixLen(p.path, group)` depth, store the prefix set), memoized in the `Index`. `groupFilled` then checks `rowReps.take(d)` against the set at each depth — O(1) per call after a once-per-`(groupPath, group)` build. It mirrors the old per-descendant scope check exactly, so behavior is unchanged (the dead `inScope` helper was removed).
- **Example.** A per-row rule `GroupFilled(SomeNonRepeatableGroup) And …` over a large document.
- **Results & discussion.** The non-repeatable `GroupFilled` path is now O(1)/call — no O(N²) left in either `groupFilled` branch. Full `:adapter` differential suite green (`GroupFilledDiffTest` + the requiredness/index-field law tests confirm behavior unchanged). With this, **no known O(N²) cliff remains in the group-fill/raw-validation paths** (the row-prefix index #4, the repeatable-fill #6, and this close out those kernel-cache analogs). Compute-overlay indexed columns and correlation buckets are now cached per computation step too (IF143, was IG60); the multi-star equality-correlation path graduated with its bind-depth-scoped hash join (IF144).

### 7. Linear index build (the cold-path / startup / JS cliff the warm harness never saw)

- **Rationale.** The `Index` build deduped group rows with `if (p.reps !in it) it.add(p.reps)` — an **O(rows) `List` membership per group placement → O(N²) to build the index**. The against-kernel harness *never saw it* (it measures **warm**, after the index is built once outside the timed region), so it hid behind that methodology — but **every COLD first `validateFull` pays it**: startup, the CLI one-shot path, and a single JS pass. It was the real reason a JS run blew up at scale (cold JVM @20k = 1.75 s; **JS @20k = 14 s**, super-linear).
- **Implementation.** Drop the check entirely: every group placement is **already unique** by `(path, reps)` because both `group()` and `autoGroup()` gate on the `instantiatedGroups` set before adding — so the `!in` scan was redundant *and* quadratic. A plain `add` makes the build O(N).
- **Example.** Any cold/first evaluation at scale — `DmInterpreter(model).validateFull(bigDoc)` on a fresh document; the CLI evaluating one large document; the JS `DocumentScaleTest`.
- **Results & discussion.** Cold build is **linear**: JVM @30k = 152–220 ms (was ~1.75 s at *20k*); **JS @10k = ~60–106 ms (was >2 s — it timed out)**. This is the **biggest win for startup and for JS**, both of which only ever run the cold path. The JS scaling guard (`DocumentScaleTest`) rose from 3k → **10k** (a scale that was *impossible* on JS before). A worked lesson in benchmark methodology: a warm against-kernel harness is right for steady-state but **blind to one-shot/startup cost** — measure the cold path separately (that is what `PerfScalingTest.startupCost` and the JS `DocumentScaleTest` now do).

### 9. O(N) `$` equality self-correlation (the hash-join — IF47, 2026-07-06)

- **Rationale.** A `$` outer-correlated filtered quantifier — `AtLeastOneFieldFilled(../G* / F Having [X] == [$X] …)` — is a **self-join**: for each of N outer rows, the naive strategy scans all N inner rows to find the matches → **O(N²)**. This is the single hottest `$` shape (the BA "predecessors" pattern), and the one the reported corpus model used.
- **Implementation.** The equality self-correlation shape (`[X] == [$X]`, ± a `CurrentRepetition` self-exclusion, and nothing else) is recognized (`parseCorrelationJoin`) and resolved by a **value-keyed bucket map** the `Document` builds + caches once per `(group, scope)` — an `outer-key → [t, f, n]` tally over the inner rows, O(N) to build — then an **O(1) lookup per outer row** (`hashJoinTally`, self-subtracting the outer row's own contribution when self-excluded). This is the kernel's own linear self-correlation strategy. A **non-equality** `Having` (e.g. `<`) keeps the O(N²) inner-scan fallback (still `$`-correct); the buckets skip un-evaluated (all-empty) rows and `Unknown` join keys (an `==` never matches those).
- **Example.** A rule iterating N `/Order/Items` rows, each firing on "another row shares this row's `Count`".
- **Results & discussion.** Measured 2026-07-06, deeply warmed, all three engines within one run: interpreter ≈3.0 ms vs generated Java ≈8.8 ms at 400 rows and ≈6.3 ms vs ≈30 ms at 1600 rows. That is encouraging equality-hash-join evidence, not current NFR certification. `OuterCorrelationPerfTest` now requires `<9×` growth for 4× rows and retains the stable against-kernel ratio check, so loss of the equality hash join crosses the catastrophe floor. It still does not time the genuine non-equality fallback; IG77 owns that separate declared-pairwise scenario and the certification estimator. Correctness is locked by `adapter.laws.OuterCorrelationDiffTest` for the exercised fast/fallback cases; IF144 separately locks legal multi-star equality forms.

### 10. Document-level index-column state (IF116, 2026-07-10)

- **Rationale.** The IF107/IF115 indexed-read gates — and the older IF15/IF60 index-aware aggregate/quantifier classification — consulted the index column per LOOKUP: a fresh `starCells` list plus a fresh duplicate-value set per call. A `validateFull` over a per-row indexed rule therefore scanned the whole column once per row — **O(rows²)** with a heavy allocation constant. The gate's `semanticIndexStaysSubQuadratic` (N=20 000) deterministically stalled 20+ minutes; the master gate's independent perf re-run caught it (the drill session's own gate run predated IF115's wiring of the guard into the validation hot path — the lesson: a perf claim is only as fresh as the last hot-path commit it covers).
- **Implementation.** `EvalContext.indexColumn(path, bindDepth)` → `IndexColumn` — the cells, the `duplicated` set, and the derived flags/tally (`anyNotCheckRelevant`, `anyEmptyOrDuplicated`, `cleanFilled`), all built once at construction so a consulting site is O(1). The RAW row context memoizes it per (column, star-scope prefix) at the DOCUMENT level (`Index.indexColumnByScope`, the twin of `indexedCell`'s `indexRowByValue` map, #4); all five former scan sites ride it. The cascade OVERLAY cannot delegate to that raw memo — its view changes as computations land, and `by d` delegation would silently serve stale raw cells (IF116) — so it keeps its OWN per-computation-step cache keyed by the same `(column, scope)` (IF143, was IG60): built once per step, shared across the step's outer rows, bypassed only for the step's own write column.
- **Example.** A rule iterating N rows, each reading `[Price For CustomerClass]` against the same N-cell index column.
- **Results & discussion.** Semantic-index growth back in the linear band: 19.0 ms@5000 → 76.6 ms@20000, min-growth **4.03×** (pre-fix: unbounded — the N=20 000 arm alone ran 20+ minutes). All twelve growth checks 2.7–4.3× (linear ≈ 4). Correctness pinned unchanged by the six index differentials + the full suites — the fix is pure memoization.

### JS performance — one code path, so every optimization carries (2026-06-24)

All the optimizations described here live in **`commonMain`**, so JVM and JS share their algorithmic structure rather than maintaining a JS-specific evaluator fork. `DocumentScaleTest` recorded roughly 61–140 ms for its exercised 10k-row Node scenario and linear-looking growth after the cold-path index fix. That evidence supports the complexity claim for that scenario only: it does not establish that every host-sensitive primitive has identical semantics or constants—decimal exactness/power complexity (IG89) and regex dialect/compilation (IG90) are known counterexamples—and it is not a true first-answer p95 certification (IG77). The lever that mattered in this measured case was the **cold-path O(N²) (#7)**: because a one-pass Node run does not benefit from JVM-style warmup, a quadratic build made it time out, while fixing the shared root restored scale. The index/memo construction is lazy, which avoids eager constructor cost but still leaves first-use work inside evaluation.

**Net effect (2026-06-24, with the recorded crossover since closed—see the results log):** the interpreter is faster-and-linear for the measured common raw-document cases on JVM and Node, and the measured first-call index construction is linear too (#7). Compute-overlay index/bucket rebuilding is now cached per computation step (IF143, was IG60), multi-star equality uses the scoped hash join (IF144), and current gates do not certify the candidate NFRs (IG77). At the 2026-06-24 baseline the interpreter matched kernel-Java at ~96 rules and still trailed at 192 (1.19×); later `repsOf` memoization, per-row resolution caching, and the composite-map-key split closed that recorded gap. A code generator would be a second strategy, not a demonstrated prerequisite for current measured throughput.

## The harness (invest here — it pays off)

Not ad-hoc `measureTime` calls sprinkled in tests — a **proper, reusable harness**, because it does double duty: it **gates** regressions *and* it's how we **find** the O(N²) hotspots in the group machinery. Design:

- **`PerfScenario`** — the unit: a real DM-JSON model + an **instance generator parameterized by scale `N`** (build 1k/10k/100k rows *programmatically*, never commit giant fixtures) + the operation (`validateFull` / `compute`) + the correctness oracle. One scenario, run by both engines.
- **Three engine adapters behind one interface** — `InterpreterEngine` (`DmInterpreter`), `KernelEngine` (Groovy via `RuntimeLaws` → `IDocumentRtService`), and `JavaKernelEngine` (the fair generated-Java baseline). The harness lives in `:adapter` (the only module with the kernel), mirroring the `laws/` differential layout, under `…/perf/`.
- **Warm-measurement discipline** — per (scenario, N): **warm up** (discard JIT-warming iterations), then time `K` iterations; report **median** (robust) + min + p90, and the **ratio** `interp_median / kernel_median`. Never mix a cold sample into this warm-throughput result; NFR-S uses the separate fresh-process protocol above.
- **Correctness first** — assert `interp == kernel` on the scenario *before* trusting any timing (a fast-but-wrong path is not a win; reuse the differential comparison). The comparison is the fired-code **multiset** (a sorted `List`, not a `Set`), so a per-row firing-count mismatch is caught, not just a missing code.
- **Three run modes** — (1) **gate mode**: single document, loose bounds, CI-friendly, fails on a catastrophic/relative regression; (2) **repeated-eval mode**: the engine built once, M slightly-different documents looped (form-input / batch) — the reuse pattern the kernel's codegen + per-run caches are tuned for, reported per-eval; (3) **profile mode**: one scenario at high `N`, interpreter-only, verbose per-iteration stats, no assert — for hunting the hotspot (JFR/async-profiler-friendly loop on JVM).
- **JVM tool choice** — start with this **custom integration harness** (whole-document evaluation is the real unit; warmup+repeats+median+ratio is the right rigor for it). Reserve **JMH** for a *specific hot inner loop* (e.g. `repsFor`/`starRows`) that needs sub-method attribution — add it only when a profile points there, not upfront.
- **JS throughput** — a Node-runnable large-`N` check on `jsTest` (the same `Document`, `measureTime`, no kernel) so the native/JS reason-to-exist is perf-gated too.
- **Output + baselines** — print a `scenario × N × interp_ms × kernel_ms × ratio` table and append machine-tagged baselines to the results log (below). The spec holds the method; the log holds the numbers.

**Built (2026-06-23, extended through 2026-07-18):** `adapter/src/test/.../perf/` — `PerfHarness` (the `PlacementSink`-driven scenario + a `PerfOp{VALIDATE,COMPUTE}` + the three engine adapters `Interpreter`/`Kernel`(Groovy)/`KernelJava` behind `PerfEngine`/`ReusableEngine` + `measure`/`runScenario`/`runRepeated`/`timeInterpreter`), `PerfCatalog` (single-sourced `perf.dm.json`, the current B-series scenarios including B9 Berlin, a parameterized `manyRules(count)`, and a fuzz scenario), `PerfGateTest`, `PerfBenchTest`, `KernelEdgeTest`, `PerfScalingTest`, and `PerfProfileTest`. `RuntimeLaws` is the shared kernel oracle; its build-once `KernelEngine` (Groovy) and `JavaKernelEngine` (the kernel's own validator compiled as Java—the Groovy-tax-free baseline) both expose fired/compute outcomes. `KernelJavaBaselineDiffTest` guards that the Java baseline fires identically to Groovy. Codegen is primed out of every timed region (non-negotiable #2). IG77 owns converting these diagnostics/catastrophe guards into the declared NFR lanes.

**Model-driven seed generator + differential fuzz net — built (2026-06-23).** The instances are built by a kernel-free **`SeedGenerator`** (`…interpreter.gen`) through the `PlacementSink` seam, so the perf harness, the **differential fuzz net** (`InterpreterKernelFuzzTest` — the correctness twin of this perf differential), and the `dmtool model seed` verb all share one generator. **Both pieces have their own spec — [SEED-GENERATOR-FUZZ-SPEC.md](SEED-GENERATOR-FUZZ-SPEC.md)** (the generator's contract + the fuzz method, diverse model, value strategy, bug track record, and per-operator extension loop); this doc only consumes the generator for the perf scenarios.

## Architecture direction (owner hint, 2026-06-23 — keep in mind)

A structural optimization to design toward (not yet committed work):

- **Decouple eval from a hierarchy — a flat, indexed instance is enough.** The validate/compute API only ever asks "the value for `(path, repetition-indices)`", so the instance backing store can be a **flat `(path, reps) → value` map**, not a tree (this *is* the task-#28 index, promoted to the primary representation). Group membership and iteration scopes come from the **model** (stable), not from walking an instance tree.
- **Prepare the model once; reuse across runs—parse-once is DONE, further preparation is profile-gated.** `ParsedModel` already parses each stored rule/computation lazily once per `DmInterpreter` and reuses the AST across calls. Declared field and predefined-type patterns are already constructed once; source inspection identifies model-static work that may still repeat on narrower lifetimes: literal condition-pattern compilation, date-format matcher construction, row-outcome reference/scope/error-path derivation, and computation dependency DFS. IG77's profile lane must measure counters/time at representative rule counts before promoting these to engine caches; IG90 owns lazy prepare-once condition patterns as part of its dialect fix. Shape: `val engine = DmInterpreter(model)` built once → loop `engine.validate(document)` / `engine.compute(document)`.
- **The caching boundary is ownership, not “value-independent only.”** Model-invariant artifacts (parsed ASTs, scopes, field metadata, dependency order) may live on the engine. Value- and structure-dependent indices/results are also encouraged when they accelerate evaluation, but they belong on the `Document`/its mutation-invalidated index, one validation call, or one row and must be discarded or invalidated with that owner. Never reuse a value-dependent result across a changed document. Fixed (IF142): `rowContextsCache` and `correlationBucketCache` are cleared with `cachedIndex` by one invalidation method on `Document.add`.
- **Open question (deferred):** between runs, do only *values* change, or also the set of repetition *rows* (add/remove)? If values-only, the structure index is reusable too; if rows change, rebuild the value store per run and reuse only the prepared model (the safe default). Decide when this is picked up — profile first.
- **Beyond prepare-once — Excel-style *incremental* recalc (deferred, trigger-gated):** recompute only a changed cell's dependent closure instead of re-running the whole document. Feasibility + the DEFER decision + the two-part re-open trigger are recorded in the archived [INCREMENTAL-EVAL-PROPOSAL](archived/INCREMENTAL-EVAL-PROPOSAL.md). The prepared model above is its prerequisite substrate; the incumbent kernel does recompute-all-per-run + per-run caches, *not* cross-edit dirty propagation.
- **Study the kernel's data representation + caches for INSPIRATION (not a copy — the license boundary holds: read for comprehension, write original).** The kernel devs spent *years* optimizing; its instance representation and its caches — `IndexFieldCache`, `ValidationCache`, `CalculationCache`, `GroupFillCache`, `RepetitionNotUniqueErrorCache` — encode hard-won structure (index-by-field, memoized group-fill, cached calculation results within a run). **Do not assume a naive fresh impl will be anywhere near kernel performance.** Get informed by what they cache and how they index, reproduce the *idea* in original Kotlin, and let the against-kernel benchmark (#29) tell the truth. Humility + measurement, not confidence.
