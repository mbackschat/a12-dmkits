# Interpreter non-functional performance — startup, throughput, relative footprint

The `:interpreter` must have **low first-answer latency**, be **fast on the hard cases**, and keep a **low relative footprint** without giving up the caches that make it fast. These are measured requirements, not hopes. This document is the single detailed source of truth for performance development acceptance, benchmark eligibility, measurement, engineering constraints, the catalog, verification status, and dated evidence. [INTERPRETER-SPEC.md](INTERPRETER-SPEC.md) “Non-functional contract” separately owns the numerical candidates and, after per-number certification (IF137), the ratified release bars; [`interpreter/CLAUDE.md`](../interpreter/CLAUDE.md) carries only the auto-loaded guard summary. A number in the results log is evidence, not a product decision or a substitute for the contract.

## Performance contract

**Standing development acceptance rule (owner-strengthened 2026-07-21; scaling clause corrected 2026-08-11, IF279).** For every protocol-valid comparable scenario and every tested scale, the interpreter must have a lower evaluation median than both dynamic-Groovy and generated-Java, and its measured **per-unit cost** must be no higher than either kernel strategy's. Any repeatable ratio at or above `1.0`, or any repeatable per-unit loss, is an active performance defect and takes priority over expanding the benchmark estate. The scaling clause used to read "its measured growth factor must be no worse than either kernel strategy", which is **not** a satisfiable requirement: for an engine that is linear over the step the measured N/4N factor is `4 - 3f` in the fixed cost's share `f` of the small-scale reading, so it ranks engines by fixed-cost share and the leanest engine loses deterministically (IF279). The growth factor stays in use as each engine's **own** catastrophe bar, never as a cross-engine comparison. Exact complete outcomes, identical model/document/runtime bindings, and the same warm/cold boundary are prerequisites; doing less work never counts as a win. This development rule does not silently promote an NFR candidate number under IF137—the certification protocol still governs release bars—but it does govern optimization and completion. If the kernel itself has bad inherent or output-sized scaling, make several focused, profile-earned root attempts to beat it; if those attempts do not improve the interpreter, stop before inventing a larger subsystem, report the evidence and attempts, and ask the owner for direction.

1. **REAL documents only — benchmarking a shortcut is cheating.** Measure the production evaluation path: the general `Document` (interpreter) and the kernel's `IDocument`, both built from **real DM-JSON models**. The spike's `Map<String,String>`-backed `RepDoc` (O(1) lookups, one-pass `star`) must **never** be the benchmarked object — it sidesteps the exact machinery (parallel index, common-prefix resolution, star aggregation) that is hard to make fast, so its numbers are a fiction. If a benchmark doesn't exercise real group resolution, it isn't a benchmark.
2. **Measure AGAINST the kernel, as a regression gate.** The perf benchmark is the **twin of the correctness differential** and lives in `:adapter` (the only module with the kernel). Before timing a scenario, use the prepared interpreter's value-independent `supportAudit()` to force the same cached rule plans execution consumes: every rule, implicit computation validation, computation alternative, customization requirement, host-sensitive primitive, RNU plan, and iteration/parallel shape. Then check `unsupported.isEmpty()` on every actual instance/variant—including the exact N used by interpreter-only cold/warm timing helpers—and compare complete validation (`code|type|indexed-pointer`) or computation (`indexed-pointer|outcome|value`) signatures across interpreter, dynamic kernel, and every declared Java-capable static strategy. An ERRORED computation's attempted value is part of that signature, just as it is for VALUE. The equality gate remains exact, while a failure reports multiset-aware only-side counts with no more than ten samples per engine and 240 characters per displayed signature; large generated documents therefore remain diagnosable without dumping their complete outcome sets. `validateFull` fails loud on unsupported (IF139), but it is neither the prepared audit nor the outcome-bearing API. IF156 now enforces both eligibility layers and refuses a timed fiction with the construct, scale, and variant named. Then record the eligible wall-clocks + ratios and apply the standing rule above: the interpreter must beat both kernel strategies at every measured scale and cost no more per unit than either (IF279 — per unit, not per growth factor).
   - **⭐ NEVER count Groovy codegen — in ANY benchmark, including startup (standing rule, re-affirmed 2026-06-24).** Kernel codegen is **always ahead of use in real-world projects**: a real deployment generates + compiles the validator at **model-load / deploy time** (cached in `IModelCodeCache`), so the kernel **never pays codegen per request** — its real cost is steady-state validation against already-generated code. Timing codegen therefore measures a cost production never incurs — a fiction that unfairly flatters any "interpreter is faster / starts faster" claim. **This is absolute and has no exception:**
     - **Comparison benchmarks** prime it out — the kernel generates on its FIRST `validateFull` (cached for the engine's life), and every timed region is preceded by a correctness `run()` + warmup, so the codegen call is always discarded. (This is also why the kernel's per-call time only JIT-warms downward over the first ~dozen calls — the Groovy validator warming, not recodegen.)
     - **Startup measurements too.** The interpreter's "fast startup" (goal #1) is measured **on its own terms** — its engine build + first-call index/parse cost in absolute terms — **NOT** as a race against the kernel's codegen. Do not put a "kernel cold start incl. codegen" number next to it; that's the forbidden comparison. The interpreter's no-codegen advantage is a **capability** point (it matters for native-image — the kernel's Groovy codegen can't go native at all — and for one-shot CLI / JS use where there's no ahead-of-time deploy step), stated as prose, never as a benchmark timing.
     - **Codegen+compile is ONCE PER DEPLOYMENT/RELEASE — it is not a per-call, setup, OR startup cost, so it belongs in NO column of ANY comparison.** It runs at model-load / deploy time (cached in `IModelCodeCache`) and is paid **zero** times per request. Consequence: in any steady-state / hot-reuse comparison BOTH engines are already *past* setup — the kernel's code generated at deploy, the interpreter's first-parse amortized — so the only thing left to compare is **per-operation evaluation cost** (tree-walk vs already-generated code). Two traps that break this even while *saying* "paid once": **(a)** listing codegen as the kernel's *per-call setup* in a comparison table — it is not a per-call cost at all; **(b)** framing a **cold / one-shot** run as "the kernel must codegen first" — in production the model is already deployed, so the kernel does **not** codegen on the call. The interpreter's *not needing* codegen is a **capability** (it runs where Groovy codegen can't — native image, JS — and where there is no deploy step), **never** a "starts faster / faster per call than the kernel" timing claim.
3. **Target the non-obvious group machinery, at scale.** Not flat single-row rules — the cases that bite: **deeply nested repeatable groups**, **parallel iteration** / cross-level references, **starred aggregates** over large lists, and **many rows (up to 100 000)**. *Invest heavily in all things groups.*
4. **Run on the PURE engine, decoupled from the CLI — it must be CHEAP to run, very often.** Both the correctness differentials and the perf harness call the **`DmInterpreter` + `Document` API directly** (kernel via `RuntimeLaws`), NOT through `dmtool`/`InterpreterEngine`/`InterpreterModelLoader`. No process spawn, no `installDist`, no JSON envelope, no native build — just in-process JUnit (and `jsTest`). "Real document" means the real `Document` *data structure* with real nested-group shape, built **programmatically in-test**, not loaded through the CLI. The CLI's loader is a separate, thinner concern with its own small test; the engine's semantics + performance are measured at the engine, so the loop stays fast enough to run on every change.
5. **The hot path stays a MONOMORPHIC CONCRETE call — extend the engine ADDITIVELY, never by interface-ifying a common path (standing design rule, 2026-06-27).** A per-cell / per-operand / per-code-point check on the formal-error or evaluation hot path must be a **monomorphic call on a concrete (`final`) type the JIT can inline** — never a `fun interface` / virtual dispatch the *common* case has to pay. The precedent is in the source: `LegalCharset` is deliberately a `final class` (NOT a SAM) "so the call is monomorphic and JIT-inlined," and `PredefinedType.accepts` is a concrete `data class` method, not an interface. So when a new consumer SPI is added (e.g. the code-based `CustomFieldType` shipped in IF44), it must be **additive + opt-in**: the declarative/common path keeps its concrete inlined call **unchanged**, and the polymorphic SPI call is reached **only** for the construct that actually uses it — exactly how `CustomCondition.check` is paid only by models that contain a `Cond.Custom` node; a consumer who registers no code-based handler pays nothing. A library consumer must run **as fast as today** even as the surface grows. This is **gated, not hoped**: a many-row, declarative-path scenario stays in the perf suite, so any deopt of an inlined hot path (e.g. unifying everything behind one interface) trips the build. Two live guards of this rule: **`CharsetPerfTest`** (the `LegalCharset` per-codepoint path — a SAM `fun interface` once blew the suite up 16 min, so it's a `final class`) and **`CustomTypePerfTest`** (the declarative custom-field-type `PredefinedType.accepts` per-cell path — locks it within a factor of plain-string-with-the-same-pattern + sub-quadratic, so a careless IF44 SPI dispatch that boxes per cell or goes megamorphic trips it). The trap to refuse is the "clean" unify-behind-one-interface refactor — it converts a free inlined check into a per-cell virtual (and, with several impls, megamorphic) call.

## The NFR certification protocol

The candidate budgets and their evidence status are single-sourced in [INTERPRETER-SPEC.md](INTERPRETER-SPEC.md) as NFR-S1/S2, NFR-P1/P2, and NFR-F1/F2. The contract posture is ratified (IF137): the numbers are **informative until per-number certified**, `PerfBounds` is the only ratified NFR/release-level floor, and the paired growth estimator is **interleaved N/4N with the median of within-pair ratios**. Other executable implementation-regression assertions remain diagnostics/catastrophe guards, not certified NFR bars. A number promotes to a release bar only per-number, once its scenario + estimator are fixed, the runner/runtime is pinned, the p95/median sampling is performed, semantic preflight passes, the measurement is reproducible, and the owner ratifies it (the six-point gate, INTERPRETER-SPEC). A later run is **certifying** only when it records the commit, scenario identity, CPU/runner, OS, JDK or Node version, heap settings, estimator, and sample count. Every actual interpreter instance must retain an outcome-bearing zero-unsupported check; every comparison scenario must additionally agree with dynamic Groovy and each declared Java-capable static strategy on complete signatures under the ratified Groovy-dynamic anchor (IF136). Message-only equality is insufficient, and `validateFull` now fails loud on unsupported (IF139). The recommended sample/fork and job/miss defaults bind a number only at its promotion, not globally. The numbers remain **UNVERIFIED CANDIDATES**, not silently “green” because an older laptop minimum was below one.

### Startup / first answer (NFR-S1 and NFR-S2)

Library startup measures the time from an already-expanded, in-memory `ModelDef` and a materialized `Document` to the first fully materialized result. The clock starts **before `DmInterpreter(model)`** and ends after `validate`/`compute`/`testRule` has produced its complete result. Model loading and document construction are separate consumer work and stay outside this library clock; engine construction, lazy parse/index initialization, evaluation, and result construction stay inside. Run at least 50 independent fresh JVM/Node processes, discard no samples, and gate the **nearest-rank p95** while reporting median too. A minimum is never a startup statistic.

Native CLI startup is a separate end-to-end measure: the parent clock starts before process launch and stops after the complete result envelope is read and the process exits. It includes process startup, option parsing, model/instance file reads, JSON/model loading, compute→apply when enabled, validation, serialization, and shutdown. Use warm OS filesystem caches for repeatability and at least 50 independent invocations. The absence of runtime codegen is a capability advantage; kernel codegen is never included in or compared with a startup timing.

Keep the absolute p95 budgets and the row/rule growth checks separate. The former catches a uniformly slow but linear implementation; the latter catches an asymptotic regression. The older `freshRunMedianMillis` helper still starts its clock **after** engine/document construction and therefore remains only a complexity probe. IF172's separate `interpreterPerformance` protocol is the first-answer evidence lane: independent JVM/Node processes clock engine construction through complete results, while the native parent clock includes spawn through complete envelope and exit.

### Warm throughput and scaling (NFR-P1 and NFR-P2)

Build each engine and materialize its document outside the timed region, perform the zero-unsupported/tri-engine correctness preflight, warm the engines, then record repeated evaluation medians. The absolute large-document budget uses the interpreter on the production `Document`; the NFR-P2 relative budget uses the same logical instance against the kernel's generated-**Java** evaluator because that ratio isolates the algorithm from Groovy's dynamic-dispatch tax. That release-candidate denominator does not narrow development acceptance: every comparable run records and beats both dynamic Groovy and generated Java.

Every scenario declares its intended complexity class. A linear or `N log N` axis is measured at `N` and `4N` and must satisfy the NFR-P1 growth bar under the ratified paired estimator (IF137): interleaved N/4N samples with the median of within-pair ratios. A genuinely pairwise semantic operation may keep an `O(outer×inner)` fallback only when the exception is explicit and correctness-locked; its interpreter median must still be lower than both kernel strategies and its per-unit cost no higher than either (IF279). An optimized equality/hash-join path is declared `O(outer+inner)` and must be gated as linear; a permissive sub-cubic guard does not protect that optimization.

### Relative footprint (NFR-F1 and NFR-F2)

**Footprint is not “minimize memory.”** Indices, hash maps, parsed-AST caches, row-context memoization, and other bounded caches are the preferred implementation when they remove repeated work or improve the complexity class. A footprint review asks whether the state has the right owner/lifetime, reaches a plateau, grows in the declared space class, and earns its cost—not whether a smaller but slower implementation exists.

Measure four relative surfaces:

1. **Dependency closure:** sum the resolved non-JDK runtime artifacts needed by a fresh interpreter consumer and compare them with the equivalent kernel/Groovy evaluation closure. Kernel, Groovy, dmtool, `:adapter`, and other-kit dependencies remain a hard zero in the interpreter graph.
2. **Packed artifacts:** compare the thin JVM artifact, packed JVM runtime, and JS KLIB with the previous release. Keep the KLIB explicitly separate: it is not a published npm-package number. IF226 shipped the functional production npm artifact only after a non-empty exported API, generated `.d.ts`, and non-repo consumer smoke passed; an empty DCE output or unpacked `node_modules` closure still fails closed rather than becoming a footprint base.
3. **Runtime state:** in forked JVM and Node probes, measure retained heap and allocation volume above fixed setup at `N, 2N, 4N, 8N`; the recommended fork count (≥5) binds at promotion (IF137). Define the JVM post-GC sampling method and run Node with `--expose-gc`, report logical cache-entry counts separately, and verify owner release as well as warm-owner plateau so GC noise cannot pass or fail the exponent accidentally. Fit a log-log space exponent per fork and gate its median plus the worst 4× step under the ratified policy. This multi-scale check does not mistake a hash table's discrete backing-array resize for a super-linear design. Report cache owners and the performance delta they buy.
4. **Native delivery:** compare the native binary with the equivalent trimmed JVM app image. This is a dmtool product measure—the binary still bundles the kernel for the MVK oracle—not an isolated interpreter-jar measure.

A >10% artifact/closure increase or >20% same-scenario runtime-footprint increase is a **review trigger**, not an automatic demand to remove a cache. It may be accepted with the measured exactness/startup/throughput benefit that pays for it. An unbounded cache, a non-plateauing repeated-eval run, or a space-complexity breach is a failure.

**When the generated path may still be preferred on footprint:** a **GC-sensitive, sustained-high-throughput** service is the workload where the generated path's primitive `long[]` indices + interned results may win, even where current medians favor the interpreter — a workload-specific hypothesis, not a result from this project, and tempered by the generated path's own super-linear large-row wall-clock (see "Code-generator row-axis scaling"), which means its allocation story is not uniformly better.

**The interpreter's JVM and JS/Node production dependency closures are now fully reconciled and measured reproducibly** by `:interpreter:interpreterRuntimeClosure` and `:interpreter:interpreterJsRuntimeClosure` (IF160, wired into `:interpreter:check`). The tasks reconcile each canonical runtime file to exactly one resolution artifact, account graph-only components, keep the own jar/KLIB separate, recursively walk the public package's production dependency/optional/peer declarations, and fail on forbidden project/published-kit/kernel/Groovy/opaque/npm edges. Separate generated reports name each host graph and remain authoritative for the clean-tree inventory and byte total. `:adapter:kernelRuntimeClosureReport` first executes a self-contained real kernel validation, then derives the informative comparison graph from that consumer's minimal compile/runtime dependencies; no ratio is promoted. IF173's local clean-commit collector injects the same definition into the current and archived previous release, records bytes/SHA for the thin JVM jar, reproducible packed JVM runtime, JS KLIB, native CLI, and native-equivalent trimmed JVM app, compiles and runs an external Java consumer solely against the unpacked packed-runtime `lib/*.jar`, and executes the same typed low-firing evaluation through both delivery comparators. Its deltas and native/trimmed ratio remain informative. **Superseded provisional baseline (2026-07-18; existing artifacts inspected, not rebuilt or certified):** the interpreter JVM jar was 556,845 bytes; its named closure was 2,984,760 bytes; the install's named kernel jars + Groovy were 12,909,518 bytes. The often-cited 33 MB native / 119 MB JVM pair was measured on 2026-06-15, before interpreter-backed native evaluation existed, and is neither same-revision nor equal-capability. IF226's publication increment added the production npm measurement only after the real export, `.d.ts`, and consumer smoke existed; it was never fabricated from the KLIB or empty production-library output. Only numerical promotion and CI scheduling are owner-gated.

**Cache lifetime is structurally guarded independently of heap noise** (IF161). `CacheLifetimeGuardTest` samples logical entries for the real `Document`, `ParsedModel`, and per-step `OverlayViews` owners at five same-owner checkpoints, fences the live engine/document, then proves many discarded owners reach a reference queue and the weak observer returns to baseline. Planted per-evaluation and global-document retention controls prove both guards can fail. The observer is internal, nullable, instance-local, and absent from the public API; overlay entries are cleared in `finally`. This proves owner-scoped plateau/release, not a retained-heap exponent, allocation result, or promoted numerical bar.

### Per-model resident cost — the P-SERVICE axis (measured 2026-08-07 on JVM, informative)

NFR-F3 asks a question the forked lane below does not: not how one engine's state grows with its document, but what **one resident model costs** when a service caches many. Re-runnable by `ModelFootprintReportTest` (opt-in via `-Da12.footprint.report=true`, prints, asserts nothing), which holds 40 instances per measurement and reports the minimum settled heap over six collections, so the per-instance figure is not a single noisy sample.

Retained bytes per instance, JVM 21.0.12. `cold` is a `PreparedModel` that has never served a request; `warm` is the same after one `createInterpreter()` + `validateFull`, which is what a cache entry holds once it has served anything.

| model | fields | rules | expanded DM-JSON | cold | warm | warm + `Interpreter` |
|---|--:|--:|--:|--:|--:|--:|
| `typedefs` | 26 | 0 | 4,726 | 32,839 | 45,892 | 46,907 |
| `order-aggregates` | 15 | 6 | 5,197 | 24,808 | 38,751 | 40,237 |
| `order-stock-low` | 29 | 1 | 5,397 | 36,487 | 52,425 | 54,259 |
| `many-rules-48` | 5 | 48 | 14,504 | 45,347 | 88,407 | 93,813 |
| `many-rules-192` | 5 | 192 | 53,779 | 154,894 | 313,946 | 329,849 |

Four readings, and the fixture set is a **shape matrix rather than a size ladder** on purpose — the first three vary fields at ~one rule, the last two vary rules at five fields — because a rules-only sweep cannot tell "there is a fixed floor" apart from "cost tracks field count":

- **The prepared model is larger than the JSON it came from**, 5.8× to 9.7× the expanded DM-JSON when warm. This is the intended space-for-time trade stated at the top of this section, but it inverts the assumption a consumer is likely to bring.
- **Cost tracks BOTH axes, at roughly 1.6 kB per field and 1.6 kB per rule.** Two independent two-point estimates agree: along the rule axis at five fields, 48→192 rules adds 225,539 B over 144 rules (1,566 B/rule); along the field axis at ~one rule, 26→29 fields adds 6,533 B (≈1,656 B/field after subtracting one rule). Predicting `order-aggregates` from those slopes gives 37.1 kB against 38.8 kB measured, within 4%. **There is no meaningful fixed floor** — an earlier Node measurement reported a "60–80 kB floor" that was in fact the small model's own total, and its rules-only dose-response could not have supported the claim. **Corrected 2026-08-07: this two-term rule is superseded by the three-term fit below.** These five fixtures carry 3–4 groups each, so the sweep could not see a group term at all; against a realistically structured model (29 groups) the two-term rule under-predicts by ~18%.
- **A warm entry costs 1.4× to 1.9× a cold one**, so a service must budget the warm figure. Sizing on `cold` understates a served cache entry by up to 2×.
- **The interpreter is now thin: it adds only 2–5% over warm.** Before model-static preparation was hoisted onto `PreparedModel` ([IF251](INTERPRETER-FINDINGS.md#if251)), a retained interpreter roughly doubled the cost, because it owned the plans. That delta is the hoist's effect, measured.

`createInterpreter()` is not lazy: `Interpreter.init` calls `engine.supportAudit()` eagerly, and the audit forces every rule plan, computation plan and pattern compile into the shared store. That is why `warm` and not `cold` is the budgeting number, and the eager audit is kept deliberately so a P-EDIT consumer learns at form open that a custom condition is unregistered rather than on the first keystroke.

Two source-verified facts change what a service should retain. `ModelWorkspace.prepare()` holds **no preparation cache** — each call re-runs a fresh deterministic assembly — and `AdmittedWorkspaceModelSource` retains its source **twice**, as a defensive `ByteArray` copy and as the decoded UTF-16 `String`. A `PreparedModel` retains neither source form; besides its `ModelDef`, fingerprint and dependency list it holds the shared model-static preparation described above. So releasing the workspace after preparation frees the source, and a service should cache expanded DM-JSON plus prepared models rather than workspaces.

This is measured context for NFR-F3, not a promoted bar: one host, one settling method, five fixtures, and no pinned fresh-process series.

#### The same axis against both kernel strategies (measured 2026-08-07, informative)

The section above measures the interpreter alone, which cannot answer what a service replacing kernel runtime services should expect. `EngineFootprintReportTest` in `:adapter` measures the same quantity for all three strategies over the same five fixtures ([IF253](INTERPRETER-FINDINGS.md#if253)); it must live there because `:interpreter` stays kernel-free in test scope. Opt-in with `-Da12.engine.footprint=true` under `-PrunPerf`; twelve instances per arm, eight settling collections, ~2 min.

Three protocol points carry the result.

**Class metadata is measured, heap alone is not the footprint.** Both kernel strategies generate and load classes per model, and class metadata lives in Metaspace plus the disjoint Compressed Class Space — neither of which `Runtime.totalMemory() - freeMemory()`, the settling method the section above uses, can see. A heap-only comparison understates them by construction.

**The JIT code cache is excluded, and that was measured rather than assumed.** Attributing it per instance produced negative per-instance deltas and charged the interpreter — which loads no classes at all — 67 kB per model, because it tracks how hot code became during the run, not how many models are resident. It is also globally bounded and JIT-evicted. So it is a property of the workload, not of a cache entry, and the harness's KDoc says not to re-add it.

**The equivalent-work check runs before any arm is measured:** the three engines validate the identical document (the interpreter's seed document, encoded as A12 Document JSON and read back by the kernel's own `IDocumentV2Serializer`), their message-code multisets must agree, and the interpreter must report nothing unsupported. That check earned its place immediately — it caught the harness binding `order-aggregates`' `CustomCondition` on neither engine, which the kernel fires and the interpreter reports unsupported, so one model was briefly comparing two different computations.

**The sixth model is derived from a real one, because the five fixtures are not realistic in scale.** They top out at 63 kB of DM-JSON with 3–4 groups, while models in the `a12-kernel-mm` reference clone reach 281 kB across 79 fields, 29 groups and 89 rules. The gap mattered: a rule of thumb fitted only to the fixtures has no group term (see the correction above). The sixth row closes it without committing anyone's model — `dmtool profile extract` reduces a real model to the identifier-free shape artifact [MODEL-PROFILE-SPEC](MODEL-PROFILE-SPEC.md) defines (counts and distributions only; the committed artifact was checked to contain no string values at all), and `ModelSynthesizer.synthesize(profile, seed = 42)` regenerates an own-domain model from it. Fidelity is exact on the axes footprint depends on — field, group and rule counts, boolean arity within bucket — and partial on operator mix and iteration capacity, which drive evaluation work rather than retained size. It is a footprint fixture, not a performance clone, and 45 of 140 compared axes do differ.

**`Java total` has the last column subtracted out, because that part is the harness, not the kernel.** `RuntimeLaws.compileInMemory` defines classes lazily from a `Map<String, ByteArrayOutputStream>` that the returned ClassLoader captures, so every generated class's bytecode stays on the heap for the engine's whole life — 56 to 271 kB per model, which a deployment loading the same classes from a jar never pays. `RuntimeLaws.compiledJavaBytecodeBytes` reports it (deterministically, from compilation rather than from GC sampling) so it can be removed. **Corrected 2026-08-07: an earlier version of this table published the unadjusted Java figures, overstating them by 13–23% and the interpreter's advantage as 4.7–10.4× rather than 3.8–9.2×.**

**The Groovy arm gets no such adjustment, because there the retention is the kernel's own design.** `ModelGroovyCode` (kernel-md-runtime-service) holds `private final String generatedPlainCode` — the generated Groovy text, non-transient, retained beside the `transient GroovyObject` parsed from it — so the generated source really is resident on the dynamic path: ~740 kB of `many-rules-192`'s 7.1 MB heap and ~476 kB of the real-shape model's 4.5 MB. That class also creates one ClassLoader per model with the comment *"we create a new ClassLoader per model to enable the deletion of corresponding class definitions from metaspace"*, which independently confirms that metaspace is the right axis for the generated code and that the kernel's authors account for it there too.

The `interp warm` and `Kernel model` columns are heap, because both arms load **zero** classes per model, so their true metaspace is zero. That is also what calibrates the measurement: their observed metaspace readings, 0 to 27 kB, *are* the noise floor. Read the kernel metaspace column against it — 87 kB is only ~3× the floor, 4.9 MB is far above it.

##### The fitted formulas

Least squares over the six rows, no intercept for the interpreter (a model with nothing in it costs nothing, and forcing the constant to zero also removes the unphysical −8.6 kB the two-term fit produces):

| target | formula | worst residual |
|---|---|---|
| interpreter, warm | `1.41 kB × fields + 1.55 kB × rules + 2.30 kB × groups` | **+3.9%** |
| dynamic Groovy, total | `0.75 MB + 14.3 kB × fields + 58.3 kB × rules` | +6.9% |
| Groovy generated classes | `34 + 3.17 × rules` | +1.3% |
| generated Java, total | *no fit* — see below | ±25% |

- **The group term is the whole reason to prefer this over the two-term rule.** Dropping `groups` moves the worst residual from 3.9% to 12.0%, and the 29-group real-model row is where it shows: 29 × 2.3 kB ≈ 67 kB, which is most of the 18% the two-term rule misses.
- **It validates out of sample.** Predicting the *previous* section's independent 40-instance measurements from this fit lands within 2.4% on all five (`typedefs` 45,866 predicted vs 45,892 measured; `many-rules-192` 312,308 vs 313,946). That is a different harness, sample size and document, so the agreement is not an artifact of the fit.
- **Where the ~1.4 kB per field actually goes, measured by layer.** On the field-dense fixture (26 fields, 4 groups, **no rules**, 24 instances): `ModelLoader.load` alone retains 32,518 B, a cold `PreparedModel` around it 32,660 B (+5 B/field — the wrapper is free), and warm 45,919 B (+510 B/field for the forced indexes and plans). So roughly 90% of a field's cost is the **parsed model**, not the preparation. These fields are also minimal — 156 JSON bytes each, `{type, id, name, fieldType}` with no labels and no enum values — so the ≈8× expansion over DM-JSON is the object graph itself rather than retained text. `FieldDef` is a wide record (path, kind, `labels: Map`, scale, signed, required, format, rangeSeparator, datePrecision, `enumValues: List`, `enumCategories: Map`, enumSValue, …), and each field is additionally an entry in several path, scope and requiredness indexes. That last attribution is **hypothesis, not measurement**: the layer split above is measured, the within-record breakdown is not, and a heap class histogram over N held models is the run that would settle it — the natural first step if this figure ever needs to come down.
- **Three parameters on six points is a fit, not a law.** Read the residuals, not the coefficients' precision, and re-derive if the fixture set changes. Weighting rules by mean boolean arity instead of counting them fits comparably (`0.78 kB per boolean operand`, worst 3.1%), which says the per-rule term is really per-AST-node and a model of unusually complex rules will run above 1.55 kB per rule.

- **The interpreter arm reproduces the 40-instance measurement above to within 1%** on every fixture (45,857 vs 45,892; 312,431 vs 313,946), from an independently written harness at a different sample size and with a different document. - **Totalled, a resident entry is 3.8× to 9.2× smaller than generated Java and 22.0× to 41.0× smaller than dynamic Groovy.**

- **Dynamic Groovy defers essentially all of that to the first evaluation.** `groovy cold` (services created, nothing evaluated) lands within 1% of the model graph alone on all six fixtures, so creating the runtime service costs nothing and the codegen is triggered by the first `validateFull`. The proximate mechanism for Groovy's per-rule class slope — lowering a rule's condition lines into closures, each its own class, past `NUM_CONDITIONLINES_PER_METHOD_GROOVY` — is consistent with the 3.17 classes/rule and with the codegen behavior `RuntimeLaws.generatedGroovySource` documents, but the slope is the measurement and the closure account remains the explanation for it.

Same caveats as above, plus one specific to this table: the interpreter arms exclude a retained `Interpreter` (2–5%, per the previous section) while the kernel arms include their runtime service, and per-model cost is the cost of a *distinct* model — a service sharing one `IModelCodeCache` across engines for the same model pays the generation once, exactly as one `PreparedModel` serves many interpreters. One further limit is specific to the derived row: a profile carries shape, not localized label and message text, so a synthesized model under-represents whatever a real text-heavy model retains for its messages.

## Why this matters (the cheating we caught)

The encouraging spike timing (`InterpreterMultiplatformTest.scalesToManyRepetitionRows`, ~30 ms / 20k rows) ran on `RepDoc`, whose field lookup is a `HashMap.get` and whose `star` is one pass — **O(N) overall**. At the time, the **production** `Document` stored placements in a `List` and did a linear `placements.firstOrNull{…}` scan on **every** `field`/`filled`/`displayValue`/`groupFilled` (and `star` was O(rows×P)) → **O(N²)** per-row evaluation. So the green spike number said nothing about the real path. ## The kernel baseline: Groovy vs Java (the fairness question, 2026-06-24)

The kernel's dynamic `validateFull` runs **Groovy-generated, Groovy-compiled** validators (the codegen architecture is in [`KERNEL-INTEGRATION-NOTES.md`](KERNEL-INTEGRATION-NOTES.md) "Code generation targets"). Compiled Groovy executes as JVM bytecode, but carries a **per-operation dynamic-dispatch / metaclass tax** over equivalent Java — measured at **~1.1–1.3× steady-state** across the rule-count sweeps (e.g. 0.078 vs 0.084 ms/row on the depth curve). The kernel team themselves treat this as real — they disable Groovy's Parrot parser (`groovy.antlr4=false`) specifically because it *"slows down the groovy compilation"*. So a naive "interp vs kernel" ratio conflates two things: the interpreter's algorithm **and** the fact that the kernel pays a Groovy tax the interpreter doesn't.

Two consequences, and what we do about each:

- **Scaling exposes the algorithm beneath a constant tax.** A constant Groovy-vs-Java per-operation factor does not change a complexity class, so record all three N/4N curves — and compare them by **per-unit cost**, the slope of `time = fixed + perUnit·N`. Requiring the interpreter's growth *factor* to be no worse than either kernel curve is the trap this bullet used to set: that factor falls as an engine's fixed cost rises, so it rewards the fatter engine (IF279).
- **The Groovy ratio includes dynamic-dispatch tax, so the Java baseline isolates the algorithm.** We run the kernel's **own generated validator compiled as Java**, via the supported **static-model runtime path** (generate Java source through `generateValidationCode(…, JAVA)`, compile in-memory with `javax.tools.JavaCompiler`, run it through `DocumentStaticRtService` — same `validateFull` scaffolding, Java underneath). Each scenario reports **interp × kernel-Groovy × kernel-Java**. Generated Java is the NFR-P2 denominator; the standing development target still requires a lower interpreter median than both strategies.

**Why this matters beyond fairness — the generator signal.** The two kernel numbers distinguish language tax from algorithmic cost while the acceptance rule requires the tree-walker to beat both. They also inform the **future generator** (the "generator-ready" layering): if a JVM-bytecode/Java target exposes a remaining opportunity, that is what a generator would chase.

**The JS generalization (forward-looking).** TypeScript/JS is the kernel's *other* documented codegen target, so this exact harness — *generate code in language X → compile/load → run through the rt path → diff against the interpreter* — generalizes to a **kernel-JS vs interpreter-JS** comparison later (the interpreter's other reason-to-exist). The baseline engine is therefore built **language-parameterized** (Java now; JS-capable later), not hardwired.

**Why code-generator JS/TS is not yet measured.** The `JAVA_SCRIPT_VK` target exists, so the comparison is meaningful, but running it is toolchain-blocked in the public-repos-only build: the generated JS validator needs the kernel's TypeScript runtime (`kernel-core-runtime-ts`, which ships **source-only** and must be `tsc`-compiled), which in turn needs `npm install` of **private, mgm-scoped `@com.mgmtp.a12.*` packages** from a private registry the public build deliberately excludes. A JS twin of `JavaKernelEngine` would generate the validator, bundle it with the built runtime, and construct a document in the TS runtime's own model — feasible with registry access (the JS analog of the existing Java baseline), unmeasured until then. Any kernel-JS-vs-interpreter-JS claim must wait on that harness.

## Cold and warm regimes: fast first answer + beat both kernel strategies

The interpreter is steered by **two CO-EQUAL goals that pull against each other** (owner direction — neither is secondary):

1. **Low cold / startup cost** — the time from *(model, document)* to the **first** answer must be small: minimal upfront work, no codegen, a fast first `validateFull`. This is the realistic latency for a one-shot CLI invocation, a native-image run, a Node-hosted JS consumer, or a freshly-built engine—not a warm steady state. The browser host has its own fixed B1 assurance lane: median ≤250 ms, starting with 10 fresh Chrome processes and expanding to 50 only when the observed range is greater than half the median, with zero discarded samples on the pinned Apple M1/Chrome runner (IF225).
2. **Beat both kernel strategies at *all* rule counts and tested scales** — the warm steady state, not just the few-rule case; generated Java remains the Groovy-tax-free algorithmic comparator, while neither kernel strategy may win a repeatable measurement.

These are **co-equal and must be gated separately**, because they measure opposite regimes and a win in one can hide a loss in the other — the index-build O(N²) (#7) was invisible to the warm gate for exactly this reason. The current warm suite supplies broad complexity and tri-engine ratio evidence; `PerfGateTest.coldStartStaysSubQuadratic` supplies only a first-validation row-growth probe. Neither certifies the full NFR-S/P contract above. **Owner policy settled 2026-07-21:** promote no candidate number now; retain the isolated `scripts/perf.sh gate` path as the nightly/manual catastrophe and regression lane, and keep the complete IF172 collector manual for release or performance-relevant evidence.

The tension: goal 2 wants the per-call rule work eliminated (cache parsed ASTs, precompute scopes), but doing that *eagerly* at construction is exactly the cold cost goal 1 forbids. The resolution is **lazy memoization** — do the work once, **on first use**, then reuse (so the *constructor* is trivial and the first call is O(N), never O(N²)):

- **Prepare-once ASTs** (`DmInterpreter`): each rule's condition / computation's expression is parsed **lazily, exactly once** (a `lazy {}` per rule — SYNCHRONIZED, so the engine is thread-safe to reuse), then reused across every call and every row. The constructor only builds the wrappers (no parsing) → startup stays cheap, and a single-rule `testRule` forces only the one rule it touches. **This is the direct analog of the kernel's compile-once-at-model-load** — but lazy. *Caveat learned by measuring:* parsing turned out **not** to be the high-rule-count bottleneck (it didn't move the crossover), so this change is for startup + hygiene (it also removed a redundant double-parse), not the headline win.
- **Per-group row-context memo** (`Document`): `contextsFor`/`attachByDepth` did an **O(valued) attach-depth scan on every rule** (and every nested row). Since many rules share a handful of iteration scopes, and the document is immutable during a validation, this is memoized **per group inside the mutation-invalidated `Index`** — computed once per distinct scope, reused across all rules. **This *was* the lever**: ~24% faster across all rule counts, crossover pushed out ~2× (see the log). This mirrors the kernel computing the row structure once and reusing it across rules.

**Historical measurement (2026-06-24, the log below; not NFR certification):** engine build was ~1.5 ms (lazy — just the AST wrappers), first `validateFull` ~57 ms on a 48-rule model (one-time lazy index build + first parse), then steady-state. A single document stayed linear to 300,000 rows (~2.5 µs/row). `PerfScalingTest` is the opt-in reporting harness for those numbers; it has no NFR assertions.

**Historical first-validation spectrum (2026-06-25, `coldStartupSpectrum`; not NFR certification):** **37 ms** (6 rules) → **62 ms** (48) → **126 ms** (192) on a ~500-row document, and **85 ms** (10,000 rows) → **495 ms** (100,000 rows) at one rule. The helper used one fresh engine/document per sample but started timing only the first `validateFull` after both had been constructed; the sweep used one sample per point. It demonstrates plausible absolute latency and near-linear first-evaluation growth, not p95 or end-to-end startup. We do not compare it with kernel codegen (non-negotiable #2); the no-codegen property is a native/JS capability, not a timing race.

## Where the kernel *used to* win (the crossover — closed 2026-06-26; was justified at the 2026-06-24 baseline)

The kernel's documented architecture is **compile-once codegen + per-run caches** (`IndexFieldCache`, `ValidationCache`, `CalculationCache`, `GroupFillCache`, `RepetitionNotUniqueErrorCache` — `kernel-core-runtime/_30_8/internal/core/`), plus short-circuit optimizations (BA doc: skip comparison rules when the root group is empty; cancel quantifiers early). So its edge is the **many-rules** regime: generated straight-line code beats a tree-walker's per-node dispatch + `Val` allocation, and that per-(rule,row) overhead accumulates with rule count.

This is **measured, not assumed** — the rule-count sweep (`KernelEdgeTest`, opt-in `-Dperf.edge=true`) finds the crossover where interp/kernel passes 1.0. The original crossover was **~96 rules vs Groovy**; the per-operation levers below (resolution caching + reduced allocation, NOT an eval-strategy change — see the next section) later produced fair generated-Java ratios of **0.40 firing / 0.52 low-firing at 192 rules** in the recorded 2026-06-27 run (the interpreter was faster in both).

**A codegen ceiling exists, but only for pathologically CONCENTRATED rules (2026-06-25, corrected).** The kernel's codegen splits its validator into methods **by error-field count** (10 fields/method Groovy, 50 Java), each holding all rules of its fields. So when **many rules pile onto few error fields**, they collapse into one method that can exceed the JVM 64 KB bytecode limit (`MethodTooLargeException`) — `manyRules` (rules on ~3 fields) trips this at ~512–768. With rules **distributed** across many fields, the recorded run compiled and measured through **1,000 rules**, so the concentrated failure is not a demonstrated general per-model ceiling. The evidence does not include the previously claimed 2,000-rule run. This is a reminder that generator method-size management is real work the interpreter avoids, not evidence beyond the measured counts. *Hint: also split by an estimated per-method statement/rule budget, not field count alone, so a concentrated model degrades into more methods rather than failing to compile.*

### Code-generator row-axis scaling — super-linear past ~10 000 rows (a kernel-side observation, 2026-06-27)

The generated validator scales **super-linearly on the row axis past ~10 000 rows — even compiled as Java**: for a single per-row rule, generated Java measured **766 ms@10k → 4211 ms@20k** (≈5.5× for 2× rows), and dynamic Groovy is worse (**755 ms@10k → 14 190 ms@30k**). The interpreter on the identical workload is flat (~0.002 ms/row — the flip side of the ~50×/165× data-axis ratios in the results log). The cause is unverified from outside, but the shape is consistent with **eager per-row allocation of validation-result objects → heap/GC pressure that compounds with row count**. This is the most impactful kernel-side perf opportunity the comparison surfaced, and the sibling of the 64 KB ceiling above. *Hint for a kernel-side fix: profile a 50k-row single-rule validation for allocation/GC; consider pooling, lazily accumulating per-row results, or streaming message emission so the row axis stays linear.*

### Eval-strategy was NOT the lever — the per-operation cost was (measured, 2026-06-25)

An early hypothesis was an **eval-strategy ladder** (compile-to-closures → partial-eval → bytecode VM → vectorize → cross-rule CSE → runtime JIT), the Futamura idea of specializing the interpreter to the model. A closure spike measured ~2.5× **on the firing-eval in isolation**, which looked decisive. **It wasn't:** productionized as a sealed compiled-node engine ("Layer 1"), it measured ~**7% end-to-end** and was reverted — `firedType` is only ~7% of `validateFull`, so an eval-strategy change can't move the dominant cost. The real per-operation levers were **resolution caching** (per-row `placeCache`/`valCache`, and the call-local complete `FormalResultCache` that evolved from the original code-only `formalErrorAt` memo) and reduced allocation, which **beat kernel-Java at 192 high-firing** — see "Kernel optimizations from SOURCE" below + the results log. The full SOTA research that informed the ladder (closures-vs-bytecode, Truffle warmup, vectorization, AOT/JS facts) and the rejected approaches are archived in [`archived/INTERPRETER-PERFORMANCE-DESIGN.md`](archived/INTERPRETER-PERFORMANCE-DESIGN.md). The two-phase short-circuit was re-measured after the resolution caches landed and rejected again; the lazy-polarity single walk captured its useful half. Reconsider it only if a future compiled/straight-line dispatch materially changes the second walk's cost.

### The kernel's per-run caches → where the interpreter is naive (the optimization map, 2026-06-24)

The crossover is the *constant-factor* gap. An **O(N²) cliff** (the kernel has a cache, the interpreter does a per-call scan) is the *steeper* danger — but **do not dismiss a constant factor as "not a cliff"**: a per-(rule,row) redundancy is a **~rules× constant** that, at 192 rules, dominates (the `ValidationCache` "repeated field reads" row below was mis-triaged exactly this way — parked as "not a cliff," it turned out the largest remaining gap). The discipline for **both**: check the interpreter's analog and **measure at real rule counts**, not assume. Read the kernel source **for the mechanism, not the expression** (clean-room): the *idea* — index by key, memoize group-fill, **resolve a field once per row** — is reproduced in original Kotlin.

**The honest lesson (the owner's skepticism, confirmed — and it kept paying out):** it is **not** easy to beat the kernel. A second investigation pass (the aggregation / parallel-iteration / calculation-cascade machinery, beyond the six named caches) found **two more silent bugs** the differential fuzz net hadn't generated:
- **Parallel iteration** (two non-nested repeatable groups, the kernel's index-keyed outer join — its *steepest* O(N²) avoidance): the interpreter was **silently wrong** (under-fired, no unsupported report). Reverse-engineered from the source (`ValidationCache.getIterationValuesForGroups`, `IndexFieldCache`, `IIdentifier.UNKNOWN = -5`) + targeted probes. The shapes still declined-loud were all confirmed by probe to be **kernel-invalid models** (`MVK_NO_WILDCARD` for a multi-frame, `MVK_MULTIPLE_INDEX_FIELDS` for an indexed frame, `MVK_NEG_CONDITION_IN_ITERATION` for a negative-over-frame) — so a valid model is never declined.
- **The computation cascade** (a computed field referencing another): the interpreter was **silently wrong** (read the stale operand → wrong value). Now **fixed** — `compute()` orders by dependency and reads prior results via a side-effect-free overlay, matching the kernel.

Across those passes we mirrored the remaining kernel-cache analogs clean-room on the measured common raw-validation paths (semantic index #4/#10, repeatable group fill #6, cold-path build #7, non-repeatable group fill #8, the cascade, and the parallel-iteration outer join), leaving no known quadratic cliff in those specific raw scenarios. That is not a whole-evaluator claim: compute overlay index columns and correlation buckets are now shared per computation step (IF143, was IG60 — the last confirmed compute-side O(rows²) cliff), and legal multi-star equality correlation now uses the bind-depth-scoped hash join (IF144). The broader source audit also found semantic gaps outside these performance cases; [INTERPRETER-GAPS.md](INTERPRETER-GAPS.md) is authoritative. The lesson: a tree-walker is not inherently fast or correct at the edges—you earn both by indexing/ordering exactly where the kernel does, probing which shapes are valid, and failing loudly on anything not yet supported.

## How the kernel's GENERATED code evaluates a rule — and what the interpreter can mimic (2026-06-25)

A deep read of the kernel's **generated Java** validator (dumped for the `manyRules` shapes + an `Or` and a 3-way `And`, via `generateValidationCode(…, JAVA)`) shows *exactly* where its per-operation edge comes from — and confirms the owner's intuition that it's **mimickable with tree-walk techniques, no codegen needed.** (Mechanism described in our own words + stylized pseudocode; the verbatim generated source is not reproduced — license-safe rule.)

**The generated shape — one rule = one method, a two-phase body.** Each rule compiles to a method that iterates its scope and, per row, does:

```
for (row in iter) {                                  // the rule's iteration scope (cached repetitions)
  if ( fieldsGiven(Qty).isKnownAndTrue()             // PHASE 1: short-circuit BOOLEAN guard —
       && compare(GT, num(Qty), num(Amount))         //   Java && / || ; reads only .isKnownAndTrue();
            .isKnownAndTrue() ) {                     //   later operands skipped once firing is decided
    var tb0 = fieldsGiven(Qty);                       // PHASE 2 (only inside the if = only when it FIRES):
    var tb1 = compare(GT, num(Qty), num(Amount));     //   RE-evaluate operands, build the typed results,
    var v   = tb0.combineUND(tb1);                    //   combine (UND for And, ODER for Or) to get polarity
    addMessage(errorField, row, code, v.fehlerType());
  }
}
```

**The two structural differences from our tree-walk** (both confirmed across `And`, `Or`, `Cmp`, `FieldFilled`, `Sum` — the pattern is uniform; only the combine differs per operator: `combineUND` ↔ our `And` type rule, `combineODER` ↔ our `orType`):

| | kernel generated code | interpreter (`Interpreter.firedType` → `evalTypedLazy`) |
|---|---|---|
| **firing decision** | **short-circuits** — `a.isKnownAndTrue() && b…` / `|| ` skips later operands (and *their* whole evaluation) once the result is forced | validation's `firedType` stays strict — `evalTypedLazy` evaluates both branches; compute preconditions use IF85's kernel-exact short-circuiting `evalCond`, and compute-mode fill quantifiers use ordered early-stopping scans |
| **polarity (VALUE/OMISSION)** | computed **only when the rule fires** (the `combineUND/ODER → fehlerType()` is inside the `if`) | computed only for **TRUE nodes** — a non-firing root skips polarity, while a firing row gets truth + polarity in one walk |
| **index/reps** | primitive `long[]` (no boxing) | boxed `List<Int>` keys, but resolved once per path in each `RowContext`; primitive reps are an unproven, trigger-gated candidate |
| **dispatch** | generated straight-line calls (no per-node `when`) | AST re-walk per node — **NOT the lever** (a JFR profile, #64, put the whole eval at ~3–4%; the compiled-node engine that targets this stays unbuilt, twice-rejected) |

**Why this matters for the profiler hotspot.** The profiler put **eval-proper at ~181 ms** (low-firing, the residual after the `formalErrorAt` memo): `ctx.field` + `Val` allocation + the walk **+ the polarity (`leafType`/`fill`)**. The kernel pays the polarity **only on the rare firing rows** and **skips whole operands** via short-circuit; the interpreter *used to* pay polarity on **every** row. In the realistic **low-firing** regime (valid documents — most rules pass) this was pure waste: e.g. `FieldFilled(Qty) And [Qty] > 50` with a small `Qty` evaluates `FieldFilled` (true) then the comparison (false → no fire), and the interpreter *also* computed the comparison's `leafType`/`fill` polarity that is then discarded. **Closed 2026-06-25 (#62)** by the **lazy-polarity single walk** (`evalTypedLazy` — polarity only on TRUE nodes). The validation-rule *short-circuit* half (skip whole operands) remains the kernel's; computation preconditions separately gained kernel-exact short-circuiting in IF85. For this benchmark's `FieldFilled(true) And …` shape there is nothing to short-circuit, so the polarity skip was the lever.

**Per-operand primitive cost is ~equal — it is NOT the lever.** `controller.vergleiche(…)` builds a `ValidierungsErgebnis` (truth **+** `fehlerTyp`, eager — set in its constructor) and `feldWertAlsZahl` returns an allocated decimal — the same order of work as our `evalCmp` + `leafType` + `Val.Num`. So polarity is eager in *both*; the kernel's win is **not** a cheaper leaf, it is **(a) not running the leaf at all when short-circuited, and (b) not combining/typing on non-firing rows.**

**The mimic that was tried — a two-phase tree-walk — REVERTED TWICE, then beaten by a lazy single walk (measured 2026-06-25).** The natural validation-rule mimic is two-phase: Phase 1 a truth-only `evalCond` (no polarity); Phase 2 the typed `evalTyped` **only when fired**. Measured both pre- and post-`placeCache`/`(C)` (bias #5): a noise-free in-run A/B re-rejected it **both** times — pre: +1.16× low-firing / −1.5× high-firing; post-(C): +4% low-firing / −6.5% high-firing. The reason is the **second walk**: the kernel affords its two-phase because Phase-2 (`combineUND`) is cheap *straight-line generated code* over cached leaves; the interpreter's Phase-2 re-**traverses** the AST and re-**evals** the leaves (and would double-invoke a `CustomCondition`), costing more on firing rows than the polarity-skip saves. **The fix is to keep ONE walk but make the polarity LAZY** — `evalTypedLazy` computes a node's type only when its truth is TRUE — which gets the non-firing skip with **no** second walk. Measured faster in **both** regimes; adopted (#62 in the results log). **Lesson:** the kernel's *two-phase structure* is not the validation win — a tree-walk cannot make the second walk cheap; the extractable win is "don't *type* what doesn't fire," and that fits in a single lazy walk. Validation still evaluates both logical operands; computation preconditions use IF85's separate short-circuiting `evalCond` because poisoning makes their read order observable.

**What this means for the real lever.** The against-kernel low-firing sweep (`KernelEdgeTest.ruleCountCrossoverLowFiring`) shows the kernel's per-operation edge is **largest in the realistic valid-document regime** (192 rules: interp/java **≈1.70** low-firing vs ≈1.16 high-firing — the kernel drops far more when rules pass, via short-circuit + no message-building + straight-line). So closing the gap requires **cheaper per-operation eval**, not an eval *restructure*. Potential directions are (a) **compiled/straight-line dispatch** (the Layer-1 sealed-node engine measured ~7% alone, but it is the prerequisite that could also make two-phase worthwhile), (b) a primitive repetition-key representation if a fresh allocation profile earns its correctness risk, and (c) **vectorized columnar eval** for the rows axis. These are profiling candidates, not current gap-ledger commitments; the structural mimic alone is not enough.

**Conclusion at the 2026-06-25 measurement point (refining the owner's assumption).** The experiment showed that mimicking the generated structure (short-circuit + two-phase) was **only potentially worthwhile on top of cheap dispatch**; bolting two phases onto the tree walk regressed the firing-heavy case. Later resolution-cache and allocation work reached and then beat the recorded fair generated-Java ratios without compiled dispatch, unboxed repetition keys, or vectorization. Those mechanisms are therefore profile-earned future options, not the current “path to parity”; a two-phase validation walk should be reconsidered only after a materially cheaper dispatch changes its measured economics.

## Kernel optimizations from SOURCE — mechanism, interpreter analog, and the biases to re-check (2026-06-25)

After the `ValidationCache` mis-triage (I had it in my own table, dismissed it on a wrong verdict, and only the profiler forced the revisit), I stopped reasoning about the kernel's optimizations from memory and **read the runtime + codegen source** (four parallel deep reads: the per-run caches, the short-circuits/pruning, the codegen rule structure + eval primitives, the index/value representation). This records *exactly why and how* each kernel technique works, the interpreter's **true** status (not the assumed one), and — the durable part — **the biases that hid the gaps**. This is iterative: re-read the source and re-run this checklist whenever a new perf problem is learned.

**Correction to a prior mental model (a bias, below): the kernel's value store is itself a `HashMap`, not array-indexed storage.** Its per-row cheapness comes from **memoization (the caches) + iteration pruning**, NOT contiguous arrays. The interpreter's `Map`-keyed `Index` is already kernel-aligned — *don't chase a column-store rewrite*; port the cache/pruning mechanisms that measurements justify, and consider primitive repetition keys only when a fresh profile earns that representation change.

### The biases to re-check (the durable lesson)

Each one already caused, or nearly caused, a mis-triage. Run this list when a new perf problem appears:

1. **Cliff-hunting** — "an O(N²) cliff is the danger; a constant factor isn't." A per-(rule,row) redundancy is a **~rules× constant** that dominates at high rule counts. *(Mis-triaged `ValidationCache`.)* → measure constant factors at real rule counts, not just complexity class.
2. **One-cache-one-analog** — "six kernel caches ⇒ six interpreter analogs." `USBIndexCache` → zero (legacy); `RepetitionNotUnique` → a *better* algorithm. → **match the result/behavior, not the data structure.**
3. **Map-vs-array** — "the kernel is fast because it stores values in arrays." It uses a `HashMap` too; speed = memoization + pruning. → don't rewrite the store; port the caches.
4. **Elegant-single-walk** — the original eager `evalTyped` walk (truth+polarity per node) was *tidy*, which hid that it did the kernel's expensive phase-2 work on every non-firing row. The shipped `evalTypedLazy` single walk closed that waste by typing only TRUE nodes, without paying for a second walk. → tidiness is not the goal; measured laziness is.
5. **Measured-once-settled** — a rejected optimization can become viable after a *related* change. The two-phase was re-measured after `placeCache` changed the cost structure and still lost; record both results, and reopen it only after another material prerequisite such as compiled dispatch changes the calculus. → **re-measure rejected optimizations when the cost structure shifts, then close the question when it does not.**
6. **Cross-run-noise** — a 20% kernel-Java shift between runs hid/faked wins (Layer 1 looked like noise; the placeCache magnitude was confounded). → use the **within-run ratio** (interp/kernel-Java in the same run) or an **in-run A/B toggle**, never cross-build absolutes.
7. **High-firing-benchmark** — the only against-kernel sweep was high-firing (`perfValues`), which hid that the kernel's edge is *largest in the realistic valid-document (low-firing) regime*. → always measure both regimes.
8. **Resolved-on-demand-is-fine** — "lazy per-call resolution is cheap." It's cheap *once*; re-done per accessor per operand per rule per row it's the dominant cost (`placeCache`). → measure the *redundancy*, not the single call.
9. **Allocation-blindness** — counting lookups/dispatch but not the per-op object churn (`Val`+`Fill`+`Res`, boxed reps). The kernel interns results + packs polarity. → count allocations on the hot path.

## Optimization catalog (rationale · implementation · example · results)

The implementations below are shared in **`commonMain`**, so JVM and JS use the same algorithmic structures; that does not by itself prove identical host-library semantics or constants. Decimal and regex host parity have their own IF163/IF164 locks. Caches and prepared artifacts are lazy where stated; non-cache algorithmic rewrites are not meaningfully “lazy.” Node evidence covers the named scenarios only. The numeric IDs are historical landing IDs, so #8 appears before the later-added #7 even though the prose follows the evaluation story.

### 1. Non-quadratic `Document` (the foundation, #28)

- **Rationale.** The general `Document` stored placements in a `List`; every `field`/`filled`/`displayValue`/`star`/`groupFilled` did a linear `firstOrNull{…}` scan, so per-row evaluation was **O(N²)** — 100k rows could not even run (a quadratic JS document blew the 2 s test timeout at 20k).
- **Implementation.** A lazily-built, **mutation-invalidated `Index`** maps `(path, reps) → placement` and `groupPath → rows`; lookups become O(1)/O(rows). Each row's `evaluated` flag is computed in **one amortized pass** over the **content-bearing** placements — `Index.content` = a valued field OR an instantiated repeatable-group row (IF53), so an all-field-empty-but-instantiated repeatable row counts as content exactly as the kernel's `GroupFillCache` does. It stays **one pass, O(document), memoized per group** (the same `content` list also feeds `GroupFilled` on a non-repeatable group and requiredness — one build, three consumers). `autoGroup` dedups via a set, and IF276's V2 predecessor materializer advances one high-water mark per concrete parent scope, so sparse or sequential placement emits every required group row exactly once instead of revisiting `1..n` for each field. `DocumentPlacementsSnapshotTest` locks the work count at 10,001 distinct group emissions for two fields across 10,000 rows. Re-measured 2026-07-06: the earlier content extension is **perf-neutral** — B1 per-row, wide sibling-groups, and the constrained-field formal check all stay linear (~4× growth for 4× rows), gated by `PerfGateTest`.
- **Example.** B1 — a per-row `[Qty] > 50` over N `/Perf/Lines`.
- **Results & discussion.** Linear: **300 000 rows at ~2.5 µs/row**. This is the prerequisite every later optimization builds on — without an O(1) value store, nothing else matters.

### 2. Prepare-once ASTs (lazy parse cache)

- **Rationale.** Before this optimization, every `validateFull` re-parsed each rule's condition—in fact **twice** (`repetitionNotUnique` + `rowOutcomes`). The hypothesis (#31) was that this per-call re-parse caused the many-rules slowdown.
- **Implementation.** A per-rule `lazy {}` (`SYNCHRONIZED`, so the engine is thread-safe to reuse) AST wrapper, built in the constructor **without parsing** (→ fast startup); the first use parses and caches, every later call/row reuses. A single-rule `testRule` forces only the rule it touches.
- **Example.** B6 / `manyRules(N)` in repeated-eval (engine reused over many documents).
- **Results & discussion.** **Honest negative result:** parsing was *not* the bottleneck — the crossover did not move. The value is **startup + hygiene** (it also removed the redundant double-parse). The lesson — *measure before assuming* — is why the next optimization was found by profiling, not guessing.

### 3. Per-group row-context memo

- **Rationale.** `contextsFor`/`attachByDepth` did an **O(valued) attach-depth scan on every rule** (and every nested row). Many rules share a handful of iteration scopes, so this was O(rules × valued) of pure recomputation.
- **Implementation.** Memoize `contextsFor` and `attachByDepth` **per group** inside the `Index` — computed once per distinct scope, reused across all rules. The clean-room analog of the kernel computing the document's row structure once and reusing it.
- **Example.** B6 — 12 rules over ~3 distinct scopes (`/Perf`, `/Perf/Lines`, `…/Subs`).
- **Results & discussion.** **~24 % faster across all rule counts**; crossover vs Groovy moved **~48 → ~96 rules**. This was the first real lever (vs #2's null result).

### 4. Row-prefix index (the semantic-index / star cliff — the steepest)

- **Rationale.** `starRows` did an **O(all-rows) `.filter` per call**; inside per-row iteration (a semantic index `[F For "v"]`, or a cross-level star aggregate) that is **O(rows²)**. Measured genuinely quadratic (growth ×3.5 per doubling, the interpreter's lead collapsing 0.17→0.66 over 500→4000 rows) while the kernel's `IndexFieldCache` stayed linear and **won at scale** — the proof that the kernel's optimization is well-founded.
- **Implementation.** The `Index` indexes each group's rows by **every prefix of their rep tuple** (built once, dropped on mutation); `starRows` is then an O(1) lookup. The clean-room `IndexFieldCache`/row-index analog — the *idea*, in original Kotlin.
- **Example.** A per-row rule `FieldFilled(Amount) And [/Perf/Lines/Amount For "NOMATCH"] > 0` (`PerfCatalog.semanticIndexPerRow`).
- **Results & discussion.** **98 ms → 6.8 ms at 4000 rows**; linear again (growth ~×2/doubling), pulling *ahead* of the kernel (ratioG 0.66→0.04). Guarded against regression by `PerfGateTest.semanticIndexStaysSubQuadratic`. Also fixes any cross-level star aggregate evaluated per row (e.g. a per-Line `Sum(Subs* / Cost)` at scale).

### 5. Single typed walk per row (no double AST walk)

- **Rationale.** `rowOutcomes` called `fires()` (a Tri-only walk via `eval`) **and then** `firedType()` (a typed walk via `evalTyped`) — **two full AST walks on every firing row**. But `evalTyped` already yields the truth value, so the second walk is redundant.
- **Implementation.** Call `firedType()` **once**: non-null ⟺ the rule fires (`truth == TRUE`), and the value *is* the polarity (VALUE/OMISSION). A firing row now costs one walk, not two.
- **Example.** B6 / `manyRules(96)` — 45 480 firing rows, each previously walked twice.
- **Results & discussion.** Crossover vs **kernel-Java reached parity at ~96 rules (ratioJava 0.99)**; the 192-rule gap narrowed **1.30 → 1.19**. The win scales with the firing ratio (no help for all-passing documents — those already walked once).

### 6. O(1) repeatable-group fill

- **Rationale.** `groupFilled`'s repeatable-group branch did `reps in rowsOf(group)` — an **O(rows) `List` membership** — so requiredness over a **sparse-required** document (many empty required fields, each triggering a `GroupFilled` check per row) was **O(rows²)**. The `GroupFillCache` analog (the repeatable half).
- **Implementation.** O(1) membership via the row-prefix index (`rowsWithPrefix(group, reps).isNotEmpty()`).
- **Example.** A form with many empty required fields across N rows (every empty field triggers the per-row group-fill check).
- **Results & discussion.** Removes the latent requiredness O(N²). (The *non-repeatable* `GroupFilled` branch was the sibling — now fixed too, #8.)

### 8. O(1) non-repeatable group fill

- **Rationale.** `groupFilled`'s non-repeatable-group branch scanned `index().valued` and tested each descendant's scope — **O(valued) per call** → O(rows × valued) when a model has `GroupFilled(nonRepeatableGroup)` checks per row. The other half of the `GroupFillCache` analog (#6 did the repeatable half). It looked hard because the scope depth varies with the rule's iteration group.
- **Implementation.** A per-`(groupPath, group)` **attach-depth index** over the valued *descendants* of `groupPath` — exactly the `attachByDepth`/`contextsFor` shape (group descendants by their `commonPrefixLen(p.path, group)` depth, store the prefix set), memoized in the `Index`. `groupFilled` then checks `rowReps.take(d)` against the set at each depth — O(1) per call after a once-per-`(groupPath, group)` build. It mirrors the old per-descendant scope check exactly, so behavior is unchanged (the dead `inScope` helper was removed).
- **Example.** A per-row rule `GroupFilled(SomeNonRepeatableGroup) And …` over a large document.
- **Results & discussion.** The non-repeatable `GroupFilled` path is now O(1)/call — no O(N²) left in either `groupFilled` branch. Full `:adapter` differential suite green (`GroupFilledDiffTest` + the requiredness/index-field law tests confirm behavior unchanged). With this, **no known O(N²) cliff remains in the group-fill/raw-validation paths** (the row-prefix index #4, the repeatable-fill #6, and this close out those kernel-cache analogs). Compute-overlay indexed columns and correlation buckets are now cached per computation step too (IF143, was IG60); the multi-star equality-correlation path graduated with its bind-depth-scoped hash join (IF144).

### 7. Linear index build (the cold-path / startup / JS cliff the warm harness never saw)

- **Rationale.** The `Index` build deduped group rows with `if (p.reps !in it) it.add(p.reps)` — an **O(rows) `List` membership per group placement → O(N²) to build the index**. The against-kernel harness *never saw it* (it measures **warm**, after the index is built once outside the timed region), so it hid behind that methodology — but **every COLD first `validateFull` pays it**: startup, the CLI one-shot path, and a single JS pass. It was the real reason a JS run blew up at scale (cold JVM @20k = 1.75 s; **JS @20k = 14 s**, super-linear).
- **Implementation.** Drop the check entirely: every group placement is **already unique** by `(path, reps)` because both `group()` and `autoGroup()` gate on the `instantiatedGroups` set before adding — so the `!in` scan was redundant *and* quadratic. A plain `add` makes the build O(N).
- **Example.** Any cold/first evaluation at scale — `DmInterpreter(model).validateFull(bigDoc)` on a fresh document; the CLI evaluating one large document; the JS `DocumentScaleTest`.
- **Results & discussion.** Cold build is **linear**: JVM @30k = 152–220 ms (was ~1.75 s at *20k*); **JS @10k = ~60–106 ms (was >2 s — it timed out)**. This is the **biggest win for startup and for JS**, both of which only ever run the cold path. The JS scaling guard (`DocumentScaleTest`) rose from 3k → **10k** (a scale that was *impossible* on JS before). A worked lesson in benchmark methodology: a warm against-kernel harness is right for steady-state but **blind to one-shot/startup cost** — measure the cold path separately (that is what `PerfScalingTest.startupCost` and the JS `DocumentScaleTest` now do).

### 9. Indexed `$` self-correlation (hash and ordered plans — IF47/IF159, 2026-07-06/2026-07-20)

- **Rationale.** A `$` outer-correlated filtered quantifier — `AtLeastOneFieldFilled(../G* / F Having [X] == [$X] …)` — is a **self-join**: for each of N outer rows, the naive strategy scans all N inner rows to find matches → **O(N²)**. Equality was the first hot shape; RV-2026-07-20-03 showed that treating a single ordering comparator as inherently pairwise was equally unsound.
- **Implementation.** `CorrelationJoin` recognizes a closed indexable boundary. Equality conjunctions use a **value-keyed bucket map** built once per `(group, scope)`, O(N) build + O(1) lookup. A single comparable field-to-outer-field `<`, `<=`, `>`, `>=`, or applicable `!=` uses a cached sorted distinct-value table with prefix `(t, f, n)` sums, O(N log N) build + O(log N) lookup. Both plans subtract the physical outer row when the `CurrentRepetition` self-exclusion applies and retain Unknown in neither truth bucket while preserving row count. Compound predicates, expression operands, unsupported kinds/non-UTC datetime ordering, and multi-star multi-row self-exclusion stay on the explicit general scan; they are fallback boundaries, not evidence that slowness is acceptable.
- **Example.** A rule iterating N `/Order/Items` rows, each firing on "another row shares this row's `Count`".
- **Results & discussion.** Equality evidence from 2026-07-06 remains ≈3.0 ms vs generated Java ≈8.8 ms at 400 rows and ≈6.3 ms vs ≈30 ms at 1600 rows. The 2026-07-20 all-equal `>` discriminator changed from ≈15.7× growth to 4.1× (2.2 ms@400 → 8.4 ms@1600) after the ordered plan. `OuterCorrelationPerfTest` checks complete interpreter/dynamic-Groovy/generated-Java signatures on those exact N/4N instances before timing. Its shared `<9×` ceiling remains only the executable NFR catastrophe floor; both kernel curves are recorded, and a repeatable ratio loss or worse interpreter curve remains a development defect. `OrderedOuterCorrelationDiffTest` locks all six comparisons, both fill-quantifier polarities, duplicates/boundaries, all-equal/no-witness, self-exclusion, and malformed/empty 3VL. `CorrelationPlanDispatchTest` locks the indexed/fallback boundary; IF144 separately locks legal multi-star equality forms. None of this promotes a candidate NFR number.

Partial validation never enters either correlation plan for a rule containing `Having`: the pinned kernel's codegen skips that whole rule at method entry. The interpreter records the filter fact in the model-static prepared plan and performs one O(1) branch before row-context or correlation-cache work (IF202). Full-validation correlation complexity and caches are unchanged.

### 10. Shared output projection for dense `RepetitionNotUnique` messages (IF191, 2026-07-21)

- **Rationale.** An all-duplicate N-row RNU rule legitimately returns N messages carrying N peer references each. The logical result is output-sized O(N²), but allocating and formatting N independent copies of the identical peer list is not required by that contract.
- **Implementation.** The call-scoped RNU cache formats and de-duplicates one immutable peer-pointer list per duplicate cluster. Row outcomes share it; a message with additional current-row references exposes a constant-size immutable joined view rather than copying the cluster. Canonical pointer strings live in the document's mutation-invalidated derived index and are reused by every message/formal path during the immutable validation call.
- **Results & discussion.** On the exact compact synthesized profile at N=100/400 (490/1,800 firings), interpreter medians were 16.85/27.28 ms versus dynamic Groovy 55.25/302.17 ms and generated Java 37.98/318.26 ms. Exact growth was 1.62× versus 5.47×/8.38×; the separate paired interpreter estimate was 3.95×. The same model, documents, fixed clock, custom callback, 12 warmups, complete outcomes, and both kernel strategies were used. This is same-run diagnostic evidence, not an IF137 promotion.

### 10. Document-level index-column state (IF116, 2026-07-10)

- **Rationale.** The IF107/IF115 indexed-read gates — and the older IF15/IF60 index-aware aggregate/quantifier classification — consulted the index column per LOOKUP: a fresh `starCells` list plus a fresh duplicate-value set per call. A `validateFull` over a per-row indexed rule therefore scanned the whole column once per row — **O(rows²)** with a heavy allocation constant. The gate's `semanticIndexStaysSubQuadratic` (N=20 000) deterministically stalled 20+ minutes; the master gate's independent perf re-run caught it (the drill session's own gate run predated IF115's wiring of the guard into the validation hot path — the lesson: a perf claim is only as fresh as the last hot-path commit it covers).
- **Implementation.** `EvalContext.indexColumn(path, bindDepth)` returns the raw `IndexColumn`: cells, duplicated values, and derived flags/tally, memoized per (column, star-scope prefix) at the document level. `Interpreter.indexColumnOf` is the complete call seam: when relevance or registered custom admission matters, it scans the identity-preserving raw cells once, applies relevance first and formal admission second, and memoizes the admission-aware typed column for the call. Validation shares it for the pass. Compute supplies a per-step memo shared across outer rows; the overlay bypasses only its own write column because that column changes as values land. Every indexed read, aggregate/fill classifier, and starred value-list expansion consumes this seam, so correctness did not reopen the O(rows²) scan.
- **Example.** A rule iterating N rows, each reading `[Price For CustomerClass]` against the same N-cell index column.
- **Results & discussion.** Semantic-index growth back in the linear band: 19.0 ms@5000 → 76.6 ms@20000, min-growth **4.03×** (pre-fix: unbounded — the N=20 000 arm alone ran 20+ minutes). All twelve growth checks 2.7–4.3× (linear ≈ 4). Correctness pinned unchanged by the six index differentials + the full suites — the fix is pure memoization.

### JS performance — one code path, so every optimization carries (2026-06-24)

## The harness (invest here — it pays off)

Not ad-hoc `measureTime` calls sprinkled in tests — a **proper, reusable harness**, because it does double duty: it **gates** regressions *and* it's how we **find** the O(N²) hotspots in the group machinery. Design:

- **`PerfScenario`** — the unit: a real DM-JSON model + an **instance generator parameterized by scale `N`** (build 1k/10k/100k rows *programmatically*, never commit giant fixtures) + the operation (`validateFull` / `compute`) + the correctness oracle. One scenario, run by both engines.
- **Three engine adapters behind one interface** — `InterpreterEngine` (`DmInterpreter`), `KernelEngine` (Groovy via `RuntimeLaws` → `IDocumentRtService`), and `JavaKernelEngine` (the fair generated-Java baseline). The harness lives in `:adapter` (the only module with the kernel), mirroring the `laws/` differential layout, under `…/perf/`.
- **Warm-measurement discipline** — per (scenario, N): **warm up** (discard JIT-warming iterations), then time `K` iterations; report **median** (robust) + min + p90, and the **ratio** `interp_median / kernel_median`. Never mix a cold sample into this warm-throughput result; NFR-S uses the separate fresh-process protocol above.
- **Correctness first** — assert `interp == kernel` on the scenario *before* trusting any timing (a fast-but-wrong path is not a win; reuse the differential comparison). The comparison is the fired-code **multiset** (a sorted `List`, not a `Set`), so a per-row firing-count mismatch is caught, not just a missing code.
- **Three run modes** — (1) **gate mode**: single document, loose bounds, CI-friendly, fails on a catastrophic/relative regression; (2) **repeated-eval mode**: the engine built once, M slightly-different documents looped (form-input / batch) — the reuse pattern the kernel's codegen + per-run caches are tuned for, reported per-eval; (3) **profile mode**: one scenario at high `N`, interpreter-only, verbose per-iteration stats, no assert — diagnostic hotspot evidence only, never comparative acceptance proof.
- **JVM tool choice** — start with this **custom integration harness** (whole-document evaluation is the real unit; warmup+repeats+median+ratio is the right rigor for it). Reserve **JMH** for a *specific hot inner loop* (e.g. `repsFor`/`starRows`) that needs sub-method attribution — add it only when a profile points there, not upfront.
- **JS throughput** — a Node-runnable large-`N` check on `jsTest` (the same `Document`, `measureTime`, no kernel) provides platform diagnostic evidence; without both kernel strategies it cannot prove the comparative acceptance target.
- **Output + baselines** — print a `scenario × N × interp_ms × kernel_ms × ratio` table and append machine-tagged baselines to the results log (below). The spec holds the method; the log holds the numbers.

**Built (2026-06-23, extended through 2026-07-21):** `adapter/src/test/.../perf/` — `PerfHarness` (the `PlacementSink`-driven scenario + a `PerfOp{VALIDATE,COMPUTE}` + the three engine adapters `Interpreter`/`Kernel`(Groovy)/`KernelJava` behind `PerfEngine`/`ReusableEngine` + `measure`/`runScenario`/`runRepeated`/`timeInterpreter`), `PerfCatalog` (single-sourced `perf.dm.json`, the current B-series scenarios including B9 Berlin, a parameterized `manyRules(count)`, and a fuzz scenario), `PerfGateTest`, `PerfBenchTest`, `KernelEdgeTest`, `PerfScalingTest`, and `PerfProfileTest`. `RuntimeLaws` is the shared kernel oracle; its build-once `KernelEngine` (Groovy) and `JavaKernelEngine` (the kernel's own validator compiled as Java—the Groovy-tax-free baseline) both expose fired/compute outcomes. `PerfRuntimeBindings` derives equivalent interpreter/kernel clocks and callbacks from one immutable source and fingerprints their stable contract ids. `pairedScenarioGrowth` tri-checks exact N/4N instances and applies the paired estimator to all three engines, failing on an interpreter loss at either scale, on a higher interpreter **per-unit cost** than either kernel strategy (`PairedAcceptance`), or on the interpreter's **own** CPU-clock N/4N growth reaching the catastrophe floor (IF279). `KernelJavaBaselineDiffTest` guards that the Java baseline fires identically to Groovy. Codegen is primed out of every timed region (non-negotiable #2). IF172 adds the structured local JVM/Node/native first-answer, warm-throughput, and fair-Java evidence lane. It remains manual evidence; `scripts/perf.sh gate` is the isolated nightly/manual catastrophe and regression lane.

Profile-derived nested models use `SeedGenerator.populateExactLeafRows` for their `N`/`4N` axis. The method reaches the exact target cardinality by distributing quota over the selected group's repeatable ancestor chain within every per-parent declared cap; unrelated repeatables stay at a small explicit default. It refuses an impossible scale before mutating either engine's sink, so the benchmark cannot silently time an underfilled model or kernel-illegal excess rows merely because no individual group cap reaches `N`. ## Architecture direction (owner hint, 2026-06-23 — keep in mind)

A structural optimization to design toward (not yet committed work):

- **Decouple eval from a hierarchy — a flat, indexed instance is enough.** The validate/compute API only ever asks "the value for `(path, repetition-indices)`", so the instance backing store can be a **flat `(path, reps) → value` map**, not a tree (this *is* the task-#28 index, promoted to the primary representation). Group membership and iteration scopes come from the **model** (stable), not from walking an instance tree.
- **Prepare the model once; reuse across runs—and prove the boundary deterministically.** `ParsedModel` parses each stored rule/computation lazily once per MODEL (owned by `PreparedModel` via `ModelStaticPlans`, IF251); `PreparedModel` reuses the resulting rule/computation plans; IF164's engine-owned registry compiles each distinct condition/declared/predefined/computation pattern once; and the whole-model dependency order plus each requested computed field's transitive closure are cached per model (IF251). `PreparationWorkCounterTest` locks the exact JVM+Node work classes and proves that different documents and repeated `validate`/`compute`/`computeField` calls add no model-static work (IF171). Date-format preparation remains owned by its semantic feature work rather than being inferred from this structural counter. Shape: `val engine = DmInterpreter(model)` built once → loop `engine.validate(document)` / `engine.compute(document)`.
- **The caching boundary is ownership, not “value-independent only.”** Model-invariant artifacts (parsed ASTs, scopes, field metadata, dependency order) may live on the engine. Value- and structure-dependent indices/results are also encouraged when they accelerate evaluation, but they belong on the `Document`/its mutation-invalidated index, one validation call, or one row and must be discarded or invalidated with that owner. Never reuse a value-dependent result across a changed document. Fixed (IF142): `rowContextsCache` and `correlationBucketCache` are cleared with `cachedIndex` by one invalidation method on `Document.add`.
- **Open question (deferred):** between runs, do only *values* change, or also the set of repetition *rows* (add/remove)? If values-only, the structure index is reusable too; if rows change, rebuild the value store per run and reuse only the prepared model (the safe default). Decide when this is picked up — profile first.
- **Beyond prepare-once — Excel-style *incremental* recalc (deferred, trigger-gated):** recompute only a changed cell's dependent closure instead of re-running the whole document. Feasibility + the DEFER decision + the two-part re-open trigger are recorded in the archived [INCREMENTAL-EVAL-PROPOSAL](archived/INCREMENTAL-EVAL-PROPOSAL.md). The prepared model above is its prerequisite substrate; the incumbent kernel does recompute-all-per-run + per-run caches, *not* cross-edit dirty propagation.
- **Study the kernel's data representation + caches for INSPIRATION (not a copy — the license boundary holds: read for comprehension, write original).** The kernel devs spent *years* optimizing; its instance representation and its caches — `IndexFieldCache`, `ValidationCache`, `CalculationCache`, `GroupFillCache`, `RepetitionNotUniqueErrorCache` — encode hard-won structure (index-by-field, memoized group-fill, cached calculation results within a run). **Do not assume a naive fresh impl will be anywhere near kernel performance.** Get informed by what they cache and how they index, reproduce the *idea* in original Kotlin, and let the against-kernel benchmark (#29) tell the truth. Humility + measurement, not confidence.

## The regression gate (mechanics)

- **Home:** `adapter/src/test/.../perf/` (has the kernel; mirrors the `laws/` differential layout). Not in `:interpreter` (kernel-free) and not in the cold-agent surfaces.
- **Two tiers (split 2026-07-10).** `PerfGateTest` (`scripts/perf.sh gate`) is the **routine maintainer landing gate**: the interpreter-only **sub-quadratic growth guards** + the against-kernel correctness canaries (`complexRealWorldAgreesWithKernel` on the full construct mix, `computeOverlayAgreesWithKernel` on the compute-overlay views — each correctness + a ratio on a reduced model whose codegen is fast). IF275 adds paired Number-index validation and computation rows because the older String-index scenarios could not measure canonical decimal projection; those rows require exact tri-engine results and an interpreter win against both kernel strategies at fixed sizes, with growth only as a secondary catastrophe check. The complete expanded gate measured 3m59s on 2026-08-09 Apple Silicon, under the ~10-minute agent-harness background cap that motivated the split. Push/PR CI does **not** run it; the dedicated `nightly-performance.yml` workflow invokes this exact launcher nightly and on `workflow_dispatch`, without repeating deterministic correctness/fuzz/demo gates. The launcher targets the single-fork `:adapter:perfGateTest`; that task always runs and is excluded from the Gradle build cache, while compilation and dependencies remain reusable. The isolation is semantic, not merely faster: `:adapter:test -PrunPerf` includes unrelated perf classes and can schedule them on parallel forks while a gate observes its small/large pair, so it is a manual all-perf sweep rather than a valid routine-gate invocation. `PerfBenchTest` (`scripts/perf.sh bench`) holds the **kernel-ratio benchmark sweeps**: the closed B1–B8 set, the B9 Europe/Berlin + UTC pair, compute/tiered/parallel, and repeated-eval. Each included catalog row performs dynamic-Groovy and every proven-applicable generated-Java evaluation plus complete semantic agreement before timing; inability to exercise an applicable strategy is a harness gap, not a passing exclusion. Run the tier at perf-relevant checkpoints (a hot-path change, a release). Shared trips live in `PerfBounds` so the tiers can't drift. `gate` accepts a method pattern (`scripts/perf.sh gate 'semanticIndex*'`); `bench` accepts one exact inventory id (`scripts/perf.sh bench B9-berlin-datetime`) and fails on an unknown id.
- **Build BOTH engines once, and check that each side pays the SAME setup (IF255, 2026-08-08).** The `PerfHarness` engines already do this; a guard written *outside* it must not use a convenience helper as its timed baseline. `RuntimeLaws.messagesPart`/`messages`/`compute(String, Doc)` now reuse a bounded engine keyed by exact model JSON, but still reconstruct and convert the V1 document on every invocation. Use the explicit `RuntimeLaws.kernelEngine(...)` seam with one prepared instance (`validationMessageCount`, `computationCount`, `computeAndApply`, `partialMessageCount`) when the interpreter also reuses its prepared document. Before the shared engine cache, the convenience path additionally expanded the model and constructed both service factories per call, inflating a real 7.17× into a reported 19.57×. The test to apply is not "is the timed region small" but "does each side pay the same setup": per-call work the interpreter also repeats, such as relevant-pointer conversion against its own per-call relevant-set indexing, belongs *inside* the clock because symmetry is what makes the ratio mean anything.
- **Entry-point coverage reconciles two DERIVED sets, not a list (IF254/IF263, 2026-08-08).** `PerfOp` models `validate` and `compute` only, so the scenario sweep cannot reach the other six `DmInterpreter` methods that evaluate over a `Document`; four of them had no timing test at all until this was measured. `InterpreterPerfCoverageTest` reflects those entry points and independently derives coverage from `@TimesInterpreterEntryPoint` on JUnit-discovered, perf-tagged timing tests. Exact typed signatures must match. There is no separate class/method pointer to drift after a test rename, and the coverage question remains untagged so it is answered on every build rather than only under `-PrunPerf`. `EntryPointPerfTest` carries the four (`testRule`, `evalCandidate`, `computeField`, `applyComputations`) against the reviewed one-rule B1 and one-computation B7 scenarios, where the kernel's whole-document call is exactly the slice the entry point computes; that one-construct property is asserted rather than assumed. Adding an entry point without a guard is now a build failure, which is the point: the estate grew a guard per incident, and an entry point that never had an incident never acquired one.
- **`PerfBounds.MIN_KERNEL_ADVANTAGE` (1.5) is a conservative FLOOR, not a target (owner, 2026-08-07) — higher is always better.** The entry-point guards trip below it via `KernelAdvantage`. It **supersedes nothing and must never be used to relax a stricter limit**: the standing development acceptance rule above still requires beating *both* kernel strategies at every scale with a per-unit cost no higher than either (IF279), and `PerfHarness.requireInterpreterBeatsBoth` plus `PairedAcceptance` enforce those two on the comparison path. Two precisions that are easy to lose. **(a) Strategy:** these guards drive `RuntimeLaws.kernelEngine`, so the floor is against *dynamic Groovy* alone and says nothing on its own about the faster generated-Java strategy. **(b) Headroom is not slack:** the guarded entries measure 3.2×–16×, so a fall to 1.6× would clear the floor and still be an active defect under the standing rule. ### Checkpoint 2026-08-08 — the façade's quadratic allocation, and why a timing guard missed it (IF256)

The public `Interpreter` façade copied a pointer list the engine had deliberately **shared** across the findings of a dense `RepetitionNotUnique` cluster ([IF191](INTERPRETER-FINDINGS.md#if191)), so one N-element list was copied N times. Fixed by removing the copy: the engine publishes an immutable snapshot and the façade recognizes it ([IF261](INTERPRETER-FINDINGS.md#if261)).

**The first remedy was a one-slot-per-channel reuse cache, and it was a bound asserted rather than measured** — it held for a single cluster and missed on *every* message of two interleaved ones, restoring the full quadratic. Nothing bounds how many duplicate clusters a document interleaves, so no slot count was defensible; enlarging it would only have moved the discriminator. **When a fix depends on a cache hitting, ask what makes it miss before asking how big it should be** — here the answer was to make the invariant a property of the value instead.

**Do not use a timing guard for an allocation defect.** Measured with the defect fully present: 500→2,000 rows grew **2.68×**, and 1,000→4,000 grew **3.80×** against a 5.4× trip line — both green. At 8,000 rows the façade produced ~64 million pointer references and killed the test JVM with `OutOfMemoryError`. `arraycopy` is cheap, so N² copies barely register on a clock while being fatal to the heap; worse, any growth guard tuned to a scale that *fits* in memory necessarily sits in the range where the defect is invisible. The guard therefore asserts the invariant directly — findings the engine gave the same list must share one list — at 40 rows, with no clock. **When the suspected cost is allocation, assert the allocation property, not a time ratio.**

### Checkpoint 2026-08-08 — partial validation repaired, and a harness that was charging the kernel twice (IF255)

**Partial validation, `SumOfProducts` under a complete concrete enumeration** (`laws/PartialSumOfProductsPerfTest`, Apple M1): **5.40×** the kernel at 250 rows, **7.17×** at 1000, growth **3.92×** for 4× rows. The path had been quadratic for its whole existence and was measured at parity with the kernel before the fix.

**The number this replaces was inflated ~2.7×, and the cause is a reusable trap.** At the time of the measurement, `RuntimeLaws.messagesPart` expanded the model, constructed both service factories, and converted V1→V2 **inside every call**, while the interpreter reused its prepared model, so each iteration charged the kernel a whole engine construction. It reported 19.57× at 1000 rows. The helper now reuses a bounded exact-model engine, but it still reconstructs the document per call and therefore remains the wrong timed baseline when the interpreter reuses a prepared document. The rule this yields: **a comparison must build BOTH engines once, and the reviewer's question is not "is the timed region small" but "does each side pay the same setup".** `RuntimeLaws.KernelEngine.partialMessageCount` is the build-once seam; relevant-pointer conversion deliberately stays inside the clock because the interpreter re-indexes its own relevant set per call, so paying it on both sides is what makes the comparison symmetric rather than merely fast.

**The published sweep figures are NOT affected, and this is the basis rather than an assurance.** Every headline number in the READMEs and the release notes — 2.1×–12.5× across the default inventory, 10×–16.7× repeated, 1.32× at the hostile point, ~155× on the huge-document edge — comes from `PerfBenchTest`/`KernelEdgeTest` via `KernelPerfEngine`, which calls `RuntimeLaws.kernelEngine(...)` **once per scenario** outside every timed region. The defect was confined to the one partial-validation guard, and no published surface cites a partial-validation ratio. The 2026-08-03 sweep also remains current on its own terms: the IF255 gates exist only on the `validatePart` path, so full validation and compute are untouched by them.

**Cost of the correctness repair.** Deciding completeness per iteration row costs a row-keyed memo: partial validation at 1000 rows moved from ~10 ms to ~15 ms while staying linear. Exactness is not traded for speed, and a linear path several times the kernel has the headroom.

**Read the ratios above as single-run snapshots, not constants.** A re-measurement on the same machine returned 4.79× / 10.00× / growth 3.17× against the 5.40× / 7.17× / 3.92× recorded here. The conclusion — linear, and several times the kernel — is what the guard asserts and what survives re-running; the individual figures move by tens of percent between runs and no published surface should quote one as a bar.

### Checkpoint 2026-08-08 — the completeness gate rebuilt as a union cover, still linear (IF259/IF260)

A second review of the IF255/IF257 repair found both gates still wrong: completeness was decided **per wildcard pattern** (suppressing a relevant set whose union is complete), and the shared row-scoping helper bound a **multi-star** operand at the path's deepest repeatable level instead of its first star, firing on rows the caller had never made relevant. Both are correctness defects; the interest here is that the fix for the first is an algorithm, not a predicate.

Completeness now takes the cover over the union of every addressing entity — each becomes a box over the levels the star iterates, and the boxes must cover the full cross-product. Recursing on the *wildcarding* boxes first is what keeps it cheap: when they alone cover the remaining levels every index is covered and no per-index descent happens, and otherwise the descent is bounded by the concrete indices actually present rather than by the declared repetition counts. So the enumerate-every-row shape — the one that made the relevant set grow with the document — stays linear in the entity count.

**Measured after the change** (`laws/PartialSumOfProductsPerfTest`, Apple M1, isolated single-class run): 250 rows **5.25×** the kernel, 1000 rows **9.41×**, growth **3.26×** for 4× rows against a linear ≈4. A strictly more general cover, and no worse than the per-pattern predicate it replaced.

### Checkpoint 2026-07-22 — IG101 resolved: depth per-row favours the interpreter (no crossover) (IF205)

The G52 depth "growth-ratio loss" above prompted a clean full-warmup sweep to large N to settle whether it is a real per-row defect (which would imply a crossover where a kernel strategy overtakes) or a metric artifact. **It is an artifact — IG101 is closed (IF205), no redesign.** Clean depth/validate, warmup 12, Apple Silicon, one run:

|---:|---:|---:|---:|---:|---:|
