# Interpreter non-functional performance — startup, throughput, relative footprint

The `:interpreter` must have **low first-answer latency**, be **fast on the hard cases**, and keep a **low relative footprint** without giving up the caches that make it fast. These are measured requirements, not hopes. This document is the single detailed source of truth for performance development acceptance, benchmark eligibility, measurement, engineering constraints, the catalog, and verification status; the dated evidence is its other half, [INTERPRETER-PERFORMANCE-RESULTS.md](INTERPRETER-PERFORMANCE-RESULTS.md), split out 2026-08-15. [INTERPRETER-SPEC.md](INTERPRETER-SPEC.md) “Non-functional contract” separately owns the numerical candidates and, after per-number certification (IF137), the ratified release bars; [`interpreter/CLAUDE.md`](../interpreter/CLAUDE.md) carries only the auto-loaded guard summary. A number in the results log is evidence, not a product decision or a substitute for the contract.

## Performance contract

**NFR #1's standing anchor — graduated here 2026-09-18 from the portable-consistency proposal, which is archived.** <a id="nfr1-standing-anchor"></a> That proposal ranked "the interpreter's performance is never compromised" above every checker goal, including H5's own budgets, on the ground that the interpreter is a shipped product and a checker gain never pays for an interpreter loss. Its operative rule: against the fixed restart baseline `c8e3b99795fe9c2ce3e9db32632a6dd8f6537043`, **no comparable interpreter measurement row may regress by more than 5 %**, the allowance applying **per row with no compensation between rows**, and **missing or inconclusive evidence fails rather than passes**. H4's row set is the interpreter-only-use collectors — `interpreterPerformance`, `performanceJvmThroughput`, `performanceAggregateReport`, `interpreterFootprint`, `footprintJvmFork*`, `footprintAggregateReport`, `verifyInterpreterPerformanceClaims`, `syncInterpreterBrowserSize`, and the adapter's `perfGateTest`, `performanceEligibilityTest`, `interpreterNativePerformance`.

**At the proposal's final gate that rule CONVERTS into a permanent bar rather than expiring, and the reason is measured rather than cautious.** The estate's permanent bars cannot see it: nothing fails on a uniform constant-factor regression below **~1.65×** and most bars need 10×–1000× (the blind-band paragraph below), so "the permanent gates take over" is not an available reading — two migration phases at +4.9 % per row would satisfy every checkpoint and then sit permanently inside a band no existing gate can detect.

**Instantiated 2026-09-18, for the DETERMINISTIC byte rows.** The baseline was *measured* at `c8e3b997` — a detached checkout of that commit in a separate clone, each captured record verified against its own `commit` field — rather than anchored on today's values, because the proposal treats measuring the baseline as the reading that needs no owner decision and re-basing as the one that does. The artifact is [`adapter/src/test/resources/perf/nfr1-standing-anchor.json`](../adapter/src/test/resources/perf/nfr1-standing-anchor.json): **66 rows** — 24 JVM-heap, 24 Node-heap, 18 delivered-size — each the baseline's own median, held at +5 % per row with no compensation between rows. `:adapter:verifyNfr1StandingAnchor` is the enforcement locus, and [`scripts/interpreter-footprint.sh`](../scripts/interpreter-footprint.sh) invokes it after the forks, **only at the anchor's own scale set** — the lane's base-N is the operator's to choose, so judging an exploratory run against a baseline captured at other scales would report every row as both missing and unknown, which is true and useless. It fails on a breach, on a row the anchor holds that the run did not produce, and on a row the run produced that the anchor has no baseline for; the last two because NFR #1 says missing evidence fails, and because a renamed scenario otherwise stops matching its baseline and starts matching nothing at all, which reads exactly like a pass.

**Whether to RE-BASE it is the owner's call, and the criteria live here because the proposal that reserved them is archived (decided 2026-09-21: hold at `c8e3b997`).** A re-base is legitimate when a row's quantity changed identity rather than its cost. The Node major moving under the Kotlin/JS toolchain is the case nobody chooses, and there the `capture` block below makes the gate refuse the run as incomparable rather than misreport it, so the remedy is a re-capture under the new major. An accepted feature cost is the other, and then only the affected rows move, each carrying its reason beside it. What never justifies one is the bar getting tight — that is the bar working. The asymmetry is why it is reserved at all: each re-base permanently forgives up to 5 % per row and resets the accumulated drift, and the blind band above means no other gate in the estate can see the difference, so two quiet re-bases are a ~10 % regression nothing ever reported.

**And it refuses an incomparable run before comparing any number.** A heap median is not a property of the code alone — it moves with warmup, repetition count, scale set, heap size, GC method, allocation instrument and runtime major — so the anchor's `capture` block pins the conditions each baseline median was taken under, and the gate reports the field that differs instead of dividing two different quantities into a percentage. The carrier worth naming is the **Node major**, because nobody chooses it: the Kotlin/JS toolchain downloads its own runtime into the isolated Gradle home (`node-v22.0.0-darwin-arm64` on 2026-09-19, which is what the baseline recorded), so a Kotlin plugin upgrade would move every Node heap row with no interpreter source change — and a regression hunt would start in the interpreter and find nothing. The comparison is **family + major, never patch-exact**, for the same measured reason the JDK pin is: a patch-exact rule reddens on every Temurin bump for a difference that moves nothing.

**What the BYTE anchor deliberately does not cover, and why that is a measurement rather than a shortcut.** H4's row set also names the timed and native collectors, and a 5 % bar cannot be carried on the gate lanes — **measured 2026-09-19**, over the 30 committed run files on one machine: 66 observation keys appear in three or more distinct runs and **all 66 already spread more than 5 % run-to-run**, the quantity being *worst-against-median* (`max/median − 1` per key) at **28.5 % for the median key and 173.2 % for the worst**, re-derived at `f5905bf9a`. H4's own wording licenses leaving them out, since it bars regression in a *comparable* row and refuses inconclusive evidence. **Two ways of rescuing them were then measured and both fail, so neither is worth retrying.** Filtering the corpus on `gcCountInWindow` halves the eligible keys and leaves the spread where it was — 0 of 66 become gateable at any threshold — and raising the per-side sample count is worse than it looks: a bootstrap of the null ratio over each key's own 17–26 runs puts the median upper bound at +40.7 % / +26.3 % / +21.0 % / +14.7 % / +9.8 % / +7.1 % for n = 1 / 3 / 5 / 10 / 20 / 40, so **at forty processes per side 48 of the 66 keys still cannot carry 5 %**. Their `1.665×` anchor is therefore not a tolerance anyone chose; it is the resolution the instrument has. Meanwhile NFR #1 is also carried by `:adapter:interpreterMeasurementCurrencyGuardTest`, which refuses interpreter production source that outruns the last recorded measurement. This includes `shared-regex/src/commonMain`, compiled into the interpreter by its build configuration. `InterpreterMeasurementCurrencyGuardTest.sharedProductionSourceInvalidatesMeasurementButTestSourceDoesNot` proves that a shared production-only commit invalidates currency while a shared test-only commit does not; currency alone does not qualify performance.

**So the timed rows' ALGORITHMIC half is gated deterministically instead, by counting the work rather than timing it (2026-09-19).** The blind band exists because a clock's noise is larger than the bar; a count has no noise, so it is barred at zero instead of five. `WorkLedger` is an internal, null-branch seam on the evaluation path that tallies three quantities per call — condition nodes, value-expression nodes, and validation rule-row instantiations — and `WorkLedgerGuardTest` holds every footprint scenario to an **exact per-row constant** at three scales. Those constants are integers in the low single digits, so the smallest regression that can exist at all, one extra node per row, is a third of the smallest row's work: there is no sub-threshold band left to hide in, which is the property the 5 % clock bar could not give. It runs in `commonTest`, so JVM and Node are held to the same integers and a carrier-specific divergence fails there too, and it needs **no baseline capture at `c8e3b997`** — a per-row constant is arithmetic, not a remembered value, so nothing here re-bases anything. What a count cannot see is cost per unit: identical work in more cycles moves nothing. Allocation is the estate's instrument for that half and is already anchored above, so the residue uncovered by both is same-work-same-allocation-more-cycles.

**Standing development acceptance rule (owner-strengthened 2026-07-21; scaling clause corrected 2026-08-11, IF279).** For every protocol-valid comparable scenario and every tested scale, the interpreter must have a lower evaluation median than both dynamic-Groovy and generated-Java, and its measured **per-unit cost** must be no higher than either kernel strategy's. Any repeatable ratio at or above `1.0`, or any repeatable per-unit loss, is an active performance defect and takes priority over expanding the benchmark estate. The scaling clause used to read "its measured growth factor must be no worse than either kernel strategy", which is **not** a satisfiable requirement: for an engine that is linear over the step the measured N/4N factor is `4 - 3f` in the fixed cost's share `f` of the small-scale reading, so it ranks engines by fixed-cost share and the leanest engine loses deterministically (IF279). The growth factor stays in use as each engine's **own** catastrophe bar, never as a cross-engine comparison. Exact complete outcomes, identical model/document/runtime bindings, and the same warm/cold boundary are prerequisites; doing less work never counts as a win. This development rule does not silently promote an NFR candidate number under IF137—the certification protocol still governs release bars—but it does govern optimization and completion. If the kernel itself has bad inherent or output-sized scaling, make several focused, profile-earned root attempts to beat it; if those attempts do not improve the interpreter, stop before inventing a larger subsystem, report the evidence and attempts, and ask the owner for direction.

1. **REAL documents only — benchmarking a shortcut is cheating.** Measure the production evaluation path: the general `Document` (interpreter) and the kernel's `IDocument`, both built from **real DM-JSON models**. The spike's `Map<String,String>`-backed `RepDoc` (O(1) lookups, one-pass `star`) must **never** be the benchmarked object — it sidesteps the exact machinery (parallel index, common-prefix resolution, star aggregation) that is hard to make fast, so its numbers are a fiction. If a benchmark doesn't exercise real group resolution, it isn't a benchmark.
2. **Measure AGAINST the kernel, as a regression gate.** The perf benchmark is the **twin of the correctness differential** and lives in `:adapter` (the only module with the kernel). Before timing a scenario, use the prepared interpreter's value-independent `supportAudit()` to force the same cached rule plans execution consumes: every rule, implicit computation validation, computation alternative, customization requirement, host-sensitive primitive, RNU plan, and iteration/parallel shape. Then check `unsupported.isEmpty()` on every actual instance/variant—including the exact N used by interpreter-only cold/warm timing helpers—and compare complete validation (`code|type|indexed-pointer`) or computation (`indexed-pointer|outcome|value`) signatures across interpreter, dynamic kernel, and every declared Java-capable static strategy. An ERRORED computation's attempted value is part of that signature, just as it is for VALUE. The equality gate remains exact, while a failure reports multiset-aware only-side counts with no more than ten samples per engine and 240 characters per displayed signature; large generated documents therefore remain diagnosable without dumping their complete outcome sets. `validateFull` fails loud on unsupported (IF139), but it is neither the prepared audit nor the outcome-bearing API. IF156 now enforces both eligibility layers and refuses a timed fiction with the construct, scale, and variant named. Then record the eligible wall-clocks + ratios and apply the standing rule above: the interpreter must beat both kernel strategies at every measured scale and cost no more per unit than either (IF279 — per unit, not per growth factor).
   - **⭐ NEVER count Groovy codegen — in ANY benchmark, including startup (standing rule, re-affirmed 2026-06-24).** Kernel codegen is **always ahead of use in real-world projects**: a real deployment generates + compiles the validator at **model-load / deploy time** (cached in `IModelCodeCache`), so the kernel **never pays codegen per request** — its real cost is steady-state validation against already-generated code. Timing codegen therefore measures a cost production never incurs — a fiction that unfairly flatters any "interpreter is faster / starts faster" claim. **This is absolute and has no exception:**
     - **Comparison benchmarks** prime it out — the kernel generates on its FIRST `validateFull` (cached for the engine's life), and every timed region is preceded by a correctness `run()` + warmup, so the codegen call is always discarded. (This is also why the kernel's per-call time only JIT-warms downward over the first ~dozen calls — the Groovy validator warming, not recodegen.)
     - **Startup measurements too.** The interpreter's "fast startup" (goal #1) is measured **on its own terms** — its engine build + first-call index/parse cost in absolute terms — **NOT** as a race against the kernel's codegen. Do not put a "kernel cold start incl. codegen" number next to it; that's the forbidden comparison. The interpreter's no-codegen advantage is a **capability** point (it matters for native-image — the kernel's Groovy codegen can't go native at all — and for one-shot CLI / JS use where there's no ahead-of-time deploy step), stated as prose, never as a benchmark timing.
     - **Codegen+compile is ONCE PER DEPLOYMENT/RELEASE — it is not a per-call, setup, OR startup cost, so it belongs in NO column of ANY comparison.** It runs at model-load / deploy time (cached in `IModelCodeCache`) and is paid **zero** times per request. Consequence: in any steady-state / hot-reuse comparison BOTH engines are already *past* setup — the kernel's code generated at deploy, the interpreter's first-parse amortized — so the only thing left to compare is **per-operation evaluation cost** (tree-walk vs already-generated code). Two traps that break this even while *saying* "paid once": **(a)** listing codegen as the kernel's *per-call setup* in a comparison table — it is not a per-call cost at all; **(b)** framing a **cold / one-shot** run as "the kernel must codegen first" — in production the model is already deployed, so the kernel does **not** codegen on the call. The interpreter's *not needing* codegen is a **capability** (it runs where Groovy codegen can't — native image, JS — and where there is no deploy step), **never** a "starts faster / faster per call than the kernel" timing claim.
3. **Target the non-obvious group machinery, at scale.** Not flat single-row rules — the cases that bite: **deeply nested repeatable groups**, **parallel iteration** / cross-level references, **starred aggregates** over large lists, and **many rows (up to 100 000)**. *Invest heavily in all things groups.*
4. **Run on the PURE engine, decoupled from the CLI — it must be CHEAP to run, very often.** Both the correctness differentials and the perf harness call the **`DmInterpreter` + `Document` API directly** (kernel via `RuntimeLaws`), NOT through `dmtool`/`InterpreterEngine`/`InterpreterModelLoader`. No process spawn, no `installDist`, no JSON envelope, no native build — just in-process JUnit (and `jsTest`). "Real document" means the real `Document` *data structure* with real nested-group shape, built **programmatically in-test**, not loaded through the CLI. The CLI's loader is a separate, thinner concern with its own small test; the engine's semantics + performance are measured at the engine, so the loop stays fast enough to run on every change.
5. **The hot path stays a MONOMORPHIC CONCRETE call — extend the engine ADDITIVELY, never by interface-ifying a common path (standing design rule, 2026-06-27).** A per-cell / per-operand / per-code-point check on the formal-error or evaluation hot path must be a **monomorphic call on a concrete (`final`) type the JIT can inline** — never a `fun interface` / virtual dispatch the *common* case has to pay. The precedent is in the source: `LegalCharset` is deliberately a `final class` (NOT a SAM) "so the call is monomorphic and JIT-inlined," and `PredefinedType.accepts` is a concrete `data class` method, not an interface. So when a new consumer SPI is added (e.g. the code-based `CustomFieldType` shipped in IF44), it must be **additive + opt-in**: the declarative/common path keeps its concrete inlined call **unchanged**, and the polymorphic SPI call is reached **only** for the construct that actually uses it — exactly how `CustomCondition.check` is paid only by models that contain a `Cond.Custom` node; a consumer who registers no code-based handler pays nothing. A library consumer must run **as fast as today** even as the surface grows. This is **gated, not hoped**: a many-row, declarative-path scenario stays in the perf suite, so any deopt of an inlined hot path (e.g. unifying everything behind one interface) trips the build. Two live guards of this rule: **`CharsetPerfTest`** (the `LegalCharset` per-codepoint path — a SAM `fun interface` once blew the suite up 16 min, so it's a `final class`) and **`CustomTypePerfTest`** (the declarative custom-field-type `PredefinedType.accepts` per-cell path — locks it within a factor of plain-string-with-the-same-pattern + sub-quadratic, so a careless IF44 SPI dispatch that boxes per cell or goes megamorphic trips it). The trap to refuse is the "clean" unify-behind-one-interface refactor — it converts a free inlined check into a per-cell virtual (and, with several impls, megamorphic) call.

## The runtime a perf number may be produced on — OpenJDK 21, enforced

**Perf runs on OpenJDK 21 and nothing else** (owner rule, 2026-08-23). `JdkIdentity.requireSupported()` sits on the one seam every timed observation passes through and refuses, naming the JVM it found and pointing at the pin; nothing is recorded. GraalVM belongs to `:cli:nativeCompile` via `GRAALVM_HOME` (a separate GraalVM 25 toolchain) and is never the build JDK — [`scripts/gradle-environment.sh`](../scripts/gradle-environment.sh) selects OpenJDK 21 and skips it.

The rule is measured, not hygienic. A JIT change moves absolute numbers by more than any anchor tolerance absorbs: swapping GraalVM 21.0.12 for OpenJDK 21.0.12.1 on one machine, one commit, one day moved **45 of 91 lanes** (median **1.15×**, worst **1.60×**) and made **10 faster**. The identity is deliberately **family + major**, because `java.version` cannot separate the vendors (GraalVM 21 reports `21.0.12`, Homebrew OpenJDK `21.0.12.1`) while a patch-exact rule would redden CI on every Temurin bump for a difference that moves nothing. If the refusal ever fires, **fix the toolchain, never the anchors**. Full account: [INTERPRETER-PERFORMANCE-RESULTS](INTERPRETER-PERFORMANCE-RESULTS.md) "Checkpoint 2026-08-23".

## A capture's machine conditions are NOT certifiable by `loadAverage` (measured 2026-09-19)

**`perf-anchor.sh` refuses a local input above 1.0 runnable threads per core, and that bar cannot see the contention that matters.** Load average fails twice over: it is a one-minute average, so it smears a burst that spans a single capture, and it counts runnable threads, so two fully saturated cores on an eight-core machine read as ~0.25/core — a quarter of the bar. Measured the same day: with this machine **92 % idle** across six `top` samples the load average still read **2.2**, and while an external Lean toolchain and a `node` process held **~200 % CPU** the column would have reported a quiet box. Four captures taken that afternoon recorded 0.24 / 0.57 / 0.49 / 0.92 per core and every one passed. **The two quantities were finally read side by side on 2026-09-20**, which is the direct number this paragraph previously argued for from mechanism alone: in the same 200 ms windows where system utilisation measured **0.132–0.256** of eight cores, `getSystemLoadAverage()` reported **3.49–5.03** — 0.44–0.63 runnable threads per core against a true utilisation of 0.13–0.26, so the column overstates by 3–4× and the 1.0-per-core bar admits both readings alike ([the probe](INTERPRETER-PERFORMANCE-RESULTS.md)).

**A CPU-time clock is not a defence, which is the part that looks like one.** `measureCurrentThreadCpu` is immune to *preemption*, so it is easy to assume it is immune to load — but stalled cycles are charged to the measuring thread, so shared-cache eviction and memory-bandwidth contention inflate a CPU-time median directly, and on Apple Silicon the thread may also land on an efficiency core. **So a null correlation against `loadAverage` does not refute contention**: that column is *independent* of the timing, which is necessary and says nothing about **sensitivity**, and an instrument that cannot register a mechanism returns a null result whether or not the mechanism is operating. Treating independence as sufficient is what let a contended capture session re-level two anchors on 2026-09-19; the fold was reverted the same day. What closed it, the same day, is the section below: not the system-wide utilisation sweep first proposed but a per-region ratio recorded on the sample itself, which is the narrower instrument and settles the same question. `loadAverage` remains unable to certify a capture — that is why `perf-anchor.sh`'s bar is not the gate — and the evidence now travels with the measurement instead of with the machine.

## The interpreter protocol's timed samples record their OCCUPANCY net of collection, and a STARVED process is refused (contract, measured 2026-09-20)

**Which collectors this reaches, stated first because the claim was published over-broad once (corrected 2026-09-19, hours after it was written).** The contract below governs the **`:interpreter` performance protocol** — the `interpreterPerformance` bundle's JVM and Node workers and the throughput lanes that share `PerformanceProtocol`. It does **not** reach the other two timed collectors, and neither omission is an oversight: `:adapter:perfGateTest` cannot form the ratio at all, because each bar writes its clock as a literal (9 sites, 6 `wall` / 3 `cpu`), so a lane emits one clock by construction — and over the 30 committed darwin run files at `93482f7c9`, **0 of 34 lanes carries both** (11 wall-only, 23 cpu-only), the growth lanes being cpu-clocked and the latency lanes wall-clocked; and `:adapter:interpreterNativePerformance` times a **child process**, for which measuring-thread CPU is not the right numerator. What those lanes record instead is provenance: the three GC/JIT fields (`gcCountInWindow`, `gcMsInWindow`, `jitMsInWindow`) that **no gate consumes**, plus `loadAverage`, which *is* judged — but only on the anchor-write path, by the very `perf-anchor.sh` check the section above measures as blind. Their two dedicated contention fields read Linux-only sources and are `None` in all 4 039 darwin observations. Extending contention evidence to them is the section below, which gives each the quantity its own carrier can form ([IF330](INTERPRETER-FINDINGS.md#if330)).

**The contract.** A timed region's wall duration says nothing about whether the region *ran*, so `PerformanceScaleSample` carries `cpuMillis` **and `gcMillis`** index-for-index with `elapsedMillis`, and a sample's **occupancy** is the **median** of its per-region

```
cpu / (wall − gc)
```

ratios — median, so one descheduled region cannot condemn a process and one healthy region cannot excuse it. `PerformanceProtocol.aggregate` refuses any fork whose occupancy for any scale falls below `minOccupancy(host)`, and the message names both causes a low ratio can have plus the field that tells them apart, so a reader neither hunts a regression that is not there nor dismisses one that is.

**Collection comes out of the DENOMINATOR, and nothing is ever filtered on it.** GC runs off the measuring thread, so a pause inflates wall while thread CPU stays flat; leaving it in the denominator makes an allocation regression read as a busy machine (measured, below). Taking it out of the wall a region is credited with asks the only question the bar is for — *while this thread was supposed to be running, was it scheduled?* — and leaves the pause itself fully visible in `elapsedMillis`, which is what every timed bar consumes. A carrier that cannot report collection sends `gcMillis: null`, which the protocol keeps **absent** across the round trip rather than writing a zero that would read as "no GC", and treats as no correction; a series that does not line up region-for-region is refused, because it could not attribute anything.

**The refusal sits in `aggregate`, never in `validateFork`, and that placement is the point.** A contended record is evidence *of contention*: it must survive on disk and merely never reach a report. Refusing it at write time would destroy the only trace of the condition that produced it.

**The floor is keyed by HOST because the two carriers cannot report the same quantity.**

| carrier | numerator | denominator correction | idle band, measured 2026-09-20 | floor |
|---|---|---|---|---|
| JVM | the MEASURING thread's CPU (`ThreadMXBean.getCurrentThreadCpuTime`) | every collector's elapsed time (`GarbageCollectorMXBean.getCollectionTime`), an UPPER bound on the pause a region paid | 0.8328–1.0000 (12 scale-samples) | **0.75** |
| Node | EVERY thread's CPU (`process.cpuUsage()`, user + system) | none — the numerator already counts V8's collector threads, so a pause raises both sides | 1.0407–2.2500 (15 scale-samples) | 0.85 |

Node exposes no per-thread CPU clock in stable form, so its numerator includes the libuv pool and V8's background GC and compiler threads — which is why an idle Node process reads *above* 1.0, why a single shared floor is wrong, and why Node needs no GC term. On the JVM the thread clock is the right numerator for the mirror-image reason: process CPU there counts the JIT and GC threads, so a process-time ratio would exceed 1.0 exactly when a first-answer measurement works hardest — and it is precisely that choice of numerator that makes the GC correction necessary. Both ratios fall when the process is starved of cycles, which is the signal the floor reads; only their healthy baselines differ.

**The JVM floor's binding sample is a COLD first answer, not the warm band.** Eleven of the twelve JVM scale-samples read 0.9887–1.0000; the twelfth is a first-answer fork at **0.8328** with no collection at all, its thread blocked on class loading while its two sibling forks read 0.9944 and 0.9921. A floor set against the warm band would refuse an honest cold measurement, so 0.75 sits below the outlier rather than below the band.

**Both directions are locked, and the does-fire half was proven under real load rather than by fixture alone.** At two-times oversubscription (16 spinners on 8 cores) the corrected occupancy read **0.313–0.348** against the idle 0.833–1.000, and `PerformanceProtocolTest` asserts the refusal on those measured triples verbatim; the measured idle minima above are asserted to be *accepted*, which is the half that stops a floor being raised until it refuses everything. There is a third lock for the defect this instrument shipped with: a capture whose *plain* ratio sits under the live floor and whose corrected ratio is healthy must be **accepted**, so the inversion below cannot return. Plus the vacuity control that each floor sits strictly between zero and its own carrier's measured idle minimum — a floor of zero would satisfy every other assertion while refusing nothing. Rationale: [IF329](INTERPRETER-FINDINGS.md#if329); the numbers: [the 2026-09-20 checkpoint](INTERPRETER-PERFORMANCE-RESULTS.md).

**Re-deriving a floor is a measurement, not a preference.** Run one bundle invocation on a quiet machine, take the lowest per-scale occupancy each carrier reports, and keep the floor below it with margin. A floor raised above a carrier's true idle minimum fires on healthy runs, which is how a contamination check comes to be deleted instead of fixed.

**Why the correction exists: on 2026-09-19 the plain ratio INVERTED the ranking, and it was measured the next day.** One scenario, an idle machine, the heap the only variable: at 1 g the capture read plain 0.8745, at 320 m it read plain **0.6868** — under that day's 0.70 floor — with a 3.6× rise in collection as the whole difference. Both are honest captures of a machine with nothing else running. Meanwhile a genuinely contaminated capture, four of eight cores busy and wall inflated **+37.5 %**, read plain **0.8302** and passed. So the bar as first shipped refused the honest capture and admitted the contaminated one. The corrected quantity holds steady across that 3.6× GC change (0.9972 → 0.9962), which is the near-exactness the fix needed.

**And the corrected ratio's SENSITIVITY is measured, which bounds what the floor may be claimed to detect.** In that same four-spinner arm wall rose +37.5 % while measured CPU rose +30.5 %, because cycles stalled on a contended core are still charged to the measuring thread — so the corrected ratio moved only **−4.0 %**, to 0.9571, well inside the idle band. **Moderate contention is invisible to a ratio, on either carrier**; what the floor detects is starvation, and it does that cleanly. Do not extend this instrument to the `:adapter` collectors expecting a contention detector: the residual is covered by the section below instead ([IF330](INTERPRETER-FINDINGS.md#if330)) — a ratio cannot carry it, so those lanes judge a windowed system-load reading, which separates the same arms without overlap.

**What occupancy does NOT do.** It certifies that a capture ran; it does not shrink run-to-run spread. Machine state stops being an *unmeasured* confound, and the variance that defeats a 5 % timed bar is untouched — which is why [IG152](INTERPRETER-GAPS.md) is declined on its own measurements rather than reopened on the strength of this instrument.

## The `perfGateTest` lanes record FOREIGN CPU DEMAND, and an absolute-anchor bar is downgraded when the machine was not ours (contract, measured 2026-09-20)

**Why a second instrument, when the section above just built one.** Occupancy answers *did this thread get scheduled*, and the measurement that fixed it also bounded it: four busy cores of eight inflate wall 37.5 % and move the corrected ratio only **−4.0 %**, because cycles stalled on a contended core are still charged to the measuring thread. Moderate contention is therefore invisible to any ratio — and moderate contention is exactly what damaged an artifact here, when a contended session re-levelled two anchors on 2026-09-19. The `perfGateTest` lanes also cannot form the ratio at all: each bar writes its clock as a literal, so a lane emits one clock by construction. So they get the complementary quantity instead.

**The contract.** `PerfMachineDemand` reads system and process CPU utilisation from `com.sun.management.OperatingSystemMXBean` once per observation, closing the window that contains that measurement, and derives **foreign demand** = `system − process`: the share of the machine somebody else was using. All three land on the observation row, and `TimingEnforcement.forAbsoluteAnchor` downgrades a bar from `GATED` to `FLAGGED` above `PerfMachineDemand.MAX_FOREIGN_CPU_UTILISATION`. A downgraded breach is reported with its reading and the corrective, never failed — an absolute time taken under that load is the machine's number — and the observation still lands in the record with its status.

**Unlike the quality counters beside it, this one is MEANT to gate, and that is a property of the quantity rather than a preference.** GC and JIT are *post-treatment*: an allocation regression causes them, so rejecting a sample on them censors the evidence of the regression, and `PerformanceRecordShapeGuardTest` forbids any consumer. Foreign demand is *pre-treatment* — no change to our code can make another process busy — so judging on it removes a confound. The same guard therefore **requires** this one to have an enforcement locus, which is the exact inverse sweep.

| what | measured 2026-09-20 (darwin-aarch64, 8 cores, 24 wall-bounded 200 ms windows per arm) |
|---|---|
| no applied load | foreign 0.080 – 0.488, and 0.193 – 0.591 on the return control |
| 4 spinners | **0.851 – 0.896** — no overlap with either unloaded arm |
| 16 spinners | 0.903 – 0.959, saturating |
| floor | **0.70**, 18 % above the worst healthy reading and 18 % below the best contaminated one |
| what occupancy said in the same arms | 1.0001 unloaded, **0.9988** at 4 spinners — indistinguishable — and 0.4063 starved |

The last row is the whole argument for keeping both: this quantity sees the contamination the ratio misses, and the ratio ranks the starvation this quantity saturates through.

**Two properties of the instrument that a reader has to know.**

- **A reading of `0.0` is ABSENT, never quiet.** Across 119 windows in which a thread held a core throughout, 17 returned exactly `0.0` — physically impossible — and the incidence was bursty rather than a rate (0 of 35 in one sweep against 13 of 60 in another, with short windows and call interleaving both refuted as causes). The cause is unknown and recorded as unknown; the row omits all three fields rather than writing a zero. **An absent reading leaves the bar at full strength**, because those failures cluster on a *quiet* machine — 0 of 24 windows unusable under four spinners against 4, 2 and 9 of 24 unloaded — so absence is weak evidence for quiet, and downgrading on it would switch the gate off where the instrument works.
- **Both accessors measure from their own previous call, so there is exactly one sampling site.** A second caller anywhere in the process would silently shorten the window an observation is credited with: well-formed, wrong, invisible at runtime. The reading is taken once in `assertWithinBudget` and passed to both the decision and the row; `PerformanceRecordShapeGuardTest` holds the accessors to `PerfMachineDemand`.

**Re-deriving the floor is a measurement, not a preference** — the same rule as the occupancy floors, and it matters more here because the baseline above is a *workstation*: OS metadata indexing alone took one to two cores throughout, which is why the worst healthy reading is as high as 0.591. Take the highest foreign reading a healthy capture produces on the machine in question, and keep the floor above it with margin. A quieter machine supports a tighter floor; a floor below that worst healthy reading turns the anchor gate off on honest runs, which is how a contamination check comes to be deleted instead of fixed.

**The native lane gets the same reading under a different NAME, because the same arithmetic means something else there.** `interpreterNativePerformance` times a child process, so `system − process` leaves the child's own work in the remainder. The obvious correction is unavailable: `ProcessHandle.Info.totalCpuDuration()` is **empty** on darwin for a child — while it runs, immediately before it exits, and after — so the parent cannot subtract the child's CPU at all. What it records is therefore **unattributed** rather than foreign demand, with its own floor measured on the real binary (unloaded 0.184–0.412 across two control arms, four spinners 0.883–0.928, sixteen 0.993–0.998; floor 0.70) and its own constant, so re-deriving one lane's cannot move the other's. **That lane reports rather than gates**, because it is `informativeOnly` and has no bar to protect: every sample carries its reading, the summary states how many samples produced one and how many were contended, and a contended run prints a flag. The reading count is part of the verdict — 3 to 6 of every 8 samples produce nothing, the parent being blocked on the child — so `contendedSamples=1` is read against it, and `contended` is stated only on a majority.

**What none of this reaches: the growth floors.** A growth ratio is taken within one run at two scales, where contention moves both arms, and no measurement here addresses that.

## `perf-results/` is a MUTABLE corpus, so a figure derived from it is dated to a commit (measured 2026-09-19)

**Committing a capture changes the population that every derived figure was computed on, in both directions**: the new runs enter it, and the writer's own retention cap silently deletes the oldest records that are neither anchor inputs nor doc-cited. Both happened in one commit — four captures added, four GraalVM-era records pruned — which moved the worst-key spread from **160.5 %** (`group-star expansion@8000`) to **84.6 %** (`charset grapheme@32000`). Re-deriving after that commit and reading the difference as a *correction to the original figure* produced a wrong doc edit; reverting the capture commit restored the original figure exactly. So **re-derive against a named corpus state, and never treat a recompute that straddles a capture commit as falsifying the earlier number** — it is measuring a different population. The retention cap also means a run cited only in prose can vanish, so cite a record you depend on where the pruner can see the citation.

## The NFR certification protocol

The candidate budgets and their evidence status are single-sourced in [INTERPRETER-SPEC.md](INTERPRETER-SPEC.md) as NFR-S1/S2, NFR-P1/P2, and NFR-F1/F2. The contract posture is ratified (IF137): the numbers are **informative until per-number certified**, `PerfBounds` is the only ratified NFR/release-level floor, and the paired growth estimator is **interleaved N/4N with the median of within-pair ratios**. Other executable implementation-regression assertions remain diagnostics/catastrophe guards, not certified NFR bars. A number promotes to a release bar only per-number, once its scenario + estimator are fixed, the runner/runtime is pinned, the p95/median sampling is performed, semantic preflight passes, the measurement is reproducible, and the owner ratifies it (the six-point gate, INTERPRETER-SPEC). A later run is **certifying** only when it records the commit, scenario identity, CPU/runner, OS, JDK or Node version, heap settings, estimator, and sample count. Every actual interpreter instance must retain an outcome-bearing zero-unsupported check; every comparison scenario must additionally agree with dynamic Groovy and each declared Java-capable static strategy on complete signatures under the ratified Groovy-dynamic anchor (IF136). Message-only equality is insufficient, and `validateFull` now fails loud on unsupported (IF139). The recommended sample/fork and job/miss defaults bind a number only at its promotion, not globally. The numbers remain **UNVERIFIED CANDIDATES**, not silently “green” because an older laptop minimum was below one.

### Startup / first answer (NFR-S1 and NFR-S2)

Library startup measures the time from an already-expanded, in-memory `ModelDef` and a materialized `Document` to the first fully materialized result. The clock starts **before `DmInterpreter(model)`** and ends after `validate`/`compute`/`testRule` has produced its complete result. Model loading and document construction are separate consumer work and stay outside this library clock; engine construction, lazy parse/index initialization, evaluation, and result construction stay inside. Run at least 50 independent fresh JVM/Node processes, discard no samples, and gate the **nearest-rank p95** while reporting median too. A minimum is never a startup statistic.

Native CLI startup is a separate end-to-end measure: the parent clock starts before process launch and stops after the complete result envelope is read and the process exits. It includes process startup, option parsing, model/instance file reads, JSON/model loading, compute→apply when enabled, validation, serialization, and shutdown. Use warm OS filesystem caches for repeatability and at least 50 independent invocations. The absence of runtime codegen is a capability advantage; kernel codegen is never included in or compared with a startup timing.

Keep the absolute p95 budgets and the row/rule growth checks separate. The former catches a uniformly slow but linear implementation; the latter catches an asymptotic regression. The older `freshRunMedianMillis` helper still starts its clock **after** engine/document construction and therefore remains only a complexity probe. IF172's separate `interpreterPerformance` protocol is the first-answer evidence lane: independent JVM/Node processes clock engine construction through complete results, while the native parent clock includes spawn through complete envelope and exit.

### Warm throughput and scaling (NFR-P1 and NFR-P2)

Build each engine and materialize its document outside the timed region, perform the zero-unsupported/tri-engine correctness preflight, warm the engines, then record repeated evaluation medians. The absolute large-document budget uses the interpreter on the production `Document`; the NFR-P2 relative budget uses the same logical instance against the kernel's generated-**Java** evaluator because that ratio isolates the algorithm from Groovy's dynamic-dispatch tax. That release-candidate denominator does not narrow development acceptance: every comparable run records and beats both dynamic Groovy and generated Java.

Every scenario declares its intended complexity class. A linear or `N log N` axis is measured at `N` and `4N` and must satisfy the NFR-P1 growth bar under the ratified paired estimator (IF137): interleaved N/4N samples with the median of within-pair ratios. A genuinely pairwise semantic operation may keep an `O(outer×inner)` fallback only when the exception is explicit and correctness-locked; its interpreter median must still be lower than both kernel strategies and its per-unit cost no higher than either (IF279). An optimized equality/hash-join path is declared `O(outer+inner)` and must be gated as linear; a permissive sub-cubic guard does not protect that optimization.

### Relative footprint (NFR-F1 and NFR-F2)

**Footprint is not “minimize memory.”** Indices, hash maps, parsed-AST caches, row-context memoization, and other bounded caches are the preferred implementation when they remove repeated work or improve the complexity class. A footprint review asks whether the state has the right owner/lifetime, reaches a plateau, grows in the declared space class, and earns its cost—not whether a smaller but slower implementation exists.

Measure four relative surfaces:

1. **Dependency closure:** sum the resolved non-JDK runtime artifacts needed by a fresh interpreter consumer and compare them with the equivalent kernel/Groovy evaluation closure. Kernel, Groovy, dmtool, `:adapter`, and other-kit dependencies remain a hard zero in the interpreter graph.
2. **Packed artifacts:** compare the thin JVM artifact, packed JVM runtime, and JS KLIB with the previous release. Keep the KLIB explicitly separate: it is not a published npm-package number. IF226 shipped the functional production npm artifact only after a non-empty exported API, generated `.d.ts`, and non-repo consumer smoke passed; an empty DCE output or unpacked `node_modules` closure still fails closed rather than becoming a footprint base.
3. **Runtime state:** in forked JVM and Node probes, measure retained heap and allocation volume above fixed setup at `N, 2N, 4N, 8N`; the recommended fork count (≥5) binds at promotion (IF137). Define the JVM post-GC sampling method and run Node with `--expose-gc`, report logical cache-entry counts separately, and verify owner release as well as warm-owner plateau so GC noise cannot pass or fail the exponent accidentally. Fit a log-log space exponent per fork and gate its median plus the worst 4× step under the ratified policy. This multi-scale check does not mistake a hash table's discrete backing-array resize for a super-linear design. Report cache owners and the performance delta they buy.
4. **Native delivery:** compare the native binary with the equivalent trimmed JVM app image. This is a dmtool product measure—the binary still bundles the kernel for the MVK oracle—not an isolated interpreter-jar measure.

A >10% artifact/closure increase or >20% same-scenario runtime-footprint increase is a **review trigger**, not an automatic demand to remove a cache. It may be accepted with the measured exactness/startup/throughput benefit that pays for it. An unbounded cache, a non-plateauing repeated-eval run, or a space-complexity breach is a failure.

**When the generated path may still be preferred on footprint:** a **GC-sensitive, sustained-high-throughput** service is the workload where the generated path's primitive `long[]` indices + interned results may win, even where current medians favor the interpreter — a workload-specific hypothesis, not a result from this project, and tempered by the generated path's own super-linear large-row wall-clock (see "Code-generator row-axis scaling"), which means its allocation story is not uniformly better.

**The interpreter's JVM and JS/Node production dependency closures are now fully reconciled and measured reproducibly** by `:interpreter:interpreterRuntimeClosure` and `:interpreter:interpreterJsRuntimeClosure` (IF160, wired into `:interpreter:check`). The tasks reconcile each canonical runtime file to exactly one resolution artifact, account graph-only components, keep the own jar/KLIB separate, recursively walk the public package's production dependency/optional/peer declarations, and fail on forbidden project/published-kit/kernel/Groovy/opaque/npm edges. Separate generated reports name each host graph and remain authoritative for the clean-tree inventory and byte total. `:adapter:kernelRuntimeClosureReport` first executes a self-contained real kernel validation, then derives the informative comparison graph from that consumer's minimal compile/runtime dependencies; no ratio is promoted. IF173's local clean-commit collector injects the same definition into the current and archived previous release, records bytes/SHA for the thin JVM jar, reproducible packed JVM runtime, JS KLIB, native CLI, and native-equivalent trimmed JVM app, compiles and runs an external Java consumer solely against the unpacked packed-runtime `lib/*.jar`, and executes the same typed low-firing evaluation through both delivery comparators. Its deltas and native/trimmed ratio remain informative. **Superseded provisional baseline (2026-07-18; existing artifacts inspected, not rebuilt or certified):** the interpreter JVM jar was 556,845 bytes; its named closure was 2,984,760 bytes; the install's named kernel jars + Groovy were 12,909,518 bytes. The often-cited 33 MB native / 119 MB JVM pair was measured on 2026-06-15, before interpreter-backed native evaluation existed, and is neither same-revision nor equal-capability; it must not be reported as the current `dmtool` size. IF226's publication increment added the production npm measurement only after the real export, `.d.ts`, and consumer smoke existed; it was never fabricated from the KLIB or empty production-library output. Only numerical promotion and CI scheduling are owner-gated.

**Cache lifetime is structurally guarded independently of heap noise** (IF161). `CacheLifetimeGuardTest` samples logical entries for the real `Document`, `ParsedModel`, and per-step `OverlayViews` owners at five same-owner checkpoints, fences the live engine/document, then proves many discarded owners reach a reference queue and the weak observer returns to baseline. Planted per-evaluation and global-document retention controls prove both guards can fail. The observer is internal, nullable, instance-local, and absent from the public API; overlay entries are cleared in `finally`. This proves owner-scoped plateau/release, not a retained-heap exponent, allocation result, or promoted numerical bar.

### Per-model resident cost — the P-SERVICE axis (measured 2026-08-07 on JVM, informative)

NFR-F3 asks a question the forked lane below does not: not how one engine's state grows with its document, but what **one resident model costs** when a service caches many. Re-runnable by `ModelFootprintReportTest` (opt-in via `-Da12.footprint.report=true`, prints, asserts nothing), which holds 40 instances per measurement and reports the minimum settled heap over six collections, so the per-instance figure is not a single noisy sample.

Retained bytes per instance, JVM 21.0.12. `cold` is a `PreparedModel` that has never served a request; `warm` is the same after one `createInterpreter()` + `validateFull`, which is what a cache entry holds once it has served anything.

|---|--:|--:|--:|--:|--:|--:|
| `typedefs` | 26 | 0 | 4,726 | 32,839 | 45,892 | 46,907 |
| `order-aggregates` | 15 | 6 | 5,197 | 24,808 | 38,751 | 40,237 |

Four readings, and the fixture set is a **shape matrix rather than a size ladder** on purpose — the first three vary fields at ~one rule, the last two vary rules at five fields — because a rules-only sweep cannot tell "there is a fixed floor" apart from "cost tracks field count":

- **The prepared model is larger than the JSON it came from**, 5.8× to 9.7× the expanded DM-JSON when warm. This is the intended space-for-time trade stated at the top of this section, but it inverts the assumption a consumer is likely to bring.
- **Cost tracks BOTH axes, at roughly 1.6 kB per field and 1.6 kB per rule.** Two independent two-point estimates agree: along the rule axis at five fields, 48→192 rules adds 225,539 B over 144 rules (1,566 B/rule); along the field axis at ~one rule, 26→29 fields adds 6,533 B (≈1,656 B/field after subtracting one rule). Predicting `order-aggregates` from those slopes gives 37.1 kB against 38.8 kB measured, within 4%. **There is no meaningful fixed floor** — an earlier Node measurement reported a "60–80 kB floor" that was in fact the small model's own total, and its rules-only dose-response could not have supported the claim. **Corrected 2026-08-07: this two-term rule is superseded by the three-term fit below.** These five fixtures carry 3–4 groups each, so the sweep could not see a group term at all; against a realistically structured model (29 groups) the two-term rule under-predicts by ~18%.
- **A warm entry costs 1.4× to 1.9× a cold one**, so a service must budget the warm figure. Sizing on `cold` understates a served cache entry by up to 2×.
- **The interpreter is now thin: it adds only 2–5% over warm.** Before model-static preparation was hoisted onto `PreparedModel` ([IF251](INTERPRETER-FINDINGS.md#if251)), a retained interpreter roughly doubled the cost, because it owned the plans. That delta is the hoist's effect, measured.

`createInterpreter()` is not lazy: `Interpreter.init` calls `engine.supportAudit()` eagerly, and the audit forces every rule plan, computation plan and pattern compile into the shared store. That is why `warm` and not `cold` is the budgeting number, and the eager audit is kept deliberately so a P-EDIT consumer learns at form open that a custom condition is unregistered rather than on the first keystroke.

Two source-verified facts change what a service should retain. `ModelWorkspace.prepare()` holds **no preparation cache** — each call re-runs a fresh deterministic assembly — and `AdmittedWorkspaceModelSource` retains its source **twice**, as a defensive `ByteArray` copy and as the decoded UTF-16 `String`. A `PreparedModel` retains neither source form; besides its `ModelDef`, fingerprint and dependency list it holds the shared model-static preparation described above. So releasing the workspace after preparation frees the source, and a service should cache expanded DM-JSON plus prepared models rather than workspaces.

This is measured context for NFR-F3, not a promoted bar: one host, one settling method, five fixtures, and no pinned fresh-process series.

#### The same axis against both kernel strategies (measured 2026-08-07, informative)

The section above measures the interpreter alone, which cannot answer what a service replacing kernel runtime services should expect. `EngineFootprintReportTest` in `:adapter` measures the same quantity for all three strategies over the same five fixtures ([IF253](INTERPRETER-FINDINGS.md#if253)); it must live there because `:interpreter` stays kernel-free in test scope. Opt-in with `-Da12.engine.footprint=true` under `-PrunPerf`; twelve instances per arm, eight settling collections, ~2 min.

Three protocol points carry the result.

**Class metadata is measured, heap alone is not the footprint.** Both kernel strategies generate and load classes per model, and class metadata lives in Metaspace plus the disjoint Compressed Class Space — neither of which `Runtime.totalMemory() - freeMemory()`, the settling method the section above uses, can see. A heap-only comparison understates them by construction.

**The JIT code cache is excluded, and that was measured rather than assumed.** Attributing it per instance produced negative per-instance deltas and charged the interpreter — which loads no classes at all — 67 kB per model, because it tracks how hot code became during the run, not how many models are resident. It is also globally bounded and JIT-evicted. So it is a property of the workload, not of a cache entry, and the harness's KDoc says not to re-add it.

**The equivalent-work check runs before any arm is measured:** the three engines validate the identical document (the interpreter's seed document, encoded as A12 Document JSON and read back by the kernel's own `IDocumentV2Serializer`), their message-code multisets must agree, and the interpreter must report nothing unsupported. That check earned its place immediately — it caught the harness binding `order-aggregates`' `CustomCondition` on neither engine, which the kernel fires and the interpreter reports unsupported, so one model was briefly comparing two different computations.

**The sixth model is derived from a real one, because the five fixtures are not realistic in scale.** They top out at 63 kB of DM-JSON with 3–4 groups, while models in the `a12-kernel-mm` reference clone reach 281 kB across 79 fields, 29 groups and 89 rules. The gap mattered: a rule of thumb fitted only to the fixtures has no group term (see the correction above). The sixth row closes it without committing anyone's model — `dmtool profile extract` reduces a real model to the identifier-free shape artifact [MODEL-PROFILE-SPEC](MODEL-PROFILE-SPEC.md) defines (counts and distributions only; the committed artifact was checked to contain no string values at all), and `ModelSynthesizer.synthesize(profile, seed = 42)` regenerates an own-domain model from it. Fidelity is exact on the axes footprint depends on — field, group and rule counts, boolean arity within bucket — and partial on operator mix and iteration capacity, which drive evaluation work rather than retained size. It is a footprint fixture, not a performance clone, and 45 of 140 compared axes do differ.

**The Groovy arm gets no such adjustment, because there the retention is the kernel's own design.** `ModelGroovyCode` (kernel-md-runtime-service) holds `private final String generatedPlainCode` — the generated Groovy text, non-transient, retained beside the `transient GroovyObject` parsed from it — so the generated source really is resident on the dynamic path: ~740 kB of `many-rules-192`'s 7.1 MB heap and ~476 kB of the real-shape model's 4.5 MB. That class also creates one ClassLoader per model with the comment *"we create a new ClassLoader per model to enable the deletion of corresponding class definitions from metaspace"*, which independently confirms that metaspace is the right axis for the generated code and that the kernel's authors account for it there too.

The `interp warm` and `Kernel model` columns are heap, because both arms load **zero** classes per model, so their true metaspace is zero. That is also what calibrates the measurement: their observed metaspace readings, 0 to 27 kB, *are* the noise floor. Read the kernel metaspace column against it — 87 kB is only ~3× the floor, 4.9 MB is far above it.

##### The fitted formulas

Least squares over the six rows, no intercept for the interpreter (a model with nothing in it costs nothing, and forcing the constant to zero also removes the unphysical −8.6 kB the two-term fit produces):

| target | formula | worst residual |
|---|---|---|
| interpreter, warm | `1.41 kB × fields + 1.55 kB × rules + 2.30 kB × groups` | **+3.9%** |
| dynamic Groovy, total | `0.75 MB + 14.3 kB × fields + 58.3 kB × rules` | +6.9% |
| Groovy generated classes | `34 + 3.17 × rules` | +1.3% |
| generated Java, total | *no fit* — see below | ±25% |

- **The group term is the whole reason to prefer this over the two-term rule.** Dropping `groups` moves the worst residual from 3.9% to 12.0%, and the 29-group real-model row is where it shows: 29 × 2.3 kB ≈ 67 kB, which is most of the 18% the two-term rule misses.
- **It validates out of sample.** Predicting the *previous* section's independent 40-instance measurements from this fit lands within 2.4% on all five (`typedefs` 45,866 predicted vs 45,892 measured; `many-rules-192` 312,308 vs 313,946). That is a different harness, sample size and document, so the agreement is not an artifact of the fit.
- **Where the ~1.4 kB per field actually goes, measured by layer.** On the field-dense fixture (26 fields, 4 groups, **no rules**, 24 instances): `ModelLoader.load` alone retains 32,518 B, a cold `PreparedModel` around it 32,660 B (+5 B/field — the wrapper is free), and warm 45,919 B (+510 B/field for the forced indexes and plans). So roughly 90% of a field's cost is the **parsed model**, not the preparation. These fields are also minimal — 156 JSON bytes each, `{type, id, name, fieldType}` with no labels and no enum values — so the ≈8× expansion over DM-JSON is the object graph itself rather than retained text. `FieldDef` is a wide record (path, kind, `labels: Map`, scale, signed, required, format, rangeSeparator, datePrecision, `enumValues: List`, `enumCategories: Map`, enumSValue, …), and each field is additionally an entry in several path, scope and requiredness indexes. That last attribution is **hypothesis, not measurement**: the layer split above is measured, the within-record breakdown is not, and a heap class histogram over N held models is the run that would settle it — the natural first step if this figure ever needs to come down.
- **Three parameters on six points is a fit, not a law.** Read the residuals, not the coefficients' precision, and re-derive if the fixture set changes. Weighting rules by mean boolean arity instead of counting them fits comparably (`0.78 kB per boolean operand`, worst 3.1%), which says the per-rule term is really per-AST-node and a model of unusually complex rules will run above 1.55 kB per rule.

Two method caveats, because the histogram and the settled-heap measurement are not interchangeable. Use the histogram for **composition** and the table above for **magnitude**: post-fix the histogram total runs ~4% above the settled-heap figure for the same arm, and pre-fix it ran 46% above it, so its absolute total is the weaker number. The histogram also found a resource leak in the harness: `compileInMemory` never closed its `StandardJavaFileManager`, so a zip filesystem per classpath jar stayed open, which the histogram attributed at ~56 kB of zipfs index nodes per compiled model. It is now closed once the compile task finishes (the returned loader needs only the in-memory byte map). Closing it removed those rows and 396 kB per engine from the *histogram*, but the settled-heap Java figures did not move by that amount — an unresolved discrepancy between the two methods, recorded rather than explained away. The published totals stay as measured by the footprint harness.

- **Generated Java resists these predictors, and two thirds of the reason is identified.** Its totals sit at 303–455 kB for 0–48 rules and jump to ~1.2–1.28 MB at 89–192, so a linear fit on `fields`+`rules` is only good to ±24% and one on generated-source bytes to ±25%. Two contributions are now measured rather than guessed. (a) **Rule count is the wrong axis:** the real-shape model's 89 rules cost *more* than `many-rules-192`'s 192 (1,283,876 vs 1,194,455), because 89 structurally varied rules over 79 fields and 29 groups compile to more program than 192 near-identical arity-2 rules over 5 fields — the fitted slope was reading a proxy. (b) **The bytecode the harness retained added non-monotonic noise on exactly that axis** (56, 68, 67, 110, 271, 206 kB — not ordered by rule count); it is subtracted above, which is what moved the range. What remains unattributed is the ~640–790 kB of Java heap that is neither the model graph, the model JSON the engine retains, nor the bytecode. A heap class histogram over N held engines is the run that would settle it; until then the honest output for Java is its measured range, not a slope.

Four readings that are not formulas:

- **The interpreter arm reproduces the 40-instance measurement above to within 1%** on every fixture (45,857 vs 45,892; 312,431 vs 313,946), from an independently written harness at a different sample size and with a different document. Two harnesses agreeing is the reason to trust either. `interp warm` is stable to ~0.1% across four runs of this harness; `interp cold` is not (13 kB to 155 kB on `typedefs` between runs), which is a second reason the served figure is the one to budget.
- **Totalled, a resident entry is 3.8× to 9.2× smaller than generated Java and 22.0× to 41.0× smaller than dynamic Groovy.**
- **The generated rule/computation code is the entire difference; the model graph is not.** The kernel's expanded Document Model is 18–186 kB — comparable to a prepared model, and smaller than one on the rule-heavy shapes. Everything above it is generated code plus its loading machinery. **Class metadata is 19% to 50% of a kernel strategy's total** — a fifth to a half, not the "about half" an earlier draft of this section claimed before the totals were computed.
- **Dynamic Groovy defers essentially all of that to the first evaluation.** `groovy cold` (services created, nothing evaluated) lands within 1% of the model graph alone on all six fixtures, so creating the runtime service costs nothing and the codegen is triggered by the first `validateFull`. Static Java is eager by contrast: `JavaKernelEngine` generates and compiles in its constructor. The proximate mechanism for Groovy's per-rule class slope — lowering a rule's condition lines into closures, each its own class, past `NUM_CONDITIONLINES_PER_METHOD_GROOVY` — is consistent with the 3.17 classes/rule and with the codegen behavior `RuntimeLaws.generatedGroovySource` documents, but the slope is the measurement and the closure account remains the explanation for it.

Same caveats as above, plus one specific to this table: the interpreter arms exclude a retained `Interpreter` (2–5%, per the previous section) while the kernel arms include their runtime service, and per-model cost is the cost of a *distinct* model — a service sharing one `IModelCodeCache` across engines for the same model pays the generation once, exactly as one `PreparedModel` serves many interpreters. One further limit is specific to the derived row: a profile carries shape, not localized label and message text, so a synthesized model under-represents whatever a real text-heavy model retains for its messages.

**The forked runtime-footprint lane is executable but informative** (IF162). From a clean commit, [`scripts/interpreter-footprint.sh`](../scripts/interpreter-footprint.sh) launches at least five independent fixed-heap JVM workers and five independent `--expose-gc` Node workers across `N, 2N, 4N, 8N`. JVM allocation uses `ThreadMXBean`; Node allocation uses V8 Inspector sampling. Both hosts perform exact semantic preflight, keep setup/warmup outside the allocation interval, report logical owner/cache counts, and prove weak owner release. Invalid or non-positive evidence fails rather than being clamped. The structured report under `interpreter/build/reports/interpreter-footprint/` preserves raw metadata/samples and derives median retained/allocation curves, fitted exponents, and worst 4× steps with `informativeOnly: true`; the task has no default `check`/CI edge and no promoted threshold.

## Why this matters (the cheating we caught)

The encouraging spike timing (`InterpreterMultiplatformTest.scalesToManyRepetitionRows`, ~30 ms / 20k rows) ran on `RepDoc`, whose field lookup is a `HashMap.get` and whose `star` is one pass — **O(N) overall**. At the time, the **production** `Document` stored placements in a `List` and did a linear `placements.firstOrNull{…}` scan on **every** `field`/`filled`/`displayValue`/`groupFilled` (and `star` was O(rows×P)) → **O(N²)** per-row evaluation. So the green spike number said nothing about the real path. Task #28 closed that gap by indexing the real `Document`; the durable rule is still to benchmark that production structure against the kernel at scale.

## The kernel baseline: Groovy vs Java (the fairness question, 2026-06-24)

The kernel's dynamic `validateFull` runs **Groovy-generated, Groovy-compiled** validators (the codegen architecture is in [`KERNEL-INTEGRATION-NOTES.md`](KERNEL-INTEGRATION-NOTES.md) "Code generation targets"). Compiled Groovy executes as JVM bytecode, but carries a **per-operation dynamic-dispatch / metaclass tax** over equivalent Java — measured at **~1.1–1.3× steady-state** across the rule-count sweeps (e.g. 0.078 vs 0.084 ms/row on the depth curve). The kernel team themselves treat this as real — they disable Groovy's Parrot parser (`groovy.antlr4=false`) specifically because it *"slows down the groovy compilation"*. So a naive "interp vs kernel" ratio conflates two things: the interpreter's algorithm **and** the fact that the kernel pays a Groovy tax the interpreter doesn't.

Two consequences, and what we do about each:

- **Scaling exposes the algorithm beneath a constant tax.** A constant Groovy-vs-Java per-operation factor does not change a complexity class, so record all three N/4N curves — and compare them by **per-unit cost**, the slope of `time = fixed + perUnit·N`. Requiring the interpreter's growth *factor* to be no worse than either kernel curve is the trap this bullet used to set: that factor falls as an engine's fixed cost rises, so it rewards the fatter engine (IF279).
- **The Groovy ratio includes dynamic-dispatch tax, so the Java baseline isolates the algorithm.** We run the kernel's **own generated validator compiled as Java**, via the supported **static-model runtime path** (generate Java source through `generateValidationCode(…, JAVA)`, compile in-memory with `javax.tools.JavaCompiler`, run it through `DocumentStaticRtService` — same `validateFull` scaffolding, Java underneath). Each scenario reports **interp × kernel-Groovy × kernel-Java**. Generated Java is the NFR-P2 denominator; the standing development target still requires a lower interpreter median than both strategies.

**Why this matters beyond fairness — the generator signal.** The two kernel numbers distinguish language tax from algorithmic cost while the acceptance rule requires the tree-walker to beat both. They also inform the **future generator** (the "generator-ready" layering): if a JVM-bytecode/Java target exposes a remaining opportunity, that is what a generator would chase.

**The JS generalization (forward-looking).** TypeScript/JS is the kernel's *other* documented codegen target, so this exact harness — *generate code in language X → compile/load → run through the rt path → diff against the interpreter* — generalizes to a **kernel-JS vs interpreter-JS** comparison later (the interpreter's other reason-to-exist). The baseline engine is therefore built **language-parameterized** (Java now; JS-capable later), not hardwired.

**Why code-generator JS/TS is not yet measured.** The `JAVA_SCRIPT_VK` target exists, so the comparison is meaningful, but running it is toolchain-blocked in the public-repos-only build: the generated JS validator needs the kernel's TypeScript runtime (`kernel-core-runtime-ts`, which ships **source-only** and must be `tsc`-compiled), which in turn needs `npm install` of **private, mgm-scoped `@com.mgmtp.a12.*` packages** from a private registry the public build deliberately excludes. A JS twin of `JavaKernelEngine` would generate the validator, bundle it with the built runtime, and construct a document in the TS runtime's own model — feasible with registry access (the JS analog of the existing Java baseline), unmeasured until then. Any kernel-JS-vs-interpreter-JS claim must wait on that harness.

## Cold and warm regimes: fast first answer + beat both kernel strategies

The interpreter is steered by **two CO-EQUAL goals that pull against each other** (owner direction — neither is secondary):

1. **Low cold / startup cost** — the time from *(model, document)* to the **first** answer must be small: minimal upfront work, no codegen, a fast first `validateFull`. This is the realistic latency for a one-shot CLI invocation, a native-image run, a Node-hosted JS consumer, or a freshly-built engine—not a warm steady state. The browser host has its own fixed B1 assurance lane: median ≤250 ms, starting with 10 fresh Chrome processes and expanding to 50 only when the observed range is greater than half the median, with zero discarded samples on the pinned Apple M1/Chrome runner (IF225).
2. **Beat both kernel strategies at *all* rule counts and tested scales** — the warm steady state, not just the few-rule case; generated Java remains the Groovy-tax-free algorithmic comparator, while neither kernel strategy may win a repeatable measurement.

These are **co-equal and must be gated separately**, because they measure opposite regimes and a win in one can hide a loss in the other — the index-build O(N²) (catalog #7) was invisible to the warm gate for exactly this reason. The current warm suite supplies broad complexity and tri-engine ratio evidence; `PerfGateTest.coldStartStaysSubQuadratic` supplies only a first-validation row-growth probe. Neither certifies the full NFR-S/P contract above. **Owner policy settled 2026-07-21:** promote no candidate number now; retain the isolated `scripts/perf.sh gate` path as the nightly/manual catastrophe and regression lane, and keep the complete IF172 collector manual for release or performance-relevant evidence.

The tension: goal 2 wants the per-call rule work eliminated (cache parsed ASTs, precompute scopes), but doing that *eagerly* at construction is exactly the cold cost goal 1 forbids. The resolution is **lazy memoization** — do the work once, **on first use**, then reuse (so the *constructor* is trivial and the first call is O(N), never O(N²)):

- **Prepare-once ASTs** (`DmInterpreter`): each rule's condition / computation's expression is parsed **lazily, exactly once** (a `lazy {}` per rule — SYNCHRONIZED, so the engine is thread-safe to reuse), then reused across every call and every row. The constructor only builds the wrappers (no parsing) → startup stays cheap, and a single-rule `testRule` forces only the one rule it touches. **This is the direct analog of the kernel's compile-once-at-model-load** — but lazy. *Caveat learned by measuring:* parsing turned out **not** to be the high-rule-count bottleneck (it didn't move the crossover), so this change is for startup + hygiene (it also removed a redundant double-parse), not the headline win.
- **Per-group row-context memo** (`Document`): `contextsFor`/`attachByDepth` did an **O(valued) attach-depth scan on every rule** (and every nested row). Since many rules share a handful of iteration scopes, and the document is immutable during a validation, this is memoized **per group inside the mutation-invalidated `Index`** — computed once per distinct scope, reused across all rules. **This *was* the lever**: ~24% faster across all rule counts, crossover pushed out ~2× (see the log). This mirrors the kernel computing the row structure once and reusing it across rules.

**Historical measurement (2026-06-24, the log below; not NFR certification):** engine build was ~1.5 ms (lazy — just the AST wrappers), first `validateFull` ~57 ms on a 48-rule model (one-time lazy index build + first parse), then steady-state. A single document stayed linear to 300,000 rows (~2.5 µs/row). `PerfScalingTest` is the opt-in reporting harness for those numbers; it has no NFR assertions.

**Historical first-validation spectrum (2026-06-25, `coldStartupSpectrum`; not NFR certification):** **37 ms** (6 rules) → **62 ms** (48) → **126 ms** (192) on a ~500-row document, and **85 ms** (10,000 rows) → **495 ms** (100,000 rows) at one rule. The helper used one fresh engine/document per sample but started timing only the first `validateFull` after both had been constructed; the sweep used one sample per point. It demonstrates plausible absolute latency and near-linear first-evaluation growth, not p95 or end-to-end startup. We do not compare it with kernel codegen (non-negotiable #2); the no-codegen property is a native/JS capability, not a timing race.

## Where the kernel *used to* win (the crossover — closed 2026-06-26; was justified at the 2026-06-24 baseline)

The kernel's documented architecture is **compile-once codegen + per-run caches** (`IndexFieldCache`, `ValidationCache`, `CalculationCache`, `GroupFillCache`, `RepetitionNotUniqueErrorCache` — `kernel-core-runtime/_30_8/internal/core/`), plus short-circuit optimizations (BA doc: skip comparison rules when the root group is empty; cancel quantifiers early). So its edge is the **many-rules** regime: generated straight-line code beats a tree-walker's per-node dispatch + `Val` allocation, and that per-(rule,row) overhead accumulates with rule count.

This is **measured, not assumed** — the rule-count sweep (`KernelEdgeTest`, opt-in `-Dperf.edge=true`) finds the crossover where interp/kernel passes 1.0. The original crossover was **~96 rules vs Groovy**; the per-operation levers below (resolution caching + reduced allocation, NOT an eval-strategy change — see the next section) later produced fair generated-Java ratios of **0.40 firing / 0.52 low-firing at 192 rules** in the recorded 2026-06-27 run (the interpreter was faster in both).

**A codegen ceiling exists, but only for pathologically CONCENTRATED rules (2026-06-25, corrected).** The kernel's codegen splits its validator into methods **by error-field count** (10 fields/method Groovy, 50 Java), each holding all rules of its fields. So when **many rules pile onto few error fields**, they collapse into one method that can exceed the JVM 64 KB bytecode limit (`MethodTooLargeException`) — `manyRules` (rules on ~3 fields) trips this at ~512–768. With rules **distributed** across many fields, the recorded run compiled and measured through **1,000 rules**, so the concentrated failure is not a demonstrated general per-model ceiling. The evidence does not include the previously claimed 2,000-rule run. This is a reminder that generator method-size management is real work the interpreter avoids, not evidence beyond the measured counts. *Hint: also split by an estimated per-method statement/rule budget, not field count alone, so a concentrated model degrades into more methods rather than failing to compile.*

### Code-generator row-axis scaling — super-linear past ~10 000 rows (a kernel-side observation, 2026-06-27)

The generated validator scales **super-linearly on the row axis past ~10 000 rows — even compiled as Java**: for a single per-row rule, generated Java measured **766 ms@10k → 4211 ms@20k** (≈5.5× for 2× rows), and dynamic Groovy is worse (**755 ms@10k → 14 190 ms@30k**). The interpreter on the identical workload is flat (~0.002 ms/row — the flip side of the ~50×/165× data-axis ratios in the results log). The cause is unverified from outside, but the shape is consistent with **eager per-row allocation of validation-result objects → heap/GC pressure that compounds with row count**. This is the most impactful kernel-side perf opportunity the comparison surfaced, and the sibling of the 64 KB ceiling above. *Hint for a kernel-side fix: profile a 50k-row single-rule validation for allocation/GC; consider pooling, lazily accumulating per-row results, or streaming message emission so the row axis stays linear.*

### Eval-strategy was NOT the lever — the per-operation cost was (measured, 2026-06-25)

An early hypothesis was an **eval-strategy ladder** (compile-to-closures → partial-eval → bytecode VM → vectorize → cross-rule CSE → runtime JIT), the Futamura idea of specializing the interpreter to the model. A closure spike measured ~2.5× **on the firing-eval in isolation**, which looked decisive. **It wasn't:** productionized as a sealed compiled-node engine ("Layer 1"), it measured ~**7% end-to-end** and was reverted — `firedType` is only ~7% of `validateFull`, so an eval-strategy change can't move the dominant cost. The real per-operation levers were **resolution caching** (per-row `placeCache`/`valCache`, and the call-local complete `FormalResultCache` that evolved from the original code-only `formalErrorAt` memo) and reduced allocation, which **beat kernel-Java at 192 high-firing** — see "Kernel optimizations from SOURCE" below + the results log. The full SOTA research that informed the ladder (closures-vs-bytecode, Truffle warmup, vectorization, AOT/JS facts) and the rejected approaches are archived in [`archived/INTERPRETER-PERFORMANCE-DESIGN.md`](archived/INTERPRETER-PERFORMANCE-DESIGN.md). The two-phase short-circuit was re-measured after the resolution caches landed and rejected again; the lazy-polarity single walk captured its useful half. Reconsider it only if a future compiled/straight-line dispatch materially changes the second walk's cost.

### The kernel's per-run caches → where the interpreter is naive (the optimization map, 2026-06-24)

The crossover is the *constant-factor* gap. An **O(N²) cliff** (the kernel has a cache, the interpreter does a per-call scan) is the *steeper* danger — but **do not dismiss a constant factor as "not a cliff"**: a per-(rule,row) redundancy is a **~rules× constant** that, at 192 rules, dominates (the `ValidationCache` "repeated field reads" row below was mis-triaged exactly this way — parked as "not a cliff," it turned out the largest remaining gap). The discipline for **both**: check the interpreter's analog and **measure at real rule counts**, not assume. Read the kernel source **for the mechanism, not the expression** (clean-room): the *idea* — index by key, memoize group-fill, **resolve a field once per row** — is reproduced in original Kotlin.

- **The computation cascade** (a computed field referencing another): the interpreter was **silently wrong** (read the stale operand → wrong value). Now **fixed** — `compute()` orders by dependency and reads prior results via a side-effect-free overlay, matching the kernel.

Across those passes we mirrored the remaining kernel-cache analogs clean-room on the measured common raw-validation paths (semantic index catalog #4/#10, repeatable group fill #6, cold-path build #7, non-repeatable group fill #8, the cascade, and the parallel-iteration outer join), leaving no known quadratic cliff in those specific raw scenarios. The broader source audit also found semantic gaps outside these performance cases; [INTERPRETER-GAPS.md](INTERPRETER-GAPS.md) is authoritative. The lesson: a tree-walker is not inherently fast or correct at the edges—you earn both by indexing/ordering exactly where the kernel does, probing which shapes are valid, and failing loudly on anything not yet supported.

## How the kernel's GENERATED code evaluates a rule — and what the interpreter can mimic (2026-06-25)

A deep read of the kernel's **generated Java** validator (dumped for the `manyRules` shapes + an `Or` and a 3-way `And`, via `generateValidationCode(…, JAVA)`) shows *exactly* where its per-operation edge comes from — and confirms the owner's intuition that it's **mimickable with tree-walk techniques, no codegen needed.** (Mechanism described in our own words + stylized pseudocode; the verbatim generated source is not reproduced — license-safe rule.)

**The generated shape — one rule = one method, a two-phase body.** Each rule compiles to a method that iterates its scope and, per row, does:

```
for (row in iter) {                                  // the rule's iteration scope (cached repetitions)
  if ( fieldsGiven(Qty).isKnownAndTrue()             // PHASE 1: short-circuit BOOLEAN guard —
       && compare(GT, num(Qty), num(Amount))         //   Java && / || ; reads only .isKnownAndTrue();
            .isKnownAndTrue() ) {                     //   later operands skipped once firing is decided
    var tb0 = fieldsGiven(Qty);                       // PHASE 2 (only inside the if = only when it FIRES):
    var tb1 = compare(GT, num(Qty), num(Amount));     //   RE-evaluate operands, build the typed results,
    var v   = tb0.combineUND(tb1);                    //   combine (UND for And, ODER for Or) to get polarity
    addMessage(errorField, row, code, v.fehlerType());
  }
}
```

**The two structural differences from our tree-walk** (both confirmed across `And`, `Or`, `Cmp`, `FieldFilled`, `Sum` — the pattern is uniform; only the combine differs per operator: `combineUND` ↔ our `And` type rule, `combineODER` ↔ our `orType`):

| | kernel generated code | interpreter (`Interpreter.firedType` → `evalTypedLazy`) |
|---|---|---|
| **firing decision** | **short-circuits** — `a.isKnownAndTrue() && b…` / `|| ` skips later operands (and *their* whole evaluation) once the result is forced | validation's `firedType` stays strict — `evalTypedLazy` evaluates both branches; compute preconditions use IF85's kernel-exact short-circuiting `evalCond`, and compute-mode fill quantifiers use ordered early-stopping scans |
| **polarity (VALUE/OMISSION)** | computed **only when the rule fires** (the `combineUND/ODER → fehlerType()` is inside the `if`) | computed only for **TRUE nodes** — a non-firing root skips polarity, while a firing row gets truth + polarity in one walk |
| **index/reps** | primitive `long[]` (no boxing) | boxed `List<Int>` keys, but resolved once per path in each `RowContext`; primitive reps are an unproven, trigger-gated candidate |
| **dispatch** | generated straight-line calls (no per-node `when`) | AST re-walk per node — **NOT the lever** (a JFR profile, task #64, put the whole eval at ~3–4%; the compiled-node engine that targets this stays unbuilt, twice-rejected) |

**Why this matters for the profiler hotspot.** The profiler put **eval-proper at ~181 ms** (low-firing, the residual after the `formalErrorAt` memo): `ctx.field` + `Val` allocation + the walk **+ the polarity (`leafType`/`fill`)**. The kernel pays the polarity **only on the rare firing rows** and **skips whole operands** via short-circuit; the interpreter *used to* pay polarity on **every** row. In the realistic **low-firing** regime (valid documents — most rules pass) this was pure waste: e.g. `FieldFilled(Qty) And [Qty] > 50` with a small `Qty` evaluates `FieldFilled` (true) then the comparison (false → no fire), and the interpreter *also* computed the comparison's `leafType`/`fill` polarity that is then discarded. **Closed 2026-06-25 (task #62)** by the **lazy-polarity single walk** (`evalTypedLazy` — polarity only on TRUE nodes). The validation-rule *short-circuit* half (skip whole operands) remains the kernel's; computation preconditions separately gained kernel-exact short-circuiting in IF85. For this benchmark's `FieldFilled(true) And …` shape there is nothing to short-circuit, so the polarity skip was the lever.

**Per-operand primitive cost is ~equal — it is NOT the lever.** `controller.vergleiche(…)` builds a `ValidierungsErgebnis` (truth **+** `fehlerTyp`, eager — set in its constructor) and `feldWertAlsZahl` returns an allocated decimal — the same order of work as our `evalCmp` + `leafType` + `Val.Num`. So polarity is eager in *both*; the kernel's win is **not** a cheaper leaf, it is **(a) not running the leaf at all when short-circuited, and (b) not combining/typing on non-firing rows.**

**The mimic that was tried — a two-phase tree-walk — REVERTED TWICE, then beaten by a lazy single walk (measured 2026-06-25).** The natural validation-rule mimic is two-phase: Phase 1 a truth-only `evalCond` (no polarity); Phase 2 the typed `evalTyped` **only when fired**. Measured both pre- and post-`placeCache`/`(C)` (bias #5): a noise-free in-run A/B re-rejected it **both** times — pre: +1.16× low-firing / −1.5× high-firing; post-(C): +4% low-firing / −6.5% high-firing. The reason is the **second walk**: the kernel affords its two-phase because Phase-2 (`combineUND`) is cheap *straight-line generated code* over cached leaves; the interpreter's Phase-2 re-**traverses** the AST and re-**evals** the leaves (and would double-invoke a `CustomCondition`), costing more on firing rows than the polarity-skip saves. **The fix is to keep ONE walk but make the polarity LAZY** — `evalTypedLazy` computes a node's type only when its truth is TRUE — which gets the non-firing skip with **no** second walk. Measured faster in **both** regimes; adopted (task #62 in the results log). **Lesson:** the kernel's *two-phase structure* is not the validation win — a tree-walk cannot make the second walk cheap; the extractable win is "don't *type* what doesn't fire," and that fits in a single lazy walk. Validation still evaluates both logical operands; computation preconditions use IF85's separate short-circuiting `evalCond` because poisoning makes their read order observable.

**What this means for the real lever.** The against-kernel low-firing sweep (`KernelEdgeTest.ruleCountCrossoverLowFiring`) shows the kernel's per-operation edge is **largest in the realistic valid-document regime** (192 rules: interp/java **≈1.70** low-firing vs ≈1.16 high-firing — the kernel drops far more when rules pass, via short-circuit + no message-building + straight-line). So closing the gap requires **cheaper per-operation eval**, not an eval *restructure*. Potential directions are (a) **compiled/straight-line dispatch** (the Layer-1 sealed-node engine measured ~7% alone, but it is the prerequisite that could also make two-phase worthwhile), (b) a primitive repetition-key representation if a fresh allocation profile earns its correctness risk, and (c) **vectorized columnar eval** for the rows axis. These are profiling candidates, not current gap-ledger commitments; the structural mimic alone is not enough.

**Conclusion at the 2026-06-25 measurement point (refining the owner's assumption).** The experiment showed that mimicking the generated structure (short-circuit + two-phase) was **only potentially worthwhile on top of cheap dispatch**; bolting two phases onto the tree walk regressed the firing-heavy case. Later resolution-cache and allocation work reached and then beat the recorded fair generated-Java ratios without compiled dispatch, unboxed repetition keys, or vectorization. Those mechanisms are therefore profile-earned future options, not the current “path to parity”; a two-phase validation walk should be reconsidered only after a materially cheaper dispatch changes its measured economics.

## Kernel optimizations from SOURCE — mechanism, interpreter analog, and the biases to re-check (2026-06-25)

After the `ValidationCache` mis-triage (I had it in my own table, dismissed it on a wrong verdict, and only the profiler forced the revisit), I stopped reasoning about the kernel's optimizations from memory and **read the runtime + codegen source** (four parallel deep reads: the per-run caches, the short-circuits/pruning, the codegen rule structure + eval primitives, the index/value representation). This records *exactly why and how* each kernel technique works, the interpreter's **true** status (not the assumed one), and — the durable part — **the biases that hid the gaps**. This is iterative: re-read the source and re-run this checklist whenever a new perf problem is learned.

**Correction to a prior mental model (a bias, below): the kernel's value store is itself a `HashMap`, not array-indexed storage.** Its per-row cheapness comes from **memoization (the caches) + iteration pruning**, NOT contiguous arrays. The interpreter's `Map`-keyed `Index` is already kernel-aligned — *don't chase a column-store rewrite*; port the cache/pruning mechanisms that measurements justify, and consider primitive repetition keys only when a fresh profile earns that representation change.

### The biases to re-check (the durable lesson)

Each one already caused, or nearly caused, a mis-triage. Run this list when a new perf problem appears:

1. **Cliff-hunting** — "an O(N²) cliff is the danger; a constant factor isn't." A per-(rule,row) redundancy is a **~rules× constant** that dominates at high rule counts. *(Mis-triaged `ValidationCache`.)* → measure constant factors at real rule counts, not just complexity class.
2. **One-cache-one-analog** — "six kernel caches ⇒ six interpreter analogs." `USBIndexCache` → zero (legacy); `RepetitionNotUnique` → a *better* algorithm. → **match the result/behavior, not the data structure.**
3. **Map-vs-array** — "the kernel is fast because it stores values in arrays." It uses a `HashMap` too; speed = memoization + pruning. → don't rewrite the store; port the caches.
4. **Elegant-single-walk** — the original eager `evalTyped` walk (truth+polarity per node) was *tidy*, which hid that it did the kernel's expensive phase-2 work on every non-firing row. The shipped `evalTypedLazy` single walk closed that waste by typing only TRUE nodes, without paying for a second walk. → tidiness is not the goal; measured laziness is.
5. **Measured-once-settled** — a rejected optimization can become viable after a *related* change. The two-phase was re-measured after `placeCache` changed the cost structure and still lost; record both results, and reopen it only after another material prerequisite such as compiled dispatch changes the calculus. → **re-measure rejected optimizations when the cost structure shifts, then close the question when it does not.**
6. **Cross-run-noise** — a 20% kernel-Java shift between runs hid/faked wins (Layer 1 looked like noise; the placeCache magnitude was confounded). → use the **within-run ratio** (interp/kernel-Java in the same run) or an **in-run A/B toggle**, never cross-build absolutes.
7. **High-firing-benchmark** — the only against-kernel sweep was high-firing (`perfValues`), which hid that the kernel's edge is *largest in the realistic valid-document (low-firing) regime*. → always measure both regimes.
8. **Resolved-on-demand-is-fine** — "lazy per-call resolution is cheap." It's cheap *once*; re-done per accessor per operand per rule per row it's the dominant cost (`placeCache`). → measure the *redundancy*, not the single call.
9. **Allocation-blindness** — counting lookups/dispatch but not the per-op object churn (`Val`+`Fill`+`Res`, boxed reps). The kernel interns results + packs polarity. → count allocations on the hot path.

### 1. Non-quadratic `Document` (the foundation, task #28)

- **Rationale.** The general `Document` stored placements in a `List`; every `field`/`filled`/`displayValue`/`star`/`groupFilled` did a linear `firstOrNull{…}` scan, so per-row evaluation was **O(N²)** — 100k rows could not even run (a quadratic JS document blew the 2 s test timeout at 20k).
- **Implementation.** A lazily-built, **mutation-invalidated `Index`** maps `(path, reps) → placement` and `groupPath → rows`; lookups become O(1)/O(rows). Each row's `evaluated` flag is computed in **one amortized pass** over the **content-bearing** placements — `Index.content` = a valued field OR an instantiated repeatable-group row (IF53), so an all-field-empty-but-instantiated repeatable row counts as content exactly as the kernel's `GroupFillCache` does. It stays **one pass, O(document), memoized per group** (the same `content` list also feeds `GroupFilled` on a non-repeatable group and requiredness — one build, three consumers). `autoGroup` dedups via a set, and IF276's V2 predecessor materializer advances one high-water mark per concrete parent scope, so sparse or sequential placement emits every required group row exactly once instead of revisiting `1..n` for each field. `DocumentPlacementsSnapshotTest` locks the work count at 10,001 distinct group emissions for two fields across 10,000 rows. Re-measured 2026-07-06: the earlier content extension is **perf-neutral** — B1 per-row, wide sibling-groups, and the constrained-field formal check all stay linear (~4× growth for 4× rows), gated by `PerfGateTest`.
- **Example.** B1 — a per-row `[Qty] > 50` over N `/Perf/Lines`.
- **Results & discussion.** Linear: **300 000 rows at ~2.5 µs/row**. This is the prerequisite every later optimization builds on — without an O(1) value store, nothing else matters.

### 2. Prepare-once ASTs (lazy parse cache)

- **Rationale.** Before this optimization, every `validateFull` re-parsed each rule's condition—in fact **twice** (`repetitionNotUnique` + `rowOutcomes`). The hypothesis (task #31) was that this per-call re-parse caused the many-rules slowdown.
- **Implementation.** A per-rule `lazy {}` (`SYNCHRONIZED`, so the engine is thread-safe to reuse) AST wrapper, built in the constructor **without parsing** (→ fast startup); the first use parses and caches, every later call/row reuses. A single-rule `testRule` forces only the rule it touches.
- **Example.** B6 / `manyRules(N)` in repeated-eval (engine reused over many documents).
- **Results & discussion.** **Honest negative result:** parsing was *not* the bottleneck — the crossover did not move. The value is **startup + hygiene** (it also removed the redundant double-parse). The lesson — *measure before assuming* — is why the next optimization was found by profiling, not guessing.

### 3. Per-group row-context memo

- **Rationale.** `contextsFor`/`attachByDepth` did an **O(valued) attach-depth scan on every rule** (and every nested row). Many rules share a handful of iteration scopes, so this was O(rules × valued) of pure recomputation.
- **Implementation.** Memoize `contextsFor` and `attachByDepth` **per group** inside the `Index` — computed once per distinct scope, reused across all rules. The clean-room analog of the kernel computing the document's row structure once and reusing it.
- **Example.** B6 — 12 rules over ~3 distinct scopes (`/Perf`, `/Perf/Lines`, `…/Subs`).
- **Results & discussion.** **~24 % faster across all rule counts**; crossover vs Groovy moved **~48 → ~96 rules**. This was the first real lever (vs #2's null result — bare: scheme unrecoverable from context).

### 4. Row-prefix index (the semantic-index / star cliff — the steepest)

- **Rationale.** `starRows` did an **O(all-rows) `.filter` per call**; inside per-row iteration (a semantic index `[F For "v"]`, or a cross-level star aggregate) that is **O(rows²)**. Measured genuinely quadratic (growth ×3.5 per doubling, the interpreter's lead collapsing 0.17→0.66 over 500→4000 rows) while the kernel's `IndexFieldCache` stayed linear and **won at scale** — the proof that the kernel's optimization is well-founded.
- **Implementation.** The `Index` indexes each group's rows by **every prefix of their rep tuple** (built once, dropped on mutation); `starRows` is then an O(1) lookup. The clean-room `IndexFieldCache`/row-index analog — the *idea*, in original Kotlin.
- **Example.** A per-row rule `FieldFilled(Amount) And [/Perf/Lines/Amount For "NOMATCH"] > 0` (`PerfCatalog.semanticIndexPerRow`).
- **Results & discussion.** **98 ms → 6.8 ms at 4000 rows**; linear again (growth ~×2/doubling), pulling *ahead* of the kernel (ratioG 0.66→0.04). Guarded against regression by `PerfGateTest.semanticIndexStaysSubQuadratic`. Also fixes any cross-level star aggregate evaluated per row (e.g. a per-Line `Sum(Subs* / Cost)` at scale).

### 5. Single typed walk per row (no double AST walk)

- **Rationale.** `rowOutcomes` called `fires()` (a Tri-only walk via `eval`) **and then** `firedType()` (a typed walk via `evalTyped`) — **two full AST walks on every firing row**. But `evalTyped` already yields the truth value, so the second walk is redundant.
- **Implementation.** Call `firedType()` **once**: non-null ⟺ the rule fires (`truth == TRUE`), and the value *is* the polarity (VALUE/OMISSION). A firing row now costs one walk, not two.
- **Example.** B6 / `manyRules(96)` — 45 480 firing rows, each previously walked twice.
- **Results & discussion.** Crossover vs **kernel-Java reached parity at ~96 rules (ratioJava 0.99)**; the 192-rule gap narrowed **1.30 → 1.19**. The win scales with the firing ratio (no help for all-passing documents — those already walked once).

### 6. O(1) repeatable-group fill

- **Rationale.** `groupFilled`'s repeatable-group branch did `reps in rowsOf(group)` — an **O(rows) `List` membership** — so requiredness over a **sparse-required** document (many empty required fields, each triggering a `GroupFilled` check per row) was **O(rows²)**. The `GroupFillCache` analog (the repeatable half).
- **Implementation.** O(1) membership via the row-prefix index (`rowsWithPrefix(group, reps).isNotEmpty()`).
- **Example.** A form with many empty required fields across N rows (every empty field triggers the per-row group-fill check).
- **Results & discussion.** Removes the latent requiredness O(N²). (The *non-repeatable* `GroupFilled` branch was the sibling — now fixed too, catalog #8.)

### 8. O(1) non-repeatable group fill

- **Rationale.** `groupFilled`'s non-repeatable-group branch scanned `index().valued` and tested each descendant's scope — **O(valued) per call** → O(rows × valued) when a model has `GroupFilled(nonRepeatableGroup)` checks per row. The other half of the `GroupFillCache` analog (catalog #6 did the repeatable half). It looked hard because the scope depth varies with the rule's iteration group.
- **Implementation.** A per-`(groupPath, group)` **attach-depth index** over the valued *descendants* of `groupPath` — exactly the `attachByDepth`/`contextsFor` shape (group descendants by their `commonPrefixLen(p.path, group)` depth, store the prefix set), memoized in the `Index`. `groupFilled` then checks `rowReps.take(d)` against the set at each depth — O(1) per call after a once-per-`(groupPath, group)` build. It mirrors the old per-descendant scope check exactly, so behavior is unchanged (the dead `inScope` helper was removed).
- **Example.** A per-row rule `GroupFilled(SomeNonRepeatableGroup) And …` over a large document.
- **Results & discussion.** The non-repeatable `GroupFilled` path is now O(1)/call — no O(N²) left in either `groupFilled` branch. Full `:adapter` differential suite green (`GroupFilledDiffTest` + the requiredness/index-field law tests confirm behavior unchanged). With this, **no known O(N²) cliff remains in the group-fill/raw-validation paths** (the row-prefix index catalog #4, the repeatable-fill #6, and this close out those kernel-cache analogs). Compute-overlay indexed columns and correlation buckets are now cached per computation step too (IF143, was IG60); the multi-star equality-correlation path graduated with its bind-depth-scoped hash join (IF144).

### 7. Linear index build (the cold-path / startup / JS cliff the warm harness never saw)

- **Rationale.** The `Index` build deduped group rows with `if (p.reps !in it) it.add(p.reps)` — an **O(rows) `List` membership per group placement → O(N²) to build the index**. The against-kernel harness *never saw it* (it measures **warm**, after the index is built once outside the timed region), so it hid behind that methodology — but **every COLD first `validateFull` pays it**: startup, the CLI one-shot path, and a single JS pass. It was the real reason a JS run blew up at scale (cold JVM @20k = 1.75 s; **JS @20k = 14 s**, super-linear).
- **Implementation.** Drop the check entirely: every group placement is **already unique** by `(path, reps)` because both `group()` and `autoGroup()` gate on the `instantiatedGroups` set before adding — so the `!in` scan was redundant *and* quadratic. A plain `add` makes the build O(N).
- **Example.** Any cold/first evaluation at scale — `DmInterpreter(model).validateFull(bigDoc)` on a fresh document; the CLI evaluating one large document; the JS `DocumentScaleTest`.
- **Results & discussion.** Cold build is **linear**: JVM @30k = 152–220 ms (was ~1.75 s at *20k*); **JS @10k = ~60–106 ms (was >2 s — it timed out)**. This is the **biggest win for startup and for JS**, both of which only ever run the cold path. The JS scaling guard (`DocumentScaleTest`) rose from 3k → **10k** (a scale that was *impossible* on JS before). A worked lesson in benchmark methodology: a warm against-kernel harness is right for steady-state but **blind to one-shot/startup cost** — measure the cold path separately (that is what `PerfScalingTest.startupCost` and the JS `DocumentScaleTest` now do).

### 9. Indexed `$` self-correlation (hash and ordered plans — IF47/IF159, 2026-07-06/2026-07-20)

- **Rationale.** A `$` outer-correlated filtered quantifier — `AtLeastOneFieldFilled(../G* / F Having [X] == [$X] …)` — is a **self-join**: for each of N outer rows, the naive strategy scans all N inner rows to find matches → **O(N²)**. Equality was the first hot shape; RV-2026-07-20-03 showed that treating a single ordering comparator as inherently pairwise was equally unsound.
- **Implementation.** `CorrelationJoin` recognizes a closed indexable boundary. Equality conjunctions use a **value-keyed bucket map** built once per `(group, scope)`, O(N) build + O(1) lookup. A single comparable field-to-outer-field `<`, `<=`, `>`, `>=`, or applicable `!=` uses a cached sorted distinct-value table with prefix `(t, f, n)` sums, O(N log N) build + O(log N) lookup. Both plans subtract the physical outer row when the `CurrentRepetition` self-exclusion applies and retain Unknown in neither truth bucket while preserving row count. Compound predicates, expression operands, unsupported kinds/non-UTC datetime ordering, and multi-star multi-row self-exclusion stay on the explicit general scan; they are fallback boundaries, not evidence that slowness is acceptable.
- **Example.** A rule iterating N `/Order/Items` rows, each firing on "another row shares this row's `Count`".
- **Results & discussion.** Equality evidence from 2026-07-06 remains ≈3.0 ms vs generated Java ≈8.8 ms at 400 rows and ≈6.3 ms vs ≈30 ms at 1600 rows. The 2026-07-20 all-equal `>` discriminator changed from ≈15.7× growth to 4.1× (2.2 ms@400 → 8.4 ms@1600) after the ordered plan. `OuterCorrelationPerfTest` checks complete interpreter/dynamic-Groovy/generated-Java signatures on those exact N/4N instances before timing. ### 13. Shared output projection for dense `RepetitionNotUnique` messages (IF191, 2026-07-21)

- **Rationale.** An all-duplicate N-row RNU rule legitimately returns N messages carrying N peer references each. The logical result is output-sized O(N²), but allocating and formatting N independent copies of the identical peer list is not required by that contract.
- **Implementation.** The call-scoped RNU cache formats and de-duplicates one immutable peer-pointer list per duplicate cluster. Row outcomes share it; a message with additional current-row references exposes a constant-size immutable joined view rather than copying the cluster. Canonical pointer strings live in the document's mutation-invalidated derived index and are reused by every message/formal path during the immutable validation call.
- **Results & discussion.** On the exact compact synthesized profile at N=100/400 (490/1,800 firings), interpreter medians were 16.85/27.28 ms versus dynamic Groovy 55.25/302.17 ms and generated Java 37.98/318.26 ms. Exact growth was 1.62× versus 5.47×/8.38×; the separate paired interpreter estimate was 3.95×. The same model, documents, fixed clock, custom callback, 12 warmups, complete outcomes, and both kernel strategies were used. This is same-run diagnostic evidence, not an IF137 promotion.

### 10. Document-level index-column state (IF116, 2026-07-10)

- **Rationale.** The IF107/IF115 indexed-read gates — and the older IF15/IF60 index-aware aggregate/quantifier classification — consulted the index column per LOOKUP: a fresh `starCells` list plus a fresh duplicate-value set per call. A `validateFull` over a per-row indexed rule therefore scanned the whole column once per row — **O(rows²)** with a heavy allocation constant. The gate's `semanticIndexStaysSubQuadratic` (N=20 000) deterministically stalled 20+ minutes; the master gate's independent perf re-run caught it (the drill session's own gate run predated IF115's wiring of the guard into the validation hot path — the lesson: a perf claim is only as fresh as the last hot-path commit it covers).
- **Implementation.** `EvalContext.indexColumn(path, bindDepth)` returns the raw `IndexColumn`: cells, duplicated values, and derived flags/tally, memoized per (column, star-scope prefix) at the document level. `Interpreter.indexColumnOf` is the complete call seam: when relevance or registered custom admission matters, it scans the identity-preserving raw cells once, applies relevance first and formal admission second, and memoizes the admission-aware typed column for the call. Validation shares it for the pass. Compute supplies a per-step memo shared across outer rows; the overlay bypasses only its own write column because that column changes as values land. Every indexed read, aggregate/fill classifier, and starred value-list expansion consumes this seam, so correctness did not reopen the O(rows²) scan.
- **Example.** A rule iterating N rows, each reading `[Price For CustomerClass]` against the same N-cell index column.
- **Results & discussion.** Semantic-index growth back in the linear band: 19.0 ms@5000 → 76.6 ms@20000, min-growth **4.03×** (pre-fix: unbounded — the N=20 000 arm alone ran 20+ minutes). All twelve growth checks 2.7–4.3× (linear ≈ 4). Correctness pinned unchanged by the six index differentials + the full suites — the fix is pure memoization.
- **Evidence.** [Checkpoint 2026-07-10 — the gate's first live catch](INTERPRETER-PERFORMANCE-RESULTS.md#evidence-10).

### 11. The compute-overlay read path (the estate's tightest cross-engine row, 2026-08-12)

- **Rationale.** The parity lanes (optimization-independent, IF281) exposed one row far tighter than the rest: `CO-correlation` — a per-Row `$`-equality self-correlation precondition under an ACTIVE cascade overlay — beat generated Java by only **1.6×**, against 5×–50× everywhere else, which is thinner than that row's own run-to-run noise. A margin thinner than the noise is not a margin. JFR on `compute` at N=800 found the cost in three places, none of them the algorithm: an operator lookup, the overlay's key handling, and a wrapper allocation.
- **Implementation, three independent fixes.**
  1. **`FunctionOp.byName` was a linear scan** — `entries.firstOrNull { it.kernelName == name }` over **53 entries with a string comparison each** — called from the expression evaluator on *every* evaluation of a node rather than once at parse time. `CurrentRepetition` sits at position 47, and the scenario's `Having` filter evaluates two of them per row pair. It is now a precomputed `Map<String, FunctionOp>`; `PredicateOp`, `ConstantOp` and `ValueListQuantOp` got the same treatment. The swap is only behaviour-preserving while `kernelName` is unique — `firstOrNull` returns the first match, `associateBy` keeps the last — so `OperatorLookupTest` asserts uniqueness rather than assuming it.
  2. **The overlay asked its question three times per read.** `field`/`filled`/`displayValue`/`cellState` each called a separate `poisoned` / `cleared` / `overlaid` helper, so one logical read cost three `repsOf` lookups, three `Pair` allocations and three hashes of a `Pair<String, List<Int>>` — whose `hashCode` walks the list. One `stateOf(path)` now resolves the cell once into a four-state answer, keeping the poisoned-beats-cleared-beats-overlaid order the helpers encoded.
  3. **The wrapped row contexts are shared per computation step.** `OverlayContext.rowContexts` re-wrapped *every* row in a fresh `OverlayContext` on every call, and `scanFilled` asks for them per outer row — O(rows) allocation per row. They are now cached in the per-step `OverlayViews`, keyed on the scope prefix rather than the bind depth, because different outer rows resolve one depth to different row sets. **This cache is safer than the value views beside it and needs no `selfTarget` bypass:** what it holds is *wrappers*, and a wrapper consults the live overlay on every read, so one handed out early in a step returns the cascade's latest answer exactly as a fresh one would.
- **Example.** `PerfCatalog.computeOverlayCorrelation` — `[C] := [Src]` guarded by `AtLeastOneFieldFilled(Row* then Src Having CurrentRepetition(Row) != CurrentRepetition($Row) and [Src] == [$Src])`, under a cascade that writes `C` per Row.
- **Results & discussion.** One isolated run, Apple Silicon. `CO-correlation` at N=800: interpreter **34.39 ms → 23.49 ms** and the worse-strategy ratio **0.63 → 0.42**, i.e. the margin **1.6× → 2.4×**; at N=200, `0.56 → 0.54`. Estate-wide the worst of 38 parity rows moved `0.63 → 0.54` (**1.6× → 1.9×**) and the median `0.17 → 0.14` (**5.9× → 7.1×**), with the growth band also tightening from `4.19×–6.40×` to `3.77×–5.43×`. In the profile `byName` fell from **7.7 % to 2.3 %** of samples. *(Superseded 2026-08-12, same day, by the checkpoint two entries below: this read "**The margin is still smaller than that row's own run-to-run noise** — `CO-correlation @200` spreads `1.90×` across three sequential isolated runs, against a `1.4×` margin at its worst observation". Both figures were taken on a cold first pair. Warmed, the row spreads `1.07×` with a `1.95×` worst-observation margin, so the margin now exceeds the noise — [IF282](INTERPRETER-FINDINGS.md#if282).)* The re-measurement on a comparative breach remains the backstop for that lane. ### 12. The parallel row context's per-path memoization (the sibling that never got it, 2026-08-12)

- **Rationale.** `RowContext` has memoized `repsOf` and the resolved placement per path since the task #64 profile, with a comment naming exactly why: the reps of a referenced path are deterministic in `(path, group, rowReps)`, and the same path is asked for many times per row — once per referenced field, again for the error pointer, again for the formal-cache key, again by the suppressor scan, with `field`/`filled`/`displayValue` each resolving independently. `ParallelRowContext`, written later for the outer-join iteration, is the same shape and never got any of it. - **Implementation.** Three memos by path (`groupOf`, `repsOf`, the placement) plus the group depths computed once per context, all deterministic in the context's immutable fields; the remaining path splits route through the document's `partsByPath` index rather than splitting a string. `resolved`/`resolvedDisplay` collapse onto the shared placement, so `field`, `filled`, `displayValue` and `messageDisplayValue` resolve a path once between them. Stable for the reason `RowContext`'s caches are: the document's structure is fixed for the length of a call, and a compute overlay changes values rather than rows.
- **Example.** `PerfCatalog.parallelFramed` — `/Plan/X/A ⋈ B` with `X` a repeatable frame; `PerfCatalog.parallel` — the plain two-group outer join.
- **Results & discussion.** Median of five sequential parity runs (`2026-08-12T004801Z`, `T004925Z`, `T005131Z`, `T005251Z`, `T005410Z`) against the three before them (`T001016Z`, `T001139Z`, `T001258Z`), same machine, all committed under [`perf-results/darwin-aarch64/`](../perf-results/darwin-aarch64/). **Not isolated, by their own records:** the five carry `loadAverage` `9.3 / 5.6 / 5.4 / 19.6 / 51.8` on eight processors against `6.2 / 4.7 / 4.2` for the three before them, so this violates the estate's own machine-to-itself rule. ## The harness (invest here — it pays off)

Not ad-hoc `measureTime` calls sprinkled in tests — a **proper, reusable harness**, because it does double duty: it **gates** regressions *and* it's how we **find** the O(N²) hotspots in the group machinery. Design:

- **`PerfScenario`** — the unit: a real DM-JSON model + an **instance generator parameterized by scale `N`** (build 1k/10k/100k rows *programmatically*, never commit giant fixtures) + the operation (`validateFull` / `compute`) + the correctness oracle. One scenario, run by both engines.
- **Three engine adapters behind one interface** — `InterpreterEngine` (`DmInterpreter`), `KernelEngine` (Groovy via `RuntimeLaws` → `IDocumentRtService`), and `JavaKernelEngine` (the fair generated-Java baseline). The harness lives in `:adapter` (the only module with the kernel), mirroring the `laws/` differential layout, under `…/perf/`.
- **Warm-measurement discipline** — per (scenario, N): **warm up** (discard JIT-warming iterations), then time `K` iterations; report **median** (robust) + min + p90, and the **ratio** `interp_median / kernel_median`. Never mix a cold sample into this warm-throughput result; NFR-S uses the separate fresh-process protocol above.
- **Correctness first** — assert `interp == kernel` on the scenario *before* trusting any timing (a fast-but-wrong path is not a win; reuse the differential comparison). The comparison is the fired-code **multiset** (a sorted `List`, not a `Set`), so a per-row firing-count mismatch is caught, not just a missing code.
- **Three run modes** — (1) **gate mode**: single document, loose bounds, CI-friendly, fails on a catastrophic/relative regression; (2) **repeated-eval mode**: the engine built once, M slightly-different documents looped (form-input / batch) — the reuse pattern the kernel's codegen + per-run caches are tuned for, reported per-eval; (3) **profile mode**: one scenario at high `N`, interpreter-only, verbose per-iteration stats, no assert — diagnostic hotspot evidence only, never comparative acceptance proof.
- **JVM tool choice** — start with this **custom integration harness** (whole-document evaluation is the real unit; warmup+repeats+median+ratio is the right rigor for it). Reserve **JMH** for a *specific hot inner loop* (e.g. `repsFor`/`starRows`) that needs sub-method attribution — add it only when a profile points there, not upfront.
- **JS throughput** — a Node-runnable large-`N` check on `jsTest` (the same `Document`, `measureTime`, no kernel) provides platform diagnostic evidence; without both kernel strategies it cannot prove the comparative acceptance target.
- **Output + baselines** — print a `scenario × N × interp_ms × kernel_ms × ratio` table and append machine-tagged baselines to the results log ([INTERPRETER-PERFORMANCE-RESULTS.md](INTERPRETER-PERFORMANCE-RESULTS.md)). The spec holds the method; the log holds the numbers.

**Built (2026-06-23, extended through 2026-07-21):** `adapter/src/test/.../perf/` — `PerfHarness` (the `PlacementSink`-driven scenario + a `PerfOp{VALIDATE,COMPUTE}` + the three engine adapters `Interpreter`/`Kernel`(Groovy)/`KernelJava` behind `PerfEngine`/`ReusableEngine` + `measure`/`runScenario`/`runRepeated`/`timeInterpreter`), `PerfCatalog` (single-sourced `perf.dm.json`, the current B-series scenarios including B9 Berlin, a parameterized `manyRules(count)`, and a fuzz scenario), `PerfGateTest`, `PerfBenchTest`, `KernelEdgeTest`, `PerfScalingTest`, and `PerfProfileTest`. `RuntimeLaws` is the shared kernel oracle; its build-once `KernelEngine` (Groovy) and `JavaKernelEngine` (the kernel's own validator compiled as Java—the Groovy-tax-free baseline) both expose fired/compute outcomes. `PerfRuntimeBindings` derives equivalent interpreter/kernel clocks and callbacks from one immutable source and fingerprints their stable contract ids. `pairedScenarioGrowth` tri-checks exact N/4N instances and applies the paired estimator to all three engines, failing on an interpreter loss at either scale, on a higher interpreter **per-unit cost** than either kernel strategy (`PairedAcceptance`), or on the interpreter's **own** CPU-clock N/4N growth reaching the catastrophe floor (IF279). `KernelJavaBaselineDiffTest` guards that the Java baseline fires identically to Groovy. Codegen is primed out of every timed region (non-negotiable #2). IF172 adds the structured local JVM/Node/native first-answer, warm-throughput, and fair-Java evidence lane. It remains manual evidence; `scripts/perf.sh gate` is the isolated nightly/manual catastrophe and regression lane.

**Model-driven seed generator + differential fuzz net — built (2026-06-23).** The instances are built by a kernel-free **`SeedGenerator`** (`…interpreter.gen`) through the `PlacementSink` seam, so the perf harness, the **differential fuzz net** (`InterpreterKernelFuzzTest` — the correctness twin of this perf differential), and the `dmtool model seed` verb all share one generator. **Both pieces have their own spec — [SEED-GENERATOR-FUZZ-SPEC.md](SEED-GENERATOR-FUZZ-SPEC.md)** (the generator's contract + the fuzz method, diverse model, value strategy, bug track record, and per-operator extension loop); this doc only consumes the generator for the perf scenarios.

Patterned seeding prepares each distinct model-static pattern once per generator (IF189). Increasing the document row count therefore multiplies value placements, not regex compilation, keeping document construction from contaminating the evaluation timing it feeds.

Profile-derived nested models use `SeedGenerator.populateExactLeafRows` for their `N`/`4N` axis. The method reaches the exact target cardinality by distributing quota over the selected group's repeatable ancestor chain within every per-parent declared cap; unrelated repeatables stay at a small explicit default. It refuses an impossible scale before mutating either engine's sink, so the benchmark cannot silently time an underfilled model or kernel-illegal excess rows merely because no individual group cap reaches `N`. The opt-in `:adapter:synthesizedModelPerfTest` lane has one closed registry for the committed compact, breadth-shaped, and depth-shaped synthesis-profile fixtures, treated here as diagnostic stress shapes rather than fidelity-certified calibration evidence; each entry binds its deterministic seed-42 synthesized leaf, expected complexity, and default N. It synthesizes the selected fixture into ignored test output before any evaluation clock, separately reports `ModelLoader` loading, interpreter construction, the exact-preflighted first answer, and warm evaluation, then runs the existing complete-result paired N/4N comparison against dynamic Groovy and generated Java. The external-model properties remain available for a focused JFR rerun. Runtime bindings and generated placements are fingerprinted, and every row carries complete scale identity (IF192). This workflow is diagnostic and opt-in; it promotes no NFR number or CI gate.

COMPUTE comparison also normalizes result granularity before asserting or timing a result. The interpreter reports every computed instance while the perf differential compares at the kernel result's change projection (input deltas only; the full `IDocumentComputationResult` has five channels — KERNEL-FINDINGS §11), so the interpreter performance instance records the generated placements and prepares their immutable pointer→seed lookup with the reusable document outside the clock. Every run still times computation, complete signature materialization, delta filtering against that lookup, and sorting (IF197/IF199). This prevents a computed STRING that equals its generated seed from becoming a phantom interpreter-only result without charging the interpreter repeatedly for input-static preparation neither kernel adapter performs.

## Architecture direction (owner hint, 2026-06-23 — keep in mind)

A structural optimization to design toward (not yet committed work):

- **Decouple eval from a hierarchy — a flat, indexed instance is enough.** The validate/compute API only ever asks "the value for `(path, repetition-indices)`", so the instance backing store can be a **flat `(path, reps) → value` map**, not a tree (this *is* the task-#28 index, promoted to the primary representation). Group membership and iteration scopes come from the **model** (stable), not from walking an instance tree.
- **Prepare the model once; reuse across runs—and prove the boundary deterministically.** `ParsedModel` parses each stored rule/computation lazily once per MODEL (owned by `PreparedModel` via `ModelStaticPlans`, IF251); `PreparedModel` reuses the resulting rule/computation plans; IF164's engine-owned registry compiles each distinct condition/declared/predefined/computation pattern once; and the whole-model dependency order plus each requested computed field's transitive closure are cached per model (IF251). `PreparationWorkCounterTest` locks the exact JVM+Node work classes and proves that different documents and repeated `validate`/`compute`/`computeField` calls add no model-static work (IF171). Date-format preparation remains owned by its semantic feature work rather than being inferred from this structural counter. Shape: `val engine = DmInterpreter(model)` built once → loop `engine.validate(document)` / `engine.compute(document)`.
- **The caching boundary is ownership, not “value-independent only.”** Model-invariant artifacts (parsed ASTs, scopes, field metadata, dependency order) may live on the engine. Value- and structure-dependent indices/results are also encouraged when they accelerate evaluation, but they belong on the `Document`/its mutation-invalidated index, one validation call, or one row and must be discarded or invalidated with that owner. Never reuse a value-dependent result across a changed document. Fixed (IF142): `rowContextsCache` and `correlationBucketCache` are cleared with `cachedIndex` by one invalidation method on `Document.add`.
- **Open question (deferred):** between runs, do only *values* change, or also the set of repetition *rows* (add/remove)? If values-only, the structure index is reusable too; if rows change, rebuild the value store per run and reuse only the prepared model (the safe default). Decide when this is picked up — profile first.
- **Beyond prepare-once — Excel-style *incremental* recalc (deferred, trigger-gated):** recompute only a changed cell's dependent closure instead of re-running the whole document. Feasibility + the DEFER decision + the two-part re-open trigger are recorded in the archived [INCREMENTAL-EVAL-PROPOSAL](archived/INCREMENTAL-EVAL-PROPOSAL.md). The prepared model above is its prerequisite substrate; the incumbent kernel does recompute-all-per-run + per-run caches, *not* cross-edit dirty propagation.
- **Study the kernel's data representation + caches for INSPIRATION (not a copy — the license boundary holds: read for comprehension, write original).** The kernel devs spent *years* optimizing; its instance representation and its caches — `IndexFieldCache`, `ValidationCache`, `CalculationCache`, `GroupFillCache`, `RepetitionNotUniqueErrorCache` — encode hard-won structure (index-by-field, memoized group-fill, cached calculation results within a run). **Do not assume a naive fresh impl will be anywhere near kernel performance.** Get informed by what they cache and how they index, reproduce the *idea* in original Kotlin, and let the against-kernel benchmark (task #29) tell the truth. Humility + measurement, not confidence.

The complete gate measured **4m44s** on 2026-08-13 Apple Silicon once it began selecting the whole routine tier by tag (3m59s on 2026-08-09, when it ran two classes), still well under the ~10-minute agent-harness background cap that motivated the split — the 2026-08-13 routine-gate-cost checkpoint in [the results log](INTERPRETER-PERFORMANCE-RESULTS.md) carries the before/after. Push/PR CI does **not** run it; the dedicated `nightly-performance.yml` workflow invokes this exact launcher on its schedule and on `workflow_dispatch`, without repeating deterministic correctness/fuzz/demo gates. The launcher targets the single-fork `:adapter:perfGateTest`; that task always runs and is excluded from the Gradle build cache, while compilation and dependencies remain reusable. The isolation is semantic, not merely faster: `:adapter:test -PrunPerf` includes unrelated perf classes and can schedule them on parallel forks while a gate observes its small/large pair, so it is a manual all-perf sweep rather than a valid routine-gate invocation. `PerfBenchTest` (`scripts/perf.sh bench`) holds the **kernel-ratio benchmark sweeps**: the closed B1–B8 set, the B9 Europe/Berlin + UTC pair, compute/tiered/parallel, and repeated-eval. Each included catalog row performs dynamic-Groovy and every proven-applicable generated-Java evaluation plus complete semantic agreement before timing; inability to exercise an applicable strategy is a harness gap, not a passing exclusion. Run the tier at perf-relevant checkpoints (a hot-path change, a release). Shared trips live in `PerfBounds` so the tiers can't drift. `gate` accepts a method pattern (`scripts/perf.sh gate 'semanticIndex*'`); `bench` accepts one exact inventory id (`scripts/perf.sh bench B9-berlin-datetime`) and fails on an unknown id.
- **Build BOTH engines once, and check that each side pays the SAME setup (IF255, 2026-08-08).** The `PerfHarness` engines already do this; a guard written *outside* it must not use a convenience helper as its timed baseline. `RuntimeLaws.messagesPart`/`messages`/`compute(String, Doc)` now reuse a bounded engine keyed by exact model JSON, but still reconstruct and convert the V1 document on every invocation. Before the shared engine cache, the convenience path additionally expanded the model and constructed both service factories per call, inflating a real 7.17× into a reported 19.57×. The test to apply is not "is the timed region small" but "does each side pay the same setup": per-call work the interpreter also repeats, such as relevant-pointer conversion against its own per-call relevant-set indexing, belongs *inside* the clock because symmetry is what makes the ratio mean anything.
- **Entry-point coverage reconciles two DERIVED sets, not a list (IF254/IF263, 2026-08-08).** `PerfOp` models `validate` and `compute` only, so the scenario sweep cannot reach the other six `DmInterpreter` methods that evaluate over a `Document`; four of them had no timing test at all until this was measured. `InterpreterPerfCoverageTest` reflects those entry points and independently derives coverage from `@TimesInterpreterEntryPoint` on JUnit-discovered timing tests carrying a performance-lane tag — either tier, since `PerfBenchTest` owns the `compute` declaration and is checkpoint-tier; an *untagged* claim stays rejected, because no lane selects it. - **`PerfBounds.MIN_KERNEL_ADVANTAGE` (1.5) is a conservative FLOOR, not a target (owner, 2026-08-07) — higher is always better.** The entry-point guards trip below it via `KernelAdvantage`. It **supersedes nothing and must never be used to relax a stricter limit**: the standing development acceptance rule above still requires beating *both* kernel strategies at every scale with a per-unit cost no higher than either (IF279), and `PerfHarness.requireInterpreterBeatsBoth` plus `PairedAcceptance` enforce those two on the comparison path. Two precisions that are easy to lose. **(a) Strategy:** these guards drive `RuntimeLaws.kernelEngine`, so the floor is against *dynamic Groovy* alone and says nothing on its own about the faster generated-Java strategy. **(b) Headroom is not slack:** the guarded entries measure 3.2×–16×, so a fall to 1.6× would clear the floor and still be an active defect under the standing rule. Read the polarity against the neighbouring `RATIO_CEILING`, which is its inverse — interp/kernel and *loose* (5.0 tolerates the interpreter being five times slower), a backstop against a large relative regression that never expressed a target. The sweep tiers still trip on `RATIO_CEILING`; retro-fitting a floor onto their twenty scenarios is separate work and is not claimed here.

- **What counts as a performance test — the classification, and the two lane tags that carry it (owner policy, 2026-08-13).** Performance is priority #1: a **release is blocked** on regressions with full coverage, and **ordinary pushes are covered by the nightly** with full coverage. One question decides a class's lane — *does it assert on a measurement of the machine (a clock or retained heap)?* — because that is exactly the property that makes a result invalid under the broad suite's 2–4 parallel forks. A semantic or structural assertion survives contention; a timing one does not.

  | it asserts… | tag | where it runs | classes |
  |---|---|---|---|
  | a clock/heap measurement, routine tier | `perf` | `scripts/perf.sh gate` → the single-fork `:adapter:perfGateTest`, **tag-selected**; nightly + the release gate | `PerfGateTest`, `KernelParityGateTest`, `CharsetPerfTest`, `CustomTypePerfTest`, `GroupScopedFillPerfTest`, `OuterCorrelationPerfTest`, `PatternPerfTest`, `EntryPointPerfTest`, `PartialSumOfProductsPerfTest` |

  | semantics, structure, or the harness's own rules | *none* | the ordinary suite, every push | **41** of the 61 test-bearing classes in `adapter/…/perf/` carry no tag at all — `PerfAnchorBudgetTest`, `GrowthFloorRetryTest`, `PairedAcceptanceTest`, `SteadyStateWarmUpTest`, `PerfMarginBandTest`, the `*ScriptTest` guards, `InterpreterPerfCoverageTest`, `PerfPreflightTest`, `PerformanceScenarioEligibilityTest`, … (13 carry a perf tag — the routine tier's `PartialSumOfProductsPerfTest` sits in `laws/` for oracle visibility — and 7 carry `fuzz`/`kernel-probe`) |

  **The denominator, and what it does NOT cover** *(corrected 2026-08-13 after review — the first version of this paragraph claimed these 14 were "the whole timing estate", and it was wrong twice over)*. They are the whole timing estate **of `:adapter`**. Two corrections, both found by widening the sweep past the JVM clock APIs it originally used:

  - **`DocumentScaleTest` does read a clock.** The claim that it "reads no clock at all" came from sweeping for `nanoTime`/`currentTimeMillis`/`Date.now`/`performance.now`; it uses Kotlin's `measureTime` and asserted `elapsed < 20.seconds` on two 10 000-row scenarios. Generous, but a wall-clock bar.

Its recall limit stands, and it is exactly what let the first version through: it finds a *named* clock read, so a bar built on a helper that hides one behind an unmatched name stays invisible. Why it is syntactic is a reproducible fact, not a claim about abandoned attempts *(restated 2026-08-13 — the first version said "every text detector that was tried leaked in both directions", which preserved no case anyone could re-run)*: a detector keyed on the four bar-asserting helpers over the current tree admits `PerfAnchorBudgetTest`, `GrowthFloorRetryTest`, `PairedAcceptanceTest`, `SteadyStateWarmUpTest` and `PerfStaleAnchorTest` — all correctly untagged, all calling those helpers on **scripted** values — and admits `KernelParityCoverageGuardTest`, which matches because it scans these very sources as text. Those are the false positives to beat, named so the next attempt starts from a corpus rather than from scratch; the residue the syntactic form leaves is enumerated above and is closed by the two mechanisms in [IF297](INTERPRETER-FINDINGS.md#if297): a runtime gate on the harness's measuring entry points, and a raw-clock source census for the reads that never reach it.

- **Why a tighter SINGLE-RUN bar is not available — the three candidate normalizers all drift ~2×–2.7× (measured 2026-08-11).** The obvious repair for the band above is a committed per-scenario budget. It cannot be set tightly, because detecting a `k×` regression needs a reference whose cross-environment stability is better than `k`, and none of the three is. Comparing the same 17 gate observations on Apple Silicon and on the hosted x64 runner: **absolute** CPU medians drift `0.91×–2.45×` (a 2.69× spread); **normalizing each lane by `B1@5000`** — another interpreter scenario in the same JVM — leaves `0.78×–2.10×`, a **2.69× spread, so it buys nothing** (constructs respond differently: `AddDays` is 2.45× slower on the runner while `complexRealWorld` is 0.91×, i.e. faster); the **kernel-advantage** normalizer is the best of the three at a 2.07× spread (`Number-index-compute@500` measured 4.67×, 6.37×, 7.33× locally and 9.68× on CI) and **1.57× of that is single-machine run-to-run noise** at the current `warmup=5, iters=5` sampling. A budget honestly derived from that data trips at ~3×, against the 4.0×–10.0× the existing `beats both` bar already gives on those lanes — not worth the machinery. A comparison **against the same environment's own recorded numbers** is not bound by that drift at all, which is the anchor bar below; what it costs is stated there, and it is not the 10–30 % a within-environment comparison could reach in principle. **Two of these three ranges are algebraic, not empirical, and saying so is part of the finding:** normalizing every observation by *one* of them cannot change their multiplicative spread (2.45/0.91 and 2.10/0.78 are both 2.69), so the `B1` result was determined before it was measured. The kernel-advantage figure is a different quantity — a within-run ratio of two engines — and its 2.07× is empirical; the three should not be summed up in one sentence as "every candidate normalizer", which is the *name the quantity before you compare numbers* trap.

- **The committed per-runner-class ANCHOR — the only bar that can see a uniform regression (2026-08-11, IF280).** `PerfAnchors` holds each of the 18 growth lanes' accepted interpreter medians, at both scales, against a number committed for **this runner class** in `adapter/src/test/resources/perf/anchors.json`. Within one class the 2.07×–2.69× environment drift is gone, so [`PerfBounds.ANCHOR_TOLERANCE`](../adapter/src/test/kotlin/io/github/mbackschat/a12/dm/adapter/perf/PerfBounds.kt) only has to cover run-to-run noise — whose honest measure is the **envelope of every anchored observation across every available run**. As first measured (2026-08-11) that was `0.92×–1.36×` over 36 observations and the tolerance was set to `1.8× + 1 ms`; re-measured over 322 observations on 2026-08-12 the binding quantity is `observed/anchor − slack/anchor` at `1.352×` worst, and the tolerance is **`1.65× + 1 ms`** with `1.22×` of margin (the 2026-08-12 checkpoint in [the results log](INTERPRETER-PERFORMANCE-RESULTS.md) carries the three sets). Five properties make it a guard rather than a report: it reuses the **already-accepted** medians, so a passing run costs nothing extra; a **breach re-measures with the observation's own estimator** (a median over `GROWTH_PAIRS` samples, not a single sample) and accepts on the median of the attempts; a **missing key inside an anchored runner class fails** under `-Dperf.anchor.required=true`, which the isolated `perfGateTest` lane sets unconditionally, because a new lane or a refreshed scenario fingerprint is precisely how a bar silently disappears — while a class with **no block at all** stays the bootstrap case and only reports; it is **judged only where the measurement supports it** (`TimingEnforcement`, below), so a broad `:adapter:test -PrunPerf` under parallel forks records and claims nothing; and the anchor is **committed, not rolling**, so `K` successive within-tolerance degradations cannot compound. Refresh it with [`scripts/perf-anchor.sh`](../scripts/perf-anchor.sh) **in the same commit as the change that made the cost legitimately higher** — that diff is the record of the acceptance, and the script **refuses** a refresh whose input does not measure every lane the anchor *file* carries — not merely every lane *that block* carries, which would miss the one case the recovery path actually exercises: a **new** runner class has no previous block, so only the other classes' key sets can see a hole in it. The gate writes every observation to the **committed** [`perf-results/`](../perf-results/README.md) tree, one JSON-Lines file per run under its runner-class directory, each carrying the conditions it ran under (commit, JDK, processor count, load average per observation, CI run id). It lived in `adapter/build/` until 2026-08-11, where `clean` deleted it, so a run could be held against one committed anchor but never against its own history; `SurvivingDataNotInBuildGuardTest` now refuses that class of mistake, and [`scripts/perf-history.sh`](../scripts/perf-history.sh) renders the history as a text table. CI does not commit, so the nightly (`workflow_dispatch`-able, so no schedule need be waited for) uploads its record as the `perf-observations` artifact, which is how a hosted-runner block gets authored at all. `PerfAnchorBudgetTest` scripts the acceptance rule, including the uniform-slowdown case no growth ratio can see; `PerfAnchorScriptTest` **executes** the refresh script for each of its refusals; `PerfAnchorResourceTest` guards the committed file's shape and `PerfAnchorCoverageGuardTest` binds every lane to an anchor at both scales, both on every push.

  **…and `AnchorBlockKeyParityTest` requires every anchored runner class to carry the SAME observation keys — the guard that makes a green local perf run mean a green nightly (2026-08-15).** The implication was false, and the mechanism is worth stating because it is not a missed step. An observation key hashes the scenario's **content** and nothing about the machine; only the milliseconds are machine-specific. So when a source change moves a fingerprint, the local block gets refreshed from a local run and goes green, while the CI block still holds the old keys — because refreshing *that* class needs observations measured on it, which only CI produces. The gate looks only at its own class, so nothing compared the two: the drift was **undetectable locally and un-preemptable**, since repairing the CI block requires the very job that fails. It reached 66 keys against 36 and the nightly reported ~20 UNANCHORED lanes. Key parity closes it because the key set is derivable anywhere, and it is *sufficient* rather than merely helpful: on a hosted runner a breach is `FLAGGED`, never failed, so an unanchored key is the only way this gate fails CI — a stale local block reddens the local gate, a stale CI block reddens this test, and both stale reddens the local gate. The guard is pinned to the incident: it fails on the exact `anchors.json` that was live when the nightly broke. It cannot speak for a real slowdown visible only on other hardware, which is flagged by design.

  **What it costs in detection, stated plainly (recomputed 2026-08-12 against the refreshed block and the tightened factor):** a uniform regression below **1.65×** on a large lane still passes, and the slack-dominated small lanes reach **2.1×–3.5×** (`wideGroups@50` anchors at 0.71 ms, `PRA@500` at 0.53 ms). Lowering the anchors widened that upper end — at the old 1.8 factor the same blocks span 1.80×–3.69× — so the tightening bought less on the smallest lanes than the factor suggests — so this is a bar where none existed, not the 10–30 % sensitivity a within-environment comparison could reach. **Tightening it was tried and refused on measurement (2026-08-12):** both blocks are now medians of three, which was the named prerequisite, but the binding quantity is a single run's distance from the anchor rather than the anchor's own precision — `1.421×` worst over 36 keys on this machine under ordinary load, against `1.345×` hosted, so `1.8` keeps only `1.27×` of margin and the local class is the noisier of the two. Raising the lanes' sampling remains the only untried lever. The band's **lower** edge is now armed instead: an observation below `0.6 × anchor − slack` reports `[perf][STALE]`, because an anchor that stopped describing the code is a ceiling at multiples of the real cost and nothing noticed it twice.

  **A block belongs to a machine, and the check is mechanical (2026-08-12).** The environment key names an os/arch family while an absolute time is a property of the hardware; `PerfEnvironment.machine` probes the machine from the OS (the JVM exposes no CPU identity) and every run records it, as does every refreshed **non-hosted** block. *(Amended 2026-08-16: a **hosted** block records no machine and folds across models. That class does not have a machine — the provider picks the CPU per job and the fleet is not enumerable — so requiring one made a refresh wait on a lottery; [IF293](INTERPRETER-FINDINGS.md#if293) had already measured that the model is not its dominant variance.)* Where a breach fails the build the identity is required, so a mismatch reads as bootstrap; where it only flags, the runner is a VM the provider picks per job and the bar stays armed while naming the machine it ran on — refusing there would remove the nightly's only absolute signal on any night the hardware differed.

- **Which bars may FAIL depends on where they run — `TimingEnforcement` (2026-08-11).** A bar that judges this run's numbers against a constant or against a previously recorded number is **self-referential**: it is a property of the machine as much as of the code. A bar that compares two engines measured in the same run on the same vCPUs is not — contention moves both and the ratio survives it. Only the first kind is conditional, and **the two kinds of self-referential bar do not share a precondition**:

  | bar | precondition | on a dedicated machine | on a hosted runner |
  |---|---|---|---|
  | growth floor (`SUB_QUADRATIC_MAX`) | none — the current-thread CPU clock already filters a sibling Gradle fork (the 2026-08-03 fix) | `GATED` | `FLAGGED` |
  | absolute anchor | the isolated single-fork lane; no clock filters a parallel-fork slice out of an absolute time | `GATED`, else `UNJUDGED` | `FLAGGED`, else `UNJUDGED` |

  **Collapsing those two into one rule switches guards off, and that is not hypothetical** — the first version of this change required the isolated lane for both, which silently disarmed `CharsetPerfTest` and `CustomTypePerfTest`. `GrowthFloorRetryTest` now pins both rules on scripted inputs for exactly that reason. *(Amended 2026-08-13: this sentence used to call those two "the only timing bars an ordinary push runs", which was the stated reason for leaving them untagged and therefore inside the broad adapter suite. **Both halves are now false** — see the classification above: no timing bar runs on an ordinary push at all, and both classes carry the routine-tier `perf` tag. The precondition table is unchanged and still correct, which is the point worth keeping: `forGrowthFloor` never required the isolated lane, so moving these two INTO it cannot disarm them. Only where they run changed.)*

  **The hosted axis is measured, not assumed.** `perfGateTest` is single-fork and non-cacheable, so it satisfies the lane axis on a hosted runner too — and the estate still red-lined there: the same commit passed one night and failed the next two on `MSC-multi-star-correlation` at a median `9.11×` against the `9.0` floor, and across three hosted runs the 18 growth observations spanned `2.48×–7.98×`, leaving the closest lane at **89 %** of its floor. `CharsetPerfTest` has the same history at `9.37×` and `10.22×`, all of them false. A hosted runner is a VM on a shared physical host; neighbours evict cache lines and consume memory bandwidth, which is spent in **user-mode** cycles, so the CPU clock does not filter it and no finer clock would. A red that cannot be told apart from a real regression, on a lane nobody watches interactively, is a false positive by construction — and the standing requirement is that the nightly never produces one.

  **What this costs, stated plainly:** on any hosted runner, the growth floors and the anchor no longer stop the build. What remains gated there is the cross-engine family — `requireInterpreterBeatsBoth`, `PairedAcceptance`'s per-unit cost, `RATIO_CEILING` — which is the "always faster than the kernel, including scaling" requirement itself, and which contention cannot fake because both engines meet it in the same run. `ABS_CEILING_MS` also still gates everywhere and is **not** a cross-engine bar: it is this run's median against a constant, so by the definition above it is self-referential. It is a deliberate always-gated exception rather than an oversight — at 410×–3800× of headroom no contention reaches it — and it is named here so the taxonomy stays true rather than tidy. A flag is not silence: the breach prints a greppable `[perf][FLAG]` line and the gate's numbers are in the committed record with their status, so `scripts/perf-history.sh` shows the trend rather than a build that happened to be green.

- **Per comparison scenario:** bind and verify the reviewed content fingerprint; build the instance once; require zero unsupported and authoritative agreement with dynamic Groovy plus every declared Java-capable strategy; warm up (JIT); time `K` iterations of each eligible engine; report `interp_ms`, `kernel_ms`, and ratio under `id@version + SHA-256`. The fingerprint covers both model representations (including the complete legal-charset definition), the generated placements and generator metadata/seed/variants, scale, operation, locale/zone, semantic result regime, and expected cardinality (review-corrected IF158). Fingerprint format v2 serializes every `ModelDef`/field/rule/computation property explicitly, including the two field-owned message maps; it no longer depends on Kotlin data-class `toString()`, whose shape changes when an unrelated defaulted property is added. The fingerprinted locale is the locale all three engines actually execute.
