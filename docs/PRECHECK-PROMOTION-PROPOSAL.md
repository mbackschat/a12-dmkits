# Precheck promotion — moving two kernel-delegated law families into rulekit

> **What this is.** A PROPOSAL and the **state carrier** for the work: the tables below are updated in the same commit as each landing, so a later session reads the table rather than a tracker. Opened 2026-09-02 from a cg-research measurement handoff; that handoff is consumed and dead.
>
> **Why.** `rulekit` reaches a verdict on 82.3 % of document-model-reachable corpus cases, and 354 of the cases it passes but upstream rejects are `kernel-delegated` — laws rulekit contains no check for. For a kernel-free consumer that is silence, not a wrong answer. Two families carry 228 of the 354.
>
> **The counts are cg-research's, not ours.** They come from `ParserCorpusRulekitSweepTest` over the MVK parser corpus joined to upstream expectations, taken on the 471-case unscoped set. They size the work; they are not an oracle for any claim here. Every law this proposal lands is measured against our own kernel and locked, per the standing basis rule.

## The bar every item clears

A promoted precheck is a **client-side refusal**, so it inherits the standing rule in full: measure that the real kernel refuses the same input, never be broader than that basis, **check the read path** (`:adapter`'s `ConditionConverter` builds these same records inbound, so an over-strict gate makes a legal model unreadable), and write the reason down for any deliberate over-strictness. One guard is estate-wide: `ClientRefusalKernelBasisCensusTest` fails any refusal citing a code no law or claim probe observed. The denominator half is **per gate, not shared** — `TemporalRefusalDenominatorTest` covers the kind gate on the records, `UntypedTemporalExtractionGateTest` the format gate on the `Dsl` factories — so an item is not done until it names its own, and naming a sibling's is how an invariant ends up advertised with nothing behind it.

**Which tier an item lands in is not a per-item design question — [MVK-LEDGER](MVK-LEDGER.md) already answers it, per code.** Its four buckets (`erased` · `pre-checked` · `kernel-delegated` · `n/a-structural`) assign every one of the 300 codes a home, and its conformance table names each tier's failure mode. The selector is **exactness**, not risk appetite: a check that reproduces the kernel's rule exactly is `pre-checked` and refuses; one that only APPROXIMATES it is `pre-checked (advisory only)` and emits a WARNING-severity PRECHECK through `Rule.deferredChecks()`, the shape worked out for `MVK_ERROR_FIELD_NOT_REFERENCED` in [KERNEL-INTEGRATION-NOTES](KERNEL-INTEGRATION-NOTES.md). Over-rejection risk does not select the tier — the measured-basis rule above already removes it.

**And the `Linter` is not one of the choices.** It emits `RK_*` codes exclusively — rulekit's own advice about a model that is LEGAL (unguarded comparisons, redundant operands, contradictory presence). Every code this proposal promotes is an `MVK_*`, which means the kernel holds the model INVALID; that is a validity verdict, not advice, so it belongs to `build()` or to `deferredChecks()` and never to lint however conservative the check. The one look-alike is `RK_NEG_CONDITION_IN_ITERATION`, and note what it did: rather than mirror the kernel's code weakly it took an `RK_` code of its own, because at that conservatism it really is advice rather than a verdict.

So an item promoting a `kernel-delegated` code answers two questions in order, and neither is a matter of taste: **can we state the kernel's rule exactly?** (if not, advisory) and **is the row's recorded reason for delegating it still true?** (if it rests on a capability we have since built, say so in the row rather than reversing it silently).

**Where a promoted check lives (settled 2026-09-03).** Intrinsic rules go in the AST node's constructor, contextual ones on `BoundModel` — the split the estate already has (78 vs 8), stated in [AF148](API-FINDINGS.md#af148) and PROJECT-DESIGN's model-bound list. The seven `Dsl.<aggregate>(model, …)` overloads A5 introduced were the wrong receiver and are gone; the checks now live on `BoundModel`. `Dsl`'s model-free forms stay for the inbound converters, whose obligation is the opposite one — never refuse a kernel-accepted shape. `Dsl.dateExtraction`/`dateTimePart` keep their model because there it RESOLVES an opaque `Calculation` rather than validating a typed operand.

### What the A1–A4 block establishes, and what it does not

Cold-reviewed 2026-09-02; every in-scope finding applied. Two limits are worth carrying forward rather than reading past.

**The split family's rule is confirmed but under-determined.** `carriesBothHalves` requires one date component and one time component, which over the admitted vocabulary has exactly **one** positive cell — the ISO date-time. So "one of each", "a day and an hour", and "exactly the ISO string" fit every measurement equally. The discriminating case is a two-half format that is not the ISO string (`yyyy HH`), which lies outside the kernel's candidate universe and has no known verdict. The implemented predicate is the most conservative of the three and is documented as such; if the vocabulary ever gains a second two-half format, this is the row to re-measure first.

**A format outside the admitted vocabulary is scanned, not delegated.** A kernel-free binding can present any string. That is deliberate and reasoned at `Dsl.dateExtraction`: the scan is the kernel's own keying applied to a declaration the kernel would reject at the model level, so no extraction verdict over it is meaningful either way.

## Partition C — the refusal census's own denominator (opened 2026-09-03, not started)

## Partition D — what the witnesses' fixtures could not express (opened 2026-09-07)

An independent differential ran this branch against the real kernel over a large external corpus of real
models. Headline: **+69 agreeing refusals, zero losses, and 15 refusals of constructions the kernel admits.**
Before the branch, zero. **All 15 trace to one gate** — D1 below.

**The class, which is the reason this is a partition and not three findings.** Every item here is a witness
whose fixture could not express a declaration shape real models use, and a grid that cannot hold a shape reads
exactly like a measured law: the rows are honest, the controls are real, and the conclusion is still wrong for
inputs the grid could not build. So the standing question for any new gate is **which declaration shapes can
this grid NOT hold?** — asked of the FIXTURE's expressiveness, not of the rows. D1 is the sharpest form: our
own fixture comment named the shape ("the sign-allowed shape") while the row measured something else, because
the builder had no way to declare it.

Each row states the reporter's prediction as a measurable claim. They are to be refuted or confirmed here, not
believed: the counts are theirs, over a corpus this repo does not hold.

## Partition E — the duplicate/overlap carrier coverage (opened 2026-09-07)

An external report counted 63 presentable cases across `MVK_DUPLICATE_PARAM1`/`MVK_DUPLICATE_PARAM2` with a
gate already refusing 26. Those counts sized the work and are **not** the denominator: the corpus is not held
here. Four denominators we own replaced it, in ascending cost — the locked laws tier (9 classes already
measuring these codes), our own carrier types (16 records), a one-run probe for the cells nobody had measured,
and the kernel's own call graph.

**The class.** Not "duplicates" — **measured-but-unpromoted**. A kernel verdict gets measured, filed and
locked, and the client gate is never wired, because the finding was filed under what it *was about* rather than
under which gate owns it. E3 is the pure case: measured 2026-08-11 under "diagnostic identity", locked, never
wired, and the carrier's own javadoc read as a complete enumeration of its slot rules while omitting it.

**The predicate is uniform and that is structural**, not a coincidence to re-verify per carrier: the whole
kernel raises both codes from two private lines with one shared caller that invokes both arms, reached from 12
call sites governing 38 operators. See [KF1015](KERNEL-FINDINGS.md#kf1015).
