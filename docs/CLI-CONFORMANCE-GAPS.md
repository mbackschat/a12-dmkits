It is the CLI-conformance peer of [`FEATURE-GAPS.md`](FEATURE-GAPS.md): that tracker holds the **BA-authoring** ergonomics of the BA+agent loop, while this one holds what a *cold agent* needs to **select, risk-assess, and recover from** a verb using the tool's own output.

> **Lifecycle.** Same `-GAPS` discipline as its siblings ([`DEV-API-GAPS.md`](DEV-API-GAPS.md), [`INTERPRETER-GAPS.md`](INTERPRETER-GAPS.md), …): a gap lives here only while open — §1 open, §2 deferred (with re-open triggers), §3 out of scope. A shipped gap is **deleted**, not kept as a "shipped" list (git is the *what/when*; the graduated `CLI-CONFORMANCE-SPEC` matrix column / `CLI-SPEC` section is the *why*).

## 2. Deferred — with re-open triggers

- **CG9 — realign observation-mode `ok` and exit with the envelope's own semantics.** <a id="cg9"></a> *(Raised 2026-08-09 by the consuming project, after it withdrew the operational half of its own report.)* `CLI-SPEC:450` records why observation mode keeps the ordinary aggregate contract, and the **information** half of that decision holds: the consumer could produce no artifact where `outcome:completed` plus `written:true` fails to separate a successful capture. What is weaker than it reads is the **reasoning** — "it would make one verb's exit mean something different from every other batch" is a cost `CommandContracts` already models, since it requires an explicit selector for every argument-dependent mode. Meanwhile `ok` is defined project-wide as "the tool did the job" (`CLI-SPEC:124`, with `model check` on an invalid model returning `ok:true, valid:false`), and a capture that dispatched every child and wrote a complete artifact did the job.

  **The constraint that must survive to whoever implements it: change both outer `ok` and the exit code, or neither.** Changing only `ok` looks like the safer, less-breaking half and is worse than doing nothing — `set -e` trips on the exit status, so the half-change preserves the entire trap while still being a contract change. The consumer named this explicitly.

  **Blocks:** nothing. The residual friction is ergonomic, and `CLI-SPEC` now publishes the `set -e` pattern that answers it. No other consumer scripting `batch --observations` exit codes was found in either repository, though consumers of the public v0.12.0 release cannot be enumerated. **Re-open at** the next already-planned breaking release, which is the consumer's own recommendation. **What it costs then:** observation-mode `ok` becomes dispatched-and-written with the exit following it, `data.allExitedZero` carries the aggregate, and the change must move `batch.schema.json` plus its CI-executed examples, an explicit `CommandContracts` mode selector, the skill, `SchemaExamplesGuardTest`, and an inverted `BatchObservationNegativeControlTest`, released as BREAKING.

- **`doNotUseWhen` on near-sibling verbs.** *(Demoted from open — 2026-07-21 cold-agent probe.)* The proposed sibling groups (`model read` ↔ `export`, `check` / `eval` / `compute`, `apply` ↔ `batch`) already **disambiguate cleanly** from `--help`. The only ambiguity found — `rule eval` ↔ `model eval --rule` — was fixed directly with a one-line cross-reference in each description. **Re-open when** the gap-finder recurrently flags an `AMBIGUOUS_MODE` sibling pair a description tweak can't resolve — then the structured `doNotUseWhen` + `AP7` matrix column earns its keep.

- **Per-verb `emits[]` (the failure space, discoverable *per verb*).** The failure space is already discoverable **reactively** — every `RK_*` / `MVK_*` code the tool emits resolves in the `diagnostics` catalog (`diagnostics` list + `diagnostics <CODE>`), each carrying a `fix`. A per-verb `emits[]` would add **proactive** planning ("what could this verb return before I run it"), but it is **not** picocli-derivable — it needs a verb→codes source that does not exist yet. This is the flip side of the `CLI-SPEC` §2 correction that removed the premature "each op advertises `emits[]` in the manifest" claim. **Re-open when** a planning or apply-the-fix consumer needs the per-verb failure space proactively, or a probe shows agents failing to anticipate a verb's errors — likely then a **proposal**, since the verb→codes derivation carries real design risk.

- **A runnable next-action command on `refused`.** The `refused` envelope already carries the referrers (in `data`) and a `fix` diagnostic; emitting the *exact* remediation invocation (e.g. the `remove --cascade` line to run) is the note's "include next actions." **Re-open when** a fix-applying harness exists to consume it, or a probe shows agents failing to recover from `refused` despite referrers + `fix`.

- **Error-classification booleans (`retryable` / `correctableByAgent` / `userActionRequired`).** For dmtool these would be near-constant — the real signal already lives in `outcome` + `source` + presence-of-`fix`, and the one distinction that matters (a cascade *decision* vs a tool bug) is already encoded in `outcome`/exit-code. **Re-open when** an apply-the-fix harness actually consumes them (the same consumer-exists discipline that withheld a machine `suggest` field).

- **An envelope `version` field.** The note warns against unversioned output-shape drift. dmtool's whole envelope contract is **derived + drift-guarded** (`SchemaVerbTest`, `result.schema`), so an embedded version buys little today. **Re-open if** the envelope must change incompatibly, or an external consumer pins the shape and needs a version to negotiate against.

- **A cross-verb stdout-purity guard ("nothing but one JSON document").** *(Corrected 2026-08-03: the earlier entry rested on “not observed” and overstated the unguarded surface.)* A strict process-boundary sweep ran one canonical successful route for all **81 live leaves**: **79 JSON-promising routes** emitted exactly one JSON value with EOF immediately after it; bare `schema` deliberately emitted orientation text and `export card` deliberately emitted Markdown. The argument-dependent `export --out-dir` route also deliberately exits 0 with empty stdout while writing its four artifacts. The **error path** remains broadly guarded by `DiagnosticConformanceFuzzTest`, and `InternalErrorBoundaryTest` specifically locks an unexpected throwable to one structured error envelope on stdout with the trace on stderr. `VerbDemonstrationTest` now guards `--text` totality across the demonstrated envelope-producing success surface; `--text` is intentionally human text, not machine JSON. The remaining deferral is therefore narrower: there is no permanent route-class-aware strict parse-to-EOF guard over every success argument mode. **Re-open when** a JSON-promising route is seen contaminating stdout, or a consumer needs that stronger permanent coverage.

## 3. Out of scope — the remote / async operation model

A cluster of the note's recommendations presuppose a **resident or remote** tool: idempotency keys (§14), long-running operations with `operationId` / resume / poll (§15), the preview-id + confirmation-token lifecycle (§13), profiles / `--target-env` / auth status (§16), `--trace-id` + a correlated audit log (§16/§21), and cursor/pagination for large result sets (§17). dmtool is **local, synchronous, single-file, stateless-per-call** — the model file is the durable state, and git is the audit trail + undo. These recommendations **void** unless a resident mode lands, and that mode — **`dmtool serve`** — is already an examined **non-goal with its own re-open triggers** in [`FEATURE-GAPS.md`](FEATURE-GAPS.md) §4. They are pointed at, not re-litigated here.
