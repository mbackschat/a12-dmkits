# dmtool CLI conformance — gaps

> **What this is.** Open and deferred gaps on the **agent-facing conformance axis** — the *self-explain* + *diagnostic* contract that [`CLI-CONFORMANCE-SPEC.md`](CLI-CONFORMANCE-SPEC.md) owns (its sibling spec [`CLI-SPEC.md`](CLI-SPEC.md) owns the verb surface + safety gate). It is the CLI-conformance peer of [`FEATURE-GAPS.md`](FEATURE-GAPS.md): that tracker holds the **BA-authoring** ergonomics of the BA+agent loop, while this one holds what a *cold agent* needs to **select, risk-assess, and recover from** a verb using the tool's own output.
>
> **Lifecycle.** Same `-GAPS` discipline as its siblings ([`DEV-API-GAPS.md`](DEV-API-GAPS.md), [`INTERPRETER-GAPS.md`](INTERPRETER-GAPS.md), …): a gap lives here only while open — §1 open, §2 deferred (with re-open triggers), §3 out of scope. A shipped gap is **deleted**, not kept as a "shipped" list (git is the *what/when*; the graduated `CLI-CONFORMANCE-SPEC` matrix column / `CLI-SPEC` section is the *why*).
>
> **Current state.** No open gaps. CG9 graduated on 2026-08-10 into [`CLI-SPEC`](CLI-SPEC.md), the batch/result schemas, explicit `CommandContracts` observation-mode selectors, and the packaged public-contract suite. The 2026-08-05 CG8 param-content gap graduated into [`CLI-CONFORMANCE-SPEC`](CLI-CONFORMANCE-SPEC.md) as the derived `contentRole` surface (locked by `ParamContentRoleTest`). The 2026-08-04 `model compute` value-form gap graduated into `compute-doc.schema.json`'s published `value` contract (locked by `ComputedValueFormTest`). The 2026-08-03 operational-contract gap graduated into [`CLI-CONFORMANCE-SPEC`](CLI-CONFORMANCE-SPEC.md), [`CLI-SPEC`](CLI-SPEC.md), and the packaged public-contract suite. The earlier 2026-07-31 property-shaped conformance gaps graduated into [`CLI-CONFORMANCE-SPEC`](CLI-CONFORMANCE-SPEC.md), [`EVAL-SPEC`](EVAL-SPEC.md), and [`PROBE-SPEC`](PROBE-SPEC.md).
>
> **Provenance.** A 2026-06-28 review of dmtool against a general "CLI tools for LLM agents" best-practices note found that dmtool already meets or beats ~80% of it — JSON-default output, a picocli-**derived** manifest that can't drift, the result envelope, the `refused`/referrers safety gate, the exit-code taxonomy, CI-executed examples. The rows below are the residual deltas, and — in §2/§3 — the ones we considered and are **not** taking, each with a re-open trigger so the decision carries its own expiry.

## 1. Open

> **All five rows below come from one 2026-08-14 cross-component audit** and share one root cause with [IF287](INTERPRETER-FINDINGS.md#if287)'s nine measured interpreter defects: a condition operand may name a GROUP, which must be expanded to the fields below it, and **expansion is opt-in at every site that resolves an operand**. The kernel primitive is correct and documents the consequence itself — `KernelAdapter.whereUsed` says *"'Direct' is exact: a rule that references an enclosing group is not listed for a field inside it"* — so every defect here is a **caller treating "not directly referenced" as "not referenced"**. **None is measured yet**; each row names its mis-answered input, and the canonical one is `/Order/Address/{Street,City}` with a single rule `NumberOfFilledFields(/Order/Address) >= 2`. **No test in `cli/` or `adapter/` exercises the group-operand direction at all.**

- **CG13 — three delete/move safety gates are blind to a group-operand reference, and one has no gate at all.** CLI-SPEC §6 promises a refactor refuses when it cannot establish safety; these cannot. **`apply`'s `FIELD_REMOVE` is ungated entirely** (`ApplyCommand.java:393-398` calls `session.removeField` and nothing else; its op keys carry no `cascade`), while its sibling `GROUP_REMOVE` (`:433-453`) does run `GroupRemoval.plan` — so a batch skips §6 for fields. `field remove` (`FieldRemoveCommand.java:94-99`) gates on exact-match `whereUsed`, so removing `/Order/Address/Street` under the canonical rule deletes it, reports success, and leaves the model **kernel-valid** because the rule still names the group — it just counts one fewer field, so no terminal check fires either. `group remove` (`GroupRemoval.java:43-48`, shared by `GroupRemoveCommand.java:82` and `ApplyCommand.java:440`) is blind to an **ancestor** group operand; its javadoc at `:19-21` documents only the descendant direction, which the kernel *does* catch. `field move`/`group move` have no reference check at all (`StructureRefactor.java:120-130`) and emit `changed.rewroteReferences: []` while an aggregate silently loses a member. And `ReferenceRewriter.java:26-27` states that a `*`-reference a rename would dangle **must be refused** — no such check exists, and a repeatable group operand *is* a `*` reference ("advertise nothing you cannot point at"). **Actionable work:** widen the gate's primitive (rulekit's `ConditionReferences.covers` already prefix-matches group paths), then lock each refusal in the does-fire tier §6 requires. **Completion gate:** every delete/move path refuses a group-operand-reached reference, with a control proving an unreached sibling stays removable.

- **CG14 — `rule eval` reports `PASSED` where the kernel SUPPRESSED.** A wrong runtime verdict in the one path whose stated purpose (`KernelAdapter.java:848-849`) is not to mislead. At `:862, 870-878` the loop compares `referenced` entries against `m.field().path()`, but `referenced` holds GROUP paths for a group operand while the formal-check message carries a FIELD path, so they can never be equal: a rule the kernel skipped because a field inside the referenced group is formally invalid returns `PASSED` with an empty suppression list. **Actionable work:** measure against the kernel's own message set on a group operand over a group holding a formally-invalid cell, then match on containment rather than equality. **Completion gate:** a differential row pins the suppressed verdict on both kernel strategies.

- **CG15 — the adapter's group expansion drops the star, pinning nested rows to repetition 1.** The interpreter's own defect shape, in conversion, fully silent, flowing into `rule read`, `rule explain`, `model report` glosses and `export`. `ConditionConverter.java:350-360` (mixed group+field) adds **declared** paths, dropping the star, while its twin `groupScopedFieldFill` (`:551-556`) uses `model.flattenGroup(reconstructStarPath(e))` and keeps it — same operator family, two arms, opposite semantics, so `FieldsNotCollectivelyFilled(/Order/Items*, /Order/Note)` means repetition 1 only while the same call without the extra operand means all rows. `:1269-1280` rebuilds `/Order/Items*` plus a declared tail carrying no `*`, and `BoundModel.flatten` iterates a level only when its segment ends in `*`, so a nested repeatable under a starred group is pinned to row 1. Same method: a kernel-legal **non-repeatable** group operand makes `flatten` throw and is reported as "converter error", and `.filter(kind == NUMBER)` at `:1273` silently narrows a mixed-kind group. Loud siblings, same shape: the group arms of `NumberOfValueInFields` (`:1122-1128`), `NumberOfFilledFields` (`:1172-1186`) and `FieldValuesNotUnique` (`:396/473/488`) report *unsupported* for shapes the kernel admits, and a mixed list whose first entity is a field mislabels a converter gap as "unresolved reference" (`:440-448` vs `isFieldFillQuantifier` `:513-519`). **Actionable work:** measure each shape's kernel admission first, then make the two arms share one star-preserving expansion. **Completion gate:** a round-trip row proves a converted group operand renders back to the authored condition.

- **CG16 — the READER half is FIXED 2026-08-14; what remains is the diff/suggest surfaces.** The reachability primitive `KernelAdapter.referrersReaching(byEntity, path)` now sits beside the exact `whereUsed`, and `model usage`, `ModelReport`'s dead-field set and `FieldDiffProjector.hasReaders` route through it, so a field read only through an ancestor GROUP operand is no longer reported `unreferenced` — which, paired with CG13, was a complete delete-a-live-field pipeline for an agent. The primitive walks ancestors **segment-wise**, because `"/Order/BillingContact/Email".startsWith("/Order/Billing")` is true and a prefix test would over-report. The published schema and CLI-SPEC §6 no longer claim `where-used` and `model usage` "can never disagree": they differ on exactly the group-reached fields, deliberately, and both now say so. *(Locked: `cli.model.ModelUsageGroupOperandTest` for the CLI surface and `adapter.review.GroupReachedReaderRiskTest` for the two adapter readers — the group-reached rows, the recursive nested-subgroup row, the **union across two ancestor levels**, the `where-used`-vs-`model usage` divergence the docs now advertise, and three vacuity controls: a field under no referenced group stays unreferenced, the segment-boundary pair, and an explicit key-presence assertion so "reported with no referrers" cannot pass as "silently dropped".)* **A cold review found four real holes in the first version of this fix, all now closed:** `FieldModifyCommand` still answered `RETYPE_AFFECTS_READERS` from the exact primitive, so one error code had two definitions in two verbs; the union row was missing, so a first-ancestor-wins walk passed the whole file (**mutation-confirmed** both before and after); `ModelReport` and `FieldDiffProjector` had changed behaviour with **no test at all** (also mutation-confirmed); and the "can never disagree" claim the row above declared deleted was still live in four places, one of them the `where-used` **published schema** and one the very file the fix edited. The conservative direction is now stated on the advertised surfaces rather than only in adapter javadoc: reachability answers "a rule reaches into this group", not "this field enters that operator's expansion" — a group-list predicate over a *repeatable* group counts rows rather than reading values, and erring toward "read" is correct where the opposite error deletes a live field. **Still open, and deliberately NOT folded into that slice** (the CG16 completion gate named the readers and the doc claim, and a slice that keeps absorbing adjacent findings is what the convergence gate refuses): `ModelDiff.java:175-181` passes referrers to the FIELD arm only, so a removed group that rules directly reference never gets `REFERENCED_ELEMENT_REMOVED`; `RelocationMatcher.refsOf` (`:149-153`) discards `groupPaths()`, so `groupRefactors` (`ModelDiff.java:409-443`) can never emit a group rename/move; and `rule check --suggest-error-field` (`RuleCheckCommand.java:188-195`) tells the author "the condition references no field inside its iteration scope" when every operand is a group, steering them off the only valid picks. **One claim in the original row is UNMEASURED and must not be repeated as fact until it is:** that `rule deps`/`rule explain` (which read the **converted** AST) disagree with `where-used` (which reads the kernel primitive). Plausible, never probed. **Actionable work:** route the three surfaces above through `referrersReaching`; measure the `rule deps` claim before acting on it. **Completion gate:** a removed group with direct referrers reports `REFERENCED_ELEMENT_REMOVED`, a group rename is emitted, `--suggest-error-field` offers a valid pick for an all-group condition, and the `rule deps` question carries a measurement either way.

- **CG17 — FIXED 2026-08-14.** `group extract`'s outward-reference gate was wrong in **both** directions at once, which is why they landed together. It looped `adapter.ruleFullNames()`, which deliberately excludes computations, so a computation inside the subtree reading an outside field passed the gate and moved into a sub-model that cannot see its own operand — every other reference site in the repo pairs `whereUsed` with `whereUsedInComputations`, and this one did not. And its membership test was `startsWith(groupPath + "/")`, under which `"/Order/Shipping"` is not inside `"/Order/Shipping"`, so a rule referencing the extracted group **itself** was refused as escaping the subtree it is the root of; that reference travels fine (the group becomes the sub-model's root), making it an over-refusal whose diagnostic named a problem the author could not fix. Both arms now share one `inside(path, groupPath)` compared at a path-segment boundary, which also keeps `/Order/ShippingNotes` out of `/Order/Shipping`. *(Locked: `cli.group.GroupExtractComputationGateTest` — the computation escape **mutation-confirmed** by disabling the computation arm and watching exactly that row go red, the root self-reference admitted, and a genuine outward reference still refused as the control proving the gate was not merely loosened. CLI-SPEC §6's refactor table carries the contract.)*

## 2. Deferred — with re-open triggers

- **`doNotUseWhen` on near-sibling verbs.** *(Demoted from open — 2026-07-21 cold-agent probe.)* The proposed sibling groups (`model read` ↔ `export`, `check` / `eval` / `compute`, `apply` ↔ `batch`) already **disambiguate cleanly** from `--help`. The only ambiguity found — `rule eval` ↔ `model eval --rule` — was fixed directly with a one-line cross-reference in each description. **Re-open when** the gap-finder recurrently flags an `AMBIGUOUS_MODE` sibling pair a description tweak can't resolve — then the structured `doNotUseWhen` + `AP7` matrix column earns its keep.

- **Per-verb `emits[]` (the failure space, discoverable *per verb*).** The failure space is already discoverable **reactively** — every `RK_*` / `MVK_*` code the tool emits resolves in the `diagnostics` catalog (`diagnostics` list + `diagnostics <CODE>`), each carrying a `fix`. A per-verb `emits[]` would add **proactive** planning ("what could this verb return before I run it"), but it is **not** picocli-derivable — it needs a verb→codes source that does not exist yet. This is the flip side of the `CLI-SPEC` §2 correction that removed the premature "each op advertises `emits[]` in the manifest" claim. **Re-open when** a planning or apply-the-fix consumer needs the per-verb failure space proactively, or a probe shows agents failing to anticipate a verb's errors — likely then a **proposal**, since the verb→codes derivation carries real design risk.

- **A runnable next-action command on `refused`.** The `refused` envelope already carries the referrers (in `data`) and a `fix` diagnostic; emitting the *exact* remediation invocation (e.g. the `remove --cascade` line to run) is the note's "include next actions." **Re-open when** a fix-applying harness exists to consume it, or a probe shows agents failing to recover from `refused` despite referrers + `fix`.

- **Error-classification booleans (`retryable` / `correctableByAgent` / `userActionRequired`).** For dmtool these would be near-constant — the real signal already lives in `outcome` + `source` + presence-of-`fix`, and the one distinction that matters (a cascade *decision* vs a tool bug) is already encoded in `outcome`/exit-code. **Re-open when** an apply-the-fix harness actually consumes them (the same consumer-exists discipline that withheld a machine `suggest` field).

- **An envelope `version` field.** The note warns against unversioned output-shape drift. dmtool's whole envelope contract is **derived + drift-guarded** (`SchemaVerbTest`, `result.schema`), so an embedded version buys little today. **Re-open if** the envelope must change incompatibly, or an external consumer pins the shape and needs a version to negotiate against.

- **A cross-verb stdout-purity guard ("nothing but one JSON document").** *(Corrected 2026-08-03: the earlier entry rested on “not observed” and overstated the unguarded surface.)* A strict process-boundary sweep ran one canonical successful route for all **81 live leaves**: **79 JSON-promising routes** emitted exactly one JSON value with EOF immediately after it; bare `schema` deliberately emitted orientation text and `export card` deliberately emitted Markdown. The argument-dependent `export --out-dir` route also deliberately exits 0 with empty stdout while writing its four artifacts. The **error path** remains broadly guarded by `DiagnosticConformanceFuzzTest`, and `InternalErrorBoundaryTest` specifically locks an unexpected throwable to one structured error envelope on stdout with the trace on stderr. `VerbDemonstrationTest` now guards `--text` totality across the demonstrated envelope-producing success surface; `--text` is intentionally human text, not machine JSON. The remaining deferral is therefore narrower: there is no permanent route-class-aware strict parse-to-EOF guard over every success argument mode. **Re-open when** a JSON-promising route is seen contaminating stdout, or a consumer needs that stronger permanent coverage.

## 3. Out of scope — the remote / async operation model

A cluster of the note's recommendations presuppose a **resident or remote** tool: idempotency keys (§14), long-running operations with `operationId` / resume / poll (§15), the preview-id + confirmation-token lifecycle (§13), profiles / `--target-env` / auth status (§16), `--trace-id` + a correlated audit log (§16/§21), and cursor/pagination for large result sets (§17). dmtool is **local, synchronous, single-file, stateless-per-call** — the model file is the durable state, and git is the audit trail + undo. These recommendations **void** unless a resident mode lands, and that mode — **`dmtool serve`** — is already an examined **non-goal with its own re-open triggers** in [`FEATURE-GAPS.md`](FEATURE-GAPS.md) §4. They are pointed at, not re-litigated here.
