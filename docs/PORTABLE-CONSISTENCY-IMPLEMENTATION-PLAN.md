# Portable consistency — implementation plan

> **Planning baseline — 2026-09-11.** Implements the reviewed [portable consistency proposal](PORTABLE-CONSISTENCY-PROPOSAL.md) at `f0cba2488`. This is the fresh plan following the restart; no implementation slice is claimed complete. The proposal owns the product contract and acceptance matrices. This plan owns execution order, prerequisites, review checkpoints and the next bounded task.

**Scope.** The checker validates the **rules and computations** of a DocumentModel, conforming to the Kernel for A12 models — including the type-compatibility laws operators impose on their operands. It must support the whole model structure as context, resolving references against it and reading its type facts, but it does not validate whether a group, field or type declaration is itself legal: that is whole-model consistency and a separate product. The only exclusion is a Kernel law that cannot fire for an A12 model. No slice, stage or record below widens this; the authority is the [proposal's scope](PORTABLE-CONSISTENCY-PROPOSAL.md#4-required-functionality-and-scope-boundaries).

**NFR #1 — the interpreter's performance is never compromised.** The proposal's highest-ranked non-functional requirement outranks every checker goal, including the checker's own H5 budgets: no comparable interpreter row regresses by more than 5% against the restart baseline, per row with no compensation between rows, and missing or inconclusive evidence fails rather than passes. Ordinary evaluation takes on no checker dependency, analysis preparation or retained source graph. Where a stage below could trade interpreter cost for checker convenience, the interpreter wins by default and the trade is escalated, not made in passing. Obligation and evidence rules: [H4](PORTABLE-CONSISTENCY-PROPOSAL.md#hard-acceptance-conditions-confirmed-by-the-owner).

The fixed interpreter comparison baseline is `c8e3b99795fe9c2ce3e9db32632a6dd8f6537043`. The abandoned attempt at `6b4c6838737b5db7ad264ba7e207446b3cfcb27d` is read-only source/evidence material. Recover individual original-code changes only after identifying their owner and retained tests; do not restore its module graph, preview API, migration harness or performance qualification.

## 1. Working boundaries

- Build a standalone KMP checker with its own admission, syntax, binding and immutable analysis state. The default is a port of our original infrastructure. A neutral shared leaf is optional and starts with no permitted types until A establishes its bounded allowlist.
- Share selected model facts and measured constraints between designated Java façades and the checker. Preserve existing Java public contracts and deliberate authoring policies. Designate consumers explicitly; do not claim repository-wide consolidation.
- Keep interpreter execution preparation independent. Check both products' production closures and shipped-file ownership, including copied sources, declarations and generated output. Build-tool reuse does not transfer ownership of shipped API files.
- Preserve default Kernel checking in JVM/native dmtool. Portable checking is an explicitly selected consumer of the published checker; it never substitutes automatically for Kernel or vice versa.

**This work is a MIGRATION, and the boundary above is about contracts rather than implementations (recorded 2026-09-12, after it was read the other way for six slices).** It is **swift and feature-scoped**, which is the half that is just as easy to get wrong in the other direction: port exactly what the demanded feature needs and no more — `selectively` and `relevant` are load-bearing, and relevance is decided by what Kernel-free checking on TS/browser JS/Node/JVM demands (admission, preparation, binding, syntax, the checks, the codes), never by language tidiness. An estate-wide conversion programme is as far outside this scope as refusing to port at all; modelkit's authoring surface, `edit`, `schemakit`, the CLI and the Kernel-bound adapter are not in it. The proposal states the method in its own words — *"Selectively port the relevant dmkits foundations into Kotlin Multiplatform"* — and its delivery targets are *"TypeScript, browser JavaScript, Node.js **and Java/Kotlin**"*, so **Java is a CONSUMER of the KMP checker, not a parallel implementation of it**: `:consistency` builds a `jvm` target beside `js`, and a JVM consumer calls the ported Kotlin directly. NFR #1 makes the framing explicit where it bounds regressions *"during the migration"* — it is a fence protecting the already-Kotlin interpreter while the port proceeds, never an argument against porting.

**So "preserve existing Java public contracts" means the CONTRACT a consumer sees, which a façade over ported Kotlin satisfies and the KMP `jvm` target satisfies outright.** Reading it as "preserve the Java implementations" converts a ported family into a permanent duplicate. **How much of that has actually happened is measured, not assumed, and it is a minority:** of nine landed `CheckFamily` laws sampled against Java main source, **six have no Java counterpart at all** (`MVK_ERROR_CODE_MISSING`, `MVK_INCOMPLETE_INPUT`, `MVK_INVALID_INDEX_FIELD`, `MVK_INVALID_SORT_FIELD`, `MVK_ERROR_WRONG_ROUNDING_MODE`, `MVK_SUPP_LANGUAGES_MISSING` — net-new capability), and **three are enforced by the typed builders too** (`MVK_ERROR_MESSAGE_MISSING`, `MVK_RULE_NAME_INVALID`, `MVK_ERROR_EMPTY_PRECONDITION`, in `Rule.java`/`Computation.java`). So the duplication is real but bounded, and its denominator is the MVK ledger's **31 `pre-checked` rows** — laws a Java builder enforces that this checker may re-implement — not the family count. C1's extraction is the plan's mechanism for collapsing each one. *(Corrected 2026-09-12: the first version of this paragraph asserted all nine had live Java originals, which was written without measuring and is wrong in the self-critical direction — the same unverified-claim failure it was documenting.)*
- Start each port with the existing implementation and test owner. Translate our own code and reuse expectations. Add a test only for a named uncovered requirement, translation defect or platform difference; use red/green TDD for new behavior and fixes.
- Complete one finite slice before opening another. Freeze its families, fixtures, oracles and exclusions before implementation. An expanding acceptance denominator triggers the repository's convergence procedure, not another patch round.

Use the proposal's [scope boundaries](PORTABLE-CONSISTENCY-PROPOSAL.md#4-required-functionality-and-scope-boundaries) and [completion criteria](PORTABLE-CONSISTENCY-PROPOSAL.md#10-completion-criteria) when partitioning work; sequencing does not change either contract.

### A1 — method finding: the legacy exclusion is per-SITE, not per-code (measured 2026-09-12)

Under the conformance rule the 60 erased rows split into 52 that are **in scope by default** — needing no evidence, since exclusion is what requires it — and 8 whose ledger cell claims legacy/H-model. Only those 8 need work.

| *control* `MVK_INVALID_ENTITY` (in scope) | 3 | **1** |
| *control* `MVK_FIELDNAME_NOT_UNIQUE` (in scope) | 1 | 0 |

Two rows kill the criterion. `MVK_INVALID_UNSPECIFIED_TYPE` is called "legacy-only" by the ledger and has **no** `hdv` file at all; `MVK_INVALID_ENTITY` is squarely in scope — it is §3.4's own worked witness — and **has** one. So the heuristic both over- and under-matches.

**The finding is that the unit of disposition is the firing SITE, not the code.** Most of these codes are referenced from several files, and a code can be raised from a legacy path and a live one. [Proposal §7](PORTABLE-CONSISTENCY-PROPOSAL.md#7-implementation-slices-and-finite-acceptance-matrices) already says one code can represent several laws firing from several sources; this measures it. A1 therefore reads each candidate's sites individually, and the ledger's "legacy-only" prose is a lead rather than a basis.

**Recall limits.** `grep -rl` counts **files mentioning the token**, not firing sites: a file may reference a code without raising it, and an indirection through a constant would not be matched. No check implementation body has been read yet, so no row above is dispositioned — this measures only that the cheap criterion fails.

### A4 — consistency corpus ownership (decided 2026-09-12)

**Reuse the conformance corpus's case convention; do not build a second corpus.** [`corpus/`](../corpus/README.md) already holds every property A4 asks for: 34 cases across 10 family directories, each carrying a stable `meta.id`, the oracle artifact identity in `meta.kernelVersion`, provenance in `meta.source`, `meta.sections` and `meta.tags`, and — the part that matters most for "one input owner" — a `modelRef` indirection into a shared `corpus/models/` tree rather than an inlined model. That is the reuse A4 requires across common replay, adapter differentials and packed consumers.

**One bounded schema change is needed, and it is the whole gap.** [`corpus/case.schema.json`](../corpus/case.schema.json) lists `['meta', 'modelRef', 'document', 'op']` as top-level **required**, and admits exactly three op kinds — `validateFull`, `validatePart`, `compute` — all of which evaluate a Document. A consistency case has **no Document by contract**. So A4 adds a consistency op kind and makes `document` conditional on the kind rather than unconditionally required, leaving every existing case valid and untouched.

**What a consistency case carries instead of a document:** the accepted / rejected / incomplete expectation, and for a rejected case the measured code. Everything else — `meta.id`, `modelRef`, `meta.kernelVersion`, `meta.sections`, `meta.tags` — keeps the existing convention, so the same tooling enumerates both kinds. Note the family is the **directory name only**: no case carries a `meta.family` and the schema does not model one, the normative taxonomy being `meta.sections`.

**Why not the other fixture trees — enumerated properly this time.** Counted as `.dm.json` models per tree (the first pass mixed three different quantities: two `models/`-scoped JSON counts and one whole-`test/resources` JSON count):

| Tree | Models | Owner's job |
|---|---|---|
| `cli/src/test/resources/models` | 18 | JUnit + eval lanes |
| `examples/models` | 14 | published demos, own CI gate |
| `adapter/src/test/resources/models` | 14 | Kernel differentials |
| `src/test/resources/models` (root module) | 7 | the `validate/laws` accept/reject tier — where the checker's own law locks live |
| `interpreter/src/commonTest/resources/**` | 47 | workspace-preparation, performance, footprint, retained-result KMP fixtures |

The first pass named only the first three and then asserted the corpus was "the only tree designed as a shared input owner" — a negative existential over a denominator two trees short, and the root laws tier is precisely the one a consistency checker's accept/reject cases are adjacent to. **The corpus is still the right owner** — it alone carries per-case oracle identity and a `modelRef` indirection — but that is now a comparison against five trees rather than an unmeasured claim of uniqueness. [CLAUDE.md](../CLAUDE.md) keeps the demo and JUnit trees deliberately decoupled, so A4 repoints none of them.

**Per-case `kernelVersion` stays useful even with M deferred.** It records which artifact each expectation was measured against, so a corpus case cannot silently outlive its oracle — and if cross-version comparison is ever revived, it needs cases keyed this way rather than a parallel corpus.

### Neutral leaf — NOT EXTRACTED, allowlist stays empty (decided 2026-09-11)

Measured by reading the import lists of the two files a neutral syntax extraction would have to move. **So the leaf is not small: a neutral parser requires moving the whole AST, two model enums, an exception type and the decimal primitive.** `Dec` carries `big.js` as its JS actual, and its reach through the evaluator is wide — `ExprEval` operates on `Dec` directly and even the polarity-arithmetic path carries many `Dec` references. *That reach is an enumeration over the evaluator, not something the two import lists establish; the import lists establish only that extraction forces interpreter changes* — which is by itself decisive under [proposal §5.1](PORTABLE-CONSISTENCY-PROPOSAL.md#51-standalone-checker-with-independent-preparation)'s "prefer a checker-owned port if a shared implementation forces interpreter changes" and under NFR #1.

Until then this is declared intent, not an enforced invariant. Extraction stays available as a later reviewed change carrying its own H4/H5 evidence.

**One design question B inherits.** The checker still needs numeric handling for numeric literals and declared field bounds, and it must not reach for `Dec` to get it: `Dec` carries the kernel's rounding and precision model, while a checker comparing declared configuration needs the value's text preserved. B decides that representation on the [transport-value rule](../CLAUDE.md) — a lexical or `BigDecimal`-style handling, never an evaluation type.

### B2 record — preparation reports what the Kernel's reader raises (decided 2026-09-12, corrected after review)

**Landed:** admission (well-formed source, retained tree, authored numeric scale, source identity, A12's comment parity), the declared element set at its canonical path, `content.modelConfig.fieldRefByShortNameAllowed`, the §5.4 category separation, and B2's five acceptance cases. Kernel-free module and test dependencies are guarded by two instruments on `:consistency:check` — `verifyConsistencyPurity` over the JVM target's compiled main and test classes (`jdeps`, the shared `verifyCompiledPurity`), which also refuses a source set that does not compile into that target, and `verifyConsistencyDependencies` over both targets' resolved runtime classpaths with an allowlist of module groups, which is the only instrument that can see a dependency nothing imports. Both replaced an import-text scan. `check` rather than `test` is what runs them, and a Kotlin Multiplatform module registers no `test` task at all, so the workflow's unqualified `test` reached neither them nor any checker test until `:consistency:check` was named explicitly.

**The canonical path is the join of `name` segments, NOT the element's `id` — corrected before landing.** The first implementation read `id` as the path, which is the claim [KERNEL-INTEGRATION-NOTES](KERNEL-INTEGRATION-NOTES.md#dm-json-shape-for-hand-authoring-fixtures) already carries a dated correction against: `id` is an opaque identifier in a namespace disjoint from the path, and keying by it once resolved ~0% of a foreign model's references. The Kernel derives the path by appending `getName()` (`DocumentModelVisitorWithFullNames:56`); `ElementDeserializer` merely *stores* `id`, so it could never have settled the question it was cited for.

**The mechanism of that error is the one this project keeps a table about, so it is recorded rather than just fixed.** A fixture sweep found `id == path` on 934 elements of 52 models — and every model in that set was one we authored, where the two are equal by habit. The counterexample class was committed in this repository the whole time (`src/test/resources/models/idmismatch.dm.json` with hash ids, plus ten `workspace-preparation` opaque-id fixtures), and the selection excluded it. One constant across every row, no row on the other side of the axis, and the agreement of 934 of them established nothing. The prior-art search missed it too, for the adjacent reason: it grepped the terms the new work used (`ElementDeserializer`, `envelope`, `discriminator`) and the record states the fact in different words.

**A declaration is retained whole, not projected.** `DeclaredElement.declaration` is the entire authored node — envelope, element-level `annotations`, and the two descriptions, all of which `ElementSerializerUtil.serializeElementBase` writes and a per-kind projection would drop. A checker-side record of a rule's parts would be the parallel A12 model [proposal §5.3](PORTABLE-CONSISTENCY-PROPOSAL.md#53-retain-invalid-input-long-enough-to-diagnose-it) forbids, and it is also what would lose an *invalid* declaration.

**Where the Kernel's reader raises, preparation diagnoses — and nothing makes it raise.** A declaration missing `type` or `name` cannot be descended into (one names the envelope, the other places the subtree); a missing `id` is reported yet the element is still placed, because `id` no longer locates it. A kind outside the Kernel's closed four — including a mis-cased `"group"`, which hits its `default:` arm — is reported rather than passing as an inert declaration, since input A12 refuses being analysed here without a word is the direction no consumer can detect. Every array and boolean member is read through a diagnosing accessor, so no well-formed JSON escapes as an exception; that class was the alternative to a verdict or a coverage gap, and [proposal §6](PORTABLE-CONSISTENCY-PROPOSAL.md#6-public-contract) admits neither.

**Only a measured A12 constraint, violated at ERROR, rejects a model.** §5.4's three categories are `FindingCategory`, and `Finding.justifiesRejection` is the single locus that grants the power to one of them; an `AUTHORING_POLICY` or `EVALUATOR_SUPPORT` finding stated at ERROR does not reject, and an `A12_CONSTRAINT` finding at WARNING does not either. The ERROR threshold is **ours**, not a Kernel rejection: `checkConsistency` returns `void` and emits notifications, and every dmkits consumer draws the line at ERROR independently. Whether A12 treats a WARNING-only model as acceptable is an `:adapter` probe nobody has run.

**`ConsistencyStatus` has no `Valid`, and the control is behavioural rather than the compiler.** An exhaustive `when` over the sealed type forces a later `Valid` variant to *edit* the test, not to fail it, so the guard iterates what `statusOf` actually returns for every category × severity instead. `complete` is a constant `false` on both variants and carries no information yet — the coverage evidence that makes it informative is F's report.

**And an empty fact base now says so, rather than reading as a clean result.** A source that declares no elements produced the same findings-free report as one whose references all resolve, so a report meant "nothing was found to check" and read "nothing was wrong". ### B3 record — a mounted model is checked as a closure, not one file at a time (2026-09-12)

**The whole analysis used to stop at a mount, and that was most models.** A group carrying `Group.modelAlias` declares elements this source does not hold, so every reference into it reads as undeclared and the only safe report was INCONCLUSIVE with a gap. `ConsistencyWorkspace.fromSources(...).check(entryModelId)` is where a caller supplies the rest — the interpreter's `ModelWorkspace` shape (finite, caller-supplied, EXACT-ID, admitted at construction, entry named per check), owned by the checker because the published artifact carries no interpreter dependency. `check(ModelSource)` stays as the one-shot the proposal's §6 also asks for.

**Nothing is rewritten to mount it.** Descent continues into the provider's root-group children with the mount's path as the parent, so every declaration is still the node its own author wrote — B2's retention, unchanged. Three Kernel facts decide the placement, all in [KF3](KERNEL-FINDINGS.md#kf3): the provider's root group is REPLACED by the mount group rather than added above it (so the provider's own root name appears in no path, and a relative reference is move-invariant), the provider is fully expanded before it is mounted, and a mount group that already carries local `elements` is an ALREADY-EXPANDED mount whose reference is silently ignored.

**A reference that named the vanished root is rehosted, and that is the half a checker gets wrong silently.** `DeclarationOrigin` carries the model a declaration was authored in together with the prefix substitution its own absolute paths need. A relative path needs none; an absolute one needs exactly the substitution the Kernel applies before integration.

**The short-name fallback turned out to have two owners, which one denominator cannot express.** [KF287](KERNEL-FINDINGS.md#kf287) measures the grid: a provider whose OWN `fieldRefByShortNameAllowed` is on has its bare names bound before integration and searches that provider alone, while every other reference is bound over the whole expanded tree under the ENTRY model's flag — so a host field of the same name makes the second ambiguous and leaves the first untouched. The first implementation scoped every reference to its author and passed its own tests, because the fixture had no name both models declared; the surviving mutant is what exposed it.

**The cold review found the denominator wrong in both directions, and the doc sentence is what caused it.** [KF287](KERNEL-FINDINGS.md#kf287) read "searches that provider alone", so the first implementation keyed the bound fallback on the AUTHORING MODEL — which drops a field the provider's own nested include contributed, and finds both copies when one provider is mounted twice. Both reject a model A12 accepts. The denominator is the MOUNT INSTANCE's expanded subtree; the finding is corrected in place and the two shapes now have rows, because the original eight-cell grid has one mount and no nesting and could not separate them. Three further review findings were the same shape — a value read by its text rather than its type (`excludeRules: "true"` is FALSE to A12), an `includeLevel` spelling A12's enum refuses being expanded as the default, and a provider's unreadable declaration diagnosed under the entry model's identity.

**The same misreading was live in the JVM readers this slice measured against, and is fixed there too.** `dm.core.ModelReader` and modelkit's `AuthoredStateReader` both read the two exclusion members with Jackson's `asBoolean`, which coerces `"true"` and `1` — so the clean-room expansion dropped an executable the Kernel keeps, and `ModelDocument.authoredState()` (and the model review built on it) reported an exclusion A12 never applies. The kernel lock that was supposed to bound this measured `{}` alone, which is *also* what the coercion reads as false; widening it to twelve spellings, including the near-misses `"True"` and `0.5` that the coercion reads as the Kernel does, is what made the divergence visible and what bounds it, and the fix is the [KF3](KERNEL-FINDINGS.md#kf3) rule the checker already used. Fixing the component you measure against is the standing directive, not scope creep.

**The mounting now answers to the Kernel's own answers, not to fixtures I wrote.** `WorkspaceMatrixReconciliationTest` runs the 20-case shared raw-workspace matrix — authored in `:adapter` through the typed kits, its expanded facts locked against the real `expand` and the JVM reader by `WorkspacePreparationParityTest` — and compares the checker's prepared paths and kinds case by case. Eleven cases agree exactly, including a repeated mount, imported typedefs, a seven-source diamond and ten sources whose element ids are OPAQUE while the locked facts are keyed by path; nine name the mount they suspend. Condition TEXT is deliberately outside the comparison: the Kernel rewrites it at expansion where this checker retains the author's own node and rehosts only when resolving a reference. The oracle costs no classpath edge, because it arrives as committed data.

**Imported typedefs need no resolution at this stage.** A type definition is a FIELD TYPE keyed by id ([KF143](KERNEL-FINDINGS.md#kf143)): it is inlined into a field's `fieldType`, so it cannot move or rename an element — the reason the three typedef-carrying cases prepare identically to the Kernel without the checker reading a single type is that mechanism, and the matrix confirms rather than establishes it, since a path-and-kind comparison is invariant under type resolution by construction. Resolution becomes load-bearing for the first family that reads a field's KIND, and belongs to that slice rather than to this one.

**Parse-once is asserted by IDENTITY, because nothing else can count reads.** A reparse and a defensive copy both produce an equal tree, so `PreparationReuseTest` measures sameness instead: a provider mounted twice yields one retained declaration node bound at two mount prefixes — §5.6's "reuse its syntax, resolve each mount separately" as a pair of assertions on one Kernel-locked workspace — and preparing the same admitted sources again reads nothing again.

**It found a silent under-report on its first run, which is the class that matters most.** A provider whose OWN root group is an unexpanded mount had its (empty) `elements` read directly, so the include contributed nothing and the inner alias was never visited — no facts, and no gap saying so, which would have turned every reference into that subtree into a finding against a model A12 accepts. The mount now gives the provider's root group the same treatment as any other group, which is what "a provider is fully expanded before it is mounted" ([KF3](KERNEL-FINDINGS.md#kf3)) means one level down. The nineteen hand-written rows in `WorkspaceMountTest` had not distinguished it: every one of them mounts a provider whose root group holds its own elements.

**What is deliberately not expanded, each suspending the analysis by name rather than guessing.** `includeLevel: MODEL_ROOT`, `excludeRules`, `excludeComputations` — each changes which declarations survive or where they land, so an unimplemented one is a coverage gap at the mount. A malformed exclusion value is NOT one: the Kernel reads it as false and the content survives (KF3's coercion matrix), so suspending there would refuse an include A12 expands in full. A cycle, a provider with other than exactly one root group, an unresolvable alias and an unsupplied source are gaps too. So is an `includeLevel` spelling A12's enum cannot read — deliberately UNDER-reported, since A12 refuses to load such a model at all and reaching `CK_MODEL_NOT_BUILDABLE` from the mount path would need it to carry findings as well as gaps.

### B1 record — reference binding classifies three outcomes, not two (2026-09-12)

**A12 rejects an undeclared name and an ambiguous one DIFFERENTLY, so the checker must too.** `MVK_INVALID_ENTITY` and `MVK_FIELDNAME_NOT_UNIQUE` carry different correctives — declare the field, versus qualify the reference so it names one — and the interpreter's existing static helper reports both as the same unresolved path ([proposal §3.4](PORTABLE-CONSISTENCY-PROPOSAL.md#34-reuse-existing-static-reference-checking-distinguish-it-from-execution-preparation)). `Reference` is therefore a three-arm sum: `Resolved`, `Undeclared`, `Ambiguous`.

**The tier rule is the Kernel's, not a re-derivation.** The declaring group is tried first and wins outright; only on a miss does the model-wide fallback apply, and only when `fieldRefByShortNameAllowed` is on — the flag gates the second tier alone, which is why it changes the verdict for a name the group lacks and changes nothing for one it has. The fallback indexes **fields**, not every element; a resolver that indexed groups too would resolve a group short name and never be noticed, so that is its own control.

**The grid's accept-side row had no committed oracle until now.** `ShortNameTierLawsTest` holds the ambiguous pair, where the flag only chooses between two rejections — which cannot show the fallback SUCCEEDING, so on its own it leaves open whether the flag enables a lookup or retitles a refusal. `ShortNameUniqueTierLawsTest` adds the unique pair (`MVK_INVALID_ENTITY` → accepted), moving exactly one thing: the sibling group declares `Other` rather than a second `Code`. §3.4 had recorded those rows as executed session evidence and explicitly not locked.

### C2 record — the reference rejections, and where their correctives live (2026-09-12)

**Both codes ride the finding, and both are A12's.** `Reference.Undeclared` → `MVK_INVALID_ENTITY`, `Reference.Ambiguous` → `MVK_FIELDNAME_NOT_UNIQUE`, each `A12_CONSTRAINT` at ERROR because each is a locked Kernel verdict rather than a policy of ours. **Sharing that guidance with the portable report is C2's remaining piece, deliberately not improvised.** The checker is Kernel-free and carries no project dependency, so it cannot read `StructuralKernelFix`; restating the prose in Kotlin would mint the second live statement the doc rules forbid. The portable findings therefore carry the code and the observation and no `fix` text, rather than advertising guidance with nothing behind it. The single-owner mechanism — a shared resource both sides read, or generation from the Java owner — belongs with F's report contract, which is where the `fix`/`explain` fields become public.

### B0 record — the reference class that needs no parser, and the one that does (2026-09-12)

**Two reference classes, and only one of them is behind the syntax layer.** A12 declares a rule's error target and a computation's target as **structured members** (`errorEntityRelPath`, `computedFieldRelPath`), not as DSL text, so `declaredReferences()` resolves them with no condition parser at all. The references inside condition and operation text are the other class, and they wait for syntax.

**The relative path resolves from the declaring ELEMENT, not from its group**, which matters because the two readings agree on almost everything anyone writes: a rule at `/Order/Check` reaches its sibling as `../Code`, and dropping that step names a child of the rule. `ErrorFieldRelativePathLawsTest` locks it, and the row that discriminates is the only one in this repository where a group-relative resolver would have disagreed with A12.

**Two neighbouring gates were measured in the same pass, because each rejects a path that resolves perfectly well** and a reader seeing only the rejection would blame the path: the condition must also reference the target (`MVK_ERROR_FIELD_NOT_REFERENCED`), and that gate is why the lock's rows vary the error field together with the condition's own reference rather than the path alone — varying the path alone moved two variables and produced three wrong expectations before the Kernel said so. With the reference present, a target inside a repeatable group is ADMITTED, which bounds the second gate rather than leaving it as a guess.

**Consequence for the checker's contract:** `declaredReferences()` answers "does this path name a declared element" and nothing more. A resolvable path is necessary and not sufficient for A12 admission, so this slice's findings must never be read as a rule-level verdict — the remaining gates belong to D.

**The first public operation is `check(ModelSource): ConsistencyReport`.** It admits, prepares, resolves the structural references and reports — INVALID when one does not resolve, INCONCLUSIVE otherwise, never VALID, because `ConsistencyStatus` has no such arm and the coverage registry that would earn it does not exist. `findings` and `diagnostics` stay separate arrays on purpose: a finding is A12's verdict on a declaration, a diagnostic is the checker saying it could not read something, and folding them together is precisely the conflation `ModelLoader.loadAndCheck` makes on the Java side.

**`checksCompleted` is evidence, and every report also states what it could NOT check.** `CheckFamily` has one constant today, so "the reference check completed" would read as "the analysis completed" if nothing said otherwise; each report therefore carries an explicit gap naming the unimplemented families, and each unreadable declaration becomes a gap of its own rather than a silent omission. An unreadable source reports at the SOURCE level with no check completed, instead of inventing a rule location for it.

**The syntax layer is the next partition, and it is not small.** The Kernel's condition lexer resolves operator keywords *dynamically per language* (`ID` carries `setTypeInLexer`, driven by the multi-language handler), so a faithful checker-owned tokenizer needs the per-language keyword catalog rather than fixed literals — and the neutral-leaf record already rules out sharing the interpreter's parser. That is B0's remaining half and slice C's foundation, with its own acceptance matrix.

### B0 record — the syntax layer reads condition references without a parser (2026-09-12)

**Acceptance matrix, all measured on `referencesIn(text, language)`.** A keyword is not a reference and its argument is; an INFIX keyword is not a reference either, which is the case a structural guess gets wrong because `And` is a bare name with no parentheses; a string literal and a comment contribute nothing however condition-shaped their content; a path is kept whole; a quoted name IS a reference whatever it spells; a category after `->` is not one; `@From` is a single terminal, so its second half is not a name. Non-goals are stated on the function: `$` is dropped because it selects an outer repetition of the same declared element, an all-digit name is read as a constant, and nothing here decides whether the text parses.

**The keyword table is PER LANGUAGE, and that is a correctness requirement rather than completeness.** A model declares `content.modelConfig.conditionLanguage.code`, the Kernel resolves a name against that language's terminals alone, and the two vocabularies are not translations of one set ([KF283](KERNEL-FINDINGS.md#kf283)). A merged table reads a German model's field named `And` as an operator and drops the reference with no diagnostic — a silent false negative, which is the worst shape a checker can have. The table is generated from rulekit's catalog plus the terminals that catalog deliberately omits, declared with their reason in `consistency/build.gradle`, and `consistency.ConditionKeywordProjectionTest` pins the union to the Kernel's own bundles in both directions so neither list can drift.

**The discriminator against arithmetic is the OPERAND, not the spacing — and getting that wrong is the slice's main correction (cold review, 2026-09-12).** The first version read `[A] / [B]` as division and `A/B` as a path by requiring path tokens to touch, and justified it in a KDoc and here with "the lexer's `entity` rule admits no whitespace between a path's parts". That is false and this repository already said so: whitespace rides the lexer's HIDDEN channel and is insignificant between any two tokens ([KF76](KERNEL-FINDINGS.md#kf76)), which `:interpreter` had already hit, root-caused and locked (IF75/IF91, `PathWhitespaceParseTest`). KF76 also gives the real discriminator in one sentence — a bare identifier is never an arithmetic operand, so `/` and `*` after a bare path segment are always path syntax — and the adjacency check had no control, surviving its mutant against the whole lane. Three of the review's findings were the same shape: re-deriving what the interpreter's findings already record, and getting wrong the cases it names as its hardest.

The tokenizer's own two departures from a naive lexer stand, and each now has a control: a quoted name keeps its own kind, because the Kernel keeps the escape in the token TYPE (`NameOhnePunktMitQuotes` is a different terminal from the keyword the name spells); and a digit run followed by a letter is one NAME, because `NameOhnePunktZifferAmAnfang` is `ZiffernFolge STR …` — splitting `1City` hands a consumer the reference `City`, which usually exists.

**The references are now bound, and binding turned up a shipped defect in the codes.** A condition's relative path resolves from the rule's GROUP while `errorEntityRelPath` resolves from the rule ELEMENT — one level apart, both spellings natural — and the floor is the root group rather than the model root, with `MVK_TOO_MANY_PARENT_GROUPS` of its own ([KF284](KERNEL-FINDINGS.md#kf284)). The same pass measured that the code for an unresolvable reference depends on WHERE it was written, and the checker was reporting `MVK_INVALID_ENTITY` for all three: it is `MVK_ERROR_FIELD_MISSING` for a rule's error target, `MVK_INVALID_ENTITY` inside a condition, and no code at all for a computation's computed field.

**That last one is why the report grew a gap rather than just a finding.** The Kernel cannot BUILD a model whose computed field is missing, so it reports that and stops — no consistency verdict is produced, not even for defects the same model plainly has. A portable report listing findings for such a model would present its own reading as A12's, so the report says so at the declaration, and the code it uses (`CK_MODEL_NOT_BUILDABLE`) is the one code this checker owns, minted only after establishing that A12 defines none. It carries every shape with that outcome rather than one of them — an unresolvable computed field, a declared target that climbs past the root, and an unsupported `conditionLanguage` — because what a consumer must act on is the same in all three: A12 never judged this model at all.

**Three further rejections the review's measurements added, all of them cases where reporting the wrong thing rejects a model A12 accepts.** A candidate at ROOT-GROUP level draws `MVK_INVALID_ROOT_GROUP` rather than `MVK_INVALID_ENTITY`. A group that MOUNTS another model (`modelAlias` with no `elements`) leaves the fact base incomplete, so the reference families are suspended with a gap instead of reporting every reference into it as undeclared. And an unsupported `conditionLanguage` is a REFUSAL, not a fallback — A12 rejects the model outright, so no reading of its conditions exists to report ([KF283](KERNEL-FINDINGS.md#kf283), corrected).

**What this does not yet do.** Reference EXTRACTION is complete and BINDING covers the paths above; what a reference is allowed to be — the iteration gates, the wildcard rules, the operand types — belongs to D, and a resolvable reference remains necessary and not sufficient. Declared non-goals, each stated at its locus: `$`, an all-digit name and the H-model row specifiers on `referencesIn`; and the turning-point label's ANCESTOR check (A12 verifies it, this does not, which under-reports). (`Group.indexFieldName` / `Group.sortFields[].name` were listed here as unexamined until their own C family landed; see its record below.)

### Syntax-layer record — partitioned, and its first phase landed (2026-09-12)

**The partition exists because the layer is not one slice, and A12 itself says where the seams are.** A condition that does not parse draws one of FOUR phase-specific codes, measured through `checkConsistency` ([KF300](KERNEL-FINDINGS.md#kf300)): `MVK_LEXER_STANDARD_ERROR` when the text cannot be tokenized, then `MVK_UNEXPECTED_TOKEN`, `MVK_EXPECTED_TOKEN_NOT_FOUND` and `MVK_INCOMPLETE_INPUT` from the parser. The phases differ in RISK as much as in code, which is what makes them separate increments rather than one.

| increment | decidable from | over-rejection risk | state |
|---|---|---|---|
| **lexical** — the text tokenizes at all | the characters alone | none: a lexical failure does not depend on the grammar | **landed** (`CheckFamily.CONDITION_LEXICALITY`) |
| ~~**balanced structure** — delimiters pair up~~ | — | — | **WITHDRAWN, measured 2026-09-12** |
| **grammatical** — the tokens form a condition A12 accepts | the full grammar | **high — this is the one that can reject a legal model** | open |

**The middle increment was withdrawn the day it was planned, and the reason generalizes.** It assumed a delimiter imbalance could be reported without a grammar by counting. A12 does not partition the failures that way: only the shape where the input ENDS with something still open draws `MVK_EXPECTED_TOKEN_NOT_FOUND`, while an unclosed value bracket (`FieldFilled([Tier)`) and a bracket closing a parenthesis (`FieldFilled(Tier]`) both draw `MVK_UNEXPECTED_TOKEN` — the parser meets a token that is wrong where it stands before it ever runs out of input. The distinction is POSITIONAL, not arithmetic, so counting can detect an imbalance but never pick which of the two codes A12 gives, and a checker that guessed would report the wrong one on three of the five measured shapes. Two of the five predictions in that grid were wrong in exactly this way. The layer is therefore two phases, not three.

**The first increment reports only the shape that was measured.** An unterminated string literal, which the checker's tokenizer already recognized and the report simply never surfaced. A12's own message text ("Character '%s' at position %d is incorrect") shows it also refuses illegal CHARACTERS, and which those are is unmeasured — `@@@` lexes cleanly and fails a phase later — so nothing is claimed about them and the report carries a gap saying exactly that.

**The gate the GRAMMATICAL increment must pass before it lands, recorded now so it is not negotiated later.** A parser stricter than A12's rejects models the Kernel accepts, which is the one direction this checker must never take, so that increment is not shippable on unit tests alone: it needs the corpus `adapter.laws.ParserCorpusSweepTest` already drives — every catalog `validExample` and `computationExample`, their German localizations, and the opt-in real corpora — replayed against the checker's parser with a 100% acceptance bar on the always-on populations. The catalog lives in `rulekit` and the checker must not depend on it, so the corpus reaches `:consistency` the way its keyword table already does: GENERATED into the module with a regenerate-and-diff guard. That generator is part of the grammatical increment, not a prerequisite to be done separately.

**Family ownership is settled, and it was not obvious.** An unknown name used as a call, a foreign-language keyword, and a bare field reference as the whole condition are each `MVK_UNEXPECTED_TOKEN` — parse failures, not reference failures. So an unresolvable name never reaches A12's reference check, and the syntax layer owns it: reporting one of them from the reference family would name the wrong defect, and reporting from both would report it twice.


### C record — first frozen family: a declaration's own SLOTS (2026-09-12)

**Frozen family: the `name` and `errorMessage` slots of a stored rule or computation.** It is the family that can land before the checker owns a syntax layer — every row reads members A12 declares as structured JSON — and it is the first one where the Java builders' knowledge is a real asset rather than an analogy, because [proposal §3.2](PORTABLE-CONSISTENCY-PROPOSAL.md#32-java-already-contains-valuable-validation-knowledge-embedded-in-authoring)'s named sources (`Rule.Builder.build`, `LocalizedText.checkDeclared`) enforce exactly these five shapes today.

| shape | A12 | the checker reports |
|---|---|---|
| `name` begins `vk_vk`, any letter case | rejects | `MVK_RULE_NAME_INVALID`, `A12_CONSTRAINT` / ERROR |
| a RULE's `errorCode` absent or blank | rejects | `MVK_ERROR_CODE_MISSING`, same |
| a rule's `severity` absent, or spelled outside its enum | **admits** the absent one; refuses to READ the others | nothing — `Rule.Builder`'s `MVK_SEVERITY_MISSING` has no Kernel basis |
| no text collected for any declared locale — the member absent or empty, every `text` blank, or every entry naming an UNDECLARED locale | rejects | `MVK_ERROR_MESSAGE_MISSING`, same |
| one declared locale's entry absent or blank, others filled | rejects | `MVK_ERROR_MESSAGE_FOR_LANGUAGE_MISSING`, same |
| `header.locales` empty | rejects, and then collects no text at all | `MVK_SUPP_LANGUAGES_MISSING` model-level, same, beside a per-declaration `MVK_ERROR_MESSAGE_MISSING` |
| a message entry without a string `locale`/`text`, or any locale code A12's parser refuses, on either side | **never reads the source** | `CK_MODEL_NOT_BUILDABLE`, same — and that declaration's messages go unjudged |
| an entry for an UNDECLARED locale | **admits**, never collecting the text | `RK_UNDECLARED_MESSAGE_LOCALE`, `AUTHORING_POLICY` / WARNING |
| DUPLICATE entries for one locale | **admits**, keeping the LAST | `MVK_LANGUAGE_DUPLICATE`, `AUTHORING_POLICY` / WARNING |

**The two admitted rows carry as much weight as the three refusals**, and they are why C1's "authoring policy remains separately classified" needed a family with real rows rather than prose: `LocalizedText.checkDeclared` refuses both, deliberately and for good reasons, and a checker that inherited either refusal would reject a model the Kernel accepts. `Finding.justifiesRejection` already withholds that power from the category; these are the first findings to exercise it.

**Both carriers measured, and the one that looked settled was not.** `MVK_RULE_NAME_INVALID` reads as a rule's law and rejects a computation too — the Kernel calls both elements "Rule" in its diagnostics ([KF160](KERNEL-FINDINGS.md#kf160), widened). The prediction going in was the opposite, and it is exactly the scope transfer that needs no new branch and so prompts no question. It also exposed a live gap in the component being measured against: `Computation.Builder.build` had no such pre-check where `Rule.Builder.build` has had one since 2026-06-10, so it now has one.

**One CONSTANT ran through every fixture this family inherited, and two rows were added to break it.** Every message measurement in [KERNEL-FINDINGS §13](KERNEL-FINDINGS.md#kf158) held two declared locales and blanked *all* of them, so "a blank text is no message" and "this locale has no message" were one observation; blanking only `de_DE` separates them and draws the per-locale code. And emptying `header.locales` is the only row on the other side of that axis: the message demand survives, so the checker may report `MVK_ERROR_MESSAGE_MISSING` without first knowing what the model declares.

**Which locale set a MOUNTED declaration answers to had no answer, and A12 gives it one layer earlier than expected.** A provider that does not declare every locale of the entry model cannot be expanded at all ([KF288](KERNEL-FINDINGS.md#kf288)), so no mounted declaration ever faces a narrower set and the entry's is the only one in play. Preparation now suspends such a mount by name — under-reporting deliberately, on the same footing as an `includeLevel` spelling A12's enum refuses.

**The family's first landing read `errorMessage` and `locales` by rules the Kernel does not use, and a cold review found six symptoms of that one mechanism.** The fixtures it was measured against all came through `ModelWriter`, which emits one canonical spelling of everything, so the checker's reader was written for canonical DM-JSON and every departure from it was a guess: locales compared as TEXT (`en-US` would have drawn a coverage gap on a model A12 admits), `header.locales` read only in its `{code}` shape (a bare-string header silently switched off every per-locale demand), the FIRST usable entry kept where A12 keeps the last, messages collected for any locale rather than only declared ones, and a shape A12's own reader refuses reported as `MVK_ERROR_MESSAGE_MISSING` — presenting the checker's opinion as A12's about a model A12 never judged. The fix is one mechanism, not six patches: both sides go through one `localeKeyOrNull` mirroring A12's parser, including which spellings it REFUSES, and a refusal is reported as a refusal. [KF290](KERNEL-FINDINGS.md#kf290) holds the measurements, taken with the two sides varied independently because a table that moves both attributes every refusal to the header.

**The family's second arm found the over-rejection C1 exists to prevent, in the component it was porting FROM.** `errorCode` and `severity` are both `pre-checked` in the [MVK ledger](MVK-LEDGER.md) — `Rule.Builder.build` refuses each — so what A12 itself does had never been asked. Measured ([KF291](KERNEL-FINDINGS.md#kf291)): the `errorCode` refusal holds, and the `severity` one does not. An ABSENT `severity` is accepted by `checkConsistency`, and `MVK_SEVERITY_MISSING` fires for none of absent/null/empty, so the builder refuses a model the Kernel admits. **The checker therefore has no severity row at all** — translating the builder's refusal, which is what "translated from Java" invites, would have shipped that over-rejection into a second consumer. Two neighbouring shapes are likewise not verdicts and are not reported: a NUMERIC `errorCode` is coerced by A12 to the code `"7"`, and an explicit JSON `null` on any rule member refuses A12's reader outright.

**One prediction of this author's was refuted outright and is worth keeping visible**: "with no declared locale, one message is enough" — the Kernel answers `MVK_SUPP_LANGUAGES_MISSING,MVK_ERROR_MESSAGE_MISSING`, because collection is keyed by declared locale and an empty set collects nothing. It had been asserted in a green checker test, which is what a self-confirming reading looks like.

**C1's compile-time extraction is BLOCKED by publication order, and that is a measured constraint rather than a preference.** C1 asks for one shared finding-producing function both consumers call, which means a dependency edge from `:rulekit` to `:consistency`: the shared function must live in `commonMain` to reach the JS target, and nothing else is reachable from both. `:rulekit` is published as `dmkits-rulekit` and `:consistency` is not published at all, so that edge would put an unresolvable coordinate in a shipped POM. Publishing `:consistency` to fix it is F's decision, taken with F's API and packaging review — [§2](#2-execution-order-and-landing-boundaries) puts packed delivery there on purpose, and F3 is where the dmkits edge is already required. So the family lands in the checker now with the Kernel as the shared oracle for both consumers, and C1's extraction rides F3. **Re-open trigger:** the first `:consistency` publication.

### C record — second frozen family: a computation's ALTERNATIVES (2026-09-12)

**Frozen family: the `computationAlternatives` list of a stored computation.** It reads structure only, like the slots family, and it is the list D's "every precondition/alternative" scope has to reach — so getting its shape wrong would put D on a fact base that misreports which alternatives exist.

| stored shape | A12 | the checker reports |
|---|---|---|
| the member absent, or an EMPTY list | rejects | `MVK_INCOMPLETE_INPUT` **and** `MVK_CONDITION_MISSING`, `A12_CONSTRAINT` / ERROR |
| an alternative with no `operation`, or a blank/whitespace/`null` one | rejects | `MVK_INCOMPLETE_INPUT` alone, same |
| ONE alternative, unguarded | **admits** | nothing |
| TWO or more, any of them unguarded — first, last or both | rejects, with ONE notification for the computation | one `MVK_ERROR_EMPTY_PRECONDITION` naming which alternatives lack a guard, same |
| a `commonPrecondition` declared beside them | changes neither row above | unchanged — it is a different slot |
| a precondition present but BLANK or whitespace | rejects, as a PARSE error | nothing — left to the syntax family, and the report says so |
| the member as an object, a scalar or an explicit `null`, or an alternative that is not an object | **never reads the source** | `CK_MODEL_NOT_BUILDABLE`, same |

**The precondition law is the one a reader gets wrong, and locating it took three rows.** A single unguarded alternative is admitted, so "an alternative may be unguarded" looks settled; add a second and the pair is refused. Two accounts fit that one observation — *the last is the fallback and owes nothing* versus *each of several owes a guard* — and they disagree on every real model, so a checker built on the wrong one either rejects legal models or passes illegal ones. Unguarding the first, the last and both all draw the same code, which settles it.

**One CONSTANT ran through every row that established it, and the rows breaking it were added deliberately.** None declared a `commonPrecondition`, so "one alternative may be unguarded" and "an unguarded alternative is fine while nothing else guards the computation" were the same observation. Declaring one separates them and changes nothing: the common guard is a different slot, not a substitute.

**Three inferences from the sibling family were each refuted or confirmed by measurement rather than carried.** `errorMessage` ADMITS an object member — its deserializer iterates the node's elements — and `computationAlternatives` as an object is UNREADABLE: two list-shaped members, two readers. A blank string counts as ABSENT for `errorCode` and a message `text` and does NOT for a precondition, which reaches A12's condition parser whatever it spells and fails there as `MVK_UNEXPECTED_TOKEN`. And an explicit `null` refuses the reader on the LIST while being an ordinary verdict on the `operation` and `precondition` inside it — the null law splits inside this one member. All three are in [KF292](KERNEL-FINDINGS.md#kf292); the one that was predicted rather than measured is the one that was wrong.

**Consequence for the report:** `COMPUTATION_ALTERNATIVES` joins `checksCompleted`, and the report gains a standing gap saying that a precondition is checked for PRESENCE only. Advertising a precondition check while silently ignoring whether it parses is exactly the "parsed but never consumed" shape, so the boundary is stated where a consumer reads it rather than only here.

### Approved decisions — the syntax layer, the shared leaf, and an early end-to-end proof (owner-approved 2026-09-12)

**The checker rebuilds its own condition parser; only the VOCABULARY is shared.** The estate has no Java parser to port — the Java path delegates to the Kernel's `IRuleParser` — and its only Kernel-free parser is the interpreter's Kotlin one. Sharing that parser would make one component serve two jobs that disagree: the checker needs source positions and error recovery to say *where* a condition is wrong, and ordinary evaluation needs neither and would pay for both. NFR #1 decides that in advance ("where a design choice trades checker convenience against interpreter cost, the interpreter wins by default"), as does §1's "keep interpreter execution preparation independent". What IS shared is data rather than code — the keyword/operator vocabulary, alongside the language-neutral operator catalog — which confines the duplication to the grammar-walking code that legitimately differs. **The duplication is deliberate and this paragraph is its written reason**, per the rule that undocumented deliberate divergence is indistinguishable from a defect.

**A minimal shared leaf is published NOW, ahead of F.** C1's extraction is the only mechanism that stops duplication accruing, and its re-open trigger is the first `:consistency` publication. The cost that justified deferring it measures to zero today: nothing is deployed, so no consumer compatibility is inherited. Publishing the whole checker would commit its API prematurely, so the leaf carries only the shared predicates — it lives in `commonMain` to reach JS and commits to almost no surface. Every family landing after it is "port and retire" rather than "port and duplicate".

**An early Node sample project proves the whole setup works, deliberately before the checker is complete.** Order 8 qualifies packed Node delivery at the end; that is too late to learn that the packaging, the JS artifact or the API shape does not survive contact with a real consumer. Order 5a therefore adds a walking skeleton: a real Node project that installs the published artifact, checks a model and asserts a report, run on a clean install in CI. **Its acceptance is the PLUMBING, not the coverage** — a checker that reports a partial verdict over a partial family set passes it, and a checker that cannot be installed or called from Node fails it however complete its families are. It is a proof of the delivery path, so it does not move F's qualification bar and never becomes an argument that the product is finished.

**Start it SIMPLE and grow it along with the checker (owner instruction, 2026-09-12).** The first version proves one model reaching one report through the published artifact and nothing more; it gains cases as families land, rather than being designed up front for a checker that does not exist yet. A sample that waits for coverage proves nothing early, which is the whole reason this row sits at 5a.

**The first working sample goes to the owner together with an API document** — `docs/CONSISTENCY-API.md`, covering the checker's public entry point, its result contract (`ConsistencyReport`: status, findings, diagnostics, `checksCompleted`, gaps) and how a Node consumer calls it. The pairing is deliberate: the sample proves the path executes and the document states what a consumer may rely on, and a reader handed either alone cannot tell a partial verdict from a complete one — which is the single most misreadable thing about a checker that reports INCONCLUSIVE by construction.

**Third closed member: `errorCodesToSuppress`, and it CLEARED a client-side refusal instead of finding one.** The member looked like the highest-risk of the five because `Computation.Builder` throws for any code outside a single-member allowlist, which is the over-rejection shape C1 exists to catch. A12 refuses the same set, so the allowlist is audited and stands — worth recording because the audit's value is the same either way, and a cleared refusal is only cheap to state once it has been measured.

**What it did find is a shape law no set-reading could reach.** A12 comma-joins the member into one `@SuppressWarning(...)` pragma and re-parses it, so a second entry fails to parse whatever it spells — measured with the supported code carried twice, which is the control that separates the comma from an invalid entry. The `List<String>` is single-valued in practice ([KF298](KERNEL-FINDINGS.md#kf298)). It also corrected an MVK-ledger row that said rulekit never authors the directive: true of the inline condition text `DirectiveLawsTest` locks, false of the structured member, which is the same one-carrier-measured-two-claimed shape the D denominator exists to prevent.

**Fourth closed member: `variantFilter`, the first family whose output is a COVERAGE GAP rather than a finding.** An `ONLY` filter removes the declaration from `checkConsistency` altogether ([KF299](KERNEL-FINDINGS.md#kf299)), so A12 ADMITS a model carrying a broken rule and reports nothing at all — no finding, no warning, no code. That makes an ERROR the wrong response: it would reject what the Kernel accepts, the one direction this checker must never take. The gap states the true thing instead — this declaration was examined by nobody, so a clean verdict does not cover it — and it is the first concrete case of the report's finding/gap split carrying real weight rather than only saying which families ran.

**It also closed two rows at once, because the carrier transfer was measured rather than assumed.** The 2×2 that killed the two rival accounts was run on a rule, and the source mechanism (`CodeGenerationRule.checkModel` generating for the default variant and only `LOG.warn`-ing) is stated at the model level and names no declaration kind — which is exactly the shape of claim that has been wrong here before, so the same grid and the same two controls were re-run on a computation. All sixteen cells match. A further pair of rows carries the BROKEN declaration through `ONLY` with an empty `variants` list and with no `variants` member, because the shape rows alone are measured SOUND and ADMITTED there cannot distinguish "checked and clean" from "never checked": both suppress. So the filter TYPE alone decides, completely, and the implementation keys on it and never reads the list — reading the list would reintroduce the account the measurement killed.

## 4. Verification and review protocol

Each implementation task records: the frozen behavior/family set, source/test owners, selected fixture ids, expected results, enforcement locus, failing control, targeted command and non-goals. New Kernel-semantic claims add the [witness grid](TESTING-SPEC.md#witness-grid-design) before fixtures. Translation reuses the original cases; shared Java/JS agreement is parity, not an independent oracle.

| Obligation | Test owner / required detector |
|---|---|
| Shared behavior and Java compatibility | Retained Java tests and applicable compiled API checks; designated-façade dependency and targeted mutation controls prove both consumers use the shared predicate |
| A12 decision/classification | Independent pinned Kernel calls in `:adapter`, using original canonical inputs; portable module tests remain Kernel-free |
| Truthful report and coverage | Common tests with explicit expected findings/gaps; controls for skipped checks, first-error short circuit, lost attribution, failed prerequisites and unsupported input. Full report projection repeats through F consumers |
| Profile manifest ↔ implementation registry ↔ executed witnesses | A defines the finite mapping and F owns the CI reconciliation. Controls must fail when a manifest claims an unregistered check or a required witness has no execution evidence. Runtime completeness tests must also fail when a required profile check is skipped, even if the remaining checks pass |
| Source fidelity and reuse | Instrument the checker parser/expansion owner for self-contained, repeated-mount, malformed and all computation-fragment cases; repeat queries and old snapshots must retain their contract |
| Standalone ownership | Compiled/installed closure plus complete shipped-file/provenance enumeration, in both directions, with forbidden-dependency/file positive controls; external consumers run without the other core or Kernel |
| Engine identity | F1's actual invocation and substitution controls; derive receipts from resolved published implementation identity, preserving requested engine and failure stage. Verify JVM/native artifacts, not backend presence alone |
| Application correctness | Proposal §12's expected results through typed packed APIs; fresh-check equivalence for H/J/L/M, explicit reuse for L, browser partial-text diagnostics for I |

Review tasks in §2 follow [CLAUDE.md's cold-review rules](../CLAUDE.md): one terminal review per bounded landing and at most one earlier foundational review. Use a fresh, same-model, read-only reviewer with the frozen diff, matrix and actual verification evidence; no implementation delegation. Where code follows an already-settled pattern, do not add another foundational review. Settle in-scope findings against their oracle; route adjacent findings to their owning task. A change to the acceptance denominator invokes repartitioning before more implementation.

Run affected retained tests and mandatory compatibility/doc checks under the [run discipline](AGENT-RUN-DISCIPLINE.md). Use [test-evidence.sh](../scripts/test-evidence.sh) to distinguish executed results from cached/stale output. Do not repeat the full estate per commit. Native rebuilding occurs in F1/final artifact qualification under the required recapture → build → gate sequence; it is not part of each checker development loop.
