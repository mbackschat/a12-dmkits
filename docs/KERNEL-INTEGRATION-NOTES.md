# Kernel integration notes (findings for future work)

Working notes gathered while scaffolding Phase 1 against the A12 kernel **`30.8.1`** public surface (sibling repo `a12-kernel`, resolved from `mavenLocal`). These are verified against the kernel source unless marked otherwise. They complement the design in [`PROJECT-PROPOSAL.md`](./PROJECT-PROPOSAL.md); when something here contradicts the proposal, this file reflects what the code actually does.

## The kernel SOURCE is the primary oracle — read it, don't decompile jars (2026-06-07)

The **full kernel source** is checked out at the sibling repo **`../a12-kernel/kernel-tool/`** (consult-only — never edit). For any question about DSL syntax, rendering, or validation semantics, **read the source first** — it's authoritative and far cheaper than decompiling the `mavenLocal` jars or guessing from the BA doc. The high-value oracles, all under `kernel-core-parser/src/main/`:

| Question | Source | What it gives |
|---|---|---|
| **Exact DSL syntax** of any construct | `antlr4/.../grammar/gen/GrammarOnly_ConditionParser.g4` + `Base_ConditionLexer.g4` | the authoritative grammar productions + every keyword terminal (e.g. `fieldAndValueListCondition: name '(' entitySpec toOp feldUndStringListenSpezifier ')'`) |
| **Canonical rendering** (AST → text) | `java/.../parsebaum/util/formatter/FormatterVisitor.java` + `FormatterUtil.java` | how the kernel formats each node — the truth our `DslRenderer` should match (verified: tolerance via `getComparisonOperator`, `ValueAsDate` → `, FirstDay`, `RangeAsNumber` start+1, `NumberOfValueInFields` ` In ` separator) |
| **Validation semantics** (why an MVK_* fires) | `java/.../check/bedingung/Check*Impl.java` (+ `check/operation`, `check/entity`) | the per-construct checkers, with **javadoc** stating the rules (e.g. `CheckFieldAndValueListConditionImpl`: `ValueNotConsistent`'s first param must be a table-backed enum, the rest match its dependent columns) |
| **Parse-tree construction** | `java/.../parsebaum/creation/creators/.../*Creator.java` | how text becomes the `IXxx` parse-tree nodes the adapter consumes |
| **Localized keywords** (EN/DE) | `java/.../grammar/languages/LexerTerminals_en.java` / `_de.java` | the keyword ↔ terminal mapping (source form of the `LexerTerminals` ResourceBundle the `KeywordParityTest` checks); grep these instead of the compiled `.class` |
| **Field-type / model structure** | `../a12-kernel`'s `kernel-md-model*` source, or its jars' `-sources` | `IDateType.DatePrecision`, `IDocumentModelInfo.getBaseYear()`, serializer mixins (the DM-JSON keys) |

This source tree resolved `DatePrecision`, `baseYear`, the `ValueAsDate`/`Now`/`BaseYear` node shapes, and `ValueNotConsistent`'s real semantics far faster than jar archaeology would. **Probing the live kernel** (a throwaway validate-and-dump test, as in the family work) stays the way to confirm *behavior* (what validates, what an operation parses to); the source is the way to learn *syntax, rendering, and the rules*.

### Renderer ↔ kernel canonical-parity guardian (`adapter.CatalogRenderCanonicalParityTest`, 2026-06-07)

A guardian that pins our `DslRenderer` to the kernel's `FormatterVisitor` (the canonical formatter, reached via `KernelAdapter.canonicalConditionText`). For **every** SUPPORTED catalog `validExample` (106): read it → re-render our AST (relative to the rule group, the kernel's own path form) → assert the kernel canonicalizes *our render* identically to the example. Both sides pass through the kernel formatter, so path-form/whitespace differences cancel and only a real token/structure divergence survives. This is **strictly stronger than the render→parse→convert→render round-trip** (which is our-renderer-on-both-sides, so it can't see a loss that's consistent on read *and* write). **German is checked too**: the same AST is rendered in DE, parsed back through a de_DE twin of the fixture, and must re-read to the same condition (its EN render equals our EN render) — catching a bad/unparseable German keyword or structure the EN pass can't. Standing at **106 checked, 0 EN-mismatched, 0 DE-mismatched, 0 opaque**.

Building it immediately caught **four** read defects no other test saw — two **silent losses** (the cardinal F10/N8 sin) and two coverage gaps:
- **`FieldValuesNotUnique(Items*/Sku)` dropped the `*`** — it converted the keys via plain `fieldRefs` (which strips the wildcard) instead of the wildcard-aware `toFieldOperand`, so write-back drew `MVK_NO_WILDCARD`. (silent loss → fixed)
- **A semantic index `[field For "x"]` was silently dropped** — the `FieldValue` path ignored `IEntityId.getSemanticIndex()` (a `List<Object>` of quoted strings / entity refs), so it rendered a bare `[field]`. Now read as `SemanticIndexValue` for the single-string-index-on-a-number-field case; anything richer stays Opaque (never silently dropped). (silent loss → fixed)
- **`NumberOfFilledGroups(g1, g2)` over multiple distinct groups** wasn't read (only the single `Group*` form) → Opaque. (coverage gap → fixed)
- **`DateFromDateTime(...)`/`TimeFromDateTime(...)` on the *left* of a comparison** was routed to the numeric-extraction path (which rejects the date/time-valued part) → Opaque. Now routed to date/time comparison. (coverage gap → fixed)

Lesson: an our-renderer-on-both-sides round-trip proves *stability*, not *fidelity* — comparing against the kernel's canonical form is what catches a consistent read+write loss. (Task #9.)

## Validating a rule via `checkConsistency` (F4 — verified by experiment)

**Enum comparison by stored value works for text-bearing enums.** `[Tier] == "PRO"` validates against the kernel even though `Tier` is a text-bearing enum (BASIC/PRO/ENTERPRISE with labels). This clarifies the §5b "text-bearing enum ↔ string: no" rule: it forbids comparing an enum to an actual **string field/expression**, not to its own **enum-value literal** (the quoted stored value). So rulekit's `EnumRef.is("PRO")` → `[Tier] == "PRO"` is correct; the value is checked against the model's enum domain at build time.

Confirmed end-to-end by the `RuleValidator` increment (inject a `Rule` into the model DM-JSON → deserialize → `expand` → `checkConsistency`):

- **A rule must carry error text.** A rule with no `errorMessage` is rejected with `MVK_ERROR_MESSAGE_MISSING` (and a companion `RULE_HAS_NO_ERRORTEXT`). The validator therefore **auto-injects a placeholder `errorMessage` per model locale** so that requirement doesn't mask the condition diagnostics we actually want to check. (Locales come from `header.locales[].code` in the DM-JSON.)
- **Both absolute and relative paths validate.** Absolute (`FieldFilled(/Subscription/Addons/MonthlyFee)`) and relative-to-the-rule-group (`FieldFilled(MonthlyFee)`, `../Tier`) are both kernel-accepted (KERNEL-FINDINGS §paths). The path form is a readability/diff choice (§18.9 / fork #9), not a correctness one. **Rulekit's treatment:** `Rule.render()`/`draft()` and `Computation.draft()` now render **relative to the group** (the authoring norm — `DslRenderer` with a base group); standalone `DslRenderer.render` stays absolute (no group context — catalog/laws output unchanged). **Keyword-segment quoting (the other fork-9 half) is implemented** — the renderer single-quotes any path segment colliding with a catalog operator keyword (`*` suffix preserved); KERNEL-FINDINGS §paths, locked by `dsl.PathPolicyTest`.
- **error-field-referenced works across path forms.** The rule's `errorEntityRelPath` was relative (`../MonthlyFee`) while the condition referenced the field by absolute path; the kernel still considered the error field referenced (no `MVK_ERROR_FIELD_NOT_REFERENCED`). They resolve to the same node.
- **Not every code is `MVK_*`.** `checkConsistency` notifications carry mixed code styles — `MVK_INVALID_TYPE_FOR_COMPARISON` (string ordering) and `MVK_ERROR_MESSAGE_MISSING` have the `MVK_` prefix, but `RULE_HAS_NO_ERRORTEXT` does not. So MVK-code extraction from the message is **best-effort**; don't assume every problem yields an `MVK_*` code.
- **Rulekit's treatment — structured `Diagnostic` + catalog-join (F4a, first increment 2026-06-04).** `checkConsistency` problems are no longer raw `Problem`s: each becomes a `Diagnostic` (`severity·source·code·summary·where·fix·explain`, LSP-shaped). The kernel message stays as `summary`, the extracted `MVK_*` as `code`, the rule path as `where.rule`. The **catalog-join** (`OperatorCatalog.byInvalidError`) then attaches the matching `invalidExample.fix` + operator `meaning` — the curated fix DB is the **catalog**, N7-locked, so kernel diagnostics and authoring examples can't drift. `ValidationResult.toJson()` renders the array for agents (files-as-API). Several operators can report one code (all ordering ops → `MVK_INVALID_TYPE_FOR_COMPARISON`), so the join takes the first catalog entry as representative — unless **span-pointing** (`lint.SpanResolver`) pins the exact one by intersecting the code's catalog candidates with the rule's used operators (`OperatorUsage`); when that intersection is a single operator, `where.operator` is filled and the join becomes operator-exact (ambiguous/unknown codes stay representative), and `where.span` is attached from the renderer emit-map (`DslRenderer.renderWithSpans`) when a single rendered node carries that operator. **The lint layer (`lint.Linter`, F4a first lint increment) emits the same `Diagnostic` shape with `source=LINT`** and its own `RK_*` codes (`RK_CONTRADICTORY_PRESENCE`, `RK_PRESENCE_NOT_COMPLEMENTARY`, `RK_REDUNDANT_OPERAND`) — these are *not* kernel codes; they catch valid-but-suspicious conditions `checkConsistency` is silent on, and (having the AST node) they *do* populate `where.operator`. A **model-context** lint, `RK_NEG_CONDITION_IN_ITERATION` (`Linter.lint(BoundModel, Rule)`), **pre-warns** the kernel-delegated `MVK_NEG_CONDITION_IN_ITERATION` (KERNEL-FINDINGS §9): it fires when a rule iterates (`BoundModel.iteratesForErrorField` — a repeatable group on the error-field path) and carries a bare negative presence predicate with no positive guard. Conservative on purpose — the kernel's real classification is the ~800-line context-sensitive `IterationNotValidVisitor`, so the lint only flags the clearly-unguarded shape and leaves the final call to F4. A second rule-context lint, `RK_INVERTED_REQUIREDNESS`, flags the inverse of the kernel's **error-scenario** semantics: an `errorCondition` is true ⇒ the data is invalid, so a requiredness rule must fire on *absence* — a bare `FieldFilled(E)` on the rule's own error field `E` fires on *presence* and is almost certainly meant to be `FieldNotFilled(E)`. Bare-only (a guarded `FieldFilled(E) And <ctx>` is a legitimate "must be empty here" rule). A pure-AST lint, `RK_UNGUARDED_NUMBER_COMPARISON` (added 2026-06-05, from the developer-path eval), pre-warns the **empty-number-as-0** trap (KERNEL-SEMANTICS §2): an unguarded ordering comparison (`<`/`<=`/`>`/`>=`) of a number field — covering two operand shapes: **field-vs-constant**, precise (flag only **where `0` satisfies the comparison**, so `[X] > 100` is not flagged since `0 > 100` is false), and **field-vs-aggregate** (`[Q] < Sum(...)` — *extended 2026-06-05 after the T4 eval miss*), advisory: the aggregate's value is unknown so we can't prove `0` fires, but the empty-as-0 substitution is a real trap, so it's flagged regardless of direction. **Field-vs-field `[A] < [B]` is still left alone** (both empties default to 0 symmetrically, so it rarely surprises), and only ordering ops are considered. Serves both personas (the CLI `check`/`add` backstop and the developer's `RuleDiagnostics`). **"Did you mean" (`model.Suggest`)** enriches the fail-fast handle errors: an unknown path (`ModelIndex.require`) or an out-of-domain enum value (`EnumRef`) appends the nearest valid name by Levenshtein distance, gated by a typo-plausible threshold so a wholly wrong name draws no misleading hint. **The gotcha/INFO channel (`lint.Advisor`, `RK_GOTCHA`)** is the same family at `severity=INFO`: for every operator a rule uses (collected by `dsl.OperatorUsage`, which descends into nested `Calculation`s), it surfaces that operator's catalog `gotchas` as proactive notes — the semantic surprises `checkConsistency` never reports because the rule is *valid* (e.g. the `AddYears` leap-day disagreement). Origin stays LINT; severity is the kind axis (WARNING = suspicious, INFO = surprising). Each catalog gotcha carries a `GotchaKind` (`SURPRISE`/`AUTHORING`/`RENDERING`); the channel emits `SURPRISE`+`AUTHORING` and **suppresses `RENDERING`** (rulekit-handled trivia — language-independent symbols, And/Or parenthesization), so the notes stay author-relevant.
- **PRECHECK origin (F4a) — pre-checks carry a `Diagnostic`.** `Rule.Builder.build()` throws `PrecheckException` carrying a `Diagnostic` (`source=PRECHECK`, the `MVK_*` it prevents — e.g. `MVK_ERROR_MESSAGE_MISSING` — or an `RK_*` like `RK_INCOMPLETE_RULE`, plus an actionable `fix`). It extends `IllegalStateException`, so the fail-fast builder contract is unchanged; a caller wanting the structured shape catches it and reads `.diagnostic()`. (Computation.Builder and the handle/path refs still throw plain exceptions — incremental migration.)
- **F11 pre-check split — bias to acceptance, never a self-inflicted false positive.** Pre-checks are now classified by whether the *live kernel* is the authority on them:
    - **Hard at `build()`** (completeness + rulekit's own structure): the five `RK_INCOMPLETE_RULE` slots, locale-declared messages, and `MVK_ERROR_MESSAGE_MISSING` — the last stays hard because `RuleValidator` deliberately **injects placeholder messages** so the kernel never arbitrates message-presence (it can't be a false positive), and `RK_ERROR_FIELD_OUTSIDE_GROUP` because it guards `Rule.errorEntityRelPath()`'s own substring math.
    - **Deferred + advisory** (kernel-semantic mirror): `MVK_ERROR_FIELD_NOT_REFERENCED` — the `covers()` heuristic only *approximates* the kernel's rule. `build()` no longer throws on it; `Rule.deferredChecks()` returns it as a WARNING-severity PRECHECK `Diagnostic`, and `RuleDiagnostics` surfaces it **only when the live kernel didn't already report the same code** (dedup against the kernel verdict). Same kernel → the kernel's ERROR wins, no double-report; a more lenient (newer) kernel → the advisory is the lone signal and never flips `ok`. So a heuristic drifting from a future kernel can never be the *sole* reason an accepted rule is reported corrupt.
- **F11 kernel-version skew — `validate.KernelVersion`.** rulekit reads the running kernel's `Implementation-Version` (`Package.getImplementationVersion()` off any kernel class — spike-confirmed `30.8.1`; see KERNEL-FINDINGS) and compares it to the catalog's `verifiedAgainst` floor (now a header field in `operators.json`). On a mismatch, `RuleDiagnostics` emits one `ENVIRONMENT`-origin INFO (`RK_KERNEL_VERSION_SKEW`) per instance — authoring stays safe (public-surface binding), but operators/semantics new to the kernel may be unmodeled and catalog fixes are keyed to the floor. Never an ERROR, never a block; silent when versions match or the version is unreadable (bias to no false alarm).
- **N7 is built on top of this** (see the dedicated section below): a harness around `RuleValidator` checks every catalog example against the real kernel.
- **Group predicates verified** (2026-06-04 experiment; N7-locked via the catalog's group entries). All seven (`GroupFilled`/`GroupNotFilled` + the five group-list quantifiers) validate on non-repeatable subgroups. **An enclosing group reference satisfies error-field-referenced** — a rule whose condition is just `GroupFilled(ShippingAddress)` with `errorEntityRelPath ../ShippingAddress/Street` passes (confirms `KERNEL-SEMANTICS.md` §"error field"). Type-direction errors: `GroupFilled(field)` → **`MVK_NO_FIELDS_ALLOWED`**, `FieldFilled(group)` → **`MVK_NO_GROUPS_ALLOWED`** — both unrepresentable with typed `GroupRef`/`FieldRef` handles. DE keywords verified per token (`GroupFilled→KontextAngegeben`, `NotAllGroupsFilled→NichtAlleOderKeinKontextAngegeben`, …). The `MVK_NEG_CONDITION_IN_ITERATION` guard rule (negative conditions × repeatable groups) is now pre-warned by the `RK_NEG_CONDITION_IN_ITERATION` lint (`lint.LinterTest`) and exercised by the iteration cluster (`adapter.laws.CorrelationLawsTest` needs the positive guard to validate).
- **The message-locale law verified** (2026-06-04 experiment; pre-checked in both authoring builders, locked by `RuleAuthoringTest`). Header `locales` are valid Java locale codes (`fr_FR` fine; `en_us` fails at *deserialize* — "Invalid locale format"). **Caveat (corrected 2026-06-05):** a bare language-only code (`en`/`de`) — the *common* form in the A12 Tools workspaces (268 bare vs 107 full) — deserializes but is **rejected by the validation mode**: `checkConsistency` throws `"Sprache en wird nicht unterstützt"`. So validation needs a **full** code (`en_US`); bare-locale models must be normalized first (KERNEL-FINDINGS §13 supplement; `dsl.BareLocaleTest`). A rule/computation must carry a message for **every** declared locale — missing one → **`MVK_ERROR_MESSAGE_FOR_LANGUAGE_MISSING`**, none at all → `MVK_ERROR_MESSAGE_MISSING`. Messages for **undeclared** locales are **silently tolerated** by the kernel — rulekit rejects them (typo/dead-text guard). Access: the declared locales are on the **public** surface after all — `model.getHeader().getLocales()` via `a12-base`'s `Model`/`Header` (not on `IDocumentModel` itself, which only adds `getContent()`).
  - **Rulekit treatment — no format assumption; read codes verbatim, match exactly.** `RuleValidator`/`LintBackstop` placeholder-message generation iterates the header's declared codes as-is (the `List.of("en_US")` fallbacks fire only for a degenerate zero-locale model). The builder sugar `Dsl.en()`/`Dsl.de()` hardcodes the **full** `en_US`/`de_DE` and so is only correct for models that declare those exact codes — for a bare-`en` model (or any other code) use `Dsl.text("en", …)`. Since coverage is exact-string, the sugar would mismatch a declared `en` (an `en_US` message ≠ `en`). No code change forced today (every fixture/test uses the full form); a per-language resolution (pick the declared code whose language matches) is the future fix if we author against bare-locale workspace models.
- **Enum-category navigation verified with exact codes** (2026-06-04 experiment; N7-locked). `[Tier -> Pricing] == "PAID"` validates; unknown category → **`MVK_CATEGORY_UNKOWN`** (the kernel's own spelling); `->` on a non-enum field → **`MVK_NO_ENUMERATION`**; comparing to an *enum* value instead of a *category* value → **`MVK_INVALID_STRING_CONSTANT_FOR_ENUM_COMPARISON`** (the kernel checks the category's value domain). DM-JSON shape (from `a12-kernel-demo`): `"categories": [{"name": …, "values": […]}]` with **positional** pairing — `categories[c].values[i]` belongs to enum `values[i]`; the comparison domain is the distinct set. The `->` symbol is not in the keyword bundles (same in EN/DE). Curiosity: `[Tier -> Pricing] == [Tier]` (category vs. plain enum field) is *accepted* by the kernel.
- **Computation slot rules verified with exact codes** (2026-06-04 experiment; pre-checked in `Computation.build()`, kernel-locked via `ComputationAuthoringTest`). Simple, tiered (all-preconditioned), and `commonPrecondition` forms validate. **Mixing preconditioned and unconditional alternatives is rejected** — `MVK_ERROR_EMPTY_PRECONDITION` (an `.otherwise(...)` API is therefore kernel-illegal: either one unconditional alternative or all preconditioned). Referencing the computed field in a precondition **or** an operation → `MVK_ERROR_REFERENCE_TO_CALCULATED_FIELD` (same code, both slots) — but the ban is on a **direct field** reference; guarding a *repeatable* computed field via `GroupFilled`/`CurrentRepetition` on its **containing group** is legal (the pre-check was refined 2026-06-08 to exact field-match — `ConditionReferences.referencesField`, not the group-prefix `covers()`; see KERNEL-FINDINGS §11). A string operation into a number computed field → `MVK_INVALID_COMPARE_TO_ENUM_OR_STRING`. Computations also require error text (`MVK_ERROR_MESSAGE_MISSING`). Computation DM-JSON shape verified against `a12-kernel-demo`: `computedFieldRelPath`, `computationAlternatives[{precondition?, operation}]`, optional `commonPrecondition`, `errorMessage`.
- **Boolean/confirm comparison rules verified with exact codes** (2026-06-03 experiment, locked by `validate.laws.BooleanConfirmLawsTest` + the N7 `True`/`False` catalog examples). Boolean field: `== True`, `== False`, `!= True` all accepted; vs a string → **`MVK_INVALID_COMPARE_TO_YESNO`** ("boolean compares only to boolean or True/False"). Confirm field: `== True` / `!= True` accepted; **`== False` → `MVK_INVALID_COMPARE_TO_YES`** ("confirm compares only to confirm or True"); boolean ↔ confirm cross-compare also `MVK_INVALID_COMPARE_TO_YES`. Confirms §5b's Boolean≠Confirm split; rulekit's `ConfirmRef` consequently offers `confirmed()`/`notConfirmed()` and **no `isFalse()`** (unrepresentable). DE keywords verified per token: `True→Wahr` (WAHR), `False→Falsch` (FALSCH).
- **The decimal-scale equality check is field-vs-field only — numeric literals are scale-exempt** (verified 2026-06-03 by experiment). Against a scale-2 field (`MonthlyFee`), the kernel accepts `== 0`, `== 0.00`, `== 0.0`, `!= 0`, and `<= 0.000` — no `MVK_INVALID_COMPARE_DEC_PLACES`. That code fires for two *fields/expressions* of different declared scale (`[Quantity] == [UnitPrice]`, N7-proven via the catalog's `Equal` invalidExample). Consequence: rulekit's `String`/`BigDecimal` literal overloads (`eq("0.00")`) are *rendering-fidelity* ergonomics, not scale-trap avoidance; the D13 cheap pre-check matters only once comparisons take **field** operands. Locked by `validate.laws.NumberLawsTest` so a kernel upgrade that changes this fails loudly.

## Build / environment gotchas

- **The machine's global Gradle config injects a private registry** (`registry.internal.invalid`). A plain `./gradlew test` then fails to resolve even public deps (it routes Maven Central parent POMs through the private mirror). Build with an **isolated, public-repos-only `GRADLE_USER_HOME`** — the same trick the bootstrap uses. The sibling `a12-kernel-demo` documents `export GRADLE_USER_HOME="$ROOT/.gradle-isolated"`. rulekit's README does the same. Don't commit a per-machine init that hardcodes the private repo.
- **Wrapper download is blocked in the offline sandbox.** The committed wrapper points at the canonical `services.gradle.org` URL (correct for outside users). Locally, the bootstrap already extracted Gradle 9.0.0 under the a12 parent's `.gradle-dist/gradle-9.0.0/` — run that binary directly when offline.
- **JDK split:** JDK 21 runs the build (toolchain target). The bootstrap additionally needs JDK 25 only to compile `a12-devtools`' build-utilities — not relevant to a consumer like rulekit. Never hardcode a JDK path in committed files; use `$(/usr/libexec/java_home -v 21)`.
- **Why JDK 21 for the build, not a newer JDK (21 vs 25/26 — decided 2026-06-15).** The build/test toolchain is **pinned** to `JavaLanguageVersion.of(21)` in every module (root, `:cli`, `:adapter`), so Gradle auto-resolves an installed JDK 21 **regardless of `JAVA_HOME`** — installing OpenJDK 25/26 alongside does *not* change what compiles or runs the tests. Moving to 25 would be an explicit toolchain bump, and it isn't worth it: (1) the source targets Java 21 features only — nothing needs 25; (2) 21 is the LTS and the validated baseline against the pinned kernel; (3) the kernel's embedded **Groovy 3.0.25** (driving the runtime-eval verbs `model eval`/`rule test`/`model compute`) is *not* validated on JDK 25 and is the exact component that already needs special handling for native — running its tests on 25 risks spurious ASM/class-version failures for no gain. **GraalVM for JDK 25 is used *only* for `:cli:nativeCompile`** (a separate toolchain via `GRAALVM_HOME`, `toolchainDetection=false` — see [`NATIVE-IMAGE-GRAALVM.md`](NATIVE-IMAGE-GRAALVM.md)); plain OpenJDK 25/26 can't build native images anyway. So: JDK 21 for the JVM dev/test loop, GraalVM 25 for native — don't bump the dev toolchain.
- **TypeScript runtime is not built/published** by the OSS bootstrap (Java artifacts only). This is the concrete blocker behind "TS *validation* is a later milestone" — TS *build+render* can come sooner, TS *validate* cannot until the kernel TS runtime is buildable here.

## Public model-API surface (verified, `kernel-md-model-api` + `kernel-md-facade`)

- **Entry points come from `com.mgmtp.a12.kernel.md.facade.DocumentModelServiceFactory`**: `createDocumentModelSerializer()` → `IDocumentModelSerializer`, `createDocumentModelService()` → `IDocumentModelService`. Both interfaces live in `...md.model.api.services`. This is all on the `kernel-md-facade` compile classpath — no internal-tier dependency needed (confirms D9/N8 is achievable).
- **Navigation is a manual tree walk; there is no path-based lookup.** `IDocumentModel.getContent().getDocumentModelRoot()` returns a synthetic root `IGroup` whose `getElements()` are the top-level groups. Recurse `IGroup.getElements()` (`List<IElement>`), dispatching `instanceof IGroup` / `instanceof IField`. `IElement` (extends `IIdNamed`, `IDescribed`, `IAnnotated`) is the common supertype.
- **`getId()` is an *opaque identifier*, NOT the path — `getName()` is the short segment, and the absolute path is the join of `getName()` segments** (= what a condition references, the kernel's `getFullName()`). In rulekit's *own* fixtures `id` is authored equal to the path, which long hid the distinction — but **real-world models (the `a12-kernel-mm` metamodels, the A12 Tools apps) carry opaque/hash ids** (e.g. `3b16e188…`). **rulekit's `ModelIndex` keys elements by the name-path** (F-IDX, 2026-06-05): keying by `getId()` resolved ~0% of foreign-model rule references (id-namespace vs name-namespace, disjoint) — the fix took kernel-mm read 0 → 74%. *(Corrects the earlier claim that `getId()` IS the path. Locked: `model.ModelIndexNamePathTest`; `IDocumentModelService.getPath(IElement)` also computes a name-path for a known element.)*
- **`IFieldType` is a bare marker** — no kind accessor. Recover the kind by `instanceof` on the concrete public subtype. **Order matters:** `IDateTimeType` and `ITimeType` both `extends IDateType`, so test them *before* `IDateType`. (Encoded in `ValueKind.of(IFieldType)`.)
- **`IField.getEffectiveType()`** is a default method that resolves an `ITypeDefType` to its underlying type (after model expansion) and returns `Optional<IFieldType>`; classify the effective type, not the raw one.
- **Key type accessors used so far:** `INumberType.getMaxFractionalDigits()` (int — the decimal scale), `getMinValue()/getMaxValue()` (`Optional<BigDecimal>`), `getTrait()` (`Optional<String>` amount/percent/permille); `IEnumerationType.getValues()`/`getCategories()` (+ nested `IEnumValue`/`IEnumCategory`); `IStringType.getPattern()`; `IDateType.getFormat()`/`getDatePrecision()` (enum `FULL`/`*_OPTIONAL`).
- **Repeatability:** `IGroup.getRepeatability()` returns `int`; **`1` = non-repeatable**, higher = max repetitions (fixture: `Addons` = 20). `IGroup.getIndexField()` → `Optional<IDocumentModelObjectReference<IField>>`. rulekit treats `repeatability != 1` as "repeats" — revisit if a model ever uses `0`/negative for "unbounded" (not yet observed).
- **Config flags worth noting:** `IDocumentModelConfig.isFieldRefByShortNameAllowed()` (gates short-name paths — relevant to the §18.9 path policy), `getConditionLanguage()` (EN/DE keyword bundle), `getDecimalSeparator()`. Model-level **base year** is `IDocumentModelInfo.getBaseYear()` (`Optional<Integer>` — lifts the date year-presence comparability rule, §5b).

## The validate seam (`IDocumentModelService`) — verified signatures

- `void expand(IDocumentModel, IDocumentModelReferenceResolver)` — **mutates in place**, recursive, best-effort if a referenced model is invalid. Required even for self-contained models (no-op there). Javadoc advises running `checkConsistency` on included models before expansion and on the expanded model after.
- `void checkConsistency(IDocumentModel, Consumer<RankedNotification>)` — reports `MVK_*` and other problems via the callback. The preferred lightweight ground-truth step (§11); surfaces rule-condition errors (e.g. `MVK_INVALID_TYPE_FOR_COMPARISON`) as notifications rather than exceptions. **Correction (2026-06-05): it is *not* codegen-free.** Internally `checkConsistency` runs `CodeGenerationRule` → `generateValidationCode`, which **emits Groovy source via ANTLR StringTemplate v4** (then discards it) — so it *does* generate code, it just doesn't *compile* it (no Groovy `parseClass`/execute). Harmless on a JVM, but it's the **AOT/native-image constraint**: the StringTemplate stage needs all `internal/templates/**` resources bundled; see [`KERNEL-FINDINGS.md`](KERNEL-FINDINGS.md) "`checkConsistency` runs runtime code generation". (Runtime Groovy *compilation* only happens on the validation-*execution* path, which rulekit never uses.)
- `byte[] generateValidationCode(IDocumentModel, IValidationCodeGeneratorConfig, Properties, Consumer<RankedNotification>)` — the generate-and-discard alternative; still in-memory, still no compile if you drop the bytes.
- **`RankedNotification`** (`com.mgmtp.a12.model.notification`, from `a12-base/model-consistency`): `getMessage()`, `getSeverity()` → `Severity` (`INFO`/`WARNING`/`ERROR`, with `isAtLeastAsSevereAs`), `getSource()` (`Object` — often an `IDocumentModel`/`IGroup`/`IField`/rule node, or `null`). rulekit fails fast on any `ERROR` (see `ModelConsistencyException`).
- **`IDocumentModelReferenceResolver`** (`...md.model.api.services`): single method `IDocumentModel getDocumentModel(String reference)` — caller-supplied; returns the *unexpanded* referenced model. Distinct from `IDocumentModelResolver.getDocumentModelById(String)` used on the runtime/`validateFull` path (don't confuse the two).
- **Dynamic `validateFull` is a different thing** — it compiles+runs Groovy to validate *documents*, needs `kernel-core-runtime-30-8` + Groovy at runtime. Not needed for checking a *rule's* legality (that's `checkConsistency`), but it **is** the engine behind the `eval-doc`/`compute-doc` verbs (does a rule fire / what does a field compute on a document instance) — see the runtime-seam note below.

## DM-JSON shape (for hand-authoring fixtures)

- Top level: `header` (id, modelVersion, locales, `modelReferences`) + `content` (`modelInfo`, `modelConfig`, `modelRoot.rootGroups[]`).
- Nodes use a **tagged-union wrapper**: `{ "type": "Group", "id": "...", "name": "...", "Group": { ... } }`, fields `{ "type": "Field", ..., "Field": { "fieldType": { "type": "NumberType", "NumberType": { "maxFractionalDigits": 2 } } } }`. Enum/string/etc. follow the same `"type"` + `"<Type>": {...}` pattern; a bare `{ "type": "StringType" }` (no payload) is valid for defaults.
- Hand-authoring is fiddly; prefer copying a known-good model. Available fixtures in `a12-kernel-demo`: `src/main/resources/models/subscription.dm.json` (small: enum + string + number-scale-2 + a repeatable subgroup — copied into rulekit's `src/test/resources/models/`), and `output/purchase-order/purchase-order.dm.json` (richer: dates, integer + decimal numbers, boolean, 5 rules).

## Document-model super/subtype (model inheritance) = a header-annotation convention (verified 2026-06-14)

A document model can declare a **super/subtype hierarchy** with other models — but it is **not** a kernel structural feature, **not** a `modelReferences` purpose, and **not** a dedicated header field. It is a **modeling convention over the generic header `annotations`**, verified empirically from the real **2025.06-ext5** `e-commerce` models:

- a base model carries `{"name":"abstract","value":"true"}` + `{"name":"subTypes","value":"ProductMovie_DM,ProductBook_DM"}` (comma-separated subtype model ids);
- a subtype carries `{"name":"superTypes","value":"ProductSingle_DM"}` (comma-separated supertype model ids).

These are just **model-level annotations** the A12 Tools modeler reads to draw/relate the hierarchy; the kernel reads + round-trips them (a `config modify --annotation` value survives the kernel's own serializer) but does not *expand/merge* a supertype's structure into the subtype. **Shared structure is factored separately via `include`** (both Product models `include Product_Common_DM`). A red herring to avoid: the metamodel's field-type **`superType`** (the `String`/`Number`/`Date` family enum category, used by cross-field type checks) is a *different* concept.

**rulekit supports it today, no dedicated feature** — the model-level annotation surface authors the convention directly: `DocumentModelDraft.annotation("superTypes", "…")` / `ConfigEditor.annotation(...)` / CLI `config modify --annotation superTypes=…` (and `abstract`/`subTypes`). Locked by `modelkit.ModelHeaderTest.theModelSuperSubtypeConventionRoundTrips` (the convention survives the kernel round-trip). It is also surfaced **read-side**: `modelkit.Workspace` parses it (`abstract`/`superTypes`/`subTypes`), so the CLI `model info` (one model) and `workspace list` (a folder) both report the graph.

## Lexer terminals — the catalog ↔ grammar parity test (implemented; "deferred" flipped 2026-06-10)

One of the catalog's **four honesty anchors** (proposal §9/N3 — v2 added construct parity against the parsetree-api name enums + `MVK_*` enum, and the opt-in semantics drift oracle against the kernel's bilingual web content catalogs; sources for those in [`KERNEL-RULE-API-SURVEY.md`](./KERNEL-RULE-API-SURVEY.md) §13). This section covers the keyword anchor: a coverage test asserting every grammar lexer terminal is represented or explicitly excluded. The terminals live in **internal-tier** classes (so N8 says don't depend on them from main code — a test may, carefully): `a12-kernel/kernel-tool/kernel-core-parser/src/main/java/com/mgmtp/a12/kernel/core/parser/internal/grammar/languages/LexerTerminals_{en,de}.java`. Each is a `ListResourceBundle` whose `CONTENTS` maps a **keyword string → a shared token constant** on `Base_ConditionLexer` (e.g. `{ "And", Base_ConditionLexer.UND1 }` in EN, `{ "Und", Base_ConditionLexer.UND1 }` in DE). So reconciliation is **per token constant**, not per string, and the bundles are not 1:1 (some tokens have several keyword spellings — `And`/`and`/`AND` all map to `UND1`/`UND2`/`UND3`). Verified EN→DE pairs used in the seed catalog: `FieldFilled→FeldAngegeben`, `FieldNotFilled→FeldNichtAngegeben`, `And→Und`, `Or→Oder`, `Length→Laenge`, `Having→Mit`, `Sum→Summe`, `Today→Heute`, `PatternMatched→WieMuster`, `PatternViolated→NichtWieMuster`. Comparison operators (`<= == != < > >=`) and arithmetic symbols are **symbolic** terminals — identical in both languages. The design choice resolved to the reflective option: both directions are built and CI-locked — `catalog.KeywordParityTest` (catalog → terminals) and `catalog.KeywordReverseParityTest` (every terminal cataloged or explicitly excluded, self-cleaning exclusion list) load the internal `ListResourceBundle` from the test classpath (N8: tests may read the internal tier).

## DM-JSON write path (F6) — and the includes-safety rule

`BoundModel.ofJson(json[, resolver])` retains the **authored, unexpanded** DM-JSON; `add(Rule)` injects the rule element (with its real localized messages) by **Jackson tree surgery on that retained source**, then re-binds the result (deserialize → expand → `checkConsistency`) and returns a **new** binding (snapshot semantics, F0 — the original is untouched). `toJson()`/`writeTo(path)` emit the retained source.

- **Includes / `modelReferences` are preserved, never inlined.** The write edits the authored source JSON, *never* a re-serialization of the kernel's **expanded** `IDocumentModel` (which would flatten includes into the base file and lose the modular structure). Guarantee made executable: `WritePathTest.toJsonReturnsTheAuthoredSourceVerbatim` asserts `ofJson(json).toJson()` equals the input byte-for-byte. The resolver passed to `ofJson(json, resolver)` is retained and reused on every `add()` re-bind, so a model with includes round-trips through expansion correctly.
- **The write gate is `BasicConsistencyCheck`** (instrument 4), not `checkConsistency` — but re-binding runs the full `checkConsistency`, a strict superset, so an invalid write fails fast at `add()` (`WritePathTest.addReValidatesAndRejectsAKernelInvalidWrite`).
- **Limitation (fails fast, by design):** a rule's target group must exist in the *base* model's authored JSON; you cannot add a rule to a group that physically lives in an *included* sub-model (its elements aren't in the base file) — `ModelWriter` throws "no group at path" rather than corrupt anything. (Editing the included file is that file's concern.)
- **Includes are now fixture-tested** (`IncludesWritePathTest`, own-domain `storefront.dm.json` → `catalog.dm.json`, adapted from the A12 Tools workspace `modelAlias` include pattern): `ofJson(base, resolver)` expands so an included field is addressable (`m.num("/Storefront/Inventory_/Catalog/ListPrice")`); pure **load+save is byte-for-byte identity** on the base (`toJson()==input`) and the catalog is **never inlined and never written** (it's the resolver's read-only source) — the two models stay separate. Adding a rule (referencing base fields) keeps them separate and re-binds with the same resolver.
- **Two honest limits** (both deferred, documented): (1) a written rule that *references an included field* needs the expanded→authored path translation (the `_`-suffixed mount path is not authorable — `MVK_INVALID_ENTITY`; KERNEL-FINDINGS §10), fork-9 work; (2) `add()` **reformats** via Jackson (pretty-printed, ~2-space) so a *modified* model isn't byte-identical to the original formatting — only an unmodified load+save is. Content/structure (incl. `modelReferences`) is always preserved.
- **The MVK ledger is fully classified (300/300, 2026-06-10) — and its evidence comes in three tiers.** The metamodel section was resolved by the rule-explanation dogfood; the three enum sections by kernel-source reading (`Check*Impl` + BA doc) with targeted probes. Tier 1: **pre-checked** rows cite an existing builder check + its lock. Tier 2: **erased** rows rest on positive typed-API evidence (verified operand typing, legacy/H-model-only constructs, the §8 un-buildables). Tier 3: **kernel-delegated** rows are *source-mined law gists* — each names the law and why rulekit leaves it to F4, but they are **not individually probe-locked**; treat them as a documented law inventory whose claims F4 enforces operationally on every validate. **All 108 of them were cross-validated against the `Check*Impl` javadocs + firing logic on 2026-06-10**: 105 confirmed verbatim, two metamodel-tier rows correctly have no Java firing site, and one drift was corrected (`MVK_FIELD_REF_OP` turned out to be a *message label* that names the `[]` op inside other codes' messages, not a fireable law). The rows also name **candidate pre-checks** (search the ledger for "Candidate") — cheap builder tightenings discovered en route; the three with clear agent-facing payoff landed 2026-06-10 (`vk_vk` name prefix, duplicate message locales, the `RangeAs*` interval law), each with its builder lock plus a kernel-tier law lock in `validate.laws.RuleSlotLawsTest`.
- **The RT-semantics ledger is the MVK ledger's runtime sibling (instrument 6, 2026-06-10).** Where the MVK ledger drains *diagnostics*, [`RT-SEMANTICS-LEDGER.md`](RT-SEMANTICS-LEDGER.md) drains *evaluation semantics*: every class of `kernel-core-runtime`'s `internal.core` package classified, guardian-locked (`adapter.RtSemanticsLedgerTest`, a version-segment-agnostic jar scan, so a kernel bump that renames `_30_8` still matches). The first drain (comparison engine + combiner family) yielded the §12 value-vs-omission message typing, the tolerance boundary, the aggregate omitted-tail law, and the `FirstFilledValue` prefix laws — and re-confirmed the discipline that a source-read is only a hypothesis until a `RuntimeLaws` law locks it (the aggregate-typing probe overturned the naive read). The `RuntimeLaws` harness gained the `Msg.type`/`typeOf` channel (`IMessage.getMessageType()`) for exactly these locks.
- **Two enforcement tiers for the message-locale laws, by surface (2026-06-10, MVK-ledger dogfood).** The typed builder pre-checks them at `build()` (`LocalizedText.checkDeclared`: a message per declared locale, no undeclared locales — `RuleAuthoringTest`); the CLI `add` path deliberately does **not** rebuild those pre-checks — it validates the condition pre-persist (messages masked by placeholders, `AddCommand`) and lets the **post-write re-validation** catch message/locale problems, never mutating the model file on failure (probe-verified: blank text and missing-locale specs leave the file byte-identical). Same guarantee, different tier — agent-facing CLI errors arrive in the kernel's vocabulary (`MVK_ERROR_MESSAGE_MISSING`) rather than the builder's.
- **Directory resolver for whole-tree apps (F-RES, 2026-06-06).** `ReferenceResolvers.directory(root…)` indexes every `header.modelType=="document"` model under the trees by `header.id` and serves it via `getDocumentModel` — covering both `include` and `typeDefinitions` references with one index (a `_TDM` type-def model is itself `modelType: "document"`). Detection is by `modelType`, **not** a filename convention. `KernelAdapter.ofJson(json, resolver)` (and the existing `BoundModel.ofJson(json, resolver)`) expand both the MVK bootstrap and the index against it. Unblocked Corpus-1 read: 64/107-blocked → **106/107 load** (the reference scheme + measurement live in [`WORKSPACE-CORPUS-ANALYSIS.md`](WORKSPACE-CORPUS-ANALYSIS.md)).

## Structure read + round-trip (M7, 2026-06-10) — ride the generic tree, not the kernel's typed serializer

`modelkit.ModelDocument.read(json)` reads an existing model into its **authored source tree** (a plain Jackson `ObjectNode`) and enumerates its structure name-path-addressed (header, doc config, includes, type-def ids, the group/field tree + field-type discriminator + repeatability). Reading is **purely textual** — no kernel, no include resolution — so a model with unresolved includes still reads and enumerates (storefront's `catalog` include surfaces without the resolver). `toJson()` re-serializes the retained tree.

**The round-trip fidelity finding (the M7 source-mining result).** The kernel's own serializer is **not** a byte-lossless round-trip: its `JsonMapper` BASE instance sets `Include.NON_EMPTY` and several mixins use `@JsonInclude(NON_DEFAULT)` (`GroupMixin.required`, `DocModelConfigMixin.fieldRefByShortNameAllowed`, …), so deserialize→serialize **drops empty/default fields**. A **generic Jackson tree** round-trip (`readTree` → `writerWithDefaultPrettyPrinter`) goes through none of that typed machinery, so it is **content-lossless** — every field/value preserved, nothing defaulted-in — modulo pretty-print whitespace. **Consequence:** structure editing (M8) mutates and re-serializes the *tree*, never the kernel's expanded/typed model. Locked by `modelkit.ModelDocumentTest` (read→write is tree-equal to the source, idempotent, and the written-back self-contained model still passes the real kernel's `checkConsistency`).

**Distinct from `BoundModel`'s write path (above).** `BoundModel` retains the authored source *string* verbatim, so an unmodified `ofJson(json).toJson()` is **byte-for-byte** identical (and a *modified* model reformats). `ModelDocument` always re-serializes the tree, so even an unmodified round-trip is content-identical-but-reformatted — the right behavior for an edit substrate (edited or not, output is uniform), and exactly the path M8's surgical edits exercise.

## Structure edits + the delete-safety rule (M8/M9, 2026-06-10)

Structure edits (`ModelDocument.addField`/`addGroup`/`removeField`/`removeGroup`/`setRepeatable`) are **surgical tree mutations**; the single validity gate is `validate()` (re-bind → `checkConsistency`), which funnels both kernel rejection tiers — deserialize/expand (e.g. a duplicate id → `IllegalArgumentException`) and `checkConsistency` (ERROR notifications) — into one `ModelConsistencyException`. `EditSession` (the layer above the ⊥ kits) composes structure + rule edits over one DM-JSON and validates once.

**Delete is deliberately *not* reference-checked at the call site** (decided 2026-06-10, locked by `EditSessionTest.removingAFieldARuleReferencesIsRejectedByTheGate`):
- **The kernel gate is the authoritative dangling-reference check.** Removing a field a rule still references leaves the condition pointing at a missing entity, so `validate()` rejects it (`ModelConsistencyException`). We don't reimplement reference analysis — the engine arbitrates.
- **An edit session must tolerate invalid *intermediate* states.** Deleting a field *and* the rule that references it has no globally-valid per-step ordering if each step self-validates; batch-then-validate-once is the model, so `remove()` never auto-validates.
- **Reference analysis lives in the adapter, above the kits.** `KernelAdapter.whereUsed(path)` (F9a) is the "what references this?" oracle; `modelkit`/`EditSession` sit *below* the adapter (and `dm.modelkit ⊥ dm.rulekit`), so a proactive check there would mean reimplementing kernel reference resolution — forbidden.

**Client feedback shape.** `removeX(path)` throws `IllegalArgumentException` *only* for an absent path (a usage error); the dangling-reference problem surfaces at `validate()` as `ModelConsistencyException` (`.getMessage()` = the kernel diagnostic; `.notifications()` carries the `MVK_*` `RankedNotification`s on the `checkConsistency` tier, else the wrapped `cause`). Same gate `BoundModel.add` uses — uniform across the edit surface.

**Deferred to the CLI remove verb** (which has the adapter): a *proactive* `whereUsed`-based check that lists referencing rules and **refuses without `--force`** / offers an **explicit `--cascade`** (never a silent cascade-delete). That's where the capability lives; it's a UX layer over the same gate.

## Reference-rewriting refactors — one `StructureRefactor` seam, standalone + `apply` (2026-06-13)

The reference-rewriting refactors (`field`/`group` rename·move, `rule` rename, `typedef` rename) are single-sourced in `cli.StructureRefactor`: per op it carries the **safety-gate composition**, the **reference entity-moves** (empty for rule/typedef — they rewrite no AST references), and the **node mutation**. The two callers share it, so the §6 gate can't drift:
- the **standalone verb** (`ReferenceRewritingRefactorCommand` + the rule/typedef commands) — gate → `rewriteAndMutate` → `validate()` → write;
- the **`apply` op-record** — gate against the **live (transiently-edited) session** (so it sees prior ops), `rewriteAndMutate`, then re-home the result into a fresh `EditSession`, deferring to the one terminal gate; a refused gate throws → the whole sequence rolls back. `extract`/`inline` stay standalone (multi-artifact). See CLI-SPEC §6/§7.

**Treatment of the empty-group serialization quirk** (KERNEL-FINDINGS "Serialization shape — a childless group's `elements` array is omitted"): the rewriter round-trips through the kernel serializer, which drops a childless group's `elements`. `core.DmJson.elementsOf` therefore treats an **id-matched group with no `elements` array as an empty container and materializes the array** (`putArray`), so inserting/relocating into a freshly-added empty group works. Without this, `field`/`group move` into an empty destination spuriously failed "no group at path" — for the standalone verb too (it always rewrites first). *(Locked: `MoveVerbTest.movesAFieldIntoAChildlessGroup`, `ApplyRefactorTest`.)*

## The kernel's internal AST + unparser (read surface for N8's kernel-adapter tier — verified)

Verified 2026-06-03 against the sibling `a12-kernel` clone, prompted by `a12-antlr4-code-editor/ANALYSIS-RULES-EDITOR-AST.md` (the Rules-editor/AST analysis). This is the surface behind **D15** — relevant to the **#3 round-trip** and foreign-rule **explain** (F9), both **Phase 2** since bidirectional modification became a declared goal (proposal §2, same day). **The comprehensive inventory — incl. the `IMVK_Service` facade, `getMvkServiceForModel` bootstrap, `changeConditionText` rename refactoring, analysis services, per-rule `hasValidConditionText`, computation services, and the TS-side findings — lives in [`KERNEL-RULE-API-SURVEY.md`](./KERNEL-RULE-API-SURVEY.md); this section keeps only the core verified facts:**

- **A high-level, ANTLR-free AST exists**: `kernel-tool/kernel-core-parsetree-api` — ~40 typed node interfaces (`ICondition`, `IOperation`, `ICompositeOperation`, `IComparisonCondition`, …) plus type enums (`LogOp`, `CalcOp`, `OperationType`). Everything (interfaces included) lives under `com.mgmtp.a12.kernel.core.parsetree.a12internal.*` and is annotated `@OnlyForUsage` — traversal/reading is the kernel's *intended* consumer usage; the `a12internal` package withholds *stability*, it doesn't forbid use.
- **Text → AST**: `ParserService` (internal tier, `kernel-core-parser`) — `parseAndCheckCondition(IRule, IProblemReporter, ExpandMode)` and, notably, `parseAndCheckCondition(IRule, String conditionText, …)` (raw text + rule context — for foreign rules the `IRule` is already in the bound model, so foreign text → `ICondition` is one call); plus snippet entry points `parseConditionSnippet` / `parseOperationSnippet`.
- **AST → text (complete unparser)**: `ConditionFormatter` (internal tier) — `formatConditionText(ICondition, IRule)`, `formatConditionPart(IParseTreeEntity, String)`, and `formatAndTranslateConditionText(IRule, Locale, …)` (en↔de; translation working at all is strong evidence of full-grammar unparse coverage). Useful as a **differential test oracle** for rulekit's renderer (test tier — N8-legal today): compare `kernelFormat(kernelParse(rulekitRender(ast)))` with rulekit's canonical text; the translate variant checks the DE dialect against the kernel's own rendering.
- **`ASTVisitor` is an abstract class (~86 visit methods) with default-`true` bodies** — a converter visitor overrides only covered constructs and traps the rest in `visitGeneral` (fail fast on "unsupported construct"); the method list doubles as the #3 coverage checklist.
- **Condition comments (concrete syntax — authored + leading-preserved)**: the AST stores no whitespace/comments (`ConditionFormatter.stripComments` handles comments separately), so a pure AST re-render canonicalizes. rulekit keeps comments in a **side-channel** beside the AST — `rulekit.dsl.Comments`, a node-identity map (the "carrier (c)" design: the 15-type `Condition` hierarchy + its exhaustive switches stay untouched). The map carries both kinds of node the kernel comments — a `Condition` branch and a `Calculation` operation. Two consequences: comments are **authorable** on rules (`Rule.Builder.comment`/`commentAfter`) and on **computations** — their operations *and* preconditions (`Computation.Builder.comment(...)`) — all rendered as `;;` lines the kernel accepts; and a rule's **leading comment is preserved by default** on read→modify→write-back (`Comments.preserveLeading`, wired in `ModelWriter.replaceCondition`, so both the typed `modifyRule(Function)` and the text `modifyRule(String)` paths carry it). A **computation's** leading comments (common precondition + first operation) are carried the same way on modify (`ModelWriter.replaceComputation`, both the typed and spec overloads); per-alternative matching across a re-expression stays positional/out of scope. The residual loss is now only *inline/trailing* comments + non-canonical formatting (no AST node to anchor them across a re-expression) — `KernelAdapter.diff` discloses exactly that, carrying the leading comment on both sides. Confirms §12's blast-radius warning for #3, now narrowed. Law-locked — KERNEL-FINDINGS "Condition comments"; `adapter.ConditionCommentLossinessTest`, `adapter.CommentRoundTripTest`, `rulekit.dsl.CommentRenderTest`/`RuleCommentTest`.
- **No construction/mutation API**: all impl classes (`ConditionImpl`, …, assembled by `ParseTreeCreator`) are internal, and `RuleBuilder` takes `errorCondition` as an opaque string. The N8 adapter is therefore **read-only by policy** — rulekit's own AST stays the only write surface (D15).
- **Dead ends checked**: `kernel-rewrite` contains OpenRewrite kernel-upgrade recipes, not rule rewriting. The official Rules editor (`a12-antlr4-code-editor` + `kernel-core-parser-web`) builds **no AST at all** — it edits the raw DSL string (token stream for highlighting, parse-for-errors with the tree discarded, ATN-walk completion), so the TS stack offers no round-trip shortcut, and "emit the string" (F6) is exactly how the platform's own tooling integrates with the kernel.

## Kernel-adapter bootstrap (Phase 2, F10/F9a foundation — verified 2026-06-04)

The opt-in `adapter` module (proposal D15/N8 tier 3, Gradle subproject — `:adapter:test`, kept out of core's `:test`) reaches the kernel's `a12internal` *read* surface for rules **already in a model** (the foreign-rule path read and exact whereUsed build on). The bootstrap chain was javap-verified against `30.8.1` and stays entirely in the `a12internal.api` tier:

1. public `IDocumentModel` (deserialize + `expand`, as `RuleValidator` does) → internal `DocumentModel` via **static** `ExternalDocumentModelSerializerService.getInternDocumentModel(IDocumentModel)` (`kernel-md-serializer`).
2. `new DocumentModelService().getMvkServiceForModel(DocumentModel, variantString, IProblemReporter)` → `IMVK_Service` (`kernel-md-model`). The `variant` is a plain `String`; the bootstrap picks the model's first `extractUsedVariants` (public service), else `""`.
3. **Acquiring a tool `IRule`** — the linchpin. `IMVK_Service` declares *no* method returning one; the kernel's own recipe (decompiled from `DocumentModelService.findIRule`) is: cast `mvk.getIEC()` to **`ElementContainer`** (`kernel-md-model`, `a12internal.services`) and `getAllRules()`, then match by `getFullName()` (== `DocumentModelService.getPath(element)`, the absolute path). The runtime IEC is always an `ElementContainer` *provided the service was obtained via `getMvkServiceForModel`* (custom `IMVK_Service` impls are rejected with an explicit message). **N8 boundary point:** this foreign-rule path is fully `a12internal.api`; the *only* way to synthesize a context `IRule` from nothing is the **impl-tier** constructor `…md.model.internal.service.mapping.Rule`, so rulekit prefers reusing a real rule and never constructs one. (Red herring: `…internal.wrapper.RuleWrapper` implements the *public* `md.model.api.IRule`, not the tool `ado.IRule` — useless here.)
4. From the `IRule`: `parseConditionNoExpand(IRule, text, pr) → ICondition` (the transport AST, `kernel-core-parsetree-api`), `formatConditionText(IRule, pr)` / `formatConditionText(ICondition, IRule)`, `getDirectlyReferencedEntities(IRule, pr) → Set<IEntity>` (each `getFullName()`), `hasValidConditionText(IRule, pr)`. `IMVK_Service` *is* the parser/formatter/meta-info (it extends those interfaces — no `getRuleParser()`-style accessors).

**Treatment (`adapter.KernelAdapter`, boundary conversion):** every public method takes/returns only rulekit or JDK types (`String`/`Set<String>`/`boolean`) — `IMVK_Service`/`ICondition`/`IRule` never escape. Read-only: no `…Impl` constructed or mutated. The bootstrap exposes `referencedFields` (exact F9a whereUsed — needs no converter), `canonicalConditionText` (kernel parse+format round-trip), and `hasValidCondition` (the per-rule fast lane, survey §10). Its **translate peer** `canonicalConditionText(rule, ConditionLanguage)` (FEATURE-GAPS §3.2, 2026-06-13; the `rule format`/`computation format` verbs) re-emits via the kernel's `formatAndTranslateConditionText` for the EN↔DE keyword switch — it takes rulekit's `ConditionLanguage`, **not** a raw `Locale`, because the kernel recognizes only `Locale.US`/`Locale.GERMANY` and silently falls back to German for any other locale (KERNEL-FINDINGS; `KernelAdapterFormatTest`). The canary `KernelAdapterBootstrapTest` authors a rule with rulekit, writes it in (F6), and reads it back — and is the N8 **pin+canary** that fails loudly if a kernel bump breaks the unstable internal surface. The converter visitor (F10) and `IProblem → Diagnostic` mapping are the next increments.

## F10 read — the converter (first slice, 2026-06-04)

The read direction: `KernelAdapter.read(ruleFullName)` parses a rule's stored condition (`parseBedingungNoExpand`) and `ConditionConverter` walks the kernel `ICondition` tree into rulekit's typed `Condition` AST. **It re-authors through the `BoundModel` handle API** (`model.field/num/str/enumOf(...)` + `.filled()/.gt()/.is()/.and()` …) rather than hand-building record nodes — so every converted node carries the D14 invariant (catalog id + model-resolved refs + provenance) automatically, indistinguishable from a hand-authored one. Recursive `instanceof` dispatch; the field kind for a comparison comes from `BoundModel.fieldAt(path).kind()` (the kernel path node has none). Literals reuse the kernel's String value via rulekit's `gt(String)`/`eq(String)`/… overloads — no re-parsing.

- **Coverage** (corpus-frequent core, grown by priority): composite And/Or (`ICompositeCondition`); comparisons on number/string/enum fields against a constant or another field (`IComparisonCondition` → `gt/lt/ge/le/eq/ne`, `str.eq`, `enum.is`); string **patterns** (`WM`/`NM` → `str.matches`/`str.violates`); **presence** — single field/group (1-element `AllFieldsFilled`/`AllGroupsFilled`→`.filled()`, `NoFieldFilled`/`NoGroupFilled`→`.notFilled()`); the **field-list and group-list quantifier families** (`AllFieldsFilled`/`AtLeastOneFieldFilled`/`NotExactlyOneFieldFilled`/… and the group analogues, multi-entity → `model.allFieldsFilled(paths…)` / `Dsl.*GroupsFilled(refs…)`); **value-list membership** (`IValueListCondition` `FieldValueIncludedInValueList`/`…NotIncluded…` → `str/enum/num .in()/.notIn()`; number values must be integers); and **aggregates** as comparison operands (`IEntityListOperation` `Sum`/`MaxValue`/`MinValue`/`NumberOfDifferentValues` over a wildcard scope → `Dsl.sum(model.flatten("…*/…"))`.gt(…) etc.), including **`Having`** (the entity's `getFilterCondition()` converts recursively → `FieldListRef.having(...)`). The wildcard `*`-path is rebuilt from `IEntityId.getIndices()` (the `WILDCARD`-marked segment); see KERNEL-FINDINGS. Plus the **iteration/uniqueness cluster**: `CurrentRepetition` (`IGroupOperation` → `Dsl.currentRepetition(group)` as a numeric operand), `RepetitionNotUnique` (`IEntityListCondition` key fields + optional `.from` scope from `getAdditionalGroupReference()`), and `FieldValuesNotUnique` (field list). Plus **dates**: a `DATE`-kind field comparison maps to `DateRef.before/onOrBefore/after/onOrAfter/eq` against a date operand — a date field, or `Today` (`IPointInTimeOperation` → `Dsl.today()`); `DifferenceInDays`/`Months`/`Years` (`IDateDiffOperation`, `getDateSpec1/2`) is a numeric operand → `Dsl.differenceInDays(a, b)`.gt(…).
- **Foreign-model read measured + unblocked (2026-06-05, modelkit spike).** Until F-IDX (name-path keying), read of *foreign* models resolved ~0% (only id==path fixtures had ever been tested). Post-fix, **kernel-mm reads at 74%** (407/553 rules), +53 `CustomCondition` correctly-Opaque ⇒ 83% understood. The wiring grew with it: **boolean/confirm comparisons** (`[flag] == True/False`, confirm `== True`/`!= True` → `BoolRef`/`ConfirmRef`) and the **`!=` direction** for string/enum. Remaining tail = F10 features (combined entity+value lists, operand wrappers, group-scope aggregates, root-group conditions, enum category-navigation). Measured by the opt-in `adapter.KernelMmReadCoverageTest` (coverage-floor gated); root cause + breakdown in [`MODELKIT-PROPOSAL.md`](MODELKIT-PROPOSAL.md) §H.
- **Read reaches 100% of kernel-mm (2026-06-06).** The whole F10 tail was built out increment-by-increment (each round-trip + kernel-validity locked): entity+value lists (constant *and* entity-valued), count aggregates (incl. `NumberOfFilledGroups(Group*)`), `Length`, multi-field `Sum`, enum **category-navigation** (incl. category-vs-category), **group-scoped field-fill** via the new `GroupListRef` (nested wildcards faithful), **root-group presence** (`IRootGroupCondition`→GroupFilled/NotFilled), **arithmetic** (`ICompositeOperation`→`Arithmetic`), constant-on-the-left normalization, and finally **custom conditions** (`IApplicationCondition`→ the typed, editable `CustomConditionRef`). Result: **553/553 (100%)**, 0 opaque. The `ReadResult.Opaque` path is retained as the safety valve for constructs a future kernel adds — both corpora currently read 100% (date shifts, the last named opaque family, converted 2026-06-07; stale example flipped 2026-06-10) — anything unconverted is still preserved verbatim. (Since 2026-06-08 the 553 is **partitioned** — `readAll()` is the 547 validation rules, the 6 computations ride `readAllComputations()`; total typed coverage is unchanged. See "`getAllRules()` ⊇ computations" below.) Floor gated at ≥545 (of 547 validation rules) in `KernelMmReadCoverageTest`, computations `== total` (6); full increment list in [`MODELKIT-PROPOSAL.md`](MODELKIT-PROPOSAL.md) §H.
- **Tolerant read — a sealed `ReadResult` result (F11 "preserve the unknown"; finding 5).** `read(rule)` returns `ReadResult.Converted(condition)` or `ReadResult.Opaque(canonicalText, reason)` — a not-yet-modeled construct is **preserved verbatim** (the raw stored condition text, re-emittable on write-back) with a reason naming it, **never lost and never reported as corrupt**. A valid rule the kernel accepts never throws. `readAll()` does a whole model, per-rule, so a user's DM reads safely (supported rules typed, the rest opaque). The converter still throws `UnsupportedConstructException` internally — it is the recursive unwind signal, caught by `read` and surfaced as `Opaque.reason()` (and remains the strict, fail-fast contract for any future authoring-side use). Coverage grows by corpus priority (`WORKSPACE-CORPUS-ANALYSIS`); the opaque variant turns the tail from hard failures into preserved-with-a-warning.
- **Opaque preserves the *raw stored* text, not the kernel-canonical form (2026-06-06).** `read` builds `ReadResult.Opaque` from `IRule.getErrorConditionText()` (the verbatim stored condition), falling back to the canonical form only when that's absent. Reason: the kernel's `formatConditionText` is **lossy for a `$` correlation** — it truncates such a condition to its first conjunct (KERNEL-FINDINGS), so preserving canonical would *lose* the rule on write-back, the opposite of "verbatim". (The `Opaque` record component is still named `canonicalText` to keep the CLI output key stable; it now carries the raw text.)
- **`$` outer-iteration correlation — authoring done; read still loud Opaque (N8; authoring 2026-06-07).** The two directions are split:
  - **Authoring (build → render → kernel-validate): implemented.** The marker is an `outer` flag on `FieldValue` (`[$path]`); `StringRef.outer()` / `NumberRef.outer()` set it, and `DslRenderer` emits `$` only in the bracketed value form (a filter comparison) — not in argument position. An authored correlation (`Sum(Items*/Count Having [$/Order/Quantity] == [Items/Count]) > 5`) renders the `$` and the real kernel accepts it. Locked by `dsl.operators.CorrelationConditionTest` (render EN/DE) + `adapter.OuterCorrelationAuthoringTest` (kernel-valid).
  - **Read (parse → convert): complete (2026-06-07) — Corpus-1 87.0% → 95.0%, `$` opaques 127 → 0.** Two pieces. **(a) Thread the outer flag** through every field-vs-field comparison kind — `fieldValueComparison` marks the left operand, the per-kind builders (`numberComparison`/`stringComparison`/`enumComparison`/`convertDateOperand`/`categoryComparison`) the right — plus `CurrentRepetition($group)`, **presence predicates** (`NoFieldFilled($a, $b)` via `FieldRef.outer`), and **value-list operands** (`FieldListRef.outer`, at the single `toFieldOperand` choke point). The marker lives on `FieldValue.outer` / `EnumCategoryAccess.outer` / `CurrentRepetition.outer` / `FieldRef.outer` / `FieldListRef.outer`. **(b) The real lever — a converter gap, not `$`:** field-list quantifiers with a `Having` filter (`AtLeastOneFieldFilled(Group*/Field Having …)`) were converted by field *path only*, **silently dropping the whole filter**; routing a single filtered entity through `flattenScope` (which converts the filter) converted the entire product-family overlap template (~60 rules). The N8 guarantee is the **post-conversion count-check** `verifyOuterPreserved`: `countOuterRefs(source)` vs the `[$`/`($` markers in the rendered conversion — fewer rendered ⇒ a kind dropped a `$` ⇒ throw `UnsupportedConstructException` ⇒ `Opaque` (verbatim). This is what *caught* the dropped-filter bug (source `$`, rendered 0 → Opaque, not corrupt) before the routing fix, and it makes partial threading **safe by construction** (`adapter.OuterCorrelationBackstopTest` drives it directly; `OuterCorrelationQuantifierReadTest` round-trips the full overlap shape). Every `$` rule in Corpus-1 now converts (**0 `$` opaques**); the last shape — a `$` on a wildcard value-list operand — was cleared by `FieldListRef.outer`. kernel-mm stays 553/553. Detail: [`MODELKIT-PROPOSAL.md`](MODELKIT-PROPOSAL.md) §H.
- **Round-trip oracle.** `ReadRoundTripTest` proves render → kernel-parse → convert → render is the identity for the covered constructs (`render(authored) == render(read(...))`), the differential check that keeps the converter honest against the real engine.
- **Boundary conversion holds.** `read` returns rulekit types (`ReadResult`/`Condition`/preserved text); the kernel `ICondition`/`IRule` never escape (the `parseCondition` hook is package-private). The converter is the only place that touches the kernel transport AST.
- **Aggregate as a comparison's *compared-against* operand — resolved 2026-06-05** (was an F10 gap, surfaced by the dev-path eval). `[Quantity] < Sum(Items*/Count Having …)` (field-vs-aggregate) and `Sum(…) > [Quantity]` (aggregate-vs-field) now read to **`Converted`** and round-trip; previously the converter threw *"number comparison against a non-field, non-constant operand"* → `Opaque`. The lift had two parts: (1) a typed **expression-vs-expression** comparison in the DSL — `NumberExpr.lt(NumberExpr)`/… plus `NumberRef` convenience, so `[field] < Sum(…)` is also *authorable*, not only readable; (2) `ConditionConverter.numericExpr` + `exprVsExpr` accept an aggregate / date-diff / current-repetition / number-field on **either** side of a comparison. Locked by `ReadRoundTripTest.roundTripsAggregatesAndHaving` (field-vs-aggregate + aggregate-vs-field cases).

## Computation read — the calculated-field read path + the N8 dep expansion (2026-06-08)

The `ReadResult` peer for **computations** (calculated fields): `KernelAdapter.readComputation` / `readAllComputations` → a sealed `ReadComputation` (`Converted(Computation)` / `Opaque(reason)`), tolerant like rule read. The read chain:

- **Enumerate:** `ElementContainer.getAllCalculations()` → `IBaseCalculationService.ICalculationRule` (the `getAllRules()` peer).
- **Extract (structured):** `new ServiceFactory().getCalculationService(mvk)` → `ICalculationService.extractCalculationInfo(cr, SILENT)` → `ICalculationInfo`, exposing the **parsed** subtrees: `getCalculatedField()`, `getCommonPrecondition(): Optional<ICondition>`, and `getPartialCalculations(): List<Pair<ICondition, IOperation>>` — the (precondition, operation) alternatives. `mvk` *is* the config (`IMVK_Service extends IServiceConfiguration`), so no separate config is built.
- **Unwrap the operation:** each alternative's operation is a `CalcOperationWithCompOp` (the kernel wraps `computedField <op> valueExpr`); take the value via the api-ish `IWithComparisonOperation.getOriginalOperation()` (which also strips any auto-added rounding) — no concrete-impl reference.
- **Convert:** `ConditionConverter.convertOperation` reuses the comparison-operand converters (`numericExpr` / `stringOperand` / `convertDateOperand` / `constantOperand` + a kind-agnostic `FieldValue`) → a rulekit `Calculation`; `convertComputation` assembles the `Computation`, **recovering messages** from `ICalculationRule.getRule().getErrorMessages()` (so the result is complete + re-addable) and rejecting non-`EXACT` rounding as `Opaque` (rulekit models exact computations only).
- **Write-back:** `ModelWriter.replaceComputation` / `removeComputation` + `BoundModel` twins (the `replaceCondition` / `removeRule` peers). Full cycle proven: read → re-express → write-back → re-read identity (`ComputationReadTest`).
- **Modify-loop + CLI write verbs (2026-06-08):** `KernelAdapter.diffComputation(name, modified) → RenderedDiff` is the `diff` peer — a before/after rendering of the *whole* computation (computed field + common precondition + each `(precondition, operation)` alternative), so the change is reviewable before write-back (`ComputationDiffTest`). The CLI authors/modifies computations too: `add` persists one from a **computation-spec** (a `computedField` key picks the computation branch; `cli.ComputationSpec` → `DraftComputation`, validated by `RuleValidator.check(…, DraftComputation, resolver)`, persisted by the **slot-based** `ModelWriter.addComputation(json, DraftComputation, messages)` — the `addRule`-from-slots peer, sharing `computationNode`). The re-express loop is the single **`modify`** verb: it writes the modified model back (in place by default, `-o` redirects) and **`--dry-run`** previews read-only (`modify --computation <name> --spec <file>` | `modify --rule <name> --condition <DSL>`). A read-only `diff` verb existed briefly on 2026-06-08, retired the same day as redundant with `modify --dry-run`. Both work over multi-file models (the `-w/--workspace` resolver threads through). `cli.ComputationCliTest`, `cli.ModifyVerbTest`.

**N8 dep expansion (the deepest internal touch, deliberate — D15/N8):** reaching the calc service added **`kernel-core-facade`** (`ServiceFactory`) and **`kernel-core-calc`** (`IWithComparisonOperation`) to the adapter's deps. Still under the guardrails: **read-only** (no `…Impl` constructed/mutated — only `extractCalculationInfo` + getters), **boundary-converted** (no kernel type escapes a public signature — `ReadComputation` / `Computation` are rulekit/JDK). **Coverage: kernel-mm 6/6 (100%), Corpus-1 626/626 (100%)** — every computation in both corpora reads. Own-domain shape locks: `adapter.ComputationShapesTest` (numeric aggregate / string-const / bool-const / time-from-date-time / enum-`FirstFilledValue`) + `adapter.ComputationReadTest` (numeric field / arithmetic / tiered + full-cycle modify).

### `getAllRules()` ⊇ computations — the partition (2026-06-08)

**Kernel fact (verified, `30.8.1`):** a computation is *stored as a rule* — its `ICalculationRule.getRule()` carries the kernel-generated **self-validation** condition of the calculated field, and that rule **also appears in `ElementContainer.getAllRules()`**. So `getAllRules()` = validation rules ∪ computation rules; `getAllCalculations()` is the computation subset (kernel-mm: 553 = 547 validation + 6 computations, all 6 in both). Worth knowing: `mvk.getDirectlyReferencedEntities(cr.getRule())` over a computation rule returns the *whole* reference set — calculated field **plus every operand** (a field read only in the operation is included), not just the precondition's fields.

**Rulekit's treatment — partition so the two element kinds never conflate:** `computationFullNames()` is the discriminator, and `ruleFullNames()` / `readAll()` / `whereUsed()` are **validation rules only** (they subtract the computation names). Rationale: reading a computation's generated self-validation condition *as if it were a hand-authored rule* is semantically wrong and double-counts it against `readAllComputations()`; and a `--rule` arg that silently accepted a computation would `explain`/`read` the wrong thing. Total typed coverage is unchanged (547 validation + 6 computations = 553) — just correctly attributed. Floor split in `KernelMmReadCoverageTest`: validation-rule floor 547, computation floor `== total` (6).

**The read surface this unlocks (whole loop now symmetric for both kinds):**
- **whereUsed (F9a) over computations** — `whereUsedInComputations(entity)` + `referencedFieldsOfComputation(name)` (the `whereUsed`/`referencedFields` peers, kernel-native so they work even on an `Opaque` computation). The CLI `where-used` emits `rules` and `computations` as separate arrays (`adapter.WhereUsedInComputationsTest`, `cli.WhereUsedVerbTest`).
- **Unified whole-model read** — `readModel(): ModelRead{rules, computations}`, two disjoint maps + `convertedRules()`/`convertedComputations()`/`fullyTyped()`; the single entry point to round-trip a foreign model completely. CLI: `read --all` (`adapter.UnifiedModelReadTest`, `cli.ReadVerbTest`).
- **explain a computation** — `ModelContext.explainComputation(Computation) → ComputationExplanation` (computed field + kind, common precondition + per-alternative precondition/operation projected with the catalog glossary + referenced fields, messages, gloss). CLI: `explain --computation` (`context.ComputationExplanationTest`, `cli.ExplainVerbTest`). A `--rule` that names a computation now redirects (`ModelPaths.ruleProblem` overload).

## Runtime behavioral-law oracle (F-LAW, 2026-06-06)

Two tiers of "law" lock the kernel's behavior — keep them distinct:

| tier | question | mechanism | location |
|---|---|---|---|
| **accept / reject** (structural) | does the kernel *accept* this condition? | `RuleValidator` + `checkConsistency` | `src/test/.../validate/laws/` ↔ `KERNEL-FINDINGS.md` |
| **fires / does-not-fire** (behavioral, **runtime**) | does a valid rule *evaluate* as intended on data? | `IDocumentRtService.validateFull` over a built document instance | `adapter/src/test/.../adapter/laws/` (`RuntimeLaws` harness) |

The runtime tier evaluates the **real engine** against a constructed document and reads back which rules fired (`IMessage.getErrorCode()`/`getRulePath()`), so a documented behavior changing under a kernel bump fails loudly. Wiring: a trivial `IDocumentModelResolver` (`id → model`) → `DocumentRtServiceFactory.createDocumentRtService(dynamicConfig)` (an `IDocumentDynamicServiceConfig` with a `HashMap`-backed `IModelCodeCache`) → build an `IDocument` via `IDocumentFactory` → `validateFull(doc, Locale)`.

**Document construction — the V1 path (lesson learned, the one shared with the TypeScript runtime; DocumentV2 is new and a separate research item):** building the instance is the subtle part. The kernel converts a V1 `IDocument` to update actions via `DocumentV1V2ConverterImpl.docV1ToUpdateActions` → `DocumentPointer.of(pathParts, repetitions)`, and that contract is:
- **one 1-based repetition index per path part** — group *and* field each get one: `/Order` → `{1}`, `/Order/Quantity` → `{1,1}`. A length mismatch makes the pointer build fail and surfaces as the opaque *"cannot convert entity instance … to update action"* (the error that blocked the first spike — root-caused from the kernel sources).
- **values are read back as Strings** during the conversion (`metaField.convertWithOnlyBasicTypeCheck(sValue)`), so pass field values as text, not `BigDecimal`/`Long`.
- **empty vs absent vs filled-row matters** — see the empty-value law and KERNEL-FINDINGS §2.

For **multi-row** iteration (§9) the harness exposes a `Doc` builder (explicit group/field placements, one repetition index per path part) and a `messages(model, Doc)` that returns each message's **row pointer** — so a law can assert *which* row a per-row rule fired on. Laws locked: `PolarityLawsTest`, `EmptyValueLawsTest` (§2), `FormalErrorLawsTest` (§3), `BooleanThreeStateLawsTest` + `FieldListQuantifierLawsTest` (§1), `RepetitionLawsTest` (§9 per-row iteration + Sum/Max aggregation). Remaining HIGH-trap laws (empty date, path walk-up, the required property) are the F-LAW backlog ([`MODELKIT-PROPOSAL.md`](MODELKIT-PROPOSAL.md) §H).

**Promoted to a public seam (2026-06-09).** The same `validateFull`/`compute` machinery is now a supported **public adapter capability**, not just the test oracle: `KernelAdapter.evaluate(Map fields, Locale)` → `EvalResult` (which rules fire on a document instance) and `KernelAdapter.compute(...)` → `ComputeResult` (what each field computes). The CLI surfaces them as **`eval-doc`** / **`compute-doc`** (CLI-SPEC §4). This required promoting the runtime tier in `adapter/build.gradle` from `testImplementation`/`testRuntimeOnly` to `implementation`/`runtimeOnly` (`kernel-md-runtime-api`, `kernel-md-document-api`, `kernel-md-runtime-service`) — the **N8 boundary still holds**: `evaluate`/`compute` take a JDK `Map` (a model-aware nested-tree walk derives the kernel rep-indices) and return rulekit records (`EvalResult`/`ComputedField`); the kernel runtime types never escape a public signature. The seam's nested-walk is pinned against `RuntimeLaws`' known-good row pointers in `EvalDocSeamLawsTest` (the spike). Findings it locked: validate ≠ compute (KERNEL-FINDINGS), empty number operand → `0` in a computation, formal checks carry `rulePath = formalePruefung`. *(`RuntimeLaws` could later delegate to this seam; not required.)*
