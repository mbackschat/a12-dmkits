# Kernel integration notes (findings for future work)

Working notes gathered while scaffolding Phase 1 against the A12 kernel **`30.8.1`** public surface (sibling repo `a12-kernel`, resolved from `mavenLocal`). These are verified against the kernel source unless marked otherwise. They complement the design in [`PROJECT-DESIGN.md`](./PROJECT-DESIGN.md); when something here contradicts the proposal, this file reflects what the code actually does.

## The kernel SOURCE is the primary oracle — read it, don't decompile jars (2026-06-07)

The **full kernel source** is checked out at the sibling repo **`../a12-kernel/kernel-tool/`** (consult-only — never edit). For any question about DSL syntax, rendering, or validation semantics, **read the source first** — it's authoritative and far cheaper than decompiling the `mavenLocal` jars or guessing from the BA doc. The high-value oracles, all under `kernel-core-parser/src/main/`:

| Question | Source | What it gives |
|---|---|---|
| **Exact DSL syntax** of any construct | `antlr4/.../grammar/gen/GrammarOnly_ConditionParser.g4` + `Base_ConditionLexer.g4` | the authoritative grammar productions + every keyword terminal (e.g. `fieldAndValueListCondition: name '(' entitySpec toOp feldUndStringListenSpezifier ')'`) |
| **Canonical rendering** (AST → text) | `java/.../parsebaum/util/formatter/FormatterVisitor.java` + `FormatterUtil.java` | how the kernel formats each node — the truth our `DslRenderer` should match (verified: tolerance via `getComparisonOperator`, `ValueAsDate` → `, FirstDay`, `RangeAsNumber` start+1, `NumberOfValueInFields` ` In ` separator) |
| **Validation semantics** (why an MVK_* fires) | `java/.../check/bedingung/Check*Impl.java` (+ `check/operation`, `check/entity`) | the per-construct checkers, with **javadoc** stating the rules (e.g. `CheckFieldAndValueListConditionImpl`: `ValueNotConsistent`'s first param must be a table-backed enum, the rest match its dependent columns) |
| **Parse-tree construction** | `java/.../parsebaum/creation/creators/.../*Creator.java` | how text becomes the `IXxx` parse-tree nodes the adapter consumes |
| **Localized keywords** (EN/DE) | `java/.../grammar/languages/LexerTerminals_en.java` / `_de.java` | the keyword ↔ terminal mapping (source form of the `LexerTerminals` ResourceBundle the `KeywordParityTest` checks); grep these instead of the compiled `.class` |
| **Field-type / model structure** | `../a12-kernel`'s `kernel-md-model*` source, or its jars' `-sources` | `IDateType.DatePrecision`, `IDocumentModelInfo.getBaseYear()`, serializer mixins (the DM-JSON keys) |
| **The general LOWERING of a rule shape** (read order, precedence, what the emitted call actually is) | `kernel-tool/kernel-core-codegen-*/src/main/resources/internal/templates/validation/{groovy,java,java_script_vk}/**/*.st` — **never the `build/resources/` copies** | the kernel's own lowering rule, universally quantified over every rule of that shape — but usually only an **index** into the bean below (see the subsection) |
| **The EMISSION SHAPE** a template interpolates | the codegen **backing bean** — `kernel-tool/kernel-core-codegen-*/…/generator/backingbeans/**` (**233** files / 232 top-level declarations, all six codegen modules); follow the interpolated attribute to its getter | the actual emitted expression (`CompositeOperation.java`'s `getFeldOperationCodeJava()` builds the `.op(arg)` chain that `CompositeOperation.st` merely interpolates) |

This source tree resolved `DatePrecision`, `baseYear`, the `ValueAsDate`/`Now`/`BaseYear` node shapes, and `ValueNotConsistent`'s real semantics far faster than jar archaeology would. **Probing the live kernel** (a throwaway validate-and-dump test, as in the family work) stays the way to confirm *behavior* (what validates, what an operation parses to); the source is the way to learn *syntax, rendering, and the rules*.

### The codegen templates are the kernel's own lowering rules — the third source instrument (2026-07-25)

A **template is universally quantified over every rule of a shape**; a generated program is one instance of it. That is what a runtime-class read cannot give you, and why the layer is a standing instrument rather than an opportunistic one. But it is an **index, not the text**: at the operand layer the template names the bean property that emits the code and nothing more (below), so "read the template" is only ever half the route. The routing rule itself (which artifact answers which kind of question, the pass-through warning, and the "a composition claim is a hypothesis" discipline) is [`DOC-DISCIPLINE.md`](DOC-DISCIPLINE.md) §1; the inventory and the measured facts are here.

**Inventory** (checkout `cb66e51` = "Release 2025.06-ext5 — 30.8.1", our pinned kernel). **426 source templates**, spread over six codegen modules (`kernel-core-codegen` 115, `-codegen-condition` 160, `-codegen-entities` 69, `-codegen-rules` 43, `-codegen-base` 33, `-codegen-meta-base` 6), in three parallel dialects plus a shared base:

| tree | count | what it is |
|---|---|---|
| `validation/groovy` | 136 | the **dynamic-Groovy** strategy — the ratified normative oracle (IF136) |
| `validation/java` | 132 | the **static-Java** strategy — co-evidence; a legal split is recorded, never adopted |
| `validation/java_script_vk` | 124 | the **JS/TS** strategy — live and shipped (below), not yet used as evidence by us |
| `common/{groovy,java,java_script_vk}` | 11 each | the shared per-dialect base (`StringParameter.st` lives here) |

**`validation/java_script_vk` is a LIVE shipped codegen target, not vestigial.** Four independent confirmations: **(1)** it is one of only **three** values of the md-model *public* config enum `IValidationCodeGeneratorConfig.ProgrammingLanguage` — `{JAVA, JAVASCRIPT, GROOVY}` — and `MdCoreConversionUtil` maps `JAVASCRIPT ↔ ProgrammingLanguage.JAVA_SCRIPT_VK` in **both** directions; **(2)** the shipped `VkValidationCodeGeneratorCli` advertises exactly `"JAVA, JAVASCRIPT or GROOVY (required)"`, with two JS-only flags (`-wjs`/`-wjse` → the published `JsCodeGenConfig.WRAPPED_IN_FUNCTION{,_EXTENDED}`), and `ExternalDocumentModelService` allows plain-source generation only for `JAVASCRIPT` or `GROOVY`; **(3)** a maintained **TypeScript runtime implements the API these templates emit calls to** — `validation/java_script_vk/conditionsDir/ApplicationCondition.st` emits `controller.applikationsBedingung(name, RtInternalIdentifier.createFromIterationState(…))`, and `kernel-rt/kernel-core-runtime-ts/src/main/js/internal/core/MainValidatorController.ts` declares `applikationsBedingung(applName: string, id: RtInternalIdentifier)` (alongside `kernel-core-runtime-api-ts`); **(4)** the template inventory tracks the enum's own capability declaration — `JAVA_SCRIPT_VK` is the sole `ProgrammingLanguage` with `withUsb == false`, and it is the sole dialect missing `operationsDir/NumberOfUsbOperation.st`. The genuinely **vestigial** targets are the other three core enum values: `JAVA_SCRIPT_REDUCED` (whose template dir would be `java_script` per `STParameterClassBase` — **absent** from the checkout), `CPLUS`, and `VBA` — none has a template tree, and none is reachable from the md public API. **"Live" does NOT make it the best-supported target — Java is** (the inference to resist; it was drawn and retracted once): Java has more templates (132 vs 124), static-Java is already an active evidence strategy while the JS dialect is used as evidence by neither project, the kernel's own runtime is Java, and every host fact our semantics account pins is a JVM fact (precision-50 `HALF_UP` `MathContext`, `java.util.TimeZone` + a pinned tzdb, UTF-16 code units, long saturation, signed-32-bit narrowing, JLS receiver-before-argument order). That a separate TS runtime had to be written *is itself the evidence*: reaching JavaScript required choices, and our two recorded never-adopted divergences are exactly those choices — so the JS strategy is a **warning map, not an oracle**. Both divergences sit in the paired **TS runtime**, never in the templates (which contain no `RegExp` at all): `BedingungsOperatorHelper.getPattern` builds a raw `RegExp` per pattern (behind IG90/IF164), and `kernel-core-runtime-ts` depends on `luxon` (the timezone edges in IG83). Neither is characterized beyond that, and no TS evidence has ever been *executed* here — a JS twin of `JavaKernelEngine` is toolchain-blocked (the TS runtime ships source-only and needs private mgm-scoped packages the public build excludes; [INTERPRETER-PERFORMANCE.md](INTERPRETER-PERFORMANCE.md) §"Why code-generator JS/TS is not yet measured"). So a claim about this strategy must name whether it sits in the template or the runtime.

**Most operand templates are PASS-THROUGHS — the emission shape lives one layer down, in the backing bean (2026-07-25).** **25 of the 26** java `operationsDir` templates are ≤3 nonblank lines and do nothing but interpolate one `*Code` attribute. `operationsDir/CompositeOperation.st` is exactly `<t.feldOperationCodeJava>`; the arithmetic emission shape (operand-0 `VkString` special-casing, the `.op(arg)` chaining via `RuntimeMethodNameFactory`) is `CompositeOperation.java` in `backingbeans/fieldoperations/`. Consequence for the routing rule: at the operand layer a template tells you *which bean property emits this*, not *what is emitted* — so a short template is a pass-through, never evidence of "no lowering", and every basis citation must **name the layer** it read (`CompositeOperation` is a template *and* a bean).

**So operand lowering is SINGLE-SOURCED BY CONSTRUCTION across all three dialects, not three implementations that happen to agree.** All three dialect copies of `operationsDir/CompositeOperation.st` interpolate the *same* attribute, `<t.feldOperationCodeJava>` — one property referenced three times, whose name records the *emission style* (method-call chaining), not a dialect. Since a byte-identical template interpolates identical attribute names, it necessarily calls the same getter on the same bean class: **one lowering, referenced three times.** The internal-branch escape hatch is closed by measurement — `getFeldOperationCodeJava()`'s body contains no `ProgrammingLanguage`/`CodeGenContext` reference, and across the operand/condition bean layer only **1 of 38** classes references either: `CompositeOperation`, in the *sibling* `getFeldOpCode()`, the CPLUS/VBA infix variant no live-dialect template interpolates (`fieldoperations` 1/23, `conditions` 0/15). Two consequences. **(1)** A groovy↔java diff at the operand layer is pointed at something that *structurally cannot vary*, so the residual space for an operand-lowering split lies entirely below the templates — leaving host-language semantics, a different runtime path being reached, and the caching/service layer as the only loci where one could live. **(2)** Because the JS dialect emits the *same* operand code, the TS runtime's raw-`RegExp`/luxon divergences **cannot** be lowering-level; they are runtime-level by construction — independent confirmation of the template-vs-runtime locus rule above.

**The groovy↔java template diff IS a viable static strategy-split detector** (measured 2026-07-25; finding only, no tooling built — evaluated because the [IF123](INTERPRETER-FINDINGS.md) class of defect is *structurally ungenerable* by a corpus or a number-biased fuzzer, so a split there cannot be found by spending a differential run). Of the 125 templates present in both dialects, **82 are byte-identical**, 19 differ by ≤4 lines, 24 differ substantially. In the semantics-bearing dirs the diff is quiet: all **24** shared `operationsDir` templates are byte-identical — which the single-sourcing above *explains* rather than merely observes — and only 5 condition templates differ at all, every one a pure host-language idiom (Groovy `[…] as T[]` vs Java varargs/`new T[]{}`, Groovy closure vs Java lambda, ST line-continuation style) carrying **no** semantic content. **So the diff's value is not in the equalities** (those are structural, not evidence) but in the two things it can still surface: a *non-idiom* textual difference in a condition template, and — the stronger signal — **asymmetry**, a construct one strategy lowers through a dedicated template and another does not.

**Exactly two asymmetries exist, and they are one construct.** `operationsDir/ConsistentValueOp.st` and `conditionsDir/EntityListAndValueConditionMixedList.st` are both **java-only**, and both are `ValueNotConsistent`: every parsed one becomes the `MixedList` bean, `ConsistentValueOp` is its dynamic-enum value op (emitting `controller.getUiXmlValuesForTableEnum(…)` via `CodeGenDynamicEnumerationBuilder`), and only `validation/java` carries either template. The instrument alone could not prove that — a missing template is a *candidate*, since the other dialect may route the construct through a differently-named template — so it was routed onward per the routing rule, and `NoMetaModelChecks.checkEnumTables()` supplied the independent confirmation by *rejecting* table enums for GROOVY/JAVA_SCRIPT_VK with `MVK_TABLE_ENUMS_NOT_ALLOWED_FOR_PROGRAMMING_LANGUAGE`: a declared capability restriction, not an accidental gap (KERNEL-FINDINGS §8 supplement). That is the detector's one real hit, and it worked as designed — candidate by reading, confirmed by a second mechanism.

**None of the above generalizes to the whole emitted program — Groovy has SIZE-TRIGGERED lowering modes with no Java counterpart.** The single-sourcing holds at the *operand* layer; the rule/computation frames are a different story, so the 24 substantial diffs must not be waved off as scaffolding. Most of them *are* packaging (the `teilvalidierungDir` diffs are exactly: no `package`/`import` in Groovy plus a `groovyPackageClassnamePrefix` on class names). But three are not, and they are marked `// Groovy only` in the backing beans: **(1) condition-line splitting** — `CodeGenRuleDefinition.getUseClosureForConditionLineCode()` returns true once a rule reaches `NUM_CONDITIONLINES_PER_METHOD_GROOVY = 50` condition lines, and Groovy then emits bare `ValidierungsErgebnis tb<i0>;` declarations plus `conditionLineSplitFunctionCode`/`…Calls` (chunked sub-methods) where Java emits one straight-line `tb<i0> = <cond>;` list; **(2) calculation closures** — `CodeGenCalculatedField.getUseClosureForCalculationCode()` returns true once a computed field reaches `NUM_CALCULATIONS_PER_METHOD_GROOVY = 10` **computation alternatives**, and only inside that arm does the Groovy `CodeGenCalculatedField.st` interpolate `t.calculationSplitFunctionCode` — whose getter flips each alternative's own flag as a **side effect**, which is what makes `CodeGenCalculationAlternative.st` emit `return true;` inside closures. **This mode is size-gated, not unconditional** — a read of the bare `forEach(… setUseClosureForCalculationCode(true))` statement without its enclosing method says otherwise and is wrong (corrected 2026-07-25 by a12-kernel-lean's Batch C triage; the composition trap of §1 in its purest form — a locally correct statement read outside the branch that reaches it). Below 10 alternatives the plain `t.calculationCode` route is emitted and no closure appears anywhere; **(3) object splitting** — `NUM_RULES_PER_CLASS_GROOVY = 10` drives the **groovy-only** `rulesDir/CodeGenRuleCheckObject_class.st`/`_line.st` and `calcDir/CodeGenCalcObject_class.st`/`_line.st`. All three are 64KiB-method/class-limit workarounds (the kernel's own `SplitFunctionsHelper` javadoc says so) and order is preserved by construction — chunks are emitted and called in `conditionCodeOutputInOrder` order — so they are **semantics-preserving by intent**. For modes (1) and (2) that intent is now a **probed fact, not a source reading** (below); for (3) it remains a source reading, but (3) is the one mode the corpora genuinely exercise at scale, so the "0 java-static splits" result does bear on it. Their practical significance is coverage, and it is now **measured, not assumed (2026-07-25)** — the thresholds were checked against the corpora that produced the certificate's "0 java-static splits":

| Groovy-only mode | threshold | engaged by our evidence? |
|---|---|---|
| **object splitting** (rule-check/calc objects per class) | `NUM_RULES_PER_CLASS_GROOVY = 10` | **YES** — kernel-mm 11 of 13 canonical models exceed 10 rules (max **89**); workspaces 2 of 107 (**29**, **16**) |
| **calculation closures** | `NUM_CALCULATIONS_PER_METHOD_GROOVY = 10` alternatives on one computed field | **not by the corpora** — over **316** computations the alternative count peaks at **7** (workspaces) and **1** (kernel-mm); the sweep's 646 computations evidence nothing here. **Locked directly instead** (`adapter.laws.CalculationClosureSplitDiffTest`) |
| **condition-line splitting** | `NUM_CONDITIONLINES_PER_METHOD_GROOVY = 50` | **not by the corpora** — over **2 460** rules the atomic-term count peaks at **4** (workspaces) and **21** (kernel-mm); nothing reaches 50. **Now covered by a purpose-built lock instead** (`adapter.laws.ConditionLineSplitDiffTest`, below) |

The committed corpus cannot reach any threshold: its models carry **1 rule each** by design. So the corpus zero is real evidence for **exactly one** of the three modes — object splitting — and was silent about the other two, whose paths no corpus model ever emitted; read the java-static zero with that scope attached. (An earlier form of this table credited the corpora with mode (2) on the strength of "646 computations compared". That was the same defect as the claim it rested on: a size-selected route restated as unconditional. The alternative-count measurement is what settles it.)

**Both corpus-unreachable modes are now locked directly, and both are semantics-preserving — no divergence found (2026-07-25).** Rather than widen a corpus that structurally cannot reach these shapes, each lock authors its shape on purpose, and each **proves its mode engaged before comparing anything** by reading the emitted Groovy for the mode's own closure marker — no runtime result can distinguish split from unsplit lowering, so without that assertion a green test would evidence nothing. Both also assert their negative controls really generated source, so neither can pass vacuously.

**Mode (2) — `adapter.laws.CalculationClosureSplitDiffTest`.** A computed field with 12 alternatives (2 chunks of 10), each firing on a distinct selector value so the winner is chosen by the document. Pins: the gate is at 10 (9 alternatives stays on the plain route); static-Java never splits at any count; and split-Groovy, unsplit static-Java, and the interpreter agree on the computed outcome with the winner in the **first** chunk, a **later** chunk, and the **last** position, plus the no-winner CLEARED case. The load-bearing semantics is that the chunk calls are ` || `-joined and each chunk ends `return false;`, so they short-circuit in authored order — which is how the unsplit route's "first alternative whose precondition holds wins" survives chunking.

**Mode (1) — `adapter.laws.ConditionLineSplitDiffTest`.** A rule whose condition is an `And`-chain of ≥50 atomic comparisons over distinct NUMBER fields, requiring the `Closure conditionLineCode_<n>` closures. Pins: the threshold is real and at 50 (49 terms stays straight-line and still generates); **static-Java never splits at any width**; and the three engines agree on fired/not-fired for an all-satisfied 60-term chain and for a single veto placed in the **first**, **middle** (110 terms = 50+50+10, veto at 75 — the only width where a chunk-call loop that emitted just the ends would be caught), **second**, and **last** positions.

Both locks close their blind spot by *exercising* it rather than documenting it — the IF123 lesson applied forward instead of retrospectively. Mode (2) is the more valuable of the two: 10 alternatives on one computed field is a realistic authored shape (the corpora already reach 7), whereas a 50-term condition chain is not. Measured over a superset of the swept models, so the "never engaged" conclusion holds a fortiori. This is the same shape as the [IF123](INTERPRETER-FINDINGS.md) "structurally ungenerable" lesson, one layer up: the region a split could hide in is the one the corpus cannot construct. *(Term count is a proxy for codegen's `conditionCodeOutputInOrder.size()`, counted as `And`/`Or` occurrences + 1 on each rule's `errorCondition`; the margin to 50 is wide enough that proxy error does not change the verdict.)*

### Renderer ↔ kernel canonical-parity guardian (`adapter.CatalogRenderCanonicalParityTest`, 2026-06-07)

A guardian that pins our `DslRenderer` to the kernel's `FormatterVisitor` (the canonical formatter, reached via `KernelAdapter.canonicalConditionText`). For **every** SUPPORTED catalog `validExample` (106): read it → re-render our AST (relative to the rule group, the kernel's own path form) → assert the kernel canonicalizes *our render* identically to the example. Both sides pass through the kernel formatter, so path-form/whitespace differences cancel and only a real token/structure divergence survives. This is **strictly stronger than the render→parse→convert→render round-trip** (which is our-renderer-on-both-sides, so it can't see a loss that's consistent on read *and* write). **German is checked too**: the same AST is rendered in DE, parsed back through a de_DE twin of the fixture, and must re-read to the same condition (its EN render equals our EN render) — catching a bad/unparseable German keyword or structure the EN pass can't. Standing at **106 checked, 0 EN-mismatched, 0 DE-mismatched, 0 opaque**.

Building it immediately caught **four** read defects no other test saw — two **silent losses** (the cardinal F10/N8 sin) and two coverage gaps:
- **`FieldValuesNotUnique(Items*/Sku)` dropped the `*`** — it converted the keys via plain `fieldRefs` (which strips the wildcard) instead of the wildcard-aware `toFieldOperand`, so write-back drew `MVK_NO_WILDCARD`. (silent loss → fixed)
- **A semantic index `[field For "x"]` was silently dropped** — the `FieldValue` path ignored `IEntityId.getSemanticIndex()` (a `List<Object>` of a single quoted string OR entity-ref key), so it rendered a bare `[field]`. Now read on a NUMBER field for **both** key forms: the constant key (`String` → `SemanticIndexValue`) and the field key (`IEntityId` → `SemanticIndexFieldValue`, DG8; `adapter.SemanticIndexReadTest`). A semantic index on a **non-number** field stays Opaque with a kind-named reason (never a silent drop) — the AST nodes carry any kind, but rulekit's `forIndex` handles are number-only, so non-number would need per-kind operand plumbing. (silent loss → fixed; field-keyed read added 2026-07-05)
- **`NumberOfFilledGroups(g1, g2)` over multiple distinct groups** wasn't read (only the single `Group*` form) → Opaque. (coverage gap → fixed)
- **`DateFromDateTime(...)`/`TimeFromDateTime(...)` on the *left* of a comparison** was routed to the numeric-extraction path (which rejects the date/time-valued part) → Opaque. Now routed to date/time comparison. (coverage gap → fixed)

Lesson: an our-renderer-on-both-sides round-trip proves *stability*, not *fidelity* — comparing against the kernel's canonical form is what catches a consistent read+write loss. (Task #9.)

### `model read` failure-reason taxonomy (`adapter.KernelAdapter.opaqueFailureReason`, 2026-07-05)

The tolerant whole-DM read (F10) degrades a rule/computation it can't convert to a verbatim `Opaque` with a `reason`, and that `reason` now names *which kind* of failure. The earlier blanket `"unresolved reference (<Class>): <message>"` collapsed three very different outcomes into one — and for a null-message crash produced the useless `"unresolved reference (NullPointerException): null"`. The three kinds:

- **`F10 converter does not yet handle …`** — an intentional coverage gap (`UnsupportedConstructException`): the construct is legal, rulekit just doesn't model it yet.
- **`unresolved reference (…): no element at path: /X`** — a benign asymmetry: a header/cross-form entity the kernel resolves but rulekit's content-only `ModelIndex` legitimately lacks. Kept verbatim (its `"no element at path:"` message is the corpus histograms' bucket key).
- **`converter error (<Class>): <message> at <Class>.<method>(<file>:<line>)`** — a converter **bug** on a rule the kernel accepts: names the exception class + the first stack frame in our own code, so the crash site is actionable.

Why it matters: a large real-world model corpus read reported **65** failures identically as `"unresolved reference (NullPointerException): null"` — indistinguishable and locus-less, hiding 65 real converter bugs behind a reassuring "reference problem" label. Locked by `adapter.OpaqueFailureReasonTest`; the benign unresolved path by `adapter.UnresolvedReferenceReadTest`.

## Validating a rule via `checkConsistency` (F4 — verified by experiment)

**Enum comparison by stored value works for text-bearing enums.** `[Tier] == "PRO"` validates against the kernel even though `Tier` is a text-bearing enum (BASIC/PRO/ENTERPRISE with labels). This clarifies the §5b "text-bearing enum ↔ string: no" rule: it forbids comparing an enum to an actual **string field/expression**, not to its own **enum-value literal** (the quoted stored value). So rulekit's `EnumRef.is("PRO")` → `[Tier] == "PRO"` is correct; the value is checked against the model's enum domain at build time.

Confirmed end-to-end by the `RuleValidator` increment (inject a `Rule` into the model DM-JSON → deserialize → `expand` → `checkConsistency`):

- **A rule must carry error text.** A rule with no `errorMessage` is rejected with `MVK_ERROR_MESSAGE_MISSING` (and a companion `RULE_HAS_NO_ERRORTEXT`). The validator therefore **auto-injects a placeholder `errorMessage` per model locale** so that requirement doesn't mask the condition diagnostics we actually want to check. (Locales come from `header.locales[].code` in the DM-JSON.)
- **Both absolute and relative paths validate.** Absolute (`FieldFilled(/Subscription/Addons/MonthlyFee)`) and relative-to-the-rule-group (`FieldFilled(MonthlyFee)`, `../Tier`) are both kernel-accepted (KERNEL-FINDINGS §10 (paths)). The path form is a readability/diff choice (§18.9 / fork #9), not a correctness one. **Rulekit's treatment:** `Rule.render()`/`draft()` and `Computation.draft()` now render **relative to the group** (the authoring norm — `DslRenderer` with a base group); standalone `DslRenderer.render` stays absolute (no group context — catalog/laws output unchanged). **Keyword-segment quoting (the other fork-9 half) is implemented** — the renderer single-quotes any path segment colliding with a catalog operator keyword (`*` suffix preserved); KERNEL-FINDINGS §10 (paths), locked by `dsl.PathPolicyTest`.
- **error-field-referenced works across path forms.** The rule's `errorEntityRelPath` was relative (`../MonthlyFee`) while the condition referenced the field by absolute path; the kernel still considered the error field referenced (no `MVK_ERROR_FIELD_NOT_REFERENCED`). They resolve to the same node.
- **Not every code is `MVK_*`.** `checkConsistency` notifications carry mixed code styles — `MVK_INVALID_TYPE_FOR_COMPARISON` (string ordering) and `MVK_ERROR_MESSAGE_MISSING` have the `MVK_` prefix, but `RULE_HAS_NO_ERRORTEXT` does not. So MVK-code extraction from the message is **best-effort**; don't assume every problem yields an `MVK_*` code.
- **Rulekit's treatment — structured `Diagnostic` + catalog-join (F4a, first increment 2026-06-04).** `checkConsistency` problems are no longer raw `Problem`s: each becomes a `Diagnostic` (`severity·source·code·summary·where·fix·explain`, LSP-shaped). The kernel message stays as `summary`, the extracted `MVK_*` as `code`, the rule path as `where.rule`. The **catalog-join** (`OperatorCatalog.operatorsForError`) then attaches the documenting operators' `invalidExample.fix` + operator `meaning` — the curated fix DB is the **catalog**, N7-locked, so kernel diagnostics and authoring examples can't drift. `ValidationResult.toJson()` renders the array for agents (files-as-API). Several operators can report one code (all ordering ops → `MVK_INVALID_TYPE_FOR_COMPARISON`); the join is **sound, not a guess** — one documenter (or several that AGREE on the fix) attaches the single corrective, several that DISAGREE attach the **union** of their distinct fixes, so no construct is mis-stamped. **Corrected 2026-07-31 — the union fixed `fix` but not `explain`.** An operator `meaning` is itself a claim about which construct rejected, and the union path kept emitting a `firstMeaning()`, so an ambiguous join still asserted an owner: a `where.operator = LessThan` rejection was explained as “less than or equal” (the four ordering operators AGREE on the fix and DIFFER in meaning, which is why only `explain` was wrong). The governing rule is now an **ownership invariant** — an operator-specific `fix` *or* `explain` only once exactly ONE owner is established, from structured `where.operator` first and then whole-token identifier intersection over the message; unresolved → a code-level corrective and **no `explain`**. A message-*pattern* extraction was tried first and rejected as unsound: the text is localized per bundle, and the default one renders `MVK_NO_CONST` as “Kein Fehler definiert!”, naming no operator at all. This replaced the unsound `byInvalidError`/`findFirst` (now removed), which stamped *whichever operator was first in `operators.json`* onto every other construct sharing the code — **the deeper root cause behind a recurring class of probe findings (F06-2 / dec-places)**: `NumberOfFilledGroups(field)` got `GroupFilled`'s fix; the dec-places computation case got the comparison fix. The `where.operator` disambiguator the F4a design intended to pin the exact one is **empty at enrich time** (`Diagnostic.fromKernel` builds `Where.rule(rulePath)` only — it lands later, on a read pass), so there was nothing to pin by and `findFirst` was a coin-flip. The later **span-pointing** pass (`lint.SpanResolver`) still pins the exact operator by intersecting the code's catalog candidates with the rule's used operators (`OperatorUsage`) once `where.operator` lands, and `where.span` is attached from the renderer emit-map (`DslRenderer.renderWithSpans`) when a single rendered node carries that operator. **The lint layer (`lint.Linter`, F4a first lint increment) emits the same `Diagnostic` shape with `source=LINT`** and its own `RK_*` codes (`RK_CONTRADICTORY_PRESENCE`, `RK_PRESENCE_NOT_COMPLEMENTARY`, `RK_REDUNDANT_OPERAND`) — these are *not* kernel codes; they catch valid-but-suspicious conditions `checkConsistency` is silent on, and (having the AST node) they *do* populate `where.operator`. A **model-context** lint, `RK_NEG_CONDITION_IN_ITERATION` (`Linter.lint(BoundModel, Rule)`), **pre-warns** the kernel-delegated `MVK_NEG_CONDITION_IN_ITERATION` (KERNEL-FINDINGS §9): it fires when a rule iterates (`BoundModel.iteratesForErrorField` — a repeatable group on the error-field path) and carries a bare negative presence predicate with no positive guard. A second rule-context lint, `RK_INVERTED_REQUIREDNESS`, flags the inverse of the kernel's **error-scenario** semantics: an `errorCondition` is true ⇒ the data is invalid, so a requiredness rule must fire on *absence* — a bare `FieldFilled(E)` on the rule's own error field `E` fires on *presence* and is almost certainly meant to be `FieldNotFilled(E)`. Bare-only (a guarded `FieldFilled(E) And <ctx>` is a legitimate "must be empty here" rule). Serves both personas (the CLI `check`/`add` backstop and the developer's `RuleDiagnostics`). **"Did you mean" (`model.Suggest`)** enriches the fail-fast handle errors: an unknown path (`ModelIndex.require`) or an out-of-domain enum value (`EnumRef`) appends the nearest valid name by Levenshtein distance, gated by a typo-plausible threshold so a wholly wrong name draws no misleading hint. **The gotcha/INFO channel (`lint.Advisor`, `RK_GOTCHA`)** is the same family at `severity=INFO`: for every operator a rule uses (collected by `dsl.OperatorUsage`, which descends into nested `Calculation`s), it surfaces that operator's catalog `gotchas` as proactive notes — the semantic surprises `checkConsistency` never reports because the rule is *valid* (e.g. the `AddYears` leap-day disagreement). Origin stays LINT; severity is the kind axis (WARNING = suspicious, INFO = surprising). Each catalog gotcha carries a `GotchaKind` (`SURPRISE`/`AUTHORING`/`RENDERING`); the channel emits `SURPRISE`+`AUTHORING` and **suppresses `RENDERING`** (rulekit-handled trivia — language-independent symbols, And/Or parenthesization), so the notes stay author-relevant.

- **F11 pre-check split — bias to acceptance, never a self-inflicted false positive.** Pre-checks are now classified by whether the *live kernel* is the authority on them:
    - **Hard at `build()`** (completeness + rulekit's own structure): the five `RK_INCOMPLETE_RULE` slots, locale-declared messages, and `MVK_ERROR_MESSAGE_MISSING` — the last stays hard because `RuleValidator` deliberately **injects placeholder messages** so the kernel never arbitrates message-presence (it can't be a false positive), and `RK_ERROR_FIELD_OUTSIDE_GROUP` because it guards `Rule.errorEntityRelPath()`'s own substring math.
    - **Deferred + advisory** (kernel-semantic mirror): `MVK_ERROR_FIELD_NOT_REFERENCED` — the `covers()` heuristic only *approximates* the kernel's rule. `build()` no longer throws on it; `Rule.deferredChecks()` returns it as a WARNING-severity PRECHECK `Diagnostic`, and `RuleDiagnostics` surfaces it **only when the live kernel didn't already report the same code** (dedup against the kernel verdict). Same kernel → the kernel's ERROR wins, no double-report; a more lenient (newer) kernel → the advisory is the lone signal and never flips `ok`. So a heuristic drifting from a future kernel can never be the *sole* reason an accepted rule is reported corrupt.
- **F11 kernel-version skew — `validate.KernelVersion`.** rulekit reads the running kernel's `Implementation-Version` (`Package.getImplementationVersion()` off any kernel class — spike-confirmed `30.8.1`; see KERNEL-FINDINGS) and compares it to the catalog's `verifiedAgainst` floor (now a header field in `operators.json`). The `->` symbol is not in the keyword bundles (same in EN/DE). Curiosity: `[Tier -> Pricing] == [Tier]` (category vs. plain enum field) is *accepted* by the kernel. A category projection is also a legal **member of a value-list quantifier** (`No(field -> Cat In …)`, rendered bare `field -> Cat`); there each literal rides the **union** of the selected members' stored/category domains, a direct ref and a category ref on the same field are distinct, and the entity-valued form gates same-base-kind + combined-reference uniqueness (SPEC-2026-07-22-05, [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §8).
- **Computation slot rules verified with exact codes** (2026-06-04 experiment; pre-checked in `Computation.build()`, kernel-locked via `ComputationAuthoringTest`). Simple, tiered (all-preconditioned), and `commonPrecondition` forms validate. **Mixing preconditioned and unconditional alternatives is rejected** — `MVK_ERROR_EMPTY_PRECONDITION` (an `.otherwise(...)` API is therefore kernel-illegal: either one unconditional alternative or all preconditioned). Referencing the computed field in a precondition **or** an operation → `MVK_ERROR_REFERENCE_TO_CALCULATED_FIELD` (same code, both slots) *for a plain self-read*; a **projected** one (enum category, semantic index, or semantic-index key) is `MVK_ERROR_SEMANTIC_INDEX_OR_CATEGORY_FOR_ERRORFIELD` and pre-empts it across slots ([kf182](KERNEL-FINDINGS.md#kf182)), which is why `Computation.build()` folds the reading mode over the whole computation instead of checking slot by slot. The ban is on a **direct field** reference; guarding a *repeatable* computed field via `GroupFilled`/`CurrentRepetition` on its **containing group** is legal (the pre-check was refined 2026-06-08 to exact field-match — `ConditionReferences.referencesField`, not the group-prefix `covers()`; see KERNEL-FINDINGS §11). A string operation into a number computed field → `MVK_INVALID_COMPARE_TO_ENUM_OR_STRING`. Computations also require error text (`MVK_ERROR_MESSAGE_MISSING`). Computation DM-JSON shape verified against `a12-kernel-demo`: `computedFieldRelPath`, `computationAlternatives[{precondition?, operation}]`, optional `commonPrecondition`, `errorMessage`.
- **Boolean/confirm comparison rules verified with exact codes** (2026-06-03 experiment, locked by `validate.laws.BooleanConfirmLawsTest` + the N7 `True`/`False` catalog examples). Boolean field: `== True`, `== False`, `!= True` all accepted; vs a string → **`MVK_INVALID_COMPARE_TO_YESNO`** ("boolean compares only to boolean or True/False"). Confirm field: `== True` / `!= True` accepted; **`== False` → `MVK_INVALID_COMPARE_TO_YES`** ("confirm compares only to confirm or True"); boolean ↔ confirm cross-compare also `MVK_INVALID_COMPARE_TO_YES`. Confirms §5b's Boolean≠Confirm split; rulekit's `ConfirmRef` consequently offers `confirmed()`/`notConfirmed()` and **no `isFalse()`** (unrepresentable). DE keywords verified per token: `True→Wahr` (WAHR), `False→Falsch` (FALSCH).
- **Correction: the decimal-scale equality check is asymmetric; literals are not globally exempt** (source-completed + discriminating experiment 2026-07-20, superseding the 2026-06-03 interpretation). The old scale-2-field probes all passed because their scale-0/1/2 literals were either equal-scale or the multiplicative-constant-capable **smaller-scale** side. The missing inverse proves the rule: a scale-0 field `== 0.00` is rejected in either operand order because the smaller-scale field cannot be padded. The parser carries signed scale independently from constant capability: a fractional literal retains authored scale, an integer strips trailing zeros (`1000` → scale `−3`), `+`/`−` use max scale with capability AND, `×` sums scales with capability OR, division is unknown/non-capable, and power is unknown/non-capable except for a scale-0 base with a simple nonnegative constant exponent. Ordering remains exempt. rulekit's typed `NumberExpr` now carries the same summary; generic/loaded expressions with unavailable model scale still defer to the live kernel. Locked by `validate.laws.NumberLawsTest` + `dsl.operators.NumericScaleGateTest`.

## Public model-API surface (verified, `kernel-md-model-api` + `kernel-md-facade`)

- **Entry points come from `com.mgmtp.a12.kernel.md.facade.DocumentModelServiceFactory`**: `createDocumentModelSerializer()` → `IDocumentModelSerializer`, `createDocumentModelService()` → `IDocumentModelService`. Both interfaces live in `...md.model.api.services`. This is all on the `kernel-md-facade` compile classpath — no internal-tier dependency needed (confirms D9/N8 is achievable).
- **Navigation is a manual tree walk; there is no path-based lookup.** `IDocumentModel.getContent().getDocumentModelRoot()` returns a synthetic root `IGroup` whose `getElements()` are the top-level groups. Recurse `IGroup.getElements()` (`List<IElement>`), dispatching `instanceof IGroup` / `instanceof IField`. `IElement` (extends `IIdNamed`, `IDescribed`, `IAnnotated`) is the common supertype.
- **`getId()` is an *opaque identifier*, NOT the path — `getName()` is the short segment, and the absolute path is the join of `getName()` segments** (= what a condition references, the kernel's `getFullName()`). In rulekit's *own* fixtures `id` is authored equal to the path, which long hid the distinction — but **real-world models (the `a12-kernel-mm` metamodels, the A12 Tools apps) carry opaque/hash ids** (e.g. `3b16e188…`). **rulekit's `ModelIndex` keys elements by the name-path** (F-IDX, 2026-06-05): keying by `getId()` resolved ~0% of foreign-model rule references (id-namespace vs name-namespace, disjoint) — the fix took kernel-mm read 0 → 74%. *(Corrects the earlier claim that `getId()` IS the path. Locked: `model.ModelIndexNamePathTest`; `IDocumentModelService.getPath(IElement)` also computes a name-path for a known element.)*
- **`IFieldType` is a bare marker** — no kind accessor. Recover the kind by `instanceof` on the concrete public subtype. **Order matters:** `IDateTimeType` and `ITimeType` both `extends IDateType`, so test them *before* `IDateType`. (Encoded in `ValueKind.of(IFieldType)`.)
- **`IField.getEffectiveType()`** is a default method that resolves an `ITypeDefType` to its underlying type (after model expansion) and returns `Optional<IFieldType>`; classify the effective type, not the raw one.
- **Read-side kind without the typed objects (`ValueKind.fromKernelType(String)`, 2026-06-22).** The surfaces that work on the **raw model tree** (`ModelDocument`, not a `BoundModel`) have no `IFieldType` to classify — only the stored DM-JSON `fieldType.type` discriminator string (`"NumberType"`, `"TypeDefType"`, …). `ValueKind.fromKernelType(String)` is the read-side inverse of that discriminator (the counterpart of `FieldKind.jsonType()` forward); `ModelDocument.fieldKind(path)` / `typeDefinitionKind(id)` use it, following a `TypeDefType` to its underlying discriminator first — the string-tree analogue of resolving `getEffectiveType()` before classifying. This is what lets **every CLI type-reporting surface** (`field`/`typedef read`, the `apply` read op, and the write echoes) speak one clean `ValueKind` vocabulary under `kind`, so the kernel discriminator never leaks to a user surface (CLI-SPEC "A field's value type is one vocabulary"; the rule treatment of `07-vocab`).
- **Key type accessors used so far:** `INumberType.getMaxFractionalDigits()` (int — the decimal scale), `getMinValue()/getMaxValue()` (`Optional<BigDecimal>`), `getTrait()` (`Optional<String>` amount/percent/permille); `IEnumerationType.getValues()`/`getCategories()` (+ nested `IEnumValue`/`IEnumCategory`); `IStringType.getPattern()`; `IDateType.getFormat()`/`getDatePrecision()` (enum `FULL`/`*_OPTIONAL`).
- **Repeatability:** `IGroup.getRepeatability()` returns `int`; **`1` = non-repeatable**, higher = max repetitions (fixture: `Addons` = 20). `IGroup.getIndexField()` → `Optional<IDocumentModelObjectReference<IField>>`. rulekit treats `repeatability != 1` as "repeats" — revisit if a model ever uses `0`/negative for "unbounded" (not yet observed).
- **Config flags worth noting:** `IDocumentModelConfig.isFieldRefByShortNameAllowed()` (gates short-name paths — relevant to the §18.9 path policy), `getConditionLanguage()` (EN/DE keyword bundle), `getDecimalSeparator()`. Model-level **base year** is `IDocumentModelInfo.getBaseYear()` (`Optional<Integer>` — lifts the date year-presence comparability rule, §5b).

## The validate seam (`IDocumentModelService`) — verified signatures

- `void expand(IDocumentModel, IDocumentModelReferenceResolver)` — **mutates in place**, recursive, best-effort if a referenced model is invalid. Required even for self-contained models (no-op there). Javadoc advises running `checkConsistency` on included models before expansion and on the expanded model after.
- `void checkConsistency(IDocumentModel, Consumer<RankedNotification>)` — reports `MVK_*` and other problems via the callback. The preferred lightweight ground-truth step (§11); surfaces rule-condition errors (e.g. `MVK_INVALID_TYPE_FOR_COMPARISON`) as notifications rather than exceptions. **Correction (2026-06-05): it is *not* codegen-free.** Internally `checkConsistency` runs `CodeGenerationRule` → `generateValidationCode`, which **emits Groovy source via ANTLR StringTemplate v4** (then discards it) — so it *does* generate code, it just doesn't *compile* it (no Groovy `parseClass`/execute). Harmless on a JVM, but it's the **AOT/native-image constraint**: the StringTemplate stage needs all `internal/templates/**` resources bundled; see [`KERNEL-FINDINGS.md`](KERNEL-FINDINGS.md) "`checkConsistency` runs runtime code generation". (Runtime Groovy *compilation* only happens on the validation-*execution* path, which rulekit never uses.)
- `byte[] generateValidationCode(IDocumentModel, IValidationCodeGeneratorConfig, Properties, Consumer<RankedNotification>)` — the generate-and-discard alternative; still in-memory, still no compile if you drop the bytes.
- **`RankedNotification`** (`com.mgmtp.a12.model.notification`, from `a12-base/model-consistency`): `getMessage()`, `getSeverity()` → `Severity` (`INFO`/`WARNING`/`ERROR`, with `isAtLeastAsSevereAs`), `getSource()` (`Object` — often an `IDocumentModel`/`IGroup`/`IField`/rule node, or `null`). rulekit fails fast on any `ERROR` (see `ModelConsistencyException`).
- **`IDocumentModelReferenceResolver`** (`...md.model.api.services`): single method `IDocumentModel getDocumentModel(String reference)` — caller-supplied; returns the *unexpanded* referenced model. Distinct from `IDocumentModelResolver.getDocumentModelById(String)` used on the runtime/`validateFull` path (don't confuse the two).
- **Dynamic `validateFull` is a different thing** — it compiles+runs Groovy to validate *documents*, needs `kernel-core-runtime-30-8` + Groovy at runtime. Not needed for checking a *rule's* legality (that's `checkConsistency`), but it **is** the engine behind the `model eval`/`model compute` verbs (does a rule fire / what does a field compute on a document instance) — see the runtime-seam note below.

## Code generation targets — Groovy (internal) vs Java/TypeScript (documented), and the two runtime paths (verified 2026-06-24, `30.8.1`)

The kernel validates/computes a document by **generating code per model** and running it. Three facts settle a recurring question ("is it Groovy-only? can it emit Java?") — established by reading the source **and** the kernel team's own dev doc (`a12-kernel/documentation/_merged/kernel-dev.md`, consult-only):

- **Three documented targets, not "Groovy + JS".** kernel-dev.md §"Getting started using code generated by Kernel at runtime" lists **Java, TypeScript, Groovy** as supported. Java + TS are the *consumer-facing* targets (embed generated validation/computation code in your own app); **Groovy is the *internal* server-side target** ("always accessed via Java API … used internally for dynamic server-side validation", hence no public docs). The `IValidationCodeGeneratorConfig.ProgrammingLanguage` enum carries `JAVA`/`JAVASCRIPT`/`GROOVY` (the core layer also lists `CPLUS`/VBA). So a **Java baseline is a supported capability, not a hack** — see [`INTERPRETER-PERFORMANCE.md`](INTERPRETER-PERFORMANCE.md) "the kernel baseline: Groovy vs Java".
- **The codegen call:** `generateValidationCode(model, config, props, notif)` returns **zipped source** (`byte[]`) in `config.getProgrammingLanguage()`'s language; default package `com.mgmtp.a12.kernel.generated.`. The generated class set is `Factory_<id>` + `Validator_<id>` + `Calculator_<id>` + `Meta_<id>`; the **`Factory_<id>` is a language-neutral entry point** implementing `IGeneratedCodeAccessFactory { getMetaObject(); getValidator(); getCalculator(); }` (`…core.rt.a12internal`) — the *same* contract whether the source was Groovy or Java.
- **Two runtime paths, picked by config type** (`DocumentRtServiceFactory.createDocumentRtService(IDocumentServiceConfig)` instance-checks the config):

| path | config | how it runs | language |
|---|---|---|---|
| **dynamic** | `IDocumentDynamicServiceConfig` → `DocumentDynamicRtService` | `DocumentModelCodeGenerator` emits **Groovy** on first `validateFull`, `GroovyClassLoader.parseClass` compiles it lazily, caches in `IModelCodeCache` | Groovy, **hardwired** (always `GroovyCodeGeneratorConfig`; the only runtime `IModelCode` is `ValidationModelGroovyCode`) |
| **static** | `IDocumentStaticServiceConfig` → `DocumentStaticRtService` | `StaticModelProvider`/`StaticModelCodeAccessor` loads **precompiled** `Factory_<id>.getInstance()` via the config's `getModelCodeClassLoader(id)` + `getModelPackage(id)` | whatever was compiled — **the supported route to run generated Java** through the *same* `validateFull` scaffolding |

  So: the dynamic path is Groovy-only and cannot be swapped (the provider hard-types Groovy), but the **static path runs precompiled Java** — generate Java source, compile it in-memory (`javax.tools.JavaCompiler`), hand the rt-service a `ClassLoader` over the compiled classes via an `IDocumentStaticServiceConfig`, and `validateFull` produces an identical `IMessage` list executing Java instead of Groovy.
- **Version caution** (kernel-dev.md, 🔥): generated code's *runtime artifacts must match the generator's kernel version*. We pin `30.8.1` and `:adapter` already depends on that kernel, so the generated Java's runtime deps are on the test classpath by construction.

## A12K-3589 kernel-API removal surface + the retirement + the ratchet (2026-07-11, `30.8.1`)

Kernel `30.8.1` marks a set of runtime-service APIs `@Deprecated(since = "30.6.0", forRemoval = true)` under ticket **A12K-3589** — they *will be deleted* in a future kernel, so a call to any of them is a compile-break time-bomb. We retired every one we called and locked the class shut. Read this on a [`KERNEL-UPGRADE`](KERNEL-UPGRADE.md): the removal ticket is expected to land, and this table is the before/after.

**The forRemoval surface (what 30.8.1 will delete) → the non-forRemoval replacement we now use:**

| retired (forRemoval, A12K-3589) | replacement used | note |
|---|---|---|
| `IDocumentRtService.validateFull(IDocument, Locale)` | `validateFull(DocumentV2, DocumentProcessingConfig)` | convert V1→V2 first (below); our default oracle config sets only the locale, while the modern call can also carry the processing-context inputs below |
| `IDocumentRtService.compute(IDocument, Locale)` | `compute(DocumentV2, DocumentProcessingConfig)` | same |
| `IDocumentComputationResult.applyTo(IDocument)` (plain `@Deprecated` 30.0.0, *not* forRemoval — retired opportunistically) | `DocumentV2 applyTo(DocumentV2)` | **`DocumentV2` is immutable** (package `…apiV2.immutable`) — `applyTo` RETURNS the applied document, it does not mutate in place; validate the *returned* instance (the compute→apply→validate flow in `KernelAdapter.evaluateApplied` / `RuntimeLaws.messagesAfterCompute`) |
| `CustomFieldTypeService` (whole class) + `ICustomFieldTypeService` (whole interface) — the *static* custom-field-type registry | `DocumentProcessingConfig.builder(locale).customFieldTypeFactory(factory)` — the **per-call** `ICustomFieldTypeFactory` | the **ICustomFieldTypeService successor**: `FormatDefinitionVordefiniert.getCustomFieldValidator` calls `factory.createCustomFieldValidator(name)` when the config factory is non-null, falling back to the (also-forRemoval) static `CustomFieldTypeService.getInstance()` only when null. So threading the factory through the config fully replaces static registration. Locked by `adapter.laws.CustomFieldTypeBoundsDiffTest` (no more per-test register/clean) |
| `DocumentProcessingConfig.additionalInformation()` | no interpreter slot | deprecated but still propagated and observable in kernel 30.8.1; the interpreter explicitly excludes it and requires consumers to close equivalent configuration over their custom implementations |

`DocumentProcessingConfig.builder(locale).build()` is the behavioral twin of the old locale-only path: its builder defaults are **null** custom-condition/field-type factories (⇒ static-registry fallback preserved), **empty** `additionalInformation`, and **no** `currentDateForTest` (the host's current date). That makes this specific migration behavior-neutral; it does not make those other inputs nonexistent. The full input record is immutable after construction and contains the effective error-message locale, optional deterministic current date, both custom factories, and the deprecated additional-information map. The default-path equivalence is proven by the full `:adapter:test` (differential + fuzz) forced fresh plus both corpus sweeps (the oracle is `KernelAdapter`/`RuntimeLaws`, so any drift would surface there).

**The V1→V2 bridge, deliberately retained (plain `@Deprecated`, *not* forRemoval).** The modern calls need a `DocumentV2`; we still build the document with the V1 `IDocumentFactory` (`createDocument`/`createGroupInstance`/`createFieldInstance`) and convert via `DocumentServiceFactory.createDocumentV1V2Converter().ofDocumentV1(...)`. That whole V1 construction API **and** the converter are plain-`@Deprecated` (superseded by a V2-native builder) but **NOT** forRemoval, so they are not a time-bomb and the ratchet leaves them alone. Migrating them to the V2-native builder is a **separate, larger effort** (it rewrites the oracle's document construction, and even the natural bridge — the converter — is deprecated), tracked as a follow-up; it is out of scope for the A12K-3589 retirement.

**The ratchet (anti-recurrence).** The kernel-facing modules (`:` / `:adapter` / `:cli`, main + test) compile with **`-Xlint:removal -Werror`** — only the `removal` lint is promoted to an error, so a *new* call to any forRemoval kernel API cannot compile, while the retained plain-`@Deprecated` V1 API (and Jackson's `fields()`) still compiles. Proven to fire (a `CustomFieldTypeService` reference fails the build) and proven zero on the current tree. Kotlin diff tests reach the kernel only through the Java `RuntimeLaws` oracle, so the Java ratchet covers them. Guardian row: [`TESTING-SPEC.md`](TESTING-SPEC.md) structural-law guardians.

## Document-model super/subtype (model inheritance) = a header-annotation convention (verified 2026-06-14)

A document model can declare a **super/subtype hierarchy** with other models — but it is **not** a kernel structural feature, **not** a `modelReferences` purpose, and **not** a dedicated header field. It is a **modeling convention over the generic header `annotations`**, verified empirically from the real **2025.06-ext5** `e-commerce` models:

- a base model carries `{"name":"abstract","value":"true"}` + `{"name":"subTypes","value":"ProductMovie_DM,ProductBook_DM"}` (comma-separated subtype model ids);
- a subtype carries `{"name":"superTypes","value":"ProductSingle_DM"}` (comma-separated supertype model ids).

These are just **model-level annotations** the A12 Tools modeler reads to draw/relate the hierarchy; the kernel reads + round-trips them (a `config modify --annotation` value survives the kernel's own serializer) but does not *expand/merge* a supertype's structure into the subtype. **Shared structure is factored separately via `include`** (both Product models `include Product_Common_DM`). A red herring to avoid: the metamodel's field-type **`superType`** (the `String`/`Number`/`Date` family enum category, used by cross-field type checks) is a *different* concept.

**rulekit supports it today, no dedicated feature** — the model-level annotation surface authors the convention directly: `DocumentModelDraft.annotation("superTypes", "…")` / `ConfigEditor.annotation(...)` / CLI `config modify --annotation superTypes=…` (and `abstract`/`subTypes`). Locked by `modelkit.ModelHeaderTest.theModelSuperSubtypeConventionRoundTrips` (the convention survives the kernel round-trip). It is also surfaced **read-side**: `modelkit.Workspace` parses it (`abstract`/`superTypes`/`subTypes`), so the CLI `model info` (one model) and `workspace list` (a folder) both report the graph.

## Lexer terminals — the catalog ↔ grammar parity test (implemented; "deferred" flipped 2026-06-10)

One of the catalog's **four honesty anchors** (PROJECT-DESIGN §9/N3 — v2 added construct parity against the parsetree-api name enums + `MVK_*` enum, and the opt-in semantics drift oracle against the kernel's bilingual web content catalogs; sources for those in [`KERNEL-RULE-API-SURVEY.md`](./KERNEL-RULE-API-SURVEY.md) §13). This section covers the keyword anchor: a coverage test asserting every grammar lexer terminal is represented or explicitly excluded. The terminals live in **internal-tier** classes (so N8 says don't depend on them from main code — a test may, carefully): `a12-kernel/kernel-tool/kernel-core-parser/src/main/java/com/mgmtp/a12/kernel/core/parser/internal/grammar/languages/LexerTerminals_{en,de}.java`. Each is a `ListResourceBundle` whose `CONTENTS` maps a **keyword string → a shared token constant** on `Base_ConditionLexer` (e.g. `{ "And", Base_ConditionLexer.UND1 }` in EN, `{ "Und", Base_ConditionLexer.UND1 }` in DE). So reconciliation is **per token constant**, not per string, and the bundles are not 1:1 (some tokens have several keyword spellings — `And`/`and`/`AND` all map to `UND1`/`UND2`/`UND3`). Verified EN→DE pairs used in the seed catalog: `FieldFilled→FeldAngegeben`, `FieldNotFilled→FeldNichtAngegeben`, `And→Und`, `Or→Oder`, `Length→Laenge`, `Having→Mit`, `Sum→Summe`, `Today→Heute`, `PatternMatched→WieMuster`, `PatternViolated→NichtWieMuster`. Comparison operators (`<= == != < > >=`) and arithmetic symbols are **symbolic** terminals — identical in both languages. The design choice resolved to the reflective option: both directions are built and CI-locked — `catalog.KeywordParityTest` (catalog → terminals) and `catalog.KeywordReverseParityTest` (every terminal cataloged or explicitly excluded, self-cleaning exclusion list) load the internal `ListResourceBundle` from the test classpath (N8: tests may read the internal tier).

The kernel facts live in `KERNEL-FINDINGS.md` §7; rulekit's treatment:

## DM-JSON write path (F6) — and the includes-safety rule

`BoundModel.ofJson(json[, resolver])` retains the **authored, unexpanded** DM-JSON; `add(Rule)` injects the rule element (with its real localized messages) by **Jackson tree surgery on that retained source**, then re-binds the result (deserialize → expand → `checkConsistency`) and returns a **new** binding (snapshot semantics, F0 — the original is untouched). `toJson()`/`writeTo(path)` emit the retained source.

- **Includes / `modelReferences` are preserved, never inlined.** The write edits the authored source JSON, *never* a re-serialization of the kernel's **expanded** `IDocumentModel` (which would flatten includes into the base file and lose the modular structure). Guarantee made executable: `WritePathTest.toJsonReturnsTheAuthoredSourceVerbatim` asserts `ofJson(json).toJson()` equals the input byte-for-byte. The resolver passed to `ofJson(json, resolver)` is retained and reused on every `add()` re-bind, so a model with includes round-trips through expansion correctly.
- **The write gate is `BasicConsistencyCheck`** (instrument 4), not `checkConsistency` — but re-binding runs the full `checkConsistency`, a strict superset, so an invalid write fails fast at `add()` (`WritePathTest.addReValidatesAndRejectsAKernelInvalidWrite`).
- **Limitation (fails fast, by design):** a rule's target group must exist in the *base* model's authored JSON; you cannot add a rule to a group that physically lives in an *included* sub-model (its elements aren't in the base file) — `ModelWriter` throws "no group at path" rather than corrupt anything. (Editing the included file is that file's concern.)
- **Adding a child into a *mount* group is refused, not silently destructive** (2026-06-20; KERNEL-FINDINGS "A mount group's local elements SHADOW the include"; probe `01-de` Finding 4). A mount group (`Group.modelAlias`) exists in the base JSON, so `containerElements` *could* append a local field/group to it — but the kernel then uses the local elements and **stops expanding the include**, silently dropping the mounted content (and still validating). So `ModelDocument.containerElements` now **throws** when the target group is a mount (the loud backstop under every `field`/`group add`, `move`, and the `apply` ops), and the CLI runs `SafetyChecks.notAnIncludeMount` first for a structured `RK_MOUNT_NOT_EDITABLE` refusal (detection: `ModelDocument.mountAliasAt`). Edit the included model, or mount under / add to a non-mount group. Locked by `MountEditRefusalTest`.
- **Includes are now fixture-tested** (`IncludesWritePathTest`, own-domain `storefront.dm.json` → `catalog.dm.json`, adapted from the A12 Tools workspace `modelAlias` include pattern): `ofJson(base, resolver)` expands so an included field is addressable (`m.num("/Storefront/Inventory_/Catalog/ListPrice")`); pure **load+save is byte-for-byte identity** on the base (`toJson()==input`) and the catalog is **never inlined and never written** (it's the resolver's read-only source) — the two models stay separate. Adding a rule (referencing base fields) keeps them separate and re-binds with the same resolver.
- **Two honest limits** (documented): (1) a written rule that *references an included field* needs the expanded→authored path translation (the `_`-suffixed mount path is not authorable — `MVK_INVALID_ENTITY`; KERNEL-FINDINGS §10), a path-policy gap; (2) `add()` **reformats** via Jackson (pretty-printed, ~2-space) so a *modified* model isn't byte-identical to the original formatting — only an unmodified load+save is. Content/structure (incl. `modelReferences`) is always preserved.
- **The MVK ledger is fully classified (300/300, 2026-06-10) — and its evidence comes in three tiers.** The metamodel section was resolved by the rule-explanation dogfood; the three enum sections by kernel-source reading (`Check*Impl` + BA doc) with targeted probes. Tier 1: **pre-checked** rows cite an existing builder check + its lock. Tier 2: **erased** rows rest on positive typed-API evidence (verified operand typing, legacy/H-model-only constructs, the §8 un-buildables). ## Structure read + round-trip (M7, 2026-06-10) — ride the generic tree, not the kernel's typed serializer

`modelkit.ModelDocument.read(json)` reads an existing model into its **authored source tree** (a plain Jackson `ObjectNode`) and enumerates its structure name-path-addressed (header, doc config, includes, type-def ids, the group/field tree + field-type discriminator + repeatability). Reading is **purely textual** — no kernel, no include resolution — so a model with unresolved includes still reads and enumerates (storefront's `catalog` include surfaces without the resolver). `toJson()` re-serializes the retained tree.

**The round-trip fidelity finding (the M7 source-mining result).** The kernel's own serializer is **not** a byte-lossless round-trip: its `JsonMapper` BASE instance sets `Include.NON_EMPTY` and several mixins use `@JsonInclude(NON_DEFAULT)` (`GroupMixin.required`, `DocModelConfigMixin.fieldRefByShortNameAllowed`, …), so deserialize→serialize **drops empty/default fields**. A **generic Jackson tree** round-trip (`readTree` → `writerWithDefaultPrettyPrinter`) goes through none of that typed machinery, so it is **content-lossless** — every field/value preserved, nothing defaulted-in — modulo pretty-print whitespace. **Consequence:** structure editing (M8) mutates and re-serializes the *tree*, never the kernel's expanded/typed model. Locked by `modelkit.ModelDocumentTest` (read→write is tree-equal to the source, idempotent, and the written-back self-contained model still passes the real kernel's `checkConsistency`).

**Distinct from `BoundModel`'s write path (above).** `BoundModel` retains the authored source *string* verbatim, so an unmodified `ofJson(json).toJson()` is **byte-for-byte** identical (and a *modified* model reformats). `ModelDocument` always re-serializes the tree, so even an unmodified round-trip is content-identical-but-reformatted — the right behavior for an edit substrate (edited or not, output is uniform), and exactly the path M8's surgical edits exercise.

## Structure edits + the delete-safety rule (M8/M9, 2026-06-10)

Structure edits (`ModelDocument.addField`/`addGroup`/`removeField`/`removeGroup`/`setRepeatable`) are **surgical tree mutations**; the single validity gate is `validate()` (re-bind → `checkConsistency`), which funnels both kernel rejection tiers — deserialize/expand (e.g. a duplicate id → `IllegalArgumentException`) and `checkConsistency` (ERROR notifications) — into one `ModelConsistencyException`. `EditSession` (the layer above the ⊥ kits) composes structure + rule edits over one DM-JSON and validates once.

**Delete is deliberately *not* reference-checked at the call site** (decided 2026-06-10, locked by `EditSessionTest.removingAFieldARuleReferencesIsRejectedByTheGate`):
- **The kernel gate is the authoritative dangling-reference check.** Removing a field a rule still references leaves the condition pointing at a missing entity, so `validate()` rejects it (`ModelConsistencyException`). We don't reimplement reference analysis — the engine arbitrates.
- **An edit session must tolerate invalid *intermediate* states.** Deleting a field *and* the rule that references it has no globally-valid per-step ordering if each step self-validates; batch-then-validate-once is the model, so `remove()` never auto-validates.
- **Reference analysis lives in the adapter, above the kits.** `KernelAdapter.whereUsed(path)` (F9a) is the "what references this?" oracle; `modelkit`/`EditSession` sit *below* the adapter (and `dm.modelkit ⊥ dm.rulekit`), so a proactive check there would mean reimplementing kernel reference resolution — forbidden.

**Client feedback shape.** `removeX(path)` throws `IllegalArgumentException` *only* for an absent path (a usage error); the dangling-reference problem surfaces at `validate()` as `ModelConsistencyException` (`.getMessage()` = the kernel diagnostic; `.notifications()` carries the `MVK_*` `RankedNotification`s on the `checkConsistency` tier, else the wrapped `cause`). Same gate `BoundModel.add` uses — uniform across the edit surface.

**Owned by the CLI remove verb** (which has the adapter): a *proactive* `whereUsed`-based check that lists referencing rules and **refuses without `--force`** / offers an **explicit `--cascade`** (never a silent cascade-delete). That's where the capability lives; it's a UX layer over the same gate.

## Field-level custom error messages — `requiredMessages` / `enum.errorMessages` (G23, 2026-06-21)

rulekit's treatment of the per-locale field error messages (kernel shape in KERNEL-FINDINGS §4/§8 — a `requirednessConfig.errorMessage` / `EnumerationType.errorMessage` array; "use default" = absence):

- **Two field-spec keys** (`field add`/`field modify`, same on the `apply` ops): `requiredMessages: {locale: text}` (the required-field message) and `enum.errorMessages: {locale: text}` (the enum invalid-value message). `enum.invalidValueMessage` (a single string) stays as a shorthand that the writer expands across every declared locale.
- **`EnumSpec` carries a per-locale `invalidValueMessages` map** (the single string is back-compat, expanded at serialize); **`requirednessConfig` messages** ride a new `ModelDocument.setRequiredErrorMessages` applied *after* requiredness (so the config exists) via `FieldModification.requiredMessages`.
- **Fail-fast precondition:** `requiredMessages` on a non-required field is refused at the modelkit layer (`IllegalArgumentException` → the verb's spec-error exit) — the message needs a `requirednessConfig` to attach to. "Use default" is simply omitting the keys; there is no `useDefault` flag to set.

## Formal-error message text — the interpreter emits its OWN wording, not the kernel's bundle (Option A, 2026-06-23)

The interpreter's `model eval` now emits a `formalePruefung` message per malformed filled field (kernel mechanism in KERNEL-FINDINGS §3). The **structural channels match the kernel exactly** — code (`FormalErrorCode.id`, the kernel's verbatim German identifier: `datumFormatFalsch`/`zahlHatUngueltigeZeichen`/`zahlHatDezimalTrenner`/`zahlFalscheAnzahlNachkommastellen`/`fuehrendesBlank`), rule path (`formalePruefung`), field pointer, severity (ERROR), type (VALUE) — locked by `adapter.laws.FormalErrorMessageDiffTest`. **The human-readable TEXT is the interpreter's own wording** (`FormalError.formalErrorText`, en/de), *not* the kernel's localized message-bundle string.

**Rationale (the current decision):** `:interpreter` is a kernel-free, independently-publishable artifact. The kernel's formal-error text lives in its German/English message bundles (e.g. en `"Only dates in the format YYYY-MM-DD are allowed."`, de `"Bitte geben Sie ein gültiges Datum JJJJ-MM-TT ein."`), and is scale-parametrized. Reproducing it byte-for-byte means **copying the kernel's copyrighted message strings into the OSS artifact** — at odds with the license-safe rule (copy the mechanism, never the expression) and brittle to kernel bundle changes. So for now the structural contract (the *code*, which is the stable, machine-usable channel) is faithful; the prose is ours.

**Concern this accepts:** the interpreter's `model eval` and the A12 kernel print *different* text for a formal error — the codes/pointers agree, the sentence differs (the interpreter emits its own English wording; the kernel's is German, EUPL-licensed — IF3). This is the deliberate, documented divergence (the only fidelity gap left in the formal-error path); with `--kernel` eval retired (Set V) it is no longer a CLI engine toggle, but it remains the accepted interpreter-vs-kernel text difference (certificate R7).

**Proposal — how to switch to byte-identical kernel text later (when wanted):** (1) confirm the licensing for shipping the kernel's formal-error strings (they are short, functional UI strings, but the bundle is a kernel asset — get owner sign-off); (2) extract the en/de templates for the `FormalErrorCode` set from the kernel's `kernel-core-runtime` formal-error resource bundles (`Constants.FORMAL_ERRORS_MESSAGES_RESOURCE_NAME`; verified emitting via `FehlerHandler.getFehlertext`), porting the scale-parameter substitution; (3) replace `formalErrorText`'s bodies with the ported templates **and flip `FormalErrorMessageDiffTest` to assert the text against the kernel's `getErrorText`** (it currently asserts structural channels only) so the text is then differentially locked. The enum + the existing structural differential make this a localized, low-risk change.

## Reference-rewriting refactors — one `StructureRefactor` seam, standalone + `apply` (2026-06-13)

The reference-rewriting refactors (`field`/`group` rename·move, `rule` rename, `typedef` rename) are single-sourced in `cli.StructureRefactor`: per op it carries the **safety-gate composition**, the **reference entity-moves** (empty for rule/typedef — they rewrite no AST references), and the **node mutation**. The two callers share it, so the §6 gate can't drift:
- the **standalone verb** (`ReferenceRewritingRefactorCommand` + the rule/typedef commands) — gate → `rewriteAndMutate` → `validate()` → write;
- the **`apply` op-record** — gate against the **live (transiently-edited) session** (so it sees prior ops), `rewriteAndMutate`, then re-home the result into a fresh `EditSession`, deferring to the one terminal gate; a refused gate throws → the whole sequence rolls back. `extract`/`inline` stay standalone (multi-artifact). See CLI-SPEC §6/§7.

**Treatment of the empty-group serialization quirk** (KERNEL-FINDINGS "Serialization shape — a childless group's `elements` array is omitted"): the rewriter round-trips through the kernel serializer, which drops a childless group's `elements`. The group-elements traversal (`elementsOf` — since Set W a kit-private replica in each internal consumer: `rulekit.write.DmJson`, `modelkit.DmNodes`, `schemakit.Carriage`) therefore treats an **id-matched group with no `elements` array as an empty container and materializes the array** (`putArray`), so inserting/relocating into a freshly-added empty group works. Without this, `field`/`group move` into an empty destination spuriously failed "no group at path" — for the standalone verb too (it always rewrites first). *(Locked: `MoveVerbTest.movesAFieldIntoAChildlessGroup`, `ApplyRefactorTest`.)*

## The kernel's internal AST + unparser (read surface for N8's kernel-adapter tier — verified)

Verified 2026-06-03 against the sibling `a12-kernel` clone, prompted by `a12-antlr4-code-editor/ANALYSIS-RULES-EDITOR-AST.md` (the Rules-editor/AST analysis). This is the surface behind **D15** — relevant to the **#3 round-trip** and foreign-rule **explain** (F9), both **Phase 2** since bidirectional modification became a declared goal (PROJECT-DESIGN §2, same day). **The comprehensive inventory — incl. the `IMVK_Service` facade, `getMvkServiceForModel` bootstrap, `changeConditionText` rename refactoring, analysis services, per-rule `hasValidConditionText`, computation services, and the TS-side findings — lives in [`KERNEL-RULE-API-SURVEY.md`](./KERNEL-RULE-API-SURVEY.md); this section keeps only the core verified facts:**

- **A high-level, ANTLR-free AST exists**: `kernel-tool/kernel-core-parsetree-api` — ~40 typed node interfaces (`ICondition`, `IOperation`, `ICompositeOperation`, `IComparisonCondition`, …) plus type enums (`LogOp`, `CalcOp`, `OperationType`). Everything (interfaces included) lives under `com.mgmtp.a12.kernel.core.parsetree.a12internal.*` and is annotated `@OnlyForUsage` — traversal/reading is the kernel's *intended* consumer usage; the `a12internal` package withholds *stability*, it doesn't forbid use.
- **Text → AST**: `ParserService` (internal tier, `kernel-core-parser`) — `parseAndCheckCondition(IRule, IProblemReporter, ExpandMode)` and, notably, `parseAndCheckCondition(IRule, String conditionText, …)` (raw text + rule context — for foreign rules the `IRule` is already in the bound model, so foreign text → `ICondition` is one call); plus snippet entry points `parseConditionSnippet` / `parseOperationSnippet`.
- **AST → text (complete unparser)**: `ConditionFormatter` (internal tier) — `formatConditionText(ICondition, IRule)`, `formatConditionPart(IParseTreeEntity, String)`, and `formatAndTranslateConditionText(IRule, Locale, …)` (en↔de; translation working at all is strong evidence of full-grammar unparse coverage). Useful as a **differential test oracle** for rulekit's renderer (test tier — N8-legal today): compare `kernelFormat(kernelParse(rulekitRender(ast)))` with rulekit's canonical text; the translate variant checks the DE dialect against the kernel's own rendering.
- **`ASTVisitor` is an abstract class (~86 visit methods) with default-`true` bodies** — a converter visitor overrides only covered constructs and traps the rest in `visitGeneral` (fail fast on "unsupported construct"); the method list doubles as the #3 coverage checklist.
- **Condition comments (concrete syntax — authored + leading-preserved)**: the AST stores no whitespace/comments (`ConditionFormatter.stripComments` handles comments separately), so a pure AST re-render canonicalizes. rulekit keeps comments in a **side-channel** beside the AST — `rulekit.dsl.Comments`, a node-identity map (the "carrier (c)" design: the 15-type `Condition` hierarchy + its exhaustive switches stay untouched). The map carries both kinds of node the kernel comments — a `Condition` branch and a `Calculation` operation. Two consequences: comments are **authorable** on rules (`Rule.Builder.comment`/`commentAfter`) and on **computations** — their operations *and* preconditions (`Computation.Builder.comment(...)`) — all rendered as `;;` lines the kernel accepts; and a rule's **leading comment is preserved by default** on read→modify→write-back (`Comments.preserveLeading`, wired in `ModelWriter.replaceCondition`, so both the typed `modifyRule(Function)` and the text `modifyRule(String)` paths carry it). A **computation's** leading comments (common precondition + first operation) are carried the same way on modify (`ModelWriter.replaceComputation`, both the typed and spec overloads); per-alternative matching across a re-expression stays positional/out of scope. The residual loss is now only *inline/trailing* comments + non-canonical formatting (no AST node to anchor them across a re-expression) — `KernelAdapter.diff` discloses exactly that, carrying the leading comment on both sides. Confirms §12's blast-radius warning for #3, now narrowed. Law-locked — KERNEL-FINDINGS "Condition comments"; `adapter.ConditionCommentLossinessTest`, `adapter.CommentRoundTripTest`, `rulekit.dsl.CommentRenderTest`/`RuleCommentTest`.
- **No construction/mutation API**: all impl classes (`ConditionImpl`, …, assembled by `ParseTreeCreator`) are internal, and `RuleBuilder` takes `errorCondition` as an opaque string. The N8 adapter is therefore **read-only by policy** — rulekit's own AST stays the only write surface (D15).
- **Dead ends checked**: `kernel-rewrite` contains OpenRewrite kernel-upgrade recipes, not rule rewriting. The official Rules editor (`a12-antlr4-code-editor` + `kernel-core-parser-web`) builds **no AST at all** — it edits the raw DSL string (token stream for highlighting, parse-for-errors with the tree discarded, ATN-walk completion), so the TS stack offers no round-trip shortcut, and "emit the string" (F6) is exactly how the platform's own tooling integrates with the kernel.

## Kernel-adapter bootstrap (Phase 2, F10/F9a foundation — verified 2026-06-04)

The opt-in `adapter` module (PROJECT-DESIGN D15/N8 tier 3, Gradle subproject — `:adapter:test`, kept out of core's `:test`) reaches the kernel's `a12internal` *read* surface for rules **already in a model** (the foreign-rule path read and exact whereUsed build on). - **Tolerant read — a sealed `ReadResult` result (F11 "preserve the unknown"; finding 5).** `read(rule)` returns `ReadResult.Converted(condition)` or `ReadResult.Opaque(canonicalText, reason)` — a not-yet-modeled construct is **preserved verbatim** (the raw stored condition text, re-emittable on write-back) with a reason naming it, **never lost and never reported as corrupt**. A valid rule the kernel accepts never throws. `readAll()` does a whole model, per-rule, so a user's DM reads safely (supported rules typed, the rest opaque). The converter still throws `UnsupportedConstructException` internally — it is the recursive unwind signal, caught by `read` and surfaced as `Opaque.reason()` (and remains the strict, fail-fast contract for any future authoring-side use). Coverage grows by corpus priority (`WORKSPACE-CORPUS-ANALYSIS`); the opaque variant turns the tail from hard failures into preserved-with-a-warning.
- **Opaque preserves the *raw stored* text, not the kernel-canonical form (2026-06-06).** `read` builds `ReadResult.Opaque` from `IRule.getErrorConditionText()` (the verbatim stored condition), falling back to the canonical form only when that's absent. Reason: the kernel's `formatConditionText` is **lossy for a `$` correlation** — it truncates such a condition to its first conjunct (KERNEL-FINDINGS), so preserving canonical would *lose* the rule on write-back, the opposite of "verbatim". (The `Opaque` record component is still named `canonicalText` to keep the CLI output key stable; it now carries the raw text.)
- **`$` outer-iteration correlation — authoring done; read still loud Opaque (N8; authoring 2026-06-07).** The two directions are split:
  - **Authoring (build → render → kernel-validate): implemented.** The marker is an `outer` flag on `FieldValue` (`[$path]`); `StringRef.outer()` / `NumberRef.outer()` set it, and `DslRenderer` emits `$` only in the bracketed value form (a filter comparison) — not in argument position. An authored correlation (`Sum(Items*/Count Having [$/Order/Quantity] == [Items/Count]) > 5`) renders the `$` and the real kernel accepts it. Locked by `dsl.operators.CorrelationConditionTest` (render EN/DE) + `adapter.OuterCorrelationAuthoringTest` (kernel-valid).
  - **Read (parse → convert): complete (2026-06-07) — Corpus-1 87.0% → 95.0%, `$` opaques 127 → 0.** Two pieces. **(a) Thread the outer flag** through every field-vs-field comparison kind — `fieldValueComparison` marks the left operand, the per-kind builders (`numberComparison`/`stringComparison`/`enumComparison`/`convertDateOperand`/`categoryComparison`) the right — plus `CurrentRepetition($group)`, **presence predicates** (`NoFieldFilled($a, $b)` via `FieldRef.outer`), and **value-list operands** (`FieldListRef.outer`, at the single `toFieldOperand` choke point). The marker lives on `FieldValue.outer` / `EnumCategoryAccess.outer` / `CurrentRepetition.outer` / `FieldRef.outer` / `FieldListRef.outer`. **(b) The real lever — a converter gap, not `$`:** field-list quantifiers with a `Having` filter (`AtLeastOneFieldFilled(Group*/Field Having …)`) were converted by field *path only*, **silently dropping the whole filter**; routing a single filtered entity through `flattenScope` (which converts the filter) converted the entire product-family overlap template (~60 rules). The N8 guarantee is the **post-conversion count-check** `verifyOuterPreserved`: `countOuterRefs(source)` vs the `[$`/`($` markers in the rendered conversion — fewer rendered ⇒ a kind dropped a `$` ⇒ throw `UnsupportedConstructException` ⇒ `Opaque` (verbatim). This is what *caught* the dropped-filter bug (source `$`, rendered 0 → Opaque, not corrupt) before the routing fix, and it makes partial threading **safe by construction** (`adapter.OuterCorrelationBackstopTest` drives it directly; `OuterCorrelationQuantifierReadTest` round-trips the full overlap shape). Every `$` rule in Corpus-1 now converts (**0 `$` opaques**); the last shape — a `$` on a wildcard value-list operand — was cleared by `FieldListRef.outer`. kernel-mm stays 553/553. Detail: [`PROJECT-DESIGN.md`](PROJECT-DESIGN.md) §21H.
- **Round-trip oracle.** `ReadRoundTripTest` proves render → kernel-parse → convert → render is the identity for the covered constructs (`render(authored) == render(read(...))`), the differential check that keeps the converter honest against the real engine.
- **Boundary conversion holds.** `read` returns rulekit types (`ReadResult`/`Condition`/preserved text); the kernel `ICondition`/`IRule` never escape (the `parseCondition` hook is package-private). The converter is the only place that touches the kernel transport AST.
- **Aggregate as a comparison's *compared-against* operand — resolved 2026-06-05** (was an F10 gap, surfaced by the dev-path eval). `[Quantity] < Sum(Items*/Count Having …)` (field-vs-aggregate) and `Sum(…) > [Quantity]` (aggregate-vs-field) now read to **`Converted`** and round-trip; previously the converter threw *"number comparison against a non-field, non-constant operand"* → `Opaque`. The lift had two parts: (1) a typed **expression-vs-expression** comparison in the DSL — `NumberExpr.lt(NumberExpr)`/… plus `NumberRef` convenience, so `[field] < Sum(…)` is also *authorable*, not only readable; (2) `ConditionConverter.numericExpr` + `exprVsExpr` accept an aggregate / date-diff / current-repetition / number-field on **either** side of a comparison. Locked by `ReadRoundTripTest.roundTripsAggregatesAndHaving` (field-vs-aggregate + aggregate-vs-field cases).

## Computation read — the calculated-field read path + the N8 dep expansion (2026-06-08)

The `ReadResult` peer for **computations** (calculated fields): `KernelAdapter.readComputation` / `readAllComputations` → a sealed `ReadComputation` (`Converted(Computation)` / `Opaque(reason)`), tolerant like rule read. The read chain:

- **Enumerate:** `ElementContainer.getAllCalculations()` → `IBaseCalculationService.ICalculationRule` (the `getAllRules()` peer).
- **Extract (structured):** `new ServiceFactory().getCalculationService(mvk)` → `ICalculationService.extractCalculationInfo(cr, SILENT)` → `ICalculationInfo`, exposing the **parsed** subtrees: `getCalculatedField()`, `getCommonPrecondition(): Optional<ICondition>`, and `getPartialCalculations(): List<Pair<ICondition, IOperation>>` — the (precondition, operation) alternatives. `mvk` *is* the config (`IMVK_Service extends IServiceConfiguration`), so no separate config is built.
- **Unwrap the operation:** each alternative's operation is a `CalcOperationWithCompOp` (the kernel wraps `computedField <op> valueExpr`); take the value via the api-ish `IWithComparisonOperation.getOriginalOperation()` (which also strips any auto-added rounding) — no concrete-impl reference.
- **Convert:** `ConditionConverter.convertOperation` reuses the comparison-operand converters (`numericExpr` / `stringOperand` / `convertDateOperand` / `constantOperand` + a kind-agnostic `FieldValue`) → a rulekit `Calculation`; `convertComputation` assembles the `Computation`, **recovering messages** from `ICalculationRule.getRule().getErrorMessages()` (so the result is complete + re-addable) and rejecting non-`EXACT` rounding as `Opaque` (rulekit models exact computations only).
- **Write-back:** `ModelWriter.replaceComputation` / `removeComputation` + `BoundModel` twins (the `replaceCondition` / `removeRule` peers). Full cycle proven: read → re-express → write-back → re-read identity (`ComputationReadTest`).
- **Modify-loop + CLI write verbs (2026-06-08):** `KernelAdapter.diffComputation(name, modified) → RenderedDiff` is the `diff` peer — a before/after rendering of the *whole* computation (computed field + common precondition + each `(precondition, operation)` alternative), so the change is reviewable before write-back (`ComputationDiffTest`). The CLI authors/modifies computations too: `add` persists one from a **computation-spec** (a `computedField` key picks the computation branch; `cli.ComputationSpec` → `DraftComputation`, validated by `RuleValidator.check(…, DraftComputation, resolver)`, persisted by the **slot-based** `ModelWriter.addComputation(json, DraftComputation, messages)` — the `addRule`-from-slots peer, sharing `computationNode`). The re-express loop is the single **`modify`** verb: it writes the modified model back (in place by default, `-o` redirects) and **`--dry-run`** previews read-only (`modify --computation <name> --spec <file>` | `modify --rule <name> --condition <DSL>`). A read-only `diff` verb existed briefly on 2026-06-08, retired the same day as redundant with `modify --dry-run`. Both work over multi-file models (the `-w/--workspace` resolver threads through). `cli.ComputationCliTest`, `cli.ModifyVerbTest`.

**N8 dep expansion (the deepest internal touch, deliberate — D15/N8):** reaching the calc service added **`kernel-core-facade`** (`ServiceFactory`) and **`kernel-core-calc`** (`IWithComparisonOperation`) to the adapter's deps. Still under the guardrails: **read-only** (no `…Impl` constructed/mutated — only `extractCalculationInfo` + getters), **boundary-converted** (no kernel type escapes a public signature — `ReadComputation` / `Computation` are rulekit/JDK). **Coverage: kernel-mm 6/6 (100%), Corpus-1 626/626 (100%)** — every computation in both corpora reads. Own-domain shape locks: `adapter.ComputationShapesTest` (numeric aggregate / string-const / bool-const / time-from-date-time / enum-`FirstFilledValue`) + `adapter.ComputationReadTest` (numeric field / arithmetic / tiered + full-cycle modify).

### `getAllRules()` ⊇ computations — the partition (2026-06-08)

**Kernel fact (verified, `30.8.1`):** a computation is *stored as a rule* — its `ICalculationRule.getRule()` carries the kernel-generated **self-validation** condition of the calculated field, and that rule **also appears in `ElementContainer.getAllRules()`**. So `getAllRules()` = validation rules ∪ computation rules; `getAllCalculations()` is the computation subset (kernel-mm: 553 = 547 validation + 6 computations, all 6 in both). Worth knowing: `mvk.getDirectlyReferencedEntities(cr.getRule())` over a computation rule returns the *whole* reference set — calculated field **plus every operand** (a field read only in the operation is included), not just the precondition's fields.

**Rulekit's treatment — partition so the two element kinds never conflate:** `computationFullNames()` is the discriminator, and `ruleFullNames()` / `readAll()` / `whereUsed()` are **validation rules only** (they subtract the computation names). Rationale: reading a computation's generated self-validation condition *as if it were a hand-authored rule* is semantically wrong and double-counts it against `readAllComputations()`; and a `--rule` arg that silently accepted a computation would `explain`/`read` the wrong thing. Total typed coverage is unchanged (547 validation + 6 computations = 553) — just correctly attributed. Floor split in `KernelMmReadCoverageTest`: validation-rule floor 547, computation floor `== total` (6).

**The read surface this unlocks (whole loop now symmetric for both kinds):**
- **whereUsed (F9a) over computations** — `whereUsedInComputations(entity)` + `referencedFieldsOfComputation(name)` (the `whereUsed`/`referencedFields` peers, kernel-native so they work even on an `Opaque` computation). The CLI `where-used` emits `rules` and `computations` as separate arrays (`adapter.WhereUsedInComputationsTest`, `cli.WhereUsedVerbTest`).
- **Unified whole-model read** — `readModel(): ModelRead{rules, computations}`, two disjoint maps + `convertedRules()`/`convertedComputations()`/`fullyTyped()`; the single entry point to round-trip a foreign model completely. CLI: `model read` (`adapter.UnifiedModelReadTest`, `cli.ReadVerbTest`).
- **explain a computation** — `ModelContext.explainComputation(Computation) → ComputationExplanation` (computed field + kind, common precondition + per-alternative precondition/operation projected with the catalog glossary + referenced fields, messages, gloss). CLI: `explain --computation` (`context.ComputationExplanationTest`, `cli.ExplainVerbTest`). A `--rule` that names a computation now redirects (`ModelPaths.ruleProblem` overload).

## Runtime behavioral-law oracle (F-LAW, 2026-06-06)

Two tiers of "law" lock the kernel's behavior — keep them distinct:

| tier | question | mechanism | location |
|---|---|---|---|
| **accept / reject** (structural) | does the kernel *accept* this condition? | `RuleValidator` + `checkConsistency` | `src/test/.../validate/laws/` ↔ `KERNEL-FINDINGS.md` |
| **fires / does-not-fire** (behavioral, **runtime**) | does a valid rule *evaluate* as intended on data? | `IDocumentRtService.validateFull` over a built document instance | `adapter/src/test/.../adapter/laws/` (`RuntimeLaws` harness) |

The runtime tier evaluates the **real engine** against a constructed document and reads back which rules fired (`IMessage.getErrorCode()`/`getRulePath()`), so a documented behavior changing under a kernel bump fails loudly. Wiring: a trivial `IDocumentModelResolver` (`id → model`) → `DocumentRtServiceFactory.createDocumentRtService(dynamicConfig)` (an `IDocumentDynamicServiceConfig` with a `HashMap`-backed `IModelCodeCache`) → build an `IDocument` via `IDocumentFactory` → `validateFull(doc, Locale)`.

**Document construction — the V1 path (lesson learned, the one shared with the TypeScript runtime; DocumentV2 is new and a separate research item):** building the instance is the subtle part. The kernel converts a V1 `IDocument` to update actions via `DocumentV1V2ConverterImpl.docV1ToUpdateActions` → `DocumentPointer.of(pathParts, repetitions)`, and that contract is:
- **one 1-based repetition index per path part** — group *and* field each get one: `/Order` → `{1}`, `/Order/Quantity` → `{1,1}`. A length mismatch makes the pointer build fail and surfaces as the opaque *"cannot convert entity instance … to update action"* (the error that blocked the first spike — root-caused from the kernel sources).
- **values are read back as Strings** during the conversion (`metaField.convertWithOnlyBasicTypeCheck(sValue)`), so pass field values as text, not `BigDecimal`/`Long`.
- **empty vs absent vs filled-row matters** — see the empty-value law and KERNEL-FINDINGS §2.

For **multi-row** iteration (§9) the harness exposes a `Doc` builder (explicit group/field placements, one repetition index per path part) and a `messages(model, Doc)` that returns each message's **row pointer** — so a law can assert *which* row a per-row rule fired on. Laws locked: `PolarityLawsTest`, `EmptyValueLawsTest` (§2), `FormalErrorLawsTest` (§3), `BooleanThreeStateLawsTest` + `FieldListQuantifierLawsTest` (§1), `RepetitionLawsTest` (§9 per-row iteration + Sum/Max aggregation). Remaining HIGH-trap laws (empty date, path walk-up, the required property) are the F-LAW backlog ([`PROJECT-DESIGN.md`](PROJECT-DESIGN.md) §21H).

**Promoted to a public seam (2026-06-09).** The same `validateFull`/`compute` machinery is now a supported **public adapter capability**, not just the test oracle: `KernelAdapter.evaluate(Map fields, Locale)` → `EvalResult` (which rules fire on a document instance) and `KernelAdapter.compute(...)` → `ComputeResult` (what each field computes). The CLI surfaces them as **`model eval`** / **`model compute`** (CLI-SPEC §5). This required promoting the runtime tier in `adapter/build.gradle` from `testImplementation`/`testRuntimeOnly` to `implementation`/`runtimeOnly` (`kernel-md-runtime-api`, `kernel-md-document-api`, `kernel-md-runtime-service`) — the **N8 boundary still holds**: `evaluate`/`compute` take a JDK `Map` (a model-aware nested-tree walk derives the kernel rep-indices) and return rulekit records (`EvalResult`/`ComputedField`); the kernel runtime types never escape a public signature. The seam's nested-walk is pinned against `RuntimeLaws`' known-good row pointers in `EvalDocSeamLawsTest` (the spike). Findings it locked: validate ≠ compute (KERNEL-FINDINGS), empty number operand → `0` in a computation, formal checks carry `rulePath = formalePruefung`. *(`RuntimeLaws` could later delegate to this seam; not required.)*
