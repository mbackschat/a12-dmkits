# Running builds and tests here — the measured discipline

The rules an agent must hold every session stay in [`CLAUDE.md`](../CLAUDE.md) "Build"; this doc carries their EVIDENCE — the incidents that produced each rule, the measurements, and the detail you need when a run surprises you. Extracted 2026-09-05, paragraphs moved verbatim so no measurement was re-derived in the move.

## The lanes — what each covers, and why a green one can still miss

**`:cli:test` IS NOT the cli estate — the checkpoint verb is `:cli:check` (standing correction, 2026-08-07).** `publicContractTest` (the black-box lane that spawns the packaged launcher: `DmtoolPublicContractTest`, `DmtoolMutationSafetyTest`, `PackagedDmtoolJourneyTest`, `CommandRouteEquivalenceTest`) hangs off **`check`**, and `routeExclusivelyHostedTests` excludes its classes from `test` — so a local `:cli:test`, however green, cannot fail on them. Its four reviewed `@TempDir` classes overlap their independent packaged-process waits in a task-local pool capped at four; this reduced the measured end-to-end lane from 409.8 s serial to 281 s with the launcher build included (2026-08-09), without deleting, batching, or moving a check in-process. New classes stay serial until they explicitly opt in. This sentence used to read `:interpreter:check :adapter:test :cli:test` and was itself the trap: `mcp` (2026-08-06) left two stale verb-count denominators in that lane and one skill term unadded, and the red went unseen for a day.

> **Why it went unseen is NOT "CI does not run that lane" — CI names it explicitly** (`ci.yml`: `… :cli:test :cli:publicContractTest …`). The actual mechanism is that **nothing had been pushed**: 129 commits sat unpushed, so CI never ran on any of them. Local green was the *only* signal, and the local command omitted the lane. *(Recorded because the first version of this note asserted the CI mechanism from the same observation that fits both — the failure mode the "match the oracle to the CLAIM KIND" rule exists to prevent. The discriminating check was one `grep` of `ci.yml` plus one `git log origin/main..HEAD`.)*

**Root `:test`, `:schemakit:test`, `:interpreter-bridge:check` and `:consistency:check` are lanes too — a `:interpreter:check :adapter:test :cli:check` checkpoint is still not the whole estate.** Root `:test` carries the `validate/laws` accept/reject tier plus the guard tasks it pulls in by `dependsOn`, so the kits' own coverage (`rulekit`/`modelkit`/`core`/`edit` — none of which has its own test source) lives there and nowhere else. `:adapter:test` needs its own invocation (perf lanes); the rest may share one. `:interpreter-bridge:check` carries the read-back mapping plus its purity lint, and `check` rather than `test` is what runs the lint. **`:consistency:check` has the same `check`-not-`test` shape and one trap of its own**: it is a Kotlin Multiplatform module, which registers no `test` task at all, so an unqualified `test` — the spelling CI used — reaches neither its `verifyConsistencyPurity` guard nor any of its tests. Name the module explicitly or it runs nowhere (added to the CI lane 2026-09-12, after a review found the H1 purity guard on no automated lane). **And never FILTER `:consistency:jvmTest` — the whole mirror estate is cheaper than a subset of it:** 119 classes in **2 s**, against 11 s for the same task filtered to two, because the filter buys nothing and the Gradle round trip dominates (measured 2026-09-15). That makes it the cheapest high-yield gate in the repository for any checker change, and the one to run the moment the checker compiles: every mirror is a cross-family grid, so a new family's branch reaching a NEIGHBOUR's fixture shows up here in seconds rather than in the 2m30s merged guard lane. It caught exactly that on 2026-09-15 — a chained semantic-index key newly reported by one family sat in the membership family's silence grid — but only after the slow lane had already failed on it. **Prefer making a lane cheap over deciding whether to run it:** the reason omitting one ever looked attractive is that up-to-date tracking was broken in specific places, and a lane whose inputs are declared costs nothing when nothing it depends on changed.

**A CHANGE TO THE CHECKER'S CHECK PATH RUNS `:adapter:checkerPreparedNodePerfTest` IN THE SAME LANDING (2026-09-18, measured).** `:consistency:check` carries no timing observation at all, and the lanes that own the checker's cost curve live in `:adapter` as opt-in `measurement`-group tasks, so a change to the check path lands with **no cost signal whatever** — and the cheapest high-yield gate above, the whole unfiltered `jvmTest` mirror estate, is a correctness oracle that says nothing about cost. Measured consequence: the cell store landed at 00:15 and made a 200-program plain-Node check **9.5x slower** (129 ms -> 1 231 ms); that survived nine commits and a cold adversarial review the same night, and surfaced only because an unrelated collector's wall time made no sense against a figure published the day before ([the measurements](PORTABLE-CONSISTENCY-RESULTS.md#cell-cost-2026-09-18)). **The growth bounds are not a substitute and cannot be made into one:** the asserted paired ratio *fell* from 6.42x to 5.75x while the absolute cost rose 9.5x, because a large linear addition depresses a ratio. So the trigger is the change, not a suspicion: the check path means the cell store, the fact reads, a per-model derived value, or the dispatch schedule. One lane, 3m07s, and it PRINTS the per-check median whether or not it asserts on it.

## The run budget — targeted by default, one scoped full run per session

**Inner loop: run TARGETED tests, not the full suite, for each minor change (standing requirement, 2026-06-24).** The full estate (+ `scripts/verify-demos.sh`, which rebuilds `installDist`) takes **>1 min** and slows development when run after every small edit. While iterating, run a **single test class** — `./build.sh :adapter:test -Pfast --tests "<FqcnOrPattern>"` (one `*DiffTest`/fuzz class is ~3–7 s), or `:interpreter:check` alone when only `:interpreter` changed. Reserve the **full suite + `verify-demos.sh`** for the **session-end checkpoint — ONE run, scoped to what changed**; the budget and its scoping rule are item (5) of the differential-loop list below, and **they govern ALL work, not only differential work**. **A session with N commits does NOT earn N full runs** — commits land on targeted green, and the single end-of-session run is what catches cross-cutting regressions. (`verify-demos.sh` is additionally gated on a verb's output shape/behavior/diagnostics changing — otherwise skip it. **Decide it by grep, and grep for the right thing:** `grep -rln '<verb-or-operator-id>' examples/*.md`. For a **catalog** edit the target is the **operator id, not the verb** — `examples/cli-tour.md` pins `meaning` *and* `gotchas` verbatim for `And`, `AllFieldsFilled`, `LessThan`, `DifferenceInDays` through `rule explain`, so the word `operators` appears nowhere in the demo that would drift; `examples/cli-discover.md` separately pins the operator **count**, so adding or removing an operator drifts it while editing one operator's prose does not. **Two triggers that do NOT look like an output change and drifted a demo twice on 2026-08-22:** editing a **`schema` property DESCRIPTION** drifts `examples/cli-discover.md`, which pins whole `schema result` blocks verbatim — a description is output; **adding an `RkCode`** drifts the same file, which pins the `diagnostics` **count**; and **appending a [KERNEL-FINDINGS](KERNEL-FINDINGS.md) entry** drifts the derived `docs/OPERATOR-INDEX.md`, regenerated with `./build.sh :cli:dumpOperatorIndex` and guarded in `:cli:docGuardTest`. None is caught by a filtered `:cli:test`, and `-Pfast` **skips `docGuardTest` outright** — which is why all three shipped red on one day, the third *after* this note was written. **That is why you are not asked to remember this: [`.githooks/pre-commit`](../.githooks/pre-commit) refuses a commit whose staged files can drift a CI-gated doc unless the doc guards' result XMLs are newer than those files, and names the non-`-Pfast` command that fixes it.** It fires on a broad trigger set on purpose — over-triggering costs one ~1-minute run, under-triggering ships red — and it is itself locked, does-fire and does-not-fire, by [`scripts/selftest-precommit-doc-guards.sh`](../scripts/selftest-precommit-doc-guards.sh) through `deliveryGuardTest`. Wire it once per clone: `git config core.hooksPath .githooks` (`scripts/doctor.sh` checks that you did). The list above is kept only to say WHICH edits drift WHICH doc, since the hook can tell you *that* something drifted but not what to regenerate.) *This sentence used to read "right before a commit", which licensed one full run per commit and contradicted item (5); an eight-commit session duly burned ~40 minutes of CPU on 2026-07-25 while staying literally compliant with it.*

**Three habits that quietly manufacture full runs — all three cost the MAINTAINER's CPU, not yours (standing rules, 2026-07-25, from the eight-full-runs retro).**

- **Don't let the report format create demand for runs.** Full-estate totals ("435 classes, 2214 tests, 0 failures") are **not** the proof-of-done and must not be a standing line in a handback — making them one forces a fresh full run after every commit. The honest evidence for a change is **the targeted test result plus the guard task that covers what changed**; the session-end full run is a regression backstop, not the deliverable. Report what you changed and what covers it.

- **Diagnose — and CONFIRM THE FIX — with the narrowest command that can discriminate.** When a full run fails, re-run **the single failing class** to classify it (real regression vs load-sensitive floor) — *never* the whole suite again. A second full run to test a flakiness hypothesis spends minutes to learn what one class answers in seconds. **The confirmation half is the one that gets missed, because it arrives disguised as diligence: a red full run does NOT create a debt for a green one.** That run already reported every other class as passing, and only your fix's BLAST RADIUS can invalidate it — so ask what the change can actually reach. A test-lane exclusion, a one-class fix, a doc or comment edit reaches nothing the prior run covered, and re-running 2700 tests to re-confirm 2695 of them is the budget smell below wearing a safety label. *(2026-08-15: a new script guard was routed into two lanes and failed 5 of 2712 in the lane that supplies no system property. Fixed in one line and verified twice — green in its owning lane, absent from the broad lane's filter — then a second full six-minute suite was launched anyway, purely on the feeling that a red run owed a green one.)*

- **NAME THE OPEN QUESTION BEFORE YOU RUN ANYTHING — and if the answer is already in this conversation, you have it (standing rule, 2026-08-24, from the three-wasted-runs retro).** The tell is not enthusiasm for testing; it is *when* the urge fires. All three wasted runs that day were launched **while composing a report**, never while genuinely uncertain: a 5m36s `:adapter:test` to confirm a one-file fix whose other 549 classes the previous run had already printed green; a `:cli:check` (load 23 on 8 cores) for a "session-end checkpoint" whose cli-side guards were green in an evidence table already on screen; and two more builds to *demonstrate* a guard whose 15 selftest checks had just passed. So the failure is not caution, it is **refusing to credit evidence you already hold the moment you are about to assert something**. Before every command: state the question it answers. If you cannot state one, or the answer is already above, do not run it — write the sentence from the evidence you have. All three classes are judgement, and deliberately so. Class 1 (a lane the diff cannot reach) was mechanised in a `scripts/lane-guard.sh` that refused the documented inner loop, `perf.sh bench` and the pre-commit hook's own prescribed fix command; it was unwired the night it landed (2026-08-24) and deleted on 2026-09-12, having changed nothing in nineteen days while three surfaces went on describing it as live. **A budget guard is not worth a false refusal**, because over-refusing gets the guard switched off and costs the trust that the correctness guards also run on — which is the asymmetry that makes this class different from a leak scan or a golden. The durable answer is to make the lane cheap rather than to forbid it: the warm root fast lane is **0.69 s** and [the Gradle selection guard](../gradle/focused-test-selection.gradle) refuses the one footgun that a price cannot fix, a filtered broad `test` silently paying for every prerequisite.

- **A run over ~1 minute gets a <5-second precondition check first (standing rule, 2026-08-24).** Roughly 33 minutes were lost in one session to two preconditions nobody checked: three anchor-capture gate runs discarded because a stray uncommitted doc edit stamped them `-DIRTY` (one `git status` would have caught it), and three GraalVM diagnostic runs that measured nothing because `-Dfoo` sets a property on the Gradle daemon and never reaches the **forked test JVM** (one 5-second probe would have caught it). Ask what would make this run worthless, then check exactly that — cheaply — before spending the minutes.

- **Treat "more testing" as a budget smell, not a safe default.** The broader run is never criticized on thoroughness, and its cost lands on the maintainer while the reassurance accrues to you. Whenever the cautious-looking option spends someone else's budget and cannot be faulted, that asymmetry is the signal to stop and pick the cheap one.

**Differential-work loop discipline (2026-07-24, from the G1 retro — the tax is the guard `dependsOn`, not compile OR execution).** A `:adapter` differential class compiles+executes in **~5–8 s** in isolation, yet `./build.sh :adapter:test --tests "<Class>"` takes **~1m40s** — because `:adapter:test` declares `dependsOn` on `corpusReplayTest` + the footprint/performance/profile fixture guards, and `--tests` filters only the test task, NOT its dependencies. An `:interpreter` edit re-runs those guards (corpusReplayTest replays the whole committed corpus THROUGH the interpreter; the fixture guards fork kernel JVMs) — ~1m33s of them. **`./build.sh -Pfast :adapter:test --tests "<Class>"` drops those guard prerequisites → ~8 s** (measured), reserving them for the checkpoint full run (no `-Pfast`; CI unchanged). Kotlin incremental compile + the build cache both work (a 1-file test edit recompiles in ~1 s; an `:interpreter` ABI change recompiles the adapter test set in ~2 s), so compilation is NOT the bottleneck. So: (1) **design the full probe matrix before the first run**; (2) **characterize divergences from the tri-check's own failure message** (`kernel=… interp=…`), never a println-then-rerun pass; (3) **batch edits and desk-check compilability**; (4) **iterate the FIX against `:interpreter:jvmTest` (~5 s, no kernel/guards); use the differential to characterize + confirm**; (5) **one full `:adapter:test` per session, at the end — scoped to what changed** (this is the project-wide full-run budget, not a differential-work-only rule — the "Inner loop" paragraph above defers to it): an interpreter/main-source change gets the full estate (guards + corpus replay); a session that changed only tests/docs/skill gets `-Pfast` + the affected guard tasks instead — with no main-source change the corpus replay and fixture guards cannot produce new information (~9 min saved, measured 2026-07-24). Independent items may land mid-session on `-Pfast` green, but if the final full run fails, fix forward before handing back; (6) the big estate's evidence standard is **verified-fresh** (result XMLs fresh, `skipped="0"`, task executed not UP-TO-DATE), not `--rerun-tasks`-forced — a source change already invalidates the task; keep `--rerun-tasks` for the doc-reading guards and review-gate re-runs, where the false-green risk is real.

## Performance measurement — isolation is part of the observation

**A new test must not perturb timing-sensitive floors that share its task (2026-07-25).** Hoist codegen, in-memory compilation, and model loading to **lazy class fields** instead of repeating them per case. A per-case regeneration in one new differential class inflated `CharsetPerfTest`'s median N/4N growth ratio to **10.24× against its 9.0× catastrophe floor** — failing a class it never touched, and reading exactly like an unrelated perf regression (it passed in isolation, which is the tell). The existing "codegen is primed out of every timed region" rule covers *perf* tests; this extends it to **any** expensive test sharing a task with a timing assertion.

**ISOLATION IS A PRECONDITION TO CHECK, NOT A STATE TO ASSUME — one `uptime` before the run (2026-09-18, measured).** The rule below forbids running anything *of yours* beside a perf lane, and that is the half you control; the machine can still be busy with something else entirely, and then the lane reports a number about the load. Two runs were wasted that way in one session before the check was made: `uptime` read **9.01 / 7.63 / 6.36** on an 8-core M1 eight minutes after the last build of mine had finished, and `top -l 2 -o cpu` named the owners — `corespotlightd` at **85 % CPU** with 66 hours accumulated and a Webex helper at 47 %, with the machine also swapping (5.3 GB compressor, 140 MB unused of 16 GB). So: **`uptime` first, and if the 1-minute average is not near idle, do not start the lane** — check `top -l 2 -n 8 -o cpu` for the owner and say so rather than measuring. `ps -o %cpu` is NOT that check: its column is a process LIFETIME average, so summing it produced "599 % total" on a machine that was 49 % idle.

**The tell in the OUTPUT, for when the check was skipped: a p95 that moved and a minimum that moved with it.** Contention inflates the tail first, so a lane whose median drifted but whose p95 exploded was contended — the checker's Node arm printed p95 **1 011 ms against 377 ms** an hour earlier on identical code, with its minimum worse too. A change in the minimum is the discriminator: real work added to every call moves the floor, while a contended run moves the floor only because the floor never got a quiet slot. **Profile SHARES are the instrument that survives this** and are what the 2026-09-18 quadratic finding rests on ([the measurements](PORTABLE-CONSISTENCY-RESULTS.md#quadratic-2026-09-18)) — a frame's percentage of its own run is unaffected by how fast the machine was.

**PERF RUNS ON OPENJDK 21 AND NOTHING ELSE (owner rule, 2026-08-23) — and you do not have to remember it.** `JdkIdentity.requireSupported()` sits on the one seam every timed observation passes through and REFUSES, naming the JVM it found and pointing at the pin; nothing is recorded. The rule is measured, not hygienic: `java_home -v 21` returns the highest-versioned JDK 21, so `brew install openjdk@21` silently displaced GraalVM 21.0.12 as the build JDK on 2026-08-19, and the same commit then measured **105.88 ms** under OpenJDK against **66.07 ms** under GraalVM on the same machine the same day — a breach read as an interpreter regression for a day. Across 91 lanes that swap moved 45 and made 10 *faster*, which no anchor tolerance absorbs. The build JDK is pinned to OpenJDK 21 in [`scripts/gradle-environment.sh`](../scripts/gradle-environment.sh) (GraalVM belongs to `:cli:nativeCompile` via `GRAALVM_HOME`); if you ever see the refusal, fix the toolchain, never the anchors.

**NEVER run anything in parallel with a perf test — a task carrying a timing assertion gets the machine to itself (owner rule, 2026-07-28).** This governs how you *launch* runs, not just how you write tests. `:adapter:test` carries performance/profile lanes, so it must be its **own** Gradle invocation: never `./build.sh :interpreter:check :adapter:test` in one command, and never a second build, demo script, native build, or eval alongside it. Concurrency does not have to be extreme to corrupt a wall-clock observation — pairing the browser gate (Chrome + Vite) with `:adapter:test` once pushed `CharsetPerfTest`'s then-wall-clock grapheme growth ratio to **9.37× against its 9.0× floor**, a 4 % overshoot that passed instantly on re-run in isolation. Sequence the lanes instead: `:adapter:test` alone, then everything else.

> **The rule covers REMOTE dispatch too — `gh workflow run` ×N is not isolation just because each job gets its own VM (2026-08-11).** Hosted runners are VMs on shared physical hosts, so concurrent jobs of your own evict each other's cache lines and consume each other's memory bandwidth. That is spent in **user-mode** cycles, so the CPU clock does not filter it and neither would `getCurrentThreadUserTime` — a finer clock is never a substitute for isolation. Three concurrently dispatched nightly-gate runs of one commit differed by **1.94×** at the whole-run level, ordered monotonically by their gate wall times (`6m37s / 9m27s / 11m57s`), which made the hosted runner class look far noisier than any evidence supports and stalled an anchor decision on a number that measured only the dispatch pattern ([IF280](INTERPRETER-FINDINGS.md#if280), [INTERPRETER-PERFORMANCE-RESULTS](INTERPRETER-PERFORMANCE-RESULTS.md) "Checkpoint 2026-08-11"). Dispatch one run, wait for it, dispatch the next. Saving wall time by fanning out is exactly the trade this rule exists to refuse.

> **Extended to the sub-quadratic growth gates 2026-08-10.** The nightly gate failed on `MSC-multi-star-correlation` at a median **9.11×** against the 9.0 floor, and the same commit had **passed one night and failed the next two** — the signature of contention, not drift. `PerfHarness.measureCurrentThreadCpu` already existed and its own doc already said "use it for CPU-work ratios and **growth floors**"; the 17 `PerfGateTest` call sites had simply never been migrated. They now route through `timeInterpreterCpu`; `timeInterpreter` is unchanged for its other 11 call sites, including `KernelEdgeTest`'s cross-engine comparisons, which stay wall-clock by the rule below. Measured after, **on the local 8-processor machine**: all **18** growth observations land in **4.00×–5.99×** (`MSC` 4.74×, `B1-per-row` 5.54× and 4.21×), against linear ≈4 and n·log n ≈4.65. *(Both halves qualified 2026-08-11 by three same-commit runs of the real 2-processor hosted runner: that envelope is a property of the MACHINE, not of the migration — on CI the same 18 lanes spanned **2.48×–7.98×**, so the closest lane sat at 89 % of its 9.0 floor and the re-measure-on-breach median is what stands between that and a false red. `FVNU-uniqueness` therefore cannot serve as the stability control the original claim rested on: it spanned **3.94×, 5.85×, 6.10×** there, a 1.55× spread, so "it barely moved" was one pair of samples from a quantity that is noisy on CI. **Caveat on these three numbers:** those runs were dispatched concurrently, which contends them against each other (see IF280) — the interleaved N/4N paired estimator protects a within-pair ratio from slow drift, so a growth figure survives that better than an absolute one does, but the clean values are the sequential re-measurement's.)*

>

> **Algorithmic-only exception adopted 2026-08-03:** `CharsetPerfTest` and `CustomTypePerfTest` now measure current-thread CPU time (`ThreadMXBean.getCurrentThreadCpuTime()`), because their factor/growth floors assert single-threaded CPU work rather than user latency. A full isolated `:adapter:test` had still scheduled these classes beside other test forks and produced a **10.22×** BMP elapsed-time growth result; the focused class passed, and the unchanged full estate passed once the observation excluded time outside the measuring thread. Multi-fork scheduler contention is the basis for the correction; the measurements establish that the excess was elapsed time, not interpreter-thread CPU work. This exception does **not** convert cross-engine throughput or user-facing latency bars: the ratified 250 ms browser first-answer median (IF225) remains wall-clock because that is what a user experiences, and Node/Chrome expose no per-thread CPU time. It also does not relax the launch-isolation rule above for the rest of the adapter performance estate.

## Evidence — what a green actually proves

**NEVER store data that must survive under `build/` — it is gitignored and `clean` deletes it (owner rule, 2026-08-11).** A `build/` tree is for *derived output*: something a later run regenerates. A **record** is the opposite — it is read back *across* runs, so putting it there destroys the only thing that makes it valuable. This is not hypothetical: the performance gate wrote every measured median to `adapter/build/perf-observations.jsonl`, so the estate could compare a run against one committed anchor but **never against its own history**, because the history was on a deletion schedule. Records now live in the committed, text-only [`perf-results/`](../perf-results/README.md) tree, one JSON-Lines file per run, each carrying the conditions it ran under (environment, JDK, processor count, load average per observation, CI run id) because the same commit measured on a busy laptop and on a 2-vCPU hosted runner are not comparable numbers. **The rule is enforced, not advised:** `SurvivingDataNotInBuildGuardTest` fails on any source-level path under `build/` that is not declared transient *with its reason*, and it also asserts the allowlist stays fully used so it cannot decay into a blanket exemption. Two ways to satisfy it — write to a committed directory, or declare why losing the file is harmless.

**A test-result XML is NOT evidence of the run you just did — result files PERSIST, and `--tests` only refreshes the classes it matched (standing rule, 2026-08-15).** [`scripts/obligations.sh`](../scripts/obligations.sh) now names a red XML before you commit, with its age, because this rule was written down and then broken by its own author within the day; the reasoning below is what the script cannot carry. Gradle writes `build/test-results/<task>/TEST-*.xml` per class and never clears the directory, so after `--tests "*Foo*"` every other class still carries its XML from whenever it last ran. A directory scan therefore silently **mixes runs**, and the mix is invisible: the stale files look exactly like fresh ones. This produced a wrong conclusion twice on 2026-08-15 — a fixture-mutation sweep read 17 "still passing" classes that had simply not been re-run, and the same habit nearly turned a partial API dump into a "drifted" verdict. Three rules, all cheap:

- **Run [`scripts/test-evidence.sh <log>`](../scripts/test-evidence.sh) instead of eyeballing the log.** It prints each test task's real state and counts only the XMLs this run wrote *for a task it executed*, withholding the rest, which is the whole check in one command. **Do not reuse a log path and then trust a timestamp yourself:** `>` truncates rather than creates, so the file keeps its original birth time — that is how a 6-second run was credited with 2016 tests on 2026-08-31. Failing that, `rm -rf build/test-results/<task>` before a run whose XMLs you will read — deleting costs nothing and removes the class.

- **A perf lane's FIGURES survive only in the result XML, and repeating the lane overwrites both carriers (measured 2026-09-17, two runs wasted).** `PerfHarness.progress` writes a tailable `adapter/build/perf-progress.log` that is truncated once per JVM, and Gradle buffers the same line's `println` into `build/test-results/<task>/TEST-*.xml` — which is per task, not per run. So N sequential invocations of one lane leave exactly **one** set of figures: the last. This is the shape reproducibility work needs most and breaks first, because the whole point is N independent estimates. **Capture after each run, not after the batch:** `grep -ohE "\[<lane-tag>\][^<]*" adapter/build/test-results/<task>/*.xml >> <somewhere outside build/>` between invocations. Redirecting each run's Gradle log does NOT save you — the measurement line is captured test stdout and is not in it.

- **Read the task line, not just `BUILD SUCCESSFUL`.** `> Task :test` executed, `UP-TO-DATE`, and `FROM-CACHE` are three different claims. A cache hit on byte-identical inputs is a *valid* green; a green you assumed was a fresh execution is not.

- **When a parse of build output surprises you, suspect the parse first.** The same day, a regex over an assertion message stopped at the first `>` inside a generic and reported an empty API surface as "drift". Before acting on a surprising build result, re-derive it a second way.

**"No case changed" after a semantics fix is a FINDING, not a relief (adopted 2026-09-05 from a12-kernel-lean's `LF146`; their measurement, not ours).** It means one of two things and both need saying out loud: the fix was vacuous, or the shape it fixed was never covered. Their instance is the sharper half of the argument, and it is about what our instruments structurally cannot see. An **under**-admission leaves a wrong answer in the estate — a case fails, a sweep of the conjunct's siblings finds it, a differential shows disagreement. An **over**-admission leaves only a *missing refusal*: no case fails, because the wrongly accepted model is well-formed by the estate's own account; no sweep finds it, because there is nothing at all where a test should be; and **a differential cannot reach it, since the model the kernel rejects never runs, so there is no execution to compare.** The instrument that worked was an outside party reasoning from a description of the shape — which works precisely because it runs nothing.

Two cheap detectors follow. **For any gate whose legality depends on a declared format, enumerate the formats and ask what the gate says about each** — theirs said nothing about eleven of twelve. And the shape that hides an over-admission is a **combination of two independently legal declarations**, which neither estate forms because neither has a reason to: the `DG51` shape we found in this repository on the day the class was named in theirs is exactly that ([KF251](KERNEL-FINDINGS.md#kf251) enumerated it: two config axes, twelve formats, and the two gates read the format differently).

**A NEW lock class must be `git add`ed before the doc guards can see it (measured 2026-09-05, twice in one session).** `Checkout.testSources()` enumerates **tracked** files, so `LockCitationResolvesTest` reports a findings-doc citation of a brand-new `*Test` as "a test class that does not exist" — a failure whose message describes a renamed or deleted class and so reads as a real defect rather than as an untracked file. Staging the file fixes it; `git add` is enough, no commit needed. The order that avoids the round trip is: write the test → stage it → then run the guards. Two sibling requirements land in the same place and are cheaper to satisfy up front, because both refuse before any test runs: every lock class needs a placement in [`SEMANTICS-MAP.md`](SEMANTICS-MAP.md) (`:adapter:verifySemanticsMapRegistration` refuses in ~2 s, `:cli:semanticsMapGuardTest` is the thorough resolver), and a new catalog `corrective` needs its ordered, digest-bound entry in `operator-fix-probes.json`.

## Long runs — capture, launch, and wait

**Capturing a long build/test run: redirect the FULL output to a file, then grep the file — NEVER pipe the build through `tail`/`head`/`grep`.** Use `./build.sh --console=plain <args> > build/run.log 2>&1` then `grep -E 'BUILD (SUCCESSFUL|FAILED)|FAILED' build/run.log`. Two traps a pipe hits (the reason [`scripts/perf.sh`](../scripts/perf.sh) exists, and the rule generalizes to any long run): a pipe **buffers**, so a backgrounded build's log stays empty until it finishes (polling looks frozen and you can't read it incrementally); and `head`/early-closing readers can **SIGPIPE the build and lose its output** entirely. Writing the raw log to a file fixes both — and a backgrounded run can then be `Read` as it grows. (Lesson codified here, not in agent memory, so it travels across machines.)

**The same mechanism bites inside CODE that launches a child, and there it silently disarms the timeout rather than the log.** Every perf lane in `:adapter` that launches a process read the child's whole output into a string and *then* called the timed `waitFor` — so the fuse could never fire, because `readText()` blocks until EOF and EOF arrives only when the child exits. Four sites carried it and the `error(…)` line naming the fuse was unreachable code in all four; a cold review found it on 2026-09-17, in lanes whose timeouts were documented in their own class comments. **And the repair that suggests itself is worse:** wait first, read second, and a child that outruns the pipe buffer blocks in its own `write` while the parent waits for an exit that can no longer come. The fix is the same one this section prescribes for the shell — redirect to a FILE, so the child never blocks and the parent never has to read before waiting. `ChildProcess.runWithFuse` is the shared locus, `ChildProcessFuseTest` locks both halves (a child that never exits must be killed by the fuse; 4 MiB of output must survive whole), and the pattern was already in the package: `ProfileCliPerfTest` had done it correctly all along. Recognising a shell rule as a code rule is the transferable part — this doc said "pipes buffer" for a year while four callers in one package assumed otherwise.

**A run that can exceed ~10 minutes must NOT be a plain backgrounded shell command — agent harnesses cap those** (Claude Code kills a background Bash task at 10 min; the kill mid-run looks like a mystery failure — it bit twice on 2026-07-10). Run it through a mechanism without that cap (in Claude Code: the Monitor tool with a generous `timeout_ms`, emitting only the result line), or split the run into sub-10-minute tiers — one reason the perf suite is two-tiered: `scripts/perf.sh gate` (the fast routine gate, every landing) vs `perf.sh bench` (the slow kernel-ratio benchmarks, perf-relevant checkpoints only); both take an optional method pattern (`perf.sh gate 'semanticIndex*'`) for a ~1-minute single-scenario re-check.

**Past ~30 minutes no single process survives, so the answer is FOREGROUND SLICES — and it needs the work to be resumable (measured 2026-09-16).** Both hosted mechanisms have a ceiling: a Monitor is killed at 30 minutes, and a harness-backgrounded task is killed by a memory watchdog under system-wide pressure, which on a 16 GB machine fired at ~34 % free with nothing large running and killed a capture at nine minutes even after its forked JVM got `maxHeapSize = '1g'`. **A foreground call is not a background task and meets neither limit**, so a 38-minute run becomes a series of sub-10-minute foreground calls. What makes that legitimate is a property of the work, not of the harness: the slices must accumulate into the same result (the native capture's `config-merge-dir` merges, so slicing yields the union) and the record of what has been done must be written **only after a slice completes**, so a timeout costs that slice's work and never corrupts the accounting. Where the work is not resumable, slicing is not available and the run belongs to the owner with the machine quiet. Worked example, with its completeness gate: [NATIVE-IMAGE-GRAALVM](NATIVE-IMAGE-GRAALVM.md#capture-slices) §5.2.

**Launch every long run through a HARNESS-MANAGED background mechanism — NEVER a hand-rolled `setsid`/`nohup`/`&` detach inside a tool call (standing rule, 2026-07-12).** The harness runs each tool invocation in its own process group and reaps that group when the call returns, so a child you background yourself dies (or is silently orphaned) the instant the tool call returns — the build never actually runs. Use the Bash tool's own `run_in_background` (harness-tracked; notifies on completion; readable incrementally — but still ~10-min-capped) or the **Monitor tool to *run* the command itself** (not to watch a separately-detached process), with a generous `timeout_ms` — **but only for a run that fits inside 30 MINUTES, because "generous" has a ceiling and reaching it is fatal (measured 2026-09-16).** Claude Code's Monitor caps `timeout_ms` at 1 800 000 ms however much more is asked for, and expiry does not merely end the watch: it kills the monitor's own process tree, which is the command. So a run longer than that, driven this way, is guaranteed to be killed mid-flight — a 36–38 minute native reflection capture died at exactly the 30-minute mark with its log frozen inside `:cli:test` and no metadata written. For anything past that ceiling the command must not BE the monitor's command; detach it (Bash `run_in_background`) and, if a watch is wanted at all, point a separate Monitor at its log; run shorter (<10 min) commands in the **foreground** so their output returns and is visible. The tell that a "backgrounded" run is actually **dead on arrival**: a 0-byte log + idle CPU + a Gradle daemon parked in `awaitExpiration` (`jstack` shows `Daemon.stopOnExpiration`, near-zero cpu) = it never received a build request — **investigate immediately, never keep waiting on a corpse.** (Cost this once: a `setsid …&` corpus sweep was reaped at launch and "watched" for 14 min against an empty log; the fix is `run_in_background`/Monitor, which is exactly why the tiered `:adapter:test` runs worked.) Corollary on visibility: Gradle **block-buffers** to a non-TTY, so `--console=plain > file` shows *nothing* until the buffer flushes — treat an empty log after minutes as a launch failure to diagnose, not "still buffering," and prefer foreground (output returns) or a Monitor that streams filtered progress lines.

**Waiting on a long run: key the poll on the command's TERMINAL marker, not an intermediate `BUILD SUCCESSFUL` (standing rule, 2026-07-12).** A bare `./build.sh` ends at `BUILD SUCCESSFUL`, but a **wrapper script** (`scripts/verify-demos.sh`, `scripts/perf.sh`) runs a Gradle sub-build that prints its OWN `BUILD SUCCESSFUL` *before* the real work — so `until grep -q 'BUILD SUCCESSFUL'` reports "done" mid-run. Grep the script's **final line** (verify-demos: `all N … demos match the live CLI`), never a `BUILD` line. (The two mechanical traps — a hand-detached `&` and a self-matching `pgrep -f` liveness gate — are hard-blocked by a `PreToolUse` hook, [`.claude/hooks/guard-long-run-antipatterns.sh`](../.claude/hooks/guard-long-run-antipatterns.sh) — one file, wired by both harnesses (`.claude/settings.json`, [`.codex/hooks.json`](../.codex/hooks.json)), since Codex sends the same payload fields and blocks on the same exit-2-plus-stderr contract. A harness with neither self-enforces from this rule.)

**Check (2) covers the loop gate as of 2026-09-07.** It refuses the bare command, the `!` form, and — newly — a `while`/`until` gate, which is the canonical spelling of the anti-pattern the check is named for and which slipped through from its first day because the anchor list held no keyword. The list stops at those two on purpose: `do`, `then` and `else` also introduce a command position but precede this string in ordinary English, so anchoring on them would refuse a commit message explaining the guard. Both directions are locked in [`scripts/selftest-long-run-guard.sh`](../scripts/selftest-long-run-guard.sh), which also pins the narrower fact the keyword anchor actually carries: `until ! …` was already caught by the original `!` anchor, so only the bang-less loop gates depend on it.
