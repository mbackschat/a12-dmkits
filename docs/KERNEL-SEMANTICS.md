# A12 Kernel — validation-language semantics

> **Provenance & role in this repo.** Owner-authored in the sibling `a12-kernel-demo` project; integrated here 2026-07-09 so this repo is self-contained — this copy is the one the docs, [SEMANTICS-MAP.md](SEMANTICS-MAP.md), and `SemanticsMapResolveTest` key on. It is the **canonical kernel-truth prose layer**: its 14 numbered sections are the `§n` taxonomy that [KERNEL-FINDINGS.md](KERNEL-FINDINGS.md) (our experiment-verified supplements), the operator-catalog facets, and the conformance corpus's `meta.sections` all mirror. The companion docs it mentions (`KERNEL-GLOSSARY.md`, `SHOWCASE.md`, `KERNEL-GRAMMAR.md`) remain in their origin projects.

A reference to how the A12 validation language *evaluates*, beyond what its syntax shows: its truth model, how it treats missing values, what the "required" property means, and the numeric, date, string, enumeration, repetition, path, and computation rules that determine when a rule fires. The behaviours below are documented in the kernel's *Validation-Language guide*; each entry cites the relevant chapter/section by title. Two claim classes share the page: those guide-documented behaviours, and — in the deepening subsections — behaviours **verified by experiment or source reading against kernel `30.8.1`**, each cited inline as *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §n / IFnn, locked by `SomeTest`)*; a claim without such a citation is the guide's.

Two facts frame everything else:

- **A rule states the *error* condition — and that polarity is fixed.** Its condition is written so that `true` means the data is invalid. `FieldNotFilled(CustomerName)` is the rule "the customer name is missing." No slot or configuration flips this: the rule's single condition slot is `errorCondition`, severity is message metadata ([§12](#12-the-validation-model)), and there is no assertion/requirement form — so a requirement must be authored as its *violation*, and a positively-written requirement is structurally valid but encodes the opposite rule, a mistake the kernel cannot catch *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) "Rule-condition polarity is fixed")*.
- **Rules and computations share one language and operator vocabulary**, but a consumer-specific clause can differ—for example validation tallies unavailable cells while a computation scan poisons when it reaches one.

**Scope:** this covers how the *validation language* evaluates. The developer/runtime side — the `DocumentV2` API, the `validateFull`/`validatePart` call surface, mapping, code-generation targets, and model include/expansion — is out of scope except where it changes evaluation (touched in [§12](#12-the-validation-model)). Authoring/grammar pitfalls (path syntax, keyword-name escaping, `Date()` operand formats) live in `KERNEL-GRAMMAR.md`.

For the vocabulary used here, see `KERNEL-GLOSSARY.md`; for runnable demonstrations, `SHOWCASE.md` (both in the origin `a12-kernel-demo` project).

## The field types at a glance

Which operators are legal on a field, and how a missing or mismatched value behaves, depends on the field's **type** — so the type model is worth holding in mind before the per-topic rules below. The kernel defines these field types (the interface names are the public `kernel-md-model-api` `fieldtypes/I*Type`):

| Field type | Variants / key config | `[Field]` yields | Special meaning for evaluation |
|---|---|---|---|
| **String** | `pattern`, min/max length | string | `Length` counts Unicode combining sequences as several characters; a `pattern` requires an accompanying error text; the basis for `Custom`. |
| **Number** | **scale** = max fractional digits; min/max value; `trait` = amount / percent / permille | number | Scale **gates `==`/`!=`** (mismatched scale is a *parse-time* error — round one side first); an unspecified number is substituted with **`0`** in comparisons (but *ignored* by min/max); orderable with `< > <= >=`. |
| **Boolean** | True / False / unset | boolean | Three states; an unspecified value leaves a comparison **not evaluated**; compares only to `True`/`False` or another Boolean; `[F] == True` is **not** the same as `FieldFilled(F)`. |
| **Confirm** | True / unset (a checkbox) | confirm | Distinct from Boolean: an unspecified value is treated as **`False`** in comparisons; compares only to another Confirm or the constant `True`. |
| **Enumeration** | `values`; *with* or *without* localized **texts**; **categories** | enum value | Compared by the **stored value**, not the display text (`[Country]=="F"`); direct field comparability uses the **effective display remapping**, so absent and identity-only labels are textless while a real remapping is display-bearing; `->` reads a value's **category** attribute. |
| **Date** | `format`; `datePrecision` = full / day- / month- / year-optional | date | Constants are `DD.MM.YYYY` (day-first); a **string literal matching that format parses as a date** (so it breaks string concatenation); precision gates `DayFromDate`/`MonthFromDate`/… and `ValueAsDate`. |
| **DateTime** *(extends Date)* | — | date-time | The required operand for `DifferenceIn{Hours,Minutes,Seconds}`, `Add{Hours,…}`, `*FromTime`, and `Now`. |
| **Time** *(extends Date)* | — | time | The operand for `HoursFromTime` / `MinutesFromTime` / `SecondsFromTime`. |
| **DateFragment** | `formatOfFragment` = `MM` / `yyyy` / `yyyy-MM` / `MM-dd` | partial date | A deliberately *imprecise* date; comparable only by the **year-presence rule** (or globally via a model **Base Year**); the fragment format decides which `Add*` apply. *(Editor: import-only.)* |
| **DateRange** | `format` (`MM` … `yyyy-MM-dd`); separator `/` | date-range | Supports only `==` / `!=` (**no ordering**); a `DateRange(...)` construction may be a comparison operand but not a nested overlap/bound-extraction operand; `DateRangesOverlap` treats endpoints as inclusive. |
| **Custom** | `name`; min/max length | string-equivalent | Treated as a **string** in rule conditions; `Valid(F, "Name")` / `Invalid(...)` runs the project's registered validator for that custom type. A declared Custom field's **whole** formal check — length bounds included — is delegated to that validator (the bounds are hints); with none registered, a *filled* custom cell fails the entire validation call. |
| **TypeDefinition** | references a reusable type definition by id | the underlying type's value | **Delegates** to the referenced type — its legality *is* that underlying type's, and is known only after the model is **expanded** (includes/type-defs resolved). |
| **Unspecified** *(experimental)* | — | — | Documented as "not a data type" — an intermediary/decoration, not used as a rule operand. |

*Reference: Models → Field types; Constants and data types; Operators and language constructs → Comparison operations. Interfaces: `kernel-md-model-api` `fieldtypes/I*Type`. The per-type evaluation details are expanded in the sections below (numbers §5, dates §6, strings §7, enumerations §8).*

## 1. Truth values and logical evaluation

### Two-valued connectives over data that can be "unknown"

The logical operators `And` / `Or` and the predicates are two-valued: a condition is satisfied or not. However, the *data* a condition reads can be in a third state — **unknown** — when a field carries a formal error (see [§4](#4-the-required-property) and [§12](#12-the-validation-model)). A field in that state cannot be evaluated by any rule. The logic itself never produces a third value; "unknown" instead makes each operand that reads the field undecidable, and the ordinary `And`/`Or` algebra decides how far that reaches — branch-scoped, not rule-scoped ([§3](#3-formal-errors-and-the-unknown-state)) *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §3, locked by `FormalErrorScopeLawsTest`)*.

*Reference: Operators and language constructs → Logical operators; Appendix → Validation and formal validation → Formal errors.*

### `And` / `Or` require explicit parentheses when mixed

There is no implicit precedence between `And` and `Or`. A condition that mixes them without brackets is a parse error (`MVK_BRACKET_MISSING`), not a default grouping.

```
( FieldFilled(A) And [A] <= 0 ) Or FieldNotFilled(B)
```

The result differs depending on where the brackets go, so the language requires them rather than choosing for you.

*Reference: Operators and language constructs → Logical operators.*

### Boolean is a three-state field type

A `Boolean` field has three states: not filled, `True`, and `False`.

```
[Flag] == True       ;; satisfied only if Flag is filled AND its value is True
[Flag] == False      ;; satisfied only if Flag is filled AND its value is False
FieldFilled(Flag)    ;; satisfied if Flag has any value (True or False)
```

Consequences: `[Flag] == True` is not equivalent to `FieldFilled(Flag)`, and `[Flag] == False` does not mean "unchecked" — an unset Boolean satisfies neither `== True` nor `== False`.

*Reference: Models → Field types → Boolean.*

### `Confirm` and `Boolean` treat an unspecified value differently

For a `Confirm` field (a checkbox with the single value `True`), an unspecified value is treated as `False` in comparisons. For a `Boolean` field, an unspecified value leaves the comparison *not evaluated* (see [§2](#2-non-specified-empty-values)). The same comparison form therefore yields different results depending on the field type.

At the stored-value tier the split repeats: a boolean's value token is lowercase `true`/`false` — any other token is a formal error ([§3](#3-formal-errors-and-the-unknown-state)) — while a confirm accepts only `true` or unspecified; a stored `false` on a confirm is itself a formal error, consistent with "a checkbox whose single value is True". **The token set is literally `true`/`false` on every A12 DocumentModel — a model that declares its own tokens (`BooleanType.notInDCustomTrueValue`) does not move this check, measured — and the comparison is case-SENSITIVE**, so `TRUE`/`True` on a boolean and `TRUE` on a confirm are formal errors too. Two neighbouring layers *are* case-insensitive and must not be read back into this one — JSON ingress normalizes `"TRUE"` to `true` before the value is stored, and comparing an already-stored value is case-insensitive — so a stored token reaches this check unnormalized only when a caller fills a document directly. Note the further distinction from the **condition** tier, where the comparison literal is the capitalized `True`/`False`: three tiers, three casings. "Not confirmed" is written `[Confirm] != True` *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §1 + §2, locked by `BooleanConfirmLawsTest` + `EmptyValueLawsTest` + `BooleanTokenFormalDiffTest`)*.

*Reference: Models → Field types → Confirm; Models → Treatment of non-specified values.*

### There is no generic negation operator

The language has no `Not`. Each negative check is a dedicated predicate with its own evaluation logic, so that conditions stay simple and the language need not define negation over the "unknown" state. The positive/negative pairs are not always logical complements:

- `NotAllFieldsFilled(L)` is satisfied when **at least one** field is known empty — including the all-known-empty case.
- `FieldsNotCollectivelyFilled(L)` is satisfied when at least one field is known filled and at least one is known empty (it excludes the all-empty case).

```
NotExactlyOneFieldFilled(A, B, C)   ;; satisfied for 0 filled with no unavailable cell, AND for 2+ filled
```

Choosing the wrong member of a pair changes which documents the rule reports.

*Reference: Preface → Kernel Language; Predicate language constructs for Field lists.*

### How the fill quantifiers count — group scopes and the two iteration ranges

- **A group operand means "the fields inside the group", recursively.** A field-fill quantifier over a group expands to a field-list quantifier over every descendant field, through nested subgroups; a repeatable group in the operand carries its `*` onto each descendant, and a mixed group+field operand list is legal *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §1 / [IF49](INTERPRETER-FINDINGS.md#if49), locked by `GroupScopedFieldFillDiffTest`)*. A **value aggregate** (`Sum`, `MinValue`, `MaxValue`, `NumberOfDifferentValues`) over a starred group expands the same way — every contained field's values, recursively *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §1 / [IF99](INTERPRETER-FINDINGS.md#if99), locked by `GroupStarValueAggregateDiffTest`)*.
- **Two iteration ranges over a starred scope.** `AllFieldsFilled` and `NotAllFieldsFilled` walk the **full declared range** — up to the group's `repeatability`, an un-instantiated repetition reading *empty* — so `AllFieldsFilled(G*)` holds only when every *declared* repetition is filled. `AtLeastOneFieldFilled`, `NoFieldFilled`, `MoreThanOneFieldFilled`, and `NotExactlyOneFieldFilled` clamp to the **instantiated** rows. `FieldsNotCollectivelyFilled` mixes the two (≥ 1 filled over the instantiated rows AND ≥ 1 empty over the declared range). On a non-repeatable scope the ranges coincide *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §1 / [IF49](INTERPRETER-FINDINGS.md#if49), locked by `GroupScopedFieldFillDiffTest`)*.
- **The group quantifiers admit a starred single group only for the count-zero / count-≥1 members.** `NoGroupFilled(G*)` and `AtLeastOneGroupFilled(G*)` count the group's **instantiated repetitions** — a created-but-empty row counts as a filled group (a row is content, [§9](#9-repetition-iteration-and-cross-array-evaluation)); a fired `NoGroupFilled(G*)` at zero rows types OMISSION, a fired `AtLeastOneGroupFilled(G*)` VALUE. That structural count applies when the **terminal itself is repeatable**: for `A*/B*/C` with non-repeatable `C`, the stars select complete ancestor environments and each `C` contributes its ordinary admitted-content × error × relevance group state instead. The `AllGroupsFilled` / `NotAllGroupsFilled` / `GroupsNotCollectivelyFilled` family rejects the asterisk *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §1/§9 / [IF68](INTERPRETER-FINDINGS.md#if68) + [IF46](INTERPRETER-FINDINGS.md#if46) + [IF193](INTERPRETER-FINDINGS.md#if193), locked by `StarredGroupQuantifierDiffTest` + `NonRepeatableGroupBelowStarDiffTest` + `GroupQuantifierLawsTest`)*.
- **The FIXED group-list quantifiers consume one common field-or-group entity list.** Despite their names, all five fixed forms admit BOTH field and group operands: a checked **field** contributes filled / empty / unavailable (formally invalid or not check-relevant) directly, a **group** contributes the [§9](#9-repetition-iteration-and-cross-array-evaluation) product state (admitted content × error × relevance). Direct duplicates and group/descendant overlap are rejected. The `AllGroupsFilled` / `NotAllGroupsFilled` / `GroupsNotCollectivelyFilled` family requires **more than one** operand and rejects root groups and wildcards — a starred field operand included. `NoGroupFilled` and `AtLeastOneGroupFilled` admit a **singleton**, including a sole root group (rejected beside another operand); a fixed singleton has exactly the scalar field/group presence semantics *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §1, locked by `GroupListEntityOperandLawsTest` + `GroupListEntityOperandDiffTest` + `GroupListFieldOperandTest`)*.
- **Validation and computation consume invalid cells differently.** In an unfiltered validation tally, a present-but-invalid cell ([§3](#3-formal-errors-and-the-unknown-state)) remains in the selected range but is neither filled nor empty. In computation, an invalid cell reached by an ordered scan poisons the computation; a cell after the complete predicate's final stop is unread. Any invalid element reached by a value aggregate makes that aggregate non-evaluable *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §1 + §3 + §11 / [IF84](INTERPRETER-FINDINGS.md#if84) + [IF85](INTERPRETER-FINDINGS.md#if85), locked by `ValidationFillQuantifierProjectionDiffTest`, `StarQuantifierInvalidCellDiffTest`, `ComputePoisonReadDiffTest`, and `ComputationFillQuantifierScanContractTest`)*.

For **unfiltered validation**, let `t` be known-filled instantiated cells, `e` known-empty instantiated cells, `u` formally unavailable instantiated cells, and `d` declared-but-uninstantiated omissions. An unavailable cell contributes to the range but to neither `t` nor `e`. A non-firing leaf exposes only the kernel-visible collapsed `FALSE_OR_UNKNOWN`; this contract does not invent a hidden false-versus-unknown distinction. Whole-condition empty-row eligibility and `Having` selection/polarity are separate from this table:

| Validation predicate | Range | Fires when | Unfiltered polarity |
|---|---|---|---|
| `AllFieldsFilled` | declared | `e = 0 ∧ u = 0 ∧ d = 0` | VALUE |
| `NoFieldFilled` | instantiated | `t = 0 ∧ u = 0` | OMISSION |
| `AtLeastOneFieldFilled` | instantiated | `t ≥ 1` | VALUE |
| `MoreThanOneFieldFilled` | instantiated | `t ≥ 2` | VALUE |
| `NotAllFieldsFilled` | declared | `e + d ≥ 1` | OMISSION |
| `NotExactlyOneFieldFilled` | instantiated | `(t = 0 ∧ u = 0) ∨ t ≥ 2` | OMISSION in the zero-filled region; VALUE in the at-least-two region |
| `FieldsNotCollectivelyFilled` | instantiated fill plus declared empty | `t ≥ 1 ∧ e + d ≥ 1` | OMISSION |

For an **unstarred fixed entity list**, let `pₜ` be definitely filled operands, `pₑ` definitely empty operands, and `pᵤ` operands in neither bucket. A checked field is definitely filled when it has an admitted value, definitely empty when cleanly empty, and unavailable when formally invalid or not check-relevant; a group operand classifies by its [§9](#9-repetition-iteration-and-cross-array-evaluation) product state. The five group-list quantifiers consume that common tally without treating unavailable as empty — a decisive witness fires beside an unavailable sibling:

| Validation predicate | Fires when | Unfiltered polarity |
|---|---|---|
| `AllGroupsFilled` | `pₑ = 0 ∧ pᵤ = 0` | VALUE |
| `NoGroupFilled` | `pₜ = 0 ∧ pᵤ = 0` | OMISSION |
| `AtLeastOneGroupFilled` | `pₜ ≥ 1` | VALUE |
| `NotAllGroupsFilled` | `pₑ ≥ 1` | OMISSION |
| `GroupsNotCollectivelyFilled` | `pₜ ≥ 1 ∧ pₑ ≥ 1` | OMISSION |

The plain numeric `NumberOfFilledGroups(g1, g2, …)` is stricter than this partial tally: any erroneous or not-fully-relevant operand makes the count unavailable ([§9](#9-repetition-iteration-and-cross-array-evaluation)) — it never consumes the bypass the quantifiers get from a decisive witness.

**Computation** instead uses ordered scans over the expanded field stream. A declared-but-uninstantiated slot is a clean absence, not a value read:

| Computation predicate | Ordered decision |
|---|---|
| `AllFieldsFilled` | Scan the declared range; first empty or uninstantiated slot → false; exhaustion → true. |
| `NotAllFieldsFilled` | Scan the declared range; first empty or uninstantiated slot → true; exhaustion → false. |
| `NoFieldFilled` | Scan instantiated slots; first filled slot → false; exhaustion → true. |
| `AtLeastOneFieldFilled` | Scan instantiated slots; first filled slot → true; exhaustion → false. |
| `MoreThanOneFieldFilled` | Scan instantiated slots; second filled slot → true; exhaustion with zero or one → false. |
| `NotExactlyOneFieldFilled` | Run the `NoFieldFilled` scan first; if it finds a filled slot, restart from the beginning and run the `MoreThanOneFieldFilled` scan. |
| `FieldsNotCollectivelyFilled` | Run the instantiated `AtLeastOneFieldFilled` scan first; if it finds a filled slot, restart from the beginning and run the declared-range `NotAllFieldsFilled` scan. |

Every invalid slot reached by these computation scans poisons the instance. Each component scan stops independently; the two composites deliberately restart their second scan and remain bounded by two linear passes. Only a suffix after the full predicate's final decision is unread *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §11 / [IF85](INTERPRETER-FINDINGS.md#if85) + [IF147](INTERPRETER-FINDINGS.md#if147), tri-engine locked by `ComputationFillQuantifierRestartDiffTest` + `BareGroupComputeExactnessDiffTest`, with exact JVM+Node traces in `ComputationFillQuantifierScanContractTest` and filtered formal classification in `FilteredStarComputeFormalInvalidityTest`)*.

## 2. Non-specified (empty) values

How an unspecified field affects a comparison depends on its **type**:

| Field type | Unspecified value in a comparison |
|---|---|
| number | a default of `0` is substituted |
| confirm | treated as `False` |
| boolean, string, enumeration, date, time, date-time | the comparison is **not evaluated** (no error) |

Other model types — such as date-fragment, date-range, and custom fields — have explicit type-family or registered-validator clauses; this primitive header does not silently define their empty behavior.

```
[Amount] < 100      ;; number: fires on an EMPTY Amount, because 0 < 100
[Date] > "01.01.2022"   ;; date: does NOT fire on an empty Date (not evaluated)
```

To avoid reporting an error on an empty number field, guard it:

```
FieldFilled(Amount) And [Amount] < 100
```

Two further points:
- The `0` substitution does **not** apply to minimum/maximum calculations — there, unspecified fields are ignored.
- There are no empty strings: `[F] == ""` is never satisfied, even when `F` is unfilled — and neither is `!= ""`: a string comparison with an **empty operand on either side** (a literal `""`, an empty coercion result such as an out-of-range `RangeAsString`) is not evaluated, for `==` and `!=` alike. Use `FieldNotFilled(F)` to test for absence *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) "numeric coercions", locked by `RangeCoercionDiffTest`)*.

*Reference: Models → Treatment of non-specified values; Appendix → Validation and formal validation → Leading and trailing spaces.*

### Why the empty case decides whether a rule is right

A rule spends most of its life reading empty fields — a document is validated continuously during data entry, so "operand empty" is the *normal* state, not the edge case — and the table above means the same comparison shape silently changes meaning with the field's type: `[Amount] < 100` fires on an empty amount, `[Date] > "01.01.2022"` stays quiet on an empty date. Getting the empty column wrong is therefore the most common way a rule is wrong in practice, in both directions (a rule that flags every half-entered document, or one that never fires because its operand type gets the not-evaluated pass). The operator catalog carries these answers machine-readably — the `emptyOperand` facet, with this section's per-kind table as its header defaults — and records the class as the #1 recurring semantic failure ([CATALOG-SPEC.md](CATALOG-SPEC.md) §4).

### Where an operator overrides its kind's default

The per-kind table is only the default; several operators put an empty operand through a different door, so the same field can get the free pass in one position and be evaluated in the next:

| position | an empty operand… |
|---|---|
| string in a `+` **concatenation** | concatenates as `""`, so the enclosing comparison **is** evaluated — `[Full] != [First] + " " + [Last]` mis-fires on empty parts unless the operands are guarded *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §2, locked by `EmptyValueLawsTest`)* |
| `Length(F)` | reads as length **`0`**, evaluated — the string family's own empty-as-0 backdoor, needing the same `FieldFilled` guard as a number *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §2, locked by `EmptyValueLawsTest`)* |
| `PatternMatched` / `PatternViolated` | not evaluated — an empty string violates no pattern; absence needs `FieldNotFilled` *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §2, locked by `EmptyValueLawsTest`)* |
| the date/time **extractors** (`DayFromDate`, …) and the date **differences** | read as the fillable **`0`** — the enclosing comparison is evaluated and can fire *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §6 / [IF73](INTERPRETER-FINDINGS.md#if73), locked by `EmptyOperandFiringDiffTest`)* |
| **value-list membership** | an empty subject makes membership UNKNOWN — *neither* the included nor the not-included form fires — and an empty numeric list *entry* never matches (the `0` substitution does not apply to entries) *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §2/§8, locked by `EmptyValueLawsTest` + `ValueListDiffTest`)* |
| the **count family** (`NumberOfFilledFields`, `NumberOfValueInFields`, …) | an empty cell is never counted — `NumberOfValueInFields(0 In …)` does **not** count an empty number as a match for `0` — but it keeps the count growable, typing a fired comparison OMISSION. **Empty and INVALID are two states here, not one**: an all-empty operand list counts `0` and compares normally, while a single formally invalid operand makes the whole count UNAVAILABLE — neither skipped nor counted ([§3](#3-formal-errors-and-the-unknown-state)) *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md#kf195) §2, locked by `NumberOfValueInFieldsDiffTest` + `FilledCountLawsTest` + `FilledCountInvalidOperandDiffTest`)* |
| operand-list `Min([A], [B])` / `Max(…)` | an empty NUMBER operand is substituted `0` and **competes in the fold** (`Min(0, B)` — the 0 can win); an empty DATE/TIME/DATETIME operand is **skipped** (the temporal-value-bearing side wins) *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §2 + §6 / [IF58](INTERPRETER-FINDINGS.md#if58)/[IF204](INTERPRETER-FINDINGS.md#if204), locked by `EmptyValueLawsTest` + `DateAggregateDiffTest` + `TemporalExtremaDiffTest`)* |
| the field-list / starred aggregates (`Sum`, `MaxValue`, `MinValue`) | the empty cell is **dropped from the fold** — `MaxValue(-5, empty)` is `-5`, no `0` folded in; `Sum` reads it as `0`, which for a sum is the same thing *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §1 + §9, locked by `MultiFieldAggregateDiffTest` + `RepetitionLawsTest`)* |

The last two rows are one design split seen from both sides — and they disambiguate the guide's min/max note above: "the `0` substitution does not apply to minimum/maximum calculations" is true of the *aggregates* `MaxValue`/`MinValue`, while the operand-list `Min`/`Max` are a separate family that does substitute. `0` is `Sum`'s neutral element but not min/max's, so the aggregates must drop empties where the sum may fold them in — which makes it easy to assume the drop extends to the *all-empty* case. It does not:

### What an all-empty selection folds to (the aggregate identities)

One operand empty is one question (above); the **whole selection** empty — every operand empty, or a starred group with zero filled cells — is another, and each aggregate has a defined identity for it:

- The NUMBER aggregates fold to the fillable **`0`**, not "undefined": `MaxValue(QTY, BQ) == 0` fires with both fields empty, and `MinValue(Items*/Count) == 0` fires on a group with no rows at all. This no-present-value identity is fillable in **both directions**, independently of field signedness and independently of whether the operator is `Sum`, `MaxValue`, or `MinValue`; the ordinary per-operator directions start only after a present value enters the fold *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §1, locked by `MultiFieldAggregateDiffTest` and `NumericAggregatePolarityDiffTest`)*. `Sum` over an all-empty list is likewise `0` *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §9, locked by `RepetitionLawsTest`)*.
- The **date-like** `Min`/`Max`/`MinValue`/`MaxValue` (DATE, TIME, and DATETIME — all one `DateCombiner`) fold to **no value**: a comparison against an all-empty temporal aggregate never fires, and a computation of it clears its target. The fold selects by resolved temporal order — TIME by its decoded time-of-day, DATETIME by its resolved instant, never a rendered label *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §6 / [IF58](INTERPRETER-FINDINGS.md#if58), locked by `DateAggregateDiffTest` and `TemporalExtremaDiffTest`)*.
- `FirstFilledValue` follows its operand **kind**: an all-empty selection yields the fillable `0` for a NUMBER operand, while every other admitted kind — Boolean, custom, string/enumeration, date/date-fragment, time, date-time, and date-range — yields no value (NOT-GIVEN) *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §1/§3 / [IF80](INTERPRETER-FINDINGS.md#if80) + [IF83](INTERPRETER-FINDINGS.md#if83), locked branch-for-branch by `FirstFilledValueKindDiffTest`, `FirstFilledValueAdditionalKindDiffTest`, and the catalog aggregate-identity probes)*.

The identity is treacherous because it hides under most thresholds: `0` and "not evaluated" produce the same non-fire for `MaxValue(…) > 3`, so a wrong mental model survives every such rule and surfaces only where `0` itself satisfies the comparison — `MinValue(…) < 10` is the shape that finally distinguishes them *(the latency observed in [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §1, locked by `MultiFieldAggregateDiffTest`)*. The catalog carries these identities per element kind as the `aggregateIdentity` facet ([CATALOG-SPEC.md](CATALOG-SPEC.md) §3c).

### The row gate — where the substitutions stop

All of the above happens inside a **content-bearing row**. Under full validation an entirely empty instance is evaluated only when the condition is one that *can* fire on emptiness — a structural property of the condition, true of the negative presence family (`NoFieldFilled`, `FieldNotFilled`, `NotAllFieldsFilled`, …) and composing through `And`/`Or`; a comparison never fires on a truly blank instance, so the empty-as-0 rows above presuppose some sibling content *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §2, locked by `EmptyRowGateDiffTest`)*. What counts as content has one wrinkle: an **instantiated repeatable row is itself content** — a created-but-blank repeat row *is* evaluated, so per-row empty-as-0 fires on every such row — while a non-repeatable group's bare structural presence is not *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §2 / [IF53](INTERPRETER-FINDINGS.md#if53), locked by `RepeatableRowContentDiffTest`)*. Runtime services evaluate the immutable V2 document, not a sparse V1 placement list: conversion of a placement at repetition `n` pads missing predecessors `1..n-1` with empty group rows and creates its ancestor path, with a nested gap scoped to the addressed parent. Those predecessor repeatable rows are therefore instantiated content under the rule above. A canonical JSON array is already explicit at every position, including an empty `{}`, so this conversion law does not create a second JSON shape *(verified: [KF178](KERNEL-FINDINGS.md#kf178) / [IF276](INTERPRETER-FINDINGS.md#if276), locked by `RepeatableRowContentDiffTest` and `DocumentPlacementsSnapshotTest`)*. Validation iteration adds one separate wrinkle: an existing repeatable parent with no concrete nested child contributes an implicit child row 1 to the rule's iteration domain, but not to stored group/content, auto-check, star, parallel-identity, or computation domains *(verified: [KF179](KERNEL-FINDINGS.md#kf179) / [IF277](INTERPRETER-FINDINGS.md#if277), locked by `RepeatableRowContentDiffTest`)*. Partial validation overrides the gate entirely: a *relevant* instance is always evaluated, empty or even phantom — see [§12](#12-the-validation-model) *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §2 / [IF54](INTERPRETER-FINDINGS.md#if54), locked by `RepeatableRowContentDiffTest`)*.

Emptiness is also only one of a field's two non-value states: a **filled but formally invalid** cell behaves differently from an empty one in every position above — that third state is [§3](#3-formal-errors-and-the-unknown-state)'s subject.

## 3. Formal errors and the "unknown" state

A field whose value violates its *data-type configuration* (wrong type, pattern mismatch, too many decimal places, leading/trailing spaces, or a checked "required" box on an empty field) produces a **formal error**. While a formal error stands, the field is "unknown" to the kernel and **cannot be evaluated in any validation rule**.

A consequence at the logic layer: a condition that appears to be a tautology is not one.

```
FieldFilled(F) Or FieldNotFilled(F)
```

If `F` has a formal error, neither branch is satisfied — the field is unknown, so even "filled or not filled" cannot be said to be true.

Formal errors differ from rule errors: they use a fixed, non-customizable message, are shown on focus-out, and block the field from participating in other rules. Rule errors are authored in the model, can be error/warning/info, and never make a field unevaluable.

*Reference: Appendix → Validation and formal validation → Formal errors.*

### House ↔ kernel vocabulary — "cell" is our coinage (declared here, once)

"Cell" is a **house term**, not kernel vocabulary — the kernel has no `Zelle`/`cell` noun (source-verified; [KERNEL-FINDINGS](KERNEL-FINDINGS.md) "Terminology"). It is a compact row×column shorthand we use in the semantics/interpreter layer; this table is its **single point of declaration**, so every surviving use maps to the kernel's own wording. Agent-facing surfaces (the operator catalog, published schema, diagnostics, the skill, API-GUIDE) do **not** use the house noun — they use the kernel wording in the right-hand column.

| house term | denotes | kernel's wording / nearest construct | why coined |
|---|---|---|---|
| **cell** | one field value at a given repetition (a repeated field's value in one row) | *field value* (`FeldWert`) at a *repetition* (`Kontext`/`Kontextnummer`); the kernel has **no single noun** for the pair | a terse row×column shorthand for "a repetition's field value" |
| **cell state** | a value's three-way evaluability: empty · filled · not-check-relevant | the kernel's separate **predicates** — `isWertAngegeben` (specified/filled), not-specified (empty), `nichtPruefungsrelevant` (not check-relevant); **not** a named kernel type | names the 3-way taxonomy the kernel leaves as loose predicates (`CellState`) |
| **(index) column** | a field's values across all repetitions of its group | "the field's values across the repetitions"; **no single kernel noun** (the uniqueness/aggregate scans operate over it) | the scan unit for uniqueness + starred aggregates (`IndexColumn`) |
| **row** | one repetition of a repeatable group (the instance holding that repetition's field values) | *repetition* (`Kontext`/`Kontextnummer`); German `Zeile` survives in kernel identifiers (`zuGrosseZeile`, the legacy `ZeileNichtEindeutig`) | reads naturally beside "cell"/"column"; used throughout both docs |

Everything below uses "cell" and "row" per this declaration.

### The three cell states — the third one is not "empty"

A field's cell (a repetition's field value — see the vocabulary table above) has three states, not two: **empty**, **filled**, and **not-check-relevant** (the kernel's `nichtPruefungsrelevant`) — present but formally invalid. [§2](#2-non-specified-empty-values)'s substitutions are the *empty* column only; an invalid cell answers every question with "unknown", which lands differently in every position:

| what asks | an empty cell | a not-check-relevant (filled-but-invalid) cell |
|---|---|---|
| a comparison reading the value | the per-kind substitution ([§2](#2-non-specified-empty-values)) | UNKNOWN — the branch cannot decide *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §3, locked by `FormalErrorLawsTest`)* |
| `FieldFilled` / `FieldNotFilled` | a definite FALSE / TRUE — the cell counts as empty | UNKNOWN — neither presence leaf decides *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §3, locked by `QuantifierMalformedDiffTest`)* |
| an unfiltered validation fill quantifier | contributes to the known-empty bucket | contributes to neither the filled nor empty bucket; another sufficient known witness can still make the complete leaf fire, otherwise the observable result is the collapsed `FALSE_OR_UNKNOWN` *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §1 / [IF84](INTERPRETER-FINDINGS.md#if84), locked by `ValidationFillQuantifierProjectionDiffTest` + `StarQuantifierInvalidCellDiffTest`)* |
| a value aggregate or count over a selection containing it | the empty cell is dropped or substituted ([§2](#2-non-specified-empty-values)) | the **whole aggregate is non-evaluable** — the enclosing rule is suppressed, wherever in the selection the cell sits: head and tail are measured identical on the *verdict*, while the formal error still names the offending row, so validation output is not position-blind *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §2/§3, locked by `AggMalformedDiffTest`)* |
| a computation reading it | the per-kind compute behaviour ([§11](#11-computations)) | the read **aborts the computing instance** — compute's poison, [§11](#11-computations) *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §11 / [IF85](INTERPRETER-FINDINGS.md#if85), locked by `ComputePoisonReadDiffTest`)* |

### What puts a cell in the third state

More than a type-format mismatch. The same mechanism — same sentinel path, same suppression — is triggered by:

- **a malformed value** — the base case above, plus the cross-kind baseline checks that run before any type format: legal charset and leading/trailing blanks. The legal charset is the model-config `supportedCharacters` when the model declares one (runtime-enforced), else the full BMP (`0x0000–0xFFFF`, so any supplementary-plane character is illegal); a per-field charset is not declarable, and a *project/codegen*-level restricted charset (e.g. DIN 91379) exists outside the DM model *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §3 / [IF43](INTERPRETER-FINDINGS.md#if43) + "`modelConfig.supportedCharacters`", locked by `BaselineValueFormalDiffTest` + `SupportedCharactersLawsTest`)*;
- **a declared-constraint violation** — range, length, pattern, digit counts, enum domain: a parseable but out-of-bounds value is exactly as invalid as an unparseable one, and a value violating several checks reports the *first* in the kernel's fixed precedence *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §3 / [IF20](INTERPRETER-FINDINGS.md#if20) + [IF70](INTERPRETER-FINDINGS.md#if70), locked by `FieldConstraintFormalDiffTest`)*;
- **the "required" checkbox on an empty field** ([§4](#4-the-required-property)) — for validation the required-and-empty cell is unknown like any other formal error; compute, by contrast, reads it as plainly empty *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §9 (the uniqueness-cache exclusion) + §11 (compute's view), locked by `RepetitionNotUniqueFormalKeyDiffTest` + `ComputeInvalidOperandDiffTest`)*;
- **a duplicate index value** — the auto `uniqueIndex` check marks every participating cell, field-locally *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §4 / [IF86](INTERPRETER-FINDINGS.md#if86), locked by `UniqSuppressionDiffTest` + `IndexAggregateDiffTest`)*;
- **an over-repetition row** — an instance beyond the group's declared repeatability, which also suppresses that row's ordinary checks *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §9 / [IF27](INTERPRETER-FINDINGS.md#if27), locked by `OverRepetitionDiffTest`)*.

### The checked value is what evaluation reads — a CRLF pair reads as one `\n`

A value that passes the formal check enters the evaluation caches in **normalized** form: the `\r\n` pair is replaced by `\n` (a lone CR stays), once, at ingestion — and every evaluation-side read sees that text. The string format measure itself measures it (a permitted `"AB\r\nCD"` is 5 characters: `maxLength 5` is clean, `minLength 6` fires, and a pattern demanding exactly one whitespace character matches); a rule read is normalized (`Length([F]) > 4` fires over that value, `> 5` does not); a computation read is normalized (a bare copy *stores* the `\n` form). Two boundaries: the line-break *permission* check runs on the raw text before normalizing — and applies to enum fields too, so a break-carrying out-of-domain value reports the newline error, never the pattern one — and the document's stored value is never rewritten; the normalization is evaluation-side only *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §3 / [IF124](INTERPRETER-FINDINGS.md#if124), locked by `CrlfLengthNormalizationDiffTest`)*.

### A `noValueValidation` string field is a raw type — no rule or computation can read its value

A string field declaring `noValueValidation` (a string-only property) stores its value but never interns it for evaluation, and the model tier closes **every value window**: a value operation over it (a comparison, a value-list entry, a computation operand, or a coercion) is rejected (`MVK_INVALID_RAW_TYPE`); `$field.value$` interpolation of it is rejected; and `Length` is authorable only as the whole rule condition `Length(f) > c` or the mirrored `c < Length(f)`. The bound `c` must be written without a decimal point and its exact integer value must lie from `-2147483648` through `2147483647`; decimal spellings including integral-valued `5.0`, fractional values, and one-step overflows are rejected `MVK_INTERNAL_ERROR`. Shape admission runs first: a non-strict comparison or a surrounding Boolean condition is `MVK_INVALID_LENGTH_OF_RAW_TYPE` even when its bound also violates the integer domain, while an ordinary String field admits non-strict decimal bounds. That one strict raw-String shape is not a rule at all: code generation **eliminates** it and lifts its bound into the generated metadata's max length, so it never fires at runtime, filled or empty. The field's own format check short-circuits too; a declared `maxLength` is not enforced on input. **Presence semantics stay ordinary**: the cell is content, so `FieldFilled` fires and quantifiers and counts over it behave normally *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md#kf35) / [IF125](INTERPRETER-FINDINGS.md#if125) + [IF29](INTERPRETER-FINDINGS.md#if29), locked by `NvvRawTypeDiffTest` + `NvvRawTypeLawsTest`)*.

### Suppression is branch-scoped — and it reaches presence checks

A formal error does not remove the whole rule; it makes the affected operand UNKNOWN and the ordinary `And`/`Or` algebra decides the rest: `healthyTrue Or [broken] > 0` still fires via its healthy branch, while `healthyTrue And [broken] > 0` is absorbed — the single-branch rule is simply the case where branch- and rule-scoped suppression look identical *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §3, locked by `FormalErrorScopeLawsTest`)*. The unknown reaches even operators that read no value: `FieldFilled(malformed)` decides nothing *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §3, locked by `QuantifierMalformedDiffTest` + `CurrentRepetitionDiffTest`)*. And the suppression is silent from the author's viewpoint: the kernel emits its own formal-error code, attributed to the sentinel rule path `formalePruefung`, while the author's rule simply produces nothing — in a validation report the discriminator is that sentinel vs the rule's slash-path *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §3, locked by `FormalErrorLawsTest`)*.

### Validation excludes; compute poisons

The two operations treat the third state with opposite temperament, and the difference matters wherever computed fields chain. **Validation excludes**: an invalid cell drops out — tallies count it in neither bucket, aggregates over it go non-evaluable, referencing branches go UNKNOWN — and nothing propagates beyond the rules that reference it. **Compute poisons**: during `compute()` the invalid cells are converted so that any *read* of one throws; the reading computation instance aborts, produces no value, and the invalid mark cascades to its own dependents' reads in turn — order-dependently, because only cells an evaluation actually reads can poison it *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §11 / [IF85](INTERPRETER-FINDINGS.md#if85), locked by `ComputePoisonReadDiffTest`)*. The compute side is unpacked in [§11](#11-computations).

## 4. The "required" property

The "required" checkbox in the field editor is more than a single flag; it expands into a generated rule, manifests as a formal error, and is reflected by a separate "mandatory" indicator.

### The "Only if the Parent Group is filled" option

The checkbox has a secondary option that changes the generated condition:

| Field (location) | Parent-filled = **no** | Parent-filled = **yes** |
|---|---|---|
| `F1` (in group `A`) | `FieldNotFilled(F1)` | `GroupFilled(A) And FieldNotFilled(F1)` |
| `F5` (in group `C`, nested under `K`) | `GroupFilled(C) And FieldNotFilled(F5)` | `GroupFilled(K) And FieldNotFilled(F5)` |

With "yes," the field is required only once its parent group is filled (a reference to the parent). For a nested field the *referenced* group also differs between the two modes — the immediate parent under "no," a higher group under "yes."

### It manifests as a formal error

A field that is required-by-checkbox and unfilled produces a **formal error**, so the field becomes "unknown" (see [§3](#3-formal-errors-and-the-unknown-state)) — a stronger effect than the equivalent author-written rule `FieldNotFilled(F)`, which leaves the field evaluable. Tabbing through an empty required field does not trigger the error on its own, because no value changes.

### The "mandatory" star is a heuristic, not ground truth

Some controls show a star indicating the field is mandatory. The star is computed by a defined "star method" that inspects a fixed set of constructs. Starred fields are always mandatory, but **not every mandatory field is starred**: deciding mandatoriness in general is not effectively decidable (the guide's example shows a case where it would depend on whether a particular large number is prime). With "Parent-filled = yes," a field may be starred, mandatory-without-a-star, or not mandatory. A missing star therefore does not imply the field is optional.

### Interaction with repeatable groups

Because "yes" emits `GroupFilled(parent)`, and `GroupFilled` is satisfied for an empty, freshly-added repeat row (see [§9](#9-repetition-iteration-and-cross-array-evaluation)), a conditionally-required field can report an error on a row the user added but left blank.

### The generated rule, precisely — and what "filled" means here

The checkbox expands into an **autogenerated rule** (name `vk_vk<field>_req`, error code `mandatoryField`, severity ERROR, type OMISSION), whose condition is decided by the field's lowest repeatable ancestor: `FieldNotFilled(field)` — **unconditional**, firing even on an un-instantiated document — for an absolutely-required field with no repeatable ancestor; `GroupFilled(R) And FieldNotFilled(field)` per instantiated row under a repeatable ancestor `R`; `GroupFilled(parent) And FieldNotFilled(field)` under "Parent-filled = yes" *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §4, locked by `RequirednessDiffTest`)*.

"The parent is filled" resolves by the parent's repeatability, with the same **formally admitted content** notion as `GroupFilled` ([§9](#9-repetition-iteration-and-cross-array-evaluation)): a repeatable parent counts a created-but-empty row; a non-repeatable parent counts an admitted filled descendant — including an instantiated repeatable descendant row, but excluding a value rejected by formal conversion. Thus malformed-only content does not activate a `relativeToParent` sibling *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §4/§9, locked by `RequirednessDiffTest` + `GroupPresenceFormalInvalidDiffTest`)*. The required-and-empty "unknown" is branch-scoped like any formal error ([§3](#3-formal-errors-and-the-unknown-state)): `[ReqNum] < 100` is suppressed, but `[ReqNum] < 100 Or <true>` still fires.

### The index field's auto-generated checks — mandatory and unique

A repeatable group's `indexFieldName` arms two automatic checks with no authored rule ([§9](#9-repetition-iteration-and-cross-array-evaluation) covers the join it keys): the index field is **auto-required** with parent-filled semantics, and its values are auto-checked for **uniqueness** — the kernel emits `uniqueIndex` on **every** row whose non-empty index value duplicates another's (not all-but-first), scoped **per parent row**, as a VALUE error; an empty index value is excluded from the uniqueness check and draws `mandatoryField` instead *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §4, locked by `UniquenessDiffTest` + `RequirednessDiffTest`)*.

An enumeration index field may additionally declare a stored token as its **S-value** (DM-JSON `sValue`) — a **model-owned index default**, never a document value. One cell is *eligible* when the index is not explicitly mandatory, its group has **exactly one instantiated row under the current parent** (sibling parents independent), and that row's index cell is **clean-empty** (absent or present-empty — never an admitted or formally invalid explicit value). **Full validation stages the S-value into its transient evaluation cache** — before the generated index checks and authored rules, without mutating the document — so the defaulted cell draws no `mandatoryField`/`uniqueIndex` and a dependent authored rule sees the staged token; ineligible shapes (multiple rows, explicit value, mandatory index) keep ordinary behavior, an invalid explicit value never exposes the S-value, and zero rows stage nothing (no phantom row). Partial validation instead suppresses the cell silently — the [§12](#12-the-validation-model) phase split *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §4/§12 / SPEC-2026-07-23-14, locked by `IndexDefaultStagingDiffTest` + multiplatform `IndexDefaultStagingMultiplatformTest`)*. A duplicate-flagged cell enters the third state ([§3](#3-formal-errors-and-the-unknown-state)) **field-locally**: rules reading *that* field are suppressed (branch-scoped) while a sibling field's rules on the same rows still fire, and an aggregate or count over a starred index column carrying any duplicated or mandatory-empty cell is non-evaluable *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §4 / [IF86](INTERPRETER-FINDINGS.md#if86), locked by `UniqSuppressionDiffTest` + `IndexAggregateDiffTest`)*. Because the kernel generates both checks, a model must not also carry the equivalent authored rules — they would double up *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) "A group's index field auto-generates its uniqueness + mandatory rules", locked by `IndexFieldLawsTest`)*.

*Reference: Appendix → Validation and formal validation → Required by Checkbox; Appendix → Mandatory fields have an asterisk in their label → Required checkbox / The star method for validation rules.*

## 5. Numbers and decimals

### `==` / `!=` use derived signed scale plus constant expandability (checked at parse time)

Every checked numeric expression carries two independent authoring facts: a **known signed scale or unknown**, and whether the expression is **multiplicative-constant-capable**. When both scales are known and differ, `==` / `!=` may pad only a capable operand on the **smaller-scale** side; an unknown scale is rejected. This is a parse-time model check, not a runtime-value comparison.

```
[Product] == [Factor1] * [Factor2]                  ;; rejected if scales differ
[Product] == RoundAccounting([Factor1] * [Factor2], 3)   ;; permitted
```

Fields carry their declared scale and are not constant-capable. A fractional literal retains its authored scale, while an integer literal strips trailing zeros and may therefore have a negative signed scale (`1000` has scale `−3`); literals are constant-capable. Addition/subtraction take the maximum operand scale and require both operands to retain the capability; multiplication adds scales and retains it when either operand has it; division has unknown scale and no capability. Power normally has unknown scale and no capability, with one narrow exception: a known scale-0 base raised to a syntactically simple, nonnegative constant exponent whose own derived scale is at most 0 has known result scale 0. Explicit rounding has its declared result scale.

Thus a scale-2 field compared with literal `0` is legal in either operand order because the scale-0 literal is the capable smaller-scale side, while a scale-0 field compared with literal `0.00` is rejected in either order because the smaller-scale field is not capable. Ordering (`<`, `<=`, `>`, `>=`) bypasses the scale gate entirely. A documented equality rewrite is `[F] <= [G] And [G] <= [F]`; otherwise round to a known scale or suppress the warning. **Strings** compare field-vs-field with `==`/`!=` only — ordering draws `MVK_INVALID_TYPE_FOR_COMPARISON` *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §5, locked by `NumberLawsTest` + `NumericScaleGateTest`)*.

The scale check is the one diagnostic you can waive inline: begin the rule condition with `@SuppressWarning(MVK_INVALID_COMPARE_DEC_PLACES)` to allow an `==`/`!=` across differing scales (e.g. comparing a checksum). It is the **only** suppressible code — naming any other (`@SuppressWarning(MVK_…)`) raises `MVK_INVALID_SUPPRESSED_WARNING`.

*Reference: Operators and language constructs → Comparison operations → Comparing numbers; Appendix → Parser messages → Arithmetic.*

### Rounding modes

There are three rounding families, each with a value-construct variant (`…Value(Field[, DecimalPlaces])`, which takes a `Number` field; `RoundAccounting([F], n)` and `RoundAccountingValue(F, n)` are equivalent). On both forms the optional `DecimalPlaces` argument is an integer from **0 to 14 inclusive**; omission means exactly zero places.

- **`RoundDown` / `RoundDownValue`** — `FLOOR`, toward **−∞**, applied to the scale-19 `HALF_UP` pre-rounded operand.
- **`RoundUp` / `RoundUpValue`** — `CEILING`, toward **+∞**, applied to the scale-19 `HALF_UP` pre-rounded operand.
- **`RoundAccounting` / `RoundAccountingValue`** — `HALF_UP` to the **nearest** value after that same pre-round; when the two neighbours are equidistant, **away from zero**. This is *not* banker's rounding (round-half-to-even): for an equidistant value such as `2.5`, `RoundAccounting` gives `3` (and `-2.5` gives `-3`), whereas banker's rounding would give `2` and `-2`.

Worked values (no `DecimalPlaces` argument), from the guide:

| input | `RoundDown` | `RoundUp` | `RoundAccounting` |
|---|---|---|---|
| `-1.5` | `-2` | `-1` | `-2` |
| `1.777` | `1` | `2` | `2` |
| `-1.777` | `-2` | `-1` | `-2` |
| `2/3` | `0` | `1` | `1` |
| `1.5` | `1` | `2` | `2` |

Note that for negatives, "down"/"up" follow the number line, not magnitude: `RoundUp(-1.777) = -1` (closer to zero), `RoundDown(-1.777) = -2`.

*Reference: Arithmetic language constructs → Rounding.*

### Arithmetic domain failures are consumer-sensitive

Division by zero produces an invalid numeric value, not an ordinary empty/unknown value. A condition comparison projects that domain failure to UNKNOWN and therefore does not fire. A legal numeric computation such as `RoundAccounting([Numerator] / [Divisor], 2)` preserves the invalid value through arithmetic, `Abs`, `Min`/`Max`, and rounding: the target has no stored value (fresh delta absent; stale input reported CLEARED), carries `berechnungsWertFehler`, and poisons a dependent read. Those value/delta observations therefore do not prove a clean empty cascade. Numeric arithmetic follows the one-pass lowered tree left-to-right: a domain-failed value still permits the later operand to be evaluated, whereas a poison thrown by a read aborts before the later operand. A date shift is a deliberate boundary: the kernel maps an invalid numeric amount to a valueless date, so that date computation clears without `berechnungsWertFehler` *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §11 / [IF177](INTERPRETER-FINDINGS.md#if177); `DivisionDomainFailureComputationDiffTest` differential-locks the runtime projections and the observable domain-left/right-poison separator, while its generated-source checks define the first-poison order that the public formal-error inventory cannot expose; `DivisionDomainFailureComputationTest` observes the interpreter's selected poison on JVM/Node)*.

The separately bounded integral-power cases (`0` to a negative integral power, and an integral exponent outside ±1000) are the **same** domain failure: they make a comparison quiet and, in a legal numeric computation, mark the Number target invalid with `berechnungsWertFehler` and poison a dependent read exactly as zero division does (a non-whole exponent stays a static authoring error, `MVK_INVALID_NUMBER_FOR_EXP`, not a runtime value) *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §11 / [IF203](INTERPRETER-FINDINGS.md#if203); `PowerDomainFailureComputationDiffTest` differential-locks both `RoundAccounting(0 ^ -1, 2)` and `RoundAccounting(2 ^ 1001, 2)` and the `0 ^ 0` / `±1000` value boundary)*.

*Reference: Arithmetic operations → Treatment of division by zero; Arithmetic operations → Examples for using the Power Operator.*

### Other numeric constraints

- **Numeric operand-list `Min`/`Max` is a nonempty ordered list of complete number-like operations, admitting at most one immediate-or-bracketed literal PER CALL.** The kernel's curly-brace grouping (`{1}`) does not hide a literal from that budget, but a literal nested inside arithmetic, another value function, or a nested `Min`/`Max` call is not an immediate constant of the outer list — each nested call checks its own budget independently. So `Min(Min([A], 1), 2)` is admitted while the flattened `Min([A], 1, 2)` is rejected (`MVK_TOO_MANY_CONST_FOR_CALC_OP`); call boundaries are authored structure and must not be flattened. Each operand is a complete numeric operation; the static result takes the union/maximum of operand scales and keeps multiplicative-constant capability only when every operand has it, and a completed call may itself appear inside surrounding arithmetic. dmkits carries the list-preserving `OpListMath`, defers the scale/capability gate, and delegates the constant check to the kernel; the interpreter folds operands left to right in authored order (order-independent for these commutative extrema). This is operand-list extrema, distinct from the field-list `MinValue`/`MaxValue` aggregates *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §5, admission locked by `OpListMathConstantLawsTest`, peer composition by `adapter.laws.InterpreterDiffTest`)*.
- `FieldValueAsNumber(source)` accepts only a source whose **entire selected text domain** is statically convertible. For String, that means value validation, exact pattern `[0-9]+`, and finite maximum length at most 15 (scale 0). For Enumeration, `source` may be the stored-token domain or a named category domain; every selected token must contain at most 15 decimal digits and follow the grammar `-?` plus digits with at most one decimal point (leading point allowed, trailing point forbidden). Its digit predicate is the host UTF-16 `char`-unit `Character.isDigit(char)` class (via Commons Lang `NumberUtils.isParsable`, which iterates `String.charAt`), not `Character.isDigit(int)` or a Unicode-scalar predicate: non-ASCII BMP decimal digits such as Arabic-Indic and fullwidth digits are admitted and converted by their decimal value, while a supplementary-plane decimal code point is rejected because its two surrogate code units are tested separately. `+`, exponent, whitespace, and comma are not admitted. Its scale is the maximum fractional length in the selected domain. (A supplementary char is in practice rejected earlier: the model's supported-characters set is BMP-only — surrogates are not even declarable — so such a token is an unsupported sign before this digit check runs; the interpreter, kernel-free with no model charset gate, is where the char-unit digit-class rejection is directly observed — SPEC-2026-07-23-07.) Runtime converts the exact selected stored/category token; missing reads as symmetric-fillable numeric 0, present is fixed, and formal unavailability remains unavailable/poison *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §5, locked by `FieldValueAsNumberDomainLawsTest`, tri-engine `FieldValueAsNumberDomainDiffTest`, and JVM/Node `FieldValueAsNumberDomainTest`)*.
- The operation-form `RoundDown`/`RoundUp`/`RoundAccounting` and `Abs` accept that conversion directly for both stored and category sources. Rounding replaces its result scale with the explicit places (omission means 0) and preserves the conversion's fill directions. `Abs` retains the selected domain's derived scale and transforms symmetric missing zero to grow-only magnitude. Clean missing computes as zero through either wrapper; formal unavailability remains poison. The child check rejects only an immediate literal or bracketed literal, not a legal conversion subtree merely because it has constants elsewhere *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §5, tri-engine `FieldValueAsNumberWrapperDiffTest`, JVM/Node `FieldValueAsNumberWrapperTest`)*.
- Those wrappers also accept `RangeAsNumber(...)` directly. Rounding assigns its authored scale and preserves the range's grow-only-missing/fixed-present directions; `Abs` keeps scale 0 and the nonnegative range value. Missing computes as zero, a filled nonnumeric selection is a fixed fallback zero, and formal unavailability remains poison. Integral result text is canonically rendered without promising trailing zeroes; authored scale remains an operation/result-type fact *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §5, tri-engine `RangeAsNumberWrapperDiffTest`, JVM/Node `RangeAsNumberWrapperTest`)*.
- `Abs` accepts a direct numeric field-list aggregate (`Sum`, `MinValue`, `MaxValue`, or numeric `NumberOfDifferentValues`). The aggregate folds first; `Abs` then changes the folded sign and fill directions while retaining derived scale. All-empty Sum/extremum zero becomes grow-only magnitude; distinct-count zero is already grow-only. Formal unavailability remains poison, including for dependent computation reads *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §5, tri-engine `AggregateAbsDiffTest`, JVM/Node `AggregateAbsTest`)*.
- The wrappers accept scale-0 temporal-derived numbers: Date/Time/DateTime components, a component of `BaseYear`, and Date-only month/year differences. Rounding assigns authored scale and preserves fill; `Abs` retains scale 0 and transforms the completed signed value. Empty stored components/differences are symmetric zero, so rounding stays bidirectional while `Abs` becomes grow-only; Base-Year-derived values are fixed and formal unavailability stays poison. Direct numeric `BaseYear` is also legal (`RoundDown(BaseYear)`, `Abs(BaseYear)`): the immediate-literal rejection does **not** classify its separate grammar branch as `konstante` *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §5/§6, tri-engine `TemporalNumericWrapperDiffTest`, authoring `BaseYearArithmeticLawsTest`, JVM/Node `TemporalNumericWrapperTest`)*.
- **Plain arithmetic division regions are structural.** Grouping, addition, subtraction, and power validate fresh child regions and expose zero open divisions to their parent; multiplication/division combine their ungrouped children's open contributions, and division adds one for itself. A plain region is rejected once that total exceeds one, so `[G] / [F] / 2` is illegal while `{ [G] / [F] } / 2`, `[G] / { [F] / 2 }`, and `[G] / 2 + [F] / 3` are legal. Braces preserve this authoring boundary but do not make the subtree opaque to the later runtime lowering.
- **Power's authoring check is narrower.** It rejects a power whose direct left operand is an ungrouped power; with the left-associative grammar, `a ^ b ^ c` is the reachable unbraced rejection. `{ a ^ b } ^ c` and `a ^ { b ^ c }` start fresh regions and are legal when their scale/exponent checks also pass.
- **Operation-valued function wrappers remain an explicit evidence boundary.** The legacy authoring walk descends through them, but a nested reset aborts the enclosing scan rather than composing like the plain-arithmetic summary above. dmkits therefore keeps wrapper legality delegated to the kernel until focused existing-harness probes characterize each wrapper; it does not infer a general transparent-or-reset rule.
- Input numbers may have at most 15 digits (checked before each validation); internal arithmetic uses higher precision.
- A Number field's scale is **always bounded** — there is no unbounded-scale decimal: a model that omits `maxFractionalDigits` gets scale `0`, never unbounded, never rejected *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §5, locked by `modelkit.NumberScaleKernelLawTest`)*.
- Tolerance comparisons exist only at fixed thresholds (`DiffersWithToleranceRange1/2/5/10`) and are satisfied when the independently normalized operands lie **strictly outside** the tolerance — `|R₁₉(a) − R₁₉(b)| > N`, so a difference of exactly `N` does not fire. An empty numeric operand reads `0` ([§2](#2-non-specified-empty-values)). A firing uses directional `!=` polarity: only movement of the normalized smaller side upward or the larger side downward can make it an OMISSION; other firings are VALUE *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §5, locked by `ToleranceComparisonLawsTest` + `ToleranceExactnessDiffTest`)*.

### Internal precision — the scale-19 comparison rescale and the 50-digit arithmetic cap

- Every NUMBER **comparison** (ordering, equality, tolerance) rescales both operands to **scale 19 `HALF_UP`** before comparing; `min`/`max` *selection* stays full-precision *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §5, locked by `PrecisionDiffTest`)*.
- Every arithmetic operation `+`/`−`/`×`/`÷`/`^` rounds to a **50-digit `MathContext`** — observable for addition and subtraction as well as high-scale multiplication, and what makes `÷` terminate at all *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §5, locked by `DecimalPrecisionParityDiffTest` + `ArithmeticDiffTest` + `DivPowDiffTest`)*.
- Number `Sum` is a zero-seeded, encounter-ordered left fold that applies that precision-50 `HALF_UP` addition after every present value. Group expansion follows model declaration order and repeated cells follow row order; missing contributors add nothing but retain their declaration for polarity. Sorting, reassociation, exact accumulation followed by one rounding, and parallel reduction are therefore invalid *(source-grounded in [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §5; staged/order primitives locked on JVM+Node by `NumericAggregateSemanticsTest`)*.
- Positive power follows the OpenJDK 21 X3.274 `BigDecimal.pow(int, MathContext)` numeric-value algorithm: binary-exponentiation intermediates use working precision `50 + decimalDigits(exponent) + 1`, followed by the final precision-50 round. Negative power is kernel-specific reciprocal-first staging: round `1 / base` at precision 50, then apply the positive algorithm to the negated exponent. Exact rational power with one final round and reciprocal-after-positive-power both differ on legal inputs *(locked by `DecimalHostParityTest` + `DecimalPrecisionParityDiffTest`)*.
- Before evaluation the kernel performs exactly one ordered post-order arithmetic rewrite. Each original multiplication, after its children are rewritten, pulls only immediate division-root operands; ordinary factors keep their order and precede extracted numerators, denominators keep division encounter order, multi-factor products are left folds, and newly created products are not revisited. Thus `a * {b/c}` and `{b/c} * a` both evaluate as `{a*b}/c`, while `x * {{a/b}/c}` becomes `{x*{a/b}}/c` and stops. This is neither direct authored-tree evaluation nor global/fixed-point fraction normalization *(locked by `ArithmeticLoweringDiffTest` + multiplatform `ArithmeticLoweringTest`)*.
- A scale-19 `HALF_UP` pre-round precedes every target-scale rounding: `RoundDown([q]/3 + [q]/3 + [q]/3, 0) == [q]` fires for `q = 1` because the independently rounded thirds sum to `1−10⁻⁵⁰` and pre-round to `1` before the floor. A multiplied-third example is not a discriminator because the one-pass rewrite makes that product exact first *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §5, locked by `RoundingLawsTest` + `ArithmeticLoweringDiffTest`)*.

## 6. Dates and time

### Constant format and string/date ambiguity

Date constants are written `DD.MM.YYYY` (day first) regardless of locale, and the decimal separator is always `.`. A string literal that matches the date format is interpreted as a **date** constant, which prevents using it in string concatenation:

```
"30.11." + [YearString]      ;; invalid: "30.11." is read as a date
"30." + "11." + [YearString] ;; valid
```

The literal is typed **by its own syntax, not by context**: `[StringField] == "15.06.2024"` is rejected (string vs a date constant), a `dd.MM.yyyy` literal compares chronologically to a DATE field *whatever the field's stored format*, and it rides in argument position (`DifferenceInDays(OrderDate, "01.01.2022")`) — while inside a value *list* a date-looking entry stays a plain string. An **ISO-format literal** (`"2022-01-01"`) is lexed as a string, never a date. The **omitted-year form** (`"13.07."`, trailing dot) is a reference-year feature: the kernel injects the model's **Base Year** (not a floor), and a model without one rejects it *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §6 / [IF52](INTERPRETER-FINDINGS.md#if52), locked by `DateLiteralDiffTest` + `OmittedYearDateDiffTest`)*.

*Reference: Constants and data types.*

### Difference and addition are not symmetric

`DifferenceInMonths` / `DifferenceInYears` return the signed count of complete months/years from the first date toward the second, discarding a fractional remainder toward zero rather than subtracting calendar fields:

```
DifferenceInMonths("31.01.2010", "30.03.2010")   ;; returns 1, not 2
```

`AddYears` maps the last day of February to the last day of February (`AddYears("28.02.2023", 1)` → `29.02.2024`), whereas `AddMonths` normally preserves the day but clamps an invalid landing to the target month's last day (`AddMonths("31.01.2008", 1)` → `29.02.2008`); the two therefore disagree across a leap-year boundary, and a naive age check built on them is wrong around leap days. Fractional offsets are truncated, not rounded.

The exact calendar corrections, pinned: `AddYears` corrects the Feb-28 boundary *into* a leap year (`28.02.1999 + 1 year = 29.02.2000`, not the plain calendar-add `28.02.2000`), and `AddMonths` clamps end-of-month overflow to the shorter month's last day (`31.01.2008 + 1 month = 29.02.2008`), never carrying into the next month *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §6, locked by `DateArithmeticLawsTest`)*. The **sub-day** family operates on epoch milliseconds: stored and constructed values remain whole-second, while `Now` retains the validation clock's millisecond remainder. `AddHours`/`AddMinutes`/`AddSeconds` carry across the day boundary and preserve that remainder; `DifferenceIn{Hours,Minutes,Seconds}(a, b)` is `(epochMillis(b) − epochMillis(a)) / unitMillis` **truncated toward zero** — a reverse difference of −5 h 30 m is `-5`, not `-6`; the argument order is `b − a`, like `DifferenceInDays` *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §6, locked by `DateTimeArithmeticDiffTest` + `NowMillisecondIdentityDiffTest`)*.

`DifferenceInDays` is not elapsed wall-seconds divided by 86,400. It orders the two model-zone legacy-calendar values, seeds a safe whole-year lower bound, and advances the earlier calendar by `DAY_OF_MONTH` until the next landing would pass the later value; the authored operand order restores the sign. Time of day therefore matters (`23:00 → 01:00` next day is `0`), and zone transitions can separate this rule from wall-coordinate division: in `Europe/Berlin`, `2024-03-30T02:30` → `2024-03-31T01:45` is `1` because the one-day calendar landing is `01:30`. A whole-date discontinuity behaves the same way (`Pacific/Apia` noon 2011-12-29 → noon 2011-12-31 is one step). The interpreter implements this rule for its supported UTC/GMT/Berlin profile and refuses wider zones before evaluation *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §6, locked by `CalendarStepDifferenceInDaysDiffTest` + multiplatform `CalendarStepDifferenceInDaysTest`)*.

*Reference: Date and Time language constructs → DifferenceInMonths / AddMonths / AddYears.*

### Constructing dates, and checking validity

`Date(Day, Month, Year)` builds a date from numeric parts (there are also a two-argument form that supplies the year from the model **Base Year**, and a four-argument century form); `Time(hour?, minute?, second?)` takes a zero-to-three-component prefix and defaults every omitted trailing component to zero; `DateTime(...)` combines a date and time. A constructed date is **invalid** if any referenced part is unfilled, or the parts don't form a real calendar date — `Date(31, 11, 2000)` (November has 30 days) or 30 February. `Valid(...)` / `Invalid(...)` test exactly that:

```
Invalid(Date(Day, Month, Year))   ;; fires on 31.11, 30.02, an unfilled part, …
```

`Valid(Field, "CustomTypeName")` is the other form: it runs the project's registered validator for that custom type against the field. (Operand-format requirements for the `Date(...)` parts — bounded integer fields, or digit-patterned strings — are an authoring concern documented in `KERNEL-GRAMMAR.md`.)

Calendar reality here is the model-zone, non-lenient legacy `GregorianCalendar` contract, not a zone-free proleptic-Gregorian predicate. Its default hybrid cutover uses Julian dates through 1582-10-04, skips 1582-10-05..14, and uses Gregorian dates from 1582-10-15: UTC `1500-02-29` is therefore real. Zone discontinuities also participate: a `Pacific/Apia` model rejects the skipped local date `2011-12-30`. This construction rule is separate from the later 1583-10-16 formal floor for stored/computed values. The interpreter implements the complete rule for its supported UTC/GMT/Berlin profile and loud-refuses other zones *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §6, locked by `ConstructedDateCalendarDiffTest` + multiplatform `ConstructedDateCalendarTest`)*.

At the strong-Kleene **truth projection**, `Valid(Date(...))` and `Invalid(Date(...))` are exact complements across all four construction states: real gives TRUE/FALSE, unreal or incomplete gives FALSE/TRUE, and malformed gives UNKNOWN/UNKNOWN (`not UNKNOWN = UNKNOWN`). The full verdict is not derivable from the other predicate's truth alone: both incomplete and unreal make `Valid` FALSE, while a firing `Invalid` must recover OMISSION for an incomplete/fillable construction and VALUE for a present-but-unreal construction. A present-but-unreal construction carries no date value, but its direct numeric extractors and date differences receive the kernel's default numeric **0**; malformed remains Unknown. Real constructed values retain their legacy-calendar identity through extractors, date differences/additions, as a direct operand of date `Min`/`Max`, and in `DateTime(Date(...), Time(...))`. This does not make a date `Min`/`Max` result a legal component-extractor source: `YearFromDate(Min(...))` is rejected by the extractor's narrower grammar. To fire `Invalid` only on a complete-but-impossible date, prefix `AllFieldsFilled(...)` *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §6, locked by `DateConstructionDiffTest`, `ConstructedDateCalendarDiffTest`, and `DateValidityLawsTest`)*.

The direct numeric date-component family is `DayFromDate`, `MonthFromDate`, `QuarterFromDate`, and `YearFromDate`. For a real date, `QuarterFromDate` maps month `m` to `((m - 1) / 3) + 1` with integer division. For an incomplete or unreal construction the whole family projects the fillable numeric default `0`, including Quarter; malformed/formally unavailable input remains UNKNOWN rather than turning the zero sentinel into quarter one *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §6, locked by `DateExtractDiffTest`, `EmptyOperandFiringDiffTest`, `ConstructedDateCalendarDiffTest`, and `ConstructedDateCalendarTest`)*.

*Reference: Date and Time language constructs → Date and time constructs → Date (Date with three parameters / Valid or invalid dates); Miscellaneous → Valid and Invalid.*

### Other date behaviours

- **Dates before 16 October 1583 are invalid — as stored or computed *values*.** The floor is always-on and exact (strict *before*: 1583-10-15 errors, 1583-10-16 is valid; a day-optional value completes its omitted day to `01` *before* the check): a stored value below it is the formal error `datumFalsch` (suppressing referencing rules, [§3](#3-formal-errors-and-the-unknown-state)), a computed one is ERRORED, and a date range floors its start the same way. It is distinct from the *opt-in* "younger than 1900" additional check *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §3 / [IF88](INTERPRETER-FINDINGS.md#if88), locked by `ComputedDateGregorianFloorDiffTest`)*. The floor is **not** a runtime criterion for the `Date(...)` *construction*: UTC `Date(29,2,1500)` is real on the legacy calendar's Julian side *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §6, locked by `ConstructedDateCalendarDiffTest`)*.
- **A date value is stored and formal-checked in its field's declared `format`, not a canonical wire format** — the same calendar date is a well-formed value in one field and `datumFormatFalsch` in another; a consumer must read each field's `format` to parse its dates *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §3, locked by `PlainDateDiffTest`)*.
- `DifferenceInHours/Minutes/Seconds` is **signed absolute-instant subtraction** (`(instant₂ − instant₁) / unit`, truncated toward zero), computed identically by the Java runtime service and Java/Groovy codegen because they call the same runtime helper. Across a daylight-saving transition the result depends on the model's configured **`timeZone`** (meta key `TimeZone`, default `UTC`), applied at parse time—not on the Java/Groovy target language. The code does not restrict valid models to the two zones emphasized by the documentation: the structural check accepts Java `TimeZone` IDs except unknown ids that collapse to GMT (literal GMT is valid), and runtime parsing uses `TimeZone.getTimeZone`. Under `UTC` the wall-clock gap equals the instant gap; under `Europe/Berlin`, `2024-03-31T01:30:00` → `03:30:00` is `DifferenceInHours = 1`. *(Corrects both the prior target-language claim and the later two-zone overstatement—[KERNEL-FINDINGS](KERNEL-FINDINGS.md) §6, source-verified 2026-07-12 and re-audited 2026-07-20. The interpreter supports UTC/GMT and the full pinned Europe/Berlin history; the wider kernel-accepted zone-id domain is the owner-deferred Route A of [INTERPRETER-GAPS](INTERPRETER-GAPS.md) IG83.)*
- Date *fragments* (partial dates) are comparable only if both formats include the year or both omit it; a missing component defaults to `01`. A model-level **Base Year** changes these rules globally. At evaluation a fragment field's value **completes to the earliest concrete date** — missing month → `01`, missing day → `01`, missing year → the declared base year — and then compares, shifts, or extracts as a plain date; the completion is shared by both kernel strategies *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §6 / [IF57](INTERPRETER-FINDINGS.md#if57), locked by `DateFragmentComparisonDiffTest`)*. A **fragment-format date range** completes its two endpoints **asymmetrically** — the start to the interval's earliest date, the end to its latest (missing month → `12`, missing day → the month's last day, leap-aware) — so a `yyyy` range `2024/2025` denotes `2024-01-01 .. 2025-12-31` *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §6 / [IF118](INTERPRETER-FINDINGS.md#if118), locked by `FragmentRangeEvalDiffTest`)*.
- **Direct temporal comparison and temporal extrema use DIFFERENT format gates** — the direct gate is *coarse*, the extremum gate is *exact*. After optional Base-Year supplementation, a **direct** comparison (`==`/`!=`/ordering) needs only matching **year presence** and matching **date/no-date class**; `==`/`!=` additionally need matching **time/no-time class**; **no direct operator requires identical component sets**. So a `yyyy-MM` fragment and a `yyyy-MM-dd` date DO compare directly, and a plain date orders against a date-time (`<`) although it may not `==` one (time-presence differs). A **temporal extremum** operand of `Min`/`Max`/`MinValue`/`MaxValue` — and of `NumberOfDifferentValues`, which shares the gate — by contrast needs **equal component SETS**: the SAME `yyyy-MM` + `yyyy-MM-dd` pair inside a `Min(...)` is rejected (`MVK_DATEFORMATS_NOT_COMPATIBLE`), and DATETIME extrema require all six components. Sets, not spellings — `yyyy-MM-dd` beside `dd.MM.yyyy` and `yyyy-MM` beside `yyyyMM` are **admitted** — and not kinds either, since a DATE `yyyy` beside a DateFragment `yyyy` is admitted; a declared **Base Year** supplements `YEAR` into both sets before the comparison. A **third** temporal gate must not be folded into this one: `FieldValuesNotUnique` requires one *identical declared format string* and refuses under its own `MVK_ONLY_STRING_ENUM_NUMBER_DATE_ALLOWED`, so it rejects both equal-set pairs the aggregates admit, and no Base Year lifts it. `Sum` takes no part — a temporal operand is `MVK_NO_NUMBER`. All of this affects authoring admission only, not resolved chronology or the extremum fold (that fold is §2/§6). a12-dmkits delegates every one of these gates to the kernel *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §6 / [KF193](KERNEL-FINDINGS.md#kf193), locked by `TemporalComparabilityGateLawsTest` + `TemporalAggregateComponentSetLawsTest`; the extremum fold itself is `TemporalExtremaDiffTest`)*.
- A partial `DateType` uses exact zero components in a monotone suffix: `DAY_OPTIONAL` admits `00.06.2024`; `MONTH_OPTIONAL` additionally admits `00.00.2024`; `YEAR_OPTIONAL` additionally admits only `00.00.0000`; every wider mode retains full and narrower shapes. A lexically shaped illegal suffix (`15.00.2024`, `15.06.0000`) is `datumFalsch`. `ValueAsDate(field, FirstDay|LastDay)` selects month before day (`00.00.2024` → `01.01.2024` / `31.12.2024`), while unknown year stays non-relevant and a direct comparison is UNKNOWN rather than borrowing the formal checker's temporary year 2000. `ValueAsDate` carries its own operand alternative (`datumAngabe2`), so besides the direct comparison it is admitted in **three nested positions** — an `Add*` **date** base, *both* `DifferenceIn*` operands, and the **date** argument of `DateTime(...)` — and rejected everywhere else a Date is expected (extractor, `DateTime`'s time argument, a `Date(...)` component, a `Min`/`Max` operand) *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md#kf88) §6, locked by `ValueAsDatePlacementLawsTest`, `ValueAsDateDiffTest`, dual-strategy `PartialDatePrecisionDiffTest`, and multiplatform `PartialDatePrecisionTest`)*.
- A `DateType`'s declared **format** may itself omit calendar components — `yyyy`, `yyyy-MM`, `yyyyMM`, `MM` and `MM-dd` are kernel-legal, while `MM.yyyy`, `MM-yyyy`, `yyyy/MM` and `dd.MM` are refused *"The date format is invalid"*, so the admitted set is a **whitelist of format strings** rather than a compositional rule (the same two components flip on their separator). **Every spelling failure on such a field reports ONE cause, `datumFormatFalsch`** — a wrong component width, a text carrying components the format omits, an out-of-range month, and an unreal month-day alike — and the position-in-time cause `datumFalsch` never arises, because no complete date is present to fall below the Gregorian floor. The separator is exact in **both** directions at the value tier too (`yyyy-MM` rejects `202006`, `yyyyMM` rejects `2020-06`), and a yearless `MM-dd` day is **leap-capable**, bounded by the month's greatest possible day (`02-29` accepted, `02-30` and `04-31` refused). They compare through the **ordinary** coarse gate above — `yyyy` with `yyyy-MM` and with a complete date, `MM` with `MM-dd`, and never across the year-presence boundary without a Base Year *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md#kf196), locked by `IncompleteDateFormatCauseDiffTest`)*. This is a third partial shape, independent of the `datePrecision` modes above and of `DateFragmentType`: the value is complete **for its format** and completes like a fragment — month and day to `01`, a missing year from the model **Base Year** (with no base year declared, comparing a year-less field is refused `MVK_INVALID_COMPARE_TO_DATE`). An extractor for a component the format omits is refused at codegen `MVK_WRONG_DATE_FORMAT_FOR_…`, so the completed components are unreadable and the completion is observable only through comparison *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md#kf176) / [IF250](INTERPRETER-FINDINGS.md#if250), locked by `IncompleteDateFormatAdmissionLawsTest` + `IncompleteDateFormatDiffTest`)*.
- `Today` ignores the time of day; `Now` is not recommended with `==`. It is legal as a computation result but unstable because the generated implicit validation rule can observe a later instant and immediately disagree. Temporal ordering admits `Now` against a DATE or DATE_TIME operand on the common timeline; equality requires matching time presence, so plain DATE `== Now` is rejected with `MVK_INVALID_COMPARE_TO_DATE`. Although it renders at whole-second precision, its equality/order and sub-day arithmetic retain the validation instant's exact epoch-millisecond identity *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §6, locked by `TemporalComparabilityGateLawsTest`, `NowDateOrderingDiffTest`, `NowDiffTest`, `NowMillisecondIdentityDiffTest`, and `ComputationValidationLawsTest`)*.
- **`BaseYear` is polymorphic by its typed use**: against a date it is the base-year *start* (`2020-01-01`); in numeric comparison, ordinary arithmetic, a Number computation, or a direct numeric wrapper it is the fixed scale-0 year number (`2020`); as a range source, `StartOfDateRange(BaseYear)` / `EndOfDateRange(BaseYear)` are `01.01` / `31.12` of the reference year. It is not an immediate `konstante` for the numeric-wrapper rejection, so `RoundDown(BaseYear)` and `Abs(BaseYear)` are legal. It is model config, not the clock; VALUE polarity. Missing configuration remains `MVK_NO_BASE_YEAR` *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §6, locked by `BaseYearDiffTest`, `BaseYearArithmeticDiffTest`, `TemporalNumericWrapperDiffTest`, `BaseYearArithmeticLawsTest`, and `adapter.PointInTimeSourceReadTest`)*.
- Date ranges support only `==` / `!=` (not ordering). A `DateRange(...)` construction may compare with a DATE_RANGE field in either direction; overlap predicates and bound extractors require fields and reject a nested construction. `DateRangesOverlap` treats endpoints as inclusive.
- **The overlap predicates differ in shape**: `DateRangesOverlap(op0, op1, …)` is **any-pair** among *all* operands' kept, filled ranges (one growing set — a list-internal pair fires even when the scalar operand is disjoint, and a same-cell self-pair via scalar + star fires every filled row), while `AtLeastOneDateRangeOverlaps(scalar In list…)` is genuinely **scalar-vs-list** (two list cells overlapping each other do not fire).
- **Their polarity follows the reached scan, not authored filter presence.** For `DateRangesOverlap`, the OMISSION flag becomes sticky only after the scan actually processes a kept, filled range from a filter-bearing operand; a filtered operand with no kept, filled range does not taint a later unfiltered pair, while a reached filtered range does taint a later pair even when that earlier range is disjoint. For `AtLeastOneDateRangeOverlaps`, only the list container holding the matched range determines polarity: a filtered match is OMISSION, an unfiltered match VALUE, and an earlier filtered-but-disjoint or empty container does not taint it. An empty, malformed, or formally unavailable scalar returns no fire before any list-internal pair can matter.
- **Filters and interval validity have separate gates.** A `Having` filter on a predicate's repetition-list argument is legal, applied per cell, and compiled to a plain boolean — a row is kept **iff the filter is TRUE**, so a malformed filter operand drops its row; because a plain predicate's argument has no enclosing iteration for `$` to correlate with, a `$`-correlated term inside such a filter is trivially TRUE, though it still composes under `And`. Intervals are **closed** (touching endpoints overlap), empty/malformed cells are skipped, and an inverted stored range normally fails its field's formal check; independently, the resolved overlap relation defensively returns false if either range is inverted *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §6 / [IF72](INTERPRETER-FINDINGS.md#if72), locked by `DateRangeOverlapSemanticsDiffTest` + `DateRangeOverlapTest` + `DateRangeOverlapLawsTest` + `FieldValuesNotUniqueDiffTest`)*.
- **`DateFromDateTime` / `TimeFromDateTime` project the source label's OWN wall components, and both need a COMPLETE DateTime.** `DateFromDateTime` reports the stored label's date with the time dropped and **no zone conversion**: at `Europe/Berlin` a `2024-06-15T00:30:00` extracts to `2024-06-15`, not to the retained instant's UTC day `2024-06-14`. Its result is a **Date** — comparable with a Date field, `Today`, and another `DateFromDateTime`, and admitted as the Date operand of `AddDays` and `DateTime(...)`, while `Now`, a `TimeFromDateTime` result, a TIME field, and its own DATE_TIME source are all `MVK_INVALID_COMPARE_TO_DATE`. One source gate serves **both** extractors: a plain DATE field and a degenerate time-only DATETIME are each `MVK_WRONG_DATE_FORMAT_FOR_OP` at the operator, so the gate asks "is this a complete DateTime". The operand is a **bare path** (`DateFromDateTime([F])` is `MVK_UNEXPECTED_TOKEN`), and the extraction is refused as a `Date(...)` component (`MVK_DATE_OR_TIME_EXTRACT_OP_NOT_ALLOWED`) and as a `DifferenceInDays` operand, while nesting inside `DayFromDate`/`YearFromDate` stays legal *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md#kf194) §6, locked by `DateFromDateTimeSurfaceLawsTest` + `DateFromDateTimeWallDateDiffTest`)*.
- **DATE_TIME rides the date format definition**: the date extractors (`DayFromDate`, …) and `DifferenceInDays` accept a datetime operand. Component extractors read its date fields; `DifferenceInDays` preserves the clock and applies its calendar-step rule. `DifferenceInMonths`, `DifferenceInYears`, and the date *arithmetic* family (`AddYears`, …) reject a datetime operand at code generation *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §6 / [IF95](INTERPRETER-FINDINGS.md#if95), locked by `DateFunctionsOverDateTimeDiffTest` + `CalendarStepDifferenceInDaysDiffTest`)*.

*Reference: Date and Time language constructs → Date fragments / Today / Now / Date Ranges.*

## 7. Strings and patterns

- String length counts Unicode combining sequences as multiple characters, so one visible glyph can occupy several characters of a length limit — the counting unit is the **UTF-16 code unit**, with no grapheme clustering (a decomposed `e` + combining accent counts 2), in `Length` and the `minLength`/`maxLength` checks alike *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §7, locked by `AbsLengthDiffTest`)*. A permitted CRLF line-break pair counts as **one** — evaluation reads the normalized `\n` form ([§3](#3-formal-errors-and-the-unknown-state)).
- `PatternMatched` / `PatternViolated` evaluate the **whole** value (anchored) and can be a performance/security risk if written to backtrack (e.g. `(a+)+`). Model validation applies Java `Pattern.compile` plus a limited `PatternUtils` restriction: some Java-valid constructs such as lookbehind are rejected, but this is **not** a Java/JavaScript-portable subset—inline flags such as `(?i)` and Java escapes such as `\R`/`\h` are kernel-valid while JS `RegExp` rejects them. A Java-side compile pre-check is therefore necessary but not sufficient for kernel acceptance, and kernel acceptance is not proof of JS portability *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §7; lookbehind locked by `PatternLawsTest`; cross-host reproduction [IF164](INTERPRETER-FINDINGS.md#if164))*. A fired pattern comparison is always a VALUE error, and an empty string violates no pattern ([§2](#2-non-specified-empty-values)) *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §2, locked by `EmptyValueLawsTest`)*.
- `+` is overloaded — numeric **addition** between Number operands, string **concatenation** between strings. The guide documents no general operand-dispatch rule beyond one pitfall: a string literal shaped like a date parses as a *date constant* and so cannot be concatenated (see [§6](#6-dates-and-time)).

*Reference: Models → Field types → String; Operators and language constructs → String operations; Miscellaneous → PatternMatched and PatternViolated.*

## 8. Enumerations

- Rule conditions compare the stored enumeration **value**, not the displayed text: write `[Country] == "F"`, not `[Country] == "France"`.
- Direct String/Enumeration comparability uses **effective display remapping**, not syntactic label presence. An Enumeration with no labels or only identity labels (display equals stored token for every member) is effectively textless and may compare with a String or another effectively textless Enumeration. Two Enumeration fields must share that effective class; if both are display-bearing, their mappings must be bidirectionally consistent in every shared locale: one shared stored token cannot have two displays, and one shared display cannot denote two stored tokens. Disjoint and partially overlapping compatible maps are accepted. `==` and `!=` share this gate *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §8, locked by `EnumComparabilityLawsTest`)*.
- Enumeration values can carry named category attributes, read with the `->` operator: `[Country -> AdministrationArea] != "EU"`. The category mapping is **positional** (`values[i]` categorizes enum value *i*) and many-to-one — the comparison fires for *every* value sharing the category value; an empty enum rides the not-evaluated track, category hop or not *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §8, locked by `EnumCategoryLawsTest` + `EnumCategoryDiffTest`)*.

### The value-list quantifiers — per-cell classification, and the `No` poison asymmetry

`AtLeastOne` / `No` / `NotAll` `…FieldValue(s)IncludedInValueList(f1, f2 In v1, …)` expand **both** sides per cell (a starred entry contributes one cell per instantiated row) and classify each by the three-way state — filled / empty / not-check-relevant (UNKNOWN, [§3](#3-formal-errors-and-the-unknown-state)):

**Admission (authoring).** For a literal value list over Enumerations, each literal must be in the **union** of the selected members' projected domains — a *direct* reference contributes its stored values, a *category* access `[field -> Cat]` contributes that category's values — and need **not** be in every member. A member may itself be a category projection, and a direct reference and a `[field -> Cat]` reference on the **same** field are **distinct** members; no exact reference may repeat. When the value list is itself a **field list** (entity-valued), both sides share one base type (String/Enumeration/Number) and carry no duplicate reference across the combined lists, but enum-domain **containment is not required**.

Each operator owns its **own pass structure** over the two operand lists — a side is never flattened into one aggregate UNKNOWN/filter summary; encounter order and the deciding operand matter:

- **`AtLeastOne`** consumes the complete values side first (empty and UNKNOWN member cells skipped outright; an empty value *set* → no fire), then scans fields in authored order to the first present match. Fired polarity follows the **decider**: OMISSION iff the matching fields operand is filtered or a filtered values operand selected a *present* member — an earlier filtered nonwitness, or a filtered values operand that kept only empty/UNKNOWN cells (or nothing), never escalates; else VALUE.
- **`No`** materializes the complete values side before fields — an UNKNOWN member **poisons** it (no fire; a fields-side match cannot rescue), while an empty member, an omitted declared tail, or a **reached values-side filter** (whatever it kept) contributes sticky omission potential. It then scans fields in authored cell order: a **match terminates non-firing before every later cell** (a later UNKNOWN/filter/tail is never reached), while a reached UNKNOWN before the match suppresses. An exhausted scan fires — including when nothing is filled at all (the sole member that can fire empty) — OMISSION iff any reached empty fields-cell / omitted tail / filter occurred or the values side carries omission potential, else VALUE.
- **`NotAll`** does not fire when the fields side has no present cell, and an UNKNOWN values member cannot poison that outcome. *(Whether the values side is even consumed in that case is a route detail, not the contract: the ordinary emission short-circuits on a fields-presence prepass before touching the values side, while the optimized emission hoists the values side ahead of the whole condition and has no prepass. The two agree because the membership test counts only given cells — so with no present fields cell the un-prepassed route collapses to the same non-firing result. Never restate the prepass as the observable contract: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) "the value-list quantifiers have TWO emission routes".)* Otherwise it consumes the values side with `No`'s classification, then **restarts** the fields scan and fires at the first present cell outside the set; an UNKNOWN fields-cell is merely skipped — the `No`-vs-`NotAll` asymmetry. The fire is OMISSION iff the outside-**witness** operand is filtered or the values side carries omission potential — it has no fields-side empty/tail account.
- An empty values **member** contributes nothing to the set (never a substituted `0`) but flags a fired `No`/`NotAll` OMISSION. A `Having` filter is accepted on either side and drops rows **before** the per-cell classification; its polarity effect is encounter- and witness-specific per the pass structures above — never one unconditional side-wide flag ([§12](#12-the-validation-model)).
- A **category projection** cell takes the underlying enum field's three-way presence: an **empty** enum via a category hop is an EMPTY cell (a fired `No` is OMISSION, and it does not poison), an out-of-domain enum is UNKNOWN, and a filled enum contributes its many-to-one category value.
- In **partial validation** a *starred* entry additionally carries a **complete-extent** fact, separate from per-cell relevance: it is established as soon as **one** relevant identifier covering the entry wildcards every repeatable level the entry reopens, asked per iteration row. `No` (either side) and `NotAll` (values side) are UNKNOWN when no such identifier exists — concrete rows, even all of them, do not establish it, and a concrete identifier beside a qualifying wildcard does not destroy it. This is the value-list half of the [§12](#12-the-validation-model) extent gate, and it is deliberately **weaker** than the all-rows aggregates' half ([IF264](INTERPRETER-FINDINGS.md#if264)).

*(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §8 / [IF60](INTERPRETER-FINDINGS.md#if60) + [IF74](INTERPRETER-FINDINGS.md#if74) + SPEC-2026-07-22-05 + SPEC-2026-07-23-16, locked by `ValueListQuantifierDiffTest` + `ValueListQuantifierStarDiffTest` + `EntityValueListDiffTest` + `ValueListQuantifierHavingDiffTest` + `ValueListQuantifierOrderDiffTest` + `EnumValueListUnionDiffTest` + `EnumValueListUnionLawsTest` + `EnumCategoryValueListReadTest` + `EnumCategoryValueListEvalTest` + `ValueListQuantifierOrderEvalTest`)*

*Reference: Operators and language constructs → Comparison operations → Comparing strings and enumerations; The Field value operator.*

## 9. Repetition, iteration, and cross-array evaluation

The repetition model is the kernel's most distinctive — and most easily mis-authored — semantics. A flat rule fires zero or one time; a rule over repeatable data fires *per row*, and several constructs turn it into what is effectively a small query language over arrays.

### When a rule iterates, and where its error lands

A rule **iterates when its condition references repeatable fields**: the iteration scope **derives from the checked condition's iteration-bearing references alone** — an ordinary (non-starred) reference contributes its deepest repeatable ancestor-or-self, compatible **nested** references select the **deepest** path, and a starred (`*`) reference stays operand-local (its binding levels iterate; the starred level and below collapse into the aggregate — see the filter subsection below). Neither the rule node's placement nor the error field's declaration adds an iteration level. The error field is **separately validated**, never a scope selector: it must be *referenced* by the condition, directly or indirectly (an enclosing `GroupFilled(Group)` counts, else `MVK_ERROR_FIELD_NOT_REFERENCED`), and it must *inhabit a compatible scope* (a genuine cross-cardinality split is rejected, `MVK_ERROR_FIELD_NOT_IN_RULEGROUP`) *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §9, locked by `IterationLawsTest`)*.

An iterating validation rule is evaluated once per **validation iteration row** of the derived scope, in document order with complete parent coordinates. Concrete rows participate normally. In addition, below every existing repeatable parent iteration row, a nested repeatable scope with no concrete child contributes one implicit child at coordinate 1, recursively; an absent outermost repeatable group still contributes no row. Under a nested scope an outer operand resolves against the current row's own parents, and each message attaches to that exact row. The implicit child is not stored content: it does not make `GroupFilled`, starred operands, mandatory/`uniqueIndex`, parallel identity, or computation see a concrete row; `RepetitionNotUnique` does consume it because it is a validation relation *(verified: [KF179](KERNEL-FINDINGS.md#kf179) / [IF277](INTERPRETER-FINDINGS.md#if277), locked by `RepeatableRowContentDiffTest` + the multiplatform `ReferenceDrivenIterationScopeTest`)*. For example, with rule group `Casino`, error field `Round` inside a repeatable `Poker` group, `FieldFilled(Poker/Round) And [Poker/Win_Loss] >= 0` reports on each offending concrete round, while an implicit empty round cannot pass the positive `FieldFilled` guard.

Static admission rejects particular operator/operand shapes that may fire on a not-filled repetition, such as an unguarded `FieldNotFilled(F)`, with `MVK_NEG_CONDITION_IN_ITERATION` naming the offending level. It is not a blanket guarantee that every accepted rule is silent on an implicit row: the accepted `Qty < 5` discriminator fires OMISSION there through empty-as-zero. **This admission is checked independently at every ordinary iteration level, and it is operator- AND operand-sensitive — not a fixed list of "negative" operators.** Per level, `And` needs one child that both references and is admitted there, while `Or` needs *every* child to. For a starred group-list leaf, the operand references only the captured prefix strictly above its first star: `AtLeastOneGroupFilled` is admitted at the queried level exactly when every list operand references it (a fixed peer outside that prefix makes the mixed list unguarded), whereas `NoGroupFilled` is unguarded whenever any operand references it; the ordinary `And`/`Or` rules then compose that classification *(locked by `StarredGroupListIterationAdmissionLawsTest`, with exact-outer-row runtime control in `StarredGroupListIterationScopeDiffTest` + `StarredGroupListIterationScopeTest`)*. For a direct iterating Number field against an immediate literal, ordinary `==`/`>=`/`<=` are unguarded exactly when the literal's **host-converted integer form is zero** (`Double.parseDouble` → `Math.round` → `(int)`), symmetrically in both operand orders — so `== 0.50` is admitted (rounds to 1) while `== -0.50` is rejected (half-up toward +∞ rounds to 0); strict `>`/`<`, ordinary `!=`, and any converted-nonzero literal are admitted. **The `(int)` narrowing is reachable too, and is the sharpest instance:** on a scale-0 field `== 4294967296` is *rejected* — 2^32 narrows to zero, so a literal of four billion classifies as zero — while `== 4294967297` is admitted. **The `parseDouble` step is equally part of the separator**, so the classifier is *not* exact-decimal: binary64 round-to-nearest-even lifts every decimal in `[½ − 2⁻⁵⁵, ½)` onto `0.5`, which then rounds to 1 — reachable on a scale-14 field once the (suppressible) dec-places gate is lifted, where `== 0.49999999999999998` is admitted while `== 0.49999999999999990` is rejected. Direct field *operations* keep that partition (`Abs`, all-iterating operand-list `MinValue`/`MaxValue`, evaluated-String `Length`), but a top-level **arithmetic** expression is a composite operation with no direct-operand branch — so `[Count] + 0 == 0` is admitted where `[Count] == 0` is rejected, changing static admission without changing runtime arithmetic *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §9 supplement "ordinary-iteration negative admission", locked by `RuleGroupIterationLawsTest`)*.

Two verified boundary rules sharpen this: the **error entity alone is not an anchor** — a rule whose error field sits deeper-repeatable than its condition references keeps the references' scope *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §9 / [IF106](INTERPRETER-FINDINGS.md#if106), locked by `CollectivelyFilledGroupScopeDiffTest`)* — and a rule with **no repeatable (non-starred) reference evaluates exactly once**, anchored at its error entity, regardless of its declaring container's instance content; the declaring group matters only for resolving relative references *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §9 / [IF103](INTERPRETER-FINDINGS.md#if103), locked by `CrossRootRuleScopeDiffTest`)*.

*Reference: Rules → Rules and repeatability → Iteration; Rules → Error Field.*

### Parallel iteration — joining two repeatable groups by key

When a rule references two repeatable groups where neither is nested in the other, they are iterated **jointly, keyed by an Index Field** that must exist on each group and **share the same name and type**. This is an *outer join* over the index values: a group with no row for a given index value counts as "not specified" for that iteration.

```
FieldsNotCollectivelyFilled(Demand/Units, Capacity/Units)   ;; iterated per shared Warehouse index value
```

Constraints (from the guide): at most **one** index field on the error field's path and on each parallel-iterated group; parallel iteration is **not allowed over rules using `RepetitionNotUnique`**; and **negative conditions are not allowed in a parallel iteration** except alongside a positive condition.

The join's mechanics, verified: the iteration value-set is the **union** of the joined groups' index values; an unmatched side reads "not specified", its pointer carrying the fixed sentinel repetition index `-5` (`IIdentifier.UNKNOWN`). An **invalid** index value — duplicated or empty — marks that group's index invalid for the parent, so references into it read three-valued UNKNOWN for unmatched values, which *suppresses* a negative operator like `FieldsNotCollectivelyFilled`. Non-repeatable intermediate groups are transparent to the join; a repeatable non-indexed *frame* is legal above exactly one joined group *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §9 / [IF19](INTERPRETER-FINDINGS.md#if19), locked by `ParallelIterationDiffTest`)*.

*Reference: Rules → Rules and repeatability → Parallel Iteration.*

### The filter operator `Having`, the `$` correlation, and aggregation

`Having` filters a repetition list (a `*`-path) down to the rows where a condition holds, before an aggregate consumes it:

```
Sum(Products*/Quantity Having [Products/ProductName] == "N33") > 100
```

A candidate is retained only when the **complete filter result is known TRUE**. FALSE or UNKNOWN drops it before the aggregate or quantifier reads the selected cell; this is still ordinary three-valued condition evaluation, so a complete condition such as `TRUE Or UNKNOWN` is TRUE and keeps the candidate.

In **computation**, the same condition tree runs without validation's unknown-as-drop projection: a formally-invalid filter operand that is actually reached poisons the reading computation ([§11](#11-computations)). Filter and target reads are interleaved by **one kept-successor lookahead** — after a candidate is kept, the iterator searches through later FALSE candidates for the next kept candidate *before* the consumer reads the current candidate's target. A poison met during that search therefore precedes a filled pending target; once one successor is kept, a terminal current target leaves every filter after that successor unread; and an earlier terminal authored operand still hides a later filtered operand completely. This is neither eager whole-selection filtering nor target-first row evaluation — though for the consume-every-row aggregates the distinction collapses (a compute poison is reported cause-blind), so the boundary is outcome-observable exactly through `FirstFilledValue`'s prefix stop *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §9/§11 / [IF214](INTERPRETER-FINDINGS.md#if214), locked by `FirstFilledValueKeptSuccessorDiffTest` + `AggregateKeptSuccessorDiffTest`)*.

The **`$` operator** — usable **only inside a filter condition** — pins a reference to the **complete current outer repetition environment** of the iterating rule, turning the filter into a *correlated subquery* (e.g. "holidays whose date equals the current stop's ETA"). The reference's own resolved group/path chooses the coordinate at that named repetition level: within one nested outer row, `$Parent` and `$Parent/Child` may therefore yield different indices. It is not one scalar “outer row number” copied to every marked path. Not every reference in a filter may be `$`-marked. `$` is not optional sugar: a filter may only iterate the repetition levels the filtered field stars, so `$` is the **sole** way a filter references an out-of-scope (outer) field *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §9 / [IF178](INTERPRETER-FINDINGS.md#if178), locked by `CorrelationLawsTest` + `CapturedOuterEnvironmentDiffTest`)*.

Correlation does not imply self-exclusion. A same-group candidate set includes the current outer coordinate unless the filter explicitly excludes it with `CurrentRepetition(G) != CurrentRepetition($G)`. `CurrentRepetition(G)` compares the coordinate of the **named repetition level**, not physical-row identity: in an `A*/B*` candidate set, comparing only `B` excludes every candidate with the same `B` leaf index across different `A` rows *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §9, locked by `CorrelationLawsTest` + `SelfCorrelatedOverlapQuantifierDiffTest` + `MultiStarOuterCorrelationDiffTest`)*.

### Where a star binds — the anchor rules

- A starred operand read from an iterating row binds the enclosing indices only for the repeatable levels **strictly above the (first) `*`** — the starred level itself always iterates its full extent. A **same-group star** therefore spans *all* rows, not the current one (only `$` correlates; a bare star never does), and a multi-star operand `A*/B*/F` binds at the levels above `A` *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §9 / [IF93](INTERPRETER-FINDINGS.md#if93) + [IF94](INTERPRETER-FINDINGS.md#if94), locked by `ComputeStarAggregatePoisonDiffTest` + `MultiStarFilteredCountDiffTest`)*.
- Declared-tail polarity follows that same boundary **hierarchically**: for `A*/B*/C*/F`, missing declared capacity at `A`, beneath any actual `A` at `B`, or beneath any actual `A/B` at `C` keeps the result fillable; an unbounded starred repetition always retains an open tail; a repeatable ancestor above the first star stays bound and contributes no tail. This is not reducible to the deepest flattened row count versus the deepest cap *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §9 / [IF194](INTERPRETER-FINDINGS.md#if194), locked by `MultiStarDeclaredTailPolarityDiffTest` + `StarOnlyIterationScopeDiffTest`)*.
- A **cross-subtree** star binds only along the **shared named ancestry** — an enclosing row's index is never applied positionally to an unrelated chain, so a cross-subtree count or presence reads identically from every iterating row *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §9 / [IF97](INTERPRETER-FINDINGS.md#if97), locked by `CrossSubtreeGroupStarDiffTest`)*.
- A bare (unstarred) reference to a repeatable group in a group-scope quantifier is an iteration anchor of its own — ancestor-or-self, per row, judging the *current* row's cells. It is admitted exactly when the rule's **error field sits inside that group**; otherwise the `*` is required (`MVK_NO_WILDCARD`). Whether the group declares an `indexFieldName` **plays no part** — the same model with and without one yields an identical accept/reject matrix *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §9 / [IF106](INTERPRETER-FINDINGS.md#if106), locked by `CollectivelyFilledGroupScopeDiffTest` + `UnstarredRepeatableGroupIterationLawsTest`; this bullet claimed index-keying as a co-requirement until 2026-08-15, on a fixture that varied both together)*.
- Once that operand is admitted, a **second** gate can still refuse it (`MVK_NEG_CONDITION_IN_ITERATION`, "the rule can fire for not filled repetitions of this repetition level"). That gate is **syntactic**, and reads neither the operator's polarity nor the condition's truth set: `FieldsNotCollectivelyFilled` is negative and admitted, `NumberOfFilledFields(...) < 1` has no negation and is refused, and `< 1` is refused where the equivalent `<= 0` and `== 0` are admitted. Treat it as kernel-owned (`IterationNotValidVisitor`) and do not reimplement it from the condition's meaning *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §9, locked by `UnstarredRepeatableGroupIterationLawsTest`)*.

`FirstFilledValue` applies a static owner entity-list gate before runtime scanning. One fixed group is already-many and is admitted; an exact non-wildcard field or fixed-group duplicate draws `MVK_DUPLICATE_PARAM1`; repeating the same starred group preserves multiple legal authored slots; and a fixed group beside its strict descendant draws `MVK_DUPLICATE_PARAM2`. Exact duplicates are scanned in authored encounter order before overlap is considered: in `(Fixed, Fixed/First, Fixed/First, Fixed)` the field is the repair witness, while reversing which repeat completes first to `(Fixed, Fixed, Fixed/First, Fixed/First)` makes the group the witness. There is no field-before-group class priority. A singleton direct field separately draws `MVK_PARAMSIZE_INVALIDN` *(verified: [KF189](KERNEL-FINDINGS.md#kf189), locked by `FirstFilledValueDuplicatePrecedenceLawsTest` + `FirstFilledValueDuplicatePrecedenceTest`)*.

At runtime, a fixed-group `FirstFilledValue` expands recursively in stable model declaration order, not lexical path order: an earlier `ZetaDirect` wins over `AlphaDirect`, and an earlier `ZetaNested/Value` wins over `AlphaNested/Value`. The scan retains directional prefix polarity rather than assigning one fill state to the whole group. A value in the first direct declaration is VALUE despite later empty declarations, while selecting the second direct or either nested declaration after an empty prefix is OMISSION. A terminal single-level starred group uses the same field-first plan across repetitions, so traversal is **declaration-major**: every instantiated row of an earlier field precedes every row of a later field. Consequently row 2 `First` wins over row 1 `Second`; an immediate row 1 `First` is VALUE despite later rows, while a no-row group star before a direct fallback makes the selected fallback OMISSION *(verified: [KF190](KERNEL-FINDINGS.md#kf190) + [KF191](KERNEL-FINDINGS.md#kf191) / [IF302](INTERPRETER-FINDINGS.md#if302), locked on both kernel strategies and the JVM/Node interpreter by `FirstFilledValueGroupOperandDiffTest` + `FirstFilledValueGroupOrderTest`)*.

Aggregation handles missing rows **per function**: **`Sum` substitutes `0`** for an unspecified field, whereas **`MaxValue` / `MinValue` ignore** unspecified fields (a Number list with none specified yields `0`; a Date list yields an empty value). The filter condition may **not** contain `CustomCondition`, `RepetitionNotUnique`, a semantic index, a parallel iteration, or a nested filter.

*Reference: Rules → Rules and repeatability → Filter operator (and → Iteration in filter condition); Arithmetic language constructs → Sum / Maximum and Minimum.*

### Other repetition rules

- `GroupFilled(G)` is satisfied for an **empty repeat row that has been created** — for a *repeatable* `G`, "filled" means "the row exists," not "the row has data." For a **non-repeatable** `G`, "filled" means *formally admitted content*: an admitted descendant field or an instantiated repeatable descendant row; the group's own structural presence and a rejected malformed-only value are not content. Error marking is independent: invalid-only yields `GroupFilled = FALSE`, `GroupNotFilled = UNKNOWN`; admitted plus invalid yields `TRUE` / `UNKNOWN`. Group-list tallies leave unavailable groups in neither bucket; the plain multi-group `NumberOfFilledGroups` instead becomes unavailable when any operand group is erroneous. A non-repeatable terminal below starred ancestors retains this product **per complete selected ancestor environment** — ancestor rows do not fill it, and malformed-only does not become empty — while a terminal repeatable `G*` retains its structural row count. Partial validation can prove positive presence from one relevant descendant, but proves an empty group only under full-group relevance *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §4/§9 / [IF193](INTERPRETER-FINDINGS.md#if193), locked by `GroupFilledDiffTest` + `NonRepGroupFilledContentDiffTest` + `GroupPresenceFormalInvalidDiffTest` + `GroupPresenceAdmissionDiffTest` + `NonRepeatableGroupBelowStarDiffTest`)*.
- Negative conditions (those that hold when nothing is specified) are not permitted in combination with repeatable groups; the parser rejects them (`MVK_NEG_CONDITION_IN_ITERATION`) unless guarded, e.g. `GroupFilled(K) And AtLeastOneFieldFilled(K/F)`. **"Negative" here is a property of the operator *and its operands*, decided per iteration level, not a fixed operator list** — see the per-level connective and converted-zero rules under "When a rule iterates".
- List predicates over a repeatable group with `*` consider **all possible** repetitions, including unspecified ones, not only those that hold data.
- An instance **beyond a group's effective repetition maximum** draws a structural VALUE error, and the over-limit rows' ordinary checks are suppressed ([§3](#3-formal-errors-and-the-unknown-state)); creating that group row still supplies structural content to its non-repeatable ancestors. A repeatable group beyond its declared maximum uses `zuGrosseZeile` / `zuGrosseKontextnummer`; a non-repeatable group has effective maximum 1 and coordinate 2 uses `zuGrosseLfdNummer` for the group and descendants. A field's own terminal coordinate is not a repetition axis: anything other than 1 is refused by Kernel document conversion before validation, whereas an over-limit **group** coordinate remains representable for formal validation *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §9 / [IF27](INTERPRETER-FINDINGS.md#if27) + [IF193](INTERPRETER-FINDINGS.md#if193), locked by `OverRepetitionDiffTest` + `OverRepetitionFormalGateDiffTest` + `GroupPresenceAdmissionDiffTest`)*.
- `NumberOfFilledGroups` has the same static operand boundary in rules and computations. The plain form admits a fixed list of distinct, disjoint non-repeatable groups (pairs and triples are kernel-measured); the starred form admits a repeatable `G*` alone or beside fixed groups. One fixed group is `MVK_PARAMSIZE_INVALIDGN`, an exact duplicate is `MVK_DUPLICATE_PARAM1`, and ancestor/descendant overlap (including a root beside its contained group) is `MVK_DUPLICATE_PARAM2`. An unstarred repeatable group has no locus-free diagnostic: it is `MVK_NO_WILDCARD` when the error field sits outside that group and reaches `MVK_PARAMSIZE_INVALIDGN` as a singleton when the error field sits inside; the starred form is admitted from either locus. These are admission facts only; starred computation runtime behavior is not inferred from them. **"At least N rows" is expressible** via the starred single-group count: `NumberOfFilledGroups(G*)` counts one repeatable group's instantiated rows *including zero*, so `NumberOfFilledGroups(Items*) < N` fires at 0…N−1 rows (the aggregate-consumed star does not put the rule into per-row iteration); "at most N" stays structural (`repeatability`) *(verified: [KF185](KERNEL-FINDINGS.md#kf185) / [IF46](INTERPRETER-FINDINGS.md#if46), locked by `GroupListDiagnosticIdentityLawsTest` + `RootGroupCountLawsTest` + `NumberOfFilledGroupsStarDiffTest`)*.
- `SumOfProducts(A*, B*)` zips its two same-group fields' rows and sums the per-row products; an empty cell reads `0` (its product is `0`), a malformed cell suppresses *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §9, locked by `SumOfProductsDiffTest`)*.
- `FieldValuesNotUnique(f1, f2, …)` — or the starred `FieldValuesNotUnique(G*/f)` over a repetition's rows — fires when two of the operands' **compared** values are equal, where equality is the **typed** comparison (a scale-0 `5` equals a scale-2 `5.00`). A cell contributes nothing when it is empty **or** when its stored value cannot be converted to the declared type: both are skipped, so two empties are not a duplicate and neither are two *equal* unconvertible values, while a duplicate elsewhere in the list still fires. The operand list is consumed as an **ordered scan that returns at the first duplicate**, which is what makes a `Having` escalate the firing to an omission **positionally** — only through a cell that yielded a compared value before that duplicate, so a filter authored after it, or one whose kept cells are all empty or all unconvertible, leaves a value error *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md#kf175), locked by `FieldValuesNotUniqueDiffTest`)*. Its operand list is admitted by three gates: **more than one operand** — a single *direct* field is rejected `MVK_PARAMSIZE_INVALIDN`, while a single *starred* slot is admitted because it expands to a row stream; **an admissible kind** — Boolean, Confirm, and DateRange are refused outright with `MVK_ONLY_STRING_ENUM_NUMBER_DATE_ALLOWED`, every other kind including Custom is admissible; and **one comparability category** for all operands (`MVK_VARYING_TYPES_NOT_ALLOWED`) — {String, Custom}, {Enumeration}, {Number}, or the temporal family {Date, Time, DateTime, DateFragment} — differing Number *scales* excepted, which is what makes the cross-scale equality above reachable. Arity runs before kind, so a direct Confirm singleton still reports `MVK_PARAMSIZE_INVALIDN`. Inside the temporal category every operand must additionally carry one **identical declared format string**, and that gate reads the format rather than the kind: a Date declared `yyyy` beside a DateFragment declared `yyyy` is admitted across kinds, while two Dates differing only in format are refused. Every gate reads the **whole operand list**, so authored position never selects the reported class — an operand offending the kind or format gate reports that code even when an earlier-authored operand already mixes categories, and the mixing code is then absent. The category gate is **stricter than token comparability and not shared with `NumberOfDifferentValues`**, which admits the very String-beside-Enumeration mix this operator refuses *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md#kf173), locked by `FieldValuesNotUniqueAdmissionLawsTest`)*. A temporal operand's compared identity is its **stored text** — the dynamic runtime compares `feldWertIntern`, a source-level reading and not a measurement — and its agreement with the decoded date rests on the **assumption** that one declared format admits one text per value. That assumption holds for every format probed, which is a measured negative rather than an unreachability proof: at the widest legal temporal format (`yyyy`) and across the cross-kind `Date`-beside-`DateFragment` pair the format gate admits, every near-miss spelling — zero-padded, signed, blank-led — is refused at input checking, so no storable document separates the two accounts and either implementation is conformant there. Our interpreter compares the decoded ISO form instead, and dynamic-Groovy, static-Java and the interpreter agree on every probed row *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md#kf175), locked by `FieldValuesNotUniqueDiffTest`)*.

### `RepetitionNotUnique`, precisely

`RepetitionNotUnique(... @From Group)` checks uniqueness within the chosen reference group; omitting or changing `@From` changes the scope (e.g. unique per order vs. unique across all orders). The verified mechanics:

- It fires **per row whose (composite) key duplicates another row's** within the scope — a composite key compares as the tuple. An **all-empty** key row is skipped, but among participants (≥ 1 key field filled) **empties match empties**. Polarity: all-filled duplicates are VALUE; a duplicate with an empty (fillable) key component is OMISSION *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §9, locked by `RepetitionNotUniqueDiffTest`)*.
- **A key is any value-validating DIRECT field — there is no Number/String-only restriction** (Enumeration, Date, Time, DateTime, Boolean, Confirm all qualify); a group (`MVK_NO_GROUPS_ALLOWED`), a wildcard (`MVK_NO_WILDCARDS_ALLOWED`), a semantic index (`MVK_SEMANTIC_INDEX_NOT_ALLOWED`), and a String configured without value validation (`MVK_INVALID_RAW_TYPE`) are rejected, and a category is not a referenceable operand. **Equality is per kind:** a Number key compares by scale-19 **value** (`5` ≡ `5.00`); every other kind compares by **exact internally-stored text** — an Enumeration key on its stored **token** (not the display label or category projection, so two different tokens sharing one category do not duplicate). The **temporal** half of that statement is a source-level reading with no behavioral witness, not a measurement: a fixed-width temporal format admits one spelling per instant, so no legal document separates stored-text from parsed-instant keying — the same unreachability [KF175](KERNEL-FINDINGS.md#kf175) records for `FieldValuesNotUnique` *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §9, locked by `RepetitionNotUniqueKeyKindLawsTest` + `RepetitionNotUniqueKeyKindDiffTest` + multiplatform `RepetitionNotUniqueKeyKindTest`)*.
- It is a per-row **3VL predicate**: a guard conjunct gates *firing*, but the duplicate cache is built over the full scope **independent of the guard** — a guard-false duplicate does not fire yet still makes its partner a duplicate *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §9 / [IF62](INTERPRETER-FINDINGS.md#if62), locked by `RepetitionNotUniqueGuardedDiffTest`)*.
- A **formally-invalid key cell drops its row from the cache**, per key cell: malformed, duplicate-index, over-repetition, and **required-empty** cells all count as unknown — the distinguishing property is *requiredness, not emptiness* (an optional-empty cell is a valid null participant); a formal error on a *non-key* field of the same row does not drop it *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §9 / [IF64](INTERPRETER-FINDINGS.md#if64), locked by `RepetitionNotUniqueFormalKeyDiffTest`)*.
- The **default reference group** (no `@From`) is the *first repeatable group below the rule group* on the key path, and uniqueness is checked per that group's **parent row** — a key two repeatable levels deep is checked across all inner rows of the whole outer scope, not per intermediate group; `@From` overrides the reference group *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §9, locked by `RepetitionNotUniqueNestedDiffTest`)*.
- Every component of a composite key must lie on one group hierarchy path; parallel branches are rejected `MVK_NOT_IN_SAME_PATH`. Components may sit at different depths on that path, and their authored order does not choose the row domain: `(Outer/Marker, Inner/Optional)` and its reversal produce the same duplicate rows and polarity. The deepest key parent supplies the concrete row coordinates while ancestor components resolve against those rows' own parent coordinates *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §9 / [IF278](INTERPRETER-FINDINGS.md#if278), locked by `RepetitionNotUniqueKeyOrderDiffTest` + `IterationLawsTest`)*.

*Reference: Predicate language constructs for Groups → GroupFilled and GroupNotFilled; Predicate language constructs for Field lists → RepetitionNotUnique.*

## 10. Paths and references

- A field or group named like a keyword (`And`, `Date`, `Today`, …) must be single-quoted in a path: `FieldFilled(Order/'Date')`.
- **`RuleGroup`** references the rule's own containing group as an entity: `GroupFilled(RuleGroup)` validates and counts as referencing the error field; a star on it is rejected *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) "Condition directives", locked by `DirectiveLawsTest`)*.
- Paths are **absolute** (`/Order/Quantity`) or **relative** (`../Other`). The guide favours relative paths within a rule's group — they are shorter and survive the group being moved. One combination *requires* absolute, though: a relative `..` up-navigation may not be combined with the `*` asterisk (`MVK_INVALID_WILDCARD_REL` — "use the absolute path notation"), so reaching upward *and* across all repetitions must be written absolutely (e.g. `/A*/F`) — which is why `CrossArrayDemo` uses absolute paths. A field elsewhere in the model may also be referenced by its bare **short name** (e.g. `[Quantity]`) when the model sets `fieldRefByShortNameAllowed` — the resolution order is the next bullet's — as this demo does.
- **A bare segment resolves declaring-group-first, then (flag-gated) model-wide — there is no ancestor walk.** A bare name first resolves against the rule's declaring group (regardless of any flag). Only on a miss, for a relative reference with `fieldRefByShortNameAllowed` on, a model-wide **unique field short-name** lookup over the model's fields runs: > 1 match is `MVK_FIELDNAME_NOT_UNIQUE` (never a silent pick), 0 falls through to `MVK_INVALID_ENTITY`; the serialized condition retains the short name. An ancestor's field is **not** found by its bare name — `[Tier]` from a rule at `/Subscription/Addons` is rejected `MVK_INVALID_ENTITY` with the flag off; reaching an ancestor takes explicit `../` navigation or the flag-gated, model-unique short-name fallback *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §10 / [IF119](INTERPRETER-FINDINGS.md#if119), locked by `ShortNameRefDiffTest` + `PathLawsTest`; corrects this section's earlier "then upward" tier — the original observation was the flag-gated fallback firing, not an ancestor lookup)*.
- In a **`..Name/rest`** path the up-count comes only from the `..` tokens; the trailing name merely *names* (and validates) the ancestor landed on — a matching `..Name/rest` resolves exactly like `../rest` *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §10 / [IF55](INTERPRETER-FINDINGS.md#if55), locked by `NamedAncestorPathDiffTest`)*.
- The asterisk `*` flattens a repeatable group into the list of its rows; if an outer repeatable group uses `*`, every repeatable group below it in the path must also use `*`.
- The `$` operator (a correlated reference to the current row) may be used only inside a filter condition, and not every reference in the filter may be `$`-marked.
- `CurrentRepetition(G) == n` cannot stand alone; it must be combined with a condition that ensures the repetition is filled.
- **A row is addressed by semantic key, never by position**: the language has no `[Field At n]`, no neighbour offset — `CurrentRepetition` *yields* an index to compare (or `$`-correlate), never one to select with; the only row-addressing form is the semantic index `[Field For key]` *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §9, grammar-verified; the construct inventory is CI-locked by `adapter.KernelConstructParityTest`)*.
- The semantic index (`Group For "value"`) is unsupported in several combinations (multiple repetition layers, several index fields, under an asterisk, and with certain predicates).
- **Index-key identity is owned by the declared index-field kind** (the kernel's `IndexFieldCache.normalizeValue`). A **Number** index field normalizes **both** the admitted stored key and the requested literal-or-field-valued key numerically, so legal decimal spellings such as `5` and `5.00` select the same row; every **non-Number** index field uses **exact internally-stored text** (a String key that visibly resembles a number is not numerically normalized). Cache membership/relevance and formal admission precede that projection: an over-limit cell is outside the cache and neither keys nor compromises; an in-cache empty, non-relevant, built-in-invalid, or registered-custom-invalid stored cell contributes no key or collision participant and compromises an unresolved lookup; a duplicated admitted key selects no row. These stages apply to semantic read/presence, contained-field scans, parallel joins, auto uniqueness, starred index consumers, and computation; the same per-kind split also appears in `RepetitionNotUnique`, whose membership relation is separate *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §9, locked by `NumericIndexKeyDiffTest` + `IndexIdentityCustomTypeDiffTest`, the String separator in `SemanticIndexDiffTest`, and JVM/Node by `SemanticIndexNumberKeyTest` + `CustomFieldTypeMultiplatformTest`)*.
- **What a semantic-index read yields**: a matched, filled cell is its value; a **clean no-match** and a matched-but-empty target cell both read as the kind's empty value ([§2](#2-non-specified-empty-values) — a number reads the fillable `0`, a fired `== 0` types OMISSION). As a **presence** operand, a clean absent row is judged like an empty cell (FALSE — `FieldNotFilled(X For "k")` fires when no row carries the key); an unavailable key/column is UNKNOWN, so neither `FieldFilled` nor `FieldNotFilled` fires. This includes an empty field-valued query when an empty, unavailable, or duplicated in-cache index cell compromises the column. A target below an indexed group inherits its nearest indexed ancestor: the key selects that outer row while coordinates through the authored target group remain ordinary iteration coordinates. Message-pointer targeting is a distinct, authored-syntax stage. An ordinary message reference to the repeated error field, directly or through a containing group, keeps physical iteration authoritative. Otherwise only semantic refs whose payload is the repeated error field or an ancestor group containing it count; one exact authored key target reanchors to its selected row or `[-5]` on clean no-match, preserving coordinates through the deepest error-containing selector and defaulting lower levels to row 1 independently of operand order. Two distinct authored key expressions fall back to ordinary error-field iteration even if Number normalization or current field values make both select the same row. Semantic refs to sibling payload fields do not add pointer targets *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §9 / [IF59](INTERPRETER-FINDINGS.md#if59), locked by `NumericIndexKeyDiffTest` + `FirstFilledValueEntitySpecDiffTest` + `SemanticIndexDiffTest` + `SemanticIndexPresenceDiffTest`)*. Validation-side indexed reads are judged **per lookup** (a malformed key cell elsewhere in the column does not suppress a clean match; an unresolvable no-match over a column with any not-check-relevant cell suppresses the referencing rule) — the compute side is stricter, per column ([§11](#11-computations)) *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §11 / [IF115](INTERPRETER-FINDINGS.md#if115), locked by `IndexedReadSuppressionDiffTest`)*.

## 11. Computations

- **Every computation rule also acts as a validation rule**: if the computed field is filled, its value must equal what the computation produces, or an error is reported. Assigning a time-dependent value such as `Now` to a computed field therefore reports an error as soon as time passes.
- The computed field's declared decimal scale is admitted by the **same constant-capability predicate the `==`/`!=` comparison gate uses** (§5 above), not by equality — which follows from the bullet before this one, since every computation carries an implicit `[target] != <operation>` comparison. Equal scales pass; a **smaller** derived scale also passes *while the whole operation stays constant-capable*, because the capable side pads up to the declared scale (a scale-2 field times the integer literal `100` derives scale 0 and is admitted at declared scale 0, 2, **and** 4); a **larger** derived scale is rejected whether or not the operation is capable, since padding only adds digits. Equality is the special case reached as soon as any **field** reference joins the operation, a field never being capable — so a *smaller* derived scale is admitted upward only while the operation stays capable: `[Rate] * 100` (derived 0, capable) is admitted at declared 0, 2 **and** 4, while `[Rate] + [Surcharge]` (derived 2, capability-free) is rejected at declared 4. *(Corrected 2026-08-11: this read "the same derived scale 4 is admitted at declared scale 2 for `[Rate] * 1.50` and rejected for `[Rate] * [Factor]`", which the lock contradicts — a derived 4 against a declared 2 is a LARGER scale, so both are rejected regardless of capability.)* A rejection is `MVK_INVALID_COMPARE_DEC_PLACES`; wrap the calculation in a rounding construct to match, or suppress that code on the computation to reach the no-fit store arm deliberately *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md#kf174), locked by `ComputedTargetScaleLawsTest`)*. This scale comparison is also decided **before** the self-reference refusal below: over an operation that reads its own target, a derived-scale mismatch is the only code reported, and suppressing that code re-exposes the self-reference underneath it — so such a computation is a two-repair rejection reported one repair at a time. The order holds in either operand position, for `+`/`-`/`*`, and when the self-read sits in a precondition instead *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md#kf181), locked by `ComputedTargetScaleLawsTest`)*.
- A computation table's preconditions must be mutually exclusive, and the computed field may not appear in any precondition — **nor in any operation** (both directions draw the same rejection). The ban is on a *direct field* reference: guarding a repeatable computed field via its **containing group** (`GroupFilled`/`CurrentRepetition` on the group) is legal *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §11, locked by `ComputationAuthoringTest`)*. Reading the computed field **through a projection** — an enum category `[target -> Cat]` or a semantic index `[target For key]` — is a *separate* rejection class, `MVK_ERROR_SEMANTIC_INDEX_OR_CATEGORY_FOR_ERRORFIELD`, whose repair is to drop the projection rather than the reference; it pre-empts the plain class when both readings occur in one operation, and it applies to operations and preconditions alike. Projecting any *other* field is an ordinary computation source *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md#kf182), locked by `ComputedTargetProjectedReadLawsTest`)*.
- A non-repeatable computed field is calculated even when all its inputs are empty (yielding `0` or an empty/space string); add an `AllFieldsFilled(...)` precondition to suppress that. Indirect calculation cycles among computed fields are possible and are not always easy to detect.

*Reference: Computation Rules → Computation Rules as Validation Rules / Number of decimal places / Preconditions / Calculation cycles.*

### One operation, three outcomes — and the operand states that decide them

Validation and computation are **separate operations**: `validateFull` never computes first, and the consumer composes the form-engine flow compute → apply → validate itself, where the apply step writes back only clean values and *empties* errored and cleared instances *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §11/§12 / [IF45](INTERPRETER-FINDINGS.md#if45), locked by `EvalDocSeamLawsTest` + `ComputeApplyDiffTest`)*. Per computed cell the outcome is a **VALUE**, **CLEARED** (no value — a stale stored value is wiped, never left standing), or **ERRORED** (a value the target cannot legally hold, returned but flagged) — the vocabulary [CONFORMANCE-CORPUS-SPEC.md](CONFORMANCE-CORPUS-SPEC.md) §7 fixes. Which outcome an operand's state produces follows [§2](#2-non-specified-empty-values)'s per-kind split, with compute's own twists:

| an operand that is… | NUMBER | DATE | STRING in a concatenation |
|---|---|---|---|
| **empty** | reads `0` — the computation produces a VALUE *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §11, locked by `ComputeDocVerbTest`)* | the operation is not evaluated — CLEARED *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §2, locked by `DateRangeComputationLawsTest`)* | concatenates as `""` — produces a VALUE while some part keeps the final text non-empty (the store gate below) *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §11 / [IF81](INTERPRETER-FINDINGS.md#if81), locked by `ConcatInvalidOperandDiffTest`)* |
| **required and empty** | still `0` — the mandatory error is validation's concern, not compute's *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §11, locked by `ComputeInvalidOperandDiffTest`)* | as empty | still `""` *(verified: [IF81](INTERPRETER-FINDINGS.md#if81), locked by `ConcatInvalidOperandDiffTest`)* |
| **filled but formally invalid** | CLEARED — and the target is poisoned for dependents (below) *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §11 / [IF76](INTERPRETER-FINDINGS.md#if76) + [IF78](INTERPRETER-FINDINGS.md#if78), locked by `ComputeInvalidOperandDiffTest`)* | CLEARED + poison — the rule is type-agnostic *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §11 / [IF78](INTERPRETER-FINDINGS.md#if78))* | CLEARED + poison *(verified: [IF81](INTERPRETER-FINDINGS.md#if81), locked by `ConcatInvalidOperandDiffTest`)* |

The guard consequence cuts both ways: over DATE operands an `AllFieldsFilled` precondition is *redundant* — a false precondition clears exactly as the unevaluated operation does *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §2, locked by `DateRangeComputationLawsTest`)* — while over a NUMBER operand the same guard *changes behaviour*: guarded clears where unguarded computes `0` *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §11, locked by `ComputeDocVerbTest`)*.

The STRING column above is the *concatenation* position's. A **bare string copy** (`X = [S]`, one operand, no `+`) of an empty operand computes nothing — CLEARED, never a stored `""` *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §2, locked by `StringCopyComputeDiffTest`)*. The `FieldValueAsString` coercion of a not-given read follows the same per-context split — a standalone copy CLEARS (the store path treats an empty string value as "no calculation was done"), a concatenation gets `""`; the coercion's operand must be a NUMBER/AMOUNT field (a string copies bare) *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §11 / [IF109](INTERPRETER-FINDINGS.md#if109), locked by `FieldValueAsStringComputeDiffTest`)*.

Behind that per-context split sits one shared **store gate: the root store takes a second decision on the final result value — a final empty string text stores no value, whatever expression produced it.** An **all-empty concatenation** (`[A] + [B]`, both empty — each part substitutes `""` and the result reaches the store as empty text) therefore computes nothing (CLEARED), the same no-value decision as the bare empty copy; the table row's "produces a VALUE" holds only while some part keeps the final text non-empty. The gate is per result kind: a DATE operation with no value already computes nothing, while a NUMBER has no empty arm (empty-as-0 folds to a real `0`, which stores). And the gate **precedes the format check** — an empty final text into a `minLength` target CLEARS, never ERRORED, because the kernel never checks a value it does not store. "No value stored" is also the multi-computation fall-through: a later computation targeting the same cell can still win, and a dependent reads the target as plainly EMPTY. The poison track is separate — an ERRORED computed value stores *with* its error mark, and an invalid-cell read throws — so neither is swallowed by the empty gate *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §11 / [IF123](INTERPRETER-FINDINGS.md#if123), locked by `EmptyConcatStoreDiffTest`)*.

### Two kinds of "no value" — the empty cascade vs the poison

A CLEARED cell is not one thing; *why* it cleared decides what a downstream computation sees:

- **A precondition/no-selection clear cascades as EMPTY.** A field whose computation produced no result because its `commonPrecondition` was false or no alternative held reads as plainly *empty* in a dependent: `FieldFilled(dep)` is false and a number operand reads empty-as-0. The mechanism is that a calculation run strips every calculated field's input value from its working data, so an un-computed calculated field reads empty regardless of what the document stored. Division by zero is **not** in this class: its public no-value/CLEARED delta masks target invalidity and a dependent read poisons *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §11 / [IF77](INTERPRETER-FINDINGS.md#if77) + [IF177](INTERPRETER-FINDINGS.md#if177), locked by `CascadeClearedDependencyDiffTest` + `DivisionDomainFailureComputationDiffTest`)*.
- **An invalidity-clear POISONS.** Reading a formally-invalid cell (an invalid operand's target, an ERRORED computed value, [§3](#3-formal-errors-and-the-unknown-state)'s third state generally) throws inside the computing instance: it aborts, skips its remaining alternatives, produces no value, and is itself marked invalid — so its dependents' reads poison in turn. Across each computed-target dependency edge this is **cause-blind**: a later read observes only that target's invalid membership, never its attempted payload, exception subtype, originating source path/cause, or producer message; the reader is silently marked invalid with no cascade message. Distinct invalid producer classes therefore collapse to the same dependent result, while a clean precondition/no-selection clear remains the EMPTY-reading class above *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §11 / SPEC-2026-07-26-04, locked by dual-strategy `ComputedDependencyCauseErasureDiffTest` + JVM/JS `ComputedDependencyCauseErasureTest`)*. The poison is **read-driven and therefore order-dependent**: for a clean left result, compute's `And` skips the right on FALSE or UNKNOWN, while `Or` skips the right only on TRUE; a poisoned left aborts either expression. The quantifier scans use [§1](#1-truth-values-and-logical-evaluation)'s operator-specific stops; both composite predicates restart their second component scan from the beginning, so only a suffix after the complete predicate's final decision is unread *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §11 / [IF85](INTERPRETER-FINDINGS.md#if85) + [IF147](INTERPRETER-FINDINGS.md#if147) + [IF40](INTERPRETER-FINDINGS.md#if40), locked by `ComputationFillQuantifierScanContractTest`, `FilteredStarComputeFormalInvalidityTest`, `ComputePoisonReadDiffTest`, and `ComputeCascadeErroredDiffTest`)*. `FirstFilledValue` is the one **stop-at-first** value combiner: it consumes its selection only until the first filled cell, so an invalid *tail* cell is invisible, while an invalid cell *before* the first given one clears the computation *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §11 / [IF111](INTERPRETER-FINDINGS.md#if111), locked by `FirstFilledValueInvalidTailDiffTest`)*. A reached **filtered** star adds [§9](#9-repetition-iteration-and-cross-array-evaluation)'s one-kept-successor lookahead: a filter poison met while locating the next kept candidate precedes the pending current target, while a terminal current target hides filters beyond the prefetched successor and every later authored operand *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §9/§11 / [IF214](INTERPRETER-FINDINGS.md#if214), locked by `FirstFilledValueKeptSuccessorDiffTest` + `AggregateKeptSuccessorDiffTest`)*.
- **Both cascade read-rules reach *inside* a downstream computation's `Having` filter and its preconditions' quantifiers** — a silently-cleared upstream target reads EMPTY there, a poisoned one poisons the reading computation *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §11 / [IF98](INTERPRETER-FINDINGS.md#if98), locked by `HavingOverComputedDependencyDiffTest`)*.

`compute` returns a **five-channel result** (`IDocumentComputationResult`), not a delta: all successful instances *including unchanged* (`getComputedFieldInstancesWithoutErrors`), their changed subset (`getComputedFieldInstancesWithChanges`), the errored instances, the cleared instances, and the operand-level formal errors (`getFormalErrorsInOperands`) — with `noErrorOccurred` true exactly when the errored **and** formal-operand channels are both empty. The VALUE/CLEARED/ERRORED vocabulary above is the three-channel **change projection** our corpus, differential, and `applyTo` select from it — a VALUE only when the computed V2 object differs from the source V2 object, CLEARED only when the source cell was filled, ERRORED unconditionally. For a Number, the computed object is a `BigDecimal`: an original `BigDecimal` is unchanged only when coefficient and scale agree, while an original `String` or negative-scale decimal remains changed even when its plain rendering and numeric amount agree. **Time is a measured exception to the intuitive text-equality control:** kernel 30.8.1 puts a clean computed `10:30:45` in `getComputedFieldInstancesWithChanges` even when the source Time already contains `10:30:45`; dynamic Groovy and generated Java agree *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §11 five-channel supplement, locked by `ComputeResultChannelsLawsTest` + `NumberResultSourceIdentityLawsTest` + `ComputedTimeTargetDiffTest` + `ComputeGranularityTest` + `CorpusCaptureTest`)*.

The channel classifications are **source-relative and stable**: `applyTo(DocumentV2)` can apply the result to a separate model-compatible destination, and it does not re-run change equality there. A successful instance unchanged in the source is therefore not written over a different destination value, while a source-classified change is applied; validation remains a separate operation after application. The Time exception above is still source-relative: because the source-identical clock is classified changed, applying that result overwrites a different destination clock *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §11, locked by `ComputeResultChannelsLawsTest.applicationUsesSourceRelativeClassificationsAgainstACompatibleDestination` + `ComputedTimeTargetDiffTest.evenTheSameClockIsSourceClassifiedAsChangedAndApplied`)*.

The same source-relative rule makes a retained **CLEARED action** distinct from recomputing "no value" on the destination. CLEARED is minted only when the source target was filled, but applying that retained action is an unguarded write of `null`: an absent destination target becomes **present-empty**, and missing repeatable ancestors are created through the addressed row. A source with an absent target mints no action and leaves an absent destination absent; ERRORED is destination-presence-guarded and also leaves it absent; changed VALUE creates the missing row and exact value; CLEARED over a filled destination empties it. The interpreter exposes the same boundary as `ComputationReport.actions` plus `applyTo(destination)`; its same-document `applyComputations(document)` is exactly retain-then-apply to that source *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §11 post-application state / [IF239](INTERPRETER-FINDINGS.md#if239), locked on dynamic Groovy + generated Java + standalone interpreter by `SeparateDestinationClearDiffTest` and on JVM + Node by `RetainedComputationResultTest`)*.

Before it computes anything, `compute` runs an **eager operand prepass**: every non-computed field that is an operand of a computation is formally validated — an **invalid value** is reported (in `getFormalErrorsInOperands`), a **required-empty** operand is **silent** (mandatoriness is validation's concern, and an empty numeric operand still reads empty-as-0 for its consumer), and an **empty or non-unique index** field is reported. Computation processing then **continues regardless of those collected errors** — there is no global abort; a focused direct-dependency witness clears the consumer while an unrelated computation proceeds. The inventory itself is not a general scheduling or poison rule: exact operand extraction and the downstream response remain dependency-, schedule-, and reached-read-sensitive under the separate execution semantics above. An erroneous computed instance is **ERRORED only** (never also CLEARED) *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §11 eager-prepass supplement, locked by `ComputationEagerPrepassLawsTest`)*.

The prepass's index half is **selection-scoped and default-aware** (SPEC-2026-07-23-15). The formal-input inventory is a checked-plan union across all computations — direct field references, every field contained by an ordinarily/conditionally referenced group, and the index fields required by semantic-index or parallel-iteration use — traversing operations, preconditions, filters, and semantic-index keys, computed fields excluded; the generated preliminary mandatory/uniqueness rules run **only for index fields that inventory retains**. So an **unused** bad index is silent, while selection is broader than a read trace: **iterating an index group selects its index** even when no operand references it, and a group reference in a precondition, a semantic-index or cross-group parallel-iteration reference, or a `Having`-filter-only reference selects too. Formal ingestion applies **the same full-call index-default staging as full validation** ([§4](#4-the-required-property)): an eligible clean-empty enum index receives its S-value *before* the preliminary rules — no `mandatoryField`, and its consumer computes on the token — while a prepass-invalidated (empty or duplicated) index cell **poisons a computation that reads it**; the inventory remains neither a read trace nor a schedule *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §11 / SPEC-2026-07-23-15, locked by the `ComputationEagerPrepassLawsTest` SPEC-15 arms, dual-strategy, + multiplatform `ComputationIndexDefaultMultiplatformTest`)*.

### The stored form — a computed value lands as a string in the target's declared shape

A computed value is stored in the target field's own declared format: a DATE in that field's `format`, not ISO *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §3 / [IF33](INTERPRETER-FINDINGS.md#if33), locked by `ComputeTargetFormatDiffTest`)*. For DATE this runtime statement has an authoring boundary: kernel 30.8.1 admits the FULL target control but rejects `DAY_OPTIONAL`, `MONTH_OPTIONAL`, and `YEAR_OPTIONAL` computation targets with `MVK_INVALID_DATE_TYPE`, because every computation's implicit comparison reads `[target]`; attempting to suppress that code is itself rejected as `MVK_INVALID_SUPPRESSED_WARNING` *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §11 / [IF237](INTERPRETER-FINDINGS.md#if237), locked by `ComputedPartialDateTargetAdmissionDiffTest`)*. A computed TIME lands as the exact `HH:mm:ss` clock: `Time(Hour, Minute, Second)` and `TimeFromDateTime(source)` both produce `10:30:45` under UTC and Europe/Berlin, and a rule evaluated after application sees `10:30:45`, never the UTC decoding of the typed V2 transport's 1970 model-zone `Instant`. Missing, impossible, or formally unavailable constructor components clear a stale target; the source-identical successful clock still follows the measured changed-channel exception above *(verified: [IF238](INTERPRETER-FINDINGS.md#if238), locked by dual-strategy `ComputedTimeTargetDiffTest` + JVM/Node `ComputedTimeTargetTest`)*. A NUMBER uses one store path shared by both kernel strategies — first a scale-19 pre-round, then one of two arms. When the natural scale fits the target, the render is **padded to the target's `minFractionalDigits`** (`10` into a two-decimal field stores `10.00`) with *no* length cap, so an over-long result stores in full and is ERRORED by the ordinary digit checks rather than re-rounded to fit. When the natural scale exceeds the target's maximum, the kernel renders at most 16 significant digits and marks the result ERRORED unconditionally; this no-fit arm is reachable on a legal model through the computation's `errorCodesToSuppress: ["MVK_INVALID_COMPARE_DEC_PLACES"]` escape hatch. **Both arms store plain dot-decimal text and never exponent notation** *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §11 / [IF82](INTERPRETER-FINDINGS.md#if82) + [IF92](INTERPRETER-FINDINGS.md#if92), locked by `ComputedNumberScaleDiffTest` + `ComputedNumberDigitOverflowDiffTest`)*. The stored form is what downstream sees: a dependent computation reads the padded string back *(verified: [IF90](INTERPRETER-FINDINGS.md#if90), locked by `CascadeComputedOperandScaleDiffTest`)*, and the change-equality above is scale-sensitive — a computed `7.00` over a stored `7` counts as a change.

A computed result is formal-checked with the **basic** format check only — type format plus declared constraints, *without* the charset / leading-blank / trailing-blank baseline that stored *input* values get — so a computed string starting or ending with a blank stores as a plain VALUE *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §11 / [IF110](INTERPRETER-FINDINGS.md#if110))*. A DATE whose `youngerThan1900Check` is enabled uses that same basic-check owner: an exact computed `1899-12-31` attempt is ERRORED, while `1900-01-01` is a VALUE *(verified: [IF237](INTERPRETER-FINDINGS.md#if237), locked by `DateBefore1900DiffTest`)*.

### Where a computation runs — the target's scope, and the parallel join

- A computation iterates over its **computed field's** repetition scope — where it *writes*, not where its node is declared — and an all-non-repeatable target computes exactly one instance even on an empty document, because a non-repeatable group is implicitly present *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §11 / [IF89](INTERPRETER-FINDINGS.md#if89), locked by `CrossGroupConstantComputeScopeDiffTest`)*. The general law, shared with rules: the iteration scope is the set of referenced repeatable fields, never the node's placement *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §9, locked by `IterationLawsTest`)*.
- Alternatives evaluate top-to-bottom and the **first whose precondition holds** supplies the value; none holding → CLEARED. The mutual-exclusivity requirement above is authoring discipline the runtime does not enforce — overlapping preconditions resolve computation to the first declared, but the implicit validation consumer below retains every holding alternative *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §11 / [IF21](INTERPRETER-FINDINGS.md#if21) + [IF175](INTERPRETER-FINDINGS.md#if175), locked by `ComputationPreconditionDiffTest` + `ComputationEvaluationLawsTest` + `ComputationOverlapValidationDiffTest`)*. Model composition can hand one field several computations; code generation flattens them, in document order, into ONE per-field first-match table, so the first **selected** alternative ends the scan — including when its operation stores no value. Only a computation that was never selected (common precondition false, or no guard matched) falls through to the next *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §11 / [IF87](INTERPRETER-FINDINGS.md#if87), locked by `MultiComputationFieldDiffTest`)*.
- Operands reaching into sibling indexed groups run [§9](#9-repetition-iteration-and-cross-array-evaluation)'s parallel iteration: rows join by the shared **index-field value**, never by physical position; an unmatched side reads empty; the calculation never *creates* a repetition (a key present only on the side group computes nothing); and an invalid index cell in *any* joined group clears **every** instance of the computation — deliberately broader than strictly necessary *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §9/§11 / [IF96](INTERPRETER-FINDINGS.md#if96), locked by `ComputeParallelIterationDiffTest`)*.
- A starred operand read from an iterating row binds the enclosing row only for levels *strictly above* the (first) star — a same-group star spans **all** rows, which is also how one poisoned sibling cell aborts every row's dependent *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §9 / [IF93](INTERPRETER-FINDINGS.md#if93) + [IF94](INTERPRETER-FINDINGS.md#if94), locked by `ComputeStarAggregatePoisonDiffTest` + `MultiStarFilteredCountDiffTest`)*.
- A **semantic-index read is column-strict in compute**: any invalid cell in the index column — malformed, duplicated, or empty — clears *every* reading computation, even one whose key matches a clean row (broader than the validation side's per-lookup rule, [§10](#10-paths-and-references)); over a clean column the compute read equals the validation read (a no-match or matched-but-empty cell reads empty-as-0). A matched **formally-invalid** cell poisons per *read cell*: a sibling computation reading a clean cell of the same row stays a VALUE. Cascade reads use the current computation state for both a field-valued query key and the selected scalar/group payload *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §11 / [IF107](INTERPRETER-FINDINGS.md#if107) + [IF108](INTERPRETER-FINDINGS.md#if108), locked by `SemanticIndexComputeNoMatchDiffTest` + `SemanticIndexMatchedInvalidCellDiffTest`)*.

### The implicit validation rule, precisely

The "also acts as a validation rule" bullet above has an exact generated shape: a field gate `FieldFilled(F) And`, the optional common precondition, then per alternative `(precondition And [F] != operation)`, `Or`-joined — so it fires only when the field is *filled* and **any holding alternative** disagrees with the stored value, with the computation's own name as the fired error code. A cleared-vs-stored mismatch is deliberately not flagged when no alternative holds. These branches reuse the authored guards and operations but **not computation's first-match selector**: if guards overlap, computation takes the first operation while a later holding mismatch can still fire validation *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §11/§12 / [IF65](INTERPRETER-FINDINGS.md#if65) + [IF175](INTERPRETER-FINDINGS.md#if175), locked by `ComputationValidationLawsTest` + `ComputationGuardedValidationDiffTest` + `ComputationOverlapValidationDiffTest`)*.

The generated rule **anchors at the computed field**: its error entity is the target's absolute location — the `computedFieldRelPath` resolved from the computation node, even across sibling subtrees or roots — independent of the declaring container's instance content (an empty declaring container does not silence it); a cross-group computation into a *repeatable* target is unreachable (codegen-rejected) *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §11 / [IF100](INTERPRETER-FINDINGS.md#if100) + [IF66](INTERPRETER-FINDINGS.md#if66), locked by `ImplicitComputationValidationScopeDiffTest` + `MultiRootComputationPointerDiffTest`)*.

## 12. The validation model

### Formal validation vs. rule validation

Formal validation is the set of field-type checks the kernel performs automatically (type, pattern, decimal places, required-by-checkbox). These carry the rule path `formalePruefung` (one of a handful of kernel-internal German identifiers) and make a field "unknown" while they stand. Author-written rules are separate and never block a field from evaluation. See [§3](#3-formal-errors-and-the-unknown-state).

### Severity is metadata: ERROR vs. WARNING vs. INFO

A rule's severity (`ERROR` / `WARNING` / `INFO`) is **metadata on the resulting message**, not part of evaluation — the condition fires identically whatever the severity. Only `ERROR`-severity messages make the document invalid: `IDocumentValidationResult.noErrorOccurred()` returns `true` even when `WARNING`s and `INFO`s are present (it considers only `ERROR`s). So a firing `WARNING` surfaces a message to the user without failing validation — useful for "are you sure?" advisories.

*Reference: Appendix → Validation and formal validation → Errors arising from validation rules; runtime API `IDocumentValidationResult.noErrorOccurred()` (`kernel-md-runtime-api`).*

### Every fired message is typed — VALUE vs OMISSION, "could filling something clear this?"

Beyond severity, every message `validateFull` raises carries a **message type** (`IMessage.getMessageType()`), a dimension the two-valued presentation elsewhere doesn't show: **OMISSION** — filling one or more currently-empty fields could satisfy the rule ("something is missing") — vs **VALUE** — no fill can; only changing a value helps ("what you entered is wrong"). Because empty operands participate in so many firings ([§2](#2-non-specified-empty-values)), the type is what tells a user *which* repair to attempt. Internally the evaluation result is three-state — fired-as-value / fired-as-omission / not-fired — with its own `And`/`Or` algebra and no negation combinator (the language has no `Not`, [§1](#1-truth-values-and-logical-evaluation)): under `And` **omission wins** (filling could still rescue the whole rule), under `Or` **value wins** (the value branch alone convicts) *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §12, locked by `ErrorTypeLawsTest`)*.

### The directional-fill machinery behind the typing

The type is not a per-operator constant — it is computed from **directional fillability**: every operand carries "could this result still grow / still shrink if something were filled", and the enclosing comparison's direction decides whether a fillable direction could clear the firing. The verified load-bearing pieces:

- **The comparison's direction is what consumes the flags — the dispatch rule**: a fired `>` / `>=` types OMISSION iff the left side can still shrink *or* the right can still grow (a fill in either of those directions could un-break the comparison); `<` / `<=` mirror it; a fired `==` is OMISSION iff *any* operand can still move; and a fired `!=` is directional by **which side is larger** — only a fill that could move the larger side down or the smaller side up can restore equality *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §1/§3, locked by `DirectionalPolarityDiffTest`; the `!=` arm is corpus-locked by the portable `empty-polarity` cases)*.
- **An empty number's fillability is asymmetric and sign-aware**: it can always grow, but can shrink only if the field is *signed* — and the trigger is `positivesOnly`, not `minValue`. So `[Unsigned] >= 0` fired on the empty substitution is a VALUE error (no fill breaks `>= 0` from above), while the signed twin is OMISSION *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §1/§3 / [IF9](INTERPRETER-FINDINGS.md#if9), locked by `DirectionalPolarityDiffTest`)*.
- **Fill propagates through arithmetic and the value functions**: write each operand's flags as `(g,s)` for can-grow/can-shrink and its current sign as `sign`. Addition produces `(a.g∨b.g, a.s∨b.s)`; subtraction produces `(a.g∨b.s, a.s∨b.g)`. Multiplication's grow bit is `(a.g∧b.g) ∨ (a.s∧b.s) ∨ (b.sign>0∧a.g) ∨ (b.sign<0∧a.s) ∨ (a.sign>0∧b.g) ∨ (a.sign<0∧b.s)`; its shrink bit is `(a.g∧b.s) ∨ (a.s∧b.g) ∨ (b.sign>0∧a.s) ∨ (b.sign<0∧a.g) ∨ (a.sign>0∧b.s) ∨ (a.sign<0∧b.g)`. Those joint terms matter even when both current signs are zero. Division first rejects a current zero divisor, then applies multiplication to the dividend and reciprocal divisor; reciprocal fill is `(b.s∨(b.sign<0∧b.g), b.g∨(b.sign>0∧b.s))`. `Round*` preserves the flags, `Abs` transforms them with the value's sign, operand-list `Min`/`Max` combine them directionally, and `RangeAsNumber` is grow-only. So `[F] != [A] + [B]` with an empty `B` types OMISSION — the right side can still move *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §1/§3 / [IF69](INTERPRETER-FINDINGS.md#if69) + [IF71](INTERPRETER-FINDINGS.md#if71), locked by `ArithmeticFillPolarityDiffTest` + `ArithmeticFillBranchTest` + `FunctionFillPolarityDiffTest`)*.
- **Power fillability is a conservative dispatch heuristic, not an exact reachability proof.** The quiet runtime-invalid domains (`0` to a negative exponent and `|exponent| > 1000`) are fixed and never reach comparison typing as a valid numeric result; a fractional exponent is rejected earlier by the authoring gate, and the primitive also fails closed if it sees one. A negative exponent recurses as reciprocal-base to positive exponent, swapping the exponent's directions. For nonnegative admitted values: a fixed exponent uses the exponent-zero and base/parity branches; a fixed base splits at `base > 1`, `base = 1`, `0 < base < 1`, `base = 0`, `−1 < base < 0`, `base = −1`, and `base < −1`, with exponent parity deciding the negative-base directions; when both operands vary, only `base > 1` with neither operand able to shrink is grow-only, and every other branch is conservatively both directions. The intentional zero-base discriminator is observable: `0 ^ empty-unsigned > 0` fires OMISSION, while the signed-exponent twin fires VALUE *(verified against both kernel strategies by `ArithmeticFillPolarityDiffTest`; every pure branch is locked by JVM+Node `ArithmeticFillBranchTest`)*.
- **Each aggregate combiner has its own directions after a present value enters the fold**: incomplete `Sum` grows and shrinks exactly when at least one **missing contributing declaration** is signed; `MaxValue` is grow-only and `MinValue` shrink-only. The all-empty NUMBER identity is the exception above: it is both-directionally fillable for all three operators regardless of signedness. A starred aggregate's un-instantiated declared tail counts as missing, keeping a firing OMISSION until the repetition is exhausted *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §1/§3/§9, locked by `AggDirectionalPolarityDiffTest`, `NumericAggregatePolarityDiffTest`, and `AggregateUncertaintyLawsTest`)*.
- **The counts can only grow** (`NumberOfFilledFields` and family): a fired `count >= n` is VALUE — no fill can lower a count — while `count < n` stays OMISSION *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §1, locked by `MultiFieldAggregateDiffTest` + `NumberOfFilledDiffTest`)*.
- **Dates ride a symmetric combiner**: a fired date comparison types OMISSION iff either side is not-given, regardless of the comparison's direction *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §6 / [IF58](INTERPRETER-FINDINGS.md#if58), locked by `DateAggregateDiffTest`)*.
- **An encountered `Having` filter escalates**: a fired quantifier over a filtered field star is unconditionally OMISSION (whatever the filter kept or dropped), and so is a fired *comparison* consuming a filtered star — every value combiner marks an encountered filtered result "not specified" *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §8/§12 / [IF101](INTERPRETER-FINDINGS.md#if101) + [IF104](INTERPRETER-FINDINGS.md#if104), locked by `HavingQuantifierPolarityDiffTest` + `HavingStarComparisonPolarityDiffTest`)*. `FirstFilledValue` is positional: it encounters each slot's filter immediately before scanning that slot, so a later filter is invisible after an earlier slot supplies the terminal value *(locked by `FirstFilledValueFilterEncounterDiffTest`)*. The filtered **counts** are the exception: they escalate only when the filter actually *counted* a value — a kept-nothing count stays directional grow-only *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §12 / [IF114](INTERPRETER-FINDINGS.md#if114), locked by `FilteredCountPolarityDiffTest`)*. The date-range **overlap predicates** are another non-escalating family — their polarity derives from the filter's placement ([§6](#6-dates-and-time)) — and the **value-list quantifiers** carry witness-/reached-specific filter polarity per their per-operator pass structures ([§8](#8-enumerations), SPEC-2026-07-23-16, locked by `ValueListQuantifierOrderDiffTest`).
- **A concatenation ORs the not-given flag across its parts**: a fired string comparison is OMISSION iff an operand carries the flag, so a concat containing *any* not-given read — an empty field, a no-match indexed read, a not-given coercion — types a fired mismatch OMISSION even though the concatenated string is non-empty *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §12 / [IF113](INTERPRETER-FINDINGS.md#if113), locked by `ConcatNotGivenPolarityDiffTest`)*.

### The same firing rule can carry either type

Because the type is computed from the data, one rule legitimately fires OMISSION on one document and VALUE on another. `NotExactlyOneFieldFilled(A, B)` fired at zero filled **with no unavailable cell** is OMISSION (filling one field reaches exactly one) but at two or more known-filled cells is VALUE (no fill gets back to one) *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §1, locked by `FieldListQuantifierDiffTest` + `ValidationFillQuantifierProjectionDiffTest`)*. `FirstFilledValue` types OMISSION when no row is filled, an instantiated empty row precedes the first filled one, or an encountered operand carries a `Having` filter. It is positionally prefix-sensitive: a filled or formally unavailable value terminates the scan, so later cells, operands, and their filters are invisible *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §1/§3 + §9, locked by `FirstFilledValueDiffTest` + `FirstFilledValueLawsTest` + `FirstFilledValueFilterEncounterDiffTest` + `FullMessageFuzzDiffTest`)*. And `CurrentRepetition` is a structural row index no fill can change — a fired comparison against it is always VALUE *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §1/§3, locked by `CurrentRepetitionDiffTest`)*. The scalar per-operator claims are carried machine-readably as the catalog's `polarity` facet; the compositional cases (arithmetic, the transforming functions, the sign-dependent aggregates) are truth tables over the operands and stay represented by their differential locks ([CATALOG-SPEC.md](CATALOG-SPEC.md) §3d).

### Full validation vs. partial validation

Every validation/computation call runs against a complete immutable processing context, not just a document. In kernel 30.8.1 that context includes the effective error-message locale, the resolved current date/instant (`currentDateForTest` when supplied, otherwise the host clock), the custom-condition and custom-field-type factories, and the deprecated-but-still-observable `additionalInformation`; project charset and model time zone supply the remaining model-scoped inputs. The interpreter exposes explicit inputs for locale, clock, both customization SPIs, charset, and time zone. It deliberately excludes the legacy additional-information map from its supported compatibility fragment, so consumers that relied on it must close that configuration over their supplied custom implementation rather than have it silently omitted.

`validateFull` checks the whole document. `validatePart` checks a "relevant" subset (e.g. the current wizard page) and guarantees only one direction: it never reports an error that could only be fixed outside that subset. It does **not** guarantee a complete check of the relevant fields themselves — some checks may be skipped for performance, and which ones is an implementation detail that may change. A document that passes a partial validation may still fail a full validation on the same fields. A field referenced by a rule but living on another screen is excluded from the relevant set unless it has the `Global` flag set.

The verified partial-validation mechanics:

- **Rule-gating by the error field**: a rule (including the auto-generated formal/mandatory/unique checks) runs only when its error field is in the relevant set **at the repetition levels the rule's ITERATION bound**. Iteration is reference-driven ([§9](#9-repetition-iteration-and-cross-array-evaluation)), so the rule's declared group does not decide this; a level below the iteration was never chosen, counts as a wildcard, and the message reports at the default first repetition. Under parallel iteration an unmatched side's own level is likewise unbound *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §12, locked by `PartialRuleGateScopeDiffTest`/`PartialParallelJoinKeyDiffTest`)*. Of the rules that run, a non-relevant referenced instance is three-valued **UNKNOWN**, and Kleene logic decides — `true Or Unknown` still fires (no value could prevent it), `true And Unknown` is suppressed *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §12, locked by `PartialValidationDiffTest`)*.
- **Global fields are auto-added to the relevant set** — by the md-runtime layer at the public `validatePart` boundary, wildcarded at all repetitions, so a rule whose error field is global runs even when the caller's set omits it *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §12 / [IF37](INTERPRETER-FINDINGS.md#if37), locked by `PartialValidationGlobalFieldDiffTest`)*.
- **A starred aggregate's relevance is per operator**: the all-rows aggregates (`Sum`, `MaxValue`, `MinValue`, `NumberOfDifferentValues`) evaluate only when every internally retained identifier for the operand wildcard-covers the starred level. The kernel first expands relevant groups into descendant field identifiers and removes narrower identifiers encompassed by a broader wildcard identifier; after filtering identifiers outside the current iteration subtree, any remaining concrete coordinate at a starred level makes the aggregate UNKNOWN. Therefore one wildcard identifier does not override unrelated concrete siblings, while a wildcard broad enough to encompass those siblings removes them before the gate. Enumerating every concrete row still leaves the aggregate UNKNOWN. `FirstFilledValue` is order-aware instead (UNKNOWN only when a non-relevant cell precedes the first filled one) *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §12 / [IF42](INTERPRETER-FINDINGS.md#if42) + [IF262](INTERPRETER-FINDINGS.md#if262), locked by `PartialValidationAggregateDiffTest`)*. **Corrected 2026-08-06, amended 2026-08-07: `SumOfProducts` has its OWN, WEAKER gate** — it evaluates under a COMPLETE concrete enumeration (every declared repetition listed), because the kernel walks its two lists in a hand-written loop with no three-value pre-survey; under a PARTIAL enumeration the kernel is SILENT, exactly like the other four. The 2026-08-06 correction read "concrete enumeration evaluates" off a both-rows case alone and dropped the gate entirely, which made the interpreter fire where the kernel does not on 5 of 180 fuzz combinations. Both granularities are pinned kernel-side by `PartialValidationAggregateDiffTest.sumOfProductsSeparatesCompleteFromPartialRowEnumeration`.
- **A starred value-list quantifier entry has its OWN, EXISTENTIAL extent gate** — not the aggregates' reduced-universal one: its complete extent is a fact separate from per-cell relevance, established as soon as **one** relevant identifier covering the operand wildcards every level it reopens (per the same star anchor, asked per iteration row). Concrete identifiers surviving beside that wildcard do **not** take it away, which is exactly where it parts company with the all-rows aggregates: on `{field wildcard} + {concrete group rows}` a starred `No` fires while `Sum` over the same rows stays UNKNOWN. Enumerating rows concretely with no wildcard anywhere still leaves it UNKNOWN. An extent-unknown entry is side-specific: `No` is suppressed to UNKNOWN on **either** side, `NotAll` on the **values** side, while `AtLeastOne` (either side) and `NotAll` on the fields side ignore it *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §12 / SPEC-2026-07-22-09 / [IF264](INTERPRETER-FINDINGS.md#if264), locked by `PartialExtentGateShapeDiffTest` + `PartialValidationValueListDiffTest` + multiplatform `PartialValidationValueListExtentTest`)*.
- **A relevant instance is always evaluated** — partial validation overrides [§2](#2-non-specified-empty-values)'s content gate, firing empty-as-0 even on an empty or phantom relevant row *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §2 / [IF54](INTERPRETER-FINDINGS.md#if54), locked by `RepeatableRowContentDiffTest`)*; and uniqueness checks need the duplicate **partner** relevant too (the duplicate caches are built from relevant fields only) *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §12 / [IF39](INTERPRETER-FINDINGS.md#if39), locked by `PartialValidationUniqueIndexDiffTest` + `PartialValidationRepetitionNotUniqueDiffTest`)*.
- **An eligible empty index field's declared S-value default is NOT injected** — the split keys on the **call kind**, not the relevant set's extent (it holds even with the whole document wildcard-relevant): where full validation stages the default ([§4](#4-the-required-property)), partial marks the same eligible clean-empty cell **silently unavailable** for the call — neither `mandatoryField` nor `uniqueIndex` is emitted (no formal message rides the suppression), dependent authored conditions read UNKNOWN and are Kleene-suppressed, and the **containing group retains error state**, so a group-absence predicate cannot prove absence over it. Ineligible shapes keep their ordinary partial behavior *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §4/§12 / SPEC-2026-07-23-14, locked by `IndexDefaultStagingDiffTest` (full + `validatePart`, dual-strategy) + multiplatform `IndexDefaultStagingMultiplatformTest`)*.

## 13. Error-message interpolation

- In a **rule-owned** error text, `$Field$` interpolates the referenced field's **name/label**, `$Field.value$` interpolates its **value**, and `$$` denotes one literal `$`. The token names are rule-relative field paths, not fixed words.
- A rule-owned `$Field.value$` may be used only if the field is referenced in the condition at least once without an asterisk, and error-text paths may not contain asterisks.
- A rule-owned `$Field.value$` reads the immutable input document's **display channel**, not the CRLF-normalized evaluation cache. A missing **or caller-supplied empty** display value selects the field format's exact active default. For a Number this is zero rendered to the declared minimum fractional digits (`0`, `0.00`, …); the current modern `DocumentV2` validation route uses `.` here even for `Locale.GERMANY` and even when `modelConfig.decimalSeparator` is `,`. A String default is empty. A different presentation-information route is a separate profile and must be characterized before support rather than guessed.
- A String type's own invalid-pattern text has a distinct `en_US` grammar: the accepted fixed tokens are exactly lowercase `$field$` and `$field.value$`. `$Field$` and an actual name such as `$Code$` are rejected as `INVALID_PARAMETER`. `$$` is likewise rejected because its empty delimited parameter is invalid, so this producer has no authored literal-dollar escape. A `$field.value$` replacement is one-pass: inserted token-looking bytes remain ordinary text.
- Requiredness text is a separate producer again. The measured `Cost $$ $field$` case is model-valid, and both dynamic Groovy and generated Java render exactly `Cost $$ Code` under the same label-or-name provider profile: the doubled pair is preserved rather than decoded. This bounded result does not establish the wider requiredness grammar.

### What a fired message carries, and where the name comes from

- A fired message's `getErrorText` is the **interpolated end-user text** — the tokens already resolved against the evaluated document (the authored template stays in the model); only the runtime can produce it, because it depends on the data *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §3, locked by `adapter.MessageInterpolationTest`)*.
- A rule-owned `$Field$` first consults the caller-supplied **`ILabelProvider`**. A present provider result wins exactly, including `""`; absence falls through to a nonempty localized model label and then the resolved path+index debug string (`fullName/idx.idx`). dmtool deliberately supplies the ordinary label-or-name policy, while standalone consumers may select another provider profile *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) §3/§13, locked by `DisplayNameDiffTest` and multiplatform `MessageDisplayPolicyTest`)*.
- A number's **unit trait** (amount / percent / permille) does **not** render into a rule-owned `$Field.value$` — the interpolation yields the bare number; the unit is a UI concern *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) "The number `trait`/unit slot")*.

## 14. CustomCondition — the escape hatch

When the language cannot express a check, `CustomCondition <Name>` delegates the decision to host code that the consuming system registers; the kernel parses and places the rule like any other but calls out to that implementation to decide whether it fires.

```
FieldFilled(id) And CustomCondition NotReverse
```

Two constraints: a `CustomCondition` is **forbidden in computation rules** and **inside filter (`Having`) conditions**. And, like any predicate, it doesn't exempt the rule from the error-field rule ([§9](#9-repetition-iteration-and-cross-array-evaluation)) — here the `FieldFilled(id)` conjunct references the error field.

When ordinary condition evaluation reaches `CustomCondition X`, the kernel calls the registered implementation with the document data view, `null` relevance for full validation or the exact external relevant set for partial validation, the exact externally addressed fields found invalid by that validation's formal pass, and the current repeated error-field pointer. The callback owns its hidden dependency checks: it must return `false` when a field it needs was not checked or is formally invalid; the evaluator does not infer that footprint or automatically suppress the call. A `true` result contributes VALUE polarity and `false` contributes the kernel's collapsed non-firing/unknown leaf.

Structural empty eligibility belongs to the complete condition. A custom leaf is empty-eligible; `Or` is eligible when either child is and `And` only when both are. Consequently, `CustomCondition X Or FieldFilled(id)` may invoke the callback and fire on a blank row, while the common `FieldFilled(id) And CustomCondition X` shape remains silent because its built-in guard blocks the complete `And`. A bare `CustomCondition X` still fails the separate authoring rule `MVK_ERROR_FIELD_NOT_REFERENCED`: the complete rule must reference its error field somewhere, but that reference need not guard callback invocation *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) "CustomCondition — a runtime CLIENT SPI", locked by `CustomConditionInvocationDiffTest`, `CustomConditionDiffTest`, and `PartialValidationCustomConditionDiffTest`)*.

Custom **conditions** and custom **field types** are the kernel's only custom hooks — there is no custom *computation* or function: a computation's operation vocabulary is closed, and `CustomCondition` (the one hook that could reach a computation) is barred there *(verified: [KERNEL-FINDINGS](KERNEL-FINDINGS.md) "Custom-extensibility surface")*.

*Reference: CustomCondition; Computation Rules (intro); Rules → Rules and repeatability → Filter operator.*
