# Documentation discipline — the doc-workflow spec

> **What this is.** The full procedures and rationale behind the project's documentation workflow, extracted 2026-07-09 from the always-loaded agent instructions (CLAUDE.md). CLAUDE.md keeps the **iron rules and the trigger table** — the parts that must interrupt an agent *before* a commit; this spec holds the *how* and the *why* each trigger points into. The two never disagree by design: a rule's one-line trigger lives there, its procedure lives here.

## 1. Where a finding lands

- **Every non-obvious finding gets written down under `docs/`** — kernel/build/environment facts default to [`KERNEL-INTEGRATION-NOTES.md`](KERNEL-INTEGRATION-NOTES.md); design decisions to [`PROJECT-DESIGN.md`](PROJECT-DESIGN.md). If a finding doesn't fit an existing doc's scope, **propose a new doc** rather than overloading one.
- **[`KERNEL-SEMANTICS.md`](KERNEL-SEMANTICS.md) is the canonical kernel-truth prose** (owner-authored; integrated in-repo 2026-07-09 from `a12-kernel-demo`, superseding the earlier consult-only-sibling policy of 2026-06-04 — the in-repo copy is now the one everything keys on, incl. [`SEMANTICS-MAP.md`](SEMANTICS-MAP.md) and its `SemanticsMapResolveTest` guard). Before each increment, read the relevant section (truth values, null semantics, formal errors, decimals, dates, enums, iteration, paths, computations, messages). **The layer split stays:** a new kernel-behavior fact lands in [`KERNEL-FINDINGS.md`](KERNEL-FINDINGS.md) FIRST (section-numbered to mirror KERNEL-SEMANTICS; every entry experiment-verified and test-locked) — folding a settled finding into the KERNEL-SEMANTICS prose is a deliberate, separate upstream edit, never part of recording the finding. rulekit's *treatment* of each fact stays in `KERNEL-INTEGRATION-NOTES.md`.
  - **The fold contract (2026-07-11).** Every KERNEL-FINDINGS heading carries a **fold-status line** as its first body line — `> Fold: folded → §n.` (the canonical claim lives in that KERNEL-SEMANTICS section; the finding keeps claim + provenance + locks, and MAY be compressed to that evidence skeleton — but **retro-compressing the existing folded entries is declined (2026-07-29); author new entries at skeleton weight instead**, because under grep/sed access the saving applies only to the full-entry fetch a reader makes when they want exactly the worked measurement that compression would delete (rationale + re-open trigger in the KERNEL-FINDINGS fold-status preamble)), `> Fold: not-foldable — <reason>.` (an authoring/structure/serialization/toolchain fact outside the canonical doc's evaluation scope, or pure provenance), or `> Fold: pending — <reason>.` (genuinely unsettled). Findings are **never deleted or renumbered**. When a new finding lands, it lands with its marker (`pending` until the deliberate fold edit ships); when a fold edit ships, it flips the marker in the same commit. **A `folded` marker is a live claim, not a one-time stamp** — appending a new paragraph to an already-folded finding either folds the new claim upstream in the same commit or flips the marker back to `pending — <what still needs folding>` (the 2026-07-17 reconciliation found four canonical sections lagging exactly this way). Enforced by `cli … KernelDocsFoldContractTest` in the `semanticsMapGuardTest` lane ([`TESTING-SPEC.md`](TESTING-SPEC.md) "Tests that read repo files at runtime"), which also pins the **canonical anchor set** — the 14 numbered sections' GitHub heading slugs + the field-types table must exist and every intra-doc `](#…)` link must resolve, so a deleted or renamed canonical heading fails the build naming the missing anchor.
  - **Semantic exports (the provenance contract, 2026-07-17).** When another project consumes our kernel-truth docs as **exported material** (e.g. a formalization effort building on the canonical semantics), the export is a **pinned snapshot, never a live link**: it carries (1) the exact a12-dmkits **revision** (commit hash) it was taken at and (2) the **file list** exported (typically `docs/KERNEL-SEMANTICS.md` + `docs/KERNEL-FINDINGS.md`, whose section anchors the guard above keeps stable). The consumer records both in its own tree; a **re-sync is a diff against that pin** — the consumer diffs the pinned revision → current head over the exported files, reviews what changed, then re-pins. We keep no registry of consumers and no tooling for this — the contract is exactly the pin + the diff, and the anchor guard is what keeps the section keys a consumer cites resolvable across our edits.
- **Cross-check findings against the kernel-team BA doc — `a12-kernel/documentation/_merged/kernel-ba.md` (consult-only, standing policy 2026-06-07).** It is carefully written and reviewed by the a12 kernel team and covers nearly every DSL aspect in prose, with worked examples and per-`MVK_*`-error rationale (the filter operator + `$`, `CurrentRepetition`, comparisons, value lists, dates, iteration). **It is original material — read/study freely, but never copy; transfer examples to our own domain** (the license-safe rule). Use it as a second oracle: when recording or trusting a kernel-behavior finding, confirm it there (it already caught one missing finding, `MVK_INVALID_ITERATION_IN_FILTER_CONDITION`, and validated the `$`/`CurrentRepetition` predecessor pattern). Companion: `kernel-dev.md` (developer-facing). **Do not write to either.**
- **GOLDEN RULE: prefer the a12-kernel SOURCES over JAR files — read the source before `javap`/decompiling or guessing** (2026-06-07, elevated to golden 2026-06-29). The full kernel is checked out at **`../a12-kernel/`** (consult-only). For DSL **syntax** read the ANTLR grammar (`kernel-core-parser/.../grammar/gen/*.g4`); for **rendering** read the `FormatterVisitor`/`FormatterUtil`; for **validation semantics** read the `check/.../Check*Impl` classes (their javadoc states the rules); for **keywords** grep `LexerTerminals_en/_de.java`; for **field-type / model API signatures** (`com.mgmtp.a12.kernel.md.model.api.*` — what `dm.core`/`ModelIndex` import) read **`../a12-kernel/kernel-md/kernel-md-model-api/`**. The map + rationale: [`KERNEL-INTEGRATION-NOTES.md`](KERNEL-INTEGRATION-NOTES.md) "The kernel SOURCE is the primary oracle". Probing the live kernel stays the way to confirm *behavior*; the source is the way to learn *syntax/rendering/rules/signatures*.
  - **The codegen TEMPLATE layer is a standing instrument, not an opportunistic one (2026-07-25) — route the question to the artifact that answers it.** The checkout holds **426 source templates** under `kernel-tool/kernel-core-codegen-*/src/main/resources/internal/templates/`, in three parallel dialects — `validation/groovy` (136), `validation/java` (132), `validation/java_script_vk` (124), plus `common/{groovy,java,java_script_vk}` (11 each). A **template is the kernel's own lowering rule, universally quantified over every rule of a shape**; a generated program is one instance of it. That universal quantification is what a runtime-class read cannot give you — though the template is an **index** as often as an answer (the pass-through warning below). Seven templates were already cited across [`KERNEL-FINDINGS`](KERNEL-FINDINGS.md)/[`INTERPRETER-FINDINGS`](INTERPRETER-FINDINGS.md)/[`SEMANTICS-MAP`](SEMANTICS-MAP.md) before this was mandated. **Exclude the `build/resources/` copies** — 426 generated duplicates, the same trap as the `delombok` trees below. The routing:

    | The question | The artifact that answers it |
    |---|---|
    | the **complete denominator** — every construct/class in scope | the class inventory + the kernel-mined [`RT-SEMANTICS-LEDGER`](RT-SEMANTICS-LEDGER.md) / [`MVK-LEDGER`](MVK-LEDGER.md) |
    | the **general lowering** for *any* rule of a shape | the **codegen template** — *but see the pass-through warning below; usually it only routes you on* |
    | the **emission shape** the template interpolates | the **codegen backing bean** (`…/backingbeans/**`, 233 files across the six codegen modules) — follow the interpolated attribute to the property that computes it |
    | the **actual order** for *one concrete* rule shape | the **generated program** |
    | an **operation's local meaning** | the **runtime class** |
    | whether a locally correct reading **actually manifests** | a **probe** (differential / laws lock) |

    **The pass-through warning — never read a short template as "no lowering here" (2026-07-25).** Most operand templates carry no lowering at all: **25 of the 26** java `operationsDir` templates are ≤3 nonblank lines, and they merely interpolate one `*Code` attribute. `operationsDir/CompositeOperation.st` is literally `<t.feldOperationCodeJava>`; the arithmetic emission shape — operand-0 special-casing, the `.op(arg)` chaining — lives in `CompositeOperation.java` under `backingbeans/fieldoperations/`. So a template answers *which bean property emits this* far more often than it answers *what is emitted*; treat it as the index, and the bean as the text. **State which layer a basis citation consulted**, because names collide across layers — `CompositeOperation` is a template *and* a bean, and `java_script_vk` is a codegen dialect that pairs with a separately-implemented TS runtime (the locus ambiguity that already bit once: the raw-`RegExp`/luxon divergences are runtime-side, and the templates contain no `RegExp`). "Per `CompositeOperation`" is not a citation; "per the `CompositeOperation` **bean**" is.

  - **A composition claim read from source alone is a HYPOTHESIS until a template, a generated program, or a probe confirms it (the subtlest way a source read lies — it survives both mechanical traps below).** Specifically: any claim about **read order, precedence, reachability, or interaction between runtime classes**. Each individual class read can be *locally correct* and the composed conclusion still wrong, because the composition is decided by the emitted code, not by the classes. This is a recurring mechanism, not bad luck — [`KERNEL-FINDINGS`](KERNEL-FINDINGS.md) §1/§3 supplement "a no-row first star DOES taint a later operand's value" is one event that produced two: `FirstValueCombiner.getValue`'s `omittedTail` clause reads correctly in isolation but only decides the all-exhausted identity, so the source-level prediction inverted the runtime outcome (our own correction) **and** grounded a12-kernel-lean's SPEC-2026-07-22-06 request that the differential then refuted. The RT-semantics ledger already implies this discipline in its "source-read proposes, law test confirms" split (§2); the rule states it in these terms so it binds *before* the reading is written down.
  - **Three traps that make a source read lie — avoid them, don't fall back to jars:** (1) **Match the FULLY-QUALIFIED class, not the file name.** The checkout has same-named classes in different modules — `…md.model.api.fieldtypes.INumberType` (the real one, `Optional<BigDecimal> getMinValue()`) vs the tool-internal `…core.tool.a12internal.api.ado.INumberType` (`Optional<Double>`). Grepping only `kernel-tool/` for `INumberType.java` finds the WRONG one. Search by the package the code actually imports. (2) **Read `src/main/java`, ignore generated `build/generated/sources/delombok/…`** (stale duplicates). When a source read still seems to disagree with the compiler, the cause is one of these (wrong module / stale `build/`), or a **version skew** — the checkout is not guaranteed to be the pinned `30.8.1`; reconcile by reading the right module at the right version. A `javap` on the resolved `~/.m2/repository-jim/.../30.8.1` jar is a *last-resort cross-check*, not the primary source (a random `~/.gradle` cache jar may be a stale 30.3.0 — another way to get misled). (3) **ANCHOR the `build/` exclusion — `grep -v '/build/'`, never a bare `grep -v build`** (2026-07-25). The unanchored form silently eats legitimate *source* paths containing the substring: it dropped five real `backingbeans/builder/*` + `buildscripts/*` files and produced a bean count of 228 instead of 233 — an undercount that looked plausible and was reported as fact. Traps (1) and (2) make you read the wrong file; this one makes you *count* the wrong set, which is worse in an inventory claim because nothing contradicts it. Any denominator mined from the checkout (a ledger's "N/N classified", a template or bean count) must state its exact filter, and a suspiciously round shortfall against another party's figure is a filter bug before it is a scope difference.
- A finding is only "done" when it's documented. When a new fact **contradicts** an existing note, update that note — don't leave stale claims.
- **After any substantive change, state which docs need updating** (the design / notes / README status / CLAUDE.md) and update them in the same change.

## 2. The kernel-coverage ledgers (anti-whack-a-mole)

**Mine constraints proactively, don't trip over them** (owner direction, 2026-06-04). Structural laws live in enumerable sources — sweep them instead of discovering by accident: **(1)** slot parity vs the public `IRule`/`IComputation` accessors (every accessor = supported or explicitly deferred); **(2)** the **MVK ledger** — every `MVK_*` code classified (erased-by-types / pre-checked / kernel-delegated / pending / unknown→experiment queue), CI-checked; **(3)** the `../a12-kernel-mm` metamodels as the **source of truth for valid DM structure** (schema oracle: `MM_*`/`CT_MODEL_HEADER` define the slots; constraint oracle: their rules encode validity laws — read-only, own-words analysis only, EUPL); **(4)** deserializer/serializer-tier checks (constraints that fire before `checkConsistency`): the write gate is `BasicConsistencyCheck` (run by `serialize()`, aborts on ERROR), its `BasicDocumentModelConsistencyCategory` enum (16 categories) the F6 output contract — every category classified (pre-checked by an authoring builder / n/a-structural), reflectively CI-locked; the deserialize tier (Jackson: locale format, type discriminators) documented in `KERNEL-FINDINGS.md`. **(5)** the parsetree-api construct-name enums as the **operator inventory** (reverse parity: every member cataloged or explicitly excluded — `adapter.KernelConstructParityTest`), catching operators the kernel *adds*; **(6)** the **RT-semantics ledger** ([`RT-SEMANTICS-LEDGER.md`](RT-SEMANTICS-LEDGER.md)) — every class of the kernel's runtime evaluation core (`kernel-core-runtime` `…internal.core`) classified (mined / already-locked / canonical / infrastructure / out-of-scope / queued), CI-locked by `adapter.RtSemanticsLedgerTest`, so *behavioral* semantics are drained from the source proactively, each fact law-locked (source-read proposes, law test confirms); **(7)** the **grammar-production ledger** ([`GRAMMAR-LEDGER.md`](GRAMMAR-LEDGER.md)) — every parser production of the condition grammar classified (`GrammarProductionLedgerTest`, opt-in vs the sibling `../a12-kernel` checkout), catching syntax *shapes* no keyword or construct enum reveals. **When the kernel (or `a12-kernel-mm`) changes, follow [`KERNEL-UPGRADE.md`](KERNEL-UPGRADE.md)** — the coupling map (each guardian ↔ what its failure means ↔ the realignment), the bump procedure, and the dry-run negative-controls. Guiding split (F11): quiet tolerance at runtime, loud detection at build.

## 3. Living surfaces and their same-commit triggers

- **Docs travel inside the feature commit, never after it.** Before committing a feature: update the affected docs — for a **DSL/API** capability make its [`API-GUIDE`](API-GUIDE.md) snippet real (test-backed) and, if it's a design observation worth keeping, record a finding in [`API-FINDINGS`](API-FINDINGS.md); for a **CLI-tool** feature update [`CLI-SPEC`](CLI-SPEC.md)/[`CLI-CONFORMANCE-SPEC`](CLI-CONFORMANCE-SPEC.md) + the CLI tour instead (the API scope rule below) — add any kernel-fact note, mark the corpus backlog — and **sweep the touched docs for stale claims**, then commit code + docs together. A shipped feature is recorded by being **documented + demonstrated + committed**, not by a separate status entry (the per-feature status board was retired 2026-06-19 — see §5). No separate "docs: refresh" commits trailing a feature.
- **[`ARCHITECTURE.md`](ARCHITECTURE.md) is the *living structural view* — update it in the same commit as a *structural* change, and never let roadmap/status creep back in.** It describes the system **as it is today**: the component map, the Gradle units + dependency edges, the package layering (`dm.core` + the sibling kits `dm.rulekit ⊥ dm.modelkit` + `dm.edit`), the N8/D15 kernel boundary, and the CLI (picocli, the self-describing surface, native-image, the eval/probe harnesses). **Triggers:** a new module / package group, a moved boundary, a renamed kit, a changed dependency edge, a new CLI verb family, a native-build change → update ARCHITECTURE.md in that commit. **Why it rotted before (don't repeat it):** it carried a "Proposed components (TBD)" section + per-phase `✅` status columns — *dispositions*, which go false the moment work ships and which no one flips because the doc wasn't in the commit reflex (the "rationale is timeless; a disposition is status" trap). So: **no roadmap, no "proposed/TBD/Phase," no status columns here** — planned structure lives in `PROJECT-DESIGN §16` or the ledgers; don't enumerate what a derived surface already lists (`manifest` for verbs, git for status) — point at it. Full discipline: ARCHITECTURE.md §7.
- **A user-facing capability lands in its living surface(s) — keep them current in the same commit.** (1) If it's a **DSL/API** capability, showcase it in [`API-GUIDE.md`](API-GUIDE.md) (a real, test-backed TYPED-builder snippet) **and**, if it's a design observation worth keeping, record a finding in [`API-FINDINGS.md`](API-FINDINGS.md) — a CLI-*only* feature is *not* showcased in the guide (it's documented in the CLI specs; see the API scope rule below). **A *canonical* guide snippet should be CI-locked verbatim to its run test** — wrap the showable lines of a passing test in `// tag::<id>[]` … `// end::<id>[]`, mark the doc fence with `<!-- snippet: <id> -->`, and register a `Lock` row in `DocSnippetFreshnessTest` (the test region is canonical, the doc mirrors it; mechanism + lifecycle in [`TESTING-SPEC.md`](TESTING-SPEC.md) "Locked doc snippets"). Teasers with `…` elisions stay hand-maintained. (2) **Whenever a CLI verb is added or its surface changes**, update **and re-verify** the showboat demos in [`../examples/`](../examples/) (per [`CLI-TOUR-SPEC.md`](CLI-TOUR-SPEC.md)) — they are **CI-gated and drift** (e.g. a new verb shifts the `manifest` list, which breaks `cli-tour`'s captured block); extend the right demo, run **`../scripts/verify-demos.sh`** (builds installDist + runs `showboat verify` on every *discovered* demo — the local equivalent of the CI gate, in one command) until green, add it to the CI gate (`.github/workflows/ci.yml`), and flip the CLI-TOUR backlog row.
  - **What the demos are for — and what they are NOT:** they do **not** serve cold-agent discoverability — the **N6 cold agent never sees `examples/`** (its material boundary is the binary alone, or binary + skill; never the repo/docs/examples). Making the CLI self-explaining *to that agent* is the self-describing surface's job (`manifest`/`--help`/`schema`/diagnostics — the **Self-explaining surface** standing requirement in CLAUDE.md; the cold agent's only "demonstration" is the binary describing itself, e.g. a read verb echoing its own output shape). The `examples/` demos exist for two *different* audiences: a **CI drift-guard** (the captured output must keep matching the live CLI, so a behavior regression fails the gate) and a **repo-equipped reader** — a human, or an agent handed the repo — learning the verb worked end-to-end. Update them for *those* reasons; don't justify them by cold-agent self-sufficiency (that's the binary's job, verified separately).
  - **The showboat gate is CI-only, so a high-churn value a demo *pins* (the `manifest` verb list, the `diagnostics` count) can drift in a *local* commit and sit there with CI red, unnoticed — it did: adding two `RkCode` codes shifted the tour's `diagnostics` count 31→33 without a regenerate, undetected until a later session.** So every value a demo pins from live code needs a **local** lock in `:cli:test`, not just the CI demo: the verb list is locked by `ManifestVerbTest.EXPECTED_VERBS`, the diagnostics count by `CliTourFreshnessTest` (runs the real verb in-process, compares to the tour's capture, fails the inner loop naming the regen command). Add such an inner-loop guard whenever a demo starts pinning a new live-derived value. **A broader, second drift class is an output-SHAPE change — a verb now echoes a new field or changes a payload, so the whole captured block moves, not one pinned scalar (it bit us twice silently: `field read` gaining the per-kind config block, and the missing-target read becoming a structured `refused` envelope — both shipped with CI red until a later session).** No single `:cli:test` lock catches a whole-block change, so the guard is *running the demos*: **after ANY change to a verb's output shape / behavior / diagnostics, run `./scripts/verify-demos.sh` before committing** (it discovers every demo, so it can't itself go stale). Treat it like the build — green demos are part of "done," not a post-commit chore.
- **Index/README surfaces drift silently — update the index in the same commit that changes what it indexes (learned: `examples/README.md` + `eval/README.md` + `scripts/README.md` all went stale).** A README that *lists or schema-describes* a directory is a derived surface with no compiler/test to catch drift, so name it in the trigger or it rots: **(a)** add/rename/remove a **demo** → update the demo table in [`../examples/README.md`](../examples/README.md) **and** the CI-gate list (`.github/workflows/ci.yml`) **and** the CLI-TOUR backlog (above); **(b)** change the **eval corpus** — **(b1)** add/rename/remove/change a **task** → update its row in the per-task catalog [`../eval/TASKS.md`](../eval/TASKS.md) **in the same commit** (hand-maintained, no drift guard — this is the surface that rots; a new *family* also needs `benchmark.workflow.js` + `EvalGoldOracleTest` wiring); **(b2)** change the **layout / filenames / task-schema fields** → update [`../eval/README.md`](../eval/README.md) (Layout + Task-schema — the *shapes*, not the inventory) **and** the recursive `eval/tasks/*/*.json` globs in the runner/skill. **Doc-responsibility split (don't duplicate):** [`EVAL-SPEC.md`](EVAL-SPEC.md) = the *method* (no per-task table); `eval/README.md` = schema + gold-shapes + how-to; `eval/TASKS.md` = the per-task inventory; `eval/RESULTS.md` = measured results; **(c)** add/rename/remove a **`scripts/` file** → update the script table in [`../scripts/README.md`](../scripts/README.md) (this one recurs — don't skip it). Rule of thumb: if you changed *what a directory contains or how it's named/shaped*, grep for the directory path across `*.md`/`*.yml` and fix every index that mentions it. **The `docs/` index ([`README.md`](README.md)) is the one such surface that is now guard-locked:** `DocsIndexGuardTest` (the `:cli` `docGuardTest` lane) fails the build if any `docs/*.md` or `docs/archived/*.md` isn't linked from the index, or if any relative link in the index doesn't resolve — so an added/renamed/moved doc must be re-indexed in the same commit.
- **The top-level [`README.md`](../README.md) is the project's feature/usage showcase — keep its samples + verb list current, but it is NOT a status board.** It leads with *what's possible*: the DSL approach, library code samples (rulekit/modelkit/`EditSession` builders), and a grouped `dmtool` verb tour with sample commands. These are **hand-maintained and NOT CI-verified** (unlike the `examples/` demos), so they drift silently — update them in the **same commit** as the change. Triggers:
  - **a CLI verb is added / renamed / removed** → fix the `dmtool` section's sample commands + the demo table (and the `examples/` index per the bullet above);
  - **a library API shown in a sample changes** (a `BoundModel`/`EditSession`/builder signature, a `Dsl.*` entry, `ModelContext`/`KernelAdapter`, a `FieldKind`/enum name) → fix the affected snippet so it would still compile;
  - **a new user-facing capability worth teasing** lands → add a short teaser (a line or a small sample) + a link to its demo/spec;
  - **a rename** (the tool name `dmtool`, a kit name, a verb) → propagate it across the README.
  Rules for the README specifically: **link docs/specs/`examples/`, never impl sources** (`src/…` is too much detail for the front door); keep samples **minimal teasers** and let the CI-gated `examples/` carry the authoritative runnable forms; **no phase/status tables in the README** (the project doesn't track per-feature status; what's built is shown by the docs + the CI-gated `examples/`). **A library code sample must use the TYPED builder, never a raw condition string** — `addRule(m -> m.rule(…).when(m.num(path).lt(0))…)`, not `addRule(…, "FieldFilled(x) And […] < 0", …)`. The string overload is the CLI/`apply` *spec* path (conditions arrive as text); a Java sample that hand-writes the DSL string **undercuts the very thesis the README sells** (typed builder > fragile strings). Mirror the canonical typed example in [`API-GUIDE.md`](API-GUIDE.md) §5b. When unsure a shown sample is still accurate, verify the API/verb against the code (or `dmtool manifest`) before committing.
- **Wrap long `dmtool` CLI calls, and write the bare `dmtool` (never `bin/dmtool`)** — in the README, `examples/`, and docs. (1) **Bare `dmtool`:** displayed commands are what an installed/plugin user types; the repo artifact `bin/dmtool` is not. The `examples/` demos call `dmtool`; their `showboat verify` runs with the repo `bin/` on PATH (`export PATH="$PWD/bin:$PATH"`), where the shim resolves it — so displayed = executed. (2) **Wrap (Cause 1 — long *commands*):** break an invocation whose command portion would scroll (~>90 cols) with trailing `\`, one logical piece per line (`-m <model>`, the `<target> <op>`, each `--flag`, a trailing `| jq …`), continuations indented 2 spaces — it reveals the call structure and reads better. (3) **Leave (Cause 2):** a *short* command followed by a long aligned `# comment` (the width is the comment, not the call) — `\` wouldn't help; comment-only scrolling is fine. Likewise leave long **Java** sample lines and compact shell `>file 2>&1; echo "(exit $?)"; jq …` capture-chains (the call within is already short). (4) **`examples/` are exact-matched:** wrapping a command doesn't change its output, so `verify` stays green; keep *output* narrow with `jq -c '{…}'` projection (output blocks can't be reflowed). Re-verify a touched demo: `export JAVA_HOME="$(/usr/libexec/java_home -v 21)"; export PATH="$PWD/bin:$PATH"; uvx showboat@0.6.1 verify examples/<demo>.md`.
- **User-facing docs (the top-level [`README.md`](../README.md) and the [`examples/`](../examples/) demos) describe *capability*, never project status or plan.** Keep out roadmap/status phrasing — no "completes the FEATURE-GAPS refactor set", no tier labels ("Tier-1/2/3"), no "deferred/parked/remaining/flagship", no "shipped 2026-..", no roadmap/milestone identifiers (a gap-proposal section like `§3.1`, milestones like `M9`/`F8`). Write what the feature *does* and how to use it. A pointer to a **contract/reference spec** is fine — link it by name (`CLI-SPEC §6` for the gate contract, `KERNEL-FINDINGS §10` for a kernel fact, the API study) — because that documents *what/why*, not *when it's scheduled*; the line not to cross is transcribing a roadmap/status. The internal design docs *may* note where a feature sits; user-facing docs never do. (The project no longer keeps a per-feature status board — what's built is shown by the docs + demos + git.) The trap is subtle in a worked demo: end a section with what the verb *did*, not with where it sits on the roadmap.
- **[`API-GUIDE.md`](API-GUIDE.md) is the DSL/API capability guide — it covers the rulekit/modelkit *library* (the typed builder, `DocumentModelDraft`/`EditSession`, the DSL), NOT the `dmtool` CLI tool.** Its narrative + snippets show **API/DSL capabilities**; the numbered **design findings** (the *why*) live in [`API-FINDINGS.md`](API-FINDINGS.md). The CLI tool's own concerns — verbs, the self-describing/conformance/diagnostics harness — are documented in [`CLI-SPEC.md`](CLI-SPEC.md) / [`CLI-CONFORMANCE-SPEC.md`](CLI-CONFORMANCE-SPEC.md) and the CLI tour, **not in the guide** (no `dmtool ...` invocations or CLI-tool meta). **Keep it current:** when a *DSL/API* feature lands, make its guide snippet real (a TYPED-builder snippet, test-backed where possible); when an interesting library usage/idiom emerges, showcase it in the guide; new API ergonomic observations go into the numbered findings list in `API-FINDINGS.md` (it seeds the N1 skill / N6 eval).

## 4. Writing style

- **Write docs like a human, not a changelog.** This holds for *all* docs — README, the design, the specs, the findings/notes. Favor a clear, scannable voice: avoid long paragraphs that string facts together with semicolons or em-dash chains — break them into **lists or tables**. `README.md` is the strictest case (it's the first doc a newcomer reads, so keep it a snapshot that points at the canonical docs rather than restating them), but the same readability bar applies everywhere prose is meant to be *read*. The one exception is the **structured, machine-checkable trackers an agent maintains** — the MVK / RT-semantics / grammar ledgers and similar — where a terse, regular shape is the point; leave those dense.
- **Reach for visuals when they out-scan prose — tables and diagrams, not walls of text.** If you'd sketch a box-and-arrow or jot a table while *explaining* something live, put that in the doc — don't transcribe it back into paragraphs. Use a **table** for comparisons, matrices, or parallel-structured facts (options × criteria, param × meaning, boundary × payload, who-builds-what × when); use an **ASCII diagram** (or mermaid where the surface renders it) for layering, data flow, topology, or state — the things a reader pictures spatially. Keep prose for the **rationale/argument** (the *why*), which doesn't tabulate. The bar: a visual must out-scan the paragraph it replaces and stay maintainable (ASCII travels everywhere and doesn't rot; don't hand-draw something fragile). Applies to all user-facing docs (README strictest). Reference example: [`EVAL-SPEC.md`](EVAL-SPEC.md) §8c — a layer diagram + boundary/parameter tables instead of three prose paragraphs.
- **Formalization discipline: match the representation to the knowledge kind, and formalize only when a consumer exists** (decided 2026-06-05). The document-model knowhow isn't homogeneous — don't ask "prose vs formal," ask *what representation per kind*: operator/structural **vocabulary** → a self-verifying machine-readable catalog (the `operators.json`/`OperatorCatalog` model, served via the CLI); **structural validity** → derive from the kernel's own oracles (MM_ metamodels / `BasicConsistencyCheck`) and make illegal states unrepresentable in the typed builder; **behavioral semantics** (empty-as-0, polarity, path walk-up) → *executable runtime laws* (`adapter/.../laws/…LawsTest` via the `RuntimeLaws` oracle — fires/does-not-fire on real data; distinct from the accept/reject `validate/laws/`) that the build can't let go stale; **rationale/the *why*** → stays prose (it doesn't tabulate). The governing test before formalizing any fact: **a consumer must exist** (the tool, the LLM, or a CI gate) — formalization that only feeds other formalization is cost without payoff and rots worse than prose. Full reasoning, the five options with trade-offs, and the per-kind gradient: [`PROJECT-DESIGN.md`](PROJECT-DESIGN.md) §21B/§21D.

## 5. Doc lifecycle

- **Specs hold the stable method; measured results live in a dated log.** Keep time-stamped, churny *results* out of spec docs — a spec is the fixed contract (method, scoring, task definitions), not a changelog of runs. Eval/benchmark results go in **[`../eval/RESULTS.md`](../eval/RESULTS.md)** (dated + time-of-day, newest first — we run several a day); [`EVAL-SPEC.md`](EVAL-SPEC.md) just points to it. `eval/RESULTS.md` lives outside `docs/`, so it's indexed from both `docs/README.md` and CLAUDE.md rather than only the docs index.
- **Doc evolution: the project design stays whole; component *detail* splits out into specs, never the argument** (decided 2026-06-03; reshaped 2026-06-19). [`PROJECT-DESIGN.md`](PROJECT-DESIGN.md) (formerly `PROJECT-PROPOSAL.md`) is **one argument**, densely cross-referenced by stable anchors (`§N`, `Fn`/`Nn`/`Dn`, forks Q1–Q12) — don't split it into per-section files. modelkit's rationale was **folded *in*** as §21 (fork #8), not fragmented out, for the same reason. When a component's design *detail* outgrows its section during implementation, extract a **component spec** (`CATALOG-SPEC.md`, `ADAPTER-SPEC.md`, `CLI-SPEC.md`, …): the spec supersedes the section's *detail*, the section shrinks to intent + a pointer. Revisit a wholesale split only if the design exceeds ~800 lines despite spec extraction.
- **Spec-vs-proposal lifecycle, and the status-surface split** (decided 2026-06-19). The doc-name *suffix* is a contract: a **spec** is a **stable, *implemented*** contract (method / verb surface / I-O — `CLI-SPEC`, `EVAL-SPEC`, `RELEASE-SPEC`); a **proposal** is **intent + rationale *not yet built*** (it graduates to a ledger — or is archived — once its items ship; `archived/` holds the parked/resolved ones); the suffix is self-describing (the 2026-07-06 `-GAPS` rename): a **`-GAPS` doc** (`FEATURE-GAPS`, `DEV-API-GAPS`, `INTERPRETER-GAPS`, `SCHEMAKIT-GAPS`, `MODEL-REVIEW-GAPS`) tracks only OPEN/deferred/out-of-scope items — a **fixed gap is DELETED, never kept as a "shipped"/"graduated" list** (git is the *what/when*; the gap's API-FINDINGS finding or CLI-SPEC section is the *why* — and findings back-reference the `Gn`/`DGn` so refs still resolve); a **`-LEDGER`** is the opposite instrument — a complete, CI-locked classification of an external constant (`MVK-LEDGER`, the RT/grammar ledgers: every kernel code/class/production), so it **keeps every row forever** by design (not gap history). A **design** is built vision + decision log (`PROJECT-DESIGN`). **The lifecycle:** when a proposal's item *ships*, **graduate its contract into the owning spec in the same commit**, then **retire the proposal** — keep it a proposal if it still holds unbuilt items; once everything graduated, **rename it** (→ `-GAPS` if it still tracks open gaps; fold into the design / `-DESIGN` if it's settled design) or **archive under `archived/`** (resolved/parked — kept as the measurement/decision record). **Never leave a `*-PROPOSAL.md` describing shipped work.** **Clarified 2026-07-29:** that bans a proposal whose items have *all* graduated — it does not ban per-stage status inside a program still in flight. A **partially** shipped program legitimately stays a proposal while it holds unbuilt items, provided it records its **graduation trigger** (what event retires it). `KERNEL-DECOUPLING-PROPOSAL` is the live instance: Stages P/Q/R shipped, Stage 5 and the §5 rulings are unbuilt, and its status is explicitly provisional pending the master review gate — so rewriting it mid-flight would be churn against an active program. Its trigger is recorded in the doc. **No per-feature status tracking (decided 2026-06-19):** a shipped feature is recorded by being **documented** (the guide/spec), **demonstrated** (the CI-gated `examples/` demos + the eval), and **committed** (git) — *not* by a hand-maintained status entry, which only duplicates the gated/derived surfaces and drifts. So: no status board, no `🔮→✅` flip-tracking, no graduation tables. What survives is **rationale** — [`API-FINDINGS.md`](API-FINDINGS.md) (the *why* behind the API, cited as `finding N`) and the design's decision log + non-goals — plus the **kernel-coverage ledgers** (MVK / RT / grammar, CI-locked — a different job). Eval results stay in [`../eval/RESULTS.md`](../eval/RESULTS.md). The design + specs state *intent + contract*; `PROJECT-DESIGN §16` is phasing *intent*, not a ✅ log.
- **Rationale is timeless; a disposition is status (decided 2026-06-19).** A *rationale* note — a finding, a decision, a "why it's built this way" — records a **decision, a tradeoff, a rejected alternative, or a principle** (things that stay true, or become a *superseded* note: "superseded YYYY-MM-DD by … because …", which is itself rationale). It must **not** state a live **disposition** — "X is parked / deferred / not yet / won't be built / low-value / still open / rides feature Y" — because that silently goes **false** the moment the plan changes. It already bit us: findings called *enum-vs-enum* / `FirstFilledValue` / `$` correlation "deferred" after they shipped; D10's module-wall *why* outlived the wall; `DEV-API-GAPS`'s "every item proposed, not built" outlived the shipping of DG1–DG6. **Dispositions belong where stating a plan is the section's job** — a roadmap / backlog / non-goals / open-questions list (dated, expected to change) — or in git; never dressed as a durable *why*. For a decision resting on a *current fact*, **embed its re-open trigger** ("revisit only if X") so the rationale carries its own expiry (the `dmtool serve` non-goal is the model). **Scope: this targets the *evolving-project* docs** (the design, the specs, `API-FINDINGS`, the treatment notes). Docs grounded in the **stable kernel + original material** — `KERNEL-FINDINGS`, the `MVK`/`RT-SEMANTICS`/`GRAMMAR` ledgers, the kernel API survey — describe an external constant, so their **kernel-truth claims** don't rot from *our* changes; leave those. **The exemption covers the kernel fact, NOT a cross-reference to our own state inside it (narrowed 2026-07-29).** `KERNEL-FINDINGS` carries 8 structured `**Interpreter status/parity/treatment` markers and references to 21 gap ids — every one of which *does* rot when the interpreter advances, which is exactly what the exemption was read as licensing. They are worth keeping: an `Interpreter status:` line is how a reader answers "do we match?" in one grep. So they stay, but as **dispositions under the normal rule**: a status marker must be **verifiable in one hop** — cite either the `IF<n>`/`IG<n>` that owns the live status (those resolve to stable anchors) **or** the interpreter artifact that carries the behavior (its class, symbol, or lock test). What is banned is a bare "we match" with nothing to check it against. *(Measured 2026-07-29: all **8** structured markers comply — 3 by id, 5 by artifact, two of those naming a `*DiffTest` outright. The phrase also occurs 19 times as ordinary prose, which this rule does not govern. Two corrections worth keeping: the rule first demanded an id **specifically**, which was over-specified — correcting it beat guessing five ids, since a wrong cite misdirects worse than the rot it prevents; and this note first said "22 markers, 17 by id", which was a grep count of the *phrase* read as a count of *markers* — name the quantity before quoting a number.)*

## 6. Doc sweeps

**A full doc sweep includes a laws-and-findings pass, not just prose.** Besides the regular stale-claim check, sweep specifically for: **(1)** stale `KERNEL-FINDINGS.md` claims — every "deferred / not yet / no … yet / rides feature X" must be re-verified against the actual code + tests (these accumulate: a feature lands but the finding that called it "deferred" doesn't get flipped — e.g. enum-vs-enum, `FirstFilledValue`, `$` correlation all drifted); **(2)** the same for the `MVK-LEDGER` classifications and `KERNEL-INTEGRATION-NOTES`; **(3)** the **two law tiers** for *gaps* — a behavior implemented without a `validate/laws` (accept/reject) or `adapter/laws` (fires/does-not-fire) lock is an unguarded fact; **(4)** **cross-check kernel-behavior findings against the kernel-team oracles** — [`KERNEL-SEMANTICS.md`](KERNEL-SEMANTICS.md) and the merged BA doc `kernel-ba.md` (which covers nearly the whole DSL and reliably surfaces both missing findings and missing examples). Verify each candidate before "fixing" it — don't swap one false claim for another.
