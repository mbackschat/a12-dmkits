# The `a12-kernel-lean` handback protocol

How this project sends measured corrections to the sibling **a12-kernel-lean** project, and why the letter's shape is what it is. Extracted from [`CLAUDE.md`](../CLAUDE.md) on 2026-09-05, which keeps the trigger that sends you here — the same split [DOC-DISCIPLINE](DOC-DISCIPLINE.md) got in 2026-07-09, and for the same reason: a protocol used episodically should not be loaded into every session.

**Scope note, because it is easy to misread the extraction.** What moved is the *workflow*. The **letter itself still lives outside version control**, at `~/Downloads/`, and the rule against giving it an in-repo home is unchanged and restated below — it is the reason this doc describes the letter rather than containing one.

**Delivery decision — apply immediately, without asking the owner to find a channel:**

| Peer availability | Required action |
|---|---|
| A live peer session is reachable through the available messaging tools | Send the full verified payload directly. That transmission freezes the letter. |
| No live peer is reachable, including when this runtime lacks the peer's messaging tool | Create a new dated letter under `~/Downloads/`, or update the unsent letter created by this session, and give the owner its clickable path. Do not substitute a chat-only update, ask for another messaging route, or wake an old inactive session. |

**Keep the fallback current while working.** Record the active batch and its verification state when an update is requested; label unfinished measurements as preliminary and not actionable. Add the verified input → observation → oracle rows and exact commit reference when the batch lands. A missing peer channel does not block repository work or excuse an omitted handback. Once the owner says the letter was delivered, or this session sends it, freeze it and start a new file for the next update. If today's basename already belongs to a frozen letter, use a fresh suffix (`-2026-09-27a`, then `b`, for example), even when the older file is absent on this machine.

**The letter lives at `~/Downloads/a12-kernel-lean-spec-corrections-<date>.md`, and the rule is: A DOC THAT HAS BEEN HANDED OVER IS FROZEN — every handback is a NEW, SELF-CONTAINED doc (owner rule, 2026-08-30).** It is an **outbound letter to another project**, not one of our docs, and the owner is its courier: once he has passed a file on, that file is a record of what was sent and is never touched again — not to correct it, not to merge a later round into it, not even to stamp it superseded. A correction to something already sent goes in the **next** letter, written so the reader needs only that one: restate what the earlier letter got wrong, in full, as a fresh claim with its own measurement. Say plainly at the top that it replaces its predecessor. Keep writing it as you work — collecting items into the *unsent* letter is the normal path, and only handover freezes it.

- **Find it first: `ls ~/Downloads/a12-kernel-lean-spec-corrections-*.md` and take the newest.** Append to it only if it is **UNSENT**. Once the owner has handed it over, start today's file instead — and never edit the sent one to point at the new one.
- **Sent or unsent is a question about the OWNER, not about the file.** Its own Section 0 tells you whether the peer has receipted what it carries, but a letter can be sent and unreceipted, and that is still sent. When you cannot tell — a letter you did not write, or one from a previous session — treat it as sent, because the cost of a needless new file is one file and the cost of editing a sent one is a broken record.
- **The freeze covers the BYTES, not just the content — never rewrite a letter's path in place.** A correction lands as a NEW dated file; amending the old path destroys the only copy of what was actually sent, which is worse than the divergence it was trying to repair. Measured 2026-08-31: three in-place amendments to a couriered letter left its handed-over bytes surviving only in the peer's conversation record, so "read the authoritative copy" named a file that no longer existed. One file, one delivery, no rewrite.
- **But the owner may still have handed one over himself, and NO SIGNAL ON THAT CHANNEL REPORTS IT — so never amend a letter whose delivery status is uncertain (measured 2026-08-31).** The peer saying it has not read the letter is not evidence the letter is unsent; it means the peer has not read it. On 2026-08-31 that inference amended an already-handed-over letter three times and then re-transmitted it, putting one filename into the peer's hands with two byte contracts — the exact failure the freeze rule exists to prevent, reached by treating a provenance fact as inferable. The rule above already says to treat a letter as sent when you cannot tell; the trap is *feeling* that you can tell. Treat a letter from before this session as sent unless the owner explicitly says otherwise; start a fresh file instead of asking to reuse it. Only a letter created in this session and still known to be unsent may accumulate updates.
- **Read the whole letter before transmitting it, and check every table is a contiguous block.** A paragraph inserted between two rows silently ejects the rows below it from the table, and a `-GAPS`-style row that stops rendering as a row is a measurement the reader never receives. One instance shipped this way on 2026-08-31, in the row mirroring the peer's own finding.
- **Name it with today's date**: `a12-kernel-lean-spec-corrections-YYYY-MM-DD.md`. Section 0 states which letter it replaces and re-derives its own denominator (how many entries the peer's ledger carries, in what state) rather than citing the previous letter's count.
- **A named file being absent is a fact to establish, never to assume in either direction.** The machine is one of several and the letter is deliberately outside version control, so `ls` before concluding anything. (On 2026-08-19 this file hard-coded the `-2026-08-12` name as "the single authority"; that file was not on the working machine, which left a session holding measurements with no channel. Hence: establish by `ls`, never by assumption.)

**Do not give it an in-repo home.** That was tried on 2026-08-14 under IG137(e) and is withdrawn: within a day the two copies had diverged in *both* directions, because the letter's state is defined by the **peer's receipts** and ours by our commits, so a copy creates two heads with no merge base. "Outside version control on one machine" is the letter's intended shape, not a defect to fix. Before adding any file "so it isn't lost", establish that it has no home already — reading a stated absence as measured is the same error the "match the oracle to the CLAIM KIND" rule exists to prevent.

**Its structure is load-bearing, because the reader is an agent doing a delta.** Section 0 states which letter this one replaces and marks every section absorbed / sent-no-receipt / NEW, so they can skip what they hold; payload rows stay *(input → observed → oracle → status)*; mechanisms are quarantined in their own section and marked as hypotheses. Self-contained does not mean bulky — a section the peer has receipted is named and summarized in a line, not re-transcribed.

**Name every SHIPPED surface that now carries one of their clauses** (requested by the peer, 2026-08-30). When a measurement of theirs lands in a schema description, a public javadoc, or help text — not just in a finding — say so in the handback, because that text is a copy of a rule they own and they cannot see it drift from their side. This is the reciprocal of the doc trigger table: internally a fact goes to its most self-describing surface, and externally the owner of the fact is told which surfaces now repeat it.
