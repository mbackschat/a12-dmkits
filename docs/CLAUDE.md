## These docs are read by grep + sed, never whole

The knowledge docs total ~4.6 MB (~1.15M tokens at 4 bytes each); `INTERPRETER-FINDINGS` alone is ~1.0 MB. Never `Read` one end to end. *(Every derived figure in this doc has a recompute command in [CLAUDE.recompute.md](CLAUDE.recompute.md) — run it rather than trusting the number.)* A finding's **heading line is the retrieval preview** — it deliberately carries claim + oracle + date, so a grep over headings is usually enough to decide what to fetch.

## Addressing — cite by id, never by title text

Every cited entry owns an **explicit anchor**, so a heading may be amended freely without rotting a link. That is the durable fix for a class that bit twice (`IF96`, `IAG4`): a generated heading slug moves the moment the claim sharpens.

| doc | id | notes |
|---|---|---|
| [INTERPRETER-FINDINGS](INTERPRETER-FINDINGS.md) | `IF<n>` → `#ifNN` | all 299 headings carry `<a id="ifNN"></a>`. Never renumber or reuse; a new finding takes the next number and must carry its anchor |
| [KERNEL-FINDINGS](KERNEL-FINDINGS.md) | `KF<n>` → `#kfNN` | all 188 entries carry `<a id="kfNN"></a>`, **trailing** — never before the `§`-tag, because two guards pin `^## §n `. Ids are dense 1..N in document order; a finding is never deleted or renumbered. `§n` is a section-*class* hint, not an address (`## §9 supplement` matches 32 entries) |
| [KERNEL-SEMANTICS](KERNEL-SEMANTICS.md) | `§1`–`§14` + heading slugs | the canonical prose; its 14 section slugs are guard-pinned, so linking them is safe. Its 120 verification cites read `§n / [IFm](INTERPRETER-FINDINGS.md#ifm)` — the two halves live in **different** docs, which is why the `IFm` half is an explicit link |
| [API-FINDINGS](API-FINDINGS.md) | ordinal, cited as `finding N` | ~123 citation sites, including production sources. Greppable exactly (`grep '^67\. '`). It is a markdown ordered list, so **never delete or insert mid-list** — rendered numbering would shift and silently break every later citation |
| the `-GAPS` ledgers | `IG<n>` `DG<n>` `IAG<n>` `IRG<n>` `MR<n>` `CG<n>` `MG<n>` | `IAG`/`IRG` rows carry `#iagN`/`#irgN` anchors and every issued interpreter API/release id remains resolvable in the [interpreter gap-ID registry](INTERPRETER-GAP-ID-REGISTRY.md), even after its live row is deleted. `CG` rows (CLI conformance) carry `#cgN` anchors. A shipped gap's row is **deleted**, so most ids you meet elsewhere are provenance, not open work — ~134 distinct `IG` ids are cited across `docs/` while only the ledger's own rows are live. Never write `pending IGn` / `IGn stays open` about a gap you have not checked against the ledger |

**Never cite an ANCHORED doc by quoting its heading.** KERNEL-FINDINGS and INTERPRETER-FINDINGS give every entry a permanent id so a citation survives a retitle — and these headings are retitled constantly, because a finding's heading carries its claim. A quoted title is the one form that cannot survive that: measured 2026-08-16, **53 of 373** quoted-title citations no longer resolve, and identifying what a rotted one MEANT is per-site reading rather than matching (one quote's most distinctive token returned 183 hits across 146 entries). The convention has already won on volume — 969 anchor citations against 215 quoted titles — so `QuotedTitleCitationRatchetTest` holds the count at its ceiling and lets it fall as sites are repaired in passing. Write `[KF123](KERNEL-FINDINGS.md#kf123)`.

**Section numbers are load-bearing.** `FEATURE-GAPS §4`, `DEV-API-GAPS §2/§3`, `INTERPRETER-GAPS §3` and `SCHEMAKIT-GAPS §3` are cited from production sources and docs. **So are `CLI-SPEC §N` and `API-GUIDE §N` — far more heavily than any of those: 230 sites (CLI-SPEC 218, API-GUIDE 13 at 2026-08-16), with `§5` and `§6` alone carrying 118.** Do not renumber; add at the end, or add a letter suffix (`2a`, `3b`, `5c`), which is what both docs already do.

**The 14 most-cited of those sections now carry explicit anchors, and the 40 citations inside `docs/*.md` link them** — `[§6](CLI-SPEC.md#op-taxonomy)`, `[§5c](API-GUIDE.md#refs-and-editors)`. The visible `§N` stays as a reading aid; the *target* is the id, so a renumber can no longer land a reader in the wrong section, and `DocAnchorResolveGuardTest`'s cross-doc arm now checks all 40 for free. **Cite the anchor when you add a citation from `docs/`.** The ~180 citations in Java/Kotlin/Gradle sources deliberately stay numeric: they sit outside that guard's scan root, so converting them buys no enforcement, and the measured live rot in that family is ~0 after the 2026-08-16 sweep.

**Why a guard cannot substitute for that discipline here (measured 2026-08-15, and a guard was built and removed on the strength of it).** These two docs carried **no `<a id=>` anchors** when that was measured, so a number was their only address — and anchor-less is the estate's default, not an oversight in two files: only **12 of the 66** docs carry one even now, the two most recent being CLI-SPEC and API-GUIDE themselves (see the paragraph above). And a number is not checkable in the direction that matters. Renumbering *downward* grows the integer range, so every plain-integer citation still resolves while now naming the wrong section: on a simulated mid-doc insert, 158 sites point at wrong content and a resolution guard flags **27**. On `5adc7198` it scores 12 caught, 7 missed, 1 introduced — and reports green, which manufactures a done-signal. **A dangling citation is cheap; a resolvable citation pointing at the wrong section is permanent, because nothing will ever flag it again.** The durable fix is the same one the addressing rule above already states: give a cited section an explicit anchor and cite the id, which does not move when a section is inserted.

**And the rot is measured, not prospective (2026-08-16).** `5adc7198` did not renumber one section, it reassigned **six integers in a single commit**: `§2` Module shape → Design principle, `§3` Dev/test workflow → op model, `§4` Verb surface → Diagnostics, `§5` export verb → Verb surface, `§6` Sizing → Op taxonomy, `§7` Packaging → Batching. Every citation written before 2026-06-11 and not swept in that commit still resolves and names the wrong section — **seven did, undetected for two months**, in `AppendableWriter`, `BatchCommand`, `Cli`, `CliMain`, `OperatorsCommand`, `WhereUsedCommand` and `ExportVerbTest`; repaired 2026-08-16. Two more (`Artifact`, `ExportCommand`) cited `§5` and survived only by luck, because `export` moved *into* the section that inherited the number. API-GUIDE has never reassigned a number — it deleted two *trailing* sections (`§9`, `§10`, in `0fe85652`), which moves nothing below them — so its sites carry no measured rot — the exposure is CLI-SPEC's, which carries 218 of the 230. **The exposure is estate-wide, not CLI-SPEC's alone.** Five cited docs have moved a section number — CLI-SPEC (218 sites), EVAL-SPEC (45), RELEASE-SPEC (39), NATIVE-IMAGE-GRAALVM (38, the highest churn rate in the estate) and ARCHITECTURE (13). The other ten, including PROJECT-DESIGN (71) and CATALOG-SPEC (62), never have. The sweep across all five turned up one further rot: `Dsl.java` cited `ARCHITECTURE §2` when that number meant "Core package layering"; it now means "Modules & dependencies", and the facade rationale it wanted lives in §3.2.

**And the reason a resolution guard keeps failing here is PRECISION, not yield — measured 2026-08-16, and it is the number to quote when someone proposes rebuilding one.** Resolving all **2 016** `<DOC> §N` citations against each target's live addressing scheme leaves **21 apparent danglers, of which only 5 are real**. The other 16 are the *resolver* mis-reading which document a `§` belongs to, because a line routinely names one doc and then cites a section of another: `[API-FINDINGS.md](API-FINDINGS.md) (and API-GUIDE §5c…)`, `DEV-API-GAPS D11; KERNEL-SEMANTICS §9`, `LICENSING.md / CLI-SPEC §11`. A proximity window cannot tell those apart, so a name-anchored guard here runs at a **76 % false-positive rate** — and a guard that fails honest content gets disabled, which is worse than no guard. Two further traps a naive resolver hits, both of which produced hundreds of phantom hits before being handled: KERNEL-FINDINGS writes its sections as `## §9 supplement`, not `## 9.`, and PROJECT-DESIGN §18 defines `§18.N` **in prose** as an ordered-list index (`"§18.9" = fork 9`), so both are live schemes that no heading regex finds. The cheap, high-precision checks are the ones with an unambiguous oracle instead: file existence (`DocRelativeLinkGuardTest`) and a cited `§N` above the target's highest live section, which is always a line number written as a section.

**A bare `§N` in a source file is not automatically a defect — the estate has a real convention, and it is decidable (measured 2026-08-16).** Across 1 154 `§N` occurrences in `.java`/`.kt`/`.gradle`: **791 name their doc at the citation**, **238 are bare and plain `§1`–`§14`**, which is the KERNEL-SEMANTICS *taxonomy area* and needs no doc (`multi-row iteration (§9)`, `the corpus capture/replay path, §9/§13`), and **41 are bare but suffixed in a file that names exactly one doc**, so they inherit it. That leaves ~84 genuinely unresolvable, and even most of those carry a **nickname** rather than a filename (`kernel-decoupling §3b`, `PROPOSAL §3a` — both mean KERNEL-DECOUPLING-PROPOSAL). So the rule to write, and the only one the corpus supports:

> A plain `§1`–`§14` may stand alone; it means the kernel-semantics area. **Anything suffixed or above `§14` must name its doc** — filename or established nickname — because that numbering belongs to some *other* document and nothing can recover which.

File-scope inheritance is **not** a safe general rule and was rejected on measurement: 141 bare occurrences sit in files naming several docs, and only 13 of those are the benign KERNEL-FINDINGS/KERNEL-SEMANTICS pair that share `§1`–`§14` by contract. *(An earlier review put this population at "502 unresolvable". That figure counts the taxonomy convention, script self-references and corpus facet tags as defects; the real number is ~84, and the 6× gap is the same over-broad matching this section warns about twice already.)*

**Partition a citation sweep by FAMILY, not by document — the mistake that made the sweep above look complete when it was not (2026-08-16).** Three families live in this estate and they need different instruments, so a sweep scoped to one silently reports the others clean: (a) the address **never existed or was deleted** — 16 live occurrences, caught by an existence check, invisible to a number-pin because a pin can only exist for a number that exists; (b) the number was **reassigned** and the citation still resolves — ~2 live, caught only by the blame audit below or by a pin at the commit that does the damage; (c) a **line number written as a section** (`DOC-DISCIPLINE §61`, `KERNEL-FINDINGS §238`) — decidable for free, because a cited `§N` above the target's highest live section is always wrong. Family (a) is the large one and was the one nobody had measured; the five-doc scope of the reassignment sweep is what hid it, and the same class then recurred *inside a guard's javadoc* on the night it was root-caused. **And use `git grep`, never `grep -r --include`:** a suffix list drops extensionless tracked files, which is how a `§B2` site in `bin/dmtool` survived a sweep that reported itself complete.

**The audit is cheap and repeatable, so run it rather than reasoning about it** — build the per-commit `number → title` map (`git show <rev>:docs/<DOC>.md`, `^#{2,4} ([0-9][0-9a-z.]*)\.`), then `git blame` each citation site and compare against the dates a number changed meaning. **But no single test decides it, and getting that wrong costs a whole sweep.** Flagging *any* title change over-reports badly: 12 of 14 candidates were sharpened titles on unmoved content (all nine `RELEASE-SPEC §11` sites are one retitle). Requiring that the old title *reappear under a different number* is the sharper test and reports zero — it also misses the real ones, because a section that is renumbered is usually retitled in the same edit (`§6 Sizing (measured …)` → `§10 Sizing` defeats it). So the loose test is the **candidate generator** and adjudication is by hand, one heading at a time. Two recall limits stand after that: a citation reformatted since the move blames to the reformat, and a post-move citation copied from an older one is invisible to both tests.

## The `-GAPS` template

All nine ledgers share one shape, so a single grep answers "what remains?" across the family. Guarded by `GapLedgerTemplateGuardTest`.

```markdown
# <scope> — gaps

> **What this is.** <scope; where the implemented contract lives; the id family>
>
> **Lifecycle.** A gap lives here only while open. When it ships its row is DELETED in the
> same commit and its rationale graduates to <spec/finding>; git is the what/when. No
> shipped list, ever.
>
> **Current state.** <why the open section looks the way it does; closure context>

## <N>. Open

_None open._          ← when drained: the marker ALONE, nothing else

## <N>. Deferred — with re-open triggers
## <N>. Out of scope
```

**The open section carries only rows or only the marker.** Closure history and lifecycle policy belong in `Current state.` / `Lifecycle.` — prose there buries the one answer a reader came for. Doc-specific sections (a framing section, a recorded-decision section) are fine; keep them outside the three canonical ones and never renumber to make room.

**A shipped gap is RETIRED from the open section — in EVERY ledger, no exceptions.** Deleting the row is the completion step, not a tidy-up afterwards: its rationale graduates to the owning spec/finding and git carries the what/when, so a row left behind and annotated "FIXED" adds nothing and costs the one answer the section exists to give. This was prose-only until 2026-08-14, when a session left three shipped rows under `## 1. Open` and the owner, not the build, caught it. `GapLedgerTemplateGuardTest.noShippedItemRemainsInAnOpenSection` now fails on a shipped marker in an item's **lead**, deliberately not in its body — a partially-shipped row legitimately says what already landed as long as its lead states the open remainder.

## Evidence vs. rationale — the split that gets misfiled (2026-08-11)

**A number you measured is EVIDENCE and belongs in a dated log. The conclusion you drew from it is RATIONALE and belongs in a findings doc.** Each doc says so itself: [INTERPRETER-PERFORMANCE-RESULTS](INTERPRETER-PERFORMANCE-RESULTS.md) holds the `### Checkpoint <date> — <topic>` entries, newest first, while its method half [INTERPRETER-PERFORMANCE](INTERPRETER-PERFORMANCE.md) holds the contract, the protocol and the harness; [INTERPRETER-FINDINGS](INTERPRETER-FINDINGS.md) is "a **rationale record, not a status surface** — the timeless fact, the decision, the *why*". [DOC-DISCIPLINE §5](DOC-DISCIPLINE.md) generalizes it: specs hold the stable method, a dated log holds the numbers. *(Those two were one file until 2026-08-15, which made this doc the standing example of the misfile it warns about.)*

**The decision test, one question:** *would this sentence still be true if the same code were measured tomorrow, or on another machine?*

| answer | it is | home |
|---|---|---|
| **no** — it names a run, a machine, a date, a wall time, a median, an envelope | dated evidence | the owning doc's dated log (perf → [INTERPRETER-PERFORMANCE-RESULTS](INTERPRETER-PERFORMANCE-RESULTS.md); eval/benchmark → [`../eval/RESULTS.md`](../eval/RESULTS.md)) |
| **yes** — it states a behaviour, a mechanism, a design consequence, a tradeoff | rationale | the finding (`IF<n>` / `KF<n>` / `API-FINDINGS`), which **links** the checkpoint rather than repeating its numbers |
| it says *"not yet / parked / pending / currently unarmed"* | a disposition | the owning `-GAPS` ledger — never either of the above |

**Why this needs stating.** The misfile is attractive, not careless: the finding is where the reasoning lives, so the measurements that motivated it feel like they belong beside it. They don't — they go stale on the next machine, and a findings doc is read as durable. It happened to IF280 (three hosted runs' medians, wall times, run ids and exceedance counts written into the finding) and only the owner noticing caught it.

**Enforcement is partial, deliberately.** `DocsEvidencePlacementGuardTest` checks the *structural* forms — no results-log entry heading in a findings doc, no CI run URL in one, and every dated checkpoint in the results doc rather than in the method doc. The judgment itself has no reliable textual marker: a run-id-shaped number and a table of measurements are both legitimate in a findings doc (measured — see the guard's own "does NOT guard" note), and a guard that fails honest content gets disabled. So the question above is yours to apply; the guard only catches the copied-entry shape.

## Writing so retrieval keeps working

- **Put the claim, the oracle, and the date in the heading.** It is what grep shows; a terse heading retrieves worse than a long descriptive one.
- **Give a new finding its anchor** in the same edit (`<a id="ifNN"></a>` / `<a id="kfNN"></a>`, trailing).
- **Cite by id**, never by a slug you constructed and never by `§n` alone.
- **Put the measurement in the log and the conclusion in the finding** — the split above, applied at the moment you are tempted to paste a number you just measured.
- **Write a new finding at skeleton weight** — claim, provenance, lock, and only the **discriminating** cases (the ones that would have falsified a rival reading). The existing long entries are deliberately *not* being retro-compressed (see the KERNEL-FINDINGS fold-status preamble for why), so the way volume stays bounded is at authoring time, not by a later sweep.
- **Amend in place.** Correct an existing entry where it lives, marked (`Corrected <date>: …`); never mint a new entry to supersede one.

## What is mechanically enforced (and what is not)

**One command runs them all: `./build.sh :docGuardTest`.** The classes below are split across the root and `:cli` modules, which both own a task of that name; the root one aggregates the cli lanes so a docs-only checkpoint cannot pick the wrong half (TESTING-SPEC, "Two modules own a task named `docGuardTest`" — a malformed ledger row shipped that way).

Guards that will fail the build: `DocsIndexGuardTest` (every doc indexed, every index link resolves) · `DirectoryIndexGuardTest` (the same, for the `scripts/` and `examples/` indexes) · `DocAnchorResolveGuardTest` (intra- **and** cross-doc fragments resolve; every IF/KF heading carries its anchor; KF ids dense) · `GapLedgerTemplateGuardTest` (the template above) · `InterpreterGapIdRegistryGuardTest` (unique issued IAG/IRG ids; live row state and title agree with the append-only registry) · `ApiFindingsNumberingGuardTest` (ordinals dense, unique, aligned) · `KernelDocsFoldContractTest` (fold markers, the §-mirror, the canonical anchor set) · `KernelDocsBasisContractTest` (a mechanism claim must name its oracle) · `DocsEvidencePlacementGuardTest` (no results-log entry or CI run URL in a findings doc; every dated checkpoint in `INTERPRETER-PERFORMANCE-RESULTS.md`, none in the method doc) · `SemanticsMapResolveTest` · `StaleGapReferenceGuardTest` (present-tense cites of deleted gaps — **source files only; markdown is not scanned**) · `ReferentDriftGuardTest` (prose still naming the pre-split home of a moved checkpoint — a rename leaves every link resolving and the sentence around it false; **markdown and source, repo-wide**) · `CliSpecVerbTableTest` · `CommandReferencesResolveTest`.

Not enforced, so verify by hand when you touch them: **whether a paragraph is dated evidence or timeless rationale** (the split above — only its structural forms are checkable), stale-gap wording in markdown (the classifier reads *logical comments*, which prose does not have — see [INTERPRETER-FINDINGS](INTERPRETER-FINDINGS.md#if141) for the measurement and why the wording was fixed instead), the [`../eval/TASKS.md`](../eval/TASKS.md) task inventory (dual-keyed `T<n>` + `family/NN` rows, so a filename-keyed guard false-positives), and compression of `folded` KERNEL-FINDINGS entries to their evidence skeleton.
