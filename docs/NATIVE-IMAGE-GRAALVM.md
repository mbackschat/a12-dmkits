# GraalVM native image — recipe, findings & status

The single durable home for building the `dmtool` CLI as a **GraalVM native image**. Other docs point here and don't duplicate it:

- [`RELEASE-SPEC.md`](RELEASE-SPEC.md) §3a — the release artifact. · [`CLI-SPEC.md`](CLI-SPEC.md) [§11](CLI-SPEC.md#packaging) — packaging *design/decision*. · `CLAUDE.md` "Build" — routes here.

> **Why its own doc:** native-image for a kernel-embedding CLI has non-obvious, interacting constraints (closed-world reflection, Groovy's `invokedynamic`, resource bundling, GraalVM-version quirks). It is **release-only** — never in the dev inner loop (that stays JVM/`installDist`), never in CI.

## 2. Build (committed, opt-in)

```sh
export GRAALVM_HOME=/path/to/graalvm-jdk-25.3.4.1/Contents/Home
./scripts/verify-graalvm-native.sh
./scripts/capture-native-config.sh
./build.sh --console=plain :cli:nativeCompile -Porg.gradle.java.installations.fromEnv=GRAALVM_HOME
./scripts/native-gate.sh
```

**`GRAALVM_HOME` is mandatory for native capture and compilation; auto-discovery is deliberately disabled.** `gradle/graalvm-native.properties` is the portable single source of the exact two-part identity: `graalvmVersion=25.3.4.1` and `javaVersion=25.0.4.1`. [`../scripts/verify-graalvm-native.sh`](../scripts/verify-graalvm-native.sh) requires both the `native-image` first line and the Oracle GraalVM runtime banner to match. The public native workflow selects the moving `25.3` Innovation train through `graalvm/setup-graalvm`, then this verifier rejects patch drift before compilation; the capture script and Gradle's `verifyGraalvmNativeToolchain` dependency enforce the same invariant locally.

The `:cli` build file carries the plugin, `toolchainDetection=false`, the mandatory exact-builder verification dependency, `imageName='dmtool'`, and the native build arguments (`-Os`, resource inclusion, locales). It also carries a **native-only** Groovy exclusion (`configurations.named('nativeImageClasspath') { exclude group: 'org.codehaus.groovy' }`). The reflection metadata is bundled at `cli/src/main/resources/META-INF/native-image/rulekit-agent/reachability-metadata.json` (auto-detected).

> **Homebrew status (measured 2026-09-02).** The current `graalvm-jdk` cask installs 25.0.4, not the 25.3 Innovation train, so it cannot satisfy this exact builder pin. Until the cask publishes 25.3, use Oracle's official 25.3.4.1 archive or JDK bundle and point only `GRAALVM_HOME` at it; do not replace the JDK-21 `JAVA_HOME` used by the ordinary build.

## 3. The three requirements beyond the defaults

### 3.1 Exclude Groovy — native-classpath-only
Groovy (`org.codehaus.groovy:groovy:3.0.25`, a kernel transitive) compiles on GraalVM 25, but **picocli's `DefaultFactory.loadClosureClass` initializes `groovy.lang.Closure` at build time** → `GroovySystem.<clinit>` reads Groovy's DGM metadata stream, which is **closed at runtime** (`java.io.IOException: Stream closed`). Excluding Groovy makes picocli skip Closure loading and startup works. **The exclusion MUST be native-only** (`nativeImageClasspath`, not `configurations.all`) — a global exclude would also remove Groovy from the JVM kernel-backed consistency and differential paths. Runtime evaluation no longer depends on Groovy: `model eval`/`rule eval`/`model compute` run on the interpreter in both JVM and native distributions. (On GraalVM 21 the failure was different — `invokedynamic`/`MutableCallSite` broke *analysis* — but the conclusion is the same: exclude Groovy from native.)

### 3.2 Bundle resources
Closed-world drops anything read via `getResourceAsStream`, so `-H:IncludeResources=` for `catalog/.*\.json` (operator catalog), `internal/templates/.*` (StringTemplate, used by `checkConsistency`), `schema/.*\.json`, `verb-examples\.json`, `.*version\.properties`, and **`.*custom-js-worker\.mjs`** (the G31 Node-worker script — `CustomJsWorker` extracts it to a temp file to invoke `node`; a missing include fails its first `--custom-conditions-js`/`--custom-field-types-js` use as "bundled worker script not found"). Verified for the existing set: the binary reads `catalog/operators.json` once these are set (a missing one fails as `IllegalStateException: … resource not found`).

> **G31 native notes (re-verify when the JS escape is first built native).** (1) The worker `.mjs` resource above must be in the include glob. (2) `--custom-conditions-js`/`--custom-field-types-js` spawn the system **`node`** via `ProcessBuilder` — native-image-clean (a subprocess, no embedded JS VM, so the kernel-free/native thesis holds), but it is a **runtime dependency**: `node` absent → the construct degrades to `unsupported` (never a crash), exactly as on the JVM. No reflection metadata is involved (the bridge uses Jackson + process I/O, already covered).

> **`-H:IncludeLocales=en,de` is REQUIRED — and is a build-host-INDEPENDENCE fix, not size tuning (added v0.8.0).** GraalVM bundles only the **build host's default locale** (+ `en`) into the image's resolvable locales unless told otherwise. The kernel's condition formatter is **German-canonical** — to render a rule in *any* language (even English) it reads the **German** terminal map (`AbstractMultiLanguageHandler.getTerminalNameByGermanTerminalName`; [KERNEL-FINDINGS](KERNEL-FINDINGS.md)). So a binary built on a **`de_DE`** host (the maintainer's Mac) silently carries the German data and `rule format` works, while one built on an **`en`/`C`** host (the Linux CI runner) **drops German** → `rule format`'s English render fails *only on that binary* with *"The german token name 'Und' is unknown"* / `ExceptionInInitializerError`. This shipped as the v0.8.0 Linux-only defect (caught by the Linux native gate over `examples/cli-jsonschema.md`). Pinning `en,de` makes every build identical regardless of host. **Reproduce a host-stripped build locally** with a forced builder locale: add `-J-Duser.language=en -J-Duser.country=US` to `buildArgs` (this mimics the Linux host on a German Mac — `LANG`/`JAVA_TOOL_OPTIONS` do **not** work, macOS reads the JVM default locale from system prefs). Negligible size cost (~−2 MB observed, since it also bounds an otherwise host-dependent set).

### 3.3 Register reflection — the tracing-agent capture, test-suite driven (partial; see §3.4)
Neither picocli-codegen nor GraalVM 25's auto-handling covers the Jackson-deserialized POJOs (`OperatorEntry` &c.) or the kernel's reflective hotspots — without config the binary throws `Cannot construct instance of OperatorEntry … configure reflection`. A **tracing-agent** capture (§5) produces `reachability-metadata.json` (~520 KB) that registers what a traced run reaches. The capture **drives the JUnit `:cli:test` suite** under the agent ([`../scripts/capture-native-config.sh`](../scripts/capture-native-config.sh)), not a hand-curated list of verb invocations — so coverage **tracks the test suite and grows with TDD**: every test that exercises a new shape (a field kind, a constraint, an operator, an apply/refactor op, an error/diagnostic path) extends the metadata automatically. This **replaces** the earlier curated capture (all fixtures × verbs + every operator + the demos), whose coverage was bounded by the invocations it remembered to list — the root cause of the v0.1.0/v0.1.1 bugs (§3.5). The suite already exercises both shapes those bugs needed: patterned fields (`FieldAddSpecTest`/`FieldModifyCommandTest`) and parser-error formatting (`DiagnosticConformanceFuzzTest`/`CheckVerbTest`).

> **⚠ A capture only ever covers the shapes it runs — so we bind it to the test suite, not a curated list.** This section once claimed a curated capture "closes the gap (0 errors)." It did **not**: the curated run had **no patterned field and no parser-error path**, so v0.1.0/v0.1.1 shipped two native-only defects (§3.5). Two changes close that for good: **(1)** the durable fix for the two bounded reflective surfaces is **rule-based, not capture-based** (§3.4 — shape-independent); **(2)** the residual out-of-package capture now **drives the JUnit suite** (§5), so it cannot silently omit a shape that has a test — and the bug-shapes now do. The agent capture is retained for the surface *outside* the §3.4 packages (operator entries, parser internals); the two bounded packages stay registered wholesale. (Measured: the test-suite capture is a **superset** of the old curated one for the native surface — its only omissions are `kernel.core.rt.*` runtime-eval classes, which native excludes anyway.)

### 3.4 The durable fix — rule-based registration of the two bounded reflective surfaces
The kernel reaches two surfaces **by name at runtime**, which static analysis cannot see and the tracing agent records only *per shape exercised* (capture-bound). Both live in **bounded, enumerable packages**, so we register every class in them **by rule** — coverage becomes **shape-independent**:

| Surface | How it's reached | Package (slash form) | #classes | Mechanism |
|---|---|---|---|---|
| Jackson model/field-type POJOs | `FieldtypeDeserializer` reflects **setters** during deserialize | `md/model/a12internal/` | 102 | wholesale `allDeclared{Methods,Constructors,Fields}` |
| StringTemplate codegen | `ObjectModelAdaptor` reflects **getters by name** during `checkConsistency` | `core/codegen/internal/generator/` | 297 | same |

Generated by **[`../scripts/gen-native-reflect-metadata.sh`](../scripts/gen-native-reflect-metadata.sh)** → committed at `cli/src/main/resources/META-INF/native-image/rulekit-manual/reachability-metadata.json` (399 entries; **separate** from the captured `rulekit-agent/` file so a re-capture never clobbers it; GraalVM merges both). **Cost: +0.8 MB** (32.7 → 33.5 MB) — negligible, since the classes are already in the image; only metadata is added. The **resource** sibling (i18n bundles) is fixed the same rule-based way: a glob `-H:IncludeResources=.*error_messages.*\.properties` in `cli/build.gradle` includes **all 12 bundles × all locales**, not the capture's en/en_US subset.

Why this beats broadening the capture: a capture covers "the shapes the run touched"; the package rule covers "**every** class in the surface, for every shape" — so a *new* field constraint, enum, date-range, computation, … cannot reintroduce the gap. The residual (a reflective class *outside* these two packages) is what the §3.6 gate must catch.

### 3.5 The bugs this closes (v0.1.0 / v0.1.1 / v0.6.0 native binaries)
Reported against v0.1.0; reproduced on v0.1.1 (same metadata). All are **native-only** — the JVM build is clean — and are instances of the same root cause (by-name reflection / lazy resource load the capture never exercised):

1. **Patterned STRING field unconstructable (reflection).** `field add` with a `string.pattern`+`patternMessage` threw `MissingReflectionRegistrationError` on `StringType.setErrorMessage(ILocalizedTextMap)` (carried by `StringType` + `EnumerationType`; the deserializer reflects setters on all 14 field types). → §3.4 Jackson-package rule.
2. **Patterned field unvalidatable (StringTemplate, *un-masked by fixing #1*).** With #1 fixed, `model check` of a patterned field threw `STNoSuchPropertyException: CodeGenMetaFields.metaFelderCode` from `ObjectModelAdaptor` during codegen → reported "not kernel-valid" though the JVM accepts it. The classic peel-one-find-the-next. → §3.4 codegen-package rule.
3. **Parser-error formatting broken in *every* locale (resource bundle).** Any invalid condition (`rule check`/`model check`) failed with `Can't find bundle … internal/vk_parser_common_error_messages/error_messages, locale <X>` — reproduced in **en_US** too, not just de_DE. The bundle loads only when *formatting a parse error*; the capture ran only valid conditions, so the whole bundle (every locale) was absent. The report's de_DE framing was a symptom: an English keyword (`FieldNotFilled`) is invalid in a `de_DE` condition language (the keyword is `FeldNichtAngegeben`), which triggered error-formatting; *valid* German conditions work on native. → resource glob.
4. **Header annotation crashes the SERIALIZE path (reflection — v0.6.0).** A model carrying a `roles` **header** annotation — the standard A12 access-control gate, which `workspace roles` actively recommends adding to every model — threw `MissingReflectionRegistrationError` on `AnnotationImpl.getName()` whenever the model was **serialized during kernel expansion**: `group extract` on any annotated model (trigger A), and `model check`/`describe`/`export`/`rule read` over a parent that **includes** an annotated sub-model (trigger B). The metadata had the annotation **setters** (deserialize) but not the **getters** (serialize) — the getters fire only during expand/copy, and no test ever *rendered* an annotated model, so the test-suite capture never recorded them. The symmetry is the tell: every type with registered setters needs its getters too. → closed at the root by a test-suite-driven re-capture (`AnnotationRenderingTest` loads/describes/exports an annotated include, so the agent records `getName`/`getValue` + any sibling header getters), with `native-battery.sh`'s annotated-include block as the runtime trip-wire. **Independently, this had escaped as a raw stack trace** (the error is an `Error`, which slipped the Exception-only `Cli` seam); the boundary now renders any such residual as a structured `RK_INTERNAL_ERROR` (CLI-SPEC [§3b](CLI-SPEC.md#result-envelope)) rather than a bare trace.
5. **Message interpolation token crashes the validate path (resource bundle — probe 11, 2026-06-22).** A rule whose error **message** carries an interpolation token (`$Field.value$` / `$Field$` / `$#Group$` — the kernel's documented way to embed a runtime value / label / row index, advertised in `schema rule add`) threw `MissingResourceException: Can't find bundle … errortext.grammar.languages.LexerTerminals` → `ExceptionInInitializerError` → exit 70, on `rule add`/`rule modify` and even `--dry-run`. The token invokes the kernel's error-text **parameter** parser (`RuleErrortextChecker` → `ErrortextParameterMultiLanguageHandler.<clinit>`), which lazily loads that `LexerTerminals` bundle — a *different* bundle from the condition parser-error one the battery already covered, and a path **no `:cli` test exercised** (the `:`/`:adapter` `MessageInterpolationTest`s exist, but the capture runs only the `:cli` suite), so the test-suite capture never recorded it. Same root as #1/#4: an un-exercised shape → a capture gap. → closed at the root by a test-suite-driven re-capture (`RuleVerbTest.addPersistsARuleWhoseMessageInterpolatesValueAndRowIndexTokens` validates a token-bearing message through `rule add`, so the agent records the bundle), with `native-battery.sh`'s `error-text PARAMETER tokens` block as the runtime trip-wire. The lesson is the recurring one: **any kernel surface the CLI advertises but no `:cli` test drives is a latent native gap** — the fix is always "add the missing shape to the suite that drives the capture," never a hand-registered one-off.

### 3.6 The whack-a-mole question — failure taxonomy, our measured exposure & the strategy
The bugs raise a fair concern: *is fixing them just whack-a-mole?* Native-image's failure modes are a **known, finite** set (anything resolved by name/dynamically at runtime that static analysis can't see). The honest defense is to enumerate that set, measure our exposure against the **real kernel** (2340 classes, probed by constant-pool reference), and pick a mechanism per class that is **rule-based** (covers all shapes) rather than **capture-based** (covers run shapes). Exposure measured 2026-06-15 on kernel 30.8.1:

| Failure class (GraalVM) | What trips it | Our exposure (measured) | Mechanism / status |
|---|---|---|---|
| **Reflection — Jackson POJOs** | deserialize reflects ctors/setters | `md.model.a12internal.*` = **102** | §3.4 **rule** (whole package) ✅ |
| **Reflection — StringTemplate codegen** | `ObjectModelAdaptor` getters **by name** | `core.codegen.internal.generator.*` = **297** (262 backing-beans), `ObjectModelAdaptor` present | §3.4 **rule** (whole package) ✅ |
| **Resources** (`getResourceAsStream`) | closed-world drops them | catalog/schema/templates/version | `-H:IncludeResources` globs ✅ |

| **Runtime codegen (Groovy)** | `GroovyClassLoader.parseClass`, invokedynamic | `groovy/lang`=4, `GroovyClassLoader`=1 — the retired `--kernel` eval path only | **excluded; the verbs run on the interpreter (native), and the `--kernel` eval path was retired** (§4) ✅ |

**The irreducible residual (stated honestly):** rule-based registration + the battery shrink the risk to "a reflective path in a class *outside* the two packages that *no battery input* exercises." That cannot be driven to zero while AOT-compiling a reflection-heavy embedded kernel — the only zero is B1 (a real JVM). The chosen posture (all three now in place): **rule-based coverage of the known surfaces (§3.4) makes the common shapes safe; the no-crash battery (`native-battery.sh`, 192 checks) catches out-of-package gaps at build time; B1 (§10, measured) is the escape hatch if the battery ever shows native can't be made robust per shape.** Failures are at least **loud** (thrown/coded), never silently-wrong.

### 3.7 An open native/JVM divergence that is NOT a reflection gap — implicit-exception messages are erased <a id="implicit-exception-messages"></a>

**Measured 2026-09-16 on the same model file through both artifacts, kernel engine, kernel `30.8.1`.** A model whose build fails *codelessly* — an implicit exception escaping the Kernel rather than a structured MVK finding — reaches the user with a different `diagnostics[].summary` per artifact:

| artifact | the `summary` the user sees |
|---|---|
| JVM launcher | `the kernel could not build this model: Cannot invoke "java.lang.CharSequence.length()" because "this.text" is null` |
| native binary | `the kernel could not build this model: Stack trace is imprecise, the top frames are missing and/or have wrong line numbers. To get precise stack traces, build the image with option -H:-ReduceImplicitExceptionStackTraceInformation` |

**The mechanism is discriminated, not inferred.** GraalVM's `ReduceImplicitExceptionStackTraceInformation` is on by default and replaces the *message* of implicitly-thrown exceptions (NPE, index, cast) with that notice; our codeless arm interpolates `getMessage()` into the user-facing summary, so the substitution travels all the way out. The control that separates "native breaks every Kernel diagnostic" from "native breaks only implicit-exception messages" was run on the same binary: a **structured** finding renders correctly there (`"code": "MVK_INVALID_TIME_ZONE"`), because its text is Kernel-authored rather than exception-derived. So the blast radius is exactly the codeless arm.

**Not a correctness divergence — a message-fidelity one.** Both artifacts agree on the verdict (`valid:false`, `KERNEL_CONFIRMED`), so nothing is mis-accepted; what the native user loses is any statement about their model, replaced by a build flag they cannot act on. Two candidate remedies, neither yet chosen: build with `-H:-ReduceImplicitExceptionStackTraceInformation` (costs image size and is a toolchain-wide change), or stop interpolating a raw exception message into that summary and render a stable sentence instead, which fixes both artifacts and is the smaller change. **Deliberately recorded rather than fixed in the same pass**: the choice touches the shipped diagnostic contract and belongs with a release decision, not with the plan edit that exposed it.

## 4. The Groovy ceiling — lifted for the verbs; the `--kernel` eval path that hit it is retired

**History (the ceiling that was):** `model eval` / `rule eval` / `model compute` used to execute the **kernel's** runtime validation against a document instance, which **generates and loads Groovy classes at runtime** (`GroovyClassLoader.parseClass`; the agent captured `Com_mgmtp_a12_kernel_generated_*` classes) — [`CLI-SPEC.md`](CLI-SPEC.md) [§11](CLI-SPEC.md#packaging)'s hard ceiling. Groovy is genuinely required by that *kernel* path (JVM and native), and the §3.1 exclusion keeps it off the native classpath, so the **kernel** engine can't run native.

**What lifted it:** those verbs now run on the **kernel-free `dm.interpreter`** — a from-scratch evaluator that reproduces the kernel's runtime semantics with no Groovy codegen (kernel-differential-verified, INTERPRETER-ARCHITECTURE/FINDINGS). So the verbs **run on the native binary** and stay on every self-describing surface. The one path that hit the Groovy ceiling — the opt-in `--kernel` eval engine — has since been **retired entirely** (Set V, INTERPRETER-DROPIN-CERTIFICATE): the interpreter is the sole runtime eval engine on every target, so no eval path invokes Groovy and no self-describing surface offers a JVM-only eval flag. `rule check`/`model check` are *structural* — they drive `checkConsistency`, which renders **StringTemplate** codegen (no Groovy compile/execute), so they too stay native (§3.4).

> **⚠ "StringTemplate, native-OK" is true only with §3.4's registration.** This line once read "native-OK — is unaffected," implying StringTemplate validate is free. It is not: StringTemplate's `ObjectModelAdaptor` resolves `<bean.prop>` by **reflective getter lookup at render time**, invisible to static analysis. Validating a *patterned* field renders a codegen path that reads `CodeGenMetaFields.getMetaFelderCode()` — unregistered → `STNoSuchPropertyException` → the model is reported "not kernel-valid" on native though the JVM accepts it (§3.5, bug 1b). Native validate is sound **only because §3.4 registers the whole codegen package**.

**Implemented — the native tree (`Cli.run(…, nativeProfile=true)`).** `Cli.JVM_ONLY_VERBS` is **empty** — no *verb* is hidden; the runtime verbs stay in the native tree (interpreter-backed) and a cold native agent discovers them normally, on the one live command tree (so `manifest`/`schema`/`--help` follow automatically). The former `Cli.NATIVE_REMOVED_OPTIONS` machinery — which stripped the JVM-only `--kernel` option in native — was **deleted** when `--kernel` eval was retired (Set V): the option no longer exists on any target, so there is nothing to strip. `Cli` detects native via `org.graalvm.nativeimage.imagecode`. **Guarded by `NativeImageRuntimeVerbsTest`** (CI, JUnit, forced-native profile on the JVM): it asserts the verbs are *present* on manifest/`--help`/`schema`, the interpreter path runs, and the retired `--kernel` flag is rejected as an unknown option on every profile — so native isn't built in CI but the contract can't regress. *(This supersedes the old hiding gate `NativeImageVerbHidingTest`, from when these verbs ran the kernel.)*

## 5. Generating the reflection metadata (tracing agent)

One committed script does it: **[`../scripts/capture-native-config.sh`](../scripts/capture-native-config.sh)** (`GRAALVM_HOME=…/graalvm-25 ./scripts/capture-native-config.sh`). The traced `Test` process clears ambient ANSI hints because `NO_COLOR` and its peers can short-circuit picocli's reflective `System.console()` TTY path; normalizing the calling shell is insufficient when a long-lived Gradle daemon retained its startup environment, and the 2026-08-09 pre-normalization recapture lost exactly that native-relevant member. It then runs the ordinary product-exercising **JUnit `:cli:test` task** under the agent — `build.gradle`'s `-PrkNativeAgent` mode points that task's `executable` at GraalVM (the agent ships there, not in the JDK-21 toolchain), attaches `-agentlib:native-image-agent=config-merge-dir`, and serializes forks (merge-dir is not fork-safe) — merging into one `reachability-metadata.json`. Repository-structure guard tasks remain mandatory dependencies of `test` and also run untraced in their own lanes. The boundary that keeps `MutationTailSingleSourceTest`'s javac `ServiceLoader` and resource-bundle traffic out of the shipped artifact is now explicit rather than task-level: a capture lifts the exclusive-lane exclusion, so `mutationTailGuardTest` is classified `untracedDuringCapture` in `cli/build.gradle` and its class alone stays excluded. Every other absorbed lane stays traced and must have its runtime inputs supplied by the traced lane. The four `publicContractTest` classes are re-hosted serially in this one traced fork: their JUnit fixed-pool properties are explicitly classified as scheduling-only because omitting them changes wall time, not which methods run, while `dmtool.executable` remains a required runtime input. A configuration-time guard rejects any unclassified missing property before an expensive capture begins. Two filters remove the remaining test-harness noise: the committed caller filter excludes JUnit/Gradle-originated reflection, while `:cli:generateNativeAgentAccessFilter` derives exact target exclusions from every compiled own `*Test`/`*Tests` class and nested class, covering test-only DTOs reached through production reflection. The traced task omits only `NativeImageMetadataHygieneTest` because that assertion reads the pre-capture destination; every mandatory test must pass. Before the recapture can replace the committed artifact, [`../scripts/check-native-metadata-removals.sh`](../scripts/check-native-metadata-removals.sh) compares against `HEAD` at **member granularity** — a removal is a (type, field/method/flag) pair the baseline had and the recapture does not — and fails unless `RK_NATIVE_REMOVAL_REASON` states why the reviewed removal is safe. JVM-only kernel-generated Groovy classes are identified by their reflective constructor dependency on `org.codehaus.groovy.runtime.callsite.CallSite`, not by unstable generated names; the raw churn remains recorded, but only the native-relevant comparison can authorize or block replacement because Groovy is excluded from `nativeImageClasspath`. The committed baseline, raw agent output, sanitized shipping candidate, canonical old/new member inventories, and raw, capture-only, and native-relevant added/removed member reports are all preserved under `build/native-metadata-regression/<HEAD>/` for the complete build/gate cycle, so the exact comparison inputs and results remain inspectable after success or failure instead of disappearing with a temporary-file trap. Member granularity is what makes the loss check usable: comparing whole entries reported every entry that merely GAINED a member as a loss (measured 2026-08-07: 5 reported, 4 of them supersets), and a guard that cries wolf is a guard that gets waived. The freshness digest covers every module build file plus the capture/removal scripts as well as source and dependency identity, because routing a test out of the traced lane can narrow metadata without changing any source file. The script then **strips own-resource globs that only a TEST resource tree provides** — the agent records what production code *asks* for, so `SpecKeys.forSchema` reading the `schema/broken-ref.schema.json` fixture off the test classpath put that glob in the shipped artifact for months, the derived access filter having removed test *classes* and nothing test *resources*. The predicate is deliberately **positive** (strip only what is found on a test tree; keep anything unresolvable) because this is the one stage whose output nothing downstream loss-checks: its earlier negative form, "no main tree provides it", dropped 4 globs on a synthetic tree where this drops 1, the extras being an `adapter/`-provided resource, one from a *generated* resources dir, and a wildcard pattern `Path.exists()` can never resolve. Roots are derived from the repository, resolution is case-exact (macOS answers yes to a miscased name that the Linux build will miss), and the same predicate backs `NativeImageMetadataHygieneTest` so the two cannot disagree. The script then copies the metadata and runs the hygiene class against that exact artifact; the hygiene check refuses both own test types and compiler services/resources. No failure is swallowed. The script delegates Gradle startup to [`../build.sh`](../build.sh), so a linked worktree shares the primary checkout's isolated cache while the traced test JVM still comes from `GRAALVM_HOME`. Then `./build.sh :cli:nativeCompile` bundles it. **Why the product test suite, not a curated verb list:** the agent only registers what it reaches, so a hand-driven list silently omits any shape it forgets (the v0.1.0/v0.1.1 bugs, §3.5). Binding the capture to the ordinary product test makes coverage track executable runtime behavior and grow with every TDD test, while excluding repository-maintenance machinery by construction.

### 5.1 Where it's stored & how often to regenerate — it is NOT a per-build cost

> **STALENESS MUST NEVER HAPPEN — so neither kind is a judgement call.** Two distinct things can lag the source, and the distinction exists to tell you *what to redo*, never *whether to bother*:
>
> | what can lag | remedy | cost | what makes it impossible to miss |
> |---|---|---|---|
> | **the BINARY** — it predates your code | `:cli:nativeCompile` | ~1m10s | a source-newer-than-binary gate, enforced on **every** path that consumes the binary: `probe/prep-probe.sh` before a probe, `scripts/native-gate.sh` before a ship |
> | **the METADATA** — the captured reflection config misses a site your change introduced | `scripts/capture-native-config.sh` | ~36–38m on the maintained macOS arm64 host (2026-09-02) | the root `CLAUDE.md` rule: re-capture before any native (re)build, unconditionally |
>
> Every source change stales the binary. The table below is the *reasoned* account of when the metadata's content actually changes — it explains **which of the two capture scripts to run and why**, and it is emphatically **not** a licence to skip the capture because your change looks harmless. [§3.5](#35-the-bugs-this-closes-v010--v011--v060-native-binaries) is why: five native-only defects shipped from exactly that reasoning, and two of them were un-masked only by fixing the previous one. The capture's own coverage is test-suite-driven, so a reflective site no test reaches is invisible to it — which means "the gate would have caught it" is false for precisely the class that has actually bitten.
>
> **The metadata's cheap detector is the capture STAMP (added 2026-08-05).** `scripts/capture-native-config.sh` records, on success only, a digest of what it was captured from — this project's test sources plus every module's main sources and the resolved external jars, i.e. the inputs of the `:cli:test` run that *is* the capture. `:cli:verifyNativeCaptureStamp` recomputes it in ~2s and both gates run it. That closes the one hole the mtime sweeps cannot see: **edit source → skip the capture → rebuild** leaves the binary newer than every source file, so both sweeps pass while the metadata describes older code. It **fails closed** — no stamp means refuse, because unknown provenance is not freshness. Re-stamping is a side effect of a real capture and never a manual step; writing one by hand would assert a freshness nothing established — so since 2026-08-07 that is **enforced, not merely stated**: `:cli:nativeCaptureStamp` refuses unless the capture script authorizes it with `-PrkCaptureInProgress`, which the script reaches only after the traced suite, the removal check and the hygiene assertion have all passed. It happened for real, minutes after a hygiene *failure*, which is why the rule now has a locus instead of a sentence.
>
> **"Every module's main sources" was false for the three KMP modules until 2026-09-16, and the reason generalizes past this bug.** The digest collected `src/main` per project — the Java layout — so `:interpreter`, `:consistency` and `:predicates`, whose sources live in `src/commonMain`/`src/jvmMain`, contributed **zero bytes**; a file added under `consistency/src/commonMain` left the digest unmoved (measured, and the same probe now moves it for all three). `:interpreter` is the native binary's only runtime-eval engine, so for every capture taken after its KMP conversion the stamp certified provenance it had never read — precisely the *edit source → skip the capture → rebuild* hole this paragraph claims to close. The trees are now **derived** (`src/main` plus every `src/*Main`) rather than named, so a new target or KMP module is covered on arrival; `jsMain` rides along because it cannot reach the JVM image but an unowed re-capture is the cheap direction. Widening the digest also invalidates the committed stamp by construction, which is the correct fail-closed outcome: the next native build is refused until a real capture re-stamps it. **The transferable lesson is that a GLOB is a hand-kept set too** — `src/main` reads as a derivation and silently encodes one module layout, so it failed exactly where an enumeration would have, and with none of an enumeration's visibility.
>
> The digest deliberately over-approximates (all modules' main sources, not a hand-listed set) because the failure directions are asymmetric: hashing too much costs a re-capture that was not owed, hashing too little ships a binary that throws. Other modules' *test* sources are excluded — only `:cli:test` is traced. That over-approximation is also why the gate has a reasoned escape hatch, `-PrkStampReason="…"`, mirroring `RK_NATIVE_REMOVAL_REASON`: `cli/src/test` is hashed whole, including the one class `-PrkNativeAgent` *excludes* from tracing, so editing `NativeImageMetadataHygieneTest` stales the stamp for a change that provably cannot alter a capture. The reason is echoed into the build log, never kept private. Residual exposure, stated rather than hidden: the stamp proves *which sources* a capture saw, not that the capture *exercised* every reflective path in them; that limit is inherent to a test-suite-driven capture and is why the operational rule stays unconditional.
>
> **Residual caveats of the capture pipeline** (measured 2026-08-07 by a focused cold review; none is live today, each is a way a *future* capture could mislead):
>
> | caveat | why it is not live | what would make it live |
> |---|---|---|
> | the strip's output is compared to nothing downstream | its predicate is positive, so it can only remove a resource physically present on a test tree and absent from every main tree | a resource served from *both* a test and a main tree |
> | only `reflection` and `resources` are compared for removals | the file has no other top-level array | GraalVM emitting a `bundles`/`serialization`/`jni` array |
> | a field's non-`name` attributes and a method without `parameterTypes` are not distinguished | every field entry is exactly `{name}` (432) and every method `{name,parameterTypes}` (1224) | a future agent version emitting richer member entries |
> | `resources` entries are compared by canonical JSON, and `jq -S` does not sort inside `tojson` | Python's round-trip preserves key order, so re-ordering does not occur | a differently-ordering writer — and it cries wolf (fail-loud), never silently accepts |
> | files other than `reachability-metadata.json` are copied unchecked, and stale files in the destination are never pruned | the capture produces exactly the one file | the agent emitting a second config file |

There are now **two committed metadata sources** (GraalVM merges both), plus a build-arg glob — and a kernel bump must refresh **all three**:

```
cli/src/main/resources/META-INF/native-image/rulekit-agent/reachability-metadata.json    (~520 KB, TEST-SUITE agent capture — §3.3/§5)
cli/src/main/resources/META-INF/native-image/rulekit-manual/reachability-metadata.json   (399 entries, RULE-BASED — §3.4)
cli/build.gradle  →  -H:IncludeResources=.*error_messages.*\.properties                  (i18n bundle glob — §3.4)
```

`:cli:nativeCompile` **reads** these; it does not regenerate them. Both metadata files derive from the **kernel's own classes**, so a kernel bump can change the class set in the registered packages, the reflective hotspots, *and* the i18n bundle base names — **all three drift on a bump and must be redone in lockstep.** Triggers and the exact redo step:

| Trigger | Redo |
|---|---|
| **Kernel bump** (`a12-kernel`) | **(1)** `./scripts/gen-native-reflect-metadata.sh` (re-derives the 399 rule-based entries from the new jars); **(2)** `GRAALVM_HOME=…/graalvm-jdk-25.3.4.1/Contents/Home ./scripts/capture-native-config.sh` (re-runs the test-suite agent capture); **(3)** confirm the i18n glob still matches the bundle layout (`unzip -l` the kernel jars for `error_messages*.properties` — §3.4); **(4)** `:cli:nativeCompile` + `./scripts/native-gate.sh`. See [`KERNEL-UPGRADE.md`](KERNEL-UPGRADE.md). |
| **CLI / catalog surface change** | a new verb, a new Jackson POJO, new operators in `operators.json` → ensure a `:cli:test` exercises it (usually already true under TDD), then re-run the capture (2). Coverage tracks the suite, so the capture follows the tests automatically |
| **A new `:cli` dependency edge** — a module joins the native classpath (2026-09-16: `project(':consistency')`, for `model check --engine portable`) | the module arrives with its own transitive surface (`:consistency` brings `kotlinx-serialization-json`), so re-run the capture (2). The edge is only as covered as the tests that cross it: `PortableEngineSelectionTest` executes the portable engine inside the traced `:cli:test`, so the suite-tracking capture reaches it. The stamp sees the edge arrive through the new external jar names, and since 2026-09-16 also sees later edits to a KMP module's own sources (§5.1 above) |
| **CLI command-class *package move/rename*** | the agent capture records command classes by **fully-qualified name**, so moving them between packages (e.g. the 2026-06-17 family-sub-package split) makes the captured FQ names stale → re-run the capture (2). A mechanical FQ-rename of `rulekit-agent/reachability-metadata.json` is a valid stopgap when GraalVM-25 isn't on hand (it was done for the split), but the next real capture supersedes it |
| **Jackson / reflection-using dependency bump** | databind internals change → re-run the agent capture (2). *Note (2026-06-18): R3/R4 added `jackson-dataformat-yaml` (SnakeYAML, reflection-using) for `workspace roles`' `roles.yaml` + `users.yaml` reads — a new reflective surface the next capture must cover; `cli.workspace.WorkspaceRolesCommandTest` exercises it, so the suite-tracking capture picks it up automatically.* |
| **New kernel reflective surface** (the gate finds a `MissingReflection`/`STNoSuchProperty` outside the two §3.4 packages) | add the offending package to `PACKAGES` in `gen-native-reflect-metadata.sh` and re-run (1) — extend the *rule*, don't hand-add one class |

The **verification gate is the trip-wire**: if any source lags, a fresh reflective path throws `MissingReflectionRegistrationError`/`MissingResourceException`/`STNoSuchPropertyException`, and the native gate fails. **But note (§3.5): the gate's inputs decide what it catches** — the demo-only gate that shipped passed while patterned-field/parser-error paths were broken. `native-gate.sh` now runs the **no-crash battery** ([`../scripts/native-battery.sh`](../scripts/native-battery.sh), §3.6 — 192 checks across every fixture × read/validate verbs + the FieldKind × constraint matrix + invalid conditions per locale + the self-describing surface (manifest/operators) + a real rule read-back), so the broad reflective/resource surface is checked, not just the happy-path demos. Add a shape to the battery whenever a new native-only gap is found.

### 5.2 Capturing in slices, when one process cannot live long enough <a id="capture-slices"></a>

The traced suite runs 36–38 minutes, and an **agent harness cannot hold a single process that long**: a harness-backgrounded task is killed by a memory watchdog, and a Monitor is killed at its 30-minute ceiling — both measured 2026-09-16, three dead captures, and the ceiling is recorded in [AGENT-RUN-DISCIPLINE](AGENT-RUN-DISCIPLINE.md). Adding `maxHeapSize = '1g'` to the traced fork (it is the only test JVM that is both single-forked and long-lived, so it alone accumulates half an hour of lazily-collected garbage against a default max heap of a quarter of physical RAM) was not sufficient on its own.

**`config-merge-dir` is what makes slicing legitimate rather than a shortcut**: it already merges, so tracing disjoint slices of the suite into one directory yields the union of their traces. That union is a **superset** of a single run's, never a subset — each slice repeats JVM and static-initializer reflection that one run traces once — and an over-approximated reachability set is the safe direction. So the knobs below change how long the capture takes, not what it contains.

| knob | effect |
|---|---|
| `RK_NATIVE_TESTS=<file>` | trace only the classes named in `<file>` (one FQCN per line), record them, stop before the assemble steps |
| `RK_NATIVE_KEEP_CFG=1` | add to an existing `$RK_NATIVE_CFG` instead of wiping it |
| `RK_NATIVE_ASSEMBLE=1` | skip tracing; run the removal check, strip, copy, hygiene and stamp over what the slices accumulated |

A slice-bounded capture would BE §3.5's defect class — coverage bounded by what someone remembered to list — so the completeness claim is mechanical instead of promised: each slice appends its classes to a manifest in the config dir, and **the assemble step refuses to stamp while any compiled test class is unrecorded**, naming the ones that are. A name that matches no compiled test class is rejected at slice time, since it would otherwise be recorded as traced while contributing no trace. Read the gate for exactly what it says — *the slicing omitted nothing*. It does not certify the traced set: the task still applies its documented exclusions, so a slice can pass 20 classes and execute 18, identical to an unsliced capture; and a reflective site no test reaches stays invisible here exactly as it is to one run, which is §3.5's open residue rather than anything slicing introduced.

Measured 2026-09-16, first chunked capture: 249 compiled test classes in 11 foreground slices, ~39 minutes total including per-slice JVM startup, every slice green, then a 13-second assemble. Per-class tracing cost varies about 2.5× (7.5 s to 19 s), so size slices by a conservative worst case rather than by an average. The removal check reported **0 committed entries removed** and the capture added 22 reflection entries and 1 resource — new CLI surfaces (`EngineOption`, its picocli converter, `PortableCheck`), the `DateFragmentType` serializer mixin, kernel runtime Groovy call-site classes and a codegen template. That delta is the normal accumulation the **unconditional pre-native-build re-capture** exists to absorb, not a missed obligation: §5.1 requires a re-capture before a native build, and none had been built since those features landed.

## 6. Sizing & shrink levers

`-Os` (GraalVM 25) remains the big lever: the current Oracle GraalVM 25.3.4.1 build is **43.74 MiB** with reflection metadata. The checksum-verified public `v0.13.0` macOS arm64 artifact is **45.64 MiB**, making the current image **1.91 MiB / 4.18% smaller**. Mach-O segment comparison locates that reduction primarily in compiled text (**−1.52 MiB**) plus the native image heap (**−0.38 MiB**). The **19 MB** bare / **~33 MB** metadata-bearing figures belong only to a pre-release 25.0.3 lab measurement with a smaller capability set; they must not be presented as a previous release or as evidence that 25.3 added 10 MB. The current binary remains materially below the historical jpackage app-image (§10: **119 MB trimmed / 147 MB**), but that old cross-revision ratio must not be transferred to the current builder without a same-commit jpackage measurement. Further levers if needed: `--strip-debug`, drop more unused kernel jars, tighter (hand-authored vs full-agent) metadata. `upx` (~50%) is possible but **breaks macOS notarization + slows startup** — not for distribution.

**Public-predecessor timing sample (2026-09-02, informative—not a builder-only benchmark).** The checksum-verified public `v0.13.0` binary and the 25.3 candidate were each run 50 times after 10 warmups with Hyperfine's shell disabled and warm OS file caches. The real `model check` outputs were equal on the compared contract fields; both manifests contained 82 verbs. The source revisions differ, so the sample answers whether the candidate has a visible end-to-end regression, not how much GraalVM alone changed.

| Command | Public `v0.13.0` median | 25.3 candidate median | Candidate delta |
|---|---:|---:|---:|
| `--version` | 55.38 ms | 55.00 ms | −0.69% |
| `manifest` | 63.04 ms | 64.23 ms | +1.90% |
| `model check` (`order-ruled.dm.json`) | 106.02 ms | 103.79 ms | −2.11% |

The deltas straddle zero and stay within 2.11%, so this sample supports **no material runtime-speed claim** for the upgrade. A builder-only performance claim requires the same clean source, metadata, and command corpus compiled by both builders.

## 7. Decision — native-only for v1 (B2)

**Decided: v1 ships native-only.** The shipped CLI is the GraalVM 25 native binary — the right fit for the agent-first, latency-sensitive use case and a single downloadable executable (the current macOS arm64 build is 43.74 MiB). GraalVM 25 closed both earlier blockers:

1. ~~Reflection coverage~~ — **done** (§3.3, the comprehensive capture).
2. ~~The runtime-eval native gap~~ — **done** (§4): the verbs run on the kernel-free interpreter and remain visible on every surface; `NativeImageRuntimeVerbsTest` guards the full native contract.

**Scope consequence of native-only:** v1's shipped CLI **does** offer runtime evaluation (`model eval`/`rule eval`/`model compute` — on the kernel-free interpreter), `model seed`, and portable `model expand`. With `--kernel` eval retired (Set V), there is no JVM-only eval engine left — evaluation is interpreter-only on every target, so native has no eval-capability gap. No jpackage/B1 full-verb distributable in v1. (B1 — a trimmed JVM + launcher, no reflection grind, **measured at 119–147 MB/OS and ~600 ms start** below — stays the documented fallback if a real consumer ever needs a bundled kernel engine outside the dev loop.) What's left for the release is **release-engineering only** — signing/distribution (RELEASE-SPEC).

**jpackage (B1) — measured 2026-06-15** (not estimated). Built from `installDist` via `jpackage --type app-image` (`jdeps`-derived module set `java.{base,compiler,desktop,management,prefs,scripting,sql}`):

| | Native (historical 2026-06-15 measurement) | B1 (historical 2026-06-15 measurement) |
|---|---|---|
| Size | **33 MB** pre-release lab binary—not a public or equal-capability baseline | **119 MB** trimmed (`--strip-debug --compress=zip-9 --no-man/-header`) / 147 MB untrimmed — runtime 99 MB + libs 20 MB |
| Cold start | **~90 ms** | ~600 ms warm, ~1.5 s first-call |
| Demos | **6/6** (incl. cli-runtime — interpreter-backed) | **6/6** |
| Native-image failure classes | the §3.6 taxonomy — *managed* (rule-based + battery), residual remains | **zero** (it's a JVM) |

**Decision (re-affirmed on measured data): native-only for v1, B1 = proven escape hatch.** The current **43.74 MiB** single-file artifact is aligned to agent-plugin delivery and is **4.18% smaller** than the actual public `v0.13.0` predecessor, while the reflection risk is now *bounded* (§3.4) + *gated* (§3.6 battery). The historical 33 MB / 119 MB and ~90 ms / ~600 ms lab pairs prove that B1 is a feasible fallback, not the current product's size or latency ratio. With `--kernel` eval retired (Set V), B1 has no unique eval win left — the runtime verbs run native on the interpreter — so B1's only remaining offer is zero native-image risk. Flip to B1 only if shipping a bundled kernel engine becomes a real need, or the battery shows native can't be kept robust per shape. The B1 build is reproducible from the recipe above (no committed artifact — it's the fallback, not the ship).

**Relative delivery-footprint NFR ([INTERPRETER-SPEC.md](INTERPRETER-SPEC.md) NFR-F1).** The proposed release ratio is native-binary size **≤40%** of the equivalent trimmed JVM app image, with **≤⅓** as the proposed design target; both remain candidate values, informative until per-number certified (IF137). Certification must compare artifacts built from the same clean commit and explicitly equivalent capability/dependency set, recording both sizes at release. This is deliberately relative, not a fixed-MB ceiling: bounded reflection metadata, resources, or interpreter caches/code that preserve correctness or improve startup/throughput are allowed, and a reviewed NFR win may justify a baseline update. The historical 33 MB / 119 MB pair was measured on 2026-06-15, before interpreter-backed native evaluation existed, so its ~28% ratio is plausibility evidence only—not proof that the current product meets either candidate. Because dmtool still bundles the kernel for the MVK oracle, the comparison measures the whole delivery, not the interpreter library in isolation. IF173's clean-commit current/previous collector now builds and executes both the native binary and a `jpackage` image staged from native's Groovy-excluded classpath; its ratio remains informative until IF137's promotion protocol is completed.

## 8. Verification gate — two gates, two targets

Both targets exercise the same public contract rather than maintaining target-specific semantic expectations:

- **JVM gate** — `:cli:publicContractTest` builds and spawns the exact `installDist` launcher; [`../scripts/verify-demos.sh`](../scripts/verify-demos.sh) discovers and exact-matches every Showboat demo. CI runs both through `:cli:check` and the demo script.
- **Native gate** — **[`../scripts/native-gate.sh`](../scripts/native-gate.sh)** first runs [`native-no-java-smoke.sh`](../scripts/native-no-java-smoke.sh) against the actual artifact, points the same `publicContractTest` task at that binary, discovers and byte-verifies every native-applicable demo, then runs the broad no-crash battery. The no-Java smoke carries a Java-dependent launcher positive control.

There is no native-demo skip registry because `Cli.JVM_ONLY_VERBS` is empty: every discovered demo must byte-match. Runtime verbs use the native-safe interpreter, so `cli-runtime.md` and the packaged journey exercise them on both targets; the retired `--kernel` eval option is guarded by `NativeImageRuntimeVerbsTest`. `cli-custom-types.md` additionally requires `node` on the host `PATH`; the gate must fail fast rather than silently skip it. > **Closed (v0.2.0) — `manifest` + a real `rule read` read-back are now in the battery.** `manifest` lives only in `cli-tour.md` (which was skipped on native back then), and the fixture sweep's `rule read` runs **without** a `<rulePathInModel>` (picocli rejects it before the read tier) — so for a while the only thing running `manifest` on a native binary was the **Windows CI smoke** (RELEASE-SPEC §4), and the rule read-back was untested locally too. This split keeps "native ≡ JVM" honest at the public process boundary while the no-crash battery covers native reflection/resource shapes beyond the happy-path journeys.
