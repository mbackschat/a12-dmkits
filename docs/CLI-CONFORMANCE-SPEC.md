# CLI conformance — the self-explain + diagnosis harness

This is the **contract** every `dmtool` verb must satisfy and the **gates** that enforce it. Its purpose is the project's #1 priority — a cold LLM agent (and a library dev) must be able to *discover* the surface and *recover* from every error using the tool's own output, never an out-of-band skill. The harness exists because that promise was silently unmet: a hand probe of 13 mutating verbs (2026-06-13) found **11 returned a bare stderr string on a not-found input** — no envelope, no code, no fix — and one accepted invalid input at exit 0. No gate caught any of it. The lesson driving this spec:

> **Gates over checklists.** Anything an LLM (or a human) can skip, will eventually be skipped. A criterion that matters becomes an executable gate that fails the build — a checklist item is only the human-readable shadow of a gate.

The home of the *safety-gate* contract is [`CLI-SPEC.md`](CLI-SPEC.md) [§6](CLI-SPEC.md#op-taxonomy); the *operator vocabulary* is the `operators` verb (the self-describing catalog; its design is the catalog spine in [`PROJECT-DESIGN.md`](PROJECT-DESIGN.md)). This doc is the *conformance* contract — what makes a verb self-explaining and well-diagnosed, and the guards that prove it.

## The anti-patterns it forbids (grounded in observed misses)

| # | anti-pattern | observed |
|---|---|---|
| **AP1** | **bare-fail domain error** — `fail(msg)` (stderr text, exit 2) for a not-found/invalid condition instead of a structured envelope | 11 of 13 mutating verbs |
| **AP2** | **asymmetric gating** — one wrong-input position richly diagnosed, its peer not | refactor source vs destination |
| **AP3** | **silent accept** — invalid input → exit 0, no diagnostic (the agent thinks it succeeded) | `config modify --decimal-separator XYZ` |
| **AP4** | **happy-path-only tests** — success + the refusals the author *thought of*, never the full error matrix | the original move verbs |
| **AP5** | **surface rot** — stale `@Command`/param descriptions feeding `manifest`/help; un-described params | the pre-flip rename descriptions |
| **AP6** | **under-surfaced verb** — a verb ships listed + described but its **I/O shape is undiscoverable** (no resolvable `schema` pointer) or it is never **demonstrated in action** | `meta` shipped with no `schema` pointer; the templates/cross-cutting verbs had no worked example |
| **AP7** | **cross-surface contract drift** — implementation, help, schema, examples, skill, and packaged artifact are each plausible alone but disagree about operational safety or success | `batch` was documented as both atomic and partial, and a failed child once left outer `ok:true` |
| **AP8** | **unattributed kernel vocabulary** — a LOCAL refusal reaches the attribution-free channel carrying the kernel's own `MVK_*` code (or naming the kernel in prose), so a consumer cannot tell our gate from the kernel's verdict. AP1's sharper sibling: the shape is a bare stderr line, but the harm is MISATTRIBUTION, and it survives wherever a refusal is coded yet unpublished | `field add` said "the kernel's cap" for its own refusal; `patterns` printed a bare `MVK_ERROR_REFERENCE_TO_CALCULATED_FIELD` from `Computation.Builder`'s pre-check |

## The two contracts

### 1. The diagnostic contract (diagnosis)

> A **domain error** of any mutating verb — and of any locator-bearing **read** verb (a not-found target) — is a **structured envelope** — `outcome ∈ {refused, rejected}`, exit `2`/`1`, `written:false` — carrying **≥1 diagnostic with `code` + `where` + `fix`**, and the `code` **resolves in the diagnostic registry**.

- **Domain error** = the CLI syntax parsed, the model loaded, the op was attempted, and a model-level precondition failed (not-found, collision, type mismatch, kernel reject, …). These MUST be structured.
- **Usage / IO errors** (bad CLI syntax, missing/unreadable `-m`) MAY stay plain text — they are picocli/IO concerns, not domain diagnoses.
- **`refused`** = a pre-mutation safety-gate precondition failed (exit 2, nothing written). **`rejected`** = the kernel re-validate failed (exit 1). Never a bare `fail()` for a domain condition; never `outcome:applied`/exit 0 on invalid input (AP3).
- Every **error-severity** diagnostic carries `code` + `where` + `fix`. `explain` (the *why*) is added where it helps.
- **A JSON spec file's own shape is a domain error, not a usage error** — the exemption above covers picocli argument syntax, while a `<rule-spec.json>` / `<computation-spec.json>` key that is missing, non-path, or self-inconsistent is content the tool *read and judged*. It rides `rejected` with the offending spec KEY in `where.arg`. Most of the class never reaches the command: `rejectInvalidSpec` validates the spec against its published schema first and names every missing or ill-typed key at once, so a command's own parse guard answers only what the schema cannot state — `rule add`'s error-field-inside-group, `computation add`'s path form, and an empty `messages` array (`minItems` is declared but not enforced). Reading the usage exemption the other way is what kept `rule add` on plain stderr until 2026-08-29, one verb out of step with its own peer.

Malformed model loads are input refusals: `outcome: refused`, exit 2, `RK_MODEL_INPUT_INVALID`, and diagnostic source `PRECHECK`. They carry no `valid` or `verification`, because loading failed before a consistency verdict. `where.arg` identifies the input file when available; the diagnostic preserves the parser's location or missing reference slot. Unexpected failures reaching the CLI exception boundary retain `RK_INTERNAL_ERROR` and exit 70. Enforcement is the typed `ModelInputException` load boundary and `Cli` mapper; `ModelInputFailureTest`, `ModelInputClassificationTest`, `InternalErrorBoundaryTest`, and `MalformedModelPublicContractTest` lock the in-process, classification, and packaged paths.

Local validation boundaries preserve that distinction too. `ModelDocument.validate` and `EditSession.validate` propagate unexpected resolver failures unchanged; `KernelModelPreparation.expand` translates only A12's `DocumentModelExpansionException` into a model rejection. CLI edit gates catch the candidate's `ModelConsistencyException`; reader catches use `BaseCommand.withFailureContext` to preserve the four types handled by `Cli` (`ModelConsistencyException`, `UnresolvedReferenceException`, `ModelInputException`, `ModelPreparationError`) and retain other failures as internal errors with their original cause. Profile parsing and the bounded-synthesis precondition use `ProfileInputException` to preserve their existing input-failure channel without catching arbitrary `IllegalArgumentException`s. `ValidationFailureBoundaryTest` and `LocalFailureBoundaryTest` lock defect identity, the real CLI error mapper, genuine expansion rejection, valid includes, and malformed-profile controls; `EditGateRejectionTierTest` locks the existing edit rejection channels.

Argument validation stays outside those loading and validation catches: scaffolding binds its model before validating pattern arguments, while config modification and typedef unimport retain their existing edit-argument failure handling before calling `validate`. `LocalFailureBoundaryTest`, `ConfigVerbTest`, and `TypedefImportVerbTest` lock malformed scaffold input, removal of the last locale, and an absent import.

### 2. The self-explain contract (discoverability)

A cold agent learns the whole surface from the tool:

| an agent can discover… | via | gate |
|---|---|---|
| every verb + its params (with op-record key) | `manifest` (derived from the live picocli tree) | `ManifestVerbTest` / `ManifestTreeTest` |
| what each verb does | the `@Command` description (non-blank, capability-only) | `ManifestVerbTest` |
| what each param means **and what to pass** | the param description **+ its `@ParamKind`** (e.g. "a FIELD_PATH that must exist" vs "a NEW_NAME you choose") | the conformance matrix (description) + `ParamKindManifestTest` (kind) |
| a verb's I/O shape | `schema <target> <op>` → the `result` schema (and `schema <verb>` for the single-token **envelope** verbs like `meta`); input-bearing verbs add an input schema with CI-executed `examples` | `SchemaVerbTest` / `SchemaExamplesGuardTest` / the conformance matrix |
| **a verb in action** | the verb's `example {intent, command}` in `manifest` — a worked, read-only invocation the agent can run | the conformance matrix / `VerbDemonstrationTest` |
| **what a `code` means** | `dmtool diagnostics` (list) / `dmtool diagnostics <CODE>` (explain) — the `operators` twin, derived from the registry | registry parity guard |
| what `severity`/`source` mean | `schema diagnostic` (the `severity`/`source` enum descriptions) | schema guard |
| whether an invocation reads/writes, what survives failure, dry-run behavior, output kind, aggregate success, and expected provenance | the generated leaf-help footer + `manifest.operationalProfiles` + the same schema annotation | `CommandContractsTest` + the packaged public-contract/mutation-safety suites |
| **what a persistence value does and does not claim** | `manifest.contractVocabulary` once, plus `schema <verb>` and the help footer for each of the 47 verbs that can write — derived from the `FailurePersistence` enum, so a new value cannot leave it behind | `CommandContractsTest` (fails on a missing *and* on an indiscriminate vocabulary) |
| **which params carry content, and which way it flows** | each param's `paramLabel` + `contentRole` (`INBOUND_CONTENT` / `OUTBOUND_DESTINATION` / `SCOPE_DIRECTORY` / `SUBJECT_MODEL`), with the vocabulary published once as `manifest.contentRoles` | `ParamContentRoleTest` (both directions + anti-vacuity + per-role reachability) |

**Content direction is derived from the label (graduated 2026-08-05; rationale corrected the same day).** `kind:"FILE"` had marked 12 of 320 params, disagreed with itself across structurally identical ones (`--output` occurs **45** times and carried it on **4**), and said nothing about direction — the same kind covered `model import-jsonschema --schema`, which is read, and its `--output`, which is written. It is now **removed**: `contentRole` replaces it on all **82** path-bearing params, so a consumer sees one file-ness signal instead of two. The lever is the **`paramLabel`** — already consistent (`<file>` ×47, `<dir>` ×13 in the live tree, extension-bearing labels elsewhere), already consumer-facing in `--help`, and mechanically inspectable. `ContentRole` derives file-ness from the label and the role from the flag, in one place, with nothing hand-listed. The label vocabulary was measured before being trusted: `<path>` is excluded because across its 8 uses (`--parent`, `--group`, `--root`) it is a *model* name-path, and `<schema>`, `<artifact>`, `<source>`, `<reference>`, `<json>` are likewise not filesystem values.

**A role describes the parameter, never the verb.** `SCOPE_DIRECTORY` and `SUBJECT_MODEL` deliberately assert nothing about writing, because both are carried by **inherited** options published once for the whole tree: `-w` is written into by `group extract` (the new sub-model lands in the first root), and `-m` is not rewritten at all by the 34 always-read-only leaves. Earlier meanings claimed "never written" and "rewritten in place" and were false in both directions. Whether an invocation writes is a per-verb fact and already has a home in `operationalProfiles`.

*Corrected 2026-08-05 — two rationales that had been published for this design were falsified by a cold review, and neither supports it:* (a) "the field type cannot carry file-ness because every path param is declared `String`" is **false** — `RootCommand.workspace` and `ModelDiffCommand`'s two workspace options are `List<Path>`, and those three are exactly the `SCOPE_DIRECTORY` params; (b) "hoisting the duplicate `--output` declarations would lose verb-specific prose" is **false** — of 45 occurrences only **10** descriptions are distinct and **36** are byte-identical, and `ReferenceRewritingRefactorCommand` already hoists four. Both came from a source-declaration grep that under-matched, generalized from a six-declaration sample; the earlier text also mis-stated the live label counts as 43/11. A type-based or partly-hoisted design is therefore a live option for a later slice, not something ruled out.

The anti-drift lever is that `fileShaped()` reads the label **independently of the classification**, so `ParamContentRoleTest` fails on a file-shaped param the rules do not place — which is what makes "a new file param cannot ship unpublished" checked rather than promised. It also guards the reverse (no role on a param that names no path), per-role reachability, that no value-less flag publishes a `paramLabel`, and — since the flag name alone cannot decide direction, as `batch --observations` proved — that no param described as being written is classified as inbound.

## The gates (what enforces each rule)

| gate | proves |
|---|---|
| **diagnostic-conformance fuzzer** | for every mutating verb — and every READ-projection verb's locator positional, regardless of `@ParamKind` (F5) — derived from the live tree, every synthesized **domain error** is a conformant structured envelope — code+where+fix, code∈registry, exit/outcome consistent, `written:false`. A new mutating OR read verb **cannot escape it.** Kills AP1/AP2/AP4. |
| **registry parity** (no-rot) | every `RK_*` code the tool can emit resolves to a registry entry — `RkCodeParityTest` scans every emit site (an enum reference, or a raw `"RK_*"` literal as in `SafetyChecks`/`ApplyCommand`) against the typed `RkCode` enum, so an un-catalogued code can't ship. `MVK_*` ride `MVK-LEDGER`/`MvkLedgerTest`. |
| **operator-rejection claim coverage** | every explicit `MVK_*` claim in an operator meaning, constraint, or gotcha is backed by operator-owned, kernel-executed evidence for that exact code and consumer context: a primary invalid example, plural code-specific corrective, or dedicated condition/computation claim probe. A global diagnostic hint is not operator evidence. The denominator is all three live prose lanes; a synthetic uncovered claim in each lane—including a real structural code on an unrelated operator—proves the same audit helper fails. This guards exact authored claims, not codeless prose or undiscovered kernel behavior. |
| **single-source derivation** (no-drift) | the `diagnostics` verb, the `diagnostic.schema` enum/examples, and the API Javadoc all **derive from the one registry** — a guard forbids a second hand-authored copy of a code's meaning. |
| **conformance matrix** (`CliConformanceMatrixTest`) | the single **derived** per-verb gate (folds the old completeness check): every verb is described, every param is described, every **envelope** verb advertises a `schema` pointer that *resolves to real JSON*, and every verb is **demonstrated** (a worked example in `manifest`). One row per verb, one column per obligation — so a new verb can't ship under-surfaced, and a newly-learned anti-pattern is a one-column change. Kills AP5/AP6. |
| **demonstration gate** (`VerbDemonstrationTest`) | every `verb-examples.json` invocation (the one `manifest` surfaces) is **executed through the tool** against a fixture and must produce its documented outcome — so the "in action" example an agent reads cannot rot. All examples are read-only (read or `--dry-run`). |
| **silent-accept guard** | scalar/enum setters reject invalid input with a structured diagnostic (or are documented freeform + kernel-confirmed). Kills AP3. |
| **attribution guard** (at the shared test sink) | no in-process CLI invocation may leave an `MVK_*` token on **stderr** without an envelope beside it carrying a `source`. It lives inside `CliTestSupport.run`, so **every** test in the estate is the detector — including ones written later for unrelated reasons — rather than a probe corpus that can only cover the cases someone thought of. That distinction is the finding, not a preference: the first fix for AP8 enumerated four spec verbs, declared the class closed, and missed `patterns`; a cold review found it. Two carve-outs, both about text that MENTIONS a code rather than reporting one: picocli usage (help documents the reject it prevents) and the `diagnostics` verb (explaining the vocabulary is its contract). Kills AP8; locked does-fire and does-not-fire by `UnattributedKernelVocabularyGuardTest`. |
| **the prose branch is unreachable elsewhere** (enumerated, not reasoned) | At `024d29f09`, the remaining reader helper could convert `PrecheckException` to prose; the measurements below tested reachability. The current helper preserves unexpected failures as internal errors (the local-boundary contract above), so that generic prose sink is gone. Measured on both candidate routes, at `024d29f09`: **(a)** the locator class — 13 read/report verbs probed with a bogus reference, every one returning a structured envelope (their `PrecheckException`s are caught upstream by the dedicated `RK_NO_SUCH_*` paths), the two exceptions being a picocli usage error and `export`, which is `RAW_JSON` by contract; **(b)** the builder-precheck class on the READ path — a hand-built, kernel-valid model carrying a rule whose error field sits outside its group (unauthorable here, `RK_ERROR_FIELD_OUTSIDE_GROUP`, won't-fix) reads back at exit 0 with a proper envelope, so an over-strict authoring check does not make a legal model unreadable. `patterns` was the one site a builder pre-check genuinely reached, and it is fixed. Locked by `BuilderRefusedShapeStillReadsTest`; the sink guard above covers any future site. |
| **negative-control rehearsals** | each gate above is proven to **fire** (a fabricated bare-fail verb → fuzzer red; an un-catalogued code → red; a param missing a kind → red) so a guard can't rot into a no-op. |
| **operational-contract owner + packaged falsification** | `CommandContracts` classifies every live leaf and every argument-dependent profile once; help, manifest, and schema render it. `DmtoolPublicContractTest`, `DmtoolMutationSafetyTest`, and `PackagedDmtoolJourneyTest` spawn the exact selected distribution launcher, reconcile the complete 81-leaf/48-write/39-preview denominator, validate envelopes and provenance, prove byte-identical rejection/dry-run plus real-write positive controls, lock rollback/partial behavior, and execute the cold-start journey. The public-contract owner also falsifies blanket envelope prose against packaged raw-artifact and raw-view controls, so the served result schema and canonical skill must resolve matching `returns.views[]` before the primary `returns.kind`. |

**Operator-prose completeness is a two-source lock (CG2, 2026-08-02).** The mechanical denominator is the live catalog: 110 meanings + 170 constraints + 192 gotchas = 472 prose units at graduation. The authored half stores only locator + digest + classification/evidence, never a second prose copy. `CatalogProseReviewGuardTest` requires exact coverage and fails on new, removed, moved, or changed units. `REJECTION` means the prose asserts a model-check refusal and is satisfied only by a structured claim with a rejected outcome; arbitrary `TEST` evidence is forbidden on that axis. `ADMISSION` identifies a positive static/model-check domain assertion and must point either to an owner-bound claim-probe side whose recorded outcome is `ACCEPTED`, or to an exact method in the dedicated `validate/laws` kernel-law package. `RUNTIME` identifies an evaluation claim and is the only semantic lane where an arbitrary reviewed runtime-test link is admissible; `DESCRIPTIVE` is exclusive. Structured catalog facets and claim probes are operator-owned, and claim-probe links pin the selected trigger/control verdict and code. The probe population is closed in both directions against the live `operator-claim-probes.json` inventory (278 at CG2 graduation), so neither an orphan probe nor an unknown review reference can pass. Positive controls reject arbitrary-test substitution for rejection or admission, cross-operator and wrong-outcome borrowing, and stale claim or probe locators. Every literal `MVK_*` token is additionally tied to an exact expected outcome.

The review that populated the registry was executed rather than inferred: at CG2 graduation the live registry contained 278 claim probes, and each runs a trigger and discriminating control against the real kernel, while runtime units name reviewed differential methods or live catalog-facet probes. The cold sweep corrected false published claims about mixed value-list entries, DATE constants in `NumberOfValueInFields`, the full `CustomCondition` name domain, direct DATE operands to `Valid`/`Invalid`, `Now` computations, and `DateRange` condition use. Later cold passes caught a confounded DateRange format probe, a borrowed runtime-test link, an over-narrow DateRange entity domain, and the arbitrary-test rejection escape hatch. The corrected DateRange probes distinguish partial-date rejection from legal DATE_FRAGMENT, mixed-format, and semantic-index operands; a dedicated tri-engine equality differential owns the runtime claim. This remains a guard over authored claims, not a claim that undiscovered kernel behavior cannot exist; cold review is the independent judgment layer.

> **`@ParamKind` classifies the value's *role*, not its multiplicity** (recorded from the Set-G T7 probe, 2026-07-10). A repeatable `Map<String,String>`/`List<String>` option — `config modify --label <locale>=<text>`, `--annotation <name>=<value>`, `--role <name>`, `--supported-character <singleton-range-or-grapheme>` — is correctly tagged `SCALAR`: each entry's *value* is a scalar, and there is deliberately **no `MAP`/`LIST` kind** (multiplicity is picocli's concern). Nothing is lost: the manifest self-describes the repeatable/map shape via the param's `flag`/label (`<locale>=<text>`) and description ("*(repeatable), e.g. `--label en_US=Permit`*", verified in the live manifest). It is also **fuzzer-inert** — the conformance fuzzer only synthesizes a `benignDefault()` for *required* params, and every one of these is optional. (Latent note for a future author: a *required* Map/List option tagged `SCALAR` would have the fuzzer pass the scalar default `"1"`, not a valid `k=v` — tag such a param `FREEFORM` instead. None exists today.)

## The conformance matrix — "is this new verb actually surfaced?"

The recurring failure mode is subtle: you add a verb, it *works*, it's *listed* in the manifest — but its I/O shape is undiscoverable or it's never shown in action, and no gate complains (AP6). The matrix (`CliConformanceMatrixTest`) makes "fully surfaced?" **one green/red signal**. It is **derived** — it walks the live `manifest` and asserts a per-verb obligation row, so a new verb is in scope automatically; you cannot opt out by forgetting to register a check.

| column | obligation | exemptions |
|---|---|---|
| **described** | non-blank capability description | none — every verb |
| **params-described** | every param has a non-blank description | none |
| **schema-resolves** | advertises a `schema` pointer that resolves to real JSON | verbs without a directional contract (below) |
| **demonstrated** | carries a CI-executed worked invocation an agent can see *in action* | the self-describing verbs |
| **status-free** | no verb/param description carries roadmap language (`TODO`, `not yet`, `for now`, `coming soon`, …) | none |
| **verdict-provenance** | `valid` appears only on a verdict route (`model`/`rule`/`workspace check`, `patterns scaffold`) | the list itself is the ledger, checked in both directions |
| **runtime-attribution** | every verb in the independent `SchemaCommand.DOC_INPUT` denominator must emit `engine:DM_INTERPRETER` and never attribute runtime output to the kernel in its manifest description, example intent, or output-schema description where present | denominator and observed engine are checked in both directions; the real shipped false sentence is the positive control |
| **receipt-totality** | a preview that ran the consistency oracle publishes `verification` | `VerbDemonstrationTest.UNGATED_PREVIEW` — today only `model normalize`, with its reason |
| **`--text` renders** | an envelope verb's `--text` output is not the JSON envelope | the artifact/raw verbs, which have no envelope |
| **operational-profiled** | every live leaf has a complete typed profile, with explicit selectors for argument-dependent behavior; the same profiles appear in manifest/schema/help | none |

**The four columns added 2026-08-01 (Phase 3) are totality columns, and each replaced a check that could not fail for the reason it existed.** They are worth reading as a set, because the shared failure mode is what makes them necessary:

- **`--text` renders** — `TextRendererDispatchTest` pins renderer dispatch given a well-formed envelope, so it is structurally blind to a verb that never produces one. That is precisely how `apply` and `batch` emitted raw JSON under `--text`. The column asserts the *inverse* over all 63 envelope demos: the output must **not** be the JSON envelope, because pass-through is the failure mode.
- **receipt-totality** — the `ConsistencyEvidence` type makes a *wrong* provenance claim unrepresentable but leaves **silence** cheap: `of(x)` compiles for any witness and yields `none()` for one that never gated. A mis-named witness or a dropped gate therefore degrades to an absent key, failing nothing. Presence is asserted per verb over an enumerated list — never `anyMatch`, which one passing verb satisfies for all of them.
- **verdict-provenance** — the behavioural backstop for a structural property. The typed factories already restrict `valid` to two of them; this covers the axis structure cannot, namely whether the route being *run* is one of those.
- **status-free** — the surface is clean today, which is exactly when this costs nothing and refuses the first "not yet" someone reaches for later. An agent reads a description at the moment it decides what to run and cannot check whether the note is still true.

**One row per verb, one column per obligation.** A newly-learned anti-pattern becomes one more column, re-checked against every existing verb at once — the same growth loop that produced AP1–AP6. The matrix *folds and strengthens* the old `ManifestCompletenessTest`: that check **skipped** a verb that advertised no schema, which is exactly how `meta` slipped through; the matrix has no skip.

**Operational behavior crosses the package boundary (AP7, 2026-08-03).** Unit tests remain the fastest local oracle, but they cannot establish that the released launcher, its command discovery, schemas, help, examples, JDK selection, and envelopes agree. The `publicContractTest` Gradle task therefore depends on a fresh `installDist` and launches that exact path directly—never the environment-selecting repo shim—and push/PR CI invokes it explicitly. Its registry denominator drives mutation safety rather than duplicating a second command list: all declared previews are byte-identical and paired with a real mutating positive control; the remaining writers persist/read back; the registered rich-input owners reject unknown or missing-required keys before writes; all persisted models pass `model check`; and every declared `ROLLBACK`, `PARTIAL`, and `CONTINUE_AFTER_CHILD_FAILURE` profile has a packaged later-failure discriminator, cross-checked **per label** rather than against a union — these guarantees differ, so a merged set cannot tell which verb promised which. The same packaged task includes `CommandRouteEquivalenceTest`, locking direct↔batch, direct↔apply, and standalone↔embedded-read parity through the distributed launcher. The native release gate points the identical task at the native binary before its demos and no-crash battery.

**The directional-contract exemption is a reasoned ledger, never an operational skip.** Every manifest leaf carries `operationalSchema`, and `schema <verb>` always returns the same `operationalProfiles` owner that help and manifest render. Where a verb also has a directional I/O contract, the manifest's `schema` pointer names it in the same response. `profile synthesize` exposes the current profile input schema, the `dm-json-model` stdout artifact, and the `-o` branch that writes the artifact and returns an applied result receipt. `model seed` exposes its `a12-document-json` stdout artifact with the exact `DocumentInstance` schema runtime verbs use as input; it has no invented receipt branch because the verb has no output-file option. Verbs with no directional shape live in `SchemaCommand.CONTRACT_EXEMPT` as a `verb → why` map; `schema <verb>` still serves their operational-only contract plus that reason:

- the four **self-describing** verbs (`manifest`/`schema`/`operators`/`diagnostics`) emit their own JSON — you run them to see it;
  **`patterns` no longer belongs in that list (2026-08-01; catalogue key corrected 2026-08-02).** It returns the standard result envelope, and its `data` payload now has a published schema (`patterns.schema.json`, served by `schema patterns`, in `DATA_SCHEMA`, conformance-checked by `DataSchemaConformanceTest`). The payload is a **`oneOf` over three shapes selected by the ARGUMENTS, not a flag** — no argument lists the catalogue, an id describes one idiom, an id plus `--arg` returns the scaffolded artifact — so all three need a real run or the `oneOf` carries unreachable branches. The catalogue calls its string-only projection `paramNames`; the detail route reserves `params` for `{name,kind,doc}` objects, so a consumer never has to infer a key's type from the route. The scaffold's `spec` is `$ref`'d from the `add` verbs' own input schemas rather than restated, since a restatement conforms to its meta-schema, executes nothing, and drifts invisibly (the `eval-doc` incident). A kernel-REJECTED scaffold returns the SAME shape with the verdict on the envelope, so it adds no branch; `--apply` is a different route that emits `changed` and no `data`;

**Descriptions are guarded only where the claim has a machine oracle.** `key:literal` claims are compared with the demonstrated envelope, interpreter runtime attribution is compared with the demonstrated `engine`, pointer syntax has its format-specific guard, and the document shape is single-sourced from `document-instance.schema.json`. General prose↔behaviour comparison is deliberately excluded: prose such as “best effort” or “what changed” has no generic oracle, and a regex broad enough to pretend otherwise would encode editorial taste as behaviour. A new claim kind joins the matrix only with its own observable oracle and positive control.
- the remaining unregistered artifact verbs (`export`, `model new`, `model expand`, `model import-jsonschema`, and `model export-jsonschema`) emit their artifact directly and stay exempt. (`model new` with `-o` additionally prints a write-confirmation envelope — the model went to the file, so stdout carries a machine-confirmable success signal — but its primary stdout form has no directional contract.)

The matrix proves the ledger is **honest**: every exempt verb exists in the manifest (no stale row) and carries a non-blank reason. Anything not exempt **must** be contract-discoverable — which is how `meta` (an envelope verb that was wrongly missing its pointer) is now locked in.

**The demonstration — every verb in action, surfaced by the binary.** A description tells an agent a verb exists; it does not show it *working*. Each verb carries a worked invocation in `verb-examples.json` (read-only by construction — a read, or a mutation under `--dry-run`), and the `manifest` surfaces it as the verb's `example {intent, command}` — so the demonstration ships *in the binary*, on the cold agent's material boundary, not in `examples/` (which the agent never sees). `VerbDemonstrationTest` **executes** every example against a fixture and asserts its documented outcome, so a drifted demo (renamed flag, changed behavior) fails the build. The matrix's `demonstrated` column accepts three forms: a `verb-examples` entry, a schema **input** example (the rich-input verbs, executed by `SchemaExamplesGuardTest`), or a reasoned row in `CliConformanceMatrixTest.DEMONSTRATION_PENDING` — a CI-locked debt ledger for a verb whose happy path needs a fixture the corpus lacks (**currently empty — every verb is demonstrated**; `typedef inline`/`import` close against the `typedefs.dm.json` + `catalogtypes.dm.json` fixtures). A **new** verb is in none of the three, so the gate fires.

## The gap-finder — the qualitative layer above the matrix (on-demand)

The matrix proves a description/example *exists, resolves, and runs*; it **cannot** judge whether the prose actually *helps* — a description can be non-blank yet useless, or a verb's semantics latent (the dual-mode `meta`). That residue is what `eval/gap-finder.workflow.js` finds. Three layers, cheapest-first:

```
deterministic matrix   →  gap-finder (this)        →  N6 benchmark
(per-commit, free)        (on-demand, ~3 agents)      (on-demand, dozens of agents)
"is it surfaced?"         "is the surface clear?"     "can an agent finish the task?"
```

**Mechanism.** The operator passes the parsed output of `bin/dmtool manifest` as `args.manifest`; the workflow derives the denominator of live top-level targets from its verb tree and refuses an absent or empty manifest. k=3 **cold** agents (opus) are each handed *only* the binary's self-description (`manifest`/`--help`/`schema`/`operators`/`diagnostics` — the N6 material boundary, no source/docs/examples). First they walk every live verb and ask whether its purpose, inputs, and outputs are clear. Then, without any extra agent calls, each tries exactly one plausible absent sibling operation per derived target and searches the same self-description for the real route; an unexplained failed guess is `MISSING_DISCOVERY`, while a corrective that names the route is not a finding. Each emits structured findings plus one `{target, candidate, attemptedCommand, observed, discoveredRoute}` receipt per target. The workflow rejects duplicates, omissions, and extras before aggregation, so three agents returning empty findings without performing the audit cannot look clean. Findings use the **fixed `gapType` enum** (`AMBIGUOUS_MODE`, `UNCLEAR_INPUT`, `UNCLEAR_OUTPUT`, `PARAM_MEANING_UNCLEAR`, `MISSING_CONSTRAINTS`, `UNCLEAR_PURPOSE`, `MISSING_DISCOVERY`, `OTHER`); a `(verb, gapType)` pair survives only if a **majority** raise it.

**The tripwire is a reasoned, both-directions-honest ledger** — `eval/gap-allowlist.json`, the same idiom as `CONTRACT_EXEMPT`/`DEMONSTRATION_PENDING`/the MVK ledger. Each entry is an accepted `(verb, gapType)` gap (by-design or won't-fix) with a reason. A run's agreed gaps diff against it: a pair **not** in the list is a new gap to triage; a list entry that **no longer surfaces** is stale and gets removed.

**It is on-demand, not a per-commit gate** (LLM cost + nondeterminism). Its output is *candidates*, not proof — a human triages them, and a gap that recurs **graduates into a new deterministic matrix column** (the AP1→AP6 growth loop). So the gap-finder *feeds* the matrix; the matrix is what actually gates. Run it via the `Workflow` tool with `{manifest: <parsed bin/dmtool manifest output>}`; results + the allow-list are the durable record.

## Never stale — the structural guarantee

The diagnostic info is **derived, never authored twice**, and **CI-verified both directions**:

- **One registry**, keyed by a typed `RkCode` enum. Emit sites reference the enum where practical; the raw `"RK_*"` literals (e.g. in `SafetyChecks`/`ApplyCommand`) are caught by `RkCodeParityTest`, so an un-catalogued code can't ship.
- Every **surface** (CLI `diagnostics` verb, `diagnostic.schema`, the API Javadoc, the dev doc) reads/points to that registry — no parallel prose to drift.
- **Forward** parity: emitted ⊆ registry (`RkCodeParityTest`, a CI scan of emit sites). **Reverse** parity: every registry entry is emitted/reachable or explicitly classified (no dead rows).
- The `diagnostic.schema` `examples` and the conformance fuzzer **execute** against the live registry every build.

The `RK_*` registry is **rulekit-owned** — it has no kernel coupling, so a kernel upgrade doesn't touch it. A kernel upgrade that adds/renames `MVK_*` codes rides the existing **MVK ledger** (`MvkLedgerTest` / [`MVK-LEDGER.md`](MVK-LEDGER.md)), not this registry; the broader kernel guardians and their realignments are in [`KERNEL-UPGRADE.md`](KERNEL-UPGRADE.md).

### What a schema change must touch <a id="schema-trigger-table"></a>

The published schemas (`cli/.../resources/schema/*.json`) are part of the self-describing surface, so they must never lag the code. A change to the thing a schema describes updates that schema in the SAME commit, and a guard fails the build when it does not. Moved here from `CLAUDE.md` on 2026-09-05, which keeps the trigger and points at this table.

| change you make | schema to touch | the guard that catches a lag |
|---|---|---|
| **add/rename a result-envelope key** (`ResultEnvelope`) | `result.schema.json` | `ResultEnvelopeFrameTripwireTest` pins the complete frame; `SchemaVerbTest` samples real effective envelope outputs against `result.schema` |
| **change a `Diagnostic`/`Where` field** | `diagnostic.schema.json` | `SchemaVerbTest`/`SchemaExamplesGuardTest` (diagnostics in real envelopes conform) |
| **change the rule/computation spec shape** | `rule-add.schema.json` / `computation-add.schema.json` (+ their `examples`) | `SchemaExamplesGuardTest` — the target-specific input examples are **executed through the tool** |
| **change the `apply`/`batch` op-record frame or add an op/key** | `apply.schema.json` / `batch.schema.json` (+ `examples`) + the `ApplyCommand.Op` enum's `keys` (field ops single-source `FieldSpec.{ADD,MODIFY}_KEYS`) | `SchemaExamplesGuardTest` — both frame example blocks are CI-executed |
| **add/rename/remove a verb** | nothing by hand for the *contract* — `manifest` + `schema <target> <op>` are **derived from the live picocli tree** (can't drift); but flip **`ManifestVerbTest.EXPECTED_VERBS`** — the **single source of the live-leaf denominator**, which `DmtoolPublicContractTest` now derives from rather than pinning its own copy (it carried a second literal, and `mcp` updated one of the two) — add a read-only `verb-examples.json` demonstration (or a reasoned `DEMONSTRATION_PENDING` row), and if the verb takes a rich JSON input, add its input schema + `SchemaCommand.INPUT_OPS` mapping. A new **cross-cutting** verb that returns the result envelope gets a `schema` pointer automatically; one that doesn't (renders an artifact / custom payload) is classified in `SchemaCommand.CONTRACT_EXEMPT` with a reason | `ManifestVerbTest`/`ManifestTreeTest` + **`CliConformanceMatrixTest`** (described · params-described · schema-resolves · demonstrated) + `VerbDemonstrationTest` (executes the example) + **`CommandReferencesResolveTest`** (a **rename** that leaves stale `dmtool …` examples fails here — every command ref must resolve against the live tree, across **both** the in-binary text (help/diagnostics/schema) **and** the command-bearing markdown an agent/installer reads: the source + public READMEs, the canonical `skill/SKILL.md`, the Codex `AGENTS.md` — markdown scanned by code-context, not prose; the tool name is single-sourced as `Cli.TOOL_NAME`. **`docs/CLI-SPEC.md` is scanned in its FENCED BLOCKS ONLY** (added 2026-08-31, after it shipped a phantom flag unscanned): a spec's prose legitimately names retired, deferred and counter-example verbs, and scanning it whole reported 13 violations of which 1 was real, which is the precision at which a guard gets switched off. **So a copyable example in a spec must resolve; put a verb you are discussing rather than recommending in prose, not in a fence.**) + **`:cli:publicContractTest`**, which `:cli:test` CANNOT run (see the checkpoint note under "Build") and which additionally pins the **return-kind vocabulary** in both `result.schema.json` and `skill/SKILL.md` — a verb introducing a new `returns.kind` must add it to both; see [the conformance matrix](#the-conformance-matrix--is-this-new-verb-actually-surfaced) and [the two-guard defense](#command-examples-never-go-stale--the-two-guard-defense) |
| **structure change** (new `FieldKind`, new structure op) | only if it changes a verb's I/O shape (above) | the relevant guard above |

The **no-rot** lever is that **every schema `examples` block is CI-executed through the tool** (`SchemaExamplesGuardTest`) — a stale example actively misleads an agent, so an unverified one cannot ship. The **no-drift** lever is that the *contracts* an agent reads (`manifest`, `schema <target> <op>`) are **derived, not authored** — they recompute from the command tree. When in doubt: add the worked `examples` so the guard executes it; never hand-author a schema fact a guard can't check.

## Command examples never go stale — the two-guard defense

Help text, diagnostic hints, and schema descriptions are riddled with worked command examples (`dmtool -m <model> rule add …`, "use `rule read`") — and so are the **command-bearing markdown surfaces** an agent or installer reads: the source + public READMEs, the canonical `skill/SKILL.md` (the **N6 material-under-test**, so a stale verb there misleads the cold agent directly), and the Codex `AGENTS.md`. A third surface is command-bearing **JS an agent harness executes**: the eval workflow (`eval/benchmark.workflow.js`) embeds `${CLI} …` command forms (`${CLI}` = its `bin/dmtool` handle), and *that* is where the task-17 recheck drifted — a positional rule passed as `rule modify --rule <name>`, whose usage error the harness silently read as "kernel rejected", scoring a correct capability 0/3. A verb rename, a tool rename, or a hand-built stale form silently turns any of these into instructions an agent *will follow into a dead end* — a real defect that the conformance matrix (which checks a verb is *surfaced*) doesn't see, because it never reads the prose. Two complementary guards cover it, and the tool name is single-sourced so a rename is one edit:

| Lever | What it does | Catches | Test |
|---|---|---|---|
| **single-source name** | `Cli.TOOL_NAME` is the one literal; `RootCommand` binds it, `manifest.tool` derives from the live name | re-hardcoded names drifting from the binding | (compile-time) |
| **pattern guard** (cheap) | forbids a fixed list of *known-bad* forms (`rulekit …`, `doc …`, the flat-verb hints, positional `<model>`) | the specific stale idioms left by past renames | `NoStaleCommandSyntaxTest` |
| **positive guard** (rename-proof) | every `dmtool …` invocation + two-token `` `target op` `` shorthand must **resolve against the live picocli tree**, across the in-binary text, the markdown surfaces above, **and the eval workflow JS** (`${CLI} …` forms, `${…}` placeholders neutralized); an invocation-count floor doubles as the tool-rename trip-wire (the JS is counted separately, keyed on `${CLI}` not the tool name, so it can't prop that floor up) | a *future* verb rename/removal, a hand-built stale command form (the task-17 class), and a tool rename that leaves the old name in the text | `CommandReferencesResolveTest` |

The positive guard is the durable one: it needs no knowledge of *which* form went bad — it derives the valid verb set and the tool name from the same tree that drives parsing, so a rename that forgets an example fails the build with the file:line and the offending token. **Scope boundaries that keep it honest:** the `examples/` demos are already guarded by Showboat (it *executes* them, so a renamed verb fails there), and the skill's plugin copies by the `sync-plugin-assets.sh --check` copy-equality gate — so the guard scans only the *canonical* markdown files. **Markdown is read by code context, not prose:** inside a fenced block the whole line is a command; outside, only inline-code spans count — so a bare prose mention ("dmtool guidance") is ignored, while a `` `rule read` `` span and a fenced `dmtool …` line are checked. Illustrative placeholders the skill teaches with (`dmtool <target> <op>`, `operators <id>`) resolve cleanly — an angle-bracket token ends the path without a violation — and a `#` shell comment or a `|` shell pipe ends the command, so a concrete `dmtool -m order.dm.json rule add … # note` still validates `rule add`, and a `dmtool … model describe | jq --arg …` doesn't mistake jq's `--arg` for a dmtool flag. **The JS surface** keys off the `${CLI}` marker (not the tool-name literal, which the JS never writes inline): the args up to the closing (escaped) backtick are taken, each `${…}` placeholder is neutralized to a `<v>` token, and the same resolve + flag-check runs — so a stale op or a phantom flag (`rule modify --rule …`) fails here **statically**, alongside the runtime usage-error backstop for the dynamically-built commands a static scan can't see.

## Library consumers — the same registry, no second source

Diagnostics aren't a CLI-only concern: the diagnostic model is **public library surface**. A dependency that drives rulekit/modelkit directly receives `Diagnostic` objects (record: `code`/`severity`/`source`/`where`/`fix`/`explain`) from `ValidationResult.diagnostics()` and the edit/validate seams. So the meaning of a code must be **dev-discoverable**, not only CLI-discoverable — and it resolves through the *same* registry the `diagnostics` verb serves:

- **`RkCode` is public.** `RkCode.byCode("RK_NO_SUCH_FIELD")` returns the catalog entry — `meaning()`, `severity()`, `source()`, `fix()`. The CLI `diagnostics` verb is a thin shell over exactly this; a library consumer calls it directly (see `Diagnostic`'s Javadoc for the idiom). `Severity` (the kernel's enum) and `DiagnosticSource` carry their own Javadoc.
- **One source, both faces.** Tool and library read the one `RkCode` enum, so they never diverge — and the parity guard above keeps it honest. `MVK_*` codes are the kernel's; their meaning is the operator catalog's (`operators`/`explain`), not this registry.

## Authoring checklist — adding or changing a verb

The checklist is the human shadow of the gates above; the gates fail the build if you skip a row.

- [ ] **Discoverable:** `@Command` description is capability-only (no status/roadmap); every param has a description (add a `@ParamKind` where the value's role isn't obvious — it's additive, spot-checked by `ParamKindManifestTest`, not required on every param); the verb appears in `manifest` (flip `ManifestVerbTest.EXPECTED_VERBS`); `schema <target> <op>` (or `schema <verb>` for an envelope cross-cutting verb) resolves, or the verb is classified in `SchemaCommand.CONTRACT_EXEMPT` with a reason; an input-bearing verb adds an input schema + a CI-executed `examples` block.
- [ ] **Demonstrated:** add a read-only worked invocation to `verb-examples.json` (a read or a `--dry-run` mutation) so `manifest` surfaces the verb *in action* and `VerbDemonstrationTest` executes it — or classify it in `DEMONSTRATION_PENDING` with a reason. **The conformance matrix enforces this and the Discoverable row's description/manifest/schema obligations** (the `@ParamKind` is additive — `ParamKindManifestTest` spot-checks it).
- [ ] **Diagnosed:** every domain-error path returns a structured envelope (`refused`/`rejected`), not `fail()`; every error diagnostic has `code` + `where` + `fix`; each `code` is an `RkCode` registry entry (so it's catalogued + explorable via `diagnostics`).
- [ ] **Symmetric:** every input position that can be wrong has a diagnostic (no AP2); no input is silently accepted (no AP3).
- [ ] **Proven:** the conformance fuzzer is green for the verb; each new refusal has a does-fire test (the §6 refactor-gate rule); a new gate has a negative-control rehearsal.
- [ ] **Documented + demonstrated** in the living surfaces (the `examples/` demo for a CLI change; the API-GUIDE snippet for a library capability), per the user-facing-no-status rule.
