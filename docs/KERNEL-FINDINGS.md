## §1 supplement — Boolean/Confirm comparability codes

The Boolean≠Confirm split is enforced at parse time with distinct codes: a Boolean compares only to `True`/`False` or another Boolean — anything else (e.g. a string) is **`MVK_INVALID_COMPARE_TO_YESNO`**; a Confirm compares only to `True` or another Confirm — `[Confirm] == False` and Boolean↔Confirm cross-comparisons are **`MVK_INVALID_COMPARE_TO_YES`**. "Not confirmed" is written `[Confirm] != True` (an unset confirm counts as not confirmed). *(Locked: `validate.laws.BooleanConfirmLawsTest`.)*

## §1 supplement — Boolean three-state matrix (runtime, 2026-06-06)

A `Boolean` has three distinct states (unset / `True` / `False`), and the runtime honors them as the spec says — verified in a filled row:

| state | `== True` | `== False` | `FieldFilled` |
|---|---|---|---|
| unset | — | — | — |
| `True` | ✓ | — | ✓ |
| `False` | — | ✓ | ✓ |

Traps pinned: `[Flag] == True` is **not** `FieldFilled(Flag)` (they diverge on a `False` value), and `[Flag] == False` ≠ "unchecked" (an unset Boolean satisfies neither equality). Contrast a Confirm, whose unset value *is* `False` (§2 supplement). *(Locked: `adapter.laws.BooleanThreeStateLawsTest`.)*

## §1 supplement — the "not …" field-list quantifiers are not complements (runtime, 2026-06-06)

Over a two-field list, the three negative fill-quantifiers disagree at the edges (fires? by filled-count):

| filled (of 2) | `NotAllFieldsFilled` | `FieldsNotCollectivelyFilled` | `NotExactlyOneFieldFilled` |
|---|---|---|---|
| 0 (none) | ✓ | **—** | ✓ |
| 1 | ✓ | ✓ | — |
| 2 (all) | — | — | ✓ |

The trap is the all-empty column: `NotAllFieldsFilled` and `NotExactlyOneFieldFilled` **include** it, but `FieldsNotCollectivelyFilled` **excludes** it (needs ≥1 filled). Picking the wrong member changes which documents the rule reports. (Verified with the row filled by a sibling, so the list fields' emptiness is what's measured.) *(Locked: `adapter.laws.FieldListQuantifierLawsTest`; interpreter parity `adapter.laws.FieldListQuantifierDiffTest`.)*

**The message TYPE of a fired quantifier is data-dependent, not per-operator (runtime, 2026-06-23).** The kernel types a fired quantifier OMISSION when the firing is **fixable by filling** a currently-empty operand, else VALUE. Most quantifiers land on one type (e.g. `AtLeastOneFieldFilled`/`MoreThanOneFieldFilled` are always VALUE — they fire *because* something is present; `NoFieldFilled`/`NotAllFieldsFilled`/`FieldsNotCollectivelyFilled` are always OMISSION — filling clears them), but **`NotExactlyOneFieldFilled` is OMISSION at k=0** (filling one → k=1 clears it) **and VALUE at k=2** (no fill reaches k=1; only emptying would). So a static per-operator polarity is wrong for it; the type must be computed from the filled-count. *(Locked: `adapter.laws.FieldListQuantifierDiffTest.messageTypeMatchesKernel`.)*

**"Kontext" = Group — a legacy German kernel term (owner-confirmed, 2026-06-26).** In older kernel/DSL vocabulary a repeatable **group** is a *Kontext* ("context"); the German operator `KontextAngegeben(G)` is today's **`GroupFilled(G)`**, and the structural over-repetition error `zuGrosseKontextnummer` (below) is literally "context number too large" = a field instance beyond the group's declared repeatability. So a real-world rule guarded by `KontextAngegeben(<group>)` transfers to `GroupFilled(<group>)` (rulekit: `m.group(path).filled()`). It is plain group presence — "≥1 descendant field of the group is filled" — not a field predicate. *(GroupFilled itself is locked by `adapter.laws.GroupFilledDiffTest`; this entry records only the terminology so a German-sourced rule reads correctly.)*

**Group-list quantifier asterisk bar (source + probe, 2026-06-17).** The *group*-list quantifiers `NotAllGroupsFilled`/`GroupsNotCollectivelyFilled`/`AllGroupsFilled` reject an **asterisk** argument — `NotAllGroupsFilled(Items*, ShippingAddress)` draws **`MVK_NO_WILDCARDS_G_ALLOWED`** (source `CheckEntityListenUtils.checkNoWildCardsInGroup`, fired on `ref.hasWildCardsInGroup()`). (BA L2397-2399 also bars a **rootGroup** argument for these three, unlike `NoGroupFilled`/`AtLeastOneGroupFilled` which allow one rootGroup — not separately probed: every group in the order fixture lives under the single root, so a rootGroup arg trips the duplicate-reference check first; left BA-stated.) *(Locked: `validate.laws.GroupQuantifierLawsTest`.)*

**A field-fill quantifier over a GROUP SCOPE = "the fields inside the group", recursively — and `AllFieldsFilled`/`NotAllFieldsFilled` iterate the FULL DECLARED repetition range, not the instantiated one (source `RuntimeController` + `ExpandService`, probe-confirmed 2026-07-06).** `AllFieldsFilled(/Group*)` / `AtLeastOneFieldFilled(/Addr)` take a **group** operand, not a field list. At parse/expand time the kernel's `ExpandService` rewrites it to a field-list quantifier over **`getAllContainedFields(group)`** — every descendant FIELD, recursively through nested subgroups (so `AllFieldsFilled(/Root/Outer)` where `Outer` wraps a sub-group `Inner{B}` requires `B` filled too). A repeatable group in the operand carries its `*` onto each descendant → starred field entities. Then the crucial special case: the runtime uses **two iteration ranges** for a starred (aggregation) entity:
- **`AllFieldsFilled` (`alleFelderAngegeben`) and `NotAllFieldsFilled` (`nichtAlleFelderOderKeinFeldAngegeben`)** iterate the **full declared range** — `EntityIterator` over `1..repeatability` at each repeatable level, *without* the `setzeEndIndicesAufMaxGesetzt` clamp — so an **un-instantiated** rep reads *empty*. Hence `AllFieldsFilled(/Lines*)` is TRUE only when **every declared repetition** (up to the group's `repeatability`) is filled: with `repeatability=2`, 2 full rows → TRUE, 1 full row → FALSE (rep 2 un-instantiated → empty). `NotAllFieldsFilled` is its empty-seeking dual (fires on any declared-range empty).
- **`AtLeastOneFieldFilled`/`NoFieldFilled`/`MoreThanOneFieldFilled`/`NotExactlyOneFieldFilled`** clamp to the **instantiated** rows (`setzeEndIndicesAufMaxGesetzt` → max-set index), so they tally only present cells (`AtLeastOne(/Lines*)` with 1 filled row → TRUE, 0 rows → FALSE). **`FieldsNotCollectivelyFilled`** MIXES the two: `mindestensEineEntity` (instantiated ≥1 filled) AND `nichtAlleOderKeine` (declared ≥1 empty). A **bare non-repeatable** group scope is a single declared rep, so the two ranges coincide there. *(Locked: `adapter.laws.GroupScopedFieldFillDiffTest` — bare/starred × both ranges × firing + polarity; interpreter treatment IF49.)*

## §1 supplement — `MaxValue`/`MinValue` over an EMPTY operand set = 0, not undefined (runtime, probe-confirmed 2026-07-06)

`MaxValue`/`MinValue` **ignore** an empty operand (an empty field, an un-instantiated rep), computing the max/min of only the *filled* values — so `MaxValue(A, empty) = A`, even a negative `A` (`MaxValue(-5, empty) == -5`, **not** 0 — the empty is dropped, it is *not* a `0` folded into the max). But when the operand set resolves to **entirely empty** (all operands empty / a starred rep list with no filled cell), the aggregate is **`0`** — the same empty-aggregate identity as `Sum` — **not** undefined/suppressed. Probe-confirmed on both the multi-field form (`MaxValue(QTY, BQ) == 0` fires with both empty) and the starred form (`MinValue(Items* Count) == 0` fires with no rows). This is distinct from a **malformed** operand, which makes the aggregate non-evaluable (→ the rule is suppressed). It was **latent** — every prior differential picked a threshold where `0` and "suppressed" coincide (e.g. `MaxValue(...) > 3` is not-fire for both), so the empty identity was never pinned until `MinValue(...) < 10` distinguished it. *(Locked: `adapter.laws.MultiFieldAggregateDiffTest`; interpreter treatment `Aggregates.max`/`min` empty → `0`.)*

## §1 supplement — the COUNT aggregates are monotonic non-decreasing → grow-only polarity (runtime, probe-confirmed 2026-07-06)

`NumberOfFilledFields`/`NumberOfFilledGroups`/`NumberOfDifferentValues`/`NumberOfValueInFields` can only **grow** under filling — filling a field / instantiating a row / adding a distinct value can only *increase* the count, never decrease it. So a fired **`count >= n`** / **`count > n`** is a **VALUE** error (no fill clears it — clearing would need *fewer* filled cells, which filling can't produce), while **`count < n`** / **`count == n`** stays **OMISSION** (filling can still reach/leave the threshold). A count therefore types directionally like an **unsigned `Sum`** (`canGrow` while a fillable operand remains, `canShrink` NEVER) — a static per-operator "count is always OMISSION" is wrong. Latent: the prior polarity locks only exercised the `<`/`==` (OMISSION) direction (`NumberOfFilledFields(...) < 2`), so the `>=` VALUE direction was never pinned. *(Locked: `adapter.laws.MultiFieldAggregateDiffTest.firedPolarityMatchesKernel` + `NumberOfFilledDiffTest`; interpreter treatment: `funcFill` types the count family `Fill.of(canGrow = leafOmission, canShrink = false)`.)*

## §11 — stored conditions are canonical ENGLISH, regardless of authoring language (serialization, verified 2026-07-06)

A rule/computation's `errorCondition`/`operation` is persisted in the DM-JSON with **English keywords**, even in a German-authored model. The condition *lexer* is language-parametric (`LexerTerminals_en`/`_de` — a German author may type `Und`/`FeldAngegeben`/`Heute`), and `DslRenderer(ConditionLanguage.DE)` can render to German for **display**, but the **stored** form is English. Verified against the real German A12 Tools workspace (2025.06-ext5): every stored `errorCondition` reads `GroupFilled(...)`/`FieldNotFilled(...)`/`And`/`NotExactlyOneFieldFilled(...)`/`MinValue(...)` — never `Und`/`FeldAngegeben`. **Consequence for the interpreter:** it only ever parses *stored* conditions, so its **EN-only parser is correct by construction** — German is a render (display) target, never a round-tripped input (INTERPRETER-GAPS §3, was IG28). The `--kernel` JVM path handles DE authoring via the kernel's own language-parametric parser; the kernel-free interpreter needs no DE lexer.

## §2 supplement — empty-as-0 is a *filled-row* behavior (runtime, 2026-06-06)

KERNEL-SEMANTICS §2 says an empty **number** field has `0` substituted in a comparison, so `[Quantity] < 100` fires on an empty Quantity. Verified against the **runtime** engine (`IDocumentRtService.validateFull`) with one refinement the spec doesn't spell out: **the substitution applies to an empty field within a *filled* group row** — a row made non-empty by at least one sibling value. An **entirely empty row** (a group instance with no field values at all) is **not evaluated**, so the same rule does *not* fire there.

Observed for `[Quantity] < 100` on `/Order[1]`: sibling `CustomerName="Acme"` + empty Quantity → **fires** (0 < 100); empty-string Quantity, valueless Quantity, or an otherwise-empty row → **does not fire**; `Quantity="200"` → does not fire (200 ≮ 100). The `FieldFilled(Quantity)` guard suppresses the empty-as-0 case even in a filled row.

**The "entirely empty row is not evaluated" rule is CONDITIONAL on the condition, not absolute (runtime + source-audited, 2026-06-23).** A truly-empty row *is* evaluated when the condition **can fire empty** — a **structural** property of the condition (`canConditionFireEmpty`), not of the data. The **negative presence conditions** fire on a blank instance — `NoFieldFilled`, `NotAllFieldsFilled`, `NotExactlyOneFieldFilled`, `FieldNotFilled` (and the group/`*` analogues) — i.e. a presence predicate fires on empty iff its count-law holds at k=0. A **comparison** does **not** fire empty (so the empty-as-0 above stays suppressed on a blank row), nor do the positive presence checks (`FieldFilled`/`AllFieldsFilled`/…) or `FieldsNotCollectivelyFilled` (needs ≥1 filled). `And` fires empty iff both branches do; `Or` iff either does. So a mandatory-presence rule (`NoFieldFilled(A, B)`) correctly fires on a completely blank form. *(Locked: `adapter.laws.EmptyRowGateDiffTest`.)*

**What counts as "entirely empty" — an INSTANTIATED repeatable-group row is CONTENT, not empty (runtime-probed 2026-07-06).** The "not evaluated" rule above is about a row with **no instantiated content**. But *creating a repeatable-group row is itself content* (the §4/§9 `GroupFillCache` split: a repeatable group is "filled" once its row is instantiated) — so a rule **IS evaluated** on an all-field-empty but instantiated repeatable row, and on a **non-repeatable ancestor whose only content is instantiated repeatable descendant rows**. Concretely, over `/Cart { Lines[*] { Qty } }` with instantiated-empty `Lines` rows and all `Qty` empty: the per-row `[Qty] < 5` **fires** (empty-as-0) on *every* instantiated `Lines` row, and the ancestor `MinValue(Lines*/Qty) < 5` **fires** (empty identity 0) @ the first row — whereas both fire **nothing** when `Lines` has **zero** rows (no content). This is the boundary the earlier "valueless Quantity / otherwise-empty row → does not fire" observations sit on: those were a **non-repeatable** `/Order` with no instantiated repeatable descendants; a repeatable row's mere existence flips it to content. A non-repeatable group's structural presence alone is NOT content. *(Interpreter parity: `adapter.laws.RepeatableRowContentDiffTest`; INTERPRETER-FINDINGS IF53.)*

**PARTIAL validation OVERRIDES the content gate — a RELEVANT instance is always evaluated (runtime-probed 2026-07-06).** In `validatePart`, the content requirement does not apply: the kernel checks **every relevant error-field instance**, firing empty-as-0 / an empty-identity aggregate even on a **non-content-bearing (empty / phantom)** relevant row — because the relevant set is the kernel's explicit "check this," which `validateFull` has no analogue of. So the two engines legitimately **disagree between full and partial** on an empty row: `MinValue(Lines*/Qty) < 5` on a `/Cart`-relevant **empty** document (zero `Lines`) fires `OMISSION @ /Cart[1]/Lines[1]/Qty` (a *phantom* row) in partial but is silent in full; likewise `[Note] < 5` on a relevant empty `Note`. The `*`-aggregate's IF42 relevance gate still bounds it under a **concrete** (non-wildcarded) relevant row (→ UNKNOWN, no fire). *(Interpreter parity: `RepeatableRowContentDiffTest.partialRelevantEmptyInstanceIsEvaluated`; INTERPRETER-FINDINGS IF54.)*

The **type-asymmetry** of the empty case (the trap — the same comparison shape behaves differently by type), all verified in a filled row:

| field type | example | empty behaviour |
|---|---|---|
| number | `[Quantity] < 100` | **fires** — `0` substituted |
| confirm | `[TermsConfirmed] != True` | **fires** — treated as `False` |
| boolean | `[ExpressShipping] == True` | **not evaluated** |
| string | `[ProductCode] == "ABC"` | **not evaluated** |
| string in a **concatenation** | `[FullName] != [FirstName] + " " + [LastName]` | **evaluated** — an empty operand concats as `""`, so `[First] + " " + [Last]` = `" "` (a real value) and the comparison fires (verified 2026-06-08, N6) |
| date | `DifferenceInDays(OrderDate, DeliveryDate) < 0` | **not evaluated** (verified via date-to-date diff, avoiding §6 literals; `DifferenceInDays(a,b) = b − a`) |

**The concatenation row is the trap an N6 run surfaced (2026-06-08).** A string field in a *comparison* gets the empty-as-not-evaluated free pass; the **same field as an operand of a `+` concatenation does not** — an unfilled string concatenates as `""`, so the concatenated expression is a real value and the comparison **is** evaluated. So a "must equal `first + space + last`" rule (`[Full] != [First] + " " + [Last]`) **mis-fires when `Full` is present but `First`/`Last` are empty** (it sees `[Full] != " "` → true) unless its operands are guarded with `AllFieldsFilled(First, Last)` — the guard a plain string comparison wouldn't need. (Verified at runtime: with `Full="Alice Smith"` and `First`/`Last` empty the unguarded rule fires; the guarded form does not; a consistent first+space+last does not fire.)

**Value-token representation (runtime document instances).** A boolean's value token is `true`/`false` (lowercase) — any other token (`TRUE`, `X`, `1`, `yes`) is a formal error (`feldJaNeinFalsch`), so the field becomes "unknown" and is not evaluated (§3). A **confirm** accepts only `true` or unspecified; `false` is a formal error (`feldJaFalsch`) — consistent with "a Confirm is a checkbox whose single value is True". *(Locked: `adapter.laws.EmptyValueLawsTest`; the runtime oracle is `adapter.laws.RuntimeLaws` — KERNEL-INTEGRATION-NOTES "Runtime behavioral-law oracle".)*

## §2 supplement — empty operand in a *computation* operation ⇒ no value (stale cleared) (runtime, 2026-06-08)

The empty-as-not-evaluated rule extends from comparisons to **computation operations**: when a computation's value expression references an empty operand, **the operation is not evaluated — the computed field gets no value, and a previously-computed (stale) value is cleared**. Verified against the runtime `IDocumentRtService.compute` (the date-range constructor case): `CoverageWindow = DateRange(OrderDate, DeliveryDate)` over an `OrderDate`-filled / `DeliveryDate`-empty `/Order` → `CoverageWindow` is **not** in the computed set (no value); a row that *already* held `CoverageWindow = 01.01.2020-01.01.2021` has it **cleared** to empty. Both-filled computes `01.01.2024-01.02.2024` (the `dd.MM.yyyy-dd.MM.yyyy` DateRangeType format). This mirrors the §2 validation-side "empty date ⇒ not evaluated" — a `DateRange` over an empty bound is the construction analog.

**Consequence (the equivalence the N6 eval relies on):** the unguarded computation and the **same computation with a `commonPrecondition AllFieldsFilled(OrderDate, DeliveryDate)` guard** compute the same value (or none) for *every* document — the guard is **redundant** (a false precondition clears the field, exactly as the unevaluated operation does). This settles the 2026-06-08 T13 judge split (judge B was right). It does **not** generalize to *string* operands — an empty string in a **concatenation** concats as `""` and *is* evaluated (the row above); the "empty ⇒ not evaluated" free pass is per-type (numbers fire as `0`, dates/strings-in-comparison are skipped, strings-in-concatenation are not). *(Locked: `adapter.laws.DateRangeComputationLawsTest`, via the `RuntimeLaws.compute` oracle.)*

## compute(): an out-of-range value is ERRORED; a computation reading an errored dependency is SKIPPED (runtime, 2026-06-26)

Two compute() facts, both probe-confirmed via `IDocumentRtService.compute`:

- **An out-of-range computed value is ERRORED, value returned.** When the computed value is not valid for the target field (e.g. a number above its `maxValue`), the kernel returns the value but flags the instance in **`getComputedFieldInstancesWithErrors()`** rather than `…WithChanges()`. So `T (maxValue 999) := [A]` with `A = 5000` yields `T = 5000`, errored. *(Interpreter: `ComputeOutcome.ERRORED`; locked `adapter.laws.ComputeErrorBucketDiffTest`, INTERPRETER-FINDINGS IF34.)*
- **A dependent of an errored computation is SKIPPED — no outcome.** In the cascade, an errored dependency's value is unusable, so the kernel does **not** compute any computation that reads it (directly or transitively): the dependent appears in **none** of the three buckets — not changed, not cleared, not errored. Probed: with `T` errored (above), `U := [T] + 1` and `V := [U] + 1` are simply **absent** from the compute result (only the errored `T` is reported). This is distinct from a *cleared* (empty-operand) dependency, which a dependent reads as empty→0; an *errored* dependency poisons the dependent subtree entirely. *(Interpreter: `compute()` tracks poisoned `(target, reps)` instances and skips dependents; locked `adapter.laws.ComputeCascadeErroredDiffTest`, INTERPRETER-FINDINGS IF40.)*

The **number** branch is confirmed for computation too (2026-06-09): a numeric copy `EffectiveFee = [BaseFee]` with **`BaseFee` empty** computes **`0`** (a value), not nothing — the empty-as-0 substitution applies in a computation operation exactly as in a comparison, so an empty *number* operand is the opposite of an empty *date* operand (which clears). **Consequence (inverts the date redundancy above):** a presence guard over a NUMBER operand is **NOT redundant** — `EffectiveFee = [BaseFee]` guarded by `FieldFilled(BaseFee)` computes **nothing** (cleared) on an empty `BaseFee`, where the unguarded form computes `0`; the two **differ**, so a candidate that adds such a guard to a number computation is **not** equivalent to the unguarded gold. (The N6 computation/modify judges carry this type split so they don't mis-equate the two.) *(Locked: `cli.ComputeDocVerbTest.anEmptyNumberOperandComputesZero` + `aGuardedNumberComputationClearsWhereUnguardedComputesZero`, via the `model compute` verb / `KernelAdapter.compute` seam.)*

## §2 supplement — TIERED computations: alternatives are selected in order by precondition; `commonPrecondition` gates the whole (source + probe-verified 2026-06-25)

A computation is a **list of `computationAlternatives`**, each an optional `precondition` + an `operation` (the value expression), optionally under a whole-computation `commonPrecondition`. The kernel codegen (`CodeGenCalculationAlternative.st`) emits, per alternative in order, `if (<precondition>) { handleValue(<operation>); continue; }` — so the runtime **evaluates alternatives top-to-bottom and the FIRST whose precondition holds supplies the value**; an alternative with no precondition always applies (an unconditional default); if **none** holds the field is **cleared** (computes nothing). A `commonPrecondition` guards the whole computation (false ⇒ cleared). This is the kernel's "tiered computation" feature.

**Probe-verified (2026-06-25)** — a `UnitPrice` computation with `[{precondition: "[Quantity] < 100", operation: "9.99"}, {precondition: "[Quantity] >= 100", operation: "0"}]`: `Quantity = 50` → `UnitPrice = 9.99` (alt 1), `Quantity = 150` → `UnitPrice = 0` (alt 2). So the precondition genuinely *selects* the operation — the discriminating-precondition case is NOT the redundant-guard equivalence above (§66, which is the narrow degenerate case of a single fill-style guard that empty-as-skip already subsumes). A precondition over an empty operand does not select its branch (it is not three-valued TRUE); a gap where **no** alternative's precondition holds → the field is **cleared** (probe-verified 2026-06-26).

**`MVK_ERROR_EMPTY_PRECONDITION` — an empty precondition is allowed only as the SOLE alternative (codegen-verified 2026-06-26).** A trailing **unconditional** alternative mixed with guarded ones is rejected at codegen — "Empty prerequisite is not allowed here." So a *tiered* computation's alternatives all carry preconditions; an unconditional operation is the ordinary **non-tiered** computation (one alternative, no precondition). The "default after guards" shape is therefore unauthorable — no consumer (or the interpreter) ever has to evaluate it. The **scale gate** also applies to an operation's *assignment*: a field operand whose scale differs from the computed field draws `MVK_INVALID_COMPARE_DEC_PLACES` (numeric **literals** are scale-exempt, §5), so a tiered operation either matches the target scale or rounds explicitly.

The **interpreter models this in full** (fixed 2026-06-26, INTERPRETER-FINDINGS IF21): `ComputationDef` carries the alternative list + `commonPrecondition`, and `DmInterpreter.compute` selects the first alternative whose precondition is 3VL-TRUE (null = unconditional), clearing the field when the common precondition fails or no alternative holds — matching the codegen selection above. dmtool's *authoring* side (rulekit `DraftComputation`, `computation add`) always supported it, so the earlier cross-stack divergence (authored-but-mis-evaluated) is closed. *(Locked: `adapter.laws.ComputationPreconditionDiffTest` — tiered low/high select, no-match→cleared, common-precondition true/false, all interp == kernel.)*

## validateFull does NOT run computations — validate and compute are separate operations (runtime, 2026-06-09)

The kernel keeps **validation** (`IDocumentRtService.validateFull`) and **computation** (`compute`) as distinct, independently-invoked operations — confirmed in the kernel dev docs (`a12-kernel/documentation/_merged/kernel-dev.md` §"Validating a document / Computations on a document": *"the use of validation and computation is very similar, therefore only one is described"*, and the worked sequence `validateFull(doc)` … `compute(doc)` … `result.appliedTo(doc)`). There is **no combined call**: `validateFull` validates the document's values **as-is** and does **not** compute computed fields first, and `compute` returns a *result* (the input is never mutated — applying it back via `appliedTo`/`apply` is a separate, opt-in step the consumer orchestrates).

**`applyTo` semantics — the apply-computed-back step (source: `IDocumentComputationResult`).** The third operation is `result.applyTo(doc)` → the **updated document** (`old + computed values`). Its javadoc is precise: it **applies the `getComputedFieldInstancesWithChanges` values and CLEARS** the instances in **both** `getComputedFieldInstancesWithErrors` **and** `getClearedFieldInstances`. So an **errored** computed value is *emptied* on apply, not carried as the bad value — same as a cleared one; only a clean VALUE is set. (`applyTo(DocumentV2)` returns a new doc, original unchanged; the deprecated `applyTo(IDocument)` mutates in place.)

**Consequence for us:** a *bare* `validateFull` sees a **computed field** as whatever the instance supplies — **empty** if absent (verified: `FieldFilled(CoverageWindow)` does **not** fire when only the `DateRange` operands are present), so a required-or-referenced computed field false-fires `mandatoryField` / misses its value. The **form-engine** answer applies the computation first. So our runtime-validate verbs **compose by default**: `model eval` / `rule eval` run **compute → applyTo → validateFull** (the form-engine flow), and **`--no-computations`** drops to the bare `validateFull`. The interpreter mirrors `applyTo` as the clean-room `DmInterpreter.applyComputations(doc)` (VALUE set, ERRORED/CLEARED emptied — INTERPRETER-FINDINGS IF45), the kernel `--kernel` path as `KernelAdapter.evaluateApplied`. `model compute` stays the pure `compute` (what does a field compute to?); the document file is never mutated by any verb (read-only — `compute`/eval report, never write `--instance`). The **engine-level** `DmInterpreter.validate == validateFull` parity stays foundational (the differentials rest on it); the *composed* path has its own differential. *(Locked: `adapter.laws.EvalDocSeamLawsTest.validationDoesNotRunComputations` (the engine split) + `adapter.laws.ComputeApplyDiffTest` (interp compute-then-validate == kernel `compute().applyTo().validateFull()`).)*

## Full vs Partial validation — `model eval` is FULL; partial may skip `*`-all-reps + `Having` rules (BA appendix, prose-only, 2026-06-17)

The kernel has two validation modes (BA "Full Validation and Partial Validation", L5303-5321). **Full validation** — our `model eval` = `validateFull` — formal-validates all fields and evaluates every rule. **Partial validation** is a page-level pre-check over an app-specified *relevant-field* set: it guarantees never to report an error fixable only *outside* that set, but **does NOT guarantee complete checking of the relevant fields** — some checks are skipped (performance/simplicity). Named skip examples: rules referencing **all repetitions** via `*` when only some are relevant (explicitly incl. `NotAllFieldsFilled`, `FieldsNotCollectivelyFilled`), and **`Having`-filter** rules. The exact skip-set is an **unstable implementation detail** (may change any release; projects must not depend on it). **Consequence:** every law we lock and every catalog example we ship is *full-validation* behaviour — a rule that fires under full validation may *not* fire under a partial page pre-check. **Prose-only by design** (the skip-set is explicitly unstable — nothing to formalize/lock). Related: the mandatory-"star" in a field's label (BA "the star method") is a *separate decidable heuristic* over a fixed allow-list of presence constructs — a UI affordance outside rulekit's scope.

## §3 supplement — a fired message's `getErrorText` is the *interpolated* end-user text (runtime, 2026-06-14)

The kernel's `IMessage.getErrorText()` returns the message **with its interpolation tokens already resolved** against the evaluated document — *not* the authored template. Its javadoc is explicit: `$<fieldname>$` is replaced by the field identifier's display string and `$<field.value>$` by the field's display value (both keeping the `$`-sign; no other substitution). Verified at runtime: a rule whose `errorMessage` is `"Discount of $Discount.value$ must not be negative."`, fired on `Discount = -5` (scale-2), yields `getErrorText()` = `"Discount of -5.00 must not be negative."` — the value token resolved, no raw `$…$` left.

**Consequence for us:** the BA's real deliverable is the text the end-user reads, and only the runtime can produce it (it depends on the data). So `KernelAdapter.evaluate` surfaces it on every `EvalMessage.message()`, and the CLI returns it as `data.messages[].message` (`model eval`) and `data.message` (`rule eval`, when fired) — closing the loop from "did it fire" to "here is exactly what the user will see" (FEATURE-GAPS G1). *(Locked: `adapter.MessageInterpolationTest`; CLI surfacing by `cli.RuleTestVerbTest.firesOnAViolatingInstance`.)*

## §3 supplement — `$field$` is the field's *display name*, and the kernel sources it from a caller-supplied `ILabelProvider` (runtime, 2026-06-23)

The `$<fieldname>$` token (above) resolves to the field's **display string** via the runtime's `identifierToString`. **Consequence for us:** both engines wire the same **label-for-locale-else-name** resolver — `KernelAdapter`'s `IDocumentDynamicServiceConfig` (so `--kernel` no longer leaks the path+index string) and the interpreter's `ModelDef.labelOf` (`renderMessage`'s name pass) — and the differential `RuntimeLaws` harness wires the matching provider so the comparison is label-to-label. ## §3 supplement — a formal error silently suppresses the author's rule (runtime, 2026-06-06)

KERNEL-SEMANTICS §3: a value violating its data-type config produces a **formal error**, and while it stands the field is **"unknown"** and cannot be evaluated in any rule. Verified at runtime with the **trap consequence made explicit**: a malformed value doesn't just raise the formal error — it **silently suppresses** an author rule that references the field (the rule's condition is never evaluated, so it does not fire, even when the would-be value clearly violates it). The kernel emits its own formal-error code; the author's code stays quiet.

Observed for `[UnitPrice] > 5` (UnitPrice scale-2) in a filled row: `"10.00"` → the author rule fires; `"10.999"` (three decimals) → **`zahlFalscheAnzahlNachkommastellen`**, author rule **not** fired; `"abc"` → **`zahlHatUngueltigeZeichen`**, not fired; a string `" ABC "` → **`fuehrendesBlank`** (leading-space formal error). These runtime formal-error codes are German internal identifiers (not `MVK_*`); they're locked as the observed contract so a kernel change surfaces in the build. *(Locked: `adapter.laws.FormalErrorLawsTest`.)*

A formal error is **attributed to a sentinel rule path** — the runtime message reports `rulePath = "formalePruefung"` (not the author rule, and not empty). So in the `model eval` output the discriminator between an author-rule violation and a kernel formal check is the **leading `/`**: an author rule's `rule` is its slash-path (`/Order/X`), a formal check's is `formalePruefung`. *(Verified 2026-06-09: `Quantity` scale-0 `"1.5"` → `zahlHatDezimalTrenner` with `rule = formalePruefung`; locked: `cli.EvalDocVerbTest.aFormalErrorIsReportedAsAKernelCheck`.)*

**Refinement (2026-06-10, RT-semantics drain — probe-corrected): the suppression is *branch-scoped*, not rule-scoped.** The unknown state makes the affected *comparison* evaluate to false-or-unknown; the ordinary `And`/`Or` three-state algebra then decides the rule. So `healthyTrue Or [broken] > 0` **still fires** via its healthy branch — a formal error does not take the whole rule out — while `healthyTrue And [broken] > 0` is absorbed (the single-branch case above, where branch- and rule-scoped look identical). KERNEL-SEMANTICS §1's "removes the rules over it from evaluation" reads stricter than the engine behaves. *(Locked: `adapter.laws.FormalErrorScopeLawsTest`.)*

**Refinement (2026-06-24, fuzz-caught): even a *presence* check on a not-check-relevant field is UNKNOWN — not just value-reading operators.** `RuntimeController.isWertAngegeben` (which backs `FieldFilled`/`FieldNotFilled` AND the field-list quantifiers) returns **UNKNOWN** when the field is **not check-relevant** (`!isPruefungsRelevant`), i.e. present-but-formally-invalid (a malformed value, a duplicate index) — only then TRUE/FALSE by filled. So `FieldFilled(malformedQty) And CurrentRepetition(Lines) > 2` does **NOT** fire (the `FieldFilled` operand is UNKNOWN → the `And` is UNKNOWN), even though `FieldFilled` reads no value and `CurrentRepetition` reads no value either. The interpreter previously matched the formal suppression only through **value-reading** operands (a malformed `[Qty]` → Unknown); a presence-only reference to a malformed field wrongly stayed TRUE and fired. Fixed at the presence check: `Interpreter.filledTri` is three-valued (empty → FALSE, present-but-invalid → UNKNOWN, present-valid → TRUE). The **field-list quantifiers share `isWertAngegeben`**, so a malformed operand makes e.g. `AllFieldsFilled` not-TRUE there too — fixed at the same root: `quantCount` is now a 3-state tally `(t = TRUE, f = FALSE)` with UNKNOWN counted in neither, and each quantifier's firing reads `(t, f, n)` (`AllFieldsFilled` `t==n`, `NoFieldFilled` `f==n`, `AtLeastOne` `t≥1`, `MoreThanOne` `t≥2`, `NotAll` `f≥1`, `NotExactlyOne` `f==n ∨ t≥2`, `FieldsNotCollectively` `t≥1 ∧ f≥1`) — reducing to the binary count law when no operand is UNKNOWN. (The kernel forbids the *negative* quantifiers — `NotAll`/`NoField`/`NotExactlyOne` — from **iterating** a repeatable group, `MVK_NEG_CONDITION_IN_ITERATION`, since they'd fire on empty repetitions; the malformed-operand parity is tested on the non-repeatable `/Order`.) *(Caught by the fuzz on `CurrentRepetition`; locked: `adapter.laws.CurrentRepetitionDiffTest.malformedErrorFieldAtFiringRow` + `adapter.laws.QuantifierMalformedDiffTest`.)*

## §3 supplement — two more NUMBER sign formal errors: signed-zero and leading-plus (runtime, 2026-06-23)

Surfaced by the **differential fuzz net** (`adapter.perf.InterpreterKernelFuzzTest` — random valid documents, assert interp == kernel), which fed a `-0`:

- **A signed zero is a formal error** — `-0`, `-0.0`, `-0.00` (any minus sign on a zero magnitude) → **`zahlNullEnthaeltVorzeichen`**. A non-zero negative (`-5`, `-0.01`) and a plain zero (`0`, `0.00`) are clean.
- **A leading plus is a formal error** — `+5`, `+0`, `+0.5` → **`zahlMitPlus`** (distinct from `zahlHatUngueltigeZeichen`; the explicit `+` is its own error, not "invalid characters").
- **Ordering: signed-zero is checked BEFORE the decimal-separator/scale checks.** `-0.0` on a **scale-0** field is `zahlNullEnthaeltVorzeichen`, *not* `zahlHatDezimalTrenner` — so a malformed value can match several checks and the kernel's precedence matters. (Leading-plus likewise wins over signed-zero: `+0` → `zahlMitPlus`.)

Both ride `formalePruefung` (the sentinel rule path) like the other formal errors, and suppress a referencing author rule (branch-scoped). *(Locked: `adapter.laws.NumberSignFormalDiffTest` — interp vs kernel over a scale-2 and a scale-0 field; the precedence is part of the lock.)*

## §3 supplement — BASELINE value checks run for EVERY kind before the type format: charset + leading/trailing blank (probe + source, 2026-06-26)

`FormalChecker.checkFieldValueFormat` runs three baseline checks on **every filled field value**, regardless of kind (string/number/date/…), **before** the type-specific format check — and they **pre-empt** it:

- **legal charset** → **`ZeichenNichtImZeichensatz`**. The legal set is `metaData.getLegalCodepoints()` — a **programming-language/codegen** config (`MetaModelImpl`, the codegen target's restricted charset; cf. the codegen `MVK_INVALID_CHAR_IN_RESTRICTED_CHARSET` "not permitted for the programming language"). It is **NOT a DM-JSON field/model property** (no `charset` key on `StringType`/`IStringType` in 30.8.1). With none configured — a plain DM-JSON model — the **default legal charset is the BMP** (`0x0000-0xFFFF`; `CharsetUtil`: "empty list ≡ 0x0000-0xFFFF"). So **any supplementary-plane character** (a UTF-16 surrogate, e.g. an emoji `😀` U+1F600) is illegal; BMP chars (`é`/`ü`/`€`/`™`/CJK) are legal. Probe-confirmed on a plain string field.
- **leading blank** → **`fuehrendesBlank`**; **trailing blank** → **`nachfolgendesBlank`** (distinct codes). Probe-confirmed across STRING, NUMBER, and DATE — and they pre-empt the type check (a ` 2024-01-01` DATE is `fuehrendesBlank`, not a date-format error).

Order: charset → leading → trailing → (type format). This **corrects** the earlier suspect §3 "string charset is not DM-JSON-declarable / no serialized key" note — the basis was about a per-field `StringType.charset` key (which indeed doesn't exist), but the runtime check fires anyway from the **default BMP** charset; the conclusion ("out of scope") was WRONG.

**Is the charset customizable? Yes — but at the CODEGEN/PROJECT level, not via the DM model.** A restricted charset *can* be declared (`KernelUtils.validateCharset`/`simplifyCharset` process a `restrictedCharset`), and the legal codepoints are **baked into the generated meta-model** by the codegen templates (`CodeGenMetaModel.st`) from the project's programming-language config — they do NOT travel with the DM-JSON model. The real-world case is a standard restricted set such as **DIN 91379** (the EU public-administration / e-government character set for names & addresses) — far NARROWER than the BMP: it would make `中文`/many symbols illegal. The probe confirms a DM-JSON model gets the **full-BMP default, NOT DIN** (`é`/`ü`/`€`/`™`/`中文` all legal), so a project-configured DIN charset is genuinely a separate input. A model loaded purely from DM-JSON (the interpreter's path **and** the dynamic-codegen `RuntimeLaws` differential) gets the BMP default, and the interpreter's BMP check matches the kernel for every such model. **Re-open trigger:** the interpreter gains a custom-charset / `legalCodepoints` SPI (e.g. to enforce DIN 91379) that a consumer wants honored — at which point the interpreter checks against the supplied set instead of the BMP default. *(Interpreter: a single cross-kind `baselineValueError` in `eval/FormalError.kt`, IF43; locked `adapter.laws.BaselineValueFormalDiffTest`.)*

## §3 supplement — DECLARED field-type CONSTRAINTS are formal errors too (range / length / pattern / digit-count / enum-domain), source + probe-verified 2026-06-25

The format checks above (decimals, invalid chars, blanks, signed-zero) test whether a value is *well-formed for its kind*. But the kernel's `validateFull` **also** auto-validates the value against the field type's **declared constraints** — and these ride the **same `formalePruefung` mechanism**: an out-of-constraint value is a formal error, the field becomes **"unknown"**, and a referencing author rule is **suppressed** (branch-scoped, §3 / IF17). No rule is involved — the kernel emits these purely from the field-type declaration.

The constraints are declared on the field type (kernel `IStringType` / `INumberType`, source-read) and the formal-error codes are the kernel's full runtime set (`FormalErrorCodesProvider.getFormalErrorCodes`, ~55 codes). The constraint → code map (the ones a DM-JSON model can declare and a document can violate):

| field type | DM-JSON declaration | runtime formal-error code |
|---|---|---|
| **NUMBER** | `minValue` / `maxValue` | `zahlZuKlein` / `zahlZuGross` |
| | `minFractionalDigits` (too few / none) | `zahlFalscheAnzahlNachkommastellen` / `zahlOhneDezimalTrenner` |
| | `zeroNotAllowed: true` *(inverted key — NOT `zeroAllowed`)* | `zahlIstNull` |
| | **leading zeros** — forbidden BY DEFAULT; `leadingZerosAllowed: true` opts out | `zahlHatFuehrendeNullen` |
| | `maxIntegerDigits` (integer-part digits above it) | `zahlZuvieleVorkommastellen` |
| | `trait:"amount"` (implicit `15 − scale` integer-digit cap; only without explicit `maxIntegerDigits`) | `stelligkeitZuLang` |
| | `minLength` / `maxLength` (value-string length) | `zahlZuKurz` / `zahlZuLang` |
| **STRING** | `pattern` (regex) | `stringFalschesMuster` |
| | `noValueValidation: true` — disables the WHOLE string check (pattern/length/newline) | *(skips all — only `maxLength` may accompany it, and it is not enforced)* |
| | `minLength` / `maxLength` | `stringZuKurz` / `stringZuLang` |
| | **newline** — forbidden BY DEFAULT; `lineBreaksPermitted: true` opts out | `stringMitNewline` |
| **ENUMERATION** | the value domain (out-of-domain stored value) | `stringFalschesMuster` |

**Two are kernel DEFAULTS, not declarations** (follow-up probe 2026-06-26): a plain number rejects a leading zero (`"007"` → `zahlHatFuehrendeNullen`; `"0"`/`"0.50"` clean) and a plain string rejects a newline (`"a\nb"` → `stringMitNewline`) unless the field opts in.

**More NumberType integer-digit / length constraints DO serialize (corrected 2026-06-26 — the earlier "no DM-JSON key" claim was WRONG):** `maxIntegerDigits` → `zahlZuvieleVorkommastellen` (integer-digit count above the cap; sign + decimals excluded); `trait:"amount"` → an implicit cap of `15 − scale` but a **distinct** code `stelligkeitZuLang` (applies only when no explicit `maxIntegerDigits`); NumberType `minLength`/`maxLength` → `zahlZuKurz`/`zahlZuLang` on the value-string length (sign + decimal point counted). All probe-verified 2026-06-26 and modeled by the interpreter (IF30). **Still out of scope (probe-confirmed):** a **charset** check (`zeichenNichtImZeichensatz`) is not declarable and does not fire by default (tab / non-ASCII / control chars on a plain string are all clean); a field-level `uniqueValue` is not DM-JSON-deserializable.

**Probe-verified (2026-06-25/26)**: `/Order/BirthDay` (`minValue:1, maxValue:31`) — `"99"` → `zahlZuGross`, `"0"` → `zahlZuKlein`; `/Order/Priority` (enum) — `"BOGUS"` → `stringFalschesMuster`; precedence — string pattern/newline fire **before** length; the **suppression** was confirmed (a rule `[BirthDay] == 99` with `BirthDay = "99"` does **not** fire — only `zahlZuGross`, the field is unknown). So an out-of-constraint value is observable two ways: the **auto-emitted formal error** *and* the **suppression of referencing rules**.

This is the same class as §94/§98 (format-error suppression) — only the trigger differs (a declared constraint / kernel default vs raw well-formedness). The **interpreter now models this dimension** (the per-cell family + the two defaults) — INTERPRETER-FINDINGS IF20, differential-locked by `adapter.laws.FieldConstraintFormalDiffTest`.

**STRING `noValueValidation` DISABLES the whole string format check** (source + probe-verified 2026-06-26). When `StringType.noValueValidation:true`, the kernel's `FormatDefinitionString.validiereFormat` returns `Valid` *immediately* — pattern, length, and the default newline check are all skipped. The key is MVK-constrained: it **forbids** `pattern`/`minLength` (`MVK_STRING_TYPE_PARAMS_INCONSISTENT` — only `maxLength` may accompany it) and **requires** `lineBreaksPermitted:true` (`MVK_STRING_TYPE_NO_VAL_AND_NO_LINE_BREAK`). So on a *kernel-valid* model the single observable runtime effect is that a declared **`maxLength` is NOT enforced** (a longer value is clean). Reachable on shipped A12 Tools StringType fields (Country/City/Person). The interpreter models it — INTERPRETER-FINDINGS IF29.

## §3 supplement — a DATE value is stored and formal-checked in the field's DECLARED format, not ISO (runtime, 2026-06-23)

## §6 supplement — the RUNTIME tolerates any date `format`, but AUTHORING (SME) accepts only 3 canonical ones (source-verified 2026-07-07)

Two consumers read a date-ish field's `format`, and they disagree — a **runtime-lenient / authoring-strict** split that the conformance corpus tripped over when its models had to become SME-openable.

- **Kernel RUNTIME** (`IDocumentRtService`, the JVM differential's oracle): `format` is *the pattern to parse stored values with*. Any pattern works — `dd.MM.yyyy` is a first-class German format (`STANDARD_DE_DATE_FORMAT`/`DATUM_FORMAT` in the runtime), so a field declaring `format: "dd.MM.yyyy"` with values like `15.06.2024` validates and evaluates normally. This is why our `order` fixture's `ApproxDate`/`ItemCoverage`/`CoverageWindow` (German format, `-` range separator) have always passed the differential (locked by the date DiffTests — legitimate coverage of the runtime's format flexibility; see the §3-supplement finding above).
- **AUTHORING / SME** (the `simple-model-editor` model deserializer): `format` is *an enum of the canonical A12 storage formats*. Its field-type mapping is a hard `switch` that accepts **only** `yyyy-MM-dd`, `yyyy-MM-dd'T'HH:mm:ss`, `HH:mm:ss` (for Date / DateTime+Time / DateRange alike) and otherwise **`throw new Error("unsupported date format: …")`** — so a model with `dd.MM.yyyy` in `format` *evaluates fine but cannot be opened in the SME*. A localized **display** format is not stored in `format` at all; it belongs in the sibling `notInDCustomFormat` (and a non-`/` range separator in `notInDCustomRangeSeparator`) — the A12 default range separator is `/` (kernel `FieldTypeConstants.A12_DATE_RANGE_SEPARATOR`). The mechanism is verified from the SME source and re-expressed here (license-safe — behavior, not code).

**Consequence for us.** Openability is a stricter bar than runtime-validity: `dmtool model describe` / `rule check` use the lenient runtime read path, so they are *not* a faithful SME proxy for this class (they accept `dd.MM.yyyy`). A model meant to open in the modeling tools must keep `format` in the canonical set. The conformance corpus therefore **canonicalizes date `format`s when it writes a standalone model** (`CaseJson.writeModel` → `CANONICAL_DATE_FORMAT`) and a guard rejects any non-canonical one (`CorpusSchemaGuardTest` via `CaseJson.unsupportedDateFormats`); the shared *differential fixture* keeps its `dd.MM.yyyy` fields (they test the runtime and are never SME-opened). *(Locked: `adapter.laws.CorpusSchemaGuardTest`.)*

## §4 supplement — the "required" property and its two modes (runtime, 2026-06-06)

The field-editor "required" checkbox is encoded in DM-JSON as `Field.requirednessConfig: {mode: …}` (kernel enum `IRequirednessConfig.Mode`). An unfilled required field raises the `mandatoryField` **formal error**, so the field is **"unknown"** (§3). The two modes — and the gotcha the BA docs flag — verified at runtime:

| mode (DM-JSON) | BA "Only if parent filled" | when required |
|---|---|---|
| `absoluteOrRelativeToNextRepAncestor` | **no** | a non-repeatable field is **always** required; a field under a repeatable ancestor is required once that ancestor is filled |
| `relativeToParent` | **yes** | required **only when the parent group is filled** |

**The gotcha — what "filled" means here.** For `relativeToParent`, "the parent is filled" means **at least one descendant field of the parent is filled** (`IRequirednessConfig` Javadoc), **not** the §9 "row exists" `GroupFilled` notion. Verified on a sub-group field (`/Order/ShippingAddress/Street`): a created-but-empty `ShippingAddress` row → **not** required (no `mandatoryField`); once a sibling (`City`) is filled → required → empty Street raises `mandatoryField`. Under `absoluteOrRelativeToNextRepAncestor` the same empty sub-group still requires Street (always). The requiredness is **stronger than `FieldNotFilled`**: it makes the field unknown, so e.g. a required-but-empty **number** is *not* the §2 empty-as-0 — a `[Quantity] < 100` rule does not fire on it (only `mandatoryField` does). *(Locked: `adapter.laws.RequiredPropertyLawsTest`.)*

**Mechanism + four more facts (source-read `AutogeneratedRulesService`/`MandatoryFieldRuleImpl` + differential, 2026-06-23).** The kernel implements `mandatoryField` as an **autogenerated rule** named `vk_vk<field>_req`, error code `mandatoryField`, severity ERROR, **type OMISSION** (filling the field clears it), with the condition decided by `relativeTo = lowestRepeatableGroupPath(field)`:

1. **`absoluteOrRelativeToNextRepAncestor`, no repeatable ancestor** → `FieldNotFilled(field)` — **unconditional**: fires even on an *un-instantiated* document (an empty doc still raises `mandatoryField` at the canonical all-1s pointer; a not-instantiated non-repeatable sub-group still requires its absolute fields).
2. **…, with a repeatable ancestor R** → `GroupFilled(R) And FieldNotFilled(field)` — **per instantiated R row** (no row ⇒ no `mandatoryField`).
3. **`relativeToParent`** → `GroupFilled(parent) And FieldNotFilled(field)`.
4. **Index fields are auto-required** — a group's `indexFieldName` gets an auto-generated mandatory rule with `relativeTo = parent` (i.e. `relativeToParent` semantics), on top of any explicit requiredness. So an instantiated repeatable row with an empty index field fires `mandatoryField` on it.

The **gotcha resolves by the parent's repeatability** (the `GroupFilled` split, §9 below): for a **repeatable** parent a *created-but-empty* row already counts as filled (the row index is content) → the field IS required; for a **non-repeatable** parent a filled descendant counts. **What "a filled descendant" means was refined 2026-07-06 (runtime-probed): it includes an INSTANTIATED repeatable descendant ROW, not only a valued field** — `Quantity` (required `relativeToParent`, parent the non-repeatable `/Order`) becomes required as soon as a `/Order/Items` row is instantiated (even all-empty), and is *not* required when `/Order` has no content at all. So this is the SAME "content" notion as the §9 `GroupFilled` operator (line 67) — requiredness and `GroupFilled` share it (they diverge only in that requiredness's *absolute* mode ignores it). And the "unknown" is **branch-scoped, not whole-rule** (§3 refinement): a required-empty operand makes its *comparison* unknown, so `[ReqNum] < 100` is suppressed but `[ReqNum] < 100 Or <true>` still fires. *(Interpreter parity locked: `adapter.laws.RequirednessDiffTest` — both modes, the repeatable-row gate incl. the instantiated-repeatable-child-fills-a-non-rep-parent case, the unconditional-absolute case, and the index field; the branch-scoped unknown for format errors by `adapter.laws.SuppressionDiffTest`.)*

## §4/§8 supplement — field-level custom error messages live in a per-locale `errorMessage` array (source-verified, 2026-06-21)

A field carries **two** kinds of custom validation error text, both the "Use Default Error Messages" deselected case (SME 840, 1123) — and both are stored the same way: a per-locale `errorMessage` array `[{locale, text}]`.

| message | DM-JSON location | kernel accessor |
|---|---|---|

## §5 supplement — numeric literals are exempt from the scale check

The `==`/`!=` decimal-scale gate applies to **field/expression operands only**. Against a scale-2 field, `== 0`, `== 0.0`, `== 0.00`, `!= 0`, and `<= 0.000` are all accepted — only field-vs-field/expression comparisons of differing declared scale draw `MVK_INVALID_COMPARE_DEC_PLACES`. Consequence: scale-explicit literals (`0.00`) are a rendering-fidelity nicety, not a correctness requirement. *(Locked: `validate.laws.NumberLawsTest`.)*

**Field-vs-field comparison (finding 18, verified 2026-06-04).** Comparing two *fields* (not just field-vs-literal): **strings** compare with `==`/`!=` only (ordering → `MVK_INVALID_TYPE_FOR_COMPARISON`, "only for numbers, amounts and dates"); **numbers** — the scale gate is **`==`/`!=`-only**: equal-scale fields compare freely, different-scale fields draw `MVK_INVALID_COMPARE_DEC_PLACES` ("max fractional digits of lhs(0) and rhs(2) differ"), but **ordering (`< <= > >=`) is scale-exempt** (verified: `[Quantity(0)] < [UnitPrice(2)]` validates; source `CheckVergleichsBedingungImpl.checkNumberComparison` — the scale check runs only when `isUnEqualsComparison`, comparing the two `getMaxFractionalDigits`; a `null` (derived/unknown) scale is the `"?"` in the message, source-read 2026-06-17). String-vs-number → `MVK_INVALID_COMPARE_TO_ENUM_OR_STRING`. rulekit: `StringRef.eq/ne(StringRef)` and `NumberRef.{lt,le,gt,ge,eq,ne}(NumberRef)` — the number `eq`/`ne` **pre-check equal scale** (the D13 gate made cheap, since the index knows both scales), ordering does not. **Enum-vs-enum is now implemented** (`EnumRef.is/isNot(EnumRef)`, compared by stored value; type-compatibility stays the kernel's call) — KERNEL-SEMANTICS §8, locked by `adapter.EnumFieldComparisonReadTest`. An arithmetic **expression** carries a *derived* scale — **multiplication raises it** (a scale-2 × scale-2 expression is scale 4, division/power are unknown), so `[x] == [a] * [b]` can draw `MVK_INVALID_COMPARE_DEC_PLACES` **even when every field shares a scale**; wrap the expression in `RoundAccounting(expr, n)`, or waive the check with `@SuppressWarning(MVK_INVALID_COMPARE_DEC_PLACES)` at the start of the condition (source-read 2026-06-17). *(Also locked: `validate.laws.NumberLawsTest.fieldVsFieldScaleGateAppliesToEqualityOnly`/`stringFieldVsFieldEqualityIsAccepted`/`multiplicationRaisesScaleSoEqualityRejectsEvenWithMatchingFieldScales` + `RenderConditionTest`.)*

**Tolerance comparisons (implemented 2026-06-07).** The kernel's `ComparisonOperation` has four tolerance members — `NE1`/`NE2`/`NE5`/`NE10` — rendered as the worded keywords `DiffersWithToleranceRange1`/`2`/`5`/`10` (DE `UngleichMitToleranz{N}`): `[a] DiffersWithToleranceRange5 [b]` is true iff the two numbers differ by more than 5 ("unequal within a tolerance"). Only for numbers/amounts. Confirmed against the kernel source: `FormatterUtil.getComparisonOperator` renders them via the same comparison-operator path as `<`/`==` (so they ride the existing `ComparisonCondition` rendering). Modeled by extending `CompareOp` with the four variants + a public `Tolerance` enum (`RANGE_1/2/5/10`, making any other range unrepresentable); authored via `NumberExpr.differsWithTolerance(Tolerance, …)` / `NumberRef.differsWithTolerance(...)`. *(Locked: `adapter.ArithmeticReadTest.roundTripsToleranceComparison` + BA-corpus `ToleranceCmp`; N7 catalog examples for all four.)* **Read also converts a tolerance op in an EXPRESSION / AGGREGATE comparison** (not just field-vs-field) — the `numberExprComparison`/`exprVsExpr` paths route `NE1`/`NE2`/`NE5`/`NE10` through `differsWithTolerance` (`adapter.AggregateToleranceReadTest`, e.g. `Sum(Items*/Count) DiffersWithToleranceRange1 [Quantity]`).

**Runtime semantics (interpreter, probe 2026-06-24).** Fires iff `|a − b| > N` — the band is **STRICT**: a difference *exactly* equal to N does NOT fire (`Range1` on diff 1 → no, diff 2 → yes; `Range5` on diff 5 → no, diff 6 → yes). An **empty** numeric operand reads as **0** (empty-as-0, like any comparison — `[Quantity=9] DiffersWithToleranceRange1 [empty]` → `|9−0|=9 > 1` fires); a **malformed** operand suppresses the rule. Polarity is **EQ-like** (kernel-probed message type): both operands present → **VALUE**; an empty (fillable) operand whose filling could close the gap → **OMISSION**. The interpreter models it as a dedicated `Cond.Tolerance` AST node (NOT a desugar to `Abs([a]−[b]) > N`, whose polarity would be wrong — `leafOmission` does not recurse into `Expr.Arith`, so the empty operand would be invisible and it would mis-type as VALUE); polarity reuses the EQ `fill`-based rule. *(Locked: `adapter.laws.ToleranceDiffTest` — firing + polarity in one assertion — + a fuzz rule `DT` = `[Qty] DiffersWithToleranceRange5 [Price]`.)*

## §5 supplement — a NUMBER field type is ALWAYS scale-bounded; `maxFractionalDigits` is mandatory (no unbounded decimal) (source + metamodel + probe, 2026-06-28)

An a12 `NumberType` carries a **mandatory** decimal scale — there is **no unbounded-scale decimal**. Three independent oracles agree:

- **Typed API** — `INumberType.getMaxFractionalDigits()` returns a **primitive `int`** (no `Optional`), unlike the genuinely-optional slots on the same interface (`getMinValue`/`getMaxValue`/`getMaxLength`/`getMaxNumberOfDigitsBeforeDecimalPlace` are all `Optional<>`). There is no "unset scale" in the model.
- **Metamodel** — `MM_SMM_FieldTypeChecks` states it in prose (";; maxFractionalDigits is a required Field in case of a number") and flags `NotAllFieldsFilled(.../maxFractionalDigits)` as an integration error for any Number-supertype field.
- **Behaviour (probe)** — a DM-JSON that **omits** the slot is **accepted**, with the scale **silently defaulting to 0** (Jackson fills the primitive `int` → 0) — never unbounded, never rejected.

Consequences: modelkit emitting `maxFractionalDigits` with a `null → 0` default is **correct** (it makes the implicit kernel default explicit), and a bare JSON-Schema `number` (no scale signal) has **no faithful import** — schemakit omits it by default rather than silently coercing a decimal to an integer (SCHEMAKIT-SPEC §4b). *(Locked: `modelkit.NumberScaleKernelLawTest`. This resolves the DEV-API-GAPS "unbounded-scale NUMBER" investigation — a kernel fact, not a modelkit gap.)*

## §5 supplement — power-operator parse laws + the quiet non-execution edges (source-read + 2026-06-17)

The `^` power operator (parser `CheckOperationImpl`): **unparenthesized nesting is rejected** — `a ^ b ^ c` draws `MVK_TOO_MANY_POW_FOR_CALC` (nest via grouping); the **exponent must have no decimal places** — a scale-0 field or integer literal is accepted, a decimal-scale field (or an unknown-scale expression) draws `MVK_INVALID_NUMBER_FOR_EXP` (`checkNoFractionalDigitsInExponent`). Arithmetic sub-expressions group with **curly braces `{ }`**, and precedence is `^` → `*`/`/` → `+`/`-`. **Runtime (BA "Power Operator", source-read but not yet law-locked here):** `a ^ b` is *not executed* — so a rule using it silently does not fire — when `b` is outside `[-1000, 1000]` or for `0` raised to a negative power, the same quiet behavior as division by zero. *(Locked: `validate.laws.NumberLawsTest.powerOperatorRejectsUnparenthesizedNesting` / `powerExponentMustHaveNoDecimalPlaces` for the validation side; the runtime non-execution edges are now locked by `adapter.laws.DivPowDiffTest` — `powZeroToNegativeIsQuiet` (`0` to a negative power) and `powExponentOutOfRangeIsQuiet` (`|exp| > 1000`), both quiet like division by zero, interp == kernel.)*

## §7 supplement — pattern-comparison slot rules and the portable-subset gate (2026-06-04 experiments)

`PatternMatched`/`PatternViolated` (DE: `WieMuster`/`NichtWieMuster`) are grammar-level *infix comparison operators* (`vglOp` alternatives like `==`), but their slot rules are far stricter than the grammar:

- **Left side: a bare string field value only.** A non-string field (number, enum, boolean) → **`MVK_INVALID_TYPE_FOR_PATTERN_COMPARISON`** ("only allowed for string values" — note: *enums are not pattern-comparable* even though they compare to strings with `==`). A string *expression* (e.g. concatenation) → **`MVK_INVALID_PARAMETER_FOR_PATTERN_COMPARISON`** ("only allowed with a field value as first parameter"). A constant → the general **`MVK_INVALID_COMPARE_TO_CONST`**.
- **Right side: a string constant only.** A field reference → **`MVK_MISSING_CONST_IN_PATTERN_COMP`**; a number constant → `MVK_INVALID_TYPE_FOR_PATTERN_COMPARISON`.
- **The regex gate is Java `Pattern.compile` *plus* a portable-subset check** (`PatternUtils.isPatternValid`; the extmp world uses `CommonUtils.isRegExValid` instead): lookbehind `(?<=a)b` is Java-valid yet rejected with **`MVK_INVALID_PATTERN`** — KERNEL-SEMANTICS §7's "portable subset" is *enforced*, not advisory. Consequence: a Java-side `Pattern.compile` pre-check is a necessary condition only; final validity is the kernel's call.
- **The empty pattern `""` is accepted** for document models (the non-extmp branch; extmp additionally requires non-empty).

## §7 supplement — string-literal escaping is quote-doubling, not backslashes

The condition lexer's rule is `StringLiteral : '"' ( '""' | ~["] )* '"'` — an embedded quote is **doubled** (`"say ""hi"""`), and **backslash is a plain character** (no escape sequences; regex classes like `\d` are written as-is). Backslash-escaping a quote (`\"`) is a parse error (`MVK_UNEXPECTED_TOKEN`). Found while building the pattern operators: rulekit's renderer had C-style escaping and would have emitted wrong regexes for any pattern containing `\` — fixed and locked. *(Locked: `validate.laws.PatternLawsTest` + `RenderConditionTest.quotesStringLiteralsTheKernelWay`.)*

## §8 supplement — `FieldValueIncludedInValueList` rides the 3VL: an empty operand is UNKNOWN (runtime, 2026-06-23)

## §8 supplement — predefined-type validity (`ValidType`/`InvalidType`) is a runtime CLIENT SPI, not kernel-core behavior (probe + source, 2026-06-24)

`Valid(field, "EMail")` / `Invalid(field, "IBAN")` validate the field's value against a **predefined custom field type**. ## CustomCondition — a runtime CLIENT SPI with TWO API levels; the interpreter must support it (probe + source, 2026-06-24)

`CustomCondition <Name>` delegates the whole fire/don't-fire decision to **client/host code**, resolved by **name** at runtime (like the predefined types — a client SPI, not kernel-core behavior). The kernel's own metamodels use it heavily (MM_Rule/MM_Field/MM_Computation/MM_Typedef…), and the owner confirms real project models use it heavily — so the interpreter MUST support it (decided 2026-06-24).

**Two API levels** (this is the key fork):
- **Core / classic** — `com.mgmtp.a12.kernel.core.rt.a12internal.validation.ICustomCondition` (formerly `IApplicationCondition`): `boolean check(IData data, Set<IIdentifier> relevant, Set<IIdentifier> formallyIncorrect, IIdentifier errorField)`. `IData` = `getValue(IIdentifier)`/`getValueForDisplay`/`iterator`/`identifierToString`; `IIdentifier` = `getName()` (path, ≥2 parts) + `getIndices()` (long[] reps) + `getUsb()`. A constructible `IdentifierImpl(name, long[])` exists in `kernel-core-utils`. The kernel's own metamodel conditions (`CheckEnumOrCategoryValue`, `CheckStringPattern`, `CheckHintList`) implement THIS level.
- **Modern / md** — `com.mgmtp.a12.kernel.md.rt.api.ICustomCondition`: `check(DocumentV2, Set<DocumentMultiPointer> relevant, Set<DocumentPointer> formallyIncorrect, PartiallyKnownDocumentMultiPointer errorEntity)`. `CustomConditionWrapper` (md-runtime-service) adapts md→core and **requires the runtime data be a `ValidationData`** ("a custom condition provided through the md-API must not be used by validation calls which bypass the md-API"). **The owner's projects target THIS (md/DocumentV2) level (decided 2026-06-24).**

**Registration:** the static `CustomConditionService.getInstanceV2().registerV2(ICustomConditionFactory)` (core-level; deprecated, `forRemoval` A12K-3589, but present in 30.8.1) OR the modern `DocumentProcessingConfig.builder(locale).customConditionFactory(...)` passed to `validateFull(DocumentV2, DocumentProcessingConfig)`. The facade `DocumentRtCustomExtensionService.registerCustomConditions(mdFactory)` wraps an md factory in `CustomConditionFactoryWrapper` and registers it into `CustomConditionService`. A factory maps name→condition (`createCustomConditionV2(name): Optional<ICustomCondition>`); first-registered name wins; `cleanRegistry()` for tests.

**Runtime semantics (probe-confirmed via constant conditions):** `CustomCondition X` fires iff `X.check(...)` returns **true**, on an **evaluated** row, and only when the relevant fields are **formally correct** (a formal error suppresses it); polarity is **VALUE**; it does **not** fire on an all-empty row. A **bare** `CustomCondition X` (referencing no field) is rejected at codegen with **`MVK_ERROR_FIELD_NOT_REFERENCED`** — it must be guarded by something that references the error field (the idiom is `FieldFilled(errorField) And CustomCondition X`). DM-JSON: the condition text is literally `… And CustomCondition <Name>` (e.g. `FieldFilled(errorField) And CustomCondition InvalidReference`).

**Oracle-harness path (for the differential) — CONFIRMED 2026-06-24.** Registering a *core* `ICustomCondition` via the static `CustomConditionService` and validating through the deprecated `validateFull(IDocument, Locale)` path invoked **constant** conditions reliably but **not data-reading ones** in the test harness (a throwing condition never threw, yet the rule fired). The reliable path — now wired into `RuntimeLaws` as the `messages/fires/typeOf(modelJson, Doc, Map<String, ICustomCondition>)` overloads — is the **modern** `validateFull(DocumentV2, DocumentProcessingConfig.builder(locale).customConditionFactory(ICustomConditionFactory.fromMap(name→mdCondition)).build())`: convert the built V1 `IDocument` to `DocumentV2` via `new DocumentServiceFactory(resolver).createDocumentV1V2Converter().ofDocumentV1(doc)`. A probe confirmed it **reliably invokes data-reading md conditions** (ACME→fire VALUE, Other→read+no-fire, empty→**not even invoked**). The md `ICustomCondition` may implement the modern `check(DocumentV2,…)` or the deprecated `check(IDocument,…)` (the default V2 method converts and delegates) — the oracle reads the error field from `IDocument.getEntityInstances()` filtered to the matching `IFieldInstance.getValue()`. `kernel-core-runtime-api` resolves to **32.3.4** in the 30.8.1 distribution; `kernel-core-utils` 30.8.1. md (`DocumentProcessingConfig`/`ICustomConditionFactory`/md `ICustomCondition`/`DocumentV2`) is already on the adapter classpath via `kernel-md-runtime-api`.

**JVM bridge for EXISTING kernel conditions — `KernelCustomConditions.fromCore` (`:adapter`, 2026-06-24).** A JVM consumer adapts a project's existing kernel **core** `ICustomCondition` (or a `name→condition` map) onto the interpreter's pure `CustomCondition` SPI, so the kernel-free interpreter runs the SAME condition object the kernel runs — replacing the kernel's generated code. The bridge supplies its **own** `IData`/`IIdentifier` over the interpreter's `CustomConditionData`/`FieldPointer` (`FieldPointer.indices: List<Int>` ⇄ `IIdentifier.getIndices(): long[]`), constructs **no** kernel `…Impl` (the kernel API documents the caller provides these — with content `equals`/`hashCode` — and the runtime re-wraps them; honors the N8/D15 "never construct kernel Impl" guardrail), and refuses mutation (`IData.addValue` throws — a condition must not mutate the data). This made `:interpreter` an `:adapter` **MAIN** dep and added `kernel-core-runtime-api:32.3.4` (`implementation`). The md `DocumentV2`-shaped conditions are reachable via a thin future `DocumentV2`→`IData` view on top of this core bridge — not built, since core `IData` is the unified cross-platform contract. Locked: `CustomConditionDiffTest` (the real-core-condition-through-the-bridge differential) + `KernelCustomConditionsTest` (bridge data-shaping).

**The JS/TS kernel runtime mirrors the `IData`-based contract EXACTLY — so `IData`-based is the UNIFIED cross-platform contract (re-checked 2026-06-24 at the owner's prompt).** The kernel ships a TypeScript runtime (`kernel-rt/kernel-core-runtime-ts` + `kernel-core-runtime-api-ts`) whose JS codegen path DOES support custom conditions, via TS twins of the **core** API: `ICustomCondition.check(data: IData, relevant: Set<IIdentifier>|undefined, formallyIncorrect: Set<IIdentifier>, errorField: IIdentifier): boolean`, `IData.getValue(IIdentifier)`/`iterator`/`addValue`, `IIdentifier.getName()/getIndices()/getUsb()`, and a `CustomConditionService` singleton (`register`/`getCustomCondition`/`cleanRegistry`) + `ICustomConditionFactory.createCustomCondition(name)` — **identical in shape to the Java core API**. There is **no `DocumentV2` in TypeScript** — `DocumentV2` is a JVM-only modern facade (`CustomConditionWrapper` adapts md→core). So the contract that exists on **both** platforms (and that the kernel's own conditions + JS codegen use) is the **`IData`-based** one — the natural, only fully cross-platform choice for a JVM+JS interpreter SPI.

**Interpreter design (kernel-free multiplatform SPI; decided 2026-06-24 — JVM AND JS/TS, prefer modern APIs):** the core defines a **multiplatform pure SPI** in `commonMain` mirroring the **`IData`-based** `ICustomCondition` contract (`CustomCondition.check` over pure `IData`/`IIdentifier`-shaped interfaces: `getValue(path,indices)`, the relevant + formally-incorrect sets, the error entity), so it compiles to JVM **and** JS and existing **Java core** AND **TS** impls plug in (their shapes already match). A project's JVM **md `DocumentV2`** impl is adapted via a thin JVM-only `DocumentV2`→`IData`-view adapter if needed. **"Prefer modern APIs"** applies to the **oracle/runtime path** (`validateFull(DocumentV2, DocumentProcessingConfig.customConditionFactory(...))`, not the deprecated `Locale`/static-service path), NOT to the SPI *contract* (which must be the cross-platform `IData`-based one). `CustomCondition X` parses to `Cond.Custom(name)`; unregistered name → reported unsupported (fail-fast). Implementation: INTERPRETER-ARCHITECTURE.md §7 (custom conditions).

## Custom-extensibility surface — the kernel registers exactly TWO custom things (conditions + field types); there is NO custom computation/function (source-verified 2026-06-26)

The umbrella over the two SPI findings above (§8 predefined-type validity, and CustomCondition): the kernel's **project-facing extension API** — `kernel-md-facade/.../DocumentRtCustomExtensionService` — exposes exactly **two** custom-registration hooks, `registerCustomConditions(ICustomConditionFactory)` and `registerCustomFieldTypes(ICustomFieldTypeFactory)` (each with a `…V2`). **There is no `registerCustomComputations`/`registerCustomFunction`/`registerCalculation` — a custom *computation* is not a kernel concept.** Corroborated four independent ways:

- **German-source sweep** (`.java` + `.g4`): the only `Applikations*` construct is `ApplikationsBedingung` (= CustomCondition). No `ApplikationsBerechnung`/`-Funktion`.
- **SPI interfaces:** the only `I(Custom|Application)*` types are condition / field-type / field-validator / **migration** (`ICustomMigrationCode` — a *third* custom hook, but it is data-migration between model versions, not validation or computation). None for functions/computations.
- **Computation vocabulary is closed:** `CalcOp` is an enum `{ADD, MULTIPLY, SUBTRACT, DIVIDE, POWER}`; a computation operation is built solely from it + the standard value-expression catalog (rounding, aggregates, date math, …). `ICalculationService`/`IBaseCalculationService` are the *internal* evaluator (`checkCalculationRule`, no register/custom methods), not a project SPI.
- **The one custom hook that could reach a computation is barred:** `CustomCondition` is **forbidden inside computation rules** (KERNEL-SEMANTICS §14).

So the kernel's custom escape hatches are for **conditions** and **field types** only. ## §8 supplement — a CUSTOM-typed field is validated by FULL DELEGATION to a registered validator; an unregistered one THROWS (source-verified 2026-06-26)

How the kernel validates a field declared with a **`CustomFieldType{name, minLength?, maxLength?}`** at `validateFull` (the sibling of the §8 `Valid`/`Invalid` *operator* — this is the *declared-field* form). Source: `FormatDefinitionVordefiniert.validiereFormat` (+ its TS twin `FormatDefinitionVordefiniert.ts`, byte-identical):

- **Full delegation, NOT generic enforcement.** Unlike a plain `StringType` (whose `FormatDefinitionString` checks `minLength`/`maxLength` itself → `stringZuKurz`/`stringZuLang`), a `CustomFieldType` field delegates the **entire** check — length included — to the registered `ICustomFieldValidator.validate(value, param, …)`. The kernel performs **no** length comparison of its own.
- **The declared bounds are only HINTS.** The kernel passes `minLength`/`maxLength` to the validator via `ICustomFieldTypeValidationParam` (`-1` = `UNSPECIFIED_LENGTH` → `Optional.empty()`), and the interface javadoc tells the validator it generally should *not* rely on them — they are informational, the validator owns the decision.
- **No registered validator → it THROWS.** `getCustomFieldValidator` resolves the validator from the factory / global `CustomFieldTypeService`; missing → `ValidatorException("Custom field validator '<name>' missing.")`, which `validateFull` surfaces as `FaultException("Unable to invoke validation")`. So a *filled* custom-typed field on a bare model fails the **whole** validation (an empty/not-relevant cell short-circuits before reaching it). There is no "fire a formal error" and no "skip".
- **The error code is the validator's OWN key**, `ICustomFieldTypeCheckError.getErrorKey()` (project-specific, e.g. `"invalidCreditCardNumber"`) — **not** a fixed kernel code like the `StringType` length codes.
- **The bounds DO reach the model + runtime** (`md.model.api.fieldtypes.ICustomFieldType.getMinLength/getMaxLength`; codegen carries them into the validation param) — they are real model properties, just never kernel-enforced.

This is the kernel truth behind the interpreter's treatment (auto-validate each filled custom cell against the consumer-registered predefined type; unregistered → report unsupported + degrade leniently, since the native runtime cannot host the validator) — INTERPRETER-FINDINGS IF26. JS/TS identical, so a Kotlin/JS consumer mirrors it.

## Partial validation (`validatePart`) — rule-gating + 3VL relevance (source + probe-confirmed 2026-06-24)

`validatePart(DocumentV2, Set<DocumentMultiPointer> relevantEntities, DocumentProcessingConfig)` validates only a *part* of the document. The contract (kernel javadoc on `IDocumentRtService.validatePart`, probe-confirmed) is two mechanisms:

- **Rule-gating by the error field.** A validation rule is **executed only if its error-field instance is in the relevant set** (this includes the auto-generated formal/mandatory/unique field checks, whose error field is the field itself). So a rule whose error field is not relevant simply does not run — no message.
- **Suppression via 3VL on non-relevant references.** Of the rules that *do* run, "validation errors will be suppressed if the rule references any repetition of a field/group that is not marked as relevant — **except for some cases where the kernel is sure that no possible value of that field/group repetition could have prevented the error**." That exception is exactly **Kleene three-valued logic**: a non-relevant reference is **UNKNOWN**, and `true Or Unknown = true` (still fires — no value could prevent it) while `true And Unknown = Unknown` (suppressed). Probe over a two-field rule confirmed: `And` with only the error field relevant → suppressed; the same as `Or` → fires; only the *other* field relevant (error field not) → not run.

Relevant pointers: `DocumentMultiPointer.of(fullName, repetitions)` with **`ALL_SEMANTIC` (index `0`)** as the per-level wildcard ("all repetitions"); a relevant **group** makes all its **descendants** relevant. The kernel **encourages** wildcarding every path level — a *subset* of repetitions has subtle suppression around wildcards/aggregates (`/RG*/f1` references not-filled reps too) and `NumberOfFilled…`/semantic-index/parallel-iteration.

**GLOBAL fields are auto-added to the relevant set — but by the MD-LAYER, not the core validator (source-verified 2026-06-26).** A field flagged **`global`** (DM-JSON `"global": true` in the Field body; `IField.isGlobal`) is **always relevant in partial validation**, regardless of the caller's set. The mechanism is precise: the **core** validator (`ValidationCommand`) does *not* touch global fields; the **md-runtime-service** layer — exactly the `IDocumentRtService.validatePart(DocumentV2, …, config)` boundary the oracle calls — injects them first (`LowKernelApiUtils.validatePartlyWith3ValueLogic` → `addGlobalFieldsToRelevantEntities`, which adds `metaModel.getValue("GlobalFields")` = each global field's pointer **wildcarded at all reps**, `MetaModelImpl` building them with all-zero `ALL_SEMANTIC` indices). `IField.isGlobal`'s own javadoc states the contract: *"Global fields should always be passed to a partial validation in addition to the usual relevant entities. The caller of the validation is responsible for passing the global fields."* So at the kernel's *public* runtime boundary they ARE auto-added; a rule whose error field is global therefore RUNS even when the caller's relevant set omits it. *(Locked: `adapter.laws.PartialValidationGlobalFieldDiffTest` — global vs. non-global control vs. the kernel; the loader mapping by `cli.interp.InterpreterRealModelDiffTest.loaderReadsTheGlobalFieldFlagIntoModelDef`.)*

**Interpreter treatment:** this maps directly onto the existing 3VL engine — `DmInterpreter.validatePart` gates each emitted message by its error field's relevance and resolves non-relevant referenced instances to `Val.Unknown` (the same `invalid`-operand mechanism formal errors already use), so Kleene logic yields the kernel's exact suppression with no special-casing; whole-document-relevant equals `validateFull`. **Starred-aggregate relevance is PER-OPERATOR (probe-confirmed 2026-06-26).** Under a subset relevant set, an aggregate over a starred reference `G*/f` is relevant per its operator:
- **all-rows aggregates** (`Sum`, `MaxValue`, `MinValue`, `NumberOfDifferentValues`, `SumOfProducts`) are evaluated **only when the relevant set WILDCARDS the starred level** — `ALL_SEMANTIC` at the repeatable group, or a relevant ANCESTOR group (descent makes all rows relevant). Enumerating concrete rows — **even ALL of them** — leaves the aggregate UNKNOWN (no firing): the `*` reference's extent is "fully known" only via a wildcard (the BA's "encourages wildcarding every path level"). Controlled probe (2 rows, no fillable tail): `Sum(Lines* / Price) > 1000` fires under a `Lines` wildcard but NOT under `{Lines[1], Lines[2]}` listed concretely.
- **`FirstFilled`** is **order-aware**: it returns the first FILLED cell's value and is UNKNOWN only when a non-relevant cell precedes that first filled cell. So it fires when the first filled row is relevant (wildcard, both-rows, or that-row-only) and is UNKNOWN when that row is non-relevant (probe: row-1-filled fires under row-1-only, suppresses under row-2-only).

This is exactly the runtime `isWertAngegeben` 3VL (a non-relevant cell read is UNKNOWN; an all-rows fold with any UNKNOWN → UNKNOWN), with the wildcard-vs-concrete distinction governing whether the star's cells are check-relevant. *(Interpreter: `DmInterpreter.starRelevantOf` + the per-operator `evalFunc` gate, IF42; locked `adapter.laws.PartialValidationAggregateDiffTest` + the randomized `perf.PartialValidationFuzzDiffTest`.)*

The oracle path is the modern `validatePart(DocumentV2, …, config)` (`RuntimeLaws.firedCodesPart`/`messagesPart`). Global fields are auto-relevant (IF37, above); a `CustomCondition` receives the relevant set (null for full, the subset for partial — IF38, source `MainValidatorController` → `getAllPruefungsrelevanteEntitiesExtern`); and uniqueness needs the duplicate **partner** relevant too (IF39 — the kernel's duplicate caches are built from the relevant fields only, `befuelleCacheMitRelevantenFeldern`). *(Locked: `adapter/…/laws/PartialValidationDiffTest` + `interpreter/commonTest/PartialValidationTest`; subset-repetition aggregates by `PartialValidationSubsetRepDiffTest` (IF35, non-directional); global fields by `PartialValidationGlobalFieldDiffTest` (IF37); custom-condition relevant-set propagation by `PartialValidationCustomConditionDiffTest` (IF38); subset uniqueness by `PartialValidationUniqueIndexDiffTest` + `PartialValidationRepetitionNotUniqueDiffTest` (IF39); per-operator starred-aggregate relevance by `PartialValidationAggregateDiffTest` (IF42, above); and a randomized `PartialValidationFuzzDiffTest` sweeps (document × relevant-subset) combinations across the WHOLE partial surface. ## §8 supplement — three enum-ish kinds: "extensible enum" is an IStringType quality, NOT a field type (source-verified 2026-06-17)

Three distinct concepts, easy to conflate:

- **Closed `EnumerationType`** — a fixed value set; a normal DM-JSON field type (the md `EnumerationType` DTO: values/categories/errorMessage/alphabeticalSorting/sValue — *no* extensible flag).
- **Extensible (non-closed) enumeration** — **not a field type at all**: an **`IStringType` with `isExtensibleEnum() == true`** (parser `FieldUtils.isExtensibleEnum` = `type instanceof IStringType && isExtensibleEnum()`; `isLikeString` = string ∪ enum ∪ ext-enum). `isExtensibleEnum()` is a **client-SPI/runtime quality** — `IStringType` is "intended to be implemented by clients", the kernel's md `StringType` **defaults it `false`**, and there is **no DM-JSON property** for it (its open/dynamic values are served at runtime, e.g. via `DynamicEnumerationService`). So a DM-JSON field is **just a `StringType` — fully buildable and modelkit-authorable**; the "extensible" quality itself is unauthorable via DM-JSON (always `false` in a plain model) but doesn't need to be: `ValidType`/`InvalidType` accept the field **because it is-a string** (`isLikeString`), which the N7 `Valid(CustomerName, "EMail")` validExample already exercises. **NOT a modelkit gap.**
- **Dynamic / table-backed enumeration** — the genuinely **un-buildable** one (the `ValueNotConsistent` finding below): values from an external table, not DM-JSON-serializable.

(The model/editor metamodel `MM_Common` carries an "ExtensibleEnumerationType" config — maxLength/displayValues — and form-model/UI notions like `fieldConfigurationEntry`/`externalEnumeration` exist, but those are **tooling/FM layers outside rulekit's DM-JSON scope**, not runtime DM field types.) *(Corrects an earlier draft that wrongly called extensible enums "un-buildable" and cited `IEnumerationType.isExtensible` — it conflated the extensible `IStringType` quality with the dynamic/table-backed enum.)*

## §8 supplement — table-backed (dynamic) enums are NOT DM-JSON-serializable ⇒ `ValueNotConsistent` is un-buildable (2026-06-08)

`ValueNotConsistent(enumField <toOp> col1, col2, …)` (DE `WertNichtKonsistent`) checks a row's dependent columns against a **table-backed** enumeration. The checker (`CheckFieldAndValueListConditionImpl`) requires its first operand to be an enum field **with a table reference** (`IEnumerationType.getTableName()`/`getDependentColumns()` present), and verifies the dependent-param arity against the column count (value checks are skipped when the runtime data table is absent).

**But that field type cannot be expressed in a document model's DM-JSON.** The public a12internal `EnumerationType` DTO declares exactly **6 properties** — `values`, `annotations`, `categories`, `sValue`, `errorMessage`, `alphabeticalSorting` — and the deserializer is **strict**: injecting `tableName`/`columnName`/`dependentColumns` raises `UnrecognizedPropertyException` (*"not marked as ignorable"*, probed 2026-06-08). The table backing is materialized at **runtime** from a separate enumeration/table catalog (`IEnumerationType` returns empty Optionals when loaded from a plain document model), not from the field's type JSON.

**Consequence:** no self-contained document model can mark a field table-backed, so the checker's precondition can never be met, so rulekit's "author DM-JSON → `checkConsistency`" oracle **cannot author or verify** a `ValueNotConsistent` rule. It is **un-buildable within single-document-model scope** — same root cause as multi-form/Vordruck (needs infrastructure outside the document model), and it makes the would-be "dynamic-enum modelkit authoring" moot (there is nothing in DM-JSON to emit). Stays a tolerant `ReadResult.Opaque` if ever encountered. *(Demonstrated by probe; not locked by a test — there is no expressible fixture to lock.)*

## §1/§3 supplement — value-vs-omission typing is DIRECTIONAL and sign-aware (source + runtime, 2026-06-23)

A fired comparison is an OMISSION error (`TRUE_AF`) only when filling an operand **in the breaking direction** could clear it (`BedingungsOperatorHelper.vergleiche`): `GT`/`GE` → `left.kannKleinerWerden || right.kannGroesserWerden`; `LT`/`LE` → the mirror; `EQ` → any operand can move; `NE` → directional on which side is larger (`getFehlerFuerNE`). The per-operand fillability of an **empty number** is asymmetric: `kannGroesserWerden = true` (always fillable larger) but **`kannKleinerWerden = hatVorzeichen`** — fillable smaller only if the field is **signed** (`RuntimeController.feldWertAlsZahl`, TS twin `BigDecimalUtils.makeDecimalFromNonEmptyString`).

- **The sign trigger is `NumberType.positivesOnly`, NOT `minValue`** (the trap): a field with `minValue:1` is still *signed* (probed — `[BirthDay] >= 0` empty types OMISSION); only `positivesOnly:true` makes it unsigned (`[StockOnHand:positivesOnly] >= 0` empty types **VALUE**). `minValue` is a range constraint, independent of `hatVorzeichen`.
- Consequence: `[Unsigned] >= 0` (empty) is a **VALUE** error — an unsigned 0 can't shrink, so no fill breaks `>= 0`; the same over a *signed* field is **OMISSION**. Both `<= X` are OMISSION (filling larger breaks them).

*(Locked: `adapter.laws.DirectionalPolarityDiffTest` (unsigned `StockOnHand` vs signed `Quantity`); the signed cases also in `adapter.laws.PolarityDiffTest`/`AggPolarityDiffTest`. The interpreter's directional treatment: INTERPRETER-FINDINGS IF9.)*

**Function-operand fillability — `CurrentRepetition` and `FirstFilledValue` (probe + full-message fuzz, 2026-06-24).** The directional fillability above extends to value FUNCTIONS, not just fields/aggregates — and the naive "any empty/short star tail ⇒ fillable" over-reports OMISSION for two:

- **`CurrentRepetition(group)`** is the structural **row index**; no field-fill changes it, so a fired comparison against it is **always VALUE** (probed: `CurrentRepetition(Lines) > 2` on row 3 → VALUE). The generic fallback wrongly reads its group argument as an "unfilled field" and types it OMISSION.
- **`FirstFilledValue(g*/f)`** is **OMISSION iff an instantiated EMPTY row PRECEDES the first filled one** — filling that earlier row could become the new first value and clear the error — else **VALUE** (the first value is fixed; *later* empties are irrelevant). Probed: `(empty, 60)` → OMISSION; `(60, empty)` and `(60)` → VALUE.

The naive star-omission notion (`starOmission`: any empty cell / short tail) is too broad for `FirstFilledValue` — only an empty row *before* the first filled matters. Both were mis-typed OMISSION until the **harness-D full-message fuzz** caught them (117/200 seeds — invisible to the codes-only gate). *(Locked: `adapter.laws.FullMessageFuzzDiffTest` + `CurrentRepetitionDiffTest`/`FirstFilledValueDiffTest`, now asserting polarity, not just firing; interpreter `EvalContext.firstStarRowEmpty` + `funcFill`.)*

## §5 supplement — tolerance boundary + comparison rescaling (runtime, 2026-06-10, RT-semantics drain)

- **`DiffersWithToleranceRange{N}` fires strictly beyond the tolerance**: satisfied iff `|a − b| > N` — a difference of *exactly* N is still within tolerance and does **not** fire, in either direction. The boundary is the trap a modeller would guess either way. *(Locked: `adapter.laws.ToleranceComparisonLawsTest`.)*
- **Source-read precision policy** (`VkBigDecimal`): a NUMBER **comparison** rescales both operands to scale 19 `HALF_UP` before comparing — and this is **`BedingungsOperatorHelper.vergleiche` (lines 164-167), not `VkBigDecimal.compareTo`** (which is plain): so the rescale applies to **all** comparison ops `<`/`>`/`<=`/`>=`/`==`/`!=`, but **NOT to `min`/`max` selection**, which the kernel does at full precision via `VkBigDecimal.compareTo` (`SummeCombiner`/`MinWertCombiner` etc.). ## Condition comments — `;;` line comments are concrete syntax: tolerated; rulekit authors them and preserves the leading one (grammar + 2026-06-12)

The condition lexer defines comments — `Base_ConditionLexer.Comment: ';;' ~('\r'|'\n')* …` — so `;;` begins a **line comment** (continued across lines that each restart with `;;`), parsed *around* a `teilBedingung` (GRAMMAR-LEDGER). A rule you don't modify keeps its text verbatim (edits are surgical on the DM-JSON). The concrete-syntax-preserving (minimal-edit) re-render that *would* keep every comment in place is the parked Phase-5 residual (PROJECT-DESIGN §16); the side-channel is the cheaper, chosen alternative for the common (leading-comment) case.

### §6 supplement — DATE/DATERANGE/TIME field *format strings* are a fixed lowercase allowlist, locale-independent (probe 08, 2026-06-22)

A field's declared date **format** must be a **lowercase Java date pattern** from a **fixed allowed set** — and that set is **independent of the model's display locale AND its `conditionLanguage`** (verified: `en_US` and `de_DE` conditionLanguage accept the identical set). The A12 editor's UPPERCASE preset labels (`YYYY-MM-DD`, `MM/MM`, …) are display labels, **rejected** as `format` values (`The date range format is invalid` / `The date format is invalid` — a kernel rejection carrying **no code and empty `where`**). Verified by `field add` against fresh `en_US`- and `de_DE`-conditionLanguage models:

- **DATE** — both `yyyy-MM-dd` and `dd.MM.yyyy` validate; `YYYY-MM-DD` rejected.
- **DATERANGE** (`format` + `separator`) — the **(format, separator) pair** is allowlisted, not free: verified-accepted **`dd.MM.yyyy`+`-`** and **`yyyy-MM-dd`+`/`** (identical under en_US and de_DE). Rejected: a spaced `" - "`; a mismatched separator (`yyyy-MM-dd`+`-`, `dd.MM.yyyy`+`/`); a non-standard format (`MM/dd/yyyy`). The separator is a single char that goes with the format.
- **DATEFRAGMENT** — lowercase `MM`/`yyyy`/`yyyy-MM`/`MM-dd` accepted; uppercase rejected. (Partial dates are DATEFRAGMENT, not DATERANGE.)
- **TIME** — the **full `HH:mm:ss` is required**; `HH:mm` (no seconds) is rejected.
- **DATE_TIME** — the **only date-bearing format is the ISO `yyyy-MM-dd'T'HH:mm:ss`** (probe-enumerated 2026-06-26); every other date-bearing form is rejected `The date format is invalid` — `dd.MM.yyyy'T'HH:mm:ss`, `MM/dd/yyyy'T'HH:mm:ss`, `yyyy-MM-dd HH:mm:ss` (space, no `'T'`), and `…'T'HH:mm` (no seconds) all fail. The degenerate **time-only `HH:mm:ss`** is also accepted as a DATE_TIME format, but it cannot receive a full computed datetime (next paragraph). So a DATE_TIME field that holds a date is effectively format-locked to ISO.

**A full `DateTime(...)` result can only target the ISO DATE_TIME field — the compatibility is enforced at CODE GENERATION (probe, 2026-06-26).** Because every computation auto-generates an implicit validation rule `FieldFilled(F) And [F] != <op>` (the "every computation is also a validation rule" finding), a computation whose operation is a full `DateTime(D,T)` but whose target `F` is the **time-only `HH:mm:ss`** DATE_TIME field is rejected at codegen with **`MVK_INVALID_COMPARE_TO_DATE`** ("only allowed to compare dates with other fitting dates") — the implicit compare pits a full datetime against a time-only one, whose date-component sets don't fit (the same `formatsConsistentRegardingFormat` gate as the `Now` finding above). Net for **`compute()`**: every *authorable* computed-datetime target is the ISO `yyyy-MM-dd'T'HH:mm:ss` field, so the stored datetime is always ISO — exactly what a clean-room interpreter emits. There is no custom datetime target format to reformat to; a computed-DATE_TIME re-formatter would be dead code. *(This is why the IG19 residual closed as parity-by-construction, not a fix — INTERPRETER-FINDINGS IF33; locked by `adapter.laws.ComputeTargetFormatDiffTest.computedDateTimeUsesTargetFormatLikeKernel`.)*

**Caveat (don't conflate two validators):** the kernel-rt **runtime value** validator `…rt._30_8.internal.formatdef.FormatDefinitionDatum#validiereFormat` *does* key off the language (`convertPruefFormat2FehlermeldungFormat(pruefFormat, param.getSprache())`, German `'d'→'T'`/`'y'→'J'`) — but that validates a date **value** entered against a format at form-fill time, NOT the field-format **declaration** at model-consistency time (the `field add` check here), which is locale-independent. An earlier "language-keyed" reading of this was a measurement artifact (a reused field name made later iterations fail on `RK_NAME_EXISTS`, misread as a format rejection). ### §6 supplement — date-time sub-unit arithmetic: day-carry on add, TRUNCATE-toward-zero on difference (probe, 2026-06-24)

### §6 supplement — `Date(...)` construction value + `Valid`/`Invalid` 3VL & polarity (probe, 2026-06-24)

Runtime semantics of the date construction family (the catalog/DSL modeling is the earlier line ~294 note; this is the *evaluation* behavior, probe-confirmed):

- **`Date(day, month, year)` of an UNREAL date is NON-EVALUABLE** — it does **not** roll over and does **not** keep an out-of-range value. Probed: with all parts present and valid numbers but `(31, 2, 2024)`, every extractor (`YearFromDate`/`MonthFromDate`/`DayFromDate`) over `Date(...)` returns no value (the guarding rule does not fire, no code). So the constructor yields a value only when the date is a **real calendar date**; otherwise Unknown.
- **`Valid(Date(...))` = all parts present (non-empty) ∧ all well-formed ∧ the date is real.** Fires VALUE.
- **`Invalid(Date(...))` = present-and-well-formed ∧ (not real ∨ some part empty)** — and its **polarity is directional**: an **empty (fillable) part → OMISSION** (filling it could make the date real), a **present-but-unreal date → VALUE**. It even fires (OMISSION) on an **all-empty row** (every part unspecified is invalid — so `Invalid` "can fire empty", unlike `Valid`).
- **A MALFORMED part (a formal error, e.g. a non-numeric in a number field) suppresses BOTH** `Valid` and `Invalid` (each goes UNKNOWN → quiet; the `zahl…` formal error fires instead). This is why the catalog calls Invalid "not the pure negation of Valid": they are complementary only when no part is malformed; a malformed part sends both to UNKNOWN.

So the interpreter classifies a `Date(...)` construction as REAL / UNREAL_PRESENT / HAS_EMPTY / MALFORMED, and drives the constructor value, the two predicates, and Invalid's polarity off that one classification.

### §6 supplement — `BaseYear` is polymorphic by the other operand: base-year-START date vs the year number (probe, 2026-06-24)

### §6 supplement — a quoted date LITERAL is typed by its own SYNTAX, not by context (probe, 2026-06-24)

### §6 supplement — partial dates: the `00.MM.yyyy` form and `ValueAsDate`/`FirstDay`/`LastDay` (probe, 2026-06-24)

### §6 supplement — date ranges are closed intervals: touching ranges overlap (runtime, 2026-06-10, RT-semantics drain)

`DateRangesOverlap` / `AtLeastOneDateRangeOverlaps` treat both the start **and** the end day as belonging to the range (`DatumBereich.ueberlappt`: overlap ⇔ `end1 ≥ start2 ∧ end2 ≥ start1`). Consequences, both probe-locked:

## §6 supplement — min/max over DATES ride a dedicated `DateCombiner`: NULL-date empty identity, valueless-operand skip, symmetric omission (source + differential, 2026-07-07)

The kernel dispatches `Min`/`Max`/`MinValue`/`MaxValue` **statically by operand type onto two combiner families** — numbers → `NumberCombiner` (`min`/`minWert`), dates → **`DateCombiner`** (`minDatum`/`minWertDatum`; the only non-number family — min/max over strings is not authorable) — and the two differ in three observable ways:

- **Empty identity.** The number combiner seeds `0` (§1 supplement — `MaxValue()` over all-empty == 0). The date combiner seeds `VkDate.NULL_DATE` — *no value* — and `BedingungsOperatorHelper.vergleicheDATUM` returns **false when either side's date is null**, so a comparison against an all-empty (or zero-row) date aggregate **never fires** (`FALSE_OR_UNKNOWN`), and a computation of it **clears** the target.
- **Operand-list emptiness.** `minDatum(d1, d2)`'s `VkDate.combine` **keeps the date-bearing side** when the other operand is valueless — an empty date operand is SKIPPED (`Min([OrderDate], [DeliveryDate])` with `OrderDate` empty is `DeliveryDate`), unlike the number form where an empty operand arrives as the substituted `0` and COUNTS. A malformed / required-empty date operand is nicht-prüfungsrelevant → the whole aggregate is suppressed.
- **Symmetric polarity.** `DateCombiner` tracks no directional `kannGroesserWerden`/`kannKleinerWerden` — only the symmetric **`nichtAngegeben`** (ORed over the operands' emptiness, plus `getValue(containsFilter)` marks any filtered result, plus the omitted-tail flag). Comparison **typing** stays static and nominal: a quoted literal beside a date-valued min/max is a DATE literal (`"20.03.2026"`), and no date/text-vs-number comparison is authorable at all (`MVK_INVALID_COMPARE_TO_DATE` / `MVK_INVALID_TYPE_FOR_COMPARISON`) — so a runtime date-vs-number pair can only ever be evaluator-made, never input-legal. *(Interpreter: kind-aware fold identity + `minMaxOperandVals` + the `starFill` date branch + `producesDate` over the min/max family; locked by `adapter.laws.DateAggregateDiffTest` incl. a codegen tri-check — IF58.)*

## §2 supplement — the filled-count aggregates (2026-06-04 experiments)

**Runtime counting semantics (2026-06-10, RT-semantics drain — `anzahlAngegebenerEntities`):**

- **A formal-error operand makes the whole count non-evaluable** — the rule is suppressed; the broken field is neither counted as filled nor skipped (contrast `FirstFilledValue`, where a broken operand *after* the first filled one is invisible).
- **The count can grow but never shrink**: with unfilled operands left, a fired comparison is an `OMISSION_ERROR`; with every operand filled, a `VALUE_ERROR` — a plain field list has no omitted-tail problem (unlike the starred aggregates, §9 supplement).

*(Locked: `adapter.laws.FilledCountLawsTest`.)*

**Generalizes to every NUMERIC COMBINER (2026-06-23, fuzz-found):** a malformed element makes the **whole combiner non-evaluable → rule suppressed**, not just counts. Probed: `Sum(Lines* / Price) > 100` with one `"abc"` element fires **only** `zahlHatUngueltigeZeichen`, never the rule. Holds for the starred aggregates (`Sum`/`MaxValue`/`MinValue`/`NumberOfDifferentValues`) and the operand-list `Min`/`Max` alike — a formal-error operand is "unknown", and an aggregate over an unknown is unknown. (Empties are different: the star drops absent/empty cells, so an empty row is *skipped*, not a suppressor; only a FILLED-but-malformed value suppresses.) **"Malformed" means FORMALLY invalid, not merely unparseable** — a fuzz seed caught that `-0` (a signed zero) *parses* as `0` yet is a formal error, so `Sum` over a `-0` element must suppress (the kernel does); the interpreter therefore decides aggregate-element validity by the **formal check**, not by parseability. *(Locked: `adapter.laws.AggMalformedDiffTest`.)*

## §4 supplement — index-field uniqueness: `uniqueIndex` flags EVERY duplicate participant, scoped per parent (runtime, 2026-06-23)

A repeatable group's `indexFieldName` is auto-checked for uniqueness (fuzz-found, with the duplicate-key pool). The kernel emits **`uniqueIndex`** on **every** row whose (non-empty) index value duplicates another's — not all-but-first: `[A, A, B]` flags rows 1 AND 2; `[X, X, X]` flags all three; `B` (unique) is clean. An **empty/absent** index value is excluded from the check — it is a requiredness concern, so it gets `mandatoryField` instead (`[A, , A]` → `uniqueIndex` on the two A-rows + `mandatoryField` on the empty). Uniqueness is **scoped per parent**: the same `PartId` under two *different* Lines does NOT clash (each Line is its own scope). It is a VALUE error (you change a value to fix it) and rides an autogenerated rule (like the mandatory check). *(Locked: `adapter.laws.UniquenessDiffTest`.)*

**The uniqueIndex error also makes the field "unknown" for any author rule referencing it — branch-scoped, exactly like a formal error (2026-06-24, fuzz-found).** Probed: with a duplicate `ItemId`, a rule `FieldFilled(ItemId) And Length(ItemId) > 0` fires only `uniqueIndex` (the `Length` rule is **suppressed** — the duplicate index value is non-evaluable); but a rule on a *sibling* field on the same duplicate rows (`[Price] > 0`) **still fires** (+ `uniqueIndex`). So a duplicate index is operand-level "unknown" — it suppresses rules that read THAT field, not the whole row (the same branch-scoped behavior as `datumFormatFalsch` / a malformed value). *(Locked: `adapter.laws.UniqSuppressionDiffTest`.)*

## §4 supplement — `FieldValuesNotUnique`: a duplicate among the operands' values, plain-list OR starred (probe, 2026-06-24)

The author-written sibling of `uniqueIndex` (the auto index check above). It has **two operand shapes, identical in semantics** (both kernel-probed): a **plain field list** `FieldValuesNotUnique(f1, f2, …)` — distinctness across named sibling fields — and a **starred** operand `FieldValuesNotUnique(Items* / Count)` — distinctness across the repetition's ROWS (the no-`--group` alternative to `RepetitionNotUnique`, on a *non-index* field; on an index field the auto `uniqueIndex` fires first and suppresses it). Probed semantics:

- **Fires iff two of the operands' values are EQUAL** — i.e. the present values are not all distinct. A VALUE error (you change a value to fix it; the clashing operands are already filled, so there is nothing to "fill"). With 3+ values, any one duplicate pair fires.
- **Empties are skipped** — an absent value contributes nothing, so **two empties are NOT a duplicate** (plain `(_, _)`/`(5, _)` and starred rows `5,_,9` all do not fire; starred `5,_,5` DOES — the two 5s duplicate, the empty row dropped). Only present values compare.
- **Equality is the typed comparison** — numbers compare **numerically** (`Quantity = 5` scale-0 vs `UnitPrice = 5.00` scale-2 → equal → fires, *not* a string compare); strings compare as strings (`"AB" == "AB"`). It accepts string fields as well as numeric ones.
- **A filled-but-formally-invalid operand suppresses** the rule (non-evaluable, like every other operator — `(abc, 5)`, or a malformed row, → only the `zahl…` formal error, the `FieldValuesNotUnique` rule goes quiet).
- The error field, as for any rule, must be **referenced in the condition** or codegen rejects it (`MVK_ERROR_FIELD_NOT_REFERENCED`).

*(Locked: `adapter.laws.FieldValuesNotUniqueDiffTest` — plain + starred — + a fuzz rule `FU` = `FieldValuesNotUnique(Qty, Price)`. Interpreter: `PredicateOp.FIELD_VALUES_NOT_UNIQUE`, `Interpreter.fieldValuesNotUnique` — collects plain-field + starred-row values, O(k²) pairwise `eq`.)*

## §9 supplement — `RepetitionNotUnique`: per-row cross-row composite-key uniqueness (probe, 2026-06-24)

The author-written **cross-ROW** uniqueness rule (vs `FieldValuesNotUnique`'s value-list, and the auto `uniqueIndex`). The rule sits at the **PARENT** group and iterates the keys' repeatable group; the error field is **inside** the repeated group, so it emits **one message per offending row**. Probed semantics:

- **Fires per row whose (composite) key DUPLICATES another row's** within the parent-row scope — `Count [5,5]` flags both rows (2 messages); `[5,7,5]` flags rows 1 & 3, not 2; `[5,7]` and a single row → none. A **composite** key is the tuple: `(Count,Weight) [(5,1),(5,2)]` distinct → none, `[(5,1),(5,1)]` → both flagged.
- **An ALL-empty key row is skipped** (`empty,empty` → none; `5,empty` → the empty row drops, the lone `5` is not a duplicate). But **among participants** (≥1 key field filled) **empties match empties**: a composite `(5,empty),(5,empty)` → the two rows ARE duplicates → flagged.
- **Polarity is directional**: an all-filled duplicate is **VALUE** (change a value); a duplicate whose key has an **empty (fillable) component** is **OMISSION** (`(5,empty),(5,empty)` → OMISSION — filling the empty `Weight` could make them distinct).
- **Keys are plain fields on one path** — no groups (`MVK_NO_GROUPS_ALLOWED`), no asterisks (`MVK_NO_WILDCARDS_ALLOWED`), all on a single path (`MVK_NOT_IN_SAME_PATH`); each must be repeatable relative to the rule group, so the rule must be authored at the PARENT (error field inside the repeated group), not inside it (`MVK_REPEATABLE_GROUP_MISSING`).
- **It is a per-row 3VL PREDICATE; a guard conjunct gates firing, NOT the cache** (probe + source, 2026-07-07). `RepetitionNotUnique(key)` composes like any predicate: `<guard> And RepetitionNotUnique(key)` fires a duplicate row only when the guard also holds there, and the combined polarity follows the ordinary `And` (OMISSION if either operand is OMISSION; a formally-invalid guard operand → UNKNOWN → suppresses). Crucially the **duplicate cache is built over the full scope INDEPENDENT of the guard** — so a duplicate whose guard is FALSE does not fire, yet it still makes its partner a duplicate. Source, BOTH strategies: runtime `RuntimeController.wiederholungNichtEindeutig` builds the cache once (`RepetitionNotUniqueErrorCache.isInitialised`) over ALL rows in `ermittleWiederholungenMitDuplikaten`, then per-row returns `TRUE_WF`/`TRUE_AF`/`FALSE_OR_UNKNOWN`; codegen `EntityListCondition.st` emits a call to that same runtime method with a per-rule cache (so codegen carries no separate RNU semantics — runtime-parity ⟹ codegen-parity). *(Locked own-domain: `adapter.laws.RepetitionNotUniqueGuardedDiffTest`, incl. a groovy-dynamic vs static-JAVA tri-check.)*
- **A FORMALLY-INVALID key cell is EXCLUDED from the duplicate cache — per-KEY-CELL, not row-wide** (source + differential, 2026-07-07). The cache is built from **check-relevant** cells only: `ermittleWiederholungenMitDuplikaten` calls `getWerteOrNullIfEinFeldNichtPruefungsRelevant`, which returns null — the whole row is `continue`-skipped — the moment ANY key cell's `isWertAngegeben` is **UNKNOWN** (`= !isPruefungsRelevant =` the cell is marked `fehlerhaft`): a bad FORMAT, a duplicate-INDEX (`uniqueIndex`) cell, an over-repetition cell, **and a required-EMPTY cell**. **The required-empty case is a CORRECTION (2026-07-07, composite-key differential): a required-empty key cell IS UNKNOWN, not a valid participant.** The kernel's mandatory check is a **PRELIMINARY autogen rule** (`CodeGenRuleDefinition.isPreliminary()` = *"exactly the auto generated rules are preliminary"* → `MainValidatorController.preliminaryError(…, PFLICHT_FELD_FEHLER, …)` → `ValidationCache.markFieldAsInvalidForValidation`) that runs BEFORE the RNU rule builds its cache, so a required-empty cell is already `fehlerhaft` ⟹ `isWertAngegeben == UNKNOWN` ⟹ the row is dropped. Only an **OPTIONAL-empty** cell (a non-required field left empty) is `isWertAngegeben == FALSE` → a valid empty participant contributing a null key component. So the distinguishing property is **requiredness, not emptiness** (differentially: `(Sku,Count)` with `Sku` required+empty on both rows and `Count` duplicated fires **nothing**; the same shape with an OPTIONAL empty component fires OMISSION). Consequences: `RepetitionNotUnique(indexField)` over a duplicated index does **not** fire (each index cell is `uniqueIndex`-invalid → excluded → no two rows are "duplicates" in the check-relevant cache; only the auto `uniqueIndex` fires), and a malformed / required-empty key cell is likewise never a duplicate. The exclusion consults only the KEY fields (`entityList`), so a formal error on a NON-key field of the same row does NOT drop it — `RepetitionNotUnique(Count)` still fires on rows whose INDEX field is a duplicate. This is the exact sibling of the field-local `uniqueIndex` suppression above (§4 supplement, IF15). *(Locked own-domain: `adapter.laws.RepetitionNotUniqueFormalKeyDiffTest` — dup-index key, malformed key, composite required-empty key, fully-duplicated control, mixed rows, the clean-non-key control, + a groovy-dynamic vs static-JAVA tri-check; the OPTIONAL-empty participant by `adapter.laws.RepetitionNotUniqueDiffTest.compositeEmptyComponentIsOmission`.)*
- **Scope (the BA "basic version", no `@From`):** the **reference group** is the **first repeatable group BELOW the rule group** on the key path, and uniqueness is checked per that group's **PARENT row** — NOT per the key's immediate parent. So a key two repeatable levels deep (`/Project/Milestones/Tasks/Effort`, rule at `/Project`) is checked across **ALL** tasks of **all** milestones (scope = the `/Project` row), not per milestone (kernel-probed on the nested project fixture). For a single-level key (`/Order/Items/Count`) the two coincide. The **`@From _Group_`** selector (the `FromScope` path-op) **overrides the reference group**, scoping uniqueness per the named group's PARENT — so `@From Milestones` (reference Milestones) checks across all milestones (global), while `@From Milestones/Tasks` (reference Tasks) narrows to per-milestone (both kernel-probed on the project fixture). `@From` resolves relative to the rule group: a relative name/path, the `RuleGroup` keyword (the rule group itself — requires it be repeatable, else `MVK …must be repeatable`), `..` segments, or an absolute `/…` path. Naming the rule group by its own name (`@From Project`) is `MVK_INVALID_ENTITY` — use `RuleGroup`. The keyword is localized (`@From` EN, `@Von` DE), unlike the `In`/`IN` separators.

*(Interpreter: a dedicated uniqueness pass `DmInterpreter.repetitionNotUniqueMessages` — recognized via `repetitionNotUnique`, routed out of the per-row `evalRule` flow like `uniqueIndex`; `scopePrefixLen` resolves the reference group (the `@From` ref via `resolveGroupRef`, else the basic-version default) → groups rows by `parent(R)` and flags `count > 1`. ## §9 supplement — `SemanticIndex` (`[field For "value"]`): keyed row lookup, absent → empty value (probe, 2026-06-24)

`[Field For "value"]` is the value of `Field` in the repetition whose **index field** equals `"value"` (the kernel's "semantic index" — by the index field, not the positional row number). Probed:

- A matched, **filled** cell yields its value — `[Items/Count For "SKU-1"]` is the `Count` of the Items row with `Sku == "SKU-1"`; `== 5` / `> 0` fire as VALUE.
- **No matching row OR a matched-but-empty cell both read as the kind's EMPTY value** (a number → 0) — `[Items/Count For "SKU-1"] == 0` **fires (OMISSION)** when there is no `SKU-1` row or its `Count` is empty (the absent value is fillable); `> 0` / `== 5` do not fire. So a missing key is NOT "unknown" — it is the empty value, exactly like a missing field reference (empty-as-0 for a number, with the field's directional polarity).

*(Interpreter: `Expr.SemanticIndex(path, indexValue)` (parsed in the `[...]` atom via a `For "…"` clause); `EvalContext.indexedCell` scans the target's repetition rows in scope for the sibling index match, returning the resolved cell or null (→ the kind's empty value). The group's index field is resolved from the threaded `indexFields`; the polarity rides the standard `fill` (fillable iff the cell is absent/empty). ## §9 supplement — `SemanticIndex` PRESENCE: absent row ≡ empty cell (FALSE), malformed cell / invalid key → UNKNOWN (source + differential, 2026-07-07)

An indexed ref is also a legal **presence operand** — `FieldFilled(Count For "SKU-1")`, `FieldNotFilled(…)`, or an operand of a fill quantifier (`AllFieldsFilled(Count For "K", Other)`) — and `FieldValueAsString(field For key)` reads through it. The kernel compiles `FieldFilled`/`FieldNotFilled` as one-operand `AllFieldsFilled`/`NoFieldFilled`; the indexed ref resolves to AT MOST ONE cell (`ValidationCache.resolveSemanticIndex` → `IndexFieldCache.lookup`, first match wins) whose presence is the ordinary `isWertAngegeben` 3-state:

- a matched, check-relevant **filled** cell → TRUE;
- a matched row with an **empty** cell, an **ABSENT row** (no row carries the key), or an **empty/no-match KEY field** (the field-keyed `[X For KeyField]` form) → FALSE — an absent row is judged like an empty cell, **not skipped**, so `FieldNotFilled([X For "k"])` FIRES when no row carries the key;
- a **malformed** matched cell, or a formally **invalid key field** → UNKNOWN (not check-relevant — neither the positive nor the negative presence fires).

`FieldValueAsString` over an indexed cell reads the matched cell's stored value; absent/empty reads as `""` (which the `vergleicheSTRING` empty rule then suppresses in a comparison). *(Interpreter: `semanticIndexPresence` behind the shared `presenceTri`; locked by `adapter.laws.SemanticIndexPresenceDiffTest` — IF59.)*

## §9 supplement — `Having`: a per-row filter on a starred aggregate (probe, 2026-06-24)

`Sum(Items* / Count Having <cond>)` (and the other aggregates) consume **only the rows for which `<cond>` holds** — the filter is evaluated per repetition row before the aggregate. Probed: rows (UnitWeight, Count) `(1,3),(2,10),(1,4)` with `Having [Items/UnitWeight] == 1` → the aggregate sees only the W==1 rows → `Sum == 7` (the unfiltered Sum is 17); `> 5` fires, `> 7` does not; `Having [...] == 9` (no matching rows) → `Sum == 0` fires. Polarity is the aggregate's own (Sum over a growable repetition → OMISSION). The filter is a full condition over the row's fields. ## §8 supplement — the value-list membership family (2026-06-04 experiments)

Five operators in two grammar shapes, not covered by KERNEL-SEMANTICS. **Shape A** `FieldValueIncludedInValueList(field, v1, …)` / `FieldValueNotIncludedInValueList(…)` (DE: `FeldWertInWerteListe`/`FeldWertNichtInWerteListe`); **shape B** `AtLeastOne|No|NotAllFieldValue(s)IncludedInValueList(f1, f2 In v1, …)` (DE: `MindestensEin…`/`Kein…`/`NichtAlle…`; `In` is a language-independent grammar literal like the symbols). Slot rules:

- **Only string, enum, and number fields participate** — a boolean/confirm field draws **`MVK_ONLY_STRING_ENUM_NUMBER_ALLOWED`** ("only allowed to use string fields, enumerations or numbers (including amounts)").
- **Numeric values are integer literals only** — the grammar's value-list `number` is `'-'? digits`; a decimal (`10.50`) is a *parse error* (`MVK_UNEXPECTED_TOKEN`), even against a scale-2 field. Negative integers are fine.
- **Value types must match the field kind** — string field vs numbers or number field vs strings → **`MVK_INVALID_TYPES_FOR_COMPARISON`** (the plural-`TYPES` sibling of the comparison code).
- **Enum domains are enforced** — shape A: an out-of-domain value → **`MVK_INVALID_STRING_CONSTANT_FOR_ENUMERATION`**; shape B → **`MVK_INVALID_STRING_CONSTANT_FOR_ENUMERATION_OR_CATEGORY`**.
- **Shape B field lists must be type-homogeneous** — mixing a string and a number (or enum) field → **`MVK_VARYING_TYPES_NOT_ALLOWED`** ("All fields must be the same type"). A single-field list is legal.
- The field slot is a **bare path** (a bracketed `[Field]` is a parse error); the value list may also contain **field references** (`[OtherField]`) and may mix them with literals; shape B's right side accepts an entity list or strings (no numbers, per grammar).

*(Locked: `validate.laws.ValueListLawsTest` + N7 examples of all five operators. **Field-valued (entity) lists are now implemented** — the value-list quantifiers take `FieldListRef` operands (incl. `*`-flattened scopes), locked by `adapter.EntityListValueListReadTest`. **Shape A with a field entry** — `FieldValueIncludedInValueList(Choice, [Allowed])`, where a value-list entry is a field rather than a constant — is also read, `adapter.ValueListFieldEntryReadTest`.)*

Then:

- **`AtLeastOne`** fires iff some TRUE fields-cell value ∈ the value set. Empty/UNKNOWN cells and members are **skipped outright** (its values collector `fuegePruefungsrelevanteFeldWerteZuWerteListe` adds only TRUE values); an **empty value SET → no fire**.
- **`No`** fires iff **no** TRUE fields-cell value ∈ the set — including when nothing is filled at all (the sole `canFireEmpty`). An **UNKNOWN fields-cell or values member POISONS** it (`FALSE_OR_UNKNOWN`, no fire) — its per-cell scan and its values collector (`fuegeFeldWerteZuWerteListe`) both bail on UNKNOWN.
- **`NotAll`** needs a filled fields-cell (`noEntityFilled` guard), fires iff some TRUE cell value ∉ the set; an UNKNOWN **values member** poisons, an UNKNOWN **fields-cell is skipped** (no guard on that side).

- **Fired polarity:** `AtLeastOne` → VALUE; `No` → OMISSION on any empty fields-cell / un-instantiated declared tail / empty values member, else VALUE; `NotAll` → OMISSION **only on the values side's account** (it has NO fields-tail flag — the `No`-vs-`NotAll` asymmetry). - **Index-field errors are field-LOCAL:** a starred INDEX field's empty cell is mandatory-empty and EVERY duplicate-valued cell carries `uniqueIndex` (§4) — those cells are UNKNOWN (skipped by `AtLeastOne`, poisoning `No`) — while a CLEAN SIBLING field in the same rows reads all its cells normally (the row is not collectively compromised).
- **A NUMBER field-list's value list is field-valued only** — a numeric literal is authoring-rejected both unquoted (`MVK_INVALID_ENTITY`) and quoted (`MVK_INVALID_TYPES_FOR_COMPARISON`); string lists take string literals. ## numeric coercions (family 4, 2026-06-07)

The number twins of the string coercions (`FieldIdOperationName`): `FieldValueAsNumber(field)` (DE `FeldWertAlsZahl`) and `RangeAsNumber(field, start, end)` (DE `BereichAlsZahl`, an `IFieldIdOperationWithParameters` carrying a **0-based** start — rendered 1-based, like `RangeAsString`). Both return a number, so they compose into comparisons/arithmetic. Two distinct convertibility rules:
- **`RangeAsNumber` tolerates any string field** — a non-numeric substring (or an empty field) yields **0**, not an error (so `RangeAsNumber(ShipmentRef, 1, 2) == 0` is valid against a plain string field).
- **`FieldValueAsNumber` requires the field to *always* convert** — the field must be a string or enumeration whose values (or category values) are all numeric, else `MVK_NO_CONVERT_IN_NUMBER`. A plain free-text string is rejected; an **enum whose values are numeric** (`"1"`/`"2"`/`"3"`) is accepted (the order fixture / corpus gained a `RushLevel`/`Grade` numeric enum for this).

Modeled as `FieldValueAsNumber`/`RangeAsNumber` (Calculation, kind NUMBER), the numeric mirror of `FieldValueAsString`/`RangeAsString`; authored via `Dsl.fieldValueAsNumber`/`Dsl.rangeAsNumber`. *(Locked: `adapter.StringCoercionReadTest.roundTripsNumberCoercions` + BA-corpus `FieldValAsNumber`/`RangeAsNum`; N7 catalog examples.)*

**Runtime semantics + interpreter status — the `Range*` substrings (2026-06-24).** Source-read `RuntimeController.getSubstring`/`bereichAlsZahl`: the substring is `value[start-1, end)` (1-based inclusive) **but** an empty value OR `end > value.length()` yields **`""`** — never a partial substring (the out-of-range cliff). `RangeAsNumber` then parses its substring **only when it is a pure run of digits (`\d+`)** — anything with a sign, a decimal point, non-digits, or empty → **`0`**. The interpreter reproduces both (`Interpreter.rangeSubstring` + the `\d+` gate). **`RangeAsString` is read and authored** in rulekit's DSL (a string coercion, alongside `RangeAsNumber`/`FieldValue*` — `adapter.StringCoercionReadTest`, `dsl.operators.RangeOperandTest`); the interpreter handles both for evaluation. *(Interpreter-locked: `adapter.laws.RangeCoercionDiffTest`.)*

**Empty-string comparison — generalized (2026-06-24).** `BedingungsOperatorHelper.vergleicheSTRING` returns **false when EITHER operand is the empty string**, for `==` AND `!=` alike — so an empty `RangeAsString` result, or a **literal `""`**, makes the comparison **not fire** (NOT "they differ"). The interpreter previously matched this only for empty string *fields* (which resolve to `Unknown`); it now matches it for *any* empty string operand (`Interpreter.evalCmp` suppresses when either side is an empty `Val.Txt`), fixing a latent `[field] != ""` divergence the `RangeAsString` work surfaced. *(Interpreter-locked: `adapter.laws.RangeCoercionDiffTest.notEqualToEmptyLiteralDoesNotFire`.)*

**Interpreter status — the value coercions `FieldValueAsString`/`FieldValueAsNumber` (2026-06-24).** `feldWertAlsString` returns the field's **RAW stored value** as a string (no re-canonicalization — `"5.00"` stays `"5.00"`), empty → `""`; `feldWertAlsZahl` parses the value to a number and an **empty** field reads as **`0`**. The interpreter reproduces both (`FieldValueAsString` → `displayValue ?: ""`; `Interpreter.fieldValueAsNumber` → empty `0`, else `decOrNull`); a formally-invalid number → Unknown (the formal mechanism suppresses). On a numeric-valued enum the number coercion equals the code's value. *(Interpreter-locked: `adapter.laws.FieldValueCoercionDiffTest` — raw-value string match + numeric-enum coercion, on `order.dm.json`.)*

## operand-list math: Abs / Min / Max (family 5, 2026-06-07)

The kernel's `IOpListOperation` (`OpListOperationName`) has two groups: the rounding family (`RoundDown`/`RoundUp`/`RoundAccounting`, modeled as `Rounding`, which carry decimal places) and the parameterless **`Abs`/`Min`/`Max`** (DE keywords are the untranslated `Abs`/`Min`/`Max`). ## NumberOfValueInFields (family 6, 2026-06-07)

## §9 supplement — per-row iteration + aggregation of missing rows (runtime, 2026-06-06)

The first **runtime** (fires/does-not-fire) checks of §9, via the multi-row `RuntimeLaws.Doc` builder:

- **Per-row iteration.** A rule whose error field reaches *through* a repeatable group is evaluated **once per existing row**, and each message attaches to **that row** (the pointer carries the row index). Verified: rule in `/Order`, error field `Items/Count`, condition `[Items/Count] > 50` over three rows `10/80/90` → fires **twice**, on `/Order/Items/Count [1, 2, 1]` and `[1, 3, 1]` (rows 2 and 3); rows `10/20/30` → fires nowhere.
- **Aggregation of missing rows.** `Sum` substitutes `0` for an empty field (so empties neither error nor suppress the aggregate): `Sum(Items*/Count)` over `40, _, 40` is `80`; over an all-empty list is `0`. `MaxValue` ignores empties: over `40, _, 10` it is `40`.
- **`GroupFilled` = the row exists, not that it has data.** `GroupFilled(Items)` fires for a created Items row whose `Count` is empty, and not when there is no Items row at all.
- **`RepetitionNotUnique`** (no `*` wildcard — the asterisk draws `MVK_NO_WILDCARDS_ALLOWED`) fires on each duplicate row of a non-index field: `Count` values `5, 5, 9` → fires on rows 1 and 2, not row 3. The **index field** already carries *built-in* uniqueness — duplicate index values raise the kernel's own `uniqueIndex` formal error regardless of any author rule, so `RepetitionNotUnique` on the index field is redundant.
  - **Placement is exacting (validate-time, verified 2026-06-22, probe F06-1).** The rule must sit at the **PARENT** of the repeated group with the error field **inside** it — `RepetitionNotUnique(Items/Sku)` is accepted only with rule group `/Order` + error field `/Order/Items/Sku` (verified VALID). The CLI's default grouping (rule group = the error field's own parent) puts the rule *at* `/Order/Items`, where the same condition draws **`MVK_INVALID_ENTITY`**; with a non-repeatable error field (rule at `/Order`, field `/Order/CustomerName`) it draws **`MVK_NO_WILDCARD`** — so `MVK_NO_WILDCARD` here is *not* a "missing asterisk" (the operator forbids one) but a wrong-scope signal. Author it with the rule group at the parent — `rule check --group /Order --field /Order/Items/Sku` — and **persist with the same `group` key** (`rule add` / `apply rule add` accept it, mirroring `rule check --group`, so a checked rule round-trips; F06-3, 2026-06-22). `MVK_NO_WILDCARD` is a **shared** code (also CurrentRepetition, aggregates, model-scope `GroupFilled`), so its enriched fix is generic — KERNEL-INTEGRATION-NOTES "Structural-code fix hints" (F06-2). The catalog (`RepetitionNotUnique` gotchas) and `FieldValuesNotUnique(Items*/Sku)` (the asterisked, no-`--group` alternative for plain cross-row uniqueness) are the authoring paths.
- **Parallel iteration** — two repeatable groups keyed by a shared index field are iterated jointly as an **outer join** over the index values; a value present on one side only counts as **"not specified"** on the other. Verified on an own-domain `staffing` fixture (`Demand`/`Supply`, both keyed by `Department`): `FieldsNotCollectivelyFilled(Demand/Headcount, Supply/Headcount)` with Demand=`{Sales, Eng}` but Supply=`{Sales}` fires once, on the `Eng` Demand row (its Supply side is not specified); when every Department is matched on both sides it fires nowhere. *(Locked: `adapter.laws.RepetitionLawsTest`, `adapter.laws.RepetitionNotUniqueLawsTest`, `adapter.laws.ParallelIterationLawsTest`; the exact-match interpreter differential is `adapter.laws.ParallelIterationDiffTest`.)*
  - **The iteration value-set is the UNION of the groups' index-field values** — source-confirmed (`ValidationCache.getIterationValuesForGroups` collects each group's `IndexFieldCache` value→repetition map keys into a sorted set). For each value, each group resolves to the row carrying it, or `IIdentifier.UNKNOWN` if absent.
  - **The unmatched side's pointer carries `IIdentifier.UNKNOWN = -5`** as its repetition index — a fixed sentinel, NOT a fresh counter. So an outer-join fire whose *error field's own group* has no row for the value points at e.g. `/Staffing[1]/Demand[-5]/Headcount` (probed; reproduced exactly). Polarity is the ordinary empty-operand rule: an iteration with an unspecified operand types **OMISSION**, all-specified types **VALUE**.
  - **An INVALID index value (duplicate or empty) is a 3VL corner.** A duplicate value still sits in the index cache (last write wins) and the union, but the kernel marks the group's index *invalid* for that parent (`IndexFieldCache.isIndexGroupInvalidForOneRepetition`); references into a group with an invalid index then read as **3-valued UNKNOWN** for unmatched values — which *suppresses* a negative operator like `FieldsNotCollectivelyFilled` (it fires only on a definite "not filled"). Probed asymmetry: a clean A-only value (error field filled, sibling missing) fires, but the same shape with an invalid index in the *sibling* group does **not** (the sibling's reference is UNKNOWN, not "empty"). Operator-specific, but fully reproducible — the interpreter models it exactly (`Document.parallelContexts` marks a group invalid for a parent when it has a duplicate/empty index there, and `ParallelRowContext` reads that group's unmatched references as `Val.Unknown` / `presenceUnknown` → the Kleene logic suppresses the negative operator). See INTERPRETER-FINDINGS IF19 for the interpreter treatment.

## §9 supplement — a rule/computation's ITERATION SCOPE is its set of referenced repeatable fields, not its node placement (corrected + matrix-verified, 2026-06-21)

> **Correction (2026-06-21):** an earlier note here claimed a `field move` *into or out of* a repeatable group is rejected `MVK_ERROR_FIELD_NOT_IN_RULEGROUP` and motivated a planned "co-move the bound rule/computation" enhancement. A full directional matrix (authored via `rule add`/`computation add`, validated through the kernel) shows that was **directionally wrong** and the enhancement is a **non-goal**. The verified truth follows.

A rule's **error field** and a computation's **computed field** are stored as a *relative* path (`errorEntityRelPath` / `computedFieldRelPath` = `"../F"`). But the kernel derives a rule/computation's **iteration scope from the repeatable fields it *references*** (the error/computed field **plus** every per-row operand), **not** from where the rule/computation node physically sits. The law: the error/computed field must **share the iteration scope** of the referenced repeatable operands. (Locked by `validate/laws/IterationLawsTest.errorFieldMustShareTheIterationScopeOfTheReferencedRepeatableFields`.)

Consequence for a reference-rewriting **`field move`** of F (matrix-verified, symmetric for rules *and* computations):

| `field move` of F | bound rule/computation (error/computed field = F) | why |
|---|---|---|
| → **into** a repeatable; the rule/comp node is at the outer scope | **accepted** — node stays put, reaches *down* (e.g. `errorEntityRelPath ../Items/DeliveryDate`, `computedFieldRelPath ../Rep/X`); the error/computed field then drives the per-row iteration | the error field inside the repeatable *is* the iteration scope; per-row operands resolve consistently |
| → **out of** a repeatable; the rule/comp references **only** F + outer/constant fields | **accepted** — node stays put, reaches *out* (`../../Qty`); nothing forces per-row iteration any more | no referenced operand is per-row, so error field + operands are all in one (outer) scope |
| → **out of** a repeatable; the rule/comp **also** references another field still **inside** the repeatable | **rejected** `MVK_ERROR_FIELD_NOT_IN_RULEGROUP` (or `MVK_NO_WILDCARD` on the operand side) | a genuine **cross-cardinality split**: F is now single-valued while a referenced operand stays per-row |

So a `field move` is rejected **only** when it would genuinely split a rule/computation across two cardinalities — and that case is **not mechanically fixable**: relocating the node ("co-move") leaves the cross-scope operand reference intact, and the *only* valid repair is to **rewrite the rule's logic** (e.g. wrap the per-row operand in an aggregate: `X = [Rep/P] * 2` → `X = Sum(Rep*/P)`), a modeling decision the tool must not invent. The existing reference-rewriting `field move` therefore already accepts every *semantically valid* cross-boundary move and correctly refuses the genuinely-broken ones; **`field move` co-move adds no capability → non-goal** (CLI-SPEC §6; FEATURE-GAPS §4). *(All behavior here is the kernel's; rulekit just lets the kernel's gate refuse the split, with `model check` as backstop.)*

## §9 supplement — the kernel tolerates an index field on a non-repeatable group (probe-observed, 2026-06-21)

A group's `indexFieldName` (the repetition row-key) is **not** kernel-gated on repeatability: a `repeatability: 1` (single) group carrying an `indexFieldName` that names a direct-child field passes `checkConsistency` (probed via raw DM-JSON + `model check` → `valid: true`). But it is a **degenerate** row-key — with no repetitions, the uniqueness check (`RepetitionNotUnique`) it would arm is vacuous and parallel iteration has nothing to iterate. So **modelkit/CLI deliberately forbid it** (`ModelDocument.setIndexField` / `group modify --index-field` require a repeatable group): the index field only earns its keep on a repetition list. **Prose-only by design** (the consumer for the kernel-tolerance fact is nobody — we refuse the degenerate case; *our* behavior is locked by `GroupModifyVerbTest.indexFieldOnANonRepeatableGroupIsRejected`, the G24 surface). This resolves the SME 1184 question (the non-repeatable allowance) — the kernel allows it, we don't, on purpose.

## §9 supplement — `GroupFilled` splits on repeatability (source-read `GroupFillCache` + differential, 2026-06-23)

`GroupFilled(G)` is **not** one rule — it depends on whether `G` is repeatable (kernel `GroupFillCache` / `ValidationCache`):

- **Repeatable `G`**: a row is filled once it is **instantiated** — creating the row is itself content (the repetition index is meaningful). A *created-but-empty* repeat row → `GroupFilled` **TRUE**. (A filled descendant also instantiates the row, so "row exists" subsumes "descendant filled".)
- **Non-repeatable `G`**: filled only when **at least one descendant field is filled** — its mere structural presence (even an explicitly-created empty instance) is **not** content → `GroupFilled` **FALSE**.

This is why the `relativeToParent` requiredness gotcha (§4) flips by parent repeatability, and it resolves the earlier "GroupFilled on an empty created repeat row" open edge (interpreter was descendant-filled-only; now matches). *(Interpreter parity locked via the requiredness gate: `adapter.laws.RequirednessDiffTest` (the created-empty-repeat-row case fires `mandatoryField`; the non-repeatable empty-parent case does not).)*

## §9 supplement — wildcard slot laws (slice 7a, 2026-06-04 experiments)

The `*` suffix is per path segment (grammar `idNameRef: idName '*'?`) and builds a **repetition list**; whether it is legal depends purely on the *slot*:

- **List slots accept starred paths**: the field-list quantifiers (`AtLeastOneFieldFilled(Addons*/Name)` …), shape-B value lists (`…(Addons*/Name In "x")`), and the count/`Sum` aggregates — iterating rule or not, and **mixing plain and starred operands in one predicate is legal**.
- **Scalar slots reject them** with **`MVK_NO_WILDCARDS_ALLOWED`** ("It is not allowed to use an asterisk"): `FieldFilled(Addons*/Name)`, a bracketed value `[Addons*/Fee]`, `GroupFilled(Addons*)`, and shape A's single-field slot.
- A star on a **non-repeatable** group is its own code: **`MVK_INVALID_WILDCARD`** ("Since 'X' is not repeatable…").
- **The negativity law (`MVK_NEG_CONDITION_IN_ITERATION`) is not an operator list** — the kernel's `IterationNotValidVisitor` (~800 lines) classifies each condition as positive/negative *in context*: the same operator flips depending on whether its operands reference the iteration (e.g. `FieldFilled(A)` is "negative" when `A` does *not* iterate but the rule does), and aggregate comparisons against constants are negativity-sensitive by comparison direction (`< / <= / != n`, `== 0`-style forms). rulekit deliberately does **not** replicate this — kernel-delegated to F4.
- **`MVK_NO_WILDCARD` (missing star) is not naively pre-checkable**: under *parallel iteration* (joined repeatable groups via same-name/type index fields) plain references to another repeatable group are legal — the pre-check waits for slice 7e's iteration model.
- **Wildcard propagation down nested repeatables (§10, 2026-06-06):** when a path flattens an outer repeatable with `*`, **every repeatable group below it on the path must also be starred**. Verified on the nested-repeatable `project` fixture (Milestones ▸ Tasks): `Sum(Milestones*/Tasks/Effort)` (outer `*`, plain inner) → **`MVK_NO_WILDCARD`**; `Sum(Milestones*/Tasks*/Effort)` accepted; and a single `*` over the outer repeatable's own field (`Sum(Milestones*/Budget)`) is fine.
- **Keyword-named fields need single-quoting in a path (§10):** a field literally named like a language keyword (the `project` fixture has one named `Date`) is rejected unquoted — `FieldFilled(Date)` → **`MVK_UNEXPECTED_TOKEN`** — and accepted single-quoted: `FieldFilled('Date')`.
- **Relative `..` + `*`: the star may not be on a `..` part (§10).** The kernel message is precise — *"In a relative path containing `..`-notation, the `..` parts may not use the `*` symbol."* So `../Items*/Count` (star on a *named* segment) is fine, but **starring the `..` itself** — `Sum(..*/Budget)` from an inner rule, to reach all repetitions of an ancestor repeatable — is rejected with **`MVK_INVALID_WILDCARD_REL`**; use the absolute form (`/Project/Milestones*/Budget`). (This is why my earlier shapes, with `*` on named segments, all passed.)
- **`fieldRefByShortNameAllowed` does not gate short-name at the consistency tier (§10).** Setting it to `false` did **not** make a bare short-name reference (`[Quantity]`) reject under `checkConsistency` — short names resolve regardless here, so that flag's enforcement lives elsewhere (editor/UI or another pass), not in rule consistency. A fact, not a reject law. *(Locked: `validate.laws.PathLawsTest`; fixture `models/project.dm.json` — the first committed model with nested repeatable groups + a keyword-named field.)*
- **The kernel ships a reference-rewriting engine for rename/move — `MoveSupportDM` (§10, 2026-06-12).** `MoveSupportDM.changePathReferencesForMove(documentModel, Map<oldPath,newPath>)` (internal, `@OnlyForUsage`, `kernel-md-model/a12internal/services`) rewrites every reference to the moved paths — rule conditions, error texts, computations (preconditions/operations/common precondition), the error/computed-field refs, **and a group's index-field and sort-field relative references** — preserving absolute-vs-relative style. (The index/sort-field rewrite is a no-op when a non-repeatable group is merely re-parented — the relative path to its own child is unchanged — but it matters for a repeatable group; the kernel handles it from the same `entityMoves` map either way, one more reason to rewrite references through this engine rather than by hand on the JSON.) It does **not** move the element itself — the caller does that afterward, confirmed by the method's own javadoc (*"the rules and computations themselves are NOT moved … Moving … must be done by the caller afterward"*); rulekit's `ModelDocument.moveField/moveGroup` is that caller-side relocation, kept in our authored-JSON surgery so source fidelity (comments/ordering) survives. **Starred-group references DO follow a group rename:** `Sum(Items* / Amount)` becomes `Sum(Lines* / Amount)` when `/Order/Items` → `/Order/Lines`, via dedicated `starredGroupsNewFullnames` handling — so `MoveSupportInternal`'s blanket javadoc limitation #6 ("References with * are not touched") is **misleading** for the group-rename case (narrower `*` edge cases may still not rewrite; the kernel re-validate is the backstop). rulekit wraps this at the N8 boundary as `adapter.ReferenceRewriter`; it is the engine that turns *refuse-if-referenced* rename into a *reference-preserving* rename/move (FEATURE-GAPS). *(Locked: `adapter.ReferenceRewriteTest`.)*
- **`getDirectlyReferencedEntities` is the canonical "what does this rule reference" set — operands included, not just the error-attached field (§9/§10).** The kernel's `getDirectlyReferencedEntities(IRule, IProblemReporter)` returns **every** field/group a rule's condition reads (the operands), and for a calculation rule it spans all four sites: the computed field, the common precondition, each alternative's precondition, **and each operation expression** — so a field read *only* inside a computation's operation is in the set even though a plain rule scan would miss it. This one primitive is the shared oracle for all three reference queries, which is why they can never disagree: **`where-used`** is its inverse (`whereUsed` over validation rules + `whereUsedInComputations` over calculations — kept as separate kinds because a calculation is also an `IRule` in `getAllRules()`), **`rule explain`/`computation explain`'s `references`** is its forward projection, and the **safe-delete cascade** is its membership test. ## §9 supplement — `CurrentRepetition` + the index-field/semantic-index cluster (slices 7e/7f, 2026-06-04 experiments; retitled 2026-06-10 — the constant-form semantic index IS supported, only the entity/`$` forms stay kernel-delegated)

`CurrentRepetition` (DE `AktuelleWiederholung`; grammar `groupOp: 'AktuelleWiederholung' '(' entitySpec ')'`) is a **numeric expression** — the current iteration index of a group.

- **Takes a group, not a field** — a field argument → **`MVK_NO_FIELDS_ALLOWED`** ("Only groups or root groups are allowed"). Structural: `Dsl.currentRepetition(GroupRef)`.
- **The rule must iterate over that group** — from a non-iterating rule it draws **`MVK_NO_WILDCARD`** ("Missing specification of an asterisk"). Position-dependent → kernel-delegated (like the RNU position law).
- **A non-repeatable group is tolerated** (its index is constant) — `CurrentRepetition(/Subscription/Billing)` from an iterating rule validates.

**No positional repetition operator — a row is addressed by semantic *key*, never by index (grammar-verified, 2026-06-16).** The grammar exposes exactly one `groupOp` (`groupOpName: 'AktuelleWiederholung'`) and one way to address a specific row — the `Fuer`/`For` **semantic index** (`entitySpec: … ('Fuer' semanticIndex)`, with `semanticIndex: entitySpec | StringLiteral`). So `CurrentRepetition` *yields* a row's index as a **number** (compare it, self-exclude via the `$` correlation), but you **cannot use a number to *select* a row**: there is no `[Field At n]`, no "current + 1" neighbour, no positional offset. `[Field For "key"]` keys on the index *field's value* (a string constant or another entity), not on a repetition position. Consequence for rulekit: a `date.atRepetition(n)`-style positional API is a non-starter — it would invent syntax the kernel lacks; the only repetition-indexed *date* read that could ever ship is the semantic-index `For` form, mirroring `NumberRef.forIndex`. ## §9 supplement — the `Having` filter and `$` correlation (slice 7d, 2026-06-04 experiments)

`Having` (DE `Mit`; grammar: `'Mit' bedingung` on an `entitySpec`) filters a `*`-repetition list before an aggregate/quantifier consumes it; `$` (`DOLLAR`, language-independent) pins a reference to the rule's outer repetition inside a filter.

- **`Having` requires a starred (flattened) field** — on a plain reference it draws **`MVK_WILDCARDS_REQUIRED`** ("At least one asterisk needs to be specified for the filtered field"). So it lives on `FieldListRef`, not on plain `FieldRef`.
- **It attaches in any list slot** — verified inside `Sum`/aggregates *and* the field-list quantifiers (`AtLeastOneFieldFilled(… Having …)`).
- **Filter-condition exclusions** → **`MVK_DISALLOWED_CONSTRUCT_IN_FILTER_CONDITION`** ("The language feature 'X' is not supported for filter conditions"): verified for `RepetitionNotUnique` and a **nested `Having`**; KERNEL-SEMANTICS §9 also lists `CustomCondition`, a semantic index, and a parallel iteration. rulekit pre-checks the two representable ones (RNU + nested Having); the rest stay kernel-delegated.
- **`$` is filter-only** — outside a filter it draws **`MVK_INVALID_OUTER_ITERATION`** ("The symbol '$' to specify rule iteration is only allowed inside filter conditions"). A valid use correlates inner to outer: `Sum(/S/Addons*/MonthlyFee Having [/S/Addons/Name] == [$/S/Addons/Name]) > 0`. (`$` on the *filtered* side without a non-`$` inner ref → `MVK_NO_ITERATION_FOR_WILDCARD` — the filter must reference a field in a starred level.)
- **Why `$` exists — `MVK_INVALID_ITERATION_IN_FILTER_CONDITION`** (from the kernel-team BA doc `a12-kernel/documentation/_merged/kernel-ba.md`, cross-checked 2026-06-07). Inside a filter you may only iterate over the repetition levels the **filtered field** stars; a reference to a field that iterates over a *different* group is rejected — `Sum(K*/G Having [K/F1] == [L/F2])` errors because `L/F2` iterates over the un-starred group `L`. The **only** fix is the `$`: `[$L/F2]` pins that reference to the outer iteration. So `$` is not optional sugar — it is the sole way a filter references an out-of-scope (outer) field. **Path notation is unrestricted** (any path valid without `$` is valid with it: `$/A/F`, `$L/F`, `$F`).
- **`$` correlation is implemented (2026-06-07, both directions) — was "deferred", now landed.** The marker is an `outer` flag on the AST value nodes (`FieldValue`/`EnumCategoryAccess`/`CurrentRepetition`), set by `.outer()` on the handles, rendered as `[$path]`/`($group)`. It threads through every field-vs-field comparison kind (number/string/date/enum/category), `CurrentRepetition($group)`, **presence predicates** (`NoFieldFilled($a, $b)` via `FieldRef.outer`), **value-list operands** (`FieldListRef.outer`), and filtered field-list quantifiers (`AtLeastOneFieldFilled(… Having …)`) — **every `$` position in Corpus-1 converts (0 `$` opaques)**. **Runtime-verified, not just structural:** the correlation fires on the rows that share an outer-row value and nowhere when distinct; the `CurrentRepetition(G) != CurrentRepetition($G)` self-exclusion is load-bearing (without it every row matches itself); and combined with `CurrentRepetition(G) < CurrentRepetition($G)` it expresses "all predecessors" — the kernel BA doc's reviewed "holidays not in chronological order" example, transferred to a schedule domain. Corpus-1 read reached 95.0% on the back of this.

*(Locked: N7 `Having` valid + `MVK_DISALLOWED_CONSTRUCT_IN_FILTER_CONDITION` invalid + `FieldListRef.having` pre-checks — `dsl.operators.IterationConditionTest`. `$` authoring kernel-valid — `adapter.OuterCorrelationAuthoringTest`; read round-trips — `adapter.OuterCorrelationReadTest`/`OuterCorrelationQuantifierReadTest`; the N8 count-check that keeps an un-threaded construct Opaque — `adapter.OuterCorrelationBackstopTest`; the **runtime behavior** — `adapter.laws.CorrelationLawsTest`. `Having`'s starred-field law stays structural (only `FieldListRef` offers it).)*

## §9 supplement — aggregate uncertainty + `FirstFilledValue` prefix sensitivity (runtime, 2026-06-10, RT-semantics drain)

## §9 supplement — `RepetitionNotUnique` slot laws (slice 7b, 2026-06-04 experiments)

## §11 supplement — computation alternatives and the calculated-field ban

- **Alternatives are all-or-nothing about preconditions**: either a single alternative *without* a precondition, or several that *all* carry one — mixing a precondition-less "otherwise" in is rejected with **`MVK_ERROR_EMPTY_PRECONDITION`**. The default branch must be an explicit complementary precondition (as the demo's `BonusComp` does with `[WeekPay] < 500`).
- The computed field may not be referenced in preconditions **nor in operations** — both directions draw the same **`MVK_ERROR_REFERENCE_TO_CALCULATED_FIELD`** (KERNEL-SEMANTICS §11 states the precondition half). **The ban is on a *direct field* reference, not the field's containing group** (BA-doc cross-check, 2026-06-08): guarding a *repeatable* computed field with `GroupFilled`/`CurrentRepetition` on its **containing group** is kernel-legal — it's exactly the BA doc's current-repetition pattern (`CurrentRepetition(RuleGroup) == 1 → "…"` where the computed field lives in `RuleGroup`). rulekit's pre-check therefore uses **exact field-match** (`ConditionReferences.referencesField`), not the group-prefix `covers()` it uses for the rule error-field check — the earlier `covers()` over-rejected this valid shape.
- A wrong-kind operation (string expression into a number computed field) is **`MVK_INVALID_COMPARE_TO_ENUM_OR_STRING`**.
- Computations require error text like rules do (`MVK_ERROR_MESSAGE_MISSING`).
- **Runtime evaluation (RT-semantics drain, 2026-06-10):** with **overlapping preconditions, the first declared alternative wins** (declaration order is the tie-break; the computed value is scale-normalized — `1.00` lands as `"1"`). **Division by zero computes nothing** — no value, no error outcome — and **clears** a stale previously computed value, so an invalid input never leaves a wrong value standing (the computation-side face of §5's "evaluates quietly"). Consistency-tier corollary: a bare **division has unknown scale** and cannot assign to a scaled computed field (`MVK_INVALID_COMPARE_DEC_PLACES`, rhs "?") — wrap it in an explicit rounding (`RoundAccounting(expr, n)`) to fix the scale. *(Locked: `adapter.laws.ComputationEvaluationLawsTest`.)*

## §11/§12 supplement — every computation is ALSO a validation rule (runtime, 2026-06-17)

The kernel auto-generates, per computation, an **implicit validation rule** `FieldFilled(F) And [F] != <term>` — so `validateFull` fires when a document's **stored** computed value disagrees with what the computation would produce. Probed deterministically with `CoverageWindow = DateRange(OrderDate, DeliveryDate)`: a stored `CoverageWindow` differing from the computed range fires; an agreeing one does not. **The fired errorCode is the computation's own name** (`CoverageWindowComp`). This is the mechanism behind the BA's two "Computation Rules as Validation Rules" self-fire traps: computing **`Now` into a field** self-fires (time elapses between the compute and validate steps), and **copying a precise date into a coarser date field** self-fires (the fragment's missing day/month read as `01`, so `[F] != [G]`). Authoring guidance: don't compute `Now` into a field; rebuild a coarse date with `Date("1","1",YearFromDate(G))` rather than copying it. *(Locked: `adapter.laws.ComputationValidationLawsTest`; the `Now`/precise-coarse cases are BA-described instances of the locked general mechanism.)*

## §12 supplement — every fired message is typed value-vs-omission (runtime, 2026-06-10, RT-semantics drain)

A dimension KERNEL-SEMANTICS doesn't cover (it presents the logic as two-valued): every message `validateFull` raises carries a **`MessageType`** — `OMISSION_ERROR` when the rule could be satisfied by *filling* one or more additional fields, `VALUE_ERROR` when only changing a value can satisfy it. Public surface: `IMessage.getMessageType()` (kernel-md-runtime-api). Internally this is the three-state `ValidierungsErgebnis` (`TRUE_WF` / `TRUE_AF` / `FALSE_OR_UNKNOWN`) with a combination algebra:

| combination | result | intuition |
|---|---|---|
| comparison over filled values | `VALUE_ERROR` | only changing the value helps |
| comparison fired on an empty-field substitution (number→0, confirm→False) | `OMISSION_ERROR` | filling the field could flip it |
| presence predicate (`FieldNotFilled`, …) | `OMISSION_ERROR` | filling satisfies it by definition |
| `And` of a value branch and an omission branch | `OMISSION_ERROR` | **omission wins** — filling could still rescue the whole rule |
| `Or` of a value branch and an omission branch | `VALUE_ERROR` | **value wins** — the value branch alone convicts |

*(Locked: `adapter.laws.ErrorTypeLawsTest`; the aggregate corollary — the omitted-tail typing — in `AggregateUncertaintyLawsTest`, §9 supplement above. Source: `ValidierungsErgebnis.combineUND/combineODER`, `BedingungsOperatorHelper.vergleiche`.)*

## The pre-`checkConsistency` tiers — the write path's output contract (instrument 4, 2026-06-04)

Two structural gates fire *outside* `checkConsistency`, found while scoping the F6 DM-JSON write path:

- **Deserialize tier (Jackson binding).** `serializer.deserialize(reader)` is a Jackson read — malformed JSON, an unknown `"type"` discriminator, an unparseable number/enum, and the **locale-format check** (`en_us` → "Invalid locale format", before any consistency pass) fail here as `IOException`/binding errors, *not* `MVK_*` codes. Not enum-enumerable; documented, not locked.
- **Convert tier (model assembly, found 2026-06-10 while locking the rule-slot laws).** Building the validation model rejects **two same-named sibling elements in one group** with a plain `IllegalArgumentException` ("Cannot have two child elements with the same name …") — *before* `checkConsistency`, so the `MVK_NAME_RULES_DUPLICATE` metamodel rule is shadowed by this tier for the same-group case. *(Locked: `validate.laws.RuleSlotLawsTest`.)*
- **Serialize/write gate — `BasicConsistencyCheck`.** `serialize(model, writer, …)` runs `BasicConsistencyCheck.checkModel` first and **aborts the write on any ERROR** — so this, not `checkConsistency`, is what an F6 `writeTo` must satisfy. ## `formatConditionText` is lossy for a `$` correlation (2026-06-06)

## The condition formatter knows exactly two languages — `Locale.US` / `Locale.GERMANY`; anything else silently falls back to German (2026-06-13)

The kernel's keyword-language switch for conditions (`formatAndTranslateConditionText(IRule, Locale, IProblemReporter)`, behind rulekit's `canonicalConditionText(rule, ConditionLanguage)`) resolves the target language through `AbstractMultiLanguageHandler`, whose **supported set is exactly two specific locales**:

```java
public static Set<Locale> SUPPORTED_CONDITION_LANGUAGES = Set.of(Locale.GERMANY, Locale.US);   // de_DE, en_US
// constructor: this.languageUsedInConditionText = SUPPORTED.contains(lang) ? lang : Locale.GERMANY;
```

So the language is keyed by **country**, not just language: `Locale.US` (en_US) → English keywords (`And`/`Or`/`If`); `Locale.GERMANY` (de_DE) → German (`Und`/`Oder`/`Wenn`). **Any other locale — including bare `Locale.ENGLISH` ("en") and `Locale.GERMAN` ("de") — is not in the set and silently defaults to `Locale.GERMANY`** (German), with no error and no diagnostic. Passing `Locale.ENGLISH` to translate an English model therefore returns *German* — the trap that surfaced this. (Source: `kernel-core-parser` `AbstractMultiLanguageHandler`/`ConditionMultiLanguageHandler`; the German branch is literally `Locale.GERMANY.equals(languageUsedInConditionText)`.)

*Consequence for rulekit:* the adapter's translate seam takes rulekit's **`ConditionLanguage`** (EN/DE), not a raw `Locale`, and maps `EN → Locale.US` / `DE → Locale.GERMANY` internally — the silent-German footgun is made unrepresentable at the N8 boundary. *(Locked: `adapter.KernelAdapterFormatTest` — EN must yield English keywords, DE German; a kernel change to the supported-locale set would surface as a German fallback the EN assertion catches.)*

## A model's condition language is independent of its display locale — and English is the convention (2026-06-20)

The model header carries **two distinct, unrelated** language settings — conflating them is a trap:

| setting | where | governs |
|---|---|---|
| **display locale(s)** | header `locales[]` | labels + messages — a rule must carry a message for every declared locale (§13) |
| **condition language** | `modelConfig.conditionLanguage.code` | the keyword language the kernel **parses and stores** *all* DSL in — rule conditions, computation **operations**, and **preconditions** (`precondition`/`commonPrecondition`) alike: `FieldFilled`/`And` (en_US) vs `FeldAngegeben`/`Und` (de_DE); one of the two `SUPPORTED_CONDITION_LANGUAGES` (§above) |

Verified (experiment + the **a12-kernel-mm** corpus):

- **The kernel parses a candidate condition in the model's `conditionLanguage`** — a keyword in the *other* language is rejected `MVK_UNEXPECTED_TOKEN` ("Unexpected found 'FieldFilled'"). (Already noted, "model condition-language gates parsing", §CustomCondition.)
- **`conditionLanguage` need NOT be a declared display locale.** A model declaring only `de_DE` with `conditionLanguage=en_US` and English-keyword conditions is kernel-valid (`checkConsistency` passes — confirmed by a hand-flip experiment and `DocumentModelDraftTest`). The condition language is a free choice between the two supported, not constrained to `locales[]`.
- **English is the corpus convention.** All 59 a12-kernel-mm models — which declare `de_DE` as their *first* display locale — set `conditionLanguage=en_US` and author English-keyword rules (`FieldFilled`/`And`/`PatternViolated`/`RepetitionNotUnique`). German-keyword conditions are the rare, explicit case.

*Consequence for rulekit:* a from-scratch model defaults `conditionLanguage` to **en_US regardless of the display locale** (it used to derive it from the first display locale — breaking English conditions on a `de_DE` model; surfaced by probe `01-de`). Treatment + the single-source guard in [`KERNEL-INTEGRATION-NOTES.md`](KERNEL-INTEGRATION-NOTES.md). *(Locked: `DocumentModelDraftTest.conditionLanguageDefaultsToEnglishRegardlessOfDisplayLocale` — a de_DE draft keeps en_US and the kernel accepts it; `ModelNewVerbTest.aGermanLocaleModelStillAcceptsEnglishDslKeywords` — English DSL validates end-to-end on a de_DE model; `ModelNewVerbTest.aGermanLocaleModelAlsoAcceptsEnglishKeywordComputationsAndPreconditions` — the sibling lock proving the model-level fix covers computation operations + preconditions, not just rule conditions.)*

## A mount group's local elements SHADOW the include — the kernel does not expand it, and stays valid (2026-06-20)

A group that mounts an include carries `Group.modelAlias`. If that same group **also** has its own `Group.elements`, the kernel uses the **local elements** and does **not** expand the include — and the model is still **kernel-valid** (no error, no warning). Experiment (`field add` into a mount group): a mount of `address` resolving `/Person/Addr/{Street,City}`, after adding a local `Extra`, resolves **only** `/Person/Addr/Extra` — `Street`/`City` silently gone — and `model check` returns `valid:true`. So local content on a mount is a *silent override*, not an extension.

*Consequence for rulekit:* a routine `field add`/`group add` whose target group is a mount used to write a local element and report `applied`, silently discarding the entire mounted include. rulekit now **refuses** an element-add into a mount group (`RK_MOUNT_NOT_EDITABLE`) — see KERNEL-INTEGRATION-NOTES; the kernel's silent-override behavior itself is the finding here. *(Surfaced by probe `01-de`; locked by `MountEditRefusalTest`.)*

## An include's locales must be a superset of the base's — not the reverse (2026-06-13)

The kernel's include locale-compatibility rule, pinned by experiment, runs in the direction that's easy to get backwards: **the included model must declare a superset of the base model's locales** — it must *cover* every locale the base declares. Extra locales in the include are harmless.

- base `{en_US}` includes `{en_US, de_DE}` → **loads** (the include over-covers; the extra `de_DE` is ignored).
- base `{en_US, de_DE}` includes `{en_US}` → **rejected on expand** (the include can't cover `de_DE`).

So a one-line "locale superset" note is ambiguous about direction; the constraint is *include ⊇ base*, enforced by the kernel on expand (not at the modelkit build tier). *(Locked: `modelkit.IncludeConstraintsTest`.)* Cycles and the single-root rule are likewise the kernel's to enforce on expand — modelkit doesn't re-implement them.

## A group's index field auto-generates its uniqueness + mandatory rules (2026-06-13)

Declaring a repeatable group's **index field** (`indexFieldName`) is all the authoring needed — the kernel **auto-generates** two validation rules for it (no rule a model has to carry), per the kernel-team BA doc (§"Index Fields"):

- **unique within each iteration**: `RepetitionNotUnique(indexField)`;
- **mandatory when the group is filled**: `GroupFilled(group) And FieldNotFilled(indexField)`.

Confirmed empirically against the runtime: two repeatable rows sharing an index value fire where distinct values don't, and a filled row with an empty index value fires too. Consequence for rulekit: modelkit's `indexField(name)` only emits `indexFieldName` — it must **not** also emit the pair (the kernel would double them). *(Locked: `adapter.laws.IndexFieldLawsTest` — differential, so it doesn't depend on the generated rules' kernel-internal error codes.)*

## The DM-JSON deserializer ignores unknown field-config keys — a round-trip must read the value *back* (2026-06-13)

The kernel's DM-JSON `JsonMapper` is annotated **`@JsonIgnoreProperties(ignoreUnknown = true)`** (`kernel-md-serializer`). So a misspelled or unsupported field-type key (e.g. `maxFractionDigits` for the real `maxFractionalDigits`, or a guessed `unit`) is **silently dropped** — the model still loads and validates clean, but the slot has *no effect*. ## The number `trait`/unit slot is a clean lowercase field attribute — `AmountWithCent` is a *separate* derived category (2026-06-13, corrects an earlier deferral)

A number field's **unit** is the DM-JSON `trait` slot, whose allowed values are the **lowercase** tokens **`amount` / `percent` / `permille`** — the authoritative client contract (`kernel-md-facade` `api.ts`: *"allowed values are: 'amount' | 'percent' | 'permille'"*). It round-trips cleanly: emit `trait`, read it back via `INumberType.getTrait()` (`Optional<String>`); the runtime treats `amount` specially via `getTrait().equals("amount")` (`TypeConverter`).

This **corrects an earlier (same-day) deferral** that called the trait "inconsistent across tiers." The confusion was conflating two distinct things:

- the field's own **`trait`** slot — lowercase `amount`/`percent`/`permille`, what we model;
- the metamodel's **`AmountWithCent` / `AmountWithoutCent`** enum (in `CT_FIELD_TYPE_ATTRIBUTES` / `MM_SMM_FieldTypeChecks`, with **no** kernel-java references) — a **derived** category used only in *cross-field* type-compatibility checks (source-vs-target decimal places in a copy/computation), not a competing representation of the field's own trait.

So there is no inconsistency for the slot itself; modeling it is just `trait:"amount|percent|permille"`. The 0-or-2-decimal "with/without cent" distinction is the kernel's *derived cross-field* concern, not a field-level constraint we pre-check. *(Locked: `modelkit.FieldConfigExtrasTest.numberUnitTraitRoundTripsThroughTheKernel`.)* Modeled via `NumberFieldBuilder.unit(NumberTrait)`.

## `modelConfig.supportedCharacters` is enforced at runtime, not just authored — out-of-set values raise `ZeichenNichtImZeichensatz` (2026-06-13)

The model-config **allowed-character set** (`content.modelConfig.supportedCharacters`, a `List<String>` where each entry is a single character or a range like `" -~"` = space-through-tilde; empty = all of Unicode-Plane-0 — `IDocumentModelConfig.getSupportedCharacters()`) is a **real runtime constraint**, not codegen-only metadata. The interpreted `IDocumentRtService.validateFull` checks string/enum/custom field **values** character-wise: a value carrying any character outside the set raises the formal error **`ZeichenNichtImZeichensatz`** ("character not in the character set" — a German-named code, not `MVK_*`-prefixed); a value drawn wholly from the set is clean. ## An include mount can exclude the included model's rules/computations — `excludeRules`/`excludeComputations`, applied at expand (2026-06-13)

A mount group (one carrying `modelAlias`) may set the booleans **`excludeRules`** and **`excludeComputations`** in its `Group` body, beside `modelAlias`. They are honored at **expand**: with `excludeRules: true`, the kernel does **not** carry the included model's own rules into the expanded model (its *fields* still mount — only the rules are dropped); `excludeComputations` does the same for computations. Empirically confirmed: a price-list model with rule `LIST_PRICE_NEG`, mounted plainly, has that code in the expanded model; mounted with `excludeRules`, it does not, while the mounted `ListPrice` field remains.

The kernel ties the flag to a mount — metamodel rule **`EXCLUDE_RULES_INVALID`** (`MM_Group_1`): `FieldFilled(excludeRules) And FieldNotFilled(modelAlias)` is an error ("excludeRules filled and modelAlias not filled"), with a twin `EXCLUDE_COMPUTATIONS_INVALID`. So the slot is meaningful only where there's a `modelAlias`; our API only emits it on a mount, so that refusal is structurally unreachable from rulekit. *(Locked: `edit.IncludeExcludeRulesTest` — plain mount keeps the rule, `excludeRules` drops it but keeps the fields, via the kernel's own expand.)* Modeled via `MountOptions.single().excludingRules()` → `ModelDocument.mount(...)` / `IncludeEditor.mount(...)` / CLI `include add --exclude-rules`.

## A type-def-only model is just a root-less `document` model; a consumer imports it with `purpose: "typeDefinitions"` (2026-06-13)

There is **no separate model discriminator** for a type-definition library. A "type-def-only" model is a normal `modelType: "document"` model that carries `content.typeDefinitions` and **no root groups** — the kernel accepts it standalone (empirically: a model with an empty `modelRoot.rootGroups`, *and* one with no `modelRoot` at all, both load + `checkConsistency`-pass). So authoring one is just emitting type-defs with an empty root.

A consumer pulls those types in via a header `modelReferences` entry whose **`purpose` is `"typeDefinitions"`** — the kernel constant **`PURPOSE_4_ONLY_TYPE_DEFS = "typeDefinitions"`** (`DocumentModelExpandSanityChecks`), **not** `"import"`. At expand, `DocumentModelExpandImportService` walks the referenced model and merges **all** its type-defs into the consumer's namespace **by id** (`addUniqueTypeDef` / `getImportedTypeDefsById`) — so a consuming field references an imported type by a **plain `typeDefinitionId`** (no alias prefix; the entry's `alias` is just a label). This differs from an `include` (`purpose: "include"`, which mounts *structure* under a group via `modelAlias`). The kernel checks `purpose == "typeDefinitions"` before expanding an import (`checkTypeDefPurpose`) and that the imported model's locales cover the consumer's.

## Attachment & Multi-Select are `usageType` group templates with kernel-validated canonical compositions (2026-06-13, source-verified)

|---|---|---|

## How `checkConsistency` actually works — structural laws ARE metamodel rules (2026-06-04)

## Rule-condition polarity is fixed — `errorCondition` fires on TRUE, no configuration (2026-06-05 investigation)

A validation rule's condition has **one fixed polarity**: the sole condition slot is `errorCondition`, and the rule fires (= the document is invalid for the error field) exactly when the condition evaluates **TRUE**. So a *requirement* must be authored as its *violation* — to require "X is filled", the `errorCondition` is "X is **not** filled". Confirmed configurable in **no** way:

- **No per-rule polarity slot.** The Rule's slots (MM_Common metamodel + public `IRule` + serializer) are exactly `errorEntity`/`errorCode`/`errorCondition`/`severity`/`errorMessage`/`guiPatterns`/`variantFilter`/`variantErrorMessages` — none flips condition-true between error/ok. `severity` (INFO/WARNING/ERROR) is UI classification only ("does not play any role in the validation language"). The `customRefErrorEntities` pairs only refine *which* entities are blamed, not polarity.
- **No alternate condition form.** There is no `validCondition`/`assertion`/`requirement`/`applicabilityCondition`. `precondition` exists **only on computations** (gates which alternative runs), not on rules — a rule folds any applicability guard into the single `errorCondition` (e.g. `GroupFilled(K) And …`).
- **No model/rule config** reinterprets the condition.
- **No generic `Not` operator** (only `And`/`Or`). Instead the language ships **matched positive/negative predicate pairs** (`FieldFilled`/`FieldNotFilled`, `AllFieldsFilled`/`NoFieldFilled`, `AtLeastOneFieldFilled`/`NotExactlyOneFieldFilled`, `FieldsNotCollectivelyFilled`, …) so the author names the violation directly by predicate choice.

**Consequence (the silent trap):** writing the requirement *positively* (e.g. `FieldFilled(X)` as the errorCondition) is structurally valid and the kernel accepts it — but it encodes the **opposite** rule (fires when X *is* filled). The kernel cannot catch this (both polarities are valid conditions). rulekit's job: teach negation (skill) and flag likely inversion (`RK_INVERTED_REQUIREDNESS` lint — AST-based, so it needs a structured/read rule, not raw condition text). Source: `a12-kernel/documentation/ba/validation_language_guide_en.adoc` (§"A Rule always describes the error condition"; "no generic negation operator"; severity is UI-only); `IRule` (md `getErrorCondition`; tool `getErrorConditionText`); `RuleSerializer` slot set; `MM_Common_v2` Rules group; `IComputation.getPrecondition` (computation-only).

## `checkConsistency` runs runtime code generation — the AOT / native-image constraint (2026-06-05 investigation)

**Why this matters.** The standalone CLI (PROJECT-DESIGN N10, [`CLI-SPEC.md`](CLI-SPEC.md)) is a candidate for **GraalVM native-image** packaging (a tiny, instant-start single binary for the modeller/BA). native-image does **closed-world** AOT: anything that *parses/compiles/defines classes at runtime* is hostile to it. So whether the kernel does runtime codegen — and on which paths — decides whether native-image is possible at all. It also bounds any future AOT/offline scenario and is a third reason a TypeScript twin can't validate (kernel codegen is JVM-only).

**The discovery.** A native-image build of the CLI (which only does `deserialize → expand → checkConsistency`) builds clean but **fails at runtime**: `Error while instantiating template "templates/common/groovy/base/StringParameter"`. The JVM build never fails. That signature = runtime template machinery the closed world couldn't satisfy.

**Root cause — `checkConsistency` generates validation code as a side effect.** It is a *registered consistency rule*, `CodeGenerationRule`, that calls `generateValidationCode(model, new GroovyCodeGeneratorConfig(...), …)` — so **every `checkConsistency` runs full validation-code generation** (this is also the §"structural laws ARE metamodel rules" mechanism above, seen from the codegen side). Two corrections to earlier assumptions fell out:

- **The engine is ANTLR StringTemplate v4, not Groovy's template engine.** The `groovy` in the path is the *target language of the emitted source*, not the engine. The kernel renders source with `org.stringtemplate.v4.{ST,STGroup,STGroupFile}` (kernel `StringTemplateUtil`/`STParameterClassBase`; the error string is thrown by `StringTemplateUtil.getTemplate`). `StringParameter.st` is trivial — `StringParameter(t) ::= << "<t.value>" >>` — emitted for **every field's string-valued metadata** (name, labels, required-error text), so *any* model with ≥1 field triggers it.
- **It is NOT model-content-dependent.** The initial symptom (held-out `catalog` failed, traced models "passed") was an artifact of only testing `catalog` on the native binary. Re-tested: the native binary fails on **all** models (subscription/order/logistics/catalog) at the same template. (`storefront` fails earlier on an unrelated missing-resolver issue.)

**Experimental verification** (probes, JVM, `-verbose:class`; reproducible scripts under the gitignored `build/native-spike/`):

- **The trigger is `checkConsistency`, not `expand`.** A probe doing `expand` only loads ~7 engine-ish classes; `expand + checkConsistency` loads **497** — the entire StringTemplate v4 compiler pipeline (`STParser`, `STLexer`, `GroupParser`, `CodeGenerator`, `Compiler`, `CompiledST`) plus kernel `StringTemplateUtil`/`StringTemplateGroup`. So model *consistency checking* is where runtime codegen happens.
- **`checkConsistency` does NOT reach Groovy compilation.** No `groovy.lang.GroovyClassLoader`/`GroovyShell`, no `org.codehaus.groovy.control.*`, no runtime-defined classes (the `__JVM_LookupDefineClass__` entries are all JDK `LambdaForm`s). The only "groovy" class is `GroovyCodeGeneratorConfig` (a config object naming the target language). **`checkConsistency` emits Groovy *source* via StringTemplate and discards it — it never compiles it.** *(This corrects the `KERNEL-INTEGRATION-NOTES` "no code emitted, no compile" claim: code IS emitted via StringTemplate; only the Groovy compile step is absent here.)*

**The native-image verdict — feasible for the checkConsistency/parse path, with care.** StringTemplate v4 compiles templates to its *own interpreted form*, not JVM bytecode, so it is **native-compatible once its resources are bundled**. The failure was a **missing resource**: `base.stg` does `import "baseDir"`, loading `baseDir/*.st` (e.g. `StringParameter.st`) *by name*; the tracing agent records the `.stg` group files but **misses the import-indirected `.st` files**, so they weren't in the image. Rebuilding with `-H:IncludeResources='internal/templates/.*'` (+ `.*\.st`/`.*\.stg`) **fixed it**: the native binary then **passed on all four self-contained models, output byte-identical to the JVM**, **~37 ms startup** (vs ~600 ms JVM, ~16×), 36 MB. So native-image is viable for rulekit's verbs (all of which are `checkConsistency`/parse-based).

**The remaining hard ceiling — Groovy runtime compilation on the validation-*execution* path.** Actually *running* a model's validators against a document (the kernel's `getValidator()`/on-the-fly testing) compiles the emitted Groovy source at runtime via `GroovyClassLoader.parseClass` (`ModelGroovyCode`) / `GroovyShell` (`OnTheFlyTestingValidatorGenerator`) — genuine runtime JVM class generation, which native-image **cannot** do and resources can't fix. rulekit's CLI never executes validation (it authors/validates *model structure*, the kernel is the runtime), so this isn't a blocker — but it is a permanent boundary: **a native rulekit must never depend on the kernel's runtime validation execution.**

**Breadth / future risk.**
- Runtime codegen in the kernel is exactly two mechanisms, both reachable from the public model-service path: **(1) StringTemplate v4** (resource-fixable; reached by *every* `checkConsistency`) and **(2) Groovy runtime compilation** (not fixable; only on validation execution). No direct ASM/Javassist/CGLIB/`javax.tools` use exists elsewhere in the kernel/base/utils sources.
- **Tracing-agent metadata is not sufficient by itself** for this kernel: import-indirected StringTemplate resources are missed, so a native build needs *broad* resource inclusion (`internal/templates/**`) plus the closed-world discipline of testing **held-out** models (the agent-only build gave a false "works" on traced models and a false "categorically broken" on the held-out one — only the resource-bundling probe got it right).
- **Performance footnote:** `checkConsistency` pays the StringTemplate parse/compile cost per process (497 classes, the ST compiler) — relevant to CLI startup and the resident-mode trade-off.

**Source anchors** (kernel-internal, consult-only — from the `a12-kernel` checkout): `StringTemplateUtil.getTemplate` (the error string) + `getActCodeGroup` (`STGroupFile`); `STParameterClassBase` / `StringParameter` (`@StringTemplateGroup("/common/$programmingLanguage$/base")`); `CodeGenerationRule.checkModel` → `ExternalDocumentModelService.generateValidationCode` (the trigger); `ModelGroovyCode` (`GroovyClassLoader.parseClass`) and `OnTheFlyTestingValidatorGenerator` (`GroovyShell`) for the execution-only Groovy wall. Templates ship in `kernel-core-codegen-base` under `internal/templates/{common,validation}/{groovy,java,…}/`.

## Parsetree construct-name enums — the kernel's machine-readable operator inventory (N3 reverse anchor, 2026-06-04)

The package `…core.parsetree.a12internal.api.types` holds ~18 construct-name enums (`kernel-core-parsetree-api`) — the kernel's own operator inventory, the second N3 parity anchor. Discovered by reflecting over each (`adapter.KernelConstructParityTest`):

- **`getRuntimeName()` returns the German keyword; the enum constant's `name()` is the English/canonical construct name.** E.g. `EntityListConditionName.AllFieldsFilled.getRuntimeName()` → `AlleFelderAngegeben`. So `name()` ≈ catalog `keywords.en`, `getRuntimeName()` ≈ catalog `keywords.de` — the matching keys for the reverse-parity test.
- **Not all enums have `getRuntimeName()`.** The symbolic families don't: `ComparisonOperation` (`GT/NE/LT/EQ/GE/LE`, tolerance `NE1/NE2/NE5/NE10`, pattern `WM/NM`), `CalcOp` (`ADD/MULTIPLY/SUBTRACT/DIVIDE/POWER`), `RootGroupConditionName` (German-only). These render as glyphs (`>`, `+`, …) or are out of scope, so they map to the catalog differently (by id) or not at all.
- **Some members are legacy German-only aliases** with no English name (`name()` == `getRuntimeName()`, both German): `EntityListConditionName.{ZeilenNichtAufsteigend, ZeilenLueckenlos, ZeileNichtEindeutig}` (the last superseded by `RepetitionNotUnique`), `EntityListOperationName.MaximalAngegebenerZeilenindex`, `FieldIdOperationName.AktuelleVordruckNummer`.
- **`RootGroupConditionName` is multi-form (Vordruck/USB) scope — and the BA doc doesn't document it (kernel↔BA-doc disparity, 2026-06-08).** The members — `MindestensEinVordruckAngegeben`, `KeinVordruckAngegeben`, `VordruckNichtFortlaufend`, `UsbNichtFortlaufend`, plus `FieldIdOperationName.AktuelleVordruckNummer` — model **multi-form documents** (a document holding several numbered *Vordrucke*/forms, with *USB* sub-units), **outside rulekit's single-document-model scope**. rulekit converts only the two that degrade to single-root-group presence (`MindestensEinVordruckAngegeben`→`GroupFilled`, `KeinVordruckAngegeben`→`GroupNotFilled`); the rest stay excluded (`KernelConstructParityTest`). **The gap:** the merged BA doc `a12-kernel/documentation/_merged/kernel-ba.md` has **zero** occurrences of "Vordruck" — it documents the common *single-model* DSL, not multi-form. So the BA doc is **not exhaustive of kernel constructs**; the construct-enum + lexer inventory (the parity guardians `KernelConstructParityTest` / `KeywordReverseParityTest`) is the authoritative list of what the kernel actually supports. **Lesson:** an absence in the BA doc is *not* evidence the kernel lacks a construct — confirm against the enums/lexer (the kernel's own machine-readable surface), not the prose alone.
- **The enums carry the full coverage backlog**, machine-readably: families rulekit hasn't modeled (date extraction, sub-day date add/diff, op-list math, tolerance comparisons, value coercions) appear as enum members with no catalog counterpart — exactly the operators a future increment (or a kernel upgrade) would add. `KernelConstructParityTest`'s exclusion list enumerates them with reasons.

## Parsing a condition to the AST — shapes for the F10 converter (2026-06-04 probe)

Verified by parsing rulekit-authored conditions via `IMVK_Service.parseBedingungNoExpand(IRule, pr)` (parses the rule's *own* stored `errorCondition`) and inspecting the `ICondition` tree:

- **`ICondition` carries no discriminator** — no `getName()`, no kind enum, only `traverse(ASTVisitor)`. Dispatch by `instanceof` against the concrete subtype interfaces.
- **Single-field presence is canonicalized into the field-list node.** `FieldFilled(x)` parses to an **`IEntityListCondition` named `AllFieldsFilled`** with a one-element entity list; `FieldNotFilled(x)` → name **`NoFieldFilled`**, one element. There is no dedicated single-field "filled" node and no `FieldFilled`/`FieldNotFilled` enum constant — the single-field and field-list forms collapse to the same node, distinguished only by entity-list arity. (So a 1-element `AllFieldsFilled`/`NoFieldFilled` round-trips to rulekit's `.filled()`/`.notFilled()`.)
- **`IComparisonCondition`**: `getOperation1()` (left) / `getOperation2()` (right) → `IOperation`; `getCmpOp()` → `ComparisonOperation` (`GT/LT/GE/LE/EQ/NE` + tolerance `NE1/2/5/10` + pattern `WM/NM`). A plain field operand is `IFieldIdOperation` with `getOperatorName() == FieldValue` (other names = `Length`/`Round…`/`AbsValue`/… wrappers); `getField().getFullName()` is the resolved absolute path. A literal is `IConstantOperation.getValue()` — **always a String**; its kind is `IOperation.getType()` (`OperationType {NUMBER, STRING, DATE, DATE_RANGE}`), not on the operand subtype. So a number comparison can be rebuilt with the kernel's literal string directly via rulekit's `gt(String)`/`eq(String)`/… overloads (no re-parsing).
- **`ICompositeCondition`**: `getLogOp()` → `LogOp {And, Or}`; `getConditionList()` → `List<ICondition>` (**n-ary**, not binary); `hasBrackets()` records source parenthesization.
- **`IEntityId` has no value-kind** and no `isGroup()` (derive from `!isField()`); the field kind comes from the model, not the path node — rulekit's converter reads it via `BoundModel.fieldAt(path).kind()`.
- **Aggregate operands** (`Sum`/`MaxValue`/`MinValue`/`NumberOfDifferentValues`/…) are `IEntityListOperation` (`getOperatorName()` → `EntityListOperationName`, `getEntityList()` → `IEntityIdList`), appearing as the left operand of an `IComparisonCondition`. For a wildcard scope like `Sum(Items*/Count)`, the single entity's `getFullName()` is `/Order/Items/Count` (**the `*` is dropped**) and `getIndices()` is `[1, 0, 1]` — the **`0` is `IParseTreeEntity.WILDCARD`**, marking which path segment was flattened (here `Items`). So the rulekit `*`-path is rebuilt by re-inserting `*` after each segment whose index is `WILDCARD`. A **`Having` filter** rides on that entity as `getFilterCondition()` → a nested `ICondition` (e.g. the `[Items/Sku] == "A"` comparison), which converts recursively and attaches via `FieldListRef.having(...)`.
- **Iteration operands/conditions.** `CurrentRepetition(group)` is an `IGroupOperation` (`getOperatorName()` → `GroupOperationName.CurrentRepetition`, `getGroup()` → the group `IEntityId`), a numeric operand of a comparison. `RepetitionNotUnique`/`FieldValuesNotUnique` are `IEntityListCondition`s (those names in `EntityListConditionName`): the key entities carry the **`ITERATION` (-1) index** at the repeatable level (e.g. `/Subscription/Addons/Name` → indices `[1, -1, 1]`), and a `… From <group>` scope, when present, rides on `getAdditionalGroupReference()` (absent → empty).

## `variantFilter` — a Field/Rule/Computation is omitted by variant (source-verified 2026-06-26)

A Field, Rule, or Computation may carry a `variantFilter` (serialized `{ "filterType": "ONLY" | "ALL_EXCEPT", "variants": [<names>] }`, in the element's type sub-object — `RuleSerializer`/`FieldSerializer`/`ComputationSerializer`). When the validation model is built for a given **variant**, `VariantFiltering.filterAcceptsVariant` decides membership (`ValidationModelConverter` gates `addChildEntity`): `ONLY` keeps the element iff the active variant is in `variants`; `ALL_EXCEPT` keeps it iff it is NOT. So with **variant == null** (the differential oracle's setting and dmtool's default), an `ONLY`-filtered element is **dropped** (no variant can match) and an `ALL_EXCEPT`-filtered element is **kept**. A dropped rule never fires; a dropped field/computation is absent from validation/compute. Interpreter treatment: the loader mirrors the null-variant decision (IF36). dmkits does **not author or interpret** `variantFilter` — it is **out of scope** (DEV-API-GAPS §3): a **pass-through** preserved verbatim on a modelkit load→edit→save (the raw-JSON tree surgery never strips an unmodeled slot), so an existing model that carries one keeps it. Locked by `modelkit.VariantFilterPreservationTest`.

## §10 supplement — the model-include (`modelAlias`) mechanism + the mount-suffix path (2026-06-04)

How a DM includes another (the workspace `purpose:"include"` scheme, adapted to our own domain in `storefront.dm.json` → `catalog.dm.json`):

- **Header**: `modelReferences: [{alias, modelType:"document", purpose:"include", reference:<includedModelId>}]`.
- **Content**: a placeholder **Group** with `"Group": {"repeatability": 1, "modelAlias": <alias>}` and **no inline `elements`** — `expand(model, resolver)` mounts the referenced model's content there. The `resolver` (`IDocumentModelReferenceResolver.getDocumentModel(reference)`) returns the included model; a directory resolver maps `reference` → `<reference>.json`.
- **The mount group *id* gets a `_` suffix on expand** (`Inventory_`), with the included root group `Catalog` nested under it — but **`id` ≠ name**. The kernel's `getId()` is an opaque/suffixed identifier; the **name-path** (the join of `getName()` segments, which is what a condition references via `getFullName()`) is the unsuffixed **`/Storefront/Inventory/ListPrice`** — and notably the included root group `Catalog` does **not** appear as a name segment (the mount surfaces the included fields directly under the mount group's name).
- **rulekit indexes by name-path (F-IDX, 2026-06-05), not by id** — so the handle path *is* the unsuffixed, condition-facing `/Storefront/Inventory/ListPrice`. (Before F-IDX the index keyed by `getId()`, exposing the suffixed `/Storefront/Inventory_/Catalog/ListPrice`; that id-path was never authorable in a condition — `MVK_INVALID_ENTITY` — which was the tell.) A *written* rule referencing an included field **does** round-trip through the kernel: add → modify → write-back → re-read is green and the include is never inlined (`ModifyIncludedRuleTest`) — the earlier "deferred fork-9 follow-up" caveat here is resolved.
- **Extract-as-include is reference-safe — the composed shape validates (2026-06-12).** The *post-extraction end state* — a subtree lifted into a sub-model and re-mounted at the same name — passes `checkConsistency`. Two legs verified: **(a)** a **parent** rule reaching into the mount (referencing `/Order/Shipping/PostalCode`) validates and resolves via `whereUsed`; **(b)** the included sub-model's **own** relative-pathed rule travels to the mount and surfaces at its composed full-name (`/Order/Shipping/PostalCodeRequired` in `readAll()`). So rules that lived inside an extracted subtree move with it for free (relative paths), and references into it survive — because the mount name-path is transparent (above). The extract refactor's safety gate (CLI-SPEC §6) still refuses what this does *not* cover: a subtree rule reaching **outside** the subtree (the sub-model can't see it) and a **repeatable** group (an include's root must be single, non-repeatable — kernel `EntityPathsRelativizer`).

- **An included model's `header.modelReferences` must be present (an empty list) — not absent (2026-06-12).** On expand, `DocumentModelExpandService.addTransitiveModelReferencesFromIncludedModel` calls `header.getModelReferences().stream()` on the *included* model, so a sub-model whose header omits `modelReferences` triggers an **NPE** during expand (surfaced as a `ModelConsistencyException`). Authoring a sub-model for an include must emit `"modelReferences": []` even when it declares none. (Bit the `group extract` refactor: clearing the field outright NPE'd; setting it to an empty array fixed it.)

rulekit treatment + the write-separation guarantee live in `KERNEL-INTEGRATION-NOTES.md`. *(Locked: `IncludesWritePathTest`, `ModifyIncludedRuleTest`, `ExtractAsIncludeProbeTest`, `ExtractGroupAsIncludeTest`.)*

## Serialization shape — a childless group's `elements` array is omitted (2026-06-13)

The kernel's `IDocumentModelSerializer` **omits the `Group.elements` array entirely for a childless group** (it does not emit `"elements": []`). So a model round-tripped through the kernel serializer — as the reference-rewriter (`adapter.ReferenceRewriter` over `MoveSupportDM`) does — comes back with empty groups carrying *no* `elements` key, not an empty one. This is consistent with the kernel's omit-empty-collection serialization (cf. the `datePrecision`-omitted-for-FULL and `modelReferences`-must-be-present quirks above): a *present-but-empty* collection and an *absent* one are not interchangeable, and the serializer prefers absent.

Consequence for any code that *inserts into* a group by walking the JSON: "no `elements` array" must be read as "an empty container," not "no such group." It bit `field`/`group move` **into a freshly-added empty group**: the move rewrites references through the kernel serializer first (dropping the destination's empty `elements`), then the node relocation looked up the destination's `elements` and found none → a spurious "no group at path". rulekit's treatment (materialize the empty array on a matched childless group) lives in `KERNEL-INTEGRATION-NOTES.md`. *(Locked: `MoveVerbTest.movesAFieldIntoAChildlessGroup` + `ApplyRefactorTest.theGateSeesPriorOpsEffects_moveIntoAJustAddedGroup`.)*

## §13 supplement — the message-locale law

Header `locales` are **arbitrary** valid Java locale codes (`fr_FR` is fine; a malformed code like `en_us` fails at *deserialization* — "Invalid locale format" — before any consistency check). English/German are not special here; only the *condition keyword* language is limited to the EN/DE bundles.

**Language-only codes (`en`, `de`): they DESERIALIZE but the VALIDATION mode rejects them** (corpus check + experiment, 2026-06-05; locked by `dsl.BareLocaleTest`). A `Locale` needs only a language, so `en` parses, and the bare form **dominates the A12 Tools workspaces**: **268** models declare `[{"code":"en"},{"code":"de"}]` vs **107** with `en_US` (e.g. `advanced/models/CommonFieldDefinitions_TDM.json`); our own fixtures and `a12-kernel-mm` use the full `language_COUNTRY` form. **BUT** `checkConsistency` (the validation mode, run by `BoundModel.ofJson`) derives a validation language from the model's locale and **rejects the bare code**: `IllegalArgumentException "Die im ValidierungsModus übergebene Sprache en wird nicht unterstützt"` ("language en is not supported in validation mode"). The full `en_US` is supported. So:

| Tier | `en` (bare) | `en_US` (full) | `en_us` (malformed) |
|---|---|---|---|
| deserialize | ✅ parses | ✅ | ❌ "Invalid locale format" |
| **validation (`checkConsistency`)** | **❌ not supported** | ✅ | — |

**Consequence:** the validate/author path requires a **full** locale code; a bare-locale model (most of the workspaces) must have its locale normalized to a supported full form (`en`→`en_US`) before it can be validated through rulekit. (Corrects an earlier note that claimed bare codes "just work" — that held only for deserialize.) The message-coverage match is still exact-string: a message must carry the **same** code the header declares.

- A rule/computation must carry an error message for **every declared locale** — a missing one is **`MVK_ERROR_MESSAGE_FOR_LANGUAGE_MISSING`**; none at all is `MVK_ERROR_MESSAGE_MISSING`.
- A message for an **undeclared** locale is **silently tolerated and ignored** — no diagnostic, so a typo'd locale code or dead text goes unnoticed (rulekit rejects it at build time for exactly that reason).
- **A blank message text counts as no message at all** (probe-verified 2026-06-10; locked: `validate.laws.RuleSlotLawsTest`): a rule whose only message has `text: ""` draws `MVK_ERROR_MESSAGE_MISSING` from `checkConsistency` plus a per-language `RULE_HAS_NO_ERRORTEXT` (the non-`MVK_` FehlertextErrorType tier) — the blank text serializes as an absent message, it does not survive as an empty one. The metamodel's `MVK_MESSAGE_FOR_LANGUAGE_MISSING` (a language row without its text) never appeared — that shape isn't producible through rulekit's surfaces. The CLI `add` path catches all of this at its post-write re-validation and leaves the model file untouched.
- **Duplicate message locales are silently tolerated at DM-JSON load** (found 2026-06-10 writing the lock — the expected rejection never came): a rule with two `en_US` texts loads and passes `checkConsistency`; one text silently wins. The metamodel's `MVK_LANGUAGE_DUPLICATE` fires only in the model-as-document tier (A12 Tools editing), not on a deserialized DM-JSON. rulekit's builders therefore pre-check duplicates (`LocalizedText.checkDeclared`, the code named). *(Tolerance locked: `validate.laws.RuleSlotLawsTest`; pre-check locked: `RuleAuthoringTest`.)*

*(Locked: `RuleAuthoringTest.requiresAMessageForEveryDeclaredLocale` / `rejectsMessagesForUndeclaredLocales`.)*

## Structure-authoring consistency laws — field types & requiredness (modelkit M1/M2, 2026-06-05)

Surfaced while building modelkit (authoring a *whole model* from scratch and running it through `checkConsistency`). These are **model-structure** validity laws (the kind-B oracle), distinct from the rule-condition `MVK_*` codes in the ledger — they fire on the model, not on a rule. Each is now respected by the `structure` builders (made unrepresentable at the API, or enforced fail-fast before emit) and locked by `structure.DocumentModelDraftTest` / `structure.FieldConfigTest`.

- **An `UnspecifiedType` field is not consistency-valid** — `MVK_UNSPECIFIED_TYPE_NO_CODEGEN` ("Field 'X' does not specify a field type. Hence, code generation is not possible."). It's an authoring *placeholder*, never valid in a complete model. So modelkit's easy-kind set is **String / Number / Date / Boolean / Confirm** — `Unspecified` is deliberately excluded (corrects the betterbuilders/Q4 "easy types incl. Unspecified" read).
- **A string `pattern` requires a localized error text** — `MVK_ERROR_MESSAGE_AND_PATTERN_INVALID` ("The pattern '…' is specified, but the corresponding error text is not."). The text lives in the **`StringType.errorMessage`** array — `[{locale, text}]`, one entry **per declared model locale**. So in DM-JSON a patterned string is `"StringType": { "errorMessage": [{locale,text}…], "pattern": "…", "maxLength": … }`. modelkit makes pattern and message inseparable in the API (`pattern(regex, message)`), replicating the message across the model's locales.
- **Enumeration labels are all-or-nothing per declared locale** — `MVK_COUNT_OF_VALUES_INVALID` ("For the language 'en-US' not every XML value has a corresponding display value."). Once *any* value carries a label, *every* value needs a label for *every* declared locale. Bare (unlabelled) enums are fine. Shape: `"EnumerationType": { "values": [{ "value": "X", "label": [{locale,text}…] }, …] }` (label is **per value**, optional, but uniform when present). modelkit enforces completeness fail-fast at emit (it knows the model locales then). **A second code guards the same law from the other direction — the add-locale cascade.** When the gap is opened *after the fact* — a labelled enum is valid in a single-locale model, then `config modify --add-locale <L>` registers a new locale the existing value-labels don't cover — the terminal gate raises **`MVK_INTERNAL_VALUES_AND_DISPLAY_VALUES`** ("The display value and the XML value were not specified together"), an **opaque** message that hides the per-locale label gap. (Asymmetric, per probe 02: adding a locale forces *enum value labels* and every *new* field's label to cover it, while pre-existing single-locale *field* labels are tolerated.) rulekit enriches this code with the per-locale cause + the remedy (do `--add-locale` and the per-value label top-ups in one `apply` so the single terminal gate sees a consistent model — `validate.StructuralKernelFix`). *(Locked: `cli.config.ConfigVerbTest.addingALocaleRejectsAnEnumWithSingleLocaleLabelsAndNamesTheCause` triggers the real code + asserts the enriched fix; `validate.DiagnosticEnricherTest` locks the hint.)*

Supporting structural shapes verified along the way (own-words; for the modelkit emitter and any future schema-oracle work):

| Slot | DM-JSON shape | Notes |
|---|---|---|
| **Requiredness** | `Field.requirednessConfig: { "mode": … }` (sibling of `fieldType`) | mode-only is valid — **no error message needed**. Modes: `notRequired` (or omit the config), `absoluteOrRelativeToNextRepAncestor` (plain required), `relativeToParent` ("only if parent group filled", §4). |
| **NumberType** | `{ "maxFractionalDigits": n, "minValue": x, "maxValue": y }` | `maxFractionalDigits` is the decimal scale (§5b); min/max optional. Valid with just a scale (M1 used `maxFractionalDigits: 0`). |
| **StringType** | `{ "minLength", "maxLength", "pattern", "errorMessage" }` | all optional; `pattern` ⇒ `errorMessage` (above). Bare `{ "type": "StringType" }` (no inner block) is valid. |
| **EnumerationType** | `{ "values": [{ "value", "label": [{locale,text}] }] }` | label per value, optional but all-or-nothing per locale (above). |
| **DateRangeType / DateFragmentType** | `{ "format", "rangeSeparator" }` / `{ "formatOfFragment" }` | both DateRange slots required; fragment needs its format (M3). |

| **Header / config** | `header{id, modelType:"document", modelVersion, locales[{code}]}` + `content.modelConfig{decimalSeparator, timeZone, conditionLanguage{code}, fieldRefByShortNameAllowed}` + `modelInfo{name, variant, revision, immutable}` | the from-scratch skeleton; a full `language_COUNTRY` locale is required for the validation mode (§13). |

## §paths supplement — relative path forms accepted in conditions (fork #9, 2026-06-04 probe)

Conditions accept paths **relative to the rule's group**, not only absolute — verified against the kernel: a bare segment for a field directly under the rule group (`FieldFilled(MonthlyFee)` at `/Subscription/Addons`), the bracketed value form (`[MonthlyFee]`), and `../` parent navigation to a sibling group's field (`FieldFilled(../Tier)` from `/Subscription/Addons`). All kernel-accepted (computation operations too). **Bare names also resolve *upward* (verified 2026-06-05 via `cli check`):** a bare segment not found directly under the rule group is looked up in **ancestor** groups — `[Tier]` from a rule scoped to `/Subscription/Addons` binds to the ancestor `/Subscription/Tier` (**no `../` needed**), exactly like `[/Subscription/Tier]`; a name found nowhere (`[Bogus]`) is `MVK_INVALID_ENTITY`. So a bare cross-(ancestor-)group reference works without `../`; `../` only matters to reach a different branch. *(This caught an eval judge out — it assumed bare = the rule group only and false-flagged correct candidates; RESULTS.md 2026-06-05 19:06.)* Descending *relatively* into a **repeatable** subgroup still hits the wildcard law (`MVK_NO_WILDCARD`) — that is the iteration rule, orthogonal to the path form. rulekit's renderer now renders rule/computation conditions relative to their group (the authoring norm — `DslRenderer` with a base group); standalone `DslRenderer.render` stays absolute, and absolute remains valid (KERNEL-INTEGRATION-NOTES). **Keyword-segment quoting (the other fork-9 half, verified 2026-06-04 probe):** a path segment whose name collides with a DSL keyword is a **parse error** unquoted — `FieldFilled(Length)` (and even absolute `FieldFilled(/Subscription/Length)`) → **`MVK_UNEXPECTED_TOKEN`** — and is escaped by **single-quoting that segment**: `FieldFilled('Length')` / `FieldFilled(/Subscription/'Length')` validate (grammar `NameOhnePunktMitQuotes : '\'' STR (STR|DIGIT)* '\''`). rulekit's renderer now single-quotes any segment matching a catalog operator keyword (per segment, `*` suffix preserved); the **full** lexer keyword set (beyond the operators rulekit catalogs) rides the N3 parity anchor. *(Locked: `dsl.PathPolicyTest`.)*

## §iteration supplement — group cardinality (minItems-style "at least N rows") has no clean rule form (probe + source, 2026-06-28)

The JSON-Schema `minItems`/`maxItems` analog — "a repeatable group must have at least/at most N rows" — has **no clean expression as an a12 rule**. Two kernel facts combine to block it (both live-probe-verified 2026-06-28 against the public facade; group repeatability itself is a structural **max only**, no min slot — see §4):

1. **The error entity controls the rule's iteration.** `IRule.getErrorEntity()` is documented as *"a highlighted entity (field or group) … controls the iteration of the rule"* — so a group error entity **is** allowed by the kernel (the `MM_Rule_1` metamodel stores it as a plain path with no field-only restriction, and the resolver `ValidationModelConverter.findReferencedEntity` returns the base `IEntity` = field **or** group). BUT pointing it at a **repeatable** group makes the rule iterate **per row**, so a condition that must fire on an *empty/absent* repetition is rejected: a rule with `errorEntityRelPath: "../Lines"` + condition `GroupNotFilled(Lines)` → **`MVK_NEG_CONDITION_IN_ITERATION`** (*"Iteration for '/Order/Lines' is specified, but the rule can fire for not filled repetitions of this repetition level"*). You cannot check "zero rows" while iterating rows.
2. **There is no single-group row-count operator.** `NumberOfFilledGroups` counts how many of **several** groups are filled — it requires **≥2** group arguments: `NumberOfFilledGroups(Lines) < 2` → **`MVK_PARAMSIZE_INVALIDGN`** (*"There must be more than one group"*). So it cannot count the rows of one repeatable group.

**Net:** "at least N rows" is not expressible as a standard rule — the iteration model fights an emptiness/cardinality check, and no operator counts one group's rows. A group **can** be a rule's error entity in principle, but that capability does **not** unlock cardinality (and there is no current consumer for it), so **do not** add `errorField(GroupReference)` to rulekit for this purpose. Consumers (e.g. the JSON-Schema importer) **omit** `minItems`/`maxItems` cardinality with a corrective to-do rather than synthesizing an (impossible) rule. *(Not test-locked — the two `MVK_*` rejections above are the evidence; reconstruct the probe to re-verify on a kernel upgrade.)*

## The condition FORMATTER is German-canonical — rendering ANY language reads the German terminal map (source-verified 2026-06-30)

The kernel's condition formatter (`ConditionFormatter` → `FormatterVisitor` → `AbstractMultiLanguageHandler`) is **German-canonical**: its parse-tree terminals are keyed by German names, and to emit a rule's condition in *any* language it maps **from the German terminal map to the target**. `getTerminalNameByGermanTerminalName(name)` short-circuits **only** when the target is German (`Locale.GERMANY.equals(languageUsedInConditionText)` → returns the German name directly); for **every other target — including English —** it does `getMapOfLocalizedTerminalIDs().get(Locale.GERMANY).get(name)` → tokenType → the target name. So the **German** terminal data (`LexerTerminals_de_DE`) is a hard dependency of formatting in **English**, not just German.

Default language: the no-locale `formatConditionText` renders in the model's `conditionLanguage` (`getLanguageUsedInConditionText()`), which the kernel **silently falls back to German** for any locale other than `Locale.US`/`Locale.GERMANY` (already noted on `KernelAdapter.canonicalConditionText`). The dmkits default is English and **independent of the display locale** (`DocumentModelDraft.DEFAULT_CONDITION_LANGUAGE = en_US`), so our models render English — but the German source map is still consulted under the hood.

**Native-image impact (the v0.8.0 Linux-only `rule format` defect).** GraalVM bundles only the **build host's default locale** (+ `en`) into the image's resolvable locales unless `-H:IncludeLocales` is set. A binary built on a **`de_DE`** host (the maintainer's Mac) carries the German terminal data → `rule format` works; one built on an **`en`/`C`** host (Linux CI) does **not** → `getMapOfLocalizedTerminalIDs().get(Locale.GERMANY)` is empty → `rule format`'s English render fails with *"The german token name 'Und' is unknown"* (or `ExceptionInInitializerError`). The output was never going to *be* German (target = `en_US`); it crashed for lack of the German **source**. Only an explicit `--lang DE` short-circuits the German-map read — which is why `rule format --lang DE` passed on Linux while the default did not. **Fix:** pin `-H:IncludeLocales=en,de` so every build is locale-complete and host-independent ([NATIVE-IMAGE-GRAALVM §3.2](NATIVE-IMAGE-GRAALVM.md)). *(Reconstruct: a forced-`en` builder via `-J-Duser.language=en` reproduces the crash on macOS; adding `-H:IncludeLocales=en,de` restores the English render. Locked at runtime by the Linux native gate over `examples/cli-jsonschema.md`.)*
