## §1 supplement — Boolean/Confirm comparability codes

The Boolean≠Confirm split is enforced at parse time with distinct codes: a Boolean compares only to `True`/`False` or another Boolean — anything else (e.g. a string) is **`MVK_INVALID_COMPARE_TO_YESNO`**; a Confirm compares only to `True` or another Confirm — `[Confirm] == False` and Boolean↔Confirm cross-comparisons are **`MVK_INVALID_COMPARE_TO_YES`**. "Not confirmed" is written `[Confirm] != True` (an unset confirm counts as not confirmed). *(Locked: `validate.laws.BooleanConfirmLawsTest`.)*

## §1 supplement — Boolean three-state matrix (runtime, 2026-06-06)

A `Boolean` has three distinct states (unset / `True` / `False`), and the runtime honors them as the spec says — verified in a filled row:

| state | `== True` | `== False` | `FieldFilled` |
|---|---|---|---|
| unset | — | — | — |
| `True` | ✓ | — | ✓ |
| `False` | — | ✓ | ✓ |

Traps pinned: `[Flag] == True` is **not** `FieldFilled(Flag)` (they diverge on a `False` value), and `[Flag] == False` ≠ "unchecked" (an unset Boolean satisfies neither equality). Contrast a Confirm, whose unset value *is* `False` (§2 supplement). *(Locked: `adapter.laws.BooleanThreeStateLawsTest`.)*

## §1 supplement — the "not …" field-list quantifiers are not complements (runtime, 2026-06-06)

Over a two-field list, the three negative fill-quantifiers disagree at the edges (fires? by filled-count):

| filled (of 2) | `NotAllFieldsFilled` | `FieldsNotCollectivelyFilled` | `NotExactlyOneFieldFilled` |
|---|---|---|---|
| 0 (none) | ✓ | **—** | ✓ |
| 1 | ✓ | ✓ | — |
| 2 (all) | — | — | ✓ |

The trap is the all-empty column: `NotAllFieldsFilled` and `NotExactlyOneFieldFilled` **include** it, but `FieldsNotCollectivelyFilled` **excludes** it (needs ≥1 filled). Picking the wrong member changes which documents the rule reports. (Verified with the row filled by a sibling, so the list fields' emptiness is what's measured.) *(Locked: `adapter.laws.FieldListQuantifierLawsTest`.)*

**Group-list quantifier asterisk bar (source + probe, 2026-06-17).** The *group*-list quantifiers `NotAllGroupsFilled`/`GroupsNotCollectivelyFilled`/`AllGroupsFilled` reject an **asterisk** argument — `NotAllGroupsFilled(Items*, ShippingAddress)` draws **`MVK_NO_WILDCARDS_G_ALLOWED`** (source `CheckEntityListenUtils.checkNoWildCardsInGroup`, fired on `ref.hasWildCardsInGroup()`). (BA L2397-2399 also bars a **rootGroup** argument for these three, unlike `NoGroupFilled`/`AtLeastOneGroupFilled` which allow one rootGroup — not separately probed: every group in the order fixture lives under the single root, so a rootGroup arg trips the duplicate-reference check first; left BA-stated.) *(Locked: `validate.laws.GroupQuantifierLawsTest`.)*

## §2 supplement — empty-as-0 is a *filled-row* behavior (runtime, 2026-06-06)

KERNEL-SEMANTICS §2 says an empty **number** field has `0` substituted in a comparison, so `[Quantity] < 100` fires on an empty Quantity. Verified against the **runtime** engine (`IDocumentRtService.validateFull`) with one refinement the spec doesn't spell out: **the substitution applies to an empty field within a *filled* group row** — a row made non-empty by at least one sibling value. An **entirely empty row** (a group instance with no field values at all) is **not evaluated**, so the same rule does *not* fire there.

Observed for `[Quantity] < 100` on `/Order[1]`: sibling `CustomerName="Acme"` + empty Quantity → **fires** (0 < 100); empty-string Quantity, valueless Quantity, or an otherwise-empty row → **does not fire**; `Quantity="200"` → does not fire (200 ≮ 100). The `FieldFilled(Quantity)` guard suppresses the empty-as-0 case even in a filled row.

The **type-asymmetry** of the empty case (the trap — the same comparison shape behaves differently by type), all verified in a filled row:

| field type | example | empty behaviour |
|---|---|---|
| number | `[Quantity] < 100` | **fires** — `0` substituted |
| confirm | `[TermsConfirmed] != True` | **fires** — treated as `False` |
| boolean | `[ExpressShipping] == True` | **not evaluated** |
| string | `[ProductCode] == "ABC"` | **not evaluated** |
| string in a **concatenation** | `[FullName] != [FirstName] + " " + [LastName]` | **evaluated** — an empty operand concats as `""`, so `[First] + " " + [Last]` = `" "` (a real value) and the comparison fires (verified 2026-06-08, N6) |
| date | `DifferenceInDays(OrderDate, DeliveryDate) < 0` | **not evaluated** (verified via date-to-date diff, avoiding §6 literals; `DifferenceInDays(a,b) = b − a`) |

**The concatenation row is the trap an N6 run surfaced (2026-06-08).** A string field in a *comparison* gets the empty-as-not-evaluated free pass; the **same field as an operand of a `+` concatenation does not** — an unfilled string concatenates as `""`, so the concatenated expression is a real value and the comparison **is** evaluated. So a "must equal `first + space + last`" rule (`[Full] != [First] + " " + [Last]`) **mis-fires when `Full` is present but `First`/`Last` are empty** (it sees `[Full] != " "` → true) unless its operands are guarded with `AllFieldsFilled(First, Last)` — the guard a plain string comparison wouldn't need. (Verified at runtime: with `Full="Alice Smith"` and `First`/`Last` empty the unguarded rule fires; the guarded form does not; a consistent first+space+last does not fire.)

**Value-token representation (runtime document instances).** A boolean's value token is `true`/`false` (lowercase) — any other token (`TRUE`, `X`, `1`, `yes`) is a formal error (`feldJaNeinFalsch`), so the field becomes "unknown" and is not evaluated (§3). A **confirm** accepts only `true` or unspecified; `false` is a formal error (`feldJaFalsch`) — consistent with "a Confirm is a checkbox whose single value is True". *(Locked: `adapter.laws.EmptyValueLawsTest`; the runtime oracle is `adapter.laws.RuntimeLaws` — KERNEL-INTEGRATION-NOTES "Runtime behavioral-law oracle".)*

## §2 supplement — empty operand in a *computation* operation ⇒ no value (stale cleared) (runtime, 2026-06-08)

The empty-as-not-evaluated rule extends from comparisons to **computation operations**: when a computation's value expression references an empty operand, **the operation is not evaluated — the computed field gets no value, and a previously-computed (stale) value is cleared**. Verified against the runtime `IDocumentRtService.compute` (the date-range constructor case): `CoverageWindow = DateRange(OrderDate, DeliveryDate)` over an `OrderDate`-filled / `DeliveryDate`-empty `/Order` → `CoverageWindow` is **not** in the computed set (no value); a row that *already* held `CoverageWindow = 01.01.2020-01.01.2021` has it **cleared** to empty. Both-filled computes `01.01.2024-01.02.2024` (the `dd.MM.yyyy-dd.MM.yyyy` DateRangeType format). This mirrors the §2 validation-side "empty date ⇒ not evaluated" — a `DateRange` over an empty bound is the construction analog.

**Consequence (the equivalence the N6 eval relies on):** the unguarded computation and the **same computation with a `commonPrecondition AllFieldsFilled(OrderDate, DeliveryDate)` guard** compute the same value (or none) for *every* document — the guard is **redundant** (a false precondition clears the field, exactly as the unevaluated operation does). This settles the 2026-06-08 T13 judge split (judge B was right). It does **not** generalize to *string* operands — an empty string in a **concatenation** concats as `""` and *is* evaluated (the row above); the "empty ⇒ not evaluated" free pass is per-type (numbers fire as `0`, dates/strings-in-comparison are skipped, strings-in-concatenation are not). *(Locked: `adapter.laws.DateRangeComputationLawsTest`, via the `RuntimeLaws.compute` oracle.)*

The **number** branch is confirmed for computation too (2026-06-09): a numeric copy `EffectiveFee = [BaseFee]` with **`BaseFee` empty** computes **`0`** (a value), not nothing — the empty-as-0 substitution applies in a computation operation exactly as in a comparison, so an empty *number* operand is the opposite of an empty *date* operand (which clears). **Consequence (inverts the date redundancy above):** a presence guard over a NUMBER operand is **NOT redundant** — `EffectiveFee = [BaseFee]` guarded by `FieldFilled(BaseFee)` computes **nothing** (cleared) on an empty `BaseFee`, where the unguarded form computes `0`; the two **differ**, so a candidate that adds such a guard to a number computation is **not** equivalent to the unguarded gold. (The N6 computation/modify judges carry this type split so they don't mis-equate the two.) *(Locked: `cli.ComputeDocVerbTest.anEmptyNumberOperandComputesZero` + `aGuardedNumberComputationClearsWhereUnguardedComputesZero`, via the `model compute` verb / `KernelAdapter.compute` seam.)*

## validateFull does NOT run computations — validate and compute are separate operations (runtime, 2026-06-09)

The kernel keeps **validation** (`IDocumentRtService.validateFull`) and **computation** (`compute`) as distinct, independently-invoked operations — confirmed in the kernel dev docs (`a12-kernel/documentation/_merged/kernel-dev.md` §"Validating a document / Computations on a document": *"the use of validation and computation is very similar, therefore only one is described"*, and the worked sequence `validateFull(doc)` … `compute(doc)` … `result.appliedTo(doc)`). There is **no combined call**: `validateFull` validates the document's values **as-is** and does **not** compute computed fields first, and `compute` returns a *result* (the input is never mutated — applying it back via `appliedTo`/`apply` is a separate, opt-in step the consumer orchestrates).

**Consequence for us:** a rule that references a **computed field** sees it as whatever the document instance supplies — **empty** if absent (verified: `FieldFilled(CoverageWindow)` does **not** fire when only the `DateRange` operands are present, since `validateFull` doesn't compute `CoverageWindow`). The `model eval` verb is `validateFull` (does a rule fire?), `model compute` is `compute` (what does a field compute to?) — peers, mirroring the kernel's split; the document file is never mutated by either (read-only — `compute` reports outcomes, never writes `--doc`). *(Locked: `adapter.laws.EvalDocSeamLawsTest.validationDoesNotRunComputations`.)*

## Full vs Partial validation — `model eval` is FULL; partial may skip `*`-all-reps + `Having` rules (BA appendix, prose-only, 2026-06-17)

The kernel has two validation modes (BA "Full Validation and Partial Validation", L5303-5321). **Full validation** — our `model eval` = `validateFull` — formal-validates all fields and evaluates every rule. **Partial validation** is a page-level pre-check over an app-specified *relevant-field* set: it guarantees never to report an error fixable only *outside* that set, but **does NOT guarantee complete checking of the relevant fields** — some checks are skipped (performance/simplicity). Named skip examples: rules referencing **all repetitions** via `*` when only some are relevant (explicitly incl. `NotAllFieldsFilled`, `FieldsNotCollectivelyFilled`), and **`Having`-filter** rules. The exact skip-set is an **unstable implementation detail** (may change any release; projects must not depend on it). **Consequence:** every law we lock and every catalog example we ship is *full-validation* behaviour — a rule that fires under full validation may *not* fire under a partial page pre-check. **Prose-only by design** (the skip-set is explicitly unstable — nothing to formalize/lock). Related: the mandatory-"star" in a field's label (BA "the star method") is a *separate decidable heuristic* over a fixed allow-list of presence constructs — a UI affordance outside rulekit's scope.

## §3 supplement — a fired message's `getErrorText` is the *interpolated* end-user text (runtime, 2026-06-14)

The kernel's `IMessage.getErrorText()` returns the message **with its interpolation tokens already resolved** against the evaluated document — *not* the authored template. Its javadoc is explicit: `$<fieldname>$` is replaced by the field identifier's display string and `$<field.value>$` by the field's display value (both keeping the `$`-sign; no other substitution). Verified at runtime: a rule whose `errorMessage` is `"Discount of $Discount.value$ must not be negative."`, fired on `Discount = -5` (scale-2), yields `getErrorText()` = `"Discount of -5.00 must not be negative."` — the value token resolved, no raw `$…$` left.

**Consequence for us:** the BA's real deliverable is the text the end-user reads, and only the runtime can produce it (it depends on the data). So `KernelAdapter.evaluate` surfaces it on every `EvalMessage.message()`, and the CLI returns it as `data.messages[].message` (`model eval`) and `data.message` (`rule test`, when fired) — closing the loop from "did it fire" to "here is exactly what the user will see" (FEATURE-GAPS G1). *(Locked: `adapter.MessageInterpolationTest`; CLI surfacing by `cli.RuleTestVerbTest.firesOnAViolatingInstance`.)*

## §3 supplement — a formal error silently suppresses the author's rule (runtime, 2026-06-06)

KERNEL-SEMANTICS §3: a value violating its data-type config produces a **formal error**, and while it stands the field is **"unknown"** and cannot be evaluated in any rule. Verified at runtime with the **trap consequence made explicit**: a malformed value doesn't just raise the formal error — it **silently suppresses** an author rule that references the field (the rule's condition is never evaluated, so it does not fire, even when the would-be value clearly violates it). The kernel emits its own formal-error code; the author's code stays quiet.

Observed for `[UnitPrice] > 5` (UnitPrice scale-2) in a filled row: `"10.00"` → the author rule fires; `"10.999"` (three decimals) → **`zahlFalscheAnzahlNachkommastellen`**, author rule **not** fired; `"abc"` → **`zahlHatUngueltigeZeichen`**, not fired; a string `" ABC "` → **`fuehrendesBlank`** (leading-space formal error). These runtime formal-error codes are German internal identifiers (not `MVK_*`); they're locked as the observed contract so a kernel change surfaces in the build. *(Locked: `adapter.laws.FormalErrorLawsTest`.)*

A formal error is **attributed to a sentinel rule path** — the runtime message reports `rulePath = "formalePruefung"` (not the author rule, and not empty). So in the `model eval` output the discriminator between an author-rule violation and a kernel formal check is the **leading `/`**: an author rule's `rule` is its slash-path (`/Order/X`), a formal check's is `formalePruefung`. *(Verified 2026-06-09: `Quantity` scale-0 `"1.5"` → `zahlHatDezimalTrenner` with `rule = formalePruefung`; locked: `cli.EvalDocVerbTest.aFormalErrorIsReportedAsAKernelCheck`.)*

**Refinement (2026-06-10, RT-semantics drain — probe-corrected): the suppression is *branch-scoped*, not rule-scoped.** The unknown state makes the affected *comparison* evaluate to false-or-unknown; the ordinary `And`/`Or` three-state algebra then decides the rule. So `healthyTrue Or [broken] > 0` **still fires** via its healthy branch — a formal error does not take the whole rule out — while `healthyTrue And [broken] > 0` is absorbed (the single-branch case above, where branch- and rule-scoped look identical). KERNEL-SEMANTICS §1's "removes the rules over it from evaluation" reads stricter than the engine behaves. *(Locked: `adapter.laws.FormalErrorScopeLawsTest`.)*

## §4 supplement — the "required" property and its two modes (runtime, 2026-06-06)

The field-editor "required" checkbox is encoded in DM-JSON as `Field.requirednessConfig: {mode: …}` (kernel enum `IRequirednessConfig.Mode`). An unfilled required field raises the `mandatoryField` **formal error**, so the field is **"unknown"** (§3). The two modes — and the gotcha the BA docs flag — verified at runtime:

| mode (DM-JSON) | BA "Only if parent filled" | when required |
|---|---|---|
| `absoluteOrRelativeToNextRepAncestor` | **no** | a non-repeatable field is **always** required; a field under a repeatable ancestor is required once that ancestor is filled |
| `relativeToParent` | **yes** | required **only when the parent group is filled** |

**The gotcha — what "filled" means here.** For `relativeToParent`, "the parent is filled" means **at least one descendant field of the parent is filled** (`IRequirednessConfig` Javadoc), **not** the §9 "row exists" `GroupFilled` notion. Verified on a sub-group field (`/Order/ShippingAddress/Street`): a created-but-empty `ShippingAddress` row → **not** required (no `mandatoryField`); once a sibling (`City`) is filled → required → empty Street raises `mandatoryField`. Under `absoluteOrRelativeToNextRepAncestor` the same empty sub-group still requires Street (always). The requiredness is **stronger than `FieldNotFilled`**: it makes the field unknown, so e.g. a required-but-empty **number** is *not* the §2 empty-as-0 — a `[Quantity] < 100` rule does not fire on it (only `mandatoryField` does). *(Locked: `adapter.laws.RequiredPropertyLawsTest`.)*

## §4/§8 supplement — field-level custom error messages live in a per-locale `errorMessage` array (source-verified, 2026-06-21)

A field carries **two** kinds of custom validation error text, both the "Use Default Error Messages" deselected case (SME 840, 1123) — and both are stored the same way: a per-locale `errorMessage` array `[{locale, text}]`.

| message | DM-JSON location | kernel accessor |
|---|---|---|
| **required-field** (shown when a required field is empty) | `Field.requirednessConfig.errorMessage` | `IRequirednessConfig.getErrorMessage(Locale)` |
| **enum invalid-value** (shown for an out-of-domain value) | `EnumerationType.errorMessage` | (validated by `FieldErrorTextParser`) |

- **"Use default" = absence.** There is **no** explicit `useDefaultErrorMessage` boolean — omitting the `errorMessage` array uses the kernel default; providing it is the custom case. (So the editor checkbox maps to presence/absence, not a stored flag.)
- **Must cover every declared locale** (like enum value labels): a partial map is kernel-rejected. The required-message array also needs the field to *be* required (have a `requirednessConfig`).

Source-read from the kernel (`IField.IRequirednessConfig.getErrorMessage`, `FieldErrorTextParser.hasValidErrorTextInRequirednessConfig`); rulekit's treatment (the `requiredMessages` / `enum.errorMessages` field-spec keys, G23) is in KERNEL-INTEGRATION-NOTES. *(Locked: `cli.field.FieldAddSpecTest` — per-locale enum + required messages round-trip; `modelkit.FieldConfigExtrasTest` reads the enum message back.)*

## §5 supplement — numeric literals are exempt from the scale check

The `==`/`!=` decimal-scale gate applies to **field/expression operands only**. Against a scale-2 field, `== 0`, `== 0.0`, `== 0.00`, `!= 0`, and `<= 0.000` are all accepted — only field-vs-field/expression comparisons of differing declared scale draw `MVK_INVALID_COMPARE_DEC_PLACES`. Consequence: scale-explicit literals (`0.00`) are a rendering-fidelity nicety, not a correctness requirement. *(Locked: `validate.laws.NumberLawsTest`.)*

**Field-vs-field comparison (finding 18, verified 2026-06-04).** Comparing two *fields* (not just field-vs-literal): **strings** compare with `==`/`!=` only (ordering → `MVK_INVALID_TYPE_FOR_COMPARISON`, "only for numbers, amounts and dates"); **numbers** — the scale gate is **`==`/`!=`-only**: equal-scale fields compare freely, different-scale fields draw `MVK_INVALID_COMPARE_DEC_PLACES` ("max fractional digits of lhs(0) and rhs(2) differ"), but **ordering (`< <= > >=`) is scale-exempt** (verified: `[Quantity(0)] < [UnitPrice(2)]` validates; source `CheckVergleichsBedingungImpl.checkNumberComparison` — the scale check runs only when `isUnEqualsComparison`, comparing the two `getMaxFractionalDigits`; a `null` (derived/unknown) scale is the `"?"` in the message, source-read 2026-06-17). String-vs-number → `MVK_INVALID_COMPARE_TO_ENUM_OR_STRING`. rulekit: `StringRef.eq/ne(StringRef)` and `NumberRef.{lt,le,gt,ge,eq,ne}(NumberRef)` — the number `eq`/`ne` **pre-check equal scale** (the D13 gate made cheap, since the index knows both scales), ordering does not. **Enum-vs-enum is now implemented** (`EnumRef.is/isNot(EnumRef)`, compared by stored value; type-compatibility stays the kernel's call) — KERNEL-SEMANTICS §8, locked by `adapter.EnumFieldComparisonReadTest`. An arithmetic **expression** carries a *derived* scale — **multiplication raises it** (a scale-2 × scale-2 expression is scale 4, division/power are unknown), so `[x] == [a] * [b]` can draw `MVK_INVALID_COMPARE_DEC_PLACES` **even when every field shares a scale**; wrap the expression in `RoundAccounting(expr, n)`, or waive the check with `@SuppressWarning(MVK_INVALID_COMPARE_DEC_PLACES)` at the start of the condition (source-read 2026-06-17). *(Also locked: `validate.laws.NumberLawsTest.fieldVsFieldScaleGateAppliesToEqualityOnly`/`stringFieldVsFieldEqualityIsAccepted`/`multiplicationRaisesScaleSoEqualityRejectsEvenWithMatchingFieldScales` + `RenderConditionTest`.)*

**Tolerance comparisons (implemented 2026-06-07).** The kernel's `ComparisonOperation` has four tolerance members — `NE1`/`NE2`/`NE5`/`NE10` — rendered as the worded keywords `DiffersWithToleranceRange1`/`2`/`5`/`10` (DE `UngleichMitToleranz{N}`): `[a] DiffersWithToleranceRange5 [b]` is true iff the two numbers differ by more than 5 ("unequal within a tolerance"). Only for numbers/amounts. Confirmed against the kernel source: `FormatterUtil.getComparisonOperator` renders them via the same comparison-operator path as `<`/`==` (so they ride the existing `ComparisonCondition` rendering). Modeled by extending `CompareOp` with the four variants + a public `Tolerance` enum (`RANGE_1/2/5/10`, making any other range unrepresentable); authored via `NumberExpr.differsWithTolerance(Tolerance, …)` / `NumberRef.differsWithTolerance(...)`. *(Locked: `adapter.ArithmeticReadTest.roundTripsToleranceComparison` + BA-corpus `ToleranceCmp`; N7 catalog examples for all four.)*

## §5 supplement — power-operator parse laws + the quiet non-execution edges (source-read + 2026-06-17)

The `^` power operator (parser `CheckOperationImpl`): **unparenthesized nesting is rejected** — `a ^ b ^ c` draws `MVK_TOO_MANY_POW_FOR_CALC` (nest via grouping); the **exponent must have no decimal places** — a scale-0 field or integer literal is accepted, a decimal-scale field (or an unknown-scale expression) draws `MVK_INVALID_NUMBER_FOR_EXP` (`checkNoFractionalDigitsInExponent`). Arithmetic sub-expressions group with **curly braces `{ }`**, and precedence is `^` → `*`/`/` → `+`/`-`. **Runtime (BA "Power Operator", source-read but not yet law-locked here):** `a ^ b` is *not executed* — so a rule using it silently does not fire — when `b` is outside `[-1000, 1000]` or for `0` raised to a negative power, the same quiet behavior as division by zero. *(Locked: `validate.laws.NumberLawsTest.powerOperatorRejectsUnparenthesizedNesting` / `powerExponentMustHaveNoDecimalPlaces`. The runtime non-execution edges await an `adapter/laws` lock.)*

## §7 supplement — pattern-comparison slot rules and the portable-subset gate (2026-06-04 experiments)

`PatternMatched`/`PatternViolated` (DE: `WieMuster`/`NichtWieMuster`) are grammar-level *infix comparison operators* (`vglOp` alternatives like `==`), but their slot rules are far stricter than the grammar:

- **Left side: a bare string field value only.** A non-string field (number, enum, boolean) → **`MVK_INVALID_TYPE_FOR_PATTERN_COMPARISON`** ("only allowed for string values" — note: *enums are not pattern-comparable* even though they compare to strings with `==`). A string *expression* (e.g. concatenation) → **`MVK_INVALID_PARAMETER_FOR_PATTERN_COMPARISON`** ("only allowed with a field value as first parameter"). A constant → the general **`MVK_INVALID_COMPARE_TO_CONST`**.
- **Right side: a string constant only.** A field reference → **`MVK_MISSING_CONST_IN_PATTERN_COMP`**; a number constant → `MVK_INVALID_TYPE_FOR_PATTERN_COMPARISON`.
- **The regex gate is Java `Pattern.compile` *plus* a portable-subset check** (`PatternUtils.isPatternValid`; the extmp world uses `CommonUtils.isRegExValid` instead): lookbehind `(?<=a)b` is Java-valid yet rejected with **`MVK_INVALID_PATTERN`** — KERNEL-SEMANTICS §7's "portable subset" is *enforced*, not advisory. Consequence: a Java-side `Pattern.compile` pre-check is a necessary condition only; final validity is the kernel's call.
- **The empty pattern `""` is accepted** for document models (the non-extmp branch; extmp additionally requires non-empty).

*(Locked: `validate.laws.PatternLawsTest` + N7 `PatternMatched`/`PatternViolated` examples.)*

## §7 supplement — string-literal escaping is quote-doubling, not backslashes

The condition lexer's rule is `StringLiteral : '"' ( '""' | ~["] )* '"'` — an embedded quote is **doubled** (`"say ""hi"""`), and **backslash is a plain character** (no escape sequences; regex classes like `\d` are written as-is). Backslash-escaping a quote (`\"`) is a parse error (`MVK_UNEXPECTED_TOKEN`). Found while building the pattern operators: rulekit's renderer had C-style escaping and would have emitted wrong regexes for any pattern containing `\` — fixed and locked. *(Locked: `validate.laws.PatternLawsTest` + `RenderConditionTest.quotesStringLiteralsTheKernelWay`.)*

## §8 supplement — a category's `description` is an editor-level note the kernel tolerates (probe + source, 2026-06-21)

An enumeration category's **optional `description`** (SME 1133 — "an optional description can be set") is **not** modeled by the kernel core: both `IEnumerationType.getCategoryValues()` and the a12internal `IEnumerationDataTable` expose categories as `name → values` only. A `description` key on a category node is **tolerated** by `checkConsistency` (probe: injected into a category, `model validate` → `valid: true`, no diagnostic) — it's an editor/tool attribute the kernel ignores. Per the owner rule (*what's editable is part of the model, unless workspace-related*), it belongs **in the model** (the category node), not workspace settings — so rulekit writes it there (`EnumCategory.description`), preserved by the generic-tree round-trip and harmless to the kernel. *(Locked: `cli.field.FieldAddSpecTest.enumCategoryCarriesAnOptionalDescription`.)*

## §8 supplement — enum-category codes and the positional mapping

In DM-JSON, a category's `values` list pairs **positionally** with the enumeration's `values` (entry *i* categorizes enum value *i*); the comparison domain is the category's distinct value set. Codes: comparing to one of the *enum's own* values instead of a *category* value → **`MVK_INVALID_STRING_CONSTANT_FOR_ENUM_COMPARISON`**; an unknown category name → **`MVK_CATEGORY_UNKOWN`** (the kernel's spelling); `->` on a non-enumeration field → **`MVK_NO_ENUMERATION`**. Curiosity: `[Enum -> Category] == [Enum]` (category vs. plain enum field) is *accepted*. *(Locked: N7 `EnumCategory` examples + `dsl.operators.EnumConditionTest`.)*

## §8 supplement — three enum-ish kinds: "extensible enum" is an IStringType quality, NOT a field type (source-verified 2026-06-17)

Three distinct concepts, easy to conflate:

- **Closed `EnumerationType`** — a fixed value set; a normal DM-JSON field type (the md `EnumerationType` DTO: values/categories/errorMessage/alphabeticalSorting/sValue — *no* extensible flag).
- **Extensible (non-closed) enumeration** — **not a field type at all**: an **`IStringType` with `isExtensibleEnum() == true`** (parser `FieldUtils.isExtensibleEnum` = `type instanceof IStringType && isExtensibleEnum()`; `isLikeString` = string ∪ enum ∪ ext-enum). `isExtensibleEnum()` is a **client-SPI/runtime quality** — `IStringType` is "intended to be implemented by clients", the kernel's md `StringType` **defaults it `false`**, and there is **no DM-JSON property** for it (its open/dynamic values are served at runtime, e.g. via `DynamicEnumerationService`). So a DM-JSON field is **just a `StringType` — fully buildable and modelkit-authorable**; the "extensible" quality itself is unauthorable via DM-JSON (always `false` in a plain model) but doesn't need to be: `ValidType`/`InvalidType` accept the field **because it is-a string** (`isLikeString`), which the N7 `Valid(CustomerName, "EMail")` validExample already exercises. **NOT a modelkit gap.**
- **Dynamic / table-backed enumeration** — the genuinely **un-buildable** one (the `ValueNotConsistent` finding below): values from an external table, not DM-JSON-serializable.

(The model/editor metamodel `MM_Common` carries an "ExtensibleEnumerationType" config — maxLength/displayValues — and form-model/UI notions like `fieldConfigurationEntry`/`externalEnumeration` exist, but those are **tooling/FM layers outside rulekit's DM-JSON scope**, not runtime DM field types.) *(Corrects an earlier draft that wrongly called extensible enums "un-buildable" and cited `IEnumerationType.isExtensible` — it conflated the extensible `IStringType` quality with the dynamic/table-backed enum.)*

## §8 supplement — table-backed (dynamic) enums are NOT DM-JSON-serializable ⇒ `ValueNotConsistent` is un-buildable (2026-06-08)

`ValueNotConsistent(enumField <toOp> col1, col2, …)` (DE `WertNichtKonsistent`) checks a row's dependent columns against a **table-backed** enumeration. The checker (`CheckFieldAndValueListConditionImpl`) requires its first operand to be an enum field **with a table reference** (`IEnumerationType.getTableName()`/`getDependentColumns()` present), and verifies the dependent-param arity against the column count (value checks are skipped when the runtime data table is absent).

**But that field type cannot be expressed in a document model's DM-JSON.** The public a12internal `EnumerationType` DTO declares exactly **6 properties** — `values`, `annotations`, `categories`, `sValue`, `errorMessage`, `alphabeticalSorting` — and the deserializer is **strict**: injecting `tableName`/`columnName`/`dependentColumns` raises `UnrecognizedPropertyException` (*"not marked as ignorable"*, probed 2026-06-08). The table backing is materialized at **runtime** from a separate enumeration/table catalog (`IEnumerationType` returns empty Optionals when loaded from a plain document model), not from the field's type JSON.

**Consequence:** no self-contained document model can mark a field table-backed, so the checker's precondition can never be met, so rulekit's "author DM-JSON → `checkConsistency`" oracle **cannot author or verify** a `ValueNotConsistent` rule. It is **un-buildable within single-document-model scope** — same root cause as multi-form/Vordruck (needs infrastructure outside the document model), and it makes the would-be "dynamic-enum modelkit authoring" moot (there is nothing in DM-JSON to emit). Stays a tolerant `ReadResult.Opaque` if ever encountered. *(Demonstrated by probe; not locked by a test — there is no expressible fixture to lock.)*

## Header `modelVersion` compatibility — same-major and not-newer than the kernel's model-format (probed 2026-06-12)

|---|---|---|
| `28.4.0` | valid | exact |
| `28.0.0` | **valid** | same major, **≤** app-format → backward-compatible |

## §5 supplement — tolerance boundary + comparison rescaling (runtime, 2026-06-10, RT-semantics drain)

- **`DiffersWithToleranceRange{N}` fires strictly beyond the tolerance**: satisfied iff `|a − b| > N` — a difference of *exactly* N is still within tolerance and does **not** fire, in either direction. The boundary is the trap a modeller would guess either way. *(Locked: `adapter.laws.ToleranceComparisonLawsTest`.)*
- **Source-only (not externally observable):** the comparison engine rescales both numeric operands to scale 19 `HALF_UP` before comparing (`BedingungsOperatorHelper.vergleiche`). Model number types cap fractional digits far below 19, so no legal model can surface the rounding — recorded as a source fact, deliberately not law-locked (nothing observable to lock).
- **The rounding operators are directional, not truncation** (`BigDecimalUtils`, second drain): `RoundDown` is **FLOOR** (toward −∞: `RoundDown(−1.4) = −2`), `RoundUp` is **CEILING** (`RoundUp(−1.4) = −1`), `RoundAccounting` is **HALF_UP** (away from zero on the .5 boundary, both signs). The negative-value behavior is the modeller trap — "down" does not mean "toward zero".
- **A scale-19 `HALF_UP` pre-rounding precedes every target-scale rounding** — and here it *is* observable: division artifacts can't leak through a rounding, `RoundDown([q]/3*3, 0) == [q]` fires for `q=1` (without the pre-round, the internal `0.99…9` would floor to 0). *(Locked: `adapter.laws.RoundingLawsTest`.)*

## Condition comments — `;;` line comments are concrete syntax: tolerated; rulekit authors them and preserves the leading one (grammar + 2026-06-12)

The condition lexer defines comments — `Base_ConditionLexer.Comment: ';;' ~('\r'|'\n')* …` — so `;;` begins a **line comment** (continued across lines that each restart with `;;`), parsed *around* a `teilBedingung` (GRAMMAR-LEDGER). So the kernel **validates a commented condition** — comments are read-tolerated. But a comment is **concrete syntax not carried in the parsed AST**: the kernel ships `ConditionFormatter.stripComments` to remove it, and rulekit's typed AST stores none.

rulekit's treatment of this kernel fact (detail: KERNEL-INTEGRATION-NOTES "Condition comments"): comments live in a **side-channel** beside the AST (`rulekit.dsl.Comments`, keyed by node identity, covering both a `Condition` branch and a `Calculation` operation), so they can be **authored** — on a rule (`Rule.Builder.comment/commentAfter`) and on a **computation**, its operations *and* its preconditions (`Computation.Builder.comment(...)`) — rendered as `;;` lines the kernel accepts. A **rule's leading comment is preserved by default** through read→modify→write-back (`Comments.preserveLeading`, applied in `ModelWriter.replaceCondition`); a **computation's** leading comments (its common precondition + first operation) are likewise preserved on modify (`ModelWriter.replaceComputation` rebuilds the element, so the old slot comments are carried — per-alternative matching across a re-expression stays positional/out of scope). The residual **#3 lossiness** is now only *inline/trailing* comments and non-canonical formatting: an AST-based re-render still drops those (the AST has no node to anchor a mid-expression comment to across a re-expression). `KernelAdapter.diff` discloses exactly that — it carries the leading comment on both sides and flags *"inline/trailing comments are not preserved by re-rendering (the leading comment is carried over)"* only when such a comment exists. A rule you don't modify keeps its text verbatim (edits are surgical on the DM-JSON). The concrete-syntax-preserving (minimal-edit) re-render that *would* keep every comment in place is the parked Phase-5 residual (PROJECT-DESIGN §16); the side-channel is the cheaper, chosen alternative for the common (leading-comment) case.

*(Locked: `adapter.ConditionCommentLossinessTest` — a leading comment is preserved (carried in `diff.after`, not flagged lossy) and an inline/trailing one is dropped with the loss disclosed; `adapter.CommentRoundTripTest` — read→modify→write-back keeps the leading comment with no manual sourcing; `rulekit.dsl.CommentRenderTest`/`RuleCommentTest` — the side-channel render + typed authoring; `rulekit.dsl.ComputationAuthoringTest` — comments on a computation's operations + preconditions, kernel-accepted. rulekit treatment: KERNEL-INTEGRATION-NOTES "Condition comments"; kernel API: KERNEL-RULE-API-SURVEY `stripComments`.)*

### §6 supplement — DATE/DATERANGE/TIME field *format strings* are a fixed lowercase allowlist, locale-independent (probe 08, 2026-06-22)

A field's declared date **format** must be a **lowercase Java date pattern** from a **fixed allowed set** — and that set is **independent of the model's display locale AND its `conditionLanguage`** (verified: `en_US` and `de_DE` conditionLanguage accept the identical set). The A12 editor's UPPERCASE preset labels (`YYYY-MM-DD`, `MM/MM`, …) are display labels, **rejected** as `format` values (`The date range format is invalid` / `The date format is invalid` — a kernel rejection carrying **no code and empty `where`**). - **DATE** — both `yyyy-MM-dd` and `dd.MM.yyyy` validate; `YYYY-MM-DD` rejected.
- **DATERANGE** (`format` + `separator`) — the **(format, separator) pair** is allowlisted, not free: verified-accepted **`dd.MM.yyyy`+`-`** and **`yyyy-MM-dd`+`/`** (identical under en_US and de_DE). - **DATEFRAGMENT** — lowercase `MM`/`yyyy`/`yyyy-MM`/`MM-dd` accepted; uppercase rejected. (Partial dates are DATEFRAGMENT, not DATERANGE.)
- **TIME** — the **full `HH:mm:ss` is required**; `HH:mm` (no seconds) is rejected.

### §6 supplement — Valid/Invalid over a constructed date are NOT complements (runtime, 2026-06-17)

`Valid(Date(...))` fires only when **all referenced parts are specified AND** they form a real calendar date; `Invalid(Date(...))` fires when the date is impossible (e.g. 31 February) **OR any referenced part is unspecified**. So they are **not logical complements** — an unspecified part fires `Invalid` but not `Valid` (runtime-verified). To fire `Invalid` only on a *complete-but-impossible* date, prefix `AllFieldsFilled(...)`. (BA "Valid or invalid dates"; corrects the catalog's earlier "Invalid = negation of Valid".) *(Locked: `adapter.laws.DateValidityLawsTest`.)*

**The BA's "1583 Gregorian floor" (L3833) is NOT observed at runtime (probed 2026-06-17, not locked).** BA says a `Date(...)` is invalid if "the resulting day is before 16 October 1583", but `Invalid(Date(1,1,1500))` does **not** fire — the runtime (`validateFull`) treats `01.01.1500` as a valid constructed date (verified with a wide-year fixture; the same rule fires correctly for an impossible date, so the mechanism works). So the floor is **not a runtime Date-construct criterion in 30.8.1**; if enforced at all it is at another layer (a field-level formal error on a pre-1583 value, or the editor), which this pass did not verify. (A 4th BA-vs-source/runtime discrepancy found this review, after `INVALID_INTERVAL`, the semantic-index operator, and the fragment-comparison code.)

### §6 supplement — date-fragment comparability partition (probe-confirmed, 2026-06-17)

Without a base year, two date(-fragment) values compare (`==`/`!=`/ordering) **only if both carry a year or neither does** — a year-bearing fragment/full date and a non-year fragment are incomparable, rejected with **`MVK_INVALID_COMPARE_TO_DATE`** ("only allowed to compare dates with other fitting dates"). ## §2 supplement — the filled-count aggregates (2026-06-04 experiments)

`NumberOfFilledFields` / `NumberOfFilledGroups` (DE: `AnzahlAngegebenerFelder`/`AnzahlAngegebenerKontexte`; the grammar's `feldListenAnzahlOp` — its third sibling `NumberOfDifferentValues` is also implemented, see the list-aggregate slot laws below) are **numeric expressions**, freely comparable and usable in arithmetic (`NumberOfFilledFields(a, b) + 1 < [Q]` validates). Slot rules:

- **`NumberOfFilledFields` needs more than one field *or* at least one group *or* a single flattened repetition list** — a single plain field draws **`MVK_PARAMSIZE_INVALIDN`** ("There must be more than one field or at least one group"), but a single wildcard scope `Group*/field` is accepted (it counts filled reps). The group form counts the filled fields *inside* the group(s); multiple groups are legal. Field kinds may be **mixed** (boolean, enum, number together — it counts presence, not values).
- **`NumberOfFilledGroups` needs more than one group *or* a single repeatable group as a wildcard scope** — two-or-more *distinct* groups are legal, and so is **one repeatable group written `Group*`** (counting that group's filled repetitions, kernel-verified 2026-06-06 against `NumberOfFilledGroups(/Order/Items*)`). A single *non-repeating* group still draws **`MVK_PARAMSIZE_INVALIDGN`**; a field argument draws the type-direction code **`MVK_NO_FIELDS_ALLOWED`**.

- Comparing the count to a **decimal literal** (`<= 1.5`) is accepted (consistent with the §5 literal-scale exemption).

*(Locked: N7 examples of both operators incl. the param-size/type-direction invalids; `NumberOfFilledGroups`'s sole-starred-root-group **acceptance** in `validate.laws.RootGroupCountLawsTest`; the `NumberOfFilledFields` root-group ban pre-checked in `CountAggregate` — `dsl.operators.AggregateConditionTest`. **Runtime counting semantics (2026-06-10, RT-semantics drain — `anzahlAngegebenerEntities`):**

- **A formal-error operand makes the whole count non-evaluable** — the rule is suppressed; the broken field is neither counted as filled nor skipped (contrast `FirstFilledValue`, where a broken operand *after* the first filled one is invisible).
- **The count can grow but never shrink**: with unfilled operands left, a fired comparison is an `OMISSION_ERROR`; with every operand filled, a `VALUE_ERROR` — a plain field list has no omitted-tail problem (unlike the starred aggregates, §9 supplement).

## §8 supplement — the value-list membership family (2026-06-04 experiments)

Five operators in two grammar shapes, not covered by KERNEL-SEMANTICS. **Shape A** `FieldValueIncludedInValueList(field, v1, …)` / `FieldValueNotIncludedInValueList(…)` (DE: `FeldWertInWerteListe`/`FeldWertNichtInWerteListe`); **shape B** `AtLeastOne|No|NotAllFieldValue(s)IncludedInValueList(f1, f2 In v1, …)` (DE: `MindestensEin…`/`Kein…`/`NichtAlle…`; `In` is a language-independent grammar literal like the symbols). ## §9 supplement — per-row iteration + aggregation of missing rows (runtime, 2026-06-06)

The first **runtime** (fires/does-not-fire) checks of §9, via the multi-row `RuntimeLaws.Doc` builder:

- **Per-row iteration.** A rule whose error field reaches *through* a repeatable group is evaluated **once per existing row**, and each message attaches to **that row** (the pointer carries the row index). Verified: rule in `/Order`, error field `Items/Count`, condition `[Items/Count] > 50` over three rows `10/80/90` → fires **twice**, on `/Order/Items/Count [1, 2, 1]` and `[1, 3, 1]` (rows 2 and 3); rows `10/20/30` → fires nowhere.
- **Aggregation of missing rows.** `Sum` substitutes `0` for an empty field (so empties neither error nor suppress the aggregate): `Sum(Items*/Count)` over `40, _, 40` is `80`; over an all-empty list is `0`. `MaxValue` ignores empties: over `40, _, 10` it is `40`.
- **`GroupFilled` = the row exists, not that it has data.** `GroupFilled(Items)` fires for a created Items row whose `Count` is empty, and not when there is no Items row at all.
- **`RepetitionNotUnique`** (no `*` wildcard — the asterisk draws `MVK_NO_WILDCARDS_ALLOWED`) fires on each duplicate row of a non-index field: `Count` values `5, 5, 9` → fires on rows 1 and 2, not row 3. The **index field** already carries *built-in* uniqueness — duplicate index values raise the kernel's own `uniqueIndex` formal error regardless of any author rule, so `RepetitionNotUnique` on the index field is redundant.
  - **Placement is exacting (validate-time, verified 2026-06-22, probe F06-1).** The rule must sit at the **PARENT** of the repeated group with the error field **inside** it — `RepetitionNotUnique(Items/Sku)` is accepted only with rule group `/Order` + error field `/Order/Items/Sku` (verified VALID). The CLI's default grouping (rule group = the error field's own parent) puts the rule *at* `/Order/Items`, where the same condition draws **`MVK_INVALID_ENTITY`**; with a non-repeatable error field (rule at `/Order`, field `/Order/CustomerName`) it draws **`MVK_NO_WILDCARD`** — so `MVK_NO_WILDCARD` here is *not* a "missing asterisk" (the operator forbids one) but a wrong-scope signal. Author it with the rule group at the parent — `rule check --group /Order --field /Order/Items/Sku` — and **persist with the same `group` key** (`rule add` / `apply rule add` accept it, mirroring `rule check --group`, so a checked rule round-trips; F06-3, 2026-06-22). `MVK_NO_WILDCARD` is a **shared** code (also CurrentRepetition, aggregates, model-scope `GroupFilled`), so its enriched fix is generic — KERNEL-INTEGRATION-NOTES "Structural-code fix hints" (F06-2). The catalog (`RepetitionNotUnique` gotchas) and `FieldValuesNotUnique(Items*/Sku)` (the asterisked, no-`--group` alternative for plain cross-row uniqueness) are the authoring paths.
- **Parallel iteration** — two repeatable groups keyed by a shared index field are iterated jointly as an **outer join** over the index values; a value present on one side only counts as **"not specified"** on the other. Verified on an own-domain `staffing` fixture (`Demand`/`Supply`, both keyed by `Department`): `FieldsNotCollectivelyFilled(Demand/Headcount, Supply/Headcount)` with Demand=`{Sales, Eng}` but Supply=`{Sales}` fires once, on the `Eng` Demand row (its Supply side is not specified); when every Department is matched on both sides it fires nowhere. *(Locked: `adapter.laws.RepetitionLawsTest`, `adapter.laws.RepetitionNotUniqueLawsTest`, `adapter.laws.ParallelIterationLawsTest`.)*

## §9 supplement — a rule/computation's ITERATION SCOPE is its set of referenced repeatable fields, not its node placement (corrected + matrix-verified, 2026-06-21)

> **Correction (2026-06-21):** an earlier note here claimed a `field move` *into or out of* a repeatable group is rejected `MVK_ERROR_FIELD_NOT_IN_RULEGROUP` and motivated a planned "co-move the bound rule/computation" enhancement. A full directional matrix (authored via `rule add`/`computation add`, validated through the kernel) shows that was **directionally wrong** and the enhancement is a **non-goal**. The verified truth follows.

A rule's **error field** and a computation's **computed field** are stored as a *relative* path (`errorEntityRelPath` / `computedFieldRelPath` = `"../F"`). But the kernel derives a rule/computation's **iteration scope from the repeatable fields it *references*** (the error/computed field **plus** every per-row operand), **not** from where the rule/computation node physically sits. The law: the error/computed field must **share the iteration scope** of the referenced repeatable operands. (Locked by `validate/laws/IterationLawsTest.errorFieldMustShareTheIterationScopeOfTheReferencedRepeatableFields`.)

Consequence for a reference-rewriting **`field move`** of F (matrix-verified, symmetric for rules *and* computations):

| `field move` of F | bound rule/computation (error/computed field = F) | why |
|---|---|---|
| → **into** a repeatable; the rule/comp node is at the outer scope | **accepted** — node stays put, reaches *down* (e.g. `errorEntityRelPath ../Items/DeliveryDate`, `computedFieldRelPath ../Rep/X`); the error/computed field then drives the per-row iteration | the error field inside the repeatable *is* the iteration scope; per-row operands resolve consistently |
| → **out of** a repeatable; the rule/comp references **only** F + outer/constant fields | **accepted** — node stays put, reaches *out* (`../../Qty`); nothing forces per-row iteration any more | no referenced operand is per-row, so error field + operands are all in one (outer) scope |
| → **out of** a repeatable; the rule/comp **also** references another field still **inside** the repeatable | **rejected** `MVK_ERROR_FIELD_NOT_IN_RULEGROUP` (or `MVK_NO_WILDCARD` on the operand side) | a genuine **cross-cardinality split**: F is now single-valued while a referenced operand stays per-row |

So a `field move` is rejected **only** when it would genuinely split a rule/computation across two cardinalities — and that case is **not mechanically fixable**: relocating the node ("co-move") leaves the cross-scope operand reference intact, and the *only* valid repair is to **rewrite the rule's logic** (e.g. wrap the per-row operand in an aggregate: `X = [Rep/P] * 2` → `X = Sum(Rep*/P)`), a modeling decision the tool must not invent. The existing reference-rewriting `field move` therefore already accepts every *semantically valid* cross-boundary move and correctly refuses the genuinely-broken ones; **`field move` co-move adds no capability → non-goal** (CLI-SPEC §6; FEATURE-GAPS-LEDGER §4). *(All behavior here is the kernel's; rulekit just lets the kernel's gate refuse the split, with `model validate` as backstop.)*

## §9 supplement — the kernel tolerates an index field on a non-repeatable group (probe-observed, 2026-06-21)

A group's `indexFieldName` (the repetition row-key) is **not** kernel-gated on repeatability: a `repeatability: 1` (single) group carrying an `indexFieldName` that names a direct-child field passes `checkConsistency` (probed via raw DM-JSON + `model validate` → `valid: true`). But it is a **degenerate** row-key — with no repetitions, the uniqueness check (`RepetitionNotUnique`) it would arm is vacuous and parallel iteration has nothing to iterate. So **modelkit/CLI deliberately forbid it** (`ModelDocument.setIndexField` / `group modify --index-field` require a repeatable group): the index field only earns its keep on a repetition list. **Prose-only by design** (the consumer for the kernel-tolerance fact is nobody — we refuse the degenerate case; *our* behavior is locked by `GroupModifyVerbTest.indexFieldOnANonRepeatableGroupIsRejected`, the G24 surface). This resolves the SME 1184 question (the non-repeatable allowance) — the kernel allows it, we don't, on purpose.

## §9 supplement — wildcard slot laws (slice 7a, 2026-06-04 experiments)

The `*` suffix is per path segment (grammar `idNameRef: idName '*'?`) and builds a **repetition list**; whether it is legal depends purely on the *slot*:

- **List slots accept starred paths**: the field-list quantifiers (`AtLeastOneFieldFilled(Addons*/Name)` …), shape-B value lists (`…(Addons*/Name In "x")`), and the count/`Sum` aggregates — iterating rule or not, and **mixing plain and starred operands in one predicate is legal**.
- **Scalar slots reject them** with **`MVK_NO_WILDCARDS_ALLOWED`** ("It is not allowed to use an asterisk"): `FieldFilled(Addons*/Name)`, a bracketed value `[Addons*/Fee]`, `GroupFilled(Addons*)`, and shape A's single-field slot.
- A star on a **non-repeatable** group is its own code: **`MVK_INVALID_WILDCARD`** ("Since 'X' is not repeatable…").
- **The negativity law (`MVK_NEG_CONDITION_IN_ITERATION`) is not an operator list** — the kernel's `IterationNotValidVisitor` (~800 lines) classifies each condition as positive/negative *in context*: the same operator flips depending on whether its operands reference the iteration (e.g. `FieldFilled(A)` is "negative" when `A` does *not* iterate but the rule does), and aggregate comparisons against constants are negativity-sensitive by comparison direction (`< / <= / != n`, `== 0`-style forms). rulekit deliberately does **not** replicate this — kernel-delegated to F4.
- **`MVK_NO_WILDCARD` (missing star) is not naively pre-checkable**: under *parallel iteration* (joined repeatable groups via same-name/type index fields) plain references to another repeatable group are legal — the pre-check waits for slice 7e's iteration model.
- **Wildcard propagation down nested repeatables (§10, 2026-06-06):** when a path flattens an outer repeatable with `*`, **every repeatable group below it on the path must also be starred**. Verified on the nested-repeatable `project` fixture (Milestones ▸ Tasks): `Sum(Milestones*/Tasks/Effort)` (outer `*`, plain inner) → **`MVK_NO_WILDCARD`**; `Sum(Milestones*/Tasks*/Effort)` accepted; and a single `*` over the outer repeatable's own field (`Sum(Milestones*/Budget)`) is fine.
- **Keyword-named fields need single-quoting in a path (§10):** a field literally named like a language keyword (the `project` fixture has one named `Date`) is rejected unquoted — `FieldFilled(Date)` → **`MVK_UNEXPECTED_TOKEN`** — and accepted single-quoted: `FieldFilled('Date')`.
- **Relative `..` + `*`: the star may not be on a `..` part (§10).** The kernel message is precise — *"In a relative path containing `..`-notation, the `..` parts may not use the `*` symbol."* So `../Items*/Count` (star on a *named* segment) is fine, but **starring the `..` itself** — `Sum(..*/Budget)` from an inner rule, to reach all repetitions of an ancestor repeatable — is rejected with **`MVK_INVALID_WILDCARD_REL`**; use the absolute form (`/Project/Milestones*/Budget`). (This is why my earlier shapes, with `*` on named segments, all passed.)
- **`fieldRefByShortNameAllowed` does not gate short-name at the consistency tier (§10).** Setting it to `false` did **not** make a bare short-name reference (`[Quantity]`) reject under `checkConsistency` — short names resolve regardless here, so that flag's enforcement lives elsewhere (editor/UI or another pass), not in rule consistency. A fact, not a reject law. *(Locked: `validate.laws.PathLawsTest`; fixture `models/project.dm.json` — the first committed model with nested repeatable groups + a keyword-named field.)*
- **The kernel ships a reference-rewriting engine for rename/move — `MoveSupportDM` (§10, 2026-06-12).** `MoveSupportDM.changePathReferencesForMove(documentModel, Map<oldPath,newPath>)` (internal, `@OnlyForUsage`, `kernel-md-model/a12internal/services`) rewrites every reference to the moved paths — rule conditions, error texts, computations (preconditions/operations/common precondition), the error/computed-field refs, **and a group's index-field and sort-field relative references** — preserving absolute-vs-relative style. (The index/sort-field rewrite is a no-op when a non-repeatable group is merely re-parented — the relative path to its own child is unchanged — but it matters for a repeatable group; the kernel handles it from the same `entityMoves` map either way, one more reason to rewrite references through this engine rather than by hand on the JSON.) It does **not** move the element itself — the caller does that afterward, confirmed by the method's own javadoc (*"the rules and computations themselves are NOT moved … Moving … must be done by the caller afterward"*); rulekit's `ModelDocument.moveField/moveGroup` is that caller-side relocation, kept in our authored-JSON surgery so source fidelity (comments/ordering) survives. **Starred-group references DO follow a group rename:** `Sum(Items* / Amount)` becomes `Sum(Lines* / Amount)` when `/Order/Items` → `/Order/Lines`, via dedicated `starredGroupsNewFullnames` handling — so `MoveSupportInternal`'s blanket javadoc limitation #6 ("References with * are not touched") is **misleading** for the group-rename case (narrower `*` edge cases may still not rewrite; the kernel re-validate is the backstop). rulekit wraps this at the N8 boundary as `adapter.ReferenceRewriter`; it is the engine that turns *refuse-if-referenced* rename into a *reference-preserving* rename/move (FEATURE-GAPS §3.1). *(Locked: `adapter.ReferenceRewriteTest`.)*
- **`getDirectlyReferencedEntities` is the canonical "what does this rule reference" set — operands included, not just the error-attached field (§9/§10).** The kernel's `getDirectlyReferencedEntities(IRule, IProblemReporter)` returns **every** field/group a rule's condition reads (the operands), and for a calculation rule it spans all four sites: the computed field, the common precondition, each alternative's precondition, **and each operation expression** — so a field read *only* inside a computation's operation is in the set even though a plain rule scan would miss it. This one primitive is the shared oracle for all three reference queries, which is why they can never disagree: **`where-used`** is its inverse (`whereUsed` over validation rules + `whereUsedInComputations` over calculations — kept as separate kinds because a calculation is also an `IRule` in `getAllRules()`), **`rule explain`/`computation explain`'s `references`** is its forward projection, and the **safe-delete cascade** is its membership test. It needs no rulekit converter coverage (it's the kernel's own answer over the bound rule), so it works even for `Opaque`-to-rulekit conditions. rulekit treatment + the consumer-facing contract (the referrer/referent symmetry, delete-cascade vs rename/move-rewrite, the query verbs): CLI-SPEC §6 "What counts as a reference". *(Locked: `adapter.WhereUsedInComputationsTest` — incl. `operandReferencedOnlyInAComputationIsFoundViaTheComputationLeg`; `cli.WhereUsedVerbTest`, `cli.RemoveVerbTest`.)*

*(Locked: `validate.laws.IterationLawsTest`; rulekit treatment: `FieldOperand` = `FieldRef` | `FieldListRef`, list slots take the operand union, scalar slots take `FieldRef` — `BoundModel.flatten(starPath)` validates star placement.)*

## §9 supplement — `CurrentRepetition` + the index-field/semantic-index cluster (slices 7e/7f, 2026-06-04 experiments; retitled 2026-06-10 — the constant-form semantic index IS supported, only the entity/`$` forms stay kernel-delegated)

`CurrentRepetition` (DE `AktuelleWiederholung`; grammar `groupOp: 'AktuelleWiederholung' '(' entitySpec ')'`) is a **numeric expression** — the current iteration index of a group.

- **Takes a group, not a field** — a field argument → **`MVK_NO_FIELDS_ALLOWED`** ("Only groups or root groups are allowed"). Structural: `Dsl.currentRepetition(GroupRef)`.
- **The rule must iterate over that group** — from a non-iterating rule it draws **`MVK_NO_WILDCARD`** ("Missing specification of an asterisk"). Position-dependent → kernel-delegated (like the RNU position law).
- **A non-repeatable group is tolerated** (its index is constant) — `CurrentRepetition(/Subscription/Billing)` from an iterating rule validates.

**No positional repetition operator — a row is addressed by semantic *key*, never by index (grammar-verified, 2026-06-16).** The grammar exposes exactly one `groupOp` (`groupOpName: 'AktuelleWiederholung'`) and one way to address a specific row — the `Fuer`/`For` **semantic index** (`entitySpec: … ('Fuer' semanticIndex)`, with `semanticIndex: entitySpec | StringLiteral`). So `CurrentRepetition` *yields* a row's index as a **number** (compare it, self-exclude via the `$` correlation), but you **cannot use a number to *select* a row**: there is no `[Field At n]`, no "current + 1" neighbour, no positional offset. `[Field For "key"]` keys on the index *field's value* (a string constant or another entity), not on a repetition position. Consequence for rulekit: a `date.atRepetition(n)`-style positional API is a non-starter — it would invent syntax the kernel lacks; the only repetition-indexed *date* read that could ever ship is the semantic-index `For` form, mirroring `NumberRef.forIndex`. The construct inventory is CI-locked by `adapter.KernelConstructParityTest` (operator set) + `GrammarProductionLedgerTest` (productions, opt-in vs the `../a12-kernel` checkout) — a kernel that later *added* a positional operator would trip them.

**Slice 7f (2026-06-04, with an index-field fixture).** A repeatable group declares an index field via **`"indexFieldName": "<containedField>"`** (own-domain fixtures `logistics.dm.json` — `Lines`/`Picks` keyed on `LineRef`; `order.dm.json` `Items` keyed on `Sku`). With that:
- **Semantic index `[Field For "value"]`** (DE `Fuer`) selects the repetition whose index field equals `value` — **works for a string constant**; the field's group must declare an `indexFieldName` else **`MVK_NO_INDEX_FIELD`**. An *entity* index that itself iterates is rejected (**`MVK_SEMANTIC_INDEX_INVALID_ITER`**) — so rulekit supports the constant form (`NumberRef.forIndex(String)`); the entity/`$` forms stay kernel-delegated. (Enum/string `forIndex` deferred — only `NumberRef` for now.)
- **Parallel iteration needs no construct** — two repeatable groups sharing a same-name/type index field iterate jointly; a rule referencing both (e.g. `FieldsNotCollectivelyFilled(Lines/OrderedQty, Picks/PickedQty)`, or a field-vs-field cross-compare) validates with *existing* handles. rulekit supports it by *not interfering*.
- **`MVK_NO_WILDCARD` (missing asterisk) confirmed correctly kernel-delegated**: under parallel iteration a *plain* cross-group reference is **legal** (`FieldFilled(OrderedQty) And FieldFilled(/Shipment/Picks/PickedQty)` validates) — so a naive "repeatable group needs `*`" pre-check would false-positive. The pre-check would require full iteration-model analysis (does the rule parallel-iterate?); deliberately left to F4.

## §9 supplement — the `Having` filter and `$` correlation (slice 7d, 2026-06-04 experiments)

`Having` (DE `Mit`; grammar: `'Mit' bedingung` on an `entitySpec`) filters a `*`-repetition list before an aggregate/quantifier consumes it; `$` (`DOLLAR`, language-independent) pins a reference to the rule's outer repetition inside a filter.

- **`Having` requires a starred (flattened) field** — on a plain reference it draws **`MVK_WILDCARDS_REQUIRED`** ("At least one asterisk needs to be specified for the filtered field"). So it lives on `FieldListRef`, not on plain `FieldRef`.
- **It attaches in any list slot** — verified inside `Sum`/aggregates *and* the field-list quantifiers (`AtLeastOneFieldFilled(… Having …)`).
- **Filter-condition exclusions** → **`MVK_DISALLOWED_CONSTRUCT_IN_FILTER_CONDITION`** ("The language feature 'X' is not supported for filter conditions"): verified for `RepetitionNotUnique` and a **nested `Having`**; KERNEL-SEMANTICS §9 also lists `CustomCondition`, a semantic index, and a parallel iteration. rulekit pre-checks the two representable ones (RNU + nested Having); the rest stay kernel-delegated.
- **`$` is filter-only** — outside a filter it draws **`MVK_INVALID_OUTER_ITERATION`** ("The symbol '$' to specify rule iteration is only allowed inside filter conditions"). A valid use correlates inner to outer: `Sum(/S/Addons*/MonthlyFee Having [/S/Addons/Name] == [$/S/Addons/Name]) > 0`. (`$` on the *filtered* side without a non-`$` inner ref → `MVK_NO_ITERATION_FOR_WILDCARD` — the filter must reference a field in a starred level.)
- **Why `$` exists — `MVK_INVALID_ITERATION_IN_FILTER_CONDITION`** (from the kernel-team BA doc `a12-kernel/documentation/_merged/kernel-ba.md`, cross-checked 2026-06-07). Inside a filter you may only iterate over the repetition levels the **filtered field** stars; a reference to a field that iterates over a *different* group is rejected — `Sum(K*/G Having [K/F1] == [L/F2])` errors because `L/F2` iterates over the un-starred group `L`. The **only** fix is the `$`: `[$L/F2]` pins that reference to the outer iteration. So `$` is not optional sugar — it is the sole way a filter references an out-of-scope (outer) field. **Path notation is unrestricted** (any path valid without `$` is valid with it: `$/A/F`, `$L/F`, `$F`).
- **`$` correlation is implemented (2026-06-07, both directions) — was "deferred", now landed.** The marker is an `outer` flag on the AST value nodes (`FieldValue`/`EnumCategoryAccess`/`CurrentRepetition`), set by `.outer()` on the handles, rendered as `[$path]`/`($group)`. It threads through every field-vs-field comparison kind (number/string/date/enum/category), `CurrentRepetition($group)`, **presence predicates** (`NoFieldFilled($a, $b)` via `FieldRef.outer`), **value-list operands** (`FieldListRef.outer`), and filtered field-list quantifiers (`AtLeastOneFieldFilled(… Having …)`) — **every `$` position in Corpus-1 converts (0 `$` opaques)**. **Runtime-verified, not just structural:** the correlation fires on the rows that share an outer-row value and nowhere when distinct; the `CurrentRepetition(G) != CurrentRepetition($G)` self-exclusion is load-bearing (without it every row matches itself); and combined with `CurrentRepetition(G) < CurrentRepetition($G)` it expresses "all predecessors" — the kernel BA doc's reviewed "holidays not in chronological order" example, transferred to a schedule domain. Corpus-1 read reached 95.0% on the back of this.

*(Locked: N7 `Having` valid + `MVK_DISALLOWED_CONSTRUCT_IN_FILTER_CONDITION` invalid + `FieldListRef.having` pre-checks — `dsl.operators.IterationConditionTest`. `$` authoring kernel-valid — `adapter.OuterCorrelationAuthoringTest`; read round-trips — `adapter.OuterCorrelationReadTest`/`OuterCorrelationQuantifierReadTest`; the N8 count-check that keeps an un-threaded construct Opaque — `adapter.OuterCorrelationBackstopTest`; the **runtime behavior** — `adapter.laws.CorrelationLawsTest`. `Having`'s starred-field law stays structural (only `FieldListRef` offers it).)*

## §9 supplement — aggregate uncertainty + `FirstFilledValue` prefix sensitivity (runtime, 2026-06-10, RT-semantics drain)

The aggregate combiners track whether their result *could still change if more fields were filled*, and that uncertainty is observable through the message typing (§12 supplement below). Drained from `Combiner`/`NumberCombiner`/`FirstValueCombiner`/`NumberOfDifferentValuesCombiner`:

- **A starred aggregate over a repeatable group stays omission-typed even when every *instantiated* row is filled** — the un-instantiated remainder of the declared repeatability counts as an omitted, fillable tail. Only **exhausting the repetition** (all declared rows instantiated and filled) makes the fired comparison a value error. *(The probe corrected the naive source-read here, which expected the filled instance to be certain.)*
- **`NumberOfDifferentValues` counts distinct *filled* values only** — an empty operand never bumps the count, but it keeps the count growable (omission-typed).
- **`FirstFilledValue` is prefix-sensitive — operands after the first filled one are never read.** A formal error *after* the first filled operand is invisible to the rule; *before* it, it suppresses the rule (unknown state); an *empty* operand before it types the fired comparison as an omission error.
- **The date aggregates (`MaxValue`/`MinValue` over a DATE scope) follow the same uncertainty laws** — omitted tail ⇒ fillable, exhausted repetition ⇒ certain, and an empty operand keeps the result fillable. Probe-corrected source-read (second drain, 2026-06-10): the date combiner has *no* per-operand empty tracking, yet the typing comes out like the number combiner's — the not-given flag travels inside the `VkDate` value through `max`/`min`.

*(Locked: `adapter.laws.AggregateUncertaintyLawsTest` + `adapter.laws.FirstFilledValueLawsTest`.)*

## §9 supplement — `RepetitionNotUnique` slot laws (slice 7b, 2026-06-04 experiments)

- **The rule sits at the parent**: every key field must have at least one repeatable group **between the rule group and the field** (or sit directly in a repeatable root group) — `RepetitionNotUnique(Addons/Name)` from *inside* `Addons` draws **`MVK_REPEATABLE_GROUP_MISSING`**; the same condition from the parent validates. Position-dependent → kernel-delegated, not pre-checked.
- **Keys are plain fields**: a group argument → `MVK_NO_GROUPS_ALLOWED`; a starred path → `MVK_NO_WILDCARDS_ALLOWED` (the iteration is implicit). **Composite keys** (several key fields) are legal. A key mixing in a non-repeatable field (e.g. `Tier`) → `MVK_REPEATABLE_GROUP_MISSING` for that field.
- **The rule must iterate** — with a non-iterating error field the plain key path draws the ordinary `MVK_NO_WILDCARD` before any RNU-specific check.
- **All keys must lie on a single path** — keys spread across two *parallel* repeatable groups (e.g. `Lines/LineRef, Picks/LineRef` on the logistics fixture) draw **`MVK_NOT_IN_SAME_PATH`**; `RepetitionNotUnique` cannot span a parallel iteration (source `CheckEntityListenUtils.checkAllRepeatableGroupsOnSamePath` — no longest-shared-path across the repeatable refs ⇒ throw; probe-confirmed 2026-06-17).
- **`@From`'s reference group must be repeatable** — `@From /Subscription` (root, non-repeating) draws **`MVK_GROUP_NOT_REPEATABLE`**; and the **keyed fields must descend from that `@From` group** — `RepetitionNotUnique(Lines/LineRef @From Picks)` (key in Lines, scope Picks) draws **`MVK_NOT_IN_GROUP`** (source `CheckEntityListenUtils.checkAllEntitiesInGroup` — each key's parent path must start with the `@From` group path; probe-confirmed 2026-06-17). Note `@From`/`@Von` is a **localized keyword** (lexer-bundle token `VON`), unlike the language-independent `In` separator.
- **`FieldValuesNotUnique` (DE `FeldWerteNichtEindeutig`) is a separate, plain field-list predicate** (the grammar's `feldListenBedingung` family, not `wiederholungBedingung`): cross-field distinctness over plain or starred operands — both shapes kernel-verified.

*(Locked: `validate.laws.IterationLawsTest` + N7 `RepetitionNotUnique`/`FromScope`/`FieldValuesNotUnique` examples; `@From` repeatability pre-checked in `RepetitionNotUniqueCondition.from`.)*

## §11 supplement — computation alternatives and the calculated-field ban

- **Alternatives are all-or-nothing about preconditions**: either a single alternative *without* a precondition, or several that *all* carry one — mixing a precondition-less "otherwise" in is rejected with **`MVK_ERROR_EMPTY_PRECONDITION`**. The default branch must be an explicit complementary precondition (as the demo's `BonusComp` does with `[WeekPay] < 500`).
- The computed field may not be referenced in preconditions **nor in operations** — both directions draw the same **`MVK_ERROR_REFERENCE_TO_CALCULATED_FIELD`** (KERNEL-SEMANTICS §11 states the precondition half). **The ban is on a *direct field* reference, not the field's containing group** (BA-doc cross-check, 2026-06-08): guarding a *repeatable* computed field with `GroupFilled`/`CurrentRepetition` on its **containing group** is kernel-legal — it's exactly the BA doc's current-repetition pattern (`CurrentRepetition(RuleGroup) == 1 → "…"` where the computed field lives in `RuleGroup`). rulekit's pre-check therefore uses **exact field-match** (`ConditionReferences.referencesField`), not the group-prefix `covers()` it uses for the rule error-field check — the earlier `covers()` over-rejected this valid shape.
- A wrong-kind operation (string expression into a number computed field) is **`MVK_INVALID_COMPARE_TO_ENUM_OR_STRING`**.
- Computations require error text like rules do (`MVK_ERROR_MESSAGE_MISSING`).
- **Runtime evaluation (RT-semantics drain, 2026-06-10):** with **overlapping preconditions, the first declared alternative wins** (declaration order is the tie-break; the computed value is scale-normalized — `1.00` lands as `"1"`). **Division by zero computes nothing** — no value, no error outcome — and **clears** a stale previously computed value, so an invalid input never leaves a wrong value standing (the computation-side face of §5's "evaluates quietly"). Consistency-tier corollary: a bare **division has unknown scale** and cannot assign to a scaled computed field (`MVK_INVALID_COMPARE_DEC_PLACES`, rhs "?") — wrap it in an explicit rounding (`RoundAccounting(expr, n)`) to fix the scale. *(Locked: `adapter.laws.ComputationEvaluationLawsTest`.)*

*(Locked: `ComputationAuthoringTest`; the BA-doc worked-example shapes — concat, tiered+rounding, division/grouping, common-precondition concat, current-repetition, parallel-iteration — transferred to own domains in `adapter.BaComputationCorpusTest`.)*

## §11/§12 supplement — every computation is ALSO a validation rule (runtime, 2026-06-17)

The kernel auto-generates, per computation, an **implicit validation rule** `FieldFilled(F) And [F] != <term>` — so `validateFull` fires when a document's **stored** computed value disagrees with what the computation would produce. Probed deterministically with `CoverageWindow = DateRange(OrderDate, DeliveryDate)`: a stored `CoverageWindow` differing from the computed range fires; an agreeing one does not. **The fired errorCode is the computation's own name** (`CoverageWindowComp`). This is the mechanism behind the BA's two "Computation Rules as Validation Rules" self-fire traps: computing **`Now` into a field** self-fires (time elapses between the compute and validate steps), and **copying a precise date into a coarser date field** self-fires (the fragment's missing day/month read as `01`, so `[F] != [G]`). Authoring guidance: don't compute `Now` into a field; rebuild a coarse date with `Date("1","1",YearFromDate(G))` rather than copying it. *(Locked: `adapter.laws.ComputationValidationLawsTest`; the `Now`/precise-coarse cases are BA-described instances of the locked general mechanism.)*

## §12 supplement — every fired message is typed value-vs-omission (runtime, 2026-06-10, RT-semantics drain)

A dimension KERNEL-SEMANTICS doesn't cover (it presents the logic as two-valued): every message `validateFull` raises carries a **`MessageType`** — `OMISSION_ERROR` when the rule could be satisfied by *filling* one or more additional fields, `VALUE_ERROR` when only changing a value can satisfy it. Public surface: `IMessage.getMessageType()` (kernel-md-runtime-api). Internally this is the three-state `ValidierungsErgebnis` (`TRUE_WF` / `TRUE_AF` / `FALSE_OR_UNKNOWN`) with a combination algebra:

| combination | result | intuition |
|---|---|---|
| comparison over filled values | `VALUE_ERROR` | only changing the value helps |
| comparison fired on an empty-field substitution (number→0, confirm→False) | `OMISSION_ERROR` | filling the field could flip it |
| presence predicate (`FieldNotFilled`, …) | `OMISSION_ERROR` | filling satisfies it by definition |
| `And` of a value branch and an omission branch | `OMISSION_ERROR` | **omission wins** — filling could still rescue the whole rule |
| `Or` of a value branch and an omission branch | `VALUE_ERROR` | **value wins** — the value branch alone convicts |

*(Locked: `adapter.laws.ErrorTypeLawsTest`; the aggregate corollary — the omitted-tail typing — in `AggregateUncertaintyLawsTest`, §9 supplement above. Source: `ValidierungsErgebnis.combineUND/combineODER`, `BedingungsOperatorHelper.vergleiche`.)*

## The pre-`checkConsistency` tiers — the write path's output contract (instrument 4, 2026-06-04)

Two structural gates fire *outside* `checkConsistency`, found while scoping the F6 DM-JSON write path:

- **Deserialize tier (Jackson binding).** `serializer.deserialize(reader)` is a Jackson read — malformed JSON, an unknown `"type"` discriminator, an unparseable number/enum, and the **locale-format check** (`en_us` → "Invalid locale format", before any consistency pass) fail here as `IOException`/binding errors, *not* `MVK_*` codes. Not enum-enumerable; documented, not locked.
- **Convert tier (model assembly, found 2026-06-10 while locking the rule-slot laws).** Building the validation model rejects **two same-named sibling elements in one group** with a plain `IllegalArgumentException` ("Cannot have two child elements with the same name …") — *before* `checkConsistency`, so the `MVK_NAME_RULES_DUPLICATE` metamodel rule is shadowed by this tier for the same-group case. *(Locked: `validate.laws.RuleSlotLawsTest`.)*
- **Serialize/write gate — `BasicConsistencyCheck`.** `serialize(model, writer, …)` runs `BasicConsistencyCheck.checkModel` first and **aborts the write on any ERROR** — so this, not `checkConsistency`, is what an F6 `writeTo` must satisfy. Its `BasicDocumentModelConsistencyCategory` enum (16 categories) is the enumerable contract: `ID_EMPTY`, `NAME_EMPTY`, `ERROR_{ENTITY,CODE,CONDITION}_EMPTY`, `COMPUTED_FIELD_EMPTY`, `COMPUTATION_OPERATION_EMPTY`, `ENUM_TYPE_DUPLICATE_{VALUE,CATEGORIES}`, `LOCALIZED_TEXT_{ELEMENT,TYPEDEF}_NULL_PROBLEM`, `INDEX_FIELD_NAME_EMPTY`, `SORT_FIELD_NAME_EMPTY`, `TYPEDEF_{TYPE_REF,ID,NAME}_EMPTY`.

rulekit's authoring builders already satisfy the rule/computation subset (`ERROR_*`, `COMPUTED_FIELD/OPERATION`, `LOCALIZED_TEXT_ELEMENT`) by construction; the rest are model-structure concerns rulekit doesn't author (it only *adds rules/computations to an already-valid model*). *(Locked: `SerializerTierParityTest` — reflective parity over the category enum, so a kernel upgrade adding a category fails loudly.)*

## `formatConditionText` is lossy for a `$` correlation (2026-06-06)

The kernel's condition formatter (`IMVK_Service.formatConditionText`, the parse+format round-trip behind rulekit's `canonicalConditionText`) **truncates a condition that carries a `$` outer-iteration correlation to its first conjunct**. A rule the kernel *accepts* and reports as valid —

— formats back to just `FieldFilled(CustomerName)`. The `$`-bearing `Sum(… Having …)` conjunct is silently dropped. (`hasValidConditionText` still returns `true` for the rule.) So the canonical form is **not a safe verbatim source** for such rules. *(Consequence for rulekit: `ReadResult.Opaque` preserves the **raw stored** `getErrorConditionText()`, not the canonical form — see KERNEL-INTEGRATION-NOTES. ## The condition formatter knows exactly two languages — `Locale.US` / `Locale.GERMANY`; anything else silently falls back to German (2026-06-13)

The kernel's keyword-language switch for conditions (`formatAndTranslateConditionText(IRule, Locale, IProblemReporter)`, behind rulekit's `canonicalConditionText(rule, ConditionLanguage)`) resolves the target language through `AbstractMultiLanguageHandler`, whose **supported set is exactly two specific locales**:

```java
public static Set<Locale> SUPPORTED_CONDITION_LANGUAGES = Set.of(Locale.GERMANY, Locale.US);   // de_DE, en_US
// constructor: this.languageUsedInConditionText = SUPPORTED.contains(lang) ? lang : Locale.GERMANY;
```

So the language is keyed by **country**, not just language: `Locale.US` (en_US) → English keywords (`And`/`Or`/`If`); `Locale.GERMANY` (de_DE) → German (`Und`/`Oder`/`Wenn`). **Any other locale — including bare `Locale.ENGLISH` ("en") and `Locale.GERMAN` ("de") — is not in the set and silently defaults to `Locale.GERMANY`** (German), with no error and no diagnostic. Passing `Locale.ENGLISH` to translate an English model therefore returns *German* — the trap that surfaced this. (Source: `kernel-core-parser` `AbstractMultiLanguageHandler`/`ConditionMultiLanguageHandler`; the German branch is literally `Locale.GERMANY.equals(languageUsedInConditionText)`.)

*Consequence for rulekit:* the adapter's translate seam takes rulekit's **`ConditionLanguage`** (EN/DE), not a raw `Locale`, and maps `EN → Locale.US` / `DE → Locale.GERMANY` internally — the silent-German footgun is made unrepresentable at the N8 boundary. *(Locked: `adapter.KernelAdapterFormatTest` — EN must yield English keywords, DE German; a kernel change to the supported-locale set would surface as a German fallback the EN assertion catches.)*

## A model's condition language is independent of its display locale — and English is the convention (2026-06-20)

The model header carries **two distinct, unrelated** language settings — conflating them is a trap:

| setting | where | governs |
|---|---|---|
| **display locale(s)** | header `locales[]` | labels + messages — a rule must carry a message for every declared locale (§13) |
| **condition language** | `modelConfig.conditionLanguage.code` | the keyword language the kernel **parses and stores** *all* DSL in — rule conditions, computation **operations**, and **preconditions** (`precondition`/`commonPrecondition`) alike: `FieldFilled`/`And` (en_US) vs `FeldAngegeben`/`Und` (de_DE); one of the two `SUPPORTED_CONDITION_LANGUAGES` (§above) |

Verified (experiment + the **a12-kernel-mm** corpus):

- **The kernel parses a candidate condition in the model's `conditionLanguage`** — a keyword in the *other* language is rejected `MVK_UNEXPECTED_TOKEN` ("Unexpected found 'FieldFilled'"). (Already noted, "model condition-language gates parsing", §CustomCondition.)
- **`conditionLanguage` need NOT be a declared display locale.** A model declaring only `de_DE` with `conditionLanguage=en_US` and English-keyword conditions is kernel-valid (`checkConsistency` passes — confirmed by a hand-flip experiment and `DocumentModelDraftTest`). The condition language is a free choice between the two supported, not constrained to `locales[]`.
- **English is the corpus convention.** All 59 a12-kernel-mm models — which declare `de_DE` as their *first* display locale — set `conditionLanguage=en_US` and author English-keyword rules (`FieldFilled`/`And`/`PatternViolated`/`RepetitionNotUnique`). German-keyword conditions are the rare, explicit case.

*Consequence for rulekit:* a from-scratch model defaults `conditionLanguage` to **en_US regardless of the display locale** (it used to derive it from the first display locale — breaking English conditions on a `de_DE` model; surfaced by probe `01-de`). Treatment + the single-source guard in [`KERNEL-INTEGRATION-NOTES.md`](KERNEL-INTEGRATION-NOTES.md). *(Locked: `DocumentModelDraftTest.conditionLanguageDefaultsToEnglishRegardlessOfDisplayLocale` — a de_DE draft keeps en_US and the kernel accepts it; `ModelNewVerbTest.aGermanLocaleModelStillAcceptsEnglishDslKeywords` — English DSL validates end-to-end on a de_DE model; `ModelNewVerbTest.aGermanLocaleModelAlsoAcceptsEnglishKeywordComputationsAndPreconditions` — the sibling lock proving the model-level fix covers computation operations + preconditions, not just rule conditions.)*

## A mount group's local elements SHADOW the include — the kernel does not expand it, and stays valid (2026-06-20)

A group that mounts an include carries `Group.modelAlias`. If that same group **also** has its own `Group.elements`, the kernel uses the **local elements** and does **not** expand the include — and the model is still **kernel-valid** (no error, no warning). Experiment (`field add` into a mount group): a mount of `address` resolving `/Person/Addr/{Street,City}`, after adding a local `Extra`, resolves **only** `/Person/Addr/Extra` — `Street`/`City` silently gone — and `model validate` returns `valid:true`. So local content on a mount is a *silent override*, not an extension.

*Consequence for rulekit:* a routine `field add`/`group add` whose target group is a mount used to write a local element and report `applied`, silently discarding the entire mounted include. rulekit now **refuses** an element-add into a mount group (`RK_MOUNT_NOT_EDITABLE`) — see KERNEL-INTEGRATION-NOTES; the kernel's silent-override behavior itself is the finding here. *(Surfaced by probe `01-de`; locked by `MountEditRefusalTest`.)*

## An include's locales must be a superset of the base's — not the reverse (2026-06-13)

The kernel's include locale-compatibility rule, pinned by experiment, runs in the direction that's easy to get backwards: **the included model must declare a superset of the base model's locales** — it must *cover* every locale the base declares. Extra locales in the include are harmless.

- base `{en_US}` includes `{en_US, de_DE}` → **loads** (the include over-covers; the extra `de_DE` is ignored).
- base `{en_US, de_DE}` includes `{en_US}` → **rejected on expand** (the include can't cover `de_DE`).

So a one-line "locale superset" note is ambiguous about direction; the constraint is *include ⊇ base*, enforced by the kernel on expand (not at the modelkit build tier). *(Locked: `modelkit.IncludeConstraintsTest`.)* Cycles and the single-root rule are likewise the kernel's to enforce on expand — modelkit doesn't re-implement them.

## A group's index field auto-generates its uniqueness + mandatory rules (2026-06-13)

Declaring a repeatable group's **index field** (`indexFieldName`) is all the authoring needed — the kernel **auto-generates** two validation rules for it (no rule a model has to carry), per the kernel-team BA doc (§"Index Fields"):

- **unique within each iteration**: `RepetitionNotUnique(indexField)`;
- **mandatory when the group is filled**: `GroupFilled(group) And FieldNotFilled(indexField)`.

Confirmed empirically against the runtime: two repeatable rows sharing an index value fire where distinct values don't, and a filled row with an empty index value fires too. Consequence for rulekit: modelkit's `indexField(name)` only emits `indexFieldName` — it must **not** also emit the pair (the kernel would double them). *(Locked: `adapter.laws.IndexFieldLawsTest` — differential, so it doesn't depend on the generated rules' kernel-internal error codes.)*

## The DM-JSON deserializer ignores unknown field-config keys — a round-trip must read the value *back* (2026-06-13)

The kernel's DM-JSON `JsonMapper` is annotated **`@JsonIgnoreProperties(ignoreUnknown = true)`** (`kernel-md-serializer`). So a misspelled or unsupported field-type key (e.g. `maxFractionDigits` for the real `maxFractionalDigits`, or a guessed `unit`) is **silently dropped** — the model still loads and validates clean, but the slot has *no effect*. Consequence for verifying a new field-config slot (FEATURE-GAPS §3.4): **"emit + load-valid" proves nothing about whether the engine honored the key** — only reading the value back through the kernel's typed field-type API (`INumberType.isZeroNotAllowed()`, `IStringType.getHintList()`, `IEnumerationType.getErrorMessage()`, …) proves it. rulekit's field-config round-trip tests therefore read back via `ModelIndex.fieldType(path)` rather than trusting a clean load. *(Locked: `modelkit.FieldConfigExtrasTest` — every §3.4 slot asserted via the kernel getter, not the emitted JSON.)*

## The number `trait`/unit slot is a clean lowercase field attribute — `AmountWithCent` is a *separate* derived category (2026-06-13, corrects an earlier deferral)

A number field's **unit** is the DM-JSON `trait` slot, whose allowed values are the **lowercase** tokens **`amount` / `percent` / `permille`** — the authoritative client contract (`kernel-md-facade` `api.ts`: *"allowed values are: 'amount' | 'percent' | 'permille'"*). It round-trips cleanly: emit `trait`, read it back via `INumberType.getTrait()` (`Optional<String>`); the runtime treats `amount` specially via `getTrait().equals("amount")` (`TypeConverter`).

This **corrects an earlier (same-day) deferral** that called the trait "inconsistent across tiers." The confusion was conflating two distinct things:

- the field's own **`trait`** slot — lowercase `amount`/`percent`/`permille`, what we model;
- the metamodel's **`AmountWithCent` / `AmountWithoutCent`** enum (in `CT_FIELD_TYPE_ATTRIBUTES` / `MM_SMM_FieldTypeChecks`, with **no** kernel-java references) — a **derived** category used only in *cross-field* type-compatibility checks (source-vs-target decimal places in a copy/computation), not a competing representation of the field's own trait.

So there is no inconsistency for the slot itself; modeling it is just `trait:"amount|percent|permille"`. The 0-or-2-decimal "with/without cent" distinction is the kernel's *derived cross-field* concern, not a field-level constraint we pre-check. *(Locked: `modelkit.FieldConfigExtrasTest.numberUnitTraitRoundTripsThroughTheKernel`.)* Modeled via `NumberFieldBuilder.unit(NumberTrait)`.

## `modelConfig.supportedCharacters` is enforced at runtime, not just authored — out-of-set values raise `ZeichenNichtImZeichensatz` (2026-06-13)

The model-config **allowed-character set** (`content.modelConfig.supportedCharacters`, a `List<String>` where each entry is a single character or a range like `" -~"` = space-through-tilde; empty = all of Unicode-Plane-0 — `IDocumentModelConfig.getSupportedCharacters()`) is a **real runtime constraint**, not codegen-only metadata. The interpreted `IDocumentRtService.validateFull` checks string/enum/custom field **values** character-wise: a value carrying any character outside the set raises the formal error **`ZeichenNichtImZeichensatz`** ("character not in the character set" — a German-named code, not `MVK_*`-prefixed); a value drawn wholly from the set is clean. Empirically confirmed (a model restricted to `A-Z`: value `"abc"` fires, `"ABC"` does not). So this slot can be both authored *and* behaviorally locked. *(Locked: structural round-trip `modelkit.SupportedCharactersTest` via `IDocumentModelConfig.getSupportedCharacters()`; runtime fires/does-not-fire `adapter.laws.SupportedCharactersLawsTest`.)* Modeled via `DocumentModelDraft.Builder.supportedCharacters(...)` / `ConfigEditor.supportedCharacters(...)` / CLI `config modify --supported-character`.

## An include mount can exclude the included model's rules/computations — `excludeRules`/`excludeComputations`, applied at expand (2026-06-13)

A mount group (one carrying `modelAlias`) may set the booleans **`excludeRules`** and **`excludeComputations`** in its `Group` body, beside `modelAlias`. They are honored at **expand**: with `excludeRules: true`, the kernel does **not** carry the included model's own rules into the expanded model (its *fields* still mount — only the rules are dropped); `excludeComputations` does the same for computations. Empirically confirmed: a price-list model with rule `LIST_PRICE_NEG`, mounted plainly, has that code in the expanded model; mounted with `excludeRules`, it does not, while the mounted `ListPrice` field remains.

The kernel ties the flag to a mount — metamodel rule **`EXCLUDE_RULES_INVALID`** (`MM_Group_1`): `FieldFilled(excludeRules) And FieldNotFilled(modelAlias)` is an error ("excludeRules filled and modelAlias not filled"), with a twin `EXCLUDE_COMPUTATIONS_INVALID`. So the slot is meaningful only where there's a `modelAlias`; our API only emits it on a mount, so that refusal is structurally unreachable from rulekit. *(Locked: `edit.IncludeExcludeRulesTest` — plain mount keeps the rule, `excludeRules` drops it but keeps the fields, via the kernel's own expand.)* Modeled via `MountOptions.single().excludingRules()` → `ModelDocument.mount(...)` / `IncludeEditor.mount(...)` / CLI `include add --exclude-rules`.

## A type-def-only model is just a root-less `document` model; a consumer imports it with `purpose: "typeDefinitions"` (2026-06-13)

There is **no separate model discriminator** for a type-definition library. A "type-def-only" model is a normal `modelType: "document"` model that carries `content.typeDefinitions` and **no root groups** — the kernel accepts it standalone (empirically: a model with an empty `modelRoot.rootGroups`, *and* one with no `modelRoot` at all, both load + `checkConsistency`-pass). So authoring one is just emitting type-defs with an empty root.

A consumer pulls those types in via a header `modelReferences` entry whose **`purpose` is `"typeDefinitions"`** — the kernel constant **`PURPOSE_4_ONLY_TYPE_DEFS = "typeDefinitions"`** (`DocumentModelExpandSanityChecks`), **not** `"import"`. At expand, `DocumentModelExpandImportService` walks the referenced model and merges **all** its type-defs into the consumer's namespace **by id** (`addUniqueTypeDef` / `getImportedTypeDefsById`) — so a consuming field references an imported type by a **plain `typeDefinitionId`** (no alias prefix; the entry's `alias` is just a label). This differs from an `include` (`purpose: "include"`, which mounts *structure* under a group via `modelAlias`). The kernel checks `purpose == "typeDefinitions"` before expanding an import (`checkTypeDefPurpose`) and that the imported model's locales cover the consumer's.

Consequence for authoring: a consumer's `typedefField` may reference an **imported** id that isn't locally declared, so rulekit's draft-time local-typedef-ref check defers to the kernel when an import is present (the kernel resolves it at expand). *(Locked: `modelkit.TypeDefModelImportTest` — type-def-only standalone valid; consumer-from-scratch import + imported-typed fields; the edit path.)* Modeled via `DocumentModelDraft.typeDefModel(id)` (provider), `Builder.importTypeDefs(ref)` / `ModelDocument.addImport(ref)` / `EditSession.addImport(ref)` / CLI `typedef import --reference` (consumer).

A12 has two **group templates**, flagged by a group's **`usageType`** slot (`IGroup.getUsageType()` → `Optional<String>`; the enum is defined in the `MM_Group_1` metamodel). | only `Field` + `Rule` elements — no sub-groups | `DOCUMENT_MODEL_MULTI_SELECT_OTHER_ELEMENTS` |

So **attachment is a heavy fixed template** (no user input beyond the group name/parent — all 8 fields + 4 rules + the `content` config are mandated boilerplate); **multi-select is light but parameterized** (the single enum/string field, its values, and its requiredness are the user's). *(Source-verified by reading the two rule classes + `MM_Group_1`, then **locked by the generators**: `modelkit.MultiSelectTemplateTest` / `modelkit.AttachmentTemplateTest` each build the template, assert the kernel **accepts** it (the attachment accept-test proves the 4 emitted condition strings round-trip byte-for-byte), and assert a **tampered** template is rejected with the right `DOCUMENT_MODEL_*` category. The generator refuses a non-`en_US`/`de_DE` model rather than emit rules the kernel can't validate — which would also NPE its `RULES_REQUIRED.get(locale)`.)*

Removal: a composite group's internal rules live inside its subtree, so `group remove` takes them with it — the safe-delete gate **excludes in-subtree referrers** so it doesn't demand `--cascade` for rules the author never wrote (CLI-SPEC §6; `cli.GroupAttachmentVerbTest`).

## Descriptions + annotations are element-wide (`IElement`/`IFieldTypeDefinition` are `IDescribed`+`IAnnotated`); the model carries a `comment` (2026-06-13)

Every element and type-def carries the same documentation metadata, not just fields: **`IElement extends IIdNamed, IDescribed, IAnnotated`** and **`IFieldTypeDefinition extends IIdNamed, IDescribed, IAnnotated`**. So a field, group, *and* rule (all `IElement`) and a type definition each have:

- **`internalDescription` / `externalDescription`** (`IDescribed`) — per-locale text (`ILocalizedTextMap extends Map<Locale,String>`), serialized **element-level** as `[{locale, text}]` (alongside `annotations`, beside the `Field`/`Group`/`Rule` body — uniform across kinds). Distinct from a field's `label` and its `helperText` (`IField`-only).
- **`annotations`** (`IAnnotated`) — `[{name, value}]`, element-level.

Separately, the model has a free-text **`comment`** at `content.modelInfo.comment` (`IDocumentModelInfo.getComment()` → `Optional<String>`) — distinct from the header `labels`/`annotations`. (The other "comment" is the inline `;;` concrete-syntax comment inside a condition/computation — a different mechanism, carried in the rulekit DSL.)

rulekit treatment: a shared **`ElementMeta<SELF>` builder mixin** (`annotation` + `internalDescription` + `externalDescription`) that `FieldAttrs`, `GroupBuilder`, and `TypeDefBuilder` extend (author side); the edit-path locator resolves field/group/**rule** by name-path and **type-def by id**, so one metadata API (`ModelDocument.setInternalDescription`/`setAnnotation`/`remove…`, the editors, and the CLI **`meta <ref>`** verb) does CRUD across them all; the model comment rides `config modify --comment`. *(Locked: `modelkit.ElementDescriptionTest`, `edit.ElementMetadataEditTest`, `modelkit.TypeDefAndModelCommentTest`, `cli.MetaVerbTest` — read-back via `IElement.getInternalDescription()` / the kernel deserialize→serialize round-trip.)*

## How `checkConsistency` actually works — structural laws ARE metamodel rules (2026-06-04)

## Rule-condition polarity is fixed — `errorCondition` fires on TRUE, no configuration (2026-06-05 investigation)

A validation rule's condition has **one fixed polarity**: the sole condition slot is `errorCondition`, and the rule fires (= the document is invalid for the error field) exactly when the condition evaluates **TRUE**. So a *requirement* must be authored as its *violation* — to require "X is filled", the `errorCondition` is "X is **not** filled". Confirmed configurable in **no** way:

- **No per-rule polarity slot.** The Rule's slots (MM_Common metamodel + public `IRule` + serializer) are exactly `errorEntity`/`errorCode`/`errorCondition`/`severity`/`errorMessage`/`guiPatterns`/`variantFilter`/`variantErrorMessages` — none flips condition-true between error/ok. `severity` (INFO/WARNING/ERROR) is UI classification only ("does not play any role in the validation language"). The `customRefErrorEntities` pairs only refine *which* entities are blamed, not polarity.
- **No alternate condition form.** There is no `validCondition`/`assertion`/`requirement`/`applicabilityCondition`. `precondition` exists **only on computations** (gates which alternative runs), not on rules — a rule folds any applicability guard into the single `errorCondition` (e.g. `GroupFilled(K) And …`).
- **No model/rule config** reinterprets the condition.
- **No generic `Not` operator** (only `And`/`Or`). Instead the language ships **matched positive/negative predicate pairs** (`FieldFilled`/`FieldNotFilled`, `AllFieldsFilled`/`NoFieldFilled`, `AtLeastOneFieldFilled`/`NotExactlyOneFieldFilled`, `FieldsNotCollectivelyFilled`, …) so the author names the violation directly by predicate choice.

**Consequence (the silent trap):** writing the requirement *positively* (e.g. `FieldFilled(X)` as the errorCondition) is structurally valid and the kernel accepts it — but it encodes the **opposite** rule (fires when X *is* filled). The kernel cannot catch this (both polarities are valid conditions). rulekit's job: teach negation (skill) and flag likely inversion (`RK_INVERTED_REQUIREDNESS` lint — AST-based, so it needs a structured/read rule, not raw condition text). Source: `a12-kernel/documentation/ba/validation_language_guide_en.adoc` (§"A Rule always describes the error condition"; "no generic negation operator"; severity is UI-only); `IRule` (md `getErrorCondition`; tool `getErrorConditionText`); `RuleSerializer` slot set; `MM_Common_v2` Rules group; `IComputation.getPrecondition` (computation-only).

## `checkConsistency` runs runtime code generation — the AOT / native-image constraint (2026-06-05 investigation)

**Why this matters.** The standalone CLI (PROJECT-DESIGN N10, [`CLI-SPEC.md`](CLI-SPEC.md)) is a candidate for **GraalVM native-image** packaging (a tiny, instant-start single binary for the modeller/BA). native-image does **closed-world** AOT: anything that *parses/compiles/defines classes at runtime* is hostile to it. So whether the kernel does runtime codegen — and on which paths — decides whether native-image is possible at all. It also bounds any future AOT/offline scenario and is a third reason a TypeScript twin can't validate (kernel codegen is JVM-only).

**The discovery.** A native-image build of the CLI (which only does `deserialize → expand → checkConsistency`) builds clean but **fails at runtime**: `Error while instantiating template "templates/common/groovy/base/StringParameter"`. The JVM build never fails. That signature = runtime template machinery the closed world couldn't satisfy.

**Root cause — `checkConsistency` generates validation code as a side effect.** It is a *registered consistency rule*, `CodeGenerationRule`, that calls `generateValidationCode(model, new GroovyCodeGeneratorConfig(...), …)` — so **every `checkConsistency` runs full validation-code generation** (this is also the §"structural laws ARE metamodel rules" mechanism above, seen from the codegen side). Two corrections to earlier assumptions fell out:

- **The engine is ANTLR StringTemplate v4, not Groovy's template engine.** The `groovy` in the path is the *target language of the emitted source*, not the engine. The kernel renders source with `org.stringtemplate.v4.{ST,STGroup,STGroupFile}` (kernel `StringTemplateUtil`/`STParameterClassBase`; the error string is thrown by `StringTemplateUtil.getTemplate`). `StringParameter.st` is trivial — `StringParameter(t) ::= << "<t.value>" >>` — emitted for **every field's string-valued metadata** (name, labels, required-error text), so *any* model with ≥1 field triggers it.
- **It is NOT model-content-dependent.** The initial symptom (held-out `catalog` failed, traced models "passed") was an artifact of only testing `catalog` on the native binary. Re-tested: the native binary fails on **all** models (subscription/order/logistics/catalog) at the same template. (`storefront` fails earlier on an unrelated missing-resolver issue.)

**Experimental verification** (probes, JVM, `-verbose:class`; reproducible scripts under the gitignored `build/native-spike/`):

- **The trigger is `checkConsistency`, not `expand`.** A probe doing `expand` only loads ~7 engine-ish classes; `expand + checkConsistency` loads **497** — the entire StringTemplate v4 compiler pipeline (`STParser`, `STLexer`, `GroupParser`, `CodeGenerator`, `Compiler`, `CompiledST`) plus kernel `StringTemplateUtil`/`StringTemplateGroup`. So model *consistency checking* is where runtime codegen happens.
- **`checkConsistency` does NOT reach Groovy compilation.** No `groovy.lang.GroovyClassLoader`/`GroovyShell`, no `org.codehaus.groovy.control.*`, no runtime-defined classes (the `__JVM_LookupDefineClass__` entries are all JDK `LambdaForm`s). The only "groovy" class is `GroovyCodeGeneratorConfig` (a config object naming the target language). **`checkConsistency` emits Groovy *source* via StringTemplate and discards it — it never compiles it.** *(This corrects the `KERNEL-INTEGRATION-NOTES` "no code emitted, no compile" claim: code IS emitted via StringTemplate; only the Groovy compile step is absent here.)*

**The native-image verdict — feasible for the checkConsistency/parse path, with care.** StringTemplate v4 compiles templates to its *own interpreted form*, not JVM bytecode, so it is **native-compatible once its resources are bundled**. The failure was a **missing resource**: `base.stg` does `import "baseDir"`, loading `baseDir/*.st` (e.g. `StringParameter.st`) *by name*; the tracing agent records the `.stg` group files but **misses the import-indirected `.st` files**, so they weren't in the image. Rebuilding with `-H:IncludeResources='internal/templates/.*'` (+ `.*\.st`/`.*\.stg`) **fixed it**: the native binary then **passed on all four self-contained models, output byte-identical to the JVM**, **~37 ms startup** (vs ~600 ms JVM, ~16×), 36 MB. So native-image is viable for rulekit's verbs (all of which are `checkConsistency`/parse-based).

**The remaining hard ceiling — Groovy runtime compilation on the validation-*execution* path.** Actually *running* a model's validators against a document (the kernel's `getValidator()`/on-the-fly testing) compiles the emitted Groovy source at runtime via `GroovyClassLoader.parseClass` (`ModelGroovyCode`) / `GroovyShell` (`OnTheFlyTestingValidatorGenerator`) — genuine runtime JVM class generation, which native-image **cannot** do and resources can't fix. rulekit's CLI never executes validation (it authors/validates *model structure*, the kernel is the runtime), so this isn't a blocker — but it is a permanent boundary: **a native rulekit must never depend on the kernel's runtime validation execution.**

**Breadth / future risk.**
- Runtime codegen in the kernel is exactly two mechanisms, both reachable from the public model-service path: **(1) StringTemplate v4** (resource-fixable; reached by *every* `checkConsistency`) and **(2) Groovy runtime compilation** (not fixable; only on validation execution). No direct ASM/Javassist/CGLIB/`javax.tools` use exists elsewhere in the kernel/base/utils sources.
- **Tracing-agent metadata is not sufficient by itself** for this kernel: import-indirected StringTemplate resources are missed, so a native build needs *broad* resource inclusion (`internal/templates/**`) plus the closed-world discipline of testing **held-out** models (the agent-only build gave a false "works" on traced models and a false "categorically broken" on the held-out one — only the resource-bundling probe got it right).
- **Performance footnote:** `checkConsistency` pays the StringTemplate parse/compile cost per process (497 classes, the ST compiler) — relevant to CLI startup and the resident-mode trade-off.

**Source anchors** (kernel-internal, consult-only — from the `a12-kernel` checkout): `StringTemplateUtil.getTemplate` (the error string) + `getActCodeGroup` (`STGroupFile`); `STParameterClassBase` / `StringParameter` (`@StringTemplateGroup("/common/$programmingLanguage$/base")`); `CodeGenerationRule.checkModel` → `ExternalDocumentModelService.generateValidationCode` (the trigger); `ModelGroovyCode` (`GroovyClassLoader.parseClass`) and `OnTheFlyTestingValidatorGenerator` (`GroovyShell`) for the execution-only Groovy wall. Templates ship in `kernel-core-codegen-base` under `internal/templates/{common,validation}/{groovy,java,…}/`.

## Parsetree construct-name enums — the kernel's machine-readable operator inventory (N3 reverse anchor, 2026-06-04)

The package `…core.parsetree.a12internal.api.types` holds ~18 construct-name enums (`kernel-core-parsetree-api`) — the kernel's own operator inventory, the second N3 parity anchor. Discovered by reflecting over each (`adapter.KernelConstructParityTest`):

## Parsing a condition to the AST — shapes for the F10 converter (2026-06-04 probe)

Verified by parsing rulekit-authored conditions via `IMVK_Service.parseBedingungNoExpand(IRule, pr)` (parses the rule's *own* stored `errorCondition`) and inspecting the `ICondition` tree:

- **`ICondition` carries no discriminator** — no `getName()`, no kind enum, only `traverse(ASTVisitor)`. Dispatch by `instanceof` against the concrete subtype interfaces.
- **Single-field presence is canonicalized into the field-list node.** `FieldFilled(x)` parses to an **`IEntityListCondition` named `AllFieldsFilled`** with a one-element entity list; `FieldNotFilled(x)` → name **`NoFieldFilled`**, one element. There is no dedicated single-field "filled" node and no `FieldFilled`/`FieldNotFilled` enum constant — the single-field and field-list forms collapse to the same node, distinguished only by entity-list arity. (So a 1-element `AllFieldsFilled`/`NoFieldFilled` round-trips to rulekit's `.filled()`/`.notFilled()`.)
- **`IComparisonCondition`**: `getOperation1()` (left) / `getOperation2()` (right) → `IOperation`; `getCmpOp()` → `ComparisonOperation` (`GT/LT/GE/LE/EQ/NE` + tolerance `NE1/2/5/10` + pattern `WM/NM`). A plain field operand is `IFieldIdOperation` with `getOperatorName() == FieldValue` (other names = `Length`/`Round…`/`AbsValue`/… wrappers); `getField().getFullName()` is the resolved absolute path. A literal is `IConstantOperation.getValue()` — **always a String**; its kind is `IOperation.getType()` (`OperationType {NUMBER, STRING, DATE, DATE_RANGE}`), not on the operand subtype. So a number comparison can be rebuilt with the kernel's literal string directly via rulekit's `gt(String)`/`eq(String)`/… overloads (no re-parsing).
- **`ICompositeCondition`**: `getLogOp()` → `LogOp {And, Or}`; `getConditionList()` → `List<ICondition>` (**n-ary**, not binary); `hasBrackets()` records source parenthesization.
- **`IEntityId` has no value-kind** and no `isGroup()` (derive from `!isField()`); the field kind comes from the model, not the path node — rulekit's converter reads it via `BoundModel.fieldAt(path).kind()`.
- **Aggregate operands** (`Sum`/`MaxValue`/`MinValue`/`NumberOfDifferentValues`/…) are `IEntityListOperation` (`getOperatorName()` → `EntityListOperationName`, `getEntityList()` → `IEntityIdList`), appearing as the left operand of an `IComparisonCondition`. For a wildcard scope like `Sum(Items*/Count)`, the single entity's `getFullName()` is `/Order/Items/Count` (**the `*` is dropped**) and `getIndices()` is `[1, 0, 1]` — the **`0` is `IParseTreeEntity.WILDCARD`**, marking which path segment was flattened (here `Items`). So the rulekit `*`-path is rebuilt by re-inserting `*` after each segment whose index is `WILDCARD`. A **`Having` filter** rides on that entity as `getFilterCondition()` → a nested `ICondition` (e.g. the `[Items/Sku] == "A"` comparison), which converts recursively and attaches via `FieldListRef.having(...)`.
- **Iteration operands/conditions.** `CurrentRepetition(group)` is an `IGroupOperation` (`getOperatorName()` → `GroupOperationName.CurrentRepetition`, `getGroup()` → the group `IEntityId`), a numeric operand of a comparison. `RepetitionNotUnique`/`FieldValuesNotUnique` are `IEntityListCondition`s (those names in `EntityListConditionName`): the key entities carry the **`ITERATION` (-1) index** at the repeatable level (e.g. `/Subscription/Addons/Name` → indices `[1, -1, 1]`), and a `… From <group>` scope, when present, rides on `getAdditionalGroupReference()` (absent → empty).

## §10 supplement — the model-include (`modelAlias`) mechanism + the mount-suffix path (2026-06-04)

How a DM includes another (the workspace `purpose:"include"` scheme, adapted to our own domain in `storefront.dm.json` → `catalog.dm.json`):

- **Header**: `modelReferences: [{alias, modelType:"document", purpose:"include", reference:<includedModelId>}]`.
- **Content**: a placeholder **Group** with `"Group": {"repeatability": 1, "modelAlias": <alias>}` and **no inline `elements`** — `expand(model, resolver)` mounts the referenced model's content there. The `resolver` (`IDocumentModelReferenceResolver.getDocumentModel(reference)`) returns the included model; a directory resolver maps `reference` → `<reference>.json`.
- **The mount group *id* gets a `_` suffix on expand** (`Inventory_`), with the included root group `Catalog` nested under it — but **`id` ≠ name**. The kernel's `getId()` is an opaque/suffixed identifier; the **name-path** (the join of `getName()` segments, which is what a condition references via `getFullName()`) is the unsuffixed **`/Storefront/Inventory/ListPrice`** — and notably the included root group `Catalog` does **not** appear as a name segment (the mount surfaces the included fields directly under the mount group's name).
- **rulekit indexes by name-path (F-IDX, 2026-06-05), not by id** — so the handle path *is* the unsuffixed, condition-facing `/Storefront/Inventory/ListPrice`. (Before F-IDX the index keyed by `getId()`, exposing the suffixed `/Storefront/Inventory_/Catalog/ListPrice`; that id-path was never authorable in a condition — `MVK_INVALID_ENTITY` — which was the tell.) A *written* rule referencing an included field **does** round-trip through the kernel: add → modify → write-back → re-read is green and the include is never inlined (`ModifyIncludedRuleTest`) — the earlier "deferred fork-9 follow-up" caveat here is resolved.
- **Extract-as-include is reference-safe — the composed shape validates (2026-06-12).** The *post-extraction end state* — a subtree lifted into a sub-model and re-mounted at the same name — passes `checkConsistency`. Two legs verified: **(a)** a **parent** rule reaching into the mount (referencing `/Order/Shipping/PostalCode`) validates and resolves via `whereUsed`; **(b)** the included sub-model's **own** relative-pathed rule travels to the mount and surfaces at its composed full-name (`/Order/Shipping/PostalCodeRequired` in `readAll()`). So rules that lived inside an extracted subtree move with it for free (relative paths), and references into it survive — because the mount name-path is transparent (above). The extract refactor's safety gate (CLI-SPEC §6) still refuses what this does *not* cover: a subtree rule reaching **outside** the subtree (the sub-model can't see it) and a **repeatable** group (an include's root must be single, non-repeatable — kernel `EntityPathsRelativizer`).

- **An included model's `header.modelReferences` must be present (an empty list) — not absent (2026-06-12).** On expand, `DocumentModelExpandService.addTransitiveModelReferencesFromIncludedModel` calls `header.getModelReferences().stream()` on the *included* model, so a sub-model whose header omits `modelReferences` triggers an **NPE** during expand (surfaced as a `ModelConsistencyException`). Authoring a sub-model for an include must emit `"modelReferences": []` even when it declares none. (Bit the `group extract` refactor: clearing the field outright NPE'd; setting it to an empty array fixed it.)

rulekit treatment + the write-separation guarantee live in `KERNEL-INTEGRATION-NOTES.md`. *(Locked: `IncludesWritePathTest`, `ModifyIncludedRuleTest`, `ExtractAsIncludeProbeTest`, `ExtractGroupAsIncludeTest`.)*

## Serialization shape — a childless group's `elements` array is omitted (2026-06-13)

The kernel's `IDocumentModelSerializer` **omits the `Group.elements` array entirely for a childless group** (it does not emit `"elements": []`). So a model round-tripped through the kernel serializer — as the reference-rewriter (`adapter.ReferenceRewriter` over `MoveSupportDM`) does — comes back with empty groups carrying *no* `elements` key, not an empty one. This is consistent with the kernel's omit-empty-collection serialization (cf. the `datePrecision`-omitted-for-FULL and `modelReferences`-must-be-present quirks above): a *present-but-empty* collection and an *absent* one are not interchangeable, and the serializer prefers absent.

Consequence for any code that *inserts into* a group by walking the JSON: "no `elements` array" must be read as "an empty container," not "no such group." It bit `field`/`group move` **into a freshly-added empty group**: the move rewrites references through the kernel serializer first (dropping the destination's empty `elements`), then the node relocation looked up the destination's `elements` and found none → a spurious "no group at path". rulekit's treatment (materialize the empty array on a matched childless group) lives in `KERNEL-INTEGRATION-NOTES.md`. *(Locked: `MoveVerbTest.movesAFieldIntoAChildlessGroup` + `ApplyRefactorTest.theGateSeesPriorOpsEffects_moveIntoAJustAddedGroup`.)*

## §13 supplement — the message-locale law

Header `locales` are **arbitrary** valid Java locale codes (`fr_FR` is fine; a malformed code like `en_us` fails at *deserialization* — "Invalid locale format" — before any consistency check). English/German are not special here; only the *condition keyword* language is limited to the EN/DE bundles.

**Language-only codes (`en`, `de`): they DESERIALIZE but the VALIDATION mode rejects them** (corpus check + experiment, 2026-06-05; locked by `dsl.BareLocaleTest`). A `Locale` needs only a language, so `en` parses, and the bare form **dominates the A12 Tools workspaces**: **268** models declare `[{"code":"en"},{"code":"de"}]` vs **107** with `en_US` (e.g. `advanced/models/CommonFieldDefinitions_TDM.json`); our own fixtures and `a12-kernel-mm` use the full `language_COUNTRY` form. **BUT** `checkConsistency` (the validation mode, run by `BoundModel.ofJson`) derives a validation language from the model's locale and **rejects the bare code**: `IllegalArgumentException "Die im ValidierungsModus übergebene Sprache en wird nicht unterstützt"` ("language en is not supported in validation mode"). The full `en_US` is supported. So:

| Tier | `en` (bare) | `en_US` (full) | `en_us` (malformed) |
|---|---|---|---|
| deserialize | ✅ parses | ✅ | ❌ "Invalid locale format" |
| **validation (`checkConsistency`)** | **❌ not supported** | ✅ | — |

**Consequence:** the validate/author path requires a **full** locale code; a bare-locale model (most of the workspaces) must have its locale normalized to a supported full form (`en`→`en_US`) before it can be validated through rulekit. (Corrects an earlier note that claimed bare codes "just work" — that held only for deserialize.) The message-coverage match is still exact-string: a message must carry the **same** code the header declares.

- A rule/computation must carry an error message for **every declared locale** — a missing one is **`MVK_ERROR_MESSAGE_FOR_LANGUAGE_MISSING`**; none at all is `MVK_ERROR_MESSAGE_MISSING`.
- A message for an **undeclared** locale is **silently tolerated and ignored** — no diagnostic, so a typo'd locale code or dead text goes unnoticed (rulekit rejects it at build time for exactly that reason).
- **A blank message text counts as no message at all** (probe-verified 2026-06-10; locked: `validate.laws.RuleSlotLawsTest`): a rule whose only message has `text: ""` draws `MVK_ERROR_MESSAGE_MISSING` from `checkConsistency` plus a per-language `RULE_HAS_NO_ERRORTEXT` (the non-`MVK_` FehlertextErrorType tier) — the blank text serializes as an absent message, it does not survive as an empty one. The metamodel's `MVK_MESSAGE_FOR_LANGUAGE_MISSING` (a language row without its text) never appeared — that shape isn't producible through rulekit's surfaces. The CLI `add` path catches all of this at its post-write re-validation and leaves the model file untouched.
- **Duplicate message locales are silently tolerated at DM-JSON load** (found 2026-06-10 writing the lock — the expected rejection never came): a rule with two `en_US` texts loads and passes `checkConsistency`; one text silently wins. The metamodel's `MVK_LANGUAGE_DUPLICATE` fires only in the model-as-document tier (A12 Tools editing), not on a deserialized DM-JSON. rulekit's builders therefore pre-check duplicates (`LocalizedText.checkDeclared`, the code named). *(Tolerance locked: `validate.laws.RuleSlotLawsTest`; pre-check locked: `RuleAuthoringTest`.)*

*(Locked: `RuleAuthoringTest.requiresAMessageForEveryDeclaredLocale` / `rejectsMessagesForUndeclaredLocales`.)*

## Structure-authoring consistency laws — field types & requiredness (modelkit M1/M2, 2026-06-05)

Surfaced while building modelkit (authoring a *whole model* from scratch and running it through `checkConsistency`). These are **model-structure** validity laws (the kind-B oracle), distinct from the rule-condition `MVK_*` codes in the ledger — they fire on the model, not on a rule. Each is now respected by the `structure` builders (made unrepresentable at the API, or enforced fail-fast before emit) and locked by `structure.DocumentModelDraftTest` / `structure.FieldConfigTest`.

- **An `UnspecifiedType` field is not consistency-valid** — `MVK_UNSPECIFIED_TYPE_NO_CODEGEN` ("Field 'X' does not specify a field type. Hence, code generation is not possible."). It's an authoring *placeholder*, never valid in a complete model. So modelkit's easy-kind set is **String / Number / Date / Boolean / Confirm** — `Unspecified` is deliberately excluded (corrects the betterbuilders/Q4 "easy types incl. Unspecified" read).
- **A string `pattern` requires a localized error text** — `MVK_ERROR_MESSAGE_AND_PATTERN_INVALID` ("The pattern '…' is specified, but the corresponding error text is not."). The text lives in the **`StringType.errorMessage`** array — `[{locale, text}]`, one entry **per declared model locale**. So in DM-JSON a patterned string is `"StringType": { "errorMessage": [{locale,text}…], "pattern": "…", "maxLength": … }`. modelkit makes pattern and message inseparable in the API (`pattern(regex, message)`), replicating the message across the model's locales.
- **Enumeration labels are all-or-nothing per declared locale** — `MVK_COUNT_OF_VALUES_INVALID` ("For the language 'en-US' not every XML value has a corresponding display value."). Once *any* value carries a label, *every* value needs a label for *every* declared locale. Bare (unlabelled) enums are fine. Shape: `"EnumerationType": { "values": [{ "value": "X", "label": [{locale,text}…] }, …] }` (label is **per value**, optional, but uniform when present). modelkit enforces completeness fail-fast at emit (it knows the model locales then).

Supporting structural shapes verified along the way (own-words; for the modelkit emitter and any future schema-oracle work):

| Slot | DM-JSON shape | Notes |
|---|---|---|
| **Requiredness** | `Field.requirednessConfig: { "mode": … }` (sibling of `fieldType`) | mode-only is valid — **no error message needed**. Modes: `notRequired` (or omit the config), `absoluteOrRelativeToNextRepAncestor` (plain required), `relativeToParent` ("only if parent group filled", §4). |
| **NumberType** | `{ "maxFractionalDigits": n, "minValue": x, "maxValue": y }` | `maxFractionalDigits` is the decimal scale (§5b); min/max optional. Valid with just a scale (M1 used `maxFractionalDigits: 0`). |
| **StringType** | `{ "minLength", "maxLength", "pattern", "errorMessage" }` | all optional; `pattern` ⇒ `errorMessage` (above). Bare `{ "type": "StringType" }` (no inner block) is valid. |
| **EnumerationType** | `{ "values": [{ "value", "label": [{locale,text}] }] }` | label per value, optional but all-or-nothing per locale (above). |
| **DateRangeType / DateFragmentType** | `{ "format", "rangeSeparator" }` / `{ "formatOfFragment" }` | both DateRange slots required; fragment needs its format (M3). |
| **TypeDef (reuse)** | declare: `content.typeDefinitions: [{ id, name, fieldType:{…} }]`; reference: a field's `fieldType: { "type":"TypeDefType", "TypeDefType": { "typeDefinitionId": "<id>" } }` | the id is **nested** under a `TypeDefType` block, not a sibling of `type` (a bare sibling → deserialize NPE "fieldType is null"). After expansion the field resolves to the typedef's underlying kind (M3). |
| **Field metadata (M4)** | label: `Field.label: [{locale,text}]` (inside the `Field` object, sibling of `fieldType`); annotations: **element-level** `annotations: [{name,value}]` (sibling of `name`, on fields *and* groups) | labels are per-locale; modelkit requires a label to cover every declared locale (uniform with enum labels). Field *descriptions* and *group labels* are rare in both corpora — not modeled yet. |
| **Header / config** | `header{id, modelType:"document", modelVersion, locales[{code}]}` + `content.modelConfig{decimalSeparator, timeZone, conditionLanguage{code}, fieldRefByShortNameAllowed}` + `modelInfo{name, variant, revision, immutable}` | the from-scratch skeleton; a full `language_COUNTRY` locale is required for the validation mode (§13). |

rulekit treatment: the `structure` package emits all of the above; modelkit's own checks (label completeness, min≤max, pattern⇔message, enum non-empty, repeatable≥2) fail fast *before* the kernel, turning these into clear authoring errors rather than cryptic `MVK_*`. *(Locked: `structure.DocumentModelDraftTest`, `structure.FieldConfigTest`.)*

## §paths supplement — relative path forms accepted in conditions (fork #9, 2026-06-04 probe)

Conditions accept paths **relative to the rule's group**, not only absolute — verified against the kernel: a bare segment for a field directly under the rule group (`FieldFilled(MonthlyFee)` at `/Subscription/Addons`), the bracketed value form (`[MonthlyFee]`), and `../` parent navigation to a sibling group's field (`FieldFilled(../Tier)` from `/Subscription/Addons`). All kernel-accepted (computation operations too). **Bare names also resolve *upward* (verified 2026-06-05 via `cli check`):** a bare segment not found directly under the rule group is looked up in **ancestor** groups — `[Tier]` from a rule scoped to `/Subscription/Addons` binds to the ancestor `/Subscription/Tier` (**no `../` needed**), exactly like `[/Subscription/Tier]`; a name found nowhere (`[Bogus]`) is `MVK_INVALID_ENTITY`. So a bare cross-(ancestor-)group reference works without `../`; `../` only matters to reach a different branch. *(This caught an eval judge out — it assumed bare = the rule group only and false-flagged correct candidates; RESULTS.md 2026-06-05 19:06.)* Descending *relatively* into a **repeatable** subgroup still hits the wildcard law (`MVK_NO_WILDCARD`) — that is the iteration rule, orthogonal to the path form. rulekit's renderer now renders rule/computation conditions relative to their group (the authoring norm — `DslRenderer` with a base group); standalone `DslRenderer.render` stays absolute, and absolute remains valid (KERNEL-INTEGRATION-NOTES). **Keyword-segment quoting (the other fork-9 half, verified 2026-06-04 probe):** a path segment whose name collides with a DSL keyword is a **parse error** unquoted — `FieldFilled(Length)` (and even absolute `FieldFilled(/Subscription/Length)`) → **`MVK_UNEXPECTED_TOKEN`** — and is escaped by **single-quoting that segment**: `FieldFilled('Length')` / `FieldFilled(/Subscription/'Length')` validate (grammar `NameOhnePunktMitQuotes : '\'' STR (STR|DIGIT)* '\''`). rulekit's renderer now single-quotes any segment matching a catalog operator keyword (per segment, `*` suffix preserved); the **full** lexer keyword set (beyond the operators rulekit catalogs) rides the N3 parity anchor. *(Locked: `dsl.PathPolicyTest`.)*
