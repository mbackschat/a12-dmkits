# `scripts/` — release & build tooling

Maintainer scripts for building, packaging, and releasing `dmtool` and the standalone interpreter. Most are not needed for the everyday dev inner loop (that's `./build.sh test` — see the top-level [`README.md`](../README.md)); they drive the **native image**, the **agent plugins**, and the two **public release mirrors**. The dev-loop verification exceptions are [`verify-demos.sh`](verify-demos.sh), which catches demo drift after a verb changes, and [`verify-build-cache.sh`](verify-build-cache.sh), which proves expensive compilation can be reused across clean worktrees.

Tokei remains local-only: both publishers run this check before any public mutation, while normal builds, release assembly, and public CI do not invoke it. | Regenerate after production-source changes; publishing refuses a stale artifact-scoped table. |

| [`release-perf-gate.sh`](release-perf-gate.sh) | Run the routine performance tier and refuse a release whose gate carried **no evidence**: the gate failed, it was *vacuous* (the anchor declined to assert), the lane wrote **no** result XML, the directory was empty, or a bar was **skipped** (JUnit reports a skip as success, summed across files). | [`ensure-dmtool.sh`](ensure-dmtool.sh) | **Canonical on-demand installer** (agent-agnostic): downloads the per-OS native binary from the release mirror, checksum-verifies it, caches it **version-aware** (`bin/<version>/`, stable symlink at `bin/dmtool`), and prints its absolute path only after both executable paths exist. A skill-launched Codex command receives no hook-only `PLUGIN_DATA`, so the fallback is the sandbox-writable host temporary directory rather than `HOME`. **There is no session hook** — it is synced **into each plugin's skill dir** (beside `SKILL.md`) and the skill runs it the first time `dmtool` is needed. | Don't run directly; edit here, then `sync-plugin-assets.sh`. |
| [`selftest-ensure-dmtool.sh`](selftest-ensure-dmtool.sh) | Behavioral guard for the installer above: stubs a fake release server and asserts the cache is **version-aware** (a `VERSION` bump re-downloads, the same version reuses, old versions prune), revalidates a same-version executable created without provenance, uses a writable temporary cache when host data variables are absent, and warns without hard-failing or printing false readiness on cache/checksum failures. | [`selftest-dmtool-launcher.sh`](selftest-dmtool-launcher.sh) | Behavioral guard for **`bin/dmtool` dispatch and its JDK gate**: fabricates a fake `java` per case and asserts the gate REFUSES every unusable Java (no executable, a failing `java -version`, an unparseable banner, an old JDK — including one hidden behind the `Picked up JAVA_TOOL_OPTIONS` line a JVM prepends) while ACCEPTING a supported or newer one, applies to a JVM launcher reached by any route but never to a native binary, and proves `RK_NATIVE=1` selects Gradle's actual `nativeCompile.outputFile` (including the Windows `.exe`) rather than falling through to the JVM launcher. `DmtoolLauncherTest` supplies that Gradle-derived path; both files and the native build configuration are inputs of `deliveryGuardTest`, so this rides CI without duplicating the producer path in the guard. | On any change to `bin/dmtool`. |
| [`prepare-dmtool-source.sh`](prepare-dmtool-source.sh) | Resolve the JVM `installDist` launcher for the repository's exact clean `HEAD`. It trusts the launcher's own source provenance as the cache key, runs `:cli:installDist` only after a mismatch or miss, rechecks the worktree and artifact after building, and prints one absolute launcher path. It never selects or rebuilds native, so sibling evidence consumers avoid native-image staleness and reflection recapture. It anchors its own working directory, so a sibling repository may call it by absolute path from anywhere; without that, `build.sh`'s bare `exec "$ROOT/gradlew"` makes Gradle treat the caller's directory as the project directory and any required rebuild fails. It runs the launcher's provenance check under the same JDK 21 pin `build.sh` applies (`a12_pinned_jdk21_home`) and keeps "the launcher did not start" a separate verdict from "the launcher named another revision", preserving the launcher's own stderr: a `JAVA_HOME` naming a removed JDK used to surface as a source mismatch on a launcher whose embedded provenance was correct. When only the pin made the check pass, it tells the caller so, because the returned path runs in the caller's environment. A launcher that is present but cannot run — a partial `installDist` — is still repaired by one rebuild; only a machine with no runnable JDK is refused before building, because rebuilding cannot fix that and `build.sh` would die naming the wrong cause. `selftest-prepare-dmtool-source.sh`, hosted by `DmtoolLauncherTest`, locks current-revision reuse, stale rebuild, dirty-source refusal, post-build provenance refusal, a rebuild forced from a foreign working directory, a stale `JAVA_HOME` with and without an available pin (the no-pin case is the one that reaches the start-failure path, and it asserts the preserved launcher stderr and the exact `JAVA_HOME` named), a corrupt install, and a build that leaves no launcher. | Before a sibling project runs a retained evidence capsule against current source; reuse the returned launcher with `batch`, and retain the result only if the source revision remains unchanged through the capsule. |
| [`selftest-prepare-dmtool-source.sh`](selftest-prepare-dmtool-source.sh) | Behavioral guard for `prepare-dmtool-source.sh` using a disposable Git repository, a fake build, and a fake launcher that reproduces Gradle's generated start-script `JAVA_HOME` gate (both the `jre/sh/java` and `bin/java` probes). It stubs the shared helper to reach the no-pin branch, so the start-failure path is exercised on every platform rather than only where `java_home -v 21` fails. | Runs through `DmtoolLauncherTest` in the input-declared `deliveryGuardTest`; run directly while changing source preparation. |

A real run requires a file-auth Codex login and consumes one model turn. |

| [`doctor.sh`](doctor.sh) | Report the state of **this machine's** build preconditions as PASS/WARN/FAIL, exiting non-zero on FAIL: a resolvable JDK 21, the Gradle home this build would actually use and whether anything foreign injects into it, whether the machine-default home runs init scripts and whether they honour the `.no-global-gradle-repos` marker, the kernel in `mavenLocal`, and the optional direnv/node conveniences. | [`gradle-environment.sh`](gradle-environment.sh) | **Shared helper, and the single source of two environment policies.** `a12_gradle_user_home` resolves the init-script-free Gradle user home consistently for the primary checkout, linked worktrees, and isolated release consumers; consumer homes may reuse its already-resolved wrapper distribution without sharing dependency caches or init scripts. `a12_pinned_jdk21_home` resolves the JDK 21 pin, because the build pinning one JDK while a launcher check kept the caller's is exactly how a stale `JAVA_HOME` became a source-provenance verdict. | [`test-evidence.sh`](test-evidence.sh) | Answer the question `BUILD SUCCESSFUL` does not: **what did that run actually execute?** Reads a saved `--console=plain` log plus the result XMLs and prints each test task's real state (EXECUTED / UP-TO-DATE / FROM-CACHE / FAILED — a task appearing twice keeps the most severe) together with test counts from **only** the XMLs written during that run. Read-only; never runs Gradle. | Whenever a build result is going to be used as **evidence** — a checkpoint, a mutation sweep, or any conclusion drawn from counts. On 2026-08-15 a stale-XML scan produced a wrong 17-class verdict, and the freshness bug this script was written to prevent was present in its own first version. |
| [`perf.sh`](perf.sh) | Run the existing interpreter **diagnostic/regression sweeps** with reliable capture and print only the result lines—`perf.sh <gate\|bench\|crossover\|distributed\|scaling\|huge\|js> [pattern-or-counts-or-scenario]`. `gate` runs the routine paired-median growth/canary tier through the dedicated single-fork, non-cacheable `:adapter:perfGateTest` task and accepts a JUnit method pattern. It passes **no** `--tests` filter by default, because the task selects the whole `@Tag("perf")` tier itself — a filter here could only ever narrow it (Gradle ANDs the two), which is how an enumerated list once left five tagged routine-tier bars running in no lane at all; `bench` runs the closed B-series kernel-ratio inventory with dynamic-Groovy/generated-Java agreement and accepts one exact scenario id (`perf.sh bench B9-berlin-datetime`, unknown ids fail). The script writes the full `-i` log to `build/perf-<mode>.log` raw (never a live `grep`/`head` pipe, which truncates via SIGPIPE), then extracts result lines. The `js` mode propagates the Node/Mocha exit after printing the captured result lines, so a failing JS performance run cannot report success (IF170). This remains the diagnostic/catastrophe harness; the separate `interpreter-performance.sh` owns fresh-process and native evidence. | For diagnostic measurements and catastrophic-regression checks; not startup certification or the everyday inner loop. |
| [`perf-anchor.sh`](perf-anchor.sh) | Refresh the committed per-runner-class performance anchor from a gate run's observations—`perf-anchor.sh <show\|refresh> [run.jsonl ...]`, defaulting to the newest run recorded under [`perf-results/`](../perf-results/README.md). `show` prints the diff a refresh would make and changes nothing. Several inputs anchor their per-key **median**; a refresh that would leave any lane the anchor file carries without a bar is **refused** (`ALLOW_REMOVALS=1` overrides), including for a new runner class, where the other classes' key sets are the only thing that can see a hole. The anchor is the only bar that can see a **uniform** interpreter slowdown (a growth ratio is unchanged by one at every factor), and it is committed rather than rolling so successive within-tolerance degradations cannot compound; refreshing it is therefore a deliberate, reviewable diff. A hosted runner's block can only be authored from a hosted run: dispatch the nightly (`gh workflow run 'Nightly performance' --ref <branch>`) and pass its `perf-observations` artifact — the script's header carries the three commands. On a **non-hosted** class, a run that cannot identify the **machine** it measured is refused, whether the field is absent or carries the probe's `"unknown"` sentinel. A **hosted** class (`-ci`) is machine-less by policy — the provider picks the CPU per job and the fleet is not enumerable — so there the machine is neither required, compared, nor written into the block, and runs on different models fold to their median. `PerfAnchorScriptTest` executes its refusals. | When a change makes a measured cost legitimately higher, in that change's own commit—or to author a new runner class's block. |
| [`mutant.sh`](mutant.sh) | **Plant one mutant, run only its control class, restore.** `mutant.sh <file> <old> <new> <test-filter> [lane]`. Measured reason to exist: the same mutant, same verdict, took **3 s** filtered to its control and **3 m 17 s** run as a lane — 10x-60x, five to ten times per review. It also refuses two failure modes that cost real work: it will not run on a file with uncommitted changes (reverting a mutant with `git checkout --` destroyed three edits in one session) and it fails loudly if the text to replace is absent, because an unapplied mutant reports SURVIVED and reads as a finding. A filter matching no test is reported as a typo, never as a kill. If you cannot name the control that should catch a mutant, that IS the finding — write the control first. | Whenever a review plants a mutant. |
| [`obligations.sh`](obligations.sh) | **Execute the trigger table instead of remembering it, and name the traps prose does not prevent.** Beyond the doc obligations it fires on two mistakes that were written into `CLAUDE.md` and then committed anyway, by the author, hours later, in one session — which is the evidence that they need a mechanism rather than a rule: a **test-result XML recording a failure** (reported with its age, since XMLs persist and a stale red is not a reason to stop) and a **backlog of unpushed commits** (129 once sat local while CI ran on none of them, so local green was the only signal). These run even with nothing staged, because "am I about to commit on red?" does not depend on the diff. Prints the same-commit obligations a change fires and names the guard covering each — `obligations.sh [ref|A..B] [--strict]`, defaulting to the staged diff. It is a **review trigger, never a guard**: it decides nothing and exits 0 unless `--strict`, because the residue it points at is semantic (*is this sentence still true?*) and a tool claiming to settle that would advertise what it cannot point at. Its distinctive rule is **referent drift**: a prose line whose `-`/`+` pair differs only inside markdown links — **label as well as target** — fires an obligation to re-read the surrounding sentence. That is the class no guard in this repo can see, because every link still resolves; blanking only `](target)` was tried first and missed the founding commit outright, whose rename changed the label too. The diff is taken with explicit `a/`/`b/` prefixes, since a user's `diff.mnemonicPrefix` emits `c/`/`i/` on a cached diff and silently made the trigger dead for the pre-commit case it exists for. | Before committing, especially any prose edit that renames a link. |
| [`selftest-obligations.sh`](selftest-obligations.sh) | Behavioural guard for the trigger above: drives it over fabricated git repositories for the fire and **do-not-fire** directions (a rename-only line fires; a rewritten sentence must not, which is the discriminator that keeps the rule from firing on most of this estate's prose), a clean tree, a path-classified row against an unrelated path, and `--strict`. Case 6 is pinned to the real commit `f9f92cdb`, the referent-drift defect the rule was built for — the only proof it fires on its own class. | [`findings-overlap.py`](findings-overlap.py) | Rank every pair of findings entries by TF-IDF cosine and split the result **same-doc vs cross-doc**, which is the split that decides whether the append-only estate is accumulating restatements — `findings-overlap.py [--threshold 0.40] [--show N]`. It exists to settle by measurement a deferred proposal to build near-duplicate detection over the corpus, and it did: across **609 entries / 185 136 pairs**, 67 pairs clear 0.40, of which **54 are cross-doc and 52 of those are `IF`\|`KF`** — the estate's deliberate pairing, where KERNEL-FINDINGS records what the kernel does and INTERPRETER-FINDINGS records the clean-room reimplementation matching it, so high similarity there is the licensing boundary working rather than a defect. Of the 13 same-doc pairs none is a restatement on inspection; the strongest, `IF112`\|`IF118` at 0.512, is a formal-side and an eval-side defect of one shape whose own first sentence reads *"The EVAL twin of IF112"*. The score is a **shortlist, never a verdict** — "restates" is semantic and the pair must be read. Recall limit, stated because it bounds the answer from one side only: this finds **lexical** overlap, so it can prove duplication exists and cannot prove none does. | To re-decide near-duplicate detection when the corpus has grown materially (~900 entries) or when same-doc pairs stop being twins-or-increments on inspection; the deferral's re-open trigger, not a routine lane. |
| [`perf-keys.sh`](perf-keys.sh) | Attribute a JFR profile's **hash-key mechanics** to the interpreter frame that built the key — `perf-keys.sh <validate\|compute\|recording.jfr> [frame ...]`. The driving modes run one ~20 s single-scenario loop under `jdk.ExecutionSample`; the third mode only reads an existing recording. It reports where the samples are, how far a key mechanic's family reaches, and — the discriminating view — which caller a shared helper's cost arrives through. It exists because this class of cost is **invisible** to a hot-methods profile: it lands in `java.util.*` frames attributed to nobody, which is how [IF284](../docs/INTERPRETER-FINDINGS.md#if284)'s sibling sweep initially missed both real members of the class ([IF285](../docs/INTERPRETER-FINDINGS.md#if285)). Recordings are timestamped per run, because a before/after instrument that overwrites its own baseline is useless — which it did once. A profile, never a bar: nothing asserts, and a contended machine moves the proportions. | Before optimizing a memo or a key, and for the before/after of any such fix. |
| [`perf-trend.sh`](perf-trend.sh) | Detect **step changes** in the committed record and report each row's run-to-run **noise** — `perf-trend.sh [pattern]`, with `ENV=` selecting one runner class and `MIN_SIDE=`/`MIN_SHIFT=`/`Z=` as the dials. Reads [`perf-results/`](../perf-results/README.md) only; never measures, never writes, and always exits 0 on a readable record, because the enforcement half ([IG121](../docs/INTERPRETER-GAPS.md) piece 1) is downstream and sizes its band from the noise printed here. Runs are grouped by `(environment, jdk-MAJOR, os, machine)` — the JDK **patch** and, on a hosted class, the **machine** are deliberately not boundaries: the provider hands out whichever it likes per job, and splitting on either shatters the history a step claim needs (all four figures re-derived from the committed hosted record on 2026-08-16, 10 runs, one control: segmenting on both leaves **0** rows carrying the six runs a step claim requires, against **142** when merged, and the rows stranded at a single run fall from **524** to **0**) so a platform change re-bases numbers instead of reading as a regression, and an **absent** field resolves to its environment's known value rather than splitting the series — the real record has 17 darwin runs predating the `machine` field, and treating null as a distinct value would halve the history every noise estimate reads. A step is reported only when its robust score clears `Z` **and** its size clears `MIN_SHIFT`: score alone flags a 12 % shift on a very quiet row, size alone flags ordinary wander on a noisy one, and `PerfTrendScriptTest` holds both halves plus the stable-series false-positive control. The change point names the commit at its boundary, which is how a re-basing revision is discovered rather than hand-maintained. **`--ratio`** switches to the cross-engine view: it derives each row's margin over each kernel strategy by joining the engines of one `(lane, scenario, n, clock)` row *within* each run — the margin series is not a key in the record — and reports the margin, its own spread, and the worst margin the record holds. That is a different quantity from the step view's noise, because both engines share a JVM and load slice so an excursion largely cancels in a ratio (a row whose absolutes swing 2× at a fixed ratio reports ±1.0 %). **The cross-arm reading** (`ARMS`, IG137 piece c) reconciles the engine arms of one row instead of leaving the reader to correlate them: all three engines share the JVM, the vCPUs and the load slice within a run, so an all-arm step in one direction is the **machine re-basing** and cannot be a code change, while arms that disagree — or step in opposite directions — attribute the move to whichever side actually made it. A row where nothing stepped prints nothing. **`BAND=<fraction>` / `BAND_SIGMA=<k>`** backtest a candidate early-warning floor (IG121 piece 1) against the current level of each row and report how many historic runs it would have tripped — the check that stopped the third guess at this band from being another unbacktested one. Measured answer: no floor reaches zero firings, because the record holds genuinely contended runs a margin cannot tell from a regression, which is why the band must warn rather than fail. | To find out whether a cost actually stepped and when, to read the per-row noise a bar must respect, and (with `--ratio`) how much headroom the parity gates actually have. |
| [`perf-history.sh`](perf-history.sh) | Render the committed performance record as a **text table**, newest runs as columns — `perf-history.sh [pattern]`, with `RUNS=` widening the window and `ENV=` selecting one runner class. Reads [`perf-results/`](../perf-results/README.md) only: it never measures and never writes. Rows from different environments are never placed in the same table (absolute timings are comparable only within a runner class), and each run's header carries the conditions that make its numbers readable (commit, JDK, processor count, load average, CI run id, machine). It **discloses** rather than splits on the machine — a table whose runs name different ones says so, an unrecorded one prints `?` and is never counted as a difference — because splitting would cut the series at the point the field was introduced and hide the continuity the table exists for. The trend column compares the newest value with the median of the earlier ones and is a report, never a verdict. Each row is labelled `lane · scenario @scale [engine/clock]`: the scenario is load-bearing, since one lane holds many and without it ten `kernel parity` rows printed identically (fixed 2026-08-12, guarded by `PerfHistoryScriptTest`). | To see whether a cost has drifted across runs, and to pick the runs worth folding into the anchor. |
| [`perf-report.sh`](perf-report.sh) | The ONE performance question, answered in one command — `perf-report.sh [pattern]`, with `ENV=`/`RUNS=` as the dials. Five sections: the newest run per runner class with its conditions and its observation **status tally**, then levels, step changes, cross-engine headroom, and what an anchor refresh would change. Sections 2-5 **delegate** to `perf-history.sh`, `perf-trend.sh` (twice) and `perf-anchor.sh show` verbatim; only the status section parses the record, because that projection existed nowhere and its absence is what sent maintainers to hand-rolled `awk` over the JSONL — the habit that produced the reader-side locale bug. ## The single-source pattern

The skill and the binary installer are shared **verbatim** by both agent plugins, so they live in exactly one place and are **copy-synced** into each plugin's skill dir (symlinks don't survive the release-mirror push). The per-agent files — each plugin's manifest and Codex's `AGENTS.md` — are maintained in place, never synced. There is **no session hook**: the binary is fetched on demand by the skill the first time `dmtool` is needed. `sync-plugin-assets.sh --check` is the no-drift guard; add a new plugin tree to its `PLUGINS` list when another agent is supported.
