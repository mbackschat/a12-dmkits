## What this module is

The **`:interpreter`** module is a Kotlin Multiplatform, native-safe rule evaluator (package `…dm.interpreter`) being **grown into the full evaluator in this repo** (decision 2026-06-23, [`../docs/INTERPRETER-SPEC.md`](../docs/INTERPRETER-SPEC.md) §8; impl in [`../docs/INTERPRETER-ARCHITECTURE.md`](../docs/INTERPRETER-ARCHITECTURE.md))—*not* extracted to a sibling repo. The committed goal is a full-blown interpreter serving two consumers: (1) dmtool's **native image** (`model eval`/`model compute`/`rule eval`; `examples/cli-runtime.md` runs end-to-end), and (2) a standalone Kotlin/JVM + Kotlin/JS API for full/partial validation, computations, and single-rule/single-computation evaluation. The API exists and is Node-tested locally; Maven/npm publication + ABI locking remain IG85 and a browser host remains unverified IG86. Correctness = agrees with the real kernel—**both its runtime AND codegen strategies** (the differential oracle verifies the runtime half; see the #1 rules §A).

**The goals, with the owner's priorities (decided 2026-06-23):** the interpreter is **(a) feature-complete** (the full operator catalog — scope), **(b) matches kernel semantics/behaviour EXACTLY** (**priority #1**), and **(c) performant** — *good* performance is **priority #1**, *equal-to-or-better-than the kernel* is **priority #2** (a stretch, plausible since we carry no Groovy/codegen). (b) and the "good performance" half of (c) are co-equal #1s and never traded against each other: never sacrifice exactness for speed, nor ship a known-slow (O(N²)) path. The #1-rules section (exact match + clean-room) governs (b); [`../docs/INTERPRETER-PERFORMANCE.md`](../docs/INTERPRETER-PERFORMANCE.md) governs (c).

**Customization-surface parity is part of (a)+(b) — a #1-priority goal (added 2026-06-27).** *The interpreter must expose, on its API, EVERY customization point the kernel offers* — a customization the kernel honors but the interpreter can't accept is a compatibility gap, NOT a "nice to have." These are the consumer SPIs the kernel takes at runtime/codegen: **custom conditions** (`ICustomCondition` → `CustomCondition`), **custom field types** (`ICustomFieldType` → the predefined/custom type registries), and the **legal/restricted charset** (the kernel's project-level `legalCodepoints`, e.g. **DIN 91379** for EU public administration → `LegalCharset`, default `BMP`, IF43). Each must (1) have a default that matches the kernel's DM-JSON default and (2) accept a consumer-supplied value so the interpreter enforces the same restriction the configured kernel would. When you discover a kernel customization the interpreter doesn't surface or does not reproduce exactly, that is a gap. **The input slots as of kernel 30.8.1** (re-audit on a [`KERNEL-UPGRADE`](../docs/KERNEL-UPGRADE.md)) are mapped: `DocumentProcessingConfig` = `{languageOfErrorMessages (locale), customConditionFactory, customFieldTypeFactory}` (its `additionalInformation` is deprecated), plus the meta-model `legalCodepoints` (charset), model `timeZone`, and `Now`/`Today` clock. Mapping the slots is not the same as semantic completeness: the full timezone-id/history domain is IG83, combined charset sequences IG88, and custom-validator rejection-code identity IG92.

**The north star—the sole runtime EVAL engine (owner-elevated 2026-07-11 "Scope A"; EXECUTED 2026-07-12, Set V).** DONE: **`--kernel` eval is retired** and evaluation is interpreter-only on every target. This is the evaluation role only; the kernel's consistency/MVK gate stays kernel-backed, so reproducing that oracle (“Scope B”) is a separate deferred question. The [compatibility certificate](../docs/INTERPRETER-DROPIN-CERTIFICATE.md) records strong evidence on its exercised surface and the historical retirement decision, not proof over every legal input. The 2026-07-19 re-audit found additional exactness, preparation, API-safety, platform, mutation, and evidence gaps; [INTERPRETER-GAPS.md](../docs/INTERPRETER-GAPS.md) is the exhaustive current list and must not be replaced by a short exception summary here. The differential estate remains the verification surface and the kernel remains the `:adapter` oracle.

## #1 rules — MATCH kernel semantics EXACTLY, via a clean-room reimplementation (decided 2026-06-23)

The interpreter has **two non-negotiables**, a WHAT and a HOW:

**(A) MATCH kernel semantics EXACTLY — BOTH evaluation strategies (runtime AND codegen).** Every behavior the interpreter produces must equal the real kernel's, bit-for-bit on every legal input. There is no "close enough." A kernel special case that is **observable through the differential** (e.g. the Feb-28 leap-year time-clearing in `AddYears`/`AddMonths`, the scale-19 compare-rescaling, the `MathContext(50)` arithmetic cap) is a **must-match**, never droppable as "obsolete." The "kernel is old — report German-only/obsolete/feature-flagged special cases for review" guidance is **narrow**: only things that are *not observable runtime behavior* are reportable-and-droppable — German message *text* (we use our own, IF3), a dead/feature-flagged code path that never executes, pure editor/rendering cruft. If a behavior changes any differential outcome, match it exactly; only genuinely unreachable/irrelevant cruft is reported for a drop decision.

**"The real kernel" means BOTH of its evaluation strategies — the md-RUNTIME dynamic service (`IDocumentRtService`) AND the Groovy CODE GENERATOR — and the interpreter must match BOTH (clarified 2026-06-27).** Compatibility is NOT "match the differential oracle"; the differential oracle (`RuntimeLaws`/`KernelAdapter`, both the runtime dynamic service) is the *primary verification surface*, but it only proves **runtime**-parity. **Codegen-parity is a co-equal target** that the runtime oracle CANNOT verify — so where a behavior lives in codegen, confirm it from the **codegen source** (`kernel-core-codegen-*`) and lock it against codegen-derived expectations. The two strategies can DIVERGE (a kernel fact to characterize, not ignore). **Ratified oracle (IF136, owner-decided 2026-07-19):** on a legal-input split the interpreter matches the **Groovy-dynamic** runtime — the production-normative anchor — while the **static-Java** codegen result is recorded as a characterized divergence (the corpus `divergences` mechanism, [`../docs/CONFORMANCE-CORPUS-SPEC.md`](../docs/CONFORMANCE-CORPUS-SPEC.md) §11) and **never adopted**. The split axis is **dynamic-Groovy vs static-Java**, not "runtime vs codegen"; the runtime differential gates the interpreter against the anchor, and a recorded static-Java split is carved out of it (it cannot gate the interpreter). The **one place a behavior is legitimately droppable is when it is DEAD in *both* strategies** — generated by neither the runtime autogen service nor the codegen (proven from source, not assumed). Worked precedent (2026-06-27): the multi-select value-uniqueness `FEHLER_MULTI_SELECT`/`uniqueValue` is dead in 30.8.1 — `AutogeneratedRulesService` has no multi-select method (runtime) AND no `IAutogeneratedRule.getGenerationType()` returns `UNIQUE_VALUE`, so `CodeGenRuleDefinition`'s `case UNIQUE_VALUE` is unreachable (codegen) — so the interpreter does NOT fire it, matching both (KERNEL-FINDINGS "multi-select value uniqueness is DEAD code"; the sibling of the dead `mandatoryGroup`).

**(B) Clean-room reimplementation, NEVER kernel delegation (the license boundary).** Reimplement the kernel's semantics; do not delegate to the kernel, and do not transliterate its source. The reason is **licensing, not preference**: the A12 kernel is **EUPL-1.2** (copyleft) / commercial. A runtime that *uses* the kernel (links/ships/calls it) is a combined work the EUPL copyleft reaches — so it would have to be EUPL (or commercial). The whole point of `:interpreter` is to give dmtool's **native runtime a kernel-FREE engine**, so that runtime carries **no kernel code and is free of the EUPL** (and the kernel's Groovy codegen can't go native anyway — delegation fails the native goal too).

A and B together: *read the kernel source to learn the exact behavior → write original Kotlin that reproduces it exactly → lock it with the differential.* Therefore:

- **Never delegate** operator evaluation to the kernel from the interpreter (no `com.mgmtp.*` call, no JS-kernel binding) — the purity lint enforces the no-link half.
- **Derive each operator from BEHAVIOR, clean-room** — the **differential oracle** (the real kernel as a *black box*: feed inputs, observe outputs) + the public BA/KERNEL-SEMANTICS spec. **Do NOT copy/transliterate the kernel's source expression** (e.g. don't port `BedingungsOperatorHelper`), because a line-by-line port can be a copyright **derivative** that re-attracts the EUPL. Copy the *mechanism/behavior* (not protected), never the *expression* — the standing license-safe rule. **Reading the kernel source is encouraged for *understanding*, not only to audit a divergence** — proactively scan the **operator sources *and* the code-generator sources** to learn an operator's real semantics and surface *surprising special cases* you'd never think to probe blind (e.g. `Now` truncation-to-day, datetime day-rollover, the `Date(...)`/`Time(...)` digit-pattern operand rules). Then the loop is *read source → write original Kotlin → verify against the differential*; the *fix* is never a transliteration.
- With `--kernel` eval retired (Set V), dmtool touches the kernel only for the **MVK consistency oracle** (`rule check`/`model check`, JVM-only) and as the `:adapter` **differential oracle** (test scope) — never on the eval path. That JVM distribution (which bundles the kernel for the oracle) is where EUPL/commercial applies; the native/JS runtime carries no kernel and stays clean.

**Separation is kept by convention + linting, not a repo wall** — the §7 hygiene rules are mechanically enforced, so don't hand-wave them:

- `:interpreter` carries **no kernel/dmtool dependency** (it is the publishable standalone artifact). The kernel **differential tests stay in `:adapter`** (never in `:interpreter`'s test source), so the module is kernel-free even in test scope.
- The **purity lint** (`:interpreter`'s `verifyInterpreterPurity`, wired into `check`) fails the build on a forbidden import: `commonMain` may not import `java.*`/`com.mgmtp.*`/`groovy.*`; `jvmMain`/`jsMain` may not import `com.mgmtp.*`/`groovy.*`. Run it as part of any `:interpreter` change.
- `:interpreter` never depends on `:`/`:adapter`/`:cli` — they consume it, never the reverse.

Extraction to a sibling repo is a **future option, not a prerequisite** — do it only if the interpreter earns an independent OSS life/release cadence (§8); the lint keeps that a lift, not a rewrite. ## Non-functional requirements — low startup, high performance, low RELATIVE footprint

The interpreter must start quickly, be **performant on the hard cases**, and keep a low **relative** footprint; these are measured requirements, not hopes. Numerical candidates live in [`../docs/INTERPRETER-SPEC.md`](../docs/INTERPRETER-SPEC.md) “Non-functional contract”; the contract posture is ratified (IF137) and each number requires per-number certification before it becomes a release bar; the method, catalog, status, and dated evidence live in [`../docs/INTERPRETER-PERFORMANCE.md`](../docs/INTERPRETER-PERFORMANCE.md). Non-negotiables:

- **REAL documents only — benchmarking a shortcut data structure is cheating.** Measure over the production evaluation path: the general `Document` (and the kernel's `IDocument`) built from real DM-JSON models. The spike's `Map`-backed `RepDoc` (O(1) lookups) must **never** be the thing benchmarked — its numbers are a fiction that hides the real complexity. A benchmark that doesn't exercise the real group resolution (parallel index, common-prefix, star) is not a benchmark.
- **Measure AGAINST the kernel, as a regression gate.** The perf benchmark is the twin of the correctness differential and lives in `:adapter` (which has the kernel): for each scenario run BOTH `kernel.validateFull` and `DmInterpreter.validateFull` over the same real instance, record both wall-clocks + the ratio, assert correctness (interp == kernel) AND a time/ratio bound that trips on an O(N²)-class regression.
- **Target the non-obvious group machinery, at scale.** Deeply **nested repeatable groups** (3–4 levels), **parallel iteration** / cross-level (common-prefix) references, **starred aggregates** over large repetition lists, and **many rows (up to 100 000)**—not the flat/obvious cases. The general `Document`'s former O(P) value scans are indexed; preserve that invariant, eliminate the confirmed overlay O(rows²) paths (IG60), and resolve the multi-star equality-correlation legality/growth risk (IG98).
- **Run on the PURE engine, decoupled from the CLI — cheap to run, very often.** Both the correctness differentials and the perf harness hit the **`DmInterpreter` + `Document` API directly** (kernel via `RuntimeLaws`), never through `dmtool`/`InterpreterEngine`/the loader — no process spawn, no `installDist`, no JSON envelope. A "real document" is the real `Document` *structure* built programmatically in-test, not loaded through the CLI. **Invest heavily in a proper, reusable harness** (scenario abstraction, warmup+repeats+median, ratio-vs-kernel, profile mode) — it gates regressions *and* finds the hotspots.
- **Low startup is true FIRST-ANSWER latency.** Measure a fresh engine from before `DmInterpreter(model)` through complete result materialization and gate p95 over independent fresh processes; keep native CLI process-to-envelope latency as a separate end-to-end measure. A minimum of first-validation-only samples is a complexity probe, not startup certification. Never count kernel codegen.
- **Low footprint is RELATIVE — caching is allowed and ADVISED for high performance.** Do **not** reject an index, hash map, memo, prepared AST, or other memory-intensive optimization merely because it raises heap use. Prefer the cache when it removes repeated work or improves the complexity class. Instead, require the cache to have a bounded owner/lifetime (engine, document/index, call, or row), correct invalidation, plateau under repeated evaluation, and linear-class space growth; report its memory/artifact delta beside the performance win. Footprint is compared with the previous release and the equivalent kernel/Groovy stack, never optimized toward an arbitrary tiny heap cap.

When these goals pull against each other: exactness is never traded; cold and warm performance are separate co-equal regimes; a bounded memory increase that demonstrably improves either is compatible with — and often required by — the relative-footprint goal.

## Structure for a future GENERATOR — separate runtime semantics from evaluation strategy (standing requirement, decided 2026-06-23)

We build the **interpreter** now, but must stay flexible to later add a **generator** (the kernel's approach: emit code per model instead of tree-walking). **Both an interpreter and a generator are evaluation *strategies* that delegate to the SAME runtime** — the operator implementations. So **don't implement the generator, but keep the layering ready for it**:

- **Layer the engine as: data-access → runtime operator semantics → strategy.** (1) **Data access** = `EvalContext`/`Document` (`field`/`filled`/`signed`/`star`/`reps`). (2) **Runtime operator semantics** = pure, AST-walk-agnostic functions over *resolved* values (`Val`/`Tri`/`Fill`): 3VL `and`/`or`, directional number compare, `quantifierFires`, the date/time math (`DateMath`), aggregates, value-list, pattern. (3) **Strategy** = the interpreter's tree-walk *today*; a generator that emits code *later* — both consume (1)+(2). This mirrors the kernel exactly: its codegen emits Groovy that calls `BedingungsOperatorHelper`/`ValidierungsErgebnis`/`Combiner` (the runtime).
- **The rule that keeps it ready:** operator semantics must **not** be inlined into the tree-walk or depend on "I am walking an AST" — they live in the shared runtime layer as pure functions a generated program could call just as the interpreter does. `DateMath` and the `PredicateOp`/`FunctionOp` registries already are; the comparison/3VL/aggregate logic in `Interpreter` should migrate there as it's touched. When adding an operator, put its *semantics* in the runtime layer, and let the strategy only **dispatch + resolve operands**.
- Detail + the target layer diagram: [`../docs/INTERPRETER-FINDINGS.md`](../docs/INTERPRETER-FINDINGS.md) IF10. The extraction of today's inlined semantics is a tracked refactor, not a prerequisite for more operators.
