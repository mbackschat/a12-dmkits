## What this module is

The **`:interpreter`** module is a Kotlin Multiplatform, native-safe rule evaluator (package `…dm.interpreter`) being **grown into the full evaluator in this repo** (decision 2026-06-23, [`../docs/INTERPRETER-SPEC.md`](../docs/INTERPRETER-SPEC.md) §8; impl in [`../docs/INTERPRETER-ARCHITECTURE.md`](../docs/INTERPRETER-ARCHITECTURE.md))—*not* extracted to a sibling repo. The committed goal is a full-blown interpreter serving two consumers: (1) dmtool's **native image** (`model eval`/`model compute`/`rule eval`; `examples/cli-runtime.md` runs end-to-end), and (2) a standalone Kotlin/JVM + Kotlin/JS API for full/partial validation, computations, and single-rule/single-computation evaluation. The API exists and is Node-tested locally; Maven/npm publication + ABI locking remain IG85. Node is the **supported** JS runtime; a browser host is an **unverified future capability, deferred** (IF138) — it re-opens when a real browser consumer materializes or the publication wave promises browser. Correctness means matching the normative dynamic-Groovy result and also static-Java wherever the two agree; a legal split is recorded but never adopted (IF136; see the #1 rules §A).

**The goals, with the owner's priorities (decided 2026-06-23; performance target strengthened 2026-07-21):** the interpreter is **(a) feature-complete** (the full operator catalog — scope), **(b) matches kernel semantics/behaviour EXACTLY** (**priority #1**), and **(c) performant** (**priority #1**). On every protocol-valid comparable scenario and tested scale, the interpreter must beat both kernel strategies—dynamic Groovy and generated Java—in absolute evaluation time, and its growth factor must be no worse than either. A repeatable loss is an active performance defect and becomes the next optimization priority; it is never accepted merely because the kernel is fast. If the kernel itself scales badly and several focused, evidence-driven root optimizations cannot improve the interpreter further, stop before designing a larger subsystem, report the evidence and attempted fixes, and ask the owner what to do. Exactness and performance are never traded against each other: never sacrifice exactness for speed, nor time a reduced result. The #1-rules section (exact match + clean-room) governs (b); [`../docs/INTERPRETER-PERFORMANCE.md`](../docs/INTERPRETER-PERFORMANCE.md) governs (c).

**Customization-surface parity is part of (a)+(b) — a #1-priority goal (added 2026-06-27).** *The interpreter must expose, on its API, EVERY customization point the kernel offers* — a customization the kernel honors but the interpreter cannot accept is a compatibility gap, not a “nice to have.” These are the consumer SPIs the kernel takes at runtime/codegen: **custom conditions** (`ICustomCondition` → `CustomCondition`), **custom field types** (`ICustomFieldType` → the predefined/custom type registries), and the **legal/restricted charset** (the kernel's project-level `legalCodepoints`, e.g. **DIN 91379** for EU public administration → `LegalCharset`, default `BMP`, IF43). Each must have the kernel-equivalent default and accept a consumer-supplied value. **The input slots as of kernel 30.8.1** (re-audit on a [`KERNEL-UPGRADE`](../docs/KERNEL-UPGRADE.md)) are mapped: `DocumentProcessingConfig = {languageOfErrorMessages, customConditionFactory, customFieldTypeFactory}` (`additionalInformation` is deprecated), plus meta-model `legalCodepoints`, model `timeZone`, and the `Now`/`Today` clock. For a stored custom-field value, `CustomFieldType.check(value, context)` receives the call locale, effective bounds (`1`/`999` when omitted), and `isDisplayValue=false`; one relevance-first invocation per concrete value supplies the cached code/message result to emission and suppression, including `$<fieldName>$` substitution (IF150/IF152). Europe/Berlin's full history + the enforced `{UTC, GMT, Europe/Berlin}` supported set (with a corrective refusal for any other kernel-legal zone) shipped as IF155; the wider non-Berlin timezone-id domain remains IG83 (Route A, deferred). Combined charset sequences shipped as IF151.

**The north star—the sole runtime EVAL engine (owner-elevated 2026-07-11 "Scope A"; EXECUTED 2026-07-12, Set V).** DONE: **`--kernel` eval is retired** and evaluation is interpreter-only on every target. This is the evaluation role only; the kernel's consistency/MVK gate stays kernel-backed, so reproducing that oracle (“Scope B”) is a separate deferred question. The [compatibility certificate](../docs/INTERPRETER-DROPIN-CERTIFICATE.md) records strong evidence on its exercised surface and the historical retirement decision, not proof over every legal input. The 2026-07-19 re-audit found additional exactness, preparation, API-safety, platform, mutation, and evidence gaps; [INTERPRETER-GAPS.md](../docs/INTERPRETER-GAPS.md) is the exhaustive current list and must not be replaced by a short exception summary here. The differential estate remains the verification surface and the kernel remains the `:adapter` oracle.

## #1 rules — MATCH kernel semantics EXACTLY, via a clean-room reimplementation (decided 2026-06-23)

The interpreter has **two non-negotiables**, a WHAT and a HOW:

**(A) MATCH kernel semantics EXACTLY — dynamic-Groovy is normative; static-Java is co-evidence.** Every behavior the interpreter produces must equal the dynamic-Groovy result, bit-for-bit on every legal input, and equal static-Java wherever the two kernel strategies agree. There is no "close enough." A kernel special case that is **observable through the differential** (e.g. the Feb-28 leap-year time-clearing in `AddYears`/`AddMonths`, the scale-19 compare-rescaling, the `MathContext(50)` arithmetic cap) is a **must-match**, never droppable as "obsolete." The "kernel is old — report German-only/obsolete/feature-flagged special cases for review" guidance is **narrow**: only things that are *not observable runtime behavior* are reportable-and-droppable — German message *text* (we use our own, IF3), a dead/feature-flagged code path that never executes, pure editor/rendering cruft. If a behavior changes any differential outcome, match it exactly under the ratified split rule below; only genuinely unreachable/irrelevant cruft is reported for a drop decision.

**"The real kernel" supplies two evidence strategies — the dynamic-Groovy md-runtime service (`IDocumentRtService`, generated/cached Groovy) and static-Java codegen.** Compatibility is not merely “the available differential passed”: `RuntimeLaws`/`KernelAdapter` gate the interpreter against dynamic-Groovy, while static-Java tri-checks and codegen-source analysis expose the second strategy. The two can diverge, which is a kernel fact to characterize rather than ignore. **Ratified oracle (IF136, owner-decided 2026-07-19):** on a legal-input split the interpreter matches **dynamic-Groovy** — the production-normative anchor — while the **static-Java** result is recorded as a characterized divergence (the corpus `divergences` mechanism, [`../docs/CONFORMANCE-CORPUS-SPEC.md`](../docs/CONFORMANCE-CORPUS-SPEC.md) §11) and **never adopted**. The split axis is dynamic-Groovy vs. static-Java, not runtime vs. codegen. The **one place a behavior is legitimately droppable is when it is DEAD in both strategies** — generated by neither the runtime autogen service nor static-Java codegen (proven from source, not assumed). Worked precedent (2026-06-27): the multi-select value-uniqueness `FEHLER_MULTI_SELECT`/`uniqueValue` is dead in 30.8.1 — `AutogeneratedRulesService` has no multi-select method (dynamic-Groovy) and no `IAutogeneratedRule.getGenerationType()` returns `UNIQUE_VALUE` (static-Java), so `CodeGenRuleDefinition`'s `case UNIQUE_VALUE` is unreachable and the interpreter does not fire it (KERNEL-FINDINGS "multi-select value uniqueness is DEAD code"; the sibling of the dead `mandatoryGroup`).

**(B) Clean-room reimplementation, NEVER kernel delegation (the license boundary).** Reimplement the kernel's semantics; do not delegate to the kernel, and do not transliterate its source. The reason is **licensing, not preference**: the A12 kernel is **EUPL-1.2** (copyleft) / commercial. A runtime that *uses* the kernel (links/ships/calls it) is a combined work the EUPL copyleft reaches — so it would have to be EUPL (or commercial). The whole point of `:interpreter` is to give dmtool's **native runtime a kernel-FREE engine**, so that runtime carries **no kernel code and is free of the EUPL** (and the kernel's Groovy codegen can't go native anyway — delegation fails the native goal too).

A and B together: *read the kernel source to learn the exact behavior → write original Kotlin that reproduces it exactly → lock it with the differential.* Therefore:

- **Never delegate** operator evaluation to the kernel from the interpreter (no `com.mgmtp.*` call, no JS-kernel binding) — the purity lint enforces the no-link half.
- **Derive each operator from BEHAVIOR, clean-room** — the **differential oracle** (the real kernel as a *black box*: feed inputs, observe outputs) + the public BA/KERNEL-SEMANTICS spec. **Do NOT copy/transliterate the kernel's source expression** (e.g. don't port `BedingungsOperatorHelper`), because a line-by-line port can be a copyright **derivative** that re-attracts the EUPL. Copy the *mechanism/behavior* (not protected), never the *expression* — the standing license-safe rule. **Reading the kernel source is encouraged for *understanding*, not only to audit a divergence** — proactively scan the **operator sources *and* the code-generator sources** to learn an operator's real semantics and surface *surprising special cases* you'd never think to probe blind (e.g. `Now` truncation-to-day, datetime day-rollover, the `Date(...)`/`Time(...)` digit-pattern operand rules). Then the loop is *read source → write original Kotlin → verify against the differential*; the *fix* is never a transliteration.
- With `--kernel` eval retired (Set V), dmtool touches the kernel only for the **MVK consistency oracle** (`rule check`/`model check`, JVM-only) and as the `:adapter` **differential oracle** (test scope) — never on the eval path. That JVM distribution (which bundles the kernel for the oracle) is where EUPL/commercial applies; the native/JS runtime carries no kernel and stays clean.

**Separation is kept by convention + linting, not a repo wall** — the §7 hygiene rules are mechanically enforced, so don't hand-wave them:

- `:interpreter` carries **no kernel/dmtool dependency** (it is the publishable standalone artifact). The kernel **differential tests stay in `:adapter`** (never in `:interpreter`'s test source), so the module is kernel-free even in test scope.
- The **purity lint** (`:interpreter`'s `verifyInterpreterPurity`, wired into `check`) fails the build on a forbidden import: `commonMain` may not import `java.*`/`com.mgmtp.*`/`groovy.*`; `jvmMain`/`jsMain` may not import `com.mgmtp.*`/`groovy.*`. Run it as part of any `:interpreter` change.
- `:interpreter` never depends on `:`/`:adapter`/`:cli` — they consume it, never the reverse.

Extraction to a sibling repo is a **future option, not a prerequisite** — do it only if the interpreter earns an independent OSS life/release cadence (§8); the lint keeps that a lift, not a rewrite. ## Structure for a future GENERATOR — separate runtime semantics from evaluation strategy (standing requirement, decided 2026-06-23)

We build the **interpreter** now, but must stay flexible to later add a **generator** (the kernel's approach: emit code per model instead of tree-walking). **Both an interpreter and a generator are evaluation *strategies* that delegate to the SAME runtime** — the operator implementations. So **don't implement the generator, but keep the layering ready for it**:

- **Layer the engine as: data-access → runtime operator semantics → strategy.** (1) **Data access** = `EvalContext`/`Document` (`field`/`filled`/`signed`/`star`/`reps`). (2) **Runtime operator semantics** = pure, AST-walk-agnostic functions over *resolved* values (`Val`/`Tri`/`Fill`): 3VL `and`/`or`, directional number compare, `quantifierFires`, the date/time math (`DateMath`), aggregates, value-list, pattern. (3) **Strategy** = the interpreter's tree-walk *today*; a generator that emits code *later* — both consume (1)+(2). This mirrors the kernel exactly: its codegen emits Groovy that calls `BedingungsOperatorHelper`/`ValidierungsErgebnis`/`Combiner` (the runtime).
- **The rule that keeps it ready:** operator semantics must **not** be inlined into the tree-walk or depend on "I am walking an AST" — they live in the shared runtime layer as pure functions a generated program could call just as the interpreter does. `DateMath` and the `PredicateOp`/`FunctionOp` registries already are; the comparison/3VL/aggregate logic in `Interpreter` should migrate there as it's touched. When adding an operator, put its *semantics* in the runtime layer, and let the strategy only **dispatch + resolve operands**.
- Detail + the target layer diagram: [`../docs/INTERPRETER-FINDINGS.md`](../docs/INTERPRETER-FINDINGS.md) IF10. The extraction of today's inlined semantics is a tracked refactor, not a prerequisite for more operators.
