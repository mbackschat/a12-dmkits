## What this module is

The **`:interpreter`** module is a Kotlin Multiplatform, native-safe rule evaluator (package `…dm.interpreter`) being **grown into the full evaluator in this repo** (decision 2026-06-23, [`../docs/INTERPRETER-SPEC.md`](../docs/INTERPRETER-SPEC.md) §8; impl in [`../docs/INTERPRETER-ARCHITECTURE.md`](../docs/INTERPRETER-ARCHITECTURE.md)) — *not* extracted to a sibling repo. The committed goal is a full-blown interpreter serving two consumers: (1) dmtool's **native image** (the `model eval`/`model compute`/`rule eval` verbs the Groovy ceiling bars — acceptance: `examples/cli-runtime.md` runs end-to-end on the native image), and (2) a **standalone Kotlin/JVM + Kotlin/JS library** for any consumer running full **and partial** validation + computations, incl. **single-rule / single-computation** eval. Correctness = agrees with the real kernel — **both its runtime AND codegen strategies** (the differential oracle verifies the runtime half; see the #1 rules §A).

**The goals, with the owner's priorities (decided 2026-06-23):** the interpreter is **(a) feature-complete** (the full operator catalog — scope), **(b) matches kernel semantics/behaviour EXACTLY** (**priority #1**), and **(c) performant** — *good* performance is **priority #1**, *equal-to-or-better-than the kernel* is **priority #2** (a stretch, plausible since we carry no Groovy/codegen). (b) and the "good performance" half of (c) are co-equal #1s and never traded against each other: never sacrifice exactness for speed, nor ship a known-slow (O(N²)) path. The #1-rules section (exact match + clean-room) governs (b); [`../docs/INTERPRETER-PERFORMANCE.md`](../docs/INTERPRETER-PERFORMANCE.md) governs (c).

**Customization-surface parity is part of (a)+(b) — a #1-priority goal (added 2026-06-27).** *The interpreter must expose, on its API, EVERY customization point the kernel offers* — a customization the kernel honors but the interpreter can't accept is a compatibility gap, NOT a "nice to have." These are the consumer SPIs the kernel takes at runtime/codegen: **custom conditions** (`ICustomCondition` → `CustomCondition`), **custom field types** (`ICustomFieldType` → the predefined-type registry), and the **legal/restricted charset** (the kernel's project-level `legalCodepoints`, e.g. **DIN 91379** for EU public administration → `LegalCharset`, default `BMP`, IF43). Each must (1) have a default that matches the kernel's DM-JSON default (so the differential — which has no project config — stays exact), and (2) accept a consumer-supplied value so the interpreter enforces the SAME restriction the configured kernel would. When you discover a kernel customization the interpreter doesn't surface, that *is* a gap: add the SPI (default-matching), thread it, and lock it. **The surface as of kernel 30.8.1** (re-audit on a [`KERNEL-UPGRADE`](../docs/KERNEL-UPGRADE.md)): `DocumentProcessingConfig` = `{languageOfErrorMessages (locale), customConditionFactory, customFieldTypeFactory}` (its `additionalInformation` is deprecated), plus the meta-model `legalCodepoints` (charset) and the `Now`/`Today` clock/timezone — each mapped to a `DmInterpreter` input (`locale` / `customConditions` / `predefinedTypes` / `legalCharset` / `EvalClock`), so the surface is currently complete.

**The north star — the sole runtime EVAL engine (owner-elevated 2026-07-11, "Scope A").** The committed end-state: the interpreter is a **100% drop-in for the kernel's runtime EVALUATION path** (`model eval`/`rule eval`/`model compute`, incl. the JVM `--kernel` behavior), so **`--kernel` eval is retired** and evaluation is interpreter-only on every target. This is the *evaluation* role ONLY — the kernel's *consistency/MVK acceptance* gate (`rule check`/`model check`, `checkConsistency`) stays kernel-backed, so dmtool keeps bundling the kernel for the oracle even after `--kernel` eval is gone; reproducing the MVK oracle ("Scope B") is a separate, deferred question, never collapsed into this. Removal is gated on a documented **compatibility certificate** — now committed, [`../docs/INTERPRETER-DROPIN-CERTIFICATE.md`](../docs/INTERPRETER-DROPIN-CERTIFICATE.md) (SPEC §8a): the eval-core surface is green-or-documented-equivalent (0 divergences on both corpora in both seeding modes), and the former broad blocker **G1 (included-model-rule relativization) is closed for the realistic population** (Set U — relative + SINGLE_RG-absolute included conditions evaluate on the default path, differentially matched to `--kernel`; kernel-free relativizer in `dm.core.ModelReader`). Two **narrow owner calls** remain before it flips fully GREEN — **G1′** the R1 residual (MODEL_ROOT-absolute / bare-`/RG` / outer-correlated-absolute included refs, still loud-guarded) and **G2** the DST-timezone divergence (IG62). The open surface is [`INTERPRETER-GAPS`](../docs/INTERPRETER-GAPS.md) IG67. The kernel remains the `:adapter` differential oracle after removal.

## #1 rules — MATCH kernel semantics EXACTLY, via a clean-room reimplementation (decided 2026-06-23)

The interpreter has **two non-negotiables**, a WHAT and a HOW:

**(A) MATCH kernel semantics EXACTLY — BOTH evaluation strategies (runtime AND codegen).** Every behavior the interpreter produces must equal the real kernel's, bit-for-bit on every legal input. There is no "close enough." A kernel special case that is **observable through the differential** (e.g. the Feb-28 leap-year time-clearing in `AddYears`/`AddMonths`, the scale-19 compare-rescaling, the `MathContext(50)` arithmetic cap) is a **must-match**, never droppable as "obsolete." The "kernel is old — report German-only/obsolete/feature-flagged special cases for review" guidance is **narrow**: only things that are *not observable runtime behavior* are reportable-and-droppable — German message *text* (we use our own, IF3), a dead/feature-flagged code path that never executes, pure editor/rendering cruft. If a behavior changes any differential outcome, match it exactly; only genuinely unreachable/irrelevant cruft is reported for a drop decision.

**"The real kernel" means BOTH of its evaluation strategies — the md-RUNTIME dynamic service (`IDocumentRtService`) AND the Groovy CODE GENERATOR — and the interpreter must match BOTH (clarified 2026-06-27).** Compatibility is NOT "match the differential oracle"; the differential oracle (`RuntimeLaws`/`KernelAdapter`, both the runtime dynamic service) is the *primary verification surface*, but it only proves **runtime**-parity. **Codegen-parity is a co-equal target** that the runtime oracle CANNOT verify — so where a behavior lives in codegen, confirm it from the **codegen source** (`kernel-core-codegen-*`) and lock it against codegen-derived expectations. The two strategies can DIVERGE (a kernel fact to characterize, not ignore): if they differ on a legal input, the interpreter matches the **production codegen** behavior, and the runtime-only differential must explicitly carve out the divergent code (it cannot gate it). The **one place a behavior is legitimately droppable is when it is DEAD in *both* strategies** — generated by neither the runtime autogen service nor the codegen (proven from source, not assumed). Worked precedent (2026-06-27): the multi-select value-uniqueness `FEHLER_MULTI_SELECT`/`uniqueValue` is dead in 30.8.1 — `AutogeneratedRulesService` has no multi-select method (runtime) AND no `IAutogeneratedRule.getGenerationType()` returns `UNIQUE_VALUE`, so `CodeGenRuleDefinition`'s `case UNIQUE_VALUE` is unreachable (codegen) — so the interpreter does NOT fire it, matching both (KERNEL-FINDINGS "multi-select value uniqueness is DEAD code"; the sibling of the dead `mandatoryGroup`).

**(B) Clean-room reimplementation, NEVER kernel delegation (the license boundary).** Reimplement the kernel's semantics; do not delegate to the kernel, and do not transliterate its source. The reason is **licensing, not preference**: the A12 kernel is **EUPL-1.2** (copyleft) / commercial. A runtime that *uses* the kernel (links/ships/calls it) is a combined work the EUPL copyleft reaches — so it would have to be EUPL (or commercial). The whole point of `:interpreter` is to give dmtool's **native runtime a kernel-FREE engine**, so that runtime carries **no kernel code and is free of the EUPL** (and the kernel's Groovy codegen can't go native anyway — delegation fails the native goal too).

A and B together: *read the kernel source to learn the exact behavior → write original Kotlin that reproduces it exactly → lock it with the differential.* Therefore:

- **Never delegate** operator evaluation to the kernel from the interpreter (no `com.mgmtp.*` call, no JS-kernel binding) — the purity lint enforces the no-link half.
- **Derive each operator from BEHAVIOR, clean-room** — the **differential oracle** (the real kernel as a *black box*: feed inputs, observe outputs) + the public BA/KERNEL-SEMANTICS spec. **Do NOT copy/transliterate the kernel's source expression** (e.g. don't port `BedingungsOperatorHelper`), because a line-by-line port can be a copyright **derivative** that re-attracts the EUPL. Copy the *mechanism/behavior* (not protected), never the *expression* — the standing license-safe rule. **Reading the kernel source is encouraged for *understanding*, not only to audit a divergence** — proactively scan the **operator sources *and* the code-generator sources** to learn an operator's real semantics and surface *surprising special cases* you'd never think to probe blind (e.g. `Now` truncation-to-day, datetime day-rollover, the `Date(...)`/`Time(...)` digit-pattern operand rules). Then the loop is *read source → write original Kotlin → verify against the differential*; the *fix* is never a transliteration.
- The `--kernel` flag (JVM-only, refused in native) is the *only* place dmtool touches the kernel; that JVM distribution is where EUPL/commercial applies. The native/JS runtime stays clean.

**Separation is kept by convention + linting, not a repo wall** — the §7 hygiene rules are mechanically enforced, so don't hand-wave them:

- `:interpreter` carries **no kernel/dmtool dependency** (it is the publishable standalone artifact). The kernel **differential tests stay in `:adapter`** (never in `:interpreter`'s test source), so the module is kernel-free even in test scope.
- The **purity lint** (`:interpreter`'s `verifyInterpreterPurity`, wired into `check`) fails the build on a forbidden import: `commonMain` may not import `java.*`/`com.mgmtp.*`/`groovy.*`; `jvmMain`/`jsMain` may not import `com.mgmtp.*`/`groovy.*`. Run it as part of any `:interpreter` change.
- `:interpreter` never depends on `:`/`:adapter`/`:cli` — they consume it, never the reverse.

Extraction to a sibling repo is a **future option, not a prerequisite** — do it only if the interpreter earns an independent OSS life/release cadence (§8); the lint keeps that a lift, not a rewrite. ## Performance — benchmark on REAL documents, measure against the kernel, invest heavily in groups (standing requirement, decided 2026-06-23)

The interpreter must be **performant on the hard cases**, and performance is **gated, not hoped for**. Three non-negotiables:

- **REAL documents only — benchmarking a shortcut data structure is cheating.** Measure over the production evaluation path: the general `Document` (and the kernel's `IDocument`) built from real DM-JSON models. The spike's `Map`-backed `RepDoc` (O(1) lookups) must **never** be the thing benchmarked — its numbers are a fiction that hides the real complexity. A benchmark that doesn't exercise the real group resolution (parallel index, common-prefix, star) is not a benchmark.
- **Measure AGAINST the kernel, as a regression gate.** The perf benchmark is the twin of the correctness differential and lives in `:adapter` (which has the kernel): for each scenario run BOTH `kernel.validateFull` and `DmInterpreter.validateFull` over the same real instance, record both wall-clocks + the ratio, assert correctness (interp == kernel) AND a time/ratio bound that trips on an O(N²)-class regression.
- **Target the non-obvious group machinery, at scale.** Deeply **nested repeatable groups** (3–4 levels), **parallel iteration** / cross-level (common-prefix) references, **starred aggregates** over large repetition lists, and **many rows (up to 100 000)** — not the flat/obvious cases. "Invest heavily in all things groups": this is where a naive impl is O(N²) and where it matters. Prerequisite: the general `Document`'s O(P) linear-scan lookups must be indexed to O(1)/O(log) first, or 100k rows can't even run.
- **Run on the PURE engine, decoupled from the CLI — cheap to run, very often.** Both the correctness differentials and the perf harness hit the **`DmInterpreter` + `Document` API directly** (kernel via `RuntimeLaws`), never through `dmtool`/`InterpreterEngine`/the loader — no process spawn, no `installDist`, no JSON envelope. A "real document" is the real `Document` *structure* built programmatically in-test, not loaded through the CLI. **Invest heavily in a proper, reusable harness** (scenario abstraction, warmup+repeats+median, ratio-vs-kernel, profile mode) — it gates regressions *and* finds the hotspots.

Method, harness design, benchmark catalog, and the regression-gate mechanics live in [`../docs/INTERPRETER-PERFORMANCE.md`](../docs/INTERPRETER-PERFORMANCE.md).

## Structure for a future GENERATOR — separate runtime semantics from evaluation strategy (standing requirement, decided 2026-06-23)

We build the **interpreter** now, but must stay flexible to later add a **generator** (the kernel's approach: emit code per model instead of tree-walking). **Both an interpreter and a generator are evaluation *strategies* that delegate to the SAME runtime** — the operator implementations. So **don't implement the generator, but keep the layering ready for it**:

- **Layer the engine as: data-access → runtime operator semantics → strategy.** (1) **Data access** = `EvalContext`/`Document` (`field`/`filled`/`signed`/`star`/`reps`). (2) **Runtime operator semantics** = pure, AST-walk-agnostic functions over *resolved* values (`Val`/`Tri`/`Fill`): 3VL `and`/`or`, directional number compare, `quantifierFires`, the date/time math (`DateMath`), aggregates, value-list, pattern. (3) **Strategy** = the interpreter's tree-walk *today*; a generator that emits code *later* — both consume (1)+(2). This mirrors the kernel exactly: its codegen emits Groovy that calls `BedingungsOperatorHelper`/`ValidierungsErgebnis`/`Combiner` (the runtime).
- **The rule that keeps it ready:** operator semantics must **not** be inlined into the tree-walk or depend on "I am walking an AST" — they live in the shared runtime layer as pure functions a generated program could call just as the interpreter does. `DateMath` and the `PredicateOp`/`FunctionOp` registries already are; the comparison/3VL/aggregate logic in `Interpreter` should migrate there as it's touched. When adding an operator, put its *semantics* in the runtime layer, and let the strategy only **dispatch + resolve operands**.
- Detail + the target layer diagram: [`../docs/INTERPRETER-FINDINGS.md`](../docs/INTERPRETER-FINDINGS.md) IF10. The extraction of today's inlined semantics is a tracked refactor, not a prerequisite for more operators.
